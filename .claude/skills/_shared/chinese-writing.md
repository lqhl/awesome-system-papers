# 中文写作与术语解释契约

本契约适用于 skill 生成或改写的所有中文叙述，包括正文、标题、表头、表格单元格、摘要、对话答案和 log 条目。默认读者具备一般技术背景，但不假设熟悉当前子领域。

用户、AGENTS.md 或具体 skill 的更严格规则优先；不得用本契约改写原始论文标题、系统名、文件名或代码标识。

## 术语决策

写作前列出会反复出现的领域术语，为每个术语选定全篇唯一的表达。来源页或原文即使中英混杂，也不能原样复制进综合文本。

1. **有成熟中文译法**：首次写成「中文术语（English）」，随后只用中文。例如「验证器（verifier）」、「工作负载（workload）」、「基线（baseline）」。
2. **英文缩写**：首次同时给出中文含义、英文全称和缩写，例如「样本外（out-of-sample，OOS）」。后文才可只用缩写。
3. **系统名、模型名、基准名、API、指标、变量和代码标识**：保留准确拼写，但在首次语义性出现时用中文说明它的角色或指标含义。
4. **没有自然中文译法**：保留英文，首次用一句通顺中文解释它是什么、为什么在当前语境中重要。
5. **中文专业术语**：对非本领域读者不自明的概念，首次还要说明它衡量什么、解决什么问题或如何影响结论，不能只补一个英文括号。

「首次」指整个产物的首次语义性出现，不在每个章节重复定义。对长篇、跨领域且有超过 5 种重复术语的产物，优先在第一张大表或深入分析前增加简短的「阅读提示」；短答案、单篇论文页和单行摘要可以在正文中行内解释。

## 可读性

- 普通叙述用中文完成语法关系。不写「中文连接词 + 连续英文名词」，不在普通句子中用 `/`、`+`、`→` 串起可直接翻译的概念。显式流程图可使用箭头，但节点叙述仍以中文为主。
- 每段主要说明一个判断：观察为什么成立、设计如何回应、证据覆盖到哪里。不把英文关键词列表当作解释。
- 描述性 H1、章节和普通表头以中文为主。表格单元格也是正文，不因为它们短就豁免术语解释。
- 同一概念全篇使用同一种中文表达。引用来源中的不同英文变体时，优先在术语表中归一，而不是在正文中轮换使用。
- 将论文直接证据、综合推断和尚未验证的建议分开写，不用英文术语密度营造专业感。

## 不翻译的内容

- frontmatter key、枚举值、英文 tags、文件名、wikilink target 和 URL。
- 论文英文原题、正式系统名、模型名、组件名、API 和代码片段。
- 公式中的变量、单位和通用指标缩写；但缩写在正文首次出现时仍需解释。
- 标准 Markdown 外链的链接文字可保留论文或产品原名。

## 成稿语义审计

在写入文件、发出答案或记录 log 前，完成以下检查：

1. 扫描 frontmatter、代码、公式、URL、wikilink target 和英文原题之外的拉丁字母词。
2. 对每个保留词回答：它是否属于不翻译范围？若是，首次是否已用中文解释？若否，立即翻译或改写。
3. 检查英文串词、斜线并列、英文普通概念标题、表头和表格单元格。
4. 检查中文专业术语是否只有名称、没有通俗定义。
5. 对写入 wiki 的文件再运行定向 `wiki-lint --language-only`。该检查只能发现确定性问题；`language_warnings=0` 不能替代前四步。

语义审计是生成 skill 的完成门槛，不是可选的二次润色。

## 正反例

- 反例：「agent-native quant research system 从 hypothesis、point-in-time data、factor/model code 到 paper/live gate 都有 artifact」。
- 改写：「面向智能体的量化研究系统（agent-native quant research system）将研究假设、历史时点可见数据、因子或模型代码、模拟与实盘发布组织为可审计的研究产物。」
- 反例：表格单元格只写「event sourcing + immutable components + replay」。
- 改写：「使用事件溯源（event sourcing，通过按顺序保存事件恢复状态）、不可变组件和事件重放。」
- 反例：首次出现直接写「OOS 收益」。
- 改写：「样本外（out-of-sample，OOS）收益，即在未参与训练或调参的数据上测得的收益。」
