# µEFI: A Microkernel-Style UEFI with Isolation and Transparency

**作者**：Le Chen, Yiyang Wu, Jinyu Gu, Yubin Xia, Haibo Chen（上海交通大学 并行与分布式系统研究所）
**会议**：USENIX ATC 2025
**链接**：https://www.usenix.org/conference/atc25/presentation/chen-le
**源文件**：[[atc2025-chen-le.pdf]]

---

## 一、背景

UEFI（Unified Extensible Firmware Interface）已取代传统 BIOS，成为现代设备（服务器、PC、移动设备）的标准固件接口，负责硬件初始化、系统引导和安全保障。UEFI Secure Boot 是其核心安全特性，通过签名验证确保只有受信任的模块能在启动过程中加载执行。

然而，UEFI 生态系统正面临严峻的安全挑战。UEFI Forum 成员已从 2013 年的 236 家增长到 2025 年的 365 家，EDK2 代码量在 2018–2025 年间扩大了 9 倍（主要受 ARM 架构推动）。随着代码规模膨胀和模块数量激增，UEFI 相关 CVE 持续增长——2022 年达到 72 个，2023 年 73 个，2024 年 45 个中有 24 个为高危。BlackLotus、LoJax、CosmicStrand 等真实 bootkit 攻击已证明 Secure Boot 的局限性。

---

## 二、要解决的问题

1. **Secure Boot 无法防御已签名模块中的漏洞**：合法签名的 DXE 驱动可能包含栈溢出、堆溢出等内存安全问题，攻击者可利用这些漏洞绕过 Secure Boot 或实现任意代码执行。CVE 分析显示，内存安全问题占高危 CVE 的 31.4%，输入验证不当占所有 CVE 的 30.8%。

2. **缺乏模块间隔离**：所有 UEFI 模块共享同一地址空间，以最高权限运行（x86 上的 SMM 或 ARM 上的 EL1）。一个模块的漏洞可波及整个固件。

3. **粗粒度访问控制**：服务和协议接口全局可访问，任何模块都能修改服务表、安装或获取任意协议，缺乏最小权限约束。

4. **供应链复杂性**：OEM、IHV、芯片厂商、BIOS 供应商层层叠加，上游缺陷会传播到所有下游设备。

---

## 三、洞察与设计

**关键洞察**：

1. **唯一调用出口（Unique Callout Gate）**：UEFI 中所有模块对外调用（服务调用和协议接口调用）都必须经过 System Table 这一中心数据结构——服务通过固定指针直接获取，协议接口通过 LocateProtocol 等服务间接获取。这意味着控制了 System Table 就控制了模块的所有对外交互。

2. **标准化协议（Standardized Protocols）**：UEFI 协议是预定义的、接口契约明确的，开发者只需依赖接口定义而无需了解底层实现。因此可以通过离线分析协议定义提取类型和结构信息，在运行时实现安全的跨模块数据传输。

基于这两个洞察，µEFI 采用微内核架构，将 UEFI 模块降权到用户态并隔离在独立地址空间（沙箱）中运行：

- **Shadow Service**：替换每个沙箱模块的 System Table 为独立副本，将核心服务调用重定向为系统调用，并实施 seccomp 风格的两级访问控制（服务级 + 协议级）。
- **Trampoline Injection**：当沙箱模块获取协议接口时，动态生成 trampoline 代码注入沙箱，将协议函数调用透明地转换为 IPC，无需修改模块代码。三种 trampoline 分别处理：跨沙箱调用、Core 调用沙箱模块、函数返回。
- **Interface Proxy**：结合离线协议分析和运行时参数验证，自动处理跨模块数据传输和输入合法性检查。

## 四、实现细节

**离线分析器**：
- 基于 LLVM/LibClang（C++，907 LOC），解析 EDK2 MdePkg 中的协议头文件
- 提取协议定义中的函数签名、参数类型、数据结构，生成 JSON 格式的协议数据库（< 20,000 行）
- 使用 Parameter Pairing 启发式方法关联 Buffer 和 BufferSize 等参数对：先检查命名模式（如 Buffer/BufferLength），再借助 LLM 分析函数注释
- 对 void* 类型参数无法明确分类为 handle/buffer/array 的情况（< 2.5%），需要人工处理

**Sandbox Manager**：
- 作为 UEFI 模块实现（C 4,773 SLOC + 汇编 253 SLOC），与 Core 同权限级运行
- 对 Core 的修改 < 100 SLOC
- 协议数据库采用 lazy loading：初始化时只解析协议表，函数和类型信息按需加载
- 跨模块内存管理：使用层级绑定追踪 callee 为 caller 分配的内存，支持级联释放

**平台支持**：
- x86_64：基于 QEMU/KVM，Core 在 Ring 0，沙箱模块在 Ring 3
- AArch64：Raspberry Pi 4，Core 在 EL1，沙箱模块在 EL0
- 基于 edk2-stable202402 版本

## 五、实验结果

**安全评估**：

| 攻击/CVE | 攻击类型 | µEFI 防御效果 |
|---|---|---|
| CVE-2021-39297 | 栈溢出（HP 笔记本） | 临时栈 + 返回 trampoline 阻止跨模块代码注入 |
| CVE-2022-1890/1891/1892 | 堆溢出 | 沙箱独立堆管理，溢出影响限于本模块 |
| ThunderStrike | Option ROM 注入 | 沙箱隔离阻止修改 DXE 服务表 |
| BootHole | GRUB2 缓冲区溢出 | 内存隔离阻止跨模块覆写 |
| BlackLotus | Secure Boot 绕过 + 函数 hook | 沙箱阻止向其他模块插入恶意 hook |

**启动性能**：

| 沙箱模块数量 | 启动开销 |
|---|---|
| 0（仅加载 Sandbox Manager） | 0.91% |
| 1–6 个模块 | 每模块平均 0.17%，总计 1.91% |

**模块执行性能（FAT + DiskIo end-to-end 测试）**：

| 平台 | 仅 FAT 沙箱化 | FAT + DiskIo 沙箱化 |
|---|---|---|
| x86_64 (QEMU/KVM) | 平均 0.35% | 平均 0.78% |
| AArch64 (RPi4) | 平均 3.85% | 平均 4.11% |

**开销分解（x86_64，跨沙箱调用）**：
- 上下文切换：平均 1,126 cycles
- 数据库查询：平均 55 cycles（缓存后）
- 参数复制/同步：视参数复杂度，数百到数千 cycles

**离线分析覆盖率**：
- 协议字段：仅 2 个需人工处理
- 复合类型字段：失败率 0.26%
- 函数参数：17.4% 为特殊指针类型，失败率 2.5%

**内存开销**：每个沙箱约 25–40 KB 额外内存（含页表、堆元数据、Shadow System Table、trampoline 等），对现代 4GB+ 固件环境可忽略。

## 六、批判性分析

1. **TCB 假设过于乐观**：µEFI 假设 UEFI Core（DXE Core）和之前的 SEC/PEI 阶段无漏洞，但论文自身 CVE 数据表明 Core 也存在漏洞。将整个 Core 加上 Sandbox Manager（~5000 SLOC）纳入 TCB，这个 TCB 并不小。

2. **实验平台代表性不足**：x86 测试在 QEMU/KVM 虚拟机中进行而非裸金属硬件，虚拟化环境下的上下文切换开销可能与真实固件环境有显著差异。缺少在真实 OEM 固件上的端到端测试。

3. **仅测试了 6 个模块，且多数较简单**：论文提到 EDK2 代码量增长 9 倍、数百个模块，但实验只隔离了 6 个模块。对于 GPU Option ROM、SmartNIC 固件等大型复杂模块的兼容性和性能影响未做验证。

4. **Parameter Pairing 的 LLM 依赖未充分评估**：离线分析器使用 LLM 分析函数注释来建立参数关联，但未报告 LLM 的准确率、假阳性/假阴性率。对于 void* 参数有 2.5% 的失败率，这些失败恰好集中在安全最敏感的场景（如网络模块解析数据包）。

5. **Mock 测试掩盖了真实开销**：排除 I/O 的 Mock-DiskIo 测试显示开销从 ~5,000 cycles 增长到 ~31,000 cycles（约 5.5x），这才是 µEFI 隔离机制的真实计算开销。论文强调的"1.91% 启动开销"很大程度上是因为 I/O 延迟远大于隔离开销，从而稀释了百分比。

6. **协议级访问控制的启发式检测存在安全漏洞**：当无法通过显式声明确定模块类型时，系统通过首个非通用协议推断模块类型。如果恶意模块先安装一个看似无害的协议，再访问敏感协议，这种 fail-stop 模型可能被绕过。

7. **特权指令模拟的开销和兼容性未量化**：论文仅简单提及"参考已有方法 trap-and-emulate 特权指令"，但未给出具体涉及哪些指令、模拟频率和性能影响。

---

## 七、总结

µEFI 首次将微内核架构引入 UEFI 固件安全，通过将模块降权到用户态并隔离在独立沙箱中，有效增强了固件的模块间隔离和访问控制。其核心技术——利用 System Table 作为唯一调用出口的 trampoline injection 和基于标准化协议的离线分析——巧妙解决了二进制兼容性和透明数据传输的难题。在 x86 和 ARM 平台上仅引入约 2–4% 的启动开销。主要局限在于 TCB 仍然较大、实验覆盖的模块数量和平台有限、以及对复杂实际固件场景的验证不足。该工作为 UEFI 固件安全提供了一条有前景的增量防御路径，适用于对固件安全有较高要求但无法全面重写固件的场景。
