# BIN2WRONG: a Unified Fuzzing Framework for Uncovering Semantic Errors in Binary-to-C Decompilers

**作者**：Zao Yang, Stefan Nagy (University of Utah)
**会议**：USENIX ATC 2025
**链接**：https://www.usenix.org/conference/atc25/presentation/yang-zao
**源文件**：[[atc2025-yang-zao.pdf]]

---

## 一、背景

二进制反编译（Binary Decompilation）是将可执行文件翻译回 C 源代码的过程，是调试、性能调优、恶意软件分析、安全加固等系统任务的核心支撑。主流反编译器包括 BinaryNinja、Angr、Ghidra、RetDec 等。然而，编译过程是有损的——类型信息、变量名、高层程序结构在编译后被剥离，加上不同的编译器（GCC、Clang、MSVC 等）、优化级别、可执行文件格式（ELF、PE、Mach-O）带来巨大的二进制多样性，反编译器经常产生语义错误的代码。

反编译的四个主要步骤——控制流恢复、控制流分析、数据流分析、代码生成——每一步都涉及不可判定问题，错误会向下游级联传播。即使是微小的错误（如分支条件恢复错误）也会导致控制流完全偏离原始程序语义。

---

## 二、要解决的问题

现有的反编译器测试方法（DecFuzzer、Cornucopia、D-Helix、DSmith）存在三大局限：

1. **源代码构造覆盖不足**：DecFuzzer 和 DSmith 不支持 switch-case 语句；多数工具不支持浮点字面量和字符串字面量，无法触发与这些构造相关的反编译缺陷。

2. **编译参数探索受限**：现有工具最多支持 2 个编译器（仅 GCC 和/或 Clang），且硬编码编译参数。DecFuzzer 完全忽略编译优化；所有工具仅支持 Linux ELF 格式，完全忽略 PE（Windows）和 Mach-O（macOS）二进制。然而，大量反编译 bug 恰恰源于特定编译器、优化或格式的组合。

3. **反编译器支持范围窄**：D-Helix 需要对每个反编译器的内部 IR 进行逐指令语义建模，每支持一个新反编译器需约 40 天人工开发；且目前仅支持 Ghidra 和 Angr 两个开源反编译器，无法覆盖 BinaryNinja 等商业工具。

## 三、洞察与设计

**关键洞察**：影响二进制代码的四个维度——源代码、编译器、优化选项、可执行文件格式——对反编译器缺陷的触发具有同等重要性，且它们的组合会产生单一维度变异无法暴露的复杂多维错误。将这四个维度统一为一个可变异的测试用例结构，比分别独立探索更能最大化二进制多样性和 bug 发现率。

基于此洞察，BIN2WRONG 设计了一套统一的 fuzzing 框架：

### 统一测试用例结构

将源代码和编译参数编码为单一测试用例：
- **前 2048 字节**编码编译参数：byte 0 选择 6 个编译器之一（GCC、Clang、TCC、ICX、MSVC、AppleClang），bytes 1-2047 映射到对应编译器的优化标志（奇/偶数控制启用/禁用），总计覆盖 5,183 个优化选项
- **后续部分**为源代码，通过 AST 级别变异生成多样化的 C 程序

### 编译变异

通过 AFL++ 自定义 mutator 实现编译参数的随机变异。利用 WINE（运行 MSVC）和 Darling（运行 AppleClang）实现跨平台支持，使 BIN2WRONG 成为首个同时覆盖 ELF、PE、Mach-O 三种格式的反编译器 fuzzer。

### 源代码变异

基于 LLVM libClang 的 AST API 实现三类 mutator：
- **表达式级**：删除/复制表达式、替换子表达式、随机替换算术/位运算操作符
- **控制结构级**：在循环中插入条件 break/continue、替换 if 条件为常真/常假、替换 goto 目标、替换 switch 表达式
- **数据级**：替换字符串/数值字面量、翻转数值符号/字节、替换类型转换

### 反编译器无关的语义测试

采用差分测试：将原始程序和反编译后重编译的程序分别执行，比较全局变量的 checksum。这种方法只依赖反编译器输出的 C 代码，不需要深入反编译器内部 IR，因此天然支持所有 C 反编译器（包括闭源商业工具）。为提高重编译成功率，实施了轻量级语法修补策略（处理类型不匹配、符号重命名、自定义类型宏注入等），将重编译率从 11.60% 提升到 47.8%。

## 四、实现细节

- 基于 **AFL++ v4.09c** 构建，利用其自定义 mutator API
- 对支持 QEMU 覆盖追踪的 5 个反编译器使用 grey-box 模式，对 Angr 和 Relyze 使用 black-box 模式
- 编译器优化映射：GCC 1,029 个选项、Clang 1,378 个、TCC 7 个、ICX 1,174 个、MSVC 217 个、AppleClang 1,378 个
- 当编译器切换时自动重映射优化字节；不兼容的优化组合自动回退到标准优化级别（如 -O1 到 -O3）
- 源代码 mutator 设计上避免注入/删除/移动变量声明以防止运行时崩溃；在 AST 节点级别添加安全约束（如 break/continue 只在循环体内）
- 种子程序使用 Csmith 生成的 10 个 C 程序，手动增加字符串字面量支持
- Bug 分析流程：每个触发 divergence 的测试用例手动最小化（约 10 分钟/个），然后去重为唯一 bug 并上报开发者

## 五、实验结果

**实验环境**：Ubuntu 22.04，Intel Core i9-12900K，64GB RAM。对比 Cornucopia 和 DecFuzzer，测试 7 个反编译器，每组实验 5 次重复，24 小时 campaign。

### 二进制多样性

| 对比基线 | BinDiff 相对提升 | Radiff2-M 提升 | Radiff2-L 提升 |
|---|---|---|---|
| vs Cornucopia | 10.39× | 9.12× | 7.13× |
| vs DecFuzzer | 17.19× | 16.94× | 16.09× |

全维度（源码+编译器+优化）联合变异产生最高二进制多样性。

### 反编译器代码覆盖

| 指标 | vs Cornucopia | vs DecFuzzer |
|---|---|---|
| 平均代码覆盖提升 | 1.16× | 1.32× |
| 覆盖增益二进制比例提升 | 3.56× | 59.61× |

76.34% 的覆盖增益二进制来自全维度联合变异。

### Bug 发现

| 反编译器 | BIN2WRONG (发现/确认/独有) | Cornucopia | DecFuzzer |
|---|---|---|---|
| Angr | 9/9/8 | 2/2/1 | 0/0/0 |
| BinaryNinja | 11/11/11 | 0/0/0 | 0/0/0 |
| Reko | 6/6/4 | 3/2/1 | 0/0/0 |
| R2Ghidra | 2/2/1 | 1/1/0 | 0/0/0 |
| Relyze | 7/N·A/6 | 2/N·A/1 | 0/0/0 |
| RetDec | 11/N·A/10 | 2/N·A/1 | 0/0/0 |
| Rev.Ng | 2/2/2 | 0/0/0 | 0/0/0 |
| **合计** | **48/30/42** | **10/5/4** | **0/0/0** |

### Bug 分类

- **数据恢复类**（68.75%）：浮点类型误识别为整数、字符串字面量丢失、函数参数遗漏等
- **表达式恢复类**（20.83%）：算术运算符误恢复、常量传播错误
- **控制结构类**（10.42%）：switch-case 重构错误、循环条件反转

### 关键影响

BIN2WRONG 发现的一个 High Severity bug（switch-case 恢复错误，Figure 4）直接促成了商业反编译器 **BinaryNinja 核心控制流重构技术的全面重写**。

## 六、批判性分析

1. **重编译率仅 47.8%**：超过一半的反编译输出无法重编译，意味着大量潜在的语义错误无法被检测。论文将此归因于语法错误难以自动修复，但这本质上限制了 bug 发现的上界。与 D-Helix 的 45% 重编译率持平并不是一个有说服力的辩护——两者都不理想。

2. **覆盖率提升与 bug 数量的关系**：论文自己承认 bug 发现更多与二进制多样性（10-17×提升）相关，而非代码覆盖（仅 1.16-1.32×提升）。但对此缺乏深入分析——为什么高多样性但低覆盖增量就能找到更多 bug？这暗示现有反编译器的 bug 密度极高，任何新输入形态都可能触发错误，而非 BIN2WRONG 的变异策略本身有多精妙。

3. **手动 bug 分析流程**：每个 bug 需 10 分钟手动最小化，且完全依赖开发者进行 fault localization。论文测试了 48 个 bug，人工成本可控，但这意味着该方法难以扩展——如果一次 campaign 产生成百上千个 divergence，人工分析将成为瓶颈。

4. **DecFuzzer 零 bug 的对比公平性**：DecFuzzer 使用 GCC -O0 单一配置，这本身就是该工具最保守的设定。更公平的对比应当让 DecFuzzer 也使用多编译器配置（手动添加），以隔离 BIN2WRONG 的变异策略贡献和编译参数扩展贡献。

5. **源代码变异的有效性未被单独验证**：论文的 ablation study（Table 3, Table 5）显示仅变异源代码（ONLY SRC）的二进制多样性远低于仅变异编译器（ONLY COM），且 ONLY SRC 几乎不产生覆盖增益二进制（0.00%）。这引发一个问题：BIN2WRONG 的主要贡献究竟来自源代码变异还是编译参数变异？数据暗示是后者，但论文并未诚实讨论这一点。

6. **缺少真实场景评估**：所有测试用例均为 Csmith 生成的合成程序。论文未展示 BIN2WRONG 在真实世界二进制上的表现——合成程序中发现的 bug 是否真的影响实际逆向工程工作流？

---

## 七、总结

BIN2WRONG 提出了首个统一反编译器 fuzzing 框架，将源代码、编译器、优化选项和可执行文件格式四个维度编码为单一可变异测试用例，基于 AFL++ 实现系统化的反编译器语义错误发现。在 7 个主流反编译器上的评估中，BIN2WRONG 实现了 10-17× 的二进制多样性提升和 1.16-1.32× 的代码覆盖提升，发现 48 个语义 bug（30 个已确认），远超对比方法。其中一个 bug 直接推动了 BinaryNinja 核心模块的重写。主要局限在于重编译率较低（47.8%）、依赖手动 bug 分析、且仅在合成程序上验证，缺乏真实场景评估。
