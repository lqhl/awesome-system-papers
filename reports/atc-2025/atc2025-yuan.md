# Internet Connection Splitting: What's Old is New Again

**作者**：Gina Yuan, Thea Rossman, Keith Winstein (Stanford University)
**会议**：USENIX ATC 2025
**链接**：https://www.usenix.org/conference/atc25/presentation/yuan
**源文件**：[[atc2025-yuan.pdf]]

---

## 一、背景

在 1990 年代，许多网络运营商部署了性能增强代理（Performance-Enhancing Proxies, PEPs），通过透明地将 TCP 连接拆分为两段来提升性能，尤其是在高延迟、高丢包的路径上。PEP 提供了中间确认点和重传功能，缩短了拥塞反馈环路，使每段连接可以针对本地网络条件独立优化拥塞控制。PEPs 被广泛部署在卫星、蜂窝和 Wi-Fi 网络中。

然而，两项近年发展对 PEPs 的价值提出了质疑：(1) BBR 拥塞控制算法（2016 年发布）是一种"基于模型"的方案，不以丢包作为主要拥塞信号，因此理论上减少了拆分连接带来的好处；(2) QUIC 传输协议（2021 年标准化）采用端到端加密，使透明的连接拆分在技术上不可行——但 QUIC 在大规模部署中并未出现显著的性能下降。

---

## 二、要解决的问题

核心问题是：**BBR 和 QUIC 是否已经让连接拆分过时了？**

具体而言：
1. BBR 不依赖丢包信号，理论上拆分连接的收益应该大幅降低，但 BBR 已从 v1 演进到 v3，其行为是否仍如此？
2. QUIC 无法被透明拆分，但其在丢包路径上的性能是否真的不需要 PEP 的辅助？
3. 不同 QUIC 实现中"相同"拥塞控制算法的行为是否一致？如果不一致，对拆分行为的评估有何影响？

---

## 三、洞察与设计

**关键洞察**：BBR 算法为了与 CUBIC 等"基于丢包"的方案公平共存，在从 v1 演进到 v2/v3 的过程中大幅增加了对丢包的敏感性，导致其端到端吞吐量在丢包场景下显著退化——这使得 BBR 重新变得像传统的基于丢包的 CCA 一样，能够从连接拆分中获益。

基于这一洞察，作者设计了一套 **Split Throughput Heuristic**（拆分吞吐量启发式方法）来系统性地分析连接拆分的效果：

1. **网络模型抽象**：用 (delay, bandwidth, loss) 三元组建模每个路径段，并定义 `compose()` 函数将两段组合为端到端路径（带宽取最小值、延迟求和、丢包独立叠加）
2. **核心启发式**：拆分连接的吞吐量可以近似为两段路径各自端到端吞吐量的最小值。这样只需测量端到端参数空间的吞吐量，就能推断拆分后的吞吐量
3. **参数空间搜索**：在 5 种带宽 × 6 种延迟 × 5 种丢包率 = 150 种网络设置上缓存端到端仿真结果，再对 7875 种路径组合进行穷举搜索

该启发式方法的关键优势是可以间接评估 QUIC 等加密协议的拆分收益——无需实际构建 QUIC 的连接拆分器，只需知道其端到端吞吐量即可。

---

## 四、实现细节

- **仿真平台**：使用 mininet 构建单段和双段网络拓扑，CloudLab x86_64 rs630 节点运行 Ubuntu 22.04.2
- **网络配置**：tc-netem 设置延迟和随机丢包，tc-htb 设置带宽，使用 RED 队列管理（adaptive hard drop 模式，最大队列延迟约 1 BDP）
- **TCP 端点**：Python http 模块封装 HTTPS；CCA 通过加载 Linux 内核模块实现，BBRv3 使用 Google 的 v6.4.0 内核分支
- **QUIC 实现**：评估了三个开源实现——Google quiche (Chromium)、Cloudflare quiche、picoquic (IETF)
- **TCP PEP**：使用 PEPsal 工具进行透明连接拆分，拦截 SYN 包并建立两个独立的 TCP 连接
- **实验规格**：每次实验传输约 10 秒的数据量，报告单流 goodput（应用层字节/请求完成时间），每组实验重复 20 次取中位数
- **代码开源**：https://github.com/StanfordSNR/connection-splitting

## 五、实验结果

### Finding 1：BBR 的拆分收益随版本演进显著增加

| CCA | 对丢包的敏感性 | 拆分收益 |
|-----|--------------|---------|
| CUBIC | 高（丢包率 1% + 延迟 20ms 时利用率降至 ~14%） | 在 Class I 场景下显著受益 |
| BBRv1 | 极低（几乎所有设置下利用率 >75%） | 几乎无收益 |
| BBRv2 | 中等（比 v1 显著增加丢包敏感性） | 显著受益 |
| BBRv3 | 中等（与 v2 相似，略有调优） | 显著受益，且在更多场景中受益 |

### Finding 2：BBRv3 在新的网络类别中受益于拆分

| 网络类别 | 描述 | CUBIC 受益 | BBRv3 受益 |
|---------|------|-----------|-----------|
| Class I | 非对称延迟 + 丢包 last-mile（如 Wi-Fi/蜂窝） | 是（942 场景） | 是（38 场景） |
| Class II | 非对称延迟 + 两段均有丢包 | 否 | 是（72 场景） |
| Class III | 对称延迟 + 两段均有丢包（如卫星网络） | 否 | 是（78 场景） |

穷举搜索中，满足拆分改善 >3× 且拆分利用率 >0.5 的场景：BBRv1 为 0，CUBIC 为 942，BBRv3 为 188。

### Finding 3：QUIC 实现间差异巨大

- Google quiche 与 Linux TCP 行为最接近
- Cloudflare quiche 的 BBR 实现性能显著低于 Linux TCP（高延迟时利用率仅 ~50%）
- picoquic 的 BBRv3 对延迟的反应与 Linux TCP 相反
- 不同 CUBIC 的 QUIC 实现（Cloudflare、picoquic）对丢包的敏感性低于 TCP，可能在更多类别的网络中受益于拆分

### 启发式准确性

端到端吞吐量预测误差几乎为零；拆分吞吐量预测略偏高，最大误差 ±14%，平均 ±4%。

## 六、批判性分析

1. **仅评估单流长连接吞吐量**：论文只关注单流稳态吞吐量，忽略了启动时间、包抖动、重传开销、短连接等 PEP 同样会影响的指标。在实际部署中，Web 流量以短连接为主，单流长连接的收益可能不代表实际用户体验的改善。

2. **仿真与真实世界的差距未被充分讨论**：使用 mininet + 固定参数的简化网络模型，不含带宽波动（蜂窝网络特征）、ACK 聚合、多流竞争等真实因素。论文承认了这些局限但未尝试量化其影响。

3. **QUIC 拆分行为完全基于推测**：对 QUIC 的所有拆分分析都基于启发式估计，没有实际的 QUIC 连接拆分器验证。虽然启发式在 TCP 上的准确性尚可，但能否外推到 QUIC（涉及不同的传输机制如 0-RTT、流多路复用）缺乏实证。

4. **参数空间有限且人工选择**：带宽范围 10-50 Mbit/s、丢包 0-4%、延迟 1-100ms——这些参数的选择具有主观性，且不反映任何真实世界的流量分布。论文声称这些"现实地反映了会看到 PEP 的网络设置"，但未提供支持证据。

5. **多流公平性问题被搁置**：PEP 最大的争议之一是它破坏了端到端公平性——拆分连接获得更高吞吐量，但可能挤占其他连接的带宽。论文仅在 limitations 中简单提及，但这恰恰是 PEP 部署的核心障碍。

6. **结论的实用性有限**：论文的主要贡献是"PEPs 可能还有用"，但没有提出任何实际可部署的新方案。对于 QUIC 连接（占比持续增长），论文只能说"如果能拆分的话可能有用"，但 QUIC 的设计目标之一就是防止被拆分。

---

## 七、总结

本文通过仿真实验重新审视了连接拆分 PEPs 在 BBR 和 QUIC 时代的价值。核心发现是 BBR 从 v1 演进到 v3 的过程中，为了公平性而增加的丢包敏感性使其重新能从连接拆分中获益，且在卫星/无线网络的中间段丢包场景中受益范围超过 CUBIC。同时，不同 QUIC 实现的拥塞控制行为差异巨大，增加了性能评估的复杂性。论文的实用价值主要在于提出了 split throughput heuristic 方法论和"按算法/实现/版本引用 CCA"的呼吁，但从仿真到真实部署仍有较大距离，且无法解决 QUIC 端到端加密带来的根本性拆分障碍。
