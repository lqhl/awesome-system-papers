# IRHash: Efficient Multi-Language Compiler Caching by IR-Level Hashing

**作者**：Tobias Landsberg, Johannes Grunenberg (Leibniz Universität Hannover); Christian Dietrich (Technische Universität Braunschweig); Daniel Lohmann (Leibniz Universität Hannover)
**会议**：USENIX ATC 2025
**链接**：https://www.usenix.org/conference/atc25/presentation/landsberg
**源文件**：[[atc2025-landsberg.pdf]]

---

## 一、背景

编译缓存（Compilation Cache, CC）通过避免冗余编译来节省时间、能源和成本，是软件开发中的重要基础设施。现有的编译缓存工具（如 Ccache、sccache）以编译器包装器的形式工作，或者直接集成在构建系统中（如 Bazel、Buck2）。其核心思路是：对翻译单元（Translation Unit, TU）计算指纹哈希，若命中缓存则跳过编译，直接复用之前的构建产物。

编译缓存的收益取决于一个权衡：缓存命中带来的节省是否超过缓存查找的额外开销。因此，在编译流程的哪个阶段进行哈希计算是关键问题——越早检测可以跳过更多编译步骤（更高的 $T_{rem}$），但越早的表示也越"表面"，容易产生 false miss（更低的 $P_{acc}$）。

---

## 二、要解决的问题

现有编译缓存方案存在以下不足：

1. **准确率不够高**：Ccache 在源码级或预处理后进行哈希，对注释、空白、未使用的代码块等表面变化敏感，产生大量 false miss（即代码变了但编译结果不变）。cHash 将哈希推迟到 AST 级别，准确率更高但仍受限于语法糖（如 C 的 typedef）。
2. **语言支持狭窄**：Ccache 和 sccache 仅支持 C/C++ 预处理器；cHash 深度绑定 C 语言的 AST 节点类型，仅支持 C 语言。对 Fortran、Haskell 等其他使用 LLVM 后端的语言无法复用。
3. **实现复杂度高**：cHash 需要为每种 AST 节点类型编写哈希规则，仅哈希操作符就需要 1200 行代码，且新增语言支持需要大量工作。

核心问题是：在编译流程的哪个层级进行缓存查找，能在准确率（$P_{acc}$）、节省潜力（$T_{rem}$）、跨语言通用性和实现复杂度之间达到最优权衡？

---

## 三、洞察与设计

**关键洞察**：编译器的中间表示（IR）是语言无关的、结构简单的寄存器级程序表示，从 AST 到 IR 的代码生成几乎不增加额外时间开销（例如 OpenSSL 中 IR 生成仅在 AST 生成后增加不到 1ms），但却能消除大量语法糖和语言特定构造（typedef、explicit、lambda 等），同时通过常量折叠等 ad-hoc 优化进一步归一化语义等价的代码。因此 IR 级别是编译缓存的最佳切入点——几乎不损失 $T_{rem}$，却能显著提升 $P_{acc}$，并且天然支持所有共享 IR 的前端语言。

基于此洞察，IRHash 在 LLVM IR 生成之后、优化之前进行哈希计算和缓存查找：

- **哈希计算**：遍历 LLVM IR 的层次结构（Module → Function → BasicBlock → Instruction），对每一层的关键属性（名称、类型、操作码、操作数、属性等）进行哈希。类型递归哈希到标量组件。内联汇编哈希其字符串表示。默认不包含调试信息。
- **缓存逻辑**：与 Ccache 类似，以哈希值为文件名在缓存目录中查找。命中时将缓存的目标文件硬链接到目标位置并终止编译；未命中时继续编译并将结果存入缓存。
- **设计决策**：选择直接遍历 LLVM 内部数据结构而非序列化的 IR（文本或 bitcode），因为：(1) 可以细粒度控制哈希包含的内容（如排除调试信息）；(2) 避免 IR 序列化的大量时间开销。

## 四、实现细节

IRHash 实现为一个 LLVM 插件，引入一个新的 IR 级编译器 pass：

- **代码规模**：总计 561 行 C++ 代码（其中哈希逻辑 ~353 行，缓存逻辑 208 行），对比 cHash 仅哈希操作符就需要 1200 行
- **哈希层次**：
  - `llvm::Module`（27 行）：哈希全局变量和函数列表
  - `llvm::Function`（25 行）：哈希名称、原型、属性、基本块
  - `llvm::BasicBlock`（4 行）：哈希指令列表
  - `llvm::Instruction`（71 行）：哈希操作码、操作数、对齐、原子性等属性
  - `llvm::Constant`（93 行）：哈希常量值
  - `llvm::GlobalVariable`（24 行）：哈希名称、类型、初始化器、属性
  - `llvm::Type`（109 行）：递归哈希到标量组件
- **集成方式**：作为 LLVM 插件可加载到所有基于 LLVM 的编译器中（Clang、Flang、GHC LLVM 后端等），pass 调度在 IR 生成之后立即执行
- **缓存命中处理**：命中时硬链接缓存文件并更新时间戳（兼容 make 等时间戳 BAR 方法）

## 五、实验结果

实验在 Intel Core i7-12700（禁用 Turbo Boost）+ 32GB 内存上进行，评估 16 个开源项目（C/C++/Fortran/Haskell），每个项目 100 个连续 commit 的增量构建，共编译 1,289,086 个翻译单元。

**准确率（$P_{acc}$）**：

| 语言 | Ccache | cHash | IRHash |
|------|--------|-------|--------|
| C 平均 | 95.32% | 99.19% | 99.87% |
| C++ 平均 | 88.20% | - | 98.86% |

IRHash 零 false hit（正确性保证），准确率比 Ccache 高 1-2 个数量级。

**哈希开销（$T_{over}/T_{total}$）**：

| 方案 | C 平均 | C++ 平均 |
|------|--------|----------|
| Ccache | 30.0% | 10.2% |
| cHash | 4.1% | - |
| IRHash | 0.4% | 0.3% |

IRHash 的相对开销极低，仅为编译总时间的 0.3-0.4%。

**端到端性能提升**：

| 方案 | C 平均 | C++ 平均 |
|------|--------|----------|
| Ccache | -9.6% | -6.0% |
| cHash | -15.7% | - |
| IRHash | -19.0% | -19.4% |
| Ccache+IRHash | -16.6% | -22.6% |

IRHash 在 C 项目上平均减少 19% 构建时间（Ccache 10%，cHash 16%），在 C++ 项目上平均减少 19.4%。Fortran (LAPACK) 减少 12.4%。组合 Ccache+IRHash 在部分项目上效果更好（如 GammaRay 从单独 10.6%/20.2% 提升到 26.4%）。

唯一例外是 ShellCheck (Haskell)，因 GHC 编译器的非确定性 bug 导致 IRHash 有 0.8% 的减速。

## 六、批判性分析

1. **评估方法偏向中等规模变更**：论文使用 Git commit 历史作为变更来源，这代表"中等规模"的变更。作者自己也承认交互式开发（小变更）和版本间变更（大变更）的场景未被充分评估。对于交互式开发这个最重要的使用场景，缺少直接的实验数据来支撑"开发者会受益更多"的论断。

2. **cHash 对比不完整**：cHash 不支持 C++ 因此在 C++ 项目上无法对比，而 C++ 正是 IRHash 优势最明显的地方（模板展开导致大量 IR 代码）。在仅有 C 项目的对比中，cHash 在 Bash 和 MbedTLS 上实际优于 IRHash，说明 AST 级方案在某些场景下仍有优势。

3. **函数级缓存的讨论过于草率**：论文提到函数级缓存可能效果更好但因过程间优化带来依赖追踪困难而放弃，但未进行任何实验量化这个"更好"到底有多大潜力。这实际上可能是比 TU 级缓存更有意义的方向。

4. **IR 规范化未启用**：论文提到 LLVM 已有 IR 规范化工具（IRNormalizer），启用后可能进一步提升 $P_{acc}$，但因担心 bug 和开销而未启用。考虑到当前 $P_{acc}$ 已经很高（99.87%），这个决定是合理的，但对于 C++ 项目（98.86%）可能仍有价值。

5. **缓存大小未限制**：实验中缓存大小不受限，但实际使用中缓存淘汰策略会影响 $P_{opt}$，论文未讨论 IRHash 在有限缓存下的表现。

6. **仅测试 Clang/LLVM**：所有项目默认编译器被替换为 Clang，未讨论使用 GCC 作为默认编译器的项目切换到 Clang 是否影响构建正确性或性能基线。

---

## 七、总结

IRHash 提出在 LLVM IR 级别实现编译缓存，利用 IR 的语言无关性和结构简单性，以仅 561 行 C++ 代码实现了跨 C/C++/Fortran/Haskell 的编译缓存方案。在 16 个开源项目的评估中，IRHash 以极低的哈希开销（~0.4%）和高准确率（99.87%）实现了平均 19% 的 C 项目构建时间缩减，优于 Ccache (10%) 和 cHash (16%)。其主要局限在于依赖 LLVM 生态（不适用于 GCC 等非 LLVM 编译器）以及 TU 级粒度限制了进一步优化的空间。
