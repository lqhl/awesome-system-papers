# STORM: a Multipath QUIC Scheduler for Quick Streaming Media Transport under Unstable Mobile Networks

**作者**：Liekun Hu, Changlong Li（华东师范大学计算机科学与技术学院、江淮前沿技术中心、硬件/软件协同设计技术与应用教育部工程研究中心）

**链接**：https://www.usenix.org/conference/atc25/presentation/hu-liekun

## 一、背景

流媒体应用（视频会议、VR/MR、云游戏、无人机实时画面等）在移动端迅速普及，对带宽和延迟提出了双重要求。移动设备通常配备多个网络接口（WiFi、4G/5G、卫星通信），Multipath QUIC (MPQUIC) 可通过多路径并行传输提升吞吐。然而，移动场景中设备频繁移动（步行、车辆、高铁）导致无线信号剧烈波动——蜂窝网络频繁切换、WiFi 漫游等——使得端到端延迟急剧上升。实验表明，启用 MPQUIC 后移动场景中尾延迟可达 4.59 秒，是静止场景的 6.38 倍，甚至比单路径传输更差。

---

## 二、要解决的问题

1. **调度器对信号变化的响应速度慢**：现有 MPQUIC 调度器（如 minRTT、DAMS）基于拥塞状态或历史指标估计路径质量，对移动导致的突发信号劣化（burst loss）响应严重滞后，无法感知无线链路层的即时变化。
2. **可靠与不可靠数据的相互阻塞**：QUIC 支持同时传输可靠（STREAM）和不可靠（DATAGRAM）数据，但现有调度器对两者不加区分。当某路径遭遇 burst loss 时，可靠数据的重传占满带宽，不可靠数据被积压；积压的不可靠数据又反过来阻塞后续可靠数据，形成恶性循环。
3. **现有路径管理机制不足**：MPQUIC 原有的 PATH_STANDBY/PATH_AVAILABLE 机制无法在无线链路突发中断时及时停用问题路径，导致在已失效路径上继续调度数据。

---

## 三、洞察与设计

**关键洞察**：多路径网络中端到端延迟的瓶颈不在核心网络（WAN），而在"最后一英里"无线链路（终端设备到基站/接入点）。通过 traceroute 方式测量发现，极端情况下 E2E RTT 达 3,781 ms，其中无线链路 RTT 占 3,750 ms。因此，如果调度器能与终端设备的无线网络模块协同设计，就可以实时感知无线链路质量变化，并在信号劣化发生的瞬间做出调度决策，而无需依赖滞后的传输层反馈。

基于此洞察，STORM 提出两个核心组件：

### Signal-Watermark Mechanism (SWM)

- **信号质量量化**：将 RSRP 和 SINR 归一化后取加权几何均值作为基础质量指数 $Q_{base}$，再通过丢包率变化趋势的调制因子 $H(\Delta loss)$ 修正，得到最终质量指数 $Q \in [0,1]$。
- **三级水位线**：设定 Good、Warning、Outage 三个阈值。低于 Warning 发送警告反馈（调整路径分配比例），低于 Outage 发送中断反馈（停用该路径）。恢复反馈采用"快抑制/慢恢复"策略——信号恢复需持续超过阈值时间 $T_{rec}$ 才发送恢复反馈，避免频繁路径切换。
- **自适应水位线**：根据实际 burst loss 效果动态调整 Outage 和 Warning 阈值。
- **与无线模块协同**：在移动端增加适配层，专用线程通过标准 Android API 每 100ms 采集信号强度，通过无锁原子变量供 SWM 读取，不阻塞 QUIC 事件循环。

### Reliability-Aware Scheduling (RAS)

- **Dual-Q 架构**：将数据分为可靠数据队列（RQ，以 block 为单位）和不可靠数据队列（UQ，以 stream 为单位）。
- **可靠数据块调度**：根据 deadline、block 大小、路径带宽和 OWD 计算每个 block 的紧迫度权重，优先调度最紧迫的 block；同时根据 SWM 反馈调整路径分配比例，信号差的路径分配更少数据。
- **不可靠数据流调度**：利用快慢路径之间的"时间空洞"（time hole）注入不可靠数据到慢路径，每次阻塞只持续单次重传周期，有效缓解可靠/不可靠数据的相互阻塞。
- **动态多路径管理**：收到 Outage 反馈后立即停用问题路径，引入 PATH_ALERT 帧传递 SWM 反馈；对已在失效路径上的未确认数据，通过 deadline-aware reinjection 决定是否在可用路径上重新注入。

## 四、实现细节

- 基于阿里巴巴 XQUIC 开源实现，修改 QUIC 协议栈共 **1,342 行 C 代码**（不含库）。
- **无线适配层**：Android 端 102 行 Java 代码，通过 `WifiManager` 和 `TelephonyManager` 标准 API 获取信号指标，不需要 root 或重编译内核。每 100ms 通过 JNI 调用更新原子变量，单次 JNI 开销仅 78µs。
- **可靠数据**映射为 STREAM 帧，**不可靠数据**映射为 DATAGRAM 帧（RFC 9221）。
- 可靠数据块元数据缓存在 vector 中；不可靠数据以双向链表按 deadline 排序，延迟 packetization 到注入慢路径时才执行，减少调度开销。
- 新增 **PATH_ALERT 帧**替代原有 PATH_STANDBY/PATH_AVAILABLE 机制，携带 SWM 反馈。
- 上层应用通过 `STORM_send` API 传入 deadline 和 priority 即可使用，无需代理。
- RAS 处理 Dual-Q 平均耗时 5.03ms（占总传输时间 7.4%），SWM 反馈算法 O(1) 复杂度。

## 五、实验结果

### 实验平台

| 类型 | 设备 | 网络 | 系统 |
|------|------|------|------|
| 控制实验 | PC | Ethernet | Ubuntu 20.04 |
| 视频会议 / 直播 | Xiaomi 12S Pro | WiFi-6 + LTE/5G | Android 14 |
| 360° 视频 | Laptop | WiFi-6 | Ubuntu 18.04 |

### 微基准测试（控制环境）

| 带宽组合 (Mbps) | MPQUIC 完成率 | DAMS 完成率 | STORM 完成率 |
|---|---|---|---|
| <20, 25> | 99.9% | ~99% | ~99% |
| <10, 15> | 26.1% | ~24% | ~75% |
| <5, 10> | ~0% | ~0% | ~50% |

- STORM 在 <5,10> 带宽组合下最大等待时间为 MPQUIC 的 49.6%、DAMS 的 45.3%。

### 真实移动网络应用

| 指标 | 改善 |
|---|---|
| 尾包延迟（P99） | 降低 **98.2%**（vs MPQUIC） |
| 流媒体帧率 | 提升 **1.95x**（vs DAMS/state-of-the-art） |
| 不流畅帧率（<24fps）比例 | 改善 95.1%（vs MPQUIC）、96.8%（vs DAMS） |
| 卡顿时长 | 降低 83.0%（vs MPQUIC）、85.2%（vs DAMS） |
| 平均重传率 | 降至 1.5%（STORM-U 为 4.1%） |
| P90 延迟 | 68.2ms（MPQUIC 89.8ms） |
| P99 延迟 | 129.8ms（MPQUIC 758.6ms） |

### 消融实验

- 去掉 SWM：goodput 降低 26.6%，rebuffering 时间增加 6.8 倍。
- 去掉 RAS：goodput 降低 15.7%，rebuffering 时间增加 2.9 倍。

## 六、批判性分析

1. **信号采集延迟问题被轻描淡写**：论文承认信号上报到用户空间有最多 200ms 延迟，但仅以"大空间位移不太可能"一笔带过。在高铁场景（300+ km/h）下，200ms 内可移动约 17 米，信号变化可能非常剧烈，SWM 的有效性在极端高速场景下存疑。

2. **实验场景代表性有限**：真实应用实验在校园内步行进行（walking around campus），这是相对温和的移动场景。论文 motivation 中大量讨论高铁、eVTOL、车辆场景，但除了信号 trace 回放外没有在这些场景中做端到端测试。微基准测试使用 Ethernet 模拟无线网络，回避了实际无线链路的复杂性。

3. **参数设置的通用性存疑**：SWM 的水位线默认值（Good=0.45, Warning=0.32, Outage=0.21）、权重系数（$w_{rsrp}=0.8$, $w_{sinr}=0.6$）和调制因子敏感度（$\gamma=0.01$）均通过经验调参确定。虽然有自适应机制，但在不同运营商、不同城市、不同网络制式下的适应性缺乏系统验证。

4. **仅支持双路径**：设计和公式始终假设两条路径（WiFi + 蜂窝）。随着设备支持更多网络接口（如 WiFi + 5G + 卫星），当前设计的扩展性未被讨论。

5. **稳定信号下改善微乎其微**：Table 4 显示在稳定信号条件下各方案差异极小（FPS 29.2 vs 29.6），说明 STORM 的价值完全依赖于信号不稳定的前提条件。如果网络基础设施持续改善（如 5G Advanced/6G 带来更好的切换机制），STORM 的适用场景可能缩小。

6. **缺少与 ML-based 调度器的对比**：论文只与 minRTT 和 DAMS 做了对比，没有与基于机器学习的自适应调度方案进行比较，而后者在该领域已有不少工作。

---

## 七、总结

STORM 是一个面向移动不稳定网络场景的 MPQUIC 调度器，通过与终端无线模块协同的信号水位线机制（SWM）实时感知链路质量变化，配合区分可靠/不可靠数据的调度策略（RAS），大幅降低了多路径传输在信号波动时的尾延迟。其核心贡献在于将调度决策从依赖传输层滞后反馈转变为基于物理层信号的即时感知，实现轻量级（O(1) 开销、1342 行代码）且实用的改进。主要局限在于实验验证集中于校园步行场景，对论文所声称的高铁、车载等极端高速移动场景缺乏直接验证，且参数调优的通用性和多路径扩展性有待进一步研究。
