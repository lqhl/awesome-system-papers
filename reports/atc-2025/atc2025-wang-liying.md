## 一、背景

低轨（LEO）卫星正从单一、昂贵的通信节点演变为太空中的联网计算系统，即 Space Computing Networks（SCNs）。这一变革背后有两大技术趋势：一是 COTS（商用现成）硬件（如 Raspberry Pi、FPGA、GPU）取代传统低性能专用芯片，带来更高性能和更低成本；二是卫星星座组网（如 Starlink 拥有 6000+ 颗卫星），实现全球覆盖和高带宽连接。

SCN 催生了两类核心应用：（1）地球观测（EO）——利用 COTS 设备进行在轨图像处理（压缩、过滤、检测），减少下行数据量，实现近实时观测（最快 6 分钟从拍摄到洞察）；（2）卫星骨干全球网络——卫星作为在轨计算节点执行网络功能（如 5G 核心的 UPF），处理用户流量、视频会议中继等。

然而，SCN 应用的设计、构建和评估极具挑战：真实星座的运营成本极高（发射一颗小卫星约 $150,000），且星座规模不断增大，研究者迫切需要高保真、可扩展的仿真平台。

---

## 二、要解决的问题

现有 SCN 仿真工具无法同时满足三个关键需求：

1. **卫星级保真度不足**：太空环境中 COTS 芯片面临能量和热管理约束（电池有限、无主动散热），导致性能显著退化。现有仿真器（如 CoteSim）的功率模型假设日照区功率恒定，与实际偏差很大；StarryNet 通过调整 CPU 核数/频率模拟设备性能，无法捕捉异构 COTS 设备的真实特性（如 GPU+CPU 架构），推理延迟偏差高达 15%，且完全无法模拟过热导致的性能降级。

2. **星座级保真度不足**：星座网络高度动态（拓扑频繁变化、节点故障），现有工具在模拟拓扑动态、节点故障对网络性能的影响方面能力有限。StarryNet 采用随机方式模拟节点故障，无法反映能量耗尽或过热导致的真实故障模式。

3. **可用性问题**：物理平台（如真实星座）难以访问、不可扩展；分析型模拟器缺乏真实软件/网络栈，无法运行用户自定义应用；现有仿真器在保真度与可扩展性之间存在根本矛盾——精确仿真单颗卫星需要大量系统开销，扩展到星座级则开销不可承受。

## 三、洞察与设计

**关键洞察**：虽然太空环境与地面截然不同，但 COTS 芯片因过热导致的性能降级在相同温度下地面和太空表现一致——因为热节流机制由芯片硬件本身决定，与所处环境无关。这意味着可以在地面通过去除散热风扇的真实 COTS 芯片采集性能-温度映射数据，再用轻量级容器镜像该行为，从而以低成本实现高保真仿真。

基于这一洞察，RHONE 采用**两阶段仿真架构**：

**离线模型构建阶段**：利用真实卫星遥测数据和地面 COTS 设备实验构建五个模型：
- **功率模型**：包含能量采集（基于太阳常数、面板效率、入射角等物理参数）和能量消耗（区分 Markov 型和函数型两种功耗模式）
- **热模型**：基于有限元分析（FEA），使用 SolidWorks 模拟卫星内部热传导，输出芯片温度随时间的变化
- **计算模型**：Hardware-in-the-loop chip mirroring——在去除风扇的真实 COTS 芯片上循环执行任务直至热节流，生成 `satPerfTable`（温度→延迟映射）；在容器中调整资源约束执行同样任务，生成 `emuPerfTable`（资源分配→延迟映射）
- **轨道与网络模型**：基于轨道参数计算卫星实时位置，推导 ISL/GSL 连接性和信号延迟

**在线仿真阶段**：将离线模型部署到 Docker 容器中：
- **State Manager**：协调各模型的嵌套交互（功率模型读取温度→输出功率→热模型更新温度）
- **Satellite COTS Aligner（SCA）**：根据当前温度查 `satPerfTable` 得到目标延迟，再查 `emuPerfTable` 确定资源分配，通过 cgroup（CPU）和 CUDA API 拦截（GPU）动态调整容器资源
- **Satellite Network Aligner（SNA）**：继承 StarryNet 管理 Docker 网络，新增多容器粒度表示（每颗卫星多个 COTS 设备）和基于模型的节点故障（而非随机故障）

## 四、实现细节

- **离线阶段**：使用天算星座遥测数据（800,000+ 条带时间戳的记录，跨 2021.12–2022.07）和 BUPT-1 卫星开源数据集。热模型使用 SolidWorks FEA，电池模型使用 PyBaMM。计算模型基于 Raspberry Pi 4B 和 Huawei Ascend Atlas 200 DK（均去除风扇），辅以程控热电冷却器模拟低温环境
- **在线阶段**：Python Requests API 协调各模型；SCA 通过 cgroup 限制 CPU 资源，通过 TGS 限制 GPU 资源；网络管理复用 StarryNet 的 Docker 网络架构
- **代码规模**：核心组件约 4500 行 Python/C# 代码
- **卫星节点结构**：每颗卫星由一个 State Manager + 多个 Docker 容器（分别代表不同 COTS 芯片）组成，可指定一个容器作为 OBC（星载计算机）负责对外通信
- **用户接口**：Monitor API（实时监控温度、能量、负载、网络状态）和 Command API（动态修改运行模式、连接性、启动任务）

## 五、实验结果

### 可扩展性（单节点服务器：2× Intel Xeon E5-2670 v3, 64GB RAM）

| 卫星数量 | CPU 使用率 (RHONE/StarryNet) | 内存使用率 (RHONE/StarryNet) | 启动时间 (RHONE/StarryNet) |
|----------|------------------------------|------------------------------|---------------------------|
| 172 | 12.1% / 18.3% | 8.9% / 10.3% | 15.1 min / 5.1 min |
| 348 | 23.7% / 27.5% | 13.5% / 16.7% | 19.8 min / 7.8 min |
| 720 | 37.7% / 42.7% | 24.5% / 33.3% | 42.2 min / 17.1 min |

RHONE 在单节点上支持 720 颗卫星（对应 Starlink 一个 shell 的规模），CPU/内存开销持平或低于 StarryNet，但启动时间更长（需离线计算环境 trace 和 COTS profiling）。

### 保真度

| 模型 | 指标 | 结果 |
|------|------|------|
| 能量采集 | NSE（99th percentile） | RHONE: 0.05 vs CoteSim: >1.5（PR 场景） |
| 能量消耗 | 各组件平均误差 | 通信 3.0%，Pi 3.5%，Atlas 3.8%，其他 4.1% |
| 热模型 | 平均温度误差 | Pi: 2.5°C，Atlas: 1.3°C |
| 计算模型 | 推理延迟相对误差 | 大多数情况 <5% |

### 用例演示

1. **卫星网络能量耗竭攻击**（720 卫星）：恶意流量导致受害卫星 COTS 设备功耗激增、电池快速耗尽至安全阈值（60%）后强制关机，带宽瞬间归零；夜间（无太阳能）更脆弱
2. **实时地球观测**（150 卫星，模拟 Planet Dove）：对比四种传输策略，图像压缩/目标检测/推理分别减少链路使用 0.3×/0.8×/0.99×；在轨推理虽增加计算功耗，但大幅减少通信功耗和带宽

## 六、批判性分析

1. **计算模型的泛化性存疑**：论文仅在两种 COTS 设备（Raspberry Pi 4B 和 Atlas 200 DK）上验证了"地面过热≈太空过热"的假设。但太空环境还有真空、辐射等因素影响芯片行为（如 SEU 导致的频率降级），仅靠"去除风扇"无法完整复现太空条件。论文承认 thermal vacuum 实验能改善精度但成本高——这恰恰削弱了"低成本高保真"的核心卖点。

2. **启动时间代价被淡化**：RHONE 启动时间是 StarryNet 的 2.5–3× (720 卫星时 42 min vs 17 min)。对于需要反复迭代实验的研究场景，这个开销不可忽视，但论文仅用一句"setup 完成后可复用"带过。

3. **实验规模有限**：保真度评估仅用 25 颗卫星的小型星座，而可扩展性评估中 720 颗卫星并未同时验证保真度。论文未展示大规模仿真下保真度是否会因资源竞争而退化。

4. **用例的深度不足**：两个 case study 更多是功能演示而非深入的系统评估。能量耗竭攻击场景没有与真实攻击数据对比；EO 场景的四种策略比较是常识性结论（压缩/检测减少带宽），缺乏 RHONE 独有的洞察。

5. **网络模型依赖 StarryNet**：SNA 继承自 StarryNet，论文对网络层的保真度几乎没有独立评估，仅在 Table 1 中标注 "✓"。网络延迟、拥塞、路由动态等关键方面的准确性未被验证。

6. **热模型需要 SolidWorks**：FEA 热模型依赖商业软件 SolidWorks 且需要卫星内部结构的精确 CAD 模型，这对大多数研究者来说门槛很高，与"高可用性"的目标有矛盾。

## 七、AI Infra / MLSys 视角

1. **设备异构性建模方法的借鉴**：RHONE 的 Hardware-in-the-loop chip mirroring 思路——先在真实硬件上 profiling 生成性能表，再用容器动态调整资源来镜像——可以迁移到 AI 推理集群的异构设备管理。在混合 GPU/NPU 集群中，不同设备的推理延迟随温度、功耗限制变化，类似的 profile-then-mirror 方法可用于更精确的负载均衡和调度。

2. **能量-热-计算耦合建模**：RHONE 展示了功率→温度→计算性能的嵌套反馈循环。这一思路对 AI 数据中心的功率受限推理（power-capped inference）场景有启发——在功率预算约束下，GPU 的 thermal throttling 会影响推理延迟，需要类似的耦合建模来做精确的 SLA 预估。

3. **卫星边缘 AI 推理优化**：EO 用例展示了在轨推理 vs 传输的 tradeoff，这是一个典型的 edge AI inference 问题。在卫星场景下探索模型压缩（量化、剪枝）、自适应推理（根据能量/温度状态动态选择模型精度）是有价值的方向。

4. **值得关注的局限**：RHONE 目前仅支持 CPU 和简单 NPU，不支持 GPU 密集型推理（如大模型），且容器化方式难以精确模拟 GPU 的显存管理和 kernel 执行行为。如果未来卫星搭载更强 AI 加速器，需要更精细的 GPU 仿真方案。

---

## 八、总结

RHONE 是一个面向太空计算网络（SCN）的全功能仿真器，通过两阶段设计（离线模型构建 + 在线容器仿真）在卫星级和星座级同时实现高保真仿真。其核心创新在于利用"地面芯片过热性能降级与太空一致"的观察，结合 Hardware-in-the-loop chip mirroring 和 FEA 热模型，以低成本容器化方式镜像真实 COTS 设备行为。在单节点上可扩展至 720 颗卫星，功率和计算模型误差 <5%，热模型误差 1.3–2.5°C。主要局限在于仅验证了两种 COTS 设备、热模型依赖商业软件、大规模场景下的保真度未被充分验证。
