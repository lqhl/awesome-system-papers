# MLE-bench: Evaluating Machine Learning Agents on Machine Learning Engineering

**作者**：Chan Jun Shern*, Neil Chowdhury*, Oliver Jaffe*, James Aung*, Dane Sherburn*, Evan Mays*, Giulio Starace*, Kevin Liu, Leon Maksin, Tejal Patwardhan, Lilian Weng, Aleksander Mądry (OpenAI)
**会议**：Preprint (arXiv 2024)
**链接**：[arXiv](https://arxiv.org/abs/2410.07095)
**源文件**：[[2410.07095v2.pdf]]

---

## 一、背景

语言模型在代码生成基准（HumanEval、MBPP 等）上已取得优异表现，并被集成到编程工具（GitHub Copilot）和 agent 工作流中。然而，这些基准主要评估单步代码片段生成能力，无法全面衡量端到端的自主 ML 工程能力——包括数据处理、模型训练、实验迭代、调试等完整流程。与此同时，AI R&D 加速的前景对安全评估提出了迫切需求：如果 AI agent 能自主完成高质量 ML 研究，可能加速科学进步，但也可能带来模型自我改进的风险。因此，需要一个标准化、有挑战性的基准来衡量 agent 在真实 ML 工程任务上的能力水平。

---

## 二、要解决的问题

1. **现有代码基准饱和且范围有限**：HumanEval、APPS 等基准评估的是孤立的代码片段生成，不涉及数据探索、模型训练、长时间迭代和调试等 ML 工程核心技能。
2. **缺乏与人类水平的直接比较**：现有评估难以量化 agent 相对于人类 ML 工程师的能力差距。
3. **ML 工程评估基准不够多样和困难**：MLAgentBench 仅有 13 个任务且提供基线方案，DSBench 和 AIDE 的评估集聚焦表格数据，缺乏足够多样性和挑战性。
4. **污染与作弊风险难以量化**：使用公开数据集和竞赛时，模型可能通过预训练记忆获得不公平优势，需要系统性的污染检测机制。

---

## 三、洞察与设计

**关键洞察**：Kaggle 竞赛天然提供了多样化、有挑战性的 ML 工程任务以及大规模的人类基线排行榜，可以直接用作评估 agent 的标准化环境——通过离线复现竞赛并与真实人类成绩对比，就能建立有意义的 ML 工程能力度量。

基于这一洞察，MLE-bench 的核心设计包括：

- **任务来源**：从 5673 个已完成的 Kaggle 竞赛中筛选出 75 个，涵盖图像分类、NLP、信号处理、时间序列预测等 15 个类别，按复杂度分为 Low（30%）、Medium（50%）、High（20%）。
- **评估指标**：以 Kaggle 奖牌体系（铜/银/金）作为衡量标准，按 Private leaderboard 排名判定，核心指标为"获得任意奖牌的竞赛比例"。
- **离线环境**：每个竞赛配备描述、数据集、本地评分代码和排行榜快照。Agent 在 Docker 容器中运行，有 24 小时时间限制。
- **反作弊机制**：禁止 agent 直接手写预测值、调用外部 LLM API 或访问在线解答；使用 GPT-4o mini 分析日志检测违规行为，使用 Dolos 工具进行代码抄袭检测（相似度 > 60% 标记）。
- **数据集重构**：对大多数竞赛重新划分 train/test split，避免与原始测试集的直接泄露，并确保新 split 的分布与原始一致。

---

## 四、实现细节

- **竞赛筛选**：至少两名 ML 工程师手动审核，排除社区竞赛、无法复现评分逻辑的竞赛、数据集过于常见（如 MNIST）的竞赛等。最终 75 个竞赛总奖金超 195 万美元。
- **执行环境**：Ubuntu 20.04 Docker 容器，36 vCPU、440GB RAM、4095GiB SSD、单块 NVIDIA A10 GPU（24GB）。使用 sysbox 运行时实现安全隔离。
- **Agent scaffold 集成**：评估了三种开源 scaffold——AIDE（Kaggle 专用，树搜索策略，最多 500 nodes）、OpenHands CodeActAgent（通用，最多 500 步）、MLAB ResearchAgent（通用，最多 2000 步）。对每种 scaffold 做了针对性修改以提高鲁棒性。
- **验证服务器**：本地 HTTP 端点 `localhost:5000/validate` 供 agent 检查提交格式有效性（不返回得分）。
- **污染实验**：计算 GPT-4o base model 对竞赛页面和 top-5 讨论帖的 token 级 familiarity（平均 token 概率），并设计了描述文字混淆实验。
- **重复实验**：主实验每个竞赛 3 个随机种子，o1-preview (AIDE) 和 GPT-4o (AIDE) 分别使用 16 和 36 个种子。

## 五、实验结果

### 主实验：不同 Scaffold 和模型

| 模型 | Scaffold | 有效提交率 | 超过中位数 | 铜牌 | 银牌 | 金牌 | 任意奖牌 |
|------|----------|-----------|-----------|------|------|------|---------|
| o1-preview | AIDE | 82.8% | 29.4% | 3.4% | 4.1% | 9.4% | **16.9%** |
| GPT-4o | AIDE | 54.9% | 14.4% | 1.6% | 2.2% | 5.0% | 8.7% |
| Claude 3.5 Sonnet | AIDE | 51.1% | 12.9% | 0.9% | 2.2% | 4.4% | 7.6% |
| Llama 3.1 405B | AIDE | 27.3% | 6.7% | 0.0% | 1.3% | 1.7% | 3.0% |
| GPT-4o | OpenHands | 52.0% | 7.1% | 0.4% | 1.3% | 2.7% | 4.4% |
| GPT-4o | MLAB | 44.3% | 1.9% | 0.0% | 0.0% | 0.8% | 0.8% |

### 资源缩放实验

| 实验 | 关键发现 |
|------|---------|
| pass@k 尝试次数 | o1-preview 从 pass@1 的 16.9% 提升到 pass@8 的 34.1%，GPT-4o pass@6 (17.0%) ≈ o1-preview pass@1 |
| 硬件变化 | CPU-only (9.1%)、单 A10 (8.7%)、双 A10 (10.2%)——性能差异不显著，agent 未能利用额外 GPU |
| 时间延长 | GPT-4o (AIDE) 100 小时上限：前几小时获得多数奖牌，之后缓慢积累，偶有倒退 |

## 六、批判性分析

1. **奖牌分布倒挂令人费解**：o1-preview 获得的金牌数（9.4%）远超铜牌（3.4%），这与直觉不符——正常分布应该是铜 > 银 > 金。论文未对此给出解释，可能意味着 agent 在能解决的竞赛上直接达到很高水平，但无法在边缘难度的竞赛上拿到基础分。这提示 agent 的能力曲线可能是阶梯式而非渐进式的。

2. **硬件无关性过于匪夷所思**：CPU-only 与单/双 GPU 的表现几乎一致，说明 agent 根本没有有效利用 GPU 来训练更复杂的模型。这严重限制了基准的有效性——如果 agent 在大多数竞赛中只使用简单方法（如 XGBoost、小型预训练模型微调），那 MLE-bench 可能并未真正测试到"ML 工程"的核心难度（大规模训练、分布式调参等）。

3. **AIDE scaffold 的优势可能引入偏见**：AIDE 是专为 Kaggle 竞赛设计的，其树搜索策略本质上就是对 Kaggle 格式的过拟合。论文标题声称评估的是"ML 工程"能力，但实际评估的更多是"在 Kaggle 竞赛格式下的表现"，这二者的差距被低估了。

4. **污染实验不够有力**：Familiarity 指标（token 级平均概率）是一个非常粗糙的污染度量。模型可能不是逐字记忆解答，而是学到了通用的 Kaggle 竞赛解题模式（如"对图像分类用 EfficientNet + TTA"），这种高层策略性污染不会被 familiarity 或 Dolos 检测到，却仍然构成人为拔高。

5. **有效提交率过低**：即使最佳模型 o1-preview (AIDE) 也只有 82.8% 的有效提交率，GPT-4o 仅 54.9%。这意味着近一半的竞赛尝试直接失败在格式层面，而非能力层面。论文花大量篇幅讨论奖牌率，但对 agent 为何频繁无法产出有效提交缺乏深入分析。

6. **时间维度的实验信息不足**：100 小时实验仅用 GPT-4o 做了，没有用表现最佳的 o1-preview 重复，浪费了揭示性能上限的机会。

---

## 七、AI Infra / MLSys 视角

1. **Agent 执行效率问题**：论文提到 agent 经常因为命令占满磁盘/内存导致进程被 kill，且不考虑代码运行时间。这暴露了当前 agent 系统在资源管理和执行规划上的根本缺陷——对 AI Infra 领域来说，为 agent 设计资源感知的执行调度器（resource-aware execution scheduler）是一个有价值的研究方向。

2. **Scaffold 设计对性能影响巨大**：AIDE 的树搜索策略使其大幅领先通用 scaffold，暗示对于 ML 实验这类"需要反复尝试"的工作流，搜索/优化策略的选择比底层模型能力更重要。这对设计 ML 实验自动化系统有启发意义。

3. **GPU 利用率为零的问题**：Agent 在双 GPU 环境下不会使用第二块 GPU，说明当前 LLM agent 缺乏分布式训练/多设备利用的能力。一个可操作的研究方向是：设计可以向 agent 暴露硬件拓扑信息并提供分布式训练模板的 scaffold。

4. **Token 成本问题**：o1-preview (AIDE) 单次 75 竞赛消耗 127.5M 输入 + 15M 输出 token，加上 1800 GPU 时，评估成本极高。如何降低 agent 评估的 token 和计算成本，本身就是一个 MLSys 问题。

5. **延伸方向**：基于 MLE-bench 的框架，可以设计面向 AI Infra 特定任务的基准——如分布式训练配置优化、推理系统调优、GPU kernel 编写等，这些任务比 Kaggle 竞赛更接近 AI Infra 工程师的日常工作。

---

## 八、总结

MLE-bench 通过复现 75 个 Kaggle 竞赛构建了一个评估 AI agent ML 工程能力的标准化基准，以 Kaggle 奖牌体系为度量建立了与人类水平的直接对比。最佳配置 o1-preview + AIDE 在 16.9% 的竞赛中获得奖牌，多次尝试（pass@8）可提升至 34.1%。该基准在任务多样性和人类基线可比性方面有明显优势，但也存在局限：GPU 利用率低暗示 agent 回避了真正的大规模训练挑战，Kaggle 竞赛格式与真实 ML R&D 流程存在差距，且污染检测手段对策略层面的记忆泄露无能为力。
