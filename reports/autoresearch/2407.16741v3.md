# OpenHands: An Open Platform for AI Software Developers as Generalist Agents

**作者**：Xingyao Wang (UIUC, AllHandsAI), Boxuan Li (CMU), Yufan Song (CMU), Frank F. Xu (CMU), Xiangru Tang (Yale), Mingchen Zhuge (KAUST), Jiayi Pan (UC Berkeley), 等 24 位作者
**会议**：ICLR 2025
**链接**：[arXiv](https://arxiv.org/abs/2407.16741)
**源文件**：[[2407.16741v3.pdf]]

---

## 一、背景

随着大语言模型（LLM）能力的快速提升，AI Agent 从简单的问答系统演进为能感知环境并采取行动的自主系统。软件开发是人类与世界交互最强大的方式之一——它支撑着从基本生活到科学技术的方方面面。因此，让 AI Agent 像人类开发者一样通过编写代码、使用命令行、浏览网页来与世界交互，成为一个极具吸引力的方向。

然而，构建这样的 Agent 面临多重挑战：如何在复杂软件系统中有效创建和修改代码？如何提供实时调试和信息收集工具？如何确保开发过程安全、不产生负面副作用？现有的 Agent 框架（如 AutoGPT、LangChain、MetaGPT）虽然各有优势，但在功能完整性上存在不同程度的缺陷——缺乏沙箱环境、缺少浏览器支持、评估框架不完善等。

---

## 二、要解决的问题

1. **缺乏统一的通用 Agent 平台**：现有框架要么专注软件工程（SWE-Agent、AutoCodeRover），要么专注网页浏览（WebArena Agent），缺乏能同时覆盖代码编辑、命令执行、网页浏览的通用平台
2. **安全执行环境缺失**：Agent 生成的代码需要在隔离环境中执行，防止对用户系统造成破坏，但多数框架缺乏内置沙箱
3. **工具生态碎片化**：不同 Agent 实现之间难以共享工具（Agent-Computer Interface），每个框架各自为政
4. **缺乏系统化评估**：没有统一的评估框架来跨任务类型（软件工程、网页浏览、通用辅助）比较 Agent 性能
5. **多 Agent 协作困难**：通用 Agent 和专业 Agent 之间缺乏标准化的任务委派机制

## 三、洞察与设计

**关键洞察**：软件是人类与世界交互最强大的方式，因此 AI Agent 应当通过软件接口（代码执行 + 命令行 + 浏览器）而非预定义的 JSON 函数调用来与世界交互。基于编程语言的动作空间（Programming Language-based Action Space）足够通用和灵活，能覆盖人类软件工程师的绝大多数任务，同时天然支持工具创建——Agent 可以通过编写 Python 函数来自行创建工具。

基于这一洞察，OpenHands 的架构包含三个核心组件：

### 1. Event Stream 架构
所有交互（用户指令、Agent 动作、环境观察）统一记录在 Event Stream 中，作为 Agent 决策的上下文。Agent 在每一步读取 State（包含 Event Stream 历史），输出一个 Action。

### 2. Agent Runtime（沙箱执行环境）
每个任务会话启动一个独立的 Docker 容器沙箱，内含：
- **Bash Shell**：执行系统命令
- **Jupyter IPython Server**：执行 Python 代码
- **Chromium 浏览器**（基于 Playwright）：执行网页交互

Runtime 通过 REST API 接收 Event Stream 中的动作并返回执行结果。支持任意 Docker 镜像，通过自动构建机制将 OpenHands 执行 API 注入用户提供的镜像中。

### 3. Agent Skills 可扩展工具库
基于 Python 包的工具库，自动导入 IPython 环境。遵循最小化原则：只在 LLM 无法直接编写代码完成的任务（如精确行级代码编辑）或需要调用外部模型时（如语音转文字）才添加新 skill。

### 4. Multi-Agent Delegation
通过 `AgentDelegateAction` 实现 Agent 间的任务委派，例如通用 CodeAct Agent 将复杂网页浏览任务委派给专业 Browsing Agent。

## 四、实现细节

### Agent 抽象
Agent 的核心是 `step(state: State) -> Action` 函数。State 包含 Event Stream 历史和辅助信息（LLM 累计开销、多 Agent 元数据等）。支持的核心 Action 类型：
- `IPythonRunCellAction`：执行 Python 代码
- `CmdRunAction`：执行 Bash 命令
- `BrowserInteractiveAction`：基于 BrowserGym 的网页交互 DSL
- `AgentDelegateAction`：委派子任务给其他 Agent
- `AgentFinishAction`：标记任务完成

### Agent Hub
社区贡献的 Agent 实现：
- **CodeAct Agent**（默认通用 Agent）：基于 CodeAct 框架，支持代码执行 + 网页浏览 + 自然语言对话
- **Browsing Agent**：专业网页 Agent，基于 WebArena 风格的零样本提示
- **GPTSwarm Agent**：基于可优化图的多 Agent 系统
- **MicroAgent**：复用通用 Agent 实现、仅定制提示的轻量级专业 Agent

### Docker 镜像管理
采用双标签系统：
- **Hash-based tag**（基于构建目录的 MD5 哈希）：保证可复现性
- **Generic tag**（基于版本号和基础镜像名）：提供稳定的最新版引用

### 评估框架
集成 15 个基准测试，覆盖三大类：
- 软件工程（SWE-Bench、HumanEvalFix、BIRD、ML-Bench、BioCoder、GorillaAPIBench、ToolQA）
- 网页浏览（WebArena、MiniWoB++）
- 通用辅助（GAIA、GPQA、AgentBench、MINT、ProofWriter、EntityDeductionArena）

### 项目规模
MIT 许可证，32K GitHub Stars，188+ 贡献者，2.1K+ 贡献。

## 六、批判性分析

1. **通用性 vs. 专业性的矛盾被低估**：论文强调 CodeAct Agent "在不修改系统提示的情况下跨三大类任务表现竞争力"，但实际上在每个单项任务上都未达到最优。WebArena 上 15.5% 远低于 AutoEval&Refine 的 20.2%，SWE-Bench 上 26.0% 与 Agentless 的 27.3% 和 MoatlessTools 的 26.7% 持平。"通用但平庸" 是否真的优于 "专业且出色"，论文未给出令人信服的论证。

2. **评估基线选择有偏向性**：论文声称"不对比使用人工 prompt engineering 针对特定 benchmark 优化的方法"，但这恰恰排除了实际表现最好的系统。这种排除策略使得 OpenHands 看起来更具竞争力，但与实际使用场景中的最佳方案相比差距不明。

3. **成本数据不完整**：许多基线方法缺少成本数据（标记为 "−"），使得成本效益的比较无法公平进行。论文暗示 OpenHands 成本合理，但没有与最优基线的成本做直接对比。

4. **社区贡献 vs. 系统贡献混淆**：论文将 188+ 贡献者和 32K Star 作为平台质量的佐证，但开源社区热度与系统技术贡献之间没有因果关系。Agent Hub 中除 CodeAct Agent 外的 Agent 实现在评估中表现如何、社区贡献的 MicroAgent 质量如何，均未讨论。

5. **安全性讨论浮于表面**：论文在附录 A 提到安全挑战，但对 Docker 沙箱的逃逸风险、Agent 通过浏览器访问外部服务的安全边界、多 Agent 委派中的权限控制等关键问题缺乏深入分析。对于一个让 AI 执行任意代码的平台，安全性应是核心贡献而非附录。

6. **可复现性存疑**：论文使用的模型版本（如 gpt-4o-2024-05-13、claude-3-5-sonnet-20240620）已经过时，且 API 模型的行为可能随时间变化。论文未提供固定的模型快照或确定性评估方案。

## 七、AI Infra / MLSys 视角

1. **Agent Runtime 的沙箱设计值得借鉴**：OpenHands 通过 Docker 容器 + REST API 的方式将 Agent 执行环境与宿主机隔离，同时支持任意 Docker 镜像。这种设计思路可以迁移到 AI Infra 中的模型评估、自动化实验管道、CI/CD 中的 AI 辅助测试等场景。

2. **Agent-Computer Interface (ACI) 的设计哲学**：AgentSkills 库的"最小化添加"原则——只在 LLM 无法直接编写代码时才封装工具——为 AI Infra 中设计 LLM 辅助运维工具提供了参考。过度封装会限制 Agent 的灵活性，不封装又会导致可靠性不足。

3. **值得跟进的方向**：
   - **Agent 驱动的 MLOps**：将 OpenHands 的 CodeAct 架构应用于模型训练流水线的自动调试、超参搜索、分布式训练故障排查
   - **AI Infra 自动化测试**：利用 Agent 的代码执行 + 网页浏览能力，自动化端到端的 ML 系统测试（如模型部署验证、推理服务压测）
   - **Event Stream 架构与可观测性**：Event Stream 的设计与分布式系统中的 event sourcing 模式高度相似，可以用于构建 AI 系统的可观测性和回放调试工具

4. **局限性**：当前 OpenHands 的 Agent 缺乏对 GPU 资源管理、分布式训练环境、模型权重操作等 AI Infra 特有操作的原生支持。将其扩展到 MLSys 领域需要大量的 domain-specific skills 和环境适配工作。

---

## 八、总结

OpenHands 是一个功能全面的开源 AI Agent 平台，通过 Event Stream 架构、Docker 沙箱执行环境、可扩展工具库和多 Agent 委派机制，为构建通用型软件开发 Agent 提供了统一框架。其 CodeAct Agent 在不做任务特定优化的情况下，在软件工程、网页浏览和通用辅助三大类 15 个基准测试上展现了合理的通用性能。作为工程平台的价值（统一架构、社区生态、评估框架）可能大于其在单项任务上的技术突破。主要局限在于通用 Agent 在各专项任务上距离 SOTA 仍有差距，以及安全性分析的不足。
