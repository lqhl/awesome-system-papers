## 一、背景

云数据中心中 VM 调度到物理主机的决策直接决定了资源利用效率，这是一个信息不完整的 NP-hard 问题。在 IaaS 环境下，糟糕的 VM 放置会导致主机资源搁浅（stranding）——剩余资源形状无法容纳新 VM。VM 分配还影响空闲主机数量，进而影响节能优化、大型 VM 的可调度性以及系统维护速度（如安全补丁的滚动更新）。

先前工作（Microsoft 的 Lifetime Alignment）已证明利用预测的 VM 生命周期可以改善调度质量，但其采用一次性预测（one-shot prediction），当预测出错时问题会累积——例如一个被误判为短命的长寿 VM 会阻止整台主机释放。

---

## 二、要解决的问题

1. **一次性预测的脆弱性**：先前 SOTA（LA-Binary）在 VM 创建时做一次生命周期预测，之后不再更新。预测误差会随时间累积，严重时一台主机上放 70 个"短命" VM，有超过 50% 概率存在一个实际长寿的 VM，导致整台主机无法释放。
2. **点预测的信息损失**：VM 生命周期本质上是多模态分布（如某类 VM 可能活 1 天或 1 周），单值预测无法捕捉这种不确定性，也无法随着 VM 运行时间的增加更新估计。
3. **碎片整理与维护被忽视**：先前工作只关注初始放置的 bin packing 质量，未考虑主机碎片整理（defragmentation）和系统维护中的 VM 迁移优化。
4. **多维资源约束**：与一维的内存分配不同，VM 调度需要同时考虑 CPU、DRAM、SSD 等多维资源，简单迁移 C++ 内存分配的方法不可行。

---

## 三、洞察与设计

**关键洞察**：VM 的生命周期不应被视为一个固定的点预测值，而应建模为概率分布，并且随着 VM 实际运行时间的增加，可以通过条件期望 E(T_r | T_u) 持续修正预测。这种"重预测"（reprediction）能从根本上纠正初始预测错误，使调度器的决策始终基于最新信息。

基于此洞察，系统设计了三个相互配合的算法：

1. **NILAS（Non-Invasive Lifetime-Aware Scheduling）**：非侵入式方法，在现有调度器的 bin packing 评分层之上增加一个 temporal cost 维度。对候选主机上所有 VM 重新预测剩余生命周期，计算新 VM 预期退出时间与主机退出时间的差值作为 temporal cost，通过量化桶（0m, 30m, 60m, ... , 168h）融入词典序评分函数。当所有其他评分维度打平时，NILAS 优先选择生命周期对齐的主机。

2. **LAVA（Lifetime-Aware VM Allocation）**：更激进的重设计。与 LA/NILAS 将相似生命周期的 VM 放在一起的策略相反，LAVA 将短命 VM 放到有长寿 VM 的主机上（要求至少短 10×），避免延长主机的整体生命周期。主机有三种状态（empty → open → recycling），以及生命周期类别（LC1: <1h, LC2: 1-10h, LC3: 10-100h, LC4: 100-1000h）。当 open 主机资源使用超过 90% 时转为 recycling，只接受更低生命周期类的 VM。当所有 residual VM 退出后，主机降一级生命周期类；当 VM 超出预期生命周期时，主机升一级（纠正欠预测）。

3. **LARS（Lifetime-Aware ReScheduling）**：利用生命周期预测优化碎片整理和维护时的 VM 迁移顺序——优先迁移最长寿的 VM，让短命 VM 在迁移过程中自然退出，减少总迁移次数。

## 四、实现细节

- **ML 模型**：使用 GBDT（Yggdrasil 库），输入特征包括 zone、VM family、VM shape、是否挂载本地 SSD、项目元数据等。将单个训练样本扩展为多个不同 T_u 值的样本（12.5%, 25%, ... 的原始生命周期），直接回归 E(T_r | T_u)。在约 1M 样本上训练，全球车队共用一个模型。
- **模型部署**：将模型编译进 Borg Prime 二进制文件（而非独立推理服务器），推理中位延迟仅 9μs，比 LA 的方案快 780×。二进制增大不到 10MB，CPU/DRAM 开销可忽略不计。模型随 Borg 一起灰度发布和金丝雀测试。
- **模型精度**：在短/长寿 VM 二分类（7 天阈值）上达到 99% precision @ 70% recall。模型精度在部署后数周内保持稳定，约每月重训一次。
- **主机评分缓存**：对大型 zone，维护主机生命周期评分缓存，仅在 VM 进出或主机到期时重新评分，其余按可配置间隔（如 60s）刷新。
- **仿真器**：开发了事件驱动仿真器，使用生产调度代码库，可回放生产 trace 进行离线评估。
- **A/B 测试**：生产环境中将主机分两半，分别运行新旧算法进行对比。

## 五、实验结果

| 指标 | NILAS | LAVA | LA-Binary | 说明 |
|------|-------|------|-----------|------|
| 空闲主机增加（仿真，24 个 C2 pool 平均） | +6.1 pp | +6.5 pp | +5.0 pp | 相对生产基线 |
| 空闲主机增加（Oracle 预测） | +9.5 pp | — | +7.5 pp | 证明 reprediction 上限更高 |
| CPU 搁浅减少（生产 whole-pool） | ~3% | — | — | 95% CI: [-5.5%, -0.49%] |
| 内存搁浅减少（生产 whole-pool） | ~2% | — | — | 95% CI: [-3.8%, -0.23%] |
| VM 迁移减少（LARS） | — | — | — | ~4.5% |
| 模型推理延迟（中位数） | 9 μs | 9 μs | ~7 ms (LA) | 嵌入二进制 vs 推理服务器 |

## 六、批判性分析

1. **LAVA 仅有仿真结果**：论文最核心的 LAVA 算法（与 NILAS 的关键区别是"反向放置"策略）仅在仿真中评估，未部署生产。所有生产数据均来自更保守的 NILAS。LAVA 在仿真中相对 NILAS 的优势仅 0.4 pp（6.5 vs 6.1），统计显著性未讨论。论文标题以 LAVA 命名但实际生产贡献来自 NILAS，有标题夸大之嫌。

2. **LARS 使用 Oracle 生命周期评估**：碎片整理实验（LARS）使用了完美预测的 Oracle 生命周期，4.5% 的迁移减少在实际预测误差下能保持多少未知。

3. **与 LA-Binary 的公平性存疑**：作者承认无法完美复现 Microsoft 的 LA 环境（不同数据中心、不同 ML 特征），且明确给 LA-Binary 使用了同一个 LAVA 模型但禁用了 reprediction。LA 原始设计可能有不同的模型优化方式，这种"公平"比较实际上有利于 LAVA 团队。

4. **仿真覆盖面有限**：24 个 C2 pool 的仿真只覆盖了一种 VM family（性能优化型）。E2（动态调整型）仅有生产 pilot 数据，缺少仿真对比。论文提到不同 pool 间存在"偶尔的反转"（inversions），但未深入分析失败案例。

5. **生产工程贡献 vs 算法创新的边界模糊**：论文的大量价值来自工程实践（模型嵌入二进制、A/B 测试方法论、灰度发布流程），这些对工业界有参考价值但算法层面的理论贡献（Section 4.1）仅给出了 Ω(m) 的渐近下界，缺乏对实际提升幅度的理论解释。

6. **能耗影响未量化**：论文多次提及空闲主机可进入低功耗模式以节能，但从未给出实际的能耗节省数据。

## 七、AI Infra / MLSys 视角

1. **ML for Systems 的生产部署范式**：本文是"将 ML 模型嵌入系统二进制"这一部署模式的典型案例。9μs 的推理延迟使得 reprediction 成为可能——这个设计选择对 AI Infra 中的在线决策系统（如 KV cache 管理、GPU 显存分配）有直接借鉴意义。将模型编译进系统二进制而非依赖外部推理服务，消除了循环依赖和可靠性风险。

2. **生命周期预测在 AI 推理系统中的应用**：LAVA 的核心思想——用生命周期分布而非点估计来指导资源分配——可以迁移到 LLM serving 场景。例如：
   - 预测请求的 KV cache 占用时长，指导 KV cache 的放置和驱逐策略
   - 预测 LoRA adapter 的热度生命周期，优化 adapter 换入换出
   - 预测 GPU 任务的执行时长分布，改善 GPU 集群的 bin packing

3. **Reprediction 机制的通用性**：随着任务执行，利用已观测的运行时间更新剩余时间估计，这个思路可用于：
   - 分布式训练中的 straggler 检测与任务重分配
   - 推理请求的 SLO 违约预警（观测到已生成 token 数后更新完成时间估计）

4. **值得跟进的方向**：
   - 将 LAVA 的生命周期分布预测方法应用于 GPU 集群的 job scheduling，特别是训练任务和推理任务混部场景
   - 探索 reprediction 在 LLM serving 的 prefill/decode 阶段调度中的应用——prefill 阶段结束后可以更准确估计 decode 阶段时长
   - LAVA 的"反向放置"策略（短命任务填充长寿任务主机的空隙）在 GPU 集群中可用于将短推理请求与长训练任务混部

---

## 八、总结

LAVA 提出了基于生命周期概率分布的 VM 调度方案，核心创新在于"重预测"机制——利用 VM 已运行时间持续修正生命周期估计，从根本上缓解了一次性预测的累积误差问题。系统设计了三个互补算法（NILAS、LAVA、LARS），其中 NILAS 已在 Google 全球云基础设施生产部署，带来 2.3-9.2 pp 的空闲主机增加和约 3% 的 CPU 搁浅减少。工程上将 GBDT 模型编译进调度器二进制的做法实现了 9μs 推理延迟，是 ML for Systems 生产落地的优秀范例。主要局限在于论文标题主打的 LAVA 算法仅有仿真验证，且相对 NILAS 的额外收益有限。
