# YOUMU: Efficient Columnar Data Pipeline for LLM Training

**作者**：Tianle Zhong (University of Virginia), Jiechen Zhao (University of Toronto), Qiang Su (The Chinese University of Hong Kong), Geoffrey Fox (University of Virginia)
**会议**：MLSys 2025

## 一、背景

LLM 训练依赖万亿级 token 的海量数据集，这些数据集在数据准备阶段（采集、清洗、去重）通常以列式存储格式（如 Apache Parquet）保存，受益于其高压缩率和高效的扫描操作。HuggingFace Hub 作为主流数据集托管平台，默认采用 Parquet 格式。

然而，训练阶段需要对数据进行随机 shuffle 以保证模型精度，而列式存储的默认 I/O 粒度是 column chunk（通常数百 MB 甚至 GB 级），与 GPU 所需的细粒度随机访问模式严重不匹配。当前的解决方案要么将 Parquet 转换为其他格式（如 JSON、Feather），导致数十 TB 的冗余存储和繁琐的版本管理；要么用大量内存缓存整个数据集来支持随机访问。

---

## 二、要解决的问题

1. **格式转换开销巨大**：将 Parquet 转换为训练友好的格式需要约 3× 额外存储空间（如 43TB FineWeb 转 JSON 需 95TB 额外空间），且频繁的模型迭代导致持续的格式转换维护成本。

2. **直接访问列式数据效率极低**：不做格式转换直接从 Parquet 读取训练数据时，由于 shuffle 需要细粒度随机访问而列式存储只支持粗粒度 chunk I/O，有效带宽利用率仅约 0.1%，性能下降超过 100×。

3. **现有替代方案各有缺陷**：
   - **分布式内存方案**（如 Ray Data）：将数据集缓存到集群内存中，内存开销与数据集大小成正比，TB 级数据集难以承受，且节点间数据交换与 GPU 通信竞争带宽。
   - **Memory-mapped I/O**（如 HuggingFace Datasets）：随机访问触发频繁 page fault 和 cache thrashing，性能严重退化；memory-mapped table 本身内存开销也很高（200B token 数据集单实例约 12GB）。
   - **Streaming/local shuffle**：只在小窗口内 shuffle，shuffle 质量差，显著影响模型精度。

---

## 三、洞察与设计

**关键洞察**：对于 TB 级 LLM 数据集，以 page（KB-MB 级）为粒度进行随机访问，相比以 column chunk（GB 级）为粒度，能提供数量级更高的 shuffle 随机性（数十亿个 page vs 数千个 chunk），同时恰好匹配 SSD 的最优随机访问粒度，从而同时解决 shuffle 质量和 I/O 效率问题。

基于此洞察，YOUMU 的核心设计是**将 shuffle 和磁盘 I/O 统一到 page 级别**，消除粒度不匹配问题：

1. **Global Page Index（控制平面）**：初始化时收集所有 Parquet 文件的 column chunk 元数据，构建跨整个数据集的三维页面索引（file index × chunk index × page index），以及文件级和 chunk 级的页号偏移列表。通过 Layered Binary Search 实现从随机 page ID 到物理地址的快速映射。

2. **Page-level I/O（数据平面）**：根据控制平面提供的物理地址和元数据，直接从磁盘读取指定 page 数据并解压。由于 Parquet page 是列内的子单元，天然跳过无关列，节省 I/O 带宽。

3. **Aggressive Buffer Shuffle**：维护固定大小的内存 buffer，每消耗一个 page 的行数就立即从磁盘读取新的随机 page 填入 buffer 并重新 shuffle，相比标准 double buffering 仅在初始化时 shuffle 一次，提供了更高的 shuffle 质量。

4. **No cache, only buffer**：因为训练数据每 epoch 只访问一次，缓存收益极低。YOUMU 只保留固定大小 buffer 用于隐藏 I/O 延迟和增强 shuffle 质量，内存开销与数据集大小解耦。

## 四、实现细节

- 基于 Apache Parquet 和 Arrow 的官方 Rust 实现，核心功能约 500 行 Rust 代码。
- 通过 PyO3 提供 Python bindings，返回 PyArrow 对象，与现有生态兼容。
- PyTorch Dataset 集成只需约 100 行 Python 代码，通过三个核心 API：
  - `get_idx_matrix(file_paths, col_id)`：构建全局页面索引
  - `shuffle_index(index_matrix)`：生成随机页面访问顺序
  - `read_page(global_page_idx)`：读取并解码指定页面
- 支持通过 Arrow 数组零拷贝转换为 DataFrame 或 DLPack tensor 格式。
- 也支持 row-wise 完全随机 shuffle（通过追踪 page 内行索引对），但会牺牲部分 I/O goodput。
- 每个 GPU 对应一个 CPU 进程，负责 I/O 和解码，CPU 开销在现代节点上合理。

## 五、实验结果

**实验环境**：16 节点集群，每节点 384GB DRAM（150GB shared memory），100Gb/s InfiniBand 互连，WekaFS 远程存储。每节点 8 个并发数据加载进程。

**模型精度（Perplexity）**：

| Shuffle 方法 | WikiText-103 (line) | WikiText-103 (doc) | arXiv | algebraic-stack |
|---|---|---|---|---|
| Row (理想) | 12.671 | 12.718 | 12.316 | 6.318 |
| Page (YOUMU 1MB) | 12.884 (+0.213) | 12.874 (+0.156) | 12.323 (+0.007) | 5.071 (-1.247) |
| Streaming (基线) | 13.371 (+0.700) | 13.570 (+0.852) | 12.655 (+0.339) | 24.741 (+18.423) |
| No shuffle (最差) | 14.324 (+1.653) | 14.127 (+1.409) | 12.801 (+0.485) | 285.424 (+279.106) |

- YOUMU page-level shuffle 的 perplexity 退化仅为 no shuffle 的 10.6%，而 streaming 是 53.3%。
- 在 C4 English 大数据集上，YOUMU 10KB page 甚至略优于理想的 full random shuffle。

**系统效率**：

| 指标 | YOUMU (page) | Ray Data (full) | HuggingFace |
|---|---|---|---|
| 内存开销 (200B token) | ~30 GB/node | ~150 GB/node | ~120 GB/node |
| Batch latency | ≤3 ms | ~1 ms | 超过阈值 |
| Shuffle wall time | <10s (仅首 epoch 元数据收集) | 数千秒 | N/A |

- YOUMU 内存开销比 HuggingFace 低最多 82%，比 Ray Data 低最多 76%。
- Ray Data 在数据集超过 1T token 时因磁盘 spilling 超 10TB 触发系统 OOM。
- YOUMU page shuffle 的 batch latency 约 3ms，比 GPU 无数据等待阈值（1.9s）低三个数量级。

## 六、批判性分析

1. **模型精度实验规模偏小**：预训练实验仅使用 160M 参数的小模型，作者承认受算力限制。小模型对 shuffle 质量的敏感度可能与 7B+ 模型不同，结论的外推性存疑。continual training 也只做了 5000 步。

2. **algebraic-stack 上 YOUMU 超越 full shuffle 的解释不够严谨**：作者将 YOUMU 在 algebraic-stack 上 perplexity 优于理想 full shuffle（5.071 vs 6.318）归因于"better shuffle randomness doesn't always lead to better accuracy"，但这本质上是在说 page shuffle 并非严格劣于 row shuffle——这需要更深入的理论分析而非经验观察。

3. **Batch latency 的公平性问题**：YOUMU page shuffle 的 3ms batch latency 与 Ray Data 的 1ms 相比已有 3× 差距。虽然都远低于 1.9s 阈值，但该阈值来自作者自己的小模型实验。对于大规模训练中的 microbatch/pipeline parallelism 场景，iteration time 可能显著缩短，此时 3ms vs 1ms 的差距是否仍然可忽略未被讨论。

4. **存储系统假设较强**：实验全部基于 WekaFS（高性能并行文件系统）+ SSD。但论文的核心 motivation 是"减少高性能存储上的冗余数据"，在普通网络存储或 HDD 上 page-level random read 的性能表现可能完全不同，论文未讨论这一限制。

5. **与格式转换方案缺乏端到端对比**：论文主要强调格式转换带来的存储和维护成本，但从未直接对比"Parquet → JSON/Arrow + 训练"与"YOUMU 直接从 Parquet 训练"的端到端训练时间和总成本，读者无法量化实际节省。

6. **Aggressive buffer shuffle 的理论分析缺失**：论文声称 page-level shuffle + buffer shuffle 提供了接近 full random 的 shuffle 质量，但缺乏严格的理论分析（如 shuffle 熵的量化比较）。

## 七、AI Infra / MLSys 视角

1. **数据管道优化是被忽视的战场**：当前 AI Infra 社区的注意力集中在计算优化（FlashAttention、并行策略）和通信优化（gradient compression、overlap），但 YOUMU 揭示了数据 I/O 管道的效率问题同样重要——尤其是在数据集规模持续增长、存储成本与 GPU 成本可比的今天。

2. **Page-level access 的思路可迁移**：YOUMU 的核心 insight——将 I/O 粒度匹配到存储设备最优访问粒度——不仅适用于训练数据加载，也可应用于：
   - KV cache offloading 到 SSD 时的数据组织
   - Checkpoint 的增量写入和随机恢复
   - 多模态训练中图像/视频数据的高效随机访问

3. **值得跟进的研究方向**：
   - **与 data preprocessing 的联合优化**：YOUMU 目前假设预处理已完成，能否将 tokenization、filtering 等操作与 page-level I/O 流水线化？
   - **多模态数据的 page-level access**：Parquet 中存储图像/音频等非文本列时，page-level shuffle 的效果和开销如何？
   - **与 tensor offloading / checkpointing 的内存协调**：YOUMU 节省了大量内存，这些内存如何被 ZeRO-Offload 或 checkpointing 利用以提升整体训练效率？

4. **最有价值的切入点**：将 YOUMU 的设计思路扩展到 online data mixing / curriculum learning 场景——这些场景需要根据训练动态调整数据采样分布，而 YOUMU 的 page-level 细粒度访问天然支持灵活的采样策略，比 chunk-level 方案有明显优势。

---

## 八、总结

YOUMU 提出了一种基于 page-level I/O 的 LLM 训练数据管道，通过将 shuffle 粒度与 SSD 最优访问粒度统一到 page 级别，消除了列式存储与训练随机访问之间的粒度不匹配问题。它避免了昂贵的格式转换，在保持接近理想 shuffle 质量的同时，内存开销比分布式内存方案低 ~80%。主要局限在于精度评估仅在小模型上进行，且对高性能 SSD 存储有较强依赖。适用于大规模 LLM 训练中数据集以 Parquet 存储、需要控制存储和内存成本的场景。
