## 1. 研究背景与动机

LLM 训练是极度数据密集型的——通常需要数万亿级别的 token。LLM 数据集在数据准备阶段以 Parquet 为代表的列式格式存储和清洗，但传统的训练数据管道需要将列式格式转换为行式格式（如 JSON）才能被训练框架使用。这一转换过程带来两个显著问题：

1. **存储成本倍增**：以 FineWeb 数据集为例（43 TB Parquet → 95 TB JSON），存储开销接近 3 倍。
2. **维护复杂度增加**：多个格式的版本控制和数据一致性管理显著增加了工程负担。

避免格式转换的直接方案则面临"粒度不匹配"问题：列式存储的默认 I/O 单位是 column chunk（通常数百 MB 到数 GB），而 LLM 训练需要细粒度的随机访问（以行为单位 shuffled），导致 I/O 有效带宽利用率极低（仅约 0.1%）。

## 2. 研究问题与核心挑战

核心问题：如何在不需要格式转换的前提下，实现高效、低内存占用的 LLM 训练数据管道？

主要挑战：

1. **粒度鸿沟（Granularity Gap）**：列式存储的 chunk 级别 I/O 与训练所需的细粒度随机访问之间的矛盾。

2. **存储效率与随机访问的矛盾**：粗粒度 I/O 节省存储但浪费带宽；细粒度 I/O 匹配随机访问但每个请求的数据量过小。

3. **Shuffle 质量与效率的权衡**：高质量 shuffle（全随机）代价高昂，低质量 shuffle（streaming local shuffle）损害模型精度。

4. **超大规模数据集的内存管理**：TB 级数据集无法全部预加载到内存，而磁盘 I/O 必须足够高效以满足 GPU 的喂数据需求。

## 3. 主要贡献

1. **YOUMU 系统**：首个无需格式转换即可直接从 Parquet 列式存储向 GPU 喂数据的 LLM 训练数据管道，实现细粒度 page 级 I/O。

2. **Global Page Index + 层级二分搜索索引翻译**：通过构建覆盖整个数据集的全局 page 地址索引（文件索引 × column chunk 索引 × page 索引），实现 $O(\log n)$ 复杂度的随机 page 访问。

3. **Page 级 shuffling + Aggressive Buffer Shuffle**：Page 级粒度的随机访问确保足够的 shuffle 质量（接近行级全 shuffle），同时引入激进的缓冲区 shuffle 策略进一步提升 shuffle 质量。

4. **极低内存占用**：仅维护固定大小 buffer（~GB 量级），无需缓存整个数据集。相比分布式内存方案，内存占用减少 ~80%。

## 4. 核心方法与设计

### 4.1 系统架构

YOUMU 由三个核心组件构成：

- **控制平面（Control Plane）**：收集 Parquet 元数据，构建 Global Page Index Store
- **数据平面（Data Plane）**：Page Fetcher 根据 Global Page Index 抓取物理 page 数据，Page Decoder 解码压缩数据
- **Python API**：与 PyTorch Dataset 接口兼容，仅需约 100 行 Python 代码即可集成

### 4.2 Global Page Index

Parquet 的 PageIndex 仅在单个 column chunk 内有效。YOUMU 构建跨越整个数据集的三维索引（file_idx, chunk_idx, page_idx），通过层级二分搜索（Algorithm 1）将随机 page 访问顺序 ID 转换为物理地址和元数据：

```
输入: 全局 page ID
1. 二分搜索文件级 page 偏移列表 → 确定文件
2. 二分搜索 column chunk 级 page 偏移列表 → 确定 column chunk
3. 计算 chunk 内 page 索引
```

### 4.3 Page 级 I/O 与 Decoding

给定 page 物理地址范围，直接从文件读取指定数据段（自然跳过不相关的 column），加载到 DRAM 后根据 column chunk 元数据（数据类型、解压算法）进行解码，最终构造 Arrow 数组用于 zero-copy 转换为 PyTorch tensor。

### 4.4 Aggressive Buffer Shuffle

标准双缓冲仅在初始化时 shuffle 一次。YOUMU 采取更激进的策略：当缓冲区中消耗了约一页数据量时，立即读取新 page 加入缓冲区并执行 shuffle（Algorithm 2）。这在 page 级 shuffle 基础上进一步增强了行级 shuffle 质量。

### 4.5 Rust 实现

基于 Apache Arrow 官方 Rust 实现，通过 PyO3 提供 Python 绑定。核心功能约 500 行 Rust 代码，在不修改 PyArrow API 的前提下提供替代 I/O 后端。

## 5. 实现细节

**技术栈**：Rust + PyO3 + Apache Arrow

## 6. 实验结果

### 6.1 模型精度（Perplexity）

测试在 WikiText-103、arXiv abstracts、C4 数据集上的困惑度：

| Shuffle 方法 | WikiText-103 (doc) | arXiv | algebraic-stack |
|-------------|-------------------|-------|---------------|
| Row (理想) | 12.718 | 12.316 | 6.318 |
| YOUMU (1MB page) | 12.874 (+0.156) | 12.323 (+0.007) | 5.071 (-1.247) |
| Streaming (基准) | 13.570 (+0.852) | 12.655 (+0.339) | 24.741 (+18.423) |
| No shuffle (最差) | 14.127 (+1.409) | 12.801 (+0.485) | 285.424 (+279.106) |

YOUMU 的 page 级 shuffle 在大多数数据集上接近理想行级 shuffle，显著优于 streaming shuffle。YOUMU 1MB 甚至在 algebraic-stack 数据集上略微超越理想 shuffle。

### 6.2 内存占用

YOUMU 内存占用相比 HuggingFace 减少 82%，相比 Ray Data 减少 76%。200B token 数据集仅需 30GB 内存（相比之下 HuggingFace 需要 ~200GB）。

### 6.3 吞吐量与 Batch 延迟

YOUMU 的 batch 延迟（page shuffle）最高仅 3ms，远低于 GPU 数据等待阈值；全 shuffle 模式下 0.4s 延迟仍可接受。

## 7. 潜在问题与局限性

1. **大 page 尺寸的带宽浪费**：当 page 尺寸较大（如 1MB）而每次训练仅需要少量 token 时，仍存在一定程度的 I/O 浪费（虽然远好于 GB 级 column chunk）。

2. **跨节点场景未充分验证**：实验主要在单节点 + 远程存储配置下进行，多节点 shuffle 场景（如 FineWeb 级别的分布式训练）的表现有待验证。

3. **与 HuggingFace 的公平性**：论文提到 HuggingFace 需要将 Parquet 转换为 Feather 格式（2.6TB vs 500GB），这一不公平的比较可能导致 HuggingFace 内存占用数字被夸大。

4. **元数据开销**：Global Page Index 需要在初始化时将所有文件的 page 元数据缓存到内存，对于超大规模数据集（万亿 token），元数据本身可能达到 GB 量级。

5. **与现有训练框架的集成**：虽然声称"minimal modifications"，但集成仍需要用户编写 Python Dataset 代码，不如开箱即用的方案方便。

## 9. 个人评注

YOUMU 精准地抓住了 LLM 训练数据管道中一个被长期忽视的效率瓶颈——列式存储的粒度不匹配问题。论文的 Global Page Index 设计和层级二分搜索索引翻译方法体现了扎实的系统思维。

从技术角度看，Page 级 shuffle 质量能够接近理想行级 shuffle 的发现具有重要意义——这意味着无需为 shuffle 质量付出格式转换的代价。实验设计也比较完善，覆盖了从预训练到持续训练、从通用语料到领域特定语料等多种场景。

然而，论文在某些方面仍可加强：多节点分布式训练场景的实验缺失、与 Petastorm 的对比不够充分、以及 page 尺寸选择缺乏自适应机制的讨论。总体而言，这是一篇系统贡献扎实、工程实现精良的工作，对 LLM 训练系统的数据管道优化具有直接参考价值。
