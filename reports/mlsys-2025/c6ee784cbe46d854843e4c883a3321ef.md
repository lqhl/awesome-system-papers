# TileLink: Generating Efficient Compute-Communication Overlapping Kernels using Tile-Centric Primitives

## 一、背景

大规模深度学习模型在 NLP、视觉、推理等领域取得了 SOTA 性能，但其巨大的计算需求必须依赖分布式并行执行。Intra-layer parallelism（层内并行）是分布式模型执行的基本构件，包括 tensor parallel FFN 和 sequence parallel self-attention。在并行执行中，设备间通信（AllGather、ReduceScatter 等集合通信）占总执行时间的 10%–50%，成为显著的性能瓶颈。

将通信与计算重叠（compute-communication overlapping）是隐藏通信开销的有效策略。现有方法主要有两种：operator decomposition（算子分解）和 kernel fusion（核融合）。算子分解实现简单但性能受限于 host 同步开销、低 cache 利用率和资源量化低效；核融合性能优越但需要大量底层硬件专业知识，开发成本极高（如 FLUX 约需 2000 行 CUDA 代码）。

---

## 二、要解决的问题

1. **算子分解方法性能不佳**：分解后的小 kernel 无法充分利用设备算力（如 Async-TP PyTorch 在某些配置下甚至没有 speedup），且 host 驱动的同步引入不可忽略的开销。
2. **核融合方法开发难度大**：需要直接操作底层 barrier 控制和通信指令（如 GPU 上的 `ld.global.acquire`、`red.release`），对硬件专业知识要求极高，难以跟上算法快速演进。
3. **现有编译器灵活性不足**：CoCoNet 和 Dist-Einsum 等编译器只能生成固定的重叠模式，无法在 tile size、tile order、resource mapping 等维度进行灵活优化。
4. **MoE 等动态工作负载缺乏支持**：现有融合库（FLUX）和框架（Async-TP PyTorch）不支持 MoE 层的通信-计算重叠，因为 MoE 的动态路由导致数据分片无法在编译时确定。

---

## 三、洞察与设计

**关键洞察**：通信和计算的优化空间本质上是正交的——它们可以使用不同的 tile size、不同的 tile order（数据遍历顺序）和不同的硬件资源映射（DMA engine vs. SM），如果将这两个设计空间解耦，就可以让每一方独立选择最优配置，通过 tile 粒度的 barrier 进行生产者-消费者同步，而不需要紧耦合的 kernel 设计。

基于这一洞察，TILELINK 采用前端-后端架构：

**前端**：定义了一组 tile-centric primitives，分为两类：
- **Signal primitives**（信号原语）：`producer_tile_notify` / `consumer_tile_wait`（生产者-消费者关系），`peer_tile_notify` / `peer_tile_wait`（跨 rank 同步），`rank_notify` / `rank_wait`（host 侧同步）。这些原语提供严格的 memory consistency 语义（release/acquire semantics）。
- **Data primitives**（数据原语）：`tile_push_data` / `tile_pull_data`（设备侧数据传输，支持 pull 和 push 两种模式），`rank_copy_data`（host 侧 DMA 传输）。

前端将通信-计算的设计空间解耦为三个子空间：
1. **Tile size**：通信和计算可以选择不同的 tile 大小（如通信 128×128，计算 128×256）
2. **Tile order**：通信可以用 ring order 或 full-mesh all-to-all，计算可以等待不同数量 rank 的数据
3. **Resource mapping**：通信可以映射到 DMA engine 或 SM，计算映射到 Tensor Core

**后端**：通过 tile-centric mapping 将前端原语编译为底层硬件指令。Mapping 包括 shape mapping（tile ID → 张量切片范围）、rank mapping（tile ID → 设备 rank）、channel mapping（tile ID → 通信 barrier）。支持两种 mapping 模式：
- **Static mapping**：编译时用仿射变换计算，适用于固定数据分片（如 tensor parallel MLP）
- **Dynamic mapping**：运行时通过 lookup table 计算，适用于动态路由（如 MoE）

## 四、实现细节

TILELINK 基于 Triton 实现，扩展了 Triton 的语言特性：

- **编译流程**：Python 程序 → Python AST（解析 BlockChannel 参数，构建 tile-centric mapping）→ Triton IR（TILELINK 原语转为 `ElementwiseInlineAsmOp`）→ Triton GPU IR + Distributed IR → LLVM IR → PTX
- **BlockChannel 参数**：封装分布式 mapping 元数据，包括当前 rank、world size、barrier 配置、producer/consumer block 关系
- **Distributed IR**：TILELINK 引入的新 IR 层，用于将通信指令翻译为 LLVM IR
- **运行时**：使用 NVSHMEM 初始化分布式环境和分配共享内存
- **内存一致性编译**：在 multi-stage pipeline 优化中，TILELINK 在原语与后续 load/store 之间强制严格数据依赖，防止编译器重排序破坏 release/acquire 语义
- **单设备优化**：自动分配 register/shared memory buffer、合并全局内存访问、避免 bank conflict、multi-stage pipeline 优化、TMA 和 Tensor Core 映射

核心代码量：用户只需约 200 行 Python 代码即可表达一个完整的 overlapping kernel（相比 FLUX 约 2000 行 CUDA）。

## 五、实验结果

实验平台：8×H800 GPU（单节点）和 16×H800 GPU（双节点），使用 NVLink 互联。

### 单层性能（8×H800）

| 工作负载 | 基线 | TILELINK Speedup |
|---------|------|-------------------|
| AG+GEMM（MLP） | cuBLAS+NCCL | 1.27×（FLUX 的 94.5%） |
| GEMM+RS（MLP） | cuBLAS+NCCL | 1.25×（超过 FLUX 1.28×） |
| Full MLP | cuBLAS+NCCL | 1.24×（FLUX 的 101.4%） |
| MoE 第一部分（AG+Gather+GroupGEMM） | vLLM | 1.51× |
| MoE 第二部分（GroupGEMM+Scatter+Reduce+RS） | vLLM | 1.31× |
| Full MoE | vLLM | 1.14×；vs cuBLAS+NCCL 最高 20.76× |
| Self-attention | PyTorch non-overlap | 5.04× |
| Self-attention | Ring Attention | 1.97× |

Self-attention 平均隐藏了 43.9% 的通信开销。

### 端到端性能

| 配置 | 模型 | 平均 Speedup vs PyTorch |
|------|------|------------------------|
| 8×H800 | 8 个 LLM（dense + MoE） | 1.32× |
| 8×H800 | Dense 模型 | 1.20× |
| 8×H800 | MoE 模型 | 1.54× |
| 16×H800（双节点） | 8 个 LLM | 1.29× |

测试模型包括 GPT-3 6.7B、LLaMA-2 7B/13B/70B、GPT-3 175B、Mixtral 8x7B/8x22B、Qwen1.5 2.7B。

## 六、批判性分析

1. **Speedup 范围跨度极大（1.17×–20.76×）**：最高的 20.76× 来自 MoE 与 cuBLAS+NCCL（非重叠）的对比，这个基线本身就很弱（未做任何 gather/scatter fusion），不能代表 TILELINK 在 well-optimized 基线下的真实收益。更公平的对比是 vs vLLM（1.14×–1.51×），数字要低很多。

2. **AG+GEMM 未超越 FLUX**：在最核心的 AG+GEMM 场景下，TILELINK 只达到 FLUX 的 94.5%。论文将此描述为"comparable"，但 5.5% 的差距在高性能计算场景中并不可忽略，尤其是在 TILELINK 宣称 decoupled design space 应该带来更好性能的前提下。

3. **缺乏与 FLUX 在 MoE 上的对比**：论文指出 FLUX 和 Async-TP 不支持 MoE，因此 TILELINK 在 MoE 上的高 speedup 部分来自"有 overlap vs 无 overlap"的不公平对比。这让 MoE 的结果更像是 capability demonstration 而非 performance comparison。

4. **端到端 speedup 与单层 speedup 的落差**：Self-attention 单层有 5.04× speedup，但端到端仅 1.32×，因为"MLP 占主导"。这说明论文的端到端收益主要来自 MLP 层的 1.20× speedup，而非 attention 的大幅加速。

5. **只支持 NVIDIA GPU**：当前仅支持 NVIDIA GPU（通过 Triton + NVSHMEM），对 AMD GPU 和 TPU 的支持仅停留在"future work"层面。考虑到 Pallas 已在 TPU 上支持类似功能，跨平台泛化能力存疑。

6. **缺少 auto-tuning**：论文未讨论如何在解耦的三个子空间中自动搜索最优配置，用户仍需手动选择 tile size、tile order 和 resource mapping，这削弱了"编译器"的自动化宣称。

7. **Dynamic mapping 的 overhead 未量化**：论文引入 lookup table 支持 MoE 的动态映射，但未报告 lookup table 本身的访问开销和内存占用。

## 七、AI Infra / MLSys 视角

**启发与借鉴价值**：
- **Decoupled design space 的思路很有价值**：将通信和计算的 tile size / order / resource binding 解耦，允许独立优化，这个抽象比 FLUX 的紧耦合设计更具扩展性。未来如果通信拓扑或硬件资源变化（如新的 NVLink 版本、CXL 互联），只需调整对应子空间的配置。
- **Tile-centric primitives 作为 distributed kernel 的编程接口**：比 operator-centric primitives（NCCL）和纯底层汇编（FLUX）之间提供了一个有价值的中间抽象层。这个抽象层可以迁移到其他分布式 kernel 场景，如 pipeline parallelism 的 send/recv overlap、expert parallelism 的 all-to-all overlap。

**可迁移到 AI Infra 的技术**：
- Static/dynamic mapping 的二分法很适合 AI Infra 中固定 vs 动态通信模式的统一处理（如 MoE 的 expert 路由 vs dense model 的 tensor parallel）
- Memory consistency 语义（release/acquire）的编译器级强制，可以借鉴到其他需要 GPU 上 fine-grained synchronization 的场景

**值得跟进的方向**：
1. **Auto-tuning for overlapping kernels**：在 TILELINK 的 decoupled design space 上构建自动搜索框架，自动选择最优的 tile size、order 和 resource mapping 组合
2. **Inter-layer overlap**：将 tile-centric primitives 扩展到 pipeline parallelism 的跨层通信重叠
3. **跨平台后端**：将 TILELINK 的前端原语适配到 AMD GPU（ROCm/HIP）和 Google TPU（XLA），验证抽象的可移植性
4. **与 EP（Expert Parallelism）深度结合**：MoE 的 dynamic mapping 机制可以扩展为更通用的 token routing-aware overlap 策略

**最有价值的切入点**：在 TILELINK 的 decoupled space 上加入 auto-tuning，因为当前用户仍需手动选择配置，这是从"编译框架"到"真正的编译器"的关键一步。

---

## 八、总结

TILELINK 是一个基于 tile-centric primitives 的 compute-communication overlapping kernel 编译框架，核心贡献在于解耦通信和计算的设计空间（tile size / order / resource mapping），并通过 tile-centric mapping（static + dynamic）自动编译为底层 GPU 代码。在 8×H800 上实现了端到端平均 1.32× 的加速，MoE 场景最高达 20.76× speedup，同时将编程量从约 2000 行 CUDA 降低到约 200 行 Python。主要局限在于仅支持 NVIDIA GPU、缺乏 auto-tuning、AG+GEMM 场景未超越手写的 FLUX 库。适用于需要快速开发高性能分布式 kernel 的 AI Infra 团队，尤其在 MoE 等动态工作负载场景有独特优势。
