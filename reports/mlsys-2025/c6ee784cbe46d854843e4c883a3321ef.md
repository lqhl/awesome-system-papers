## 1. 研究背景与动机

大规模深度学习模型通常需要分布式系统来高效执行训练和推理。在模型并行场景下，设备间通信（AllGather、All2All 等）与计算的重叠是提升端到端性能的关键。然而，现有的通信-计算重叠方案存在以下问题：

1. **编译器方法局限**: 现有的基于编译器的方案（如 CoCoNet、Dist-Einsum）往往只能处理固定的通信模式，缺乏足够的灵活性来支持复杂模型中的多样化重叠策略。
2. **算子中心原语不足**: 现有的 tile-level 编程原语（如 GSPMD）限制在固定的重叠模式，无法针对特定算子进行细粒度优化。
3. **手动内核编写的工程负担**: 为每种新的工作负载编写自定义 CUDA 内核会带来巨大的工程成本。

TileLink 的目标是提供一个统一的、tile-centric 的编程抽象，能够系统性地探索从模型级、层级到算子级的整个设计空间。

## 2. 研究问题与核心挑战

**核心问题**: 如何设计一套统一且高效的 tile-centric 原语，使得在现代深度学习框架中实现各类通信-计算重叠策略变得系统化和自动化？

**具体挑战**:
1. **异构通信模式**: MoE（Mixture-of-Experts）中的 All2All、Attention 中的 AllGather 等不同通信模式需要不同的重叠策略。
2. **Tile 级依赖管理**: 需要在 tile 粒度上追踪生产者和消费者之间的关系，确保正确的执行顺序。
3. **编译时优化**: 需要从 Python AST 自动生成高效的 CUDA/HIP 内核。
4. **跨平台可移植性**: 内核需要能运行在 NVIDIA Hopper、AMD 等不同架构上。

## 3. 主要贡献

1. **Tile-centric 编程模型**: 提出了一套完整的 tile-centric 原语，包括信号原语（producer/consumer/peer tile notify）、通道映射（Tile ID → Rank → Barrier）和编译基础设施。
2. **灵活的重叠策略探索**: 支持模型级、层级和算子级的通信-计算重叠，覆盖 GEMM+RingReduceScatter、AllGather+MoE、AllGatherKV 等多种模式。
3. **自动内核生成**: 从 Python AST 自动生成高效的融合内核，使用 BlockChannel 类管理共享内存和 warp 级线程分配。
4. **与现有框架集成**: 可与 PyTorch、TensorFlow 等现有框架无缝集成，支持 Torch 算子级集成。

## 4. 核心方法与设计

### 4.1 Tile-centric 原语

TileLink 定义了三类核心原语：

| 原语名称 | 功能 |
|---------|------|
| `producer_tile_notify(tile_id, mode)` | 标记生产者 tile 完成，通知消费者 tile |
| `consumer_tile_wait(tile_id)` | 消费者 tile 等待所有依赖的生产者 tile 完成 |
| `peer_tile_notify(tile_id, rank)` | 标记当前 tile 完成，通知指定 rank 的对等 tile |

### 4.2 通道映射

TileLink 通过三个映射函数建立 tile 与硬件资源之间的关联：
- `f_S`: Tile ID → 设备 Rank
- `f_R`: Rank → 通信 Barrier
- `f_C`: Tile ID → 通信 Channel

### 4.3 Python AST 编译

TileLink 的编译管道将 Python AST 转换为可执行内核：

```
Python AST + BlockChannel class
    → 中间表示（包含 l2a, c, r 等 Channel 注解）
    → LLVM/NVCC 后端
    → 可执行 CUDA/HIP 内核
```

### 4.4 重叠模式设计

TileLink 支持三种典型的通信-计算重叠模式：

1. **GEMM + RingReduceScatter**: 在 GEMM 计算的同时进行 Ring 式的 ReduceScatter 通信
2. **AllGather + MoE**: 在 AllGather 通信的同时进行 MoE expert 的本地计算
3. **AllGather + FlashAttention**: 在 KV AllGather 的同时执行 FlashAttention 计算

### 4.5 融合内核设计

TileLink 支持基于融合的重叠方法，通过融合计算内核与通信内核来减少中间结果的存储和访存开销。

## 7. 潜在问题与局限性

1. **编程复杂度**: 虽然 TileLink 提供了高级抽象，但 tile 粒度的依赖管理仍然需要开发者对硬件架构有较深理解。
2. **编译时优化空间**: 目前基于 Python AST 的编译方案可能在复杂控制流场景下表达能力有限。
3. **硬件依赖**: 某些优化（如 NVSHMEM）依赖于特定硬件特性，在非 NVIDIA 架构上可能需要替代方案。
4. **与 PyTorch 等框架的集成深度**: 目前的 Torch 算子级集成可能还不足以支持所有模型架构。

## 8. 未来工作

1. 扩展 TileLink 原语以支持更多通信模式（如 ReduceScatter）
2. 探索更高级别的自动并行化优化
3. 在更多硬件架构上进行验证
4. 与主流深度学习框架的更深度集成

## 9. 个人评注

TileLink 的核心价值在于提供了一个系统化的方法来探索通信-计算重叠的设计空间。在大模型训练中，通信往往成为性能瓶颈，尤其是在 MoE 等稀疏激活场景下。TileLink 的 tile-centric 抽象允许开发者从更细的粒度来管理数据依赖和执行顺序，这是一个重要的创新。

论文的设计让我联想到 TVM 的 tensor expression 抽象——两者都试图通过高级抽象来实现自动优化。但 TileLink 更专注于通信-计算重叠这一特定场景，因此在设计上更加聚焦。

不过，论文在实验部分的数据呈现略显不足——很多图表只展示了相对性能，而缺乏绝对性能的对比。此外，作为一个相对底层的系统，TileLink 的易用性也是一个值得关注的问题。
