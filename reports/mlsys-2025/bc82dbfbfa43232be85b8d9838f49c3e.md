# SOLA: Optimizing SLO Attainment for Large Language Model Serving with State-Aware Scheduling

## 一、背景

LLM 服务系统需要在满足延迟 SLO（Service-Level Objectives）约束的前提下最大化吞吐量。LLM 推理包含 prefill 和 decode 两个阶段，对应两个关键延迟指标：TTFT（Time-to-First-Token）和 TPOT（Time-per-Output-Token）。现有系统（如 vLLM、Sarathi-Serve、DeepSpeed-FastGen）采用粗粒度的调度策略——要么优先 prefill（改善 TTFT 但恶化 TPOT），要么优先 decode（反之），要么通过 SplitFuse 做固定的折中——都无法根据运行时状态动态调整策略。

在实际服务场景中，SLO 通常同时对 TTFT 和 TPOT 设定约束（如 TTFT ≤ 500ms, TPOT ≤ 200ms），SLO attainment（满足 SLO 的请求比例）是衡量服务质量的核心指标。

---

## 二、要解决的问题

1. **TTFT 与 TPOT 之间的分布偏差（bias）**：现有固定策略导致一个指标远好于 SLO 约束，另一个却大量超标。例如 vLLM 默认优先 prefill，TTFT 很好但 35% 的请求 TPOT 超标。
2. **请求间延迟分布的高方差（variance）**：不同请求的延迟差异大，部分请求远低于 SLO 而另一些严重超标，说明系统资源分配不均衡。
3. **缺乏 SLO 感知的调度**：现有的请求优先级策略（如 SJF）只基于请求长度排序，不感知实时的 SLO 满足状态，无法在 TTFT/TPOT 之间以及不同请求之间做有效权衡。

---

## 三、洞察与设计

**关键洞察**：在 LLM 服务过程中，TTFT 和 TPOT 的 SLO 满足程度存在系统性的不对称，且不同请求对 SLO 的余量差异很大。如果调度器能感知每个请求的实时延迟状态和系统级的 SLO 满足统计，就可以在每次 iteration 级别做两层 trade-off——在 TTFT 与 TPOT 之间做平衡（phase-level），以及在不同请求之间做资源再分配（request-level），从而将 "浪费" 在已满足 SLO 请求上的资源转移给即将超标的请求。

基于此洞察，SOLA 的设计包含：

1. **细粒度调度框架**：在每个 iteration 级别，通过三个可变参数控制调度策略——排序函数 $F_i$（请求执行顺序）、$n_i$（最大执行请求数）、$k_i$（最大执行 token 数）。这三个变量每次 iteration 都可以变化，形成完整的调度设计空间。

2. **State Monitor**：实时监控两类状态：
   - 请求级状态：每个请求的实时 TTFT/TPOT、已生成长度、预测剩余长度
   - 系统级状态：$p^{TTFT}_i$ 和 $p^{TPOT}_i$（所有请求中 TTFT/TPOT 的最大比例），用于判断全局 SLO 满足趋势

3. **Strategy Generator**：基于监控状态，将调度转化为约束优化问题：
   - 当 TPOT 更接近超标时，优化 TPOT（优先 decode），以 TTFT 为约束
   - 当 TTFT 更接近超标时，优化 TTFT（优先 prefill），以 TPOT 为约束
   - 当两者都超标时，松弛约束直到一个指标满足

4. **层次化优先级（Hierarchical Prioritization）**：先决定 phase 级优先级（prefill vs decode），再在同一 phase 内按预测的 TTFT/TPOT 降序排列请求（将最可能超标的请求优先执行）。

## 四、实现细节

- **基于 vLLM（v0.4.2）实现**：SOLA 作为独立 Python 框架，替换 vLLM 原有调度器，复用其 continuous batching、PagedAttention、FlashAttention 等基础设施。
- **Peak Memory Prediction**：借鉴 LightLLM 的设计，在新请求加入前预测峰值内存消耗，避免 preemption（swap/recomputation）带来的额外延迟。
- **Cost Model**：分别为 prefill 和 decode 建立多项式 cost model：
  - Prefill：$C^p = a_0 \sum l^{has} l^{in} + b_0 \sum (l^{in})^2 + c_0 \sum l^{in} + d_0$
  - Decode：$C^d = a_1 \sum 1 + b_1 \sum l^{has} + c_1$
  - 使用 offline profiling 初始化参数，运行时通过动量更新的 scaling ratio $\gamma_i$ 在线校准
- **Constrained Workload**：
  - 优化 TTFT 时，控制 token 数 $k_i$ 满足 TPOT 约束（Eq.1），利用 tile-quantization 对齐（如 A100 的 128 倍数）
  - 优化 TPOT 时，控制 prefill 请求数 $n_i$ 满足 TTFT 约束（Eq.2）
- **调度开销优化**：使用内存阈值减少不必要的内存预测计算，统计过程优化，动量更新避免重复矩阵乘法。

## 五、实验结果

**实验平台**：8×NVIDIA A100 80GB SXM4 GPUs，CUDA 12.1，PyTorch 2.3.0

**模型和数据集**：

| 模型 | 并行策略 | 数据集 | Tight SLO (TTFT/TPOT) | Loose SLO (TTFT/TPOT) |
|------|---------|--------|----------------------|---------------------|
| Llama3-8B | TP=1 | ShareGPT | 0.4s/0.15s | 0.6s/0.225s |
| Qwen1.5-14B | TP=2 | ShareGPT | 0.8s/0.2s | 1.2s/0.3s |
| Llama3-70B | TP=4 | ShareGPT | 0.5s/0.2s | 1.0s/0.4s |
| Vicuna1.5-7B-16k | TP=1 | LongBench | 2.55s/0.16s | 3.825s/0.24s |
| Qwen1.5-72B | TP=4 | LongBench | 2.425s/0.2s | 4.85s/0.4s |

**主要结果**：

| 指标 | vs vLLM-S | vs vLLM-D | vs SJF |
|------|-----------|-----------|--------|
| 90% SLO attainment 下 goodput 提升 | 1.27× | 1.11× | 1.08× |
| 99% SLO attainment 下 goodput 提升 | 1.11× | 1.06× | 1.04× |

- SLO attainment 从 45.5% 提升到 99.4%（最佳情况）
- 调度开销仅增加 0.40%-0.45%（总 serving 时间占比）
- Cost model 平均绝对误差 4.98%-5.92%（长文本 arXiv 数据集 8.91%）
- 在 loose SLO 下优势更明显（trade-off 空间更大），tight SLO 下与 SJF 接近

## 六、批判性分析

1. **Goodput 提升幅度有限**：在 99% attainment 标准下，SOLA 对比 SJF 仅提升 1.04×，对比 vLLM-D 仅 1.06×。考虑到 SOLA 引入了完整的 state monitoring、cost model 和约束优化求解器，这个收益是否值得系统复杂度的增加值得商榷。

2. **基线选择偏向有利**：实验基于 vLLM v0.4.2，这是一个较老的版本。后续 vLLM 版本已大幅改进调度策略（如 prefix caching、更好的 chunked prefill）。与更新的系统（如 SGLang）对比可能会缩小差距。

3. **Cost Model 的局限性**：多项式 cost model 在长文本（arXiv）上误差跳升至 8.91%，而 SOLA 的约束优化严重依赖延迟预测的准确性。当预测不准时，可能导致错误的调度决策（如误判哪些请求即将超标），反而降低 attainment。论文未讨论预测误差对最终 attainment 的敏感性。

4. **单机场景的局限性**：论文明确只考虑 prefill 和 decode 在同一 GPU 上的场景，不适用于 disaggregated serving（如 DistServe、Splitwise）。而在生产环境中，大规模部署通常采用 prefill-decode disaggregation，SOLA 的设计空间在这种架构下需要重新定义。

5. **输出长度预测的粗糙处理**：SOLA 的请求级优先级排序依赖输出长度预测（$l^{left}$），但论文只用了简单的分布统计方法，且承认"长度预测不是本文重点"。然而这是系统的关键路径——错误的长度预测会导致 TPOT 排序错误，进而影响 request-level trade-off 的有效性。

6. **Ablation 不够充分**：只给出了一个场景（Qwen1.5-72B + LongBench）的 ablation，state-aware scheduling 和 peak memory prediction 各贡献约 3% 的 attainment 提升，但无法区分各个子组件（hierarchical prioritization、constrained workload、cost model tuning）的独立贡献。

## 七、AI Infra / MLSys 视角

1. **SLO-aware 调度的范式价值**：SOLA 将 LLM serving 调度从"优化单一指标"转向"约束优化多个 SLO"，这一思路对 AI Infra 有普遍启发。未来的 serving 系统需要更系统地处理多维 SLO（不仅是 TTFT/TPOT，还可能包括 token accuracy、cost 等），SOLA 的约束优化框架提供了一个可扩展的起点。

2. **State-aware scheduling 与 disaggregated serving 的结合**：SOLA 目前只考虑单机场景。一个有价值的延伸方向是将 state-aware 机制扩展到 prefill-decode disaggregated 架构中——在 prefill 和 decode 实例之间做跨节点的 SLO-aware 负载均衡和请求路由。

3. **与 speculative decoding 的交互**：Speculative decoding 改变了 TPOT 的分布特性（accept/reject 导致 per-token 延迟变化更大），SOLA 的 cost model 和 state monitoring 需要适配。这是一个值得探索的方向。

4. **在线 cost model 的改进**：当前的多项式 cost model 过于简单。可以考虑用轻量级 ML 模型（如小型 MLP）替代，或利用 GPU kernel 级别的 profiling 数据做更精准的预测，特别是在 mixed batching 场景下。

5. **最有价值的切入点**：将 SOLA 的 iteration-level 细粒度调度思想与 prefix caching、multi-LoRA serving 等新兴技术结合——这些技术引入了新的资源竞争维度（cache hit rate、adapter switching overhead），需要更细粒度的 SLO-aware 调度决策。

---

## 八、总结

SOLA 提出了一个面向 SLO attainment 优化的细粒度 LLM serving 调度框架，通过实时监控请求级和系统级状态，将调度问题建模为约束优化，在每个 iteration 动态调整 prefill/decode 优先级和工作负载大小，实现 TTFT-TPOT 之间及不同请求之间的双层 trade-off。系统在 5 种模型×2 种数据集配置下验证有效，90% attainment 下平均提升 1.08-1.27× goodput，调度开销仅 0.4-0.45%。主要局限在于仅适用于单机非 disaggregated 场景、cost model 精度对长文本下降明显、以及在 tight SLO 下相对 SJF 优势有限。
