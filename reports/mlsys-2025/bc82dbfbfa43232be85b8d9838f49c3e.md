## 1. 研究背景与动机

LLM Serving 中，Service Level Objectives（SLO）通常包含两个关键指标：TTFT（Time-to-First-Token，首 token 延迟）和 TPOT（Time-per-Output-Token，每 token 生成时间）。现有 Serving 系统（vLLM、FasterTransformer 等）对所有请求采用粗粒度的固定调度策略：
- **Prefill-prioritized**（vLLM 默认）：优先处理新到达请求的 Prefill，TTFT 优秀但 TPOT 退化
- **Decode-prioritized**（FasterTransformer）：优先处理 Decoding，TPOT 优秀但 TTFT 退化
- **Mixed scheduling**（SplitFuse）：交替处理两种请求，但无法精确平衡

这种粗粒度策略导致两个问题：
1. **分布偏差**：TTFT 和 TPOT 的 SLO 达成率严重不平衡（一个达标率极高，另一个极低）
2. **请求间方差**：不同请求的延迟分布方差大，大量请求同时超标或同时远低于 SLO

## 2. 研究问题与核心挑战

### 2.1 细粒度调度的设计空间

SOLA 将调度问题形式化为：每次迭代（iteration）控制两个变量：
- **执行顺序（F）**：waiting queue 中请求的执行顺序
- **工作负载大小（n, k）**：本次迭代处理的请求数量（n）和 token 数量（k）

这是现有系统所忽视的——它们仅控制阶段级优先级，不控制请求级执行顺序和工作负载。

### 2.2 双重权衡

**TTFT vs TPOT 权衡**：优先 Prefill 会聚合大量 Decoding 请求，增加每个请求的 TPOT；优先 Decoding 则延长等待中的 Prefill 请求的 TTFT。

**请求间权衡**：不同请求有不同的输入/输出长度，等待时间越长，其 TTFT/TPOT 超标风险越高；调度策略需要在"拯救"高风险请求和"浪费"低风险请求之间权衡。

### 2.3 三种竞争类型

- **Prefill vs Decoding**：两阶段争抢 GPU 计算资源
- **Prefill vs Prefill**：两个等待中的 Prefill 请求，决定谁的 TTFT 更长
- **Decode vs Decode**：内存满时决定哪些请求被换出 CPU 或重新计算

## 3. 主要贡献

1. **细粒度调度框架**：在迭代级别上控制请求执行顺序和工作负载，实现 vLLM 等现有系统无法支持的细粒度调度。
2. **State-Aware Scheduling**：监控两类状态（单个请求视角：$t_{TTFT}$、$t_{TPOT}$、$l_{left}$；系统视角：$p_{TTFT}$、$p_{TPOT}$、$D$），基于状态动态调整调度策略。
3. **约束优化问题转换**：将 TTFT/TPOT SLO 达成问题转化为约束优化问题，通过松弛约束处理边界情况。
4. **层级优先级排序**：先确定阶段优先级（Prefill 或 Decoding），再在同一阶段内按请求级指标（TTFT、预测剩余长度）排序。

## 4. 核心方法与设计

### 4.1 状态监控（State Monitor）

每次迭代结束后更新：
1. **请求延迟**：记录执行时间到总延迟，计算实时 $t_{TTFT}$ 和 $t_{TPOT}$
2. **系统延迟统计**：$p_{TTFT} = \max_r(t_{TTFT}^r) / T_{TTFT}^{SLO}$，100% 达成率当且仅当 $p \leq 1$
3. **请求长度**：记录已生成长度 $l_{out}$，预测剩余 $l_{left}$（基于历史输出长度分布 $D$）
4. **系统长度分布**：用于长度预测

### 4.2 约束优化问题

SOLA 根据系统状态选择优化目标：

| 条件 | 优化目标 | 约束 |
|------|---------|------|
| $p_{TPOT} > 1 > p_{TTFT}$ | 最小化 $\max(t_{TPOT})$ | $\max(t_{TTFT}) \leq T_{TTFT}^{SLO}$ |
| $p_{TTFT} > 1 > p_{TPOT}$ | 最小化 $\max(t_{TTFT})$ | $\max(t_{TPOT}) \leq T_{TPOT}^{SLO}$ |
| $p_{TTFT} > 1, p_{TPOT} > 1$ | 松弛约束后最小化超标延迟 | — |

当两个指标都超过 SLO 时，对约束进行 a% 松弛（如 90% 的请求满足 SLO），使优化问题仍有解。

### 4.3 层级优先级排序（F）

**第一层（阶段级）**：
- 优化 TTFT（约束 TPOT）：优先处理 Prefill 请求
- 优化 TPOT（约束 TTFT）：优先处理 Decoding 请求

**第二层（请求级）**：
- Prefill 请求：按 TTFT 风险（当前 TTFT / SLO 余量）排序
- Decoding 请求：按剩余输出长度（$l_{left}$）排序（越长越优先，避免被换出）

### 4.4 约束工作负载控制（n, k）

- **优化 TTFT**：限制 Prefill 请求数量 $n$，确保 TPOT 不超标
- **优化 TPOT**：限制 Decoding 请求总 token 数 $k$，确保 TTFT 不超标

## 5. 实现细节

SOLA 实现为 Python 独立框架，通过接口集成到 Serving 系统。当前支持 vLLM 作为后端，利用其 continuous batching、paged attention 和 tensor parallelism 基础设施。

**峰值内存预测**：借鉴 LightLLM 的方法，在每次迭代前预测新请求加入后的峰值内存使用量，提前决定是否接受请求，避免内存溢出导致的请求抢占开销。

**成本模型自适应**：基于运行时统计调整缩放比例：
$$\gamma = \alpha \cdot \gamma_0 + (1-\alpha) \cdot \gamma_{prev}$$
利用 Serving 过程的连续性（KV Cache 长度变化趋势）进行线性调整。

## 6. 实验结果

**硬件**：NVIDIA A100 80GB GPUs
**模型**：LLaMA3-8B（TP=1）、LLaMA3-70B（TP=4）、Qwen1.5-14B（TP=2）、Qwen1.5-72B（TP=4）、Vicuna-7B-16K（TP=1）

**数据集**：ShareGPT（对话场景）、LongBench（长文本理解）

### 6.1 SLO 达成率对比

**严格 SLO（TTFT=0.4-0.8s，TPOT=0.15-0.2s）**：
- vLLM（Prefill-prioritized）：SLO 达成率 45.5%
- vLLM（Decode-prioritized）：SLO 达成率约 65%
- **SOLA**：SLO 达成率 **99.4%**

**宽松 SLO**：
- SOLA 在 99% 达成率下仍能服务 1.04-1.27× 更多的请求

### 6.2 Goodput 对比

在 90% SLO 达成率约束下：
- SOLA 相比 vLLM-Prefill、vLLM-Decode、SJF 基线，在所有模型上均达到最高 Goodput
- 平均提升 1.08-1.27×（90% SLO）和 1.04-1.11×（99% SLO）

### 6.3 长上下文场景

Vicuna-7B-16K 和 Qwen1.5-72B（LongBench）上：
- vLLM 的 Decode-prioritized 策略 TPOT 极低但 TTFT 极高
- SOLA 通过动态调整，在两个指标间取得平衡，整体达成率最优

## 7. 潜在问题与局限性

1. **仅集成 vLLM**：当前实现仅支持 vLLM 后端，对其他 Serving 系统（TensorRT-LLM、SGLang 等）的集成需要额外适配工作。
2. **SLO 固定的假设**：SOLA 假设 SLO 在 Serving 期间固定，对动态 SLO（不同用户/请求有不同 SLO）的支持需要扩展。
3. **预测准确性的依赖**：$l_{left}$ 预测基于历史分布，在开放域对话（输出长度难以预测）场景下准确性可能下降。
4. **仅考虑吞吐量的公平性**：SOLA 优化 SLO 达成率，但未显式处理多用户间的公平性（如不同优先级用户、不同计费等级）。
5. **峰值内存预测的简化**：假设请求的 KV Cache 增长与 token 数成正比，未考虑注意力稀疏性等因素。

## 9. 个人评注

SOLA 是一项针对 LLM Serving 调度优化的深度分析工程工作。其核心贡献在于揭示了现有粗粒度调度策略（Prefill/Decode-prioritized）的根本局限，并提出了基于细粒度状态感知的系统化解决方案。

论文最有价值的是将调度问题形式化为约束优化问题的数学框架。这种建模方式的价值在于：
1. 将"TTFT/TPOT 权衡"从模糊的工程直觉变成了可量化的优化目标
2. 通过松弛约束处理边界情况，避免了优化问题在极端场景下无解的问题
3. 为后续研究提供了一个可扩展的基准框架

状态监控的设计也体现了良好的工程直觉：通过 $p_{TTFT}$ 和 $p_{TPOT}$ 两个指标实时感知系统状态，并据此动态切换优化目标（TTFT vs TPOT）。这种"感知-决策"的闭环控制模式是自适应系统的经典设计。

然而，SOLA 与 vLLM 的深度绑定也是其局限所在——vLLM 的调度器是高度优化的 C++/CUDA 实现，SOLA 的 Python 原型在生产环境中的性能开销需要认真评估。此外，SOLA 假设 SLO 固定且仅有一个优先级层次，与实际商业场景中复杂的多级 SLO 体系存在差距。

总体而言，对于关注 LLM Serving 质量（而非仅仅是吞吐量）的实践者，SOLA 提供了一个有价值的分析框架和设计参考。其细粒度状态感知调度的核心思想，值得在更广泛的 Serving 系统设计中借鉴。
