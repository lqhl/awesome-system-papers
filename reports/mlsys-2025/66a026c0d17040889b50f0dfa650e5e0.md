## 1. 研究背景与动机

在线 LLM 推理（Online LLM Inference）为聊天机器人和自主 Agent 等应用提供支持。现代 LLM 推理引擎依赖请求批处理（Request Batching）来提高吞吐量，但 GPU 内存的有限容量严重限制了实际能达到的批处理大小。

**核心矛盾**:
1. GPU 计算能力持续增长（H100 比 V100 快约 30 倍）
2. 但 GPU 内存容量增长缓慢（H100 80GB vs 需求数百 GB）
3. 这导致 GPU 计算资源被大量浪费

**现有方案的局限**:
- **离线批处理**: 不适合在线推理场景
- **Chunked Prefill**: 通信开销较大
- **CPU 卸载（Offloading）**: 现有方案主要针对训练，对推理场景考虑不足

NEO 的目标是：**利用附带的 CPU 内存（作为 GPU"免费"资源）来卸载部分注意力计算和 KV Cache，实现高吞吐量且低延迟的在线推理**。

## 2. 研究问题与核心挑战

**核心问题**: 如何在不影响推理精度和延迟的前提下，通过 CPU 卸载来扩大有效批处理大小，从而更高效地利用 GPU 计算资源？

**具体挑战**:
1. **GPU-CPU 通信与计算的重叠**: 解码阶段的注意力计算和 GPU-CPU 通信需要精确重叠。
2. **CPU 注意力计算效率**: CPU 上的注意力计算需要高效的 kernel 实现。
3. **负载感知调度**: 动态工作负载下需要自适应地决定哪些请求应卸载到 CPU。
4. **Prefill 阶段的高计算需求**: Prefill 阶段的计算量远大于解码阶段，难以完全卸载。

## 3. 主要贡献

1. **对称流水线（Symmetric Pipelining）**: 将单个解码批次拆分为两个子批次，分别在 GPU 和 CPU 上执行注意力计算，实现线性操作和注意力操作的精确重叠。
2. **负载感知调度**: 考虑非对称的流水线特性，自适应地决定是否将请求卸载到 CPU。
3. **高效的 CPU 注意力 kernel**: 针对 CPU 架构优化了注意力计算，实现高达数十倍于 PyTorch eager 的加速。
4. **与 SwiftLLM 的集成**: 在 AWS GPU 实例（g4 with T4, g5 with A10G）和本地 8×H100 测试平台上进行了评估。
5. **开源实现**: 基于 SwiftLLM 的完整开源实现。

## 4. 核心方法与设计

### 4.1 问题分析

解码阶段的计算分解：
- **Prefill 阶段**: 需要计算整个输入序列的 KV Cache，通信和计算量都很大
- **Decode 阶段**: 每个 token 只需计算与已缓存 KV 的注意力，KV Cache 通信成为主要开销

### 4.2 朴素卸载方案

简单的 CPU 卸载方案：
1. 将所有请求的 KV Cache 传输到 CPU
2. CPU 执行注意力计算
3. 将注意力结果传回 GPU

问题：CPU 计算速度远慢于 GPU，通信开销巨大。

### 4.3 对称流水线

NEO 的核心设计：

```
GPU Sub-batch:          [Prefill+Decode(Linear)]  → [Decode(Attn)]  → [Combine Results]
                        ↓                              ↑
CPU Sub-batch:          [TrQKV] → [Decode(Attn)] → [TrO]  → [Decode(Linear)] ← Combine Results
```

将解码批次分成两个子批次：
- **GPU 子批次**: 在 GPU 上执行线性操作和注意力计算
- **CPU 子批次**: 将 KV Cache 传输到 CPU，在 CPU 上执行注意力计算

### 4.4 线性与注意力操作的重叠

关键洞察：在解码阶段，线性操作和注意力操作是相互独立的，可以并行执行。

```
Decode iteration t:
  GPU: Linear_t  →  Combine(O_t, O_t_cpu)
  CPU: TrQKV_t   →  Attn_t   →  TrO_t
```

### 4.5 负载感知调度

NEO 调度器考虑：
- **非对称流水线**: GPU 和 CPU 的计算速度不对称
- **输入/输出长度分布**: 不同请求的 IO 长度差异
- **资源可用性**: 动态调整卸载策略

## 5. 实验结果

### 5.1 负载-延迟曲线

在三种配置下的实验：
1. **2xH100 + Llama-3.1-70B + AC**: NEO 在高请求率下显著优于 vLLM
2. **A10G + Llama-3.1-8B + AC**: NEO 在中等请求率下优势明显
3. **T4 + Llama-2-7B + OSC**: NEO 在资源受限场景下表现优异

### 5.2 延迟分布

在 A10G + Llama-3.1-8B 配置下，NEO 的 P50、P90、P99 延迟均显著低于 vLLM。

### 5.3 吞吐量灵敏度

在不同 AWS EC2 实例上的实验：
- 使用更大的 CPU 实例（如 x8large）可获得更高吞吐量
- CPU 卸载相比 GPU-only 基线有显著提升

### 5.4 与 Chunked Prefill 对比

NEO 与 Chunked Prefill 的对比实验表明，两种方法各有优劣，适用场景不同。

## 6. 潜在问题与局限性

1. **CPU 注意力性能**: 虽然论文声称实现了高效的 CPU kernel，但在高端 GPU（如 H100）上，CPU 计算仍然可能是瓶颈。
2. **Prefill 阶段支持**: NEO 主要针对解码阶段，对 Prefill 密集型场景的适用性有限。
3. **通信开销**: 在高带宽需求场景下，GPU-CPU 通信仍可能成为限制因素。
4. **延迟敏感性**: 对于极低延迟需求的场景，CPU 卸载可能不是最佳选择。

## 7. 未来工作

1. 探索 GPU 与 CPU 的动态资源分配
2. 结合量化技术进一步减少数据传输
3. 在更多模型和硬件配置上验证

## 8. 个人评注

NEO 针对的是一个非常实际的问题：在 GPU 内存容量增长跟不上模型规模增长的背景下，如何充分利用附带的 CPU 资源来扩大有效批处理大小。这是一个聪明的想法——CPU 内存通常是"免费"的（已经包含在服务器成本中），但往往没有被充分利用。

论文的对称流水线设计是核心创新。通过将解码批次拆分并在 GPU 和 CPU 上并行执行线性操作和注意力计算，NEO 实现了通信与计算的有效重叠。不过，这个设计的有效性依赖于 GPU 和 CPU 的计算速度大致匹配，在某些配置下可能不成立。

论文的实验覆盖了多种实际配置（AWS GPU 实例、本地 H100 集群），这增强了结果的可信度。不过，作为一个相对激进的设计（将计算卸载到 CPU），在实际生产环境中的稳定性和可维护性还需要进一步验证。

总体而言，NEO 为资源受限场景下的 LLM 推理提供了一个有价值的解决方案。其设计思路——利用"免费"资源来缓解 GPU 内存压力——对于其他 ML 系统设计也有启发意义。
