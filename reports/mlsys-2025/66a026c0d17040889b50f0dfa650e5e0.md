# NEO: Saving GPU Memory Crisis with CPU Offloading for Online LLM Inference

**作者**：Xuanlin Jiang (Peking University), Yang Zhou (UC Berkeley / UC Davis), Shiyi Cao (UC Berkeley), Ion Stoica (UC Berkeley), Minlan Yu (Harvard University)
**会议**：MLSys 2025
**链接**：https://github.com/NEO-MLSys25/NEO
**源文件**：[66a026c0d17040889b50f0dfa650e5e0.pdf](../../papers/mlsys-2025/66a026c0d17040889b50f0dfa650e5e0.pdf)

---

## 一、背景

LLM 在线推理（chatbot、coding assistant、autonomous agent）要求低延迟和高吞吐。现代推理引擎（vLLM、SGLang）通过 request batching 提高吞吐，但 batch size 受限于 GPU 显存——模型权重 + KV cache 占据了绝大部分 HBM。GPU 算力往往因显存不足而严重闲置：以 A10G 为例，125 TFLOPS 算力配 24GB 显存，batch size 被限制在几十甚至个位数。

与此同时，GPU 服务器上的 host CPU 拥有大量内存（64GB–2TB）和可观的内存带宽（200–537 GB/s），且在云上已包含在 VM 价格中，属于"免费"资源，但目前在 LLM 推理中几乎完全闲置。

---

## 二、要解决的问题

1. **GPU 显存瓶颈导致 batch size 受限**：KV cache 随序列长度线性增长，GPU 显存无法容纳足够多的并发请求，GPU 算力大量浪费。
2. **已有 offloading 方案不适合在线推理**：
   - **KV cache swap（FlexGen 等）**：反复在 GPU-CPU 之间搬运 KV cache，PCIe 带宽成为瓶颈，严重增加延迟。
   - **全量 compute offloading（FastDecode）**：将所有 decoding attention 搬到 CPU，CPU 成为严重瓶颈；且需要 832 核 AMD EPYC 远程服务器才能服务一块 A10G，成本远高于 GPU 本身。
   - **静态调度策略**：假设固定 input/output 长度，无法适应真实动态 workload。
3. **GPU 与 CPU 能力差异巨大**：如何在一次推理迭代内平衡两者的计算和内存带宽，不让任何一方成为瓶颈？

---

## 三、洞察与设计

**关键洞察**：Decoding attention 是 memory-bandwidth-bounded 操作（arithmetic intensity 极低），而 GPU 和 CPU 在内存带宽上的差距（如 600 vs 200 GB/s）远小于算力差距（125 vs 1.2 TFLOPS）。因此，将 decoding attention 部分卸载到 CPU 在性能上是可行的，不会像卸载 dense computation 那样造成灾难性瓶颈。

### 核心设计

**1. Asymmetric Pipelining（非对称流水线）**

NEO 将 KV cache 系统分为 GPU-cache 和 CPU-cache 两部分，请求根据存储位置分为 GPU-request 和 CPU-request。每次推理迭代形成两个非对称 sub-batch：

- **Batch-0（GPU 主导）**：包含所有 prefilling 请求 + GPU decoding 请求 + 少量 CPU decoding 请求，linear stage 较长。
- **Batch-1（CPU 主导）**：包含大部分 CPU decoding 请求，attention stage 较长。

两个 batch 交替执行 "long stage" 和 "short stage"，GPU 的 linear 操作与 CPU 的 attention 操作重叠执行，最小化 pipeline bubble。

相比 symmetric pipelining（FastDecode），asymmetric 设计的优势：
- 充分利用 GPU 显存（不像 symmetric 那样 GPU 显存大量闲置）
- Prefilling 阶段集成到 GPU batch 中，CPU 不再闲等
- 无需切分为两个相同大小的 batch，避免了 real-world workload 下不可能均分的难题
- GPU attention kernel 每次迭代只调用一次（symmetric 需要两次），减少 kernel launch 开销

**2. Load-Aware Scheduling（负载感知调度）**

调度器在每次迭代时：
- 同时生成 GPU-only 方案和 asymmetric pipelining 方案
- 估算两者的 T/x（每 token 时间），选择更优方案（Greedy 原则）
- 动态决定哪些请求放 GPU、哪些放 CPU，保证 CPU 计算时间被 GPU 计算时间"隐藏"（Balancing + Hiding CPU 原则）
- 通过 offline profiling + linear interpolation 估算各组件时间

调度开销 < 3ms/iteration，相对于数百毫秒的迭代时间可忽略。

## 四、实现细节

- 基于 **SwiftLLM**（vLLM 简化版，约 2K 行代码，性能相当）实现，NEO 额外增加 4K 行 Python + 1.5K 行 C++。
- **CPU Kernel（PACPU）**：自实现的 paged attention for CPU，使用 Intel ISPC 编译器生成 SPMD 代码，支持 AVX2/AVX512/ARM Neon，跨平台可移植。优化包括：
  - SIMD load/store 指令最小化指令开销
  - 请求维度并行（类似 Flash Decoding），每个线程处理连续内存块
  - 内存访问顺序精心编排保证连续性
- **Kernel Launch 开销优化**：将 Triton-JIT kernel 替换为 CUDA C++ kernel，LLaMa-3-8B 每层 kernel launch 开销从 1.2ms 降至 0.6ms。
- **Layer-wise swapping**：新 prefill 请求的 KV cache 逐层生成、逐层传输，与计算重叠。
- **多 GPU 支持**：基于 Ray actor + NCCL tensor parallelism，每个 GPU 配独立 CPU KV cache 分区。
- 开源地址：https://github.com/NEO-MLSys25/NEO

## 五、实验结果

### 测试平台

| 实例 | GPU | CPU | 内存 |
|------|-----|-----|------|
| AWS g5.4xlarge | A10G (24GB) | EPYC 7R32 (8 cores) | 64GB |
| AWS g4dn.4xlarge | T4 (16GB) | Xeon P-8259CL (8 cores) | 64GB |
| Local HGX | 8×H100 (80GB) | Xeon 8462Y+ (64 cores) | 2TB |

### 主要结果（在线推理吞吐提升，相同延迟约束下）

| 设置 | 对比 vLLM | 对比 GPU-only baseline |
|------|-----------|----------------------|
| T4 + Llama-2-7B | ~6× (563%) | 最高 7.5× |
| A10G + Llama-3.1-8B | 6.4% | 最高 26% |
| 2×H100 + Llama-3.1-70B | 14.3% | 最高 14% |

### 关键发现

- T4 上收益最大，因为 16GB 显存极度受限，offloading 后 batch size 大幅提升。
- 延迟分布与 vLLM 在各 percentile 上几乎一致，吞吐提升不以延迟为代价。
- 对比 FastDecode+：NEO 在所有 output length 下都优于 baseline（因调度器可随时回退到 GPU-only），而 FastDecode+ 在长 output 时因 CPU 过载性能降至 baseline 60% 以下。
- **CPU 带宽敏感性**：g5.2xlarge → g5.16xlarge，吞吐提升从 12.2% 增至 79.3%，证实内存带宽（而非 CPU 算力）是决定性因素。

## 六、批判性分析

1. **收益范围跨度极大**：标题和摘要突出 "7.5×" 的最高收益，但这仅出现在 T4 上——一块 2018 年的入门级 GPU（16GB 显存）。在更主流的 A10G 和 H100 上，收益分别为 6-26% 和 14%，远不如 7.5× 抢眼。论文的 framing 有选择性地放大了最佳场景。

2. **Baseline 选择不够公平**：
   - SwiftLLM 作为主要 baseline，在 2-GPU 设置下比 vLLM 低 8.8%，这意味着 NEO 在 H100 上报告的 14% 增益中，有部分来自 baseline 本身的弱势。
   - 没有与 chunked prefill 在相同框架下公平对比——vLLM 的 chunked prefill 结果放在附录中，且论文解释"GPU 显存太小导致 piggyback 的 decoding 请求不够多"，但这恰恰是 NEO 声称要解决的场景。

3. **CPU 资源并非真正"免费"**：
   - 论文反复强调 host CPU "comes with the GPU as free"，但 g5.16xlarge（实现 79.3% 增益的实例）比 g5.4xlarge 贵 4 倍。论文将 CPU 升级的收益归功于 NEO，却不讨论成本效率（throughput/dollar）。
   - 在 on-premise 场景下论文自己也承认 "NEO may not achieve better perf-TCO"。

4. **能耗问题回避**：论文承认 CPU offloading 增加能耗，但以 "cloud users don't care" 一笔带过，仅对 T4 声称 throughput-per-watt 更优，其他 GPU 完全回避了这一分析。

5. **SwiftLLM 作为实现基础的局限**：NEO 构建在 2K 行的简化引擎上，缺少 vLLM/SGLang 的大量优化（speculative decoding、prefix caching、continuous batching 优化等）。论文声称 "could be adapted to other frameworks"，但未提供任何证据。考虑到 asymmetric pipelining 对调度器的侵入式修改，移植难度可能很大。

6. **动态 workload 适应性**：虽然论文强调 load-aware scheduling 处理动态 workload，但调度策略仍然依赖 offline profiling + linear interpolation 来估算延迟，在极端情况下（如 attention 与 KV cache 长度的非线性关系）可能不准确。论文在 Figure 9 中也承认某些 workload 下 NEO 略低于 baseline。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **异构计算的粒度选择很关键**：NEO 的核心贡献不在于 "offload to CPU" 这个 idea 本身（FastDecode 等已提出），而在于**部分 offloading + 非对称流水线**的设计哲学——不是把整个操作搬到弱设备上，而是找到性能特征匹配的操作子集。这一思路可以推广到 GPU+NPU、GPU+FPGA 等异构场景。

2. **Memory bandwidth 而非 compute 是 attention offloading 的关键**：CPU 敏感性实验清晰验证了这一点。对于 AI Infra 工程师，这意味着在选择 offloading target 时，应重点关注内存带宽指标而非算力。ARM 服务器（如 AWS Graviton4，537.6 GB/s/socket）可能是比 x86 更好的 offloading target。

3. **调度器设计中的"主动回退"策略**：NEO 调度器每次迭代都评估 GPU-only vs. offloading，可以随时回退。这种"保底不亏"的设计在生产系统中非常重要，值得推广到其他异构调度场景。

### 值得跟进的方向

1. **与 disaggregated serving 结合**：NEO 只在 decoding 阶段 offload attention，而 DistServe 等系统已经将 prefill 和 decode 分离到不同 GPU。将 NEO 的 CPU offloading 嵌入 disaggregated decode 实例中，可能进一步提升 decode-heavy workload 的吞吐。

2. **集成到 vLLM/SGLang**：论文最大的实际限制是实现在 SwiftLLM 上。如果在 SGLang 的 radix attention 或 vLLM 的 paged attention 基础上实现 CPU offloading path，结合 prefix caching 等已有优化，实际收益可能更大（也可能更小，需要验证）。

3. **CXL 内存扩展场景**：CXL 提供的内存带宽（~64 GB/s per link）虽低于 DDR5，但延迟远低于 PCIe swap。在 CXL 扩展内存上存放 KV cache + 在 host CPU 上运算 attention 的组合方案，可能是 NEO 思路的自然延伸。

4. **长上下文推理优化**：论文 Discussion 中提到 chunked prefill 与 NEO 的结合，在 100K+ 上下文场景下，KV cache 显存压力极大，CPU offloading 的收益空间应该更大，值得深入研究。

---

## 八、总结

NEO 是一个面向在线 LLM 推理的 CPU offloading 系统，通过非对称 GPU-CPU 流水线和负载感知调度，将部分 decoding attention 计算和 KV cache 卸载到 host CPU，在不牺牲延迟和精度的前提下提升推理吞吐。核心 insight 是 decoding attention 的 memory-bandwidth-bounded 特性使得 CPU 可以胜任部分工作。在显存极度受限的场景（T4）收益巨大（7.5×），在主流 GPU 上收益中等（14-26%）。主要局限在于实现基于简化引擎 SwiftLLM，未集成到生产级框架；且 CPU 资源的"免费"假设在实际部署中需要更审慎的成本分析。
