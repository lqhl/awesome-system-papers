## 一、背景

RLHF (Reinforcement Learning from Human Feedback) 是 ChatGPT 等大语言模型成功的关键训练技术。典型的 RLHF 工作流（基于 PPO 算法）涉及四个独立的 LLM（Actor、Reward、Reference、Critic），在每个训练迭代中执行六种模型函数调用（Actor Generation、Reward Inference、Critic Inference、Reference Inference、Actor Training、Critic Training），这些调用之间存在复杂的数据依赖关系。

现有的 LLM 训练系统主要针对预训练和 SFT 等监督训练范式设计了成熟的并行化策略（DP、TP、PP 的 3D 并行），但 RLHF 的多模型、多任务、异构计算负载特性使得直接沿用这些固定策略会导致严重的训练效率问题。

---

## 二、要解决的问题

1. **对称并行化导致 over-parallelization**：现有系统（如 DeepSpeed-Chat）对所有 LLM 使用相同的全局并行策略，将所有 GPU 分配给每个模型，导致大量同步和通信开销。不同类型的计算任务（generation vs. inference vs. training）对并行策略的需求完全不同，单一策略必然次优。

2. **非对称并行化导致 GPU 空闲**：另一些系统（如 OpenRLHF、NeMoAligner）将不同 LLM 放到不同 GPU 组上，但由于任务间的数据依赖，不同组的 GPU 经常处于空闲状态（GPU underutilization），无法充分利用集群资源。

3. **固定资源分配的根本局限**：以上两种策略的共同问题是资源分配和并行策略在整个训练过程中是固定的，无法根据不同模型函数调用的实际计算特性动态调整。

---

## 三、洞察与设计

**关键洞察**：RLHF 工作流中不同的模型函数调用（如 Actor Generation vs. Actor Training vs. Critic Training）具有截然不同的计算特性和资源需求，因此它们应该使用不同的 GPU 资源分配和不同的并行化策略；而在函数调用之间动态重新分配模型参数（parameter reallocation）的代价相对于计算本身是可接受的，因此可以通过参数重分配实现函数调用级别的细粒度资源编排。

基于这一洞察，REAL 系统包含两个核心组件：

### Execution Plan Generator
- 将 RLHF 工作流解析为 **dataflow graph**，节点为模型函数调用，边为数据/参数版本依赖
- 为每个函数调用独立指定 **device mesh**（GPU 分配）和 **parallelization strategy**（dp, tp, pp, mbs 四元组）
- 搜索空间巨大（128 GPU 集群上超过 10^16 种组合），采用 **MCMC (Metropolis-Hastings) 搜索算法**，结合轻量级 profiling-assisted runtime estimator 快速评估候选方案
- Estimator 通过对单层进行 profiling（耗时仅数分钟），然后用线性插值估算整个函数调用的时间/内存开销（评估一个方案仅需数百微秒）

### Runtime Engine
- Master-Worker 架构：centralized master 解析依赖、调度任务，model workers 作为 RPC server 执行计算
- 支持不同函数调用在不相交的 device mesh 上并发执行
- 参数重分配采用层次化过程：外层循环处理 pipeline stage 映射，内层循环处理 DP+TP mesh 间的参数传输，使用贪心分配最小化通信代价

## 四、实现细节

- **代码规模**：Python 41k LoC + C++ 2.5k LoC，搜索引擎和 simulator 用 C++ 实现以保证速度
- **搜索空间约束**：Device mesh 限制为整数个节点或节点内连续 GPU 切片（如 (1,1), (1,2), (1,4), (1,8), (2,8)...），确保多个 mesh 能完整覆盖集群
- **并行策略空间**：每个函数调用的策略为 (dp, tp, pp, mbs) 四元组，其中 mbs（micro-batch 数）用于控制内存
- **MCMC 搜索**：以能量分布 P(p) ∝ exp(-β·cost(G_p)) 定义目标分布，cost 包含 OOM 惩罚项（α 为大整数），从贪心初始解出发迭代采样
- **内存管理**：区分 static memory（梯度、优化器状态）和 active memory（KV cache、activations、可重分配参数），计算每个设备的 peak memory 确保不超限
- **参数重分配通信**：从 (dp1, tp1, pp1) 映射到 (dp2, tp2, pp2)，每个目标 GPU 贪心选择通信代价最低的源 GPU，所有源 GPU 并行广播
- **用户接口**：通过 Python dataclass + `@auto` decorator 定义实验，用户只需声明 dataflow graph，系统自动搜索 execution plan 并通过 SLURM 部署
- **通用性**：支持 PPO 之外的 RLHF 算法（DPO、ReMax、GRPO），只要工作流可以分解为模型函数调用的 dataflow graph

## 五、实验结果

**实验环境**：128 × NVIDIA H100 GPU，NVLink 节点内互联，RoCE 3.2 Tbps 节点间互联。使用 LLaMA-3 模型（7B/13B/34B/70B）。

### 端到端吞吐量对比 (vs. Baselines)

| 对比系统 | 最大加速比 | 说明 |
|----------|-----------|------|
| DeepSpeed-Chat | 3.58× | 对称并行策略 + ZeRO-3，大规模时有 OOM 和稳定性问题 |
| OpenRLHF | ~2-3× | 非对称三组 GPU，vLLM generation + DeepSpeed training |
| NeMoAligner | ~2× | 非对称两组 GPU，TRT-LLM + Megatron-LM |
| veRL (HybridFlow) | ~1.3-1.5× | 支持 colocation，concurrent work |

### REAL vs. REAL-Heuristic (3D 并行启发式方案)

| 场景 | 平均提升 | 最大提升 |
|------|---------|---------|
| Context 2048 | 54% | - |
| Context 8192 | 81% | - |

### Wall-time 分解 (70B Actor + 7B Critic, 128 GPU)

| 函数调用 | REAL (s) | Heuristic (s) |
|---------|---------|--------------|
| Actor Gen | 185.1 | 241.8 |
| Rew Inf | 5.6 | 12.6 |
| Ref Inf | 35.6 | 63.5 |
| Critic Inf | 5.6 | 12.5 |
| Critic Train | 20.8 | 35.7 |
| Actor Train | 108.0 | 163.4 |

### Profiling 与搜索开销

- Profiling 时间：7B ~30s, 70B ~200s
- 单个 execution plan 评估：~数百微秒
- Estimator 精度：估算时间与实际运行时间高度相关

## 六、批判性分析

1. **Generation 长度假设过于理想**：实验使用固定最大长度的合成数据（prompt 和 generation 都填满），消除了真实场景中 generation 长度变化带来的影响。作者在 Discussions 中承认 REAL 对动态 generation 长度不鲁棒，但这恰恰是真实 RLHF 训练中最常见的场景——随训练进行模型输出分布变化，generation 长度波动很大。这意味着论文展示的性能数字可能是 best case。

2. **搜索不保证最优性**：MCMC 搜索是启发式的，不保证找到全局最优。虽然实验显示搜索结果优于手工方案，但缺乏与穷举搜索在小规模上的对比来评估搜索质量的上限差距。

3. **Estimator 精度缺乏严格验证**：Figure 12 显示估算时间与实际时间的相关性，但只有少量数据点（heuristic 和 searched 各一个 per setting）。缺少对更多候选方案的估算误差统计分析，难以判断 estimator 是否会在某些区域系统性偏差导致搜索走向次优。

4. **Baseline 配置的公平性**：各 baseline 系统使用的是默认配置而非经过调优的最佳配置。例如 OpenRLHF 的 GPU 分组方式、NeMoAligner 的两组划分比例是否是其最优配置并不清楚。veRL 作为 concurrent work 其结果最接近 REAL，这暗示更公平的对比下差距可能更小。

5. **70B Actor + 13B Critic 是最大规模**：128 GPU 对于 70B 模型来说并非大规模，真实训练场景往往使用数百甚至上千 GPU。论文未展示更大规模集群上搜索空间爆炸和参数重分配通信开销的变化趋势。

6. **Parameter reallocation overhead 被弱化**：论文通过 Figure 11 的 GPU time breakdown 展示 P2P 通信占比不大，但未单独量化参数重分配的绝对开销及其随模型/集群规模的增长趋势。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **函数调用级粒度的资源编排思想**：REAL 打破了"一个模型一套并行策略"的惯例，将编排粒度下沉到模型函数调用级别。这一思想可以推广到其他多阶段 LLM 工作流，如 speculative decoding（draft 和 verify 阶段）、MoE 训练（不同 expert 的计算特性不同）、multi-agent 场景等。

2. **轻量级 profiling + 快速 estimator 的搜索范式**：通过少量单层 profiling 构建 cost model，然后在几百微秒内评估一个完整方案，这种方法对任何需要在大搜索空间中找到好的系统配置的场景都有参考价值（如 serving 的 batching 策略、混合并行策略自动搜索）。

3. **参数重分配作为一等公民**：将参数在 GPU 之间的重新分配视为系统设计中的常规操作（而非特殊处理），这对下一代训练框架的设计有指导意义——框架应原生支持动态的并行策略切换。

### 值得跟进的方向

1. **动态 generation 长度下的自适应调度**：当前 REAL 假设 generation 长度固定，如何在运行时根据实际 generation 长度动态调整 execution plan（或维护一组 plan 按条件切换）是一个实际且有价值的研究问题。

2. **与 kernel-level 优化的协同**：REAL 的方法与 FlashAttention、CUDA Graph、算子融合等正交，如何将这些优化的性能模型纳入搜索 estimator，实现端到端的自动优化，是一个系统整合方向。

3. **扩展到更大规模和异构集群**：当集群规模增大到千卡级别或包含异构加速器时，搜索空间和参数重分配的通信拓扑变得更加复杂，需要更高效的搜索算法和通信规划。

4. **与 online RLHF/RLAIF 的结合**：随着 online RLHF 和 RLAIF 的流行，训练和推理的交替更加频繁，REAL 的参数重分配思想在这些新范式下可能有更大的优化空间。

---

## 八、总结

REAL 提出了参数重分配（parameter reallocation）这一核心技术，允许在 RLHF 训练的不同模型函数调用之间动态重新分配 GPU 资源和并行策略，打破了传统固定并行策略的局限。系统通过 MCMC 搜索配合轻量 estimator 自动发现高效的 execution plan，在 LLaMA 模型（7B-70B）和 128 H100 GPU 上实现了相比基线最高 3.58× 的加速。其主要局限在于对固定 generation 长度的假设、搜索的非最优性、以及在更大规模集群上的可扩展性尚未验证。该工作为 RLHF 及更广泛的多模型协同训练场景的系统优化提供了重要的设计思路。
