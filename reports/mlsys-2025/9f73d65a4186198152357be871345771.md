## 一、背景

随着深度学习模型规模持续增长（GPT-3 175B、Llama 2 70B 等），高效的分布式训练变得至关重要。当前主流做法是将 data parallelism（DP）、tensor parallelism（TP）和 pipeline parallelism（PP）组合使用。JAX/XLA 的 GSPMD 编程模型通过 sharding annotation 简化了 SPMD 并行化，但 SPMD 模型在跨低带宽网络（如 DCN）扩展时面临 collective 通信瓶颈。Pipeline parallelism 只需 Point-to-Point 通信，是跨节点扩展的理想选择，但 GSPMD 仅能编码 GPipe 这一种 PP schedule，无法表达 1F1B、Interleaved 1F1B 等更高效的 MPMD schedule。

---

## 二、要解决的问题

1. **SPMD 模型无法表达灵活的 pipeline schedule**：GSPMD 将 PP 编码为 sharding，所有 actor 在同一时刻执行相同计算（SPMD），无法实现 1F1B 等 MPMD schedule，导致 bubble 时间长、内存浪费。
2. **GPipe schedule 的固有缺陷**：GPipe 要求存储所有 microbatch 的 activation，内存开销大，强制全量 rematerialization，训练步时间增加约 20%。
3. **现有 PP 系统（Megatron、DeepSpeed）要求深度侵入模型代码**：模型实现必须绑定具体的并行策略，修改成本高、灵活性差。
4. **同构 stage 假设**：GSPMD 编码要求所有 stage 有相同的 dataflow graph 和 shape，不支持异构 stage。

---

## 三、洞察与设计

**关键洞察**：Pipeline parallelism 本质上是一种 MPMD 计算模式——不同 actor 在同一时刻执行不同 stage 的计算。将 PP 强行编码为 SPMD sharding 是错误的抽象层级，正确做法是在 SPMD 之上构建 MPMD 层，让每个 SPMD task 独立编译执行，由 MPMD runtime 协调调度。

基于这一洞察，JaxPP 的核心设计包括：

1. **`pipeline_yield` 标记**：用户在模型代码中插入轻量级的 `pipeline_yield` 调用标记 stage 边界。JaxPP 根据数据依赖关系自动推断 stage 划分，无需将模型重构为独立函数。该标记对 autodiff 透明，可与 JAX 的 `vmap`、`checkpoint` 等 transformation 组合。

2. **`accumulate_grads` API**：封装 gradient accumulation 循环，用户提供 microbatch 梯度函数和 schedule（如 1F1B），JaxPP 自动展开为 task graph。API 限制循环体不产生跨迭代依赖，确保 schedule 灵活性。

3. **Single-controller MPMD runtime**：一个 driver 进程追踪和编译整个训练步骤，将 Jaxpr IR 切分为多个 SPMD task，通过 Ray RPC 分发到远程 actor。每个 actor 管理一组高带宽互连的设备，task 内部使用标准 SPMD 并行。

4. **自动通信推断**：JaxPP 从 task graph 自动推断 send/receive 操作，使用 NCCL P2P 通信。按拓扑序调度异步 send/receive，避免死锁，同时实现通信与计算的 overlap。

5. **Task fusion**：将所有 task dispatch 融合为每个 actor 一次 RPC 调用，避免多次往返的开销。

---

## 四、实现细节

- **基于 JAX/XLA 构建**：不 fork JAX 或 XLA，使用上游版本。每个 task 由 XLA 编译为标准 SPMD 程序。唯一的自定义 kernel 是 cuDNN attention API。
- **Stage 推断算法**：先为每个 `pipeline_yield` 创建 task，收集其依赖的计算；再将剩余计算分配到 operand 所在的 task。不允许循环体内的计算复制。
- **Placement inference**：从 `pipeline_yield` 注解推断输入输出的 placement，向前后传播，确保数据 pinned 在正确 actor 上。
- **Weight sharing 优化**：对 tied embedding 等共享权重，实现 loop commuting pass，将梯度累加从 `g = ((g₁+g₂)+g₃)+...` 重写为 `g = Σg₁ + Σg₂ + ...`，避免跨 actor 传输多份 partial gradient（可达数 GB）。
- **Buffer deletion**：生成 local schedule 后执行 liveness 分析，插入 deletion 操作。Send 完成后立即释放 buffer，未完成的放入 pending queue。
- **RemoteMesh**：`RemoteMesh((PP,), spmd_mesh=(TP, DP))` 指定拓扑，自动将高带宽互连的设备分配给同一 actor。
- **Schedule 声明式指定**：用户提供 `[Task(i, ty, stage)]` 列表，支持任意自定义 schedule。

## 五、实验结果

实验在 NVIDIA EOS 集群（DGX H100，InfiniBand NDR400）上进行，评估 GPT-3 175B 和 Llama 2 70B 的 BF16 训练。

### 主要性能对比

| 系统 | 模型 | GPU 数 | GBS | Step Time (s) | TFLOPS/device |
|------|------|--------|-----|---------------|---------------|
| JaxPP | GPT-3 175B | 128 | 256 | 9.22 | 478 |
| JAX FSDP | GPT-3 175B | 128 | 256 | 10.70 | 412 |
| JAX SPMD PP | GPT-3 175B | 128 | 256 | 13.96 | 316 |
| NeMo | GPT-3 175B | 128 | 256 | 8.82 | 500 |
| JaxPP | Llama 2 70B | 64 | 128 | 7.42 | 490 |
| JAX FSDP | Llama 2 70B | 64 | 128 | 8.44 | 431 |
| NeMo | Llama 2 70B | 64 | 128 | 7.02 | 519 |

### 关键结果

- **vs JAX SPMD PP**：JaxPP 快 51.2%（478 vs 316 TFLOPS），同时减少约 1K 行用户代码。
- **vs JAX FSDP**：JaxPP 吞吐提升 1.16×。
- **vs NeMo**：JaxPP 达到 NeMo 的 95.6% 吞吐（GPT-3 175B），但 JaxPP 是 model-agnostic 的。
- **Weak scaling**：64→1024 GPU 扩展效率 98.33%，优于 JAX FSDP 的 93.97%。
- **性能分解**：相比 SPMD PP，主要收益来自 rematerialization 减少（~20%）和异步 P2P 通信 overlap。

## 六、批判性分析

1. **与 NeMo 的对比不够公平**：NeMo 使用了 tensor sequence parallelism 和 AsyncTP（Collective Matmul）等优化，而 JaxPP 没有。论文将此差距归因于"JaxPP 是通用框架"，但这恰恰说明通用性带来了实际性能代价。95.6% 的吞吐比看似接近，但在大规模训练中 4.4% 的差距意味着显著的成本增加。

2. **模型覆盖面窄**：仅评估了 GPT-3 175B 和 Llama 2 70B 两个模型，且都是标准 dense Transformer。论文声称支持异构 stage 和 Expert Parallelism，但未提供任何 MoE 模型的实验验证。

3. **Single-controller 的可扩展性存疑**：论文展示了 1024 GPU 的 weak scaling，但实际大规模训练（如 Llama 3 用了 16K GPU）的场景下，单 controller 的 tracing、编译和 dispatch 开销可能成为瓶颈。论文未讨论编译时间。

4. **Interleaving/dispatch overhead 的 tradeoff 未充分分析**：Figure 7 显示 circular repeat 从 6 到 12 时性能下降，但论文仅定性描述了"task 太小导致 dispatch 开销"，缺乏量化分析（如 dispatch 延迟 vs 计算时间的比值）。

5. **缺少与最新 schedule 的对比**：论文声称支持 Zero Bubble PP 等新 schedule，但未实际评估。Given that Zero Bubble PP 是当前 SOTA schedule，这是一个重要缺失。

6. **内存使用数据缺失**：论文反复强调 1F1B 相比 GPipe 的内存优势（2-3× reduction），但未提供实际的内存占用数据对比。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **SPMD + MPMD 分层架构**是一个重要的设计模式：节点内用 SPMD（TP + DP），节点间用 MPMD（PP），匹配硬件拓扑的带宽层级。这一思路可推广到更多异构场景（如 GPU-CPU 混合训练、multi-datacenter 训练）。

2. **`pipeline_yield` 的 dependency-based stage inference** 比显式 stage function 更优雅，降低了 PP 的接入成本。这种"annotation-driven, compiler-inferred"的范式可以迁移到其他分布式计算场景。

3. **Loop commuting pass** 对 weight sharing 梯度的优化思路精巧，避免了大量跨节点通信。类似的代数变换可以应用于其他有 shared parameter 的场景（如 LoRA adapter sharing）。

### 值得跟进的方向

- **自动 schedule 搜索**：JaxPP 提供了灵活的 schedule 接口但需要用户手动指定。结合 Alpa 的 cost model 思路，自动搜索最优 PP schedule + 并行策略组合是一个自然的延伸。
- **Inference pipeline parallelism**：JaxPP 的 MPMD runtime 可以适配到长序列推理场景（如 sequence parallelism for long-context inference），其异步 P2P 机制天然适合。
- **与 AsyncTP/Collective Matmul 的集成**：弥补与 NeMo 的性能差距，这需要在 XLA 层面实现 computation-communication overlap。

---

## 八、总结

JaxPP 是 NVIDIA 提出的基于 JAX/XLA 的 MPMD pipeline parallelism 系统，通过在 SPMD 编程模型之上引入时间并行维度，使用户能以最小代码改动（`pipeline_yield` + `accumulate_grads`）实现灵活的 PP schedule（如 Interleaved 1F1B）。在 GPT-3 175B 训练上，JaxPP 比 JAX SPMD PP 快 51.2%，比 FSDP 快 1.16×，达到 NeMo 95.6% 的性能，同时保持 model-agnostic 的通用性和 98.33% 的 weak scaling 效率。主要局限在于与手工优化系统（NeMo）仍有性能差距，以及大规模（>1K GPU）场景下 single-controller 架构的可扩展性有待验证。
