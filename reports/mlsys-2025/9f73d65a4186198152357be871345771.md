## 1. 研究背景与动机

在大规模深度学习训练中，数据并行（Data Parallelism）和张量并行（Tensor Parallelism, TP）已广泛应用于加速训练。然而，当模型规模进一步增大时，单个设备的内存已无法容纳完整模型参数，传统 SPMD（Single Program Multiple Data）编程模型在扩展性上面临严峻挑战。具体而言：

1. **SPMD 模型的通信瓶颈**: 在大规模设备集群中，所有集合通信操作（Collective Operations）都在 SPMD 模型下执行，当设备数量增多时，集合通信的开销会显著损害性能。
2. **流水线并行的灵活性需求**: 现有的流水线并行（Pipeline Parallelism, PP）实现往往与特定模型架构紧耦合，难以灵活定义用户自定义的梯度累积调度策略。
3. **异构并行策略的统一编程**: 不同并行策略（DP、TP、PP）之间需要无缝集成，而现有框架缺乏统一的抽象来描述这些并行策略。

JaxPP（JAX Pipeline Parallelism）正是为了解决这些问题而提出的。

## 2. 研究问题与核心挑战

**核心问题**: 如何在大规模 GPU 集群上高效训练超大模型，同时保持编程模型的灵活性和易用性？

**具体挑战**:
1. **流水线气泡（Pipeline Bubbles）**: 传统流水线并行调度（如 1F1B）在管道填充和排空阶段会产生大量空闲气泡，降低 GPU 利用率。
2. **设备放置（Device Placement）**: 如何将模型的不同阶段自动映射到远程设备，并自动推断通信依赖关系。
3. **动态调度与容错**: 用户自定义流水线调度需要灵活的任务分发机制，同时保证远程执行的可靠性。
4. **通信与计算重叠**: 远程 SPMD 任务的集合通信需要与计算充分重叠。

## 3. 主要贡献

1. **MPMD 流水线并行编程模型**: 提出了一个允许用户自定义流水线调度策略的编程模型，通过 `@task` 装饰器和 `pipeline_yield` 原语实现任务的声明式定义。
2. **自动设备放置与通信推断**: JaxPP 能自动将流水线阶段分发到远程设备集群，并自动推断任务间的 AllGather、Send、Receive 等通信操作。
3. **重新计算策略（Recomputation Policy）**: 引入基于 JAX checkpoint API 的细粒度重计算策略，可在编译时优化激活内存使用。
4. **高效的运行时调度**: 通过远程 SPMD Actors 实现长生命周期的工作进程，避免重复的调度开销。
5. **与上游 JAX/XLA 兼容**: 无需自定义内核，仅使用 cuDNN 的注意力 API，降低了工程复杂度。

## 4. 核心方法与设计

### 4.1 MPMD 流水线并行模型

JaxPP 的核心设计基于 MPMD（Multiple Program Multiple Data）模型，区别于传统的 SPMD。在 MPMD 模型下，每个流水线阶段可以是不同的"程序"，通过显式的 `pipeline_yield` 进行阶段间的数据传递。

```python
@task
def s0(a, b):
    z = ...
    x = pipeline_yield(x, 's0')
    return (z, x)

@task
def s1(c, d, z):
    y = c + d * z
    y = pipeline_yield(y, 's1')
    return y
```

### 4.2 设备放置推断

编译阶段，JaxPP 根据用户提供的 `partitioning` 规范和设备网格形状，自动推断每个任务的设备放置：

```python
partitioning = [batch ▷ data, mlp ▷ model]
```

### 4.3 循环重复调度（Circular Repeat Scheduling）

针对流水线气泡问题，JaxPP 提出了循环重复调度策略：将多个 microbatch 在设备间循环排列，使得不同阶段的计算可以更充分地重叠。

### 4.4 重计算策略

通过 JAX 的 `jax.checkpoint` API，可以选择性地对中间激活进行重计算，以空间换时间：

```
∑ robatches( g(i)+g(i)+... ) ⇝ ∑ g(i) + ∑ g(i)
```

### 4.5 任务图与通信推断

JaxPP 在编译时构建任务依赖图，自动插入 AllGather、Send、Receive 等通信操作，确保分布式执行的正确性。

## 5. 实现细节

JaxPP 基于上游 JAX 和 XLA 实现，主要依赖：
- JAX 的函数式编程模型（`jax.grad`、`jax.pmap`）
- XLA 的编译器基础设施
- GSPMD 的分片注解机制
- cuDNN 的 FlashAttention API

运行时架构采用 Driver Process + Remote SPMD Actors 的设计：
- Driver Process 负责任务分发和调度协调
- Remote SPMD Actors 是长期存活的工作进程，避免重复的进程创建开销

## 6. 实验结果

### 6.1 GPT-3 175B 模型训练

在 64 块 H100 GPU 上训练 GPT-3 175B，配置为 TP=8 × PP=8：

| 配置 | GBS | GA | GPUs | PP | TP | Step Time | TFLOPS/device |
|------|-----|-----|------|-----|-----|-----------|--------------|
| JaxPP | 256 | 32 | 128 | 8 | 8 | 9.22s | 478 |
| JaxPP | 1024 | 32 | 512 | 8 | 8 | 9.32s | 473 |
| JAX FSDP | 256 | 1 | 128 | 1 | 1 | 10.70s | 412 |
| JAX SPMD PP | 256 | 128 | 128 | 16 | 4 | 13.96s | 316 |
| NeMo | 256 | 64 | 128 | 8 | 4 | 8.82s | 500 |

**分析**: JaxPP 在使用更多 GPU（512）时，相比单节点 128 GPU 的 FSDP 基线提升了约 20% 的吞吐量（9.32s vs 11.30s step time）。不过，NeMo 的结果（8.82s）仍然优于 JaxPP。

### 6.2 Llama2 70B 模型训练

在 8 DGX H100 节点（64 GPU）上训练 Llama2 70B，JaxPP 也展示了良好的扩展性。

### 6.3 流水线气泡分析

实验表明，使用循环重复调度（circular repeat size = 6）可以在保持相近 TFLOPS 的同时，最小化流水线气泡。

## 7. 潜在问题与局限性

1. **与 NeMo 的差距**: 在 GPT-3 175B 实验中，NeMo 的 step time（8.82s）仍然优于 JaxPP（9.22s），说明 JaxPP 在极致性能上仍有提升空间。
2. **调度开销**: 虽然采用了长生命周期 Actors，但 dispatch overhead 在小批量情况下可能仍然显著。
3. **自定义内核缺失**: 仅使用上游 JAX/XLA 和 cuDNN，虽然降低了工程复杂度，但可能限制了进一步的性能优化空间。
4. **通信推断的完整性**: 自动通信推断在复杂拓扑结构下的行为还需要更多验证。

## 8. 未来工作

1. 进一步优化循环调度策略，减少流水线气泡
2. 探索与张量并行的更深度结合
3. 支持更复杂的设备拓扑（如 3D 网格）
4. 减少 dispatch overhead

## 9. 个人评注

JaxPP 提出了一个优雅的 MPMD 流水线并行编程模型，通过函数式编程的 `@task` 装饰器和 `pipeline_yield` 原语，实现了灵活的用户自定义调度策略。这一设计很好地解决了传统流水线并行与特定模型紧耦合的问题。

论文的核心亮点在于将 SPMD 和 MPMD 的优势结合：底层使用高效的 SPMD 执行远程任务，上层通过 MPMD 的任务图抽象提供灵活的用户接口。自动通信推断和placement inference 也是非常实用的自动化优化。

不过，论文的实验部分略显单薄——在与业界领先的 NeMo/Megatron 方案的对比中，JaxPP 并没有展示出明显的优势。这可能是因为 JaxPP 更侧重于编程灵活性和原型快速开发，而非极致性能。对于需要快速实验新流水线调度策略的研究者来说，JaxPP 是一个值得关注的选择。
