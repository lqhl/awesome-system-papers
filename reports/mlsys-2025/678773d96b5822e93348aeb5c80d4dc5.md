# AdaParse: An Adaptive Parallel PDF Parsing and Resource Scaling Engine

**作者**：Carlo Siebenschuh, Kyle Hippe, Ozan Gokdemir, Alexander Brace, Arham Khan, Khalid Hossain, Yadu Babuji, Nicholas Chia, Venkatram Vishwanath, Rick Stevens, Arvind Ramanathan, Ian Foster, Robert Underwood（University of Chicago, Argonne National Laboratory）

## 一、背景

科学文献是训练科学领域大语言模型的关键数据来源，但绝大多数科学文献以 PDF 格式分发。PDF 是面向排版的格式，并非为机器可读性设计，解析质量参差不齐。现有的 PDF 解析工具可大致分为三类：

1. **文本提取工具**（如 PyMuPDF、pypdf）：速度极快但准确率有限，遇到嵌入文本质量差或文本加密时容易出错
2. **OCR 工具**（如 Tesseract、GROBID）：不依赖嵌入文本层，但计算成本高，需要后处理
3. **Vision Transformer**（如 Nougat、Marker）：解析质量最高，但推理成本极高（单节点 4×A100 仅能处理 1-2 PDF/s），难以大规模部署

当前科学文本数据集规模有限（如 Dolma 仅含 70B 科学 token），且约 80% 的 ACM 等出版商论文未被 PILE 和 S2ORC 收录。因此，构建高质量、万亿 token 级别的科学文本数据集，需要兼顾解析准确率和吞吐量的大规模解析方案。

---

## 二、要解决的问题

1. **单一解析器无法兼顾质量与效率**：高质量解析器（Nougat）吞吐量极低（~1-2 PDF/s/node），而高吞吐解析器（PyMuPDF，~315 PDF/s）准确率不足
2. **没有通用最优解析器**：不同 PDF 的内容复杂度差异巨大，"简单"文档用轻量工具即可获得高质量输出，复杂文档则必须使用重型解析器
3. **质量评估指标与人类偏好不一致**：BLEU、ROUGE 等指标无法完全捕捉科学文本的正确性（如 "hyperthyroidism" vs "hypothyroidism" 编辑距离仅为 2，但语义完全相反）
4. **大规模并行解析的系统挑战**：异构 PDF 导致负载不均衡，I/O 密集型工作负载需要优化文件系统访问模式

---

## 三、洞察与设计

**关键洞察**：大部分科学 PDF 是"简单"文档，可以用轻量级文本提取工具以高得多的吞吐量获得与计算密集型解析器相当甚至更好的输出质量；而文本提取工具输出中的畸形模式（如 LaTeX 残留、空白注入、字符乱序）本身就是判断文档解析难度的有效信号。

基于此洞察，AdaParse 设计了一个层级分类流水线，利用 PyMuPDF 的快速文本提取结果来决定是否需要调用更昂贵的解析器：

1. **CLS I（验证阶段）**：基于提取文本的聚合统计特征（如字符数量）判断文本是否有效。无效则直接送往 Nougat
2. **CLS II（改进判断阶段）**：基于文档元数据（创作工具、发布年份、页数）判断是否值得用更好的解析器重新解析
3. **CLS III（解析器选择阶段）**：使用微调的 SciBERT（LLM 变体）基于提取文本中的细微模式选择最适合的解析器

系统提供两个变体：
- **AdaParse(FT)**：合并 CLS I 和 CLS II，使用 fastText 嵌入，不调用 LLM，吞吐量更高（~78 PDF/s）
- **AdaParse(LLM)**：使用 SciBERT 进行 CLS III 推理，准确率更高，支持 DPO 对齐人类偏好

## 四、实现细节

**偏好对齐**：通过 Direct Preference Optimization (DPO) 将解析器选择与人类判断对齐。23 位跨学科科学家在类似 ChatBot Arena 的界面上提供了 2794 个偏好标注（642 个文档页面），标注者间一致率达 82.2%。DPO 用于 SciBERT 的 LoRA 微调后训练。

**并行执行优化**（基于 Parsl 工作流引擎，部署于 Polaris 超算）：
- **模型持久化**：Nougat 的 Swin Transformer（350M 参数）加载需 ~15s，通过 warm-start 机制让模型权重在 worker 进程间持久化，避免重复加载
- **I/O 优化**：将输入 PDF 聚合为压缩 ZIP 归档，传输至节点本地 RAM 存储，避免频繁读写 Lustre 分布式文件系统上的小文件
- **GPU 资源共享**：PyMuPDF 仅用 CPU，Nougat 用 GPU，两者无资源竞争
- **固定分辨率逐页解析**：Nougat 使用 (896, 672) 固定图像输入尺寸，batch size = 10 页，规范化任务大小以获得一致的执行时间
- **计算预算约束**：限制每节点最多 α = 5% 的文档使用 Nougat

**形式化**：将解析器分配建模为多目标优化问题——最大化总准确率的条件期望，同时约束总计算成本不超过预算 T。该问题天然可分解为 embarrassingly parallel 工作负载。

## 五、实验结果

**实验环境**：Polaris 超算（ANL），560 节点，每节点 32 核 AMD Milan + 4×A100 40GB + Lustre 文件系统。

**基准数据**：25,000 篇跨学科、跨出版商的 PDF（ArXiv, BioRxiv, BMC, MDPI, MedRxiv, Nature），8 个领域，67 个子类。测试集 1,000 篇 born-digital PDF。

### 解析质量（born-digital PDF）

| Parser | Coverage% | BLEU% | ROUGE% | CAR% | WR% | AT% |
|---|---|---|---|---|---|---|
| Marker | 96.7 | 47.5 | 64.2 | 59.6 | 26.6 | 73.3 |
| Nougat | 93.0 | 48.1 | 66.5 | 65.8 | 27.9 | 69.8 |
| PyMuPDF | 91.3 | 51.9 | 67.3 | 67.0 | 24.4 | 76.7 |
| pypdf | 92.0 | 43.6 | 58.7 | 32.3 | 2.4 | 72.4 |
| GROBID | 81.0 | 26.5 | 52.4 | 54.8 | – | 20.6 |
| Tesseract | 91.3 | 48.8 | 64.2 | 67.8 | 18.7 | 72.5 |
| **AdaParse** | **91.5** | **52.1** | **67.6** | **67.1** | **25.5** | **76.9** |

### 吞吐量（128 节点）

| Parser | 吞吐量 (PDF/s) |
|---|---|
| PyMuPDF | ~315 |
| AdaParse(FT) | ~78 |
| Nougat | ~8 |
| Marker | ~0.1 |

- AdaParse 在 BLEU、ROUGE、Accepted Tokens 三个指标上超过所有单一解析器
- 吞吐量比 Nougat 高 17×，同时准确率实际高出 0.2%
- BLEU 预测 R² = 40.0%（PyMuPDF）/ 46.5%（Nougat）
- 在模拟扫描退化和 OCR 退化文本层场景下同样表现稳健

## 六、批判性分析

1. **"比 Nougat 高 0.2%"的准确率提升微乎其微**：BLEU 52.1% vs 51.9% 的差异在统计上是否显著未报告，且论文承认 BLEU 仅解释 47% 的用户偏好变异，这意味着这个 0.2% 的提升在用户感知层面可能完全不可区分

2. **α = 5% 的 Nougat 使用限制是人为设定的**：这个比例的选择缺乏充分论证。如果允许更高比例的 Nougat 使用，单一 Nougat 策略可能在质量上超越 AdaParse，吞吐量的优势也会缩小。论文未给出 α 的敏感性分析

3. **基线不完整**：论文未与近年更先进的 PDF 解析工具（如 2024 年的 MinerU、Docling 等）进行比较。Nougat 作为"高质量解析器"的代表在 2025 年已略显过时

4. **Ground truth 质量存疑**：使用 HTML 解析结果作为 ground truth，但 HTML 到纯文本的转换本身也会引入误差，且仅限于有 HTML 版本的论文，引入选择偏差

5. **DPO 数据规模偏小**：仅 712 个训练样本用于 DPO 微调，23 位标注者的学科覆盖虽广但每人标注量有限。论文未讨论标注者疲劳或学习效应对偏好一致性的影响

6. **扩展性瓶颈未深入分析**：PyMuPDF 在 ~128 节点时因文件系统竞争而出现吞吐量饱和，但 AdaParse 以 PyMuPDF 为基础，理论上会面临同样的瓶颈。论文未讨论 AdaParse 本身的扩展性上限

7. **Win Rate 指标设计有利于 AdaParse**：WR 和 AT 指标是论文自定义的，且基于同一批标注数据训练和评估，存在循环论证的风险

---

## 七、AI Infra / MLSys 视角

1. **自适应计算调度范式的启发**：AdaParse 的核心思想——根据输入特征动态选择计算路径——可迁移到 LLM 推理场景。例如，根据请求复杂度动态选择不同大小的模型（speculative decoding 的路由版本），或在 MoE 架构中进行更精细的 expert 路由

2. **数据预处理流水线的系统优化**：论文展示的 I/O 优化策略（ZIP 聚合、节点本地 RAM 缓存、模型 warm-start）对大规模数据预处理流水线有直接参考价值。特别是在 Lustre 等并行文件系统上处理海量小文件时的优化经验

3. **DPO 用于系统决策对齐**：将 DPO 从 RLHF 场景迁移到系统配置选择是一个有趣方向。可以探索用类似方法对齐编译器优化选择、内存管理策略、调度算法等系统决策与用户偏好

4. **可跟进的研究方向**：
   - 将自适应路由思想应用于 LLM 推理中的 KV cache 管理——根据请求特征选择不同的缓存/压缩策略
   - 构建面向科学文献的端到端 RAG pipeline，集成 AdaParse 作为文档解析层，研究解析质量对下游 LLM 任务的定量影响
   - 探索用 LLM-as-a-Judge 替代人工标注来扩大偏好数据规模，降低 DPO 对人工标注的依赖

---

## 八、总结

AdaParse 提出了一种自适应 PDF 解析策略，通过层级分类流水线将文档路由到最合适的解析器，结合 DPO 对齐人类偏好。在 Polaris 超算上的实验表明，AdaParse 在限制仅 5% 文档使用 Nougat 的前提下，实现了比 Nougat 高 17× 的吞吐量和略优的 BLEU 分数。该工作的主要价值在于系统层面的工程优化和自适应调度思想，但核心的准确率提升较为边际，且基线对比不够全面。适用于需要大规模高质量解析科学文献语料库的场景。
