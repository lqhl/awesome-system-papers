## 一、背景

在 IoT 边缘设备上部署 DNN 已成为趋势，MCU（微控制器）因低功耗、低延迟和数据隐私优势成为重要的推理平台。然而 MCU 的计算和存储资源极度受限，需要通过量化、剪枝、神经架构搜索等手段压缩模型。

权重剪枝（pruning）通过将不重要的权重置零来减少计算量和存储，但稀疏工作负载的不规则内存访问和较低的算术密度使得实际加速效果往往低于预期。N:M 半结构化稀疏（每 M 个权重中保留 N 个非零值）在精度损失和硬件友好性之间取得了平衡，已在 NVIDIA A100 GPU 上获得硬件支持（2:4 格式），但在 MCU 上的加速方案仍然缺乏。

现有 MCU 上的稀疏加速工作要么针对非结构化稀疏、要么依赖复杂的专用加速器或大面积的硬件扩展（如 SSR），不适合面积和功耗极度敏感的超低功耗 MCU。

---

## 二、要解决的问题

1. **MCU 上缺乏 N:M 稀疏支持**：现有 MCU 稀疏加速方案主要针对非结构化稀疏或 blockwise 稀疏，未利用 N:M 格式的结构化优势。

2. **纯软件方案性能受限**：在 MCU 上实现 N:M 稀疏内核时，索引解压和激活值加载操作产生大量额外指令（内循环 22-23 条指令中仅 8 条 MAC），严重制约加速效果，尤其 1:4 稀疏反而比 dense 更慢。

3. **硬件加速器面积开销过大**：完整稀疏加速器或 SSR（Sparse Stream Semantic Registers）带来 20-44% 的面积开销，对超低功耗 MCU 不可接受。

4. **端到端部署缺乏编译器支持**：现有 DNN 编译器不支持稀疏内核的 tiling、内存布局优化等，无法直接部署稀疏网络。

## 三、洞察与设计

**关键洞察**：N:M 稀疏内核的主要瓶颈不在计算本身，而在于从 im2col buffer 中根据压缩索引加载对应激活值的间接寻址操作——索引解压（shift+mask）和字节加载可以合并为单条指令（xDecimate），从而将内循环指令数从 22 条降至 12 条，以仅 5% 的面积代价获得接近 2× 的额外加速。

### 整体方案

论文提出三层贡献：

**1. 软件内核设计（SW-only）**：
- 采用 "Decimate Im2col" 策略：保持 im2col 变换不变，在内循环中根据 NZ 索引从 im2col buffer 选取对应激活值
- 支持 Conv 和 FC 层的 1:4、1:8、1:16 稀疏格式
- 使用 N:M 压缩格式存储权重：NZ 值 + 4-bit（或 2-bit）相对索引
- 内循环 unrolling factor 为 1×2（两个空间位置，一个输出通道）

**2. ISA 扩展（xDecimate 指令）**：
- 将索引解压 + 间接字节加载合并为单条 R-type 指令
- 语法：`xdecimate rd, rs1, rs2`，rs1 存 im2col buffer 基地址，rs2 存压缩索引，rd 为目标寄存器
- 使用一个 CSR（control-status register）自动递增来追踪当前位置
- 硬件实现为 eXtension Functional Unit (XFU)，集成到 RI5CY 处理器的 ID/EX/WB 三个流水线阶段

**3. 编译器集成（MATCH）**：
- 修改 pattern recognition 以识别 N:M 稀疏模式
- 调整 tiling 引擎考虑压缩后的权重和索引大小
- 优化 L2 内存布局，将权重和索引交错存储以支持单次 DMA 传输

## 四、实现细节

### xDecimate 硬件实现

- 在 RI5CY/CV32E40P（RV32IMC + Xpulpv2）处理器中添加 XFU
- EX 阶段核心逻辑（以 1:8/1:16 为例）：
  - `o ← rs2[(csr[2:0]*4+3):(csr[2:0]*4)]`（从压缩索引中提取偏移）
  - `addr ← rs1 + M * csr[15:1] + o`（计算激活值地址）
- WB 阶段：从内存响应中提取字节，写入 rd 的正确位置
- CSR 每次执行自动递增，`xDecimate.clear` 指令重置
- 支持数据转发以处理连续 xDecimate 指令的数据依赖
- 面积开销：5.0%（基于 22nm 工艺，200MHz，worst-case 条件）
- RTL 开源：https://github.com/eml-eda/cv32e40x_decimate

### FC 层特殊处理

- FC 层无输入复用，但为复用同一 xDecimate 指令，离线重排 OFFSETS 数组，交替存储两个相邻输出通道的索引
- 实现 2 通道 unrolling：vB1 存第 i 通道的激活值，vB2 存第 i+1 通道的

### 存储格式

- 1:4 稀疏：权重内存减少 68.75%（2-bit 索引）
- 1:8 稀疏：权重内存减少 81.25%（4-bit 索引）
- 1:16 稀疏：权重内存减少 90.62%（4-bit 索引）

### 目标平台

- Vega PULP SoC：10 个 RISC-V 核心（1 FC + 1 DMA + 8 计算核），128KB L1 共享 scratchpad，1.6MB L2，16MB L3 HyperRAM
- 使用 GVSoC 虚拟平台仿真

## 六、批判性分析

1. **评测规模偏小**：端到端实验仅在 CIFAR10/CIFAR100 上评测 ViT-Small 和 ResNet18，这些都是非常小的模型和数据集。论文虽声称"更大模型会获得更大加速"，但未提供实际验证。

2. **ViT 评测不完整**：由于 MATCH 编译器不支持 attention 层，ViT 的评测是拼凑两个编译器（MATCH + Deeploy）的逐层结果，非真正的端到端部署，可能遗漏层间调度和数据搬运的开销。

3. **仅支持固定 N=1 的稀疏模式**：论文仅实现 1:4、1:8、1:16，未探索 2:4 等其他 N:M 组合。考虑到 2:4 是 GPU 上最常用的格式，这一限制值得注意。

4. **能耗数据缺失**：作为超低功耗 MCU 上的工作，论文未报告任何能耗数据，仅在 future work 中提及将做 FPGA 原型以估算能耗。对于 IoT 场景，能耗比延迟更重要。

5. **与 ARM 平台的可迁移性未验证**：论文多次声称设计可迁移到 ARM Cortex-M 等平台，但未提供任何 ARM 上的实验结果，仅停留在概念层面。

6. **ISA 扩展的 xDecimate 指令增加了 NZ 索引的存储开销**：Conv 层中需要复制每个 NZ 索引（用于 2× unrolling），虽然论文认为"开销可接受"，但在 Table 2 中 ResNet18 ISA 版本的内存确实高于 SW-only 版本（如 1:4 从 3.66MB 增至 4.35MB），部分抵消了稀疏带来的存储优势。

7. **基线对比的公平性**：与 (Yu et al., 2017) 的对比中，论文指出其高 speedup 是因为 Flash 加载延迟，但两者的目标平台（ARM Cortex-M4 vs RISC-V PULP）、稀疏格式（blockwise vs N:M）完全不同，可比性有限。

## 七、AI Infra / MLSys 视角

1. **N:M 稀疏格式在异构硬件上的统一支持**：本文展示了 N:M 稀疏从 GPU（NVIDIA A100 的 2:4）到 MCU 的延伸。对于 AI Infra 而言，一个启发是设计统一的 N:M 稀疏编译器 pass，使同一稀疏模型能无缝部署到 GPU、CPU、MCU 等不同硬件。

2. **轻量级 ISA 扩展的设计思路**：xDecimate 用 5% 面积换取 ~2× 加速的思路，可迁移到 AI 推理芯片设计中。未来的 RISC-V AI 加速器可以考虑类似的"间接寻址加速"指令来支持稀疏 attention、稀疏 MoE routing 等场景。

3. **编译器-内核协同优化**：MATCH 编译器对 tiling、内存布局的修改配合底层内核设计的方法，对构建端到端稀疏推理 pipeline 有参考价值。特别是将压缩权重和索引交错存储以支持单次 DMA 传输的设计，可类比到 GPU 上的 weight layout 优化。

4. **值得跟进的方向**：
   - 可变稀疏度（per-layer/per-channel N:M 比例）的编译器自动调优
   - 将 xDecimate 思路扩展到支持 2:4 格式，与 GPU 训练时的稀疏格式对齐
   - 在 edge AI 芯片上探索 N:M 稀疏 + 低比特量化（如 INT4/INT2）的联合优化

---

## 八、总结

本文针对超低功耗 RISC-V MCU 上 N:M 半结构化稀疏 DNN 推理，提出了软件内核 + 轻量级 ISA 扩展（xDecimate）+ 编译器集成的三层方案。在 Vega PULP SoC 上实现了 ResNet18 最高 3.21×、ViT 最高 1.81× 的端到端加速，精度损失 < 1.5%，硬件面积开销仅 5%。方案的优势在于以极低的硬件代价获得显著的稀疏加速，适用于 IoT 边缘推理场景。主要局限在于仅验证了小规模模型/数据集，缺乏能耗评估，且 N:M 格式限于 N=1。
