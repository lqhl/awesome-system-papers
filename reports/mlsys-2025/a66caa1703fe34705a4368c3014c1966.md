# LUMOS: Efficient Performance Modeling and Estimation for Large-Scale LLM Training

**作者**：Mingyu Liang (Cornell University), Hiwot Tadese Kassa, Wenyin Fu, Brian Coutinho, Louis Feng (Meta), Christina Delimitrou (MIT)
**会议**：MLSys 2025
**链接**：https://proceedings.mlsys.org/paper_files/paper/2025

## 一、背景

大规模 LLM 训练需要跨数百甚至数千 GPU 的分布式部署，涉及 3D 并行（数据并行 DP、张量并行 TP、流水线并行 PP）等复杂策略。为了优化训练效率，工程师需要理解模型的运行时行为——包括计算与通信的重叠、GPU 利用率、各阶段耗时分布等。然而，现有的性能建模方法要么基于高层解析模型（如 AmPeD、Calculon），缺乏细粒度执行细节；要么基于 trace 的方法（如 dPRO、Daydream）无法准确捕获现代 LLM 中复杂的跨 stream 依赖关系，导致性能预测误差较大。

---

## 二、要解决的问题

1. **现有 trace-based 方法无法准确建模 LLM 的执行行为**：LLM 训练中广泛使用的 compute-communication overlap 引入了复杂的 inter-stream 依赖，现有工具（如 dPRO）忽略了这些依赖，导致过度乐观地估计并行执行程度。例如，dPRO 在 GPT-3 175B 上的迭代时间误差高达 21.8%。
2. **配置探索成本高**：调整并行策略或模型架构需要在真实硬件上重新部署和运行，消耗大量 GPU 资源和时间。
3. **解析模型泛化能力差**：解析模型通常针对特定实现和硬件配置，难以跟上快速演进的模型和系统栈，且无法提供 operator/kernel 级别的细粒度信息。

---

## 三、洞察与设计

**关键洞察**：LLM 训练中 compute 和 communication kernel 在不同 CUDA stream 上并行执行时，存在四类依赖关系（CPU-CPU、CPU-GPU、GPU-CPU、GPU-GPU），其中 inter-stream GPU 依赖（通过 `cudaEventRecord` / `cudaStreamWaitEvent` 机制同步）和 runtime 动态依赖（如 `cudaStreamSync`）是准确建模 overlap 行为的关键，但被现有方法忽略。只要完整捕获这四类依赖，就能用 trace replay 精确重现 LLM 的执行行为。

基于这一洞察，Lumos 的设计包含三个核心模块：

1. **Trace Collection**：利用 PyTorch Kineto 内置 profiler 收集 CPU operator、CUDA runtime event 和 GPU kernel 的 trace，仅需在模型代码中插入约 10 行 hook 代码，无需框架或模型层面的额外插桩。
2. **Execution Graph Construction**：从 trace 中提取 CPU task 和 GPU task，通过 correlation ID、线程顺序、CUDA stream 顺序、以及事件同步机制识别四类依赖关系，构建完整的 task-level execution graph。
3. **Graph Manipulation + Simulation**：支持用户指定新的并行策略（调整 DP/PP）或模型架构（层数、hidden size），通过操作已有 execution graph 生成新图，再通过离散事件模拟估计性能，无需真实硬件运行。

---

## 四、实现细节

- **实现规模**：约 5,200 行 Python 代码。
- **Task 分类**：仅包含 CPU task（PyTorch operator + CUDA runtime event）和 GPU task（GPU kernel），每个 task 记录 metadata、所在 thread/stream。
- **依赖识别**：
  - Intra-thread：同一 CPU 线程上连续 task 的顺序依赖。
  - Inter-thread：通过检测线程内执行间隙，识别跨线程阻塞（如 backward 线程等待 forward 完成）。
  - CPU→GPU：通过 Kineto trace 中的 correlation ID 关联 CUDA launch event 与 GPU kernel。
  - GPU→CPU：`cudaDeviceSync` / `cudaStreamSync` 创建从 GPU task 到 CPU task 的依赖。
  - GPU→GPU (intra-stream)：同一 CUDA stream 内 kernel 顺序执行。
  - GPU→GPU (inter-stream)：通过 `cudaEventRecord` + `cudaStreamWaitEvent` 事件对识别。
- **Graph Manipulation**：
  - 调整 DP：仅更新 communication task 的执行时间（使用内部 fleet trace 性能模型）。
  - 调整 PP：重新划分 layer 到 stage，按调度策略（如 1F1B）重排 forward/backward 执行顺序，插入 stage 间 communication task。
  - 调整模型架构：增减 layer 时复制/删除对应 task 并重建依赖；调整 hidden size 时修改 operator 输入维度并更新关键 kernel（GEMM、通信 kernel）执行时间。
  - 不支持修改 TP（因 TP 通常固定在单节点内）。
- **Simulator**：基于 Algorithm 1 的离散事件模拟器，区分 fixed dependency（初始化时确定）和 runtime dependency（运行时动态分配），逐 task 调度执行并输出模拟 trace。

## 五、实验结果

**实验环境**：Meta 生产 ML 集群，最多 512 NVIDIA H100 GPU（32 台服务器），8×400Gbps RoCE 网络。CUDA 12.4 + PyTorch 2.5。

**模型**：基于 NVIDIA 开源 GPT-3 实现（MLPerf Training Benchmarks），四种规模变体：

| 模型 | 参数量 | 层数 | d_model | d_ffn | 注意力头数 |
|------|--------|------|---------|-------|-----------|
| GPT-3 15B | 15B | 48 | 6144 | 12288 | 48 |
| GPT-3 44B | 44B | 48 | 12288 | 24576 | 48 |
| GPT-3 117B | 117B | 96 | 12288 | 24576 | 96 |
| GPT-3 175B | 175B | 96 | 12288 | 49152 | 96 |

**Replay 精度**：

| 指标 | Lumos | dPRO (baseline) |
|------|-------|-----------------|
| 平均迭代时间误差 | **3.3%** | 14% |
| 最大误差 | ~5% | 21.8% |

- Lumos 在所有模型规模和并行配置下均保持 <5% 的 replay 误差。
- dPRO 系统性地高估 overlap 执行时间、低估总迭代时间，根因是未建模 inter-stream 依赖。
- SM utilization 时间序列对比显示 Lumos 与实际测量高度吻合。

**Graph Manipulation 预测精度**：

| 场景 | 平均误差 |
|------|---------|
| Scale-out DP（16→128 GPU） | ~3-5% |
| Scale-out PP | ~3-5% |
| 同时调整 DP + PP | 4.2% |
| 模型架构变化（层数/hidden size） | 与实际值高度吻合 |

## 六、批判性分析

1. **不支持 Tensor Parallelism 修改**：论文以"TP 通常固定"为由回避了 TP 的 graph manipulation，但 TP 的选择（TP=4 vs TP=8）对性能影响显著，尤其是跨节点 TP 场景。这是一个重要的实用性缺口。
2. **Kernel 执行时间预测依赖"内部性能模型"**：新配置下的 GEMM 和通信 kernel 时间使用 Meta 内部的 fleet trace 模型估算，但论文未公开该模型的细节和精度，外部用户无法复现此关键环节。这实质上将一个核心挑战外包给了不公开的组件。
3. **评估模型单一**：仅在 GPT-3 变体上评估，未涉及 MoE、多模态模型、或使用 FlashAttention/Ring Attention 等现代优化的模型。GPT-3 的执行模式相对规则，能否推广到更复杂的模型架构存疑。
4. **不估计内存消耗**：论文明确承认不建模 OOM 场景，但在实际配置探索中，内存约束往往是首要限制。一个不考虑内存的性能预测工具的实用价值会打折扣。
5. **Profiling 前提假设**：需要在目标硬件上先跑一次 profiling，获取 baseline trace。对于评估新硬件（如从 H100 迁移到 B200）的场景不适用。
6. **Scale-out 验证规模有限**：DP scale-out 仅验证到 128 GPU（从 16 GPU 基线），对于实际生产中的千卡甚至万卡规模，通信模式可能发生质变（如 congestion、topology-aware routing），Lumos 的线性外推是否成立未验证。

## 七、AI Infra / MLSys 视角

1. **实用价值**：对 AI Infra 团队而言，Lumos 的最大价值在于用低成本 trace（单次 profiling）+ simulation 替代反复的大规模实验来评估并行策略。在 GPU 资源紧张时，这种"profile once, simulate many"的范式非常实用。

2. **可迁移的设计思路**：
   - 四类依赖的完整建模方法可以直接应用于推理系统的性能分析（如 prefill-decode overlap、continuous batching 的调度分析）。
   - Graph manipulation 的思路可以扩展到 serving 场景的 capacity planning——从小规模 profiling trace 预测大规模部署的吞吐和延迟。

3. **值得跟进的方向**：
   - **支持 TP 修改和 Sequence Parallelism**：这是论文明确留下的 gap，技术上需要处理 all-reduce/all-gather 的 kernel 拆分与重组。
   - **集成 memory estimation**：结合 activation memory、optimizer state 建模，使工具能同时输出"能不能跑"和"跑多快"。
   - **跨硬件预测**：将 kernel 执行时间预测从 fleet trace 模型替换为 roofline model 或硬件 simulator，实现从 H100 trace 预测 B200 性能。
   - **与自动并行框架集成**：将 Lumos 作为 Alpa/Galvatron 等自动并行搜索框架的 cost model 后端，替代当前的粗粒度解析模型。

4. **最有价值的切入点**：将 Lumos 的 execution graph + simulation 方法适配到 LLM inference serving（如 vLLM、TensorRT-LLM），建模 prefill/decode 阶段的 GPU 资源争用和调度决策，这是当前 inference 优化中缺乏好工具的痛点。

---

## 八、总结

Lumos 是首个针对大规模 LLM 训练的细粒度 trace-driven 性能建模工具，核心创新在于完整捕获四类 task 依赖关系（特别是 inter-stream GPU 依赖），实现了 3.3% 平均误差的高精度 replay，显著优于 dPRO 的 14%。通过 graph manipulation 支持并行策略和模型架构的 what-if 分析，降低了配置探索的硬件成本。主要局限在于不支持 TP 修改、不建模内存消耗、kernel 时间预测依赖非公开的内部模型，且仅在 GPT-3 上验证。适合已有 baseline profiling trace、需要快速评估不同 DP/PP 配置的 AI Infra 团队使用。
