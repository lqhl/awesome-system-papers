# Radius: Range-based Gradient Sparsity for Large Foundation Model Pre-training

**作者**：Mingkai Zheng, Zhao Zhang（Rutgers University, Department of Electrical and Computer Engineering）
**会议**：MLSys 2025
**链接**：https://proceedings.mlsys.org/paper_files/paper/2025/hash/54dd9e0cff6d9214e20d97eb2a3bae49-Abstract-Conference.html

## 一、背景

大规模基础模型（Foundation Models）的预训练代价极高，LLaMA-7B 在 A100 集群上需要 82,432 GPU 小时，LLaMA-65B 需要超过 100 万 GPU 小时。在 3D 并行（DP + PP + TP）训练架构中，数据并行（Data Parallelism）引入的梯度同步通信是主要瓶颈之一——Optimus-CC 报告通信占 GPT-8.3B 训练时间的 40%。

梯度压缩是减少通信量的经典方法，包括稀疏化（sparsification）、低秩近似（low-rank approximation）和量化（quantization）。然而，现有方法多基于过时的假设：DGC 等 top-k 稀疏化方法假设低带宽网络（1 Gbps Ethernet）和 SGD 优化器，而现代 GPU 集群已配备 400-800 Gbps InfiniBand，且 AdamW 已成为 LLM 预训练的标准优化器。直接将 top-k 稀疏化应用于 AdamW 会导致训练不收敛。

---

## 二、要解决的问题

1. **Naive top-k 与 AdamW 不兼容**：top-k 直接作用于原始梯度，但 AdamW 对梯度执行非线性变换（一阶/二阶动量估计 + weight decay），导致被选中的 top-k 梯度不一定对应最大的参数更新。实验证实 naive top-k + AdamW 训练会发散。

2. **top-k 稀疏化的可扩展性差**：传统 top-k 方法中，每个 worker 的 top-k 索引不同，必须使用 allgather 收集所有 worker 的 (值, 索引) 对，通信量与 worker 数 n 成正比（$C_{allgather} \propto D \cdot (n-1)/n$），当 n 足够大时甚至超过 dense allreduce 的开销。同时 allgather 需要 n 倍缓冲区，内存开销也很大。

3. **低秩近似在大模型上计算代价过高**：PowerSGD 的正交化操作引入的计算开销超过了通信节省（实测 PowerSGD rank=128 的计算开销达 574.70 ms，远超 Radius 的 66.54 ms）。

---

## 三、洞察与设计

**关键洞察**：在 LLM 预训练过程中，经过约 15-20% 的总训练步数后，具有最大绝对值的梯度（top-1%）在梯度向量中的索引位置在时间上是高度稳定的——即哪些参数产生大梯度在连续多步中基本不变。

基于此洞察，Radius 的核心设计思路是：

1. **索引复用（Index Resampling）**：不必每步都重新计算 top-k 索引。引入重采样间隔 T，每 T 步做一次 dense allreduce 并重新选择 top-k 索引，中间 T-1 步复用同一组索引。由于所有 worker 在 dense allreduce 后拥有相同的聚合梯度，top-k 索引在所有 worker 上天然一致。

2. **仅用 allreduce 通信**：因为所有 worker 共享同一组 top-k 索引，只需对压缩后的 dense 子向量（大小为 d·D）执行 allreduce，避免了 allgather 的 O(n) 通信量和内存开销。allreduce 通信量为 $2(n-1)/n \cdot d \cdot D \cdot \beta$，与 worker 数 n 解耦。

3. **Gradient Correction**：在执行 top-k 选择之前，先对梯度施加 AdamW 的一阶/二阶动量校正（$\hat{m}_t / (\sqrt{\hat{v}_t} + \epsilon) + \lambda w_t$），使得 top-k 选择的是对参数更新贡献最大的维度，而非原始梯度最大的维度。

4. **Error Feedback**：使用残差缓冲区累积每步被丢弃的非 top-k 梯度值，在下一次 dense allreduce（每 T 步）时补偿回去，防止信息永久丢失导致发散。

---

## 四、实现细节

- 基于 **Megatron-LM** 框架实现
- top-k 选择使用 `torch.topk` 函数
- Gradient correction 复用 NVIDIA Apex 的 fused AdamW 实现，减少计算开销
- 索引存储优化：不使用 Int64 格式存储索引，而是用 **binary buffer**（布尔掩码）标记每个梯度是否被选为 top-k，大幅减少内存占用
- 使用 SGD 优化器执行实际参数更新（丢弃其动量缓冲区以进一步节省内存），gradient correction 阶段已完成了 AdamW 的核心计算
- PyTorch 的 slicing 操作不支持大于 INT32_MAX 的 binary buffer，因此每层维护独立的索引缓冲区以支持超过 2.1B 参数的模型
- 训练前 15-20% 步数使用标准 dense allreduce（warm-up 阶段），之后切换到 Radius

## 五、实验结果

**实验环境**：NERSC Perlmutter 超算，16 节点 × 4 NVIDIA A100-80GB，节点内 NVLink 3（600 GB/s），节点间 HPE Slingshot 11（每 GPU 25 GB/s NIC，总计 100 GB/s）。

**模型与数据**：GPT-355M（24 层, 16 头, d=1024）和 GPT-2.0B（24 层, 32 头, d=2560），OpenWebText 数据集，纯 DP=64 训练。

### 训练效率（GPT-2.0B, 64 A100 GPUs）

| 配置 | 训练 PPL | 验证 PPL | Wall-clock 时间 (天) | 加速比 |
|------|---------|---------|-------------------|--------|
| Baseline (dense allreduce) | 10.86 | 11.42 | 6.44 | — |
| Radius d=0.9, T=200 | 10.87 | 11.37 | 6.82 | -5.55% |
| Radius d=0.5, T=200 | 10.89 | 11.39 | 5.73 | 12.40% |
| Radius d=0.4, T=200 | 10.94 | 11.41 | 5.43 | 18.55% |
| Radius d=0.4, T=400 | 10.94 | 11.46 | 5.41 | 19.03% |
| Radius d=0.1, T=200 | 11.85 | 11.98 | 4.78 | 34.76% |

## 六、批判性分析

1. **模型规模过小**：实验仅覆盖 355M 和 2.0B 参数模型，距离当前主流的 7B-70B+ 规模有很大差距。作者声称 Radius 适用于"large foundation model pre-training"，但未提供任何大于 2B 的实验证据。梯度 top-k 索引的时间稳定性是否在更大模型上仍然成立是未经验证的关键假设。

2. **仅测试纯 DP 配置**：实际 LLM 训练使用 3D 并行（DP + PP + TP），而实验中 PP=1, TP=1，即纯数据并行。论文自己也承认未来工作需要扩展到 3D 并行。在真实场景中，DP 组的大小通常远小于 64（因为 TP/PP 已经分走了部分 GPU），此时通信压缩的收益可能大幅缩水。

3. **单次实验无方差报告**：作者明确承认由于计算预算限制，每个配置只跑了一次实验（相同随机种子）。下游任务评估分数的波动无法与 baseline 做统计显著性比较，Table 4-6 中部分指标 Radius 优于 baseline 可能纯属噪声。

4. **warm-up 阶段抵消了部分加速**：Radius 在前 15-20% 步使用 dense allreduce，端到端加速比（19%）显著低于稳态加速比（21%）。对于更长的 warm-up 或更短的总训练步数，实际收益会进一步缩水。作者尝试从 5% 开始切换但导致下游任务性能显著下降，说明这个 warm-up 比例并非保守估计。

5. **d=0.1 的结果被过度宣传**：Table 2 中 d=0.1 达到 34.76% 加速，但训练 PPL 从 10.86 劣化到 11.85（+9.1%），验证 PPL 从 11.42 到 11.98（+4.9%）。论文在摘要和结论中仍将其作为亮点提及，但这种精度损失在实际应用中通常不可接受。

6. **互连带宽场景单一**：实验全部在 Perlmutter（Slingshot 11, 25 GB/s per GPU NIC）上进行。对于更常见的 InfiniBand HDR/NDR（200-400 Gbps per port）集群或 NVSwitch 全互联架构，通信占比和加速效果可能完全不同。

7. **与 Naive top-k 的对比（Section 6.5）使用了不同的硬件**：baseline 和 Radius 在 Perlmutter 上测试，而 naive top-k 对比实验在 Vista（GH200 + NDR InfiniBand）上进行，硬件差异使得比较不够公平。

## 七、AI Infra / MLSys 视角

1. **梯度时间局部性是有价值的观察**：top-k 梯度索引在训练中后期的稳定性值得在更多场景中验证——不同模型架构（MoE、Vision Transformer）、不同训练阶段（SFT、RLHF）以及更大模型规模。如果这一性质普遍成立，可以衍生出更多基于"预测哪些参数重要"的优化方法。

2. **与 ZeRO 的结合值得探索**：当前 Radius 仅在全模型复制的 DP 上测试。在 ZeRO-1/2/3 下，通信模式不同（parameter/gradient/optimizer state sharding），Radius 的索引复用策略是否仍然适用是一个值得研究的问题。

3. **对推理侧的启发**：梯度稀疏性的时间稳定性暗示模型参数更新的空间分布具有结构性。这一观察可能对参数高效微调（LoRA 等方法中 rank 和目标层的选择）以及模型剪枝提供新的视角。

4. **可操作的研究方向**：
   - 将 Radius 扩展到 TP/PP 通信压缩（论文作者自己的 future work）
   - 在 7B-70B 规模上验证梯度索引稳定性假设
   - 探索自适应重采样间隔 T——根据梯度分布变化动态调整而非固定值
   - 与梯度量化（如 FP8 通信）正交组合，进一步压缩通信量

---

## 八、总结

Radius 提出了一种基于梯度 top-k 索引时间稳定性的稀疏化通信方法，通过索引复用将 allgather 替换为 allreduce，并通过 gradient correction 解决了 top-k 与 AdamW 的兼容性问题。在 64 A100 GPU 上训练 GPT-2.0B 时实现 19% 端到端加速且不损失下游任务性能。核心局限在于仅验证了较小规模模型和纯 DP 场景，距离真实大模型训练的适用性仍需更多实验支撑。
