# Rubick: Exploiting Job Reconfigurability for Deep Learning Cluster Scheduling

**作者**：Xinyi Zhang (East China Normal University), Hanyu Zhao, Wencong Xiao, Xianyan Jia, Yong Li, Wei Lin (Alibaba Group), Fei Xu (East China Normal University), Fangming Liu (Peng Cheng Laboratory / HUST)

**源文件**：[270339c997293ca2988c62f4308e389f.pdf](../../papers/mlsys-2025/270339c997293ca2988c62f4308e389f.pdf)

---

## 一、背景

大模型训练时代，3D parallelism（DP/TP/PP）与 ZeRO 系列等训练策略的组合为同一个训练任务提供了多种可配置的执行计划（execution plan），每种计划对 GPU、CPU、内存、网络带宽等多维资源的需求截然不同。在多租户共享 GPU 集群中，资源可用性随时间动态变化，但现有集群调度器将训练任务视为黑盒——用户静态选择执行计划，调度器在不了解执行计划的情况下分配资源，导致执行计划与实际可用资源之间的 mismatch，训练性能和集群利用率均远非最优。

---

## 二、要解决的问题

1. **执行计划与资源分配脱节**：用户在提交任务时静态选择执行计划，不了解集群资源的动态变化；调度器分配资源时也不考虑执行计划的具体需求。两者独立决策，无法做到联合优化。
2. **不同执行计划的多维资源需求差异巨大**：例如 ZeRO-Offload 大量使用 CPU 和内存，而 TP 则消耗更多网络带宽。用固定资源请求无法适配不同计划的实际需求。
3. **没有单一"最优"计划**：最优执行计划随可用资源量变化——4 台 8-GPU 服务器上 3D parallelism 最优，但 1 GPU 时只有 ZeRO-Offload 可行。调度器需要理解这种复杂的 model-plan-resource 性能特征。
4. **现有弹性调度仅支持 Data Parallelism 的 scaling**：无法利用训练策略切换（如从 TP 切到 ZeRO-Offload）来适应资源变化。

---

## 三、洞察与设计

**关键洞察**：不同训练策略（3D parallelism、ZeRO-DP、ZeRO-Offload、GC、GA 等）对多维资源（GPU、CPU、内存、带宽）的需求存在本质差异，且同一模型在不同资源约束下的最优执行计划不同。这意味着执行计划本身是一个可调度的维度——通过将执行计划选择纳入集群调度，可以用更少的资源实现相同甚至更好的性能，释放出的资源可服务于其他任务。

基于此洞察，Rubick 的核心设计思路是**将执行计划规划（execution planning）与资源分配（resource allocation）统一为集群调度的联合优化问题**：

1. **Performance Model**：为每种模型类型建立性能模型，用 7 个可拟合参数刻画迭代时间的各组成部分（forward、backward、communication、optimizer、offload）及其重叠关系。模型考虑 GPU 数量、CPU 核数、NVLink/RDMA/PCIe 带宽等多维资源，能够预测任意执行计划和资源组合下的训练吞吐。
2. **Resource Sensitivity Curves**：基于性能模型，为每个任务构建资源敏感度曲线——在每种资源量下选择最优执行计划，并计算对应吞吐。曲线的斜率反映任务从额外资源中获益的程度。
3. **调度策略**：优先分配资源给敏感度最高的任务；可从敏感度最低的任务中 shrink 资源；为 guaranteed 任务找到以更少资源达到同等性能的更优计划（performance guarantee 而非 resource guarantee）。

---

## 四、实现细节

- **框架集成**：基于 Kubernetes + Kubeflow，用 Python 实现调度器。训练框架使用 PyTorch + DeepSpeed 0.9.2 + Megatron-DeepSpeed v2.4。通过修改启动命令的 CLI flags 即可切换执行计划，无需修改模型或框架代码。
- **重配置流程**：调度器指示任务保存 checkpoint → 退出 → 用新执行计划和资源配置重新启动 → 从 checkpoint 恢复。全局 batch size 在重配置前后保持不变，不影响训练收敛。
- **性能模型拟合**：每种模型类型最少需要 7 个 profiling 数据点（不同资源+计划组合下的吞吐测量值）。模型上线后可在线更新：当预测误差超过阈值时，用真实训练 metrics 重新拟合。
- **CPU 绑定**：ZeRO-Offload 下，每个训练进程绑定到分配的 CPU cores，提升参数更新性能。
- **内存分配**：内存不参与 GPU/CPU 的搜索循环，因为额外内存不提升性能；仅在确定执行计划后按需分配。
- **调度算法复杂度**：资源敏感度曲线可预计算并缓存，调度时仅需查表比较斜率，效率较高。

## 五、实验结果

**实验环境**：8 台服务器，每台 8× NVIDIA A800 80GB GPU，96 vCPU，1600GB 内存，400GB/s NVLink，100GB/s RDMA。

**性能模型精度**：

| 模型 | GPU 范围 | 平均误差 | 最大误差 |
|------|----------|----------|----------|
| ViT (86M) | 1-8 | 2.59%–4.23% | 6.19%–8.32% |
| RoBERTa (355M) | 1-8 | 2.21%–7.42% | 4.29%–10.44% |
| BERT (336M) | 1-8 | 3.70%–6.37% | 6.90%–8.62% |
| T5 (1.2B) | 1-32 | 2.41%–6.71% | 6.34%–9.55% |
| GPT-2 (1.5B) | 1-30 | 2.39%–5.52% | 3.08%–8.90% |
| LLaMA-2-7B | 1-64 | 1.90%–4.70% | 2.90%–9.45% |
| LLaMA-30B | 12-64 | 4.29%–6.15% | 8.52%–9.69% |

**端到端集群实验**（406 jobs trace，64 GPU 集群）：

| 调度器 | 平均 JCT | P99 JCT | Makespan |
|--------|----------|---------|----------|
| **Rubick** | **0.96h (1×)** | **7.1h (1×)** | **15.3h (1×)** |
| Sia | 2.5h (2.6×) | 12.2h (1.7×) | 18.8h (1.23×) |
| Synergy | 3.1h (3.23×) | 13.5h (1.9×) | 21.5h (1.4×) |

**消融实验**：仅重配置执行计划（Rubick-E）降低 JCT 1.3×，仅重分配资源（Rubick-R）降低 1.9×，联合优化（完整 Rubick）降低 3.2×。

**大模型比例增加**：随着 trace 中大模型（LLaMA-7B/30B）比例增大，Rubick 相对优势从 2.6× 增长到 3.4×。

**重配置对精度的影响**：重配置引起的 loss 差异始终小于更换随机种子的差异，影响可忽略。

## 六、批判性分析

1. **重配置开销被低估**：论文的重配置通过 checkpoint-restart 实现，但对 checkpoint 保存/加载的时间开销、I/O 带宽占用等未做详细量化分析。对于 30B 级别模型，checkpoint 可能需要数十 GB 写入，重配置频率受限于此开销，但论文未讨论最优重配置频率的权衡。

2. **评估规模偏小**：64 GPU 集群相对于实际生产环境（千卡甚至万卡）偏小。在大规模集群中，调度器的决策空间指数增长，搜索效率和敏感度曲线的缓存/更新是否能 scale 存疑。论文的 trace simulation 也基于同一 64-GPU 配置，缺乏更大规模的验证。

3. **Baseline 比较存在偏差**：Sia 的开源实现仅支持 DP jobs，论文作者自己实现了 Sia 的 3D parallelism scaling 方式（仅 scale DP degree）作为 Rubick-R 的变体。这意味着与 Sia 的比较并非对等的开源系统比较，Sia 在完整实现 3D parallelism 支持后可能表现更好。

4. **性能模型泛化性受限**：7 个可拟合参数的解析模型假设了较为固定的训练流程结构。对于 MoE、sequence parallelism、activation offloading 等更复杂的策略组合，模型是否仍然适用未验证。论文虽提到可扩展，但无实证。

5. **全局 batch size 不变的约束**：重配置时保持全局 batch size 不变虽然保证了收敛等价性，但也限制了优化空间——有些场景下调整 batch size 可能带来更大的吞吐提升。

6. **多租户场景验证不充分**：MT trace 仅设置了两个租户（一个 guaranteed，一个 best-effort），实际生产环境通常有数十个租户、复杂的 quota 层级和公平性约束，论文未探讨更复杂的多租户场景。

---

## 七、AI Infra / MLSys 视角

1. **执行计划作为调度维度的范式启发**：Rubick 的核心贡献在于将训练策略选择从"用户静态配置"提升为"调度器动态优化"。这一范式对 AI Infra 有广泛启发——随着 LLM 训练中策略组合日益复杂（expert parallelism、context parallelism、ring attention 等），将更多的训练配置决策纳入调度器的联合优化空间将越来越重要。

2. **性能建模方法的迁移价值**：7 参数解析模型通过少量 profiling 数据点预测多种策略下的性能，这种轻量级 profiling + 解析建模的方法论可迁移到推理调度场景——例如预测不同 batch size、sequence length、KV cache 策略下的推理延迟。

3. **值得跟进的方向**：
   - **Inference serving 场景的 reconfigurability**：推理服务中 continuous batching、PagedAttention、speculative decoding 等策略同样有多维资源权衡，可否用类似方法做 serving cluster 的联合优化？
   - **大规模集群的 scalable scheduling**：Rubick 的贪心调度在 64 GPU 上有效，但万卡集群需要分层/分区调度设计，如何在保持 reconfigurability 的同时 scale 调度决策？
   - **Heterogeneous GPU 集群**：论文使用同构 A800 集群，但 production 环境常混合 A100/H100/H800，不同硬件下性能模型和重配置策略的适配是一个有价值的延伸方向。

4. **最有价值的切入点**：将 Rubick 的 performance model + resource sensitivity curve 思路应用于 **混合训练/推理工作负载的集群调度**——现实中训练和推理任务共享集群，两者的资源需求模式差异巨大，联合优化空间比纯训练场景更大。

---

## 八、总结

Rubick 首次将训练执行计划规划与集群资源调度统一为联合优化问题，通过轻量级性能模型预测多种策略-资源组合的性能，利用资源敏感度曲线指导动态重配置，在 64-GPU 集群上实现了平均 JCT 降低 3.2× 的显著效果。其核心价值在于揭示了执行计划作为调度维度的潜力，尤其适用于大模型比例高、资源动态变化的共享集群场景。主要局限在于评估规模较小、重配置开销分析不充分、性能模型对新型并行策略的泛化性有待验证。
