# Rubick: A White-Box ML Cluster Scheduler with Job Reconfiguration

## 研究背景与动机

现代 AI 训练集群（ML Cluster）托管着数百甚至数千个并发的训练任务，这些任务来自不同的团队、使用不同的模型架构（CNN、GNN、Transformer）、具有不同的资源需求（GPU 数量、内存大小、网络带宽）。传统的 ML 集群调度器（如 Kubernetes、YARN）主要针对无状态服务设计，**无法有效处理 ML 训练任务的以下特殊需求**：

1. **资源异质性**：ML 训练任务需要 GPU、CPU、内存、网络带宽、存储 IO 等多种资源，资源间存在复杂的依赖关系
2. **生命周期长**：ML 训练任务可能运行数天甚至数周，期间可能遇到 GPU 故障、网络抖动等硬件问题
3. **资源需求动态变化**：训练任务在不同阶段（pre-training、fine-tuning、evaluation）对资源的需求差异很大
4. **优先级和抢占**：紧急任务需要优先调度，低优先级任务可能需要被抢占

现有调度器（如 Kubernetes + Volcano、YARN + GPU Plugin）将 ML 任务视为"黑盒"，只管理 GPU 数量等粗粒度资源，无法深入理解任务内部状态（如数据并行度、模型并行度），导致**资源利用率低下**（典型集群 GPU 利用率 30-50%）。

## 研究问题与核心挑战

Rubick 要解决的核心问题：**如何设计一个"白盒"ML 集群调度器，通过理解并动态调整训练任务的并行化配置（DP/TP/PP/ZeRO/Gradient Checkpointing），在满足作业约束的前提下最大化集群资源利用率**？

具体挑战：
1. **作业配置空间的复杂性**：一个 7B 模型可能有数十种合法的并行化配置，每种配置的资源需求和训练效率都不同
2. **运行时瓶颈识别**：如何实时识别训练作业的瓶颈（GPU 内存不足？通信带宽不足？计算不足？）并做出正确的配置调整？
3. **配置调整的开销**：改变并行化配置意味着需要重新分片模型/数据和重启训练，这本身就有显著开销
4. **多作业联合优化**：整个集群的最优不等于每个作业单独最优之和，需要联合优化

## 主要贡献

1. 提出了 **Rubick**，首个"白盒"ML 集群调度器，能够感知并动态调整训练作业的并行化配置
2. 设计了 **Job Plan Reconfiguration** 机制，允许在作业运行时根据集群状态动态修改 DP/TP/PP/ZeRO 等配置
3. 提出了 **Resource-Performance 联合建模**，将作业的资源配置映射到吞吐量/收敛速度
4. 在华为内部 ML 集群上验证，Rubick 使集群 GPU 利用率从 38% 提升至 67%，平均作业完成时间（JCT）降低 31%

## 核心方法与设计

### 1. 白盒作业建模（White-Box Job Modeling）

Rubick 的核心是**将每个 ML 训练作业建模为白盒**，而非传统调度器的黑盒视角。

```
黑盒视角（传统调度器）:
  Job { id: 123, num_GPU: 8, memory: 64GB }
  → 调度器只知道需要 8 GPU，不知道作业内部结构

白盒视角（Rubick）:
  Job {
    id: 123,
    model: LLaMA-7B,
    data_parallelism: 4,
    tensor_parallelism: 2,
    pipeline_parallelism: 1,
    zero_stage: 2,
    gradient_checkpointing: true,
    current_throughput: 850 samples/s,
    bottleneck: "memory"
  }
  → 调度器理解作业的内部结构和当前瓶颈
```

白盒建模使 Rubick 能够：
- 识别作业的真实瓶颈（是 GPU 内存不足导致 OOM，还是通信带宽不足？）
- 预测不同配置下的性能（如果 TP 从 2 增加到 4，吞吐量会如何变化？）
- 做出有针对性的配置调整决策

### 2. Job Plan Reconfiguration

Rubick 的关键创新是 **Job Plan Reconfiguration**——在作业运行时动态修改其并行化配置。Reconfiguration 包括以下几种类型：

**类型 1：配置缩减（Configuration Shrinking）**
- 场景：当集群资源紧张，无法满足作业的当前配置时
- 动作：自动降低并行度（如 TP 从 4 → 2），释放 GPU 给其他作业
- 副作用：降低的并行度意味着每张 GPU 需要承载更多工作，吞吐量下降

**类型 2：配置扩展（Configuration Expansion）**
- 场景：当集群有空闲资源时
- 动作：提高并行度（如 DP 从 4 → 8），加速作业完成
- 副作用：更高的并行度意味着更大的通信开销和可能的内存压力

**类型 3：配置变形（Configuration Reshaping）**
- 场景：作业遇到 OOM 或通信瓶颈
- 动作：改变并行化策略（如将 TP 转换为 ZeRO，减少模型状态复制）
- 目标：在保持资源总量不变的前提下，消除瓶颈

```
Reconfiguration 决策引擎:
  输入：当前集群状态 + 作业白盒模型 + 配置候选空间
  输出：最优配置调整方案
  方法：基于强化学习（RL）的配置搜索，奖励函数为集群整体 throughput

  State: {可用 GPU 数, 各作业当前配置, 各作业瓶颈类型, 队列状态}
  Action: {对作业 i：将 TP 从 x 改为 y，将 DP 从 a 改为 b}
  Reward: Σ 作业 throughput - λ × 迁移开销
```

### 3. 瓶颈感知调度

Rubick 的调度器内置了一个**瓶颈感知模块**，能够实时识别每个作业的当前瓶颈：

- **Memory-bound**：GPU HBM 利用率 > 90%，计算利用率 < 30%
  → 推荐使用 ZeRO、gradient checkpointing 或降低 TP
- **Communication-bound**：NCCL 通信时间 > 40% 总时间
  → 推荐降低 TP/PP，增加 DP
- **Compute-bound**：计算时间 > 60% 总时间
  → 推荐增加 TP/PP，提高每 GPU batch size

瓶颈识别基于轻量级 profiling：Rubick 在作业运行时周期性采样 GPU 利用率、内存使用、通信时间等指标。

### 4. 多作业联合优化

Rubick 使用 **多作业调度算法**，在集群级别而非作业级别进行优化：

1. **全局资源视图**：Rubick 维护整个集群的资源视图，包括可用 GPU、内存、网络拓扑
2. **配置空间预搜索**：对每个待调度作业，预先生成多个可行的配置方案及其资源需求
3. **装箱优化**：使用约束求解器（基于 OR-Tools）找到满足所有作业约束的资源分配方案

## 实现细节

Rubick 基于 Kubernetes + Volcano 实现，核心组件包括：

**Rubick Scheduler**：修改自 Volcano scheduler，添加了白盒作业建模和配置搜索模块。

**Profiler Agent**：在每个计算节点上运行的轻量级 agent，负责收集 GPU 利用率、内存使用、通信时间等指标。

**Reconfiguration Controller**：管理作业配置的动态修改，支持 Checkpoint-based 迁移（将训练状态保存后用新配置重启）。

**Configuration Search Engine**：基于 RL 的配置优化器，使用 PPO 算法训练策略网络。

## 实验结果

### 华为内部 ML 集群测试

Rubick 在华为内部 256-GPU ML 集群上进行了 30 天的生产测试。

**GPU 利用率**：
| 调度器 | GPU 利用率 | 提升 |
|--------|----------|------|
| Kubernetes 默认调度器 | 32% | baseline |
| Volcano 调度器 | 38% | +6% |
| Rubick | 67% | +35% |

**平均作业完成时间（JCT）**：
| 工作负载 | Kubernetes | Volcano | Rubick |
|----------|-----------|--------|--------|
| Mix (轻量+重量) | 14.2h | 12.8h | 9.8h |
| Heavy (重量级为主) | 22.4h | 19.1h | 13.6h |
| Burst (突发流量) | 28.7h | 24.3h | 16.8h |

**资源效率**：
- Rubick 在相同 GPU 数量下处理的作业数量比 Kubernetes 多 2.1 倍
- 通过配置扩展，Rubick 在空闲资源出现时能够自动加速低优先级作业

### 消融实验

- 白盒建模 vs. 黑盒调度：白盒建模使配置调整决策准确性从 42% 提升至 89%
- 瓶颈感知 vs. 盲目调整：瓶颈感知使无效 reconfiguration 减少 71%
- 联合优化 vs. 独立调度：联合优化使集群 throughput 额外提升 18%

## 潜在问题与局限性

1. **Reconfiguration 开销**：配置调整需要保存 checkpoint 并重启作业，每次 reconfiguration 引入约 2-5 分钟的停机时间，频繁 reconfiguration 可能反而降低效率

2. **RL 训练的不稳定性**：配置搜索使用 RL，但 RL 策略的训练在长时间运行的生产集群上可能不稳定，需要仔细调参

3. **仅支持 NVIDIA GPU**：当前实现依赖 NVIDIA DCGM（Data Center GPU Manager）进行 profiling，对 AMD、昇腾等国产 GPU 的支持缺失

4. **与抢占调度的冲突**：当高优先级作业需要抢占低优先级作业时，reconfiguration 策略可能与抢占策略冲突

## 未来工作

1. 研究无 checkpoint 的在线 reconfiguration（通过迁移训练状态而非重启）
2. 将 Rubick 扩展到推理集群的调度
3. 探索 Rubick 与 model cascading、speculative execution 的联合优化

## 个人评注

Rubick 代表了 ML 集群调度领域的一个重要趋势：**从黑盒调度走向白盒调度**。传统调度器将作业视为"需要 N 个 GPU 的任务"，而 Rubick 试图理解作业的内部结构和瓶颈。这是一个很有野心的目标，也是未来智能调度系统的必经之路。

Job Plan Reconfiguration 是一个创新的设计，但其实际效果取决于 reconfiguration 开销与收益的权衡。在生产环境中，2-5 分钟的停机时间对于长时间运行的训练任务是否可接受，是一个需要仔细评估的问题。

总体而言，Rubick 是华为内部 ML 基础设施实践的结晶，体现了工业界在大规模 AI 集群管理上的深度积累。论文的写作风格偏工程化，对系统设计的细节描述充分，但对算法和理论的分析相对薄弱。
