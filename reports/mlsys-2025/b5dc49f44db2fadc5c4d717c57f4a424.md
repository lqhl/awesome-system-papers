# Optimizing LLM Queries in Relational Data Analytics Workloads

## 一、背景

LLM 正在被广泛集成到数据分析平台中（AWS Redshift、Databricks、Google BigQuery 等），用户可以在 SQL 查询中调用 LLM 对关系型数据的每一行执行分类、实体抽取、摘要、翻译等自然语言任务。然而，LLM 推理代价极高：一块 NVIDIA L4 GPU 运行 Llama3-8B 每秒仅能处理 6KB 文本，处理 15GB 数据需要约一个月；使用 OpenAI GPT-4o 处理同等规模数据需花费约 $18K。因此，优化 batch 数据分析场景下的 LLM 推理成本和延迟具有重大意义。

现有 LLM serving 系统（vLLM、SGLang 等）已支持 prefix KV cache 复用，商业 API（OpenAI、Anthropic、Google Gemini）也推出了 prompt caching 服务，对缓存命中的 prompt 提供 2-10× 折扣。然而，直接将关系型数据按默认顺序发送给 LLM，cache 命中率往往很低。

---

## 二、要解决的问题

1. **默认行列顺序导致低 cache 命中率**：关系型表的默认字段顺序和行顺序未针对 prefix sharing 优化。例如第一个字段包含唯一值（如 review content）时，所有后续字段的共享前缀被完全阻断，PHC（Prefix Hit Count）为 0。
2. **固定字段顺序的局限性**：对所有行使用统一的字段排列顺序，最多可比最优 per-row 排列差 m 倍（m 为字段数），因为不同行的最佳字段优先级不同。
3. **最优重排序的计算复杂度**：对 n 行 m 字段的表，潜在排列方式为 n! × (m!)^n，搜索空间呈指数级增长，暴力搜索不可行。

---

## 三、洞察与设计

**关键洞察**：在 batch 数据分析工作负载中，完整的表结构和内容在推理前已知（offline/batch 场景），因此可以利用关系型数据中固有的重复模式（如 foreign key join 产生的重复值、热门商品的重复描述、RAG 中重复的 context），通过对请求的行顺序和每行内部的字段顺序进行智能重排，最大化 KV cache 的 prefix 复用。

基于此洞察，论文提出两层重排策略：

1. **OPHR（Optimal Prefix Hit Recursion）**：最优递归算法。对每个字段的每个 distinct value，将表拆分为两个子表（包含该值的行去掉该字段 + 不包含该值的行保留全部字段），递归求解最优 PHC。该算法可证明最优，但复杂度为指数级。

2. **GGR（Greedy Group Recursion）**：贪心近似算法。每步选择贡献最大 HITCOUNT 的 (field, value) 对进行递归拆分，而非穷举所有组合。递归深度为 O(min(n, m))。两项关键加速：
   - **Functional Dependencies（FD）**：利用数据库 schema 中的函数依赖关系（如主键 → 外键），当某字段被选入 prefix 时，其函数决定的所有字段自动紧随其后排列，减少搜索空间。
   - **Table Statistics**：利用字段的 cardinality 和 value 长度分布进行早停判断，避免全表扫描。当递归达到指定深度或 HITCOUNT 低于阈值时，退回使用统计信息确定固定字段排序。

## 四、实现细节

- 约 1.3K 行 Python 代码实现，集成到 Apache Spark（PySpark）中。
- LLM 调用封装为 PySpark UDF，接受 system prompt、query prompt 和一行数据作为输入。
- 使用 JSON 格式编码每行的字段名-值对，以便 LLM 解析。
- GGR 的 HITCOUNT 函数计算公式：`tot_len = len(v)^2 + Σ_{c' ∈ inferred_cols} Σ_{r ∈ R_v} len(T[r,c']) / |R_v|`，乘以 `(|R_v| - 1)` 得到总贡献，其中平方项反映 Transformer 注意力的二次复杂度。
- 行/列递归深度可配置（实验中行递归深度 4、列递归深度 2），早停阈值设为 0.1M hit count。
- GGR 内存开销 O(n × m)，每步递归缩小表规模。
- 后端 LLM serving 使用 vLLM，自动利用 RadixAttention 进行 prefix cache 复用。

## 五、实验结果

**硬件**：单 NVIDIA L4 GPU（24GB，GCP g2-standard-4）用于 Llama-3-8B；8×L4（GCP g2-standard-48）用于 Llama-3-70B。

**数据集与查询**：7 个数据集（Movies、Products、BIRD、PDMX、Beer、SQuAD、FEVER），16 个查询覆盖 5 种类型（Filter、Projection、Multi-LLM、Aggregation、RAG）。

| 指标 | 结果 |
|------|------|
| 端到端延迟加速（vs No Cache） | 1.8× – 3.8× |
| 端到端延迟加速（vs Cache Original） | 1.5× – 3.4× |
| Prefix Hit Rate 提升 | 从 10-50% 提升至 57-86%（+30-75%） |
| OpenAI API 成本节省 | 20% – 39% |
| Anthropic API 成本节省 | 最高 79% |
| 实际 API 实验（FEVER，GPT-4o-mini） | 32% 成本节省（$0.81 → $0.55） |
| 实际 API 实验（FEVER，Claude 3.5 Sonnet） | 21% 成本节省（$5.49 → $4.33） |
| GGR 求解时间 | 所有数据集 < 15 秒（< 0.01% 查询时间） |
| 准确率影响 | 大多数情况 ±5% 以内，大模型更鲁棒 |
| GGR vs OPHR PHR 差距 | < 2%（在可运行的小规模子集上） |

Llama-3-70B 上 Filter 查询的加速为 1.9× – 3.3×，趋势与 8B 一致。Llama-3.2-1B 上 PHR 提升类似，但由于小模型占用 GPU 内存少、batch size 已较大，prefix caching 的相对收益较小。

## 六、批判性分析

1. **加速倍数高度依赖数据特征**：不同数据集的加速差异很大（1.5× 到 3.4×），PDMX 等字段多且值唯一的数据集加速仅 1.8×。论文在 abstract 中突出 "up to 3.4×" 的表述有选择性报告 best case 的倾向。

2. **实际 API 实验规模过小**：OpenAI/Anthropic 的真实 API 实验仅用了 FEVER 数据集的 1000 行，且为满足 1024 token 的最低缓存要求，对每个字段值做了 5 倍重复——这是一种人为构造的设定，与真实数据分布可能有较大偏差。

3. **假设条件的局限性**：
   - 假设完全 exact match 的 cell 匹配，不支持子串匹配。虽然在关系型数据中合理，但 RAG 场景中 context 的微小差异（如不同 chunk 策略）会大幅降低效果。
   - 假设 offline batch 场景，所有请求预先已知。对 online/streaming 查询不适用。

4. **准确率评估不够全面**：仅在 Filter 查询（输出短、约束强）上评估准确率，未评估 Projection 和 RAG 等长输出查询的质量变化。字段重排对长文本生成任务的影响可能更显著。

5. **Functional Dependencies 的可用性**：论文假设 FD 信息"readily available"，但实际中很多分析工作负载使用 DataFrame/CSV 而非正式数据库，FD 需要额外推断。论文未讨论 FD 缺失或不完整时 GGR 的退化程度。

6. **与 serving 系统的耦合度**：虽然论文强调方法可"easily applied"，但实际需要修改分析引擎的查询计划（在 Spark UDF 前插入重排逻辑），且依赖 serving 后端支持 prefix caching（如 vLLM 的 RadixAttention），并非完全透明。

## 七、AI Infra / MLSys 视角

1. **Workload-aware scheduling 的启发**：本文的核心思路——利用 batch 工作负载的全局信息优化 KV cache 复用——可以推广到更多 AI Infra 场景。例如在大规模 embedding 计算、batch evaluation、数据标注等场景中，对输入请求的排序优化都可能带来显著收益。

2. **与 prefix-aware serving 的协同设计**：论文在 client 端（分析引擎）做重排，serving 端（vLLM）做 prefix caching，两者解耦。一个有价值的研究方向是让 serving 系统主动感知 batch workload 的结构化特征（如关系型 schema），在 serving 端做更智能的调度。

3. **可迁移到 RAG 系统优化**：在 RAG pipeline 中，多个 query 可能检索到相同的 context chunk。利用类似的重排策略，按共享 context 的频率对请求排序，可以最大化 prefix cache 复用。这对大规模 RAG 服务（如企业知识库问答）尤其有价值。

4. **值得跟进的方向**：
   - **Online/streaming 场景的近似重排**：如何在请求持续到达时，用滑动窗口或 micro-batch 策略近似实现 prefix-aware 调度？
   - **多租户 serving 中的跨用户 prefix sharing**：不同用户的 batch 查询可能共享系统 prompt 或相似数据，如何跨租户优化？
   - **与 disaggregated prefill-decode 架构的结合**：在 prefill-decode 分离的架构中，prefix 重排可以进一步减少 prefill 阶段的计算量和 KV cache 传输开销。

---

## 八、总结

本文针对关系型数据分析中的 batch LLM 调用场景，提出通过对输入表的行顺序和每行内字段顺序进行智能重排来最大化 KV cache prefix 复用的方法。核心算法 GGR 利用贪心递归、函数依赖和表统计信息，在 < 15 秒内完成求解，实现 1.5-3.4× 的端到端延迟加速和最高 32% 的 API 成本节省，且对模型准确率影响在 ±5% 以内。方法适用于 offline batch 分析场景，对字段值重复率高的数据集效果最佳，但对 online 查询和高基数数据的适用性有限。
