## 一、背景

机器学习（ML）框架如 PyTorch、TensorFlow 是 ML 系统的核心基础设施，提供模型训练和推理的关键库和工具。这些框架使用 C++ 和 CUDA 实现核心功能并编译为共享库（shared libraries），Python 作为前端封装。随着模型规模和复杂度的增长，ML 系统积累了大量技术债务，其中软件膨胀（software bloat）是一个重要来源。

软件膨胀指运行时不需要的代码和功能，分为两类：Type I 是普遍无用的代码（如死代码）；Type II 是依赖具体使用场景的冗余代码。共享库占 ML 框架总大小的 75%-93%，例如 PyTorch 的 GPU 版 `torch.so` 为 881MB，CPU 版仅 482MB。现有的去膨胀（debloating）研究仅关注传统软件中 CPU 侧的代码，完全忽略了 ML 框架中占主导地位的 GPU 代码。

---

## 二、要解决的问题

1. **GPU 代码膨胀被忽视**：ML 共享库中 GPU 代码占比 68%-91%，但现有去膨胀工具和研究均未涉及 GPU 代码分析与去膨胀。
2. **GPU 代码结构不公开**：GPU 代码（`.nv_fatbin` section）缺乏公开规范，难以分析和定位内部的 kernel 代码。
3. **专有库无法源码分析**：cuDNN、cuBLAS 等关键库闭源，无法进行源码级去膨胀。
4. **现有 profiling 工具开销大**：NSys 等工具设计用于性能调试而非 kernel 检测，每次 kernel 调用都记录数据，引入高达 126% 的性能开销。
5. **膨胀导致资源浪费**：多余代码增加存储开销、CPU/GPU 内存占用和执行时间，尤其影响资源受限环境和冷启动敏感场景（如 serverless ML）。

---

## 三、洞察与设计

**关键洞察**：所有 GPU kernel 的启动都必须先经过 CPU 侧的 `cuModuleGetFunction` 调用，且该函数对每个 kernel 只调用一次（后续执行复用 function handle）；同时，被同一 CPU-launching kernel 调用的所有 GPU-launching kernel 会被编译进同一个 cubin 文件中。因此，通过监控 CPU 侧这个单一函数就能以极低开销检测所有使用的 kernel，再通过 cubin 粒度的保留策略就能安全地保留整个 kernel call graph。

基于此洞察，作者设计了 **Negativa-ML**，包含两个核心组件：

1. **Kernel Detector**：利用 NVIDIA CUPTI API hook `cuModuleGetFunction`，记录被调用的 kernel 名称。只拦截 CPU-launching kernel（每个 kernel 仅一次），不拦截 GPU-launching kernel，因此开销远低于 NSys。

2. **Kernel Locator**：定位已使用 kernel 在共享库中的文件范围。
   - 使用 `cuobjdump` 从共享库中提取 cubin 文件列表及其包含的 kernel。
   - 如果一个 cubin 包含已使用的 CPU-launching kernel，则保留整个 cubin（及其对应的 element）。
   - 利用 element header 中的 compute-capability 字段过滤不匹配当前 GPU 架构的 element。
   - 将需要保留的文件范围传递给 Negativa 的 compaction 模块，将未使用部分清零并维护内存地址映射。

---

## 四、实现细节

- **GPU 代码结构**：共享库中 GPU 代码组织为 regions → elements → cubins 的层次结构。每个 element 包含一个 element header（含 compute-capability 字段）和一个 cubin。cuobjdump 提取的 cubin 文件名中的索引对应共享库中 element 的索引。
- **保留策略**：element 被保留当且仅当：(1) 其 compute-capability 匹配运行 workload 的 GPU 架构；(2) 其 cubin 包含至少一个被 kernel detector 检测到的 CPU-launching kernel。
- **Compaction 阶段**：复用已有工具 Negativa 的 compaction 模块，将未使用代码清零，并将文件偏移映射回原始内存地址以保证共享库加载时的正确性。
- **CPU 代码去膨胀**：同样复用 Negativa 的三阶段流程（detection → location → compaction），对 CPU 侧函数进行去膨胀。

## 五、实验结果

**实验平台**：AWS 实例（16 CPU, 64GB RAM, NVIDIA T4 GPU）；额外使用 1×H100 和 8×A100 40GB 进行补充实验。

**评估框架与 workload**：4 个 ML 框架（PyTorch 2.3.1, TensorFlow 2.16.2, vLLM 0.6.3, Transformers 4.42.3），3 个模型（MobileNetV2 4.3M, Transformer 65M, Llama-2-7b 7B），共 10 个 workload。

### 文件大小与代码缩减

| 指标 | 缩减范围 |
|------|---------|
| 总文件大小 | 40%-55% |
| CPU 代码大小 | 46%-72% |
| CPU 函数数量 | 65%-93% |
| GPU 代码大小 | 66%-75% |
| GPU element 数量 | 88%-99% |

### 运行时性能改善

| 指标 | 最佳缩减 | 平均绝对缩减 |
|------|---------|-------------|
| Peak CPU Memory | 74.6% | 2501 MB |
| Peak GPU Memory | 69.6% | 443 MB |
| Execution Time | 44.6% | 2.6 s |

### 关键发现

- **GPU 代码是膨胀主要来源**：GPU element 缩减超过 97%，远高于 CPU 代码。
- **Pareto 分布**：10% 的共享库贡献了 90% 以上的总大小缩减。
- **架构不匹配是主因**：超过 80% 被移除的 element 因不匹配目标 GPU 架构（单个 PyTorch 共享库包含 6 种 GPU 架构的代码）。
- **不同模型/workload 使用大量共同函数**：torch_cuda.so 中函数的 Jaccard 相似度 > 0.7，但 kernel 相似度很低（< 0.5）。
- **Kernel Detector 开销**：41%（vs NSys 的 126%），且为一次性预处理开销。
- **跨 GPU/分布式场景有效**：H100 和 8×A100 分布式推理场景下同样有效。

## 六、批判性分析

1. **Workload 代表性不足**：只用 3 个模型、10 个 workload 评估，且未训练到收敛。作者声称"训练主要是重复迭代，几个 epoch 足以获得代表性结果"，但不同训练阶段（如 warmup、learning rate scheduling、gradient accumulation 变化）可能触发不同的 kernel path。

2. **Type II bloat 的固有局限被轻描淡写**：去膨胀后的库是 workload-specific 的——换一个模型或改变 batch size 可能就需要重新去膨胀。论文未充分讨论这一部署复杂性，也未评估不同 workload 之间去膨胀结果的可复用性。

3. **运行时改善的因果关系不清晰**：峰值内存和执行时间的改善被归因于去膨胀，但论文未分离各因素的贡献。例如，CPU 内存下降可能主要来自共享库文件大小缩减（mmap），而非代码层面的优化。执行时间改善（绝对值约 2.6s）主要来自加载时间缩减，对长时间训练任务几乎无感知。

4. **GPU 代码膨胀的 80%+ 源于架构不匹配**：这本质上是一个打包策略问题（fat binary 包含多架构代码），而非"隐藏的膨胀"。NVIDIA 已提供 `--gencode` 编译选项来指定目标架构。将此归为"软件膨胀的新来源：源自硬件"有些言过其实。

5. **cubin 粒度保留的精度损失未量化**：论文选择以整个 element/cubin 为粒度保留代码（而非精确的 kernel 级别），这必然引入 false retention。论文未量化这一保守策略导致了多少额外保留。

6. **安全性和正确性验证不充分**：论文仅声称"输出和最终指标没有差异"，但未给出系统性的 correctness 测试（如全量 test suite），也未讨论边界情况（如 dynamic kernel dispatch、JIT compiled kernel）。

7. **缺乏与替代方案的对比**：例如直接使用 `--gencode` 编译特定架构的 PyTorch、或使用 container 级别的去膨胀工具，论文未对比这些更简单的替代方案。

---

## 七、AI Infra / MLSys 视角

1. **对部署优化的启发**：揭示了 ML 框架共享库中大量冗余代码的存在，尤其是 GPU 代码因 fat binary 多架构支持而膨胀严重。对于 serverless ML、edge deployment、容器化部署等场景，去膨胀可以显著减小镜像大小和冷启动时间。

2. **"Used bloat" 概念值得深入研究**：论文在 Discussion 中提出 TensorFlow 中存在"used bloat"——被执行但无实际贡献的代码（如优化器初始化的冗余函数调用）。这是一个有意思的方向，可以结合 profiling 和 causal analysis 来识别。

3. **可迁移到推理引擎定制化**：vLLM、TensorRT-LLM 等推理引擎也面临类似问题。针对特定模型架构（如 decoder-only transformer）的推理引擎，可以预先去膨胀不相关的算子支持，减小部署包大小。

4. **值得跟进的方向**：
   - **Kernel 级别精细去膨胀**：突破 cubin 粒度限制，实现 kernel 级别的 GPU 代码裁剪。
   - **跨 workload 共享去膨胀**：分析多个 workload 的 kernel 使用集合，生成支持一组 workload 的最小共享库。
   - **与框架编译流程集成**：将去膨胀作为 PyTorch/TensorFlow 的编译选项或部署工具链的一环，而非事后处理。
   - **动态 kernel 场景的处理**：PyTorch 2.0 的 `torch.compile` 和 Triton JIT 编译产生的动态 kernel 如何与去膨胀兼容。

---

## 八、总结

本文提出 Negativa-ML，通过 hook CPU 侧 `cuModuleGetFunction` 检测使用的 GPU kernel，并以 cubin/element 粒度定位和去除未使用的 GPU 代码，扩展至 ML 框架共享库的全面去膨胀。在 4 个框架、10 个 workload、300+ 共享库上的评估显示，ML 框架高度膨胀（GPU 代码缩减最高 75%，CPU 代码缩减最高 72%），去膨胀后峰值内存和执行时间分别降低最高 74.6% 和 44.6%。但膨胀的主因是 fat binary 多架构打包，去膨胀后的库是 workload-specific 的，实际部署价值需结合具体场景评估。
