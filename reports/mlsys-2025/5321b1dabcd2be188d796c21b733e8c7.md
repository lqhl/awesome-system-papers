## 1. 研究背景与动机

软件膨胀（Software Bloat）指的是代码和功能在运行时未被使用却仍然存在于软件中的现象。对于机器学习系统而言，膨胀是技术债务的重要来源——它不仅浪费存储和内存资源，还可能导致启动时间延长、安全漏洞增加和运行时性能下降。

ML 框架（TensorFlow、PyTorch）是 ML 生态系统的核心，其核心功能以共享库（shared libraries）的形式打包，包含大量 CPU 代码和 GPU 代码（占 torch.so 的 68%-91%）。现有软件去膨胀研究仅关注 CPU 代码，完全忽略了 GPU 代码——这在 ML 系统中的占比往往更大。此外，cuDNN、cuBLAS 等专有库无法进行源代码级分析，进一步增加了 GPU 代码去膨胀的难度。

## 2. 研究问题与核心挑战

核心问题：如何在无法访问 GPU 代码结构规范的情况下，识别并消除 ML 框架共享库中的 GPU 代码和 CPU 代码膨胀？

主要挑战：

1. **GPU 代码结构的黑盒特性**：GPU 代码在共享库中的组织方式缺乏公开规范（仅有 .nv_fatbin section），无法直接定位单个 kernel 的文件偏移范围。

2. **cuDNN/cuBLAS 专有库**：这些关键库是闭源的，无法进行源代码分析。

3. **CPU 和 GPU 代码的联合去膨胀**：ML 框架同时包含两类代码，需要统一处理。

4. **正确性保证**：去膨胀不能影响 ML 工作负载的计算结果。

## 3. 主要贡献

1. **Negativa-ML 工具**：首个同时对 ML 框架共享库中 CPU 代码和 GPU 代码进行去膨胀的工具，基于作者此前的 CPU 去膨胀工具 Negativa 构建。

2. **GPU Kernel 检测**：提出利用 CUPTI API hook `cuModuleGetFunction` 的方法，以极低开销检测 ML 工作负载使用的 GPU kernel。

3. **GPU Kernel 定位**：提出利用 cuobjdump 分析 .nv_fatbin 结构，通过 cubin 索引映射到共享库中精确元素（Element）的方法。

4. **全面的膨胀分析**：对 4 个主流 ML 框架（PyTorch、TensorFlow、vLLM、Transformers）、10 个工作负载、300+ 共享库进行了系统性分析。

## 4. 核心方法与设计

### 4.1 GPU Kernel 检测器（Kernel Detector）

关键洞察：`cuModuleGetFunction` 在每次加载 kernel 时被调用，且每个 kernel 仅调用一次。因此 hook 该函数即可检测所有被使用的 CPU-launching kernel。

实现方式：使用 Nvidia CUPTI API 在运行时拦截 `cuModuleGetFunction`，记录传入的 kernel 名称。被记录的 kernel 即视为"被使用"。

### 4.2 GPU Kernel 定位器（Kernel Locator）

关键观察：
- 如果一个 kernel 由另一个 kernel 启动（GPU-launching kernel），两者会被编译到同一个 cubin 中
- 因此只要保留包含 CPU-launching kernel 的 cubin，对应的 GPU-launching kernel 也会被保留

定位步骤：
1. 使用 cuobjdump 从共享库提取所有 cubin 及其中包含的 kernel 名称
2. 将 kernel 名称与检测到的 used kernel 列表匹配
3. 确定 cubin 在 .nv_fatbin 中的索引，映射到对应的 Element
4. 根据 Element header 中的 compute-capability 字段确定是否需要保留（是否匹配运行环境的 GPU 架构）

### 4.3 压缩（Compaction）

保留符合条件（匹配 GPU 架构 + 包含 used kernel）的 Element，将其他 Element 从共享库中移除。保留内存地址有效性。

### 4.4 膨胀分类

- **Reason I**：Element 不匹配 GPU 架构（如编译了 Volta/Turing/Ampere 三种架构，但只运行在 Ampere 上）
- **Reason II**：Element 匹配架构，但不包含任何被使用的 kernel

## 5. 实验结果

### 5.1 膨胀规模

**关键发现**：ML 框架极度膨胀：
- GPU 代码减少高达 75%，CPU 代码减少高达 72%
- 总文件大小减少高达 55%
- 10% 的共享库贡献了 90% 的总膨胀（Power Law 分布）

**各框架对比**：

| 框架 | 操作 | 总文件大小减少 | CPU 代码减少 | GPU 代码减少 |
|------|------|--------------|------------|------------|
| PyTorch | MobileNetV2 训练 | 55% | 68% | 75% |
| PyTorch | MobileNetV2 推理 | 55% | 70% | 75% |
| TensorFlow | MobileNetV2 训练 | 48% | 46% | 73% |
| vLLM | Llama2 推理 | 48% | 68% | 72% |
| Transformers | Llama2 推理 | 53% | 72% | 71% |

### 5.2 运行时性能改善

| 指标 | 最佳减少 |
|------|--------|
| 峰值 CPU 内存 | 74.6% |
| 峰值 GPU 内存 | 69.6% |
| 执行时间 | 44.6% |

注意：改善幅度因工作负载类型差异较大，训练类工作负载受益更多。

### 5.3 GPU 膨胀的根本原因

超过 80% 的被移除 Element 属于 Reason I——即编译了针对不同 GPU 架构的代码。这意味着软件膨胀不仅来自功能代码，还来自硬件支持代码。

## 6. 潜在问题与局限性

1. **跨版本迁移性**：去膨胀后的共享库能否在不同版本或配置的 PyTorch/TensorFlow 中正常工作，需要进一步验证。

2. **动态加载的 kernel**：如果某些 kernel 在训练初期不常用但在特定阶段才被触发（如训练中途的优化操作），当前的检测方法可能遗漏这些 kernel。

3. **与框架更新的兼容性**：去膨胀后的共享库在更新 PyTorch/TensorFlow 版本后可能失效，需要重新去膨胀。

4. **cuDNN/cuBLAS 等专有库**：这些关键库中的 GPU 代码膨胀无法处理（因为是闭源二进制），论文仅分析但无法去膨胀。

5. **正确性验证**：论文提到验证了输出一致性，但未详细说明测试覆盖的边界情况（如数值精度变化）。

## 7. 未来工作

1. 扩展到更多 ML 框架（JAX、MXNet 等）
2. 自动化 kernel 检测和定位的优化
3. 探索编译时去膨胀的可能性（而非运行时分析）

## 8. 个人评注

Negativa-ML 是一篇非常"接地气"的 MLSys 论文——它关注的是 ML 工程师每天都会遇到但很少系统性研究的问题（ML 框架的体积臃肿）。论文的亮点在于发现了一个之前完全被忽视的问题域（GPU 代码膨胀）并提出了可行的解决方案。

从技术角度看，GPU Kernel 检测利用 `cuModuleGetFunction` 的策略非常巧妙——开销低、精度高。Kernel 定位通过 cuobjdump + cubin 索引映射的方法虽然依赖 CUDA 工具链，但具有足够的工程可操作性。

最发人深省的发现是超过 80% 的 GPU 膨胀来自不同 GPU 架构的支持代码——这揭示了软件膨胀与硬件多样性的深层联系。随着边缘 AI 芯片的多元化（NVIDIA GPU + Apple Neural Engine + Google TPU + 各类 ASIC），这一问题可能会更加严重。

不足之处在于实验场景的规模——主要在小模型（MobileNetV2、Transformer-65M）和单卡设置下验证，对大规模 LLM 训练场景的覆盖有限。总体而言，这是一篇问题驱动、解决方案清晰、具有实用价值的论文。
