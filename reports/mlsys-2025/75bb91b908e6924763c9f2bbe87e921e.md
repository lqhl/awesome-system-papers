# Supply-Chain Attacks in Machine Learning Frameworks

**作者**：Yue Gao (University of Wisconsin–Madison), Ilia Shumailov (Google DeepMind), Kassem Fawaz (University of Wisconsin–Madison)
**会议**：MLSys 2025
**链接**：Proceedings of the 8th MLSys Conference, Santa Clara, CA, USA, 2025
**源文件**：[[75bb91b908e6924763c9f2bbe87e921e.pdf]]

---

## 一、背景

机器学习（ML）系统日益依赖开源软件（OSS）生态，框架如 PyTorch、TensorFlow、Transformers 等通过 PyPI/conda 分发，形成了深层依赖链。传统供应链攻击（如 PyTorch 2022 年的 torchtriton 事件、HuggingFace 的 AI-Jacking 漏洞）已证明这些生态的脆弱性。然而，现有安全研究主要关注传统软件供应链（恶意系统调用、数据泄露）或 ML 算法层面的对抗攻击（数据投毒、后门），两者割裂而未考虑交叉风险。与此同时，ML 包的依赖数量远超传统软件——HuggingFace Transformers 有 305 个直接和传递依赖，是 requests 库的 20 倍以上，攻击面显著更大。

---

## 二、要解决的问题

1. **传统供应链防御对 ML 特有威胁失效**：现有检测工具主要监控敏感系统调用和异常网络流量，但 ML 模型本身的鲁棒性、隐私性可以通过不触发这些传统警报的方式被攻击。
2. **Python 运行时缺乏内存隔离**：Python 中所有包共享同一内存空间和执行栈，上游依赖可以覆写下游应用的全局变量和局部变量，且无语言级隔离机制。
3. **ML 社区安全意识不明**：尚不清楚 ML 开源社区的供应链安全意识是否足以应对其面临的更高风险。

---

## 三、洞察与设计

**关键洞察**：Python 的 import 机制使得任何被导入的包（包括传递依赖）都能访问和修改下游应用的全局对象和函数栈中的局部变量，这种"同等信任"的内存共享模型可以被利用来实施针对 ML 模型的隐蔽攻击——不触发任何传统安全告警（无敏感系统调用、无异常网络流量），却能破坏模型的完整性和安全性。

基于此洞察，论文提出了一类新的 ML 特定供应链攻击范式，分为两大方向：

### 变量覆写机制
- **全局变量覆写**：上游依赖通过 `import torch; torch.pi = 3.0` 直接修改框架全局对象，利用 Python 的模块缓存机制确保修改持久生效，甚至可通过 C-extension 隐藏覆写代码。
- **局部变量覆写**：通过 `inspect` 模块访问调用栈帧（`currentframe().f_back`），修改下游函数的局部变量；对于不可变类型，使用未文档化的 `PyFrame_LocalsToFast` API 强制更新。

### 攻击应用
- **后门注入**：覆写模型的 forward 函数，在输入包含特定 trigger 时返回攻击者指定输出；对 LLM 覆写 tokenizer 注入 jailbreak prompt。
- **管道漏洞注入**：将安全的 area interpolation 枚举值替换为不安全的 nearest neighbor，使图像缩放攻击成为可能。
- **模型窃取**：在 forward 函数中通过栈帧导航获取模型权重，利用隐写术编码到输出中。
- **防御绕过**：覆写 softmax 函数增大 top-1 类的 margin 以绕过模型窃取检测；拦截 HTTP/gRPC 请求绕过 jailbreak 验证服务。

## 四、实现细节

**攻击实现要点**：
- 全局变量覆写封装在 `try-except ImportError` 中，确保目标框架未安装时静默跳过
- 局部变量覆写使用 `ctypes.pythonapi.PyFrame_LocalsToFast` 处理不可变类型
- C-extension 版本通过 `PyEval_GetFrame()` + `PyFrame_GetBack()` + `PyFrame_GetLocals()` 实现相同功能且不暴露 Python 源码
- 所有攻击代码可放在依赖包的 `__init__.py` 中，导入即触发

**安全意识分析实现**：
- 数据集：GitHub Top-50 ML 项目的 549,635 个 Issues/PRs + Top-50 Linux 项目的 302,033 个 Issues/PRs
- 两阶段 LLM 辅助过滤：GPT-3.5 粗筛（偏向高召回）→ GPT-4 精筛（识别具体安全措施类别）
- 映射到 Ladisa et al. (2023) 的供应链安全措施分类体系（20 类防护措施）
- 人工验证：两名安全研究员标注 200 个样本，Cohen's kappa = 0.85，LLM 方法召回率 97.8%，精确率 78.9%

## 五、实验结果

### ML 依赖数量对比

ML 包的 PyPI 依赖数量显著高于 Linux 项目维护的包，部分 ML 包超过 300 个依赖，而 Linux 项目均不超过 150 个。

### 安全意识分析

| 指标 | ML 社区 | Non-ML（Linux）社区 |
|------|---------|-------------------|
| 安全相关 IS/PRs 占比范围 | 0.87%–13.98% | 0.32%–12.79% |
| 分布特征 | 相似——多数项目集中在低百分比区间 | 相似 |

**关键发现**：
- 基础 ML 框架（PyTorch 1.40%、TensorFlow 1.83%、Keras 0.87%）安全讨论占比显著低于上层应用（pytorch-lightning 4.31%、streamlit 4.45%）
- 最常讨论的安全措施是 version pinning（21 个项目）、typo detection（19）、dependency resolution（18），但多为功能驱动而非安全动机
- 最有效的安全措施（代码隔离、审查流程、防抢注）讨论最少
- ML 和非 ML 社区安全意识分布高度相似，但 ML 社区面临更大的攻击面
- PyTorch 安全 PR 接受率仅 64.20%，存在维护者对安全 PR 的推回现象（如拒绝移除 fsspec、networkx 依赖的 PR）

## 六、批判性分析

1. **攻击实用性存疑**：所有攻击均为 PoC 级别，未在真实 ML 服务或生产环境中验证。实际攻击需要攻击者能向依赖包提交恶意代码并通过 code review——论文未讨论这一关键前提的可行性。现代大型项目（如 PyTorch）的 PR review 流程是否真的无法发现 `inspect.currentframe().f_back` 或 `torch.pi = 3.0` 这类代码？
2. **安全意识代理指标粗糙**：用 Issues/PRs 中讨论安全话题的百分比作为"安全意识"的代理变量存在明显问题——安全工作可能通过私有渠道（security advisories、内部审计）进行，不反映在公开讨论中。论文自身也承认了这一局限但未充分处理。
3. **GPT 标注的精确率仅 78.9%**：这意味着约 21% 的被标记为安全相关的讨论实际上并不相关，对定量结论的可靠性构成影响，尤其是在安全讨论占比本身就很低（1-5%）的情况下。
4. **ML vs Non-ML 对比不公平**：选择 Linux 项目作为非 ML 基准不太合理——Linux 项目多为系统级软件（C/C++/Go），与 Python ML 项目在语言生态、开发文化、依赖管理方式上差异巨大，难以得出有意义的对比结论。
5. **防御讨论薄弱**：论文提出的防御建议（静态分析检查跨包变量覆写）缺乏具体设计和评估，"迁移到编译语言"的建议在 ML 生态中短期内不现实。
6. **攻击模型假设隐含矛盾**：假设 ML 服务已部署传统安全防御和 ML 对抗防御，但同时假设攻击者可以通过依赖链注入代码——如果防御方已经做到了传统安全监控，为何不对依赖包的导入行为做基本审查？

---

## 七、AI Infra / MLSys 视角

1. **依赖链信任问题值得关注**：对于生产级 AI 推理服务（如基于 vLLM、TGI 的部署），依赖链中的隐蔽攻击确实是真实威胁。论文揭示的 Python 内存共享问题为 AI Infra 的安全加固提供了具体方向——例如在推理框架中对关键函数（softmax、forward、tokenizer）做运行时完整性校验。

2. **启发性的攻击面分析方法**：将 ML 特有漏洞（对抗样本、模型窃取）与传统供应链漏洞结合分析的思路，对 AI Infra 安全团队有参考价值。可以系统性地梳理推理/训练框架中哪些变量、函数如果被覆写会导致 ML 层面的安全问题。

3. **值得跟进的方向**：
   - 为 ML 框架设计轻量级的运行时 integrity monitor，在关键路径（模型加载、推理、tokenization）做变量完整性检查
   - 研究 Python 包级别的内存隔离机制（如基于 subinterpreter 的沙箱），在不牺牲性能的前提下限制依赖包的访问权限
   - 建立 ML 框架的供应链安全审计工具，自动检测跨包全局变量修改和栈帧操作

4. **最有价值的切入点**：针对主流推理框架（vLLM、TensorRT-LLM 等）做供应链攻击面评估，量化其依赖链中的真实风险，并设计实用的检测/防御工具。

---

## 八、总结

本文提出了一类利用 Python 运行时内存共享特性的 ML 特定供应链攻击，通过覆写下游 ML 框架的全局/局部变量实现后门注入、管道篡改、模型窃取和防御绕过，且不触发传统安全检测。同时通过 LLM 辅助分析 GitHub Top-50 ML 项目的安全讨论，发现 ML 社区的供应链安全意识与非 ML 社区相当，未达到其更高风险所要求的标准。论文的主要贡献在于揭示了 ML 供应链的独特攻击面和社区安全意识的不足，但攻击均停留在 PoC 阶段，防御方案也缺乏具体实现和评估。
