# SparseTransX: Efficient Training of Translation-Based Knowledge Graph Embeddings Using Sparse Matrix Operations

**会议**：MLSys 2025
**链接**：https://github.com/HipGraph/SpTransX

## 一、背景

知识图谱（Knowledge Graph, KG）是以有向图形式存储实体与关系的结构化数据，广泛用于链接预测、实体分类等下游任务。知识图谱嵌入（KGE）将实体和关系映射到连续向量空间，其中基于翻译的模型（TransE、TransR、TransH、TorusE 等）因结构简单、效果好而被广泛使用。

然而，训练大规模知识图谱嵌入计算开销大、内存需求高。现有框架（TorchKGE、DGL-KE、PyG）依赖 PyTorch 的 embedding 模块，通过细粒度的 scatter/gather 操作提取和更新嵌入，导致：（1）不规则内存访问模式、（2）高昂的梯度计算开销、（3）大量的密集矩阵内存占用。与此同时，GNN 领域已广泛采用 SpMM 等稀疏操作进行加速，但 KGE 框架尚未采纳这一思路。

---

## 二、要解决的问题

1. **embedding 梯度计算成为训练瓶颈**：profiling 显示，embedding backward（`EmbeddingBackward0`）在多个翻译模型上占据 CPU 训练时间的约 40%，是排名前三的 CPU 密集型函数。
2. **细粒度 scatter/gather 操作效率低**：每个 triplet 需分别 gather head、tail、relation 的 embedding，backward 时再分别 scatter 梯度，操作碎片化，无法利用高性能矩阵乘法的优化技巧。
3. **GPU 内存占用过高**：密集矩阵表示和大量中间变量限制了 batch size，尤其 TransH 等模型在较大 embedding 维度下容易 OOM。

---

## 三、洞察与设计

**关键洞察**：翻译模型的核心计算（head - tail 或 head + relation - tail）可以用一个稀疏关联矩阵（incidence matrix）与嵌入密集矩阵的 SpMM 来统一表达，从而将多次离散的 scatter/gather 操作合并为单次矩阵乘法，天然适配已有的高性能 SpMM 优化（SIMD、cache blocking、WARP-level GPU primitives）。

**设计方案**：

1. **稀疏关联矩阵构造**：
   - **ht 计算**（head - tail）：构造 $A \in \{-1,0,1\}^{M \times N}$，每行只有两个非零元素（head 位置 +1，tail 位置 -1），乘以实体嵌入矩阵 $E \in \mathbb{R}^{N \times d}$ 即得所有 triplet 的 (h-t) 向量。
   - **hrt 计算**（head + relation - tail）：将实体和关系嵌入纵向拼接为 $E \in \mathbb{R}^{(N+R) \times d}$，关联矩阵扩展为 $A \in \{-1,0,1\}^{M \times (N+R)}$，每行三个非零元素，一次 SpMM 即完成。

2. **四个模型的稀疏公式化**：
   - **TransE / TorusE**：直接用 hrt SpMM + L2 norm（TorusE 用 torus distance）。
   - **TransR**：利用 $M_r(h-t) + r \approx 0$ 的变换，先 SpMM 计算 ht，再乘投影矩阵加 relation。
   - **TransH**：推导出 $(h-t) + d_r - w_r^T(h-t) \cdot w_r \approx 0$，复用 ht SpMM 结果。

3. **反向传播同样是 SpMM**：$\partial L / \partial X = A^T \times (\partial L / \partial C)$，$A^T$ 仍是稀疏矩阵，前向和反向均受益于高性能 SpMM。

4. **框架设计**：PyTorch 2.3 实现，模块化架构包含模型层、数据加载层（支持 TTL/RDF/CSV/SQLite streaming）、稀疏核接口（CPU 用 iSpLib，GPU 用 DGL g-SpMM）。

---

## 四、实现细节

- **稀疏格式**：CPU 使用 CSR 格式（iSpLib），GPU 使用 COO 格式（DGL g-SpMM），框架自动根据所选 SpMM 库生成对应格式的 mini-batch。
- **优化技巧**：SIMD 向量化、loop unrolling、cache blocking、tiling、WARP-level GPU primitives、动态负载均衡、代码生成。
- **内存映射支持**：当嵌入矩阵超过 CPU 内存时，支持 PyTorch memory-mapped tensors 流式加载（适配 LLM 预训练嵌入如 BERT/T5/GPT 的场景）。
- **负采样**：每个正样本生成一个负样本，预生成于训练循环外。
- **可扩展性**：论文附录 D 展示了扩展到 DistMult（乘法 semiring）、ComplEx（复数乘法）、RotatE（乘法+减法）的方案，通过修改 SpMM 的 semiring 运算符实现。
- **代码开源**：Python 包 https://github.com/HipGraph/SpTransX，MIT 许可。

## 五、实验结果

**实验平台**：NERSC Perlmutter，单 NVIDIA A100-SXM4 40GB GPU / AMD EPYC 7763 64 核 512GB DDR4 CPU。

**数据集**：7 个 KG 数据集（FB15K、FB15K237、WN18、WN18RR、FB13、YAGO3-10、BioKG），规模从 ~87K triplets 到 ~4.8M triplets。

**训练配置**：200 epochs，lr=0.0004，margin=0.5，MarginRankingLoss，L2 dissimilarity。

| 指标 | 结果 |
|------|------|
| **CPU 加速比** | TransE: 3.1x–5.3x, TransR: 2.5x–2.8x, TransH: 2.1x–4.5x, TorusE: 1.9x–2.0x（vs TorchKGE/DGL-KE/PyG） |
| **GPU 加速比** | TransE: 1.1x–4.2x, TransR: 1.1x–2.8x, TransH: 1.1x–OOM, TorusE: 1.5x–1.8x |
| **GPU 内存效率** | TransH 模型平均 11x 优于 TorchKGE；TorchKGE 在 FB13/YAGO3-10 上 TransH OOM |
| **FLOPs（CPU 平均）** | TransE: 220 vs 484 (TorchKGE), TransR: 567 vs 1158, TransH: 9.7 vs 19.6, TorusE: 290 vs 388（×10^10） |
| **Cache miss rate** | 除 TransH 外均低于 TorchKGE（TransE: 26.5% vs 29.4%） |
| **模型精度** | Hits@10 与 TorchKGE 一致或更好（WN18 上 TransE: 0.79±0.003, TransR: 0.33±0.006 vs 0.29±0.006） |
| **分布式扩展** | COVID-19 数据集 TransE 模型，4→64 GPU 从 706s 降至 180s，通信未成为瓶颈 |

## 六、批判性分析

1. **加速比变异范围大**：CPU 上 TransE 加速比从 3.1x 到 5.3x 跨度较大，但论文未深入分析不同数据集上加速比差异的根本原因（是受图结构影响还是数据规模影响？），仅笼统地说"consistent across datasets"。

2. **GPU 加速不如 CPU 显著**：GPU 上多个模型加速比仅 1.1x–1.8x，说明 GPU 上 SpMM 的优势被其他开销（kernel launch、数据传输）稀释。论文将此归因于"GPU 已经很快"，但缺乏 roofline model 或 bandwidth/compute utilization 的分析来定量解释。

3. **基线框架版本可能不公平**：DGL-KE 使用 PyTorch 1.7.1 和 CUDA 11.0（远低于 SpTransX 的 PyTorch 2.3 + CUDA 12.1），新版本 PyTorch 本身的 embedding 操作优化可能贡献了部分加速比。

4. **仅实现了翻译模型**：虽然附录讨论了 DistMult/ComplEx/RotatE 的理论扩展，但实际未实现和评测，"can be extended" 的说法缺乏实验验证。

5. **分布式实验过于初步**：仅在一个数据集上测试到 64 GPU，未报告通信占比、scaling efficiency，也没有与分布式基线（如 DGL-KE 的分布式模式）对比。

6. **Hits@10 精度对比条件不完全一致**：固定 lr=0.0004 不用 scheduler 时 SpTransX 略低于 TorchKGE（TransE 0.72 vs 0.74），加了 scheduler 后才追平。这暗示 sparse 公式可能改变了 loss landscape，但论文未讨论。

7. **缺少端到端应用场景评估**：所有实验仅测量训练时间和 Hits@10，未展示在实际下游任务（如推荐、问答）中的端到端价值。

## 七、AI Infra / MLSys 视角

1. **SpMM 替代 scatter/gather 的思路可迁移**：这一方法论对 GNN 训练、推荐系统中的 embedding 操作、以及任何涉及大规模 embedding lookup + gradient scatter 的场景都有启发。特别是大规模推荐系统中 embedding table 的梯度更新是已知瓶颈，类似的稀疏矩阵重构思路值得尝试。

2. **Semiring SpMM 的通用性**：通过修改 semiring 运算符适配不同模型（加法→乘法、实数→复数）的设计模式，为构建通用稀疏计算原语提供了参考。这与 GraphBLAS 的理念一致，可考虑在 AI Infra 中引入更灵活的 semiring 抽象。

3. **局限性启示**：GPU 上加速不显著表明，对于已经 compute-bound 的场景，减少操作次数的收益有限。未来工作应关注 memory-bound 场景（如大规模嵌入表、长序列 KV cache 管理），sparse 技术在此类场景中更有发挥空间。

4. **值得跟进的方向**：
   - 将 SpMM 思路扩展到 KG+LLM 联合训练场景（论文提到了 LLM embedding 初始化但未深入）
   - 与 2D/3D matrix distribution 结合的大规模分布式 KGE 训练
   - 在推荐系统 embedding training 中验证类似的 incidence matrix 重构方法

---

## 八、总结

SparseTransX 提出将翻译模型的 KGE 训练中碎片化的 scatter/gather 操作统一为稀疏关联矩阵与嵌入矩阵的 SpMM，在不改变模型精度的前提下，CPU 上实现最高 5.3x 加速、GPU 上最高 4.2x 加速，并大幅降低 GPU 内存占用。该方法适用于各类翻译模型且可扩展到非翻译模型，但 GPU 加速效果有限、分布式验证不充分、基线版本不统一是其主要局限。核心贡献在于揭示了 KGE 训练与稀疏矩阵运算之间的数学等价关系，为该领域引入了一条新的优化路径。
