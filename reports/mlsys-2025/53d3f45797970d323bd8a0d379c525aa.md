# PipeFill: Using GPUs During Bubbles in Pipeline-Parallel LLM Training

**作者**：Daiyaan Arfeen (Carnegie Mellon University), Zhen Zhang, Xinwei Fu, Yida Wang (Amazon Web Services), Gregory R. Ganger (Carnegie Mellon University)
**会议**：MLSys 2025
**链接**：Proceedings of the 8th MLSys Conference, Santa Clara, CA, USA, 2025
**源文件**：[[53d3f45797970d323bd8a0d379c525aa.pdf]]

---

## 一、背景

大规模 LLM 训练通常需要结合 Data Parallelism (DP)、Tensor Parallelism (TP) 和 Pipeline Parallelism (PP) 三种并行策略。其中 PP 将模型按层切分到多个节点上，以 microbatch 流水线方式执行前向和反向传播。然而 PP 不可避免地产生 pipeline bubble——流水线在每个 minibatch 的填充和排空阶段，各 GPU 存在大量空闲时间。

随着训练规模扩大（更多 DP replica → 每个 replica 的 microbatch 数减少），bubble 比例急剧上升。论文给出的数据显示：一个 40B 参数 LLM 从 1K GPU 扩展到 8K GPU 时，单 GPU TFLOPS 下降超过 60%，bubble 占比可超过 60%。这构成了"缩短训练时间"与"GPU 集群效率"之间的核心矛盾。

---

## 二、要解决的问题

1. **Pipeline bubble 导致 GPU 严重空闲**：PP 训练中 bubble 比例为 (p-1)/(m+p-1)，大规模训练时 p 增大、m 减小，bubble 可超过 60%。
2. **现有 bubble 填充方案局限性大**：PipeFisher 用 K-FAC 填充 bubble，Bamboo 用冗余计算填充——它们都依赖于主训练任务本身，仅适用于特定场景。
3. **独立任务填充面临三大挑战**：
   - **内存管理**：主训练任务在 bubble 期间仍占据大部分 GPU 显存，填充任务可用内存有限，需避免 OOM。
   - **上下文切换**：必须保证填充任务的执行完全不影响主训练任务的性能，需精确控制填充时长。
   - **调度**：不同 pipeline stage 的 bubble 具有异构特性（时长、可用内存不同），需要灵活的调度策略匹配用户目标。

---

## 三、洞察与设计

**关键洞察**：Pipeline bubble 是由 PP 内部的数据依赖造成的，与其试图消除 bubble 或填充与主任务相关的计算，不如利用这些空闲时段执行完全独立的任务。独立任务不引入新的依赖关系，只要精确控制执行时间和内存使用，就能在不影响主任务的前提下回收 bubble 中的 GPU 算力。

基于此洞察，PIPEFILL 设计了三个核心组件：

1. **Instrumented Pipeline Engine**：在现有 pipeline schedule 中插入 bubble instruction，用于（a）profiling bubble 时长和可用内存，（b）在 bubble 开始/结束时通过同步原语通知 Executor。还支持将主任务的 optimizer states offload 到 CPU，以增加 fill job 可用内存。

2. **Fill Job Executor**：为每个 GPU 创建独立进程，负责执行填充任务。核心是 Execution Plan 算法（Algorithm 1）：将 fill job 的计算图线性化后，贪心地将节点打包到连续的 bubble 中，确保不超出时长和内存约束。执行时通过 `cuda.set_per_process_memory_fraction` 设置内存上限，即使 fill job OOM 也不影响主进程。

3. **Fill Job Scheduler**：作为 bubble 资源和外部集群调度器之间的接口，支持用户自定义调度策略（如 SJF、Makespan-Minimizing），通过打分函数决定将哪个 fill job 分配到哪个 GPU 的 bubble 上。

## 四、实现细节

- **基于 DeepSpeed** 实现，修改了其 pipeline engine，支持 GPipe 和 1F1B 两种 schedule。
- **Bubble profiling**：训练开始时，bubble instruction 以指数递增的等待时间（100ms → 200ms → ...）探测 bubble 时长，直到观测到主任务吞吐下降。通过 `torch.cuda.memory_allocated()` 测量可用内存，并调用 `torch.cuda.empty_cache()` 释放临时缓冲区。
- **主任务 offloading**：将 Adam optimizer states offload 到 CPU，offloading 与 forward pass 重叠，onloading 与 gradient synchronization 重叠，对主任务无额外开销。
- **Executor 进程间通信**：主训练进程通过 IPC 信号通知 Executor 进程 bubble 的开始。Executor 使用 ZeRO-Offload / ZeRO-Infinity 支持大模型 fill job 的 CPU/NVMe offloading 和 activation checkpointing。
- **Fill job 类型**：支持训练和 batch inference 两类（不支持延迟敏感的 online inference）。
- **GPipe 两个 bubble**：fill-drain bubble（minibatch 切换时）和 fwd-bwd bubble（前向饱和到反向开始）；1F1B 的 fwd-bwd bubble 更短但有额外非连续小 bubble（PIPEFILL 不填充这些小 bubble）。

---

## 五、实验结果

**实验平台**：16 台 AWS EC2 p3.16xlarge（每台 8× V100 16GB，NVLink 连接），大规模实验通过 event-driven simulator 完成。

**主训练任务**：物理集群用 5B 参数 LLM（16 pipeline stages），模拟器用 40B 参数 LLM（8-way TP + 16-stage PP，1K-8K GPU）。

| 指标 | 结果 |
|------|------|
| GPU 利用率提升（8K GPU，trace mix） | >45% |
| GPU 利用率提升（8K GPU，仅 BERT inference） | >63% |
| 主任务 slowdown | <2%（填充 ≤68% bubble 时长时） |
| 低规模（1-2K GPU）利用率提升 | 5-15% |
| 4K GPU 时利用率 vs 2K 传统 PP | 89%（trace mix），96.7%（BERT inference） |
| 8K GPU 等效额外 GPU 算力 | 1500-2600 GPU |
| 模拟器 vs 物理集群误差 | <5% TFLOPS，<2% fill job recovered FLOPS |

**Fill job 特性分析**：

| Fill Job 类型 | GPU TFLOPS | 相对独占执行的性能 |
|------|------|------|
| Batch inference（BERT 等） | 较高（内存需求低，batch size 大） | ~30% |
| Training（小模型） | 中等 | ~30% |
| Training（大模型，如 XLM 2.8B） | 较低（需 CPU offloading） | 更低 |

**敏感性分析**：
- GPipe vs 1F1B：低规模时 GPipe 多恢复 20% 利用率，大规模时差距缩至 5%。
- 1F1B-interleave 恢复的 TFLOPS 比 1F1B 少 10-30%。
- Free memory 从 2GB→4GB 恢复 TFLOPS 提升 30%；4GB→8GB 仅提升 12.2%。
- Bubble 时长缩减 50% 仅降低 TFLOPS 5.3%。

## 六、批判性分析

1. **硬件平台陈旧**：实验基于 V100 16GB（2017 年硬件），当前主流训练使用 H100/H200（80GB+ HBM），显存更充裕的情况下 bubble 中可用内存比例和 fill job 效率会显著不同，论文的定量结论可迁移性存疑。

2. **模拟器主导的大规模结果**：核心卖点——8K GPU 63% 利用率提升——完全来自模拟器。虽然小规模物理实验验证了模拟器精度（<5% 误差），但模拟器假设 DP 执行完全可预测、bubble 在所有 replica 间相同，大规模真实集群中的网络抖动、stragglers、故障恢复等问题未被考虑。

3. **Fill job 实际效率偏低**：所有 fill job 相对独占执行仅达到约 30% 的性能。这意味着虽然"回收了 63% 的 bubble"，但这些回收的算力的实际产出效率很低。论文在报告利用率时用 TFLOPS 而非 useful throughput，可能高估了实际收益。

4. **调度复杂度被低估**：论文假设 fill job 的 profile（每个 node 的执行时间和内存需求）预先已知且准确，但实际中不同 fill job 的内存使用可能有波动，特别是 transformer 模型的 activation 大小依赖于 sequence length。Executor 的 OOM 隔离机制虽然保护了主任务，但 fill job 频繁 OOM 重启的开销未被讨论。

5. **与更先进 pipeline schedule 的对比缺失**：论文仅考虑了 GPipe、1F1B 和 interleaved 1F1B。近年来出现了 zero-bubble pipeline（如 ZeroBubble、DualPipe）等显著减少 bubble 的 schedule，如果 bubble 本身被大幅缩小，PIPEFILL 的价值空间就会被压缩。论文未讨论这一趋势。

6. **Fill job 选择受限**：由于 bubble 中可用内存仅约 4.5GB（16GB 的 ~28%），fill job 被限制为小模型或需要激进 offloading 的配置。CNN 模型（如 EfficientNet）因 activation 大而表现很差。这限制了系统的通用性。

---

## 七、AI Infra / MLSys 视角

1. **"碎片化算力回收"是重要方向**：PIPEFILL 提出的核心思想——将大规模训练中的结构化空闲时间（bubble）暴露为可调度资源——对 AI Infra 有广泛启发。类似思路可以扩展到其他场景：gradient synchronization 等待时间、checkpoint 写入时间、数据加载 stall 等。

2. **与 zero-bubble schedule 的互补性**：即使采用 ZeroBubble 等先进 schedule，大规模训练中仍可能存在通信等待、load imbalance 等空闲时间。PIPEFILL 的 Executor + Scheduler 架构可以作为通用的"碎片算力回收层"集成到训练框架中。

3. **可操作的 future work**：
   - **在 H100/H200 上验证**：更大的 HBM、更高的 CPU-GPU 带宽（PCIe 5.0、NVLink-C2C）会显著改变 fill job 的效率特性，值得重新量化。
   - **Inference serving 集成**：将 pipeline bubble 暴露给推理服务系统（如 vLLM），在训练 bubble 中处理 batch inference 请求，实现训练-推理混部。
   - **与弹性训练结合**：fill job 本身也可以是弹性训练任务的一部分，当 bubble 可用时分配额外的 micro-step，不可用时暂停。
   - **预测性调度**：Pipeline bubble 的出现是周期性、可预测的，可以用此特性做预取和预调度，减少 context switch 开销。

4. **对集群调度器的启示**：PIPEFILL 的 Scheduler 接口设计（将 bubble 作为资源暴露给上层调度器）是一个有价值的抽象。未来集群调度器可以将"pipeline bubble 算力"作为一种新的资源类型纳入全局调度决策。

---

## 八、总结

PIPEFILL 提出了一种利用 pipeline parallel 训练中 bubble 时间执行独立 fill job（训练或 batch inference）的系统，通过 bubble profiling、内存管理、计算图分区和灵活调度，在对主训练任务 <2% slowdown 的前提下，将 8K GPU 大规模 LLM 训练的 GPU 利用率提升最高 63%。其核心价值在于"碎片化算力回收"的思想和系统化实现，但受限于老旧硬件平台验证、fill job 实际效率偏低、以及未与 zero-bubble 等新 schedule 对比，实际落地价值需要在现代硬件和更先进的训练框架上重新评估。
