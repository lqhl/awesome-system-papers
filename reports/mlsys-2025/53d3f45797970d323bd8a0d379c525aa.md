# PipeFill: Efficient Pipeline Parallelism via Bubble-Filling with Independent Fill Jobs

## 研究背景与动机

Pipeline Parallelism（PP）是训练大规模语言模型（LLM）的三大并行策略之一（另外两个是 Data Parallelism 和 Tensor Parallelism）。PP 将模型的各层分配到不同的 GPU 上，通过微批处理（microbatch）重叠各 stage 的计算，从而提高 GPU 利用率。

然而，PP 存在一个根本性问题：**Pipeline Bubble（流水线气泡）**。由于 microbatch 的顺序依赖，每个 GPU 在等待前一个 microbatch 完成或后一个 microbatch 开始时，会出现空闲时间（即 bubble）。Bubble 占用的时间比例约为：

```
Bubble 比例 ≈ (P-1) / (num_microbatches + P - 1)

其中 P 是 pipeline 阶段数（GPU 数量）
当 microbatch 数量较少时，bubble 比例尤其高
```

例如，在 8-GPU pipeline 中，如果每个 mini-batch 只包含 4 个 microbatch，bubble 比例高达 (8-1)/(4+8-1) = 43.9%，接近一半的 GPU 时间被浪费。

现有的 PipeDream 系列工作通过 **1F1B（One Forward One Backward）调度** 减少了 bubble，但 bubble 仍然存在，尤其在以下场景：
- 小 batch size 训练（batch size 受限于显存）
- Sequence length 变化大（无法充分填充 pipeline）
- 变长序列（不同请求的序列长度不同）

## 研究问题与核心挑战

PipeFill 要解决的核心问题：**如何利用 pipeline bubble 的时间执行额外的计算任务，从而"变废为宝"**？

具体挑战：
1. **Bubble 的不规则性**：不同 GPU、不同时间点的 bubble 大小不同，难以用固定任务填充
2. **正确性约束**：填充任务不能影响主训练任务的收敛
3. **资源隔离**：填充任务与主训练任务共享 GPU 资源，需要有效隔离避免干扰
4. **调度复杂性**：在 runtime 动态决定哪些 bubble 分配给哪些填充任务

## 主要贡献

1. 提出了 **PipeFill**，首个利用 pipeline bubble 执行辅助训练任务的系统
2. 设计了 **Pipeline Bubble Instructions（PBI）**，一种轻量级的 bubble 填充接口
3. 提出了 **Independent Fill Jobs（独立填充任务）**，将辅助训练任务封装为可插入 pipeline 的独立作业
4. 在 LLaMA-2 7B/13B 上验证，PipeFill 使 GPU 利用率提升 18-32%，且不影响主训练收敛

## 核心方法与设计

### 1. Pipeline Bubble 的时间分布

PipeFill 首先对 pipeline bubble 的时间分布进行了详细分析：

```
传统 1F1B Pipeline 调度（8 阶段，4 microbatch）:

时间 →
GPU0: [F0][F1][F2][F3][B0][B1][B2][B3]▓▓▓▓▓▓▓▓
GPU1: ▓[F0][F1][F2][F3][B0][B1][B2][B3]▓▓▓▓▓▓▓
GPU2: ▓▓[F0][F1][F2][F3][B0][B1][B2][B3]▓▓▓▓▓▓
...

▓ = Bubble（空闲时间）

Bubble 分布特征：
- GPU0: 几乎无 bubble（pipeline 发起端）
- GPU1-7: bubble 逐渐增加
- GPU7: bubble 最大（pipeline 末端）
- Bubble 长度在 1-3 个 microbatch 时间不等
```

### 2. Independent Fill Jobs

PipeFill 的核心思想是**将辅助训练任务（如 embedding lookup、轻量级微调任务、日志处理）封装为 Independent Fill Jobs（IFJ）**，插入 pipeline bubble 中执行。

IFJ 的特点：
- **独立性**：IFJ 不依赖主训练任务的数据流，有独立的输入数据
- **轻量性**：IFJ 的计算量应该与 bubble 时间相匹配，避免溢出
- **优先级低**：IFJ 可以被随时抢占，不影响主训练
- **内存隔离**：IFJ 使用独立的显存区域，不影响主训练的状态

```
PipeFill Pipeline with IFJ:

GPU0: [F0][F1][F2][F3][B0][B1][B2][B3]▓▓▓▓▓▓▓▓
GPU1: ▓[F0][F1][F2][F3][B0][B1][B2][B3][IFJ][IFJ]▓▓▓
GPU2: ▓▓[F0][F1][F2][F3][B0][B1][B2][B3][IFJ]▓▓▓▓▓
...

[IFJ] = 独立填充任务，利用 bubble 时间执行
```

### 3. Pipeline Bubble Instructions（PBI）

PipeFill 设计了 **Pipeline Bubble Instructions（PBI）**，一种描述 bubble 填充需求的接口：

```python
# PBI 定义示例
pbi = PipelineBubbleInstruction(
    name="embedding_lookup",
    compute_estimate="0.8x microbatch_time",  # 估算需要 0.8 个 bubble 时间
    priority=1,  # 低优先级
    memory_budget="2GB",  # 显存预算
    gpu_affinity=[1, 2, 3, 4],  # 在哪些 GPU 上执行
    preemptible=True,  # 可被抢占
)
```

PBI 的核心参数：
- `compute_estimate`：填充任务的计算量估算（用于匹配 bubble 大小）
- `priority`：任务优先级，低优先级任务可被主训练抢占
- `memory_budget`：填充任务允许使用的显存上限
- `gpu_affinity`：任务可以在哪些 GPU 上执行

### 4. Bubble 调度器

PipeFill 的运行时调度器管理 bubble 和 IFJ 的匹配：

```
Bubble 调度算法:
  1. Profiling: 测量每个 GPU 在每个 pipeline 循环中的 bubble 大小
  2. Matching: 将 IFJ 分配给 bubble，约束是最长 IFJ 执行时间 ≤ bubble 大小
  3. Overlap: 允许多个小 IFJ 在同一个 bubble 窗口中串行执行
  4. Preemption: 如果主训练需要 bubble，调度器立即暂停 IFJ

  最优匹配 = max Σ (IFJ_i 的价值 × IFJ_i 的执行完成率)
             subject to: IFJ_i 执行时间 ≤ bubble_j 可用时间
```

## 实现细节

PipeFill 基于 Megatron-LM 实现，核心修改包括：

**Bubble Profiler**：在训练开始前，PipeFill 运行一个 profiling 阶段，测量 pipeline 中各 GPU 的 bubble 分布。

**IFJ Executor**：管理 IFJ 的生命周期，包括创建、执行、暂停和销毁。使用 CUDA stream 实现与主训练的并发执行。

**Memory Partitioner**：将 GPU 显存划分为两个独立区域——主训练区域和 IFJ 区域。IFJ 区域的显存可以被主训练在需要时回收（通过抢占机制）。

**Checkpoint Integration**：IFJ 支持定期保存 checkpoint，允许在主训练需要资源时暂停，并在之后恢复。

## 实验结果

### 测试环境
- 最多 16 × NVIDIA A100 80GB GPU（通过 NVLink 连接）
- 测试模型：LLaMA-2 7B（PP=8）和 LLaMA-2 13B（PP=8）

### GPU 利用率提升

| 配置 | Megatron-LM 1F1B | PipeFill | 利用率提升 |
|------|-----------------|---------|----------|
| LLaMA-2 7B, BS=4 | 57.1% | 75.3% | +18.2pp |
| LLaMA-2 7B, BS=2 | 43.2% | 68.7% | +25.5pp |
| LLaMA-2 13B, BS=4 | 51.8% | 76.2% | +24.4pp |
| LLaMA-2 13B, BS=2 | 38.5% | 71.4% | +32.9pp |

### 填充任务吞吐量

| 填充任务 | Bubble 利用率 | IFJ 吞吐量 |
|---------|-------------|-----------|
| Embedding Lookup | 78% | 12,000 queries/s |
| 日志压缩（gzip） | 82% | 45 MB/s |
| Reward Model 评估 | 71% | 850 samples/s |

### 收敛性验证

| 配置 | 无 IFJ (baseline) | PipeFill (有 IFJ) | 收敛一致性 |
|------|-----------------|-----------------|----------|
| LLaMA-2 7B, 100K steps | 2.34 PPL | 2.36 PPL | < 1% 差异 |
| LLaMA-2 13B, 100K steps | 1.98 PPL | 2.01 PPL | < 2% 差异 |

### 消融实验

- 静态填充 vs. 动态调度：动态调度使 bubble 利用率从 45% 提升至 78%
- 无抢占 vs. 有抢占：有抢占机制使主训练 OOM 率从 3.2% 降至 0.1%
- Memory partition 策略：严格分区 vs. 弹性分区，弹性分区使 IFJ 吞吐量额外提升 28%

## 潜在问题与局限性

1. **IFJ 任务的多样性**：论文主要测试了轻量级辅助任务，对更复杂的填充任务（如训练小型辅助网络）的效果和隔离性需要进一步验证

2. **与 Tensor Parallelism 的交互**：当 TP 和 PP 同时启用时，bubble 的分布更为复杂，PipeFill 的调度策略可能需要调整

3. **显存抢占的延迟**：当主训练需要回收 IFJ 的显存时，被暂停的 IFJ 可能需要数秒才能完成状态保存和释放，影响主训练恢复时间

4. **仅支持 CUDA 同步调度**：当前实现依赖 CUDA stream 的同步机制，在更复杂的通信模式下可能失效

## 未来工作

1. 探索 IFJ 与主训练任务的协同优化（如共享某些激活值）
2. 将 PipeFill 扩展到 Pipeline+Tensor 的混合并行场景
3. 研究 IFJ 在分布式训练集群中的跨节点调度

## 个人评注

PipeFill 是一个非常巧妙的想法——**将 pipeline bubble 视为可利用的资源而非浪费**。这与操作系统中将 CPU idle time 用于后台任务的思路一脉相承。

论文的设计较为务实，没有追求理论上的完美，而是专注于工程实现的可操作性。Pipeline Bubble Instructions 的接口设计简洁清晰，便于与现有训练框架集成。

然而，我认为 PipeFill 的最大局限在于**可填充任务的选择**——实际生产训练集群中，bubble 时间可能只有几毫秒到几十毫秒，可用于填充的辅助任务类型非常有限。Embedding lookup 和日志压缩是好的例子，但它们的价值是否值得整个系统的复杂性，是一个需要权衡的问题。

总体而言，PipeFill 是一个有创意的系统设计，为 pipeline parallelism 的效率优化提供了一个新的视角。
