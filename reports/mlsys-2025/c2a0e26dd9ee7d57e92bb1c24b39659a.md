# ThunderServe: High-Performance and Cost-Efficient LLM Serving in Cloud Environments

## 一、背景

LLM 推理服务需要大量 GPU 资源，而高端 GPU（如 A100、H100）供不应求且价格高昂。云环境提供了多种型号的 GPU（A100、A6000、A5000、A40、3090Ti 等），价格差异显著（$0.223/hr ~ $1.753/hr），为降低 LLM 服务成本提供了可能。同时，LLM 推理天然分为 prefill（计算密集）和 decode（内存带宽密集）两个阶段，各阶段对硬件资源的需求特征不同。Phase splitting（将 prefill 和 decode 分离到不同设备）已被证明能提高硬件利用率，但现有工作均假设高速互联（NVLink / InfiniBand），未适配云环境中异构、低带宽的网络条件。

---

## 二、要解决的问题

1. **异构资源池的调度难题**：云上 GPU 型号各异、数量有限，如何从全局视角将不同类型的 GPU 分组为 model serving group，并决定每组负责 prefill 还是 decode，是一个组合优化难题（本质是 NP-hard 的 job shop scheduling 问题）。

2. **异构低带宽网络下的 KV cache 传输瓶颈**：Phase splitting 必须在 prefill 和 decode 副本之间传输 KV cache。云环境中 GPU 间通过 PCIe + Ethernet 连接，带宽远低于 NVLink/InfiniBand，KV cache 传输开销不可忽略，可占端到端延迟的 16-30%。

3. **工作负载与资源的动态变化**：云上 GPU 可能随时下线，请求分布（编码 vs 对话等）也会变化。现有系统重新调度需要从头生成部署计划并重新加载模型参数（如 175B 模型重新加载需 5 分钟以上），导致服务严重中断。

---

## 三、洞察与设计

**关键洞察**：Prefill 阶段是计算密集型，decode 阶段是内存带宽密集型，而云上不同型号 GPU 的算力和带宽各有优势——这种"工作负载异构性"与"硬件异构性"天然匹配，可以将高算力 GPU（如 A40, 149.7 TFLOPS）分配给 prefill，高内存带宽 GPU（如 3090Ti, 1008 GB/s）分配给 decode，从而在相同预算下获得比同构集群更好的性价比。此外，phase designation 和 orchestration 的调整不需要重新加载模型参数，可实现近零开销的在线重调度。

### 系统架构

ThunderServe 将部署优化建模为**两层层次优化问题**：

- **上层问题**：将可用的异构 GPU 分组（group construction），并为每组指定 prefill 或 decode 角色（phase designation）。采用 **Tabu Search** 算法求解，通过四种邻域构造操作（翻转 phase、拆分组、合并组、移动 GPU）迭代搜索最优方案。初始解通过层次聚类（按 GPU 间网络带宽）生成。

- **下层问题**：给定分组和 phase 后，为每组推导最优并行配置（TP/PP），并确定 prefill-decode 副本间的请求路由（orchestration）。并行配置推导考虑了云环境特性（禁止跨节点 TP、支持非均匀 PP 分层、用 DP 最小化跨 stage 通信）。Orchestration 建模为 **Two-Stage Transportation Problem (TSTP)**，通过线性规划求解最优请求分发比例。

### 轻量级重调度

当工作负载或 GPU 可用性变化时，仅调整 phase designation 和 orchestration（不改变 group construction 和 parallel configuration），无需重新加载模型参数。整个过程约 13 秒完成（vs 全量重调度 157 秒）。

### KV Cache 压缩

将 16-bit KV cache 量化为 4-bit 进行传输，接收端立即反量化为 16-bit 用于计算。通信量减少 4 倍，KV cache 传输占比从 16-30% 降至 4-9%，模型精度损失 < 2%。

---

## 四、实现细节

- **代码量**：约 20K 行 Python + C++/CUDA
- **核心依赖**：集成 FlashAttention 和 PagedAttention 加速推理，使用 DistServe 的 batching 策略
- **Tabu Search 参数**：搜索步数 N_step=100，每步邻域数 N_nghb=10，记忆列表长度 N_mem=5
- **通信建模**：使用 alpha-beta 模型估算 KV cache 传输时间：T_kvcomm = α_ij + 2bshN_bytes/β_ij
- **SLO 评估**：内置 inference task simulator（源自 DistServe），估算不同配置下的 SLO attainment
- **运行时流程**：① 启动时生成部署计划并实例化副本 → ② 请求按 orchestration 分发到 prefill/decode 副本 → ③ 持续监控工作负载 → ④ 检测到负载变化时触发轻量重调度

## 五、实验结果

### 硬件配置

| 环境 | GPU | 价格 |
|------|-----|------|
| 云（Vast.ai） | 2×4×A6000 + 2×4×A5000 + 1×8×A40 + 2×4×3090Ti（共 32 GPU） | $13.542/hr |
| 本地 | 1×8×A100-80GB | $14.024/hr |

### 模型与负载

LLaMA-30B，Coding 和 Conversation 两种工作负载（Azure Conversation 数据集）。

### 主要结果

| 对比 | 指标 | 提升 |
|------|------|------|
| vs HexGen（云） | E2E latency deadline | 最高 1.8×、平均 1.4× 降低（coding）；最高 1.4×、平均 1.3× 降低（conversation） |
| vs DistServe/vLLM（本地） | E2E latency deadline | 最高 2.5×、平均 1.8× 降低 |
| vs HexGen | 吞吐量 | 1.5×（coding）、1.3×（conversation） |
| vs DistServe | 吞吐量 | 1.5×（coding）、2.1×（conversation） |

### 调度开销

| 方案 | 调度时间 | 参数加载 | 总计 |
|------|---------|---------|------|
| 全量重调度 | 54±5s | 103±10s | 157±13s |
| 轻量重调度 | 13±2s | 0s | 13±2s |

### KV Cache 压缩精度影响

在 CoQA、TruthfulQA、GSM8K 上，4-bit vs 16-bit 精度差异均 < 2%。

## 六、批判性分析

1. **实验规模有限**：只在 32 GPU 的云集群上测试，且仅用 LLaMA-30B。对于更大模型（70B+）和更大集群，Tabu Search 的搜索时间（当前 54s@32GPU）是否线性增长未知，可扩展性存疑。

2. **基线选择不够全面**：云环境下只对比了 HexGen，未与 Helix（同为异构 GPU 服务系统）进行对比。本地环境对比的 DistServe 和 vLLM 运行在 8×A100 上，但其价格（$14/hr）对应的是云 rental 价格，不是实际购买成本——这种"同预算"对比对云方案天然有利（云上可以租更多低端 GPU），并不能真正说明系统设计的优越性。

3. **KV Cache 压缩方案过于简化**：直接借用 KIVI 的量化方案，传输后立即反量化。这种"传输时量化、计算时全精度"的做法虽然保证精度，但没有与其他 KV cache 压缩方案（如 token pruning、selective transmission）对比，也没有评估在更长序列（如 32K+ tokens）下的通信瓶颈是否仍然可控。

4. **Tabu Search 的解质量保证缺失**：论文没有分析 Tabu Search 找到的解与最优解的差距（optimality gap），也没有在小规模问题上与精确求解器对比。搜索参数（N_step=100, N_nghb=10, N_mem=5）的选择缺乏敏感性分析。

5. **轻量重调度的适用范围有局限**：仅调整 phase designation 和 orchestration，group construction 和 parallel configuration 不变。当 GPU 大面积下线或硬件组成发生重大变化时（如新增不同型号的 GPU），轻量重调度无法适应，仍需全量重调度。论文只展示了 4/32 GPU 下线的场景，缺乏更极端情况的评估。

6. **缺乏与 spot instance 场景的结合**：云环境中 spot/preemptible instance 的价格更低但随时可能被回收，这是云 LLM 服务的重要场景，论文完全未涉及。

## 七、AI Infra / MLSys 视角

1. **Phase splitting + 异构 GPU 的组合思路值得借鉴**：将推理阶段的计算特性差异与硬件异构性显式对齐，这一思路可以推广到更多场景——例如 MoE 推理中 expert 的异构部署、speculative decoding 中 draft model 与 verification model 的异构分配。

2. **两层层次优化框架的通用性**：上层处理资源分组/角色分配、下层处理并行配置/路由，这种分解方式对其他大规模调度问题（如多租户 GPU 集群管理、异构训练集群调度）有参考价值。

3. **轻量重调度是实用的工程抽象**：将部署计划分为"重操作"（group construction, parallel config）和"轻操作"（phase designation, orchestration），在 workload 变化时只调整轻操作——这种分层设计思想适用于所有需要在线调整的 serving 系统。

4. **可跟进的研究方向**：
   - 将 ThunderServe 的调度框架扩展到 **MoE 模型**（expert placement + routing 的联合优化）
   - 结合 **spot instance** 的弹性伸缩，设计价格感知的部署策略
   - 在 **disaggregated memory** 架构下重新设计 KV cache 传输策略（RDMA + 远端内存 vs 本地量化压缩）
   - 将 Tabu Search 替换为 **learned optimizer**（如 RL-based scheduler），加速大规模集群的调度收敛

---

## 八、总结

ThunderServe 是首个将 phase splitting 与异构 GPU 云环境结合的 LLM serving 系统。通过两层层次优化（Tabu Search + LP）联合优化 GPU 分组、phase 分配、并行策略和请求路由，配合 KV cache 4-bit 量化压缩和轻量级重调度机制，在相同预算下实现了比同构集群方案最高 2.5× 的延迟降低和 2.1× 的吞吐提升。系统主要适用于拥有多种型号 GPU 的云环境，局限性在于实验规模较小（32 GPU / LLaMA-30B）、Tabu Search 可扩展性未充分验证、以及轻量重调度在极端场景下的适用性有限。
