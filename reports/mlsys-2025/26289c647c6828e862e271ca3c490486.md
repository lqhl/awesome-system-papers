# Rethinking Key-Value Cache Compression Techniques for Large Language Model Serving

**作者**：Wei Gao (NTU, S-Lab, Shanghai AI Lab), Xinyu Zhou (NTU), Peng Sun (Shanghai AI Lab, SenseTime), Tianwei Zhang (NTU), Yonggang Wen (NTU)
**会议**：MLSys 2025
**链接**：https://github.com/LLMkvsys/rethink-kv-compression
**源文件**：[[26289c647c6828e862e271ca3c490486.pdf]]

---

## 一、背景

LLM 推理中 KV cache 是主要的内存瓶颈。以 LLaMA3-70B 为例，FP16 格式下 batch size 512、prompt 长度 2048 时，模型权重需要 130GB，而 KV cache 需要额外 512GB。为缓解这一问题，研究者提出了大量 KV cache 压缩算法，主要分为量化（quantization）和稀疏（sparsity）两大类。然而，尽管学术论文中展示了良好的压缩效果，这些方法在生产环境中的实际部署仍然非常有限。

---

## 二、要解决的问题

现有 KV cache 压缩研究存在三个被忽视的关键维度（Missing Pieces）：

1. **吞吐量评估不充分**：大多数压缩算法仅在 Transformers (TRL) 框架上测量吞吐量，未考虑 FlashAttention 和 PagedAttention 等生产级优化。在集成这些优化后，KV cache 压缩的性能增益大幅缩水甚至消失。
2. **响应长度分布偏移被忽略**：压缩 KV cache 可能导致模型生成更冗长的响应（verbose responses），抵消吞吐量收益，最终导致端到端延迟增加而非减少。
3. **缺乏对负样本的分析**：现有研究只报告整体准确率，掩盖了 KV cache 压缩对特定任务类型（如代码补全、问答）造成严重质量退化的事实。

---

## 三、洞察与设计

**关键洞察**：KV cache 压缩算法的实际效果不能仅通过内存缩减和整体准确率来衡量——吞吐量、响应长度分布变化和逐样本质量三个维度共同决定了压缩方法能否在生产环境中真正带来收益。

基于这一洞察，作者从以下三个维度系统性地重新审视现有方法：

**维度一：吞吐量分析**。在 LMDeploy（集成 PagedAttention + FlashAttention）上重新测量压缩算法的 prefill 和 decoding 吞吐量。发现：
- TRL 上的高 speedup 在生产级框架上不可复现（Observation 1）
- 量化方法（如 GEAR）的去量化和误差校正步骤引入额外计算开销
- 稀疏方法需要额外 pass 来计算 attention score 作为重要性指标，与 FlashAttention 的 one-pass 设计冲突
- 只有在 KV cache 较重（大 batch、长序列）时，压缩才可能带来吞吐量优势

**维度二：响应长度分析**。通过对比 FP16 和压缩方法在 ShareGPT 上的输出长度分布，发现压缩后模型倾向于生成更长的响应。更高的压缩比会加剧这一现象。

**维度三：负样本分析**。在 LongBench 上逐样本评估，以 10% 性能下降为阈值识别负样本。发现所有压缩方法在特定任务（尤其是代码补全）上存在严重质量退化。

---

## 四、实现细节

作者提供了三个实用工具：

1. **Throughput Predictor**：基于轻量级模型预测在给定 batch size 和 prompt 长度下，压缩算法能否带来吞吐量优势。预测准确率 85.8%–88.5%。

2. **Length Predictor**：基于 BERT 分类器预测压缩算法对特定请求的输出长度影响。预测准确率 87.8%–95.7%。

3. **Negative Sample Benchmark**：编译了一组压缩方法的失败样本数据集，用于公平评估未来的压缩算法。

**Request Router**：结合上述两个预测器实现请求路由，在 4 GPU 集群上（1 GPU 运行 FP16，3 GPU 运行压缩模型），根据预估的端到端延迟将请求路由到最优 GPU。

评估选用的压缩算法：
- 量化：KIVI（per-channel key + per-token value 量化）、GEAR（量化误差低秩近似）
- 稀疏：StreamingLLM（保留首尾 token）、H2O（基于累积 attention score 动态驱逐）

实验框架：TRL、TRL+FlashAttention、LMDeploy（v6.0.1 修改版）。模型：LLaMA-2-7B/13B/70B、LLaMA-3.1-8B、Mistral-7B。硬件：NVIDIA A6000 GPU（通过 NVLink 互联）、H800 GPU。

## 五、实验结果

### 吞吐量分析

| 场景 | 关键发现 |
|------|---------|
| TRL vs LMDeploy | LMDeploy 的 FP16 基线已远快于 TRL，压缩算法在 TRL 上的 speedup 不可迁移 |
| Prefill 阶段 | KIVI、StreamingLLM 接近 FP16；GEAR、H2O 一致性地降低 prefill 吞吐量 |
| Decoding 阶段 | 仅在 KV cache 较重时（大 batch size、长 KV length）压缩方法才有优势 |
| 张量并行 (TP) | 更大 TP 在 prefill 阶段有显著收益，但在小 batch decoding 阶段收益有限 |

### 响应长度分析

| 压缩比 | 响应变长比例 | 平均长度增加 |
|--------|------------|------------|
| 低压缩比 | ~30% 样本变长 | 适度 |
| 高压缩比 | 分布显著偏移 | 更多样本生成冗长输出 |

温度变化（T=0.9–1.1）导致的长度变化远小于 KV cache 压缩的影响。

### 端到端延迟与路由

| 路由策略 | FP16 | KIVI | GEAR | H2O | StreamingLLM |
|---------|------|------|------|-----|-------------|
| Baseline | 11.4s | 9.1s | 13.4s | 10.6s | 10.3s |
| w/ Throughput | - | 7.7s | 9.1s | 8.3s | 8.2s |
| w/ Length | - | 10.9s | 13.0s | 11.2s | 11.3s |
| w/ Both | - | 6.3s | 7.4s | 6.9s | 6.6s |

组合路由策略实现 1.45–1.80× 端到端延迟加速。

### 负样本分析（LLaMA-3.1-8B-instruct，LongBench）

| 任务类型 | FP16 Baseline | KIVI | GEAR | H2O | StreamingLLM |
|---------|--------------|------|------|-----|-------------|
| Summarization | 31.6 | 24.8 | 23.7 | 24.7 | 24.3 |
| Question Answering | 52.0 | 28.8 | 28.7 | 33.8 | 30.4 |
| Code | 97.0 | 30.0 | 30.0 | 57.2 | 61.3 |

代码补全任务受影响最大，KIVI 和 GEAR 从 97.0 暴跌至 30.0。

## 六、批判性分析

1. **评估框架选择偏差**：作者选择 LMDeploy 而非 vLLM 作为主要评估框架，理由是 vLLM 难以集成 KIVI（2024 年 4 月开的 issue 至今未解决）。这虽是现实约束，但 vLLM 作为最广泛使用的 serving 框架，缺少在其上的评估削弱了结论的实用性。

2. **压缩配置单一**：所有压缩方法均使用固定的压缩比（如 cache size 512），未系统性探索压缩比与各维度指标的 Pareto 前沿。不同压缩比下的最优方法可能完全不同。

3. **负样本分析缺乏根因解释**：论文发现代码补全任务退化最严重，但未深入分析为什么——是因为代码 token 分布更均匀导致 attention score 区分度低，还是量化误差在特定 token pattern 下被放大？缺少这种分析使得 "发现" 停留在现象描述层面。

4. **响应变长的因果机制未阐明**：论文只是观察到压缩后响应变长，但未解释这一现象的内在原因。是因为信息丢失导致模型 "犹豫" 生成更多 token 来弥补，还是 EOS token 的概率被系统性压低？如果是后者，可能有更简单的缓解方案。

5. **工具实用性存疑**：Throughput Predictor 和 Length Predictor 的训练数据来自特定模型和硬件配置（A6000 + LMDeploy），在不同 GPU、不同框架、不同模型上的泛化性未验证。Request Router 的 4-GPU 设置（1 FP16 + 3 压缩）也是一个相当人为的场景。

6. **Survey 部分的时效性问题**：Table 1 涵盖了截至 2024 年 10 月的方法，但 KV cache 压缩领域发展极快，论文发表时很多新方法（如基于 sliding window + quantization 的混合方案）已经出现，Survey 的参考价值在持续下降。

## 七、AI Infra / MLSys 视角

**启发与借鉴**：

1. **系统-算法协同设计的必要性**：这篇论文最核心的贡献不是某个具体算法，而是揭示了算法研究与系统实现之间的巨大鸿沟。KV cache 压缩算法在 TRL 上的 speedup 到了 LMDeploy 上可能完全消失——这对 AI Infra 研究者是一个警示：评估 serving 优化时必须在生产级框架上进行。

2. **响应长度感知的 serving 系统**：论文发现的 "压缩导致响应变长" 现象对 serving 系统设计有重要启示。现有的 serving 系统（vLLM、TensorRT-LLM）在做 scheduling 时主要考虑 prefill 和 KV cache 内存，而忽略了压缩策略对输出分布的影响。一个有价值的研究方向是设计 length-aware scheduler，将预测的输出长度纳入调度决策。

3. **Per-request 自适应压缩**：论文的负样本分析表明不同任务类型对压缩的容忍度差异极大。这暗示了一个重要的系统优化机会：根据请求的任务类型（可用轻量级分类器识别）动态选择压缩策略或压缩比，而非全局使用统一配置。

**可操作的研究方向**：

- **压缩感知的 FlashAttention kernel**：当前 FlashAttention 不保存 attention scores，导致稀疏方法需要额外 pass。设计一个在 one-pass 内同时输出 attention output 和 top-k token importance 的 fused kernel 是一个有价值的系统优化。
- **KV cache 压缩 + speculative decoding 联合优化**：压缩节省的内存可以用于运行 draft model 或存储更多 speculative tokens，但两者的交互尚未被研究。
- **基于 EOS 概率校准的长度控制**：如果压缩导致 EOS 概率系统性下降，可以在 decoding 时对 EOS logit 进行校准补偿。

---

## 八、总结

本文从生产部署的实际视角重新审视了 KV cache 压缩技术，揭示了三个被现有研究忽视的关键问题：生产级框架上的吞吐量收益缩水、压缩导致的响应变长、以及特定任务类型的质量崩溃。论文提供的 throughput predictor、length predictor 和 negative sample benchmark 为未来研究提供了更完善的评估工具。主要局限在于评估配置较为单一、根因分析不够深入、以及工具的跨配置泛化性未经验证。对于 AI Infra 从业者而言，最重要的 takeaway 是：KV cache 压缩算法的部署决策不能仅看内存缩减和整体准确率，必须在生产框架上做端到端评估，并关注压缩对输出分布的系统性影响。
