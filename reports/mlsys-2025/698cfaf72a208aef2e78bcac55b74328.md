## 1. 研究背景与动机

LLM 推理的内存需求（模型权重 + KV Cache）往往超出单 GPU 的显存容量。现有的基于 offloading 的 LLM 推理方案（如 FlexGen、DeepSpeed-ZeRO）将模型权重和 KV Cache 存储在 CPU 内存，通过 PCIe 逐层传输到 GPU 进行计算。然而，这种方案存在严重的 I/O 瓶颈：

- FlexGen 中，PCIe 数据传输占 OPT-66B 和 LLaMA2-70B 执行时间的 91-98%
- 即使尝试将传输与计算重叠，PCIe 带宽限制仍然导致大量空闲 GPU 时间

与此同时，现代 CPU（如 Intel Sapphire Rapids）配备了专用 GEMM 加速单元（AMX），在 BF16/INT8 精度下计算能力显著提升。FlexInfer 的核心洞察是：对于 Decoding 阶段这种内存密集型任务，CPU 计算（无需 PCIe 传输）可能比 GPU offloading 更快。

## 2. 研究问题与核心挑战

### 2.1 Prefill 和 Decoding 阶段的计算特征差异

- **Prefill 阶段**：计算密集，GPU 高算力优势明显；CPU 计算即使有 AMX 加速，在长输入时仍比 GPU 慢 1.3-10×（取决于批次大小）。
- **Decoding 阶段**：内存密集，KV Cache 传输成为瓶颈；CPU 计算因无需 PCIe 传输，TPOT 比 GPU Offloading 低 30-70%（SPR CPU with AMX）。

这意味着：**Prefill 适合 GPU + Offloading，Decoding 适合 CPU-only**。

### 2.2 静态策略的局限性

现有方法使用固定策略处理两个阶段：
- FlexGen：整个过程使用 GPU + Offloading，Decoding 的 TPOT 很高
- CPU-only：Prefill 阶段性能差
- SplitGen（静态切分）：Prefill/Decoding 使用相同策略，无法适应不同场景

### 2.3 动态策略选择的需求

最优策略取决于多个因素：
- 输入序列长度
- 输出序列长度
- 批次大小
- CPU/GPU 计算吞吐量和内存带宽
- PCIe 带宽

## 3. 主要贡献

1. **Phase-aware 执行策略**：为 Prefill 和 Decoding 阶段分别选择最优执行策略（CPU-only、GPU + Offloading、SplitGen）。
2. **性能估算器**：基于硬件配置和运行时参数（序列长度、批次大小），预测每种策略的 TTFT 和 TPOT，选择最优策略。
3. **执行规划器**：结合理论模型和离线 profiling 数据（效率因子），估算各策略性能，动态选择。
4. **推理执行器**：管理 CPU/GPU 工作分配和数据传输，支持不同阶段使用不同策略。

## 4. 核心方法与设计

### 4.1 三种执行策略

**CPU-only**：所有计算在 CPU 上执行，模型权重、激活和 KV Cache 全部驻留在 CPU 内存。适合 Decoding 阶段和超大模型（超出 GPU 内存）的 Prefill。

**GPU + Offloading（FlexGen 风格）**：模型权重和 KV Cache 存储在 CPU，通过 PCIe 传输到 GPU，与 GPU 计算重叠。适合计算密集的 Prefill 阶段。

**SplitGen（静态切分）**：模型前 N-M 层在 CPU 执行，后 M 层在 GPU 执行。Prefill 阶段：CPU 计算与 GPU 权重加载重叠；Decoding 阶段：CPU 层执行完后只传输最终输出到 GPU，无需每层传输。

### 4.2 性能估算模型

TTFT 估算：
- CPU-only: $TTFT = (C_{Prefill} + D_{Prefill}) / (TH_{CPU} \cdot Eff_{CPUComp} + BW_{CPU} \cdot Eff_{CPUMem})$
- GPU Offloading: $TTFT = \max(C_{Prefill}/(TH_{GPU} \cdot Eff_{GPUComp}), D_{Prefill}/(BW_{GPU} \cdot Eff_{GPUMem} + BW_{ICN} \cdot Eff_{ICN}))$
- SplitGen: $TTFT = \max(C_{Prefill}/(TH_{GPU} \cdot Eff_{GPUComp}), D_{Prefill}/(BW_{GPU} \cdot Eff_{GPUMem})) + t_{transfer}$

引入效率因子 $Eff_{Device}$ 来桥接理论性能与实际硬件性能差距。

### 4.3 成本模型自适应

使用运行时统计数据（实际延迟 vs. 预测延迟的比例）调整缩放比例：
$$\gamma = \alpha \cdot \gamma_0 + (1-\alpha) \cdot \gamma_{prev}$$
$$C_{p/d} = \gamma \cdot C_{p/d}^0$$

利用 Serving 过程的连续性（KV Cache 长度变化趋势），线性调整成本模型。

### 4.4 实现

基于 HuggingFace 扩展，支持三种执行策略和不同阶段使用不同策略。CPU 计算使用 IPEX（Intel Extension for PyTorch）优化内核。

## 5. 实验设置

**两套服务器配置**：
- **Server 1**：2× Xeon 8352Y（Ice Lake，无 AMX）+ NVIDIA A100 40GB + PCIe 4.0（32 GB/s）
- **Server 2**：2× Xeon 6454S（Sapphire Rapids，有 AMX）+ NVIDIA H100 80GB + PCIe 5.0（64 GB/s）

**模型**：OPT-30B/66B、LLaMA2-70B、LLaMA3-70B

**指标**：End-to-End Latency、TTFT、TPOT

## 6. 实验结果

### 6.1 端到端延迟

**Server 1**：
- FlexInfer 相比 FlexGen：平均降低 75% 延迟
- FlexInfer 相比 CPU-only（SPR）：降低 25-56%

**Server 2**：
- FlexInfer 相比 FlexGen：平均降低 76% 延迟
- FlexInfer 相比 CPU-only（SPR）：降低 18-70%（取决于批次大小）

### 6.2 TTFT 和 TPOT 分解

对于 OPT-66B（Server 2）：
- TTFT：FlexInfer 比 FlexGen 降低 6.6%（SPR CPU 配合 GPU Offloading 适合 Prefill）
- TPOT：FlexInfer 比 FlexGen 降低 49.1%（CPU-only 适合 Decoding）

### 6.3 输入序列长度的影响

输入长度从 128 增加到 1024 时：
- CPU-only 和 SplitGen 性能显著下降（Prefill 计算量增加，CPU 劣势更明显）
- FlexInfer 在所有输入长度下保持最低延迟（动态选择 Prefill 用 GPU Offloading）

### 6.4 输出序列长度的影响

输出长度从 128 增加到 1024 时：
- FlexGen 和 FlexGen_Opt 延迟线性增长（Decoding 每步都需 PCIe 传输）
- CPU-only 和 SplitGen 延迟增长较慢（Decoding 无 PCIe 开销）
- FlexInfer 在所有输出长度下保持最优

### 6.5 PCIe 流量分析

FlexInfer 根据阶段动态选择策略，Prefill 阶段使用 GPU Offloading 传输必要数据，Decoding 阶段使用 CPU-only 避免 PCIe 传输，总流量显著低于 FlexGen。

## 7. 潜在问题与局限性

1. **仅支持 LLaMA 系列模型**：论文明确指出当前仅支持 LLaMA 架构，对其他模型（Mixtral、Qwen 等 MoE 或非 LLaMA 架构）的支持需要额外适配工作。
2. **未考虑 KV Cache 量化**：FlexInfer 假设 KV Cache 以 FP16 存储和传输，与 KV Cache 量化技术（QServe、KIVI 等）结合的潜在收益未探索。
3. **CPU-GPU 协同开销被低估**：在切换执行策略时（如 Prefill 结束切换到 Decoding），需要重新分配 KV Cache 和模型权重的内存布局，可能产生额外开销。
4. **通信重叠优化的实现复杂性**：SplitGen 策略需要在 CPU 和 GPU 之间精确协调执行顺序，实现难度较高。
5. **未与连续批处理集成**：论文未讨论 FlexInfer 在 continuous batching 场景下（多个请求混合 Prefill/Decoding）的行为。

## 8. 未来工作

1. 扩展到更多模型架构（MoE、视觉语言模型等）
2. 结合 KV Cache 量化技术
3. 探索与连续批处理的集成
4. 研究动态切换策略在多请求混合场景下的行为

## 9. 个人评注

FlexInfer 是一项针对 CPU-GPU 异构 LLM 推理的系统优化工作，其核心价值在于揭示了一个常被忽视的事实：**Prefill 和 Decoding 阶段的计算特征差异，足以支撑使用完全不同的执行策略**。

论文的分析方法值得称赞：通过实验数据清晰展示了 GPU + Offloading 和 CPU-only 在两个阶段的优势分布。这不是显而易见的——传统观点认为 GPU 全面优于 CPU，CPU 参与推理只是权宜之计。FlexInfer 证明了在特定场景（Decoding 阶段、内存密集型任务）下，CPU 完全可以成为主角。

成本模型的设计体现了良好的工程直觉：结合理论模型和离线 profiling 的效率因子，利用 Serving 过程的连续性进行自适应调整。这种"模型预测 + 运行时反馈修正"的模式是自适应系统设计的经典范式。

然而，论文的局限性也值得注意：仅支持 LLaMA 架构，且未与主流 Serving 系统（vLLM、TensorRT-LLM）集成，使其实际部署价值打了折扣。此外，FlexInfer 的优化目标（CPU-GPU 协同）在当前 GPU 显存越来越大（H200 141GB）、KV Cache 量化技术日趋成熟的背景下，是否具有持续的场景价值，值得思考。

总体而言，这是一篇思路清晰、分析透彻的系统论文。对于在异构硬件环境（如 CPU-GPU 混合集群、边缘设备）上进行 LLM 推理的实践者，FlexInfer 提供了有价值的分析框架和设计参考。
