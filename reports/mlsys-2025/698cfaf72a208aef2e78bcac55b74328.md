## 一、背景

LLM 推理面临严峻的显存容量挑战：GPT-175B 仅权重就需要 350GB（FP16），远超单卡 GPU 显存。KV cache 随序列长度和 batch size 增长进一步加剧内存压力（如 OPT-66B 在 seq=4096、batch=32 时 KV cache 达 288GB）。

Offloading 方案（FlexGen、DeepSpeed-ZeRO 等）将权重和 KV cache 存储在 CPU 内存中，通过 PCIe 逐层传输到 GPU 执行。但 PCIe 带宽有限，数据传输占总执行时间的 87%–98%，成为性能瓶颈。

与此同时，现代 CPU 开始配备专用矩阵乘法硬件（Intel AMX、IBM MMA、Arm SME），在特定场景下 CPU 推理已能与 GPU offloading 方案竞争甚至超越。但 CPU 计算吞吐量整体仍远低于 GPU，不能简单替代。

---

## 二、要解决的问题

1. **PCIe 传输瓶颈**：现有 offloading 方案中，即使 overlap 传输和计算，PCIe 数据传输仍占据绝大部分执行时间（96%–98%），GPU 算力严重浪费。
2. **CPU 算力浪费**：offloading 方案将所有计算放在 GPU 上，CPU 仅作为存储使用，其计算资源（尤其是 AMX 等加速硬件）完全闲置。
3. **固定策略无法适配多变场景**：prefill 阶段是 compute-bound，decode 阶段是 memory-bound，二者对 CPU/GPU 资源的需求截然不同。现有方案（FlexGen、HeteGen）对两个阶段使用相同策略，无法兼顾。不同的 batch size、序列长度、硬件配置（CPU 有无 AMX、PCIe 版本）都会改变最优策略，需要动态选择。

---

## 三、洞察与设计

**关键洞察**：LLM 推理的 prefill 和 decode 两个阶段具有截然不同的计算/内存特性——prefill 是 compute-intensive 的，GPU offloading 尽管有 PCIe 开销仍能受益于 GPU 高吞吐；decode 是 memory-bound 的，CPU 因为无需 PCIe 传输且拥有足够内存带宽，反而比 GPU offloading 更快（TPOT 低 60%–70%）。因此，对两个阶段分别选择不同的执行策略可以显著降低端到端延迟。

### 系统设计

FlexInfer 由两个核心组件构成：

**1. Execution Planner（执行规划器）**：基于分析模型预测 TTFT 和 TPOT，为 prefill 和 decode 阶段分别选择最优执行策略。输入包括：模型架构参数、运行时信息（序列长度、batch size）、硬件配置（CPU/GPU 吞吐、内存带宽、PCIe 带宽）。通过离线 profiling 获取效率校正因子弥补理论与实际性能差距。

三种候选策略：
- **CPU-only**：全部在 CPU 执行，无 PCIe 传输，适合 decode 阶段和小 batch。
- **GPU with Offloading（FlexGen）**：全部在 GPU 执行，overlap 传输与计算，适合 compute-intensive 的 prefill。
- **SplitGen（CPU-GPU 静态分区）**：前 N-M 层在 CPU 执行，最后 M 层常驻 GPU。在 decode 阶段可避免重复传输 M 层权重。

**2. Inference Executor（推理执行器）**：根据 Planner 选定的策略协调 CPU 与 GPU 的计算、数据传输与同步。支持两个阶段使用不同策略。

## 四、实现细节

- 基于 HuggingFace Transformers 库扩展，支持 prefill/decode 阶段使用不同执行策略。
- 修改 Intel Extension for PyTorch（IPEX）使其支持选择性地将部分层或操作（Attention、FFN）放到 GPU 执行（原版仅支持 CPU）。
- CPU-GPU 通信使用独立 CUDA stream 实现传输与计算的 overlap。
- CPU 端使用 IPEX 优化的 kernel（AMX 或 AVX-512）。
- 性能估算模型使用解析公式（Equation 1-3），分别建模 CPU-only、GPU offloading、SplitGen 三种策略的 TTFT 和 TPOT，包含效率校正因子。
- 目前支持 LLaMA（2/3）和 OPT 模型家族，可扩展到其他 HuggingFace 兼容模型。

## 五、实验结果

**硬件平台**：

| 配置 | Server 1 | Server 2 |
|------|----------|----------|
| CPU | 2× Xeon 8352Y (ICL, 无 AMX) | 2× Xeon 6454S (SPR, 有 AMX) |
| GPU | NVIDIA A100 40GB | NVIDIA H100 80GB |
| CPU 算力 (BF16) | 9.0 TFLOPS | 144.2 TFLOPS |
| CPU 内存 | 256GB | 512GB |
| PCIe | 4.0, 32GB/s | 5.0, 64GB/s |

**模型**：OPT-30B、OPT-66B、LLaMA2-70B、LLaMA3-70B

**主要结果**：

| 指标 | Server 1 | Server 2 |
|------|----------|----------|
| E2E latency 降低（vs FlexGen，平均） | 75% | 76% |
| TPOT 降低（vs FlexGen） | 77.7% | 79.6% |
| 变 input length 时 E2E 降低 | 72.9% | 70.2% |
| 变 output length 时 E2E 降低 | 73.3% | 70.5% |

- TTFT 方面：Server 2 降低 6.6%，Server 1 与 FlexGen 持平（ICL CPU 算力不足，prefill 阶段仍选 GPU offloading）。
- FlexGen_Opt（利用 GPU 显存缓存部分权重）降低 23%/50%，SplitGen 降低 37%/61.7%，均不及 FlexInfer。
- PCIe 流量分析：FlexInfer 在 prefill 使用 FlexGen、decode 使用 SplitGen/CPU-only，decode 阶段 PCIe 流量接近零。

## 六、批判性分析

1. **基线过于陈旧**：主要对比的是 FlexGen（2023），属于较早的 offloading 方案。未与 PowerInfer、HeteGen 进行直接端到端对比（仅在 related work 中定性讨论），也未与 llama.cpp 等广泛使用的 CPU 推理方案对比。75% 的提升数字因此需要 contextualize。

2. **模型和精度覆盖有限**：仅测试 OPT 和 LLaMA 家族，且全部使用 BF16。未涉及量化模型（INT8/INT4），而实际 offloading 场景中量化是标配，会显著改变 compute/memory tradeoff。

3. **场景受限**：固定 output length 为 32（主实验），仅在 Section 6.5 扩展到 1024。实际应用中输出长度往往远大于 32，decode 阶段占比更大，这恰好有利于 FlexInfer 的策略选择。但论文未充分探讨更大 batch size（>32）和更长序列（>1024）的情况。

4. **策略空间过于简单**：仅三种候选策略，且 SplitGen 的分区粒度是整层级别的静态分配。未探索更细粒度的算子级别分区（如 attention 在 GPU、FFN 在 CPU），也未考虑动态负载均衡。

5. **估算模型精度未充分验证**：论文声称使用分析模型预测性能并选择最优策略，但未报告估算模型的预测精度（predicted vs actual latency 的误差）。效率校正因子通过离线 profiling 获取，但未说明 profiling 的 overhead 和泛化性。

6. **缺乏 serving 场景评估**：所有实验都是 offline batch 推理（固定 batch size），未考虑 online serving 中请求动态到达、batch 变化的场景，而这才是 LLM 推理的典型部署模式。

## 七、AI Infra / MLSys 视角

1. **Phase-aware 执行策略的启发价值**：FlexInfer 的核心 insight——prefill 和 decode 应该用不同策略——与 disaggregated serving（Splitwise、DistServe）的思路一脉相承，但从异构计算（CPU+GPU）而非纯 GPU 集群的角度切入。这种思路可以推广到更多异构资源组合（如 GPU+NPU、不同代 GPU 混合）。

2. **CPU 算力在 AI Infra 中的潜力**：论文最有价值的实验数据是 SPR CPU（AMX）在 decode 阶段 TPOT 比 H100 offloading 低 60%–70%。这意味着在 decode-heavy 的长文本生成场景中，CPU 集群可能是成本效益更高的选择。值得探索的方向：将 CPU 专门用于 decode 的 disaggregated architecture。

3. **可操作的 future work**：
   - 将 FlexInfer 的策略选择与 continuous batching / chunked prefill 结合，支持在线 serving
   - 探索量化（INT8/INT4）对 CPU-GPU 策略选择的影响——量化后 compute 减少，可能改变 prefill 阶段的最优策略
   - 更细粒度的算子级分区：将 attention 的 QKV projection 放 CPU、attention score 放 GPU，或基于 layer importance 做异构分配
   - 扩展到多 GPU + CPU 的混合集群场景

4. **最有价值的切入点**：将 phase-aware 策略选择与 KV cache 量化/压缩结合——decode 阶段 CPU 执行的主要瓶颈是内存带宽，如果 KV cache 可以用 INT4/INT8 存储，CPU 的内存带宽优势会进一步放大。

---

## 八、总结

FlexInfer 提出了一种 phase-aware 的 CPU-GPU 混合 LLM 推理系统，核心创新在于为 prefill 和 decode 阶段分别选择最优执行策略（CPU-only / GPU offloading / CPU-GPU 静态分区），通过分析性能模型动态决策。在两种服务器配置上，相比 FlexGen 平均降低 75%–76% 的端到端延迟。该系统适用于 GPU 显存不足以装下完整模型的单卡场景，主要局限在于策略空间较简单、基线偏旧、缺乏在线 serving 评估，且未探索量化模型的影响。
