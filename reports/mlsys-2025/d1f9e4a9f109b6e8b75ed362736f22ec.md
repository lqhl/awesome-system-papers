# AIOpsLab: A Holistic Framework to Evaluate AI Agents for Enabling Autonomous Clouds

**作者**：Yinfang Chen (UIUC), Manish Shetty (UC Berkeley), Gagan Somashekar (Microsoft), Minghua Ma (Microsoft), Yogesh Simmhan (IISc), Jonathan Mace (Microsoft), Chetan Bansal (Microsoft), Rujia Wang (Microsoft), Saravan Rajmohan (Microsoft)

## 一、背景

随着企业越来越依赖超大规模云系统，微服务架构和 serverless 计算带来了可扩展性，但也引入了巨大的运维复杂性。云故障可能级联扩散，导致大规模宕机（如 Amazon 一小时损失 1 亿美元）。AIOps（AI for IT Operations）旨在自动化故障检测、定位、根因分析和修复等运维任务，减少人工干预。近年来，LLM agent 的进展使端到端自动化运维成为可能，催生了 **AgentOps**（Agent for Operations）这一新范式——让 AI agent 自主管理整个 incident 生命周期，实现"自愈云"。

然而，虽然 Dev 侧已有 SWE-bench、WebArena 等成熟的 agent 评测框架，Ops 侧缺乏高质量的、面向真实云环境的交互式 benchmark，制约了 AIOps agent 的发展与评估。

---

## 二、要解决的问题

1. **缺乏端到端评测框架**：现有工具（故障注入、可观测性、混沌工程）各自孤立，没有统一的框架将部署、故障注入、负载生成、遥测收集和 agent 评估串联起来。
2. **评估场景不够真实**：现有 AIOps benchmark 多依赖静态数据集（时间序列指标、固定 Q&A 格式），无法捕捉真实云环境的动态性和不可预测性。
3. **任务覆盖不全**：现有方法多聚焦于 incident 生命周期的单个阶段（如异常检测或故障定位），缺少跨检测→定位→根因分析→修复的完整评估链。
4. **Agent-Cloud 交互接口缺失**：云环境的现有接口（API、CLI、Dashboard）并非为 LLM agent 设计，信息过载或格式不友好会影响 agent 性能。
5. **功能性故障评估缺位**：大多数故障注入工具只注入"症状型故障"（如网络丢包、Pod 崩溃），无法模拟配置错误、软件 bug 等有真实根因的"功能型故障"。

---

## 三、洞察与设计

**关键洞察**：要真正评估 AIOps agent 的端到端能力，必须在活的云环境中构建交互式评测——agent 需要像真实运维人员一样，通过查询日志/指标/链路追踪、执行 shell 命令等动作与云系统动态交互，而非在静态数据集上做离线推理。同时，评估场景需要包含具有真实根因的功能性故障（而非仅症状注入），才能检验 agent 的诊断和修复能力。

基于此洞察，AIOpsLab 的核心设计包括：

1. **Problem 形式化定义**：每个问题 P = ⟨T, C, S⟩，其中 T 是任务（检测/定位/RCA/修复），C 是上下文（环境 + 问题描述），S 是预期解。构建了 4 级任务分类体系。

2. **Orchestrator 编排器**：核心组件，负责：
   - 部署云服务（通过 Helm + Kubernetes）
   - 注入故障（通过故障库）
   - 生成负载
   - 管理 agent-cloud 交互的会话生命周期
   - 执行评估

3. **Agent-Cloud Interface (ACI)**：为 agent 提供统一、简洁的 API 接口（`get_logs`、`get_metrics`、`get_traces`、`exec_shell` 等），抽象底层云环境复杂性。agent 只需实现一个 `get_action(state) -> str` 方法即可接入。

4. **双类型故障库**：
   - **症状型故障**：网络丢包、Pod 失败等（通过 ChaosMesh 注入），用于 Level 1-2 任务
   - **功能型故障**：认证撤销、端口误配、节点错误分配等有真实根因的故障，支持 Level 1-4 全链路评估

5. **可观测性层**：集成 Prometheus（指标）、Jaeger（链路追踪）、Filebeat+Logstash（日志），支持在线和离线评估。

---

## 四、实现细节

- **云服务**：集成 DeathStarBench 的 SocialNetwork（28 个微服务）和 HotelReservation、OpenTelemetry Astronomy Shop Demo、TiDB Operator 等多种应用。
- **故障库**：15 种故障类型，涵盖功能型（认证缺失、端口误配、权限撤销、用户注销、buggy 镜像、错误缩容、节点错误分配、PV 重部署、错误二进制、Operator 过载、服务不可达）和症状型（网络丢包、Pod 失败、容器 kill）。
- **问题池**：100 个问题，评估中选取 48 个代表性问题，覆盖 4 个任务级别。
- **Agent 注册**：轻量级——41-60 行代码即可接入一个 agent。
- **评估指标**：正确性（Accuracy）、时间（TTD/TTM）、步数、token 消耗。支持 LLM-as-Judge 评估推理质量。
- **负载生成**：适配各应用自带的负载工具（wrk2、Locust）。

## 五、实验结果

评估了 4 种 LLM agent：GPT-4-W-SHELL、GPT-3.5-W-SHELL、ReAct、FLASH。

### 总体性能

| Agent | LoC | 平均时间(s) | 平均步数 | 平均 Tokens | 准确率 |
|-------|-----|------------|---------|------------|--------|
| GPT-4-W-SHELL | 41 | 28.61 | 6.44 | 6,394 | 49.15% |
| GPT-3.5-W-SHELL | 41 | 12.44 | 14.70 | 2,558 | 15.25% |
| ReAct | 49 | 43.79 | 11.50 | 16,941 | 55.93% |
| FLASH | 60 | 99.64 | 8.48 | 6,484 | **59.32%** |

### 各任务性能

| 任务 | GPT-4 | GPT-3.5 | ReAct | FLASH |
|------|-------|---------|-------|-------|
| Detection | 69.23% | 23.07% | 76.92% | **100%** |
| Localization @1 | **61.54%** | 30.77% | 53.85% | 46.15% |
| Localization @3 | 61.54% | 30.77% | **69.23%** | 61.54% |
| RCA | 40.90% | 9.09% | **45.45%** | 36.36% |
| Mitigation | 27.27% | 0% | 36.36% | **54.55%** |

### 关键发现

- FLASH 在检测任务上 100% 准确，整体最优，但在 RCA 和定位上不如 ReAct。
- 更多 token 不等于更好性能（ReAct 消耗 16K+ tokens 但仅略优于 FLASH 的 6K）。
- 步数限制影响显著：FLASH 和 ReAct 随步数增加而提升，但 GPT-3.5 在 5 步后饱和。
- 传统非 LLM 方法（MKSMC、RMLAD、PDiagnose）在检测和定位任务上均大幅落后于 LLM agent。

## 六、批判性分析

1. **评测规模有限**：总共 100 个问题，实际只评估了 48 个"代表性"问题，且每个 agent 只跑一次（无重复实验报告）。对于涉及 LLM 的 stochastic 系统，缺少方差/置信区间分析，结果的统计显著性存疑。

2. **Agent 选择和公平性**：FLASH 是作者团队的工作，"由于未公开，我们开发了简化版本"——这意味着评测中的 FLASH 并非原版实现，对比基线的公平性打了折扣。GPT-3.5 和 GPT-4 仅用最朴素的 shell wrapper 接入，没有做任何 prompt engineering 或工具调用优化，这种"naïve baseline"设置使得 LLM 能力被严重低估。

3. **功能型故障的"根因"过于简单**：15 种故障虽然名义上覆盖功能型，但大多数是单点、确定性的配置错误（端口改错、认证撤销等），与真实生产环境中涉及多服务级联、时序相关、间歇性的复杂故障相去甚远。

4. **检测任务过度简化**：检测任务被定义为"是否有故障"的二分类，与真实场景中从海量告警中识别异常的难度不可同日而语。论文自己也承认了这一点，但并未提供更复杂的评测变体。

5. **Noop 问题暴露的假阳性**：只有 GPT-4 在无故障场景下正确判断"无异常"，其他 3 个 agent 都报假阳性。但论文只设置了 2 个 noop 问题，样本量太小，无法系统性评估 agent 的假阳性率。

6. **缺乏与真实 incident 数据的对比**：论文没有验证 AIOpsLab 构造的评测场景与真实生产 incident 的分布和难度是否对齐。微软作为作者单位，拥有大量真实 incident 数据，但论文未利用这些数据做 validation。

7. **可观测性数据的处理问题**：论文发现 agent 在使用 metrics 和 traces 时容易被信息过载干扰，但 AIOpsLab 框架本身并未提供数据预处理或摘要机制，而是将问题留给了未来工作。

## 七、AI Infra / MLSys 视角

1. **Agent 评测方法论的借鉴**：AIOpsLab 的 Problem = ⟨Task, Context, Solution⟩ 形式化和 4 级任务分类体系，可以迁移到 AI Infra 领域的 agent 评测。例如，评估 LLM agent 在分布式训练故障诊断（GPU 故障检测→定位→根因→自动恢复）中的能力，可以复用类似的框架设计。

2. **ACI 设计思路对 MLOps 的启发**：为 agent 设计简洁、结构化的云交互接口而非暴露原始 CLI，这一思路可应用于训练/推理集群管理。例如，为训练任务调度 agent 设计 `get_gpu_utilization`、`get_training_metrics`、`get_nccl_logs` 等专用 API。

3. **可操作的研究方向**：
   - **训练集群自愈**：构建类似 AIOpsLab 的框架，专门评估 agent 在 GPU 集群环境中的故障处理能力（checkpointing 失败、NCCL timeout、OOM、stragglers）
   - **遥测数据摘要**：论文暴露了 agent 处理原始 metrics/traces 时的信息过载问题。开发面向 LLM 的遥测数据压缩/摘要方法（如将 Prometheus 指标自动转化为自然语言摘要）是一个有价值的方向
   - **推理系统运维自动化**：将 AIOpsLab 的思路应用于推理服务（如 vLLM、TGI）的自动运维评测——SLO 违规检测、KV cache 异常、batch scheduling 问题的自动诊断

4. **最有价值的切入点**：基于 AIOpsLab 的框架设计，针对 GPU 训练集群构建专用的故障注入和评测 benchmark。真实训练场景中的故障模式（硬件故障、通信超时、梯度异常、资源争抢）与通用云微服务故障差异很大，需要专门的故障库和评估指标。

---

## 八、总结

AIOpsLab 提出了首个面向 AIOps agent 的端到端交互式评测框架，通过 Orchestrator 编排云部署、故障注入、负载生成和遥测收集，并通过 Agent-Cloud Interface 为 agent 提供标准化交互接口。框架构建了包含 100 个问题的 benchmark，覆盖检测、定位、根因分析和修复 4 个任务级别。实验表明当前最优 agent（FLASH）整体准确率仅 59.32%，表明自主云运维仍有很大提升空间。框架的主要局限在于评测规模较小、故障类型仍偏简单、检测任务过度简化，但其整体架构设计和 Problem 形式化为后续 AIOps agent 研究提供了有价值的基础设施。
