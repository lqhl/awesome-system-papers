# RDMA Point-to-Point Communication for LLM Systems

**作者**：Nandor Licker, Kevin Hu, Vladimir Zaytsev, Lequn Chen（Perplexity AI）
**会议**：arXiv preprint, 2025年10月
**链接**：https://arxiv.org/abs/2510.27656
**源文件**：[2510.27656v1.pdf](../../papers/ai-infra/2510.27656v1.pdf)

---

## 一、背景

大语言模型（LLM）的系统架构正在经历根本性的转变：disaggregated inference（prefill 与 decode 分离）、Mixture-of-Experts（MoE）路由、异步强化学习微调等新范式正在成为主流。这些新范式的共同特点是需要灵活的点对点（P2P）通信，而非传统的 collective 通信。

传统 LLM 框架几乎完全依赖 NCCL 或 torch.distributed 等 collective 通信库。这些库擅长静态通信模式（如 tensor parallelism、data parallelism），但对新兴工作负载有根本性限制：固定成员关系阻碍动态扩缩容、同步初始化带来额外开销、统一 buffer 大小迫使稀疏模式也使用 dense 通信。

与此同时，RDMA 技术本身已经成熟（400 Gbps、亚微秒级延迟），但不同云厂商部署了不同的 RDMA 实现：NVIDIA ConnectX 使用传统的 Reliable Connection（RC）传输并保证有序交付，而 AWS Elastic Fabric Adapter（EFA）实现了专有的 Scalable Reliable Datagram（SRD）协议，提供可靠但无序的交付。这种硬件异构性导致了严重的厂商锁定问题。

---

## 二、要解决的问题

1. **厂商锁定**：现有的高性能 P2P 通信方案绑定特定硬件。DeepEP 依赖 NVIDIA 独有的 IBGDA（GPU-initiated RDMA），仅支持 ConnectX；NVSHMEM 在 EFA 上性能严重退化；Mooncake 和 NIXL 缺乏 EFA 支持或仍处于早期阶段。没有跨云厂商的可行方案。

2. **Collective 通信的局限性**：对于 disaggregated inference、MoE routing、RL weight sync 等场景，collective 通信存在四大限制——固定成员关系、同步初始化、操作顺序约束、传输大小统一。

3. **硬件抽象缺失**：ConnectX RC 保证有序交付，EFA SRD 本质上无序。两种硬件的编程模型差异巨大，缺乏统一的高性能抽象层。

4. **RL 权重同步慢**：现有框架通常通过 Rank0 汇集再广播，瓶颈在单个 NIC 上，万亿参数模型的权重更新需要数十到数百秒。

---

## 三、洞察与设计

**关键洞察**：ConnectX RC 和 EFA SRD 虽然编程接口不同，但都支持可靠但无序的交付——ConnectX RC 可以忽略排序保证，而 EFA SRD 本身就是无序的。因此，可以以"可靠无序交付"作为最大公约数，构建跨硬件的统一抽象。

基于这一洞察，作者设计了 **TransferEngine**，一个可移植的 RDMA P2P 通信库，核心设计包括：

- **统一接口**：暴露 SEND/RECV（两端参与）和 WRITEIMM（单端操作）两类原语，不依赖消息顺序保证
- **IMMCOUNTER 原语**：一种新的完成通知机制。每个 WRITE 可携带 32 位 immediate value，接收端通过计数器累加来判断完成状态，无需依赖消息排序
- **透明多 NIC 管理**：自动检测拓扑并将请求分片到多个 NIC（EFA 上需要聚合 4 个 100 Gbps NIC 达到 400 Gbps）
- **每 GPU 一个 worker 线程**：线程绑定到对应 NUMA 节点的 CPU 核心，所有数据结构分配在正确的 NUMA 节点上
- **零拷贝与 WR 模板化**：预填充 libfabric/libibverbs 描述符公共字段，减少提交开销

TransferEngine 用 Rust 实现，通过三个生产系统展示其能力：KvCache 传输、RL 权重更新、MoE dispatch/combine。

## 四、实现细节

### TransferEngine 架构

- 每个 GPU 对应一个 DOMAINGROUP，内含 1-4 个 DOMAIN（每个管理一个 NIC）
- Worker 线程在紧密循环中：提交新请求 → 推进 pending 请求 → 轮询 completion queue
- 跨线程通信使用 lock-free queue
- 回调由专用线程处理，避免阻塞 worker

### 硬件特化优化

- **EFA**：使用 libfabric，强制所有传输包含有效目标描述符（EFA 要求），WR 模板化
- **ConnectX-7**：使用 libibverbs，每对 peer 建立 2 个 RC QP（SEND/RECV 和 WRITEIMM 分离），WR chaining（最多 4 个 WR 链接减少 doorbell ring），启用 `IBV_ACCESS_RELAXED_ORDERING` 允许乱序 PCIe 事务

### KvCache 传输

- 全局调度器选择 prefiller 和 decoder 节点
- Decoder 预分配 KV pages，通过 SEND 通知 prefiller 页面索引
- Prefiller 在每层 attention output projection 后通过 UVM watcher（CUDA Graph 兼容）触发逐层传输
- 支持 MLA（replicated KV cache）和 GQA（page-wise offsets/strides 切片）
- 完成通知通过 IMMCOUNTER，无需显式完成消息

### RL 权重更新

- 每个 training GPU 通过 one-sided RDMA WRITE 直接写入 inference GPU，利用全集群带宽
- Controller 在初始化时计算静态传输调度表
- 四阶段流水线：H2D memcpy → full_tensor() + 融合 + 量化 → RDMA 传输 → 全局 barrier
- 内存水位线控制防止 OOM

### MoE Dispatch/Combine

- 使用 host proxy thread 协调 GPU 和 NIC（而非 IBGDA）
- 分为 split kernel：sender half 准备数据，receiver half 重排 token
- 两阶段 dispatch：先用 private buffer 投机发送少量 token（隐藏路由信息交换延迟），再根据路由信息将剩余 token scatter 到 contiguous receive buffer
- NVLink 用于节点内传输，与 RDMA 并行
- 内存屏障顺序优化：先 signal host，再发 NVLink write（避免 NVLink write 拖慢 barrier）

## 五、实验结果

**硬件平台**：8×NVIDIA H200 GPU + NVLink，每 GPU 配 1 个 400 Gbps ConnectX-7 或 2 个 200 Gbps EFA NIC，双路 Intel Sapphire Rapids CPU。

### P2P 通信吞吐

| 操作类型 | 消息大小 | EFA | ConnectX-7 |
|---------|---------|-----|-----------|
| Single WRITE | 64 KiB | 16 Gbps | 44 Gbps |
| Single WRITE | 1 MiB | 145 Gbps | 245 Gbps |
| Single WRITE | 32 MiB | 336 Gbps | 378 Gbps |
| Paged WRITE | 1 KiB | 17 Gbps (2.11M op/s) | 91 Gbps (11.10M op/s) |
| Paged WRITE | 64 KiB | 364 Gbps (0.69M op/s) | 370 Gbps (0.71M op/s) |

与 NIXL v0.6.1 性能接近，TransferEngine 略优。

### MoE Decode 延迟（EP=64, 128 tokens/rank）

| 方案 | Dispatch (us) | Combine (us) |
|------|-------------|-------------|
| Ours-EFA-SRD | 286 | 406 |
| Ours-CX7-RC | 190 | 311 |
| DeepEP-CX7-GDA | 180 | 327 |
| pplx-CX7-GDA | 317 | 530 |
| pplx-CX7-RC | 1669 | 1058 |

在 ConnectX-7 上，16/32 rank 时 TransferEngine 全面优于 DeepEP；64 rank 时 combine 仍优于 DeepEP，但 dispatch 因 proxy 开销略慢。EFA 延迟仅比 ConnectX-7 高约 30%，这是首个在 EFA 上可用的 MoE routing 实现。

### RL 权重更新

万亿参数模型（Kimi-K2 规模）从 256 个训练 GPU（bf16）到 128 个推理 GPU（fp8）仅需 **1.3 秒**，比现有 RL 框架快 100× 以上。

### MoE Prefill 延迟

DeepEP 在 prefill 场景通过 NVLink 预聚合 token 减少 RDMA 数据量，combine 阶段通过 sender-side partial sum 降低 RDMA 字节数（但精度降为 bf16），因此在大多数配置下 prefill 性能更好。TransferEngine 的 decode-optimized kernel 在 prefill 场景内存开销较大。

## 六、批判性分析

1. **Prefill 场景竞争力不足**：论文承认在 prefill 场景直接复用 decode kernel "without tweaks"，导致内存开销大、性能不如 DeepEP。这不仅仅是"未优化"的问题——DeepEP 的 sender-side partial sum 是一个架构级优势，不是简单调优能弥补的。论文将此轻描淡写为 "accuracy and determinism" 的 trade-off，但实际上 bf16 accumulation 在大多数生产场景中是可接受的。

2. **Host proxy 的可扩展性隐患**：EP=64 时 dispatch 已经出现 proxy 线程成为瓶颈的迹象（每个 inter-node peer 需要一次 scatter enqueue，56 个 peer 的排队开销约为微秒级）。随着 EP 进一步增大（如 EP=128 或 EP=256），这个开销会线性增长。论文未讨论这一扩展性问题。

3. **RL 权重更新的 100× 比较不公平**：1.3 秒 vs "tens to hundreds of seconds" 的 100× 加速引用的 baseline 是 NeMo-RL 的 blog post 和 Slime 的 blog post，而非正式发表的学术工作或公平的 apple-to-apple 比较。那些框架可能使用了完全不同的集群规模、网络拓扑和参数量。论文没有提供受控实验。

4. **仅单一集群拓扑评测**：所有实验在 H200 + NVLink + 双路 Sapphire Rapids 上完成。未验证在其他拓扑（如 PCIe-only、不同 NVLink 版本、不同 CPU 架构）上的表现。TransferEngine 的 NUMA 亲和、线程绑定等优化高度依赖特定拓扑。

5. **缺少端到端推理性能数据**：所有 benchmark 都是微基准测试（单独的 dispatch/combine 延迟、单独的 KvCache 传输吞吐）。没有展示在完整推理 pipeline 中的端到端延迟或吞吐改善。特别是 disaggregated inference 场景，KvCache 传输只是其中一环，整体 TTFT 和 TPS 的改善未知。

6. **EFA 上的性能差距被淡化**：虽然论文强调"首个可用的 EFA 实现"，但 EFA 在 256 KiB 单次 WRITE 时只有 54 Gbps（ConnectX-7 的 46%），MoE decode 延迟高约 30-50%。这对于延迟敏感的 decode 场景是否真正"可用"值得商榷。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **"可靠无序交付"作为跨硬件抽象的最大公约数**：这一洞察非常有价值。在 AI Infra 中，我们经常面临硬件异构性问题（不同 GPU、不同互联、不同云厂商）。寻找不同硬件的"功能交集"而非"功能并集"来构建抽象层，是一种实用的设计哲学。

2. **Host proxy 的可行性**：DeepEP 等方案认为 IBGDA（GPU-initiated RDMA）是低延迟 MoE routing 的必要条件。本文证明了即使使用 host proxy（需要额外的 GPU→PCIe→CPU→NIC 往返），通过仔细的流水线设计和 NVLink/RDMA 并行，仍然可以达到甚至超过 IBGDA 的性能。这打开了一个重要的设计空间——不是所有场景都需要最极致的硬件特化。

3. **IMMCOUNTER 作为无序环境下的同步原语**：这个设计可以推广到其他需要在无序网络上实现 barrier 或 completion notification 的场景，例如分布式 KV store、参数服务器等。

### 值得跟进的方向

1. **Prefill 场景的优化**：当前 kernel 是 decode-optimized，prefill 场景直接复用导致内存开销大。设计专门的 prefill kernel（支持 chunked transfer、sender-side partial sum）是一个明确的工程方向。

2. **与 collective 通信的自适应切换**：论文将 P2P 和 collective 定位为互补关系，但未探讨何时应该使用哪种。在实际 LLM 推理中，不同阶段（attention、MoE、TP all-reduce）的最优通信策略可能不同。构建一个统一的通信调度器是有价值的研究问题。

3. **跨云多 NIC 聚合的泛化**：TransferEngine 对 EFA 的 4-NIC 聚合策略可以泛化到更多异构网络场景，如混合使用不同代际/厂商的 NIC。

4. **EP 扩展到 128+ 时的 proxy 优化**：通过 batch submission、multi-threaded proxy、或 hybrid GPU-initiated/host-proxy 方案解决 EP=64+ 时的 proxy 瓶颈。

### 最有价值的切入点

如果要基于本文做延伸工作，最有价值的方向是**将 TransferEngine 集成到主流推理引擎（vLLM/SGLang）中，实现生产级的 disaggregated inference + MoE routing 统一方案**，特别是在 EFA 环境下。目前 vLLM 的 disaggregated inference 和 MoE 通信是分离实现的，且缺乏 EFA 支持。

---

## 八、总结

TransferEngine 通过识别 ConnectX 和 EFA 的共同功能子集（可靠无序交付），构建了跨硬件的 RDMA P2P 通信抽象。它通过 IMMCOUNTER 原语实现无序环境下的完成通知，透明管理多 NIC，并用 Rust 实现了高度优化的运行时。三个生产系统（KvCache 传输、RL 权重更新 1.3s/万亿参数、MoE dispatch/combine）验证了其性能——在 ConnectX-7 上达到或超越 DeepEP，同时首次在 EFA 上实现了可用的 MoE routing。主要局限在于 prefill 场景竞争力不足、host proxy 在大 EP 规模下的可扩展性、以及缺少端到端推理性能的验证。
