# OSWorld-Human: Benchmarking the Efficiency of Computer-Use Agents

**作者**：Reyna Abhyankar, Qi Qi, Yiying Zhang
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[6364d3f0f495b6ab9dcf8d3b5c6e0b01.pdf]]

---

## 1. 背景

Computer-Use Agents (CUAs) 是当下生成式 AI 的重要落地方向:借助 LLM/VLM 的感知与推理能力,让 agent 像人一样通过鼠标键盘和截图操作桌面应用,目标是自动化复杂数字工作流。代表产品包括 OpenAI Operator、Anthropic Claude Computer Use、Google Project Mariner,以及 UI-TARS、Agent S2、InfantAgent、Jedi 等开源系统。

评测方面,OSWorld 是该领域的旗舰 benchmark —— 覆盖 Ubuntu/Windows/MacOS 三种系统、9 类桌面应用(Chromium、GIMP、LibreOffice 套件、VS Code、Thunderbird、VLC 等),共 369 个真实任务,既支持 GUI 操作也支持 CLI。过去一年业界在 OSWorld 榜单上疯狂刷分,top 模型的成功率已从 28% 涨到 40%+。

但这些进步几乎都是"只谈准确率"—— 社区对 CUA 的**时间效率**几乎零系统研究。

---

## 2. 要解决的问题

论文指出目前 CUA 评测体系的一个致命盲区:**SOTA 系统虽然准确率看着漂亮,但端到端延迟往往长到实际不可用**。

- 例子:把文档段落行距改成两倍行距,Agent S2 需要 12 分钟,人类不到 30 秒。
- Agent S2 跑一个 OS 任务耗时 40+ 分钟,而任务设计上人类应该几分钟完成。
- 现有 benchmark 只报 success rate,完全看不出 agent 走了多少弯路。

具体的研究问题可以拆成三层:

1. **Latency 究竟花在哪了**? 是 LLM planning、reflection、grounding、截图,还是动作执行?
2. **Step 效率如何衡量**? 成功率掩盖了 agent 可能绕路 10 倍才完成任务的事实。
3. **能否给出"人类金标准轨迹"作为参照**,让社区知道距离"理论最优步数"还差多远?

---

## 3. 洞察与设计

**关键洞察**:在 agentic CUA 的单步循环 (observe → plan → ground → act → reflect) 中,**所有重度 LLM 调用(planning + reflection)会随 step 数增长而单调变长**,因为 prompt 包含全部历史 screenshot 和中间推理。因此效率瓶颈可被同时从两端打开:(a) 降低每个大模型调用的延迟,(b) 压缩 agent 完成任务所需的总 step 数。**这两条路在延迟上都是乘法收益,而且彼此独立。**

基于这一洞察,论文做了三件事:

### 3.1 第一次 CUA 延迟剖析
以 Agent S2 + GPT-4.1(planner/reflection/retrieval) + UI-TARS-7B-DPO(grounding, 单卡 A6000 跑 SGLang)为对象,在 OSWorld 官方的 37 任务 10% 子集上逐步细测,把每步拆成 retrieval / planning / grounding / action / screenshot / reflection 六类并统计耗时与 token。

结论:**planning + reflection 占 75%~94% 的端到端时间**(Figure 1 的甘特图里绿色+黄色几乎吞没了整条时间轴);grounding 因调小模型 + SGLang 只占 3%~6%;screenshot/action 可忽略。Figure 3 显示越到后面的 step,LLM 调用 latency 和 prompt token 数越大,最末期的 step 可以比开头慢 3×。

### 3.2 OSWorld-Human:人类金标准轨迹
由两位 CS 研究生对全部 369 个 OSWorld 任务**人工标注**"最少步数"轨迹 —— 先从 OSWorld 每个任务给出的 source(论坛回答、gold file)里提取步骤,再映射到 OSWorld action space;缺 source 的任务自己做一遍、另一位交叉校验;最后在 OSWorld 虚拟机中真跑一次,确保 evaluation score 通过。为避免环境耦合,不记录具体坐标。

每个任务给出两种参考轨迹:
- **Single-action**:细粒度到每个鼠标/键盘操作
- **Grouped-action**:把可共享同一 screenshot 观察的连续动作打包成一个 "step"(例:click cell → type formula → fill column 可以合成 1 个 step)

grouped 轨迹总步数严格 ≤ single,**揭示了 agent 理论上能把 observation/LLM 调用次数降低多少**。Table 3 显示所有应用上的 grouped 平均步数都显著小于 single(最猛的是 LibreOffice Calc,从 13.6 → 5.9)。

### 3.3 WES (Weighted Efficiency Score) 度量
为避免"agent 快速失败也算高效"这种漏洞,论文拆成两个指标:

$$\mathrm{WES}^+ = \sum_t r_t \cdot (t_{exp} / t_{actual})$$

$$\mathrm{WES}^- = -\sum_t (1 - r_t) \cdot (t_{actual} / S)$$

- WES+ ∈ [0, 1]:成功任务的"步数效率加权"。成功率越高、越贴近人类步数,分越高。
- WES- ∈ [-1, 0]:失败任务的"浪费 step budget 惩罚"。失败得快惩罚小,把 S 步预算耗光再失败惩罚大。
- 两者一起,才能兼顾准确率和效率。

## 4. 实现细节

论文在工程层面比较轻,核心工作是 benchmark 构造和详尽 trace。

- **Agent S2 trace 采集**:在 Agent S2 默认配置(最多 50 step/task)上,把 planner/reflection/retrieval 都换成 GPT-4.1,grounding 用 UI-TARS-7B-DPO(A6000 + SGLang),对 OSWorld 的 37 任务子集逐步记录 timing + token。
- **Observation 对比实验**:对每个应用各采样 1 个任务,分别跑 screenshot-only、screenshot + a11y tree、screenshot + a11y + SoM(Set-of-Marks)三种 observation 配置,a11y tree 设 10k token 上限。
- **OSWorld-Human 数据集规模**:369 任务 × 2 轨迹(single + grouped),与 OSWorld 同等规模。
- **Baseline 评估范围**:16 个 OSWorld 榜单公开 trajectory 的 CUA,覆盖 SS / A11y / SS+A11y / SoM 四种 observation 类型,包括 UI-TARS-1.5、Agent S2 (Gemini 2.5 / Claude 3.7)、InfantAgent、GPT-4o、Gemini-Pro-1.5、Llama-3-70B 等。WES 评估时各 baseline 用各自的 max step S 计算惩罚,保证公平。
- **Data/code release**:论文承诺开源 OSWorld-Human 全部轨迹 + 原始 latency trace。

## 5. 实验结果

### 5.1 延迟与 step 的剖析 (37 任务 Agent S2 trace)

| 维度 | 观察结果 |
|------|---------|
| LLM 调用占比 | planning + reflection = 总时间 **75%~94%**;retrieval 0.7%~8.9%;grounding 3%~6% |
| Step-level 时间增长 | 第 45-50 step 的 LLM 调用 latency 中位数是第 1-5 step 的 ~3× |
| Prompt token 增长 | 从开头 ~1k-2k 上涨到末期 >10k,prefill 主导 latency |
| A11y tree 成本 | 生成树 3-26 秒/step;LibreOffice 系列尤为严重,整体 task latency 可翻几倍;GIMP 反例外收益(少走弯路) |
| SoM 贡献 | 叠在 SS+A11y 上时可显著降低 step 数(LibreOffice Writer 从 50 → 16, VLC 3 → 2, GIMP 17 → 12) |

### 5.2 OSWorld-Human 上 16 个 CUA 的 WES 结果 (摘录)

| Observation | Baseline | Orig. Succ. (%) | WES+ Single (%) | WES+ Grouped (%) | WES⁻ |
|---|---|---:|---:|---:|---:|
| SS | UI-TARS-1.5 (100) | 42.5 | 23.7 | 14.3 | -0.22 |
| SS | Agent S2 + Gemini 2.5 (50) | 41.4 | 28.2 | 17.4 | -0.26 |
| SS | InfantAgent (50) | 35.3 | 13.3 | 8.2 | -0.22 |
| SS | Agent S2 + Claude 3.7 (50) | 34.5 | 20.0 | 11.4 | -0.42 |
| SS | UI-TARS-72B-DPO (50) | 24.6 | 15.6 | 10.6 | **-0.16** |
| A11y | GPT-4 (15) | 12.2 | 8.6 | 6.1 | -0.29 |
| A11y | Llama-3-70B (15) | 1.6 | 0.4 | 0.3 | -0.70 |
| SS+A11y | GPT-4V (15) | 12.2 | 8.5 | 5.7 | -0.46 |
| SoM | Gemini-Pro Vision (15) | 1.1 | 0.5 | 0.3 | -0.72 |

核心结论:
- OSWorld 最好的 agent (Agent S2 + Gemini 2.5, 41.4%) 在 grouped-action WES+ 上只拿 **17.4%**,实际比 raw success rate 缩水 **2.4×**。
- 折算到步数维度,leading agents 平均比人类多 **1.4×~2.7×** step。
- WES- 最好的反而是 UI-TARS-72B-DPO(-0.16),但它 WES+ 平平,说明它"失败失败得很快";这正是 WES+/- 双指标设计想暴露的。
- OSWorld 榜单的相对排序在 WES+ 上基本保留,但绝对分数差距放大,榜单"看起来都不错"的 agent 其实跨度被拉得很开。

## 6. 批判性分析

论文选题好、数据集贡献明确,但整体偏观测性研究,几处值得推敲:

1. **样本规模不均衡的延迟结论被泛化**。延迟剖析只用了 37 个任务(OSWorld 的 10%),而且只测了 Agent S2 这一个 framework。论文在 §3.4 强调"结论可推广到其他 agentic 系统",但只是定性论证(都遵循 observe-call-act 模式),没有做哪怕一个其他 agent 的消融对照。UI-TARS-1.5 这种 single-call 模型在 Table 4 里表现并不差,未必遵循同样的 latency 组成。

2. **Grouped-action 的可操作性被轻描淡写**。论文提出 grouping 能省大量 step 和 LLM 调用,但 grouped 轨迹是**人类事后合并**的结果 —— 现实 agent 执行 `click → type → enter` 前并不知道 `type` 的内容会不会触发新窗口或报错;若中途出错,合并成一个 step 意味着 error recovery 粒度变粗。论文没有讨论 grouping 在 on-line 执行时的可行边界,也没有实证说明 agent 即使按 grouped 执行也能保持同等 success rate。

3. **WES 指标设计存在耦合漏洞**。WES+ 用 $t_{exp}/t_{actual}$,但 $t_{exp}$ 是"人类估计的 step",和"LLM 调用次数"并非一一对应(尤其 grouped 版本),用它来"approximate end-to-end latency"有粗糙之处。两个 step 数相同的 agent,若一个历史 prompt 滚动累加而另一个做了 summarization,latency 可能差几倍,但 WES 分数一样。

4. **OSWorld-Human 的标注客观性**。数据集由 2 名研究生互审构造,未给出标注不一致率、第三方复审或与 crowd worker 的对比。对于"什么步数是真正必要的"这种带主观性的任务(键盘快捷键是否算作 1 步?先搜菜单再点是否比直接记住快捷键多一步?),缺少方法论上的透明度。

5. **未对 A11y tree / SoM 的结论做因果分析**。"A11y 帮助 GIMP 少走步"只是现象,作者没讨论为何某些应用受益而 LibreOffice 受害,也没深入到 tree node 数 vs. step 数的回归;OSWorld 上的 A11y 效果可能严重受实现质量影响(Linux 下 LibreOffice 的 a11y 子树出名地冗杂)。

6. **缺乏对 "planning/reflection 可否省略"的量化论证**。既然 reflection 占那么大比重,自然会问"砍掉 reflection 会损失多少准确率"。论文有提"减少 step 数"作为优化方向,但没有做任何 prompting 或 architectural ablation(哪怕把 reflection 改成隔 N 步一次),工程可操作性缺位。

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 社区最大的价值是**把 agent 性能研究从"跑分社区"拉回了"系统社区"**,几个可操作的延伸方向:

1. **Agent 专用的 prompt cache / KV cache 复用**。论文指出 LLM call 的 prefill 主导 latency,而每一步 prompt 包含了前 N-1 步的 screenshot + history。这是典型的 prefix caching 场景:每个任务内的所有 LLM 调用共享巨大前缀。把 SGLang、vLLM 的 RadixAttention / prefix cache 用到 agent-serving 场景,结合 per-session scheduling,可以非常自然地把末期 step 的 latency 压下来。值得跟进的研究问题:**如何在 multi-tenant agent serving 下调度共享 prefix 以最大化 hit rate,同时保证截图这种"不可哈希的变长输入"被正确处理**(screenshot 图像 token 复用粒度怎么定义)。

2. **Speculative decoding for reflection**。Reflection 调用的 output 偏短(Figure 2 里 completion token 中位数 <100),但 prompt 巨长。这是 spec decoding 的理想场景 —— prefill 是瓶颈,decode 短、结构化(yes/no + 简短解释)。一个小 draft model + 大 verifier 很容易在 reflection 上拿到 2-3× 加速。

3. **Agent Runtime 的 step-merging 调度器**。论文 grouped-action 的观察可以直接产出 research 问题:**一个 online runtime 能否自动识别"下一步不需要新 screenshot"? 什么信号(previous action 类型、UI diff 预测、action 间依赖分析)能触发跳过 observation+planning?** 这是一个典型的 online streaming inference 系统设计问题,可以借鉴 DB query planner 的延迟绑定思路。

4. **动态 observation 剪枝**。A11y tree 在 LibreOffice 下能产出几万 token,但绝大部分 DOM 节点与当前任务无关。可以做一个轻量级的 DOM summarization 模型(或 RL-trained pruner),把 a11y tree 压成 task-relevant subtree,在保持 success rate 的前提下压缩 prompt。这类工作在 web agent 界已经有 (WebArena 的 accessibility tree 修剪),但桌面 agent 几乎没人做。

5. **WES 是一个更好的系统评测目标**。对 MLSys 研究者来说,传统 agent paper 用 success rate 意味着"慢但正确"等于"好",让 systems 类工作难以评估。WES+/- 直接把 step 效率带进来,给了 serving system、caching system、scheduling system 一个可竞争的指标。短期可跟进的工作:以 WES+ 为 reward signal 做 agent 的 RL fine-tune,用 OSWorld-Human 作为参考轨迹来做 process reward。

6. **延伸到长 horizon agent**。本文的分析揭示了一个本质问题:**agent 做的 step 越多,每步越贵,这是二次方的灾难**。对于 SWE-agent、AutoGPT 这类动辄 100+ step 的长链路 agent,这个现象会更严重。OSWorld-Human 的方法论(人工金标准 + WES)可直接套用到 SWE-bench 或 Web 这些 domain,给整个 agent benchmarking 提供一个共通的效率评估框架。

---

## 8. 总结

OSWorld-Human 是第一篇认真测量 computer-use agent **时间效率**的工作,核心贡献在于:(a) 对 Agent S2 做了首次系统的 CUA latency breakdown,定位到 planning + reflection 的 LLM 调用占 75%-94% 且随 step 数递增;(b) 为 OSWorld 全部 369 任务提供人工金标准轨迹(single + grouped 两种粒度),首次让"agent 多走了多少步"可定量;(c) 提出 WES+/- 双指标,把 success rate 与 step 效率解耦。评估显示即使 OSWorld 榜首的 agent 也要比人类多 1.4-2.7× 步数。局限是实证只覆盖 Agent S2 一个 framework,WES 与 latency 的关联偏粗糙,grouping 未做 online 可行性验证;但 benchmark 和指标本身会对整个 CUA 社区产生直接影响,也给 ML serving/caching/scheduling 方向留出了清晰的研究切入点。
