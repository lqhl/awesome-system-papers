# Stream2LLM: Overlap Context Streaming and Prefill for Reduced Time-to-First-Token

**作者**：Rajveer Bachkaniwala, Chengqi Luo, Richard So, Divya Mahajan, Kexin Rong
**单位**：Georgia Institute of Technology
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[02522a2b2726fb0a03bb19f2d8d9524d.pdf]]

---

## 1. 背景

现代 LLM 推理越来越依赖外部上下文检索来提供准确、最新的回答,典型形式包括 RAG 类的 ANNS 向量检索和在线 web 抓取。然而这些检索操作通常要花 200 ms 到几秒,期间 LLM 推理引擎处于等待状态。用户可感知的关键指标 Time-To-First-Token (TTFT) 由此被严重拖慢——要么等齐完整上下文再开始推理(TTFT 差),要么让模型在不完整上下文下生成(质量差),两难。

近期工作 PipeRAG (Jiang et al., 2024) 和 AquaPipe (Yu et al., 2025) 提出把检索与推理重叠(streaming context):上下文分块到达时就增量喂给 LLM 做 prefill。这些工作证明单请求下 TTFT 可显著下降,但它们只针对单请求或固定 batch 的场景,没有处理真实生产部署中最关键的问题——多租户下多个并发请求会争抢 GPU 显存,调度策略必须动态适应异步到达的 chunk。这篇论文面向的就是这个多租户 streaming prefill 场景。

---

## 2. 要解决的问题

把 streaming context retrieval 从 "单请求 demo" 推到 "多租户生产部署" 面临若干独特挑战:

1. **动态工作负载**。每个请求的输入会随 chunk 异步到达而增长,总 KV cache 占用随时间变化,且不同请求的 chunk 到达速率差异巨大(作者实测 ANNS 中位数 37 ms/chunk,crawler 中位数 701 ms/chunk 且 P95 达 3.1 s)。传统 FCFS 或 progress-based 调度抓不住"谁刚收到新 chunk,应该被优先处理"这个时间维度的优先级。

2. **显存竞争与抢占策略**。多个请求共享有限的 GPU KV cache 池,OOM 时必须抢占。vLLM 原本的策略(recompute / swap)以"抢占队尾"为依据,既没有结合调度语义,也没有按硬件成本模型做 recompute vs swap 的权衡。

3. **两种截然不同的 streaming 模式**。append mode(crawler 类,逐步追加 chunk)和 update mode(ANNS 类,整个上下文集合被迭代替换)对 KV cache 的处理需求完全不同:append 模式下缓存完全有效,update 模式下大量旧 cache 会被作废。没有统一机制会导致要么错用过期 cache 产出错误,要么全量重算浪费算力。

4. **baseline 调度的灾难性尾延迟**。作者后续实验显示,若仅开启 streaming 但沿用默认 vLLM 调度,在内存压力下 P99 TTFT 反而比不开 streaming 还差(crawler 0.71×、ANNS 0.19×)——也就是说"光有 streaming 不够,必须配套调度"。

## 3. 洞察与设计

**关键洞察**:在多租户 streaming 场景里,**"调度决策(谁该被优先跑)"和"资源获取(分配 / 抢占 KV block)"是两件应当解耦的事**。把两者耦合在一个控制循环里会导致:(a) 调度策略被硬编码的抢占规则覆盖;(b) cache invalidation 与 allocation 时序混乱,难以做到只作废真正变化的 token。把它们拆成两个独立 phase 后,priority 策略可以单独演进,而 allocation / preemption 可以基于硬件成本模型独立决策。此外,两种 streaming 模式的 cache 管理可以被 **longest common prefix (LCP) invalidation** 这一统一抽象覆盖——append 模式下 LCP = 旧序列,无失效;update 模式下 LCP 是变化点之前的前缀,只作废之后的 blocks。

基于这两点,系统设计包含四个模块:

**1) 两阶段调度(Section 4.1,Figure 2)**

- **Phase 1 — Priority Ordering & Feasibility**:scheduler 调用选定策略(LCAS / FCFS / MCPS 等)对所有未完成请求排序,然后做 feasibility 检查(token budget + GPU block budget),把无法装下的请求放进 `not_scheduled_reqs`,保留优先级顺序。**此阶段不分配资源也不改请求状态**。
- **Phase 2 — Resource Acquisition & Adaptive Preemption**:按 Phase 1 的顺序尝试分配 GPU block,失败则按优先级顺序从 `not_scheduled_reqs` 选抢占候选,再用成本模型决定 recompute 还是 swap。

**2) LCP-based Cache Invalidation(Section 4.2,Figure 1)**

统一处理 append 与 update。当 prompt 从 `[d1, d2, q]` 更新到 `[d1, d2', q]` 时,LCP = `[d1]`,只作废 LCP 之后的 KV block,保留前缀。关键实现细节:若被抢占请求正处于 CPU swap 状态再收到 update,要先在 CPU 侧作废 LCP 之后的 blocks 并释放 CPU 内存,resume 时只 swap 回 LCP 之前的 blocks 然后重算后续,避免对 swap 状态的污染。

**3) 基于硬件成本模型的抢占(Section 4.3,Figure 4)**

离线对每种目标硬件(A40/H100/H200)profile 两个 piecewise-linear 模型:
- `recomputation_latency(T)`:prefill T 个 token 的延迟
- `swap_latency(C)`:GPU ↔ CPU 传输 C 个 block 的延迟

抢占时比较 `C_recomp` 与 `2·C_swap`(双向传输),选低者。在 H200 上两条曲线交点偏左,token 多时 swap 更便宜;A40 带宽差,recompute 几乎总胜(指数级更差的 swap 曲线)。这回答了 "update 模式下为什么几乎总选 recompute"(update 令 effective KV cache 在 invalidation 后很小,recompute 成本天然低)。

**4) 四种调度策略(Section 4.4,Table 1)**

| 策略 | append 适用 | update 适用 | 理由 |
|------|------------|------------|------|
| DEFAULT vLLM (FIFO) | Poor | Poor | 忽略 chunk 到达时间 |
| FCFS (双层:完成/部分) | Good | Moderate | 对完成请求友好,但忽略 freshness |
| MCPS (按已算 token) | Good | Poor | update 后 `num_computed_tokens` 会重置到 LCP,优先级崩塌 |
| **LCAS** (最近 chunk 到达时间优先) | Good | Good | 新 chunk 到 → 优先级抬高,立即处理,cache 仍暖 |

## 4. 实现细节

- 基于 **vLLM v1** 修改,保持与 PagedAttention 的兼容。
- EngineCoreRequest 新增三个 flag 暴露 streaming 语义:`is_streaming_prompt`(未完整输入)、`is_streaming_prompt_finished`(收尾)、`is_prompt_update`(append vs update 切换)。
- Driver 暴露 `new_stream / append / update` 三个便利函数。
- 调度器类型通过环境变量 `SCHEDULER_TYPE`(`DEFAULT_VLLM / FCFS / MCPS / LCAS`)在运行时选择。
- KV cache manager 同时维护 GPU 与 CPU block pool 以支持 swap 路径;recompute 路径直接把 block 释放回 free pool 并把 `num_computed_tokens` 重置为 LCP 长度。
- 事件遥测:每个请求记录 `QUEUED / SCHEDULED / KV_ON_GPU / PREEMPTED_SWAP / PREEMPTED_RECOMPUTE / FINISHED` 状态迁移,便于离线做调度诊断。
- 调度开销:50 并发请求下排序 latency 为 FCFS/LCAS 15–16 µs、MCPS 12–13 µs;500 并发 P99 仍 < 165 µs。
- 硬件成本模型 profile 一次约 5 分钟/GPU 配置,落盘为 JSON。
- artifact 已开源:https://github.com/rajveerb/stream2llm(MLSys artifact branch,MIT license)。

## 5. 实验结果

**硬件**:2× NVIDIA H200 (141 GB) / 2× H100 (80 GB),Llama-3.1-8B-Instruct,TP=2,GPU 显存利用率 80%,token budget 2048–8192。

**工作负载**(作者自采):

| Metric | Mean | P50 | P95 |
|--------|------|-----|-----|
| ANNS (update mode, 500 queries) — Total Tokens | 13K | 10K | 31K |
| ANNS — Retrieval Latency | 4.5 s | 3.9 s | 8.5 s |
| Crawler (append mode, 4,322 queries) — Total Tokens | 9.1K | 5.8K | 28.9K |
| Crawler — Retrieval Latency | 9.9 s | 9.3 s | 16.7 s |

ANNS 构建 Fineweb-edu 索引(372 GB,DiskANN,`L=10000`)+ SQuAD 查询;crawler 基于 crawl4ai + OpenAI SimpleQA。

**主结果 1 — Prefill TTFT(Figure 5–7)**:

- Crawler:streaming 在所有负载下持续优于非 streaming,中位数 TTFT 提升 3.9×(QPS 0.5)到 **10.8–11.0×**(QPS 4)。
- ANNS:streaming 贡献 P95 加速 **2.49–2.63×**(QPS 1);QPS 2 下 FCFS 达 2.26× P95 加速,LCAS 1.81×,MCPS 因 `num_computed_tokens` 崩塌降到 1.53×。
- MCPS 在 crawler QPS 2/4 处降到 0.73× / 0.71×,被新 chunk 请求反向压制。

**主结果 2 — 内存压力下的 ablation(Table 3)**,人为把 chunk delay ×10/30 放大以撑爆 KV pool:

| | Crawler P99 | ANNS P99 |
|---|---|---|
| Default Stream | 0.71× | 0.19× |
| FCFS + Recompute | **10.03×** | 1.84× |
| FCFS + Swap | 6.69× | 1.26× |
| FCFS + Cost-Based | 8.62× | 2.04× |
| LCAS + Recompute | 9.23× | 1.79× |
| LCAS + Swap | 4.80× | 0.97× |
| LCAS + Cost-Based | 9.14× | 1.79× |
| MCPS + Recompute | 0.73× | 0.19× |

**关键发现**:内存压力下 "只开 streaming + 默认调度" P99 会比非 streaming baseline **更差**(0.71× / 0.19×),调度策略直接决定尾延迟是否崩盘。

**抢占统计(Table 4)**:cost-based 在 crawler 上 SWAP/RECOMPUTE = 17–21% / 79–83%,在 ANNS 上几乎全走 RECOMPUTE(98–100%),印证 update 模式 invalidation 后 effective cache 很小、重算便宜。

**吞吐(Figure 11)**:streaming + 任意调度与 non-streaming 的 trace completion time 偏差在 ~1% 内,TTFT 收益不以牺牲吞吐为代价。

## 6. 批判性分析

1. **"11× TTFT 加速"的框定过于乐观**。11× 只出现在 crawler QPS=4 的**中位数**下,比较对象是完全不做 streaming 的 baseline。此处 baseline 必须等完整检索(median 9.3 s,P95 16.7 s)才开始 prefill,所以"加速"的主体是 **retrieval latency 本身**,而非调度/系统设计的贡献。去掉 streaming 的部分,纯调度策略在内存充裕时各方案几乎趋同(Figure 6 低 QPS 区间),论文标题里的 order-of-magnitude 叙事有夸大嫌疑。

2. **内存压力实验靠"人为拉长 delay"制造**。Table 3 的内存压力场景是把 chunk delay ×10/×30 后合成出来的,并非原始 trace 行为。这固然能放大 scheduler 差异,但也意味着结论"调度策略在生产中至关重要"需要证据——生产 QPS 下到底多久会遇到这种 delay 放大?作者没给。在默认 H200(141 GB)上几乎不触发抢占,这反向说明真实工况下 LCAS 相对 FCFS 的差异可能被 GPU 显存扩大化解掉。

3. **LCAS 的 starvation 被轻描淡写**。作者在 §4.4 承认 LCAS 下 chunk 到达稀疏的请求可能无限期被推迟,但评估里没有给出公平性指标(如 chunk 到达间隔 vs 完成 TTFT 的相关性)。对于 crawler P95 inter-arrival 3.1 s 的长尾请求,LCAS 很可能是它们的恶化方向——主结果只看 P50/P95,没覆盖 P99.9。

4. **只评估 prefill instance**。论文在 §2/§6 都强调只评 prefill-decode disaggregated 架构中的 prefill,TPOT 交给独立 decode 实例处理。但 streaming prompt 的 cache invalidation 直接影响 KV block 在 disaggregated 链路中如何传递——invalidation 和 KV transfer 的相互作用没评估,可能在真实 prefill→decode pipeline 中带来新的 stall。

5. **没覆盖的基础对比**。AquaPipe 无公开实现,论文以 "no public implementation" 为由放弃直接比较;PipeRAG 因架构差异(encoder-decoder cross-attention)也不比。结果是 Stream2LLM 的唯一对手只有 vanilla vLLM。在"streaming multi-tenant"这个新 niche 里没有第二套系统共同垫底,TTFT 绝对数字的说服力打折。

6. **成本模型是 idle-system profile**。§4.3 承认当前模型是在空载下 profile 的,但生产环境 PCIe 带宽在多请求 swap 风暴时会被显著挤压,cost prediction 会失真。论文没评估 cost model 预测误差在负载下如何漂移,而 cost-based 策略在 Table 3 中有时反而不如纯 recompute(crawler FCFS P99:cost 8.62× < recompute 10.03×),暗示模型精度可能就是瓶颈。

## 7. AI Infra / MLSys 视角

这篇论文值得 AI infra 研究者关注的核心贡献是"解耦调度与资源获取"与"LCP-based cache invalidation"两个抽象——它们都不是 streaming RAG 特有,而是 vLLM 这类 inference engine 演化到下一阶段必须的基础设施。

**可迁移的 insight**:
- **两阶段调度框架**本身可以泛化到非 streaming 场景,比如多优先级混合推理(在线请求 + batch 离线请求),当前 vLLM / SGLang 的 scheduler 都是单阶段耦合的,迁移成本低但能解锁更多调度策略。
- **LCP invalidation** 对 agentic workload 尤为相关:agent 会反复修改 history、重写 system prompt,prefix cache 的有效/失效语义接近 update mode。类似 RadixAttention 可以考虑把 LCP 逻辑深度嵌入 radix 树,做到作废粒度更细。
- **Hardware-aware cost models**是 systems ML 里反复被呼吁但很少被完整实现的思想。Stream2LLM 把它落到 recompute vs swap 的简单二元决策上,下一步值得尝试用到更复杂场景:tensor/pipeline parallel 间的 activation/KV 迁移、CPU offload 层次(CPU RAM → NVMe)、speculative decoding 的 rollback 成本估计。

**值得跟进的 future work**:
1. **在线 adaptive 成本模型**:§4.3 的静态 profile 在高争抢下显然不准。把 PCIe/HBM 实时带宽作为反馈信号,做 online regression,成本模型会准得多。这是一个独立可发论文的方向。
2. **streaming + speculative decoding** 的组合:update mode 下大面积作废 KV 时,如何同时处理 draft model 的状态是未解的。
3. **prefill-decode disaggregated 下 streaming KV 的跨实例传递**:当 prefill 端在 streaming,prefill→decode 的 KV handoff 何时/以什么粒度发生?这是本文留白处。
4. **公平性调度**:LCAS 的 starvation 风险可以用 aging / deadline 类思路修补,是一个小切入点。
5. **更普适的 streaming prompt benchmark**:论文自采 trace 是突出贡献,如果能开放成标准 benchmark(类似 ShareGPT/LongBench 对 LLM serving 的作用),社区会显著受益。

**小实验室切入点**:Stream2LLM 的 artifact 已开源且没有 GPU 也能跑 5 分钟 artifact-only 路径,是一个很好的 vLLM v1 扩展样板——在它基础上做 scheduler/cost model 的改进,工程门槛远低于从零搓 serving 系统。

---

## 8. 总结

Stream2LLM 把"streaming context + inference 重叠"这条已被单请求工作证明的思路,推进到多租户多请求的真实生产形态。核心贡献是三件事:(1) 两阶段调度架构将 priority 与资源分配解耦,为 streaming 场景下灵活的抢占策略铺路;(2) LCP-based cache invalidation 用同一机制处理 append / update 两种检索模式,最小化重算;(3) 硬件感知的 cost model 在 recompute 与 swap 之间做在线选择。在 crawler + ANNS 两类真实 trace 上展示 TTFT 最高 11× 改进、吞吐零损耗,同时揭示"streaming 若无配套调度在内存压力下 P99 反而恶化"的重要反面发现。适合作为 vLLM / SGLang 这一类 serving 系统演化 streaming 能力时的直接参照,但在生产适用性方面对工作负载选择、baseline 可对比性、cost model 动态化仍有较大打磨空间。
