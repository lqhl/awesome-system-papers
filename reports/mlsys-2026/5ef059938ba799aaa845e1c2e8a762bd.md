# MAC-Attention: A Match–Amend–Complete Scheme for Fast and Accurate Attention Computation

**作者**：Jinghan Yao, Sam Ade Jacobs, Walid Krichene, Masahiro Tanaka, Dhabaleswar K Panda
**会议**：MLSys 2026
**链接**：[MLSys 2026 Proceedings](https://proceedings.mlsys.org/paper_files/paper/2026)
**源文件**：[[5ef059938ba799aaa845e1c2e8a762bd.pdf]]

---

## 1. 背景

LLM 长上下文推理(几万到十几万 token)正在成为标配:长文档理解、多轮对话、代码库分析、科研文献处理都依赖这种能力。但 decode 阶段每生成一个 token 都要把完整 KV cache 从 HBM 重新读出来做 attention,因此 **decode 是 IO-bound 的**:KV 流量(而非计算)是延迟的主导因素。

围绕这一瓶颈已经有了两条主流路径:
1. **压缩 KV**(低秩投影 / 量化):减少每个 token 占用的字节数,但损失保真度。
2. **选择 / 驱逐 token**(StreamingLLM、H2O、SnapKV、Quest 等):缩短有效上下文,但牺牲访问完整性,在延迟召回、跨文档关联、长生成、分布式证据等场景退化明显(RULER 等基准已经反复证明这一点)。

IO-aware kernel(FlashAttention、FlashInfer)和分页 KV(vLLM 的 PagedAttention)只能改善访问局部性,无法改变「序列越长 KV 越大」这个根本问题。

---

## 2. 要解决的问题

作者要解决的核心问题:**能不能在不损失 attention 保真度、不限制可访问 token 范围的前提下,把长上下文 decode 的 KV 流量降下来?**

具体子问题:
- 压缩 / 选择类方法的精度损失在长生成、长程召回任务上不可接受(LongGenBench 这类评测中错误会随 decode 步数累积放大)。
- 现有 prefix reuse / tree decoding 类方法依赖请求间字面前缀重叠,适用面窄。
- Recycled attention 等「stepwise reuse」方案要交替全 / 部分 attention,调度复杂且仍然受限于 top-k 选择的近似性。

需要一种新的复用范式:**单流内**、**基于查询语义相似度**、**不依赖字面前缀**、**保留完整 KV 访问能力**。

---

## 3. 洞察与设计

**关键洞察**:在单一 decode 流中,query 向量呈现强烈的时间冗余 —— 多轮对话、代码生成、长推理这类任务里,模型在不同时刻往往「想问类似的问题」。如果当前 query $Q_m$ 与历史某个 query $Q_p$ 在 pre-RoPE 空间里足够接近,那么它们对前缀 $[1, p]$ 上 KV 引起的 attention 分布也高度相关 —— 直接复用 $Q_p$ 那一步缓存好的 attention summary 即可避免重读整个长前缀。但有两个细节决定了能否兼顾保真度:

1. **匹配必须在 pre-RoPE 空间做**:RoPE 把相对位置编码成正交旋转 $R(m-p)$,即使 $\tilde Q_m \approx \tilde Q_p$,经过 RoPE 后的 $\|Q_m - Q_p\|$ 也会随 $|m-p|$ 增长(频率混叠导致 destructive phase mixing),命中率会被位置项淹没。在 pre-RoPE 空间匹配可剥离位置相位,直接度量语义相似度。
2. **匹配位置附近的局部 token 贡献了大部分近似误差**:softmax 概率质量集中在 decoding cursor 附近,直接用 $AS_{1:p}^{(p)}$ 作为 $AS_{1:p}^{(m)}$ 的近似时,误差主要由 $[p-r+1, p]$ 这段「高质量带」贡献。只要重新计算这一短带($r$ 通常 256),近似误差就被压到与 full attention 不可区分。

### Match–Amend–Complete 三阶段方法

基于上述洞察,作者提出 MAC-Attention,核心 pipeline:

![Figure 2: Match-Amend-Complete with async cache update](../../markdowns/mlsys-2026/5ef059938ba799aaa845e1c2e8a762bd/images/7b2fa2c5982e10b830d72349d3131405425f91a8ea88abfa9383e33cf58a8977.jpg)

每个 (request, head) 维护两个容量为 $K$ 的 ring buffer:
- **Query Ring**:存最近 $K$ 步的 pre-RoPE query $\tilde Q_t$。
- **Attention-Summary Ring**:存对应的「修正后的前缀 summary」$AS_{1:t-r}^{(t)} = (S_{1:t-r}^{(t)}, Z_{1:t-r}^{(t)})$。

每一步 decode:

- **Match**:用当前的 $\tilde Q_m$ 与 ring 里 $K$ 个候选做 L2 距离扫描,接受门限 $\|\tilde Q_m - \tilde Q_p\| < \sqrt{2d}(1-\tau)$(基于 isotropic Gaussian 假设下 $\chi_d^2$ 分布的「随机巧合」基线归一化)。L2 而非 cosine,因为 cosine 只控方向不控幅度,而幅度直接影响 logit scale 和 softmax sharpness。
- **Complete**(关键路径):若命中,加载 $AS_{1:p-r}^{(p)}$,用真实 post-RoPE 的 $Q_m$ 在 KV 区间 $[p-r+1, m]$ 上重算 $AS_{p-r+1:m}^{(m)}$,然后用 FlashAttention 风格的 log-domain online merge $\oplus$ 把两段 summary 合并。整个过程**完全跳过 KV 区间 $[1, p-r]$**。
- **Amend**(异步,off-critical-path):为了让本步生成的 token 将来能被复用,在辅助 stream 上算出 $AS_{r+1:m}^{(m)}$ 并通过 online subtraction $\ominus$ 从 $AS_{1:m-1}$ 中扣掉,得到下一个待存的 $AS_{1:m-r}$,连同 $\tilde Q_m$ 插入 ring。

**复杂度**:命中时 attention 阶段 IO 与计算量为 $O(r + (m-p))$,与序列长度 $L$ 无关;不命中则 fallback 到 $O(L)$ 的 full attention,**输出与基线逐位相同**(无精度损失下界)。

## 4. 实现细节

### 微流水线(三个 kernel)

![Figure 3: Decode micro-pipeline with SplitQ match and per-head SplitKV scheduling](../../markdowns/mlsys-2026/5ef059938ba799aaa845e1c2e8a762bd/images/7597649eab08e3222353585b499992026ef1d877917beadf2414345fd4a72f10.jpg)

- **K1 — Match kernel(SplitQ L2 match)**:tiled,每个 tile 内 streaming pass 计算 $\|\tilde Q_m\|^2 + \|\tilde Q_p\|^2 - 2\tilde Q_m^\top \tilde Q_p$,bf16 读入 + fp32 累加,warp-only shuffle reducer 消除 barrier 停顿。这个 kernel 比 attention 更 memory-bound,因为它必须扫描所有 query head(GQA 下 attention 只扫共享的 KV head)。
- **K2 — Amend & Complete kernel(per-head SplitKV)**:不同 head 命中位置 $p$ 不同,因此 band+tail span $[p-r+1, m]$ 长度异质。作者把 (request, head) 轴展平,**按 span 长度比例分配 CTA**(图 3b 的绿块数量),长 span 多 CTA、短 span 共享 CTA。kernel 内做 attention 并 in-place log-domain merge。
- **K3 — Rectify-Append kernel(辅助 stream)**:计算下一步要用的 $AS_{1:m-r}$,写三行(query / rectified attention / ln-LSE 标量),用单个 event 与主 stream 同步,延迟可被下一层的 K1/K2 完全隐藏。也支持 in-place 同 stream 模式。

### 状态布局

- 两个 ring 都按 request 全局长度 mod $K$ 索引,recent window 物理连续,O(1) 插入。
- $K \le 1024$、$r \le 512$ 是默认操作区间;K=1024、L=120K 时辅助 HBM 开销 ≈ KV cache 的 5%(线性于 $K$、反比于 $L$)。
- $S$、$Z$ 必须用 fp32 防止多次 merge 累积误差;ring 本身 bf16/fp16 即可。

### 与现有栈的兼容

- **MQA/GQA**:matching 仍按 query head 粒度做(不同 head 复用不同 $p$),attention 按 KV head 粒度做。
- **Paged KV**:不改变底层布局,scheduler 把 query head 映射到对应 KV head。
- **IO-aware kernel(FlashAttention / FlashInfer / FlashDecoding)**:K2 直接在其上构建,merge 操作用 Milakov-Gimelshein 的在线 normalizer 公式。

### 实现栈

SGLang 0.4.9 + FlashInfer 0.2.7 kernel,H100 SXM5 + CUDA 12.8.1。可被捕获到 CUDA Graph 摊销 launch 开销。

## 5. 实验结果

### 平台与基准

- 硬件:NVIDIA H100 SXM5
- 模型:LLaMA-3.1-8B/70B、Phi-4-Mini、GLM-4-32B、Qwen3-30B-A3B-Instruct(MoE)
- 基准:LongBench v2(120K)、RULER(120K)、LongGenBench(16K 连续生成)
- 默认配置:$K=1024$,$r=256$,$\tau=0.45$(召回类)/ $\tau=0.75$(生成类)

### 精度:与 full attention 持平甚至小幅超越

**Table 1 主结果(LongBench v2 / LongGenBench / RULER)**:

| 模型 | 方法 | LB v2 Overall | LongGenBench Acc. | RULER | KV 节省 |
|---|---|---|---|---|---|
| LLaMA-3.1-8B | Full | 29.0 | 34.7 | 79.8 | 0% |
| LLaMA-3.1-8B | Quest-1K | 26.2 | 27.2 | 72.4 | 98% |
| LLaMA-3.1-8B | **MAC** | **30.2** | **38.2** | 78.8 | **99%** |
| LLaMA-3.1-70B | Full | 31.4 | 41.9 | 80.1 | 0% |
| LLaMA-3.1-70B | **MAC** | **32.2** | 43.6 | 78.0 | **99%** |
| Phi-4-Mini | Full | 28.0 | — | 74.4 | 0% |
| Phi-4-Mini | **MAC** | **29.8** | — | 73.1 | 91% |
| Qwen3-30B-A3B (MoE) | Full | 37.0 | — | — | 0% |
| Qwen3-30B-A3B (MoE) | **MAC** | 36.6–37.6 | — | — | hit ≥ 99.5%, skip ≥ 98.6% |

要点:
- LongBench v2 上 MAC **平均超过 full attention**,作者推测是 baseline 长上下文计算本身有数值噪声。
- LongGenBench(最严苛,误差会逐 token 累积):MAC 在 8B/70B 上 finish rate 与 baseline 相当,accuracy 还略高。
- MoE 模型(Qwen3-30B-A3B):专家路由没有破坏 query 语义重复模式,hit rate ≥ 99.5%。

### 速度:attention 阶段最高 ~46×,端到端最高 2.6×

在 batch=1 / 32K 这种最不利场景,MAC-60% 甚至会比 baseline 慢一点点(固定 reuse 开销大于节省),作者明确指出此时应回退 full attention。

| KV % | Full | Quest | RocketKV | Multipole | **MAC** |
|---|---|---|---|---|---|
| 1 | 234 µs | 581 µs | 823 µs | 192 µs | **63 µs** |

Quest / RocketKV 这类 selection 方法因为额外的索引 / 排序开销,实际比 FlashInfer full attention 还慢 —— 这是个对该领域颇为冲击的事实。

### Ablation:Rectification 误差 vs. band 宽度 / reuse gap

误差 $\mathrm{Err}(m) = \|o_m^{\mathrm{MAC}} - o_m^{\mathrm{full}}\|_2 / \|o_m^{\mathrm{full}}\|_2$ 随 $r$ 增大快速衰减,$r \approx 8$ 已能去除大部分差异,$r \ge 256$ 实际上与 full attention 不可分。深层略需要更宽的 band。

### 异常 / 限制(Table 8 - Prefill 探索)

把 MAC 同时启用到 prefill 阶段(window=inf 全局匹配)的 ablation 显示:**hit/skip 仍然很高,但 Overall accuracy 普遍下降到 26.6–27.4(baseline 29.0)**,主要因为 prefill 内 reuse gap 极大、固定短 band 不够。作者建议 distance cap、自适应 band 等 mitigation,但承认 prefill 不是 production 配置。

## 6. 批判性分析

1. **「30.2 > 29.0」的反向超越需要更严谨解释。** 作者把 LongBench v2 上 MAC 略胜 full attention 归因于「baseline 长上下文计算的数值噪声」,但没有给出固定 seed 下的方差或多次重复实验。在长生成基准上这种 0.5–1.0 个点的「超越」很容易被随机性吞掉,应该补 95% CI 或多 seed 重复。

2. **Prefill 退化被弱化处理。** Section 5 一直强调 decode-only,但 Table 8 显示一旦想把 MAC 用在 prefill 就明显劣于 baseline(Overall 26.6 vs 29.0,~2.4 个点)。在大多数生产场景里 prefill latency 同样是关键 SLO(TTFT),论文把 prefill 单独丢到附录、并用「ablation only, not production」轻轻带过,实际上削弱了「完整 pipeline 加速」的故事。

3. **「46×」是 attention 阶段、且在最有利配置下取的最大值。** 实际端到端在 128K 上是 2.6×,256K + batch=32 这种规模本身就只在 batch serving 高负载场景才有,普通用户体感(batch=1)只有 ~7× attention 阶段、~1.4–1.7× 端到端。Abstract 里把不同语境下的最大值并列陈述,容易让读者误判收益规模。

4. **「O(1) on hit」依赖 hit rate ≥ 99% 这个经验事实,而非定理。** 论文反复声明命中后复杂度与序列长度无关,这是对的;但整体期望复杂度仍然是 hit rate 加权的 $O(1) + (1-\text{hit}) \cdot O(L)$。一旦遇到 query 多样性高的工作负载(比如 agent 连续工具调用、跨域问答),hit rate 可能远低于 LongGenBench 上观测到的 99%,论文没有给出 hit rate 退化场景的下界分析。

5. **Match kernel 在大 GQA 下会反客为主,但论文一笔带过。** Figure 8a 清楚显示 GQA 40-10 + K=2048 时 match 是 attention 的 2×,作者只说「所以默认 K=1024」。但这意味着 MAC 对 query head 数量增长(未来更大的 LLM)不友好,需要把 match kernel 本身按 head 分块或加近似最近邻索引,这是个明显的 follow-up 但论文没讨论。

6. **「pre-RoPE 是语义空间」的假设缺少正面证据。** 论文从 RoPE 旋转造成 phase mixing 的角度反向论证「post-RoPE 不该匹配」,但没有正面验证 pre-RoPE query 在多大程度上是 position-invariant 的语义表示 —— 直觉上不同 token 类别(标点 / 实词 / 代码符号)的 pre-RoPE query 也可能因语法角色相近而误匹配,论文没给出语义类别上的 confusion matrix。

7. **MoE 实验只测了 1 个模型,且未做长生成。** Qwen3-30B-A3B 上只跑 LongBench v2 Overall acc,LongGenBench / RULER 没出现。MoE 的专家路由稳定性是否在 16K 连续生成下也保持,论文没有回答。

## 7. AI Infra / MLSys 视角

这是一篇典型的 AI Infra / MLSys 论文,本节从该视角评估:

**对该领域的核心启发**:

1. **「时间复用」是与「压缩 / 选择」并列的第三条 KV 优化路径,且更优雅。** 在 KV cache 优化已经被 KV compression、KV eviction 反复挖掘的当下,作者把视角切到 query 而非 KV 上 —— 这是个被低估的方向。后续可以把这个「query-side semantic reuse」思想扩展到:
   - **跨请求 query reuse**:同一 user 多轮对话间,系统级共享 query ring(类似 paged-KV 但在 query 侧)。
   - **tree-decoding 场景**(speculative / beam search):候选分支间的 query 几乎一致,merge 路径上的 attention 可以批量复用。

2. **online-mergeable summary 的代数结构值得挖掘。** Log-domain associative merge $\oplus / \ominus$ 在 FlashAttention 里只用于行内并行,这里被作者推到「跨时间步的 prefix 复用」。这个抽象 + ring-buffer 结构 + amend 修正,是一个干净的 systems primitive,**任何「带前缀状态、可在线合并」的 reduction 都可以借鉴**(比如 RNN/Mamba 的 hidden state、prefix sum-based positional encoding)。

3. **CTA 粒度的 per-head 异质 workload 调度是稀疏 / 自适应 attention 的常见痛点。** MAC 的 SplitKV scheduling(把 (request, head) 展平 + 按 span 长度比例分配 CTA)对所有「每个 head 走不同 KV 子集」的稀疏 attention 都有借鉴意义(比如 Quest、SnapKV、TidalDecode)。把这个 planner 抽出来做成通用库会很有用。

4. **「Match kernel 被 GQA 倒置 memory-bound 关系」是个有趣的 system insight**:GQA 设计的初衷是减少 KV head 来降低 attention 的 memory 流量,但任何「per query head」操作(MAC match,以及未来的 per-head sparsity index)都会**反向放大** memory 压力。这暗示未来 attention 优化要把 query side 也纳入 IO 模型。

**值得跟进的 future work**:

1. **自适应 (τ, K, r) 调度**:论文已经在 Figure 5 显示不同 layer 的 acceptance pattern 差异很大,但只用了全局固定参数。**per-layer / per-head / per-step adaptive policy** 是一个非常具体的 follow-up,可以用一个轻量 MLP 或 EMA 的统计量在线学。
2. **降低 prefill 退化**:作者提的 distance cap + adaptive band 是好方向,但更根本的可能是 prefill 内部用 chunk-level summary(而不是 token-level)做 reuse。
3. **MAC + speculative decoding 组合**:speculative 的 draft model 也会反复生成相似 query,如果 verify 阶段能复用 draft 的 attention summary,有望进一步把 verify 的 attention 开销压到 O(r)。
4. **hit rate 下界保证**:理论上证明「在某类语言模型 + 某类输入分布下 hit rate ≥ p」会让这个方法从「实验上 work」升级到「有理论根据 work」。
5. **跨请求 / 跨 session 的 query memory**:把 ring 扩展为 LRU 缓存,或者用 ANN 索引(HNSW / IVF)在长 history query 上做近似匹配 —— **「query-level prefix cache」可能是下一个 vLLM 级别的 system idea**。

**最有价值的切入点**:把 MAC 的「pre-RoPE 语义匹配 + log-domain associative merge」这个 systems primitive 抽出来,作为一个通用的「stateful reuse layer」放到 vLLM / SGLang 上,允许任何 IO-aware attention kernel 即插即用复用历史 attention summary。这个抽象一旦稳定,可以孵化出整个新的优化家族。

## 8. 总结

MAC-Attention 提出了一个 **training-free、model-agnostic、能与 IO-aware kernel + paged-KV + GQA 完全兼容**的 attention 加速方案,核心机制是用 pre-RoPE L2 距离匹配历史 query,复用其修正后的 attention summary,只重算高质量带 + tail,通过 log-domain online merge 合成最终输出。命中时 attention 阶段 IO 与计算与上下文长度无关。

实测在 LongBench v2 / RULER / LongGenBench 上保持(甚至小幅超过)full attention 精度,attention 阶段最高 46× 加速、端到端最高 2.6× 加速,KV 访问减少最高 99%。MoE 模型上 hit rate 仍 ≥ 99%,展示了较好的通用性。

**适用场景**:长上下文 batch decode(尤其 batch ≥ 8、context ≥ 64K),query 重复模式明显的工作负载(对话、长生成、代码补全)。

**主要局限**:(1) prefill 阶段需要更复杂的策略,固定短 band 会导致精度下降;(2) hit rate 高度依赖 query 重复性,query 多样性大的负载会退化到 full attention;(3) 大 GQA 比例下 match kernel 自身可能成为瓶颈,K 不能盲目增大;(4) batch=1 + 短上下文场景下固定 reuse 开销可能反向 regression,需要 runtime fallback。
