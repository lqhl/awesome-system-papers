# HELIOS: Adaptive Model and Early-Exit Selection for Efficient LLM Inference Serving

## 一、背景

Early-Exit LLM（EE-LLM）是一类允许 token 在中间层提前退出的语言模型，通过跳过简单 token 的后续层计算来降低生成延迟、提高推理吞吐量。随着模型规模持续增大（如 Llama2-70B、CodeLlama-34B），推理的计算和内存开销成为关键瓶颈。EE-LLM 作为一种无需牺牲精度的加速方案，已在工业和学术界广泛采用（LayerSkip、EE-LLM 框架等）。

---

## 二、要解决的问题

现有 EE-LLM serving 框架存在两个核心限制：

1. **延迟收益有限**：现有框架仅依赖单一模型，无法提前退出的 token 必须遍历所有剩余层，平均生成延迟受制于这些"难 token"。
2. **无法增大 batch size**：
   - Early exit 的具体层取决于输入请求、运行时才能确定，因此框架必须加载所有层的权重以应对最坏情况，GPU 显存占用与 vanilla 解码完全相同。
   - EE-LLM 中不同 token 的退出层不同，导致 batch 内 token 之间存在同步开销，现有框架默认只用 batch size=1。

两个问题叠加，使得 EE-LLM 的吞吐量提升远低于理论潜力（相比 vanilla 解码仅提升约 16%）。

---

## 三、洞察与设计

**关键洞察**：

1. **不同模型的 early exit 具有互补性**——在一个模型上无法提前退出的 token，往往可以在另一个模型上成功提前退出。例如 OPT-1.3B 的前 6 层可处理 74% 的 token，剩余 26% 中有 57% 可以仅用 OPT-6.7B 的前 9 层完成。两者联合使用可将 early exit 比例从 ~74% 提升至 ~92%。
2. **低置信度 token 的预测通常是正确的**——即使 token 在 early exit 层未达到置信度阈值，其预测结果在遍历完所有后续层后仍保持不变的概率高达 85%-92%。因此可以"贪心地"允许这些 token 提前退出，并只加载最可能被使用的层，节省显存。

基于上述洞察，HELIOS 的设计分为 5 个步骤：

1. **候选模型选择**：从 Model Repository 中根据 SLO 和硬件约束选出 Top-K 候选模型（默认 3 个）。
2. **实时评估**：对每个候选模型运行 5 个请求的 profiling，收集 early exit 分布和准确度（用 perplexity 作为 reference-free 指标），结果存入 Performance History Table（PHT）。
3. **贪心加载 + token 生成**：选择最优模型，仅加载到最常用的 early exit 层（如 OPT-1.3B 只加载前 6 层），节省的显存用于增大 batch size。使用 Confidence Breach Counter（CBC）追踪连续未达阈值的 token 数，超过阈值（默认 100 token 窗口中 50 次）时触发决策。
4. **加载更多层 vs. 切换模型**：当 CBC 超限时，HELIOS 比较两个选项的开销——(a) 加载当前模型的剩余层 vs. (b) 切换到另一个候选模型的部分层，选择开销更小的方案。
5. **周期性重新评估**：每服务 RI=150 个请求后重新 profiling，更新 early exit 分布以适应请求流特征的变化。

## 四、实现细节

- **模型配置**：支持 pre-trained EE-LLM（LayerSkip 发布的 Llama2-7B/13B/70B、Llama3-8B、CodeLlama-34B，支持任意层退出）和 post-training modified EE-LLM（OPT-1.3B 和 OPT-6.7B，在 1/4 深度处插入 auxiliary head，冻结 backbone 微调 50K 步）。
- **准确度评估**：使用 perplexity 作为 inference-time 无需参考的准确度指标，要求候选模型使用相同 tokenizer 和词表以保证公平比较。
- **同步开销消除**：贪心加载模式下，所有 token 在同一步都退出相同的 early exit 层，完全消除 batch 内同步问题。
- **显存节省来源**：包括模型权重（只加载部分层）和 KV cache（未加载层无需存储），两者均按跳过层数线性减少。
- **硬件**：4× NVIDIA A100 (40GB)，大模型使用 tensor parallelism（Llama2-70B TP=4，CodeLlama-34B TP=2）。

---

## 五、实验结果

**数据集**：ShareGPT（对话）、CNN-DailyMail（摘要）、CodeXGLUE（代码生成）、GSM8K（数学推理）、HellaSwag（句子补全）。

| 指标 | 对比基线 | HELIOS 提升 |
|------|---------|------------|
| 吞吐量 | OPT-1.3B standalone EE-LLM | 1.48× |
| 吞吐量 | OPT-6.7B standalone EE-LLM | 2.13× |
| Batch size | 现有 EE-LLM 框架 | 最高 15.14× |
| TTFT | OPT-1.3B / OPT-6.7B | 1.39× / 2.23× 降低 |
| TPOT | OPT-6.7B | 降低 46.6% |
| 显存节省 | CodeLlama-34B + Llama2-70B → HELIOS | 从 192GB 降至 42GB（67.4%） |
| 准确度 | OPT-1.3B standalone | perplexity 仅增加 0.01 |
| 能耗 | OPT-1.3B (0.50Wh) / OPT-6.7B (1.01Wh) | 0.45Wh（节省 10%） |

其他关键发现：
- HELIOS 将需要遍历所有层的 token 比例从 ~22% 降至 ~7.4%（3× 降低）
- 吞吐量提升在不同置信度阈值下保持稳定，而 standalone EE-LLM 随阈值增大急剧下降
- Re-assessment Interval RI=150 是吞吐量和准确度的较好平衡点

## 六、批判性分析

1. **实验规模偏小，模型偏旧**：全部评估在 4×A100 (40GB) 上完成，使用的模型为 OPT-1.3B/6.7B、Llama2 系列等较老模型。未展示在 Llama3-70B+、Mixtral 等现代主流模型上的效果，也未在 H100/B100 等新硬件上验证。
2. **Batch size=1 的吞吐量评估有局限**：Section 5.1 明确限制 batch size=1 来"单独评估 early exit 的收益"。但生产环境中从不使用 batch size=1，这使得核心的吞吐量对比数字（1.48×）的实际参考价值存疑。
3. **准确度评估仅用 perplexity**：Perplexity 仅衡量 token 级别的概率分布，无法反映生成质量（如摘要的忠实度、代码的功能正确性）。论文声称"negligible accuracy impact"但未提供任何 task-specific 指标（ROUGE、pass@k、exact match 等）。
4. **"token 不变"的观察需更审慎解读**：论文发现低置信度 token 在后续层后预测不变的概率高达 85-92%，但这是在汇聚统计意义上的。在实际生成中，即使 8% 的 token 预测错误也可能导致严重的语义偏差（如代码生成、数学推理场景），而论文未分析错误 token 的分布特征和对下游任务的影响。
5. **候选模型需共享 tokenizer**：这一约束显著限制了模型组合的多样性，实际部署中能使用的模型组合可能很少。论文未讨论这一限制对方法通用性的影响。
6. **模型切换开销被轻描淡写**：切换模型需要加载新的权重到 GPU 显存，论文用 CBC 机制来摊销开销，但未详细报告切换延迟的绝对值和对尾延迟的影响。
7. **Early exit 的训练/微调成本未计入**：post-training modified 模型需要 50K 步微调，pre-trained 模型需要专门训练。这些前置成本未与 speculative decoding 等无需额外训练的方案做公平对比。

## 七、AI Infra / MLSys 视角

**启发与借鉴**：

- **多模型协同 serving 的新范式**：HELIOS 提出的"利用多个模型的互补 early exit 特性"思路，可以推广到其他异构模型协同场景。例如在 MoE 推理中，不同 expert 的激活模式也具有互补性，类似的动态选择机制可能有效。
- **贪心层加载是一个值得深入的方向**：只加载最可能用到的层、将节省的显存用于增大 batch size，这一思路与 offloading（如 FlexGen）形成互补——前者是"按需加载"，后者是"按需卸载"。两者结合可能产生更高效的显存管理策略。
- **与 Speculative Decoding 的融合空间**：论文在 Section 6 讨论了与 speculative decoding 的关系，但未深入。一个有价值的方向是将 HELIOS 的多模型 early exit 作为 draft stage，用更大模型做 verification，可能同时获得两种方法的加速。

**可操作的 future work**：

1. 将 HELIOS 的多模型 early exit 机制与 continuous batching（如 vLLM 的 PagedAttention）结合，解决动态 batch 场景下的 early exit 同步问题。
2. 研究 early exit 分布预测——是否可以根据 prompt 特征（长度、领域、复杂度）预测最优模型和退出层，避免运行时 profiling 开销。
3. 在 prefill 阶段应用类似的多模型 early exit 策略，加速长 context 的 prefill 计算。

---

## 八、总结

HELIOS 提出了一个多模型协同的 EE-LLM serving 框架，通过利用不同模型 early exit 的互补性和低置信度 token 仍正确的观察，实现了贪心层加载以节省显存、动态模型切换以最大化 early exit 比例。在 OPT 和 Llama 系列模型上实现了 1.48× 吞吐量提升和最高 15.14× 的 batch size 增大。核心思想——多模型互补 early exit 和按需层加载——具有一定启发性，但评估使用的模型较旧、规模偏小，且准确度评估仅限 perplexity，距离生产级部署还有较大差距。
