# HELIOS: Adaptive Model and Early-Exit Selection for Efficient LLM Inference Serving

**作者**：Avinash Kumar, Shashank Nag, Jason Clemons, Lizy John, Poulami Das
**单位**：University of Texas at Austin, NVIDIA
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[1f0e3dad99908345f7439f8ffabdffc4.pdf]]

---

## 1. 背景

Early-Exit LLM (EE-LLM) 是一类允许 token 在 Transformer 中间层"早退"的语言模型——当某层 token 的预测概率超过预设 confidence threshold 时，就直接作为最终输出，不再走剩余层。理论上这能同时降低 token 生成延迟（per-token latency）与提升服务吞吐。主流工作如 LayerSkip (Elhoushi et al., 2024)、EE-LLM (Chen et al., 2024)、EE-Tuning (Pan et al., 2024) 都围绕单个模型做 early-exit 的训练与推理框架。

然而 EE-LLM 推理服务的实际吞吐收益远不及预期。以 CodeLlama-34B 和 Llama2-70B 为例，EE-LLM 相对 vanilla auto-regressive decoding 只提升了 16% 的吞吐（Figure 1(b)），这与 early-exit 的"跳过 50%+ 层"的计算节省不成比例。HELIOS 正是围绕这种落差提出的改进框架。

---

## 2. 要解决的问题

现有 EE-LLM serving 框架吞吐受限的两大根因：

1. **单模型导致 latency 收益上限受困于"难退 token"**。不满足 confidence threshold 的 token 必须继续走剩下的所有层，平均 token 生成延迟被这部分尾部 token 拖累。以 OPT-1.3B 为例，仍有 22%+ 的 token 需要完整 24 层。

2. **无法获得内存节省，batch size 无法放大**。早退深度仅在运行时才确定，框架必须把所有层权重都加载到 GPU 上以应对最坏情况；同时还必须为跳过的层**也**计算并缓存 KV（因为未来的 token 可能走到那里，需要 attend 先前所有 token）。例如 Llama3.1-405B 在 8×B100 节点上光权重就占 52% HBM。结果 EE-LLM 的内存足迹与 vanilla decoding 完全一致。

3. **批处理同步开销**。EE-LLM 下同批内不同 token 的退出层各异，要么等最慢的那个，要么退化为 batch size=1——现有框架默认选后者，直接放弃了 batching 的收益。

---

## 3. 洞察与设计

**关键洞察 1（跨模型互补性）**：不同 EE-LLM 的早退分布是互补的——在模型 A 上没能早退的 token，往往能在模型 B 上早退。作者的实测数据：OPT-1.3B 单独使用时，24 层的模型有 73% token 在前 6 层退出，剩余 22% 走完全部 24 层；但这 22% 中的 57% 只需要 OPT-6.7B 的前 9 层就能退出。联合使用两个模型后，92% 的 token 都能通过早退产出，远高于任一单模型的 73–77%。

**关键洞察 2（低置信 token 往往也不会改变）**：即使一个 token 在早退层没达到 confidence threshold，它在遍历后续层后的预测结果也常常保持不变。OPT-6.7B Layer-9 置信度 0.2 门槛下，92.1% 的 token 在走完全部 32 层后仍与第 9 层的预测一致；即使 threshold 设为 0，也有 85% 不变。CodeLlama-34B 的 Layer-16 甚至有 90% 的 token 不会再变。所以"没过 threshold"≠"预测会错"。

**整体设计**（Figure 4 四步骤）：

1. **Step-1 候选模型选择**。从 Model Repository (MR) 根据 SLO 和硬件约束，用 TopK 筛出 ≤3 个候选模型（默认 3 个）。

2. **Step-2 实时评估**。对每个候选模型用 5 个真实请求做在线 profiling，生成：
   - 早退分布 profile
   - Perplexity（作为 reference-free 的 accuracy proxy）
   - TTFT / TPOT / 吞吐等指标
   结果写入 Performance History Table (PHT)。期间产生的 token 并不丢弃，因为候选池已经过初筛。

3. **Step-3 用最优模型服务 + Greedy Loading**。基于 PHT 中的早退分布，只加载最可能被用到的前 K 层权重（例如 OPT-1.3B 只加载 6 层）。对剩余少量需要更多层的"High-Exit Token" (HT)，HELIOS 权衡两种补救策略：
   - **Option A**: 加载当前模型的剩余层
   - **Option B**: 切换到另一个候选模型的"截断版"（如 OPT-6.7B 只加载 9 层）
   
   决策依据是实时 telemetry 下的总开销。
   
   为避免抖动，HELIOS 维护 **Confidence Breach Counter (CBC)**，只有当连续 100 个 token 内出现 ≥50 次 threshold 未达（CBC_max=50），才触发重新决策。

4. **Step-4 周期性重评估**。每 RI=150 个请求后重新跑 Step-2，适配请求流特征漂移。默认不重选候选池，因为作者实测某些模型（Llama3-8B、Llama2-13B）跨任务稳定领先。

这个设计同时消除了 batching 的同步问题：因为给定某时刻，所有 token 都只走相同的 K 层（当前加载的深度），退出点对齐。

## 4. 实现细节

- **框架**：基于 EE-LLM framework (Chen et al., 2024) 做 fine-tune 和 serving，与先前 EE-LLM 工作保持一致。

- **模型**：
  - Pre-trained EE-LLM：使用 LayerSkip 在 HuggingFace 上开放的 Llama2 (7B/13B/70B)、Llama3-8B、CodeLlama-34B 变体，支持任意层退出。
  - Post-training modified：用 OPT-1.3B 和 OPT-6.7B 作为 base，在 1/4、1/2、最终层插入 auxiliary exit heads，冻结 backbone 微调 50K 步，数据集 RedPajama + The Pile，loss 为各 exit 层 loss 的等权和。

- **硬件**：4×NVIDIA A100 40GB，NVLink all-to-all（400 GB/s），64-core AMD EPYC。大模型用 tensor parallelism：Llama2-70B TP=4，CodeLlama-34B TP=2，其余 TP=1。

- **Accuracy 评估**：采用 Perplexity 作为在线 reference-free 指标。选型考量：
  - Reference-based (ROUGE/BLEU) 需要 ground truth，不可用
  - LLM-based (G-Eval) 需要额外加载评估 LLM，代价过高
  - BLANC 需要反复 mask/re-encode，不适合实时推理
  - 为保证跨模型 Perplexity 公平比较，限定 MR 中模型必须共享 tokenizer 和 vocab

- **数据集**：ShareGPT（主 workload）+ 一个包含 CNN/Dailymail (summarization)、gsm8k (math reasoning)、CodeXGLUE (code)、HellaSwag (completion) 的混合流。

- **关键超参数**：CBC_max=50、window=100、RI=150、每候选模型评估 5 个请求、TopK=3。

## 5. 实验结果

**主吞吐收益**（batch size 限制为 1 以隔离早退贡献，Figure 8）：

| 配置 | 吞吐 vs HELIOS |
|---|---|
| OPT-1.3B 单独 | 1.48× lower |
| OPT-6.7B 单独 | 2.13× lower |

**token 退出分布**（Table 4）：

| 方案 | OPT-1.3B L6 | L12 | L24 | OPT-6.7B L9 | L17 | L32 |
|---|---|---|---|---|---|---|
| OPT-1.3B only | 73.0% | 4.7% | 22.3% | — | — | — |
| OPT-6.7B only | — | — | — | 73.6% | 4.8% | 21.6% |
| HELIOS | 70.19% | 1.38% | 6.78% | 20.90% | 0.14% | 0.61% |

HELIOS 下 91% token 走最浅早退，"走完全模型"的比例从 22% 降到 7.39%（3× 减少）。

**Batch size**（Figure 9，各模型对比）：HELIOS 最高 15.14× batch size 提升。Table 6 memory 足迹：

| 场景 | 单独 (GB) | HELIOS (GB) | 节省 |
|---|---|---|---|
| CodeLlama-34B | 63 | \- | \- |
| Llama2-70B | 129 | 42 | 67.4% |
| Llama2-7B | 12.9 | \- | \- |
| Llama2-13B | 24.8 | 11.5 | \- |

**TTFT / TPOT**（Table 5）：HELIOS 的 TTFT 0.033s（OPT-1.3B 0.042s, 6.7B 0.069s），TPOT 0.008s（降低 46.6% vs OPT-6.7B）。

**Perplexity**：HELIOS 比两模型中较优的 OPT-1.3B 只高 0.01，基本无损。

**Sensitivity 实验**：
- Confidence threshold 增大时 HELIOS 吞吐几乎不变，而单一 EE-LLM 迅速跌落（Figure 10）
- RI=50 时吞吐最高，到 250 递减，默认选 150 做折中（Figure 11）

**多 SLO 泛化**（Appendix E）：HELIOS 也可优化 TTFT（1.39×–2.23× 降低）、accuracy（动态切到大模型）和 energy。

## 6. 批判性分析

1. **基线过弱**：论文主比较对象就是"单模型 EE-LLM"，Related Work 里虽然讨论了 speculative decoding、LayerSkip 的 self-speculative、INFaaS、Clipper 等，但**没有任何一个被纳入实际吞吐/batch size 对比**。特别是 LayerSkip 的自投机解码与 HELIOS 的目标高度重合，缺了这个对比难以证明 HELIOS 的相对优势。

2. **"互补性"的理论基础薄弱**。Insight-1 基于 OPT-1.3B/6.7B 这对同家族模型的实证观察，但为什么不同容量的模型会有互补早退分布？论文没有机制性解释——可能只是"大模型对难 prompt 更稳"的另一个说法，此时 HELIOS 其实退化为"简单 token 用小模型，难 token 用大模型"的级联架构，这是很老的思路（cascaded inference），新意没这么大。

3. **92.1% "token 不变"的泛化性可疑**。这个数字来自 OPT-6.7B + CNN-Dailymail + threshold 0.2 + Layer-9 这一特定组合。Figure 13 虽然给出了 Llama 系列的多模型数据，但都是英文自然语言/代码，**对数学推理（GSM8K）、长链条 reasoning 的影响没有评估**——这些任务对单个 token 的错误非常敏感（错一个数字答案就错了）。Perplexity 也不是好 proxy，它对"正确链式推理"并不敏感。

4. **多模型同时驻留的开销被遮蔽**。Table 6 中"HELIOS 用 CodeLlama-34B + Llama2-70B 只占 42GB"这个数字很惊艳，但它暗中假设 HELIOS 不需要把两个模型的**全部权重**都加载到 GPU。实际部署时，如果早退分布漂移需要临时加载更多层，冷启动延迟（从 CPU/NVMe 加载到 GPU）怎么摊销？论文只在 CBC 机制里含糊地提"evaluate overheads"，没给具体的延迟 breakdown。

5. **关键超参完全经验化**。CBC_max=50、window=100、RI=150、候选 5 请求评估——这些值的 sensitivity 只对 RI 做了简略分析，CBC_max 和 window 完全没有消融。读者无法判断这是否是在 ShareGPT 上过拟合的结果。

6. **Speedup 主要来自模型缩小，不是早退本身**。HELIOS vs OPT-6.7B 吞吐 2.13×，但 HELIOS 大量使用 OPT-1.3B（70% token 走 1.3B 的 L6）——真正的对照组应该是"纯 OPT-1.3B 无早退"，而不是"OPT-6.7B"。把"换小模型"的收益归给"多模型 + 早退"框架，有混淆变量之嫌。

7. **实验规模偏小**。4×A100 40GB，三种模型组合，没有 concurrent request 压力测试（没看到真正意义上的 load testing 数据，如 p50/p99 latency under varying request rate）。MLSys 级别的 serving 论文通常需要至少 hundreds QPS 下的 SLO attainment 数据。

8. **Perplexity 作为 accuracy 代理在代码/数学任务上不合理**。Section 5.2 只用"HELIOS 比 OPT-1.3B perplexity 高 0.01"一句带过，没在 gsm8k 上报 exact match、在 CodeXGLUE 上报 pass@1——这些才是真正决定"answer is correct"的指标。

## 7. AI Infra / MLSys 视角

这篇论文对 LLM serving 研究有几个值得借鉴的点：

1. **"跨模型协同 + 层级 greedy loading"是一个新颖的调度维度**。vLLM 家族关注 KV cache 层面的内存管理，Splitwise/DistServe 关注 prefill/decode 分离，而 HELIOS 展示了"模型本身的层数"也可以当作一个弹性资源 —— 这条轴过去一直被认为"模型是原子的"。可迁移到 MoE 场景：按 expert activation profile 动态决定加载哪些 expert 的完整权重。

2. **Greedy Loading 的思想对 pipeline parallelism 有启发**。PP 现在是静态切分，如果结合运行时 profile，理论上可以让"热点层"在更多 PP stage 上副本化。

3. **PHT + CBC + RI 这套"在线 profile + 惰性切换"的控制循环**是很通用的设计模式，可以推广到 adaptive batch size、adaptive quantization bit-width、adaptive speculative draft model 选择。

4. **值得跟进的具体研究问题**：
   - **跨模型权重复用**：Llama2-7B 和 Llama2-13B 共享同一个 tokenizer 且训练数据高度重叠，它们的浅层是否可以**共享**？如果能共享，HELIOS 的多模型驻留内存开销能进一步压缩。
   - **与 vLLM/PagedAttention 的集成**：HELIOS 声称 KV cache 足迹也减少了（因为只加载 K 层），但没说怎么和 PagedAttention 的分页粒度兼容。这是工业落地的关键障碍。
   - **与 Speculative Decoding 的融合**：HELIOS 本质是"自适应选一个小模型 + 早退"，这和"小模型 draft + 大模型 verify"在动机上高度重叠。一个统一的 adaptive cascaded speculative framework 值得探索。
   - **向 MoE 推广**：MoE 里的 expert 激活稀疏性和这里的"early-exit 分布"有天然对应，HELIOS 的 PHT + CBC 机制可以直接改造为 expert-level 的 selective loading。

5. **如果做延伸工作的最佳切入点**：把 HELIOS 的"greedy layer loading"做得更细 —— 比如 per-request 的 layer 预测（而不是 per-request-stream），结合小型 router model 做 layer prediction。这比全局 RI 粒度精细很多，可能能把 7.39% 的 full-model traversal 进一步压低。

---

## 8. 总结

HELIOS 用两个朴素但有效的洞察——"不同模型的早退分布互补"和"低置信 token 往往也不会改变"——把 Early-Exit LLM 的吞吐和 batch size 分别提升 1.48× 和 15.14×，同时保持 perplexity 损失可忽略。其核心贡献是把"模型选择"从一次性的静态决策变成了运行时自适应的动态策略，并通过 greedy layer loading 把被浪费的后期层权重腾出来给 KV cache。局限在于：基线对比仅限单模型 EE-LLM，未包含 speculative decoding / LayerSkip self-speculative 等同类方法；关键超参（CBC_max、window size）缺乏敏感度分析；accuracy 只用 perplexity 衡量，对代码、数学等任务说服力不足；实验规模限于 3 台 A100 且没有高并发压测。总的来看是一个 solid 的 serving 层工作，适合作为 EE-LLM 方向的 baseline 改进，但离 production-grade serving framework 还有距离。
