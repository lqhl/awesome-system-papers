# BatchLLM: Optimizing Large Batched LLM Inference with Global Prefix Sharing and Throughput-oriented Token Batching

**作者**：Zhen Zheng, Fanghao Zhou, Xin Ji, Chuanjie Liu, Taosong Fang, Gang Peng
**单位**：Microsoft;Chinese Information Processing Laboratory, ISCAS / UCAS
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[a97da629b098b75c294dffdc3e463904.pdf]]

---

## 1. 背景

LLM 正越来越多地被用于搜索引擎、广告、推荐系统等信息处理任务。由于这些任务的数据量巨大且在线 SLO 难以满足,通常会把高频文档/查询放到离线批量处理(或半离线缓存)的通路上,整体的性能指标是**吞吐而非延迟**。

这类任务有两个非常明显的特征:

1. **批量规模大,静态批信息已知**:所有 prompt 在进入推理引擎之前就全部就绪,prompt 的长度、内容、prefix 分布均可以提前分析。
2. **prompt 之间存在显著的 prefix 共享**:例如 snippet 生成任务,同一份网页文档会配不同的 query 生成多个 prompt,文档部分就是共享前缀。更进一步,随着模型推理能力增强以及任务特定微调,system instruction/prompt 模板的作用被压缩,**长 context(如文档正文)成为主要的共享前缀**。

主流推理引擎 vLLM、SGLang 等的核心设计目标是低延迟的流式在线服务,将这类 offline 大批量、强 prefix 共享的场景直接套到它们上面并非最优。

---

## 2. 要解决的问题

作者指出现有 SOTA 推理引擎在 throughput-oriented 批处理场景下存在三个结构性问题:

1. **隐式 LRU prefix cache 无法达到最优 KV 复用**:vLLM 的 radix tree + LRU 策略只基于"历史访问"做缓存淘汰,在大批场景下会过早淘汰"即将被复用"的 KV 块,同时把已经无用的 KV 块保留很久。作者实测一个工业 snippet 生成任务的最优可节省 token 比例是 58.1%,但 vLLM 只做到 35.8%。
2. **面向流式的请求调度和 token-batching 对批场景是次优的**:
   - 按到达顺序调度,无法把共享同一 prefix 的请求聚在一起处理,进一步加剧 LRU 的过早淘汰问题,也延长共享 prefix 的 KV 生命周期。
   - Chunked-prefill 只用 "token 数 + request 数" 做阈值,request 数上限(vLLM 默认 256)一到就无法继续拼 prefill chunk,decoding-dominated 的 iteration 出现大量"token 数谷值",GPU 吃不饱。
3. **Prefix-shared Attention 内核仍有优化空间**:现有实现(如 Cascade Inference)把 prefix 部分的 MatMul 和 distinct 部分的 matrix-vector 拆成独立 kernel,产生 tail effect 和 kernel launch overhead。

---

## 3. 洞察与设计

**关键洞察**:离线/大批的 prompt 全部事先已知,批的长度分布、prefix 分布、共享关系都可以在调度前一次性算清楚。因此**"隐式 LRU cache"完全可以被一个显式、全局的 prefix 组织方式替代**,而且因为性能指标是吞吐不是延迟,调度器有自由度去重排请求、刻意推迟长 prefill 以拼出高利用率的 token-batch。在此前提下,长 context 任务的多级 prefix 可以被压缩到一层,不损失明显的复用比例。

围绕这一洞察,BatchLLM 提出三组相互配合的优化(整体流程如 Figure 3 所示):

**(1) 显式全局 prefix 识别与一层化 (Sec.4.2)**

- 对整个批先建 compact prefix tree(即 radix tree)。
- 由于 tree 的第一层 prefix 未必是"最划算"的共享 prefix,作者在 tree 上跑一个 DP(Algorithm 1):自底向上对每个节点 `d`,先递归优化其子树,然后枚举孙节点 `gchild`,用 `gain = (leaves(gchild) − 1) × tokens(gchild)` 与 `current = tokens(child)` 比较;若 gain 更大,就把 `child` "fork 下来再和 `gchild` 合并",等价于在更深的层做第一层共享。最终整棵树上只保留一层 prefix,其余层当作各请求的 distinct 部分展开。
- 伪 token 例子(Figure 4):6 条 prompt 初始 tree 的第一层共享只能节省 4 个 token,DP 后变成可以节省 8 个 token 的"深层 fork"。
- 工业数据集上多级 prefix 的 token saving 是 56%,一层化后只降到 55%,几乎无损,但大幅简化了下游的 token-batching 和 kernel 设计。

**(2) 基于 prefix-sharing group 的调度与 memory-centric token batching (Sec.4.3)**

- **分组调度**:DP 后每棵子树的 prompt 自然组成一个 prefix-sharing group,调度最小单位从 request 变成 group。同一 group 的请求一齐启动/结束,共享 prefix 的 KV 在整组完成后立即释放,生命周期被压缩到最短。
- **三队列 token-batching**:分别维护 common prefix 队列、distinct prompt 队列、decoding 队列。每个 iteration 按"decoding → distinct prompt → common prefix"顺序从三个队列取 token,这样 decoding 先发射,能和后来的长 prefill chunk 拼在同一 batch;active 请求先于 inactive 请求调度,尽早释放内存。
- **按 R 重排 group**:
  $$R_{group} = \frac{1}{L_{fprefix} + \sum L_{distinct}}$$
  (output 长度用数据集经验值归一化为 1)。R 越大的 group 越靠前,使"decoding 占比高"的请求更早进入流水线,方便和后面的长 prefill 混在一起(Figure 1)。
- **Memory-centric batching**:放弃 "request 数量" 作为硬上限,改成用 KV 显存容量阈值 `M_threshold` 作为唯一的硬约束 + chunk size `S_chunk` 作为软上限。只要剩余显存足够装下新 prefill chunk 的 KV,就可以继续拼,直接消灭"decoding 已满 256 但 GPU 还有大量空闲"的 valley(Figure 2 vs Figure 9)。

**(3) Prefix-shared Attention 的水平融合 (Sec.5)**

- 把 prefix 部分(MatMul 形态)和 distinct 部分(matrix-vector 形态)塞进一个 Triton kernel,用不同 thread block 跑不同的分片,两块各自 auto-tune 自己的 tiling。
- 这样一次 kernel launch 完成 partial attention + online softmax 的大部分工作,显著减少 tail effect 和 launch overhead。
- 选用 Triton 的代价是单纯 FlashAttention 部分在 A100 上仍比 CUDA 版慢,但带来的好处是同一份实现可以跑 NVIDIA 和 AMD(MI200),工业部署价值高。

## 4. 实现细节

- **Prefix 识别模块**:独立的 Python 预处理脚本,接受 nested input_ids,输出 prefix-sharing group 的元组列表 `(prefix_tokens, [distinct_0, distinct_1, ...])`。
- **调度和 token-batching**:集成在 vLLM v0.6.4 上,在其 token batching 函数之上实现 group-wised 调度、三队列结构、memory-centric 约束。Baseline 也用 vLLM v0.6.4。
- **Attention 内核**:用 OpenAI Triton 实现,利用 Triton 内置 autotuner 调 tile size;对 launch overhead 做 AOT 优化 —— NVIDIA 上 warm-up,AMD 上用 AOTriton。
- **Prefix 一层化的离线开销**:8000 请求的工业数据集上 DP 只需 1.51 秒,端到端执行 919.54 秒,开销 <0.01%,基本忽略不计。

## 5. 实验结果

**平台**:NVIDIA A100 80GB (CUDA 12.1) 和 AMD MI200 (ROCm 6.1);Ubuntu 20.04,EPYC 7V12。
**模型**:Llama-3.1-8B、Qwen-2.5-14B、Llama-3.1-70B (4-bit GPTQ)、Qwen-2.5-7B(工业任务)。
**Baseline**:vLLM v0.6.4(+ prefix-caching / + chunked-prefill 各种组合),SGLang v0.4.1。

**端到端微基准(Figure 5/6)**:

- 最强 vLLM 配置(+ prefix-caching + chunked-prefill)作为对照,BatchLLM 在 A100 上加速 1.4–3×,MI200 上 1.8–4.1×。
- 对 SGLang 分别加速 1.2–2.5×(A100)和 1.3–2.8×(MI200)。
- 共享度越大、共享 prefix 越长,优势越明显:prefix 长 16000、share-degree 16 时,BatchLLM 相对最佳 baseline 加速 **10.8× / 9.5×**(vLLM / SGLang)。
- 作者还做了"vLLM + python sorted() 预聚合同 prefix"的对照:vLLM 吞吐从 6 提到 13.02,BatchLLM 仍然是 18。说明即使强行帮 vLLM 排序,BatchLLM 仍靠一层化 attention + 更好的 batching 保持领先。

**工业 snippet 生成任务(Table 1)**:Qwen-2.5-7B,8000 查询,avg share-degree ≈ 3,avg prefix ≈ 1570 token,avg distinct ≈ 30 token。

| 配置 | A100 吞吐 | MI200 吞吐 |
|---|---|---|
| vLLM | 5.45 | 2.75 |
| vLLM + chunked-prefill | 5.48 | 2.84 |
| vLLM + prefix-caching | 6.2 | 3.27 |
| vLLM + c + p | 6.71 | 3.36 |
| BatchLLM | **8.67 (1.30×)** | **4.24 (1.26×)** |

**Token saving 比较(Figure 8)**:

- 微基准 prefix=2000 / sd=16:vLLM(c+p) 40.1%,BatchLLM **85.2%**(达到理论上界)。
- 微基准 prefix=16000 / sd=16:vLLM 6.3%,SGLang 5.2%,BatchLLM **92.6%**,随 prefix 变长 LRU 的崩溃更严重。
- 工业数据:vLLM(c+p) 35.8%,BatchLLM 58.1%。

**Token-batching breakdown(Table 2 + Figure 9)**:在工业任务上对 token-batching 做消融,BatchLLM 关闭 token-batching 优化后 8.16,开启后 8.47。Figure 9 表明 memory-centric batching 明显压平了 Figure 2 中的"token 数 valley"。

**Kernel 对比(Figure 10)**:与 CUDA 版 FlashAttention、Triton FlashAttention 和 Cascade Inference 对比。尽管 Triton FA 本身弱于 CUDA FA,BatchLLM 的水平融合 kernel 在 chunked-prefill 场景下多数 case 与 Cascade Inference 相当或更优;不过在"共享 prefix 远长于 distinct 部分"的长 KV 场景下不及 split-k 方案,作者列为后续工作。

## 6. 批判性分析

1. **1.3×–10.8× 跨度过大,宣传数字容易被平均化解读**。最耀眼的 10.8× 出现在 prefix=16000 / sd=16 的极端条件下,此时 vLLM 的 LRU cache 实际被摧毁(命中率只剩 6.3%),baseline 被严重低估;**真正贴近工业场景的数字是 snippet 任务的 1.26–1.3×**。论文 abstract 同时抛出两个数值并无错,但现实部署中应以后者为基准预期。

2. **"output 长度近似恒定"的假设对哪些任务成立作者没量化**。group reorder 的 `R_group` 完全丢掉了 decoding 长度信息,只保留 `1 / (L_prefix + ΣL_distinct)`。这对 snippet 这种"同任务输出长度高度集中"的场景合理,但对多样化 offline 场景(如对文档做摘要 + QA + 翻译混合批)会降级。论文提到"对多个任务做了 profiling 发现 output 分布集中",但未给出 σ / 分位数,也没有 output 长度方差大时的退化实验。

3. **多级 prefix 只损失 1% 的结论强依赖于"长文档主导 prefix"**。作者论证第一层一层化的合理性时,核心论据是"新 LLM 推理增强 + 任务微调让 instruction 变短,文档正文主导 prefix"。但对还没微调的通用部署(比如大量场景仍然靠长 system prompt + 模板),多级 prefix 的复用比例差距可能远大于 1%,DP 的 "fork + merge" 会浪费掉上层 instruction 的共享。

4. **Group 粒度调度的延迟/公平性代价未评估**。同一个 group 的请求被强行"同时启动、同时完成",离线场景没问题;但一旦混入带 SLO 的在线流量(比如 hybrid 在线/离线),晚到的同 prefix 请求要等下一 group 才能复用,反而把单请求延迟拉长。论文没讨论在 workload 混合场景下的表现。

5. **Memory-centric batching 的"valley 消除"是在关闭 prefix-sharing 条件下展示的**。Figure 9 的 caption 特意标注 "Prefix-sharing disabled to demonstrate general batched/offline inference efficacy",意味着 prefix-sharing 场景下 valley 是否被同样干净地消除,读者无法直接从图上看出。Table 2 的端到端 0.31 绝对提升(8.16→8.47)也只是个位数百分比,和微基准里的放大倍数不在一个量级。

6. **Triton 实现承认比 CUDA FlashAttention 慢,作者用"跨 NVIDIA/AMD"的工程性优势合理化**,但 ablation 只给了 kernel 层面的对比,没有给"如果把 batching/scheduling 创新挪到 CUDA 后端(例如 FlashInfer)"会怎样的对照。换句话说,BatchLLM 的系统收益是否依赖"恰好 Triton 实现也够用",缺乏独立验证。

7. **Cascade Inference 的对比边界值得警惕**。Cascade Inference 本身也是 prefix-aware attention,BatchLLM 相对它的 kernel-only 收益大部分在于水平融合而不是算法突破;而论文的端到端增益里有相当部分来自 **"vLLM 的 LRU 对长共享很差"**,这部分只能说明 vLLM 目前还没做这类 offline 路径,并不意味着 BatchLLM 的技术一定是唯一或最优解。

## 7. AI Infra / MLSys 视角

这篇论文几乎可以视为一份 "offline LLM inference" 的系统设计模板,对 AI Infra 研究有若干可直接借用的点:

1. **"调度前拥有完整批信息"是一个被严重低估的假设**。现在主流 inference engine 都默认"请求流式到达、未来未知"的世界观,但大量企业级场景(离线排序、BI 报表、搜索索引 build、指令调优 SFT 的数据合成、RL rollout)都是纯离线批。把 scheduler 从 online 模型里解耦出来,专门做一条 "静态信息可见"的 offline lane,整体吞吐提升空间非常大 —— BatchLLM 的工业数据 1.26–1.3× 只能算基线。可跟进方向:把 BatchLLM 的思想推广到**多模型混合批**(多个 LoRA、多个 expert)的全局调度。

2. **Memory-centric batching 是个可迁移的设计原则**。"用显存容量 + chunk size 做硬约束,而不是 request 数"这点不只适用于 prefix-shared 场景,对普通 chunked-prefill 也可能有收益(Figure 9 恰好是在关闭 prefix-sharing 的条件下展示 valley 消除的)。可将其抽象为 **"资源-中心化的 continuous batching"** 框架,把 KV memory、SRAM 占用、NVLink 带宽等都纳入统一的 admission control。

3. **DP-based prefix tree refactoring 是个工具性贡献**。一层化的思路与其说是性能优化,不如说是"把复杂结构压扁以匹配 kernel fast path"的工程模式,未来在 MoE routing、speculative decoding 的 draft tree 剪枝、RAG 多级 cache 结构整理中都能复用。

4. **可操作的未来研究点**:
   - **R_group 的数据驱动化**:用一个轻量的 length predictor 替换 "output 长度恒定" 的假设,在 group 内、group 间做二次排序,对 output 长度方差大的任务应该能继续挤性能。
   - **Offline + online 混合 lane**:保留 BatchLLM 的 group 调度作为 offline 通道,用 priority 把 online 请求插进来,研究如何在不破坏 prefix 聚合的前提下满足 SLO(与 Fairness in Serving LLMs 那一脉工作的 orthogonal 组合)。
   - **Prefix-aware disaggregation**:把 BatchLLM 的 DP 一层化和 Mooncake / MemServe 这一类 KV pool 结合,预先把热 prefix 挂到 prefill 节点上,batch 级别的亲和性调度。
   - **Kernel 层**:把水平融合和 split-K 自动切换做进 FlashInfer/FlashAttention 的 template,根据 prefix/distinct 长度比自动选 path,解决论文末尾自认的"long-KV 劣势"。

5. **对小型实验室友好的切入点**:DP 前缀识别和 prefix-sharing group 调度这两块是**纯 Python + 工程**实现(<500 行量级可以复现),不需要 GPU 大集群;在自己的 vLLM fork 上跑一个 offline ranking/snippet 数据集,就能复现 30%+ 的吞吐提升,非常适合做 ablation 驱动的 follow-up 论文。

---

## 8. 总结

BatchLLM 针对"大批量 + 强 prefix 共享 + 吞吐导向"的 LLM 推理场景,做了一套自洽的系统优化:把 LRU 隐式 prefix 复用替换为 DP 驱动的全局一层化 prefix 提取,用 prefix-sharing group 作为调度单位并按 R_group 重排,用显存容量而不是请求数做 batching 硬约束,最后用水平融合的 Triton attention 内核压掉 kernel 级开销。端到端在微基准上相对 vLLM/SGLang 最佳配置加速 1.3×–10.8×,在真实的 snippet 生成工业数据上有 1.26–1.3× 的可靠收益。局限在于"output 长度相对集中""prefix 以长文档为主"的假设对非 snippet 类场景可能打折,且方案面向纯 offline,对 hybrid 在线/离线流量的兼容性尚未验证。整体上是一篇"规模化 LLM 离线服务"方向结构清晰、工程价值高的系统工作。
