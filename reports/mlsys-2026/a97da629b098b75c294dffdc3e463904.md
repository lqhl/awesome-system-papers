# BatchLLM: Optimizing Large Batched LLM Inference with Global Prefix Sharing and Throughput-oriented Token Batching

**作者**：Zhen Zheng, Xin Ji, Taosong Fang, Fanghao Zhou, Chuanjie Liu, Gang Peng（Microsoft, ISCAS/UCAS）
**会议**：MLSys 2026
**链接**：[arXiv:2412.03594](https://arxiv.org/abs/2412.03594)
**源文件**：[[a97da629b098b75c294dffdc3e463904.pdf]]

---

## 一、背景

LLM 正被大规模应用于搜索引擎（snippet generation）、广告、推荐系统等信息处理任务。这类任务通常以大批量或离线方式执行，核心性能指标是吞吐量而非延迟。同时，不同 prompt 之间天然存在 prefix sharing 特性——例如搜索引擎中同一网页文档被多个查询共享。

现有推理引擎（vLLM、SGLang）主要面向在线 streaming 场景优化，在大批量吞吐场景下存在三个核心问题：(1) LRU-based implicit prefix caching 无法实现全局最优的 KV 复用；(2) 面向在线服务的调度和 token batching 策略无法充分利用 GPU；(3) prefix-shared Attention kernel 存在 tail effect 和 kernel launch overhead。

---

## 二、要解决的问题

1. **Prefix 过早驱逐**：vLLM 的 LRU cache 在大批量场景下会过早驱逐即将被复用的 KV context，同时保留不再使用的 KV context。实测中，最优 token saving ratio 为 58.1%，但 vLLM 仅达 35.8%。

2. **Token batching 不充分**：现有系统按 FCFS 顺序调度请求，不聚合共享前缀的请求；以 request 数量而非 memory 为阈值限制 batch size，导致 decoding-dominated iterations 出现大量"valleys"（GPU 利用率低谷）。vLLM 默认 256 request 上限，即使内存充裕也无法继续 batch。

3. **Attention kernel 开销**：现有 prefix-shared Attention 在 prefix 和 distinct 部分分别启动独立 kernel，多级 prefix 进一步放大 tail effect 和 launch overhead。

---

## 三、洞察与设计

**关键洞察**：在大批量/离线推理场景中，所有 prompt 的特征（长度、prefix 结构）在处理前就已知，因此可以利用这些全局信息进行 ahead-of-time 的 prefix 识别、请求重排和 memory-aware batching，而非依赖运行时的隐式 LRU 缓存策略。

基于此洞察，BatchLLM 提出三层优化：

### 1. Explicit Global Prefix Identification
- 在整个 batch 上构建 compact prefix tree（Radix tree），显式识别所有共同前缀
- 观察到工业任务中多级 prefix 长度由单一层级（如网页文档）主导，因此设计 DP 算法将多级 prefix 简化为单级 prefix，在 token reuse 仅损失约 1% 的条件下大幅降低系统复杂度
- DP 算法自底向上遍历 prefix tree，对每个节点判断是否将子节点的 prefix merge 到父节点：当 `(leaves(gchild) - 1) × tokens(gchild) > tokens(child)` 时执行 fork-and-merge

### 2. Throughput-oriented Token Batching
- **Prefix-sharing group scheduling**：将共享同一 prefix 的请求组织为 group，以 group 为调度单位，确保 prefix KV 被完整复用后立即释放
- **Request group reordering**：按 `R_group = 1 / (L_prefix + ΣL_distinct)` 排序，优先调度 decoding 占比大的 group，使其 decoding tokens 能与后续长 prefill chunks 混合
- **Memory-centric token batching**：以 KV memory 使用量（而非 request 数量）作为 batch 限制阈值，允许在 decoding-dominated iterations 中 batch 更多 tokens，消除"valleys"
- 维护三个队列（common prefix / distinct prompt / decoding），按 decoding → distinct → prefix 顺序取 token 组 batch

### 3. Horizontal Fused Prefix-shared Attention
- 将 prefix 和 distinct 部分的 partial Attention 计算融合到同一 GPU kernel，不同部分在不同 thread blocks 执行
- 使用 auto-tuning 为两部分分别选择最优 tiling 配置
- 基于 OpenAI Triton 实现，同时支持 NVIDIA 和 AMD GPU

---

## 四、实现细节

- **Prefix 识别**：Python 独立预处理脚本，输入 nested token id lists，输出 prefix-sharing group tuples `(prefix_tokens, [distinct_0_tokens, distinct_1_tokens, ...])`。8000 requests 处理耗时仅 1.51 秒（<0.01%）
- **Token batching**：集成在 vLLM v0.6.4 中，定制 group-wise scheduling 和 token batching 逻辑，替换原有的 per-request scheduling
- **Attention kernel**：Triton 实现，支持 AOTriton（AMD）和 warm-up compilation（NVIDIA）减少 launch overhead。限制是 Triton FlashAttention 性能仍低于 CUDA 版本
- 预定义 KV memory threshold `M_threshold` 和 chunk size `S_chunk` 作为 batching 参数

## 五、实验结果

**硬件**：NVIDIA A100 80GB、AMD MI200

**模型**：Llama-3.1-8B、Qwen-2.5-14B、Llama-3.1-70B（4-bit GPTQ）、Qwen-2.5-7B

### Microbenchmark（6400 requests）

| 对比基线 | A100 加速比 | MI200 加速比 |
|---|---|---|
| vs vLLM + prefix-caching + chunked-prefill | 1.4×–3× | 1.8×–4.1× |
| vs SGLang | 1.2×–2.5× | 1.3×–2.8× |

Sharing degree 和 prefix 长度越大，加速越显著。当 shared prefix = 16000、sd = 16 时，vLLM/SGLang 的 token reusing ratio 仅 6.3%/5.2%，BatchLLM 达 92.6%，加速比 10.8×/9.5×。

### Industry Workload（snippet generation, Qwen-2.5-7B, 8000 queries）

| 系统 | A100 吞吐 | MI200 吞吐 |
|---|---|---|
| vLLM + c + p | 6.71 | 3.36 |
| BatchLLM | 8.67 (1.30×) | 4.24 (1.26×) |

### Token Saving Ratio

| 场景 | vLLM + c + p | BatchLLM | 最优上界 |
|---|---|---|---|
| Industry workload | 35.8% | 58.1% | 58.1% |
| Micro (prefix=2000, sd=16) | 40.1% | 85.2% | 85.2% |

### DP 算法 Prefix 简化

多级 prefix saving ratio 56% → 简化为单级后 55%，仅损失 1%。

## 六、批判性分析

1. **Industry workload 加速比远低于 microbenchmark**：论文标题和摘要突出 1.3×–10.8× 的加速范围，但实际 industry workload 仅 1.26×–1.30×。这是因为真实工作负载的 sharing degree 平均仅约 3、prefix 平均 1570 tokens，远不如 microbenchmark 中 sd=16、prefix=16000 的极端设置。论文对此差异未做充分讨论。

2. **Workload 假设较强**：整个优化建立在"所有 prompt 提前已知"的前提上，适用于纯离线/大批量场景。但论文对 semi-online（持续到达的小批量）场景缺乏讨论。当 batch 规模不够大或 prefix sharing 程度低时，全局分析的收益会迅速递减。

3. **Output 长度假设为常数**：Request reordering 依赖 R = L_decode / L_prefill 排序，但论文假设所有 request 的 output 长度相同（"normalize L_prefill into 1 for all requests uniformly"）。虽然声称工业任务 output 长度分布集中，但未给出具体分布数据或假设失效时的性能退化分析。

4. **Triton vs CUDA 的性能差距被轻描淡写**：论文承认 Triton FlashAttention 性能低于 CUDA 版本，但仍选择 Triton 以支持跨平台。Kernel benchmark 中 BatchLLM 的 Triton kernel 在某些 case 下甚至不如 CUDA Cascade-Inference，但论文将此归结为"Triton compiler 的局限"而非设计问题。

5. **Baseline 版本较旧**：vLLM v0.6.4、SGLang v0.4.1 在论文提交时已非最新版本。vLLM 后续版本可能已改进 prefix caching 策略（如 hash-based eviction 改进），baseline 的代表性存疑。

6. **缺少与 sorted vLLM 的完整对比**：论文在 6.2.1 节末尾提到将 vLLM 请求按 prefix 排序后吞吐从 6 提升到 13.02（而 BatchLLM 为 18），说明简单排序已能获得大部分收益。但这一重要 baseline 只在单一配置下报告，未在所有实验中系统对比。

## 七、AI Infra / MLSys 视角

1. **离线/批量推理是被忽视的重要场景**：学术界和工业界对 LLM serving 的关注集中在在线服务的延迟优化，但信息处理类任务（搜索 snippet generation、广告排序、推荐）的离线推理量巨大。BatchLLM 指出了这一 gap，其"利用全局信息优化"的思路值得在更多离线场景中推广。

2. **Prefix sharing 的显式管理 vs 隐式缓存**：论文最核心的贡献是证明在 batch 已知的前提下，显式的 prefix 识别和调度远优于 LRU-based implicit caching。这一 insight 可迁移到 RAG 场景（多文档共享 system prompt）、multi-turn 对话（共享 conversation history）等。

3. **Memory-centric batching 的启示**：用 KV memory 而非 request 数量作为 batching 限制，是一个简单但有效的设计转变。这一思路对 disaggregated inference（prefill/decode 分离部署）的 decode 端调度也有借鉴意义。

4. **可跟进的研究方向**：
   - 将 BatchLLM 的全局 prefix 优化与 speculative decoding 结合，在大批量场景中进一步提升吞吐
   - 将 explicit prefix management 扩展到 disaggregated serving 架构，在 prefill node 和 decode node 之间高效传递 prefix group 信息
   - 研究 semi-online 场景下的增量 prefix tree 更新策略，使 BatchLLM 的优化能适用于持续到达的请求流

---

## 八、总结

BatchLLM 针对大批量离线 LLM 推理场景，利用所有 prompt 提前已知的全局信息，提出显式 prefix 识别（DP 算法简化多级 prefix）、throughput-oriented token batching（group scheduling + request reordering + memory-centric batching）和 horizontal fused Attention kernel 三层优化。在 microbenchmark 上加速 1.3×–10.8×，在工业 workload 上加速约 1.3×。系统设计简洁有效，但适用场景限于大批量离线推理且 prefix sharing 程度较高的任务，对在线或低 sharing degree 场景的价值有限。
