# FP8-Flow-MoE: A Casting-Free FP8 Recipe without Double Quantization Error

**作者**：Fengjuan Wang, Zhiyi Su, Xingzhu Hu, Cheng Wang, Mou Sun
**单位**：Zhejiang Lab
**会议**：MLSys 2026
**链接**：[MLSys 2026 Proceedings](https://proceedings.mlsys.org/paper_files/paper/2026)
**源文件**：[[072b030ba126b2f4b2374f342be9ed44.pdf]]

---

## 1. 背景

大规模 Mixture-of-Experts(MoE)模型已经成为现代 LLM 的主流形态 —— 例如 DeepSeek-V3(671B)只激活部分专家即可达到 dense 模型难以企及的容量/成本比。但专家数量的爆炸式增长带来了严重的显存、计算和通信压力,训练一次动辄消耗几千张 H100 卡月。

为缓解这一压力,低精度训练从 FP16/BF16 一路走到 FP8。Hopper 架构原生提供 FP8 Tensor Core,理论上可将算力翻倍、通信量减半。DeepSeek-V3 率先在数千亿参数尺度验证了 FP8 训练的可行性,并开源了两个关键内核:DeepGEMM(grouped GEMM)和 DeepEP(cross-node all-to-all)。但这两个组件只解决了 GEMM 与通信单点效率问题,一条端到端的 FP8 训练 recipe 仍然缺位。

FP8 训练当前的主流整合方式仍以 BF16 dataflow 为骨架,只在 GEMM 和部分通信 kernel 边界处做 FP8 加速,因而伴随大量 quantize-dequantize(Q/DQ)cast。本文正是为填补这一 gap 而生。

---

## 2. 要解决的问题

本文聚焦两个互为因果的问题:

1. **Cast 密集带来的效率损失**:在 BF16-centric 的 dataflow 中,DeepSeek V3 风格的 FP8 实现一个 MoE forward-backward 过程会插入多达 **12 次 Q/DQ cast**。作者通过 DeepEP 实测发现,单对 Q/D 大约将通信端的 FP8 加速比从 1.6× 砍到 1.4×;一个 MoE 层累积约 3 对 Q/D,FP8 内核的理论收益被几乎抹平 —— 甚至有时低于 BF16 baseline。额外的 cast 还引入中间张量拷贝,削弱 FP8 本该带来的显存节省。
2. **朴素去 cast 会产生 "double quantization error"**:如果直接把所有张量保留为 FP8、跳过中间 BF16 storage,就会遇到一个数值稳定性问题。MoE grouped linear 需要在 Fprop/Dgrad 用 row-wise 量化、在 Wgrad 用 column-wise 量化;两种 layout 的 scaling factor 是沿不同维度统计 per-tile max 得到的,一般不相等。在 row-wise 量化的 FP8 张量上直接做 column-wise 再量化,等价于在两个互不对齐的离散网格间做二次映射,rounding error 会被放大,造成方向性的精度损失和收敛不稳。公式上:

   $$E = Q_{col}(D(Q_{row}(X))) - Q_{col}(X) \neq 0$$

   之前的 FP8 MoE 实现为了回避这个问题,只能用 dequantize → transpose → requantize 的朴素三步法,把两次量化绕回 BF16 中转 —— 但这正是上一个问题的根源。

核心难题在于:**要么引入冗余 cast 吃掉 FP8 收益,要么直接接受 double quantization error 损失收敛性**。现有系统只能在两者之间折衷,无法兼得。

---

## 3. 洞察与设计

**关键洞察**:**当 scaling factor 被约束为 2 的幂时,row-wise 与 column-wise 两种量化 layout 之间的转换不再涉及 rounding —— 只需要在 FP8 编码上调整 exponent bit 即可精确互转,完全无需 dequantize/requantize。**

具体推导:设 row-wise 的 tile scale 为 $s = 2^T$,column-wise 的 tile scale 为 $s' = 2^{T'}$。若两者都是 2 的整数次幂,那么 $s/s'$ 也是 2 的整数次幂,相当于在 FP8 E4M3 的编码里把 E 位减去 $D = T' - T$、把 scale 加上 $D$,最终的实数值保持不变(前提不溢出/下溢)。对应地,原来需要三步完成的 transpose + 跨 layout 量化就被替换成一次"**调 exponent + 改 scale**"的 in-place 操作,作者称为 **Direct Transpose**(Algorithm 1)。实测显示 Direct Transpose 相对 naive 三步法有 **2–3× 加速**。

![Fig 1: 不同张量形状下 Direct Transpose 相对 naive 转换的加速比](../../markdowns/mlsys-2026/072b030ba126b2f4b2374f342be9ed44/images/49eb689a88acb8ddd53a961ec66a0e86a25086c9af1dcf5fb4062825cc9d51ff.jpg)

基于这一洞察,作者进一步提出 **FP8-Flow-MoE**,一个 FP8-centric 的端到端 dataflow:

- 整个 MoE 层(router → dispatch → permute+padding → grouped linear 1 → activation → grouped linear 2 → unpermute+unpadding → combine)的中间表示**一律保持 FP8**,只在两处保留 BF16:
  1. grouped linear 1 输出到 activation function 之间(因为 SwiGLU/GELU 等非线性会放大量化误差,reduction 本身又易溢出);
  2. grouped linear 2 到 combination/dispatch 的反传路径(同样涉及 reduction)。
- 其他所有 stage、包括通信路径,都只传 FP8 tensor + 其 scaling factor。
- 通过 Direct Transpose 在 Wgrad 处完成 row/col layout 切换,回避 double quantization error。

端到端 cast 次数从 DeepSeek V3 实现的 **12 次降到 2 次**,实现了"casting-free"。四种 dataflow 形态对比如下:

## 4. 实现细节

FP8-Flow-MoE 的落地依赖三个核心算子的新实现与融合,且与 NVIDIA TransformerEngine、Megatron-LM 兼容。

**(1) Scaling-aware Transpose(Algorithm 1)**

- 输入 row-wise 量化的 FP8 张量 $X^{row}$ 与其 scaling factor $S^{row}$
- 对每个 128×128 block:取 $S_{max} = \max S_{i,\cdot}^{row}$,将 column-wise scaling $S^{col}$ 全部对齐到 $S_{max}$(避免溢出);对 block 内每个元素,通过 $k = \log_2(S_{max}/S_{i,\cdot}^{col})$ 计算需要偏移的 exponent 位数,在 FP8 编码里把 E 替换为 $E - k$ 即得到 column-wise 版本
- 全程无 dequantize/requantize,无 FP32 中转

**(2) Fused Permute + Padding / Unpermute + Unpadding**

FP8 GEMM 要求每个 expert 的输入 token 数是 16 的倍数,于是在 permute(让同一 expert 的 token 内存连续)之后必须再做一次 padding。作者把两个 element-wise、互不依赖的 pass 融合成单 kernel,通过 thread-block mapping 直接把重排后的 token 写到 padded layout 中的目标 offset,省掉一次全量 HBM 读写和 kernel launch 开销。反向做对称的 unpermute+unpadding 融合。

![Fig 3: Fused permute+padding 在 BF16/FP8 下的加速](../../markdowns/mlsys-2026/072b030ba126b2f4b2374f342be9ed44/images/e7f77321292881b5e996e58fa653803bcc78b62a3592be567021c1f25ed37f21.jpg)

![Fig 4: Fused unpermute+unpadding 的加速(反向更大)](../../markdowns/mlsys-2026/072b030ba126b2f4b2374f342be9ed44/images/968a2ffeb27f45e27d57392dcf93acee2557849746e0e77b96e31919a1791ef7.jpg)

- 前向 fused permute+padding:最高 1.7× 加速
- 反向 fused unpermute+unpadding:最高 6.6× 加速

**(3) Fused SwiGLU + Quantization**

SwiGLU 之后紧跟着一次 row-wise 量化,如果按独立 kernel 排布会多一轮 HBM 往返。作者把 SwiGLU 与 FP8 量化融合为单 kernel,直接输出 FP8 tensor + scale,无额外 BF16 中转缓冲。实测融合版本与 Megatron 原生 SwiGLU 的 latency 基本一致,意味着 "顺手做了量化" 的边际开销接近零。

![Fig 5: Fused SwiGLU+quantization 在多种 tensor shape 下的性能](../../markdowns/mlsys-2026/072b030ba126b2f4b2374f342be9ed44/images/4586433e6ecb01b4e2513151f84f07f57275933496e87912bb36433a478be8d4.jpg)

**(4) 与 DeepEP 集成**:通信路径直接发送 FP8 tensor + scaling factor,不在 send/recv 边界再做 Q/D。FP8 通信理论上减半,但实际要同时传 scale,buffer 翻倍,实测加速上限约 1.6×。

其中多个 kernel 已被合入 NVIDIA/TransformerEngine 上游;作者声明其余将很快开源。

## 5. 实验结果

**实验平台**:32 节点 NVIDIA Hopper 集群,每节点 8 张 80GB H100,共 256 卡。所有 end-to-end 实验关闭 compute-comm overlap,以隔离计算效率因素。

### 5.1 收敛性验证(DeepSeek-V2-Lite,16B)

在 200B tokens 上对比 BF16 vs FP8-Flow-MoE,同等超参/学习率/data order/并行度。

![Fig 6: 200B tokens 训练 loss 曲线(BF16 vs FP8-Flow-MoE)](../../markdowns/mlsys-2026/072b030ba126b2f4b2374f342be9ed44/images/dd485b69da461b6461578fa1e99a5becd2cf49f064fc49cf42afc30a7d2fab7e.jpg)

两条 loss 曲线从 warm-up 到稳定段几乎重合,没有梯度 underflow、数值漂移或发散。

### 5.2 效率评估(DeepSeek-V3,671B)

三种 recipe 对比:**BF16 baseline** / **Blockwise**(TE 风格,FP8 限 grouped GEMM)/ **FP8-Flow-MoE**。三种 EP/PP 配置:8/32、16/16、32/8。两种 activation checkpointing:`AC=full`(全层)、`AC=sel (+MoE expert)`(选择性,不 checkpoint expert,用以检验 FP8 对激活显存的压缩)。指标:TGS = tokens/GPU/s,Mem = 峰值显存 GB。

## 6. 批判性分析

**(1) 关键洞察的适用边界被含糊处理**

整个 Direct Transpose 的正确性前提是 **scaling factor 被约束为 2 的幂**(UE8M0 表示)。但在 DeepSeek 与 TransformerEngine 的生产实现里,scaling factor 常常是 FP32 标量,并非严格的 power-of-two。论文在推导正文里假设 $s = 2^T$,在 Algorithm 1 里又写 "align all scaling factors within a transposed block to the largest one" —— 这一对齐步骤本身就意味着:
- 如果原 scaling 不是 power-of-two,对齐会引入精度损失;
- 如果原 scaling 是 power-of-two,对齐到 block 内 max 等价于把其他 tile 的动态范围"压低",小尺度 tile 的 MFU 会显著下降。

论文对这个 trade-off 几乎没有量化讨论,只说"provided that no overflow or underflow occurs",这一前提在大规模 MoE 训练中的实际满足程度应当通过专门实验说明。

**(2) 数学推导与代码有多处表述问题**

- Eq. (1) 括号不闭合、Eq. (16)/(17) 编号空挂无公式体,Algorithm 1 中 $k = \log_2(S_{max})/S_{i,\cdot}^{col}$ 明显应为 $\log_2(S_{max}/S_{i,\cdot}^{col})$;Eq. (9) 之后的等式链条也存在编号错位。虽然这些多为排版问题,但对以 "scaling-aware" 为核心卖点的算法而言,严谨性在 camera-ready 版本里理应更高。
- "align all scaling factors within a transposed block to the largest one (to avoid overflow)" 与论文前面 "scale between row/col layouts 可无损转换" 的叙述是有轻微冲突的 —— 后者的精确性需要每个 tile 各自的 scale;一旦 block 内统一到 max,就回到了 coarser-grained 量化,精度会劣化。这一细节对收敛曲线的影响论文没提。

**(3) 实验设计的隐藏弱点**

- **收敛性只在 16B / 200B tokens 上验证,但效率实验全在 671B 上**。最有说服力的证据应该是 671B 上跑通几千步、loss 曲线与 BF16 重合,但论文显然没跑完(671B × 200B tokens 算力巨大)。纯粹用 16B 的收敛结果外推 671B 略显单薄,尤其考虑到 MoE 规模放大后路由的长尾效应会放大低精度的敏感性。
- **"up to 21%" 的表述容易误导**。EP8 下相对 Blockwise 只提升 3%,相对 BF16 只 6%;只有在 EP32 这个"baseline 快撑不住"的配置下才冲到 21%。文章主推 21%,但 EP8/EP16 才是更常见的生产配置。
- **BF16 / Blockwise 在 EP32+`AC=sel` 下 OOM** 被作为 "memory superiority" 的关键证据。但这是 baseline 的 AC 策略没有匹配到对应 workload,并不完全说明 FP8-Flow-MoE 的方法论优势 —— 如果 baseline 选更激进的 AC 或者 tensor parallel,OOM 可能也能缓解。
- **关闭了 compute-comm overlap**。作者解释是"isolate computation efficiency",但真实训练里 1F1B + overlap 是标配,在这个 setting 下 FP8-Flow-MoE 的 end-to-end 收益可能缩水。
- **没有和 DeepSeek V3 的原生 FP8 实现直接比**。Blockwise 对应的是 TE,比较的是 "只在 GEMM 里做 FP8";但 DeepSeek V3 本来就是 persistent FP8 dataflow(论文 Fig 2(c) 承认这一点),为什么不直接 head-to-head 对比?可能是因为 DeepSeek V3 训练框架未完全开源,但缺少这个比较让 "21% 提升" 的归因少了一个重要参照点。

**(4) "12 cast → 2 cast" 的措辞有营销嫌疑**

DeepSeek V3 在通信阶段是 FP8,不必按论文 Fig 2(c) 那样画出那么多 Q/D。真实 V3 实现里,每个 MoE forward 大致 4 对 Q/D(2 对在 dispatch/combine,2 对在 layout 切换)加上反向对称数。从"12→2"的对比更像是和最朴素的 FP8 drop-in 实现对比,而非业界已有的成熟 baseline。

## 7. AI Infra / MLSys 视角

本文是典型的 MLSys 工作,对 AI Infra 研究有多个启发点:

**(1) 把量化 layout 变换下沉到 bit-level 是被忽视的优化面**

Direct Transpose 的 insight 完全不是 "发明新算子",而是意识到 "2 的幂 scale + FP8 编码 = 可无损 exponent 平移" 这一数值性质。类似的"把看似需要 dequant 的操作用 bit-trick 完成"的优化面在 int4/int8/MXFP4 推理里可能同样存在 —— 比如 AWQ / GPTQ 的 per-group scale 如果约束到 power-of-two,也可能让一些推理 kernel(尤其是 reorder/shuffle/dequant)变得非常廉价。

**(2) Dataflow-level vs kernel-level 优化的分工**

MLSys 社区长期把精力放在单个 kernel 的极致优化(例如 FlashAttention、DeepGEMM、DeepEP),但 FP8-Flow-MoE 说明 **dataflow-level 的重新设计能带来跨 kernel 的乘法收益**:把 cast 从 12 次降到 2 次,这种宏观结构性的调整对端到端吞吐的影响往往超过单 kernel 提升。对训练/推理框架的启示是:应该让 precision/format 成为 graph-level optimizer 的一等公民,而不是依赖用户在 kernel 边界手动塞 Q/D。

**(3) 对 future work 的延伸方向**

- **更低精度延伸**:Direct Transpose 的思路可推广到 MXFP4(OCP FP4 带共享 exponent),甚至二值/三值量化,关键是 scaling 表示要满足"一元运算可逆"。
- **Attention 里的 FP8 dataflow**:本文专门避开了 attention,因为 softmax 的数值敏感性更强。但 attention 在 decode/inference 上同样有 KV-cache FP8 的需求,能否借用 "scaling-aware transpose" 思路在 KV-cache 的 reorder/rotate 上减少 Q/D,是个值得探索的方向。
- **Compiler-level 自动插 cast**:既然 "12→2" 这种规划对人类是可分析的,是否可以写一个 graph pass,按 FP8/BF16 可行性自动把 cast 推到最优位置?(类似 MLIR 上的 "tensor layout propagation" pass)
- **与 overlap schedule 的 co-design**:本文暂时关掉 overlap,但理论上 FP8 dataflow 让通信体积减半,应该为 overlap 创造更多 slack,反而应该是 overlap 优化的好 substrate。这里有联动优化的空间。

**(4) 对小规模团队的启发**

本文并不依赖大规模基础模型训练(只在 16B 上做收敛验证),但通过充分的 kernel 层 benchmarks + 合理的大模型 throughput 实验讲清楚了故事,是 "聚焦系统层技术贡献" 的好范例。对资源有限的团队,可以类比的做法是:选定某个被忽视的数值性质(如 power-of-two scale、特殊 sparsity pattern),围绕它重新设计 dataflow,用 kernel-level micro-benchmark + 中等规模端到端实验构建完整证据链。

---

## 8. 总结

FP8-Flow-MoE 提出了一条 FP8-centric 的 MoE 训练 dataflow,核心贡献是通过 **scaling-aware(Direct)Transpose** 算子在 bit 层消除 row/col layout 切换带来的 double quantization error,从而把 end-to-end cast 次数从 12 次压到 2 次;配合一组融合的 permute/padding/SwiGLU 量化 kernel,在 DeepSeek-V3(671B)上实现相对 BF16 最高 16%、相对 TE Blockwise 最高 21% 的吞吐提升,以及最多 16.5GB 的峰值显存节省,同时在 16B / 200B tokens 上维持与 BF16 几乎重合的 loss 曲线。

论文适合的场景:大规模 MoE 训练,尤其是 EP 很大、通信密集的配置;对 TE/Megatron 有集成依赖的团队。局限:scaling factor 必须接近 power-of-two、大模型收敛只靠 16B 外推、且对比 baseline 没有直接挑战 DeepSeek V3 原生实现。整体而言,本文是把"FP8 要从 kernel 替换走向 dataflow 重构"这一观点系统化、可落地的一步重要工作。
