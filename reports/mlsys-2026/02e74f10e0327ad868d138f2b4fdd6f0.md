# From Tokens to Layers: Redefining Stall-Free Scheduling for LLM Serving with Layered Prefill

**作者**：Gunjun Lee, Jiwon Kim, Jaiyoung Park, Younjoo Lee, Jung Ho Ahn
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[02e74f10e0327ad868d138f2b4fdd6f0.pdf]]

---

## 1. 背景

大语言模型推理服务必须同时满足两类 SLO：首 token 延迟 TTFT（time-to-first-token）和出字间隔 TBT（time-between-token），而硬件预算（算力、显存、互连带宽）却是固定的。服务系统的主要技术脉络从 FasterTransformer 的静态批处理，演进到 Orca/vLLM 的 continuous batching，再到 Sarathi-Serve 引入的 chunked prefill：把长 prompt 按 token 维度切分成若干 chunk，与 decode 交织执行，既抑制 TBT 尖峰又保持 "stall-free" 的解码流。chunked prefill 目前是主流开源引擎的默认 prefill 策略。

与此同时，模型架构向 Mixture-of-Experts（MoE）演进。MoE 把单个 FFN 替换成多个专家 + 路由，每个 token 只激活 top-k 个专家，从而用较少的激活算力支撑数千亿乃至万亿参数规模。典型配置如 Qwen3-30B-A3B（128 专家 / top-8）、GPT-OSS-20B（32 专家 / top-4）已经成为事实标准。加上长上下文趋势（10k~100k+ token prompt）把 prefill 阶段拉得越来越重，MoE + 长上下文这两股趋势在同一台机器上叠加，给 co-located serving 带来新的瓶颈结构。

此外，随着 AI factory 规模膨胀，服务能耗（特别是 HBM/NVLink 数据搬运能耗）已经成为一等约束。

---

## 2. 要解决的问题

chunked prefill 在 MoE 模型上存在结构性的效率损失：

- **专家权重重复加载**：chunk 是沿 token 维度切分，每个 chunk 都要**完整穿过所有 decoder 层**。每经过一次 MoE 层，就要把被激活的专家权重从 HBM 加载一次。chunk 越小（受 TBT SLO 约束必须保持小）、prompt 越长，重复加载就越严重。论文实测 Qwen + arXiv 工作负载下，chunked prefill 的专家权重搬运量相比理想情况高达 39% 的冗余。

- **sparsity erosion**：chunked prefill 产生的 hybrid batch 通常 >256 token，一次 batch 就能激活几乎全部专家，MoE 的稀疏优势在 prefill 阶段被消灭；但每个专家分到的 token 又不足以把 MoE 的 GEMM 推过 arithmetic ridge point（现代加速器 100~300 Op/B，对应 batch 需 >200），所以 MoE 仍停留在 memory-bound 区间。结果是**既不享受稀疏的带宽节省，又没有享受稠密的算力饱和**。

- **chunk size 的死结**：小 chunk 保 TBT 但放大冗余专家加载；大 chunk 缓解冗余但单次迭代时间拉长、p99 TBT 直接违反 SLO（表 2 中 chunk=2048 时 p99 TBT 从 48ms 升到 129ms）。在严格延迟约束下，efficiency-throughput 最优点在 chunked prefill 下根本不可达。

因此，论文要回答的核心问题是：**能否在不放弃 stall-free decoding 的前提下，消除 chunking 引入的 MoE 权重重复加载？**

---

## 3. 洞察与设计

**关键洞察**：chunked prefill 的冗余来自于把"并发控制粒度"和"模型穿透粒度"耦合在同一个 token 维度上 —— 为了压低 TBT 必须切小 chunk，而切小 chunk 必然让每个 chunk 都把整个模型的所有层再穿一遍。如果把并发控制的粒度从 token 维度迁移到 layer 维度，**每一层对同一个 prompt 只需执行一次**，MoE 权重的重复加载从物理上被消除，而"每次迭代都有 decode 工作"这一点依然可以保留，stall-free 性质不变。

基于这一洞察，论文提出 **layered prefill**：

- **模型纵向切分为 G 个连续 layer group**。decoder-only Transformer 的层是同构且顺序执行的，天然适合 vertical partition。
- **one-group-per-iteration 规则**：每次迭代恰好有**一个指定的 layer group 同时执行 prefill + decode**，其余 group 只跑 decode。prefill 在迭代之间按 group 顺序向下推进，经过 G 次迭代就完成整条 prompt 的 prefill。
- **stall-free 保证**：每次迭代所有 layer group 都至少在做 decode，所以 decode 吞吐不被阻塞，TBT 保持稳定。
- **正交性**：layered prefill 和 chunked prefill 是正交的，可以叠加使用。两者结合后既能处理超长 prompt（类似 chunked pipeline parallelism），又能在 chunk size 足够大（如 8192）时把 MoE 推过 ridge point，使 MoE 从 memory-bound 切换到 compute-bound 区间。

论文的 microbenchmark（图 2）显示，在 L=8192 固定的情况下，MoE 部分 runtime 随 chunk size 从 512 增大到 8192 约从 300 ms 塌缩到 80 ms —— chunk 越大，每个 expert 分到的 token 越多，reuse 越充分。这正是 layered prefill（相当于沿 layer 方向扩大"每层所见的有效 batch"）与"加大 chunk size"可以叠加获益的定量依据。

## 4. 实现细节

- **基础框架**：vLLM 上实现，attention 使用 FlashAttention-3，其余层大部分用自写 CUDA kernel + `torch.compile`，用 CUDA Graphs 加速 prefill 和 decode 两个阶段。

- **并行策略**：在 2× H100（80GB，NVLink 互联）上用 tensor parallelism。

- **layer group 数量自适应**：为了让"每次迭代 prefill 的工作量"与 chunked prefill baseline 的 512-token chunk 大致等价，取

  $$G(L) = \max(1, \lceil L / 512 \rceil)$$

  其中 L 是 prompt 长度。例如 L=8192 时 G=16，L=512 时 G=1。作者明确说 512 只是用来对齐 chunked prefill baseline 的可比性，并非内在参数。

- **小请求合并**：当多个短 prompt 同时到达，合并成一个 batch 减少调度开销。

- **评测模型**：Qwen3-30B-A3B（128 专家 / top-8 / 48KB KV per token）、GPT-OSS-20B（32 专家 / top-4 / <34KB KV per token），都用 bfloat16。

- **能耗测量**：NVML API 读累积能耗，任务开始/结束时分别采样相减；per-token 能耗 = 总能耗 /（prompt token + 输出 token）。

## 5. 实验结果

评测使用 ShareGPT（多轮对话，mean input 2340 token，p90 5696）和 arXiv Summarization（长文摘要，mean input 9194，p90 17152）两个有代表性的数据集，SLO 设置：

| 模型 | 数据集 | TTFT SLO | TBT SLO |
|---|---|---|---|
| Qwen | ShareGPT | 5 s | 125 ms |
| Qwen | arXiv | 10 s | 125 ms |
| GPT | ShareGPT | 5 s | 100 ms |
| GPT | arXiv | 10 s | 100 ms |

**端到端 SLO attainment（图 3）**：

- Qwen/arXiv：chunked 在 1.5 req/s 崩盘，layered 到 1.7 req/s 仍接近 100%，sustain 提升约 14–45%。
- Qwen/ShareGPT：layered 到 4.8 req/s 仍有明显优势，chunked 在 4.4 req/s 开始下降。
- GPT/arXiv：layered 在 2.1–2.7 req/s 保持 100%，chunked 越过 2.3 req/s 急剧下滑。
- GPT/ShareGPT：layered 到 6.4 req/s 仍 >90%，chunked 在 6.2 req/s 急剧掉。

**SLO 拆分（图 4）** 显示：两种调度的 TBT attainment 基本都贴 100%，说明两者都实现了 stall-free；layered prefill 的优势**完全来自 TTFT**，即更短的队列等待 + 更短的 prefill runtime。这和 Table 6 的单点数据一致：Qwen/arXiv @ 1.3 req/s 下，chunked mean TTFT = 2.80s / p99 = 8.65s，layered 仅 1.24s / 4.10s。

**MoE 专家权重搬运量（Table 7，100 请求累计）**：

| 数据集 | Chunked | Layered | 降幅 |
|---|---|---|---|
| ShareGPT | 28.5 TB | 25.1 TB | -12.0% |
| arXiv | 35.6 TB | 21.7 TB | -39.0% |

长 prompt 比例越高，layered 带来的权重搬运减少越显著。

**单请求出字曲线（图 5）**：Qwen/arXiv @ 1.3 req/s，layered 的端到端延迟从 9.4s 降到 5.5s（-41%）。

**能耗（Table 8）**：

| 模型 | 调度 | Req rate | Mean TTFT | J/tok |
|---|---|---|---|---|
| Qwen | Chunked | 1.3 | 2.80s | 56.6 |
| Qwen | Layered | 1.3 | 1.23s | 51.7 (-9%) |
| Qwen | Layered | 1.6 | 2.46s | 44.2 (-22%) |
| GPT | Chunked | 2.1 | 3.00s | 37.4 |
| GPT | Layered | 2.1 | 0.87s | 34.3 (-8%) |
| GPT | Layered | 2.7 | 2.18s | 29.8 (-20%) |

在保持或改善 TTFT / TBT 的前提下，layered prefill 同时拿到 +20~29% 的可用吞吐和 -20~22% 的 per-token 能耗。

## 6. 批判性分析

- **所谓"stall-free"的 overhead 被轻描淡写**。layered prefill 的每次迭代需要遍历**全部 G 个 layer group**（其中 G-1 组只跑 decode），而 chunked prefill 的一次迭代也是整模型穿透，所以从 per-iteration compute 角度两者相同。但 layered prefill 把 prefill 工作量**硬性强制拉长到 G 次迭代**，也就是说**即使 prefill 完全可以一次跑完**，新进 prompt 的 TTFT 下界被抬高到 G × iter_time。当 prompt 长度 L 不够长（例如 L=512 → G=1）时退化成常规调度没问题，但中等长度（L=2048 → G=4）是否一定优于大 chunk chunked prefill，实验缺少针对 L 的扫描。

- **公式 G = ⌈L / 512⌉ 的选择过于 ad hoc**。作者自己承认 "512 is an arbitrary value"，且目的是对齐 baseline 的可比性，而不是最优。如果 chunked prefill 允许 chunk size 自适应（比如 L=8192 时用 1024 甚至 2048 的 chunk + 少数 TBT 违反），对比基线可能没有表里那么虚弱。**消融对比里缺少 "chunked prefill with adaptive chunk size" 这条曲线**，这让 layered vs chunked 的对比稍显片面。

- **layer group 数必须整除层数？** 第 7 节的 future work 已经承认："particularly for models where the layer count is not an even multiple of the group count"。对于层数不是 G 的整数倍的模型，如何分组、最后一组是否过大导致 iteration time 跳变，论文没有讨论。

- **Batch 合并策略的复杂度被隐藏**。prefill 分 G 个迭代完成意味着同一时刻系统里可能有多个处于不同 group 进度的 prefill 请求叠加，加上 decode 请求，batch 组合的 scheduling 状态空间比 chunked prefill 更复杂。论文一句 "When multiple small inputs arrive concurrently, we merge them into a single batch" 带过，但**多请求不同 layer group 进度并发的调度细节、边界 case（某个 prefill 请求抢占、cancel 时怎么回滚）都没有描述**。

- **评测平台太窄**。只有 2× H100，两个模型。对 pipeline parallelism / expert parallelism 场景（大集群 MoE serving 的常态）如何兼容 layered prefill 没给出答案。作者在 conclusion 里也承认 "extend this approach to complex multi-GPU environments" 是 future work，但论文标题立的旗是 "redefining stall-free scheduling"，在 TP-only 小集群上做出改进 ≠ 普适 redefinition。

- **TTFT 改进背后有"容量换延迟"的嫌疑**。图 3 显示 layered 在低请求率时几乎 100% SLO，但这部分改善与其说是 layered 的架构优势，不如说是 chunked baseline 的 queuing delay 更重；layered 把 queue 清空的速度更快（因为 prefill 占用资源更少）。所以实验里低 req rate 时 TTFT -50%~-70% 的数字，要警惕是"把 baseline 拍到它本来就处于崩溃边缘的区域"后得到的。

## 7. AI Infra / MLSys 视角

这篇论文直接落在 AI Infra 核心战场（LLM serving for MoE models），对今后的研究有几个可迁移的启发：

- **调度粒度迁移是一类值得系统化的方法论**。"把并发控制维度从 X 迁到 Y" 这种设计手法在系统研究里反复出现（如 Sarathi 把 request-level 切到 chunk-level、ZeRO 把 parameter shard 的粒度从 per-param 切到 partitioned stages）。layered prefill 把"调度粒度从 token 迁到 layer"写成一个显式 design principle 是有价值的。后续工作可以沿这条主线问：**还有哪些维度可以作为调度轴？**比如 **expert 维度**（把路由到同一组 expert 的 token 组成调度单元，让 expert 只加载一次）、**sequence 维度 × layer 维度的联合调度**（类似 attention sink 的静态驻留策略）。

- **MoE expert weight staging 是 future 工作的高价值切入点**。论文消除了"同一个 prompt 重复 load expert"的问题，但没有触及"不同 prompt 之间 expert 权重是否可以在 HBM 驻留 / 在 layer group 边界做预取" 。一个可操作的延伸：把 layered prefill 的 group 边界作为 expert prefetch 的天然 checkpoint，预测下一个 group 将会激活哪些 expert，提前从 GDDR/NVMe 拉入 HBM。

- **pipeline parallelism × layered prefill 的兼容性是紧迫课题**。生产规模 MoE serving 基本都是 PP+TP+EP 混用。layered prefill 把模型按层分组的做法天然和 PP 对齐，但两者组合时如何映射（group 是否等于 PP stage？跨 stage 的 layer group 调度如何同步？）还没答案。这是一个具体可做的工程 + 研究题目。

- **warehouse-scale 能耗**。论文只在单 node 上给出 per-token energy 数字。如果把 layered prefill 放进数据中心级的 workload mix（异构 request size、MoE/dense 混部、多模型共用 HBM），J/tok 的优势能保留多少？这是一个非常适合做 multi-tenant serving benchmarking 的研究问题。

- **理论上界的对齐**。MoE 专家权重搬运量的下界是每个 prompt 必须至少经历每一层一次的 expert load，论文的 arXiv 上 -39% 距离这个理论下界有多远？能否设计一个刻画"调度引发的冗余搬运比例"的形式化指标，把 chunked prefill / layered prefill / 其他方案放在一个统一 taxonomy 里评估？

- **对 vLLM / SGLang 生态的直接影响**。这篇的实现跑在 vLLM 上，如果能 upstream 或开源，生态侧很快就能复现。可以跟进这篇论文是否在 vLLM v1 engine 里有对应 PR 或 RFC，判断业界采纳速度。

## 8. 总结

Layered prefill 把 LLM serving 的 prefill 调度粒度从 token 迁移到 layer，用 "one-group-per-iteration" 规则既保住 stall-free decoding 又消除 chunked prefill 在 MoE 模型下的专家权重重复加载。在 Qwen3-30B-A3B 和 GPT-OSS-20B 两个主流 MoE 模型、ShareGPT + arXiv Summarization 两个数据集、2× H100 的评测中，取得 TTFT 最高 -70%、E2E 延迟 -41%、MoE 权重搬运 -39%、per-token 能耗 -22% 的收益。**适用场景**：co-located prefill+decode 的 MoE serving，尤其是长 prompt / 低 decode batch 的场景。**主要局限**：baseline 对比只覆盖 fixed-chunk chunked prefill，大集群 PP/EP 兼容、layer 数非 G 整数倍、小到中等 prompt 长度下的收益都还没被充分验证；TTFT 提升中有一部分来自于 baseline 被压在崩溃边缘，净架构收益的精确量化需要更细的实验切片。
