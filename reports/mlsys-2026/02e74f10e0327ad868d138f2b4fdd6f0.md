# From Tokens to Layers: Redefining Stall-Free Scheduling for LLM Serving with Layered Prefill

**作者**：Gunjun Lee, Jiwon Kim, Jaiyoung Park, Younjoo Lee, Jung Ho Ahn（Seoul National University）
**会议**：MLSys 2026
**链接**：[arXiv:2510.05580](https://arxiv.org/abs/2510.05580)
**源文件**：[[02e74f10e0327ad868d138f2b4fdd6f0.pdf]]

---

## 一、背景

LLM 推理服务需要同时满足 TTFT（Time-to-First-Token）和 TBT（Time-Between-Token）两项延迟 SLO，同时最大化吞吐。当前主流的 co-located serving 系统采用 chunked prefill 调度：将长 prompt 沿 token 维度切分为多个 chunk，与 decode 交替执行，从而实现 stall-free decoding、稳定 TBT。

与此同时，MoE（Mixture-of-Experts）已成为 LLM 扩展的主流架构。MoE 通过稀疏激活（每个 token 只路由到少量 expert）来扩大参数规模而不成比例增加计算量。然而，MoE 的 expert weight loading 特性与 chunked prefill 的调度方式之间存在根本性冲突：chunked prefill 把 prompt 切成多个小 chunk，每个 chunk 都需要遍历所有 transformer 层并重复加载 expert 权重，导致严重的带宽浪费和能耗增加。

---

## 二、要解决的问题

1. **Sparsity erosion**：Chunked prefill 形成的 hybrid batch（prefill chunk + decode batch）通常很大（>256 tokens），激活了大部分 expert（coverage 可达 86%–98%），但每个 expert 分到的 token 数很少（远低于 accelerator 的 ridge point），MoE 层始终处于 memory-bound 状态。这意味着 MoE 的稀疏性优势被完全侵蚀——大量 expert 被加载但利用率极低。

2. **Redundant expert weight reloads**：一条长 prompt 被切成 N 个 chunk，每个 chunk 都要遍历全部层并加载 expert 权重，导致 expert weight 总加载量随 chunk 数线性增长。在 arXiv 数据集上（平均 prompt 长度 ~9K tokens），chunked prefill 的 MoE weight load 占 prefill runtime 的 50% 以上。

3. **Chunk size 的两难**：增大 chunk size 可以减少 expert 重复加载和降低能耗，但会增加单次 iteration 时间，导致 TBT 尾延迟违反 SLO。例如 chunk size 从 512 增到 2048，p99 TBT 从 48ms 飙升到 129ms，超出 SLO。

---

## 三、洞察与设计

**关键洞察**：Chunked prefill 沿 token 维度切分 prompt，迫使每个 chunk 重复遍历所有 transformer 层、重复加载 expert 权重；而如果改为沿 layer 维度切分模型，每一层只需处理完整 prompt 一次，从根本上消除了 chunk 带来的 expert 重复加载问题，同时仍能维持 stall-free decoding。

基于此洞察，论文提出 **Layered Prefill**：

- **Layer group 划分**：将模型的 decoder 层栈划分为 G 个连续的 layer group。
- **One-group-per-iteration 调度规则**：每个 iteration 中，仅一个指定的 layer group 同时执行 prefill 和 decode，其余 group 仅执行 decode。Prefill 逐 group 推进，G 个 iteration 完成整个 prefill。
- **Stall-free 保证**：每个 iteration 所有 group 都执行 decode，decode 永远不会被 prefill 阻塞。
- **消除重复加载**：每个 layer 只处理 prompt 一次（而非每个 chunk 一次），expert weight 加载次数等于层数而非层数 × chunk 数。

**与 chunked prefill 的正交性**：两种方法可以组合使用——layered prefill 处理 layer 维度，chunked prefill 处理 token 维度。组合后可以处理超长 prompt，并且由于 layered prefill 允许使用更大的 chunk size（在 compute-bound 区域切分不再增加延迟），进一步减少 expert reload。

---

## 四、实现细节

- **Layer group 数量自适应**：G(L) = max(1, ⌈L/512⌉)，即让每个 group 的 prefill 工作量近似等于 512-token chunk 的工作量，保持与 chunked prefill baseline 的 iteration 时间可比。
- **短请求合并**：多个短 prompt 同时到达时合并为一个 batch 处理。
- **基于 vLLM 实现**：在 vLLM 上实现，使用 FlashAttention-3 做 attention，自定义 CUDA kernel + torch.compile 处理其余计算，使用 CUDA Graphs 加速 prefill 和 decode 阶段。
- **硬件环境**：2× NVIDIA H100 80GB GPU，NVLink 互连，tensor parallelism。

## 六、批判性分析

1. **评估规模过小**：所有实验仅在 2× H100 上使用 tensor parallelism 完成，模型规模为 20B–30B。实际生产环境中 MoE 模型通常是 100B+ 级别（如 DeepSeek-V2 236B、Mixtral 8x22B），需要 expert parallelism 和 pipeline parallelism。论文在 conclusion 中提到 "future work can extend to complex multi-GPU environments"，但这恰恰是 layered prefill 最大的不确定性——layer group 划分与 pipeline parallelism 的交互、expert parallelism 下 expert 分布在不同 GPU 时 sparsity erosion 是否仍是主要矛盾，都未验证。

2. **仅评估两个 MoE 模型，Expert 配置差异有限**：Qwen（128 expert, top-8）和 GPT-OSS（32 expert, top-4）的 expert-to-top-k ratio 分别为 16:1 和 8:1，都是高稀疏度配置。对于 top-k/expert 比更高的模型（如 Mixtral 的 8 expert top-2），sparsity erosion 问题是否仍严重、layered prefill 的收益是否显著，缺乏讨论。

3. **Layer group 数量的选择过于简化**：G(L) = max(1, ⌈L/512⌉) 是一个 heuristic，论文承认 512 是 "arbitrary value"。但 layer 总数不一定能被 G 整除，不同 layer group 的计算量可能不均衡（尤其当模型存在异构层时）。论文在 conclusion 提到这一点但未解决。

4. **KV cache 管理开销被忽略**：Layered prefill 中，prefill 的中间激活需要跨 iteration 保存（一个请求的 prefill 分布在 G 个 iteration 中完成），这意味着中间激活的生命周期延长了 G 倍。论文没有讨论这对 GPU 内存的额外压力，尤其在高并发场景下。

5. **Baseline 对比不够充分**：只与 chunked prefill（Sarathi-Serve 风格）对比。没有与 prefill-decode disaggregation（如 DistServe、Splitwise）、Pod-Attention 等更先进的调度方案对比。这些方案通过将 prefill 和 decode 分配到不同的 GPU 来彻底避免干扰，可能在 MoE 场景下同样有效。

6. **Energy 测量粗粒度**：使用 NVML 的 cumulative energy counter 测量整个 GPU 的能耗，无法区分 HBM traffic、compute、idle 各自的贡献。论文关于 "减少 off-chip bandwidth 从而降低能耗" 的因果推断缺乏直接证据。

## 七、AI Infra / MLSys 视角

1. **调度维度的启发**：论文提出的 "从 token 维度切换到 layer 维度" 的调度思路具有一般性。在 pipeline parallelism、speculative decoding、disaggregated serving 等场景中，也可以探索 layer-granularity 的调度。例如，在 prefill-decode disaggregation 系统中，可以用 layer group 作为 disaggregation 的粒度而非整个模型。

2. **MoE serving 的 sparsity erosion 问题值得重视**：论文清晰地量化了 chunked prefill 下 MoE 的 sparsity erosion（Table 1 和 Table 7），这一观察对所有 MoE serving 系统都有参考价值。在设计 MoE 调度时，需要同时考虑 batch size 对 expert coverage 的影响和对 per-expert utilization 的影响。

3. **可跟进的研究方向**：
   - **Layered prefill + expert parallelism**：在多 GPU expert parallel 场景下，layer group 划分如何与 expert 分布协同，是最直接的延伸工作。
   - **自适应 layer grouping**：根据实时 workload 特征（prompt 长度分布、请求到达率）动态调整 group 数量和分组方式。
   - **Layered prefill 与 speculative decoding 的结合**：speculative decoding 的 verification 阶段类似小规模 prefill，layered 调度可能有助于减少 verification 的 expert reload 开销。

4. **最有价值的切入点**：将 layered prefill 扩展到 multi-node、multi-GPU 的大规模 MoE 模型（如 DeepSeek-V3 级别），并与 expert parallelism、pipeline parallelism 联合设计调度策略。这是论文明确留下的 gap，也是工业界最关心的场景。

---

## 八、总结

本文提出 layered prefill，将 LLM 推理调度的切分维度从 token 转向 layer：将模型按层分组，每个 iteration 仅一个 layer group 执行 prefill+decode、其余 group 仅 decode，从而在保持 stall-free decoding 的同时消除了 chunked prefill 在 MoE 模型中因重复加载 expert 权重带来的带宽和能耗开销。在 Qwen3-30B-A3B 和 GPT-OSS-20B 上的评估表明，layered prefill 可将 expert load traffic 减少最多 39%、TTFT 降低最多 70%、端到端延迟降低 41%、单 token 能耗降低最多 22%。主要局限在于仅在 2-GPU 小规模环境下验证，未涉及 expert parallelism 和大规模部署场景。
