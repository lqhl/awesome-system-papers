# Beyond the Buzz: A Pragmatic Take on Inference Disaggregation

**作者**：Tiyasa Mitra, Ritika Borkar, Nidhi Bhatia, Ramon Matas, Shivam Raj, Dheevatsa Mudigere, Ritchie Zhao, Maximilian Golub, Arpan Dutta, Sailaja Madduri, Dharmesh Jani, Brian Pharris, Bita Darvish Rouhani

## 1. 背景

LLM 推理服务正在从单节点部署快速演进到数据中心规模的多节点部署。这种规模化转变让系统级优化拥有了更广阔、表达力更强的设计空间。社区围绕一个核心目标做了大量探索:在保证交互性 (interactivity, 通常用 tokens/s/user 衡量) 的前提下,最大化每 GPU 的吞吐 (server throughput, 即摊销成本)。

Disaggregation (推理拆分) 是其中最受瞩目的方向之一:把自回归 LLM 推理的 prefill (context, 计算密集) 和 decode (generation, 访存密集) 两个阶段拆到不同的模型实例上,各自独立优化。过去一年里相关学术工作和开源实现层出不穷 (DistServe、Mooncake、TensorRT-LLM Dynamo、vLLM disagg、P/D-Serve 等),NVIDIA Blackwell + FP4 也为大规模推理基础设施提供了新硬件基线。然而真实部署中的采纳仍然有限,主要瓶颈在于设计空间太复杂、系统协调难度大。

---

## 2. 要解决的问题

现有研究和开源实现主要存在三个不足:

1. **缺乏全空间的系统性评估**。已有工作大多聚焦小规模 testbed 和 peak throughput 场景,没有完整刻画 throughput–interactivity Pareto frontier,因此难以回答"什么时候用 disaggregation、用哪种配置"这类工程决策问题。
2. **设计变量耦合严重**。Disaggregation 的收益同时依赖于模型分片策略 (TP/EP/PP/CPP/TEP)、prefill/decode 实例的 batch size、context-to-generation GPU 比例 (rate matching)、流量模式 (ISL/OSL)、模型架构 (MLA vs GQA) 与硬件 (NVLink domain 大小) —— 任意一维选错都可能让收益归零甚至变负。
3. **关键工程问题没有量化结论**。例如:KV cache 跨节点传输是否会成为瓶颈?固定 ctx:gen 比例 (大多数开源实现的现状) 相对于动态 rate matching 损失多少?context chunking 在不同 attention 架构下的实际增益如何?

本文给出第一份针对 datacenter 规模 disaggregated inference 的系统性研究,覆盖数十万设计点。

---

## 3. 洞察与设计

**关键洞察**:Prefill 和 decode 两个阶段在计算特性 (compute-bound vs memory-bound)、SLA 维度 (FTL vs TTL)、最优分片策略上差异足够显著,值得用独立的硬件资源池和独立的并行策略分别服务。但这种拆分的收益高度非均匀 —— 取决于流量模式、模型规模和延迟约束 —— 因此必须用全空间搜索 + 动态 rate matching 才能稳定拿到 Pareto 最优。

整体设计沿两个正交维度展开:

**1) 模型分片策略**

- 评估的并行度组合包括 TP、EP、PP、CPP (Chunked Pipeline Parallelism)、TEP (TP attention + EP FFN),覆盖各种 batch size。
- 用 NVIDIA 内部高保真 GPU performance simulator (输入: 模型架构 + 流量 + GPU 配置;输出: 各 (batch, 并行策略) 组合的 latency/throughput) 构造 Pareto 曲线。
- **Prefill 侧推荐 CPP**:Chunked Pipeline Parallelism 把输入序列切成更小 chunk,每个 chunk 独立处理 (复用之前 chunk 的 KV cache 但不依赖其输出),并用 PP 让早期层处理新 chunk 的同时晚期层处理旧 chunk。这样能在不引入宽 TP 的前提下,把长 ISL 的 FTL 压到 SLA 内,且吞吐几乎不受 PP 度数影响 (Figure 5 显示 ISL=256K、64 GPU 上 PP 从 1 增长到 32,FTL 单调下降而 tokens/s/GPU 几乎保持不变)。
- **Decode 侧偏好高 TP + 适度 batch**:随 TTL 收紧,batch size 减小、TP 维度增大;NVLink domain 内的 EP 在 DeepSeek-R1 上长期占优。

**2) Rate matching (流量速率匹配)**

- 给定 prefill mapping (满足 FTL ≤ 10s 这类宽松约束) 后,对每个候选 decode mapping 用一个整数求解器在 TTL 约束下最小化总 GPU 数,搜出最优 (DP_c, DP_g) 比例,使 DP_c × R_c ≈ DP_g × R_g (R_c, R_g 分别为单实例 prefill / decode 请求处理速率)。
- Figure 1 中 Pareto 曲线上每个蓝点都是一次 rate matching 的输出。
- 假设 KV cache 在 prefill 各层产出后立即逐层流式传输到 decode 池,与后续层的 prefill 计算重叠 —— 该假设的合理性由 §5 用带宽公式定量验证。

## 4. 实现细节

论文不发布开源系统,而是用一个 **proprietary high-fidelity GPU performance simulator** 完成全部测量,核心组件包括:

- **Simulator 输入/输出契约**:输入模型 (DeepSeek-R1, Llama-3.1-8B/70B/405B)、ISL/OSL/QPS、GPU 配置 (NVLink domain 8 或 72,FP4 Blackwell);输出每个 (batch, parallelism) 组合的 latency 和 throughput。
- **设计点扫描规模**:hundreds of thousands of design points,覆盖多种 (并行策略 × batch size × ctx:gen 比例 × 流量模式 × 模型) 组合。
- **Co-located baseline**:对照组同时启用 piggybacking (Sarathi-style chunked prefill + decode 混合 batch) 和无 piggyback 两种模式,Pareto 曲线取两者的上包络;对 DeepSeek-R1 还专门处理了 MLA 在 prefill chunking 下重复计算 down/up projection 的开销 (建议缓存 up-projected KV)。
- **Rate matching 算法** (Algorithm 1, 2):
  1. PrefillConfigSelection: 在满足 FTL_cutoff 的所有 prefill 配置中按 throughput = B/(FTL × G) 选最优。
  2. RateMatching: 对每个 decode 配置算 decode_request_throughput = decode_throughput / (OSL−1),用 α = round(prefill_thr / decode_request_thr, tolerance=0.03) 把比值化为最简分数,得到 num_prefill_gpus 和 num_decode_gpus,系统 throughput = decode_throughput / (1+α)。
- **流量模型简化**:用真实部署 trace 的 P50 ISL/OSL 的最近 2 次方近似动态流量,Appendix C 验证 P50 近似得到的 Pareto 曲线与完整 trace 模拟出的曲线高度吻合。
- **KV cache 带宽估算**:给出 BW_egress 和 BW_ingress 的解析公式 (Eq. 1, 2),把 KV transfer 是否成为瓶颈的判断完全 analytical 化,不需要实测。

## 5. 实验结果

所有结果都做了归一化 (作者明确表示主要传达趋势而非绝对数字),覆盖 DeepSeek-R1 / Llama-3.1-{8B, 70B, 405B},硬件为 Blackwell + FP4。

| 维度 | 关键发现 |
|---|---|
| 流量模式 (Figure 1, 8) | Disaggregation 在 **prefill-heavy** 流量 (如 ISL 16384 / OSL 2048) 下显著优于 piggybacked co-location,Pareto 曲线整体外推;在 generation-heavy 流量 (ISL 1024 / OSL 32768) 下两者几乎重合,disagg 优势消失 |
| 模型规模 (Figure 7) | 模型越大,disagg 收益越显著 (Llama-3.1-405B > 70B > 8B);8B 模型上 disagg 几乎无优势 |
| 模型架构 (Figure 6) | DeepSeek-R1 (MLA) 与 Llama-3.1-70B (GQA) 在不同延迟区间收益形态不同;DeepSeek-R1 的 piggybacking 因 MLA 重复算 down/up projection 而吃亏 |
| Prefill 并行 (Figure 5) | DeepSeek-R1 ISL=256K、64 GPU 上 PP 从 1 → 32,FTL 几乎线性下降 (log2 轴上),tokens/s/GPU 保持 ~1.0,验证 CPP 是长 ISL prefill 的最优解 |
| Rate matching (Figure 9, 10) | 最优 ctx:gen 比例随模型 (DeepSeek-R1 在 ISL=16K/OSL=2K 下从 ~3.7 滑到 ~0.1) 和延迟目标剧烈变化;固定比例 (3.5 或 0.5) 在某一延迟段尚可,但跨延迟段一律远差于 dynamic rate matching;固定 0.5 的 throughput 在大部分区间被 co-located 反超 |
| NVLink domain (Figure 11) | 72-GPU NVLink domain 全程优于 8-GPU domain;DeepSeek-R1 在中等延迟靠更高 EP + 更大 batch 受益,Llama-3.1-70B 在低延迟靠更高 TP 受益 |
| KV cache 带宽 (Figure 12) | DeepSeek-R1 ISL=16K/OSL=2K 下,egress + ingress 联合峰值 < 1.4 GB/s/GPU;ISL=1M 下 ~1.8 GB/s/GPU。**远低于现有数据中心 NIC 带宽**,KV transfer 不会成为系统瓶颈 |
| 流量近似 (Appendix C) | P50 ISL/OSL 的最近 2 次方近似下的 Pareto frontier 与完整 trace 模拟基本一致 |

## 6. 批判性分析

- **Simulator 是闭源 + 高保真自证**。全部结论建立在一个未公开的 NVIDIA proprietary simulator 之上,论文没有给出仿真器的校准误差 (例如和真机端到端测量的 MAPE),也没有 ablation 显示如果换不同抽象层次的 simulator 结论是否成立。这让结果的可复现性、独立验证可能性几乎为零,作为 MLSys 论文是显著的可信度短板。
- **数字全部归一化,绝对量纲不可推断**。作者明示是要传达趋势,但 disagg 在很多曲线上"赢"的幅度看起来很温和 (Figure 6 DeepSeek-R1 ISL 16K/OSL 2K 上 disagg 与 piggyback 的差距并不悬殊),没有绝对 tokens/s/GPU 就难以判断收益是否值得 rate matching 增加的工程复杂度。
- **"动态 rate matching"具体怎么动态没说清**。Figure 10 把固定 0.5 / 3.5 / optimal 三条曲线对比,但 optimal 是 offline per-latency-target 算出来的;真实部署里流量模式漂移、SLA 切换的 online 重平衡机制 (GPU 实例迁移、KV cache 状态搬移、in-flight 请求处理) 完全没讨论,而这恰是 disagg 落地的真正难点。
- **"existing datacenter bandwidth is sufficient"的结论略乐观**。Eq. 1/2 假设 KV cache 与 prefill 后续层完全 overlap,前提是网络 latency 不引入额外阻塞;长 ISL (1M) 下 1.8 GB/s/GPU 的需求虽然单流不大,但乘以高密度 GPU 数 + concurrent flows + 跨机架拓扑后,fabric 拥塞和 tail latency 可能让 overlap 假设失效。论文没做带 in-cast 或 fabric 拥塞的扫描。
- **Co-located baseline 中 piggybacking 的实现细节模糊**。论文反复引用 Sarathi[1, 2],但具体 chunk size 的扫描策略、是否对 piggyback 也做了同等强度的搜索空间,没有充分交代。如果 disagg 享受了"全空间搜索"而 baseline 只用了"默认 piggyback",对比结果的公平性会受影响。
- **不分析 SLO 违例和尾延迟**。整篇都谈 P50 ISL/OSL + 平均 throughput–TTL Pareto,没有 P99 FTL/TTL、不谈 TTL jitter,而 disagg 在 ctx→gen KV transfer 抖动下的 tail behaviour 是实际部署里更受关注的指标。
- **Section 7 (future work) 极为轻描淡写**。把 KV reuse、speculative decoding、inference-time compute 等真正会改变 disagg 决策面的方向都列为 "interesting",但没有指出这些会如何 invalidate 当前结论 (例如 speculative decoding 会显著改变 decode 的 compute/memory 比,从而推翻 ctx:gen 比例的推荐)。

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 研究者的价值主要在 **方法论** 和 **设计空间地图**,而非具体技术创新:

- **可借鉴的 insight**:
  1. **CPP 作为长 ISL prefill 的优选** —— 用 PP × chunking 替代宽 TP,在不增加跨节点 all-reduce 压力的前提下满足严格 FTL,值得在 vLLM / SGLang 等开源推理框架里实现并验证。
  2. **Rate matching 应该作为 first-class optimizer** —— 现有开源 disagg 实现普遍把 ctx:gen 比例固定 (Mooncake、Dynamo 都接近这种状态),论文给出固定比例的代价量化曲线,可以作为推动框架做 online rate matching 的论据。
  3. **MLA + chunked prefill 的重复 down/up projection 是一个具体的优化点** —— 缓存 up-projected KV 是一个明确可落地的实现工作,适合作为开源 PR 切入。
  4. **P50 ISL/OSL 近似法**对自己做 design space exploration 时极为实用 —— 在 trace replay 太贵的场景下,用 P50 + 最近 2 次方就能拿到趋势上正确的 Pareto。

- **可跟进的 future work**:
  1. **Open-source simulator 重建**:把论文里的 prefill/decode latency 模型 (考虑 attention 类型、并行度、batch、ISL) 用 GPU roofline + comm 解析公式重建,可推动社区共享一个透明的 disagg design space explorer。
  2. **Disagg + speculative decoding 联合优化**:speculative decoding 把 decode 从 memory-bound 推回 compute-bound,会重新改变 ctx:gen 最优比例和最优 TP/EP 选择,这里几乎是空白。
  3. **Online rate matching 的控制器设计**:研究在流量漂移 + SLO 切换下如何低成本地迁移 prefill/decode 实例 (含 KV cache 状态、在飞请求),给出一个 RL 或 MPC 控制器并量化 SLO 违例。
  4. **KV transfer 的 fabric-level 实测**:Eq. 1/2 是 ideal-overlap 假设,实测在共享 fabric 下大量 concurrent KV flows 的 tail latency,做出 disagg 的 fabric-aware 部署 guidance,会比 NVIDIA 这篇更落地。
  5. **MoE + disagg 的协同**:DeepSeek-R1 已经是 MoE,但论文没单独剖析 EP routing imbalance 在 disagg decode 池里的放大效应,这是后续值得做的 microbenchmark + 调度优化。

- **最有价值的切入点**:**为现有开源框架 (Dynamo / vLLM disagg / SGLang) 实现并 evaluate 一个 dynamic rate matching controller**,把论文 Algorithm 2 工程化,是一个收益清晰、可复用、能直接发 paper 或 OSS contribution 的工作。

---

## 8. 总结

本文以 NVIDIA 内部高保真 simulator 为工具,首次系统扫描了 datacenter 规模 disaggregated LLM inference 的设计空间 (hundreds of thousands of points),给出三条可操作的部署指南:**(1)** disagg 主要适合 prefill-heavy 流量 (ISL ≫ OSL) 和大模型 (>10B);**(2)** prefill 用 Chunked Pipeline Parallelism,decode 在收紧 TTL 时用更高 TP;**(3)** 必须做 dynamic rate matching,固定 ctx:gen 比例会在大部分延迟区间 underperform co-located 基线。同时通过解析公式说明 KV cache 跨节点传输不会成为瓶颈。论文的主要价值是为 LLM serving 工程决策提供了一份"地图",局限在于 simulator 闭源、绝对数字归一化、忽略尾延迟与 online 控制问题,可信度和可复现性需要后续工作补足。
