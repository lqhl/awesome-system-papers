## 1. 背景

AI 训练与推理长期由 NVIDIA 单一硬件栈主导,但 AMD MI355X(CDNA4)等新一代 GPU 在峰值算力(BF16 2.5 PFLOPs,MXFP6 10.1 PFLOPs)和显存容量(288 GB)上已经反超 B200,HBM 带宽也达到 8 TB/s 与 NVIDIA 持平。然而 AMD 软件生态极不成熟,所谓「CUDA moat」使高性能 AMD kernel 仍依赖 AITER / Composable Kernel 中由少数专家手写的原始汇编;即便是 PyTorch SDPA 这样的常用算子,在 MI355X 上跑 Llama GQA backwards 也只有 259 TFLOPS,距离硬件峰值差距显著。

与此同时,NVIDIA 生态的主流 kernel 编程范式正从底层 CUDA/CUTLASS 向 C++ 嵌入式 DSL 迁移 —— ThunderKittens (TK)、CuTe DSL、Gluon 等提出用「tiles + bulk compute operators + wave specialization」三件套简化高性能 kernel 开发。本论文要回答的核心问题就是:这套在 NVIDIA 上成功的编程抽象,是否能原样平移到 AMD?还是需要一套全新的原语?

---

## 2. 要解决的问题

具体而言,作者把 AMD AI kernel 开发面临的挑战拆解成三层:

1. **Programmable memory(寄存器 + shared memory)的访问模式复杂**。(1) HIPCC 编译器不允许把 AGPR 作为 MFMA 的输入操作数,而 attention backwards 这类同时涉及矩阵和向量操作的 kernel 需要灵活使用所有 512 个寄存器;(2) 不同 MFMA shape(16×16×32 / 32×32×16 等)在 AMD 上的 register layout 彼此不兼容,不像 NVIDIA 所有 shape 都由 16×16 核心矩阵复合而来,因此无法用单一 swizzle 策略统一;(3) shared memory 的 bank 行为与 phase 划分随指令(ds_read_b128 / ds_read_b64_tr_b16 / ds_write_b64 等)差异很大,phase 内线程不连续,给 swizzle 设计带来额外复杂度。

2. **Compute/memory 重叠调度(occupancy)不能沿用 NVIDIA 的 wave specialization**。NVIDIA 的 producer-consumer 模式依赖 TMA、wgmma 接受 shared memory 操作数、register reallocation、mbarrier 等硬件特性,AMD 全部缺失。此外 AMD 寄存器在 wave 间静态分配,producer wave 占用的寄存器不再贡献计算,直接限制了每个 thread block 能计算的 output tile 大小和算术密度。实测 wave specialization 只能跑到 BF16 GEMM 峰值的 80%。

3. **Chiplet 架构的非可编程缓存利用率低**。MI355X 有 8 个 XCD,每个含 32 个 CU 与私有 L2,XCD 之间共享 LLC。现有框架基本忽略了这种分层缓存,默认的 row-major block 调度经常导致 L2 命中率只有 36%(尤其当输出矩阵宽度与 XCD 数互素时);而单纯优化 L2 又会打崩 LLC 命中率。

## 3. 洞察与设计

**关键洞察**:TK 提出的「tiles + bulk operators」前端抽象本身在 AMD 上完全成立,但下层「实例化这些抽象的算法」——调度、memory movement、cache 感知——必须根据 AMD 的硬件特性重新设计。更具体地说:(a) AMD 寄存器文件是 NVIDIA 的 2 倍大、tensor core shape 更小,天然允许另一条深流水线路径——通过细粒度 load/compute 阶段而非大 tile 异步流水线来隐藏延迟;(b) AMD 每个 CU 有 4 个 SIMD,wave 间的物理并行性可以替代 wave specialization 达到同样甚至更好的 overlap 效果;(c) L2 带宽约为 LLC 的 3 倍,cache swizzle 必须在两层之间协同优化而非各自极化。

基于这三条洞察,HipKittens 框架保留 TK 的前端(register/shared tile 数据类型 + 类 PyTorch bulk operators),但在后端引入三类 AMD 专有原语:

1. **Developer-controlled register scheduling + 多 layout tile**。显式 pin tile 到具体寄存器编号,绕过 HIPCC 使 AGPR 可作为 MFMA 输入;tile 可按 MFMA shape 参数化。对 shared memory,不去追求一个通用 swizzle,而是为常见的共现 layout 组合(如 16×32 row + 16×32 column)预置 bank-conflict-free swizzle。Global to shared 走 AMD 的 `buffer_load` 异步指令(类 TMA,绕过寄存器文件),其 swizzle 是在 HBM 地址上做而非 shared memory 地址上做。

2. **两种通用调度模式替代 wave specialization**:
   - **8-wave ping-pong**(平衡负载):每 thread block 用 8 个 wave(每个 SIMD 驻留 2 个),两组各 4 wave 在每个 SIMD 内轮流承担 compute / memory 角色,由条件 barrier 控制切换。大 tile、代码短,已足以匹敌 BF16 GEMM、FP8 GEMM、attention forward 的手写汇编。
   - **4-wave interleave**(非平衡负载):每 SIMD 仅 1 wave,在小 base tile 粒度上精细交错 compute 与 memory 指令。代码量大但更榨性能,在 MHA backwards 上从 894 提升到 1091 TFLOPs。

3. **XCD-aware chiplet swizzling(Algorithm 1)**:把 2D grid flatten 后按 `nXCD × C` 周期分配 block(保证 C 个连续 block 共用同一 XCD L2),再在同一 XCD 内按 W 行高的垂直窗口做分层遍历。参数 W 控制 L2 tile 形状(MI355X 最优 8×4 或 4×8),C 控制跨 XCD 的 LLC 协同。成本模型为 `BW = LLC_BW × LLC_hit + L2_BW × L2_hit`,两参数联合调参可同时推高两层命中率。

## 4. 实现细节

- **框架形态**:C++ 嵌入式头文件库,继承 ThunderKittens 的接口风格。Tile 由 `dtype × rows × cols × layout × MFMA_shape` 参数化,行列需为 MFMA shape 的倍数。对外暴露 `load / store / mma_ABt / mma_AtB / exp2 / col_max / sum / div / swap_layout_and_transpose` 等 bulk 算子。
- **显式寄存器 pinning**:以 `split_many_t<type_list<range<24, 39>>, 4>` 指定 4 个寄存器范围作为 tile 的底层存储;接口与编译器托管版本完全一致,开发者可按需混用。
- **Phase/bank solver**:由于 AMD 官方未充分文档化不同 ds_read / ds_write 指令的 phase 划分与 bank 行为(附录 Table 5 列出 `DS_READ_B128 = 4 phases × 64 banks`、`DS_WRITE_B64 = 4 phases × 32 banks` 等),作者写了两个小 solver 枚举线程对撞测出完整表,HK 据此挑选 swizzle。
- **编译器 hint**:在 HK 原语之上辅以 `__builtin_amdgcn_sched_barrier`(硬分界)、`__builtin_amdgcn_sched_group_barrier`(指令分组排序,按 MFMA/VMEM/DS 等 mask)与 `__builtin_amdgcn_s_setprio`(wave 优先级 0-3)三类 intrinsic,用在 cluster 级别而非逐指令,兼顾可编程性与性能。
- **MI325X 变体**:MI325X 的 shared memory 只有 65 KB,放不下 double buffer,因此改用寄存器文件 double buffer,直接 HBM→register,再在 mma 之后用 ds_write 刷到 shared memory。
- **代码规模**:FP8 GEMM 8-wave 版 48 行、4-wave 版 183 行;MHA backwards 8-wave 版 331 行、4-wave 版 989 行。Attention kernel 每 wave 计算 32×128 的 O tile,hot loop 显式划分 8 个 cluster,穿插 mma_AtB、online softmax(col_max / sub_col / exp2 / col_sum)、ds_read、buffer_load。
- **平台**:CDNA3(MI325X)与 CDNA4(MI355X)均验证;benchmark 在 AMD 官方 Docker `rocm/7.0-preview:rocm7.0_preview_pytorch_training_mi35x_beta` 中,500 轮 warmup + 100 轮测量,输入 $\mathcal{N}(0,1)$。

## 5. 实验结果

主要工作负载对比(MI355X,batch 16,heads 16/64,head dim 64/128):

| Kernel | HK 相对最强基线 | 基线说明 |
|---|---|---|
| BF16 GEMM | 与 AITER / HipBLASLT 打平;**1.3–3.0×** 快于 Triton | 单一 8-wave 调度覆盖多种 shape |
| FP8 GEMM | 与 AITER 打平;3222(8-wave) vs 3327(4-wave)TFLOPs | — |
| GQA causal/non-causal FWD | 1.0–2.1× AITER, 1.3–4.5× PyTorch, 1.0–1.4× CK, 1.2–4.5× Triton | head dim 64 情况下更显著 |
| GQA non-causal BWD | **1.8×** 优于 PyTorch SDPA / CK / AITER(8-wave);4-wave 达 **2.3×** | AITER 在 seq 8192 只有 272/384 TFLOPS |
| MHA BWD | 与 AITER 汇编版打平 | 使用多 MFMA shape + AGPR pinning |
| Fused dropout+residual+layernorm | 1.1–2.2× AITER / torch.compile | memory bound |
| Rotary embedding | 1.1–2.2× AITER / torch.compile | memory bound |

消融证据:

- **Producer-consumer vs 非 wave-specialization**(Table 2,M=N=K=8192 BF16 GEMM):4P/8C 输出 128×256 tile 仅 893 TFLOPs,0P/8C 输出 256×256 tile 达 **1610 TFLOPs**,已超过 TK 在 B200 上的 1538;证明 AMD 上 output tile size 是主导因素。
- **Register pinning**(Table 1,MHA 4-wave BWD seq 8192):无 pinning 909 TFLOPs,pinning 后 **1091 TFLOPs**,首次超过 AITER 汇编的 1169 前的水位。
- **Chiplet swizzling**(Table 4,M=N=K=14592 BF16 GEMM):row-major 36% L2 / 76% LLC / 10.7 TB/s / 900 TFLOPs;XCD W8/C64 的 swizzle 达 78% L2 / 55% LLC / **16.6 TB/s / 1068 TFLOPs**(相对基线 **+19%**),而只顾 L2(W8/C542)会掉 LLC。
- **稳定性**:用 HK kernels 预训练 Llama 1B 和 BERT 110M 在 Slim Pajama 10B tokens 上,perplexity 与 PyTorch/AITER 版本持平。

## 6. 批判性分析

- **「统一编程模型」的证据其实只到前端层**。作者在 intro 与 conclusion 反复强调 HK 证明了 TK 的抽象可跨厂商,但全文真正跨厂商复用的只有 tile 数据类型与算子签名,schedule、register、swizzle、cache 策略几乎全部重写。对「一套 DSL 多种硬件」的愿景,这实际上是反例而非支持证据 —— 前端复用的边际收益远小于后端需要重做的工作量,论文对这一点轻描淡写。

- **「与 AITER 汇编 kernel 打平」的公平性存疑**。BF16/FP8 GEMM 和 MHA fwd 的打平基线都是 AITER 的极少数明星 kernel,而 HK 出现显著增益的场景(GQA BWD、head dim 64 attention、memory-bound)恰好都是 AITER 覆盖不足的 workload —— 这更像是「在没有手写汇编的地方赢」而非「全面超越汇编」。文章在叙述中把这两类成果混在一起,让读者容易把局部优势误读为普适优势。

- **Scheduling pattern 的「可普适性」证据薄弱**。作者主张 8-wave ping-pong 与 4-wave interleave 这两种模式「跨 workloads 达到峰值」,但论文里只覆盖了 GEMM、attention、fused LayerNorm、RoPE 四类计算;对 conv、scan、state-space 模型、MoE 等 AMD 场景的同样重要的 workload 均未测试。4-wave interleave 的代码量是 8-wave 的 3–5 倍(Table 3),「tradeoff 可编程性」这个说法实际上把相当一部分复杂度外部化给开发者承担。

- **Chiplet swizzling 的调参开销被隐去**。Algorithm 1 依赖 W 与 C 两个参数,论文说「靠硬件计数或小规模扫描选」,但 Table 4 自己的数据就显示不同 M=N=K 的最优 (W, C) 完全不同(9216 时 W5/C25 最佳,14592 时 W8/C64 最佳),意味着生产部署需要配套 autotune 基础设施,而 HK 并未提供。

- **FP6 case study 透露了 HK 当前方法论的边界**。附录 F 显示 FP6 GEMM 因 ds_read 指令的对齐问题导致 49% hot loop cycles 花在寄存器 shuffle 上,单纯的「显式寄存器 pinning + sched_barrier」组合已不足以解决;这暗示再往前推一代硬件或更窄数据类型时,HK 的原语集合可能需要再次扩展。

- **可维护性问题**。HK 大量依赖未文档化的 phase/bank 行为(Table 5 是作者自己枚举出来的),以及未在稳定 API 中暴露的 LLVM intrinsics;未来 ROCm / MFMA ISA 版本变化很可能让这些假设失效,后续 port 成本论文未讨论。

## 7. AI Infra / MLSys 视角

对做 AI 系统/推理框架的研究者,这篇论文给出几条可直接迁移的思路:

- **「大 output tile + 深流水线」比 wave/warp specialization 更本质**。在硬件缺少 TMA / mbarrier / register reallocation 的场景(包括但不限于 AMD、部分国产 NPU、RDNA 消费卡),宁可放弃 producer-consumer 分工,换更大的 per-block tile size 以放大算术密度。对自研推理框架来说,这意味着 kernel DSL 的默认模板应在「specialized vs monolithic」之间允许切换,而非硬编码为前者。
- **Chiplet / tile-based cache scheduling 将成为下一代 kernel DSL 的必选项**。NVIDIA Blackwell(2 chiplet)、AMD MI355X(8 XCD)、华为 Ascend 910B/C、国内多卡互联方案都有类似的分层 cache / NOC 拓扑。Algorithm 1 提供的「Flatten → 按周期分组 → 垂直窗口」思路可以直接推广到双层 cache + NOC 的调度 —— 值得跟进的研究问题包括:给定 cache 层级与带宽比,能否自动求解最优 (W, C) 参数?是否可以把这个分析融入 Triton/TileLang 等编译器后端?
- **寄存器生命周期是 LLM kernel 的独立瓶颈**。attention backwards 的 Table 1 显示显式 pinning 能带来 20% 性能提升,这对 NVIDIA 侧同样有价值,尤其是 GQA / MLA 等高寄存器压力场景。一个可行的 future work 是把 HK 的 register-range 抽象移植到 TK 或 Gluon,系统化研究 register pinning 对 RLHF / long-context 训练的影响。
- **可跟进的切入点**:(1) 把 HK 的 8-wave ping-pong 适配到 MoE、SSM、linear attention 等非主流 workload,验证可普适性;(2) 基于 HK 原语构建 AMD 端的 MegaKernel(类似 Hazy Research 的 Llama-1B megakernel),在 inference 延迟与吞吐上对标 FlashAttention 家族;(3) 在 chiplet swizzle 基础上做 autotune,把 W/C 从人工调参转成 cost-model 驱动;(4) 研究 HK 原语在 FP4 / MX 系列新数据类型上的扩展,FP6 case study 已经暴露问题,FP4 必然更尖锐。

---

## 8. 总结

HipKittens 是首篇系统研究 AMD CDNA3/CDNA4 上高性能 AI kernel 编程原语的论文,贡献在于:(1) 指出 ThunderKittens 的 tile + bulk operator 前端抽象可跨厂商,但 register pinning、bank-aware swizzle、8-wave ping-pong / 4-wave interleave 调度、XCD 感知的 chiplet swizzling 这四类后端算法必须针对 AMD 重写;(2) 在 BF16/FP8 GEMM、MHA/GQA 正反向、LayerNorm、RoPE 上给出一套与 AITER 汇编 kernel 匹敌甚至超过的参考实现,Triton 基线最高被甩开 3×。适用场景:任何需要在 AMD MI300/350 系列 GPU 上落地高性能 AI workload 的团队,特别是现有 AITER 未覆盖的 attention 变体与 memory-bound kernel。主要局限:跨厂商统一 DSL 的愿景仍停留在前端层;两种调度模式在 MoE / SSM 等未测试 workload 的普适性待验证;chiplet swizzle 参数依赖 autotune 而论文未提供;重度依赖未文档化的 AMD phase/bank 行为与 LLVM intrinsic,存在长期维护风险。
