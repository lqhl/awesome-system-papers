## 一、背景

AMD GPU 在峰值算力和显存带宽上已与 NVIDIA 最新一代持平（MI355X 的 BF16 算力 2.5 PFLOPs vs B200 的 2.2 PFLOPs，显存带宽均为 8.0 TB/s），但软件生态的不成熟形成了所谓的"CUDA moat"——AMD 上峰值性能的 kernel 只能由少数专家用原始汇编编写（如 AITER 库），无法规模化扩展到 AI 工作负载的广度。

在 NVIDIA 侧，ThunderKittens (TK) 等轻量级 C++ 嵌入式 DSL 通过 tile-based 编程原语显著简化了高性能 kernel 的开发。但这些框架仅支持 NVIDIA，直接封装 PTX/CUDA。编译器方案（Triton、Mojo）虽然可编译到 AMD，但在性能和新硬件特性支持上均有不足。

---

## 二、要解决的问题

1. **AMD kernel 开发极度依赖手写汇编**：AITER 等库的最快实现是原始汇编，难以扩展到更多 AI 工作负载。例如 AITER 在 GQA backwards 上仅达到 SoTA 的 30%，PyTorch Llama GQA backwards 仅达 24%。
2. **现有 tile-based DSL 不支持 AMD**：ThunderKittens、CuTe DSL、Gluon 均绑定 NVIDIA 硬件。
3. **编译器在 AMD 上性能不足**：HIPCC 阻止开发者使用 AGPR 作为矩阵指令的输入操作数；Triton 在寄存器生命周期管理和内存访问降级上存在问题。
4. **NVIDIA 的 wave specialization 调度模式在 AMD 上失效**：AMD 静态寄存器分配导致 producer wave 消耗寄存器却不贡献计算，wave specialization 仅达峰值 BF16 GEMM 性能的 80%。
5. **chiplet 架构的层次化缓存未被利用**：MI355X 有 8 个 XCD（chiplet），每个有独立 L2 cache，所有 chiplet 共享 LLC，但现有框架忽略了这种层次结构。

---

## 三、洞察与设计

**关键洞察**：Tile-based 编程抽象（tile 数据结构 + PyTorch 风格的批量运算符）是跨 GPU 厂商通用的，但实例化这些抽象的算法——调度模式、内存访问模式、缓存优化策略——必须根据 AMD 的架构特性重新设计。具体而言，AMD 的静态寄存器分配、异构矩阵指令布局、以及 chiplet 架构的层次化缓存，使得 NVIDIA 上成功的模式（wave specialization、统一 swizzle 策略）不再适用。

基于这一洞察，HipKittens (HK) 设计了三层优化原语：

### 1. 可编程内存的优化访问模式

- **开发者控制的寄存器调度**：绕过 HIPCC 编译器，允许开发者将 tile 的寄存器显式 pin 到特定的 VGPR/AGPR，从而直接使用 AGPR 作为矩阵指令输入（HIPCC 不支持），消除冗余的 `v_accvgpr_read` 指令。
- **异构矩阵核形状的 tile 支持**：AMD 的每种 MFMA 指令使用完全不同的矩阵布局（不像 NVIDIA 有统一的 16×16 基础构建块），且 shared memory 的 bank 结构和线程执行顺序随内存指令不同而变化。HK 为常见的共现布局组合设计了无 bank conflict 的 swizzle 模式。

### 2. 计算与内存重叠的调度模式

识别出两种通用的高性能调度模式，替代在 AMD 上失效的 wave specialization：

- **8-wave ping-pong**（适用于计算/内存平衡的工作负载）：每个 thread block 8 个 wave，每个 SIMD 2 个。两组 wave 交替执行计算和内存操作，通过条件 barrier 控制交替。支持大粒度 tile 操作，代码紧凑。
- **4-wave interleave**（适用于不平衡工作负载）：每个 SIMD 1 个 wave，细粒度交错计算和内存指令。性能更高但代码更长。

### 3. 非可编程缓存的优化访问模式

- **Chiplet-aware grid scheduling**：Algorithm 1 通过 XCD 分组和层次化窗口遍历，联合优化 L2（chiplet 内）和 LLC（跨 chiplet）的缓存命中率。两个可调参数 W（窗口高度）和 C（chunk 大小）控制 L2/LLC 重用的权衡。

## 四、实现细节

**框架接口**：C++ 嵌入式 DSL，tile 数据结构参数化为 dtype（FP32/BF16/FP16/FP8/FP6）、行列数、布局（行/列主序）。提供 PyTorch 风格的运算符（mma、exp、add 等），直接封装 AMD CDNA 汇编/HIP 指令。

**寄存器 pin 机制**：通过 `split_many_t` 和 `range` 模板定义寄存器范围，允许开发者在 tile 声明时指定物理寄存器位置。接口与标准编译器管理的 tile 完全一致。

**编译器 hint**：利用 LLVM 的 `sched_barrier`、`sched_group_barrier`、`s_setprio` 等 intrinsic 指导指令调度，在 cluster 边界建立硬分隔，在 cluster 内部精细控制指令交错顺序。

**共享内存 swizzle**：为不同的 shared memory 指令（`ds_read_b128`、`ds_read_b64_tr_b16`、`ds_write_b64` 等）建立了 phase-bank 表（通过自建 solver 逆向确定），并设计了对常见共现布局无 bank conflict 的 swizzle 模式。

**同步**：使用 `buffer_load_dword` 系列指令实现异步 HBM→LDS 加载（类似 TMA），通过 `vmcnt`/`lgkmcnt` 控制等待；使用 shared memory atomics 替代 mbarrier，开销可忽略。

**Chiplet swizzle 算法**：先将 2D grid 展平，按 XCD 做 round-robin 去交错（chunk size C），再在 L2 tile 内做窗口化遍历（window height W）。推荐 L2 tile 形状为 8×4 或 4×8。

**Kernel 实现规模**：8-wave FP8 GEMM 热循环仅 48 行代码，4-wave MHA backwards 为 989 行。

## 五、实验结果

**平台**：AMD MI325X (CDNA3) 和 MI355X (CDNA4)，对比 NVIDIA B200。基线包括 AITER（汇编）、CK、HipBLASLT/PyTorch、Triton、Mojo。每个 kernel 500 次 warmup + 100 次测量。

## 六、批判性分析

1. **实验仅覆盖 AMD 平台，跨厂商通用性未验证**：论文声称 tile-based 抽象可跨 GPU 厂商通用，但 HK 仅在 AMD CDNA3/CDNA4 上验证。TK 和 HK 的前后端完全不同（TK 封装 PTX/CUDA，HK 封装 AMD 汇编/HIP），所谓的"统一"仅在抽象接口层面，开发者仍需为每个平台学习不同的调度模式和优化策略。

2. **8-wave ping-pong 的"通用性"可能被高估**：论文声称 8-wave 足以匹配汇编 kernel，但 Table 3 显示 4-wave interleave 在 FP8 GEMM 上快 3%，在 MHA backwards 上快 22%。对于性能敏感的生产场景，开发者仍需在两种模式间选择并分别优化，削弱了"简单通用"的叙事。

3. **基线公平性存疑**：AITER 作为核心基线，论文使用时间点为 2025 年 10-11 月（ROCm 7.0 preview beta），AMD 的软件栈正处于快速迭代中。在 beta Docker 环境下的基线数字可能不代表成熟版本的性能。此外，Mojo 的 MHA kernel 被批评有 bank conflict，但 Mojo 也在快速演进。

4. **FP6 case study 暴露了框架的局限性**：Appendix F 详细描述了 FP6 GEMM 中遇到的大量底层困难（内存对齐、bank conflict、寄存器溢出到 scratch memory、需要手动插入 v_nop 指令），这些恰恰说明 tile-based 抽象在新数据类型面前的脆弱性——开发者仍需深入理解硬件细节。

5. **端到端训练验证规模偏小**：仅验证了 Llama 1B 和 BERT 110M 的 10B token 预训练。现代 LLM 训练涉及的 kernel 组合远比单独的 GEMM/attention/layernorm 复杂（如 MoE dispatch、all-reduce overlap、activation checkpointing），未验证这些场景。

6. **代码复杂度的权衡被轻描淡写**：4-wave MHA backwards 需要 989 行热循环代码，且需要显式寄存器 pin、编译器 hint、多种 MFMA 形状混合。这与"简单编程抽象"的宣传存在张力。

## 七、AI Infra / MLSys 视角

1. **打破 CUDA moat 的务实路径**：HipKittens 证明了高性能 AMD kernel 可以通过 C++ DSL 而非纯汇编实现，这对 AI Infra 社区探索多硬件支持具有重要参考价值。随着 AMD MI300X/MI355X 在云服务商的部署增加，这类跨平台 kernel 框架的需求将持续增长。

2. **Chiplet-aware scheduling 的普适性**：随着 NVIDIA Blackwell（2 chiplet）和未来 GPU 进一步采用 chiplet 架构，Algorithm 1 中联合优化 L2/LLC 命中率的思路具有跨平台迁移价值。可以研究如何将此策略扩展到 NVIDIA 的 multi-GPC 架构。

3. **寄存器 pin 机制的启示**：显式寄存器控制在 attention backward 等寄存器压力极大的 kernel 中带来显著收益（Table 1 中 20% 的性能提升）。这一思路值得在其他寄存器密集型 AI kernel（如长序列 attention、MoE routing）中探索。

4. **值得跟进的方向**：
   - 将 HK 扩展到 MoE dispatch kernel（COMET 风格的计算-通信重叠在 AMD 上如何实现）
   - 探索 HK 在 AMD MI355X 上的分布式训练集成（如何与 RCCL 协同优化）
   - FP6/FP4 低精度推理 kernel 的系统化支持（当前 FP6 支持仍处于初步阶段）
   - 基于 HK 抽象构建自动调参系统，自动选择 8-wave/4-wave 模式和 tile 大小

---

## 八、总结

HipKittens 首次系统性地研究了 AMD GPU 上高性能 AI kernel 的编程原语，提出了开发者控制的寄存器调度、8-wave ping-pong / 4-wave interleave 调度模式、以及 chiplet-aware 缓存优化三大核心技术。在 BF16/FP8 GEMM、attention forward/backward、memory-bound kernel 等主流 AI 工作负载上，HK 达到或超越了 AMD 手写汇编 kernel 的性能，并显著优于编译器方案。其主要局限在于跨平台通用性仅停留在接口层面、4-wave 模式的编程复杂度较高、以及在新数据类型（FP6）上仍需大量底层手动优化。
