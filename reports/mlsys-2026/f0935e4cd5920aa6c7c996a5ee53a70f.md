# Speculative Decoding: Performance or Illusion?

## 一、背景

Speculative Decoding（SD）是加速 LLM 推理的主流技术，核心思路是用轻量级方法（小模型、n-gram 匹配等）先猜测未来 token，再由目标大模型一次性并行验证。自 Leviathan et al. (2023) 提出以来，SD 已广泛应用于 chat completion、问答、代码生成等场景，并衍生出 draft-model-based、EAGLE/EAGLE-3（辅助 head）、n-gram（无训练）、Multi-Token Prediction（MTP，联合训练）等多种变体。

然而，此前对 SD 有效性的评估存在严重缺陷：大多数研究使用研究原型而非生产级推理引擎，且几乎都在 batch size=1 这一不切实际的配置下测试，无法反映真实部署场景。不同 SD 变体之间也缺乏系统性的横向对比。

---

## 二、要解决的问题

1. **评估不可靠**：现有 SD 研究基于原型实现，缺少 CUDA Graphs、continuous batching 等生产级优化，结论无法迁移到实际部署
2. **batch size=1 的假设不切实际**：真实服务场景下 batch size 远大于 1，SD 在高并发下的表现未被充分研究
3. **缺乏变体间的系统比较**：Draft-model、EAGLE、n-gram、MTP 等方法各自为战，用户缺乏选择指导
4. **性能瓶颈不明确**：SD 加速的上限在哪里？当前方法距离理论最优还有多大差距？
5. **新兴工作负载未覆盖**：reasoning workload（长链推理）和 MTP 等新场景下的 SD 表现尚不清楚

---

## 三、洞察与设计

**关键洞察**：SD 的端到端加速受限于两个核心因素——verification 阶段的执行代价（始终是最大开销）和 token acceptance rate 的高度变异性（在单个请求内、跨请求、跨数据集三个维度上均存在显著差异）。不同 SD 方法在不同 token 位置上表现互补，意味着通过自适应组合多种方法可以逼近理论上界。

本文不提出新的 SD 方法，而是构建了首个基于生产级引擎的系统性评估框架：

1. **生产级基准测试**：在 vLLM v0.10.1（启用所有默认优化）上评估多种 SD 变体，覆盖 Llama3.1-8B、Llama3-70B、Qwen3-8B、GLM-4.5-Air-106B 等模型，使用 6 个多样化数据集（CNN/DailyMail、ShareGPT、InstructCoder、GSM8K、AIME22-24、GPQA-Main）

2. **执行时间与内存分解**：将 SD 过程拆解为 drafting、verification、rejection sampling、system overhead 四个阶段，量化各阶段开销

3. **三维度 acceptance 行为分析**：从位置级、请求级、数据集级三个粒度分析 token 接受模式

4. **理论上界推导**：
   - **Oracle proposed length**：假设已知每步的 accepted length，设置 proposed length = accepted length，消除浪费的 verification
   - **Oracle Combine**：假设已知每个位置上哪种 SD 方法更优，自适应选择最佳方法
   - 两者结合得到 SD 的理论加速上界

## 四、实现细节

**实验平台**：NVIDIA H100 80GB GPU，8B 模型用单卡，70B/106B 模型用 4 卡（tensor parallel=4）。基于 vLLM v0.10.1，tree-style 实验使用 SGLang v0.5.9。

**SD 变体配置**：
- Draft-model：Llama3.2-1B / Qwen3-0.6B，每步提议 3 个 draft token
- EAGLE / EAGLE-3：fine-tuned 辅助 prediction heads，每步 3 个 draft token
- n-gram：training-free，prompt lookup（max=7, min=3），默认 3 token/步，部分实验 5 token/步
- MTP：co-trained 辅助 heads（仅 GLM-4.5-Air），3 token/步

**Speedup 公式**：E(speedup) = (1 - α^{k+1}) / ((1-α)(kc+1))，其中 α 为 acceptance rate，k 为 proposed length，c 为 draft/target 模型执行时间比

**Simulator 设计**：基于真实 benchmark 数据的模拟器，支持 oracle acceptance（所有 proposed token 均被接受）和 oracle combine（每个位置选最优方法）两种模式，用于量化理论上界与实测加速之间的差距。

**Acceptance 测量**：采样最多 200 个请求，每步最多提议 20 个 token，记录每步实际接受的 token 数量，用于构建 position-level acceptance profile。

## 五、实验结果

### 端到端加速（非 reasoning 工作负载）

| 模型 | 数据集 | 最佳 SD 方法 | BS=1 加速 | BS=128 加速 |
|------|--------|-------------|-----------|------------|
| Llama3.1-8B | GSM8K | EAGLE | 1.73× | 1.21× |
| Llama3.1-8B | ShareGPT | EAGLE | 1.68× | ~1.61× |
| Llama3-70B | ShareGPT | Draft-model | 1.96× | ~1.72× |
| Llama3.1-8B | InstructCoder | n-gram | 与 EAGLE 相当甚至更优 | - |

### 核心发现

| 维度 | 发现 |
|------|------|
| Batch size | 加速比随 batch size 增大而下降，大模型（70B）下降更快 |
| SD 变体 | n-gram 在代码编辑任务上最强；Draft-model 在 70B 上最优但在 8B 上效果减弱；EAGLE-3 整体稳健 |
| Tree vs Chain | Tree（k=21）在 BS=1 时略优（1.85× vs 1.65×），但 BS≥64 时低于 1×，chain 更稳健 |
| Reasoning | EAGLE-3 在 Qwen3-8B-Thinking 上达 1.64×–1.80×，n-gram 也表现良好（1.50×–1.58×） |
| MTP | GLM-4.5-Air 上仅 1.3×–1.8×，因单 MTP head 在后续位置 acceptance 急剧下降（0.92→0.68→0.38） |

### 执行时间分解

- Verification 占总时间 42%–95%，随模型和 batch size 增大而增大
- n-gram drafting < 2%；EAGLE drafting 12%–20%（BS=1）/ 3%–7%（BS=512）
- Draft-model 在小模型上 drafting 开销显著（Qwen3-8B 上高达 47%@BS=1）

### 内存开销

- n-gram：零 GPU 内存开销
- EAGLE/EAGLE-3：静态权重增 3%–5%，per-token KV cache 增 1%–3%
- Draft-model：取决于 draft model 大小，Qwen3-0.6B+8B 时 per-token KV cache 增 1.77×

### 理论上界

- Oracle proposed length 在 InstructCoder+n-gram BS=1 下达 2.75×（实测最佳为 2.1×）
- Oracle Combine（EAGLE + n-gram 自适应组合）可达 4.9× 端到端加速
- InstructCoder 上理论上界与实测差距最大，ShareGPT/CNN-DailyMail 次之

## 六、批判性分析

1. **数值非确定性的影响被低估**：论文承认 greedy decoding 下不同 batch size 和 SD 变体的输出不一致（Tab. 1），归因于 GPU kernel 非确定性，但未量化这种不一致对 acceptance rate 测量本身的影响。如果 acceptance profile 本身因非确定性而波动，那么基于固定 profile 推导的 oracle 上界可能并不稳固。

2. **Oracle 上界的实用价值有限**：Oracle Combine 假设了一个完美的预测器，能在每个 position 选择最优 SD 方法并精确预测 accepted length。论文承认了这些简化，但 4.9× 这个数字很容易被误读为"可达到的加速"。实际上，构建这样一个预测器本身可能需要额外计算和训练，会增加 c（execution-time ratio），从而削弱理论增益。论文未讨论构建此类预测器的现实可行性。

3. **实验覆盖面的局限**：
   - 仅使用 H100 GPU，未涉及 A100 或更低端硬件，而 SD 的 memory-bound/compute-bound 分界点高度依赖硬件
   - 仅评估 greedy decoding（temperature=0），但真实部署中常用 sampling（temperature>0），这会显著影响 acceptance rate
   - 缺少在线 serving 场景（请求到达率变化、preemption 等）的评估

4. **n-gram case study 的 BLEU 分析过于粗糙**：仅测量 prompt 与完整输出之间的 BLEU 重叠，未考虑 n-gram 实际可利用的上下文（包含已生成的 token），作者也承认这一局限。这意味着 BLEU 与 speedup 的相关性可能被高估或低估。

5. **Tree-style 实验使用不同引擎**：chain 用 vLLM，tree 用 SGLang，两者的系统优化不同（如 FlashAttention-3 vs FlashInfer），这引入了引擎差异的混淆变量，削弱了 tree vs chain 对比的公平性。

## 七、AI Infra / MLSys 视角

**对 AI 系统研究的启发**：

1. **Verification 是真正的瓶颈**：论文清楚地表明，SD 的主要开销不在 drafting 而在 verification。这提示推理系统优化应重点关注如何降低 verification 的冗余计算——例如选择性验证（只验证高置信度的 draft token）或早期退出机制。

2. **自适应 SD 策略是高价值方向**：不同方法在不同位置/请求/数据集上互补的发现（Fig. 11），直接指向了一个研究问题：设计一个轻量级 router/predictor，在运行时动态选择最优的 drafting 策略。这需要平衡预测开销与预测精度。

3. **Batch-aware SD 调度**：SD 加速随 batch size 下降是一个系统级问题。一个可操作的方向是在 serving 引擎中实现 batch-aware 的 SD 开关——在低负载时启用 SD，高负载时自动退回标准 decoding，或根据当前 batch size 动态调整 proposal length。

4. **MTP 的工程优化空间**：GLM-4.5-Air 的 MTP 仅用单个 head 自回归复用，acceptance 急速下降。如果模型在预训练时联合训练多个独立的 MTP head（每个负责不同 draft position），可能显著提升效果。这是模型架构与推理系统协同设计的典型案例。

5. **最值得跟进的切入点**：构建 position-aware adaptive SD controller——利用在线观测到的 acceptance pattern，动态调整每步的 proposal length 和方法选择。论文的 oracle 实验已经证明了 2.2× 的额外提升空间，即使只捕获其中一部分也足以产生显著加速。

---

## 八、总结

本文是首个在生产级推理引擎（vLLM）上对 Speculative Decoding 进行系统评估的工作。核心贡献在于：（1）揭示了 SD 的加速在现实 batch size 下显著低于 batch size=1 的理想化评估；（2）通过执行时间分解证明 verification 是绝对主导开销；（3）发现不同 SD 方法在 acceptance behavior 上的互补性，并通过 oracle 模拟量化了理论加速上界（最高 4.9×）。论文的主要局限在于仅覆盖 greedy decoding 和 H100 硬件，且理论上界所需的完美预测器缺乏现实构建路径。对于 LLM 推理系统的开发者和研究者，这是理解 SD 实际表现和优化方向的重要参考。
