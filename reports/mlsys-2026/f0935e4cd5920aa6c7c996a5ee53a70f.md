# Speculative Decoding: Performance or Illusion?

**作者**：Xiaoxuan Liu, Jiaxiang Yu, Jongseok Park, Ion Stoica, Alvin Cheung
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[f0935e4cd5920aa6c7c996a5ee53a70f.pdf]]
**代码**：https://github.com/orgs/SpecDecode-Bench/repositories

## 1. 背景

Speculative Decoding(SD)自 2023 年提出以来,已成为加速 LLM 推理的主流技术之一。基本思想:用一个便宜的 drafter 并行预生成若干候选 token,再让 target 大模型在一次 forward pass 里并行验证这些 token,从而摊薄 decoding 阶段的 memory-bandwidth 瓶颈。

围绕 SD 已经产生一个庞大的变体家族:

- **Draft-model-based**:用一个小的 LLM(如 Llama-3.2-1B 配 Llama-3-70B)作为 drafter
- **Draft-model-free / 带训练头**:EAGLE、EAGLE-3、Medusa — 在 target 模型上挂一个轻量的 prediction head,事后微调
- **Co-trained**:Multi-Token Prediction (MTP),随 target 模型联合训练(DeepSeek-V3、GLM-4.5 用的就是这种)
- **Training-free**:n-gram / prompt lookup,基于历史文本做字符串匹配
- **Tree-style**:在 chain 基础上扩展为树,一次验证多条候选

每篇新论文都会报告一个可观的 speedup 数字(通常 2–3×),但**这些数字大多是在研究型 prototype、batch size = 1、单请求场景下测出来的**。vLLM/SGLang 这类生产级推理引擎普遍启用 CUDA Graph、continuous batching、chunked prefill 等优化后,SD 在 batch size > 1 的真实部署环境中究竟还剩多少收益,此前并无系统性的公开评估。

---

## 2. 要解决的问题

作者把现有 SD 评测的缺陷归纳为三点:

1. **评测平台不现实**:以往工作大多在 prototype 上做,缺少 CUDA Graph 等 production 级优化,导致 overhead 被系统噪声掩盖、变体之间无法公平对比
2. **batch size = 1 的幻觉**:生产部署普遍 batch ≥ 16,而 SD 的本质是「用闲置算力换延迟」,随着 batch 变大系统从 memory-bound 滑向 compute-bound,SD 的收益会迅速缩水。单 batch 下的 speedup 对真实部署几乎没有参考价值
3. **缺少变体横向比较**:n-gram / EAGLE / Draft-Model / MTP / 树形验证各有适用场景,但没有统一的工作负载去量化「什么模型、什么任务下该用哪种 SD」
4. **只看平均指标**:过去的评测停留在 dataset-level 的 average acceptance rate,没有 position-level、request-level 的分解,无法回答「为什么同一个 SD 方法在两个看起来相似的 workload 上 speedup 差一倍」

更根本的问题是:**当前 SD 距离理论上限还有多远?如果存在 gap,这个 gap 是被 drafter 精度吃掉了,还是被无效验证吃掉了?**这个问题关系到后续 SD 研究应该往哪个方向走。

---

## 3. 洞察与设计

**关键洞察**:

- **Verification 主导执行时间,drafting 并不是瓶颈**。在几乎所有配置下,target 模型的验证 forward 占总时间 42%–95%,drafting(n-gram < 2%,EAGLE 3%–20%,Draft-Model 3%–47%)相对便宜。这意味着:**加强 drafter 不如降低「被拒绝 token 的验证浪费」**
- **Acceptance pattern 不是静态的**,呈现三个层面的高方差:request 内部不同 position、不同 request 之间、不同 dataset 之间。特别是 n-gram 和 EAGLE **在不同 position 上各有所长** — n-gram 在代码编辑这类局部重复强的场景能拿到很长的 burst,而 EAGLE 在语义抽象的位置更稳定
- **如果存在 oracle 能提前知道每一步会被接受多少个 token,从而提出"正好"那么多个**,就能把 verification cost 降到最低 — 这是 SD 的 **theoretical upper bound**
- **进一步,如果 oracle 还能在每个 position 上动态选择"n-gram 还是 EAGLE",两种方法的互补性可以再解锁一大块 speedup**

基于这些洞察,作者的"设计"并不是新做一个 SD 系统,而是三件事:

1. **在 vLLM v0.10.1.1 上做 production-grade 评测**:覆盖 Llama3.1-8B / Llama3-70B / Qwen3-8B / GLM-4.5-Air-106B 四种 target 模型,n-gram / EAGLE / EAGLE-3 / Draft-Model / MTP 五种 SD 方法,CNN/DailyMail / ShareGPT / InstructCoder / GSM8K / AIME22-24 / GPQA-Main 六种数据集,batch 1–128(reasoning workload 限制到 1–16 避免 KV cache 抢占),H100 80GB
2. **构建一个 simulator**:基于真实 profiling 数据(position-level acceptance trace),在 CPU 上模拟各种"假想"SD 配置 — 最重要的是 **oracle 模式**(知道每一步的 accepted length,刚好提议那么多),以及 **oracle-combine 模式**(每个 position 在 n-gram / EAGLE 中挑表现最好的那个)
3. **把 end-to-end speedup 分解成 execution breakdown × acceptance distribution**,用这个两维视角逐个 workload 解释性能差异

---

## 4. 实现细节

评测方法学层面的几个关键决定:

- **用 token throughput 而非 latency 作为指标**:相同 prompt + 温度 0 的贪心解码下,不同 batch size 仍会生成不同长度的文本(由 kernel 并行和浮点非确定性导致),所以 latency 不可比。throughput 消除这个干扰
- **Memory 分析用解析式而非 profiler**:Static memory = Σ (模型参数 × 2 bytes),Per-token KV cache = L × 2 × n_kv × d_head × 2 bytes。避免 activation 等 transient 内存的噪声
- **Tree verification 用 SGLang**:vLLM 当时的 draft-tree 路径没充分优化,作者切换到 SGLang v0.5.9 做树形对比(FlashAttention-3 for chain,FlashInfer for tree)
- **Simulator 的实现**:用真实 position-level acceptance trace 驱动,离线重放。Oracle 模式把"proposed length = actual accepted length",完全消除了浪费验证;oracle-combine 则在每个 position 挑"哪个 proposer 能接受更多" — 注意这是 **upper bound**,作者诚实地承认它假设了一个不存在的完美 predictor,并忽略 EAGLE head 的 KV cache partial prefill 开销

GitHub 仓库 `SpecDecode-Bench` 下有两个 repo:基于 vLLM 的 profiling suite 和独立的 simulator,simulator 可以在笔记本上跑(30–40 分钟)。

## 5. 实验结果

### 5.1 End-to-end speedup

所有 SD 变体在大多数配置下都比 no-SD 基线快,但收益随 batch size 增大显著衰减,尤其对大模型:

| 配置 | EAGLE Speedup@bs=1 | EAGLE Speedup@bs=32 | 衰减 |
|---|---|---|---|
| Llama3.1-8B + ShareGPT | 1.68× | 1.61× | -4.3% |
| Llama3-70B + ShareGPT | 1.96× | 1.72× | -14.0% |

原因:70B 用 4 卡 TP,小 batch 下已经 compute-bound,没有多余算力白白验证被拒绝的 token。

不同 SD 变体的相对强弱:

- **Draft-Model**:在 70B 上最强(1B draft 的 c ≈ 12.5%,acceptance rate 可达 75%),但在 8B 上 drafter 相对成本飙升(c ≈ 37.5%),反而被 EAGLE-3 甚至 n-gram 超过
- **n-gram**:仅在 InstructCoder(代码编辑)这类 prompt-output 重复率高的任务上发挥,其他 workload 普遍垫底。五 token 提议(k=5)比 k=3 在高重复任务上能再拿 100% 相对提升
- **EAGLE/EAGLE-3**:跨 workload 最稳,中位表现最好
- **MTP (GLM-4.5-Air)**:只有一个 MTP head 被反复自回归调用,position-wise acceptance 从 0.92 → 0.68 → 0.38 快速衰减,GPQA-Main 上 1.3×–1.8×,低于理论上限
- **树形验证**:只在 bs=1 有优势,bs=64 时宽树(k=21)反而跌破 1×,原因是验证更多最终被拒绝的分支。chain-style 整体更稳健

Reasoning workload(AIME22-24、GPQA-Main)由于 CoT 更长、有更多重复的数学符号和变量,n-gram 的 acceptance 随 sequence length 快速上升,能和 EAGLE-3 接近。EAGLE-3 在 Qwen3-8B-Thinking 上拿到 1.64×–1.80×。

### 5.2 Time / memory breakdown

CNN/DailyMail 上的执行时间分解(Fig 4 实际数值):

| Stage | n-gram | EAGLE | EAGLE-3 | Draft-Model |
|---|---|---|---|---|
| Drafting | < 2% | 12%–20% @ bs=1 → 3%–7% @ bs=512 | 同 EAGLE | 21%–47% @ bs=1 → 3%–16% @ bs=512 |
| Verification | 主导 | 42%–95% | 同 | 42%–72% @ bs=1 → > 85% @ bs=512 |
| Rejection Sampling | < 1.7% | < 1.7% | < 1.7% | < 1.7% |
| Other(vLLM overhead)| 3%–12% | 3%–12% | 3%–12% | 3%–12% |

内存开销普遍很小:n-gram 0%,EAGLE/EAGLE-3 < 10%,Draft-Model 视 drafter 大小而定(Qwen3-0.6B + Qwen3-8B 的 per-token KV cache 从 144 KiB 涨到 256 KiB,1.77×)。

### 5.3 Acceptance behavior

用 proposed length = 20、但只前进 1 token 的方式探测每个 position 能被接受多少,得到:

- **Draft-Model**:mean / std 最大,例如 InstructCoder 70B 上 mean accepted length 5.6–18.3 tokens
- **n-gram**:heavy-tailed,大部分 request 短,少数 burst 超过 15 tokens(代码模板复用导致)
- **EAGLE/EAGLE-3**:分布紧凑对称,中位 2–4 tokens,std 小

### 5.4 Oracle upper bound

在 Llama3.1-8B 上跑 simulator,`Oracle` = 知道每步会被接受多少就提议多少,`Oracle Combine` = 每个 position 还能自由选 n-gram 还是 EAGLE:

| Dataset | Best fixed-k | Oracle | Oracle Combine |
|---|---|---|---|
| InstructCoder @ bs=1 | ~2.1× (k=5) | ~2.75× | 近 5× |
| ShareGPT @ bs=1 | ~1.28× (k=3) | ~1.43× | ~2.7× |
| GSM8K @ bs=1 | ~1.15× (k=5) | ~1.18× | ~2.1× |

作者在摘要里给出的 "4.9×" 最优 speedup 数字对应 InstructCoder 上 Oracle Combine 的近 5× 峰值,来自 n-gram(在代码重复处拿大 burst)+ EAGLE(在过渡位置兜底)的互补。

## 6. 批判性分析

这篇论文作为 **benchmark & measurement paper**,方法学扎实,但一些结论需要批判看待:

- **"4.9× speedup" 是 oracle 数字,不是可实现数字**。论文明确承认这是 upper bound,假设了完美 predictor + 忽略 EAGLE head 的 KV prefill 开销。摘要和 introduction 里仍把 4.9× 当成重要"卖点"呈现,容易让读者误解为实际达成 — 事实上这是"最大 headroom",不是"SPD 还能跑多快"
- **benchmark 侧重 vLLM 一家实现**。评测结论(尤其 draft-tree 在 bs > 1 掉速)很大程度依赖 vLLM v0.10.1.1 当时的实现成熟度 — 作者自己切到 SGLang 做树形对比就是这个问题的佐证。结论"tree 在大 batch 下没用"可能是 vLLM/SGLang 当前实现的特征,而非 tree verification 的本质劣势
- **硬件单一**:只测 H100(8B 单卡、70B 4 卡 TP、106B 4 卡)。在 A100、L40S、MI300X、消费级 4090 上的 compute/memory roof 比不同,结论的 extrapolation 需要小心 — 例如 B100 的 FLOPs 翻倍会让"compute-bound 临界 batch"进一步右移,SD 反而可能在更大 batch 下仍有收益
- **Draft-Model 在 8B 上垫底的归因有循环论证嫌疑**:作者用 drafter/target 的 forward time ratio(12.5% vs 37.5%)解释 8B 下 Draft-Model 变差,但 forward time ratio 本身就是 batch size 和硬件利用率的函数。如果把 Qwen3-0.6B 换成更小的 draft(比如专门蒸馏的 0.3B 版),结论可能完全翻转
- **MTP 评测只用了 GLM-4.5-Air,样本太小**。作者观察到 GLM 的 MTP head 被反复自回归复用导致 acceptance 衰减,但 DeepSeek-V3 的 MTP 设计是多层独立 head(不是一个 head 复用),这两种 MTP 放在一起讨论并不公平。论文承认了这一点但没扩展评测
- **"n-gram 在代码重复场景有用"是已知的**(PLD 原始论文就报过),本文的贡献更多是量化 BLEU-4 阈值(> 0.6 后 n-gram 反超 EAGLE)。这个阈值对其他编程语言、其他 prompt 格式能否迁移,尚未验证
- **Oracle Combine 的 predictor 被轻描淡写**。"a lightweight predictor" 作为未来工作提出,但 predictor 本身若需要跑一遍小模型来判断"用 n-gram 还是 EAGLE",那它的 drafting overhead 可能就把预期收益吃掉了。这个 future work 的可行性其实不 trivial

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 研究者的价值非常高,因为它是一份**诚实的、带数据的 SD "祛魅"报告**,并在祛魅的同时指出了 SD 研究还剩下哪些值得做的事。

**对 SD 研究方向的启发**:

- **Drafter 的 acceptance rate 已经不是主要瓶颈**。EAGLE-3 的 per-position acceptance 已经很高,继续卷更精准的 drafter(训更大的 head、更复杂的 tree)边际收益很小;真正的 headroom 在 "**减少无效验证**"。具体说就是:**动态决定 proposed length**(短路径下少提议、长路径下多提议),或**动态选择 drafter**(不同 position 用不同方法)
- **自适应 SD 是一个被量化过的大蛋糕**。Oracle Combine 和 best fixed-k 之间有 2–5× 的 gap,设计一个轻量 meta-controller 识别 "当前 position 适合 n-gram 还是 EAGLE,以及应该提议几个 token" 是一个 well-scoped 的研究问题
- **MTP 是被低估的方向**。GLM-4.5-Air 只开源了第一个 MTP head 就拿到 1.3–1.8×,如果训练多层独立 MTP head(类似 DeepSeek-V3 设计),acceptance rate 不会像现在这样逐 token 衰减,效果值得系统性评估
- **Tree vs chain 在 production 场景下需要重新审视**。chain + 动态 k 可能比固定 tree 更实用,这点对 SGLang/vLLM 的上游优化有直接指导意义

**可迁移到其他 AI Infra 场景的方法论**:

- **把 performance 分解为 "execution efficiency × acceptance pattern" 两维**的分析框架可以套用到其他 "proposer + verifier" 架构:比如 Medusa、lookahead decoding、投机查询(speculative query execution)等
- **用 simulator + 真实 trace 回放评估 upper bound** 是非常有借鉴价值的工程方法。这套方法其实也适用于 KV cache 调度、分布式 scheduling、甚至 agent planning — 只要有"决策 + 开销"这样的结构,就可以写一个类似 simulator 来给出 oracle bound
- **non-determinism 作为副作用被明确记录**:同一 prompt 在不同 batch size 下生成长度不同(he 2025 的 floating-point / kernel non-determinism),这一点对任何要做"可重现 benchmark"的 AI Infra 工作都是重要 caveat

**具体的 future work 切入点**:

1. **Lightweight adaptive proposer**:训一个 O(0.1%)大小的路由模型,根据最近 k 个 hidden state 预测当前 position 用 n-gram 还是 EAGLE,以及最优 proposed length。目标是闭合 Oracle Combine 到真实系统之间的 gap
2. **Verification-aware scheduling**:生产环境 vLLM 里,当系统从 memory-bound 滑向 compute-bound 时,应该动态关闭 SD 而不是硬跑。这是一个 scheduler-level 的研究,可以借助本文 simulator 做离线策略搜索
3. **MTP head 的训练策略**:既然单层 MTP 衰减严重,多层独立 MTP 是否值得训?开销 vs 收益的 sweet spot 在哪里?这需要 foundation 模型 + 系统方向的联合研究
4. **SD × prefix caching 的交互**:reasoning workload 下的长 KV cache 会被 SD 的多个 draft 分支 "污染",本文没有系统研究这一点,是一个值得独立做的 evaluation

---

## 8. 总结

这是 SD 领域第一篇在 production-grade 推理引擎(vLLM)上做系统性评测的论文,核心价值不在提出新方法,而在**用真实数据回答三个问题**:(1)SD 在 batch size > 1 的真实部署下还剩多少收益?(2)收益从哪里来、被什么吃掉?(3)距离理论上限还有多远?

结论可以总结为三句话:**verification 主导 cost,acceptance 变异远比以往认识的大,SD 距离理论上限还有 2×+ 的 headroom**。后两点把未来 SD 研究引向"自适应 proposer selection + 动态 proposed length",而非继续卷更强的 drafter。

适用场景:想在生产环境部署 SD 的工程师(选型参考)、做 SD 优化的 MLSys 研究者(问题框架 + 基线数据)。主要局限:oracle 数字被营销化、硬件单一、vLLM 实现细节耦合较深;具体哪种 SD 方法在你的 workload 上最好,仍需用本文 simulator 在你自己的 acceptance trace 上重放一次。
