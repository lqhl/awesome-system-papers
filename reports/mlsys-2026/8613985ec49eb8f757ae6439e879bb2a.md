# Meeting SLOs, Slashing Hours: Automated Enterprise LLM Optimization with OPTIKIT

**作者**：Nicholas Santavas, Kareem Eissa, Patrycja Cieplicka, Piotr Florek, Matteo Nulli, Stefan Vasilev, Seyyed Hadi Hashemi, Antonios Gasteratos, Shahram Khadivi

## 1. 背景

企业在大规模部署 LLM 时陷入一个结构性困境:一方面,LLM 驱动的业务功能需求呈指数级增长(eBay 等公司要在从 8B 到 70B+ 参数的多种模型上构建生成式 AI 应用);另一方面,GPU 是昂贵且供应有限的稀缺资源。为了让 LLM 的部署在经济上可持续,组织必须对模型做系统化的优化(量化、压缩、推理引擎调参)。

然而,这类优化在工业界长期是一门「小众手艺」——掌握 GPTQ/SmoothQuant/FP8 这些技术细节、熟悉 vLLM/TensorRT-LLM 不同后端的调参陷阱、并能在生产 SLO 约束下选出最优配置的工程师极少。现有开源工具(GuideLLM、TensorRT-Sweep、SCOOT 等)各自只覆盖优化链路的一个片段,不具备端到端生产能力;而商用云服务又存在数据主权(data sovereignty)和企业系统集成的阻碍。结果是:优化工作被压到少数 ML Systems 专家身上,成为功能迭代的瓶颈,且容易产生不可复现的优化产物和组织内的重复劳动。

---

## 2. 要解决的问题

作者的目标是在企业内部构建一个自动化、端到端、可在异构 GPU 集群上扩展的 LLM 优化平台,系统性地消除上述瓶颈。要落地需同时解决:

1. **端到端一致性**:从 fetch 模型 → 压缩 → 统计评估 → 推理 benchmark → 运行时调参 → 上传,整条流水线要被声明式描述并可复现,避免片段式工具拼接产生的断层;
2. **资源感知**:Heterogeneous GPU(H100、H200、A100 混合)集群下,不同阶段的算力和数据特征差异很大(量化需要单卡长时间算子、benchmark 需要多卡并行起推理服务),要做动态池化分配并在阶段间清理资源;
3. **SLO 驱动的运行时调参**:压缩后的模型要在真实 SLO(p95 latency、TTFT、TPOT)下找到可持续的最大吞吐配置,并判断系统是否已达到稳态(steady state);
4. **专家知识标准化**:quantization recipe、calibration 数据采样、benchmark 加载模式等需要被抽象成可复用、可注册的标准化组件,让非 ML 系统专家的业务团队也能直接用;
5. **企业级基础设施集成**:要嫁接到 HDFS、内部模型仓库(MMS)、experiment tracking、Ray 调度器、Grafana 等现有系统,而不是搭一套平行栈。

## 3. 洞察与设计

**关键洞察**:LLM 生产部署的优化瓶颈主要不是算法瓶颈,而是**工作流瓶颈**——每个子任务(量化、calibration、benchmark、runtime tuning)单独看都已有成熟技术,真正稀缺的是把它们按正确顺序串起来、在异构资源上自适应分配、在 SLO 约束下自动收敛的**自动化框架**。只要把这条流水线本身标准化、声明化,就能把专家经验「物化」成平台能力,把 80–100 小时的人工优化压到 15–25 小时的自动化运行。

基于这个洞察,OPTIKIT 的设计围绕三条原则:

- **Automation**:所有阶段通过 declarative task definition 组合,用户只需声明 recipe 和 SLO;
- **Resource Awareness**:根据每个阶段的计算/数据特性动态分配 GPU/CPU,阶段间显式销毁 actor pool 回收资源;
- **Interoperability**:用标准化接口接 model registry、calibration 数据源、experiment tracking。

**整体 Flow**(Figure 2):Fetch → Model Compression(并行多 trial 采样 calibration)→ Statistical Evaluation → Inference Benchmarking → Deployment Tuning → Upload。若 SLO 不满足,调参迭代返回 Benchmarking 步骤。

**三层架构**(Figure 3):

| 层 | 职责 |
|---|---|
| Actor-Based Execution Layer | Ray actor 池,每种 actor 封装一类原子任务(QuantizationActor、BenchmarkerActor、TunerActor),独立管理 GPU/CPU,故障隔离 |
| Flow Composition Layer | 实现 BaseFlow 契约,把底层 actor 组装成 pipeline,负责 actor pool 的 sizing、queue load balancing、阶段间 teardown;每个 Flow 绑定版本化 Docker 镜像,通过 Flow Registry 注册 |
| Submission Engine Layer | 校验 job spec(Pydantic schema)、打包运行时、对接企业调度器,统一本地/远程执行入口 |

**四个核心子系统**:

- **Optimizer**:Backend-agnostic 压缩引擎。定义 Optimization-Backend 抽象接口,vLLM 的 LLMCompressorBackend 实现 GPTQ(int_w8a8 / int_w4a16)和 RTN-based FP8 dynamic 三类 recipe。引入 Recipe 概念,将 quantization scheme、calibration 要求、layer exclusion 策略打包为声明式配置;支持 uniform random、length-weighted、token-stat stratified 等多种 calibration sampling,并预留 adaptive calibration 扩展点。
- **StatEval**:统计评估模块。支持 vLLM(offline)和 OpenAI(online)两类后端,兼容任何 OpenAI 风格 endpoint。内置 GSM8K(推理)、IFEval(指令跟随)、Do-Not-Answer(安全)三个开源 benchmark,覆盖 LLM 三大核心能力;另有未公开的 eBay 内部 benchmark 作为生产指标代理。
- **Benchmarker**:SLO-driven 性能测试工具。最关键的两个算法组件是:
  - **稳态回归检测**:把请求到达时间 $r_i$ 和完成时间 $c_i$ 建成线性模型 $r_i = \alpha + \beta c_i + \varepsilon_i$,估计斜率 $\beta$。$\beta \approx 1$ 表示稳态(完成速率跟上到达速率),$\beta > 1$ 表示队列在无限增长的过载状态。判定条件为 $|\beta - 1| \leq \tau_\beta$($\tau_\beta$ 取 0.02–0.05)。
  - **Exponential Search(Algorithm 1)**:基线 closed-loop trial 先检查 SLO 是否可行,再用 open-loop 测试。SLO+稳态均通过则 `r ← 2r`,否则 `r ← (LB + r) / 2` 中点折半,直到 $|\text{best} - r| \leq T$ 收敛,输出最高可持续 rate。
- **Tuner**:Bayesian 自动超参优化。目标函数:

$$\text{fitness}(c) = \frac{\text{throughput}(c)}{\text{tensor\_parallel\_size}(c)} + \lambda \cdot \text{slo\_penalty}(c)$$

其中 $\lambda = -1000$ 对 SLO violation 施加强惩罚,throughput 按 per-GPU 归一化保证不同并行度的公平比较。搜索空间包括 tensor/data parallelism($\{1, 2, 4, 8\}$)、max_num_seqs、max_num_batched_tokens、context size(按 $(\text{input} + \text{output}) \times 1.15$ 预留);底层用 Ray Tune 的 Optuna 搜索器,算法为 TPE(Tree-structured Parzen Estimators)实现的贝叶斯优化。每个 trial 起一个临时 BenchmarkerActor,launch vLLM server,跑 steady-state 负载测试并把指标回报给 Tuner。

**总控制流(Algorithm 2)**:trial-parallel actor-pool 模式。每个阶段创建池、并行执行 $N_{\text{trials}}$ 个 trial、阶段结束显式 destroy pool 回收 GPU(保证分布式状态重置),然后进入下一阶段。

## 4. 实现细节

- **底层框架**:基于 Ray(Moritz et al., 2018)构建的分布式 Python SDK,所有计算任务包装成 `@ray.remote` actor。
- **Docker 版本化**:每个 Flow 绑定到特定 Docker image,确保运行时环境和依赖的可复现性,不同 release 之间完全隔离。
- **Recipe 注册机制**:Recipe 是声明式的,包含 quantization scheme、calibration 样本数、layer-selection 策略。论文当前提供 `int_w8a8`(GPTQ + SmoothQuant)、`int_w4a16`(GPTQ)、`fp8_dynamic`(RTN-based,不需要 calibration)三种。新 recipe 可在不改动核心优化逻辑的前提下注册进来。
- **Submission Engine**:job spec 定义了模型元数据(对接 eBay MMS model registry)、calibration 数据位置(HDFS)、flow_params(recipe、num_trials)、compute_config(如 `ResourceSKU.H100_8`)。Submitter 把完整 OPTIKIT runtime 打包成 self-contained bundle 提交到企业调度器。
- **Actor Pool 生命周期**:每个阶段的 actor pool 在开始时创建(sized to resource budget R),结束时显式 destroy 来释放 GPU 并重置分布式状态。这种 barrier 式同步是目前架构的设计,也是论文明确标注的未来优化点。
- **Trial 并行**:量化和 benchmark 阶段按 trial 并行执行(每个 actor 独立处理一个 trial);calibration 阶段为每个 trial 独立采样不同的 calibration 子集以捕捉 sampling 方差。
- **默认参数**:W8A8 用 256 个 calibration 样本、W4A16 用 512 个,跑 5 个独立 trial;Tuner 跑 30 次 TPE 迭代;Benchmarker 每个 sweep 持续 900s 请求提交以达到稳定利用率。
- **开源**:作者声明将开源整个系统,便于外部贡献和复现。

## 5. 实验结果

**实验环境**:eBay 生产集群中的 NVIDIA H100 GPU,对三个代表性模型做了端到端评估:Qwen 2.5 7B Instruct、Mistral Small 3 24B Instruct、Llama 3.3 70B Instruct。每个模型覆盖四类工作负载(见 Table 2),从 throughput-oriented 到 tight-latency 全谱。

### 5.1 统计质量(Table 3)

| Quantization | 平均 recovery | 备注 |
|---|---|---|
| FP8 Dynamic | > 99% | 不需要 calibration,无 trial 方差 |
| INT W8A8 | > 99% | 偶尔出现敏感 task(Mistral IFEval 降到 93.5%) |
| INT W4A16 | 可用但不稳定 | Qwen IFEval 上甚至超过 FP baseline(102.8%),但 RSD 高达 2.6% |

Mistral Small 3 24B 的 IFEval 是唯一明显退化点(93.5% recovery),作者归因于多指令遵循能力对低精度量化更敏感。Llama 3.3 70B 量化后 GSM8K 和 IFEval 基本保持 ≥ 100% recovery,只有 Do-Not-Answer 降到 95%。

### 5.2 Reproducibility(Table 4)

用 Qwen 2.5 7B 跑 100 次统计。默认 vLLM 下 GSM8K 的 RSD 是 0.243%,IFEval 是 0.652%;开启 vLLM deterministic 模式后 GSM8K RSD 降到 0.0%,IFEval 降到 0.129%。但作者明确指出:deterministic 模式禁用了多进程,无法在同一 Python session 中卸载 VRAM,仅适用 offline inference,**不是生产级方案**。这个 finding 也是论文 future work 的一部分。

### 5.3 推理性能(Table 5 核心结果)

每项指标是 SLO-compliant 的 per-GPU normalized TPS:

| Model / SLO | Baseline FP16 | Quant-only | Tuning-only | Q + T 联合 |
|---|---|---|---|---|
| Qwen 2.5 7B | 3.52* | 5.96 (1.69×) | 6.79 (1.93×) | 7.50 (**2.13×**) |
| Mistral 24B (p95 lat.) | 0.604* | 1.732 (**2.87×**) | 0.937 (1.55×) | 1.734 (2.87×) |
| Mistral 24B (TTFT/TPOT) | 0.562* | 0.562 (1×) | 0.750 (1.33×) | 0.875 (1.55×) |
| Llama 3 70B | 0.468* | 0.593 (1.26×) | 0.468 (1×) | 0.585 (1.25×) |

`*` 表示该 baseline 在某些 TP 档位上 SLO 根本不满足,只能靠 Q 或 T 才能进入可行区。

### 5.4 ROI 数据(Figure 1)

- 人工优化:80–100 小时专家工时(内部估算)
- OPTIKIT 自动化:15–25 小时端到端运行
- 最高吞吐增益:2.87×(Mistral 24B, p95 latency scenario)

## 6. 批判性分析

**论文是一篇扎实的工业工程报告,但也有多处值得审视的问题:**

1. **Baseline 定义偏弱,放大了"优化收益"**。Table 5 里所有 Baseline FP16 都带 `*` 标注——意思是这些 FP16 基线在作者选择的 TP 档位上**本来就 SLO 不合规**。用一个不可用的基线去和优化后的合规配置比倍数,是典型的 apples-to-oranges。一个更公正的对比是:「让一个中等水平工程师手工调过 vLLM 参数」作为基线,此时的 gain 会显著收窄。论文也没有提供「不用 Tuner 但手动粗调过 TP 和 max_num_seqs」的中间态数据。

2. **人工 vs 自动化工时对比的统计基础薄弱**。「80–100 小时」这个数字来自「internal estimates on internal data」,没有说明样本量、是否是同一个工程师在同样熟悉度下的对比、是否剔除了首次学习成本。对企业 ROI 叙事的核心数字,这种 estimation 不够严谨。

3. **Reproducibility 自相矛盾**。Section 5.3 承认 vLLM 非 deterministic 时 recovery 会随机波动(RSD up to 1.4%),而 automated 模型选择是基于「best-performing trial」——这等于基于采样噪声做决策。论文把这问题归到 future work,但它其实威胁到 Algorithm 2 里选择 $q^* \in S$ 的合理性:所选"代表性"量化模型未必真的是最优的。

4. **W4A16 的评价相互打架**。Section 5.3 说 "INT4 while viable... greater sensitivity to task characteristics",但 Table 3 里 Qwen IFEval 上 W4A16 的 mean 反而是 0.761(低于 full precision 0.773)、RSD 2.6%,Do-Not-Answer 的 RSD 也比 W8A8 高一个数量级。如果量化后要靠随机 seed 才能撞到 "102.8% recovery",那 W4A16 在生产中其实不应推荐给业务方——但论文没有明确这一点。

5. **SLO 设置的任意性**。Mistral Small 3 24B 的 TTFT p50 ≤ 50ms + TPOT p50 ≤ 10ms 是非常严格的组合(TPOT 10ms ≈ 100 tok/s 硬底线)。这类 SLO 的合理性、是否代表真实 eBay 生产场景,论文没有交代。系统的 gain 对 SLO 参数敏感度极高——调松 SLO 可以让 Tuner 显得更好,调紧则相反。

6. **Steady-state 判据的 tolerance 是经验值**。$\tau_\beta \in [0.02, 0.05]$ 的选择依据只写了「depending on noise and sampling granularity」,但这个阈值直接决定 exponential search 何时判定 trial 稳定。在高噪声的短 sweep 下,偏紧可能永远不 converge、偏松可能把过载误判为稳态。论文没给出 robustness 分析。

7. **Synchronization Barrier 的成本被低估**。作者自己在 future work 承认当前每阶段做 barrier 同步,不能异步调度 actor,导致 trial 数不能整除 GPU 数时 GPU 利用率偏低。这其实是对"2× per-GPU throughput 收益"的隐性拖累——如果阶段内部的实际 GPU 占用率只有 60%,Table 5 的绝对数字就在高估可部署的算力效率。

8. **评价 benchmark 覆盖面偏窄**。只用 GSM8K(推理)+ IFEval(指令)+ Do-Not-Answer(安全)。长上下文能力(RULER、LongBench)、多语言、工具调用等能力是否也在 INT4/W8A8 下保持,论文没做实验。在 Section 6 中作者自己提到 short-context calibration 对 long-context 任务的影响是 open question——但这其实是把一个本应在论文里验证的点 deferred 到了 future work。

9. **比较 Table 1 的 ✓/× 自打折扣**。Table 1 对其他工具的 feature 评估缺乏细致的引用依据。例如 SCOOT 的 inference benchmarking 能力被标 ✓,deployment tuning 也标 ✓,但 Model Compression 和 Statistical Evaluation 标 ×——作者只是想突出 OPTIKIT 是唯一全勾的那行。这种市场化比较适合企业 pitch deck,但在学术论文里略显 heavy-handed。

## 7. AI Infra / MLSys 视角

这篇论文本身就是 AI Infra / MLSys 论文,更适合从「可借鉴 insight」角度读:

- **Recipe 抽象是被严重低估的工程设计**。把 quantization scheme + calibration 策略 + layer exclusion 打包成可注册、可版本化的 declarative 配置,是 ML 系统平台化的核心抽象。这个模式可以直接迁移到其他优化维度:distillation recipe、prune recipe、speculative decoding 配置 recipe、KV cache 压缩 recipe。任何一个想做「LLM 优化平台」的团队都应该优先定义自己的 Recipe schema。

- **Steady-state regression 判据可以成为 SLO-driven benchmark 的标准组件**。相比 GuideLLM 这类只看 avg/p95 latency 的工具,通过 $r_i$ 和 $c_i$ 的线性回归斜率 $\beta$ 来判定 queue 是否发散,是一个非常优雅的低开销诊断方法。值得进一步研究:在 continuous batching + chunked prefill 下,这个模型是否还成立?是否需要为 prefill / decode 两阶段分别拟合?是否能推广到 disaggregated serving(prefill/decode 分离架构)的稳态检测?

- **Actor Pool 生命周期 + Barrier 同步的 trade-off 很值得研究**。作者自己承认这是次优,future work 是做全局异步调度。这个方向非常有价值:在 trial-parallel + 阶段间资源复用之间,如何设计一个 GPU 利用率接近 100%、又能保持 trial 结果可复现的调度器?相关工作可参考 Ray Workflow、Flyte、以及学术界的 ML pipeline scheduler(Alpa 的 pipeline parallelism 调度)。

- **Calibration Data Sampling 是被研究圈忽视的方向**。Section 4.1 提到了 uniform、length-weighted、token-stat-stratified 几种 sampling,并暗示 "adaptive calibration"(即根据量化过程的中间结果动态调整采样)是未来方向。这其实可以是一篇独立的论文——将 active learning 思想应用到 calibration sampling:每轮根据量化引入的激活分布偏移动态补采样。与 SpQR、AWQ 的 outlier-aware 方法结合应该有新空间。

- **Bayesian TPE + per-GPU normalized throughput 的目标函数**。把 throughput 按 TP 归一化是一个简单但非常重要的 choice——否则 Tuner 会收敛到 TP=8 的「看起来吞吐最高但单卡效率低」的配置。这个 normalization 思路可以推广到:按 GPU-hour 成本归一化、按 $ per request 归一化,用于跨硬件代际(H100/H200/B200)的联合调优。

- **可操作的跟进研究方向**:
  1. 把 pruning(Wanda、SparseGPT、hardware-structured 2:4 sparsity)接入 Optimizer 的 Recipe 抽象,验证 prune + quantize 的联合 recipe 是否能在 Tuner 目标函数下自动找到最优点;
  2. 用 OPTIKIT 做 quantization 与 speculative decoding 的联合优化——两者都改变推理 runtime 的性能剖面,Tuner 需要同时搜索 quantization level 和 draft model 配置;
  3. 将 Steady-state regression 判据扩展到 disaggregated serving,针对 prefill cluster 和 decode cluster 分别拟合 $\beta$,作为 KV cache transfer 背压的在线信号;
  4. Reproducibility 问题严重影响自动模型选择——可以做一个 hypothesis testing layer,基于 paired bootstrap / BCa confidence interval 来决定「这个 trial 是否真的比另一个好」,再把结果反馈给 Algorithm 2 里的 $q^*$ 选择逻辑。

## 8. 总结

OPTIKIT 是 eBay 在生产环境中落地的自动化 LLM 优化框架,核心贡献是把 quantization、statistical evaluation、SLO-driven benchmarking、Bayesian runtime tuning 这四个原本割裂的子任务,用 Ray actor pool + declarative recipe + Flow Registry 的分层架构串成了端到端的流水线。最突出的工程 insight 是:把「稳态回归检测 + exponential search」作为 benchmark 算法、把「throughput / TP + SLO penalty」作为 Tuner 的目标函数,两者联合保证了在真实 SLO 下找到可持续吞吐最大化的配置。

实验上,在 Qwen 7B / Mistral 24B / Llama 70B 上取得了 1.25×–2.87× 的 per-GPU 吞吐提升,人工优化工时从 80–100 小时降到 15–25 小时。主要局限在于:FP16 baseline 很多情况下本身不合规,放大了 gain 的视觉效果;non-deterministic 环境下基于 best-trial 选模型有统计 rigor 问题;synchronization barrier 架构带来的 GPU 碎片化是下一步的关键瓶颈。这篇工作的价值更多体现在工业界的平台化实践参考——对学术研究而言,Recipe 抽象、Steady-state 判据、per-GPU normalization 等设计思路都值得迁移到其他 LLM 系统研究场景。
