## 一、背景

企业大规模部署 LLM 面临 GPU 资源有限与需求快速增长之间的矛盾。模型规模从 8B 到 70B+ 参数不等，手动优化（量化、推理参数调优、部署配置）需要深厚的 ML 系统专业知识，而这类专家在组织中极为稀缺。现有工具要么只覆盖优化流程的某个环节（如 TensorRT-Sweep 只做推理调优、GuideLLM 缺少部署调优），要么存在数据主权问题（云端服务），无法提供端到端、生产级的自动化优化方案。这种局面导致优化工作成为组织瓶颈，不同团队重复劳动，结果难以复现。

---

## 二、要解决的问题

1. **专家瓶颈**：LLM 优化（模型压缩、硬件特定调优、推理运行时配置）依赖少数专家，无法随业务扩展。手动优化一个模型需要 80-100 小时专业工作。
2. **工具碎片化**：现有方案只解决部分问题——要么只做量化、要么只做推理 benchmark、要么只做运行时调优，缺乏覆盖全流程的统一框架。编排、资源管理和质量保证的负担仍落在用户身上。
3. **异构基础设施管理**：企业环境中 GPU 类型多样（A100/H100/H200），模型架构和使用场景各异，需要灵活的资源分配和优化策略。
4. **可复现性**：生产环境中模型评估的可复现性受 CUDA 非确定性影响，缺乏统计严格的评估协议。

---

## 三、洞察与设计

**关键洞察**：LLM 优化的各个阶段（压缩、评估、benchmark、运行时调优）虽然技术各异，但可以被抽象为统一的 staged pipeline，通过声明式配置和动态资源分配实现自动化编排，使非专家团队也能获得专家级优化效果。

### 系统设计

OPTIKIT 是一个基于 Ray 的分布式 Python SDK，包含三层架构：

- **Actor 执行层**：专用 Ray Actor 处理具体优化任务（量化、评估、benchmark），支持故障隔离和细粒度 GPU/CPU 分配。每个阶段之间显式销毁 Actor Pool 以回收资源。
- **Flow 编排层**：Flow 实现 `BaseFlow` 契约，将低级 Actor 组合为可执行 pipeline。Flow 通过 Flow Registry 注册，支持团队扩展新工作流而不修改核心代码。
- **提交引擎层**：负责作业验证（Pydantic schema）、打包、分布式执行，提供统一的本地/远程执行接口。

### 四大核心子系统

1. **Optimizer**：后端无关的压缩框架，通过 recipe 机制（int_w8a8、int_w4a16、fp8_dynamic）将量化配置声明化，支持自适应校准数据采样。
2. **StatEval**：统计评估库，支持 vLLM 离线和 OpenAI 在线推理后端，覆盖 GSM8K、IFEval、Do-Not-Answer 等 benchmark。
3. **Benchmarker**：SLO 驱动的性能测试工具，通过回归分析检测稳态（β ≈ 1 表示到达/完成速率平衡），结合指数搜索 + 二分法找到最大可持续请求速率。
4. **Tuner**：基于 Ray Tune + Optuna（TPE）的贝叶斯运行时参数优化，搜索 tensor parallelism、max_num_seqs、max_num_batched_tokens 等参数，以 per-GPU 吞吐量为优化目标，SLO 违反施加大惩罚（λ = -1000）。

## 四、实现细节

- 基于 **Ray** 构建分布式执行框架，Actor 按需创建和销毁，stage 间设同步屏障保证资源回收
- 量化 recipe 封装所有超参数（量化方案、校准需求、层选择策略），通过 `get_recipe()` + `recipe.create()` 生成完整配置
- 校准数据采样支持均匀随机、长度加权、token 统计分层等策略
- Benchmarker 稳态检测：拟合回归 $r_i = \alpha + \beta c_i + \epsilon_i$，判定 $|\beta - 1| \leq \tau_\beta$（τ 通常 0.02-0.05）
- Benchmarker 搜索：通过指数倍增找上界，二分法（midpoint halving）收敛到最高可持续速率
- Tuner 搜索空间：tensor parallel ∈ {1,2,4,8}，max context size = (input_len + output_len) × 1.15
- 每个 Flow 绑定版本化 Docker 镜像，确保跨版本可复现
- 整体流程：Fetch → Quantization（多 trial 并行）→ Statistical Evaluation → Benchmarking → Tuning → Upload

## 五、实验结果

**实验环境**：NVIDIA H100 GPU，vLLM 推理栈。

**模型**：Qwen 2.5 7B Instruct、Mistral Small 3 24B Instruct、Llama 3.3 70B Instruct。

### 量化精度保持（Table 3）

| 模型 | 量化方式 | GSM8K Recovery | IFEval Recovery | Do-Not-Answer Recovery |
|------|---------|---------------|----------------|----------------------|
| Qwen 2.5 7B | FP8 | 99.0% | 98.1% | 100.2% |
| Qwen 2.5 7B | INT W8A8 | 99.6% | 99.2% | 100.3% |
| Mistral 24B | FP8 | 99.5% | 99.1% | 100.1% |
| Mistral 24B | INT W8A8 | 101.3% | 93.5% | 99.0% |
| Llama 3.3 70B | FP8 | 100.1% | 100.9% | 95.4% |
| Llama 3.3 70B | INT W8A8 | 100.2% | 101.2% | 95.6% |

FP8 和 INT W8A8 平均 recovery > 99%，INT W4A16 表现不稳定。

### 推理吞吐量提升（Table 5）

| 模型 | Baseline TPS | 量化 only | 调优 only | 量化+调优 | 总增益 |
|------|-------------|----------|----------|----------|--------|
| Qwen 2.5 7B | 3.52* | 1.69× | 1.93× | 2.13× | 7.50 TPS |
| Mistral 24B (p95) | 0.604* | 2.87× | 1.55× | 2.87× | 1.734 TPS |
| Mistral 24B (TTFT/TPOT) | 0.562* | 1× | 1.33× | 1.55× | 0.875 TPS |
| Llama 3.3 70B | 0.468* | 1.26× | 1× | 1.25× | 0.585 TPS |

*标注表示 baseline 未满足 SLO。

### 工程时间节约

手动优化约 80-100 小时 → OPTIKIT 自动化 15-25 小时，端到端运行时间 16-27 小时/模型。

## 六、批判性分析

1. **吞吐量增益的不均匀性**：Qwen 7B 获得 2.13× 提升，但 Llama 70B 仅 1.25×，且调优 only 对 Llama 70B 完全无效（1×）。论文将此归为"throughput-focused regimes 的 diminishing returns"并轻描淡写，但这恰恰是最需要优化的大模型场景。

2. **Baseline 设置问题**：大量实验的 baseline 标注为 "SLOs not met"（*），意味着 FP16 + 默认参数本身就不可用。在这些场景下的增益倍数缺乏参考意义——与其说是"优化"，不如说是"使其可用"。将此报告为 2.87× 增益具有误导性。

3. **缺乏与同类工具的直接性能对比**：Table 1 只做了功能矩阵比较（有/无某组件），但没有在相同模型和硬件上与 SCOOT、GuideLLM 等做吞吐量或延迟的直接 benchmark 对比。

4. **评估 benchmark 覆盖不足**：仅使用 GSM8K、IFEval、Do-Not-Answer 三个通用 benchmark，对于声称的 "production-grade" 系统，缺少任务特定（如 eBay 电商场景）的质量评估结果。论文提到有 proprietary benchmark 但完全未披露数据。

5. **Stage 间同步屏障的效率损失被忽视**：论文在 Future Work 中承认同步屏障导致 GPU 利用率不佳（trial 数不整除 GPU 数时），但未量化这一开销。对于声称"resource-aware"的系统，这是显著的设计缺陷。

6. **校准数据策略的评估缺失**：论文介绍了多种采样策略（均匀随机、长度加权、token 统计分层），但实验中全部使用 NeuralMagic 的默认校准数据集，未验证不同策略的实际效果差异。

7. **可复现性问题**：Table 4 展示了 CUDA 非确定性带来的评估变异，但论文仅讨论了 vLLM 确定性模式的局限，未给出实际生产中采用的统计检验方法。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

- **SLO 驱动的自动化调优范式**：将推理优化从"追求最大吞吐"转为"SLO 约束下的最优配置搜索"，这一建模方式对任何推理服务系统都有借鉴意义。fitness 函数中 SLO 惩罚项的设计（λ = -1000）简单有效。
- **稳态检测的回归方法**：用请求到达-完成时间戳的线性回归斜率判断系统是否过载（β > 1），比简单的延迟阈值更能反映系统动态行为，可迁移到通用 serving benchmark 工具中。
- **Recipe 抽象**：将量化配置声明化的思路可以推广到更广泛的模型优化场景（如 pruning + quantization 联合搜索、distillation pipeline）。

### 值得跟进的方向

1. **压缩-调优联合优化**：当前 pipeline 是顺序执行（先压缩再调优），搜索空间爆炸问题限制了多技术组合。能否设计高效的 co-optimization 策略（如压缩方案与 serving 配置的联合贝叶斯优化）是一个有价值的研究问题。
2. **异步 stage 调度**：突破同步屏障限制，实现 trial 级别的流水线并行（前一个 trial 评估完成后立即进入 benchmark，不等待同批次其他 trial），可显著提升 GPU 利用率。
3. **Workload-aware 自适应校准**：根据目标部署场景的实际 query 分布动态选择校准数据，而非使用通用数据集。

---

## 八、总结

OPTIKIT 是 eBay 开发的端到端 LLM 优化框架，基于 Ray 构建分布式 pipeline，自动化模型量化、统计评估、推理 benchmark 和运行时调优的全流程。系统在 Qwen 7B、Mistral 24B、Llama 70B 上验证，最高实现 2.87× per-GPU 吞吐提升，同时将工程时间从 80-100 小时缩减到 15-25 小时。其核心价值在于将专家级优化知识编码为可复用的自动化 pipeline，降低非专家团队的使用门槛。主要局限包括：大模型场景增益有限、stage 间同步导致资源浪费、缺乏与同类工具的直接性能对比。
