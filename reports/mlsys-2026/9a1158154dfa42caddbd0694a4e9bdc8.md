# HexiScale: Accommodating Large Language Model Training over Heterogeneous Environment

**作者**:Ran Yan, Fangcheng Fu, Youhe Jiang, Bin Cui, Xiaonan Nie, Binhang Yuan
**单位**:The Hong Kong University of Science and Technology,Peking University
**会议**:MLSys 2026
**链接**:https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**:[[9a1158154dfa42caddbd0694a4e9bdc8.pdf]]

---

## 1. 背景

大语言模型(LLM)的训练极度依赖 GPU 算力,GPT、Llama、Mixtral 等模型动辄需要数千张高端 GPU 持续运行数月,训练成本成为限制 LLM 演化的主要瓶颈。主流训练系统(Megatron、DeepSpeed 等)通常假设底层集群是**同构**的 —— 所有 GPU 具有相同的算力(peak FLOPS)、相同的 HBM 容量、以及对等的 GPU-GPU 网络带宽。

然而现实世界的 GPU 资源天然是**异构**的:芯片厂商大约每 24 个月发布一代新架构(Turing 2018、Ampere 2020、Hopper 2022、Blackwell 2024),而老型号(如 K80)仍在被云平台长期使用。云服务商、科技公司和研究机构手里往往堆积着跨代际、跨型号的 GPU 资源。如果能把这些"碎片化"的异构资源组合起来协同训练 LLM,就能大幅降低训练门槛、让 LLM 训练"民主化"。

---

## 2. 要解决的问题

现有训练系统在异构场景下遇到两大根本性挑战:

- **GPU 算力与显存不均衡**:同一集群中 GPU 的 peak FLOPS 和 HBM 容量可能相差数倍(如 A800-80G vs 4090-24G vs 3080Ti-12G)。如果所有 GPU 被分配同样大小的计算负载,强 GPU 会被拖慢到弱 GPU 的节奏,显存小的 GPU 会 OOM。
- **GPU-GPU 网络带宽异构**:NVLink(200 GB/s)、PCIe(16–32 GB/s)、Ethernet(1 GB/s)的带宽差距可达两个数量级。一旦把本应走 NVLink 的 tensor parallel 通信放到 Ethernet 上,单层通信开销会从 0.01s 飙升到 1.88s,彻底摧毁系统效率。

Megatron、DeepSpeed 这类系统强制所有 DP group/TP group/PP group 采用**完全对称**的并行度,在异构环境下必然出现:强 GPU 被当作弱 GPU 使用、高带宽链路闲置、低带宽链路被迫承担 tensor parallel 等问题。Galvatron 允许每个 stage 分配不同层数但并行度仍对称,灵活性有限。Metis 支持单 pipeline 内变化的 DP/TP 组合,但其设计偏向高 DP 并行度,放大了 pipeline bubble。总之,**现有系统要么不支持足够细粒度的非对称分区,要么缺乏有效的调度算法**,无法真正释放异构算力。

---

## 3. 洞察与设计

**关键洞察**:异构集群的并行策略**必须在 data、pipeline、tensor 三个维度上都允许完全非对称** —— 即不同 pipeline 可以有不同 batch size、不同 pipeline 可以有不同 TP 度、不同 pipeline stage 可以分配不同层数、甚至不同 stage 的 TP 度也可以不同。只有这种细粒度的非对称能力,才能让每块 GPU 按自身的算力/显存/带宽承担"恰到好处"的负载。在这种自由度下,把 GPU 划分到 pipeline 的问题天然匹配**带宽敏感的图分区问题**:高带宽 GPU 内部建议共享 tensor parallel,低带宽链路则放在 data parallel 同步处。

HexiScale 基于此洞察的核心设计:

**(1) 非对称计算分区**。每条 pipeline 可以独立设置 batch size 与 TP 度。同一 pipeline 的不同 stage 允许分配不同数量的 transformer 层。每个 stage 选择一个 **leader GPU** 负责跨 stage 的激活/梯度通信,然后 broadcast 给 stage 内的 TP group。

**(2) 非对称梯度同步**。不同 pipeline 的同一 transformer 层因 TP 度不同,参数/梯度可能被切成不同大小的分片。HexiScale 的做法是:找出最小分片尺寸,把较大的梯度进一步切成与之对齐的多个 chunk,然后在不同的 DP 子集上独立 all-reduce —— 实现"异构分片"的 data parallel 同步,不引入额外通信量。

**(3) 两阶段层次化图分区调度**。第一阶段(Figure 2):把所有 GPU 建成全局图,vertex 权重是算力 c_d,edge 权重是 GPU 对之间的带宽 β,使用多级图分区(coarsen → partition → project → refine,依赖 HEM 和 Kernighan-Lin 算法)将 GPU 切成 D_dp 组,每组构建一条 pipeline;第二阶段(Figure 3):对每条 pipeline 的 GPU 集合再建"secondary graph",先按带宽聚类成多个 GPU 子组,每个子组内部搜索局部最优的 TP/PP 组合,最后用 top-k 贪心搜索确定 pipeline stage 的排列顺序(让 inter-group 的低带宽链路被 pipeline parallel 利用,而不是让它压垮 tensor parallel)。

**(4) 迭代优化**。第一阶段迭代枚举 D_dp(pipeline 数量),并基于历史 cost 的移动平均自适应选择**最大化或最小化 cut**(对应为 DP 分配高带宽或低带宽):当 pipeline 执行时间主导时,minimize cut 把大带宽留给 pipeline;当 DP 通信主导时,maximize cut 把大带宽留给 DP。第二阶段迭代调整每条 pipeline 的子组数 k_i。模拟器用 cost model(附录 A)估算每个方案的迭代时间,OOM 方案标注为无穷大。

## 4. 实现细节

- **Transformer 层**:基于 FlashAttention-2 API 构建,自带 TP 支持,叠加 HexiScale 自己实现的非对称 pipeline parallel 语义。
- **非对称 DP 同步**:通过向 FSDP 注册自定义 communication hook 实现梯度 chunk 拆分 + 子集 all-reduce。
- **系统优化**:支持 gradient accumulation(降低 DP 通信频率)和 activation recomputation(降低显存占用)。
- **Pipeline 通信**:每个 stage 的 leader GPU 负责跨 stage 的 point-to-point send/recv,接收后在本 stage 的 TP group 内 broadcast 给其他 GPU。
- **调度器**:第一阶段使用基于 multi-level graph partitioning 的算法(参考 METIS 库的思路,用 HEM + 递归二分 + Kernighan-Lin refine);第二阶段用 top-k 贪心枚举 stage order。50 次迭代即可收敛,320 张 GPU 规模下 12 核 CPU 仅需不到 2 分钟。
- **Cost model**:同时考虑计算时间、通信时间、网络 latency α_{d,d'}(NCCL 在大量 microbatch 下 latency 累积显著),模拟器误差 < 2%。

## 5. 实验结果

**模型与基线**:Llama-2 7B、Llama-2 13B、Llama 30B;基线包括同构集群下的 Megatron、Galvatron、FSDP,以及异构集群下的 Metis。

**异构集群设置**(跨机 Ethernet 约 0.7 GB/s):
- Setting 1:1×8×3080Ti + 1×8×3090 + 3×8×4090(总 FLOPS 比 2×8×A800-80G 高 1.36%)
- Setting 2:1×8×3080Ti + 1×8×3090 + 1×8×4090 + 1×8×A800-NVLink
- Setting 3:1×8×3090 + 2×4×3090 + 4×8×4090 + 1×8×A800-NVLink(vs 4×8×A800-80G)

**核心结论**:

| 对比维度 | 结果 |
|---|---|
| HexiScale (异构) vs Megatron/Galvatron (同构 Ethernet) | MFU gap 最小 **0.3%**,平均 **3.5%** |
| HexiScale vs Galvatron (异构) | 最大 **2.5×** MFU,平均 **2.1×** |
| HexiScale vs Metis (异构 Setting 3) | **1.6×** MFU(Metis 17.1%,HexiScale ~27.5%) |
| 大规模模拟(240 GPU,30B/70B) | 比 Metis 快 **1.6×–1.9×**,比 Galvatron 快 **2.7×–3.3×** |
| 同构 RDMA 设置下 | 与 Megatron/Galvatron 表现相当(HexiScale 非对称设计不拖后腿) |

**Ablation**:关闭非对称并行支持,性能最多下降 23%(30B),平均 15%;关闭 gradient accumulation,性能最多下降 15%(30B),平均 12%。延迟 breakdown 显示 HexiScale 相比 Galvatron 主要是减少了 pipeline bubble 和跨机通信时间。

**调度算法评估**:
- 模拟器误差全部 < 2%(Real vs Simulation,例如 Llama-2 7B Homo-RDMA 53.7% vs 54.0%,30B Hetero-3 27.5% vs 28.0%)。
- 相对于随机图分区,HexiScale 在 20 轮搜索中平均高出 **8%**(7B)到 **23%**(30B)MFU。
- 64–320 GPU 规模下调度时间 < 2 分钟,可扩展性良好。
- Case study:30B 在 Setting 3 下发现 4 条 pipeline,其中 A800 pipeline 单 stage 跑 60 层 TP=8,4090 pipeline 跑 3 stages 共 42 层 TP=4,3090 作为小 stage 分担少量层,充分体现了"按硬件特性分配负载"。

## 6. 批判性分析

1. **"comparable to homogeneous" 的声明需要谨慎解读**。论文强调 HexiScale 在异构集群上 MFU 仅比同构集群低 0.3%–3.5%,但前提是:(a) 同构对照用的是 **Ethernet 跨机连接**,而非论文也测试过的 RDMA 场景;(b) 异构集群的总 FLOPS 被刻意调到与同构集群相近(±5%)。在**有 RDMA 的同构数据中心**,Megatron/Galvatron 的 MFU 比 HexiScale 在异构集群上**显著更高**(例如 Llama-2 7B 同构 RDMA 53.7% vs 异构 Setting 1 的 31.2%),gap 接近 20 个百分点。真实场景下,"同构 RDMA" 才是 LLM 训练的主流基线,这里的 gap 其实很大。

2. **Ethernet 同构基线的合理性存疑**。把同构 A800 集群限定为 Ethernet 跨机,是一个相对弱的基线 —— 实际运营的同构集群几乎一定会配 RDMA。用这个弱基线对比得出 "HexiScale 接近同构" 的结论,对读者可能造成误导。

3. **调度算法的 near-optimal 无法验证**。论文将问题定义为 NP-hard,然后用两阶段启发式给出"near-optimal"解,但缺少与精确解(例如小规模 MILP)的 gap 验证(只在附录 D 简单提了 MILP 对比,正文没细节)。图 8 只显示比随机分区好 8%–23%,这个 margin 并不能证明接近最优;也可能其他启发式算法同样能拉开与随机的差距。

4. **异构配置是人为挑选的"好场景"**。三个 Heterogeneous setting 都精心配置了至少一台高带宽机器(NVLink A800 或连续的 8× 同型号 GPU),让 HexiScale 的 TP 分组有"肥沃土壤"。如果集群真的极度碎片化(例如 1×A800 + 1×4090 + 1×3090 + 1×3080Ti 都分散在不同机器),TP 根本没法用,HexiScale 的核心优势 —— 允许某些 pipeline 用高 TP —— 就不成立,系统性能会急剧退化,但论文未呈现此类"最坏情况"。

5. **非对称 DP 同步的正确性只是工程论述**。论文描述了通过切 chunk + 子集 all-reduce 实现异构 DP,但没有给出严格的数学证明说明梯度同步语义与对称 DP 完全等价。在实际训练中,异构分片可能引入细微的数值差异(尤其是 fp16/bf16 累加顺序不同),需要额外的 loss 曲线验证。

6. **Metis 对比不公平**。Metis 未开源训练系统,HexiScale 运行的是"Metis 调度器输出的方案 + HexiScale 模拟器"。如果 HexiScale 模拟器对 Metis 设计假设估计得不够好,Metis 的性能可能被低估。

7. **7B 尺度实用价值存疑**。7B 模型完全可以塞进单张 A800 甚至 4090,异构训练反而引入跨机通信开销。真正有动机"挖掘碎片算力"的是 70B+ 级别模型,而论文只给了 70B 的**模拟结果**,没有实机。大模型 scaling 的实际挑战(例如 activation 显存、跨机通信放大)可能让真实数字与模拟产生偏差。

8. **Bubble 占比论述不完整**。论文多次声称 HexiScale 相比 Megatron/Galvatron 显著减少 bubble,但在自身的异构设定下,跨机低带宽仍然会引入 pipeline 通信延迟,bubble 比例到底是多少、与同构 RDMA 集群的 bubble 差距多大,没给出具体数字。

## 7. AI Infra / MLSys 视角

这篇论文对 AI 基础设施研究有几方面启发:

**直接启发**:
- **非对称并行的系统抽象**是当前训练框架演进的重要方向。Megatron-LM 的对称并行模型是 2020 年代初形成的,当时还没有"用消费级 + 上代企业级 GPU 拼算力"的迫切需求。HexiScale 展示了"每条 pipeline 独立配置、每个 stage 独立配置"的可行实现路径,值得集成到开源主流框架(如 DeepSpeed、PyTorch FSDP2)。
- **图分区作为 scheduling 元算法**很有借鉴价值。以往 parallelism 搜索多使用 DP(如 Alpa)或 MILP,容易遇到爆炸的搜索空间。把"GPU 分组"这个子问题抽象成带权图切分 + METIS 风格多级算法,在 320 GPU 规模下 2 分钟搞定,性价比极高,可以迁移到推理场景的 request routing、KV cache sharding 等问题。
- **asymmetric DP chunk + 子集 all-reduce** 是一个被低估的通信原语。它允许不同 pipeline 在相同 transformer 层上使用不同 TP 度,这种能力在 **MoE 训练**中也有价值 —— 不同 expert 的 TP 度可以按负载动态调整。

**可迁移到推理场景**:
- **异构推理集群**(例如 L40S + H100 混合)现在已是很多推理服务商的现实。HexiScale 的 GPU 分组 + pipeline 分层思路可以迁移到 PD 分离架构:Prefill 节点和 Decode 节点本来就对算力/带宽需求不同,可以用类似图分区算法把异构 GPU 分配给 P 和 D 两类 worker。
- **KV cache 的异构存储**:异构 DP 同步的 chunk 拆分思路启发 KV cache 可以按 GPU 显存能力动态分片,不同 replica 持有不同大小的 cache 段。

**有价值的未来方向**:
1. **动态资源弹性**:现实集群 GPU 时常被抢占、掉线或加入。HexiScale 目前是静态规划一次,如果能支持训练中途 re-partition(例如基于 checkpoint 迁移 + 增量 scheduling),价值会大很多。可研究问题:给定一次 graph re-partition 的成本(通信开销 + restart time),如何决策何时触发?
2. **与 fault tolerance 结合**:异构集群天然 MTBF 较低,HexiScale 的 pipeline 分组是否能和 Gemini、Varuna 等 fault-tolerant 训练系统结合,使单个 pipeline 失败不影响其他 pipeline?
3. **将 cost model 从 hand-crafted 升级为 learned model**:目前 cost model 是基于解析公式,在复杂网络(如异构 NIC + 多层交换机)下精度可能不足。可以尝试用小规模采样 + 回归模型代替。
4. **与 sparse training/MoE 结合**:MoE 模型每个 expert 的负载高度不均,天然适合非对称并行。HexiScale 的调度思路可以直接迁移到 **异构 MoE 训练**,这是一个具体的研究入口。
5. **向下扩展到 LoRA/SFT 场景**:LoRA 微调的模型参数显存占用很小,更适合异构集群。HexiScale 目前的 benchmark 以 pre-training 为主,在 SFT/RLHF 场景下是否有类似收益值得研究。

**最有价值的切入点**:结合 HexiScale 的 graph-partition 调度器 + ByteDance MegaScale 类的 straggler detection 机制,做一个**动态异构训练系统**,应对真实生产环境中 GPU 频繁掉线、不同节点网络突发拥塞的场景。相比单纯追求静态最优 MFU,动态适应性可能是真实落地时更大的价值点。

---

## 8. 总结

HexiScale 系统性地解决了异构 GPU 集群上 LLM 训练的两大核心难题 —— 算力/显存不均衡与 GPU-GPU 带宽不均衡 —— 通过**在 data、pipeline、tensor 三个维度上全面支持非对称分区**,以及**两阶段层次化图分区调度算法**。在 7B–30B 模型的实验中,它在异构集群上的 MFU 能逼近同构 Ethernet 集群(最小 0.3% gap),并显著优于 Galvatron(2.1×)和 Metis(1.6×)。适用场景是已经持有或能访问到多代际、多型号 GPU 的研究机构、中小云服务商、以及想用"捡漏"消费级/上代 GPU 训练中等规模模型的团队。主要局限是:(a) 与真正的同构 RDMA 集群相比仍有 ~20pp 的 MFU 差距;(b) 依赖集群中存在至少几台"结构良好"的高带宽机器才能发挥 TP 优势;(c) 静态规划,缺少对动态 GPU 加入/退出的支持;(d) 70B+ 大模型缺乏实机验证。整体上,这是推动 LLM 训练民主化的一篇扎实系统工作,其非对称并行与图分区调度思路对 AI Infra 领域具有可迁移的方法论价值。
