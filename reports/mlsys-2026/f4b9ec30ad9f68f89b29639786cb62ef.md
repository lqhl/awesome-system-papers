## 1. 背景

近年大模型训练越来越依赖合成数据,以缓解人类标注数据稀缺、昂贵或涉及隐私的问题。Llama 3、Phi-4、DALL·E 3 等代表性工作均把合成数据作为关键来源。更进一步,业界正从「单模型生成」转向「多智能体协作生成」(agentic synthetic data generation):由不同角色的 agent 通过多轮对话、工具调用、环境交互来生成更高质量、更多样、结构更复杂的数据。Kimi K2 用大规模多 agent pipeline 生成工具使用与推理示例;CWM 用自主软件工程 agent 生成多步代码理解轨迹。这类工作流普遍包含循环、条件分支等复杂控制流,远超传统线性 ETL pipeline,对底层运行时框架提出了新的可扩展性与灵活性要求。

---

## 2. 要解决的问题

现有框架不能同时满足「大规模合成数据生成」所需的可扩展性与灵活性:

1. **通用 agent 框架不为大规模数据生成优化**:Autogen、LangGraph、CrewAI 等面向 chatbot、个人助手等场景,提供 agent 工作流抽象,但单个进程内调度成千上万并发任务时调度开销显著。
2. **领域专用框架灵活性差**:AgentInstruct、SWE-Agent、SWE-Synth、TaskCraft、AgentSynth 等把 orchestration 和 scheduling 硬编码进具体业务逻辑,迁移到新场景需要重写大量代码。
3. **集中式 orchestrator 是可扩展性瓶颈**:单 orchestrator 同时管理上万个并发任务时,本身成为热点,无法线性扩展。如 Coral 官方实现使用单 orchestrator,在 Llama-3.1-8B 上扩到一定 GPU 规模后吞吐就饱和。
4. **批级调度造成 GPU 空闲**:复用 Spark/Ray Data 这类批处理引擎时,batch barrier 等待 batch 内最慢任务完成,异构、动态控制流任务下空闲严重。
5. **大消息(对话历史)在 agent 之间反复传递,网络开销随并发线性增长**;直接 offload 到外部 cache(如 Redis)又会引入 agent–cache 双向流量,反而加倍带宽。

---

## 3. 洞察与设计

**关键洞察**:多 agent 工作流的全部状态(控制流位置、对话历史、中间结果)都可以序列化进单一 orchestrator 消息中,在 agent 之间点对点传递;一旦做到这点,agent 自身就可以无状态、可任意水平扩展,集中式 orchestrator 也就不再是必要成分。配合「row-level scheduling」(每条数据完成后立刻进入下一阶段,不等同 batch 中其他任务),可以彻底消除 batch barrier 带来的空闲时间——这与 LLM serving 中「continuous batching」按 token 调度异曲同工。

基于这一洞察,Matrix 的核心设计是 **P2P agent 架构 + 分布式服务层**:

- **可序列化的 Orchestrator 消息**:封装控制流(下一步该哪个 agent)+ 数据流(对话历史等),通过分布式队列在 agent 间传递。
- **无状态 Ray Actor agent**:每种 agent role 对应一组 Ray actor,任务级状态全部在 Orchestrator 消息里,actor 自身不持有任务状态,可弹性扩缩。
- **Driver 仅负责发送任务**:把传统集中式 orchestrator 的「全程协调」职责退化为「初始投递」。任务一旦投递就在 agent 网络中自驱动地推进,直到 `_sink` agent 持久化最终结果。
- **行级调度**:每个任务独立流转,完成的任务立即进入下游,不需要等同 batch 其他任务,消除 batch 调度气泡。
- **分布式服务层**:LLM 推理、容器化工具执行等重型计算下沉到独立服务(vLLM、SGLang、FastGen、Apptainer),与 agent 解耦,独立扩展。
- **Sequential / Hierarchical Orchestrator**:配置化的执行顺序(顺序、循环、条件分支),通过 Hydra 描述,无需改代码就能切换工作流。

架构示意(图 1):Configuration → Agent Environments(Data Loader → Multi-Agents → Continue 判定 → Sink) ↔ Cluster Management(Llama / vLLM / Apptainer Container / Ray / SLURM) ↔ Monitoring(Grafana,自定义队列长度、pending 异步任务等指标)。

P2P vs 集中式对比(图 2):集中式 orchestrator 在单进程里跑所有 agent 工作流,LLM/Container 服务通过它中转;P2P 模式中 Driver 仅创建 orchestrator 投递给 Agent1,Agent 间互发,LLM/Container 通过 agent 直接调用,Sink 在另一节点收尾。

## 4. 实现细节

**核心算法 (Algorithm 1)**:

- `AgentActor` 是 Ray remote class,内含 `_event_loop`:从 `self.queue` 取 orchestrator → 调用 `process()` → 更新对话历史与下一步 agent 索引 → 从下一个 role 的 actor 列表里随机选一个 send 出去(`random.choice` 实现负载均衡)。
- `SequentialOrchestrator` 维护 `history` 与 `index`,`current_agent()` 返回 `_sink` 或 `order[index]`。
- `create_team(cfg)` 按配置实例化每个 role 对应数量的 Ray actor。
- 主流程对 dataset 每个 item 创建 orchestrator,投递给首个 agent;最大并发由 `max_concurrency` 与 semaphore 控制,投递时 -1,sink 完成时 +1,依赖 Ray RPC 避免 race。

**分布式服务层关键工程点**:

- **gRPC 替代 HTTP** 调用 LLM 推理服务,降低 per-request 开销。
- **本地缓存活跃 model replica URL**,绕开 Ray head node 转发,避免 head node 网络瓶颈。
- **Container 池 + ID registry**:Apptainer 容器是有状态的,多次调用需要路由到同一容器实例,而非随机选择,所以维护 container ID → Ray actor 映射。

**容错(4.5)**:利用 SLURM 低 QoS 队列、AWS spot instance 等机会性算力。LLM/容器调用失败时刷新 live replica 列表后重路由;**agent actor 不放在机会性节点上**——节点标签区分 permanent vs opportunistic,agent 只调度到 permanent 节点,避免恢复 orchestrator 队列的复杂性。这是「设计上躲开」而非「真正解决」agent 抢占恢复问题。

**消息卸载(4.6)**:对话历史中超过阈值(实验中为 512 字节)的内容存入 Ray distributed object store,history 中只保留 object ID,按需读取;orchestrator 完成后统一删除。对象不可变,适合广播读取场景。

**支持的并行(4.3)**:数据并行(分区独立处理)、任务并行(asyncio,单 driver 处理万级并发)、agent 并行(每个 role 多 actor 实例)。

**开源栈**:SLURM + Ray + vLLM + SGLang + Apptainer + Hydra + Grafana,代码仓库在 `facebookresearch/matrix`。

## 5. 实验结果

三个 case study,32 A100 节点 / 13 H100 节点规模:

### 5.1 Collaborative Reasoner (Coral)

teacher / student / answer-extractor / answer-matcher 四 agent + 多轮 agreement loop。基线为 Coral 官方实现(单 orchestrator + asyncio)。31 节点 248 GPU 上,以 MMLU-Pro 为种子任务跑 Llama-3.1-8B:

| Metric | Coral Baseline | P2P-Agent |
|---|---|---|
| Runtime | 9:03:22 | 4:17:05 |
| Concurrent tasks | 5,000 | 12,400 |
| Total trajectories | 300k | 1M |
| Agreement correctness | 0.4732 | 0.4778 |
| Tokens generated | 6.17 亿 | 20.0 亿 |
| Tokens / sec | 18,917 | 129,833 (**6.8×**) |

扩展性曲线(图 4):随 max concurrency 从 400 → 10000,P2P 接近线性;Coral 基线在 6000 处饱和,10000 时反而下降。

### 5.2 NaturalReasoning(数据策展)

Filter (3B 分类器) → Score (70B) → Question (70B) → Sink。25M DCLM 网页文档,32 节点,3B 模型 32 副本,70B 模型 56 副本,max concurrency 14k。过滤通过率 5.45%,共生成约 100 万条高质量推理 QA。

**三种并行的消融**(500k 子集,Table 3,归一化吞吐):

| 配置 (data, task, agent) | 吞吐 | 解读 |
|---|---|---|
| (1, 14000, 1) | 1.00 | 实测仅 ~700 并发,输入管道瓶颈 |
| (20, 700, 1) | 1.61 | 提升数据并行,达到 14k 实际并发 |
| (240, 1, 1) | 0.38 | 仅靠数据分区,无任务并行 → 极差 |
| (240, 50, 1) | 1.43 | 数据 + 任务 → 接近最优 |
| (1, 14000, 2) | 1.03 | 增加 agent 并行收益微弱 |
| (1, 14000, 10) | 0.91 | 进一步增加 agent 反而下降 |

**Vs Ray Data 行级 vs 批级调度对比(Table 4,25M doc,均 14k 并发,10+ 小时)**:

| Metric | Ray Data | P2P-Agent |
|---|---|---|
| Runtime | 12:57:28 | 17:57:55 |
| Webdoc processed | 9.3M | 25M |
| Tokens / sec | 2,778 | 5,853 (**2.1×**) |

### 5.3 Tau2-bench(工具使用 + 用户模拟)

user-simulator / assistant / tool-executor / reward-calculator 四 agent + STOP 与 tool_call 分支(图 6)。13 H100 节点,1.5k 容器,gpt-oss-120b 56 副本:

| Metric | Tau2 Baseline | P2P-Agent |
|---|---|---|
| Runtime | 1:13:41 | 1:15:21 |
| Concurrent tasks | 500 | 1,500 |
| Total trajectories | 1,519 | 22,800 |
| Average reward | 0.5918 | 0.5921 |
| Tokens / sec | 2,654 | 41,003 (**15.4×**) |

扩展性(图 7):基线 Tau2-agent 在 500 线程后吞吐崩塌(单节点 Python 线程瓶颈);P2P 持续增长直到 1500。

**Message offloading 效果(图 9)**:Tau2-bench 对话内容分布(图 8)中约 12% 超过 512 字节;开启 offloading 后峰值集群网络从 ~1 GB/s 降到 ~760 MB/s,减少约 20%。

## 6. 批判性分析

- **三个 baseline 的可比性都不严格**。
  - Coral baseline 使用单 orchestrator,本身就是「集中式 vs P2P」的极端反面教材;Coral 团队若也允许多个 orchestrator 实例(如多进程),差距会大幅缩小。论文没做这种对照。
  - Tau2 baseline「all tools and environment logic directly in Python threads on a single node」——本质是「单机 vs 集群」对比,15.4× 的数字大部分来自硬件规模差,而非 P2P 设计本身。一个公允的基线应是 Tau2 + 多进程 + 分布式容器服务,但论文没构造。
  - Ray Data 对照里,P2P 用的是 Setting 2(20, 700, 1),Ray Data 用 Setting 4(240, 50, 1),并行配置不一致,且作者承认「700 batch size 对 Ray Data 会出现峰谷,改成 50 才平滑」——意味着 Ray Data 没在「公平的最优配置」下被测试。
- **吞吐对齐数据质量** 这一论点不够强。三个实验里只检查了 agreement correctness / average reward 这种粗粒度指标,均「持平」。但合成数据的下游价值是 fine-tune 后模型能力,这里没有 end-to-end 验证;且 P2P 跑的轨迹数是基线的 3–15 倍,如果存在质量分布差异,粗均值掩盖不了下游 SFT 效果差距。
- **「row-level scheduling」并非新颖概念**。论文自己也承认「类似 LLM serving 的 continuous batching」,这部分贡献更多是「把工业界已知 pattern 套到 agent workflow 上」的工程化整合,理论新意有限。
- **Setting 1 vs Setting 2 暴露设计缺陷**:同样目标 14k 并发,只靠任务并行(Setting 1)只能跑到 700 实际并发,要达到目标必须靠数据分区。这意味着 Matrix 的「数万并发」不是即开即得,需要用户对输入管道做容量规划。论文把它讲成「灵活性」,但本质是用户负担。
- **Agent parallelism 没有意义**(Setting 5: 1.03×, Setting 6: 0.91×)。论文以「LLM 推理在 Ray Serve 那边,agent 是 I/O bound」自圆其说,但这同时削弱了「P2P 多 agent 弹性扩缩」的论证——既然加 agent 实例没用,所谓的弹性扩展在论文展示的 workload 下是空头支票。
- **容错机制是回避问题**:agent actor 不放在机会性节点上,即「不让易抢占的事情发生」。一旦 agent actor 故障,分布式队列里的 orchestrator 怎么恢复、是否会丢任务、如何检测,论文未论证。
- **Message offloading 收益夸大**:20% 网络带宽缩减来自仅 12% 的消息超过 512 字节;在大多数对话较短的 workflow 中,offloading 的收益几乎为零,论文一句「适合未来多模态」属于愿景而非实证。

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 研究者有几个可借鉴的设计思路:

- **「状态 in message」是分布式 agentic 系统的关键解耦原语**。一旦把任务全部状态压进可序列化消息,agent 就可以做成无状态服务,水平扩展、热升级、跨节点容错都变简单。这个思路直接可迁移到 RLHF rollout 调度、自主 software engineering agent farm、auto-eval pipeline 等场景。
- **Row-level vs batch-level scheduling 的边界**值得继续研究。Continuous batching 已在 token 级证明价值,Matrix 把它推到 task 级。下一步可以看 agent 内部的工具调用、子任务也是否值得行级调度,以及如何与 LLM serving 内的批处理协同(端到端 throughput-latency 优化)。
- **gRPC + 本地副本缓存绕过 Ray head node** 这个工程经验是干货——大规模 Ray 集群里 head node 网络瓶颈是常见踩坑,值得在新建 RL/agent 系统时直接采纳。
- **Object store offloading 模式**对未来多模态 agent 系统有想象空间:图像、音频、视频内容显然不能塞进消息体,Ray object store(或类似 Plasma)可能是必要的数据平面。
- **可跟进的研究问题**:
  1. 真正分布式的 agent fault tolerance:消息队列持久化 + exactly-once 语义,而不是「不要在 spot 上跑 agent」。
  2. 异构 agent role 的资源调度:GPU agent / CPU agent / 高内存 agent 共存时,如何动态调整副本数,Matrix 现在是配置静态指定。
  3. 把 Matrix 与 RLHF rollout 系统(如 OpenRLHF、verl)对比,看「数据合成 + 偏好采样 + 训练」一体化时是否还能保持 P2P 简洁性。
  4. 对话历史的 prefix cache 共享:同一 orchestrator 内多 agent 反复调用 LLM,跨 agent prompt prefix 高度重叠;若 LLM 服务能感知 orchestrator ID,可大幅提升 KV cache 命中率。这是把 P2P 上下文与 LLM serving 调度协同的潜在切入点。
  5. 把 Matrix 的 pattern 反向应用到训练侧:DiLoCo 类的 P2P 训练协调能否复用「状态序列化 + 行级调度」?

---

## 8. 总结

Matrix 把多 agent 合成数据生成框架从「集中式 orchestrator + 批级调度」重构为「P2P 消息驱动 + 行级调度 + 分布式服务层」,在 Coral / NaturalReasoning / Tau2-bench 三个 workload 上获得 2–15× 吞吐提升,同时保持下游质量指标持平。核心贡献是一套清晰的工程范式——orchestrator 状态全序列化、agent 无状态化、重型计算下沉、Ray object store 卸载大消息——以及对应的 Hydra 配置化抽象。论文工程价值高于学术新意:行级调度、gRPC 绕 head node、object store 卸载等都是工业界已知 pattern 的整合,但整合得当;baseline 比较不够公平,15.4× 这种数字有相当部分来自硬件规模差而非架构本身;agent 容错、agent 并行收益都有待加强。适合作为大规模 LLM 训练数据合成的实用框架,以及 P2P agent 系统设计的参考实现。
