# CRAFT: Cost-Aware Expert Replica Allocation with Fine-Grained Layerwise Estimations

**作者**：Adrian Zhao, Zhenkun Cai, Zhenyu Song, Lingfan Yu, Haozheng Fan, Jun Wu, Yida Wang, Nandita Vijaykumar

## 1. 背景

Mixture-of-Experts (MoE) 通过用一个 router 加一组 expert 替换 dense Transformer 的 FFN 块,把「总参数量」与「每 token FLOPs」解耦,成为当下大模型的主流架构。DeepSeek-R1、Kimi-K2、Qwen3、Llama-4 Scout 等千亿到万亿参数模型都走这条路线。代价是巨大的 GPU 显存占用:所有 expert 的参数必须被持有,即便每个 token 只激活其中的 top-K(实际中 K 常取 8)。

部署 MoE 时,**Expert Parallelism (EP)** 把不同 expert 切到不同 GPU,通过两次 all-to-all(dispatch 与 combine)把 token 送到目标 GPU 再收回来。EP 的可扩展性很好,但 router 是按 token 分布动态路由的,自然语言的 Zipfian 分布会让少数 "hot expert" 承担远超平均的负载,结果就是 GPU 级的 token 负载不均衡:一部分 GPU 空转、一部分网络拥塞,整体效率下降。

现代推理框架(SGLang、vLLM、TensorRT-LLM、DeepSpeed)普遍采用两种 EP 负载均衡手段:
- **Expert placement**:根据离线负载分布,把 hot 和 cold expert 搭配到同一 GPU。
- **Expert replication**:对 hot expert 复制一份或多份,把流量摊到多个 GPU。

DeepSeek 开源的 **EPLB** 是目前被广泛采纳的方案,同时支持 placement 与 replication,但 replication 部分采用「每层每 GPU 均匀一份」的粗粒度策略。

---

## 2. 要解决的问题

EPLB 在追求 load balance 时把 replica 当成了「无成本」资源,实际上:

1. **Replica 吃显存**:一个 replica 就是一份完整的 expert 权重。大 MoE 模型动辄 60 个 MoE 层、384 个 expert,即便是「每层每 GPU 一份」的最小 EPLB 配置,也会压缩 KV cache 空间。在 6 节点 Kimi-K2 部署里,EPLB 把 KV cache 缩小了 75%。
2. **Replica 边际收益急剧递减**:作者实测 balancedness 随 replica 数 sublinear 增长,超过某个阈值(文中约 16/GPU)后增益可忽略,但内存开销继续翻倍。
3. **不同层收益差距悬殊**:极度 skew 的层(如 Kimi-K2 第 51 层,hottest expert 负载是均值的 27 倍)从 replication 中获益巨大;已经比较均衡的层(如第 20 层,peak/mean ≈ 2.5)基本不需要 replication。统一复制策略在平衡层上浪费显存、在极度 skew 层上复制不足。

一句话概括:EPLB 的 replication 策略系统性地 over-replicate,导致 KV cache 收缩带来的并发损失超过了 load balance 带来的效率收益,在小集群或低 skew 数据集上甚至让 goodput 不如单纯 placement 基线。

---

## 3. 洞察与设计

**关键洞察**:MoE 各层对 replication 的收益曲线差异极大,可以按「高 skew / 低 skew」粗分。高 skew 层 replication 收益显著,低 skew 层几乎无收益;且对任意层,balancedness 增益都呈 sublinear 趋势,存在一个明确的饱和点。因此 **replica 应该被当成稀缺资源,按层粒度按收益分配**,而不是均匀撒。

基于这一洞察,CRAFT 提出了三步工作流:

**Step 1 — 估计各层 replication benefit。** 在离线 profiling 阶段,对每层用一组预设的 replica 数 {1, 2, 4, ..., D}(D = GPU 数,base-2 几何级数)回放一次 token 负载分布,测量 balancedness 增益。得到一个 L × K 的 benefit 矩阵 T(L = MoE 层数,K = log₂ D + 1)。

**Step 2 — 确定全局 replication factor R。** R 表示「每 GPU 平均持有的 replica 数」,总 replica 数 r = R × D。R 可以手动设定(显存约束驱动),也可以让 CRAFT 按「每 replica 平均收益最大」的准则自动选。论文最终落点是 R = 8 在各配置下大体最优。

**Step 3 — 求解每层 replica 数。** 形式化为 **Multiple-Choice Knapsack Problem (MCKP)**:每层从 {0, 1, 2, 4, ..., D} 中选一个 replica 数,总和 ≤ r,最大化 ΣT。虽然 MCKP 是 NP-hard,但 L、D、K 都小(典型 60 × 8 × 4),一个 O(L · C · |T|) 的动态规划就能以伪多项式时间求解。

**Step 4 — Capacity-aware 专家分配。** 由于各层 replica 数不再整除 D,朴素分配会让各 GPU 持有的 expert 数目不均,进而产生显存碎片(KV cache 对齐到各 DP rank 最小值):
- **主目标**:新增一个 expert 总是优先放到「当前 expert 数最少」的 GPU。由于 r = R × D,每 GPU 最终 replica 总数严格相等,KV cache 对齐无压力。
- **次目标**(tie-breaking):层内 expert 按「跨 node 均匀分布」打散,进一步减小 node 级流量不均。

最后用标准的 greedy placement(按 expert 负载从大到小,优先放到当前负载最小的 GPU,遵守 capacity 约束)得到最终 placement plan。

图 7 里给出的典型示意:4 层 × 4 GPU × 8 expert,R = 2 时 CRAFT 给 Layer 3(最 skew)分 4 replica,Layer 1、2(中等 skew)各分 2,Layer 4(已均衡)0 replica;相比 uniform replication 的 r=16,只用了一半 replica 就达到近似完美的 load balance。

## 4. 实现细节

CRAFT 作为 EPLB 的直接替代品集成进 SGLang v0.4.8。三段核心算法以附录伪代码形式给出:

- **Algorithm 1 Per-Layer Replication Benefit Estimation**:对每个待评估 replica 数 r,调用 greedy PLACEMENT 得到 placement plan,然后逐 batch 回放离线负载 W,按「同一 expert 的多个 replica 平分其 token 负载」的规则汇总到各 GPU,计算 avg(G)/max(G) 作为 balancedness。benefit 定义为相对 placement-only 的增量。
- **Algorithm 2 Replica Allocation Solver**:二维 DP,状态 dp[ℓ][c] 表示前 ℓ 层共用 c 个 capacity slot 时的最大总 benefit,转移枚举当前层选 0 或 r ∈ {1, 2, 4, ...}。choice 矩阵记录最优决策用于回溯。
- **Algorithm 3 Balanced Intra-Layer Interleaved Replica Assignment**:先把 ⌊R[ℓ]/D⌋ 份 replica 均匀分给所有 GPU,再用 INTERLEAVESELECT 把 R[ℓ] mod D 份余数交错分到 expert 最少的那些 GPU,并保证跨 node 均匀。

上线开销:一次初始化约 10s(回放所有层、所有 replica 数)。相对于框架冷启动的分钟级开销可忽略;支持周期性动态 rebalance 时,可以把这 10s 与正在运行的 batch 在 CPU 上 overlap。推理时 CRAFT **零额外 runtime overhead**,它只是改变了 expert 的静态 placement plan。

框架配置:DP + TP-attention(head-parallel)+ EP,dispatch/combine 用 PyTorch + NCCL P2P(支持 EFA),chunked prefill 最大 4096 token。

## 5. 实验结果

**硬件**:AWS p4de.24xlarge,每节点 8× A100-80GB,节点间 EFA + NVLink 内互联;6、8、12 节点三种配置。

**模型**:
- D — DeepSeek-R1-671B:58 MoE 层,256 expert,top-8
- K — Kimi-K2-1000B:60 MoE 层,384 expert,top-8

**数据集**:FinePDFs-德语(E)、FinePDFs-日语(J)、Lambada(L)、RedPajama-arXiv(A),4096 input + 256 output。两字母 + 节点数构成配置名,如 KE8 = Kimi-K2 + 德语 + 8 节点。

**基线**:BASE(仅 placement)、EPLB(每 GPU L 个 replica)、CRA8(CRAFT, R=8)。

| 指标 | CRA8 vs EPLB | CRA8 vs BASE |
|---|---|---|
| 端到端 goodput(DeepSeek-R1, 8 节点) | 1.15× 平均,最高 1.2× | — |
| 端到端 goodput(Kimi-K2, 8 节点) | 1.12× 平均,最高 1.17× | — |
| TTFT(固定请求率,低于饱和) | 与 EPLB 基本持平 | 降低 29%(最高 58%) |
| Goodput(高 skew 数据集 E、J) | — | 1.42× |
| Goodput(低 skew 数据集 L、A) | — | 1.14× |
| Goodput(6 节点 K×6) | CRA8 vs BASE 1.14×;EPLB 反而比 BASE 低 46% | — |
| Replica 用量 | 比 EPLB 少 7.25×–7.5× | — |
| 初始化额外开销 | ~10s | — |

**Replication Factor Sweep (Figure 9)**:R 从 1 到 32 扫描,goodput 先升后降,R = 8 是多数配置的最优点。R 过小时 balance 不足,R 过大时 KV cache 萎缩反噬吞吐。

**Scalability (Figure 8)**:集群从 6 → 8 → 12 节点时,CRA8 goodput 1.65× 与 1.6× 线性扩展,BASE 因为 skew 放大无法扩展,EPLB 因为 KV cache 进一步被压缩,在小集群尤其糟糕(6 节点 K× 上比 BASE 低 46%)。

**ITL**:CRAFT 与 EPLB 在 max throughput 下 decoding ITL 基本一致,因为 decode batch 小,MoE 块的瓶颈是 collective latency,attention 占比更高。

## 6. 批判性分析

**Profiling 分布与线上分布的假设过于乐观**。CRAFT 完全依赖离线 profiling 数据构建 benefit 矩阵。论文用与评估样本同域但不重叠的数据做 profiling,本质上假设线上推理流量与 profiling 流量分布一致。在真实服务中,用户请求的语种、话题、长度都会随时间漂移,原本"高 skew 第 51 层"可能在新分布下变成"中等 skew",导致 over/under allocation。作者在 Overhead 节顺带提了一句可以周期性 rebalance,但没有量化 rebalance 周期、漂移幅度对 goodput 的影响 —— 这是生产可用性的关键环节,几乎被一笔带过。

**Benefit 估计的粒度设计偏保守**。Step 1 只在 {1, 2, 4, ..., D} 这 log₂D+1 个点评估 benefit,假设 benefit 函数在层内单调凹且几何采样足够。对大集群(D = 64),Step 1 只采 7 个点,层内 benefit 曲线如果不平滑(作者在 Figure 6 已经展示了 Layer 11 在 1 个 replica 就饱和、Layer 51 要到 16 才饱和,跨度很大),MCKP 可能被迫在「给 1」和「给 2」之间二选一,失去细粒度调节能力。论文没有讨论更密集采样下的 Pareto 改进空间。

**实验覆盖面偏窄**。评估清一色 A100-80GB + EFA,没有 H100/H200、InfiniBand、不同 TP/PP 切法的对照。CRAFT 的核心卖点是"省下来的显存给 KV cache",但不同硬件配比(GPU FLOPs vs 显存 vs 网络)下这笔账会完全不同;在 H200-141GB 上显存更宽松,EPLB 的 over-replication 惩罚可能没这么重,CRAFT 的相对优势就会缩水。

**端到端收益的归因不够干净**。CRA8 相对 EPLB 的 1.15× goodput 包含了两个效应:(a) replica 减少 → KV cache 变大 → 更高并发;(b) per-layer 精细分配 → 比 EPLB 同等 replica 下 balancedness 更高。论文没有做一个"CRA8 capacity 但 uniform 分配"的消融,因此读者无法判断收益主要来自 (a) 还是 (b)。从 Figure 1 看 balancedness 曲线,CRAFT 在 R=64 处才收敛到 EPLB 同水平,暗示 (a) 可能占主导 —— 如果真是这样,CRAFT 的核心贡献其实是"让 replication 预算可控",benefit 估计只是锦上添花。

**与训练态 replication 工作的区分较模糊**。Related Work 提到 SwiftMoE 在训练期做 adaptive 非均匀 replication,作者指出训练方法不能直接搬到推理因为 replica 搬运无法 overlap。但 CRAFT 本身是静态策略,动态性只在周期性 rebalance 时体现,某种意义上是"离线版的 SwiftMoE",新颖性主要在推理系统的工程集成(MCKP + capacity-aware assignment),而非 insight。

**"Observation 2: 集群越大 replication 越有效"的解读有滑坡**。作者说大集群每 GPU expert 数少导致 placement 无法平滑负载,因此 replication 更有必要。但反过来也意味着大集群 KV cache 本身就被拆得更碎,EPLB 的显存开销在小集群更致命、在大集群反而能吸收掉。Figure 8 里 12 节点 EPLB 已经能跑到 BASE 之上,支持这个观点。换句话说,CRAFT 的价值在小集群最突出,在超大集群可能会和 EPLB 收敛 —— 这反而削弱了它"为 trillion-scale 部署而设计"的叙事。

## 7. AI Infra / MLSys 视角

这篇论文本身就是 MoE 推理系统方向的工作,与 AI Infra 高度相关。几个可借鉴与延伸的方向:

- **"配额制资源分配 + 收益估计"的方法学可复用**。把 MCKP 作为资源分配求解器,在给定预算下最大化某个可量化指标,这套范式在很多 AI 系统子问题里都适用:KV cache 跨层/跨 attention-head 压缩配额、量化精度跨层分配、speculative decoding 的 draft budget 分配、动态 batch 内不同请求的 beam 数/采样温度分配。CRAFT 本质上是"把 sublinear 收益 + 稀缺资源"的通用抽象落到了 MoE replication 上。

- **Benefit 估计的 online 化是 future work 的富矿**。当前 CRAFT 每次初始化回放一次 profiling 数据得到 benefit matrix,但线上负载漂移时需要重新估计。可以研究:(a) 基于实时 routing 统计的流式 benefit 估计器,用少量历史窗口近似;(b) 基于 bandit / RL 的 online replica adjustment,把 MCKP 求解与运行时 decoding 重叠;(c) 把 benefit 估计做成 expert 自身的一个元信息(如 "skew score"),随 model checkpoint 一起发布,避免每个部署单位重新跑。

- **CRAFT 与 Expert Offloading / CPU-GPU hybrid 的组合**。在 H100/H200 及更小规模部署中,热度分层已经被用于 offloading 决策(hot expert 留 GPU、cold 放 CPU)。CRAFT 的层级 skew 画像可以直接喂给 offloading 策略:低 skew 层的冷 expert 优先 offload,高 skew 层保留 GPU 并 replicate。这是一个把 "replication-friendly" 与 "offload-friendly" 联合优化的问题。

- **Training 时的 expert 分配 co-design**。CRAFT 接受 router 的 routing 分布为外生变量。反过来,如果在训练期引入 "replication-awareness" 的辅助 loss,鼓励 router 把 skew 集中在少数层、其他层保持均衡,CRAFT 在该模型上的 replica 预算就能进一步压缩。这是 router 与推理系统的 co-design 方向。

- **值得跟进的具体研究问题**:
  1. 在 prefill / decode 分离架构(P/D split)下,prefill 的 skew 与 decode 显著不同,CRAFT 当前是统一 plan。分阶段分别求解 plan 再在切换时动态加载,能否进一步提升 goodput?
  2. Multi-model / multi-tenant 部署,多个 MoE 模型共享 GPU 集群时,CRAFT 的 benefit 矩阵可以跨模型聚合吗?MCKP 是否能推广到多模型联合求解?
  3. 当前 benefit 是 balancedness(avg/max load),但真实目标是端到端 goodput。能否直接拟合一个 "balancedness → goodput" 的回归函数,让 MCKP 直接优化 goodput?

## 8. 总结

CRAFT 指出 EPLB 为代表的主流 MoE 推理系统 replication 策略存在显著的"均匀分配陷阱":各层对 replication 的收益差距悬殊,统一复制既浪费显存又压榨 KV cache 并发。作者把 replica 分配形式化为 MCKP,辅以 capacity-aware 的交错 placement,在 SGLang 上实现 1.14× 平均 goodput(最高 1.2×)与 7× 以上的 replica 节省。核心贡献是工程性而非理论性的 —— 首次细粒度量化了 MoE replication 的 sublinear benefit 曲线,并给出了一个干净、零 runtime overhead、可直接替换 EPLB 的生产级方案。主要局限在于依赖离线 profiling 分布假设、benefit 估计粒度较粗,以及收益来源(显存节省 vs 精细分配)缺乏干净的消融。对于正在跑 DeepSeek-R1、Kimi-K2 级别模型的团队,CRAFT 是非常直接的落地优化;对研究者,这套"收益估计 + 配额求解"的方法学在 AI Infra 的其他资源分配场景有较大迁移空间。
