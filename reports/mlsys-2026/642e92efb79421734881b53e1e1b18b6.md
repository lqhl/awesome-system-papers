## 1. 背景

大模型训练(LLM pre-training/post-training)已经演化到需要同时使用上万张 GPU、承载万亿级参数量。在各种并行技术中,Fully Sharded Data Parallel (FSDP,又名 DeepSpeed ZeRO) 是最基础也最常用的一种:它把模型参数、梯度和优化器状态在数据并行组内分片存放,显存摊平,而代码侵入性最小,与模型结构解耦。FSDP 通常是第一个上手的选择,之后再视情况叠加 TP/EP/PP 等形式。

与此同时,前沿模型训练正在出现越来越多「结构感知」(structure-aware) 的训练方法:

- **非 element-wise 优化器**:Shampoo、Muon 需要完整的二维权重矩阵来做 Newton–Schulz 预条件或 matrix-sign 运算,更新逻辑在矩阵层面而非元素层面;
- **Block-wise 量化**:DeepSeek-V3 的 FP8 训练、8-bit Adam 等,要求每个量化块(e.g. 32×32、128×128)完整落在单一设备上,否则需要跨设备交换 scaling factor。

这两类方法都要求 tensor 的 "块结构" 在分片过程中得到尊重。

---

## 2. 要解决的问题

现有 FSDP 系统同时面临「灵活性」与「性能」两大缺陷:

**灵活性**:
- DeepSpeed ZeRO / PyTorch FSDP1 采用 element-wise 分片:把一层的参数拼成一个大 buffer,再按字节均分,根本无视结构边界,non-element-wise 计算、redistribute、block-wise 量化统统不支持;
- PyTorch FSDP2 升级到 per-parameter 的 Shard(0) DTensor,但仍是 row-wise 等分,分片边界不能保证与量化块对齐;
- Megatron-FSDP 回到拼接式分片,但通过填充 pad 让 tensor 看起来是 row-wise DTensor,并未真正支持任意块粒度。

**性能**:
- FSDP2 的 per-parameter 分片在 AllGather 之后,各参数落在 output buffer 的**交错地址**(interleaved address),需要 per-param Copy-Out 才能拼成连续的完整张量做计算;ReduceScatter 之前再做一次反向 Copy-In。论文实测 GPT-OSS-120B 在 64×H800 下,这些 copy 占 iteration 时间最高到 14%(表 1:Shard(0) AllGather 43.71 ms + Copy-Out 5.22 ms;Shard(1) 甚至要 13.72 ms 的 Copy-Out);
- FSDP1/FSDP2 都不强制 NCCL buffer 地址对齐,在某些 case 下集合通信严重退化;
- Megatron-FSDP 为了把拼接张量伪装成 Shard(0) DTensor 而插入 padding,MoE 场景下 buffer 膨胀 33%;
- DeepSpeed 与 FSDP1 依赖 PyTorch 的 `record_stream` 做隐式释放,显存碎片化,peak 比 veScale-FSDP 高 20%;
- 在 10K+ GPU 规模下,上述所有瑕疵都被线性放大。

## 3. 洞察与设计

**关键洞察**:

1. **FSDP 需要的不是一种更好的 shard,而是一种能表达"原子不可切块"粒度的抽象**。DTensor 既有的 Shard(dim) 只能二选一:要么元素级要么整行级,都落在"结构对齐"之外。如果每个参数能声明"这个 tensor 的原子块是 32 行"或"原子块是 128×128 2D 块",FSDP 的分片就能在满足块约束的前提下自由决定"每个 device 放几个块",从而自然支持 block-wise 量化与 Shampoo/Muon 这类非 element-wise 优化器。

2. **Transformer 参数结构高度规整,为"通信 buffer 布局"的 NP-hard 问题提供了近优启发式**。尽管在 buffer 里给任意块布局找最优是 NP-hard 的(可归约为 Partition 问题),但实际模型中 linear 权重占主导、块粒度在层间高度一致,几种简单排序(默认顺序 / 按块大小排序 / 按 shape 排序) 就能得到最优或近最优解,DP 搜索完全可行。

3. **零拷贝是 FSDP 性能的头号杠杆**。FSDP2 的 Copy-In/Copy-Out 本质是"per-param tensor 的独立存储" 与"NCCL 一个连续 buffer"之间的不匹配。只要 buffer 本身就被设计成"多 tensor 共享的全局 buffer,每个 tensor 的数据指针直接指向 buffer 的某个切片",收发前后都不需要拷贝。

**设计方案**(三个核心组件,见 Figure 3):

### 3.1 RaggedShard:新的 DTensor placement

在 DTensor 已有的 Shard / Replicate / Partial 之外新增第四种 placement(Figure 4):

- 参数化两个独立维度:**sharding granularity**(原子不可切块的大小,可以是 element、row、或自定义的 2D block)与 **sharding distribution**(每个 device 放多少个这样的块);
- Row-wise RaggedShard = 每 device 行数可以不等;
- Block-wise RaggedShard = 2D 块粒度,完美对齐量化块边界,是最通用的形式,可以退化到之前所有 shard 形式;
- 与 TP (Shard(0)/Shard(1)) 与 EP 正交组合:当内层是 Shard(0) 时,引入 `StridedRaggedShard` 携带 reorder/stride 元数据;当内层是 Shard(dim>0) 时,ragged 粒度自动取用户定义粒度与该维 stride 的 LCM,保证不切穿;
- 直接复用 PyTorch Distributed Checkpoint 栈,checkpoint 能力 for free。

### 3.2 Structure-aware 规划算法

Figure 6 展示了 grouped RaggedShard 通信的三大低效来源(naïve 拼接情况下):块被切穿、tensor 内部被 pad、设备间 buffer 不等大。veScale-FSDP 的做法是「先 permute,再在 tensor 之间而非 tensor 内部 pad」:

- **形式化**:目标是 minimize 每 device 的 uniform buffer size S,受三个约束:tensor 内部连续、tensor 之间不重叠、块不跨 shard 边界(`(kS - ℓ_t) mod g_t = 0`);
- **复杂度**:证明 NP-hard(归约自 Partition);ILP 在大规模下耗时到分钟级,实际不可用;
- **启发式 DP**:定义 `dp(t, i; S)` = 放下 t 之前所有 tensor 加 t 的前 i 个块所需的最小 shard 数。利用 `dp(t, i; S)` 在 i 上的单调性,把 tensor 内部的 block 索引压缩为 O(m) 个段;再把 case (3) (tensor 完全覆盖至少一个 shard 的情况) 的可行 S 限制在候选块大小的 LCM 的倍数上二分搜索;排序+前缀剪枝给 2-approximation;
- **总复杂度**:O(|T|² · m · log(E) · log(|T|m));
- **实测 runtime**:< 0.3s,一次性开销可忽略。

### 3.3 Distributed Buffer (DBuffer)

Figure 7 展示的通信底层原语,把 RaggedShard 规划出的布局落地:

- 在 N 维设备 topology 上提供全局 buffer 语义,每维都有 placement;
- Group-level operator:把多 tensor 的 add/scale/zero/copy 融成一个 kernel,而不是 per-tensor kernel launch,减少通信前的 fragmented 计算;
- **Zero-copy access**:每个 tensor 的 `.data` 指针持久映射到 global buffer 内部某个切片,AllGather/ReduceScatter 前后都不需要拷贝;
- **In-place communication and computation**:直接在 buffer 上原地做 redistribute。

## 4. 实现细节

- **代码规模**:7.6K 行 Python,作为 FSDP2 的 drop-in 后端,用户 API 仍是 PyTorch 原生 `fully_shard`,几乎零迁移成本;
- **兼容性**:纯插件式模块,兼容多版本 PyTorch 与标准 distributed runtime,不依赖 ByteDance 内部基建;
- **8-bit Adam 接入**:通过 `orig_param_policy` 接口让用户 per-parameter 声明量化粒度,论文案例里 matrix 参数设成 32 行粒度,每 device 独立量化本地 shard,无任何通信;
- **Distributed Muon 接入**(Algorithm 2):grad → MomentumUpdate → `Redistribute(u, RaggedShard(r))` 把 2D matrix 全部聚到 root rank → 只在 root 上跑 Newton–Schulz → `Redistribute` 回原 placement。非 root rank 上 Newton–Schulz 是 no-op,用户写起来是干净的 SPMD;再叠加异步 redistribute 做通信计算 overlap,加上 `torch.compile` 后在 256 Hopper GPU 上 MFU 到 47.3%;
- **生产部署**:已上线 ByteDance Seed 绝大多数训练 workload。

## 5. 实验结果

**硬件**:NVIDIA H800 集群(§6.1、§6.4、§6.5),Hopper 集群(§6.2、§6.3);§6.1 覆盖 128/256 GPU 下的 ZeRO-3 FSDP 与 2-way/4-way HSDP。

**基线**:DeepSpeed ZeRO v0.17.6、PyTorch 2.7.1 FSDP1、FSDP2、Megatron-FSDP,一律 ZeRO-3 + BF16 混精。

### 5.1 端到端性能(1024 GPU,Figure 8)

| 模型 | 吞吐相对最佳基线 | 峰值显存节省 |
| --- | --- | --- |
| LLaMA-3-70B(dense) | +5%(vs DeepSpeed/FSDP1/FSDP2),略优于 Megatron-FSDP | 16–30% |
| GPT-OSS-120B(MoE) | +11~66% | 16–30%,FSDP2 在 256 GPU 直接 OOM |
| Internal-Model-160B(MoE) | +11~66% | 16–30% |

GPT-OSS 上 FSDP2 从 128 跑到 256 GPU 时,expert 数是 128 但 GPU 数是 256,DTensor 为了 even-split 把 AllGather buffer 翻倍 → OOM;换 Shard(1) 又会双倍 Copy-Out 开销(表 1)。

### 5.2 扩展性(Figure 9)

- **Weak scaling(800B MoE, 1K→8K GPU)**:近似线性;
- **Strong scaling(120M global batch)**:8K GPU 仍线性,16M batch 下 1K→8K 也有 3.4× 加速,超过该点后 FSDP 通信占 dominant,上 EP 再缓解;
- **Model scaling(1K GPU, 400B→2.4T 参数)**:1K GPU 能跑 2.4T 参数模型,MFU 随模型增大反而微涨。

### 5.3 结构感知训练(64 GPU,Figure 10)

- **8-bit Adam**:loss 曲线与 DDP 版本贴合(仅因 ReduceScatter vs AllReduce schedule 不同产生微小差异);
- **Muon**:veScale-FSDP 版本与 DDP 版本 loss 重合,比 AdamW 低约 0.01 loss(训练 ~80B token 后);
- 两者都是"几十行代码"落地,如果用 FSDP2 要么改模型要么手写 collective。

### 5.4 Planning 质量(Figure 11)

在 DeepSeek-V3-671B 与 GPT-OSS-120B 上跑不同粒度(1× / 16× / 128× row):

- 1× 与 16× 粒度:两模型均 <3% padding 开销;
- 128× 粒度:DeepSeek-V3 最高 ~7%,GPT-OSS 出现 18% 的尖峰(因为 GPT-OSS 把所有 expert 融到一个 tensor,失去了按 expert 局部 pad 的自由度);
- 尖峰根源:NCCL even-input 对齐 + RaggedShard 粒度要向两者的 LCM 对齐,FSDP group size 跨过 LCM 倍数时跳变;
- 实践建议:用 HSDP 控 FSDP group 大小、hidden size 选小合数因子而非大互质数;
- 算法本身 runtime < 0.3s。

### 5.5 组件拆解(32 GPU GPT-OSS + 8-bit Adam,表 2)

| 配置 | 归一化吞吐 |
| --- | --- |
| Combined | 100.0% |
| Disable DBuffer | 92.8% |
| Disable Planning | 65.4% |
| Disable RaggedShard | N/A(不改模型/优化器就根本跑不了) |

Planning 贡献最大 —— 关掉后量化块会跨 shard,系统被迫走 DTensor redistribute 补齐 → 通信爆炸。

## 6. 批判性分析

**1. "65.4%" vs "11~66% 更快"之间存在解释落差**。§6.5 表 2 的 ablation 是 "32 GPU + 8-bit Adam"这个专门展示 RaggedShard 价值的场景,disable Planning 之后 34.6% 的损失主要来自 "量化块跨 shard 后必须走 redistribute 补齐"。但端到端 §6.1 里 LLaMA-3-70B(非量化 baseline)的收益只有 5%,远小于 MoE 上的 66%。作者把"66%"当作主要卖点贴在 abstract 上,容易让读者误以为所有场景都有类似提升。实际上 veScale-FSDP 的杀手锏是「MoE + 结构感知训练」,而不是"更好的通用 FSDP"。

**2. "NP-hard + 启发式 DP" 的乐观感假设**。作者承认三种 tensor order 都近优,是因为 transformer 参数规整。但这个假设对以下场景不一定成立:(a) 非 transformer 架构 (e.g. Mamba、RWKV 里 state 相关 tensor 形状差异大);(b) 复杂的多 expert 异构 MoE;(c) 自定义 optimizer 增加了奇怪的辅助 tensor。论文只提了一句"for non-transformer architectures, alternative tensor orderings can be plugged in",没给证据说 DP 在这些场景下还能保持 < 0.3s 与近优解。

**3. Figure 11 的 18% padding 尖峰被淡化**。作者把它归因于"GPT-OSS 把 expert 融合成一个 tensor"的模型层决策,给出的建议是"用 HSDP 控 group 大小、选合数维度"。但这实际上是把问题推给了模型设计者 —— 而 HSDP 本身又会降低 FSDP 的并行效率,没给出"在给定 GPT-OSS 下选择 HSDP 相对 FSDP 的吞吐 trade-off"。

**4. 基线公平性存疑**。veScale-FSDP 在对比 Megatron-FSDP 时主要攻击其"buffer padding inflation",但 Megatron-FSDP 的设计初衷是优先 checkpoint 兼容性;§2.3 里提到 Megatron 为了 "保留 Shard(0) 语义与 DTensor checkpoint 兼容" 而填充 —— veScale-FSDP 通过自家的 StridedRaggedShard 解决了兼容性,但实现复杂度代价是什么、是否引入了新的工程负担(例如用户需要理解新概念),论文没讨论。

**5. "DBuffer 只占 7.2% 加速"的含义**。DBuffer 虽然被宣传成核心组件,但消融下只贡献 7.2%。真正吃到大部分收益的是 Planning;RaggedShard 甚至直接被标 N/A 规避了定量比较。这让"三层架构缺一不可"的叙事略显勉强。更诚实的提法是:"RaggedShard 是能力启用,Planning 是性能关键,DBuffer 是锦上添花"。

**6. 生产验证描述偏营销**。"已部署到 ByteDance Seed 大部分训练 workload" 没给具体 workload 类型分布、故障率、版本迁移代价等信息。作为系统论文,10K GPU 的真实可靠性数据(训练失败率、checkpoint 恢复时间)会比吞吐曲线更有价值。

**7. Lessons Learned 有自嗨嫌疑**。Lesson 1 "小规模可以预测大规模"对普通 FSDP 成立,但对 MoE + EP 叠加的复杂情况,AllToAll 主导时就不好外推,论文自己在 §6.2 的 strong scaling 里也承认 "very large scales 有 performance drop";Lesson 2 "站在 DTensor 肩上"是软文,Lesson 3 "解耦"更多是理念而非可验证的系统性洞察。

## 7. AI Infra / MLSys 视角

veScale-FSDP 对 AI 系统研究的启发非常直接,几条最可迁移的观察:

**(1) "结构感知" 将成为下一代训练框架的核心抽象**。量化粒度 + 矩阵优化器这两股潮流都要求"块结构"穿透整个分布式栈。谁能把"块"从一个 per-layer 的私有概念提升到系统级一等公民(像 veScale-FSDP 把它做进 DTensor placement),谁就能在 FP4/FP8 训练、sparse attention、state-space 模型等方向抢占抽象高地。**Future work**:把 RaggedShard 的思想扩展到 Activation Checkpointing、Gradient Accumulation、KV cache 的 paged 分布式视图里。

**(2) "Zero-copy buffer 原语" 是 FSDP 之外的通用性能武器**。DBuffer 的 "多 tensor 共享连续 buffer + per-tensor 持久指针映射" 思路能直接搬到:推理端 paged KV cache 的跨 GPU 通信、训练 checkpoint 的 flush、RL 训练中 actor/critic 参数同步 等场景。所有"group 多 tensor 做集合通信"的地方都值得检视一下是否还有 Copy-In/Out 可以消除。**Future work**:在 PyTorch Distributed RPC 里提供类似 DBuffer 的原语,让 LLM inference serving 也能零拷贝做模型 refresh。

**(3) "NP-hard 通信布局问题" 其实是个被忽视的优化方向**。大多数分布式训练框架直接按 bucketing 做 AllGather/ReduceScatter,没人认真 formulate "多 tensor 多 device buffer 布局" 的联合优化。veScale-FSDP 证明了 "NP-hard + 模型先验(linear 主导 / 粒度一致) → 多项式 DP" 是行得通的。**Future work**:把类似 formulation 推广到 EP AllToAll、Tensor Parallel AllReduce 的 buffer 规划,尤其是在 MoE 中 expert 激活分布不均时的 padding 问题上。

**(4) 对小团队最有价值的切入点**:与其重写 FSDP,不如在 RaggedShard 框架上做"结构感知优化器库"——实现 Muon、Shampoo、SOAP、8-bit/4-bit Adam 等一系列结构感知优化器的 FSDP 版本,作为 veScale 或 PyTorch 生态的插件。这个方向工程量小但学术价值高,因为 RaggedShard 在 PyTorch roadmap 上已经是 planned feature,意味着未来几个月内 PyTorch 原生 FSDP 就会有这个能力,优化器接入是个开放 niche。

**(5) 值得关注但未被解决**:cross-host RDMA 场景下 DBuffer 的 NUMA/PCIe 亲和性、FP8 训练时 scaling factor 在 ReduceScatter 后如何融回 RaggedShard 的 accumulator、以及"1T+ 参数模型 + 万卡 scale" 下 Planning 算法能否保持 <0.3s(论文只在更小规模做过 runtime 测量)。

---

## 8. 总结

veScale-FSDP 把 FSDP 的核心抽象从"按 dim 均等切分"升级为"按任意块粒度 + 任意 device 分布切分",用 RaggedShard(灵活性)、structure-aware 规划(NP-hard 的启发式解)、DBuffer(零拷贝通信)三件套把"灵活性不足"和"大规模性能退化"同时解决,在 MoE 模型上相对现有 FSDP 实现达到 11–66% 吞吐提升与 16–30% 显存节省,已在 ByteDance 10K+ GPU 生产线上验证。最适用的场景是 MoE / 量化训练 / 矩阵优化器;对纯 dense LLaMA-70B 类 workload 增益有限(~5%);对非 transformer 架构与异构 MoE 尚缺证据。RaggedShard 已被 PyTorch 列入 2026 H1 roadmap,意味着这条路线很可能成为下一代分布式训练的事实标准。
