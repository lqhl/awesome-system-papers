# MoEBlaze: Breaking the Memory Wall for Efficient MoE Training on Modern GPUs

**作者**：Jiyuan Zhang, Yining Liu, Siqi Yan, Lisen Deng, Jennifer Cao, Shuqi Yang, Min Ni, Bi Xue, Shen Li
**单位**：Meta Platforms Inc, Thinking Machines Lab
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[2b44928ae11fb9384c4cf38708677c48.pdf]]

## 1. 背景

过去几十年处理器吞吐的增长远快于内存带宽,形成了著名的"memory wall"。在大规模 LLM 训练中,这道墙的影响尤其显著:即使有充足的算力单元,端到端吞吐往往受制于参数和激活值的读写和交换速度。

Mixture-of-Experts (MoE) 架构通过稀疏激活让万亿参数模型的训练成本变得可承担,GShard、Switch Transformer、GLaM、Mixtral、DeepSeek-V3 等一系列工作证明了这种路线的价值。但 MoE 的稀疏性本身又是一把双刃剑:因为每个 token 只激活少数几个 expert,compute density 反而降低,且 token routing 过程需要把 activation 在不同 expert 的 buffer 之间重排,放大了内存与带宽的压力。

在 trillion-token scale 训练中,序列变长、batch 变大、routing 机制更复杂,token dispatch 和 expert FFN 中间激活所占的 memory footprint 急剧膨胀,直接限制了一次能跑的最大 batch size 和序列长度。MoE 工程栈的内存瓶颈已经从"参数放不下"演进到"激活放不下"。

---

## 2. 要解决的问题

论文聚焦 MoE 训练过程中的两个激活内存瓶颈:

1. **Token routing buffer**:现有 dropless routing 实现(MegaBlocks、DeepSpeed-MoE、TurboMoE 等)都会物化一个 `L × K × d` 大小的 per-expert routed-token 缓冲区。以 DeepSeek 配置为例(L ≈ 2M tokens, K=4, d=6144, bf16),仅此一个 buffer 就达 ~94 GB。

2. **FFN 中间激活**:现代 MoE 普遍采用 SwiGLU/SiLU 等更复杂的激活函数,其 forward 需要保存 `a = xW₁`、`b = xW₂`、`σ(a)`、`SiLU(a)`、`SiLU(a) ⊙ b` 等多个中间结果供 backward 使用。DeepSeek 配置下 FFN 中间激活的 footprint 达 ~98 GB/layer。

这两者共同让 MoE layer 的 activation memory 成为主要 bottleneck,直接压缩了可训练的 batch/sequence 规模。已有方案要么靠 token-dropping/padding(牺牲模型质量),要么在稀疏 kernel 上做文章(但没有根除中间 buffer),都没能同时做到零容量损失、高吞吐和低内存。

---

## 3. 洞察与设计

**关键洞察**:per-expert 物化 routed-token buffer 并不是必需的——只要维护轻量级的 token↔expert 映射索引,MLP 计算和聚合就可以直接"on-the-fly"从原始未置换的 activation tensor 里 gather/scatter,从而跳过所有的中间排列缓存。此外,SwiGLU 的多个 pointwise 中间结果都是 memory-bandwidth bound 的,与其写入 global memory 不如在 backward 里重算。

基于此,MoEBlaze 由两大模块组成:

### 3.1 索引驱动的 token dispatch 与训练算法(Section 3)

用四个紧凑的索引数据结构替代物化的 routed-token buffer:

- **expert_token_indices** (`L × k`):每个 expert 被路由到的 token id 列表,跨 expert 连接
- **expert_token_offsets** (`E + 1`):每个 expert 区间在 `expert_token_indices` 内的起止偏移,相当于 prefix sum
- **token_expert_indices** (`L × k`):每个 token 被路由到的 expert id 列表(按 token id 排序)
- **token_index_map** (`L × k`):每个 token 的 k 个 expert 输出在中间 buffer 中的位置,用于最终加权聚合

forward 过程只需保留**两层 MLP 之间的中间结果**(SwiGLU epilogue 之前)用于 backward,不再保留 routed-token activation。backward 时 expert summation 反向不再 materialize `L × k × d` 的 routed gradient,而是通过同一套索引 scatter/gather。

### 3.2 并行化的 dispatch 数据结构构建(Section 4)

朴素做法是把所有 `(expert_id, token_id)` pair flatten 后用 radix sort 全局排序,但 GPU 上多 pass 的全局内存访问和 multi-kernel pipeline 使其成为 CPU-side bottleneck。MoEBlaze 用三步 atomic-free 构建替代 sort:

1. **Build Dense Token-Expert Map**:分配 `L × E` 的 dense bitmap,每个 warp 处理若干 token 行,写入 `(i, e)` pair,因为每 token 的 top-k expert id 互不重复,保证 intra-warp 无冲突
2. **Compute Expert Lengths**:CTA 映射到 `dense_token_map` 的列(每个 expert 一个 CTA),warp-level reduction 统计非零条目,prefix sum 得到 offsets
3. **Route Indices to Gates**:两步策略生成 location map,tile-level scan(每 CTA 做 exclusive scan)+ 加上每 expert 的 global offset,得到目标位置后并行 scatter,全程 atomic-free

### 3.3 SwiGLU kernel 融合 + activation checkpoint(Section 5)

把 `xW₁`、`xW₂` 两个 GEMM 与 SwiGLU epilogue 融合进单个 kernel:输入 x 只加载一次,同时 stream 过 `W₁/W₂` 两条 GEMM 路径,在 register/shared memory 中计算 `SiLU(a)` 并立即和 `b` 相乘,仅把最终乘积写回 global memory。

进一步省下 `SiLU(a)` 的 forward 保存,在 backward 里重算——因为 SiLU 是 pointwise 操作,memory-bandwidth bound 的代价远高于它的算力开销,recompute 反而更快。

backward 时,对共享输入 x 的两条梯度路径做 in-place tiled reduction,避免两个单独的 activation buffer。

## 4. 实现细节

论文只给了 high-level 的算法伪码(Algorithm 1)和三步 dispatch 构建的描述,没有披露完整 kernel 源码或代码规模。从文中可推断的实现要点:

- 目标硬件为 NVIDIA H100,利用 warp-group matrix multiplication (WGMMA) 和 Tensor Memory Accelerator (TMA)
- 软件栈:PyTorch 2.0.1 + CUDA 12.1;kernel 语言部分感谢了 Triton 专家 Hongtao Yu(暗示 fused SwiGLU MoE kernel 可能用 Triton 实现)
- `token_expert_indices` 和 `expert_token_indices` 是同一套数据的正反向映射,便于 forward gather 和 backward scatter 复用
- fused forward 保存 `A`、`B`、`Y_swi` 作为 backward 状态;`SiLU(A)` 不保存,在 backward 通过 `S_recomp ← SiLU(A)` 重算
- backward 中 `∇W₁, ∇W₂` 通过 `FusedBwdW(X, ∇A, ∇B)` 融合计算;`∇X` 通过 `FusedBwdX(∇AW₁ᵀ, ∇BW₂ᵀ)` 融合聚合

论文未给出:分布式版本实现、与 Triton/CUTLASS 的具体粘合方式、dispatch 构建的端到端延迟 breakdown。

## 5. 实验结果

**硬件/软件**:单张 NVIDIA H100,PyTorch 2.0.1,CUDA 12.1。
**基线**:MegaBlocks(只与这一个 baseline 对比)。
**指标**:相对 MegaBlocks 的 speedup,和用 PyTorch saved tensor hooks 量化的 activation memory。
**配置**:7 种 MoE 组合(见 Table 1),覆盖 d ∈ {512, 1024, 2048}、E ∈ {4, 8, 16}、k ∈ {1, 2, 4}、batch ∈ {16, 32}、seq ∈ {512, 1024, 2048}。

### SiLU 激活

| 指标 | 最低 | 最高 | 代表配置 |
|---|---|---|---|
| Activation memory reduction | — | ~3.6× (conf4: 22000 → 6100 MB) | conf4 优势最大 |
| End-to-end speedup | 1.4× | 3.7× | conf4 为峰值 |

### SwiGLU 激活

| 指标 | 最低 | 最高 | 代表配置 |
|---|---|---|---|
| Activation memory reduction | ~2× | ~4× (conf3: 40000 → 10000 MB) | 全配置稳定 ≥ 2× |
| End-to-end speedup | 2× | 6.2× | conf1 为峰值 |

论文论点:SwiGLU 相比 SiLU 的收益更高、更稳定,因为 fused kernel 消除了更多 pointwise 中间量的 global memory 流量;dispatch 开销部分的收益则在小配置(conf1)上更显著。

## 6. 批判性分析

1. **baseline 单一且过时**:论文在 related work 中承认 TurboMoE (Aminabadi et al., 2025) 也做了 fused metadata-driven kernel,但评测里完全没有与之对比。MegaBlocks 已经是 2023 年的工作,在 H100 上未必代表 SOTA,单 baseline 难以支撑"over 4× speedup"的一般性论断。文中还出现了 `Megablocks ??` 的引用占位符(Section 6 开头),暴露出稿件未完成的痕迹。

2. **缺少模型质量证据**:通篇只有 performance/memory 数字,**没有任何 loss curve、eval accuracy 或 downstream task 指标**。作者反复强调"without sacrificing accuracy",但这是一个算法级声明——on-the-fly gather/scatter + SiLU recompute 在数值上虽然等价,但实际 float 精度与 MegaBlocks 的差异、大规模训练下的累积误差,完全没有实验验证。

3. **评测规模与 motivation 严重脱节**:Introduction/Background 用 DeepSeek 尺度(L ≈ 2M tokens, d=6144, h=24576)说明 94 GB + 98 GB 的瓶颈,但 Table 1 里最大配置 conf4 也只有 `d=2048, h=8192, L=32×1024=32K tokens`,比 motivation 小两个数量级。单 H100 上的 toy-scale 测试无法说明方法在真实 trillion-token 训练中能否兑现同样的收益。

4. **Figure 6 caption 错误**:Figure 6 说"using SiLU as the activation function",但它在 6.6 节(SwiGLU speedup)里,显然应为 SwiGLU。这种基础错误和 Section 6 开头的 `??` 占位符一起,让人怀疑实验部分的审稿严谨度。

5. **conf 之间的 speedup 变化没有给出解释性 breakdown**:speedup 从 1.4× 跳到 6.2× 跨度巨大,作者笼统归因于"更大 d 受益更多"或"SwiGLU 更受益",但没有拆解 dispatch-build/fused-GEMM/recompute 各自贡献,也没给出单独去掉 SwiGLU fusion、只留 dispatch 优化的 ablation。

6. **未来 dispatch 构建的 end-to-end 开销未量化**:三步 atomic-free 构建虽然 asymptotically 比 radix sort 省 pass,但 `L × E` dense bitmap 在 L 较大、E 较大时内存和扫描成本同样显著(conf4: L=32K × E=16 = 512K 项,尚可;真实 DeepSeek: L=2M × E=256 = 512M 项,光分配这个 bitmap 就是 GB 级),论文没有讨论扩展性拐点。

7. **"不伤精度"的避 padding/drop 路线对 load imbalance 的容忍**:on-the-fly gather 意味着每个 expert 处理的 token 数 `L_i` 仍然不均。论文只字未提 expert load skew 对 fused kernel warp occupancy 的影响;在极端 imbalance 下(热点 expert),fused kernel 的性能表现可能退化。

8. **单设备场景的局限已经被作者自己点明**:Conclusion 承认分布式版本只是 future work。但 MoE 训练的主要痛点恰恰在 all-to-all 通信与设备间 expert 放置,单卡 memory/speed 优化对真实生产训练的贡献是受限的。

## 7. AI Infra / MLSys 视角

MoEBlaze 是典型的"把物化的中间 buffer 换成 metadata + on-the-fly gather"思路,这条路线在其他 AI Infra 场景也有很强的复用价值:

- **可迁移的方法论**:
  - **FlashAttention 化思想向 routing 层延伸**:FlashAttention 把 attention 中间量(Q·Kᵀ / softmax)留在 SRAM,MoEBlaze 类比地把 routed-token activation 留在索引结构里。这启发了"跨 sparse op 的 buffer 消除":比如 block-sparse attention、top-k MoE routing、dynamic batching 中间态都可能用同样的 lightweight-index + fused-kernel 模式重构。
  - **SwiGLU fused + recompute 的做法**对推理端的 LLM prefill kernel 有直接参考价值:FlashDecoding、SGLang、vLLM 的 FFN kernel 里 SwiGLU intermediate 同样占大头,重算比保存更划算的 insight 通用。
  - **Atomic-free 的 three-stage dispatch build**是通用 GPU primitive,可用于任何 `many-to-one` 聚合场景,比如 graph neural network 的 edge-aggregation、sparse embedding lookup 的 gradient scatter。

- **值得跟进的 future work**:
  1. **分布式 MoEBlaze**:与 DeepEP/TorchDynamo/FSDP 的 all-to-all 路径结合,把 metadata-based dispatch 扩展到 cross-GPU routing,看能不能消除 per-rank staging buffer。
  2. **定量化 dispatch 构建成本**:在 L 上限达到 DeepSeek 级别(2M tokens)时,dense_token_map 本身的内存(L × E bits)开始不可忽略,需要 hierarchical sparse bitmap 或 tile-wise streaming。
  3. **与 FP8 / MXFP4 训练融合**:Hopper/Blackwell 上 FP8 GEMM 把算力 bound 转回到 memory bound,MoEBlaze 的 fused pipeline 在 FP8 下应有更大收益,但也需要验证 SiLU recompute 在 FP8 下的数值稳定性。
  4. **对 MoE inference** 的适配:prefill 阶段同样存在 token dispatch buffer 问题,将 MoEBlaze 思路移植到 DeepEP-style decoding 或 EP parallelism 推理栈,可能带来显著的峰值显存节省。
  5. **Expert load imbalance 的 robustness**:在热点 expert 场景下研究 fused kernel 的 warp scheduling,考虑与 Tutel-style flexible-parallelism 结合。

- **最有价值的切入点**:把 MoEBlaze 的 metadata-only routing 思想和 **DeepSeek/DeepEP 的 group-limited routing + all-to-all 优化**结合,在多节点 EP 场景做一个端到端评测——这个方向既填补了论文的最大空白(分布式),又能直接应用到 2025+ 的主流 MoE 训练栈。

---

## 8. 总结

MoEBlaze 用一套 `(expert_token_indices, token_expert_indices, token_index_map)` 为核心的 lightweight 索引结构替代传统 MoE 中的物化 routed-token buffer,配合 atomic-free 三步并行 dispatch 构建和 SwiGLU fused kernel + SiLU recompute,在单张 H100 上相对 MegaBlocks 拿到 1.4×–6.2× 训练加速和 2×–4× 激活内存节省。核心贡献在于把"大而重的中间 buffer"替换成"轻量 metadata + on-the-fly gather",思路可直接迁移到其他 sparse op 和 LLM inference 场景。主要局限是基线单一(仅 MegaBlocks,未对比 TurboMoE)、实验规模远小于 motivation 的 DeepSeek 场景、未提供模型质量与分布式评测,以及稿件中存在引用占位符与 figure caption 错误等小瑕疵。对 MoE 训练栈的工程师,最实用的 takeaway 是第三段——atomic-free 三步 dispatch build 和 SwiGLU epilogue 融合,即便脱离 MoEBlaze 整体框架也可单独落地。
