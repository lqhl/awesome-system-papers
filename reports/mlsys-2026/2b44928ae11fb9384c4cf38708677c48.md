# MoEBlaze: Breaking the Memory Wall for Efficient MoE Training on Modern GPUs

**作者**：Jiyuan Zhang, Yining Liu, Siqi Yan, Lisen Deng, Jennifer Cao, Shuqi Yang, Min Ni (Meta Platforms Inc), Bi Xue (Thinking Machines Lab), Shen Li (Meta Platforms Inc)
**会议**：MLSys 2026
**链接**：[arXiv:2601.05269](https://arxiv.org/abs/2601.05269)
**源文件**：[[2b44928ae11fb9384c4cf38708677c48.pdf]]

---

## 一、背景

Mixture-of-Experts (MoE) 架构通过稀疏激活实现了万亿参数模型的高效训练，成为大规模 LLM 的主流架构选择（如 DeepSeek-V3、Mixtral）。然而，处理器算力增长远超内存带宽增长的"memory wall"问题在 MoE 训练中尤为严重：MoE 的稀疏性降低了计算密度，同时 token routing 过程需要大量辅助 buffer 来重排和存储 token，导致 activation memory 成为训练规模扩展的核心瓶颈。以 DeepSeek 配置为例，单个 MoE 层的 routing buffer 就可消耗约 94GB 显存，中间 activation 还需额外约 98GB。

---

## 二、要解决的问题

1. **Token routing 的显存开销**：现有实现（无论 token-dropping 还是 dropless routing）都需要为每个 expert 分配独立的 buffer 来存储路由后的 token，显存占用与 L×K×d 成正比，在长序列、大 batch 场景下极为庞大。

2. **中间 activation 的显存放大**：SwiGLU 等现代激活函数需要在前向过程中 materialize 并保存多个中间张量（如 sigmoid、SiLU 输出等）供反向传播使用，进一步加剧显存压力。

3. **现有 dispatch 实现效率低**：基于排序的 token dispatch 方法需要多 pass radix sort，全局内存访问频繁，kernel launch 开销大，GPU 并行度受限。

---

## 三、洞察与设计

**关键洞察**：Token routing 并不需要真正 materialize 出完整的路由后 token buffer——只需维护轻量级的索引数据结构（expert-token 映射和 token-expert 映射），就可以在 expert 计算时通过 on-the-fly gather 直接从原始未重排的 activation tensor 中读取数据，从而完全消除中间 routing buffer。

基于这一洞察，MoEBlaze 的设计包含两个核心组件：

**1. Memory-Efficient Token Routing**：不创建路由后的 token buffer，而是生成四个轻量索引结构：
- `expert_token_indices`：每个 expert 被分配的 token ID 列表（大小 L×K）
- `expert_token_offsets`：每个 expert 的 token 起始偏移（大小 E+1）
- `token_expert_indices`：每个 token 被路由到的 expert ID（大小 L×K）
- `token_index_map`：每个 token 在 expert_token_indices 中的位置（大小 L×K）

Expert 计算时直接通过这些索引从原始 tensor on-the-fly gather，输出聚合也通过索引直接 in-place reduce。

**2. Activation Checkpoint + Kernel Co-design**：将 SwiGLU 的两个 first-layer projection (W1, W2) 和激活函数 epilogue 融合为单个 kernel，输入只读一次；前向不保存 SiLU 中间结果，反向时 recompute（因为 SiLU 是 elementwise 操作，计算代价低但存储代价高）。

---

## 四、实现细节

**高效 Dispatch 数据结构构建**：替代全局排序的三步并行方法：
1. **Build Dense Token-Expert Map**：构建 L×E 的 dense bitmap，每个 warp 处理不相交的 token 行，无写冲突。
2. **Compute Expert Lengths**：每个 CTA 负责一个 expert 列，warp-level reduction 统计 token 数，随后 prefix sum 得到 offsets。
3. **Route Indices to Gates**：两阶段无 atomic 构建 location map——CTA 内 tile-level scan 得到局部偏移，加上全局 expert offsets 得到最终位置。

**Fused SwiGLU Kernel**：
- 前向：单 kernel 完成 X→(W1, W2) 双 GEMM + SiLU 计算 + 乘法，只写最终输出到 global memory；保存 A、B、Y_swi 用于反向。
- 反向：recompute SiLU(A)（不从显存读取），融合两个分支的梯度计算，tiled reduction 聚合梯度，无临时 global buffer。

实验在 NVIDIA H100 GPU 上进行，利用了 warp-group matrix multiplication 和 Tensor Memory Accelerator 等硬件特性。

---

## 五、实验结果

实验基于单个 NVIDIA H100 GPU，PyTorch 2.0.1 + CUDA 12.1，baseline 为 Megablocks。

**SiLU 配置下的 Activation Memory（MB）**：

| 配置 | d | E | K | B | Seq | MoEBlaze | Megablocks | 节省比 |
|------|-----|----|----|----|----|----------|------------|--------|
| conf1 | 512 | 4 | 1 | 32 | 2048 | ~1500 | ~2500 | ~1.7× |
| conf4 | 2048 | 16 | 4 | 32 | 1024 | 6,100 | 22,000 | 3.6× |

**SwiGLU 配置下**：conf3 (d=1024, E=16, K=4) Megablocks 消耗 >40,000MB，MoEBlaze 约 10,000MB，约 4× 节省。

**训练速度**：
- SiLU：1.4×–3.7× speedup（conf4 最高 3.7×）
- SwiGLU：2×–6.2× speedup（更复杂的计算暴露更多融合优化机会）

## 六、批判性分析

1. **实验仅限单 GPU**：所有实验都在单个 H100 上进行，但实际 MoE 训练的核心挑战在于分布式 Expert Parallelism 场景下的跨节点通信。on-the-fly gather 在分布式设置下是否仍然高效（需要跨设备 gather），论文未给出任何证据，仅声称"core mechanisms are also applicable to distributed settings"作为 future work。

2. **Baseline 选择单一**：仅与 Megablocks 对比。TurboMoE (Aminabadi et al., 2025) 在 related work 中被提及且同样采用了 fused kernel 策略，但实验中完全缺席。考虑到 TurboMoE 也声称大幅优于 Megablocks，直接对比才能说明 MoEBlaze 的真实优势。

3. **无端到端训练验证**：所有实验只测量单个 MoE 层的前向+反向时间，没有完整模型的端到端训练实验（loss 曲线、收敛性、吞吐量），也没有在实际 LLM 训练任务上的验证。

4. **Dense Token Map 的显存开销被淡化**：构建 dispatch 数据结构的第一步需要分配 L×E 的 dense bitmap。当 L=2M、E=256 时，这个 dense map 本身就不小，论文未讨论其在大规模配置下的开销。

5. **Speedup 跨配置差异大**：SiLU 下 speedup 从 1.4× 到 3.7× 变化范围大，说明收益高度依赖于具体配置（d、E、K 的组合），但论文未深入分析哪些因素主导收益。

6. **缺少 ablation study**：三项优化（memory-efficient routing、fused kernel、activation checkpoint）的独立贡献未被分解量化，无法判断各组件的边际贡献。

---

## 七、AI Infra / MLSys 视角

1. **索引替代 buffer 的思路通用性强**：MoEBlaze 用轻量索引 + on-the-fly gather 替代 materialized buffer 的思路，可推广到其他存在 token 重排需求的场景（如 Expert Parallelism 的 all-to-all 通信、Sequence Parallelism 中的 token 重分布）。

2. **Activation checkpoint 与 kernel fusion 的协同设计**：论文展示了"哪些中间结果值得保存、哪些应该 recompute"这一决策应与 kernel 设计联合优化，而非简单套用通用 activation checkpointing。这对 AI Infra 中的自动化 recomputation 策略设计有启发。

3. **分布式扩展是最直接的 follow-up**：在 Expert Parallelism 下，token dispatch 涉及跨设备 all-to-all 通信。能否将 MoEBlaze 的索引方案与通信 overlap，减少 all-to-all 的 buffer 开销，是一个有价值的研究方向。

4. **与 DeepSeek 架构的适配**：论文多次以 DeepSeek 配置为例，但 DeepSeek-V3 采用了 auxiliary-loss-free load balancing 和 multi-head latent attention，这些特性与 MoEBlaze 的索引方案如何交互，值得探索。

---

## 八、总结

MoEBlaze 通过轻量索引数据结构替代 materialized routing buffer、以及 activation checkpoint 与 kernel fusion 的联合优化，在单 GPU 上实现了 MoE 训练显存最高 4× 节省和最高 6.2× 加速。其核心思想——用 on-the-fly gather 替代中间 buffer materialization——简洁有效。主要局限在于缺少分布式场景验证和完整模型端到端实验，实际大规模训练中的适用性仍需进一步验证。
