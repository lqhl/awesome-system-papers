# ProfInfer: An eBPF-Based Fine-Grained LLM Inference Profiler

**作者**：Bohua Zou, Debayan Roy, Dhimankumar Yogesh Airao, Weihao Xu, Binqi Sun, Yutao Liu, Haibo Chen
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[6ea9ab1baa0efb9e19094440c317e21b.pdf]]

---

## 1. 背景

LLM 正在从研究阶段走向大规模生产部署,其中**端侧(on-device)和边缘推理**成为一类重要场景:移动设备上的对话助手、写作工具、翻译、本地教育工具等,都倾向于在本地跑 LLM,以获得离线能力、低延迟、用户隐私和更低的网络依赖。Apple 的 On-Device Foundation Models 就是这一趋势的典型。

与传统 CNN 不同,LLM 推理有两个显著特点:(1) **自回归式**逐 token 生成,分为 compute-bound 的 prefill 阶段与 memory/bandwidth-bound 的 decode 阶段;(2) 模型参数规模相对于移动/边缘 SoC 的算力、内存、功耗和散热预算远远偏大,需要量化、KV cache、算子 offload、MoE 稀疏化、speculative decoding 等多种技巧。

推理引擎生态中,`llama.cpp` 凭借纯 C/C++ 实现、GGML 执行引擎、异构后端(CPU/GPU/NPU)支持,以及 Ollama、PowerInfer、mlc-llm 等衍生项目,成为端侧推理事实上的基石之一。

然而在观测性上,端侧 LLM 推理引擎普遍缺少 ONNX Runtime / TensorRT 那种成熟的 built-in profiler。现有工具要么需要重新编译、在源码里插桩,要么粒度太粗(只报 tokens/s、throughput),要么依赖专用硬件 profiler 引入不可忽略的 overhead。近年一些工作尝试用 **eBPF**(Linux 内核从 2014 年起支持、后拓展到 macOS/Windows)对 ML 负载做无侵入 tracing,但这些工作基本没把 eBPF 的低层信号与 LLM 推理的算子语义挂起来,也很少考虑移动/边缘场景的 overhead 约束。

---

## 2. 要解决的问题

作者把端侧 LLM 推理的可观测性空白拆成四个具体缺口:

1. **粒度不足**。现有 profiler 报的是粗粒度的 TPS、TTFT、TPOT,无法回答"这一次 forward pass 里哪个算子慢""KQ/KQV 为什么随 context 增长越来越慢""MoE 某个 expert 为什么这个 iteration 耗时突然飙高"这类问题。
2. **侵入性高**。llama.cpp 自带的 `ggml_graph_dump_dot` 要多做一次 forward pass,引入 ~13% 的额外开销;ONNX Runtime profiler 约 8%;GPU 硬件 profiler 则依赖专用硬件。对移动/边缘场景来说这些开销都不可接受。
3. **缺少 operator × hardware counter 的关联**。单看算子执行时间无法区分是 memory-bound 还是 compute-bound,必须把 PMC(cycles、cache refill、stalled cycles 等)与具体算子对齐。
4. **缺少对动态行为的观测**。MoE 专家激活、算子 offload、推理线程被外部任务抢占等动态行为无法在静态图或 aggregated 指标上体现,但这恰恰是端侧性能波动的主因。

## 3. 洞察与设计

**关键洞察**:llama.cpp / GGML 的运行时里,token 生成、graph 计算、operator 计算、后端选择等核心行为都**对应到稳定、语义清晰的 C/C++ 函数边界**(`llama_decode`、`ggml_backend_graph_compute_async`、`ggml_compute_forward` 等)。这些函数的入参又是结构良好的 C struct(`ggml_tensor` 携带类型、维度、source 指针等全部信息)。因此,无需改源码或重编译,只要用 eBPF uprobe 挂上这些函数并在处理器中解引用参数,就能从低层 eBPF 事件流重建出 LLM 推理的完整高层语义(token → graph → operator → 计算依赖 DAG)。再叠加 `perf_event` 挂 PMC 与 Linux 调度器 tracepoint,就能把"算子语义 + 硬件计数器 + 线程调度"这三个层面用 thread ID × timestamp 打通。

### 3.1 整体架构

ProfInfer 分为 **Tracer**(在线采集)和 **Analyzer**(离线分析):

![](../../markdowns/mlsys-2026/6ea9ab1baa0efb9e19094440c317e21b/images/0df3b4c8d7cfda5dab266c08345e5ac02d57dc7d090a088e8e7c0b167a765938.jpg)

- **Tracer**:用户态负责编译/加载 BPF 程序、挂 probe、轮询 ring/perf buffer、根据 QoS 动态开关探针;内核态的 probe handler 在每次触发时记录 timestamp、thread ID、CPU ID,必要时解引用函数参数,解析算子结构或读 PMC,并通过 buffer 提交到用户态。
- **Analyzer**:把原始 trace 处理成三种视图 —— **ProfDAG**(算子级 DAG + 性能指标)、**ProfTime**(timeline,兼容 Chrome Trace / Perfetto)、**ProfStat**(横截面统计:跨 token、跨算子类型、跨 expert)。

### 3.2 多粒度 eBPF Tracing

ProfInfer 按四个粒度挂 probe(CPU/OpenCL/Rockchip NPU 三种 backend):

| 粒度 | 被 probe 的函数 | 采集信息 |
|---|---|---|
| Token | `llama_decode` (uprobe + uretprobe) | TTFT / TPOT / batch size |
| Graph | `ggml_backend_graph_compute_async` | 每次 forward pass 各 graph 的时长、backend 类型 |
| Operator (CPU) | `ggml_compute_forward` | tensor 维度、类型、source 指针、PMC |
| Operator (OpenCL/NPU) | `ggml_cl_compute_forward` / `ggml_rk_compute_forward` | tensor 信息 |
| Kernel 调度 | `sched_switch`, `sched_wakeup` tracepoint | 推理线程的 runnable/running/idle 状态 |

所有 handler 都至少记录 timestamp、PID、CPU ID。

### 3.3 PMC 集成

针对 Cortex-A76,作者挑选了 `l3d_cache_refill`(64 B 单位,对应 DRAM 读)、`mem_access_wr`(16 B 单位,对应写)、`major-faults`(页错误)、`cycles`、`idle-backend-cycles`(backend 停顿周期)。用 `perf_event_open` 给每个推理线程开一个 fd,uprobe/uretprobe 对 `ggml_compute_forward` 进入和返回时各读一次 PMC,差值即算子级 counter 增量,再对所有推理线程求和就得到该算子的聚合 PMC。

### 3.4 MoE Expert Activation 追踪

MoE 模型每个 iteration 只激活 top-k 专家。作者对 `ggml_compute_forward_mul_mat_id` 挂 uprobe,在内核态通过二级指针解引用读出 k 个被激活 expert 的 ID,配合 PMC 就能把"激活序列 → 冷专家换入 → 磁盘 I/O / page fault → 算子耗时"这条链路完整可视化。

### 3.5 QoS 驱动的动态开关

Tracer 会监控解码速度,当跌破 QoS 目标(如 5 tokens/s)时关闭部分高开销 probe。这是"用 token 级 probe 的低开销数据反过来决定 operator 级 probe 是否启用"的自适应策略。

### 3.6 三类视图

- **ProfDAG**:从 raw trace 恢复计算 DAG(见 Algorithm 1),按 thread ID 分组、按 timestamp 排序,每两条相邻事件配成一次算子调用;通过源 tensor 指针地址反向匹配生产者节点建立依赖边,用 networkx 画图并用 ms 或 MB/s 等任意指标着色。
- **ProfTime**:把 trace 转成 Chrome Trace Event Format,用 Perfetto 打开,同时显示 token / graph / operator 三个 track,再叠加 thread 状态(running / runnable / idle)。
- **ProfStat**:三个切片 —— (a) 跨 token:prefill/decode 耗时随上下文长度的变化 (b) 算子类型 × 输入维度:例如 MatMul 的时间 vs 理论计算量 (c) 跨 expert:MoE 专家激活频率和时间开销。

## 4. 实现细节

- **代码与工具链**:两套实现并存,一套基于 BCC + Python bindings(跑在 Ubuntu 上,便于快速迭代);一套基于 libbpf + C(跑在 OpenHarmony 上,因为 OpenHarmony 默认无 Python)。两套用的是语义相同的 BPF API 集合(`bpf_ktime_get_ns`、`bpf_probe_read_user`、`attach_uprobe`、`open_perf_event` 等,见 Table 1)。
- **被 probe 的目标**:llama.cpp 源码跨 `libllama`(C++) + `libggml-base`(C) + CPU/OpenCL/NPU operator 库;作者对整个软件栈做过静态遍历才锁定最上述 5 个函数。
- **结构体解析**:uprobe handler 在 eBPF 程序里用 `bpf_probe_read_user` 按字段偏移解 `ggml_tensor`,拿到 name(如 `ffn_out-0`)、op type(如 `GGML_OP_MUL_MAT`)、tensor 指针地址、维度数组、source 指针数组。
- **ProfDAG 构建(Algorithm 1)**:以一个线程的有序事件序列为主线,相邻两条配对为一个算子调用;多线程间的端到端耗时取"最早 invoke — 最晚 return";PMC 在每个线程上算差值再累加。图结构靠 `src` 指针回溯:见过的地址连边,没见过的视为常量输入(权重)节点。
- **硬件适配**:支持 Orange Pi 5 Plus(RK3588 + OpenHarmony)、Orange Pi 5 Ultra(RK3588 + Ubuntu)、RUBIK Pi 3(QCS6490 + Ubuntu)三款设备;backend 覆盖 Cortex-A76 CPU、ARM Mali GPU(经 CLBlast)、Adreno GPU(OpenCL)、Rockchip NPU。

## 5. 实验结果

### 5.1 Overhead 对比

| 工具 | 相对 overhead |
|---|---|
| `llama.cpp` built-in `ggml_graph_dump_dot` | 13% |
| ONNX Runtime built-in profiler | ~8% |
| ProfInfer (BCC,全开 Str./PMC/P-buf.) | 4.0% |
| ProfInfer (BCC,最小配置) | 2.8% |
| ProfInfer (libbpf) | 1.7–2.2% |
| ProfInfer (仅 token/graph 级) | 0.1% |

probe handler 本身 CPU 占用 0.41%–0.70%,prefill 阶段完全无影响。libbpf 版本比 BCC 再降 ~1%,但部分特性不支持。

### 5.2 Profile 驱动的洞察

作者用 ProfInfer 跑了 LLaMA3.2-1B、Qwen2.5-1.5B、Gemma2-2B、Qwen1.5-MoE-A2.7B-Q4 等,给出了几条具体观察:

- **模型结构差异**:Qwen2.5 在 self-attention 里每三个 MUL_MAT 后多一个 ADD;Gemma2 多出 6 个算子(3 × SOFT_MAX + UNARY/RMS_NORM/MUL 各一);ProfDAG 还显示相同中间 tensor 的 MUL_MAT 不总是连续执行。
- **Intra-op 并行,无 inter-op 并行**:4 线程下 llama.cpp 把 MatMul 并行开在线程间,但不同算子间是纯串行;`MatMul 占 TTFT 和 TPOT 的 97% 以上`。
- **线程负载不均**:激活函数上一个线程占用 80% 时间另一个几乎空闲;MatMul 能均分 —— 暴露了 GGML 调度策略的改进空间。
- **KV cache 增长的具体瓶颈**:Figure 9 显示 450 token 的解码过程中,每 iteration 耗时从 ~118 ms 爬到 ~122 ms,**增量基本由 KQ 和 KQV 贡献**(分别从 0 爬到 2.22 ms 和 2.07 ms),其他算子稳定。
- **Memory-bound 上限在 2 线程**:Figure 11 显示增加到 2 线程 MatMul 显著加速,第 3、4 线程只有小幅收益;4 线程下 backend stalled cycle 占比超 80%,是明显的资源浪费。
- **BLIS 的作用**:把 BLIS 接到 4 线程 Cortex-A76 上,prefill 速度 2×,PMC 显示内存访问下降 75%。
- **CPU vs GPU 的维度拐点**:Adreno GPU 在中等 MatMul 上快于 CPU,但 LM Head(词表 MatMul,矩阵大得多)的 GPU 性能反而暴跌(图 12 中 GPU 比 CPU 慢 ~3×),暗示端侧应按 tensor 维度做**选择性 offload**。
- **MoE 瓶颈在磁盘 I/O**:Qwen1.5-MoE-A2.7B-Q4 仅 4-bit 量化后仍需 8.9 GB,Orange Pi 5 Ultra 内存装不下,必须 mmap。ProfInfer 显示算子耗时与"当前 iteration 4 个 expert 和它们上一次被激活的平均距离"呈正比;major page fault + 内存访问计数证实 MoE 瓶颈是 **disk I/O 而非 memory bandwidth**。

## 6. 批判性分析

- **"eBPF 非侵入"的边界被低估了**。文章多次强调"无需修改 llama.cpp 源码",但挂 uprobe 需要精确定位函数地址、理解 C struct 内存布局,实质上与 llama.cpp / GGML 的实现细节强耦合。一旦 GGML 重构函数名或调整 `ggml_tensor` layout,大量 offset 需要重新对齐。这比"重编译时打开 profiling flag"更脆弱,却在论文里被包装成优点。作者没讨论版本兼容性、也没给出 probe 自适应机制。
- **Overhead 基线不完全公平**。ONNX Runtime 的 8% 与 `ggml_graph_dump_dot` 的 13% 是在不同工具做不同事时测的。ONNX Runtime profiler 记录全算子 timing + memory;ProfInfer 在最小配置下(仅 token/graph 级)只有 0.1% overhead,但这时它也没采集 operator 级数据。真正公平的对比应是"采集同样粒度下两者的开销",作者没提供。
- **端侧并发与 MoE 章节的结论其实普适,不需要 ProfInfer**。"MoE 换入 cold expert 导致 page fault"、"LM Head 在 GPU 上慢"这些结论是经验系统工作者本来就预期的。ProfInfer 的价值是给出量化的因果证据,但读者容易把这些经验结论误读为"ProfInfer 独家发现",论文在 discussion 部分叙述时措辞有放大嫌疑。
- **单机 llama.cpp 之外的 generalizability 含糊**。作者声称框架"applicable to similar runtime architectures",但实际只演示了 llama.cpp + GGML。vLLM、MNN-LLM、TensorRT-LLM 的函数边界不同、线程模型不同,要把同一套 probe 思路迁移过去需要相当多重新工程。Future work 一句"extension to other backends remains future work"把这块含糊带过。
- **QoS-driven 探针开关有隐含风险**。当 decoding 速度跌破阈值时自动关闭 operator 级 probe,意味着**最需要性能诊断的那个时刻恰好失去最关键的数据**。论文没讨论这个内生矛盾,也没给 probe 切换本身引入的抖动评估。
- **PMC 选择局限于 A76**。Table 3 的 counter 名(`l3d_cache_refill`、`mem_access_wr`)是 ARMv8 A76 的事件,不是所有端侧 ARM 核都直接可用(如 Cortex-X 系列、Apple Firestorm)。如果要在苹果或高通自研核上迁移,PMC 配置需要大改,而作者没给出抽象层。
- **只测性能,没做多工具对照**。除 overhead 对比外,论文没有和 eInfer、eGPU、PyTorch Profiler 等最相关工作在同一 LLM workload 上做可观测性 feature 或 accuracy 对照。"Works better" 的断言更多来自功能清单,而非实测。
- **结论写法偏宣传**。Abstract 说"turning performance profiling into a practical tool for optimization, scheduling, and resource-aware deployment",但全文并没给出由 profiler 反哺到优化 / 调度的闭环案例。BLIS 加速 prefill 是已有技术,并非由 ProfInfer 诞生。

## 7. AI Infra / MLSys 视角

对 AI 基础设施研究者,这篇论文提供了几条值得吸收的 insight 和可延伸的方向:

**可借鉴的技术思路**

- **用 eBPF 做跨层语义桥接**。把 `ggml_tensor` 这样的结构体在内核态解引用重构出"算子粒度 + 硬件计数器 + 线程状态"的三维视图,这套做法可以直接复用到 vLLM(`SchedulerOutput`、`ModelRunner.execute_model`)、SGLang、MLX 等其他 LLM runtime。只要目标 runtime 的数据结构有稳定的 ABI 边界,这个 pattern 就成立。
- **QoS 触发式自适应 tracing**。用低粒度信号(token-level latency)反向驱动高粒度 probe 的启停,这一机制可以扩展到云端大规模 serving,例如在高 SLA 违规风险时动态开启算子级 profiling,把诊断窗口开在真正有问题的推理请求上。
- **PMC + 算子语义对齐诊断 memory/compute-bound**。对端侧 CPU 推理来说,"stalled backend cycles / total cycles > 80%"就是一个明确的"别再加线程了"的标志。如果迁移到 GPU 侧,可以用 Nsight Compute 的 roofline + algorithmic tag 做类似映射,用来指导 kernel fusion / launch overlap 策略。

**值得跟进的 future work(具体可操作)**

1. **端侧推理引擎的统一可观测接口**。ProfInfer 现在是 llama.cpp 专属,可以提炼一个"Runtime Probe Contract"(模型入口、图入口、算子入口、expert 入口四类探针 + 统一参数解析规范),让 MNN-LLM、mlc-llm、ExecuTorch 都 pluggable。这对学界研究 on-device inference 是一个缺失但明确需要的基础设施。
2. **MoE 冷 expert 的在线预取调度**。作者已经发现 MoE 的瓶颈是 disk I/O、且与 expert 激活距离正相关。一个自然的延伸是:基于 expert 激活历史做 **在线 prefetch**,甚至把 profile 反馈进 routing 层做 cost-aware gating(比如 top-k 决策中对"在内存里"的 expert 给一点 bias)。已有 PowerInfer、Fiddler 等工作可以参考。
3. **Profiler 反哺 graph partitioning**。论文 Section 7 自己提到了这点但没实现。结合 ProfDAG 得到的算子级时间 + memory bandwidth 指标,给 GGML 的 `ggml_backend_sched` 加一个 learned 或 cost-model-based 的 partition 策略,可能比手动 offload layer 数有明显提升。对学术小组是可重复的中等规模课题。
4. **跨请求干扰建模**。Figure 8 展示了外部高优先级任务对推理线程的延迟影响。在 cloud serving 中多 tenant 共享 GPU / CPU 也有类似问题。可以把 ProfInfer 的 sched_switch / sched_wakeup + operator trace 思路搬到 serving 端,构建"干扰感知"的请求调度器。
5. **端侧 LLM 的可预测性建模**。作者观察到 dense model 的 decode speed 在 MatMul 复杂度上线性,给了"给定超参即可预测 tps"的可能。这可以发展成一套端侧 LLM latency 预测器,用来做 SLO 约束下的自动模型选型 / 量化决策。

**切入点建议**

如果要基于这篇做延伸工作,**最有价值的切入点是把 ProfInfer 的 tracing 闭环进调度**:作者已经证明数据拿得到、overhead 足够低;真正开放的问题是 "已知 operator × PMC × thread 状态,怎样反馈到 runtime 决策"(包括 graph partitioning、expert prefetch、线程数自适应)。这个方向对小型实验室友好 —— 不需要大规模集群,只需一两台 Orange Pi 就能跑完整实验。

## 8. 总结

ProfInfer 提出了一个基于 eBPF、面向端侧 llama.cpp 的细粒度、无侵入 LLM 推理 profiler。核心贡献是把 eBPF 的低层事件流与 LLM 推理的高层语义(token / graph / operator / expert)打通,配合 PMC 和 Linux 调度器 tracepoint,给出 ProfDAG、ProfTime、ProfStat 三种视图,在 < 4%(BCC)/ < 2%(libbpf)的 overhead 下揭示了包括 KV cache 增长瓶颈、线程并行天花板、MoE 磁盘 I/O 瓶颈、CPU vs GPU 维度拐点在内的多个具体性能现象。适用场景是 Linux-based 移动/边缘设备上的 LLM 推理调优与系统研究。主要局限在于与 llama.cpp 实现强耦合、对其他推理引擎的可迁移性偏理论、QoS-driven 探针开关可能在关键时刻丢失诊断数据,且"用 profiler 指导优化"的闭环在本文中并未实际走通。
