# ProfInfer: An eBPF-based Fine-Grained LLM Inference Profiler

## 一、背景

大语言模型（LLM）正从云端扩展到移动和边缘设备，以实现离线推理、低延迟、用户隐私保护等目标。然而，移动设备在处理器算力、内存容量、缓存层次、散热和能耗等方面存在严格约束。llama.cpp 等推理引擎虽已广泛使用，但缺乏细粒度、非侵入式的性能剖析能力——开发者甚至无法判断某个工作负载是 memory-bound 还是 compute-bound。

通用 ML 推理引擎（如 ONNX Runtime、TensorRT）提供了内置 profiler，但 LLM 推理引擎（特别是面向边缘场景的）普遍缺少 operator 级别的可观测性。现有 profiler 要么需要重编译/运行时插桩，要么只提供粗粒度的 throughput、token rate 等指标，无法暴露动态算子图、线程调度、硬件计数器等关键维度。

---

## 二、要解决的问题

1. **缺乏细粒度可观测性**：LLM 推理引擎（如 llama.cpp）不暴露 operator 级别的执行时间、内存访问模式和线程行为，开发者无法定位性能瓶颈。
2. **现有 profiler 侵入性强**：llama.cpp 内置的 `ggml_graph_dump_dot` 仅输出架构信息且带来 13% 的开销；ONNX Runtime profiler 约 8% 开销；硬件级 profiler 依赖特定硬件支持且开销不可忽视。
3. **eBPF 与 LLM 语义脱节**：已有的 eBPF profiling 工作（如 eInfer、eGPU）未将低级硬件指标与高层 operator 语义对齐，也未适配移动/边缘环境。
4. **动态工作负载难以分析**：MoE 模型的 expert 激活、speculative decoding 等动态行为导致性能波动，缺乏工具进行针对性诊断。

---

## 三、洞察与设计

**关键洞察**：llama.cpp（及其底层 GGML 库）的软件栈中存在明确的分层函数调用接口——token 级（`llama_decode`）、graph 级（`ggml_backend_graph_compute_async`）、operator 级（`ggml_compute_forward` 等）——这些函数的入口和出口可以通过 eBPF uprobe/uretprobe 动态挂载探针，无需修改源码即可精确关联"模型语义 → 算子执行 → 硬件行为"三个层次的信息。

基于此洞察，ProfInfer 设计了三层探针体系：

- **Token 级**：挂载到 `llama_decode`，测量 TTFT（prefill）和 TPOT（decode），并根据 QoS 要求动态开关探针以控制开销。
- **Graph 级**：挂载到 `ggml_backend_graph_compute_async`，区分不同后端（CPU/GPU/NPU）的计算图及其执行时间。
- **Operator 级**：挂载到各后端的 `compute_forward` 函数，提取算子类型、tensor 维度、源 tensor 地址（用于重建 DAG），并可读取 PMC（Performance Monitoring Counter）获取 cache miss、内存访问、CPU stall cycle 等硬件指标。

此外还挂载 Linux scheduler 的 `sched_switch` 和 `sched_wakeup` tracepoint，追踪线程调度行为和干扰检测。

ProfInfer 提供三种分析视图：
- **ProfDAG**：重建计算图拓扑并叠加性能指标（执行时间、内存带宽等）。
- **ProfTime**：生成 Chrome Trace Event Format 的时间线，可在 Perfetto 中可视化 operator 并行度、后端调度、线程抢占。
- **ProfStat**：统计视图，分析 KV cache 增长对延迟的影响、MatMul 的 memory boundedness、MoE expert 激活模式等。

## 四、实现细节

- 基于 BCC（Python 绑定，用于 Ubuntu）和 libbpf（C 库，用于 OpenHarmony）两套 eBPF 框架实现。
- 探针通过 `bpf_probe_read_user` 解析 C struct 指针（如 `ggml_tensor`），提取算子名称、类型、tensor 维度和源 tensor 地址。
- MoE expert 激活追踪：挂载 `ggml_compute_forward_mul_mat_id`，通过二级指针解引用读取 top-k activated expert ID。
- PMC 集成：通过 `open_perf_event` 为每个线程打开文件描述符，在 uprobe/uretprobe handler 中调用 `perf_read` 读取 `l3d_cache_refill`、`mem_access_wr`、`cycles`、`idle-backend-cycles`、`major-faults` 等计数器。
- ProfDAG 重建算法（Algorithm 1）：按 thread ID 分组 → 按时间戳排序 → 遍历 operator 事件对（start/end）→ 通过源 tensor 地址匹配建立 DAG 边。
- 支持 ring buffer（低内存开销但可能丢事件）和 perf buffer（事件感知但开销更高）两种数据传输模式。
- 支持的后端：CPU、OpenCL（GPU）、Rockchip NPU。

测试设备：OrangePi 5 Plus（RK3588, OpenHarmony）、OrangePi 5 Ultra（RK3588, Ubuntu）、RUBIKPi 3（QCS6490, Ubuntu）。

## 五、实验结果

### 开销分析

| 配置 | 解码速度下降 | 探针 CPU 负载 |
|------|-------------|--------------|
| BCC 全功能（Str+PMC+P-buf） | 4.0% | 0.70% |
| BCC 无 PMC | 3.6% | 0.66% |
| BCC 最小配置 | 2.8% | 0.61% |
| libbpf 全功能 | 2.2% | 0.41% |
| libbpf 最小配置 | 1.7% | 0.41% |
| 仅 token+graph 级追踪 | 0.1% | - |

对比：llama.cpp 内置 dump_dot 开销 13%，ONNX Runtime profiler 约 8%。

### Profile-driven 发现

- **架构差异可视化**：ProfDAG 清晰展示 LLaMA 3.2-1B、Qwen 2.5-1.5B、Gemma 2-2B 的 self-attention 实现差异（Qwen 多一个 ADD，Gemma 多六个算子）。
- **MatMul 主导**：>97% 的 TTFT 和 TPOT 时间花在 MatMul 上。
- **线程负载不均衡**：activation function 中一个线程承担大部分计算，另一个空闲 80%；但 MatMul 负载基本均衡。
- **KV cache 增长影响**：随上下文长度增长，KQ 和 KQV 算子时间阶梯式增长，是解码延迟递增的主因。
- **Memory boundedness**：2 线程即可接近内存带宽瓶颈，4 线程导致 >80% 的 stalled backend cycles，属于资源浪费。
- **GPU vs CPU 选择性 offload**：GPU 仅在特定 tensor 维度范围内优于 CPU；LM Head 等大矩阵在 GPU 上反而更慢。
- **MoE expert 激活分析**：operator 执行时间与 expert 激活距离近似成正比，表明瓶颈在于 disk I/O（mmap 换页）而非内存带宽。

## 六、批判性分析

1. **实验平台代表性有限**：所有实验在三块 ARM 开发板（RK3588、QCS6490）上进行，均为相对小众的嵌入式平台。未在主流移动设备（手机/平板）或主流边缘 AI 芯片上验证，难以判断发现的普适性。

2. **仅支持 llama.cpp 一个推理引擎**：论文声称框架"applicable to similar runtime architectures"，但未在 MNN-LLM、mlc-llm 等其他移动推理引擎上做任何验证。需要手动分析源码定位 probe 点这一事实，使得迁移成本不可忽视。

3. **GPU/NPU 后端支持不完整**：OpenCL 后端需要依赖引擎内置的 `GGML_OPENCL_PROFILING` flag 配合，NPU 后端仅支持自研的 Rockchip 后端。这与"非侵入式"的核心主张部分矛盾。

4. **模型规模过小**：测试模型均为 1B-2.7B 参数量级，且均为 4-bit 量化。对于实际边缘部署场景中更大的模型（7B+）或不同量化方案，profiling 行为和开销可能显著不同。

5. **缺乏端到端用例验证**：论文展示了丰富的 profiling 可视化，但未给出一个完整的"通过 profiling 发现瓶颈 → 优化 → 性能提升"的闭环案例，使得工具的实际优化价值停留在定性层面。

6. **动态探针开关的 QoS 机制未充分评估**：论文提到根据解码速度动态关闭探针以保证 QoS，但未给出该机制的具体触发条件、响应延迟和对 profiling 完整性的影响。

---

## 七、AI Infra / MLSys 视角

1. **eBPF 作为 ML 系统可观测性工具的潜力**：ProfInfer 展示了 eBPF 在 ML 推理场景中的可行性——零修改源码、<4% 开销、operator 级粒度。这一思路可以迁移到服务端推理引擎（vLLM、TensorRT-LLM）中，用于生产环境的在线 profiling，替代需要重编译的侵入式 profiler。

2. **Operator-Hardware 语义对齐**：将 PMC 数据（cache miss、stall cycles）与具体 operator（KQ、KQV、FFN MatMul）精确关联的方法，对理解 LLM 推理的微架构行为很有价值。可以扩展到 GPU 上（结合 CUPTI 或 NSight），做 kernel-level 的 roofline 分析。

3. **MoE 推理的 I/O 瓶颈量化**：expert 激活距离与执行时间的正比关系，以及"瓶颈在 disk I/O 而非内存带宽"的结论，对 MoE offloading 策略（如 expert 预取、缓存替换策略）有直接指导意义。

4. **可跟进的研究方向**：
   - 基于 operator-level profiling 的自动 graph partitioning：利用 ProfInfer 的数据驱动异构后端的最优分图策略。
   - 将 eBPF profiling 扩展到 GPU kernel 级别（结合 eGPU 的工作），实现端到端的异构推理全栈 profiling。
   - 基于 profiling 数据的 adaptive batching / scheduling：在多租户边缘推理场景中，实时调整资源分配。

---

## 八、总结

ProfInfer 是一个基于 eBPF 的轻量级 LLM 推理 profiler，通过在 llama.cpp 的多层函数接口上动态挂载探针，实现了 token/graph/operator 三级粒度的非侵入式追踪，并集成硬件 PMC 数据。其核心价值在于将 eBPF 的系统级追踪能力与 LLM 推理语义对齐，在 <4% 开销下提供了丰富的可视化分析。主要局限在于仅验证了 llama.cpp 一个引擎、模型规模偏小、GPU/NPU 支持不完整，且缺乏优化闭环的端到端验证。
