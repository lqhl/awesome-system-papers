# Optimizing PyTorch Inference with LLM-based Multi-Agent Systems

**作者**：Kirill Nagaitsev, Luka Grbcic, Samuel Williams, Costin Iancu
**单位**：Northwestern University; Lawrence Berkeley National Laboratory
**会议**：MLSys 2026
**链接**：[MLSys 2026 Proceedings](https://proceedings.mlsys.org/paper_files/paper/2026)
**源文件**：[[54229abfcfa5649e7003b83dd4755294.pdf]]

---

## 1. 背景

GPU 已经成为现代 AI/ML 工作负载性能优化的核心战场。新一代硬件(H100、未来 B200)持续刷新 SM 数、tensor core 吞吐与显存带宽,而要把这些算力真正喂饱,通常需要手写 CUDA/Triton kernel,掌握 GPU 并行模型、内存层次、调度行为。这是一道极高的工程门槛。

主流的两条自动化路径各有局限:

- **模型级编译器**(TorchInductor、TensorRT、ONNX Runtime、XLA)走通用图优化和算子库选择,但跟不上新架构,常远逊于手写 kernel——FlashAttention 当年比 PyTorch 原生注意力快了 7.6×,正是手写实现的胜利。
- **DSL/库**(Triton、CUTLASS、ThunderKittens)简化了开发,但用 Triton 写到峰值仍需深度专家。

近一年涌现出一批 **LLM-based GPU kernel 生成系统**(KernelBench 论文、Sakana AI CUDA Engineer、CUDA-L1、METR KernelAgent、Kevin、Astra、AlphaEvolve、OpenEvolve 等),把 PyTorch → 优化 kernel 的任务转化为 LLM 引导的搜索。但这些工作大多只报告端到端性能,**多智能体系统内部的设计选择(prompt 策略、解空间维护、agent 角色分工)对效果到底有多大影响,几乎没有系统性消融**。这正是本文要补的空白。

---

## 2. 要解决的问题

LLM 多智能体 PyTorch/kernel 优化本质上是一个 **explore-exploit 搜索问题**:

- *Exploration*:维护广泛的合法解避免早熟收敛
- *Exploitation*:把算力集中到当前最优解上继续打磨

围绕这个 tradeoff,作者提出几个未被回答的核心问题:

1. **不同 agent 角色(brainstorm / code / error-fixing)各自的边际贡献是多少?** 错误修复 agent 真的必要吗?
2. **解空间维护策略**——岛屿数 (islands)、精英存档大小 (archive size)、长/短期记忆——如何与 explore/exploit 比例交互影响最终速度?
3. **prompt 是 mutation(用 1 个 seed)还是 crossover(融合多个 elite)更好?**
4. **优化步骤的"颗粒度"**(每次改动多少行代码、复杂度多高)与最终性能是否相关?
5. 给定固定预算(LLM 查询数 / 美元),怎样的配置在 cost-performance 上 Pareto 最优?

---

## 3. 洞察与设计

**关键洞察**:在 LLM 多智能体 kernel 优化中,**激进的、exploit-heavy 的搜索策略比传统进化算法的"广撒网"更高效——前提是必须配一个错误修复 agent 兜底**。原因是 LLM 单步生成的代码改动幅度本就远超传统进化算法中的"小变异",每一步都接近一次"大跳跃式"重写;只要 EFA 能修复其中可修复的错误,大跳跃带来的速度增益就会压倒探索的多样性收益。简单说:**让模型大胆改、然后兜底修**,胜过让模型小心翼翼地变异。

基于此洞察,作者构建了 **PIKE (PyTorch Inference Kernel Evolution)** 这一逻辑框架:

![](../../markdowns/mlsys-2026/54229abfcfa5649e7003b83dd4755294/images/9328e89c4665f719f8a2eab9fd8531e1850d8c1f3ddafdad13441dcb9ed3c629.jpg)

**逻辑流程五阶段**(图 1 上半部分):
1. **Library**:存储初始模型与历史合法解,可组织为 islands(岛屿式遗传算法)
2. **Seed Selection**:按 ε:(1−ε) 的 explore/exploit 比从 history 或 elite pool 选种子
3. **Prompt Construction**:由 **Code Optimization Agent (COA)** 接受问题、原始模型、种子,生成新优化方案;可选 mutation(1 个种子)或 crossover(多个种子);可加入 **Initial Brainstorming Agent (IBA)** 提供的优化思路列表
4. **Evaluation**:Docker 容器内编译 → 正确性测试(`torch.allclose`,atol/rtol = 0.01)→ 性能测时(Triton `do_bench`);失败时进入 **Error Fixing Agent (EFA)** 循环,最多 5 次
5. **Post-Processing**:合法解入库,继续下一轮直到耗尽预算

**两个具体实现**:

- **PIKE-B (Branching)**:100% exploit、纯 mutation。每轮选 top-k(k=4) 解,把每个解复制 n/k=2.5 份作为下一轮 seed,n=10 并行 COA 调用。无 islands、短期 library。

  ![](../../markdowns/mlsys-2026/54229abfcfa5649e7003b83dd4755294/images/ba2c1a0a0eb1d97c0fe462de0a79f20cc8e7eb3e5b34f0eba95edb57c0876560.jpg)

- **PIKE-O (OpenEvolve)**:基于开源 OpenEvolve 框架的实现,默认 3 islands、archive=12、parallel=10、explore=0.2/exploit=0.7、crossover-only。作者补丁加入 EFA(原 OpenEvolve 没有)。论文系统性消融把 PIKE-O 一步步改成与 PIKE-B 等价(`mut` → `npar` → `1isl` → `EO` → `SL`),验证哪些参数才是真正关键。

整套框架的精髓是把**所有这些"看似很重要的进化算法概念"(islands、crossover、长期 archive、parallel evaluation)逐一打开来看,**最后发现它们在这个特定任务上多数不重要——甚至有害(高并行带来的"早期低质量解被反复采样"反而是 exploration 的隐性偏置)。

---

## 4. 实现细节

- **LLM 选型**:主体用 Gemini 2.5 Pro(input/output \$1.25/\$10 per 1M tokens),EFA 可降级为 Gemini 2.5 Flash(\$0.30/\$2.50 per 1M tokens)做 cost-down 实验
- **Temperature**:0.8,鼓励同一 seed 在并行调用下产生多样化代码
- **预算**:每个任务固定 300 LLM 查询,对应 \$25–50 不等;与 METR 实验设置对齐
- **测时基础设施**:bare metal H100 80GB HBM3、Intel Xeon 8480+(40+ 线程)、Docker 隔离;每解需独占 GPU lock,Triton `do_bench` 至少 1 次 warmup(覆盖 autotuning)+ 多次定时执行取均值,定时区间内执行 `torch.cuda.synchronize`
- **输入数据集**:在 KernelBench 250 任务上做了大幅清理——直接采用 METR 提供的 Level 3-pike(30 任务,均长 85 LoC)与 Level 5(14 任务,均长 493 LoC)。Level 3-pike 又额外删除了 LSTM/GRU(因 PyTorch 原生实现 launch overhead 太大,导致 LLM 用 CUDA Graph 套出 ~1000× 假性 speedup)
- **比较分析指标**:除了端到端 speedup,还测每步的 EFA 修复尝试次数、SLOC、(seed, generated_code) 的 LoC diff、用 OpenAI text-embedding-3-large 计算的 cosine similarity——这些用来量化"步骤颗粒度"

## 5. 实验结果

### 5.1 端到端性能(Level 3-pike,H100)

主结果(以 PyTorch Eager 为基线的 geomean speedup):

![](../../markdowns/mlsys-2026/54229abfcfa5649e7003b83dd4755294/images/e2c199c088cc2735a9d3b4105922032449ba542a875d2d0ae244112457169946.jpg)

| 方法 | Speedup (300 query) | \$25/task budget |
|---|---|---|
| **PIKE-B (full)** | **2.88×** | 2.31× |
| PIKE-B (cheap EFA, Flash) | 2.59× | **2.51×** |
| PIKE-B (no EFA) | 1.98× | 1.79× |
| PIKE-B (no IBA) | 2.68× | 2.14× |
| PIKE-O (default) | 2.17× | 1.85× |
| PIKE-O (no EFA) | 2.15× | 1.83× |
| PIKE-O (mut,npar,1isl) | 2.75× | 2.14× |
| PIKE-O (mut,npar,1isl,EO,SL) | **2.81×** | 2.33× |
| METR (KernelAgent) | 1.40× | — |
| torch.compile (max-autotune) | 1.64× | — |
| TensorRT | 1.41× | — |

### 5.2 Level 5(SOTA 2024 模型,H100)

![](../../markdowns/mlsys-2026/54229abfcfa5649e7003b83dd4755294/images/df0b4792bb810de5293292c7e896a1183be666baec951f6a1e72e5c8df19ff6b.jpg)

PIKE-B 拿到 2.57×,PIKE-O (mut,npar,1isl,EO,SL) 2.47×,显著优于 METR (1.50×)、torch.compile (1.29×)、TensorRT (1.25×)。

### 5.3 关键消融与动力学

- **EFA 对 PIKE-B 至关重要**(2.88 vs no-EFA 1.98),对 PIKE-O 几乎不影响(2.17 vs 2.15)——因为 PIKE-B 步幅大、错误率高,而 PIKE-O 步幅小、生成代码本身就更易通过(96.7% vs 79.3%)
- **IBA(brainstorming)边际收益不大**:有 IBA 2.88、无 IBA 2.68
- **PIKE-O 渐进改造**:`default → mut → mut+npar → mut+npar+1isl → mut+npar+1isl+EO+SL` 速度从 2.17 → 2.15 → 1.99 → 2.75 → 2.81。**关键变量是减少 islands + 限定短期 library**,而不是 parallelism 或 explore/exploit 数值
- **步骤颗粒度数据**(Table 2):

| 指标 | PIKE-B | PIKE-O |
|---|---|---|
| 生成代码平均 SLOC | 244 | 169 |
| \$25 预算下完成步数 | 160 | 198 |
| 300 查询所需平均成本 | \$50.96 | \$39.59 |
| EFA 5 次内修复成功率 | 79.3% | 96.7% |
| 步间 cosine similarity | 0.91 | 0.87 |
| 最佳解后端分布(CUDA / Triton) | 6 / 23 | 19 / 11 |

PIKE-B 改得多、错得多、贵但效果更好;且更倾向产出 Triton(autotuning 友好);PIKE-O 改得少、稳健、更倾向 CUDA。

### 5.4 任务级亮点(Level 3-pike & Level 5)

部分任务取得超大幅 speedup(均经过正确性验证):

- **VisionAttention (28.67×, PIKE-B)**:FP16 + Triton flash attention + 自定义 input/output projection kernel
- **MinGPTCausAtt (14.59×, PIKE-O′)** / **Mamba2ReturnFinalState (15.01×, PIKE-O′)**:整个模型融合到单 monolithic CUDA/Triton kernel
- **DenseNet121TransitionLayer (~13×)**:发现 Conv2d(1×1) ↔ AvgPool2d(2×2) 可以交换顺序,先池化再卷积大幅减少计算量
- **Level 5 / DeepSeek3 MOE small batch (~10×)**:消除 expert for-loop,把 expert 权重打包做 batched matmul

普遍的"中奖配方":**FP16 精度降级 + 自定义 Triton flash attention + 大算子图融合 + autotuning**。

## 6. 批判性分析

**1. 比较口径偏向己方,需谨慎**:文中多次强调 PIKE 单跑 300 queries 就胜过 METR,但 METR 公开结果是"4 次 300-query run 的最佳值",**总预算其实是 PIKE 的 4 倍**;在固定总预算口径下结论可能改写。论文虽然提到这一点,却仍把 METR 1.40/1.50 作为单点对照写在每张柱状图右边,容易误导。

**2. LSTM/GRU "因为 baseline 太烂被剔除"是双刃剑**。论文承认 LSTM/GRU 被剔除是因为 PyTorch 原生实现 launch overhead 太大、LLM 用 CUDA Graph 拿到 1000× 假性收益。但这件事反过来质疑了**整个 baseline 选择的合理性**:其他保留任务(MLP、ShallowWideMLP、VanillaRNN 等小模型)同样可能存在 launch-bound 偏向,被报告的 28× / 15× 的极值有多少是 *真实算子优化* vs *launch overhead 套利*,文章没有量化。

**3. 数值正确性边界过松**。`atol=0.01, rtol=0.01` 是 KernelBench 沿用的标准,但允许 FP16 的存在意味着许多大幅 speedup 来自精度降级。在生产推理(尤其 LLM)场景这通常没问题,但在 ML 研究/精度敏感领域,把 FP16 算作 "正确" 然后报 28× speedup 是不公平的——torch.compile 和 TensorRT 的对照是 *默认 FP32*。**应该补一组让所有 baseline 也允许 FP16 的对照**。

**4. PIKE-O 的"消融剥离"实质是确认结论**。从 default PIKE-O(2.17)逐步剥离到 (mut,npar,1isl,EO,SL)(2.81)的过程,每一步都是把 PIKE-O 改得更像 PIKE-B,然后宣告"exploitation-heavy 更好"。这个论证逻辑是循环的:**作者从一开始就相信 exploit 更好,因此设计的剥离方向就是 exploit 化**。如果没有走相反方向(把 PIKE-B 加 islands、加 crossover、加更长 archive)的对照,无法排除"PIKE-B 优势来自其他未消融变量"的可能。

**5. cost 数据隐藏了 LLM 价格波动风险**。论文 \$25–50/task 的成本基于 Gemini 2.5 Pro 当时定价。300 query × 30 任务的 \$750 已不便宜,且每代模型价格涨跌剧烈;cost-performance 曲线高度依赖时间快照,**对决策者实用价值有限**。

**6. cosine similarity 作为代码"语义相似度"代理过于粗糙**。用 text-embedding-3-large 做代码向量化是 NLP 视角,无法刻画"用 Triton 重写 vs 用 CUDA 重写"这种**架构级**的差异。0.91 vs 0.87 之间的差距能否解释"步骤颗粒度",证据链很弱。

**7. EFA 的具体策略黑箱**。EFA 5 次尝试上限是关键超参,但论文没有报告"5 次中第 N 次成功的分布",也没消融上限值(2/3/10);EFA prompt 设计完全未提及。这对工程复现是大缺失。

**8. 长尾任务"全部 1.0× fallback"现象**。Level 5 中 DeepSeek3、RWKV、Llama2、HunyuanTrans 等 4/14 任务两个 PIKE 变体均 1.00×(意味着没有任何合法解优于 Eager),论文未深入分析失败模式;这表明该方法在**真正的大型 SOTA 模型上反而失灵**,而 \$50/task 的代价仍要支付。

## 7. AI Infra / MLSys 视角

这篇论文对 AI 系统研究者有几个值得跟进的观察:

**1. "exploit-heavy + EFA" 的搜索范式可能复用到其他系统级搜索任务**。PIKE 的洞察——"LLM 单步改动本就是大跳跃,所以传统进化算法的多样性维护反而是冗余"——可以直接迁移到:
- vLLM/SGLang 调度策略搜索
- TritonGen / TVM schedule 自动调优
- Distributed training 的并行策略搜索(类似 Alpa/Galvatron 的搜索空间)
传统这些工作往往用大量 islands + crossover,可能也存在过度 exploration 的问题,值得用 PIKE 的视角重新审视。

**2. EFA 是 LLM 代码 agent 的"准编译器"角色**。把错误修复独立成 agent 而不是塞回 COA 同一个 prompt,效果差异巨大(2.88 vs 1.98)。这一观察对**任何让 LLM 写代码再执行**的系统(SWE-agent、Devin-like 框架、自动 bug 修复)都成立。EFA 的设计——更便宜的模型 + 紧凑的错误反馈——本身值得作为研究子课题。

**3. 后端选择偏置(Triton vs CUDA)与搜索策略相关,这个观察非常有意思**。Exploit-heavy 倾向 Triton(autotuning 友好,LLM 不需要写很多硬件细节),explore-heavy 倾向 CUDA(更多冷门 kernel 套路被采样到)。这个发现可以指导未来工作:
- 如果想要 Triton 解,设计更 exploit-heavy 的 agent
- 如果想要 CUDA 创新,反而需要保留一定 exploration
- 是否可以**用搜索策略本身作为 backend selector 信号**?

**4. 成本是核心瓶颈,RL 微调路径的价值被反衬**。\$50/task × 30 = \$1500 跑一次 Level 3-pike,这个成本下 PIKE 只比开源工具 torch.compile 好 1.7×。同期工作 Kevin (Baronio et al. 2025) 用 multi-turn RL 训练专用模型,可能在 inference 阶段更便宜。**值得跟进的方向**:把 PIKE 这种 prompt-engineered agent 当作"教师",蒸馏出更便宜的 student 模型/policy。

**5. KernelBench 自身的 baseline 问题需要 MLSys 社区认真对待**。论文揭示的"LSTM/GRU baseline 太烂导致假性 1000× speedup"暴露出 KernelBench 当前作为 benchmark 的**严重瑕疵**——很多"AI 自动写 kernel 击败专家"的论文可能都建立在 inflated baseline 上。MLSys 社区需要一个新的 benchmark suite,以 *production-grade PyTorch 实现*(已经被 inductor / TRT compile 过的版本)作为 baseline,而不是 naive eager 版本。

**6. 可操作的延伸研究问题**:
- *跨任务记忆迁移*:300 query 在每个任务独立耗费,有没有可能把"FP16 + flash attention 替换"这种通用 motif 学习成 library,大幅降低后续任务的搜索成本?
- *混合后端搜索*:能否设计一个 meta-agent,先决定用 Triton 还是 CUDA,再调用对应的子 agent?
- *运行时 verifier*:除了 `torch.allclose`,加入数值稳定性、batch-size scaling、不同 GPU 上的可移植性等多维度验证,避免 overfit 单点 H100。

---

## 8. 总结

PIKE 是一个把 LLM 多智能体 PyTorch/kernel 优化系统**结构化**起来的逻辑框架,核心贡献不是"又一个 SOTA",而是 **首次系统性消融 multi-agent 设计选择**,并给出 actionable insight:**exploit-heavy 的 mutation-only 搜索 + 错误修复 agent** 是当前最有效的配方,优于复杂的岛屿式遗传算法和 crossover-heavy 策略。在 KernelBench Level 3-pike 上达到 2.88× geomean speedup(H100),显著超越 torch.compile(1.64×)、TensorRT(1.41×)与 METR(1.40×)。主要局限:成本仍达 \$25–50/task、对真正 SOTA 大模型(DeepSeek-V3 / Llama2)长尾失效、与对照方法的预算口径有偏向、剔除任务理由值得商榷。适用场景:**中等复杂度 PyTorch 模型的 H100 推理优化,且能接受 FP16 精度降级**。
