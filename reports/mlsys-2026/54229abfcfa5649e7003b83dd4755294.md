# Optimizing PyTorch Inference with LLM-Based Multi-Agent Systems

**作者**：Kirill Nagaitsev (Northwestern University), Luka Grbcic, Samuel Williams, Costin Iancu (Lawrence Berkeley National Laboratory)
**会议**：MLSys 2026
**链接**：[arXiv:2511.16940](https://arxiv.org/abs/2511.16940)
**源文件**：[[54229abfcfa5649e7003b83dd4755294.pdf]]

---

## 一、背景

AI/ML 推理工作负载的性能优化是当前最关键的系统挑战之一。GPU 硬件快速迭代，软件需要不断适配新硬件以充分利用性能。传统方法包括手写 CUDA kernel 和使用模型编译器（如 TorchInductor、TensorRT、XLA），但手写 kernel 需要深厚的 GPU 并行、内存层次和调度专业知识，而编译器需要持续更新且通常无法达到手写 kernel 的性能（如 FlashAttention 曾比 PyTorch 原生实现快 7.6×）。

近期，基于 LLM 的多智能体系统展示了自动化 kernel 优化的潜力，能够匹敌甚至超越传统编译器。KernelBench 作为首个开放基准，将任务定义为将 PyTorch 算子翻译为优化 kernel。然而，多智能体系统内部的动态机制——各 agent 的角色、提示策略、解决方案库设计——尚未被系统性研究。

---

## 二、要解决的问题

1. **缺乏多智能体 PyTorch 优化的统一比较框架**：现有工作（METR、AI CUDA Engineer、CUDA-L1 等）各自开发独立系统，但缺乏逻辑框架来系统性比较不同策略的效果。

2. **Explore-exploit 权衡未被研究**：LLM-based kernel 优化本质是搜索问题，探索（避免过早收敛）与利用（聚焦最优解）的权衡如何影响性能，尚无系统分析。

3. **关键系统组件的交互效应不明**：Island 数量、并行度、elite archive 大小、Error Fixing Agent (EFA) 的作用、mutation vs. crossover 等参数如何交互影响最终性能，缺乏实证研究。

4. **现有编译器性能天花板**：torch.compile 和 TensorRT 等自动化工具在复杂模型上仍远低于手写 kernel 性能。

---

## 三、洞察与设计

**关键洞察**：在 LLM-based kernel 优化的搜索过程中，exploit-heavy（利用为主）的策略配合 Error Fixing Agent，比 explore-heavy（探索为主）的策略表现显著更好。这是因为 exploit-heavy 策略会在每一步做更大、更激进的代码变换（更大的 LoC 变更），虽然更容易产生错误，但配合 EFA 修复后能达到更高的优化峰值。

基于此洞察，论文提出了 **PIKE（PyTorch Inference Kernel Evolution）** 逻辑框架，包含以下关键阶段：

1. **Library（解决方案库）**：存储初始 PyTorch 模型和 LLM 生成的有效解，支持 island 分段、短期/长期历史。
2. **Seed Selection（种子选择）**：通过 explore/exploit ratio ε:(1-ε) 从库中选择种子解。
3. **Prompt Construction（提示构造）**：支持 mutation（单种子）和 crossover（多种子），可选 brainstorming。
4. **Code Optimization Agent (COA)**：根据问题描述、原始模型和种子生成优化代码。
5. **Evaluation（评估）**：编译、验证正确性、测量性能。
6. **Error Fixing Agent (EFA)**：对编译/正确性失败的解进行迭代修复。
7. **Post-processing**：将有效解存回库，满足退出条件时返回最优解。

框架的两个具体实现：

- **PIKE-B（Branching Search）**：纯 exploit 策略，每轮选 top-k 解复制为下轮种子，mutation-only，短期记忆，无 island。
- **PIKE-O（基于 OpenEvolve）**：支持 island、crossover、长期记忆、并行评估，通过消融实验逐步调整为类 PIKE-B 的 exploit-heavy 配置。

---

## 四、实现细节

**PIKE-B 算法**：
- 参数：population size n=10, error-fix attempts m=5, top-k=4
- 流程：IBA 生成 n 个初始优化思路 → 并行评估 → EFA 修复错误 → 按性能指标排序 → 选 top-k 复制为 n/k 份种子 → 迭代
- 总 budget：300 LLM queries per task

**PIKE-O 实现**：
- 基于 OpenEvolve 框架修改，增加 EFA 循环
- 默认参数：population=25, archive size=12, islands=3, explore ratio=0.2, exploit ratio=0.7, parallel evaluations=10
- 消融变体：逐步去除 crossover (mut)、并行 (npar)、多 island (1isl)、提高 exploit ratio (EO)、缩小 library (SL)

**评估器**：
- Docker 容器化，独立进程运行每个解
- 使用 Triton 的 do_bench 计时工具，含 warmup
- 正确性检查：torch.allclose(atol=0.01, rtol=0.01)
- 40+ CPU 线程并行编译，H100 GPU (80GB HBM3, PCIe)

**LLM**：Gemini 2.5 Pro 为主，cheap EFA 变体用 Gemini 2.5 Flash。温度 0.8。

## 五、实验结果

**基准**：METR-refined KernelBench，包含 Level 3-pike（30 tasks，~85 LoC）和 Level 5（14 tasks，~493 LoC）。

### Level 3-pike 主要结果（300 queries budget, H100）

| 方法 | Geomean Speedup |
|------|----------------|
| PIKE-B | **2.88×** |
| PIKE-O (mut,npar,1isl,EO,SL) | 2.81× |
| PIKE-B (no IBA) | 2.68× |
| PIKE-B (cheap EFA) | 2.59× |
| PIKE-O (mut,npar,1isl) | 2.75× |
| PIKE-O (default) | 2.17× |
| PIKE-B (no EFA) | 1.98× |
| torch.compile | 1.64× |
| TensorRT | 1.41× |
| METR | 1.40× |

### Level 5 主要结果

| 方法 | Geomean Speedup |
|------|----------------|
| PIKE-B | **2.57×** |
| PIKE-O (mut,npar,1isl,EO,SL) | 2.47× |
| METR | 1.50× |
| torch.compile | 1.29× |
| TensorRT | 1.25× |

### 成本效率（Level 3-pike, $25/task budget）

| 方法 | Speedup |
|------|---------|
| PIKE-B (cheap EFA) | **2.51×** |
| PIKE-O (mut,npar,1isl,EO,SL) | 2.33× |
| PIKE-B | 2.31× |

### PIKE-B vs PIKE-O 动态对比

| 指标 | PIKE-B | PIKE-O |
|------|--------|--------|
| Mean SLOC of generated code | 244 | 169 |
| Mean steps completed ($25 budget) | 160 | 198 |
| Mean cost per task (300 queries) | $50.96 | $39.59 |
| Solutions working before EFA 5-attempt max | 79.3% | 96.7% |
| Mean cosine similarity between steps | 0.91 | 0.87 |
| Best solutions CUDA/Triton | 6/23 | 19/11 |

**关键优化模式**：精度降低 (FP16) + 自定义 flash attention kernel、全模型/子图融合为单一 CUDA/Triton kernel、操作重排序减少计算量、Triton autotuning。最高单任务加速达 28.67×（VisionAttention）。

## 六、批判性分析

1. **与 METR 的比较不完全公平**：PIKE 使用单一 SOTA 模型 Gemini 2.5 Pro，而 METR 的公开结果来自多个模型（o1, Claude 3.5 Sonnet, gpt-4o, o3-mini-high）的最佳组合。虽然 budget 都是 300 queries，但 METR 跑了 4+ 轮取最优，而论文仅跑单轮。这使得 PIKE 实际的 query-normalized 优势可能小于呈现的数字。但论文也承认了这一点。

2. **超参数搜索不充分**：论文明确承认受限于成本未能做完整超参数搜索。PIKE-B 和 PIKE-O 的参数可能并非最优，消融实验也是单向递进而非交叉验证。这削弱了"exploit-heavy 策略更优"这一结论的普遍性。

3. **基准规模有限**：Level 3-pike 仅 30 tasks，Level 5 仅 14 tasks，且经过了多轮筛选（去掉 LSTM/GRU、MLP 噪声等）。在如此小的 task 集上，个别 outlier（如 VisionAttention 28.67×、MinGPTCausAtt 10.83×）对 geomean 影响显著，结论的统计可靠性存疑。

4. **正确性检查宽松**：atol=0.01, rtol=0.01 的容差允许 FP16 精度降低通过，而精度降低恰恰是最大的加速来源之一。这意味着一部分"优化"实际上是牺牲了数值精度，但论文将其与真正的算法优化（如 kernel fusion）混在一起汇报，未区分精度-性能权衡。

5. **成本分析仅考虑 LLM 费用**：$30-50/task 的成本未包含 GPU 评估时间（40+ CPU 线程 + H100 数小时运行）的硬件成本。对于实际部署场景，这可能是更大的瓶颈。

6. **缺乏与人类工程师的直接对比**：论文声称消除手工 kernel 开发的需求，但未提供人类专家在同一 task 集上的表现和耗时数据。

7. **泛化性存疑**：所有实验仅在 H100 PCIe 上进行，未测试其他 GPU 架构（A100、AMD MI300X 等）。不同 GPU 上 exploit vs. explore 的最优配比可能不同。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **LLM 作为 kernel 工程师的可行性进一步验证**：在 KernelBench 的复杂任务上平均 2.88× 加速超越 torch.compile (1.64×) 和 TensorRT (1.41×)，表明 LLM-based 优化已经是推理系统工程的实用工具。

2. **Exploit-heavy + EFA 的组合模式**：这一发现对所有 LLM-based code optimization 系统（不限于 kernel）都有参考价值——与其广泛探索，不如聚焦已有最优解做激进变换，然后用专门的修复 agent 处理由此产生的错误。

3. **Triton vs. CUDA 的 backend 选择洞察**：exploit-heavy 策略倾向产出 Triton 解（23/29），explore-heavy 倾向 CUDA 解（19/30）。这暗示 Triton 的 autotuning 能力与迭代精炼更契合，而 CUDA 的灵活性更适合广泛搜索。

### 可迁移的技术

- **进化式 branching search 用于 serving 系统配置优化**：PIKE-B 的 top-k 复制 + mutation 范式可迁移到推理 serving 系统的配置搜索（batch size、tensor parallelism、quantization 方案组合）。
- **EFA 模式用于自动化 CI/CD kernel 回归修复**：当新 GPU driver 或框架版本导致 kernel 失败时，EFA 式的迭代修复流程可自动化修复。

### Future Work 方向

1. **多 GPU 架构泛化**：在 A100、H200、AMD MI300X 上验证 exploit/explore 权衡是否一致，以及能否用一次搜索生成多平台优化 kernel。
2. **与 profile-guided 优化结合**：当前 PIKE 只用 runtime 作为反馈信号，加入 GPU profiler（nsight compute）的 bottleneck 分析作为额外上下文可能提升搜索效率。
3. **精度-性能 Pareto 优化**：区分精度降低带来的加速和算法优化带来的加速，让用户选择可接受的精度损失范围。
4. **端到端模型服务集成**：将 PIKE 集成到 vLLM、SGLang 等 serving 框架中，作为离线 kernel 优化流水线的一部分。

---

## 八、总结

PIKE 提出了一个用于比较多智能体 PyTorch 优化系统的逻辑框架，并通过 PIKE-B（branching search）和 PIKE-O（OpenEvolve-based）两种实现进行系统性消融实验。核心发现是 exploit-heavy 策略配合 Error Fixing Agent 在 H100 上的 KernelBench 任务中取得最优的 2.88× 平均加速，显著超越 torch.compile (1.64×) 和 TensorRT (1.41×)。论文的主要贡献在于提供了理解和调优 LLM-based kernel 优化系统的分析框架，但结论受限于较小的基准规模、单一 GPU 平台和不完整的超参数搜索。
