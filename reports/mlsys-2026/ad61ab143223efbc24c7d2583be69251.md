# SAKURAONE: An Open Ethernet–Based AI HPC System and Its Observed Workload Dynamics in a Single-Tenant LLM Development Environment

**作者**：Fumikazu Konishi, Yuuki Tsubouchi, Hirofumi Tsuruta
**单位**：SAKURA Internet Research Center
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[ad61ab143223efbc24c7d2583be69251.pdf]]

---

## 1. 背景

随着 LLM 训练规模急剧上升,AI 计算基础设施从原本的 HPC 共享设施快速演进为以 GPU 为核心、以 RDMA 为 fabric 的专用集群。美国大型科技公司有能力自建超大规模训练集群,而日本工业界长期依赖国家级共享设施(如 ABCI 3.0、TSUBAME 4.0),不能稳定获取商用所需的容量与时间窗。与此同时,开放交换栈(SONiC + SAI、RoCEv2 over Ethernet)在 hyperscale 数据中心已经成熟,理论上可以替代 InfiniBand,但在中等规模(数百到上千 GPU)、面向连续 LLM 训练的生产环境里,公开的运行数据十分稀缺。

本论文是 SAKURA Internet 关于 SAKURAONE 集群的 experience report:100 节点 × 8 张 H100、800 GbE leaf–spine + SONiC、2 PB all-flash Lustre,在 ISC 2025 TOP500 排第 49 位,且是 Top 100 中**唯一**采用完全开放网络栈的系统。文章既给出系统设计与基准测试结果,也基于 9 个月单租户单项目(日语医疗 LLM)的运行 telemetry 报告了工作负载动力学。

---

## 2. 要解决的问题

论文同时回应两类问题:

**系统层面:**

- 开放 Ethernet 栈(SONiC/SAI + RoCEv2)能否在生产级 LLM 训练里达到 InfiniBand 等级的可用性与效率?
- 中等规模(数百节点)集群应该如何设计 GPU–NIC 亲和、rail-optimized 拓扑、ECN/PFC 调参,才能把 collective 通信压住?
- 计算 fabric 与存储 fabric 之间应当怎样物理与逻辑隔离,避免 checkpoint I/O 与 collective 互相干扰?

**运营层面:**

- 中等规模、单租户单项目场景下,真实的 LLM 训练工作负载呈现什么形态?既有工作多来自 hyperscale(Microsoft、Meta)和早期 DNN 集群(Philly/MSRA、SenseTime),100–1000 GPU 量级且专注 LLM 的运营数据公开极少。
- 项目从 continued pretraining(CPT)进入 fine-tuning 阶段时,资源使用模式如何变化?调度器又应该提供哪些原语来适应这种相位转移?

## 3. 洞察与设计

**关键洞察**:

1. SONiC 在 hyperscale 网络已被验证,只要把 ECN min/max、PFC Xoff/Xon、shared buffer 这些参数按交换机实际 buffer 容量精细调过,800 GbE Ethernet + RoCEv2 就能在 production AI fabric 里追上 InfiniBand 的效率,关键瓶颈不在协议本身而在 cross-layer(firmware/kernel/RDMA stack)的协调。
2. 对于 LLM 项目,即便是单租户单项目,工作负载在数量上由小作业主导(76.9% 单节点),在 GPU-occupied time 上由大作业主导(17 节点以上占 73.3%);这种 "long-tail" 不是多租户特有的现象,而是 LLM 开发本身固有的双重性(快速迭代实验 + 生产级训练)。
3. 用户主动取消(CANCELLED)是项目里的主导终止状态(占 GPU-occupied time 73.5%),这并非系统不稳定,而是 practitioner 在线监控 loss curve、判断收敛即终止的"自适应控制"行为—— traditional batch-oriented HPC 的调度假设在此失效。

**设计:**

- **计算节点**:Supermicro 8U 机箱,2× Intel Xeon Platinum 8580+(60C/120T)、1.5 TB DDR5-5600、8× H100 SXM(80 GB)、4× 7.68 TB NVMe scratch、8× ConnectX-7 400 GbE 用作 GPU fabric、2× ConnectX-7 400 GbE 专用存储平面。
- **GPU–NIC 亲和**:用 `nvidia-smi topo -mp` profile 出 PIX(同一 PCIe domain)关系,把 NIC0–2、NIC4–7、NIC9 各绑到 GPU0–GPU7 用于 inter-node collective(NCCL/MPI over RoCEv2);NIC8 + NIC10 (mlx5_bond_0) 专属存储;NIC3 留作备份。这个分层避免了 collective 与 I/O 在同一根 NIC 上排队。
- **网络拓扑**:rail-optimized leaf–spine,两个 pod,每 pod 8 个 leaf,8 个 spine。leaf 与 spine 之间走 800 GbE(2× 400 GbE),交换机使用 Edgecore AIS800-640(Broadcom Tomahawk 5,51.2 Tb/s 全双工),NOS 是 SONiC。每节点 8× 400 GbE 上行到本 pod 的 leaf 集,跨 pod 通过 spine 提供等价最短路径。
- **存储**:4 台 DDN ES400NVX2-NDR200 全闪 Lustre,2 PB 可用容量,目标聚合 ~100 GB/s。每节点双 400 GbE 上 storage switch,active dual-controller,OSS/MDS 服务跨 controller 分布。
- **RoCE 调参**(Table 15):ECN min/max = 2 MB/10 MB,ECN max marking probability = 1%(刻意保守,优先靠 PFC),PFC Xoff = 36.5 MB,Xon offset = 18 KB,shared buffer dynamic α = 1.66%。这套参数在简化的两层拓扑上用 RingAllReduce 与 AlltoAll 扫描后得到。
- **软件栈**:Rocky Linux 9.4 + Slurm 22.05.9 + Singularity/Apptainer + Pyxis + 多版本 CUDA 12.x、cuDNN、NCCL,通过 module 隔离工具链版本。

## 4. 实现细节

- **HPL 配置**:HPL-NVIDIA 25.4.0、N = 2,706,432、NB = 1024、process grid 16 × 49(784 GPU)。
- **HPCG 配置**:HPCG 3.1、784 进程 × 16 线程、global grid 4096 × 3584 × 3808(~55.9B unknowns、~1.51T nonzeros、~40 TB 内存)。
- **HPL-MxP 配置**:HPL-MxP-NVIDIA 25.4.0、N = 2,989,056、NB = 4096、process grid 24 × 32(768 GPU)、Sloppy FP8(sloppy-type=1)。
- **MLPerf v4.1 GPT-3 175B**:32/64/96 节点(256/512/768 GPU)三种规模;PP=16、VP=6、TP=4(96N 时 TP=8),DP 随节点扩展;global batch 1024/1536/2304;CP=1,SP 开启。
- **MLPerf v4.1 Llama 2 70B LoRA**:1/8/64/96 节点;TP=4、PP=1、CP=1 或 2、SP 开启,global batch 8/8/64/96。
- **工作负载分析数据**:2024 年 12 月 – 2025 年 3 月,Llama-3.1-70B-instruct + Qwen2.5-72B-instruct 的 CPT + EHR→标准代码 mapping 的 instruction tuning;基于 Slurm accounting 数据 + DCGM telemetry 提取作业状态、节点数、平均 GPU 利用率。
- **故障数据**:2025 年 1–3 月 21 起独立故障事件,从用户上报与平台监控两个独立通道收集,工程师交叉验证去重。
- **带宽 snapshot**:从 NIC 累积字节计数器算 60 秒满帧差值速率,DCGM 取 ±2 秒内最近样本算每 GPU NVLink/PCIe 平均;由于交换机 telemetry 聚合所有 pod 流量,无法精确归因到单个作业。

## 5. 实验结果

| Benchmark | 指标 | 数值 |
|---|---|---|
| HPL | Rmax | 33.95 PFLOP/s(43.31 TFLOP/s/GPU,效率 78.3%) |
| HPCG | Validated | 396.295 TFLOP/s |
| HPL-MxP(FP8) | Rmax / LU-only | 339.86 / 539.19 PFLOP/s |
| IO500(96 节点) | Total / BW / IOPS | 214.09 / 139.80 GiB·s⁻¹ / 327.84 kIOPS |

**MLPerf GPT-3 175B time-to-train(unverified)**:32N 105.31 min、64N 58.30 min、96N 41.86 min;MFU 38.3% / 41.2% / 35.9%。在相同节点数下与官方 NVIDIA Eos(DGX H100 SuperPOD + InfiniBand)结果差距 2–17%(32N 1.09×、64N 1.17×、96N 1.26× —— 96N 用线性外推,实际可能更差)。

**MLPerf Llama 2 70B LoRA(unverified)**:1N 28.44 min、8N 4.79 min、64N 1.94 min、96N 1.26 min;1N/8N 与 Eos 差距分别 1.02× / 1.05×。

**Profiling(GPT-3 175B,rank 0)**:32N → 64N 计算占比 81.7% → 78.0%、通信 16.4% → 19.3%、idle 1.9% → 2.7%、comm-comp overlap 72.3% → 67.2%;NCCL kernel 中 SendRecv(PP) 始终占 ~90%,DP/TP collective 是次要项,符合 PP=16/VP=6 的 cross-pod 模型。

**Workload 观察**(2024-12 至 2025-03,SAKURAONE 上的医疗 LLM 项目):

| 观察 | 关键数字 |
|---|---|
| 1. CANCELLED 作业 | 占总 GPU-occupied time 73.5%;FAILED 作业占 16.9% 数量但仅 0.3% 时间(说明失败多在早期发生) |
| 2. Long-tail 资源消耗 | 76.9% 单节点、86.4% ≤ 4 节点,但只占 1.8% / 4.6% GPU 时间;≥ 17 节点的占 3.3% 数量、73.3% 时间 |
| 3. 利用率随规模分布 | 17–32 节点中位 GPU 利用率 98.4%,low-util(<20%) 时间仅 1.1%;1 节点中位 23.4%,low-util 时间 69.2% |
| 4. 长尾运行时 | 17–32 节点作业里 13.6% 持续 > 1 周 |
| 5. 阶段转移 | 2025-01 中–02 中以 17–32 节点 CPT 为主;2 月中起 3–16 节点 fine-tuning 作业逐渐增加 |
| 6. 故障组成 | GPU 故障 9/21(42.9%)、互联交换 5(23.8%)、NVLink/NVSwitch/PCIe 4(19.0%);10/21 通过节点重启解决;1 月 13 起、2 月 5 起、3 月 3 起(burn-in 效应明显) |
| 7. 单端口峰值带宽 | Job A 8 端口均匀 ~22.6 GB/s、NVLink/GPU 502 GB/s;Job B 6 端口 ~18.9、2 端口 ~8 GB/s,PCIe 也呈现一致的不对称 |

## 6. 批判性分析

- **MLPerf 数字的"unverified"标签被反复使用**。论文自己注明 GPT-3 与 LoRA 的 time-to-train 都未走官方 submission 流程,但又把它们直接和 NVIDIA Eos 的官方结果做 1.02–1.26× 的比例对比。这种比较缺少必要的对齐说明:Eos 与 SAKURAONE 的 software stack(NeMo / Megatron 版本、CUDA、NCCL)、checkpoint 策略、warmup 步数都可能不同,直接报比例容易让读者误以为 17% 的差距是网络栈本身造成的。
- **"开放栈与 InfiniBand 等价"的论据不够强**。整篇文章对 InfiniBand 的对比只来自 Eos 一个数据点,且没有控制变量实验(比如同样的硬件换 IB 跑 MLPerf)。Section 8.1 反复强调"需要 deep cross-layer expertise",这反而暗示开放栈的总拥有成本很可能不低,论文却未量化运维成本或调参时间。
- **96N MFU 退化没有 root-cause**。GPT-3 175B 在 96 节点 MFU 从 41.2% 跌到 35.9%,作者承认"profiling 在该规模下不可行,留给 future work"。这是篇 system 论文最该有的实验,被一句话带过有点遗憾;读者无法判断这是 cross-pod spine 拥塞、TP 从 4 到 8 的变化,还是 DP=6 的非平凡 grid 引入的负载不均。
- **"CANCELLED 占 73.5% 是高效"的解读偏乐观**。把高取消率解释成"用户主动管理"诚然合理,但反过来说也意味着调度系统**完全没有**在 LLM 训练 lifecycle 上做任何协助 —— 没有自动收敛检测、没有 checkpoint-aware preemption、没有 cost-budget alarm。论文在 8.5 节才提"checkpoint-based preemption 是 future work",但同一篇文章又把现状说成是优点,前后立场不一。
- **Workload 数据样本极薄**。整个 LLM 项目只有 4 个月(2024-12 至 2025-03),且单租户单项目,作者自己也指出"不能直接外推到多租户场景"。但论文又频繁与 Jeon et al. 2019(Philly,18 个月、多租户)、Kokolis et al. 2025(Meta,数千 GPU)做模式比较,这种规模差距下"模式相似"的结论说服力有限。
- **Per-rail 不对称的解释含糊**。Job B 出现 2 个 NIC 端口仅 8 GB/s 的现象,作者只说"PCIe 也有同样不对称",但没有进一步定位是 NCCL 的 ring/tree 选择问题、应用层 imbalance 还是 fabric 拥塞。这恰恰是 rail-optimized 设计最敏感的故障模式,值得专门研究而不是一段话带过。
- **故障统计无法支撑 MTTF/MTTR**。作者诚实指出"基于 Slack 上人工日志、时间戳不精确",但同时又把"42.9% 是 GPU 故障"和"10/21 通过 reboot 解决"作为系统设计原则的支撑。如果数据本身的精度不足以支撑 MTTR,那也很难支撑这些原则推论。
- **ECN max marking probability = 1% 的选择没有充分论证**。作者承认"看起来过于保守,实际更靠 PFC",但只在两层简化拓扑上做的扫描,没有在生产 four-pod 拓扑上验证;这种关键参数若未来 workload 改变(例如 MoE all-to-all 主导),很可能立即暴露问题。

## 7. AI Infra / MLSys 视角

这是一篇典型的 system experience paper,对 AI Infra 研究者有以下可借鉴价值:

- **GPU–NIC 亲和的 PIX 级别绑定**,在 H100 这种每节点 8 NIC + 8 GPU 的对称硬件上做得很彻底,值得在自建集群里复制。NIC3 留作 secondary 而非分摊负载,这种 "宁可少一根也不要 cross-PCIe-domain" 的取舍背后逻辑,可以扩展到对 multimodal 训练(图像 + LLM 同时存在 storage I/O 与 collective)的 fabric 设计。
- **存储平面与计算平面物理 + 逻辑分离**,在 LLM 训练 hourly multi-TB checkpoint + concurrent data generation 这种 mixed pattern 下被验证有效。但论文没给出 checkpoint 与 collective 真的并发时的 P99 延迟,这是值得后续深入测量的方向。
- **作业相位转移的观察(CPT → Fine-tune)** 是篇里最 actionable 的发现。它直接指向一个具体研究问题:**集群应该在 phase transition 时自动重配 partition、queue policy、reservation 策略**。当前 Slurm 完全静态,需要管理员手动调整;一个能根据近期作业 size 分布自适应调整 partition 容量与优先级的 scheduler 是清晰的研究切入点。
- **CANCELLED 占主导与 checkpoint-aware preemption** 可以连成一条 future work:既然用户多以 loss 收敛为终止信号,scheduler 完全可以监听 checkpoint 事件,把"checkpoint 完成 + idle gap"当成安全 preemption 点,在大作业中间塞短作业,同时不浪费已训练的步数。这条路 Tiresias、Themis 等做过基础工作,但都不是为现代 LLM 训练管线设计的(那时还没有 step-level checkpoint 这种廉价语义)。
- **Open Ethernet 栈在 800 GPU 规模可行** 是有价值的存在性证明,但要让这成为 MLSys 社区的可复用结论,需要进一步:(i) 在不同 collective 模式(MoE all-to-all、PP 重叠)下对比与 IB 的差距;(ii) 把 ECN/PFC 调参从经验规则升级为基于 workload signature 的自动调优(可能用强化学习或贝叶斯优化);(iii) 给出一套针对 SONiC + RoCEv2 的标准 telemetry pipeline,让其他实验室能在不需要"deep cross-layer expertise"的前提下复现。
- **中等规模(100–1000 GPU)集群的 telemetry 数据**本身就是对社区的贡献,因为以前的 Philly、Borg、Meta 的数据都来自 hyperscale 环境,中等规模的 production LLM 集群运营数据极其稀缺。如果 SAKURA 后续能开源 sanitized trace,会非常有价值。
- **可能的延伸研究方向**:(1) phase-aware scheduler design;(2) RoCE 参数的 workload-driven 自适应 tuning;(3) 单租户单项目下的 GPU "filler workload" 框架 —— 把 idle slot 卖给 inference / data generation / evaluation,且不影响主作业 SLA;(4) 用 SAKURAONE 的 fault data 训练一个 LLM training failure predictor。

## 8. 总结

SAKURAONE 是一份兼具系统设计与运营 telemetry 的 experience report:在 800 张 H100 + 完全开放的 SONiC/SAI + RoCEv2 fabric 上,达到了与 InfiniBand-based DGX SuperPOD 相差 2–17% 的 LLM 训练性能,并以 33.95 PFLOP/s HPL 排进 TOP500 第 49 位。基于 4 个月单租户医疗 LLM 项目的 telemetry,论文记录了 LLM 开发负载的双重性(数量上小作业主导、时间上大作业主导)、用户主动取消的 73.5% 占比、CPT → Fine-tune 的相位转移,以及 GPU 占 42.9% 的故障组成。

主要贡献是给中等规模(100–1000 GPU)的开放栈 LLM 集群提供了存在性证明与公开运营数据,补上了过往文献只有 hyperscale 数据的空白。主要局限是:与 InfiniBand 的对比仅靠一个外部数据点;MLPerf 数字未走官方验证;workload 样本仅 4 个月单租户,scheduling 与 queueing 的结论不能外推到多租户;96N MFU 退化原因未查清。对于想在中等规模自建 AI 集群的工业用户,本文是一份值得参考的 reference design;对于 MLSys 研究者,文中的 phase-aware scheduling、checkpoint-based preemption、RoCE 自适应调参是清晰的 follow-up 方向。
