## 1. 背景

生成式模型正在重塑直播行业:基于图像扩散模型的流式管线(如 Daydream、TouchDesigner、StreamDiffusion)让创作者能够实时对直播视频进行风格迁移、背景替换、特效合成等操作,大幅降低后期制作成本。但图像扩散模型逐帧生成天然存在时间一致性缺陷,在连续流上会出现闪烁、漂移和运动断裂。

与此同时,视频扩散模型(Wan、CausVid、Self-Forcing 等)通过显式建模时序依赖带来了更强的时间一致性,并通过蒸馏、稀疏注意力、因果 DiT 等手段将推理速度推进到"准实时"。一个自然的问题是:视频扩散能否取代图像扩散,成为下一代实时直播 AI 管线的底座?

然而,当前视频扩散系统主要针对离线吞吐优化,单次前向就处理 81 帧乃至数百帧的大 chunk,这与直播场景下严格的 SLO(首帧时延 TTFF、每帧截止时间 DDL、低抖动)本质冲突。本文就是在这个张力下构建一套面向实时流式推理的视频扩散服务系统。

---

## 2. 要解决的问题

作者将现有视频扩散在直播场景下的缺陷归纳为四条:

1. **SLO 不达标**。主流视频扩散模型(Wan、CausVid、Self-Forcing)按 $1 \times T \times H \times W$ 的固定大块推理,T 从 81 起步。按 TTFF ≈ $2BTHWP_{model}/(C_{device}\rho_{VAE})$ 估算,H100 上 480p + 1.3B + 81 帧 chunk 的理论 TTFF 达 5.31s,远超直播要求的 ~1s。固定输入尺寸也无法随硬件负载自适应调度。
2. **长时漂移**。CausVid、Self-Forcing 从 Wan-2.1-T2V 蒸馏而来,训练目标是 5–10 秒短片段;在持续直播(小时级)下,sink token 老化、RoPE 相位累积、anchor cache 不刷新导致视觉漂移和一致性下降。
3. **高速运动下的运动撕裂**。现有视频扩散训练数据偏向慢速场景,推理端用固定 noise schedule + 大 chunk 抑制帧间差异,结果对快动作(镜头猛摇、打斗)会出现模糊、残影、motion tearing。
4. **多 GPU 扩展性差**。序列并行(Ulysses、Ring-Attention)在短序列工作负载下通信占比过大(跨卡通信 40–120 ms,是本文管线的 20–40 倍);朴素流水并行对 FPS 几乎没提升。直播场景下每帧 DDL 约束让传统并行策略难以奏效。

## 3. 洞察与设计

**关键洞察**:直播场景下的因果视频 DiT 工作负载天然位于 memory-bound 区间(H100 上 4 帧 chunk 的算术强度 ≈ 0.84,远低于 660 FLOP/Byte 的 ridge AI);并且随着硬件代际演进(V100 → GB100 算力涨 17×,HBM 带宽只涨 7×)与 VAE 压缩率提升,这一 memory-bound 特性只会愈发明显。因此**为直播流式推理设计系统,必须围绕"显存流量塑形"而非"算力利用率"来做调度**——要把固定大 chunk 换成可调的小 chunk,用 batch 而非 sequence 来提升带宽利用率,用 pipeline 而非 sequence parallelism 来扩展多卡。

基于这一洞察,StreamDiffusionV2 的设计分为两层:

### 3.1 实时调度与质量控制(单卡)

- **SLO-aware batching scheduler**。把固定输入 $1 \times T \times H \times W$ 重塑为 $B \times T' \times H \times W$:$T'$ 保持很小(几帧)以压住每步延迟,$B$(stream batch size)则跟随瞬时硬件负载自适应。基于 memory-bound 假设下 $L(T,B) \approx (A(T,B) + P_{model})/(\eta \mathrm{BW}_{HBM})$,FlashAttention 让激活开销 $A(T,B) \propto \mathcal{O}(BT)$,因此频率 $f = BT/L(T,B) \propto B/(1+B)$,单调增大直至 roofline 拐点。
- **Adaptive sink token + RoPE refresh**。针对长时漂移:维护 sink token 集合 $\mathcal{S}_t$,对每个新 chunk 嵌入 $\mathbf{h}_t$ 与旧 sink 计算余弦相似度 $\alpha_i = \cos(\mathbf{h}_t, s_i^{t-1})$,把相似度低于阈值 $\tau$ 的 sink 替换为 $\mathbf{h}_t$,从而让 sink 跟随 prompt 语义演化;RoPE 相位在帧数超过 $T_{reset}$ 后周期性复位以消除位置漂移。滚动 KV cache 保留 sink + 最近几帧 rolling tokens,chunk 边界处刷新 anchor cache。
- **Motion-aware noise scheduler**。对连续潜在帧计算 frame-diff $d_t = \sqrt{\|v_t - v_{t-1}\|_2^2 / (CHW)}$,按短窗归一化到 $[0,1]$ 得 $\hat{d}_t$;噪声率按 $s_t = \lambda[s_{max} - (s_{max}-s_{min})\hat{d}_t] + (1-\lambda)s_{t-1}$ 做 EMA 平滑。快动作给保守去噪(抑制撕裂),慢动作给激进去噪(恢复细节)。

### 3.2 可扩展流水并行编排(多卡)

- **Multi-pipeline orchestration**。将 DiT 的 $n$ 层按 rank 切分,每 rank 处理一个 micro-step 后 ring 方式传给下一 stage;把 $n$ 个去噪步看作额外的 batch 乘数,刷新后的延迟模型变为 $L(T, nB)$。配合 SLO-aware batcher,让所有设备保持高利用率,聚合吞吐逼近带宽 roofline。
- **DiT block scheduler**。首尾 rank 还要跑 VAE encode/decode,静态等分会让 VAE 所在 stage 成为瓶颈,产生 pipeline bubble。引入在线测量执行时间、按实测延迟动态重分配 DiT block 的轻量级调度器,把每 stage 延迟拉齐。
- **Stream-VAE**。短 chunk(4 帧)的流式 Video-VAE 变体,在 3D 卷积内缓存中间特征以维持时间一致性。
- **Asynchronous communication overlap**。每卡维护两个 CUDA stream(compute + comm),跨 GPU 传输与本地计算重叠,以进一步隐藏通信延迟。

## 4. 实现细节

- 基座模型:Wan 2.1 + CausVid 蒸馏后的 causal DiT(1.3B / 14B 两档),训练无关(training-free)。
- 评测平台:4× H100 80GB(NVLink)与 4× RTX 4090 24GB(PCIe);bf16,不使用 TensorRT 或量化。
- 分辨率:$512 \times 512$ 与 480p($832 \times 480$);去噪步数 1–4 可调。
- Sink token 刷新阈值 $\tau$ 取较大值以确保语义对齐;RoPE 周期 $T_{reset}$ 在 chunk 边界处触发复位。
- 关键硬件参数(H100 roofline 分析,Appendix A):FP16 dense 990 TFLOPS,HBM 1.5 TB/s,ridge AI = 660 FLOP/Byte;DiT 配置 $C=2048, L_q=1536, L_{kv}=1536\times 6, N=30$,NSight 实测 DiT 显存流量 5.2 GiB,实测 intensity ≈ 0.84 — 确认 memory-bound。
- 可选增强:Appendix C 中用 REPA(配 DINOv2 特征对齐)联合 DMD 做蒸馏训练以提升生成质量,损失 $\mathcal{L} = \mathcal{L}_{DMD} + \lambda \mathcal{L}_{REPA}$。这部分不是 training-free 主线的一部分。

## 5. 实验结果

**TTFF(端到端首帧时延)**

| 方法 | 16 FPS 输入 | 30 FPS 输入 |
|---|---|---|
| Wan2.1-T2V-1.3B(50 步) | — | ~103s(280× 我们) |
| CausVid(2 步) | — | ~6.7s(18× 我们) |
| **StreamDiffusionV2** | **0.47s** | **0.37s** |

**FPS(4× H100 NVLink)**

| 模型 / 分辨率 | 1 步 | 4 步 |
|---|---|---|
| 1.3B / 480p | 42.26 | >40 |
| 1.3B / 512² | 61.57 | 60+ |
| 1.3B(论文摘要峰值) | **64.52** | 61.57 |
| 14B / 480p | 39.24 | — |
| 14B / 512² | **58.28** | 31.62 |
| 1.3B / 4090 PCIe / 480p | ~16 | — |
| 1.3B / 4090 PCIe / 512² | ~24 | — |

**SLO 指标(512² @ 1 步,1s SLO budget,H100)**

| 方法 | p50 | p90 | p95 | p99 | Jitter 均值 | Miss Rate |
|---|---|---|---|---|---|---|
| **StreamDiffusionV2** | 361 ms | 484 ms | 497 ms | 585 ms | 21 ms | **0.2%** |
| CausVid(+ StreamVAE) | 1672 ms | 2958 ms | 3304 ms | 3896 ms | 235 ms | 99.9% |

**生成质量**

| 指标 | StreamDiffusion | StreamV2V | CausVid | **本文** |
|---|---|---|---|---|
| Text-Image CLIP ↑ | 26.48 | — | 27.69 | **29.29** |
| Temporal CLIP ↑ | 95.24 | 96.58 | 98.48 | **98.51** |
| Warp Error ↓ | 117.01 | 102.99 | 78.71 | **73.31** |

**消融**:只开 Dynamic Noising 把 Warp Error 从 79.51 降到 75.71;只开 Sink Token 降到 73.64;两者都开 73.13。

**并行对比**:Ring-Attention 与 DeepSpeed-Ulysses 因通信开销几乎没有吞吐增益;StreamDiffusionV2 的实测吞吐贴近理论 roofline 值。

## 6. 批判性分析

- **消融覆盖不全**。论文对 sink token、motion-aware noise 这两个与质量相关的模块给了消融,但对 SLO-aware batching、DiT block scheduler、Stream-VAE、异步通信 overlap 这四个带来大部分 FPS 收益的系统级模块**只有合在一起的端到端数字**,读者无从判断 FPS 涨幅到底来自哪一块。
- **"Training-free"与 REPA 微调边界模糊**。文中反复强调 training-free,但附录又给出了 REPA + DMD 的联合蒸馏方案以"提升质量"。论文并没有明确说明 Table 2 中 CLIP 29.29 / Warp 73.31 是否用到了 REPA 微调模型,这直接影响质量结论的解释力。
- **基线选择偏颇**。质量对比里的 CausVid v2v 被作者自己称为"naïve noising–denoising scheme";StreamDiffusion、StreamV2V 是图像扩散(天然不利)。缺少与 Self-Forcing、LongLive 等同代因果视频扩散在**同一 SLO 约束**下的公平比较。
- **1.3B 与 14B FPS 过于接近**。14B 模型 FPS (58.28) 接近 1.3B 模型 (64.52) 的解释是"两者共享 VAE 且 VAE 占 30% 耗时",这反过来说明**当前系统瓶颈其实压在 VAE 而不是 DiT**,那么 DiT 侧"近线性流水加速"的 marketing 信息就要打折扣,尤其在 14B 模型下 DiT 部分真实加速比应单独报。
- **长时漂移量化不足**。论文反复强调支持"小时级"直播稳定,但未给出连续运行 1 小时 / 10 分钟的 CLIP drift / warp error 随时间曲线,sink token 刷新策略的收益仍然是定性的。
- **Motion-aware noise 的阈值敏感性未讨论**。$s_{max}, s_{min}, \lambda, \sigma$ 都是经验常数,作者没给参数扫描,也没讨论极端场景(全静止 vs. 持续高速)下的退化模式。
- **4090 PCIe 结果不够 friendly**。480p 只有 16 FPS,与"让个人创作者也能用上"的叙事有落差;PCIe 下是否仍能守住 1s SLO 不被回答。
- **jitter 指标定义不规范**。表 1 给出均值 21 ms / std 30 ms / p50 13 ms 这种组合,但 jitter 通常定义为相邻帧到达间隔差,文中未明确是按何种方式采样。
- **SLO miss rate 对比不完全等条件**。CausVid baseline 用的是 81 帧固定 chunk,本就是离线配置;若对 CausVid 也改成小 chunk 再对比,差距可能大幅收窄。

## 7. AI Infra / MLSys 视角

这篇工作是 **LLM 服务系统的调度范式向视频扩散迁移**的典型样本,对 AI Infra 读者有以下可借鉴点:

- **Attention sink 迁移**。sink token 的动态刷新本质是把 StreamingLLM(Xiao et al., 2024)的 attention sink 机制从文本扩展到视频潜在表示,并额外加入了"语义相似度触发替换"策略。这个思路值得推广到其他长序列流式推理(例如长语音合成、连续代码补全)。
- **Roofline 驱动的系统设计方法论**。论文用 H100 roofline 分析把问题结构化成"因果 DiT 在短 chunk 上是 memory-bound" → "因此应当走 pipeline+batch 而非 sequence parallelism",这种先做硬件特征分析再选并行策略的做法,比传统"哪种并行最常见就用哪种"更扎实,值得在做 LLM 推理系统设计时也 default 采用。
- **SLO 调度迁移**。LLM 推理里的连续批处理(continuous batching,vLLM)与 SLO-aware admission(DistServe)与本文的 SLO-aware batching scheduler 思想一致。下一步很自然的方向是**统一的多模态生成服务系统**:把文本 token 生成与视频潜在帧生成放在同一调度器下,根据 DDL 共享 GPU。
- **Pipeline 微步 rotation**。Fig. 6 里的 micro-step rotation(Rank 0 发 $x_1$ 到 Rank 1,同时处理 $x_2$)与 Megatron-LM 的 1F1B pipeline 非常相似,只是去噪步数被当成一种额外的"虚拟 micro-batch"维度。这种**把去噪迭代映射为 pipeline depth** 的思路,也可以推广到 reasoning LLM 的 speculative decoding 流水化。
- **VAE 瓶颈值得单独处理**。14B 模型下 VAE 占比 30% 说明 VAE 已经变成新瓶颈。可跟进方向:(1) VAE 专用的流式量化;(2) 将 VAE decoder 与下一 chunk 的 DiT forward 做跨 iteration 重叠;(3) tokenizer/VAE 与 DiT 的异构硬件协同(VAE 上 CPU 或小卡,DiT 上大卡)。
- **Memory-bound 长期趋势**的论述(compute 增速远大于 HBM 增速,VAE 压缩进一步降低 AI)是 MLSys 研究者能直接引用的宏观论据,支持"带宽优化的价值在未来只会上升"这一判断。
- **可延伸的研究切入点**:
  - 量化 + 稀疏化叠加在本文 pipeline 上(本文主动回避了 TensorRT / 量化,留了很大空间)。
  - 动态 sink token 策略的理论分析(何时刷新最优、刷新粒度与漂移的定量关系)。
  - 异构 GPU 集群下的 DiT block 调度策略:现有 scheduler 还只在同构集群上演示,H100+4090 异构池下该怎么切?
  - 与 speculative decoding 思想结合:能否用一个小 student DiT 先预测潜在帧,大 teacher DiT 去 verify/refine?

## 8. 总结

StreamDiffusionV2 把视频扩散模型从离线大 chunk 吞吐导向,改造成满足直播 SLO 的实时流式服务系统。核心贡献有三:(1) 以 SLO-aware batching 为中心、stream batch × pipeline parallel 的联合调度,逼近 memory-bound roofline;(2) 适配长时流的 sink token 动态刷新 + RoPE 复位 + 滚动 KV cache,以及 motion-aware noise controller 对高速运动的适配;(3) 配合 DiT block 动态重分配和异步通信 overlap,把 14B 模型在 4× H100 上推到 58.28 FPS / 0.47s TTFF、1s SLO miss rate 0.2% 的工业级水平。系统整体 training-free、tunable、可在个人级 4090 与企业级 H100 间 portable。主要局限在于:系统模块的消融还不充分,VAE 正在成为新的瓶颈,长时漂移只做了定性验证,以及质量对比中的基线公平性有争议。对 AI Infra 读者而言,这篇论文的真正价值在于它示范了**如何把 LLM 服务系统的 SLO 调度范式移植到扩散模型服务**,以及**用 roofline 分析反向驱动并行策略选择**的方法论。
