# Spira: Exploiting Voxel Data Structural Properties for Efficient Sparse Convolution in Point Cloud Networks

## 1. 背景

点云（point cloud）数据是 LiDAR、深度相机等 3D 传感器输出的核心数据形式，广泛应用于自动驾驶、机器人、AR/VR 和无人机感知。由于点云在 3D 空间中天然稀疏（典型占用率 < 1%），直接套用标准稠密 3D 卷积既浪费计算又浪费显存，因此主流做法是先把连续点云量化成离散的 voxel 网格，再在 voxel 上做 Sparse Convolution（SpC）。Voxel 化 SpC 已经成为 SemanticKITTI、ScanNet、Waymo 等主流 benchmark 上目标检测和语义分割任务的 SOTA 基础算子。

一个 SpC 层的执行由两步组成:

1. **Voxel Indexing**：生成输出坐标（downsampling），并构造 kernel map —— 一个 $|V_q| \times K^3$ 的表，记录每个输出 voxel 与每个 weight offset 对应的输入 voxel 索引。这一步需要:(i) 预处理阶段把坐标组织到查询数据结构中（哈希表、排序数组等）；(ii) 在数据结构上做 lookup；(iii) 可选的后处理阶段，过滤 / 重排 kernel map 以配合后续计算。
2. **Feature Computation**：按 kernel map 聚合输入特征计算输出特征。业界有两种 dataflow —— output-stationary（以输出坐标切分线程块，会多做无效零乘）和 weight-stationary（以 weight offset 切分线程块，需要 atomicAdd 合并部分和）。

过去五年围绕 SpC 已有 MinkowskiEngine、SpConv2、TorchSparse、PCEngine、TorchSparse++、Minuet 等多个引擎迭代，不断优化哈希、搜索和 dataflow，但都**没有系统地利用 voxel 坐标本身的结构特性**。

---

## 2. 要解决的问题

作者归纳现有 SoTA 引擎（TorchSparse++、Minuet）的两大瓶颈:

1. **Voxel Indexing 中的 pre-processing 与 post-processing 开销大**。Minuet 用基于二分查找的 mapping 算法，搜索比 TorchSparse++ 快 4.31×，但需要先 sort / 组织坐标结构，pre-processing 时间可以和搜索时间持平。TorchSparse++ 在 weight-stationary 下，则需要把整张 kernel map 转置并过滤，post-processing 开销不可忽视。
2. **dataflow 支持不灵活**。Minuet 只支持 weight-stationary；TorchSparse++ 两种都支持但切换粒度是**层级**的 —— 整层要么 output-stationary 要么 weight-stationary。这浪费了 kernel map 内部不同列（不同 weight offset）密度差异巨大这一特性。

论文还指出另一个被忽视的观察:**同一网络内所有 SpC 层的 voxel indexing 在语义上彼此独立**，但现有引擎把它们串行放在每一层的前向路径上，占用端到端延迟且 GPU SM 利用率很低。

作者的整体问题陈述是:**能否从 voxel 数据本身的数学结构入手，把 indexing 的 pre/post-processing 压到极低，把 dataflow 粒度细化到 weight-offset 级，并把全网络 indexing 并行起来?**

## 3. 洞察与设计

**关键洞察**：voxel 坐标具备三条未被前人充分利用的结构性质:

- **Integer Property**：voxel 坐标都是整数，且是 stride 的整数倍。这意味着在排好序的坐标数组里，$(x, y, z)$ 与 $(x, y, z + s_p)$ 若都存在，就一定是数组中的连续位置（中间不可能插入其他坐标），从而可以用 O(1) 的局部线性扫描代替额外的 binary search。
- **Bounded Property**：实际应用中 $(R_x, R_y, R_z)$ 是有限的（室内 < 房间尺度；户外自动驾驶 < LiDAR 最大探测距离 ~150m），量化后 voxel 整数坐标取值范围很小。室外典型配置中 $v_x, v_y, v_z$ 分别只需要 12、12、8 bit，可以**把整个 3D 坐标打包进一个 32-bit 整数**（极端场景用 64-bit 也绰绰有余，精度可达毫米）。
- **Neighboring Property**：物体表面连续，所以 submanifold 卷积中，kernel map 列密度与 weight offset 的 L1-norm 强相关 —— L1-norm 越小的 offset 列越稠密，L1-norm 越大的越稀疏。实测 K=5 时，L1-norm=1 的列平均 39.4% 非零，而 L1-norm=6 的列只有 5.4%。

基于这三条性质，Spira 是 MLSys 领域第一个「voxel 结构性质感知」的 SpC 引擎，由四个核心设计组成:

### 3.1 One-Shot Z-Delta Search（对应 Integer Property）

核心出发点是:只要第一层输入坐标排好序，后续所有层（submanifold 层恒等继承、downsampling 层排序去重）天然保持有序，于是**根本不需要重新建查询数据结构**。

然后把 $K^3$ 个 weight offset 按 $(x, y)$ 分组，每组 K 个 offset 共享同样的 $(x, y)$、只在 z 方向上依次递增 $s_p$。对每组内 K 个查询:只对 "anchor"（最小 z）做一次 binary search 定位起始位置，剩下 $K-1$ 个查询通过**线性扫描至多 $K-1$ 个连续内存位置**即可解析。结果是把 $|V_q| \times K^3$ 次 binary search 降到 $|V_q| \times K^2$，而且剩余的查询天然 cache 友好。

### 3.2 Packed-Native Voxel Indexing（对应 Bounded Property）

把 $(v_x, v_y, v_z)$ 三元组打包进单个 32-bit 或 64-bit 整数，**且在 downsampling 和 mapping 两个 kernel 里全程保持 packed 态**:

- **Downsampling 中按 $s_q = 2^m$ 取整**：等价于把 packed 值与一个位掩码按位与，mask 把每一维的低 $m$ bit 清零。
- **排序去重**：packed 值在 lexicographic 序下与原三元组一一对应（因为每一维各自占据不相交的 bit 段），所以 radix sort 直接对 packed 整数排序即可。
- **查询生成**：$\text{packed}(q_i) + \text{packed}(\delta_k) = \text{packed}(q_i + \delta_k)$，且比较 `>` 也保序，整个 mapping 过程无需解包。

最终得到四重收益: 坐标显存占用降到 1/3、全局内存带宽 3× 更高、排序 key 更小、单次 compare 代替三次。

### 3.3 Adaptive Hybrid-Dataflow Feature Computation（对应 Neighboring Property）

把 Full Output-Stationary 与 Full Weight-Stationary 看作两个极端，中间允许**按 weight offset 切分**:对每一层用可调阈值 $t$，把 L1-norm $< t$ 的 offset 分到 output-stationary（列密，适合少量无效零乘），L1-norm $\geq t$ 的分到 weight-stationary（列稀疏，适合跳零但付出 atomic 代价）。$t = 0$ 退化为 full WS、$t = \text{L1NormMax}+1$ 退化为 full OS。

关键实现细节:论文用了一个**巧妙的线程分发策略**让三种 dataflow 都几乎没有转置代价 —— z-delta search 在 full OS 模式下自然写出 $|V_q| \times K^3$ 布局；在 full WS / hybrid 下让同一 weight offset 的不同输出 $q_i$ 分配到同一 thread block，写出 $K^3 \times |V_q|$ 布局。hybrid 模式只需转置 dense 子矩阵、只过滤 sparse 子矩阵，大幅削减 post-processing。

阈值 $t$ 用 5 个样本场景 offline 调参，全网络耗时 < 3 秒。

### 3.4 Network-Wide Voxel Indexing

作者通过推导发现，downsampling 的递推 $V_i = \lfloor V_{i-1}/2^i \rfloor \cdot 2^i$ 可以展开成只依赖 $V_0$ 的闭式表达 $V_i = \lfloor V_0 / 2^i \rfloor \cdot 2^i$，因此**所有层的 downsampling 彼此无依赖**；而 mapping 只依赖同一层的 downsampled 坐标，层间也没有真依赖。

于是 Spira 把全网络所有层的 voxel indexing 放到网络开头用多个 CUDA stream 并发执行，填满原本空闲的 SM；kernel map 存入 global memory，推理时各层 feature computation 按需消费。实测 voxel indexing 总耗时降到 1/1.72，全网络推理再提 1.05–1.12×。

## 4. 实现细节

- **代码开源**：https://github.com/SPIN-Research-Group/Spira
- **打包方案**：默认 32-bit packing，bit 分配 (12, 12, 8) for $(v_x, v_y, v_z)$，支持任意灵活配置；64-bit packing 覆盖到千米级空间 + 毫米级分辨率。
- **排序**：使用 RadixSort（Adinets & Merrill 2022 的 Onesweep 实现），线性复杂度，32-bit/64-bit 初始一次排序的开销仅占总推理时间 1.3%/1.6%，大场景 < 0.3%。
- **Submanifold 对称性复用**：对 weight offset $\delta_l = (b, c, d)$ 和 $\delta_n = (-b, -c, -d)$ 的对称性，weight-stationary 只需存储 / 过滤一半 kernel map。
- **Kernel map 显存**：平均 ~40MB，Jetson Orin AGX 这类边缘设备也能承受。
- **Tuning 开销**：21 层网络选阈值 $t$ < 3 秒，与 TorchSparse++/Minuet 的 2–5 秒相当；支持场景切换时重新调参。
- **评测系统**：6 张 GPU，从消费级 GTX 1060 / RTX 3090、工作站 Quadro RTX 5000、数据中心 A100 / H100，到边缘 Jetson Orin AGX（50W）。
- **评测网络**：SparseResNet (21 层)、MinkUNet (42 层)、CenterPoint Large (20 层，K=5 backbone)。
- **数据集**：SemanticKITTI（0.11%）、ScanNet（1.57%）、Waymo（0.16%），覆盖室内外、稀疏密集场景。

## 5. 实验结果

### 5.1 端到端推理性能

| GPU | vs Minuet | vs TorchSparse++ |
|---|---|---|
| RTX 3090 | 1.70× avg | 1.62× avg |
| A100 | 2.05× avg | 1.58× avg |
| 六 GPU 综合 | — | **1.68× avg，最高 3.04×** |

Spira 32-bit 与 64-bit packing 性能差异可忽略（~1.6% 初始排序开销），证明即使高精度场景也能吃到收益。

### 5.2 层级性能

| 层配置覆盖 | vs Minuet | vs TorchSparse++ |
|---|---|---|
| 多种 $(C_{in}, C_{out}, K)$ | 2.19× avg, 3.44× max | 2.03× avg, 2.60× max |
| 综合 | **2.11× avg，最高 3.44×** | |

### 5.3 Mapping 性能（voxel indexing 单独切片）

Spira z-delta search 相对三类基线的最大加速: Minuet 2.85×、TorchSparse++ 9.49×、Simple BSearch 3.45×。Minuet 和 TorchSparse++ 分别有 8–36.5% 和 18.3–55.5% 的 pre-processing 开销，Spira 完全消除。

### 5.4 各核心点消融（UNet 端到端）

| 累加组件 | 相对 TorchSparse++ 加速 |
|---|---|
| + 32-bit packed-native Simple BSearch | ~1.00× baseline |
| + z-delta search | 1.18× |
| + hybrid dual-dataflow | × 1.07 额外 |
| + coordinate packing（单独增量） | × 1.02 |
| + network-wide streamed indexing | × 1.05（voxel indexing 总耗时降 1.72×） |

### 5.5 合成数据 / 扩展性

- 在随机生成、**不遵循 neighboring property** 的合成场景（密度 0.12%–12.5%）上，Spira 仍有 Minuet 1.80×、TorchSparse++ 1.59× 平均加速 —— 说明收益并非完全来自 neighboring property。
- 固定密度 1.25%、非零 voxel 数从 $10^4$ 扩到 $5 \times 10^6$，Spira 仍有 2.05× 平均（最高 2.25×）。
- 内存占用 ($K{=}13, B{=}4$):TorchSparse++ 17GB / Minuet OOM / Spira 16GB + 1.81×，大 kernel 下优势更明显。

### 5.6 Dataflow 选择画像

ScanNet（1.57% 稠密）中，ResN / ResNL 网络更多层被分到高阈值的 hybrid 或 full output-stationary；KITTI/Waymo（0.11–0.16% 稀疏）则偏向 weight-stationary 或低阈值 hybrid。UNet（42 层，大层为主）在三个数据集上都以 weight-stationary 为主，output-stationary 为辅。

## 6. 批判性分析

- **神经网络输出数值正确性未验证**：全文专注 latency / throughput，但 packed-native 在 downsampling 用位运算取代整除运算、hybrid dual-dataflow 把一个 kernel 拆成两个再合并，这些改造在数值上都声称等价，却没有给出任何精度 / mIoU / mAP 比较表。对检测/分割下游任务，验证 end-to-end 推理结果与原引擎 bit-wise 或 epsilon 内一致是必要的，论文把这一点完全略过。
- **Bounded Property 的场景假设有边界**:论文反复说 12+12+8 bit 足够室外 LiDAR，但自动驾驶之外的场景（例如室外大范围 aerial LiDAR、地质扫描、建筑 BIM）有可能超过这个范围；文中只列举了 Waymo 的 150m 和室内，没有量化边界情况下的 fallback（要从 32-bit 升到 64-bit）对 cache 行为和排序性能的影响是否线性。
- **Network-Wide Indexing 的显存代价被一笔带过**：文中说 kernel map 平均 40MB「边缘 GPU 也能承受」，但 Table 4 的 $K=13, B=4$ 场景 Spira 占到 16GB（RTX 3090 只有 24GB 总量），且 Jetson Orin AGX 本来就是内存共享架构；把所有层的 kernel map 提前 materialize，对更极端的 batch / kernel 配置是否会 OOM，其权衡并没有清晰给出 pareto 曲线。
- **Hybrid dual-dataflow 的阈值调参是 per-dataset 的**：作者说重新调参 ~3 秒可以接受，但这依赖「使用方知道当前数据集属于哪个 distribution」这个隐含假设。真实部署（例如自动驾驶车辆在郊区 → 市中心切换）中，阈值是每帧自适应还是按 session 预设，文中没给工程方案。
- **Layer-wise 2.11× 但 end-to-end 只 1.68×** 的差距被解释为「非 SpC 层稀释」，但没有拆分出哪部分是 BN/ReLU/memory copy、哪部分是 SpC 层以外的瓶颈。对读者评估「把 Spira 集成进自家推理栈预期收益」而言，这份拆分是缺失的。
- **Dataflow 只有两种变体的历史包袱**：output-stationary 和 weight-stationary 是二元划分，Spira 用 L1-norm 阈值把 weight offset 再分一次；但是否还存在第三维（例如按 channel 分？按输出 voxel 的邻居密度分？）值得探索，论文并未在 related work 里交代自己的 hybrid 是否已经是 dataflow 空间的 optimum。

## 7. AI Infra / MLSys 视角

虽然 Spira 是点云专用引擎，但其方法论对 AI Infra / MLSys 有多重可迁移价值:

1. **「利用数据结构性质反推 kernel 设计」范式**:Spira 的四大点（one-shot search、packed-native、hybrid dataflow、network-wide parallelization）都是从 voxel 数据性质出发反推的 kernel / runtime 设计。这个模式直接可迁移到 **LLM KV-cache indexing**（KV 坐标也有整数 / 有界 / 连续访问性质）、**MoE expert routing**（token-expert 映射同样需要快速 lookup + 动态负载）、**稀疏 attention mask 构建**（block-sparse attention 的 indexing 开销常被忽略）。
2. **One-shot / zero pre-processing 设计哲学**:现代 LLM inference 里也有大量「先建索引，再查询」的结构，比如 PagedAttention 的 block table、prefix cache 的 hash 表。Spira 证明如果**维持原生数据的有序性**，整个 pre-processing 阶段可以省掉。值得跟进:KV cache block table 能否在 token 层面维持某种整数不变量，让 lookup 退化成局部线性扫描?
3. **Packed-Native 层面的 insight 和 AI Infra 中的 quantization 有同构性**:AI Infra 里常用 int4/int8 量化权重节省显存，但很少有人把**索引**也量化。Spira 告诉我们 index 本身也能 bit-pack，并且在 packed 域直接做算术 / 排序 / 比较。对于 RoPE 位置编码、sparse tensor 的 row/col index 这类场景，可以复用。
4. **Network-Wide 并行化提示了「prologue / epilogue 编译」空间**:把所有层的 voxel indexing 提前到网络入口，本质上是对整张计算图做**依赖分析 + 搬运**。类似技术可以用在 **LLM 推理的 graph compilation**（把所有层的 RoPE 索引、block table 构建、量化表查表一次性合并）、**Training 中的 optimizer state prefetch**、**MoE routing 的提前计算**。
5. **Hybrid dataflow 的思想在 attention / matmul 里值得复制**:长 context attention 有 streaming / materialized 混合策略，FlashAttention variants 之间其实也是「output-stationary vs weight-stationary」的取舍。Spira 把这个取舍下放到 kernel map 列粒度，相同思想可以下放到 attention 的 **per-head 甚至 per-token-block** 粒度。

**具体可操作的 future work 切入点**:

- **将 z-delta 思想移植到 block-sparse attention 的 mask 构建**:大模型的 sparse attention 也需要建「哪个 query 能访问哪些 key」的映射表，能否通过 token position 的有序性省掉 pre-processing?
- **MoE routing 的 packed index**:token-expert 分配表目前都是 int32，能否按 expert 数量上界做 bit-pack 后加速 all-to-all 和 histogram?
- **跨会议组合**:Spira 的 z-delta 算法 + EuroSys'24 的 Minuet、OSDI'25 上的一些 LLM serving 工作，在「低延迟推理 + 稀疏 indexing」这条线上有明确的研究链可以追。
- **sparse DL compiler 集成**:文中 Section 7 明确提到 Spira 的 idea 可以和 SparseTIR、TACO、Finch 协同，Spira 是手写 kernel + runtime，下一步把 z-delta / packed-native 抽象成 IR-level 的 lowering rule 是很自然的延伸。

## 8. 总结

Spira 是第一个系统利用 voxel 坐标「整数、有界、邻域连续」三大结构性质的 GPU SpC 引擎。它用 z-delta search 把 kernel map 构建的 pre-processing 开销完全消除，用 packed-native indexing 把坐标访问成本降到 1/3，用阈值可调的 hybrid dataflow 把 output-/weight-stationary 的取舍下放到 weight-offset 粒度，用 network-wide concurrent indexing 把原本串行的 indexing 提前并行到网络入口。在 3 个点云网络、3 个数据集、6 张 GPU 上取得端到端平均 1.68× / 最高 3.04× 的加速，显著超越 TorchSparse++ 和 Minuet 两大 SoTA。适用场景是自动驾驶、AR/VR、机器人等点云推理为瓶颈的部署；主要局限是缺少下游精度验证、network-wide materialization 在极端 kernel/batch 配置下的显存压力，以及 dataflow 阈值依赖 per-dataset 调参这一工程假设。对 MLSys 社区的启发则远超点云本身 —— 其「从数据结构性质反推 kernel 设计」的方法论，可以启发 LLM serving、MoE routing、sparse attention 等领域的下一轮 indexing 优化。
