# Automated Algorithm Design for Auto-Tuning Optimizers

## 一、背景

自动性能调优（auto-tuning）是高性能计算（HPC）中的关键技术，通过系统性地探索线程布局、数据布局、循环变换等大规模参数搜索空间，使应用在特定硬件架构上达到最优性能。传统的 auto-tuning 框架依赖 Simulated Annealing、Genetic Algorithm、Particle Swarm Optimization 等经典优化算法，但这些算法需要仔细的超参调节，且并非针对 auto-tuning 特有的大规模、不规则、离散搜索空间而设计。

与此同时，大语言模型（LLM）在代码生成和算法合成领域展现出强大能力。FunSearch、EoH、ReEvo、LLaMEA 等工作已证明 LLM 可以自动生成和迭代优化启发式算法。这自然引出一个问题：能否让 LLM 自动生成针对 auto-tuning 问题的优化算法？

---

## 二、要解决的问题

1. **算法设计依赖专家经验**：现有 auto-tuning 优化器（GA、SA、PSO 等）是人工设计的通用算法，无法自动适配 auto-tuning 搜索空间的特殊结构（大规模、离散、含约束、不规则）。
2. **超参调优成本高**：即使选定了优化算法，还需要花费大量时间（如论文中提到的 7 天）进行超参搜索才能获得好的性能。
3. **缺少问题特定的优化策略**：不同 auto-tuning 应用（天文信号处理、卷积、热模拟、矩阵乘法）的搜索空间结构差异显著，但现有方法无法针对特定问题自动设计优化策略。
4. **此前无人系统性研究 LLM 生成 auto-tuning 优化器**：虽然 LLM 在经典连续/组合优化问题上已有应用，但在 auto-tuning 领域尚属空白。

---

## 三、洞察与设计

**关键洞察**：auto-tuning 的搜索空间具有大规模、离散、含约束、不规则等共性结构特征，而 LLM 具备从问题描述和搜索空间信息中提取这些结构特征并据此生成定制化优化策略的能力——如果将 LLM 的代码生成能力与进化算法的选择机制结合，就可以自动发现比人工设计更优的优化器。

### 系统设计

系统由三个核心组件组成：

1. **Kernel Tuner**：Python 开源 auto-tuning 框架，支持 CUDA/HIP/OpenCL 等后端。负责构建搜索空间、编译执行 kernel、测量性能。新增 `OptAlg` wrapper 以接入外部优化算法。

2. **LLaMEA**（Large Language Model Evolutionary Algorithm）：将 LLM 作为变异算子嵌入进化算法框架。LLM 仅生成优化算法代码，不接触 kernel 代码或执行过程，保证正确性和可复现性。

3. **闭环评估流程**：
   - 初始化 4 个 LLM 生成的候选优化器作为种群
   - 每个候选器在 Kernel Tuner 中评估，获得 performance score P
   - 高分算法被选择保留，低分被淘汰
   - LLM 通过 3 种变异 prompt（改进策略、生成新算法、简化算法）生成 12 个后代
   - 迭代直至预算耗尽

### Prompt 设计

- 向 LLM 提供任务描述、`OptAlg` 基类接口、`SearchSpace` 对象用法示例
- 可选地注入搜索空间特定信息（参数值域、约束条件）
- 生成失败时将 stack trace 反馈给 LLM 进行自我调试

### 评估方法论

采用社区标准的 autotuning methodology，定义 performance score P：
- 以随机搜索为 baseline，以全局最优为上界
- 在等距时间采样点上计算相对性能曲线
- 跨多个搜索空间取均值，同时捕捉搜索效率和最终质量

## 四、实现细节

- **LLM 选择**：使用 GPT o4-mini（成本效益最优）。也试过 Gemini 2.0 Flash，能生成合法算法但性能不如 o4-mini。
- **进化参数**：4 parents + 12 offspring per generation，共 100 次 LLM 调用/run，5 independent runs/kernel/method，总计 4000 次 LLM 调用。
- **评估加速**：利用预穷举搜索空间模拟评估，单个优化器评估从数小时降低到秒/分钟级别。每个候选器最大 5 分钟 wall-clock time。
- **失败率**：约 25% 的生成优化器因代码无效、运行时错误或超时被丢弃。
- **Benchmark**：BAT benchmark suite 中的 4 个 GPU kernel（Dedispersion、2D Convolution、Hotspot、GEMM），在 6 种 GPU（AMD MI250X/W6600/W7800、Nvidia A100/A4000/A6000）上运行，产生 24 个搜索空间。训练/测试各 12 个搜索空间。
- **两个最佳算法**：
  - **HybridVNDX**（目标 Dedispersion）：结合 Variable Neighborhood Descent、动态邻域权重、k-NN 代理预筛选、精英重组、tabu 搜索和模拟退火
  - **AdaptiveTabuGreyWolf**（目标 GEMM）：小种群 Grey Wolf 变体，结合 leader-mixed proposal、shaking 探索、tabu list、模拟退火接受准则
- **共性特征**：两个最佳算法都将计算开销保持轻量，并充分利用 Kernel Tuner 的 neighbour API 进行架构无关的离散搜索。

## 五、实验结果

### 搜索空间信息的影响

| 目标应用 | 无额外信息 | 有额外信息 | 差异 |
|---|---|---|---|
| Convolution | 0.429 | 0.426 | -0.003 |
| Dedispersion | 0.383 | 0.515 | +0.132 |
| GEMM | 0.432 | 0.516 | +0.084 |
| Hotspot | 0.373 | 0.388 | +0.015 |
| **均值** | **0.404** | **0.463** | **+0.057 (+14.6%)** |

- 针对特定应用生成的算法相比非针对性算法平均提升 **30.7%**。

### 与人工设计算法对比

| 算法 | 类型 | 相对 LLM 最佳 |
|---|---|---|
| HybridVNDX (LLM) | LLM 生成 | 最佳 |
| AdaptiveTabuGreyWolf (LLM) | LLM 生成 | 次佳 |
| Kernel Tuner GA | 人工设计 + 7 天超参调优 | 低 0.126 |
| Kernel Tuner SA | 人工设计 + 7 天超参调优 | 低 0.282 |
| pyATF DE | 人工设计 | 低 0.274 |

- LLM 生成的优化器平均比人工设计算法性能高 **72.4%**。
- GA 仅在 Hotspot 上优于 LLM 生成算法，其他应用均被显著超越。
- LLM 生成算法在训练集外的 GPU 和应用上也展现良好泛化能力。

## 六、批判性分析

1. **Benchmark 规模有限**：仅 4 个 GPU kernel + 6 种 GPU = 24 个搜索空间。这些 kernel 均为经典 HPC benchmark（Dedispersion、Convolution、Hotspot、GEMM），缺少更复杂的实际应用（如深度学习算子、稀疏计算）。72.4% 的提升数字在更广泛的 workload 上是否成立存疑。

2. **基线公平性存疑**：对比的 GA 和 SA 虽然经过 7 天超参调优，但这两种算法本身就是较为基础的优化器。论文没有与 Bayesian Optimization（如 GPTune、HyperMapper）进行对比，理由是"设备目标和假设不同"，但这个排除理由不够充分——至少可以在相同搜索空间上运行 BO 方法作为参考。

3. **LLM 成本被低估**：论文报告了 token 数量但未给出美元成本。4000 次 o4-mini 调用的总成本、与 7 天超参调优的计算成本对比缺失。声称"成本可被快速摊销"但缺乏量化支撑。

4. **"72.4% 提升"的表述具有误导性**：performance score 是相对于随机搜索 baseline 的归一化指标，其绝对差异（如 0.126）对应多大的实际运行时间改善未做说明。读者难以判断这个提升在实际场景中是否有意义。

5. **泛化能力论证不够严格**：训练集和测试集使用相同的 4 个 kernel，只是 GPU 不同。真正的泛化应该是在未见过的 kernel 类型上测试。论文承认了这一点但将其留作 future work。

6. **生成算法的可解释性**：两个最佳算法本质上是 VND + SA + tabu search 和 Grey Wolf + SA + tabu 的组合，这些都是已知的经典优化原语。LLM 的"创新"更多是组合已有组件并调参，而非真正发现全新的优化策略。论文对此未做深入讨论。

7. **单一 LLM 依赖**：主要结果基于 o4-mini，Gemini 2.0 Flash 表现较差但未详细分析原因。不同 LLM 生成的算法差异有多大、稳定性如何，缺乏系统性消融实验。

---

## 七、AI Infra / MLSys 视角

1. **对 AI 编译器 auto-tuning 的启发**：现代 AI 编译器（TVM、Triton、XLA）同样面临大规模离散搜索空间的 auto-tuning 问题。本文的 LLM 生成优化器方法可以直接迁移到这些场景，替代或补充现有的 cost model + search 策略。

2. **Kernel Tuner 的 `SearchSpace` 抽象值得借鉴**：其提供的 `generate initial population`、`get neighbours`、`repair invalid configuration` 三个 API 构成了一个简洁而通用的搜索空间接口，适合作为 LLM 生成优化器的标准化交互层。

3. **可操作的研究方向**：
   - 将此方法应用于深度学习算子（Attention、Convolution、GEMM 的各种变体）的 auto-tuning，验证在更复杂搜索空间上的效果
   - 探索在线生成优化器：在 tuning 过程中根据中间结果动态调整优化策略，而非离线预生成
   - 结合 hardware performance counter 数据作为额外上下文注入 LLM prompt，生成更具硬件感知能力的优化器

4. **潜在局限**：AI Infra 场景下搜索空间往往比本文的 benchmark 大 1-2 个数量级（如 TVM 的搜索空间可达 10^10+），LLM 生成的优化器能否在这种规模下保持优势需要验证。

---

## 八、总结

本文首次系统性地将 LLM 驱动的自动算法设计引入 auto-tuning 领域，通过 LLaMEA + Kernel Tuner 的闭环框架自动生成优化算法。实验表明 LLM 生成的优化器在 4 个 GPU kernel × 6 种 GPU 的 benchmark 上平均比人工设计算法提升 72.4%，且注入搜索空间信息可额外带来 14.6% 的提升。主要局限在于 benchmark 规模较小、基线选择保守、泛化能力验证不足。核心贡献在于验证了"让 LLM 自动设计 auto-tuning 优化器"这一范式的可行性，为 HPC 和 AI 系统中的自动化调优开辟了新方向。
