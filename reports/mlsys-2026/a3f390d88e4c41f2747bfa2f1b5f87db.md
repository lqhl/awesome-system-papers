# Automated Algorithm Design for Auto-Tuning Optimizers

**作者**：Floris-Jan Willemsen, Niki van Stein, Ben van Werkhoven
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[a3f390d88e4c41f2747bfa2f1b5f87db.pdf]]

---

## 1. 背景

自动性能调优(auto-tuning)是高性能计算(HPC)与 AI 工作负载中的关键技术。对于同一份算法,往往有成千上万种功能等价但性能差异巨大的程序变体(thread layout、data layout、loop transformation、tile size、shared memory 使用策略等),需要根据具体硬件架构和输入规模选出最佳配置。代表性框架包括 ATLAS (线性代数)、FFTW (FFT)、OpenTuner、CLTune、Kernel Tuner 等。

核心困难在于搜索空间:

- **规模巨大**:如本文实验中 Hotspot 的 Cartesian 搜索空间超过 2200 万,GEMM 约 66 万
- **不连续/非凸/不规则**:大量约束使有效配置稀疏,例如 Hotspot 约束后仅剩 35 万
- **评估昂贵**:每个配置都要编译 + 执行 + 测量
- **噪声大**:GPU 上的执行时间有显著方差

传统方法依赖 Simulated Annealing (SA)、Genetic Algorithm (GA)、Particle Swarm Optimization (PSO) 等元启发式算法,但这些算法并非为 auto-tuning 场景量身定做,超参数选择敏感,在不同搜索空间上的性能表现不稳定。

与此同时,LLM 在代码生成、算法合成方向能力迅速提升,FunSearch、EoH、ReEvo、LLaMEA 等工作展示了用 LLM 作为「算法生成引擎」+ 进化算法作为选择机制,可以合成有竞争力的优化算法。但这类自动算法设计在 auto-tuning 领域尚未被研究。

---

## 2. 要解决的问题

现有 auto-tuning 优化算法的痛点:

1. **算法与搜索空间不匹配**:SA/GA/PSO 等通用元启发式,对 auto-tuning 搜索空间的离散、不规则、约束密集等特点不敏感,浪费大量评估预算在无效配置上。
2. **超参数依赖重**:即便同一个 GA,在不同 kernel/GPU 上需要不同的种群规模、变异率才能出好结果;Willemsen et al. 2025b 用 7 天做超参数优化才勉强让 GA/SA 稳定。
3. **设计工程成本高**:人工设计针对 auto-tuning 特化的新算法需要领域专家,周期长,且难以跟上硬件与应用的演化。

研究问题:**能否让 LLM 自动生成针对 auto-tuning 特化的优化算法,性能匹配甚至超越人工设计的 SOTA?额外的搜索空间信息能否显著提升生成算法质量?**

---

## 3. 洞察与设计

**关键洞察**:

1. **LLM 提出、进化算法筛选**的闭环能把 LLM 的「创造性噪声」转化为高质量优化器——即使 LLM 生成的算法一部分报错、一部分平庸,进化选择能保证只有高分候选存活,所以 LLM 不需要每次都正确。
2. **Auto-tuning 问题具备共性结构**,一个针对某 kernel 生成的优化器往往能泛化到其他 kernel 与硬件,因为搜索空间的「离散、约束密集、评估昂贵」特征是共通的。
3. **把搜索空间特征(参数可选值、约束)放进 prompt** 能让 LLM 合成出更特化的优化策略——这部分信息通常是算法开发者设计元启发式时会内化吸收、却从未被显式编码进传统优化器的。
4. **评估驱动**优于代码正确性检查:生成算法只要能跑,Kernel Tuner 的标准化 performance score 会给出客观分数,低质量算法自然被淘汰,无需人工审查代码。

**系统设计**:

- **Kernel Tuner**(目标框架):开源 GPU kernel 自动调优框架,支持 CUDA/HIP/OpenCL/OpenACC。本文给它加了 `OptAlg` wrapper 接口,允许外部注入任意优化算法。
- **LLaMEA**(算法生成器):Large Language Model Evolutionary Algorithm。用进化算法作为 meta-strategy:
  - 种群规模:4 parents + 12 offspring per generation
  - 精英策略保留高分父代
  - 多种 LLM 驱动的变异 prompt(探索 vs 利用)
  - 遇到 stack trace 错误自动回灌给 LLM 做 self-debug
- **性能打分 P**:基于 Willemsen et al. 2024 的社区标准方法,定义为 `(S_baseline(t) - F(t)) / (S_baseline(t) - S_opt)`。0 表示等同 random search baseline,1 表示立即找到最优解。多个搜索空间取均值聚合。
- **两种 prompt 模式对比**:
  - 基础版:只给 auto-tuning 任务描述 + Kernel Tuner OptAlg 接口说明
  - 增强版:额外注入目标应用的可调参数值集与约束

整个过程分生成阶段(4 parents × 12 offspring × 若干 generation,使用训练集 12 个搜索空间)和评估阶段(测试集 12 个未见过的搜索空间)。生成成本一次性付出,之后反复复用。

## 4. 实现细节

**LLaMEA 闭环**:
- 每次 generation:LLM 在给定 prompt 下产出 16 个候选优化器的 Python 代码
- 每个候选在 Kernel Tuner 内以 pre-exhaustively explored search spaces 模拟执行(避免实际编译 kernel),单个候选墙钟时间上限 5 分钟,超时即丢弃
- 观察到的失败率约 25%(invalid code / runtime error / timeout)
- 每个 kernel × 每种 prompt 策略跑 5 次独立 run(降低随机性),取最佳优化器

**成本数据**:
- 总 LLM calls:100 per run × 5 runs × 4 kernels × 2 prompt 模式 = 4000 次
- LLM:GPT o4-mini(与 gemini-2.0-flash 对比后选择,后者生成的算法质量偏低)
- 每个优化器的 token 总量:Fig 5 显示平均几十万到百万 token 级(整个 5-run 过程累计)

**关键架构改动**:
- Kernel Tuner 新增 `OptAlg` 基类,允许任意外部优化算法接入
- 暴露 `SearchSpace` 对象给生成的算法,提供:生成初始种群、检索某配置的邻居、修复违反约束的无效配置三个核心方法

**生成出的两个最佳算法**(都是 extra info 模式):

1. **HybridVNDX**(target Dedispersion):
   - Variable Neighborhood Descent (VND) 为骨架
   - 动态邻域权重(roulette wheel)
   - k-NN 代理模型做候选预筛选(Hamming distance)
   - Tabu list(size=300)避免重复
   - 精英重组(elite size=5)
   - Simulated annealing 接受准则(T0=1.0, cooling=0.995)
   - 100 步无提升则重启

2. **AdaptiveTabuGreyWolf**(target GEMM):
   - Grey Wolf 风格的 leader 机制,维护种群(p=8),每步以 3 个 best 作为 α, β, δ
   - 对非 leader 个体,每维独立从 {α, β, δ, self} 中采样
   - "Shaking" 扰动:s=0.2 概率做邻域步进或随机跳跃
   - Tabu list 长度 L=3p,SA 接受准则带温度衰减 + 停滞时轻度 reheating
   - 停滞 τ=80 步后重启 worst ρ=30% 个体

两个算法有共同特征:(a) 把 evaluation time 当主成本,控制逻辑轻量;(b) 用 SearchSpace 的邻居 API 做架构无关的移动,同时满足约束。

## 5. 实验结果

**实验平台**:
- 6 块 GPU:AMD MI250X / AMD W6600 / AMD W7800 / Nvidia A100 / Nvidia A4000 / Nvidia A6000
- 训练集(生成阶段):MI250X + A100 + A4000 × 4 kernel = 12 搜索空间
- 测试集(评估阶段):W6600 + W7800 + A6000 × 4 kernel = 12 搜索空间
- 4 个 kernel:Dedispersion、Convolution、Hotspot、GEMM(BAT benchmark suite)
- 每种算法在每个搜索空间运行 100 次降噪
- 优化预算:baseline 到达 median-optimum 距离 95% 处所需时间

**额外信息的影响**(表 2):

| 目标应用 | 无 extra info | 有 extra info | 差值 |
|---|---|---|---|
| Convolution | 0.429 | 0.426 | -0.003 |
| Dedispersion | 0.383 | 0.515 | **+0.132** |
| GEMM | 0.432 | 0.516 | **+0.084** |
| Hotspot | 0.373 | 0.388 | +0.015 |
| 平均 | 0.404 | 0.463 | +0.057 (+14.6%) |

**目标对齐的影响**(表 3):相比不针对该应用生成的「非目标」算法,目标生成平均提升 30.7%。其中 Dedispersion + extra info 提升 +0.219(+46%),GEMM + extra info 提升 +0.251(+47%),但 Hotspot 两种版本都劣于非目标平均(−0.045 / −0.134)。

**与人工设计算法对比**(Fig 8-9):

| 算法 | 类别 | 聚合 P |
|---|---|---|
| HybridVNDX (生成,target Dedispersion) | LLM | 最佳 |
| AdaptiveTabuGreyWolf (生成,target GEMM) | LLM | 次佳 |
| Kernel Tuner GA(经 7 天超参数调优) | 人工 | 落后 0.126 |
| Kernel Tuner SA(经 7 天超参数调优) | 人工 | 落后 0.282 |
| pyATF DE | 人工 | 落后 0.274 |

**平均比人工设计算法好 72.4%**。唯一例外是 Hotspot 应用上 GA 仍然占优。

## 6. 批判性分析

**1. "72.4% 比 human-designed 更好"口径存在选择偏差**。表 3 显示 Hotspot 目标生成的两个版本(-0.045、-0.134)都输给了非目标平均,说明生成器并非在所有应用上都稳定胜出。但 Section 4.4 的比较只拿出「两个最佳生成算法」(Dedispersion-target、GEMM-target)去跟 GA/SA/DE 比,把没打过 baseline 的 Hotspot-target 和 Convolution-target 版本排除在外。公平对比应该是用所有 8 个生成算法(或随机一个目标)的平均 P 与 GA/SA 比较。

**2. "训练/测试集"划分虚弱**。虽然 kernel 相同但 GPU 换了(训练 A100+A4000+MI250X,测试 A6000+W6600+W7800),但搜索空间实际上由 kernel 参数决定,不同 GPU 上搜索空间大小和约束结构高度相似。真正的 OOD 评估应该换 kernel(加入未见过的 FFT、SpMV 等),这样才能证明 LLM 合成的算法不是把训练 kernel 的结构硬编码进去。

**3. 生成成本被轻描淡写**。4000 次 LLM call(o4-mini),若按公开 API 定价粗估也是数百美元量级。而 GA 的超参数优化只需要 7 天一次性工作。论文以"生成成本一次性摊销"辩护,但对比时并未扣除这部分成本,也没报告 LLM 调用的碳/能耗成本。

**4. 只用 o4-mini,结论对模型选择的敏感性未系统评估**。论文只提了"gemini-2.0-flash 不如 o4-mini",但没给出数字。若换成 GPT-4o、Claude Opus、Gemini 2.5 Pro,生成算法的分布会如何变化?论文承认这是 future work,但这意味着 72.4% 这个具体数字很大程度上是 o4-mini 的能力上限,不是"LLM + LLaMEA"范式的能力上限。

**5. HybridVNDX 和 AdaptiveTabuGreyWolf 虽然名字不同但结构相似**——论文自己在 4.3.2 末尾承认 "various elements are similar to the first (e.g., the tabu list and simulated annealing approach)"。这暗示 LLM 在生成阶段很可能收敛到单一模式(VND + SA + tabu list),多样性受限。如果真正新颖的算法少,那 LLM 的"创造力"故事就被削弱。

**6. 搜索空间的"pre-exhaustively explored"前提很强**。Section 4.1.2 说优化器评估靠查 cached 结果而不是实际执行 kernel,这让生成阶段可行,但也意味着这个框架目前只能在已经穷举过的搜索空间上生成算法。真实的 auto-tuning 场景恰恰是因为穷举不可行才需要优化器——存在「为求数据去穷举,为穷举却先需要优化器」的循环问题,论文未讨论如何打破。

**7. 基线算法的超参数调优是否公平**。GA/SA 的超参数是在训练集 12 个搜索空间上调的 7 天,但生成算法的进化选择也是看训练集性能。如果让 GA/SA 用更长时间、更大搜索空间调超参,差距会如何缩小?论文没给 sensitivity analysis。

## 7. AI Infra / MLSys 视角

这篇论文虽然针对 GPU kernel auto-tuning,但对 AI Infra 有很强启发价值:

**1. LLM-as-Optimizer-Synthesizer 范式的可迁移性**:同样的闭环(LLM 生成 + 进化选择 + 评估反馈)可以直接迁移到以下 MLSys 场景:
- **分布式训练的 schedule/placement 策略**:让 LLM 生成 pipeline parallelism 调度算法,用 Megatron/FSDP 作为评估环境
- **LLM 推理的 batch 调度策略**:vLLM/SGLang 内部的 continuous batching / prefill-decode disaggregation / chunked prefill 等策略的超参数组合,本质上也是 auto-tuning
- **Tensor parallelism 切分策略搜索**:Alpa、AutoDist 等用 ILP/DP 搜索,改为 LLM 生成启发式或许能在更大模型上仍保持快速
- **MoE 专家路由策略**:不同 expert assignment 算法的选择

**2. "搜索空间信息注入 prompt"的启发**:对 ML 编译器(TVM、XLA、Hidet)的 auto-scheduler,目前主流做法是 Ansor 式的 learned cost model;本文暗示把 search space 的结构特征(例如参数可选值分布、约束图结构)直接放进 prompt,让 LLM 合成特化 cost model / search policy 可能是新路径。TVM 的 MetaSchedule、Hidet 的 autotune 可以试试这个方向。

**3. 可复用的评估方法论**:论文用的 performance score P(相对 random search baseline 的归一化积分)是个不错的 cross-space 对比框架。在评估 LLM serving 系统的不同调度策略时也可以借鉴——不同 workload 下固定 baseline,用 P 做聚合比较,避免被某一个高方差 workload 主导。

**4. Future work 的切入点**:
- 把这个框架扩展到 LLM 推理引擎的调度器自动合成:搜索空间 = (batch size, chunk size, prefill/decode ratio, KV cache eviction policy) 等,用 vLLM/SGLang 的真实 serving 数据作为训练集
- 跨 LLM 对比(GPT-5 vs Claude Opus 4.x vs Gemini 2.5 Pro vs Qwen-coder)做模型选择的 sensitivity 研究,给出 LLM 能力与生成算法质量的 scaling law
- 把 LLaMEA 换成 reasoning model(o3/Claude thinking),看推理能力对算法合成质量的增益
- 解决"穷举依赖"问题:在非 pre-explored 搜索空间上做 online LLaMEA,用 surrogate model 近似 cost 来支撑进化
- 把 SakanaAI 的 ADAS(Automated Design of Agentic Systems)、DeepMind 的 AlphaEvolve 思路整合进来,生成不仅是优化器、还是整个 auto-tuning pipeline 的 self-improving 系统

**5. 对具体研究者的启发**:写一个 "auto-tuner for vLLM scheduling" 的小 paper 可能门槛不高——复用 LLaMEA 开源框架、把 vLLM 的 continuous batching 调度器作为 OptAlg 接口、用 LMArena/ShareGPT trace 作为评估,完全可做。

## 8. 总结

本文提出将 LLM 与进化算法结合(LLaMEA)的闭环自动生成 auto-tuning 场景专用的优化算法,集成到 Kernel Tuner 框架并在 4 个 kernel × 6 GPU = 24 个真实搜索空间上评估。核心贡献:(a) 首个把 LLM 驱动的算法合成应用到 auto-tuning 的闭环框架;(b) 证明在 prompt 中加入搜索空间特征能带来 14.6% 平均性能提升,针对目标应用能带来 30.7% 提升;(c) 生成的最佳两个算法 HybridVNDX 与 AdaptiveTabuGreyWolf 比经过 7 天超参数调优的 GA/SA/DE 平均好 72.4%,已集成到 Kernel Tuner 开源代码中。适用于 GPU kernel 调优、有明确搜索空间与评估度量的黑箱优化问题。主要局限:仅测试 o4-mini 单一 LLM,Hotspot 应用上生成器不稳定,训练/测试集虽然换了 GPU 但 kernel 相同,强 OOD 泛化性未验证,且评估依赖 pre-exhaustively explored 搜索空间,与真实 auto-tuning 场景存在一定差距。
