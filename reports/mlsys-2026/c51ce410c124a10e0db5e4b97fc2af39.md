# RDMA Point-to-Point Communication for LLM Systems

**链接**:https://proceedings.mlsys.org/paper_files/paper/2026

## 1. 背景

新一代 LLM 部署形态正在从单一的训练 / 推理集群向异构、动态、解耦的架构演化。三类典型工作负载已成为主流:

- **Disaggregated Inference**(Splitwise、DistServe、Mooncake):将 prefill 和 decode 拆到不同节点,需要在两组 GPU 之间高带宽传输 KV cache。
- **Mixture-of-Experts (MoE)**:每个 token 需要被路由到少量 expert,触发 all-to-all 风格的稀疏点对点 dispatch / combine。
- **Asynchronous RL Fine-Tuning**:训练集群与推理集群分离,每完成一个训练 step 都要把新权重推送到 inference 节点。

在网络层,主流加速器集群基于 RDMA 提供 400 Gbps 量级带宽,但硬件碎片化严重:NVIDIA ConnectX 系列基于传统 Reliable Connection (RC),保证有序交付;AWS EFA 使用专有的 SRD 协议,无序交付;Alibaba eRDMA、Google Falcon 也各有差异。现有 LLM 框架几乎只用 NCCL / `torch.distributed` 这类 collective 抽象,SEND / RECV 性能不足,而需要点对点能力的方案普遍存在 vendor lock-in:DeepEP 必须依赖 ConnectX 才能用 IBGDA,NVSHMEM 在 EFA 上性能严重退化,Mooncake 和 NIXL 要么不支持 EFA,要么仍是 preview 阶段。

---

## 2. 要解决的问题

LLM 系统对网络层的需求与 collective 抽象之间存在结构性错配:

1. **Collective 不适配新模式**:固定 membership 阻碍 disaggregated inference 的弹性扩缩;同步初始化阻塞独立 peer 间通信;操作有序性需要全局协调,即使是稀疏 P2P 也被迫付出 dense 同步代价;统一 buffer size 对稀疏 MoE 浪费严重。
2. **现有 RDMA 库 vendor 锁定**:DeepEP 绑死 ConnectX + IBGDA;NVSHMEM 在 EFA 上不可用;Mooncake / NIXL 缺乏 EFA 支持。在云上跨厂商部署 LLM 时,没有一套高性能的可移植 P2P 抽象。
3. **多 NIC 透明聚合**:在 AWS p5 上,要达到 400 Gbps 必须聚合 4 张 100 Gbps EFA,管理多 NIC 的复杂度被推给上层。
4. **Completion 通知与无序交付的兼容**:RC 依靠 in-order 交付来推断完成,但 EFA SRD 是无序的,需要一种不依赖顺序的完成通知机制。

## 3. 洞察与设计

**关键洞察**:ConnectX RC 与 EFA SRD 之间存在一个关键的功能交集 —— 两者都能提供 *reliable but unordered* 的交付语义(RC 可以选择忽略其有序保证,SRD 本身就是无序的)。只要把 LLM P2P 通信库**主动放弃顺序保证**,就能在异构 RDMA 硬件上构造出统一的 WRITE / WRITEIMM 抽象,并通过一个独立的 IMMCOUNTER 原语(基于 immediate value 的累加计数)替代依赖顺序的完成通知。这是整个 TransferEngine 设计成立的前提。

基于这个洞察,论文提出 **TransferEngine**,具备如下设计:

- **统一最小 API**:`reg_mr`(内存注册)、`submit_send/recvs`(两侧 SEND/RECV)、`submit_single_write` / `submit_paged_writes`(单次或分页 WRITE,可携带 32-bit immediate)、`submit_scatter` / `submit_barrier`(对预注册 PeerGroup 的低延迟 scatter)、`alloc_uvm_watcher`(CPU 监听 GPU 进度)、`expect_imm_count`(基于 IMMCOUNTER 的回调注册)。所有操作**无任何顺序保证**,完成依靠 IMMCOUNTER 显式声明。
- **架构(Figure 1)**:每个 GPU 配一个 worker 线程,绑定到对应 NUMA 节点;worker 管理一个 DOMAINGROUP,内部由若干 DOMAIN 组成,每个 DOMAIN 对应一张 NIC;额外有 IMMCOUNTER、Callback Worker、UVM polling 线程协作。多 NIC 在 DOMAINGROUP 内透明 sharding / load-balance,对上层只暴露单一 NetAddr。
- **IMMCOUNTER**:每个 immediate value 维护一个计数器,sender 完成 WRITEIMM 或 receiver 收到 WRITEIMM payload 都会触发 +1。通知方式可以是 GPU 端 GDRCopy 同步、CPU polling 或独立线程上的回调 —— 不依赖任何顺序假设。
- **三个生产应用**(Sections 4–6)分别展示这套抽象的覆盖面:
  - KvCache transfer:逐层 paged write + UVM watcher 驱动 + `expect_imm_count` 完成检测;
  - RL weight update:从 256 个训练 GPU 直接 P2P WRITE 到 128 个推理 GPU,跑满全集群带宽;
  - MoE dispatch / combine:host proxy 模式调度 scatter,在 ConnectX-7 上超过 DeepEP,在 EFA 上首次给出可用实现。

## 4. 实现细节

**TransferEngine 本体**

- 用 Rust 实现,核心是 lock-free queue + per-domain worker thread。worker 线程绑定到对应 NIC 所在 NUMA core,数据结构在 pin 之后才分配,避免跨 NUMA 访存。
- 单 worker 最多管 4 个 DOMAIN (NIC),独立线程通过 GDRCopy polling GPU 更新 UVM watcher。
- worker 主循环优先提交新请求(降低 first-write latency),其次做 pending request 进度推进,最后 poll completion queue 以更新 IMMCOUNTER 并触发回调,所有回调集中在一条专用 callback 线程上执行。

**硬件特化**

- *AWS EFA*:基于 libfabric,每张 NIC 一个 fabric domain。EFA 不接受免 immediate-only zero-sized write,因此为所有 transfer 强制注入有效 descriptor。批量 transfer 与 PeerGroup 操作启用 work request templating(预填充公共字段)。
- *NVIDIA ConnectX-7*:基于 libibverbs。每个 peer 用 UD QP 做 RC handshake,然后建立 *两个 RC QP*:一个专门跑 SEND/RECV,另一个专门跑 WRITE/WRITEIMM —— 因为 RECV 与 WRITEIMM 都按 work request posting 顺序消耗 receiver 的 WR,共享一个 QP 会互相阻塞。除 WR templating 外还使用 WR chaining(`next` 指针把至多 4 个 WR 串起来,降低 doorbell ring),并打开 `IBV_ACCESS_RELAXED_ORDERING` 允许 NIC ↔ GPU 之间乱序 PCIe 事务降低延迟。

**KvCache Transfer (Section 4)**

- decoder 提前分配 KV pages,通过 `submit_send` 把 page index 列表发给 prefiller。
- prefiller 在 chunked prefill 中,每完成一层 attention output projection,就在 CUDA Graph 内 increment UVM watcher;TransferEngine 检测到变化即触发该层 paged write。
- 处理 MLA / GQA 不同 sharding:MLA 下随机配对 prefiller 和 decoder rank 来均衡复制流量;GQA 下用 page-wise offset / stride 切片。KV layout 上把 head 放在 page 之前,保证连续 head 的 page 在内存中相邻,以 maximize 单次 write 的 size。
- 完成检测靠 decoder 端 `expect_imm_count`,prefiller 不再发显式完成消息。
- 取消逻辑:decoder 触发 cancel 后必须等 prefiller 显式确认才能复用 KV pages(防止迟到的 RDMA write 改写复用过的 page)。心跳消息用于检测 transport-level failure。

**RL Weight Update (Section 5)**

- 控制脚本启动时 gather 所有 train + inference GPU 的参数 metadata(name / shape / dtype / DTensor sharding),计算静态权重传输 schedule(谁 → 谁、什么顺序),broadcast 到所有 train GPU。
- 每个 train step 后,由 controller 触发,所有 train GPU 用 one-sided WRITE 直接打到对应 inference GPU 的显存,inference 端**完全无感**。
- 每个 parameter tensor 拆成 4 阶段 pipeline(Figure 5):H2D memcpy(若 FSDP offload 到 CPU)、`full_tensor()` + projection fusion + 量化、RDMA WRITE、跨 MeshGroup 的 GLOO barrier。`full_tensor()` 调用会临时占额外显存,通过可配水位线限制 in-flight task 数防 OOM。

**MoE Dispatch/Combine (Section 6)**

- 拆成 split kernels:sender 准备 send buffer,receiver 把数据 shuffle 到下游 GEMM 友好的 layout,kernel runtime 短到允许彼此 overlap 与 micro-batching。
- host proxy 用 GDRCopy poll GPU 进度,buffer 就绪即调用 TransferEngine 发起 transfer。
- 双轮发送策略:先用 routing info 之外的小 *private buffer* 投机 dispatch 一小撮 token,隐藏路由信息交换的延迟;路由信息抵达后再用一个 *contiguous shared buffer* 发剩余 token。每个 inter-node peer 上,dispatch 至多 2 个 WRITE,combine 1 个 WRITE。
- 节点内通过 NVLink 推送数据,双 buffer 配合 release-acquire flag 同步。kernel 的 write 顺序经过精心排布:先 signal host(让 RDMA 尽早起跑),再 grid barrier,再发 NVLink writes,以最短化到 first RDMA transfer 的关键路径。
- combine 复用 dispatch 阶段的 buffer,因此需要 NVLink 与 RDMA 双 barrier 才能覆盖写入。

## 5. 实验结果

平台:每节点 8× NVIDIA H200,通过 NVLink 互连,每 GPU 配一张 400 Gbps ConnectX-7 *或* 双 200 Gbps EFA,挂在双路 Intel Sapphire Rapids 上。

### 5.1 P2P 通信带宽 (Figure 8 + Table 2)

| 操作 | 消息大小 | EFA (TransferEngine) | ConnectX-7 (TransferEngine) |
|---|---|---|---|
| Single WRITE | 256 KiB | 54 Gbps | 116 Gbps |
| Single WRITE | 32 MiB | 336 Gbps | 378 Gbps |
| Paged WRITE | 64 KiB | 364 Gbps (0.69M op/s) | 370 Gbps (0.71M op/s) |
| Paged WRITE | 1 KiB | 17 Gbps (2.11M op/s) | 91 Gbps (11.10M op/s) |

- 与 NIXL v0.6.1 对比,TransferEngine 在 single WRITE 场景下整体略胜;paged WRITE 下 NIXL 在小 message size 性能急剧下降(< 64 KiB 几乎为 0),TransferEngine 在 1 KiB 起就已稳定爬升。
- Single WRITE 要 16 MiB 才能跑满,paged WRITE 上 32 KiB 就饱和 —— 这正是 KV cache page size 的甜区。

### 5.2 RL 权重更新

- 在 Kimi-K2 (1T)、DeepSeek V3 (671B)、Qwen3 (235B) 上,从 256 train GPU (bf16) → 128 inference GPU (fp8) 的全权重广播只需 **1.3 秒**,相比现有 RL 框架(NeMo-RL、slime 等)**快 100×+**。

### 5.3 MoE Decode Latency (Figure 11)

EP=64(代表 DeepSeek-V3 setting,7168×fp8 + 56×fp32 scale,batch 128,top-8):

| 实现 | Dispatch (µs) | Combine (µs) |
|---|---|---|
| Ours-EFA-SRD | 286 | 406 |
| Ours-CX7-RC | **190** | **311** |
| DeepEP-CX7-GDA | 180 | 327 |
| pplx-CX7-GDA | 317 | 530 |
| pplx-CX7-RC (NVSHMEM 通过 IBRC) | 1669 | 1058 |

- Ours-CX7-RC 在 EP16/EP32 下 dispatch / combine 双线优于 DeepEP(尽管 DeepEP 用 IBGDA,本工作只用 host proxy);EP=64 时 dispatch 受 56 个 inter-node peer 的 enqueue 开销影响略落后,但 combine 仍领先。
- EFA 端首次给出可用 latency,落后 ConnectX-7 仅约 30%(虽然 256KiB 单 NIC 带宽不到一半)。

### 5.4 Send/Receive 拆分(EP=64)与 private buffer 大小

- dispatch send / combine 全面优于 DeepEP(因为只做 memory copy);combine receive 也快(本地 accumulation 路径更优)。两者总耗时不到 transfer 时间的 15%,proxy 调度开销隐藏在 send kernel 内部。
- private buffer:intra-node 至少 32 token 才能掩盖 route 交换;inter-node ConnectX-7 24 token 即可,EFA 因 route 传得更慢需要 ≥ 32。

### 5.5 MoE Prefill (Figure 12)

- 在大 chunk(4096 token)下,DeepEP 通过 sender-side partial sum + 仅传一份 token 复制(NVLink 内做 fan-out)取得更低延迟,本工作未做这层优化,因此在 prefill 场景落后。

## 6. 批判性分析

1. **RC 与 SRD 的"共同语言"被简化叙述**:把 ConnectX RC 当作"可以忽略顺序"使用,确实是对的;但 RC 仍然是 connection-oriented(N² 量级 QP 扩展开销),与 SRD 的 connectionless 性质有量级差异。论文用 "Ours" 一列在 Table 1 同时占据两栏勾选的方式弱化了这一点 —— 真实部署在大规模(64+ rank)集群上,QP 数膨胀很可能是 ConnectX 路径的下一道瓶颈,论文没给数据。

2. **MoE 评测的"超越 DeepEP"前提需要小心解读**:Figure 11 显示在 EP=8(intra-node)Ours 比 DeepEP 慢约 2µs(53 vs 43);EP=64 dispatch 也已被 DeepEP 反超(286/190 vs 180)。论文挑选 EP16/EP32 作为"state-of-the-art"的主战场,但实际生产部署常用的 EP=64 / EP=128 这一段优势已经很微弱甚至消失。摘要里的措辞("exceeding DeepEP decode latency on ConnectX-7")略有 best-case 选取嫌疑。

3. **Prefill 落后被一笔带过**:论文承认 prefill 落后是因为没做 "single-copy + NVLink fan-out" 优化,但这正是 DeepEP 的 *主要工程贡献*。在生产 LLM 服务里 prefill phase 的 throughput 往往直接决定 batch size 上限,把这一项让出去意味着 TransferEngine 要么只能跑 decode-only,要么在 prefill-heavy 场景下不得不退回 DeepEP。论文没量化这种切换成本,也没讨论是否能在 TransferEngine 之上 retrofit 类似优化。

4. **RL 权重更新对比基线偏弱**:1.3 秒的对比对象是 NeMo-RL 早期版本和 slime 的 blog post,而非经过严格调优的 collective baseline(例如已有 hierarchical broadcast + NVLink-aware 的 NCCL 优化)。"100×" 的 speedup 多半来自把 collective 路径上的 single Rank0 NIC 瓶颈消除,这其实是任何 P2P 实现都能拿到的红利,不一定是 TransferEngine 独有的贡献。

5. **可移植性的覆盖面有限**:论文标榜 portable,但实测只跑过 ConnectX-7 与 EFA。Alibaba eRDMA、Google Falcon、新一代 ConnectX-8 / BlueField 等都没有数据,后续是否需要再加一层硬件特化(像 EFA / CX7 各写了一套 DOMAIN backend)是未明确回答的开放问题。

6. **Failure handling 一笔带过**:论文 Section 4 末尾承认 "complexity lies in errors and cancellation",但实际只描述了心跳 + 取消令牌的概念,没有故障注入测试、没有量化 cancellation latency、也没说 DOMAIN 内某 NIC 失效时如何 failover。生产 trillion-param 部署里这恰恰是稳定性的核心。

7. **Rust 实现选择没量化收益**:虽然合理(避免 GIL、NUMA pinning 友好),但论文没给与 C++ 等价实现的对比数据,无法判断 Rust 自身带来的 zero-cost abstraction 是否有真实差距。

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 研究方向极具启发,几个值得跟进的延伸方向:

1. **"放弃顺序保证"作为可移植性原语**:这是一种漂亮的"求最大公约数"思路 —— 与其在每种硬件上实现各自的强同步,不如把上层应用强制写成对乱序友好的形式,把通知逻辑收缩到一个 IMMCOUNTER。这一思路可以推广到 inter-DC RDMA / RoCEv2、甚至跨云通信(unreliable underlay + reliable overlay)。值得研究的问题是:**还有哪些 LLM 通信原语本质上不需要顺序保证?**(例如 expert parallel 的 all-to-all、speculative decoding 的 draft 传输、MoE 分级 routing。)

2. **Host-proxy MoE vs IBGDA**:本工作用 host proxy 在 ConnectX-7 上击败了 IBGDA 路径的 DeepEP(EP=16/32),挑战了"GPU-initiated 一定更快"的常识。原因是 bulk transfer + 较少 packet 反而胜过 per-token GPU-initiated send。这给 *MoE kernel 设计* 提供新视角:**减少 transfer 数量比降低 per-transfer latency 更重要**,可以延伸到对 NVSHMEM-style 抽象的重新审视。

3. **UVM watcher + GDRCopy 作为 GPU-CPU 同步原语**:把 CUDA Graph 中的 layer-by-layer 进度通过单字 UVM update + CPU polling 暴露出来,触发 RDMA 起跑,绕开了 stream callback 的高延迟。这套机制可以泛化到任何"训练/推理 中间态实时外发"场景:reasoning trace streaming、partial activation offload、跨节点 KV expansion 等。

4. **静态 schedule + one-sided WRITE 的 RL 权重同步**:思路简单但收益巨大。延伸方向:能否在 *训练侧也用 one-sided* 来做异步 weight averaging?能否把这套 schedule 编译成"通信 IR",像 GSPMD 那样自动从 sharding spec 推导?能否在 schedule 里直接加入 quantization step 让 WRITE 写出 fp8?

5. **多 NIC 透明聚合的 API 范式**:把 4 张 EFA 100Gbps 表示为单一 NetAddr,让上层完全无感,这是云上部署 LLM 的实际刚需。值得跟进的问题是:**异构 NIC 混合**(例如同一节点 2× EFA + 2× ConnectX 互联)能不能也透明 sharding?**更细粒度的 QoS**(KV 流 vs 权重流共享 NIC)如何在这套抽象下表达?

6. **小切入点**:沿着这套 API 上,可以做一个"基于 TransferEngine 的 disaggregated speculative decoding 框架" —— draft 模型在 prefill 集群跑,verify 在 decode 集群跑,中间态(候选 token + logit)以小块 P2P 传输,正好契合 IMMCOUNTER + paged write 的特性,且无任何现成方案。

---

## 8. 总结

TransferEngine 通过识别 ConnectX RC 与 EFA SRD 的 *reliable-but-unordered* 共同语义,以一套 Rust 实现的最小 API + IMMCOUNTER 完成通知,在 LLM 系统场景下提供了一个真正可移植的 RDMA 点对点通信库。在 KV cache 传输、RL 权重同步(1.3s for 1T 模型)、MoE dispatch/combine(ConnectX-7 上击败 DeepEP,EFA 上首次可用)三个生产场景上验证了通用性与性能。主要局限在于 prefill MoE 场景未做单复制 + NVLink fan-out 优化,可移植性也只在 ConnectX-7 与 EFA 两套硬件上验证;摘要中"exceeding DeepEP"的措辞在 EP=64 与 intra-node 设置下并不完全成立。但作为云原生 LLM 部署的基础设施,其"P2P 不再被锁在某家 NIC"的工程价值是显著的。
