## 1. 背景

大规模深度学习模型已经成为 ChatGPT、Gemini 等产品的基础设施。为了训练这些模型,业界开发了大量深度学习系统,涵盖 3D 并行(Megatron-LM)、显存优化(DeepSpeed、FSDP)、以及模型专用的 kernel 优化(FlashAttention)等方向。

在 Apple 的实际场景中,除了对性能和可扩展性的通用需求,还有两个额外的硬约束:

1. **模块化(Modularity)**:模型工程师需要能用极少的代码量切换不同架构与训练方法 —— 例如把 FFN 换成 MoE、加上 RoPE —— 而不必到处改动上下游模块。
2. **硬件无关(Hardware-Agnostic)**:作为一家大型科技公司,Apple 不能把所有 ML 工作负载绑定到单一硬件供应商,必须同时支持 GPU、TPU、AWS Trainium 等多种加速器,跨 AWS / GCP / Azure / 自建集群运行。

现有系统要么专为单一硬件优化(Megatron-LM → NVIDIA GPU,Pax/Flax/MaxText → Google TPU),要么模块化能力受限(大多数框架依赖 subtyping),难以同时满足这两条要求。AXLearn 就是 Apple 在此背景下自研并开源的生产级训练系统。

---

## 2. 要解决的问题

AXLearn 想要回答:如何构建一个生产级训练框架,使得新增模型/架构特性的工程代价不随系统规模线性或平方级膨胀,同时保持跨硬件后端的性能竞争力?

具体可以拆分为几个子问题:

1. **Subtyping 带来的级联改动**:在传统 ML 框架中,把某个子层(比如 FFN)替换成新实现(MoE),需要沿父类一路继承/改签名,LoC 变化沿模块树传播。DeepSpeed 在 QwenV2 → QwenV2 MoE 的迁移中就额外引入了 200+ LoC,在生产环境里这个数字会进一步放大到数千行。
2. **模块化的量化缺位**:"模块化"在软件工程里一直是"口头规则",缺乏可度量指标,导致框架设计者无法权衡设计选择。
3. **硬件迁移成本**:同一份代码要跨 GPU/TPU/Trainium 运行,即使在 XLA 之上也需要不同的 sharding、remat、kernel 选择,如何把这些 target-specific 配置与模型定义解耦?
4. **大规模生产运维**:失败检测、checkpoint 恢复、AOT 编译验证、goodput 监控等在数千 chip 规模上的可用性。

## 3. 洞察与设计

**关键洞察**:神经网络层天然具有组合性 —— 只要父子层在 I/O 接口(通常只是 input/output dim)上达成一致,任何子层都可以被"原位替换",不必通过 subtyping 去修改父层。基于此,如果系统所有模块都严格遵循 encapsulation,那么新增特性(MoE、RoPE)的代价就应当与系统模块数无关,即 **O(1) LoC-Complexity**。这是一个关于可组合性(composition)优于子类化(subtyping)的工程假设,而不是对某种特定算法的优化。

基于这个洞察,AXLearn 的核心设计包括:

### 3.1 LoC-Complexity 形式化框架

作者提出用"新增某个特性 F 所需修改的 LoC 随系统规模(N = 模块数,M = F 的变体数)的渐近增长"作为衡量框架可扩展性的指标。用这个度量对比各系统:

| 系统 | LoC-Complexity(RoPE) | LoC-Complexity(MoE) | 生产估算 (RoPE / MoE) |
|------|---------------------|---------------------|----------------------|
| Megatron-LM | O(NM) | O(N) | 400 / 20 |
| DeepSpeed | O(NM) | O(NM) | 320 / 4000 |
| TorchTitan | O(NM) | O(NM) | 240 / 400 |
| Flax | O(NM) | N/A | 600 / N/A |
| Praxis | O(NM) | O(M) | 300 / 5 |
| MaxText | O(NM) | O(NM) | 200 / 300 |
| **AXLearn** | **O(1)** | **O(1)** | **0 / 0** |

AXLearn 在 1,000+ 个内部实验中用同一段 10 行代码片段启用 MoE;而在 DeepSpeed 的等价方案下,预计需要改动 4,000+ LoC。

### 3.2 层次化配置(Hierarchical Config)

AXLearn 把训练配置组织成一棵"模块树",每个 `Module` 都自带 `Config` 类,父模块不直接指定子模块超参,而是通过"延迟绑定"让子模块在实例化时继承必要的维度参数:

```python
class TransformerLayer(Module):
    class Config(Module.Config):
        self_attention: AttentionLayer.Config
        feed_forward: FeedForwardLayer.Config
```

用户可以在不修改 `TransformerLayer` 的情况下,把 `feed_forward` 换成任何符合 I/O 接口的实现(例如 MoE)。与之对比,TorchTitan/DeepSpeed 采用 flat 配置,扩展时需要同步修改多处 config class。

### 3.3 Config Modifier 与 Mesh Rules

由于配置是一棵树,可以写出通用的"遍历修改器":

```python
def replace_config(cfg, tgt, new_cfg):
    def enter_fn(child):
        for key, value in child.items():
            if isinstance(value, tgt.Config):
                new_cfg.set(**value.items())
                child.set(key, new_cfg)
    cfg.visit(enter_fn=enter_fn)
```

这就是 "10 行代码全局启用 MoE" 的本质:一次树遍历,把所有 FFN 节点替换为 MoE 节点。

在硬件维度,作者用 **mesh rules** 把"accelerator type → config modifier list"的映射注册到训练程序,例如 TPU v5e 自动切换到 slice 内 FSDP + slice 间 DP + dot product 激活卸载 + INT8,H100 则走 8-way TP + FSDP + QKVO save + FP8 delayed scaling。target-specific 配置与模型定义彻底解耦。

### 3.4 InvocationContext

JAX 程序必须是纯函数式的,这与 NN 训练天然的 stateful 行为(参数、PRNG、summary 收集)矛盾。AXLearn 引入 `InvocationContext` 抽象,以调用栈的形式管理子模块状态:父模块调用子模块时,自动压栈一个上下文,负责 split PRNG、创建 summary collection 等,子模块返回时弹栈并聚合到父 collection。关键设计是 `InvocationContext` 持有模块引用但反之不成立,使得 context 可以在模块层次之外访问(例如 optax 优化器、JAX `custom_vjp` backward),不破坏封装。

### 3.5 系统架构总览

AXLearn 由 **Composer + Runtime** 两部分组成:
- **Composer**:层库 + 配置生成器 + 并行策略 + rematerialization + AOT 编译,产出一个可以喂给 XLA 的 JAX 程序。
- **Runtime**:调度 JAX 产生的加速器程序到集群,提供 monitoring、checkpointing、fault tolerance。

编译入口始终是 XLA/GSPMD,因而天然 hardware-agnostic;必要时在每个后端用 custom kernel(cuDNN / Pallas / Nki / SplashAttention)替换默认实现。

## 4. 实现细节

- **底层框架**:基于 JAX + XLA + GSPMD 构建,所有 sharding annotation 由 XLA 自动传播。
- **并行策略**:原生支持 FSDP、Pipeline Parallelism、Expert Parallelism、Sequence Parallelism、Tensor Model Parallelism;用户通过配置而非代码选择策略。
- **显存优化**:
  - Rematerialization(activation checkpointing)通过"tag"标记关键点(QKV projection、output 等),用户选择保存/卸载到 CPU/重算。
  - Optimizer state offload 到 CPU,适配 TPU v5e 等 HBM 受限平台。
- **自定义 kernel**:FlashAttention 层在不同后端透明分发 —— GPU 上优先 cuDNN,fallback 到 Pallas;Trainium 走 AWS Neuron Nki;TPU 走 JAX Pallas SplashAttention。所有 kernel 都是 config modifier 级别的"drop-in replacement"。
- **AOT 编译**:复用训练 codepath 做 JAX Ahead-of-Time 编译,单机 CPU 就能捕捉 OOM、分片错误等问题,大幅降低分布式调试成本。
- **Checkpointing**:异步写,行为类似 Orbax,但同时支持 S3 / GCS 等云存储,后台 GC 按策略删除旧 checkpoint。
- **失败恢复**:
  - "watchdog" 监控 step time / 硬件利用率,异常时重启 host 或 dump stack。
  - Slice-level hot-swap:调度器 over-provision 备用 replica,故障时 4 分钟完成切换,9 分钟恢复 checkpoint,端到端损失 ~21 分钟。
  - 持久编译缓存避免重启后重编。
- **Golden config tests**:把关键训练 config 序列化成人类可读格式与代码一起 commit,任何训练动态的变化都能在 diff 中捕捉,避免"一个实验的改动影响其他实验"。
- **推理复用**:同一份训练层库可以复用为推理引擎,attention 的 KV cache 作为独立组件,可插入 continuous batching、disaggregated prefill/decode、paged KV cache 等推理优化,无需重写模型。
- **开源**:Apache 2.0 license,仓库 https://github.com/apple/axlearn

## 5. 实验结果

### 5.1 模块化度量

见第 3.1 节的 LoC 对比表。AXLearn 用 10 行代码在 1,000+ 实验中启用 MoE,DeepSpeed 等价方案估计需要 4,000+ LoC。

### 5.2 训练性能(Table 3,global batch size=1024)

| 模型 | 硬件 | 系统 | MFU | Throughput |
|------|------|------|-----|-----------|
| Llama2-7B | 32×H100-8 | PyTorch FSDP | 29.9% | 1.6M tok/s |
|  |  | Megatron-LM | 44.9% | 2.5M tok/s |
|  |  | MaxText | 54.7% | 3.0M tok/s |
|  |  | **AXLearn** | **54.2%** | **3.0M tok/s** |
| Llama2-7B | tpu-v5p-512 | MaxText | 61.6% | 1.6M tok/s |
|  |  | **AXLearn** | **66.2%** | **1.7M tok/s** |
| Llama2-7B | 64×Trainium2-16 | AXLearn | 24.2% | 3.5M tok/s |
| Llama2-70B | 64×H100-8 | Megatron-LM | 47.2% | 538K tok/s |
|  |  | **AXLearn** | 40.0% | 456K tok/s |
| Llama2-70B | tpu-v5p-1024 | MaxText | 64.4% | 341K tok/s |
|  |  | **AXLearn** | **68.0%** | **360K tok/s** |
| Qwen-3 30B-A3B | tpu-v5p-1024 | **AXLearn** | 31.58% | 1.3M tok/s |
| Qwen-3 30B-A3B | 64×B200-8 | Megatron-LM | 20.20% | 4.1M tok/s |
|  |  | AXLearn | 19.22% | 3.9M tok/s |

要点:TPU 上 AXLearn 全面领先;H100 上与 MaxText 持平,但落后于 Megatron-LM(作者归因为 PyTorch 比 XLA 有更细粒度的调度能力,并且这是"为 hardware-agnostic 付出的成本")。

### 5.3 扩展性

- 70B 模型从 256 → 4,096 chip,MFU 63.0% → 52.4%。
- 150B 模型从 8,192 → 32,768 chip,MFU 40.6% → 37.6%(per-chip sequence 长度缩短 16 倍)。

### 5.4 推理性能(vs. vLLM,TPU)

| 模型 | 系统 | TTFT | TPOT | Throughput |
|------|------|------|------|-----------|
| Llama2-7B | vLLM | 538.6 ms | 22.4 ms | 1117 tok/s |
|  | AXLearn | 40.1 ms | 9.1 ms | 3125 tok/s |
| Llama2-70B | vLLM | 80 s | 189.8 ms | 705 tok/s |
|  | AXLearn | 150.5 ms | 28.1 ms | 1139 tok/s |

AXLearn 在 TPU 上的 TTFT 比 vLLM 快 500× / 530×。作者明确指出 vLLM 对 TPU 的支持仍处于实验阶段,这不是公平 benchmark,而是"训练框架顺带产出的推理能力"。

### 5.5 故障恢复

32,768 TPU 规模下一次完整硬件故障事件:异步 checkpointing 无性能损失;故障检测立即触发 slice-level hot-swap,4 分钟切换,9 分钟恢复 checkpoint,总共损失约 21 分钟训练时间。

### 5.6 生产使用情况

AXLearn 自 2021 年底开发至今,从数名工程师发展到数百人参与,支持 10,000+ 并发实验,跨数十个硬件集群,训练的模型服务 10 亿+ 用户。

## 6. 批判性分析

1. **LoC-Complexity 作为框架度量的局限**
   LoC-Complexity 看似提供了一个"可量化的模块化指标",但它只衡量"新增一个已知特性 F 所需改动的 LoC",前提是 F 的接口已经能在 AXLearn 的模块抽象里得到一致表达。对于超出现有 I/O 契约的特性(例如需要引入 cross-layer gradient 通信、或与 KV cache 耦合的投机解码),AXLearn 同样需要扩展接口,只不过论文没有讨论这类场景下的 LoC 成本。把所有框架的 MoE / RoPE 改动一律按 worst-case O(NM) 估算,"生产估算列"中的 4,000 LoC 与 0 LoC 形成了接近 stunt-like 的对比,有自证其说之嫌。

2. **MFU 对比掩盖了绝对吞吐差距**
   在 Llama2-70B 64×H100 场景,Megatron-LM MFU=47.2% vs. AXLearn 40.0%,绝对 throughput 相差 ~18%(538K vs. 456K tok/s)。论文用一句"PyTorch 比 XLA 调度更细粒度,这是 hardware-agnostic 的代价"就带过,但这对成本敏感的用户来说是实打实的开销。作者应当给出"用 AXLearn 以 18% 性能损失换取跨硬件调度能力,在什么业务场景下能赚回来"的分析,而不是只声明"这是我们愿意付出的"。

3. **vLLM 对比明显不对等**
   500× TTFT 加速完全建立在 vLLM TPU 支持"仍处于实验阶段"的前提上。这不是证明 AXLearn 推理引擎好,只是证明 vLLM 在 TPU 上没优化。如果要论证"训练框架能免费产出生产级推理",应该在 vLLM 最佳发挥的 GPU 平台上做对比 —— 论文刻意选了 TPU。这属于 cherry-picking。

4. **恢复时间基准缺失**
   "slice-level hot-swap 4 分钟 + checkpoint 恢复 9 分钟 + 共 21 分钟损失"只有一条数据曲线,没有与 MegaScale、Megatron-LM 等同类系统在同规模下的恢复时间对比。单点数字难以评估是否"行业领先"。

5. **MoE 20 模型 × 4000 LoC 的估算偏激进**
   DeepSpeed 生产估算 4,000 LoC 假设"20 个模型变体,每个 200+ LoC",但"20 个模型变体是否都要独立启用 MoE"本身依赖于组织的研发风格。Apple 生产环境重视模型多样性(20 变体 × 10 attention 变体),但不是所有公司都需要这种扩展规模 —— 在实验室或小团队场景,subtyping 的代价根本不会暴露。因此 LoC-Complexity 的"不可承受"主要是在 Apple-scale 才成立,论文没有足够讨论该结论的 scope。

6. **Trainium MFU 偏低且未深入分析**
   Llama2-7B/70B 在 64×Trainium2-16 上 MFU 只有 24.2% / 25.0%,显著低于 TPU 和 H100,但吞吐却是最高的(因为 FLOP 预算高)。论文既然把 Trainium 作为 hardware-agnostic 的卖点之一,应该解释为何 MFU 如此低 —— 是 XLA/Neuron compiler 成熟度问题、kernel 没完全 tune,还是 Trainium 本身架构特点?

7. **Golden config tests 的假阳性率缺失**
   作者把"config 序列化 + diff review"作为防止"一个实验改动影响另一个实验"的机制,但在 10,000+ 实验的规模下,任何基础层改动都可能触发大量 golden file diff,review 负担与 false positive 比例应当讨论。

## 7. AI Infra / MLSys 视角

1. **LoC-Complexity 可推广为子领域通用度量**:把"新增特性所需 LoC 与系统规模的渐近关系"作为度量,这个思路其实在 MLSys 领域很稀缺。推理框架(vLLM、SGLang)、Agent 框架、RAG 系统同样面临"新增解码策略/新模型/新后端"的扩展性问题。把类似 framework 应用到 LLM 推理框架的模块化评估(例如:新增 speculative decoding 算法需要改多少 LoC)是一个有意思的 follow-up。

2. **Mesh Rules 抽象值得借鉴到推理服务**:把 target-specific 配置(sharding、remat、kernel)从模型定义中剥离,用映射表驱动,这对"一套推理服务代码跑遍 GPU/TPU/NPU"是直接可迁移的模式。像 vLLM 这样的 GPU-native 系统如果走向多硬件,Mesh Rules 等价物几乎是必要的。

3. **InvocationContext 与 tracing 的关系**:其本质是把"隐式 threaded state"做成显式栈,使得 JAX 纯函数约束下还能写出 imperative 风格代码。在 PyTorch 2.x 的 `torch.compile` + `functorch` 体系下,有相似的张力。如果社区关心"compile-friendly 的 PyTorch 框架设计",AXLearn 的 InvocationContext 是一份值得细读的参考。

4. **Training ↔ Inference 统一的具体路径**:AXLearn 通过 KV cache 作为 encapsulated 组件实现了训练→推理的代码复用。FlashInfer、SGLang、vLLM 等推理框架目前独立演进,与训练脚本几乎没有复用;AXLearn 的做法指出另一条路 —— 如果训练框架从一开始就把 KV cache、decode loop 设计成可替换模块,推理优化可以无损地"插入"而不需要重写。这对开源社区的"训推一体"讨论有方法论启发。

5. **Golden config tests 在 LLM 工程中的泛用价值**:把实验 config 序列化成 reviewable diff,在 prompt engineering、RLHF recipe、Agent trajectory 等场景同样可以适用。任何"隐式配置导致实验不可复现"的问题都可以套这个模式。

6. **可操作的 follow-up 研究问题**:
   - 能否把 AXLearn 的模块化原则搬到推理引擎?具体设计一个 O(1) LoC-Complexity 的推理框架,benchmark 其"新增 speculative decoding / MoE expert parallelism / disagg PD"的扩展成本。
   - 在 strict encapsulation 约束下,能否自动化"config modifier"的生成?即用户给出"我想新增 feature F",系统自动生成最小 LoC 的 modifier(潜在的 LLM-based 代码合成场景)。
   - AXLearn 在 H100 上 MFU 低于 Megatron-LM,可以研究"XLA + 自定义 Pallas kernel 能否在不牺牲 hardware-agnostic 的前提下追平 Megatron-LM 的绝对性能"。

## 8. 总结

AXLearn 是 Apple 过去四年在生产环境打磨、服务 10 亿+ 用户的大模型训练框架,其核心贡献是在 JAX/XLA 之上建立了一套严格遵循 encapsulation 的模块化抽象:层次化配置、config modifier、mesh rules、InvocationContext 协同起来,使得"添加 RoPE / MoE 等新特性"的工程代价从 O(NM) 压缩到 O(1)。作者还提出 LoC-Complexity 作为框架可扩展性的量化度量。适用场景是跨硬件(GPU/TPU/Trainium)、多团队、千级实验规模的生产训练环境;主要局限是 H100 上性能较 Megatron-LM 仍有 ~18% 差距(hardware-agnostic 成本)、LoC-Complexity 在"标准特性"以外的泛化能力未充分论证,以及部分对比(vs. vLLM on TPU)存在 cherry-picking 嫌疑。对想构建类似规模训练/推理基础设施的团队,AXLearn 是目前最系统的开源参考之一。
