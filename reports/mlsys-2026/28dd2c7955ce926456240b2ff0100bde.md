# AXLearn: Modular, Hardware-Agnostic Large Model Training

**作者**：Mark Lee, Chang Lan, Tom Gunter, John Peebles, Hanzhi Zhou, Kelvin Zou 等（Apple）；Danyang Zhuo（Duke University，访问学者）

**源文件**：[[28dd2c7955ce926456240b2ff0100bde.pdf]]

## 一、背景

大规模深度学习模型已广泛应用于聊天机器人、视频会议、编程辅助等领域。训练这些模型需要高效的分布式系统，现有系统（Megatron-LM、DeepSpeed、PyTorch FSDP、MaxText 等）在性能和可扩展性上已做了大量优化。然而，Apple 作为大型科技公司，面临两个独特需求：(1) 内部工程师需要快速实验多种模型架构和训练方法，要求系统具备高度**模块化**；(2) 不能依赖单一硬件供应商，需要在 GPU、TPU、AWS Trainium 等多种后端上**硬件无关**地训练。现有系统大多只针对特定硬件优化（如 Megatron-LM 专注 NVIDIA GPU），或只支持特定架构（如 MaxText 主要支持 LLM），无法同时满足这两个需求。

---

## 二、要解决的问题

1. **子类化（subtyping）导致的模块耦合问题**：现有 ML 框架普遍采用继承机制实现神经网络层。当需要将 FFN 替换为 MoE 时，理论上只需几行代码，但由于子类化的传播效应，实际需要修改整个继承层级的祖先模块。以 DeepSpeed 为例，QwenV2 到 QwenV2MoE 的适配需要超过 200 行代码修改，且随模型变体数量线性增长。

2. **硬件锁定**：Megatron-LM 深度绑定 NVIDIA GPU，JAX 生态系统（Haiku、Flax、Pax、MaxText）主要优化 Google TPU。缺乏真正跨硬件平台的训练系统。

3. **JAX 函数式编程与状态管理的矛盾**：JAX 要求纯函数式编程（无状态），但神经网络训练本质上是有状态的（参数、PRNG、训练摘要等），需要在保持 JAX 兼容性的同时提供良好的开发体验。

---

## 三、洞察与设计

**关键洞察**：神经网络本质上是**组合式（compositional）**的——层与层之间只需约定输入/输出接口，内部实现细节应该被严格封装。如果用组合（composition）而非子类化（subtyping）来构建系统，新功能的集成复杂度可以从 O(N)（N 为系统中模块数量）降低到 O(1)。

基于这一洞察，AXLearn 的核心设计包括：

- **严格封装的层次化配置系统**：每个模块通过 `Config` 对象封装所有可配置参数，子模块的配置独立于父模块。用户通过配置树（config tree）组合模块，而非通过继承修改。例如，将 FFN 替换为 MoE 只需一个约 10 行的 config modifier，可复用于 1,000+ 实验配置。

- **Config Traversal 机制**：由于配置是层次化的树结构，可以通过递归遍历（config modifier）对任意节点进行修改，支持 Python 原生控制流（循环、递归等），避免了 DSL 的局限。

- **Mesh Rules**：将硬件相关优化表达为「加速器类型 → config modifier」的映射，实现硬件无关的模型定义与硬件特定的优化策略解耦。

- **基于 XLA/GSPMD 的硬件抽象**：利用 XLA 编译器自动处理分片传播，在需要时插入自定义 kernel（GPU 用 cuDNN/Pallas，TPU 用 SplashAttention，Trainium 用 NKI kernel）。

---

## 四、实现细节

- **InvocationContext**：解决 JAX 函数式编程与有状态训练的矛盾。模块调用时自动将 context 压栈，管理 PRNG key 分裂、训练摘要收集、状态更新等副作用。Context 持有模块引用但模块不持有 context 引用，使得第三方库（如 optax）和 JAX 自定义 `vjp` 等特殊代码路径也能透明集成。

- **并行策略**：原生支持 FSDP、pipeline parallelism、expert parallelism、sequence parallelism、tensor model parallelism，全部通过配置指定而非代码修改。

- **内存优化**：支持可配置的 rematerialization（通过 tag 标记 remat 点）、optimizer state offloading 到 CPU 内存。

- **AOT 编译**：支持在单机 CPU 上完成完整的编译检查（包括 OOM 检测），避免浪费大规模集群资源。

- **容错机制**：watchdog 监控步时间和硬件利用率；基于健康副本的快速 checkpoint 恢复（而非从存储重新加载）；Kubernetes 原生 slice-level hot-swap，故障节点可被备用节点快速替换。

- **Golden Configuration 测试**：将关键训练配置序列化为人类可读格式并提交到代码仓库，通过 diff 追踪配置变更，防止隐式配置破坏。

- **统一训练与推理**：复用训练代码库做推理，KV cache 作为封装组件可独立替换，支持 continuous batching、disaggregated prefill/decode、paged KV cache 等推理优化。

## 五、实验结果

### 模块化分析（LoC-Complexity）

| 系统 | LoC-Complexity (RoPE) | LoC-Complexity (MoE) | LoC 估算 (RoPE) | LoC 估算 (MoE) |
|---|---|---|---|---|
| Megatron-LM | O(NM) | O(N) | 400 | 20 |
| DeepSpeed | O(NM) | O(NM) | 320 | 4000 |
| TorchTitan | O(NM) | O(NM) | 240 | 400 |
| Flax | O(NM) | N/A | 600 | N/A |
| Praxis | O(NM) | O(M) | 300 | 5 |
| MaxText | O(NM) | O(NM) | 200 | 300 |
| AXLearn | O(1) | O(1) | 0 | 0 |

### 训练性能

| 模型 | 硬件 | 系统 | MFU | 吞吐量 |
|---|---|---|---|---|
| Llama2-7B | 32×H100-8 | AXLearn | 54.2% | 3.0M tokens/s |
| Llama2-7B | 32×H100-8 | Megatron-LM | 44.9% | 2.5M tokens/s |
| Llama2-7B | tpu-v5p-512 | AXLearn | 66.2% | 1.7M tokens/s |
| Llama2-70B | 64×H100-8 | Megatron-LM | 47.2% | 538K tokens/s |
| Llama2-70B | 64×H100-8 | AXLearn | 40.0% | 456K tokens/s |
| Llama2-70B | tpu-v5p-1024 | AXLearn | 68.0% | 360K tokens/s |
| Qwen-330B-A3B | 64×B200-8 | Megatron-LM | 20.2% | 4.1M tokens/s |
| Qwen-330B-A3B | 64×B200-8 | AXLearn | 19.2% | 3.9M tokens/s |

### 推理性能（TPU，vs vLLM）

| 模型 | 指标 | AXLearn | vLLM | 加速比 |
|---|---|---|---|---|
| 7B | TTFT | 40.1ms | 538.6ms | ~13x |
| 7B | TPOT | 9.1ms | 22.4ms | ~2.5x |
| 7B | 吞吐量 | 3125 tokens/s | 1117 tokens/s | 2.8x |
| 70B | TTFT | 150.5ms | 80s | ~500x |
| 70B | TPOT | 28.1ms | 189.8ms | ~6x |
| 70B | 吞吐量 | 1139 tokens/s | 705 tokens/s | 1.6x |

### 可扩展性

- 70B 模型：256→4096 TPU chips，MFU 从 63.0% 降至 52.4%，接近线性扩展
- 150B 模型：8192→32768 TPU chips，MFU 从 40.6% 降至 37.6%

### 故障恢复

在 32,768 TPU 上的生产训练中，硬件故障后 hot-swap 4 分钟完成，checkpoint 恢复 9 分钟，总计 21 分钟恢复时间。

## 六、批判性分析

1. **推理对比基线不公平**：论文将 AXLearn 的 TPU 推理性能与 vLLM 在 TPU 上的实验性支持进行对比，作者自己也承认 vLLM 的 TPU 支持尚不成熟。500x TTFT 加速这样的数字更多反映的是 vLLM TPU 后端的不成熟，而非 AXLearn 推理引擎的优越性。如果与 vLLM 在 GPU 上的表现或其他成熟 TPU 推理引擎对比，结论可能截然不同。

2. **GPU 上性能并不占优**：在 H100 GPU 上，Megatron-LM 在 Llama2-70B（47.2% vs 40.0% MFU）和 Qwen-330B（20.2% vs 19.2% MFU）上均优于 AXLearn。论文将此归因为 "PyTorch 有更细粒度的调度能力"，但对于大量使用 GPU 的团队而言，这是一个实质性的性能差距。论文用 "这是我们愿意接受的权衡" 一笔带过，但未量化这一权衡的实际成本。

3. **LoC-Complexity 指标的局限**：论文提出用渐近 LoC 变化量度量系统可扩展性，这个指标虽有启发性，但存在明显局限——LoC 数量不等于工程复杂度。10 行高度抽象的 config traversal 代码的认知负担可能远高于 200 行直观的子类化代码。论文未评估开发者的实际使用体验（如上手时间、debug 难度）。

4. **Trainium 性能缺少对比基线**：Trainium2 上的结果仅展示了 AXLearn 自身数据，无任何基线对比。MFU 仅 24-25%，远低于 TPU 和 GPU 上的数据，但论文未深入分析原因。

5. **模块化的隐性成本未讨论**：严格封装和纯组合式设计在提升模块化的同时，可能增加间接层次和运行时开销。论文未讨论这种设计模式在 debug、性能调优时带来的额外复杂度。

## 七、AI Infra / MLSys 视角

1. **组合优于继承的系统设计哲学**：AXLearn 用 LoC-Complexity 这一形式化指标证明了在 ML 系统中组合式设计的优越性。这一思路可以推广到其他 AI Infra 组件的设计中（如推理引擎、数据管道、evaluation 框架），尤其是在需要支持多种模型变体的场景下。

2. **Config Modifier + Mesh Rules 的分离模式**：将模型定义（what）与硬件优化（how）通过 config modifier 和 mesh rules 解耦，是一个值得借鉴的设计模式。随着硬件多样性持续增长（GPU、TPU、Trainium、Gaudi、自定义 ASIC），这种解耦将变得越来越重要。

3. **AOT 编译作为开发范式**：在大规模训练中，能在单机 CPU 上完成编译检查（包括 OOM 检测）是一个极具实用价值的能力，可以大幅减少调试成本和集群资源浪费。这对其他基于 XLA 的系统有直接借鉴意义。

4. **训练-推理统一架构的可行性**：AXLearn 展示了通过模块化设计，用同一套代码支持训练和推理的路径。虽然专用推理引擎在性能上仍有优势，但对于需要快速迭代模型的团队，统一架构可以显著减少工程开销。

5. **值得跟进的方向**：
   - XLA 在 GPU 上的性能差距如何缩小（目前 vs Megatron-LM 有 ~7% MFU 差距）
   - 组合式设计在更复杂场景（如多模态模型、异构并行）下的表现
   - Golden Configuration 测试模式在其他 MLOps 场景中的应用

---

## 八、总结

AXLearn 是 Apple 开源的大模型训练系统，核心创新在于通过严格封装和纯组合式设计实现了 O(1) 的功能集成复杂度，同时基于 JAX/XLA 实现了 GPU、TPU、Trainium 的硬件无关训练。在 TPU 上达到 SOTA 性能，在 GPU 上与 Megatron-LM 有小幅差距但换来了跨平台能力。InvocationContext 巧妙解决了 JAX 函数式编程与有状态训练的矛盾。该系统已在 Apple 内部支撑了数百工程师、上万实验、横跨数十个硬件集群的大规模训练。论文的核心权衡——用 GPU 上的少量性能换取硬件灵活性和工程效率——对于多云部署的大型组织具有参考价值。
