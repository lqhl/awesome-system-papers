# Using Span Queries to Optimize for Cache and Attention Locality

**作者**:Paul Castro, Nick Mitchell, Nathan Ordonez, Thomas Parnell, Mudhakar Srivatsa, Antoni Viros i Martin
**会议**:MLSys 2026
**链接**:https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**:[[3416a75f4cea9109507cacd8e2f2aefc.pdf]]

## 1. 背景

Transformer 模型推理对 KV cache 的依赖几乎决定了系统吞吐:KV cache 把自注意力的 quadratic 复杂度摊销在跨 token、跨请求的复用之上,直接削减 prefill 阶段的 GPU 负载。vLLM 等主流推理服务器正是围绕这一思想设计 —— 以 PagedAttention 把序列切成 block,通过 prefix 共享在多轮 chat 之间最大化复用。

然而,LLM workload 正在快速越过 chat completion 这一原点。Inference-time scaling(ITS)、判别 / 生成器(judge-generator)、deep research、agentic workflow 都把若干次 model call 编织成树状或图状流程;RAG 则在每次请求中穿插不同顺序的 corpus fragment。这些场景下,被复用的 token 不再具有稳定的 prefix 排列,vLLM 在第一个不匹配 block 处就会停止前缀扫描,导致缓存命中率随场景规模渐近至 0%。已有工作如 Block Attention(Ma et al., 2025)和 CacheBlend(Yao et al., 2025)针对 RAG 提出了可重用的 cache 策略,但都局限于单一 use case,且没有把"顺序是否重要(commutativity)"这一根本约束显式表达出来。

## 2. 要解决的问题

论文聚焦于一个被现有系统忽略的本质冲突:**推理服务器的接口语义假设输入有严格顺序,而新兴 workload 的语义往往允许部分排列**。具体表现为:

1. **接口僵化**:vLLM 的 chat completion API 把输入视作有序 token 序列,无法表达"这几个片段顺序无关"或"内层 generate 的输出可任意排列"等高级语义。
2. **不同 workload 的 cache 失效模式同源但被独立处理**:RAG 的乱序 fragment、nested generation 的乱序 candidate、agent 的乱序工具调用结果,本质上都是"被复用的 block 位置变了",但被各自的论文/系统单独优化,缺乏统一抽象。
3. **dual output paradox**:chat completion 同时产出两件东西 —— 给客户端的回答,以及写入 KV cache 的 token 序列。两者并不一致(例如 nested generation 中,写入 cache 的输出会因为下游 prefix 不同而变成"死缓存")。这使得跨调用复用在没有服务器配合时几乎不可能。
4. **lost-in-the-middle**:小模型在长上下文中央的信息上注意力衰减,这是模型层面的痛点,但目前只在模型/RoPE/数据层做研究,没有从 query 编排层下手的方案。

## 3. 洞察与设计

**关键洞察**:chat、RAG、ITS、agentic workload 不是四类独立场景,而是一个**带有 commutativity 注释的表达式树**(expression tree of model calls)的特例。一旦在 query 层显式表达"哪些子树彼此可交换",cache locality 与 attention locality 这两件看似无关的事就能用同一套高层重写规则同时优化。

基于这个洞察,论文提出 **Span Query** —— 一个声明式中间表示。Span query 是一棵表达式树,节点是 chat completion (C)、retrieve (R)、fragment (F)、generate (G)、message (S/A/U) 等算子,叶子之间通过两种 join 算子连接:`✶`(non-commutative,顺序敏感)与 `+`(commutative,顺序无关)。

![chat / RAG / nested generation 的 span query 可视化](../../markdowns/mlsys-2026/3416a75f4cea9109507cacd8e2f2aefc/images/b17933e4d9a3f696f3d92faa95ed66bb1fc17f24d72c74fad1922ae892b6c63f.jpg)

设计要点:

- **声明式 + 树形**:子树语义独立,可并行调度;输出仍是 span query,集合在执行下闭合,整套结构与 map-reduce 同构。
- **commutativity 是一等约束**:由用户(或客户端 SDK)在 query 中显式声明,不是猜测。优化器借此判断能否复用、能否乱序送入 outer call。
- **高层重写器**(Section 5.1):一组 fixpoint 迭代的树重写规则,例如把 `C` 展开为 `G(✶(...))`,把 `R` 展开为 `+(F1, F2, ...)`,以及核心的 **plus distribution** —— 把 `+` 推入 `G` 内部,以化解 dual output paradox(强迫服务器把"被加在前面的 commutative 输入"与生成结果一起入 cache,使下游真正能命中)。

## 4. 实现细节

### Query 序列化

为了让 vLLM 能"无感地"消费这棵树,论文用一组 **special token** 把树括号化:`(` 表示子树开始,`)` 表示分隔/结束,`)n` 中的 `n` 直接指向该子树起始位置(避免 vLLM 端维护解析栈)。block alignment 通过 padding 特殊 token 保证(对齐后扫描每个 block 只看首个 token 即可知边界)。

![括号化序列示例](../../markdowns/mlsys-2026/3416a75f4cea9109507cacd8e2f2aefc/images/02bc677aef62adb49805d262af70a7f2487c36b5e937ddba12667ff66924c526.jpg)

### vLLM 改动:仅 492 行

| 模块 | LoC |
|---|---|
| `core/block_pool.py` | 68 |
| `core/kv_cache_manager.py` | 89 |
| `core/kv_cache_utils.py` | 73 |
| `core/sched/output.py` | 4 |
| `core/sched/scheduler.py` | 19 |
| `core/single_type_kv_cache_manager.py` | 4 |
| `worker/gpu_model_runner.py` | 232 |
| **总计** | **492 / 260 000** |

两层改动:

1. **Scheduler 层**:扫描 block 时引入"挂起 hash 累积"逻辑 —— 遇到 `(` 暂停累积(让 span 内部的 hash 与外部前缀无关),遇到 `)` 恢复。这是让 cross-request 复用成立的关键。
2. **GPU runner 层 + CIDRA**:命中的 cache block 通常需要做 **ReRoPE**(撤销旧位置的 rotary 编码,叠加新位置)。论文提出 **CIDRA**(Concurrent In-place Duplicating ReROPE Algorithm):
   - 构建 block 重定位的依赖图,用 in-place 操作减少临时显存。
   - 节点出度 > 1 时复制节点,把图化为严格 permutation graph。
   - 跑 strongly connected components 找环、bin-packing 把独立子图批量送 GPU;偶发的大环 fall back 到 CPU。
   - 小批量时把多层 tensor concat 后一次发射,降 kernel launch 开销。

### Trailing partial block 的取舍

vLLM 不缓存未填满的 block,而 nested generate 的 inner output 长度通常不是 block size 的整数倍。论文选择**裁掉尾部不齐的 token**,以保证 cache 命中(承认会损失少量精度);未在工程上做更深入的修改。

## 5. 实验结果

### RAG microbenchmark(2857 token / doc,1–32 文档)

![RAG TTFT:Stock vLLM vs Span Query (cache miss / cache hit)](../../markdowns/mlsys-2026/3416a75f4cea9109507cacd8e2f2aefc/images/e0cd1a6627ccfc88c09bd062dc104613b7fe3df7b463d027348ae53156a4bb19.jpg)

- **Cache hit 路径**:32 文档下 TTFT 从 ~25 s 降到 < 2 s,**~10–20× 加速**。
- **Cache miss 路径**:即便没命中,因为 span 让 attention 退化为块内稀疏,TTFT 依然约为 stock vLLM 的 1/3。
- **CIDRA 吞吐**:峰值约 **500 tokens/ms**(在 ~6 k token 序列长度处),曲线非单调(短序列吃不满 GPU,长序列受 batch 大小限制)。

### Nested generation microbenchmark(judge-generator)

![inner fan-out = 24 时的 TTFT 对比](../../markdowns/mlsys-2026/3416a75f4cea9109507cacd8e2f2aefc/images/574ebe35326d67eb7d65518c716783e479908277b8252e3ddfbb4e77be424c8e.jpg)

- inner temperature = 0 时 stock vLLM 的 prefix cache 已最优,span query 收益接近 0(符合预期)。
- inner fan-out = 1:温度变化下 span query 仅快 7–32%。
- **inner fan-out = 24,任意非零温度:span query TTFT 快 12–13×**。
- 速度稳定到 **p99**,p99 之后开始抖动。

### Bulk execution(2Wiki / NaturalQuestions)

| Bulk size | 2Wiki | NQ |
|---|---|---|
| 1 | 1.21× | 1.03× |
| 1024 | 1.31× | 1.05× |
| 整 corpus | 1.59× | 1.13× |

数据集 fragment 仅 ~100 token,处于 RAG 曲线最左端,因此整体加速远小于 microbenchmark;调度器按 fragment 复用聚类后,bulk 越大命中率越高。

### Attention locality(needle-in-haystack)

![granite3.3-2b 优化前 vs 后,准确率随 hay 长度变化](../../markdowns/mlsys-2026/3416a75f4cea9109507cacd8e2f2aefc/images/3de27c4cf1af57204aac1715fd88d3957c21fd3cdfa276c7b0d646030aeb461e.jpg)

把 8-way judge 改写为 3 ply 的 2-way tree reduce(divide-and-conquer)后:

- 未优化的 2b 模型在 ~100 char hay 之后就掉到 0%;
- 优化后 2b 模型一直撑到接近 1000 char,且**优化后的 2b 模型准确率 > 未优化的 8b 模型**。

## 6. 批判性分析

- **加速数字几乎全部来自 microbenchmark,且基线选择极不利于 vLLM**:RAG microbenchmark 用"完全随机内容、每篇 2857 token"的合成文档,跨请求复用度被人为推到上限;真实 RAG 的命中率受语料更新、检索 top-k 漂移影响,无法稳定接近 100%。把 microbenchmark 的 10–20× 直接换算成 production 价值是危险的 —— bulk benchmark 中 NQ 数据集就只剩 1.13×,自己的实验已经印证。论文却把 microbenchmark 数字写进 abstract 与 intro。
- **Trailing partial block 裁切的精度代价没有量化**:Section 5.3.2 声称"接受裁掉 inner generate 最后一个 block"换来命中率,却没有给端到端任务质量(F1、ROUGE、judge accuracy)的对比。在 nested generation 中被裁掉的可能正是 candidate 的关键尾词。
- **"492 LoC"是一个好看的标题,但忽略了 ReRoPE 在 GPU runner 层的复杂度**:gpu_model_runner.py 一个文件就改了 232 行,占改动总量的 47%,而 CIDRA 算法本身的正确性、并发安全性论文只用文字描述了一段,缺乏形式化或单测覆盖说明。
- **Span query 语言本身被刻意推到 future work**:Section 4.1 直接说"我们 defer language design",但所有可视化的 query 都是手画树,实际客户端如何写、是否需要 SDK、是否兼容 OpenAI / LangChain API 完全没谈。这让 span query 的"通用性"承诺打了折扣 —— 如果用户必须改写已有应用才能受益,迁移成本可能远超 12× TTFT 的诱惑。
- **特殊 token 的 fine-tuning 风险被一笔带过**:论文承认"重载现有 token 可能降低准确率",但没有给即便是简单 perplexity 对比。生产环境部署 span query 的人需要知道这条路是否在自己的 base model 上安全。
- **Attention locality 的对照不公**:Figure 17 把"未优化 8b vs 优化 2b"作为爆点,但没把"优化 8b"画在同一张图。如果 8b 在 tree reduce 下也大幅提升,那就只是 divide-and-conquer 提示工程的胜利,与 span query 的系统贡献无关。
- **CacheBlend 比较只在引言一带而过**:论文反复强调自己 10–20× 远超 CacheBlend 的 3–4×,但实验里没有任何直接对比的曲线 —— 二者在同一 benchmark、同一硬件上的端到端结果缺位。
- **CIDRA 在大环时 fall back CPU**,论文称"我们的实验里很少",但没说 fan-out 进一步放大(例如 100+ candidate)或多租户混合负载下,CPU 路径会不会成为瓶颈。

## 7. AI Infra / MLSys 视角

这篇论文在 MLSys 圈子里的定位很清晰:**把"语义层的 commutativity"提升为推理服务器的一等公民**,这是过去两年 RAG / Agent serving 研究里被反复触碰、却没人系统化的角度。对小实验室和 AI Infra 研究者,有几个值得跟进的方向:

1. **把 span query IR 与现有 Agent 框架对接**:LangGraph、DSPy、SGLang 程序的执行图本身就是 commutativity 信息的天然来源,但目前都没有把这层信息下推给 vLLM。直接做一个 LangGraph → span query 的编译器,验证真实 agent loop 上的 TTFT 收益,可能比再设计一门 query 语言更有杠杆。
2. **commutativity-aware scheduler**:论文 Section 5.8 的 bulk execution 只用了一个朴素 greedy。如果把 span query 的复用图视作多机多租户调度问题(类似 PagedAttention 把内存当作页),可以做带优先级、带 SLA 的复用调度,这是一个适合做 OSDI / NSDI 投稿的扩展点。
3. **Trailing partial block 的精度 - 命中率 trade-off 量化**:论文留下的最大坑。一个可独立成篇的工作:在多个常用 nested-generation 任务(judge-generator、self-refine、ToT)上系统测量"裁切 vs 不裁切"对最终 task accuracy 的影响,并提出可学习的裁切策略。
4. **CIDRA 的 GPU kernel 优化**:目前用 PyTorch 级别 batched op 跑到 500 tokens/ms。写一个融合 ReRoPE 的 CUDA / Triton kernel,把 RoPE 的撤销 + 重应用合并成一次 kernel,可能再有 2–4× 的吞吐提升。这种系统层小工作适合一个研究生学期完成。
5. **Attention locality optimizer 推广到非 judge 场景**:论文只示范了 judge 的 tree reduce。同样的 commutative + divide-and-conquer 结构在 multi-document QA、code review aggregation、log summarization 上是否成立,值得做横向 benchmark —— 这是"用编排技术补偿模型能力"的低成本路线,对小模型部署很有吸引力。
6. **与 DRAM / SSD 多级 KV cache 协同**:llm-d 等系统正在把 KV cache 推到 DRAM 与 SSD。span query 提供了块级别的"语义命中线索",可以指导 cache 替换策略(commutative 子树的 block 比 prefix block 更值得保留,因为它在多个未知排列下都可能命中)。

短期最有价值的切入点是 **(1) + (3) 的组合** —— 在一个真实 agent benchmark 上,做"LangGraph 编译 + 裁切策略 + 端到端任务质量评估"三位一体的实验,既能验证 span query 的实用性,也能补足原论文的方法论盲区。

## 8. 总结

Span Query 提出了一个简单但被忽视已久的抽象:把 LLM 调用编排成带 commutativity 注释的表达式树,统一表达 chat、RAG、ITS、agentic workload。配合 vLLM 仅 492 行的修改和 CIDRA 重定位算法,在 RAG / nested generation microbenchmark 上拿到 10–20× TTFT 加速,并意外发现同一抽象可被高层重写成 divide-and-conquer 形式以缓解 lost-in-the-middle。论文最大的贡献在于"commutativity 应作为推理服务器一等约束"这一认知上的位移,而非工程数字本身;局限在于真实数据集(NQ)收益骤降至 1.13×、trailing block 裁切的质量代价未量化、与 CacheBlend 缺直接对比、span query 客户端语言被推迟到 future work。它适合作为 RAG / Agent serving 系统设计的参考起点,但在生产部署前需要补上"真实 workload + 端到端质量"的实验。
