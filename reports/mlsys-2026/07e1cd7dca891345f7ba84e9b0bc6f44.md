# Event Tensor: A Unified Abstraction for Compiling Dynamic Megakernel

**作者**：Hongyi Jin, Bohan Hou, Guanjie Wang, Ruihang Lai, Jinqi Chen, Zihao Ye, Yaxing Cai, Yixin Dong, Xinhao Cheng, Zhihao Zhang, Yilong Zhao, Yingyi Huang, Lijie Yang, Jinchen Jiang, Gabriele Oliaro, Jianan Ji, Xupeng Miao, Vinod Grover, Todd C. Mowry, Zhihao Jia, Tianqi Chen

## 1. 背景

LLM 推理对延迟和硬件利用率的极致追求,使 GPU 调度模型本身的开销成为系统瓶颈。当前主流框架(如 PyTorch + cuBLAS/NCCL、vLLM、SGLang)采用 **kernel-by-kernel** 调度:每个算子对应一次 GPU kernel launch,kernel 之间存在隐式同步屏障。在自回归 decoding 中,一次迭代要发起几百到上千个细粒度 kernel,每次 launch 5–10 µs,而最快的 kernel 仅 2 µs 即可完成,launch 开销直接主导端到端延迟。CUDA Graph 通过捕获-回放消除 launch gap,但 kernel 边界仍在,跨 kernel 的细粒度并行无法暴露。

最近 megakernel(如 Stanford Hazy Research 的 no-bubbles megakernel、Mirage Persistent Kernel)通过把整张计算图融合进单个常驻 kernel,把算子拆成 tile 级别的 task 分发到不同 SM,从而同时消除 launch 开销并通过 task 级依赖打破 kernel 边界,在 LLaMA-1B 等单 batch dense 推理场景上展示了显著加速。然而要把这类技术真正用到生产 LLM serving,还有两个根本难题:**dynamic shape**(continuous batching 让 batch size、序列长度都不固定)和 **data-dependent dynamism**(MoE 的 expert routing 在运行时才能确定 token-expert 对应)。

---

## 2. 要解决的问题

现有 megakernel 工作落地生产 serving 系统时存在两类核心障碍:

1. **动态性表达力不足**
   - **Shape dynamism**:支持动态 batch size 通常需要为每个可能的 shape 重新生成或重编译 kernel,启动延迟极高,甚至当 shape 空间过大时根本不可行。CUDA Graph 同样要为每个 shape 单独 capture,vLLM 实测在 Qwen3-32B 上要 capture 67 张图,SGLang 需要 51 张,warmup 分别耗时 123 s 和 583 s。
   - **Data-dependent dynamism**:MoE 这类 routing 决策在运行时产生,task 之间的依赖图不是编译期可知的。现有抽象无法精细描述「token 0 通知 expert 3,token 1 通知 expert 1」这类按 runtime 张量值索引的事件依赖。

2. **可编程性差**
   - 手写 megakernel 要管理几十万到上百万的 tile-level 同步,极易出错。
   - 不同 workload 适合不同调度策略(静态预分配 vs. on-GPU 动态 dispatch),手写实现切换调度策略要重写整个 kernel,无法在编译器层统一。

论文要解决的不是「单个 megakernel 能不能写出来」,而是「能不能在编译器 IR 中给出一个统一抽象,既表达 megakernel 内部的细粒度依赖,又同时承载 shape 和 data-dependent 两种动态性,并允许编译器自动生成 static / dynamic 调度变体」。

---

## 3. 洞察与设计

**关键洞察**:megakernel 中,SM 级别 task 完成所产生的「event」天然形成多维结构(因为 task 本身就是按 tile 坐标多维分布的);因此可以把这些事件升格为 IR 中的**一等张量(Event Tensor)**,这样所有现成的张量基础设施 —— 符号 shape、index 表达式、broadcast、shard —— 都能直接复用到细粒度同步上。这条认知是论文方法论的支点:把 fine-grained synchronization 从「需要专门 runtime 数据结构管理的零散 semaphore」变成「编译器原生理解的张量对象」,既能用符号 shape 表达 dynamic shape(同一个 Event Tensor 在 batch=1/B=2 时分别 materialize 成 1×2 和 2×2 的依赖图),又能用 `i->topk[i,:]`、`i->range(exp_indptr[i], exp_indptr[i+1])` 这样的 index 表达式表达 data-dependent 的事件触发与更新。

基于这个洞察,论文构建了三层设计:

**(a) Event Tensor 语言构造**

- **Device function**:类似 CUDA kernel,但每次 launch 是「一个 task」(粒度为一组 SM/CTA),每个 task 由多维坐标索引。
- **Event Tensor**:多维事件数组,元素是带 wait_count 的 event。原语:`E[i].notify()`(原子递减计数器)、`E[i].wait()`(spin 直到计数器归零)、动态调度下还可以触发后继 task。
- **Graph function**:计算图节点既包含数据 tensor 也包含 Event Tensor,通过 `in_edges`/`out_edges` + 一段 lambda(如 `"ij->i"`、`"i->topk[i,:]"`)指定 producer-task 通知哪些 event、consumer-task 等待哪些 event。

**(b) 两种动态性的张量表达**

- *Shape dynamism*:Event Tensor 维度可以是符号变量 `B`(batch size),编译期生成的 megakernel 是 shape-generic 模板,运行时按真实 shape 实例化依赖图,无需 recompile。
- *Data-dependent dynamism* 通过两个机制:
  - **Data-Dependent Event Update**:event 的 wait_count 在运行时根据 routing 张量(如 `topk`)初始化 —— 例如 expert i 的 event 计数器 = 路由到它的 token 数;
  - **Data-Dependent Task Triggering**:一个 event 触发的 consumer task 数量也是 runtime 决定的,通过前缀和张量 `exp_indptr` 编码,expert i 触发 `[exp_indptr[i], exp_indptr[i+1])` 范围内的 GroupGEMM tiles。

**(c) ETC 编译器:两种调度变体的统一 lowering**

- **Static scheduling**:host 端预计算每个 SM 的任务队列,生成 persistent main loop,Event Tensor 依赖被 lower 成显式 `notify()`/`wait()`。适合 GEMM、AllGather+GEMM 这类规则、可预测的 workload,同步开销最小。
- **Dynamic scheduling**:运行时由 on-GPU 调度器维护 ready queue,事件触发后原子地 push 后继 task,空闲 SM 原子 pop 执行。适合 MoE 这类 token 路由不均衡、单 task 时长不可预测的 workload,以负载均衡换取小幅 push/pop 开销。
- 两种 pass 共享同一份 device-function 实现,workload 间切换不需要重写 kernel。

## 4. 实现细节

- **基础设施**:在 Apache TVM 上实现一系列 compiler pass。device function 用基于 TVM 的 tile DSL(Hou et al., 2026 的 Axe)编写,但 Event Tensor 抽象本身是 DSL-agnostic,理论上可嫁接到 Triton、CuteDSL。

- **Event Tensor 的运行时 lowering**:Event Tensor 直接 lower 成一个整型 tensor,复用现有 tensor 数据结构,不引入专门的 event runtime。`notify()` 编译为硬件 atomic decrement,`wait()` 编译为 spin-wait counter == 0。运行时数据结构只剩「整型张量 + 调度器任务队列」,远比传统 task-graph 框架(必须把整个 task graph materialize 在内存中并由通用 task executor 遍历)轻量。

- **Static scheduling pass(Algorithm 1)**:
  1. host 端 `GenerateStaticSchedule`(round-robin 策略)生成 per-SM 任务队列,作为常量缓冲区编译进 kernel;
  2. 每个 task grid 在融合 kernel 中插入 `dispatch logic + wait(in_edges) + tile_logic + notify(out_edges)`;
  3. 形成单个 persistent kernel,主循环不断从预计算队列取任务直到完成。

- **Dynamic scheduling pass**:在 task 完成后插入 `scheduler.pop`,在某个 event counter 减到 0 时插入 `scheduler.push(consumers)`。Push-pop 用 global memory 中的中央 ready queue 实现(实现简洁,大规模时存在潜在争用)。Appendix E 提到 **early push** 优化:producer 一旦被 dispatch(无需完成)就把 consumer push 入 queue,真正的依赖通过 consumer 起始处的 wait 保障,把 push 开销从关键路径移除。

- **Static 处理动态性的退化方案**:无法直接表达 dynamic shape,故采样代表性 shape 集合,未见过的 shape 复用「下一个更大采样值」的队列;data-dependent 时按 worst case 把 notify/wait 重写为 `E[0].notify/wait`(单点同步,丧失大部分细粒度并行)。这解释了为什么 MoE 上 dynamic scheduler 优于 static。

- **End-to-end pipeline**:计算图(Event Tensor 已定义、算子已切 CTA tile,可由 Triton 等 kernel DSL 提供)→ 图级优化(memory planning)→ tile 级优化(指令映射、流水线)→ static 或 dynamic 调度 pass → 生成 persistent-kernel 风格 GPU 代码 → 权重 prefetch pass(允许 tile 在 input activation 到达前预取权重)→ static 时还会 materialize per-SM 队列。

- **集成**:ETC 已合入「a major open-source system」(从作者背景与上下文看,极大可能是 Apache TVM / MLC-LLM 体系)。

## 5. 实验结果

实验平台:8× NVIDIA B200 + NVLink,Ubuntu 24.04,CUDA 13.0,PyTorch 2.8。

### 5.1 融合通信-计算 kernel(8-way TP, 8192 tokens,基于 8 个 LLM 的 MLP 配置)

| Workload | 调度器 | ETC 相对最强基线最大提速 | 备注 |
|---|---|---|---|
| GEMM + Reduce-Scatter | dynamic | 高达 **1.40×**(over cuBLAS+NCCL) | 在 8 个 MLP 配置上一致最优,显著超 cuBLASMp、Triton-Distributed、TP-Async |
| All-Gather + GEMM | static | 高达 **1.40×**(over cuBLAS+NCCL) | 用 ring DMA + static schedule 严格 overlap |

Triton-Distributed 在 B200 上尚未充分调优,有些配置 cuBLAS+NCCL 反而打过 TP-Async / Triton-Dist,反衬 ETC 提速的稳健性。

### 5.2 MoE layer(Qwen3-30B-A3B,128 experts, top-k=8,单 B200,dynamic scheduler)

| Token 数 | 1 | 8 | 32 | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|---|---|---|
| ETC 相对最强基线 | 1.18× | 1.13× | 1.02× | 1.02× | 1.13× | **1.23×** | 1.20× | 1.18× |

基线为 Triton 3.4.0 与 FlashInfer 0.2.14。优势来源:data-dependent Event Tensor 打破 baseline 中 GroupGEMM 阶段间的全局 barrier,加上 on-chip 动态调度提供 routing 不均衡下的负载均衡。

### 5.3 端到端低 batch serving(prefill 512 + 100 output token)

| 模型 / 设置 | ETC 相对 vLLM | ETC 相对 SGLang |
|---|---|---|
| Qwen3-30B-A3B, TP=1, bs=1 | **1.48×** | 1.20× |
| Qwen3-32B, TP=1, bs=1 | 1.15× | — |
| Qwen3-32B, TP=1, bs=64 | — | 1.09× |
| Qwen3-32B, TP=4 | 0.99–1.06× | 略慢于 SGLang |

ETC 与 vLLM 在 TP=4 下都慢于 SGLang,作者归因于 SGLang 的 CPU scheduler 优化。Appendix D 用「raw kernel time」(剔除 CPU 框架开销)评测,ETC 相对 vLLM 在 30B-A3B bs=1 提至 1.49×、32B bs=1 提至 1.13×,TP=4 上 1.08×。

### 5.4 Warmup 开销(Qwen3-32B)

| 方法 | Warmup 时间 | JIT/Graph capture 次数 |
|---|---|---|
| SGLang (JIT) | 583 s | 51 |
| vLLM (JIT) | 123 s | 67 |
| **ETC (AOT)** | **35 s** | 0 |

ETC 离线编译一次 shape-generic megakernel(Qwen3-32B 编译 107 s),运行时无需任何 capture/recompile。warmup 比 vLLM 快 3.5×,比 SGLang 快 16.7×。

### 5.5 Static vs. Dynamic 调度权衡(相对 unfused megakernel baseline)

- MoE(数据相关): dynamic 在 token≥128 时 1.06–1.08×,优于 static(1.02–1.04×);单 batch 时 dynamic 0.95×(调度开销不划算)。
- Qwen3-32B TP=4(规则、分布式): static 1.06–1.09×,**dynamic 仅 0.82–0.89×**,因为分布式场景下跨 SM push 远端 ready queue 开销爆炸。

## 6. 批判性分析

1. **「state-of-the-art LLM serving latency」言过其实**。摘要级 claim 与正文数据存在落差:Qwen3-32B TP=4 这个最贴近真实生产部署的场景,ETC 实际只与 vLLM 持平(0.99–1.06×),被 SGLang 反超;作者把这归因为「我们 CPU scheduler 没人家好,不是抽象本身的问题」 —— 但若抽象的优势在生产部署里被工程因素稀释到看不见,声称 SOTA 是不公平的。

2. **MoE 收益高度依赖 token 数**。Table 2 显示 dynamic 对 unfused baseline 的提升仅 8.1%(1024 token 处),而对 static 的提升仅 4.0%。Section 5.2 的 1.23× 是相对外部库(Triton/FlashInfer)而非自己的 unfused 版本 —— 这说明很大一部分 MoE 收益其实来自「整个 MoE 融合到一个 kernel」,而不是 Event Tensor 抽象本身。如果用同等强度手写 megakernel 做基线,1.23× 这个数字可能压缩到接近持平。

3. **TP=4 场景的「dynamic 调度比 static 慢 11–18%」是个红灯**。论文把这解释为「分布式 push 开销大」一笔带过,但这意味着他们引以为豪的 dynamic scheduling 只在「单卡 + 大 batch + 数据相关」这个相当窄的甜点区有用。生产 LLM serving 的主流是多卡 TP/EP,正好落在 dynamic scheduler 的劣区。

4. **Worst-case 退化让 static 在动态 workload 上几乎失去意义**。3.1 节末尾承认,static 处理 data-dependent 时把 notify/wait 重写成 `E[0]`(单点同步)、shape dynamism 用「下一个更大采样值」的队列。这两个退化都把 fine-grained 并行直接退成 coarse-grained,与论文核心卖点背道而驰,但实验中没单独 ablate「static + 动态 workload」的损失。

5. **B200 + 8 卡的硬件不具普适性**。所有评测都在最顶配硬件上,而 megakernel 的核心收益(消除 launch overhead、暴露细粒度并行)在中端硬件、长序列、大 batch 场景下边际收益完全不同。论文没在 H100/A100 上验证,也没评估对 prefill / 大 batch 场景的影响(只是说「不会变差」)。

6. **可编程性的量化缺失**。论文反复强调「降低 megakernel 编程复杂度」,但没有任何 LoC、开发时间、bug rate 之类的对比,只是定性宣称。第三方研究者很难判断 Event Tensor DSL 真比手写 Mirage / no-bubbles megakernel 简洁多少。

7. **中央 ready queue 的扩展性留作 future work**。3.2 节自承「集中式 queue 在大规模时存在 contention」,但全部实验止步于 8 卡,扩展到 EP=64 / 多节点时这个设计能否撑住,完全未知。

## 7. AI Infra / MLSys 视角

这篇论文对 AI infra 研究有三层启发:

1. **「同步原语张量化」是值得迁移的范式**。把过去散落在 runtime 的 semaphore/event 升格为编译器 IR 一等张量,是借鉴 SparseTIR、Relax 已有的「让 IR 理解符号 shape + index 表达式」基础设施的自然延伸。这个思路可推广到:
   - **流水线调度**(把 pipeline stage 的 event 表达成 tensor,用 index 表达式描述 micro-batch → stage 的依赖);
   - **KV cache 管理**(PagedAttention 中页 → 物理块的依赖也可以用类似 index 表达式表达,可能减少手写 lookup 逻辑);
   - **Speculative decoding**(draft → verify 的依赖天然 data-dependent,Event Tensor 抽象可以直接表达「verify task 依赖哪几个 draft token」)。

2. **AOT-only 的 megakernel 解决了 serving 工程上一个长期痛点**:CUDA Graph recapture / torch.compile JIT 在生产环境的 P50/P99 抖动、warmup 时间一直是 vLLM/SGLang 用户的高频抱怨。Event Tensor 用符号 shape 一次编译终身使用,这条路径如果真能 hold 住生产负载,会显著降低部署运维成本。值得跟进:
   - 在 disaggregated prefill/decode 架构(DistServe)中把 Event Tensor 跨节点扩展;
   - 把 prefix caching、chunked prefill 这类需要灵活 shape 的 feature 用 Event Tensor 重新表达。

3. **可操作的 future work 切入点**:
   - **(a)** 自动化「图 → Event Tensor task graph」的 lowering(论文的 Conclusion 明确点名为 future work)。当前用户仍要手写 in_edges/out_edges 和 index 表达式,如果能从标准 PyTorch FX graph 自动推导,会大幅扩展用户基础。
   - **(b)** 把 dynamic scheduler 的中央 queue 改成分布式/分层 queue,直接对标 EP=64+ MoE 的 production-scale。这是一个可独立成文的 system 工作。
   - **(c)** Event Tensor + speculative decoding:draft model 产出的 acceptance pattern 是天然的 data-dependent 触发,正好契合论文抽象。结合 EAGLE/Medusa 做 ablation 是有价值的延伸。
   - **(d)** 把 Event Tensor 嫁接到 Triton 或 CuteDSL —— 论文宣称 DSL-agnostic,但实际 demo 只在 TVM 上。如果能给 Triton 加一个 Event Tensor extension,推广到现有大量 Triton-based MoE/Attention kernel,影响力会大很多。

---

## 8. 总结

Event Tensor 提出了一个**优雅且明显被低估的小抽象**:把 megakernel 内部 fine-grained 同步事件升格为编译器 IR 一等张量,从而同时获得符号 shape(对付 dynamic batch)和 index 表达式(对付 data-dependent dynamism)两种早已成熟的张量基础设施支持。这让 ETC 编译器能 AOT 生成 shape-generic 的常驻 megakernel,在 GEMM+RS / AG+GEMM / MoE 等代表性算子上取得 1.18–1.40× 的稳健加速,并把 LLM serving warmup 从分钟级压到 35 秒。

论文最坚实的贡献其实是 **warmup**(把生产 serving 的一个真实痛点从 123–583 s 压到 35 s)和 **抽象的简洁性**;端到端 latency 的 SOTA 声明在多卡场景下站不住脚,且 dynamic scheduling 在分布式部署上明显劣化。整体上这是一篇 abstraction-first 的工作:Event Tensor 这个抽象很可能比论文本身报告的实验结果更有长尾影响,因为它给后续 megakernel + dynamic dispatch 的研究提供了一个可以共用的编译器底座。
