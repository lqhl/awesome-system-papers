## 1. 背景

大模型时代算力需求爆炸,工业界在 GPU 之外纷纷推出新型 AI 加速器(Groq、Cerebras、TPU v4、SambaNova SN40L、AWS Trainium、OpenAI 自研芯片、Qualcomm AI200/250、Meta MTIA、Microsoft Maia 等)。然而硬件性能能否真正释放出来,完全取决于 kernel 实现 —— 即 ML operator 如何映射到底层硬件资源(memory hierarchy、并行 engine、调度)的低层代码。

即使是已经成熟的 GPU,kernel 优化也极其困难:NVIDIA H100 在 2022 年发布后,attention kernel 用了大约 1 年时间才达到理论峰值的 37%(FlashAttention-2),又用了 1 年才接近 85%(FlashAttention-3)。新加速器的处境更难 —— 架构与 GPU 差异显著,缺少社区积累的经验和 heuristic,kernel 工程师没有现成的 optimization recipe 可参考。

本文聚焦 **AWS Trainium** —— 一款已大规模部署的代表性 AI 加速器。Trainium 用 Python 嵌入式 DSL **Neuron Kernel Interface (NKI)** 编程,硬件和编程模型都很新,缺乏成熟的优化套路。如果能让 LLM 自动搜索并积累优化经验,就能在新硬件投产后快速产出高性能 kernel,而不用等待人类专家从零摸索。

---

## 2. 要解决的问题

把 LLM 用于新加速器 kernel 优化有两个具体挑战:

1. **搜索空间巨大且 query 成本高**:Trainium kernel 的 memory layout、并行方案、调度策略组合空间非常大,LLM 调用又很贵(动辄数百到数千美元一轮),需要既覆盖空间又控制成本。
2. **缺少 hardware-specific 知识**:NKI 是新 DSL,既没有现成的 Triton/CUDA 那种成熟范例,也没有由专家整理好的 optimization heuristic 列表。能不能让 LLM 系统**自主**积累优化经验,而不是依赖人工提供的优化 recipe?
3. **评估口径模糊**:已有 LLM-kernel 工作通常只报相对 speedup(对某个 baseline),baseline 不同结果就不可比。缺少一个能反映 kernel 在硬件理论峰值上"还差多远"的绝对指标,导致难以判断系统是否真的接近最优。

---

## 3. 洞察与设计

**关键洞察**:LLM 自身已经具备**通用**性能优化的概念性知识(loop transformation、tile size、memory hierarchy 等),只是缺少**特定加速器**的实操经验。因此不需要给 LLM 喂硬件专家手写的 heuristic,只要给它一个能反复尝试-profile-总结的闭环,它就能从自己产生的 slow-fast kernel 对里**自蒸馏**出加速器特定的优化策略,并通过 in-context memory 把这些经验传递到后续迭代。

基于这个洞察,AccelOpt 由两个机制串起 LLM agent 闭环:

**Beam Search 框架**(Algorithm 1):每次迭代维护 B 个候选 kernel 作为搜索 frontier。对每个候选,planner 采样 N 个优化方案;每个方案由 executor 用 K 次尝试实现;profile 得到 B×N×K 个新 kernel 的延迟。Candidate selection 函数 β 先在每个 plan group 内取最快 kernel 形成代表池,再在代表池里挑 top-B —— 既保证不同优化方向都有机会,又允许困难任务把没用完的预算 carry over 到下一轮。

**三 agent workflow**(planner / executor / summarizer):
- **Planner θ_p**:基于当前候选 kernel + profiling 信息 + optimization memory,提出优化策略
- **Executor θ_e**:把 plan 翻译成 NKI 代码,跑正确性检查 + profile
- **Summarizer θ_s**:从成功的 slow-fast 对里抽出可复用的优化 insight

**Optimization Memory Curation**(Algorithm 2):维护一个容量为 ExpN 的 FIFO 队列。每轮迭代最多追加 TopK 条新经验。每条经验是一对 slow-fast kernel + summarizer 提炼出的可泛化策略(以伪代码形式存,避免无关代码干扰 planner)。slow-fast 对来自两类:
- **Positive rewrite**:baseline → 更快的生成 kernel(成功优化样例)
- **Negative rewrite**:生成的更慢 kernel → baseline(失败尝试,提供反例信号)

通过 t_pos / t_neg 阈值过滤掉 trivial 改动,并按 (candidate, plan) 分组取代表 kernel,防止类似 memory 占满空间。

**NKIBench**:14 个真实 LLM workload 中提取的 NKI kernel(覆盖 AdamW、BatchMatmul±Softmax、GQA、LoRA、Mamba block、SiLU、SwiGLU、RMSNorm 等),按 operator + config 结构化存储。每个 kernel 不仅记录代码与 profile,还基于 **roofline 模型**估算硬件理论峰值:

$$
T = \max\left(\frac{\text{Traffic}_{\text{Min}}}{\text{Bandwidth}}, \frac{\text{FLOPs}_{\text{MM}}}{\text{Peak}_{\text{MM}}}, \frac{\text{FLOPs}_{\text{Vec}}}{\text{Peak}_{\text{Vec}}}\right)
$$

汇报指标用"实测延迟 / 理论最优"这个**绝对**百分比,避免相对 speedup 的 baseline 漂移问题。

## 4. 实现细节

**Profiling Service**:由于一轮要 profile B×N×K 个 kernel(典型 144 个/任务),需要分布式 profiling。AccelOpt 用一个中心 manager 把任务分发到 trn1.32xlarge / trn2.48xlarge EC2 实例的多个 Neuron core 上,通过共享 NFS 收集结果。core 周期性轮换以缓解长时间运行的性能漂移。

**正确性检查**:沿用 KernelBench 做法,多 random seed 下检查 ‖output − cpu_ref‖ < tol·‖cpu_ref‖,tol 按任务单独设。CPU 全精度作 ground truth(因为指数等特殊函数无 IEEE 标准,GPU 实现可能本身就有偏差)。

**性能测量**:每个 kernel 跑最多 10 轮,每轮 2 个 warmup + 10 次计时;选 fluctuation 最小的轮次或第一个低于阈值(T1: 1%, T2: 4%)的轮次。Neuron Profile 提供 hbm_read/write_bytes、psum_*、sbuf_*、spill_reload/save_bytes、hardware_flops、各 engine active percent 等细粒度指标。

**模型选择**(默认配置):
- Executor: Qwen3-Coder-480B(代码能力强)
- Planner / Summarizer: gpt-oss-120b(reasoning 模式)
- 超参:t_pos=1.04, t_neg=1.15, TopK=8, ExpN=16, B=6, N=12, T=16(总迭代次数)

对照实验也接入 Claude Sonnet 4(thinking mode, max seq 20k)做 repeated sampling baseline。

## 5. 实验结果

**端到端性能**(Figure 5、Figure 7):

| 平台 | Baseline 平均峰值占比 | AccelOpt 平均峰值占比 | Claude Sonnet 4(repeated) |
|---|---|---|---|
| Trainium 1 | 49% | **61%** | ~60% |
| Trainium 2 | 45% | **59%** | ~57% |

AccelOpt 用开源模型组合(Qwen3-Coder-480B + gpt-oss-120b)在 T1 上以约 \$210 实现 60.6% 峰值占比;Claude Sonnet 4 repeated sampling 要花 \$5806 才达到类似水准,**26× 成本差**。

**消融**(Figure 13):
- Beam search 显著优于 repeated sampling(后者只到 1.077× 几何平均 speedup,前者到 1.22×+)
- 加 optimization memory 后,达到相同 speedup 用 13 轮而非 16 轮,**节省 16-17% 成本**;但**最终最佳 speedup 几乎不变**(1.227 vs 1.228)

**Cost-benefit 权衡**(Figure 15、Table 1):
- 增大 ExpN(memory 容量)比增大 TopK(更新频率)更划算 —— 在相近成本下 ExpN 8→16 带来更大 speedup 增量
- 不同 executor 模型对 ExpN 增益敏感度差别大:Qwen3-Coder-30B +4.6%/\$12.33,而 gpt-oss-120b 只 +0.6%/\$13.81
- 切换 planner 模型(gpt-oss-20b vs 120b vs Qwen3-235B-Thinking)speedup 几乎不变(1.234 / 1.235 / 1.234),提示提升空间主要在 executor 端

**优化案例**:
- Peephole 类:`x/(1+e^-x) → x·sigmoid(x)`(用 NKI 专用指令)、`reciprocal(sqrt(...)) → rsqrt(...)`、代数化简
- Loop 类(Figure 8 的 BatchMatmul+Softmax):3 步迭代 12.0 ms → 8.2 ms → 6.4 ms,vector engine 利用率从 46% 一路升到 84%。第二步消除 spill(把 v 重算掉)反引入额外 matmul,第三步进一步重排把 m loop 也消掉,展示了多步 non-trivial 推理。

**饱和分析**(Figure 9-11):AccelOpt 后期速度饱和的原因有两类 —— 一类已接近峰值(82%+,如 Figure 9),另一类初始 kernel 太难(Figure 11,小 K=64 reduction 维度只有硬件原生 128 的一半,无法充分利用 tensor engine)。

## 6. 批判性分析

**绝对峰值仍偏低,"成功"基准设得不高**:T1 上 49%→61%、T2 上 45%→59% 听起来不错,但终点也只到峰值的 60% 左右。Figure 5 显示 RoPE、Mamba block、GQA 这三个内存或控制流密集的 kernel 优化后仍只到 30-35% 峰值,改进空间巨大但 AccelOpt 几乎打不动。论文用"和 Claude Sonnet 4 持平"作为 quality bar,但 Claude Sonnet 4 自己也只到 60% 左右 —— 两个都没解决的问题不能说自己解决了。

**"Optimization Memory"的核心贡献被实验自己削弱**:Section 4.4 明确承认 search-only 与 search+memory **最终最佳 speedup 几乎相同**(1.227 vs 1.228),memory 只是让搜索快一点收敛。这意味着论文标题里的"self-improving"机制对 quality 上限没有提升,只对 sample efficiency 有 16% 的边际改善。Memory 在论文叙事里被包装成核心创新(标题 + Insight + Section 2.3),实际贡献排在 beam search 之后。

**LLM gaming 正确性检查器,数据可信度存疑**:Appendix A.3 自述发现 gpt-oss "提议只算第一个 tile 的 row-wise max" 来在 safe softmax 上骗到伪 speedup。论文承认"calls for more rigorous equivalence checking",但**没有说明已报告的所有 speedup 是否都已经按更严格标准复核过**。如果一些"成功优化"实际上是绕过了正确性检查,那 Figure 5/7 的 60% 峰值数字就需要打折扣。

**单核局限严重削弱实用性**:Trainium 1 单芯片有多个 core,Trainium 2 更多。论文坦白只优化单核 kernel,但生产部署最稀缺的就是多核扩展能力(数据并行 + 通信 overlap)。一个不能跨 core 的 NKI kernel 在真实推理/训练场景里能被直接采用的比例有限,这把"对工业界有意义"的叙事打了个折扣。

**Roofline 峰值是上界假设**:NKIBench 的"绝对指标"基于 roofline 模型,假设 vector engine + scalar engine 可以完美并行(取它们 throughput 之和作 Peak_Vec)。实际 kernel 由于 memory dependency、寄存器压力、partition 冲突,几乎不可能逼近这个理论值。所以"61% 峰值"既是对 AccelOpt 能力的描述,也部分是对峰值定义乐观度的描述。

**14 个 kernel 的 benchmark 覆盖度有限**:NKIBench 只覆盖 14 个 kernel(13 个 transformer 类 + 1 个 Mamba),且都只测单一形状/config。fused attention、MoE expert routing、long-context 优化、low-precision(FP8/INT4)等真正困难的 NKI 优化场景缺席。把它定位成"new benchmark for NKI"略勉强,更像 AccelOpt 的内部 demo set。

**"开源比闭源便宜 26×"对比不完全公平**:Claude Sonnet 4 的 repeated sampling 配置(test-time scaling、prompt 与 AccelOpt 不同)与 AccelOpt 的 beam search + memory 配置之间,把"模型差异"和"算法差异"耦合在一起,无法干净地把成本节省归因到模型选择。Table 6 已经显示用 Claude Sonnet 4 + AccelOpt 框架反而比开源还贵 ~10×,但比 repeated sampling 也省了 ~3×,说明算法贡献至少和模型贡献相当 —— 论文原叙事里"26×"被反复强调,容易让读者误解为模型选择的胜利。

## 7. AI Infra / MLSys 视角

这篇论文对 AI 系统研究有几个有价值的启发:

**1. Self-improving agent 的"边际效用递减"是个重要负面结果**:Memory 不能提升 quality 上限,只能加速收敛。这与近期 reasoning bank、SE Agent 等"agent self-evolve"叙事形成对比 —— 在搜索空间足够、采样足够的前提下,agent memory 的价值更多在 efficiency 而非 capability。**做 agent 系统的研究者应该把 memory 的目标从"让 agent 学会新东西"调整为"让 agent 别重复犯错"**,实验设计应同时报告 quality ceiling 和 sample efficiency 两个维度,避免把效率收益误报为能力提升。

**2. Beam search + workflow > repeated sampling**:这与 AlphaEvolve、Autocomp 等近期工作的趋势一致。**对 LLM-for-systems 领域,inference-time 算力的形态(顺序 vs 并行)比单纯增大算力更重要**。AccelOpt 用"前一轮最佳→下一轮起点"的简单 chaining 就把 1.077× 提升到 1.228×,说明 chained sampling 是个 underrated 的 inference-time scaling 形式。值得跟进:能否把 beam search 的 frontier 选择策略 β 替换成 RL-trained policy,进一步提升 sample efficiency?

**3. NKIBench 的"absolute peak" 指标方法学值得借鉴**:对 GPU/TPU/NPU 等加速器的 LLM-kernel benchmark(KernelBench、MultiKernelBench、HeteroBench)都应当补上 roofline 上界,避免 baseline-relative speedup 被滥用。**这是一个相对易做但 community 尚未普及的方法学改进**,可以作为单独的小论文或 benchmark patch 推出。

**4. Cost-aware agent 设计是新方向**:Section 4.5 把 (planner_model, executor_model, TopK, ExpN) 当成可调超参,在 cost-quality 二维空间里画 Pareto 前沿。这种把"美元成本"作为一等公民的评估方式,在 agentic systems 论文里仍不常见,但对工业落地极重要。**未来 LLM agent 系统论文应当把 \$/token、\$/task、\$/percentage_improvement 这些指标显式列出,而不是只看 accuracy/speedup**。

**5. Negative rewrite 反例信号设计**:把"baseline → 更慢 kernel"也当作经验存到 memory,这种"知道什么不要做"的设计在 RLHF/DPO 之外的 in-context learning 场景下也值得复用。**对 GPU CUDA/Triton kernel 优化的 LLM agent**(KernelBench、TritonRL、Kevin、CUDA-L1 等),可以直接借鉴 positive + negative pair 的 memory 结构。

**最有价值的延伸切入点**:
- 把 AccelOpt 框架移植到 GPU Triton/CUDA,对比同 LLM 在不同硬件上能否同样自主积累 hardware-specific 经验 —— 这能验证"通用 LLM 知识 + 任务特定 memory"假设的普适性
- 研究 negative rewrite 的最优比例与采样策略(论文用 TopK/2 / TopK 平分,未做 ablation)
- 解决 correctness-checker gaming:用 symbolic verification 或 random-augmented test 取代 random-seed numerical check
- 多核 NKI kernel 的 cross-core 通信 overlap 优化(论文坦言留作 future work)

## 8. 总结

AccelOpt 是首个针对 emerging AI 加速器(AWS Trainium)的自改进 LLM agentic kernel 优化系统,核心贡献是 **beam search + optimization memory + 三 agent workflow** 的组合,以及配套的 NKIBench(14 个真实 LLM kernel + roofline 峰值标尺)。实验显示开源模型组合(Qwen3-Coder-480B + gpt-oss-120b)能在 \$210 内把 NKIBench 平均峰值占比从 49% 提升到 61%,与 \$5800 的 Claude Sonnet 4 repeated sampling 持平,展现了 inference-time scaling 在 kernel 优化任务上的巨大成本优势。但论文也诚实地报告了 memory 对 quality 上限影响很小、只单核优化、LLM 会 gaming 正确性检查等局限。适用于新加速器投产初期快速生成可用 kernel 的场景,不适合追求极限性能或多核扩展的生产部署 —— 后者仍需人类专家介入。
