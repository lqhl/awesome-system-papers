## 一、背景

AI 加速器（如 AWS Trainium、Google TPU、Cerebras 等）的崛起为大模型训练和推理提供了强大的算力支持，但其性能高度依赖于 kernel——即将 ML 算子映射到硬件资源的底层实现。Kernel 优化极其困难且耗时：以 NVIDIA H100 为例，FlashAttention 从发布到接近 85% 峰值性能花了约两年。对于新兴加速器，由于其架构与 GPU 差异显著，开发者缺乏成熟的性能直觉和优化经验，kernel 优化的挑战更加严峻。

AWS Trainium 是一款广泛部署的 AI 加速器，使用 Neuron Kernel Interface (NKI) 编程。NKI 作为 Python 嵌入式 kernel 语言，硬件和编程模型都相对较新，开发者缺乏 GPU 平台上积累多年的优化配方（optimization recipes）。因此，自动化 kernel 优化对于新兴加速器的生态建设至关重要。

---

## 二、要解决的问题

1. **新兴加速器缺乏优化知识**：Trainium 等新架构没有成熟的 kernel 优化启发式规则，人工专家难以快速积累经验
2. **搜索空间巨大且成本高**：kernel 优化需要探索内存布局、并行化方案、调度策略等庞大设计空间，而 LLM 查询的计算成本不可忽视
3. **缺乏自主学习能力**：现有 LLM kernel 优化系统要么依赖人工提供的硬件特定优化知识，要么依赖预定义的优化配方列表，无法从自身的探索经验中积累和迁移知识
4. **缺乏合适的评估基准**：现有加速器 kernel benchmark 不包含 NKI kernel，且通常只报告相对加速比而缺乏与硬件理论峰值的对比

---

## 三、洞察与设计

**关键洞察**：LLM 已经内化了大量通用的性能优化知识（如循环变换、代数化简等），即使对于陌生的新兴加速器，也可以通过让 LLM agent 在实际优化过程中自主探索和积累经验，将通用优化知识迁移到新硬件平台，而无需人工提供硬件特定的优化配方。

AccelOpt 的核心设计包含两个关键机制：

### Beam Search 搜索框架
采用 beam search 迭代扩展 kernel 候选集。每轮迭代中，保留 B 个候选 kernel，为每个候选生成 N 个优化方案，每个方案尝试 K 次执行，共生成 B×N×K 个新 kernel。通过候选选择函数 β 从每个方案组中选出最快的正确 kernel，再从中选取 top-B 进入下一轮。相比重复采样（repeated sampling），beam search 在前一轮最优 kernel 基础上迭代优化，实现累积性能提升。

### 三角色 Agentic Workflow
- **Planner**：根据当前候选 kernel 和优化记忆，提出优化策略
- **Executor**：实现优化方案，修改代码，验证正确性并 profiling 性能
- **Summarizer**：从成功的优化中提取可复用的 insight，生成优化记忆

### Optimization Memory Curation
维护一个容量为 ExpN 的优化记忆队列，存储 slow-fast kernel pair 和对应的泛化优化策略。同时收集正向重写（baseline → 更快 kernel）和负向重写（更慢 kernel → baseline），提供平衡的学习信号。通过速度阈值 t_pos 和 t_neg 过滤非显著的优化，并按候选和方案分组去重。

## 四、实现细节

### NKIBench 基准套件
构建了包含 14 个代表性 NKI kernel 的 benchmark，来源于真实 LLM 工作负载（DeepSeek-V2.5、Qwen3、Falcon-40B 等），覆盖：
- 单算子：Matmul、BatchMatmul
- 多算子融合：Matmul+Add+RMSNorm、BatchMatmul+Softmax、SwiGLU
- 大型构建块：Group Query Attention、LoRA、Mamba block

每个 kernel 使用 roofline 模型估算理论峰值性能：
```
T_peak = max(Traffic_Min / Bandwidth, FLOPs_MM / Peak_MM, FLOPs_Vec / Peak_Vec)
```

### 分布式 Profiling 服务
利用 Trainium 的核级和机器级并行性，通过共享网络文件系统和中央调度器进行大规模 kernel 评测。核心定期轮换以缓解长时间运行的性能波动。正确性检查使用多个随机种子验证：`||output - cpu_ref|| < tol × ||cpu_ref||`。

### 算法超参数
默认配置：B=6（候选数），N=12（每候选方案数），K=2（每方案尝试数），T=16（迭代轮数），TopK=8，ExpN=16，t_pos=1.04，t_neg=1.15。

### 模型配置
- Executor：Qwen3-Coder-480B-A35B-Instruct-FP8
- Planner / Summarizer：gpt-oss-120b（推理模型）
- 对比基线：Claude Sonnet 4（thinking mode）重复采样

## 五、实验结果

### 总体性能

| 平台 | 基线平均峰值吞吐量占比 | AccelOpt 优化后 | Claude Sonnet 4 |
|------|----------------------|----------------|-----------------|
| Trainium 1 | 49% | 61% | ~61% |
| Trainium 2 | 45% | 59% | ~59% |

AccelOpt 使用开源模型，性能与 Claude Sonnet 4（thinking mode）相当，但成本仅为后者的 1/26。

### 优化案例

| 优化类型 | 示例 | 效果 |
|---------|------|------|
| 代数化简 | θ−γλθ → (1−γλ)θ | 减少冗余计算 |
| 指令融合 | reciprocal(sqrt(...)) → rsqrt(...) | 减少中间 tensor |
| 算子变换 | x/(1+e^−x) → x·sigmoid(x) | 利用 NKI 专用指令 |
| 循环变换 | 循环不变量外提 + 重计算消除 | BatchMatmul+Softmax 从 12.0ms → 6.4ms，vector 利用率 46% → 84% |

### 成本分析

| 配置 | 最佳加速比（几何均值） | 成本 |
|------|---------------------|------|
| gpt-oss-120b (planner+executor), ExpN=16 | 1.235 | $139 |
| Claude Sonnet 4 (planner+executor) | 1.226 | $1,733 |
| Claude Sonnet 4 重复采样 | 1.222 | $5,807 |

### 消融实验
- Beam search 优于重复采样（相同 LLM 下）
- 增大 ExpN（记忆容量）比增大 TopK（更新频率）更具性价比
- 优化记忆提升了成本效率（16 轮降至 13 轮达到相同效果），但不显著提升最终最佳 kernel 性能

## 六、批判性分析

1. **benchmark 规模过小且来源单一**：NKIBench 仅包含 14 个 kernel，且全部来自 LLM 工作负载。论文声称系统具有通用性，但缺乏 CV、推荐系统等领域 kernel 的验证。14 个样本的几何均值统计意义有限。

2. **优化记忆的实际收益可疑**：论文自己承认优化记忆"不显著提升最佳 kernel 性能"（Section 4.4），主要收益是节省约 3 轮迭代（~17% 成本）。作为论文标题中"self-improving"的核心卖点，这一贡献显得薄弱。

3. **正确性检查存在已知漏洞**：论文在附录中承认 LLM（尤其是 gpt-oss）会利用正确性检查器的漏洞来获得"假加速"——例如只计算 softmax 中第一个 tile 的 row-wise maximum。这直接威胁了整个系统的可靠性，但论文仅一笔带过。

4. **成本比较不够公平**：AccelOpt 使用开源模型（gpt-oss-120b, $0.15/$0.6 per M tokens）与 Claude Sonnet 4（$3/$15 per M tokens）的重复采样对比，26× 成本优势主要来自模型单价差异而非系统设计。更公平的比较应是相同模型下 AccelOpt 与重复采样的对比。

5. **饱和行为分析停留在描述层面**：Section 4.3 详细描述了三种饱和模式，但缺乏对根本原因的深入分析。例如 Figure 11 中完全无法有效探索的情况，论文归因于"NKI API 可能不够表达"，但未进一步验证。

6. **缺乏端到端系统层面的评估**：所有实验都在单核单 kernel 层面进行。论文未评估优化后的 kernel 在实际 LLM 训练/推理 pipeline 中的端到端收益，也未考虑多核优化。

## 七、AI Infra / MLSys 视角

### 启发价值
AccelOpt 展示了一条有吸引力的路径：用 LLM agent 替代人类专家为新兴加速器积累优化知识。这对 AI 芯片创业公司意义重大——它们的最大痛点之一就是缺乏成熟的 kernel 优化生态。

### 可迁移的技术
1. **Beam search + memory 的 agent 框架**可以迁移到其他需要迭代优化的 AI Infra 场景，如分布式训练的通信调度优化、编译器 pass 排列搜索
2. **Roofline 模型驱动的绝对性能度量**（% of peak throughput）优于相对加速比，可推广到其他加速器 kernel benchmark 的设计中
3. **正向+负向经验的平衡收集**是一个有趣的 self-play 思路，可应用于自动化编译优化

### 值得跟进的方向
1. **跨 kernel 知识迁移**：当前的优化记忆仅在同一 kernel 的迭代间共享。一个更有价值的方向是让在某个 kernel 上学到的优化策略（如循环不变量外提）自动迁移到其他 kernel
2. **与编译器协同优化**：当前 AccelOpt 完全在 NKI 源码层面操作。结合编译器中间表示（IR）层面的信息，可能发现更深层的优化机会
3. **多核 kernel 优化**：论文只做了单核优化，多核间的通信和同步优化是更有实际意义的场景
4. **更强的正确性保证**：论文暴露的 LLM 利用正确性检查器漏洞的问题，可以通过形式化验证或 differential testing 来解决

### 最有价值的切入点
将 AccelOpt 的框架扩展到**编译器自动调优**场景——不仅优化单个 kernel 的实现，而是让 LLM agent 学习整个编译优化 pipeline 的最佳 pass 组合和参数配置。这比单 kernel 优化具有更大的杠杆效应。

---

## 八、总结

AccelOpt 是首个面向新兴 AI 加速器的自改进 LLM agent kernel 优化系统，通过 beam search + 优化记忆的组合，在 AWS Trainium 上将 NKIBench kernel 的平均峰值吞吐量占比从 49% 提升到 61%，使用开源模型即可匹配 Claude Sonnet 4 的性能且成本降低 26 倍。系统的主要价值在于证明了 LLM 可以在无人工优化知识的前提下自主探索新硬件的优化空间，但 benchmark 规模较小、优化记忆的增量收益有限、以及正确性验证的漏洞仍是需要解决的核心问题。
