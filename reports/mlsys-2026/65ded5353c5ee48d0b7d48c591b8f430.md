# PRISM: Parametrically Refactoring Inference for Speculative Sampling Draft Models

**作者**：Xuliang Wang, Yuetao Chen, Maochan Zhen, Fang Liu, Xinzhou Zheng, Xingwu Liu, Hong Xu, Ming Li
**会议**：MLSys 2026
**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[65ded5353c5ee48d0b7d48c591b8f430.pdf]]

---

## 1. 背景

LLM 推理本质是 auto-regressive 生成,decoding 阶段每生成一个 token 都要把整套模型参数从 HBM 搬到片上,是典型的 memory-bandwidth-bound 工作负载,GPU 计算单元长期 stall。speculative decoding(Leviathan et al., 2023)在不破坏 lossless 输出分布的前提下,用一个轻量 draft 模型先猜 γ 个 token,再让 target 模型在一次前向里并行验证,把高带宽成本摊到多个 token 上,显著提升 decoding 阶段的算力利用率。

EAGLE 系列(Li et al., 2024a;b;2025a)是当前最重要的一支技术路线:不再用一个独立的小 LLM 当 drafter,而是在 target 模型最近一次验证产生的最后一层 hidden state 之上,接一个小 transformer block,把"上下文 token + target hidden state"融合后做下一步 token 预测。该路线下的 HASS(Zhang et al., 2025a)、Griffin(Hu et al., 2025)、Jakiro(Huang et al., 2025)分别从 context alignment、token 同步、MoE 头等角度做了进一步优化。

近一年的趋势是 **draft 模型变大**。从 EAGLE-1 单 transformer block(0.48B)到 EAGLE-3(1.03B–2.19B),再到 Scylla(Yan et al., 2025)和 Meta 的 Llama-Speculative(Tang et al., 2025)直接堆 5 层 transformer 或者引入 MoE FFN,drafter 相对 target 模型的参数比例从早期的 0.1%–1% 一路涨到 6%–20%(论文 Table 1)。这条路线的内在矛盾是:堆大 drafter 能涨 acceptance rate,但 drafter 自身的延迟也线性增加,挤压 speculative decoding 留给端到端的速度收益。

---

## 2. 要解决的问题

speculative decoding 的端到端加速比近似为 `acceptance_length / (1 + draft_cost / target_cost)`。所有"做大 drafter"的工作都在分子(更高 acceptance length)和分母(更高 draft 成本)之间走钢丝,需要小心调参才能找到一个甜蜜点。具体的痛点是:

1. **capacity 与 inference cost 高度耦合**:单一 drafter 网络中,所有 draft step 走同一套参数。想增加 capacity 只能把 transformer 加深或加宽,而每多一层都直接挤占每一个 draft step 的延迟预算。
2. **训练成本随 draft 步数二次膨胀**:为了缓解 exposure bias,SoTA drafter 普遍采用 context alignment(HASS、EAGLE-3、Griffin),即训练时为每个 draft step 单独跑一次 forward + backward。drafter 越深,这 n 次 forward + backward 的成本越高。
3. **大多 drafter 仍停留在 PyTorch 复现**:SoTA drafter 的 acceptance length 数字大多在 PyTorch eager 模式下测得,缺少 CUDA Graph、continuous batching 等系统侧优化下的真实端到端验证。

---

## 3. 洞察与设计

**关键洞察**:speculative decoding 的"预测难度"在 draft 步序列上是非均匀的——后面的步越来越难,acceptance rate 单调下降(论文 Figure 1)。既然不同 step 的难度差异显著,那就没必要用同一套参数处理所有 step。把 draft 步的计算路径**沿时间轴**(而不是 MoE 那样沿 token 轴)路由到不同的参数子集,既能扩 capacity,又不增加单步活跃参数量。

基于这个观察,作者提出 PRISM(Parametrically Refactor Inference for Speculative decoding draft Models)。结构上(Figure 3):

- drafter 包含 M 个"处理模块"(processing module),每个模块由一个 fusion FC + 一个 transformer layer 组成
- 给定 K 个 draft 步,定义一个满射 `f_map: 1..K → 1..M`,把每个 draft 步唯一地映射到一个处理模块
- 不同模块共享 KV cache:第 k 步的 transformer 拿到的 KV cache 是第 k-1 步的输出 KV cache,只是过的 transformer 权重换了
- token embedding 和 LM head 全程冻结,只训练 fusion FC 和 transformer 块

该设计带来两个直接收益:

- **capacity 与单步延迟解耦**:总参数量 = M × 单 transformer 大小,但任一 step 的 active 参数量等同于一个 single-transformer drafter,延迟不变。
- **adaptive 表示深度**:由于第 k 步的输出隐藏状态会作为第 k+1 步的输入,而 k+1 步又走另一组参数,等价于构造了一个深度随 step 增加的级联网络,把更多的累计计算分配给更难的后段预测——和 Figure 1 的难度分布天然匹配。

训练分两阶段:第一阶段只训一个模块(等价于 HASS),loss 为 CE + MSE;第二阶段把训好的 transformer 权重 **复制 M 份** 作为各模块初始化,去掉 MSE,继续做 context alignment 训练并在 forward 间真切地切换模块。

值得注意的是,主实验中 PRISM 只用了 **M = 2 个模块**:模块 1 专门处理 prefill,模块 2 处理所有后续 decoding 步。也就是说论文实际验证的"step-wise specialization"等价于"prefill / decode 双阶段 drafter",而不是真的为每个 draft step 各配一组参数。

## 4. 实现细节

- **基础架构**:复用 EAGLE / HASS 的 fusion 结构(token embedding 与 target 的最后一层 hidden state 拼接,过 FC 融合),只在原本的"一份 transformer"位置改成多份并按步切换。
- **KV cache 跨模块传递**:第 k 步 transformer 输出的 K、V 直接当作第 k+1 步 transformer 的历史 KV cache 使用,不重新算。所有模块的 hidden size、head 数完全一致,这一传递成本仅是地址空间切换。
- **训练数据**:ShareGPT(8.5%)+ UltraChat(57.9%)+ OpenThoughts2(33.6%),约 80 万样本,统一截断到 2048 token,OpenThoughts2 去掉 `<think>` 标签内容。
- **训练硬件**:8×A100 40G 或 4×A100 80G,数据规模 100K–800K,1 天到 2 周不等。
- **context alignment**:沿用 HASS 风格,对齐 hidden state 和 KV cache,共 3 步。在 PRISM 上,由于每步只过一个子网络的 forward + backward,context alignment 的开销显著低于在大型 monolithic drafter 上做。
- **集成 SGLang**:作者把 PRISM 实现进 SGLang(目前已经把 EAGLE/HASS 等做了大量底层优化的开源推理引擎),与 CUDA Graph、continuous batching 协同。这是相对于多数只在 PyTorch eager 下报数的对比工作的核心差异。

## 5. 实验结果

### 设置

| 项目 | 配置 |
|---|---|
| target 模型 | LLaMA-2-7B-chat、LLaMA-3-8B-Instruct |
| baseline | Vanilla(无投机)、Standard(LLaMA-160M / LLaMA-3.1-1B 当 drafter)、EAGLE-2、HASS、EAGLE-3 |
| benchmark | MT-bench、HumanEval、GSM8K、Alpaca、CNN/DM、Natural Questions |
| 硬件 | 1×A800 80G(主表),2×4090 24G(扩展表) |
| 树形结构 | 主结果 6 step × 4 branch,最多验证 16 token;scaling 实验 6 step × 10 branch,最多 60 token |
| batch size | 1 |

### 主结果(Table 4,A800)

PRISM 在所有 6 个 benchmark、2 个 target、greedy 与 non-greedy 两种采样下,acceptance length(AL)和 throughput(TPS)均稳居第一。代表性数字:

| target | benchmark | T | EAGLE-2 TPS | HASS TPS | PRISM TPS | vanilla TPS |
|---|---|---|---|---|---|---|
| LLaMA-2-7B | HumanEval | 0 | 283.84 | 305.31 | **316.16** | 96.10 |
| LLaMA-2-7B | CNN/DM | 0 | 218.83 | 235.41 | **255.08** | 92.77 |
| LLaMA-3-8B | HumanEval | 0 | 212.36 | 235.38 | **251.96** | 85.88 |
| LLaMA-3-8B | GSM8K | 0 | 197.66 | 216.75 | **237.41** | 85.98 |

整体对比:相对 EAGLE-2 平均 AL 提升 14.09%、TPS 提升 14.21%;相对 HASS 平均 AL 提升 5.69%、TPS 提升 6.10%。相对 vanilla auto-regressive,PRISM 的 TPS 加速比稳定在 2.4× 以上,LLaMA-2-7B 上 HumanEval 达到 3.29×。

CNN/DailyMail(长上下文摘要)上 PRISM 相对 HASS 的领先尤其明显,作者推测 step splitting 架构在长文档场景受益更大。

### Scaling laws(Figure 4–6)

- 与 EAGLE-2 / HASS 的对比:全数据规模(100K–800K)上 PRISM 的 AL 都更高;低数据区间(<200K),三者都还在涨,但 PRISM 起点和斜率都更优;高数据区间(>400K),EAGLE-2 / HASS 已饱和,PRISM 还在持续涨。
- 与 EAGLE-3 的对比(Figure 5):小数据 PRISM 数据效率更好,大数据二者收敛到相同 AL。作者明确承认这"可能是数据集复杂度有限"。
- step-wise 行为:PRISM 在前几步 acceptance 更高,EAGLE-3 在后几步更高,两者曲线都比 EAGLE-2 / HASS 更平。
- 消融(Figure 6):直接堆 2 个 transformer 但不做 step-wise 路由的对照模型,在所有数据规模都明显劣于 PRISM,说明收益来自"按步路由"而非"参数变多"。

### 超参数(Figure 7、8)

- batch size 越大,speculative decoding 收益越小(因为 LLM 转向 compute-bound),但 PRISM 在中等 batch 下仍有合理加速;
- tree topology 越大整体越好但收益饱和;固定验证 token 数时,**深而窄**的树优于浅而宽的树。

### 4090 实验(Table 5)

数字与 A800 同序,PRISM 同样领先;在 24G 内存的边缘卡上 LLaMA-3-8B 仍能以 PRISM 跑出 ~252 TPS,验证了在内存更紧的部署上的可行性。

## 6. 批判性分析

1. **"step-wise specialization"在主实验里只是 prefill / decode 双模块**。论文反复强调"为不同 draft 步分配不同参数",但 Section 4 末尾交代:"PRISM evaluated in the main experiments consists of two processing modules. While the first one is assigned uniquely to process the first prefill step, the second is responsible for all subsequent decoding steps."。换言之,主表里 PRISM 相对 HASS 的优势,本质是**多了一个专门服务 prefill 步的 transformer**,而不是真的把 6 个 decoding 步路由到 6 套参数。论文标题、Figure 2/3 和 motivation Figure 1 共同营造的"M 个模块对应 K 个 step"叙事,在主结果里并没有真正落地。

2. **第二阶段训练用"复制权重"初始化各模块,削弱了 specialization 的语义**。M 份 transformer 初值完全相同,只在第二阶段微调中分化。如果分化幅度有限,PRISM 实际接近"参数量 ×M 但功能相近"的集成模型,这恰好和上文"主实验只有 M=2"叠加,使得 PRISM 究竟在多大程度上利用了 step 间难度差异并不清晰。论文没有报告各模块训练后参数差异的度量。

3. **scaling 故事的内部矛盾**。Figure 4 强调 PRISM 在 600K 之后仍在涨而 EAGLE-2/HASS 已饱和,然而 Figure 5 又承认 PRISM 与 EAGLE-3 在大数据区间收敛、归因于"数据集复杂度有限"。如果数据集复杂度有限,Figure 4 里 PRISM 仍在涨的部分,合理解释也可以是"参数量翻倍带来 capacity 余量",而不一定是"step 路由本身有可扩展性"。该 confounding 没有被很好地控制。

4. **CNN/DM 优势的因果链不完整**。论文写"PRISM works exceptionally well, compared to other baselines on CNN/Daily Mail work load, outperforms HASS by potentially suggests the step splitting architecture may work better for long context tasks"——句子残缺(缺少具体百分比)且只是 speculate。要论证"长上下文受益更大",需要按上下文长度分桶分析或合成长上下文实验,论文并未提供。

5. **2.6× 加速的 reference 不清晰**。abstract 称"boosts the decoding throughput of an already highly optimized inference engine by more than 2.6×",但正文表格中 PRISM 相对 vanilla 的 TPS 比通常在 2.4–3.3× 之间,相对 HASS 仅 5%–10%。"2.6×"显然是相对 vanilla 的某个平均数字而非相对 SoTA drafter 的提升,容易引起误解。

6. **未充分考虑显存与 KV cache 切换的系统成本**。PRISM 把 drafter 总参数量翻 M 倍意味着多 M 倍的权重 HBM 占用;每步换模块意味着权重 cache miss 率上升,在 batch=1 这种极端 memory-bandwidth-bound 场景里,这一开销可能被 acceptance length 提升掩盖,但在更大 batch 下会先一步吃掉收益。论文把 batch size 实验作为附属(Figure 7)而没有展开 PRISM vs HASS 在 batch=4/8/16 下的对比。

7. **EAGLE-3 是否被公平比较存疑**。EAGLE-3 在 LLaMA-3-8B 上的 1.03B 参数量与 PRISM 的 2 ×(单 transformer block)在数量上不对等;论文只在 scaling 曲线上和 EAGLE-3 对比,但主表(Table 4 / 5)并未列 EAGLE-3 数字,使得"PRISM 全面超越 SoTA"的印象建立在跳过最强 baseline 的基础上。

8. **训练时间 1 天–2 周的成本未细分**。第二阶段训练每步要 backward 通过 M 个不同模块,M=2 时已经看不到明显成本,但若按论文叙事推到 M=6,context alignment + 第二阶段训练成本会是一个不可忽视的开销,论文没有给出 M 增长时的训练成本曲线。

## 7. AI Infra / MLSys 视角

这篇论文的可借鉴价值主要落在以下几条:

1. **"沿时间轴做 conditional computing"是一个值得继续挖的设计模式**。MoE 是沿 token 维度路由,PRISM 是沿 auto-regressive step 路由——这一思路可以推广到 multi-token prediction(如 Medusa head)、long generation 中的 chunked decoding、agent loop 中的"思考-行动"切换等场景。任何"步序列内难度/语义差异显著"的任务都值得问:能否给不同步段分配不同 expert?

2. **drafter 训练成本的工程化关注是个 underexplored 方向**。PRISM 的核心系统侧优势其实是"context alignment 的 forward + backward 局限在子网络里"。同样的 idea 反过来可以提示 monolithic drafter 训练上的优化:能否做 partial backprop、stage-wise checkpoint 来降低 context alignment 的训练开销?这对工业界把 drafter 训练塞进每周迭代节奏很关键。

3. **SGLang 集成的方法学**值得复用。多数 speculative decoding 论文只在 PyTorch eager 下报 acceptance length;真正进入 CUDA Graph + continuous batching 后会暴露调度、KV cache 管理、speculative branch resize 等大量工程问题。后续 drafter 工作应当默认要求"端到端 SGLang/vLLM/TRT-LLM 数字"作为 baseline。

4. **可操作的延伸研究方向**:
   - **真正的 K=6 配置**:用实际的 6 个独立模块跑主实验,验证"step-wise specialization"是否真的能持续涨点,还是 M=2 之后边际收益递减。
   - **router 学习**:目前 `f_map` 是手写的 surjection,可以引入轻量学习 router(类似 Soft MoE 的 gating)按 token 难度动态分配模块。
   - **跨模块差异度量**:训练后量化各模块参数距离 / activation 分布距离,验证 specialization 真实发生。
   - **batch scaling**:在 batch=8/16 下系统比较 PRISM、HASS、EAGLE-3 的 TPS 与 GPU memory footprint,得到部署侧真实 trade-off 曲线。
   - **结合 disaggregated speculative decoding**(SwiftSpec)、SLO-aware speculative decoding(AdaServe):drafter 内部的 step 路由可以与系统级的 draft / verify pipeline 异步化结合,在不同 SLO 下选择不同 M。
   - **训推一体的扩展**:RL rollout 加速(论文 Section 5 提到的 RhymeRL)中,大量长序列生成场景天然适配 PRISM 的"后段难度大"前提,值得直接迁移。

5. **对小规模团队的启发**:PRISM 走的是"用现有 drafter 做架构小改 + 训练流程重设"的路径,没有自研新硬件、新 kernel,这种"算法-训练流程协同设计"的低门槛优化路径对没有大量算力的实验室而言是一个可复制的范式。

---

## 8. 总结

PRISM 把 conditional computing 的思想从"沿 token"迁移到"沿 auto-regressive 步",通过让不同 draft 步走不同 transformer 模块,实现 drafter capacity 与单步推理成本的解耦。在 6 个 benchmark、2 个 target 模型上 PRISM 相对 EAGLE-2 / HASS 取得稳定的 5%–14% TPS 提升,并在 SGLang 真实推理引擎上验证了端到端有效性。主要贡献是提出了一种新的 drafter 设计范式,适用对 LLM decoding throughput 敏感、batch=1 或 batch 较小的场景。主要局限是主实验只用了 M=2 模块,导致论文标题与实际验证之间存在一定 gap;scaling 故事在大数据区间被自己的 EAGLE-3 实验弱化;与 SoTA 的 EAGLE-3 缺乏在主表里的并列对比。
