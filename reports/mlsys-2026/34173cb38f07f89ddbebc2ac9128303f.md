# Chakra: Advancing Performance Benchmarking and Co-design using Standardized Execution Traces

**作者**:Srinivas Sridharan, Taekyung Heo, Louis Feng, Zhaodong Wang, Matt Bergeron, et al.
**单位**:Meta, Georgia Institute of Technology, Hewlett Packard Enterprise
**会议**:MLSys 2026(原始为 MLBench'23 workshop 论文)
**链接**:https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**:[[34173cb38f07f89ddbebc2ac9128303f.pdf]]

---

## 1. 背景

现代深度学习依赖大规模分布式训练,训练任务被按数据并行、模型并行、流水线并行或 3D/4D 混合并行拆分到 GPU/TPU 这类 NPU 上。平台如 Meta ZionEX、Google Cloud TPU、NVIDIA DGX 层出不穷,最优并行策略仍是活跃研究方向。

业界已经普遍认同:硬件-软件协同设计(HW-SW co-design)是 AI/ML 平台持续进化的关键。现有的"完整工作负载基准"如 MLPerf 在系统落地后做公平比较上发挥作用,但它并不适合 **早期**、**快节奏**的体系结构探索,模拟器/仿真器面向未来系统做 what-if 分析时缺乏趁手的输入。

更深的一层矛盾是 **产权壁垒**:SOTA 模型和自研加速器往往分属不同公司(例如 Meta 的 DLRM 跑在 NVIDIA GPU 上),双方都无法把完整细节交给对方。云厂商现状是把模型参数表附带 NDA 发给硬件厂商,但无法复现实际负载;硬件厂商和学界则只能从 MLPerf 等基准反推,容易针对个别 use case 过度优化、违反 Amdahl 定律。

---

## 2. 要解决的问题

论文把 AI 系统协同设计中的 infra 空缺归纳为三条:

1. **没有通用的执行轨迹交换 schema**:PyTorch、TensorFlow 等各自产出格式不同的 trace,既无法跨组织交换,也没有一条面向"性能建模"视角设计的公共字段定义。
2. **缺少配套工具链**:转换器、可视化、trace feeder、replay 基准都需要各队重复造轮子,瓶颈定位与 debug 效率低。
3. **无法合成可共享的轨迹**:直接共享生产 trace 会泄露模型 IP;要做未来系统的性能投影,还需要能扫描到远超当前规模(更多 NPU、更高带宽)的合成轨迹。

目标是给 AI 系统协同设计造一条"标准化流水线":从框架产 ET → 转成公共 schema → 供 simulator/emulator/benchmark 消费 → 再通过生成模型合成更多可共享轨迹。

---

## 3. 洞察与设计

**关键洞察**:把协同设计所需的信息(compute/memory/communication 算子的尺寸与依赖)与"模型本身/数据集"解耦是可行的——这些信息在 PyTorch/TensorFlow 的执行过程中已经自然产生,只是没有被显式导出。只要编码算子维度和依赖而不编码权重、层定义、数据,就能在保留性能建模全部要素的同时,天然脱敏模型 IP。这是整个框架能成立的前提。

基于这一洞察,Chakra 把"执行轨迹"(Execution Trace,ET)抬升为第一等公民,配套以下几块组件(Figure 1 汇总):

![Figure 1: Chakra 基础设施总览](../../markdowns/mlsys-2026/34173cb38f07f89ddbebc2ac9128303f/images/34ca1ea5084ecea95bf8eb85abc7240335af41dd7a0159ffe492cb828995bcf7.jpg)

- **Chakra ET schema**(§3):极简可扩展的 protobuf-like schema。`Node` 必填字段只有 `id / name / type / parent / attribute`,`type` 是 enum(INVALID / MEM_LOAD / MEM_STORE / COMP / COMM_SEND / COMM_RECV / COMM_COLL),所有领域相关元数据塞到 `AttributeProto` 这种键值对里(设计灵感来自 ONNX 的 `AttributeProto`)。`parent` 是 repeated uint64,用来编码节点依赖。
- **轨迹收集两条路径**:(a) 通过扩展 PyTorch 的 Execution Graph Observer 从真实执行中导出 trace;(b) 通过生成模型合成可共享轨迹。
- **生成模型**(§4):关键抽象是"master trace"——把 ?? 个 rank 各自的 per-NPU trace 做无损压缩成一份 master,再能反向拆成 ?? 份,这样可以避免合成时破坏集合通信(collective)的跨 rank 约束。在 master trace 上训练一个 **分层** 生成模型,包含 Comm Length Generator → Job Size Generator → Comm Type Generator → Message Size Generator(Figure 2),每个子模块可以单独替换/调试,比单一黑盒模型可解释性强很多。
- **设计选择讨论**(§3.3):
  - *Pre-execution vs. post-execution*:schema 兼容任意阶段。预执行 trace 适合 what-if 投影但更贴近模型本身;后执行 trace 精确但绑定具体系统。
  - *Multi-node 表示*:每个 NPU 一份 trace,简化收集和 replay,代价是失去全局调度重分派能力。
  - *Execution graph vs. execution trace*:graph 面向框架内部精确执行优化(PyTorch/TensorFlow/ONNX),trace 面向 replay/simulation,应该 framework-agnostic。

## 4. 实现细节

- **schema**:`Node` + `AttributeProto` 两张表(Table 1/2)。`type` 枚举保持最小,所有语义延展都走 `attribute` 的键值列表,三种值族 `float / int / string` 及各自的 repeated 版本。protobuf 风格,跨语言友好。
- **ET Converter**:目前支持 PyTorch JSON trace(compute 节点由 `duration` 字段识别,communication 节点名为 `record_param_comms`,子节点名以 `nccl:` 起头,用来抽取 comm type 和 size)和 FlexFlow graphviz(需改 FlexFlow 源码补 metadata,集合通信在 FlexFlow 里拆成 P2P,要二次整合)。TensorFlow 列为 future work。
- **Visualizer**:`graphviz → PDF` 输出(Figure 3),可用来做 simulator debug 辅助。
- **Timeline Visualizer**:读取 callback-based simulator 的 CSV,借 Chrome `chrome://tracing` 的 trace event profiler 呈现 per-NPU 时间线,能直观看到 compute/comm 是否重叠。
- **Test Case Generator**:C++ 类库方便手写 ET,自带 DP/MP/PP 示例。
- **Trace Feeder**:C++ 库,供 simulator 消费轨迹。已做 ASTRA-sim 接入。
- **ASTRA-sim-v2 集成**(§6.2):替换原本基于文本输入+手写训练 loop 的 workload 层为"按 ET 驱动"(Figure 5)。graph execution engine 每次放出所有 dependency-free 的节点,节点完成后触发依赖解除,直到所有节点耗尽。节点耗时有两种来源:(a) 直接读 ET 里的实测值(建模原系统),(b) 交给 ASTRA-sim-v2 基于 NPU/网络模型计算(建模未来系统)。该版本同时新增了"同一时刻不同 NPU 跑不同 op"的能力,突破了 v1 "同步执行相同 op"的限制。

![Figure 5: ASTRA-sim-v2 接入 ET 后的分层结构](../../markdowns/mlsys-2026/34173cb38f07f89ddbebc2ac9128303f/images/3347b43886a2c83cb549ea1b38049eb3aa5b2345ae4a349289f850b93d98bb6f.jpg)

## 5. 实验结果

论文的实验部分实质上是 "ASTRA-sim-v2 驱动的性能投影 case study",而不是对 Chakra 本身的基准评估。

**模型与并行策略**:MLP(合成 6 层模型,实验 MP / MLP-DP-MP / MLP-MP-DP 三种)、Transformer(165M 参数,MP-DP 混合 + ZeRO-2)、DLRM(embedding 用 MP,MLP 部分用 DP)。Transformer 和 DLRM 的 ET 由真实模型转成 Chakra schema。

**目标拓扑**:
- 2D-torus:8×8,link bandwidth 62 GB/s
- DGX-2-like:分层交换式,dim1 600 GB/s,dim2 37.5 GB/s

**实验 1:扩大 NPU 数量**(4 / 16 / 64,Figure 6)

| 模型 | 2D-torus | 观察 |
|------|----------|------|
| Transformer | 单调提升(64 NPU 达 3× 归一性能) | compute 占主导(4 NPU 下 compute ≈ 25× comm),扩容明显降低 compute 时间 |
| MLP-DP-MP / MLP-MP-DP | 16 NPU 达 ~2.15×,64 NPU 回落到 ~1.75× | exposed comm 开始压过 compute 节省 |
| MLP-MP | 单调下降,64 NPU 归一性能 ~0.3× | exposed comm 完全主导(Figure 7b:compute 5 vs. exposed comm 360) |
| DLRM | 略微下降 | comm/compute 比不利 |

![Figure 6: 不同 NPU 数下的归一化性能](../../markdowns/mlsys-2026/34173cb38f07f89ddbebc2ac9128303f/images/c87f283a6b4a3e75d82e5f22f4fbc6945c49b0d537018e858016d3f5b224f624.jpg)

Figure 7 的 breakdown 对比特别直观:Transformer 在 64 NPU 下 compute=4, exposed comm=19,整体仍减少;而 MLP-MP 在 64 NPU 下 compute=5, exposed comm=360,通信完全把收益吃光。

**实验 2:网络带宽扫描**(Figure 8)。DGX-2-like 在 dim2 带宽较低时常不如 2D-torus;MLP-MP 对带宽最敏感(最低带宽组合下 exposed comm = 128× compute),Transformer 对带宽最不敏感。

整体结论是:这套链路能正确复现"通信饱和、compute-dominant 模型受益于扩容"等基本物理规律,作为 Chakra → ASTRA-sim-v2 端到端流通性的 PoC 是成立的。

## 6. 批判性分析

- **"PoC 级"实验,缺失验证方案**。论文用 ASTRA-sim-v2 给出了若干归一化趋势,但没有把任何一个 Chakra ET 驱动的仿真结果和 **真实硬件** 的测量值做交叉验证。一个建立在 ET 之上的协同设计框架,首先要证明 replay/simulation 在同拓扑下的误差(迭代延迟、utilisation)低于某个阈值,而论文只在 §6.3 引用了已发表的 critical-path 模型(< 10 % GMAE)作为旁证,没给 Chakra 链路自身的数字。
- **生成模型描述过于草率**。§4 提到用 Gaussian Mixture 拟合 message size,用分层 generator 生成 comm sequence。但 (a) 训练数据规模、来源、split;(b) 合成轨迹与真实轨迹的 KL / wasserstein 距离;(c) replay 成功率之外的保真度指标都缺失。"tested on replay system and found they work correctly"这种定性描述不足以支撑"能代表生产负载"的主张。
- **混淆了"schema 极简"与"生态通用"**。把所有领域信息甩到 `AttributeProto` 的 key-value 里,确实让 schema 本身极薄,但把复杂度转嫁给了每一个 converter、simulator、visualizer——它们都要自己理解"PyTorch 约定下 comm type 写在 nccl: 前缀的 child 节点里"这类隐式约定。不同生产者写入的 attribute 名字不统一时,跨组织可交换性仍然会破坏。schema 之上需要一份规范化的 attribute 字典,论文没有提供。
- **TensorFlow 支持、其他并行范式(PP、MoE、推理)、非 NCCL 通信栈**全部缺席。对一篇主张"universal schema"的文章来说,只覆盖 PyTorch + FlexFlow 是不够的。
- **"每 NPU 一份 trace"的设计** 在当下 MoE / 动态调度场景下会引入严重的保真度折损,作者在 §3.3.2 承认了这一点但没有对应的缓解方案。
- **模型 IP 脱敏的强度未验证**。声称 ET 去掉模型细节即可脱敏,但 trace 本身带有精确的 tensor size、通信量、并行策略——这些在 LLM 时代几乎就等价于暴露了模型规模和并行配方,是否还能算"obfuscation"取决于威胁模型,论文没有给出攻击分析。
- **定位偏 position paper**。全文更像一个工作进展报告 / 社区号召,而不是一篇有可复现结论的 systems 论文。这也解释了为什么以 workshop 文本形式存在,但被收录到"MLSys 2026"目录下略显尴尬——读者需要了解 Chakra 当前更成熟的版本(例如 MLCommons 下的延续工作)才能获得完整上下文。

## 7. AI Infra / MLSys 视角

Chakra 本身就是 MLSys 基础设施工作,对 AI Infra 方向启发如下:

- **把"trace"当作协同设计的公共货币**。思路可直接迁移到推理侧:LLM serving 的 compute/comm/kv-cache 行为同样具备"高度可trace、又高度 IP 敏感"的双重特征,现成的 Chakra schema 经扩展后能做推理系统仿真的输入(比如给 vLLM / TensorRT-LLM 的 forward pass 加 Chakra ET 导出)。
- **"master trace"做跨 rank 生成建模** 是一个值得复用的抽象。对 expert-parallel/tensor-parallel 并行,同步点和集合通信存在强跨 rank 约束,直接对 per-rank trace 建模会破坏合法性;master trace 思路可以推广到 MoE 路由、pipeline bubble 等带"全局一致性约束"的场景。
- **future work 可操作的切入点**:
  1. 对当下 LLM 训练(例如 Megatron-LM / Megatron-Core 常见 3D parallelism + SP + expert parallelism 组合)做一次 Chakra ET 端到端流通的 fidelity 验证(replay 迭代时间误差、comm 利用率误差)。可以补上论文缺失的"Chakra 自身准确度"这块。
  2. 扩展 schema 支持 **异步/overlap 细粒度语义**:现代分布式训练的 compute-comm overlap 已经依赖 stream、graph scheduler,粒度细于节点级依赖,需要补 edge 上的时间锚点而不是只有 `parent`。
  3. 设计 **trace 合成器的 fidelity 评估方法**:从 collective sequence similarity、per-iteration bandwidth profile、scaling law 三个层面给出可量化的合成保真度指标。
  4. 探索 **trace 级模糊化 / 差分隐私**:对 tensor size、message size 做加噪处理后,评估 simulator 对拓扑设计决策的鲁棒性,解决第 6 节提到的"obfuscation 强度不足"问题。
  5. 把 Chakra ET 做成 **LLM serving benchmark 的底座**:把 inference 的 prefill/decoding 异构请求流编码成 ET,给 SLO-aware 调度器和 serving simulator 提供可共享输入。

---

## 8. 总结

Chakra 提出一套面向分布式 ML 系统协同设计的 **标准化执行轨迹 schema** + 配套工具链(converter、visualizer、trace feeder、test case generator、生成式轨迹合成器),并通过把 ASTRA-sim 升级到 v2(由 ET 驱动)给出端到端 PoC。其最大价值在于为 HW-SW 协同设计圈划出了一个共同语言——厂商可以共享脱敏后的 ET 做性能投影,学术界可以借助它在 ASTRA-sim/SST 这类仿真器上复现生产级负载。但作为一篇 position paper 性质的 workshop 论文,在自身保真度验证、生成模型严谨性、schema 规范化方面都留有明显空白,需要把它视作 MLCommons Chakra 生态的起点而非终点。适合 AI 基础设施研究者作为背景资料阅读,并结合 Chakra/ASTRA-sim 当前代码库理解真实落地形态。
