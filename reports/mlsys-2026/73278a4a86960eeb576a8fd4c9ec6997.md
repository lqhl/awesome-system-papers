# Hawkeye: Reproducing GPU-Level Non-Determinism

**作者**:Erez Badash, Dan Boneh, Ilan Komargodski, Megha Srivastava
**会议**:MLSys 2026
**链接**:[MLSys 2026 Proceedings](https://proceedings.mlsys.org/paper_files/paper/2026) · [GitHub: badasherez/gpu-simulator](https://github.com/badasherez/gpu-simulator)
**源文件**:[[73278a4a86960eeb576a8fd4c9ec6997.pdf]]

---

## 1. 背景

现代大模型训练与推理几乎完全依赖托管式 ML-as-a-Service 平台(AWS SageMaker、Google Vertex AI、Azure ML、Replicate、TogetherAI 等),用户把大量算力外包给云端时,如何确认服务商确实按合同跑完了指定模型、没有 backdoor、没有偷偷缩短训练步数、没有换小模型应付推理?这是 **verifiable ML** 研究的核心问题。

传统密码学 verifiable computation(zk-SNARK、STARK、Bulletproofs 等)的一条基本假设是**可验证的计算必须是确定性的**。但现代 ML 工作流跑在 GPU Tensor Core 上,涉及 FP16/BF16/FP8 的混合精度矩阵乘、浮点非结合性、rounding mode、subnormal 处理和 accumulation order,这些都受硬件实现影响。论文给出一个具体的反差:同样的 FP16 向量点积 $A \cdot B^T$,在 L40S(Ada Lovelace)上算出 0,在 A100(Ampere)上算出 0.0020。这些微小差异在一次推理或训练中累积,足以造成输出 token 不一致、权重漂移,从而让「auditor 跑一遍对比结果」这种最朴素的验证策略完全失效。

已有的应对要么是强制关闭非确定性硬件特性(代价是数倍 slowdown)、要么是给 intermediate 结果做额外 rounding 存档(存储代价大)、要么干脆 hand-wave「差异足够小可以忽略」(缺乏对 adversarial 行为的保证)。

---

## 2. 要解决的问题

论文要解决一个明确且范围克制的子问题:**在一块已知型号的 NVIDIA GPU 上执行过的 Tensor Core `mma` 指令(16×16 tile 的 MatMul-Accumulate),能否在 CPU 上做到 bit-exact 重现,并且不需要修改原 GPU kernel?**

拆成具体挑战:

1. Tensor Core 内部 pipeline(mixed-precision 乘法、截断对齐、分组累加、最终截断到输出精度)是闭源的,IEEE 754 只规定每个单点浮点操作,未规定硬件的 accumulation order、internal mantissa 位宽、rounding mode、subnormal 处理策略。
2. 非结合性意味着同一 dot product 在不同 accumulation 次序下得到不同 bit pattern,可能跨两个相邻 GPU 架构(Ampere → Hopper)结构就变了。
3. 单纯用 `cuobjdump` 反汇编 SASS / 读 PTX 手册无法解决 —— 硬件层级的数值行为远比指令级手册精细。需要一套能**外推得到数值 pipeline**的 black-box 测试方法。

---

## 3. 洞察与设计

**关键洞察**:Tensor Core 的 mma 指令虽然是硬件黑盒,但其浮点数值行为(累加分组结构、内部 mantissa 位宽、shift 时的 rounding mode、subnormal 归一化、最终截断)的**每一维都可以通过精心设计、只用一次 mma 调用的"微分探针"测试独立探测出来**,且这些维度一旦确定下来,在跨架构(Ampere/Hopper/Lovelace)和跨精度(FP16/BF16/FP8)切换时变化有限,可以用同一套 test suite 枚举重建。

基于此洞察,Hawkeye 设计了 5 类 targeted test,每类测试用特殊构造的 16×16 tile 把整个 dot product 结果的 bit pattern "压缩"到对某一个数值行为参数敏感:

1. **Summation Dependency and Order Test**:用"计算中性子组"(computationally neutral subgroup)的思想 —— 若把某个子集的元素调成互相抵消(和为 0),最终 bit-level 结果不变,就说明这个子集是硬件累加树中的一个"节点"。穷搜 16 个 product 的子集,从中性子集的嵌套结构推断累加树。
2. **Internal Precision Detection Test**:两个大数互相抵消 + 一个小数 $2^{-c}$,扫描 $c$ 直到小数被舍入掉,$c-1$ 就是内部 mantissa 位宽。
3. **Rounding Mode Detection Test**:构造刚好处于 "nearest tie" 边界的产品,观察最终结果属于哪个方向,四次测试足以把 5 种常见 rounding mode 全部排除到只剩 truncation。
4. **Post-Multiplication Normalization Test**:看未归一化的 raw product 是否会扩大对齐 shift 从而吞掉小数,以此判断归一化发生在乘法后还是累加后。
5. **Subnormal Behavior Detection Test**:把一个 subnormal 数乘一个大 normal 数得到范围内但 mantissa 退化的结果,再看小数能否幸存。

通过这 5 项测试,论文对 Ampere + FP16 得到了一张清晰的 pipeline 图景:

![Figure 1. Ampere Pyramid 累加结构](../../markdowns/mlsys-2026/73278a4a86960eeb576a8fd4c9ec6997/images/c08e4656cc26ad67ee77db36710bcba6e3ead00606161af873cdc3101e2def58.jpg)

Ampere 采用**两阶段金字塔**:初始 accumulator C 先与前 8 个乘积 sum 得到中间结果,再与后 8 个乘积 sum 得到最终结果;内部 mantissa 24 bit(等价于 FP32);alignment shift 用 **round-towards-zero**(truncation);乘法后**不归一化**,raw significand 直接送进累加;subnormal 输入相乘**不重新归一化**;最终截回 FP16 同样是 round-towards-zero。

![Figure 2. Hopper 单阶段累加结构](../../markdowns/mlsys-2026/73278a4a86960eeb576a8fd4c9ec6997/images/0b16023b2f289b87d7c9da9fe386293f48092f84ca54febc8cfe02e3dd7d573b.jpg)

Hopper 则改成**单阶段 16 路累加**:C 与 16 个乘积在同一级 Σ 中完成;内部 mantissa 25 bit(比 Ampere 多一位);其他行为与 Ampere 一致。Lovelace 与 Ampere 同构。BF16 下 Hawkeye 还需额外测试 FP32 累加的 out-of-range 处理(temporary overflow 允许 + 最终 saturate 到 ∞)和最小有效贡献指数(Ampere 为 $2^{-156}$,Hopper 为 $2^{-157}$)。

## 4. 实现细节

- **硬件探针**:Hawkeye 用 inline PTX 直接调用 `wmma.mma.sync` 指令,在 BF16/FP16 场景下 PTX 编译到单条 `HMMA` SASS,确保测试刻画的是硬件本体而不是 CUDA lib 的 wrapper。
- **测试代码**:每个 targeted test 是一个自定义 CUDA kernel,分配 16×16 tile,精细填入前文所述的构造值,比较硬件输出与预期 bit pattern。
- **CPU simulator**:按恢复出的 pipeline 写一套软件模拟(Algorithm 12~14),分三阶段:(a) FP 乘法 + mantissa 左移 3 位扩展到内部精度;(b) Grouped Summation,用 truncating alignment shift 统一指数后做有符号定点加法;(c) 最终归一化并截断回输出精度。Ampere FP16 的 GroupSum 调用两次(前 8 + 后 8);Hopper 调用一次(16 合一)。
- **代码开源**:https://github.com/badasherez/gpu-simulator,覆盖 Ampere/Hopper/Lovelace × FP16/BF16/FP8 三种精度组合(FP8 是 E4M3 的 Hopper 扩展实现)。

## 5. 实验结果

**正确性**:在 Ampere、Hopper、Lovelace 上分别生成 100,000 个随机 16×16 tile(FP16/BF16/FP8 各精度下),比对硬件 mma 输出与 CPU simulator 输出 —— **100% bit-exact 一致**。

**性能基线**(4096×4096 矩阵在 Apple M4 Pro CPU 上跑,10 次平均):

| Precision | Architecture | Time (s) | Std (s) |
|---|---|---|---|
| FP16 | Ampere | 50.8 | 3.2 |
| FP16 | Hopper | 47.2 | 2.5 |
| BF16 | Ampere | 52.5 | 2.9 |
| BF16 | Hopper | 48.2 | 2.6 |
| FP8 | Hopper | 40.6 | 0.6 |

论文把性能定位为"baseline",承认这是未经优化的 Python/C 模拟,没用整数化重写,也没跑 GPU 版模拟器;verifiable ML 场景下 auditor 只需要一次重演,慢一点可以接受。

## 6. 批判性分析

1. **把"MatMul 可复现"包装成"verifiable ML 可行"有跳跃**。Abstract 和 Introduction 反复强调"解决了 verifiable ML 的一个根本障碍",但论文只覆盖了 Tensor Core 的 16×16 tile MatMul-Accumulate 这一条路径。真实 LLM 训练/推理里大量吃时间的是 attention(fused softmax + dropout + matmul)、LayerNorm、RoPE、activation,它们各自有独立的数值路径,paper 在 §9 的 future work 里把这一大段"higher-level operations... require additional reverse engineering"轻描淡写地甩出去。以当前成果直接声称"paves the way for efficient and trustworthy third-party auditing"与覆盖面并不匹配。

2. **性能开销对真实 workload 是灾难级**。4096×4096 单次 FP16 MatMul 要 47–53 秒 CPU 时间,对比 H100 tensor core 同尺寸 ≈0.2ms,慢了 **5 个数量级**。paper 辩解"auditor 只需重演一次",但 verifiable training 场景下,单次 GPT-3 量级训练大概要跑 $10^{20}$ 级别的 FLOP,"auditor 重演一次"意味着按当前 simulator 性能需要几个世纪的 CPU 时间。paper 没给出从 1 次 4096 MatMul 到完整训练审计的开销估算,这个缺失让"可行性"宣称显得不扎实。

3. **对 "knowing which GPU was used" 这一前提缺乏对抗性讨论**。论文依赖 auditor 知道原执行用的是 A100/H100/L40S 哪一款。在 adversarial 设定下,一个恶意服务商完全可以声称自己用了 H100 而实际用 A100,两种架构的输出差异正好是 paper 第 1 节给的反例 (0 vs 0.0020)。如何证明"claimed GPU = actual GPU"?paper 只字未提,但这恰恰是 verifiable ML 最需要解决的中间层。

4. **test suite 的完备性没有理论保证**。"5 个维度的 targeted test 覆盖了 Tensor Core 所有数值行为"是基于 **Ampere/Hopper/Lovelace × 三种精度 = 9 种组合观察得出的经验结论**,没有 formal argument 证明不存在"第 6 维"需要探测。例如 NaN/Inf propagation、denormal arithmetic 的跨架构差异、tensor memory accelerator(TMA)在 Blackwell 上带来的新行为,都可能打破假设。

5. **100% bit-exact 的验证样本量不足**。100,000 个随机矩阵听起来很多,但在 $2^{256}$ 级的输入空间里连沧海一粟都不是;论文声称"worst-case bit-exact"却只做随机采样、没做对抗性构造(比如专门挑能触发 subnormal overflow、NaN propagation、saturation edge 的矩阵)。一个有 adversarial edge case 泄漏的 simulator 在 adversarial verifiability 下是不合格的。

6. **Hopper 25-bit mantissa 的结论仅从实验外推**。Ampere 24-bit 对应 FP32 accumulator 是已知的 NVIDIA 白皮书事实;Hopper 多出 1 bit 是 paper 独立观察,但没有与 NVIDIA 官方文档交叉核对。如果这个 bit 来自某种 guard bit 或 post-round offset 而不是真正的内部 mantissa 宽度,后续扩展到 Blackwell/FP4 时逆向规则可能失效。

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 研究有多个层面的价值:

1. **硬件数值行为刻画的方法论本身就是贡献**。即便不关心 verifiable ML,"computationally neutral subgroup"这种用**抵消式构造**把一维数值行为隔离出来的技巧,可以直接搬到对 LayerNorm 融合 kernel、FlashAttention block-softmax 归一化 order、NCCL all-reduce reduction tree 等任意模糊的数值 pipeline 做 reverse engineering 上。对 AI Infra 团队做**跨硬件数值等价性验证**(例如"我们的 TRT-LLM backend 跟 PyTorch eager 差在哪一步 rounding 上")是现成工具。

2. **跨架构 bit-exact 仿真可直接服务 determinism 工程**。Thinking Machines Lab 2025 年关于"defeating nondeterminism in LLM inference"的 blog 正是论文引用对象。Hawkeye 把 determinism 的**硬件侧**问题从"只能关掉加速"降级为"CPU 侧一次性重演",这可以用来做**推理端回归测试基座** —— 每次模型更新后在 CPU simulator 上重算几个 canary batch,对比线上 GPU 输出,做端到端数值监控。

3. **值得跟进的 future work**:
   - 把 Hawkeye 的 suite 扩展到 **attention / LayerNorm / softmax** 的 fused kernel,特别是 Hopper TMA + cutlass 的 persistent kernel 模式下,output 并不是一次 mma 能覆盖的。
   - 与 **zkML / TEE / Verde 这类 verifiable training 框架集成**,Hawkeye 产出的 CPU reference 正好可以做 probabilistic spot-checking 的 oracle;结合 merkle commitment 可以把 auditor 开销从 O(全部训练) 降到 O(采样步数)。
   - 探索 **Blackwell / B200 / FP4** 的数值行为,看是否出现前 5 维测试无法覆盖的新特性。
   - 研究 **non-NVIDIA 加速器**(AMD MI300、Google TPU、Intel Gaudi)的 systolic array / matrix engine 行为,可能需要扩展 suite,但基本方法论可迁移。
   - 一个有意思的逆向切入点:能否用 Hawkeye 来做**恶意 GPU 行为检测**?比如服务商用"剪枝过的" silicon 或者降级版 H100,通过比较几次 canary mma 的 bit pattern 与"正品 H100" reference,可以在不触碰 kernel 代码的前提下探测硬件欺诈。

4. **对小团队的启发**:这篇论文的工作量(两位一作 + 主要实验 ≈ 几千行 CUDA/Python)其实不大,但科学价值很高,说明**把成熟领域的一个"大家都当成黑盒"的假设做扎实的逆向**就是值得发表的系统工作。类似的机会在 AI Infra 里到处都是(比如 NCCL 的 reduction order、cuBLAS 的 split-K 策略、FlashAttention 2/3 的 masking 精度),都可以用 Hawkeye 式的 black-box 探针方法攻克。

---

## 8. 总结

Hawkeye 通过一套可组合的 targeted test,把 NVIDIA Tensor Core 在 Ampere/Hopper/Lovelace 架构、FP16/BF16/FP8 精度下的 16×16 MatMul-Accumulate pipeline 完整逆向出来,并实现了 CPU 上 100% bit-exact 的重演,为 verifiable ML 这一长期被 GPU 非确定性阻挡的研究方向提供了最底层的可行性基础。其核心方法论——用"计算中性子组"等抵消式构造隔离硬件数值维度——在任何涉及跨硬件/跨 backend 数值一致性的 AI Infra 工作中都具备直接参考价值。主要局限在于:覆盖面仍限于 MatMul 本身、CPU 重演开销比 GPU 高 5 个数量级、对"auditor 如何可信地知道原 GPU 型号"这一前提没有讨论,因此离真正可部署的 verifiable ML 还差 fused kernel 逆向、性能优化、GPU 身份验证三块关键拼图。
