# A Lightweight High-Throughput Collective-Capable NoC for Large-Scale ML Accelerators

**作者**:Luca Colagrande, Lorenzo Leone, Chen Wu, Tim Fischer, Raphael Roth, Luca Benini
**会议**:MLSys 2026
**链接**:https://proceedings.mlsys.org/paper_files/paper/2026

## 1. 背景

随着 Transformer 模型规模呈指数级增长,大规模 ML 加速器对算力的需求也在飞涨。现代加速器(如 NVIDIA Blackwell、Cerebras WSE-3、Tenstorrent Blackhole、SambaNova SN40L、Meta MTIA)纷纷在单芯片上集成成千上万个处理单元(PE),通过 2D mesh 拓扑组成 tile-based manycore SoC。

然而,过去 20 年峰值 FLOPS 提升了约 60000×,而 DRAM 带宽只增长了约 100×。算力与数据移动之间的差距越拉越大,使得绝大多数 ML 工作负载已经从 compute-bound 转向 memory-bound / communication-bound。在这样的体系结构下,片上集合通信(collective communication)——尤其是 broadcast、reduction、barrier——成了制约性能扩展的关键瓶颈。

虽然分布式系统层面已经有比较成熟的硬件加速方案(如 NVIDIA SHARP、NCCL),但 *片上* 集合通信的硬件支持还极少:历史上的 NoC 多关注 cache 一致性的多播,且只考虑短确认消息的 reduction;算术 reduction 一直被认为面积成本过高,不适合放到片上网络里。

## 2. 要解决的问题

作者要解决的核心问题是:**如何在 tile-based ML 加速器上以低硬件代价提供高吞吐的片上集合通信**。具体拆成几个子问题:

1. **多目的地寻址的可扩展编码**——一次 multicast 请求要表达多个目的节点,且编码开销不能随节点数线性膨胀。
2. **AXI 协议下 multicast 与 reduction 的耦合**——multicast 写请求会产生多份 B 响应,网络必须就地聚合;反之 reduction 请求会产生 multicast 响应。两者必须同时支持。
3. **算术 reduction 的硬件成本**——若在每个 router 内部塞 FPU,面积代价不可接受。已有工作普遍只支持「短消息聚合」类 reduction。
4. **避免死锁与公平仲裁**——multiple 并发 reduction 在 mesh 中路径交叉时可能死锁,需要无显式 deadlock-recovery 的设计。
5. **要给程序员提供可用的同步原语**——单纯支持数据 multicast/reduction 不够,barrier 等基础同步原语也要硬件加速。

## 3. 洞察与设计

**关键洞察**:

- **(DCA 的根本前提)** 计算 tile 内的 FPU 阵列已经是大块面积投资,且在等待数据搬运时往往空闲;与其在 NoC 里再造一组算术单元,不如让 NoC 直接「借用」cluster 内的 FPU——类似 DMA 借用内存端口。这就是 **Direct Compute Access (DCA)** 的来源。
- **(地址编码)** 在结构化 mesh 下,用「目的地址 + mask」的方案表达多目的地,编码长度只随地址空间对数增长,且与目的节点数无关——天然适合大规模加速器。
- **(协议级耦合)** AXI 的 AW + W + B 三段式请求-响应天然让 multicast 与 reduction 成对出现,因此硬件设计也应作为对偶方案统一处理。
- **(同步原语)** Barrier 的开销主要不是计数器更新,而是中断分发与原子 read-modify-write 链路;用网内 LsbAnd reduction + multicast 中断可以把 barrier 的每节点开销从 ~3 cycle 降到 ~1 cycle。

**设计方案**——基于 SoA 的 FlooNoC(同样是 ETH 团队的工作)做扩展:

- **Multi-address encoding**:沿用之前的 multicast XBAR 工作,把 (X, Y) 坐标 mask 塞进 AXI 的 AWUSER 字段,bit = 1 表示对应坐标位为「don't care」。NI 把地址 mask 翻译成 (X, Y) mask 写入 flit 头。
- **Multicast Router 扩展**:在 `xy_route_fork` 内根据 mask 同时选中多个 output 端口,通过 `stream_fork` 复制 flit。要求所有目标端口都 ready 才接收输入,避免阻塞。
- **Parallel Reduction Router 扩展**:每个输出端口配备 `output_arbiter`,把 reduction packet 路由到 `reduction_arbiter`;`synchronization` 模块等齐所有源节点的 flit 到齐再 forward。3 种轻量算子:`CollectB`(响应聚合)、`LsbAnd`(barrier 用)、`SelectAW`(请求聚合)。死锁避免靠「每个 input port 一个独立的 sync 模块,被仲裁的 reduction 必能完成」。
- **Wide Reduction Router 扩展**:对宽数据(64-bit FP)做 reduction 的硬件代价高,因此每个 router 只放 *一个* 集中式 wide reduction unit,且每次只支持 2-input。Pipelined 算术单元配 hdr buffer 隐藏延迟,实现每周期一次 reduction。提供 `offload` 端口给外部 compute 资源。
- **Direct Compute Access (DCA)**:Snitch cluster 暴露三个 512-bit 端口(2 个操作数 + 1 个结果)给 NoC router 的 offload 接口。512-bit 操作数被拆成 8 个 64-bit slice,送给 8 个 SIMD FPU 并行计算;DCA 请求与 core 的 FPU 请求通过 tag 区分、路由结果。在 Snitch cluster 上每周期可执行 8 次 FP64 或 64 次 FP8 的 reduction。
- **System Address Map**:为了简化 mask 翻译,要求 collective-targetable 子区域是 (X, Y, W, H) 子 mesh,W、H 为 2 的幂、地址连续按 Y-major 排列——多数情况下用 mesh padding 即可满足。

## 4. 实现细节

- **基础架构**:在 FlooNoC(separated narrow + wide network,前者 64 bit、后者 512 bit)之上扩展。所有改动保持 AXI4 协议兼容。
- **Cluster**:8 个 RV32I Snitch 核 + 第 9 核 DMA,共享 128 KiB L1 SPM,每核挂一颗 64-bit SIMD FPU。
- **基线 SoC**:5×4 mesh,memory tile 内含 1 MB L2 SPM,compute tile 内挂 Snitch cluster。
- **工艺与时序**:TSMC 7 nm,FUSION COMPILER 2024.09,1 GHz 频率目标(SS,−40 °C,0.675 V)。所有改动 *无* 时序回退。
- **Barrier 实现**:每节点对 cluster-0 L1 SPM 内的中心计数器做 `amoadd`(SW 基线)或 `LsbAnd` reduction(HW 版本),完成后通过 `fence` 等待。HW 版本的 barrier 完成中断走 multicast 一次性广播给所有参与者,避免轮询。
- **Multicast/Reduction 软件基线**:在每个对比点都用 *最优* 软件实现作为基线——naive sequential、pipelined sequential(seq,需要找最优 batch size)、binary tree。建立解析模型 (Eq. 1–6) 验证测量值。
- **代码与可复现**:RTL 代码、测试代码均开源(脚注链接);仿真用 QuestaSim 2023.4。
- **能耗估计**:对 cluster tile 0 做 placed-and-routed 后用 PrimeTime 2022.03 在 TT、25 °C、0.75 V、1 GHz 下做 gate-level 功耗估计。

## 5. 实验结果

**面积**(TSMC 7 nm,基线 = 原 FlooNoC router):

| 配置 | Router 面积开销 | 备注 |
|---|---|---|
| + multicast | +5.8% | flit-fork + minimal response reduction |
| + parallel reduction | +2.7% (累积 +8.5%) | 主要在 narrow request router |
| + wide reduction | +13.62 kGE (累积 +16.5%) | 集中式,共享所有输出 |
| 完整 collective 支持 | **+16.5%** router / **<1%** 全 cluster tile | NI 仅 +3.5% |

**Barrier 同步**(narrow reduction):

- 软件 barrier:每多一个 cluster 增加 ~3.3 cycle
- 硬件 barrier:每多一个 cluster 增加 ~1.3 cycle(理论极限 1 cycle/cluster)

**Multicast 性能**(4×4 mesh,1 KiB–32 KiB):

- 1D multicast:hw 相对最佳软件 baseline 加速 2.3×–3.2×
- 2D multicast:软件实现随行数显著恶化,硬件几乎平坦
- 整体几何均值:**2.9× speedup**

**Reduction 性能**(同样配置):

- 1D reduction:加速 2.0×–3.0×
- 2D reduction:由于 wide reduction 每 router 仅 2-input,首列 router 同时收 3 路输入会造成 1.9× 慢化(32 KiB 时);但仍随 row 数保持近似平坦
- 整体几何均值:**2.5× speedup**

**端到端 GEMM**(分析模型 + 实测 component):

| Kernel | 基线 | 硬件加速 |
|---|---|---|
| SUMMA(16×16 mesh) | memory-bound | 仍 compute-bound 直到 256×256 mesh,**up to 3.8× speedup** |
| FusedConcatLinear | reduction 在关键路径 | **up to 2.4× speedup** |

**能耗**(16×16 mesh,典型角):

- SUMMA:HW 相对 SW 最多节省 1.17×(256×256 mesh,主要来自减少 hop 数)
- FusedConcatLinear:HW 节省 1.13×(主要来自 DCA 让 Snitch 核进入 low-power 状态)

详细的能耗分布(Table 1):HW 版本明显减少 hop 数和 SPM write 数,DCA reduce 的能耗(19.0 pJ/OP)略低于普通 SW reduce(22.4 pJ/OP)。

## 6. 批判性分析

1. **「端到端」加速实际上是分析模型外推,不是端到端实测**。Section 4.3 的 GEMM 加速比来自把 `T_comp`(已有模型 + 单次实测)和 `T_comm`(本工作的实测模型)代入 max() 公式得出。256×256 mesh 的 3.8× speedup 是从未实际仿真过的尺寸——RTL 仿真规模显式止于 4×4 mesh。论文承认这是 "estimated",但摘要里只用「up to 3.8×」很容易被误读为实测。

2. **2D reduction 出现 1.9× 慢化的硬件局限被轻描淡写**。Wide reduction 每个 router 只支持 2-input,任何一列首端汇聚 ≥ 3 路时就要分多周期;论文给的解决方案是「随行数仍接近平坦」——但这是因为软件实现退化得更厉害,绝对吞吐其实是降的。在不规则 mesh 或非对称工作负载下这个缺陷会更明显。

3. **DCA 与正常计算的资源争用没有讨论**。DCA 借用 cluster 内 8 颗 FPU,文中说 cores 可以「进入 low-power 状态」——但 SUMMA 这种 compute-bound 场景下 FPU 本身就在跑 GEMM,DCA 介入会不会拖慢 inner kernel?论文没有对争用情况下的性能/能耗做评估。

4. **Multi-address mask 编码的灵活性损失被技术细节掩盖**。强制要求 collective region 是 W、H 为 2 的幂的对齐子 mesh,意味着任何不规则 partition、动态 tile 重映射都要 padding,实际上会浪费 mesh 资源——文中只说「In most cases」可以满足,没有给量化数据。

5. **能耗节省 1.17× 的对比方法略显「自利」**。HW 版本的 SUMMA 节省主要来自 hop 数下降,但通信能耗仅占总 GEMM 能耗的小头(计算占主导)——这个比例被完全淡化在结论里,只强调了 HW 多么 efficient。

6. **关键 baseline 比较的公平性**。软件 baseline 都用本团队优化过的 hw barrier 来同步——这意味着软件 multicast/reduction 的 baseline 已经吃了硬件 barrier 的红利,所以单算 multicast/reduction 加速比是公平的;但宣传「16.5% 面积换 N× 总收益」时如果不剥离 barrier 部分,会高估单独 multicast/reduction 路由器扩展的边际价值。

7. **泛化性论证略显单薄**。Section 3.3 列了一长串「同样有 2D mesh + 算术单元 + 可编程通信」的加速器(WSE-3、Blackhole、MTIA、SN40L 等),但这些芯片大多是闭源的,DCA 能否真正接到它们的 FPU 阵列、与现有 NoC 协议如何兼容,文中没有具体讨论。

## 7. AI Infra / MLSys 视角

这篇论文对 AI Infra 研究者有几个清晰的启发点:

1. **「In-network compute by resource sharing」是个好范式**。DCA 的核心思想——网络借用计算 tile 已有的算术单元——并不局限于片上。在多 GPU / 多节点场景,SHARP 是在 InfiniBand switch 上加专用 ALU;但更激进的方案是让 NIC 借用主机 GPU 的 SM 闲置资源,或在异构系统中让 inter-node fabric 借用 NPU 的 vector unit 做 reduction。值得探索的具体研究问题:**能否在 RDMA stack 之上设计一个 GPU-in-the-loop 的 in-network reduction 抽象,让 NCCL allreduce 跳过 host CPU?**

2. **Barrier 加速的可移植启示**。把 barrier 拆成「LsbAnd reduction + multicast notify」是一个普适的设计 pattern,不只在 NoC 上有用。在大规模分布式训练中,barrier 同步开销也是 bottleneck(尤其是 pipeline parallel 中的 micro-batch 边界)。这套思路可以迁移到 NCCL 层面:用 **AND-reduction over network + 单次 broadcast** 替代 ring-based barrier。

3. **GEMM communication-bound 现象的量化值得借鉴**。论文展示了 256×256 mesh 上 GEMM 利用率 < 50%,这与大模型推理在 H100 cluster 上的现象同构(comm 占比快速上升)。其分析模型(Eq. 7–9 + SUMMA 形式)可以直接拿来分析 tensor parallel + sequence parallel 在多卡上的拐点。

4. **Future work 方向**:
   - **(a)** DCA 的概念可以扩展到 chiplet 间互联——AMD 的 Infinity Fabric / NVIDIA 的 NVLink 上做类似的「邻接 chiplet 借用 FPU」是否能减少 allreduce 跨 chiplet 流量?
   - **(b)** 把 DCA 与 LLM 推理的 KV cache 操作绑定:KV cache 的 gather/scatter 本质就是 collective,且在不同 attention head 间存在大量空间局部性,正好契合 multi-address mask 编码。
   - **(c)** 把 wide reduction 的 2-input 限制升级为 N-input(用 Snitch FPU 的 SIMD 流水)——可能让 2D reduction 不再退化。
   - **(d)** 与 sparsity 结合:LsbAnd 这种位级 reduction 天然适合稀疏元素的 mask 聚合,可以用来加速稀疏 attention 的 indices 同步。

5. **最有价值的切入点**:把 DCA 从「片上 NoC 借用同 cluster FPU」推广到「rack-scale fabric 借用同节点 GPU SM」——这是一条把 in-network compute 真正跨过单 die 边界的路径,在 LLM 训练超大规模 allreduce 上有立刻可量化的影响。

## 8. 总结

这篇 MLSys 2026 的论文提出了一个轻量级、collective-capable 的片上 NoC 设计,在 ETH 团队的 SoA FlooNoC 基础上加入 multicast、reduction 和 barrier 硬件加速。最大的创新是 **Direct Compute Access (DCA)**——让 NoC 直接借用 Snitch cluster 内已有的 FPU 阵列做 in-network arithmetic reduction,从而以仅 16.5% router 面积开销(< 1% 全 tile 开销)换来 multicast/reduction 操作 2.9×/2.5× 的几何均值加速,并通过模型外推估计 GEMM 端到端可加速 3.8× 并节能 1.17×。设计思路简洁、与 AXI4 协议保持兼容、代码开源,适用范围覆盖大多数 tile-based ML 加速器(WSE-3、MTIA、SN40L 这类)。主要局限是 wide reduction 仅 2-input 导致 2D 场景退化、端到端 GEMM 加速来自分析模型而非真正的大尺度仿真,以及对 mesh padding / DCA 资源争用等代价的讨论不够深入。
