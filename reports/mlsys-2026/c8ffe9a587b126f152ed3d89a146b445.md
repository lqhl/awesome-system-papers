# FlashInfer-Bench: Building the Virtuous Cycle for AI-Driven LLM Systems

**作者**：Shanli Xing, Yiyan Zhai, Alexander Jiang, Yixin Dong, Yong Wu, Zihao Ye, Charlie Ruan, Yingyi Huang, Yineng Zhang, Liangsheng Yin, Aksara Bayyapu, Luis Ceze, Tianqi Chen

## 1. 背景

LLM 推理系统(vLLM, SGLang, TensorRT-LLM, MLC-LLM)的性能与成本在很大程度上由底层 GPU kernel 决定。GEMM、各种 attention 变体、Fused MoE、采样后处理这几类 kernel 占用了绝大部分执行时间,而它们的实现高度依赖硬件特性(SM 数、内存层次、tensor core 代次)、数值格式(BF16/FP8/INT8)与 workload 形状(序列/批量长度、cache 布局、稀疏度)。手工调优需要资深工程师投入巨大精力,因此学术界与工业界开始尝试用 LLM agent 自动生成 GPU kernel。KernelBench、TritonBench、Kevin、KernelLLM 等工作已经证明前沿模型具备生成 GPU 代码的初步能力,但要把这些 AI 生成的 kernel 真正投入生产仍存在显著的"最后一公里"问题。

---

## 2. 要解决的问题

把 LLM 自动生成的 kernel 接入真实推理系统,作者识别出三个具体瓶颈:

1. **任务规约的歧义**:LLM 系统中 kernel 有许多隐式契约(ragged tensor、page table、dtype、layout 约束),agent 拿不到精确的接口定义就难以产出正确实现;
2. **workload 失真**:已有 benchmark 多用均匀或随机输入,而真实 LLM 推理流量呈高度倾斜分布,模型在 micro-benchmark 上的 speedup 不能代表在线收益;
3. **部署鸿沟**:即便 agent 给出了候选 kernel,把它塞进 vLLM/SGLang 之类的引擎仍要改源码、重新编译、过 CI。这条路每加一次都要工程师介入,无法形成自驱动的"生成—评测—部署"闭环。

此外还有评测自身的**奖励黑客**(reward hacking)与安全风险:LLM 可能从残留显存里读到参考输出来"作弊",或调用 vendor 库绕过手写要求。

---

## 3. 洞察与设计

**关键洞察**:**"kernel 生成 → 评测 → 部署"三段被人工流程切断的根本原因是缺一种自包含、可序列化、人和 agent 都能读写的 kernel 通用语言。一旦把 Definition/Workload/Solution/Evaluation 四样东西约束到同一个 JSON schema 里,agent 提交、benchmark 执行、引擎运行时分发就能在同一对象上无损流转,从而把人工集成成本压到接近零,形成"虚善循环"(virtuous cycle)。**

整套设计围绕这个洞察展开,核心是 **FlashInfer Trace** schema(见 Figure 2):

- **Definition**:JSON 描述算子的 I/O tensor、dtype、维度轴(每个轴标记为 `var` 或 `const`)、可选约束,加一段 PyTorch 参考实现作为唯一的语义事实来源。**坚持非常具体的 Definition**(精确到某个模型某层调用,如 `gemm_n128_k2048` 来自 Qwen3-30B-A3B 的 `moe.gate`),拒绝可选输入和行为开关。
- **Workload**:绑定到某个 Definition,把 `var` 轴赋上具体整数,输入张量来自实测 safetensors dump、随机生成或字面量。
- **Solution**:一份满足某个 Definition 接口的实现,包含源码文件、入口点、目标硬件与软件版本。支持 CUDA、Triton、CUTLASS、CuTe DSL 等多语言。
- **Evaluation**:不可变的执行记录,绑定 Definition × Solution × Workload,记录 status、correctness/performance summary、运行环境快照。

围绕 Trace 的其他部件:

- **Dataset**(Figure 3):用 SGLang 跑 DeepSeek-V3、Llama-3.1-8B、Qwen3-30B-A3B 三个模型对 ShareGPT prompts 做服务,采集 GEMM、Ragged/Paged GQA、Ragged/Paged MLA、Fused MoE、RMSNorm、Sampling 八类 kernel,经按性能敏感轴去重后,每个 Definition 保留约 50 个 workload。
- **Robust Benchmark**:对确定性 kernel 做 elementwise 比较 $|y_{sol}-y_{ref}| \le \epsilon_{abs}+\epsilon_{rel}|y_{ref}|$;对低精度 kernel 用 matched-ratio(如 95% 元素满足紧界);对 stochastic 采样 kernel 改用 Total Variation Distance 与 mask 违规检查。每个 kernel 进程隔离,CUDA context 跑完销毁,防止"黑客"攻击,同时提供 persistent worker pool 加速大规模 sweep。
- **`flashinfer_bench.apply()`**(Figure 5):decorator 或 imperative API 包住引擎里的算子,启动时构建 AOT 索引(按形状等特征建 key,挑最快 solution),在线运行时从 input args 构 key 做 O(1) 查表,命中就走优化 kernel,否则 fallback。

## 4. 实现细节

- **Schema 实现**:Trace 序列化为单个 JSON 对象,可直接 round-trip 提交到 leaderboard。`var` 轴在 workload 阶段绑定整数,`const` 轴在 Definition 阶段固定,使 agent 可针对静态形状做特化优化。
- **Dataset 规模**:八类 kernel × 不同 const 配置 = 41 个 distinct Definition,合计 1,600 个 workload。
- **Agent 评测框架**(Algorithm 1):feedback-loop 形式,每一轮 agent 生成 → benchmark → 反馈结果 → optimize,跑满 N 轮后选 speedup 最大的 PASSED 解。在 NVIDIA B200 上跑,共评测 240 个 solution、9,600 条 evaluation 结果。
- **Benchmark 调度器**:为每个 (Solution, Workload) job 构建 cost matrix(考虑 baseline 残留与 warm compile cache),用 Hungarian algorithm 分派 micro-batch 到设备 worker;cost model 用 EWMA 在线更新。失败 solution 自动从 persistent 退化到 isolated 模式;CUDA binary 缓存到磁盘避免重复编译。
- **`apply()` 索引**:启动前根据可配置错误阈值过滤 traces,从 workload 抽特征作 key,挑最快 solution 作 value;选出现频次最高的一批 AOT 编译,其余 JIT;开 CUDA Graph + warmup 后单次调用开销 1–2 µs。
- **集成方式**:与 FlashInfer kernel 库一等公民集成,通过环境变量 `FIB_ENABLE_APPLY=1` 在 SGLang/vLLM 中零代码替换。

## 5. 实验结果

### 5.1 Agent 在 41 个 kernel 上的整体表现(fast_p 指标)

`fast_p` 表示 kernel 在多少比例的 workload 上既正确又达到 p 倍 baseline 加速;曲线 AUC 综合反映 correctness × performance。

| 模型 | fast_0(正确率) | fast_0.95(快于 baseline) |
|---|---|---|
| GPT-5 (2025-08-07) | 83.9% | 排名第三 |
| GPT-o3 | 71.3% | 排名第二 |
| Gemini-2.5-Pro | 48.8% | 排名第一(在 fast_0.95) |
| Claude-Opus-4.1 | (相对最低) | — |

### 5.2 语言对比(整体 correctness)

| 模型 | CUDA | Triton |
|---|---|---|
| GPT-5 | 83% | 96% |
| GPT-O3 | 58% | 96% |
| Gemini-2.5-Pro | 29% | 79% |
| Claude-Opus-4.1 | 25% | 83% |

Triton 在所有模型上都显著超过 CUDA。

### 5.3 错误类型

总计 32 个 correctness 错误中,**30 个是编译错误**,只有 2 个 runtime/numerical 错误(主要是大输入下 padding 计算错)。编译错误三类典型模式:API 误用、host/device 上下文混淆、dtype/shape 错误。

### 5.4 Case Study:GEMM (n4096, k4096) 上 GPT-5 的 Triton vs CUDA

| 指标 | CUDA | Triton |
|---|---|---|
| 平均执行时间 | 0.5 ms | 0.11 ms |
| 加速比 | 1× | 4.5× |
| Tensor core 指令 | WMMA(老) | tcgen05(新) |
| 软件流水 | 无 | 编译器自动深度 4 |

GQA Paged Decode case study:CUDA 实现仅用 online softmax,缺 tiling/异步执行/pipeline,即使 explicit prompt 提示优化策略,GPT-5 在 10 次尝试中也未能生成正确利用这些技术的 CUDA kernel。

### 5.5 端到端替换实验(SGLang + Llama-3.1-8B,fused_add_rmsnorm h=4096)

| 配置 | Kernel 延迟 (bs=64, ms) | E2E 延迟 (bs=64, ms) |
|---|---|---|
| Original (Apply Disabled) | — | 933 |
| Fallback Substitution (FlashInfer) | 0.0112 | 934 |
| Gemini-2.5-Pro Triton | 0.0160 | 939 |
| GPT-5 Triton | 0.0247 | 1055 |

`apply()` 自身开销 < 0.8%(934 vs 933);kernel 越慢 E2E 越慢,验证了"kernel 收益→ E2E 收益"的传递性。

## 6. 批判性分析

1. **"端到端替换有效"的演示其实是反证**:E2E 实验里所有 substitution 配置都**没有比 Original 更快**。Fallback(把 FlashInfer 自己的 kernel 经 apply() 转一道)做到了几乎打平(+1ms / 0.1%),agent 生成的 Gemini-Triton 落后基线 5–18ms,GPT-5 Triton 慢了 122ms。论文标题是"AI-Driven LLM Systems",但实验里 AI 生成的 kernel 还**赶不上 FlashInfer 手写基线**,只能证明 apply() 机制本身轻量。

2. **"虚善循环"目前没闭环**:论文反复强调 virtuous cycle,但实测数据并未显示 agent 在多轮迭代后逼近 SOTA。对 GQA paged decode,即便给出 explicit hint,GPT-5 在 10 次尝试中仍 0/10 生成正确的优化版本;循环跑下去也跳不出 LLM 当前能力的 ceiling。

3. **"奖励黑客"防御与"agent 学会调 cuBLAS"自相矛盾**:作者花大力气在 isolation、隐藏 workload、TVD 校验上防止 reward hacking,转身又表扬"agent 学会调 cuBLAS"达到 SOTA。从 benchmark 设计角度看,允许调 vendor 库本身就是另一种 reward hacking——它绕过了"用 LLM 生成 kernel"的初衷。建议自相矛盾:一边说"训练时禁库",一边又把这种解纳入 leaderboard 计分。

4. **"real-world workload"覆盖偏窄**:Dataset 只用 SGLang 默认配置 + ShareGPT prompts 跑三个模型。生产流量的多 tenancy、long-context、speculative decoding、prefill/decode 分离等关键 pattern 全没覆盖。基于这样数据集挑出的"最快 kernel"放到别的引擎(vLLM 的 chunked prefill、TRT-LLM 的 in-flight batching)上未必仍然是最快。

5. **不支持多 GPU 与通信 kernel**:论文自己也承认。但通信(NCCL all-reduce、TP、EP all-to-all)恰恰是大模型推理性能的最大瓶颈之一,没有这部分,FlashInfer-Bench 距离覆盖"production LLM systems"还有相当距离。

6. **样本量统计意义不足**:240 个 solution 摊到 41 个 Definition × 4 模型 × 2 语言 ≈ 0.7 个/格,几乎没法做有统计意义的模型间比较;"GPT-5 第一、Gemini 第二"这种排名很容易被几次 random 翻转。

7. **错误分类粗糙**:"30/32 是 compilation error" 看起来鼓舞人心(似乎只要解决编译问题就大功告成),但 fast_p 曲线显示**就算编译过了,大部分 solution 也跑不到 baseline 的一半**。compilation 只是入门门槛,真正的瓶颈是"会写但写不快"。

## 7. AI Infra / MLSys 视角

这篇论文与 AI Infra 高度相关,值得作为多条 future work 的起点:

- **Trace schema 这一抽象本身有复用价值**:类似的"Definition + Workload + Solution + Evaluation"四元组可以泛化到 distributed training operator(comm + compute fused kernel)、vLLM/SGLang 的 scheduler policy、甚至 RL 训练里的 rollout config。一个团队若想做 agent-driven 系统优化,可以直接借鉴这个 schema 设计自己领域的 trace。
- **`apply()` 模式值得移植**:零侵入、AOT 索引 + O(1) 在线分发的思路,可以套到 attention backend selector、KV cache layout selector、even quantization config selector 上,把"需要专家手调的开关"变成"agent 自动 sweep 出最佳点位 + 运行时按 workload 选择"。
- **Reward hacking vs library calls 是一个真问题**:论文揭示但没解决——agent 学会绕过手写要求调 vendor 库,在 leaderboard 上算"高分"。一个有研究价值的方向是设计"分级评测":分别报告"纯生成"、"允许调用 X 库"、"允许 X+Y 库"等多档,而不是把 cuBLAS 的成绩混在一起算。
- **Compilation 错误率高是数据问题**:论文指出 30/32 错误来自编译。这意味着用更多 Triton/CUDA 编译错误—修复对作 SFT/DPO 数据,可能比堆 RL feedback 更直接。可以基于 FlashInfer-Bench 的 9600 条 trace 反向构造一个"错误—修复"语料库。
- **缺失的 communication kernel 是空白**:多 GPU 推理(TP/EP/SP all-reduce、KV cache transfer)的 kernel 优化目前几乎完全靠 NCCL/手写。把 FlashInfer-Bench 范式扩展到通信 kernel(Definition 加 process group/topology 维度,Workload 加 message size 分布)是有清晰落地价值的延伸方向。
- **可操作的延伸研究问题**:
  1. 在 H100/H200/B200 三代硬件上 cross-evaluate 同一批 solution,量化 agent 的"硬件特化"能力 vs "硬件无关"代码的比例。
  2. 把 apply() 与 speculative decoding、chunked prefill 等动态调度策略叠加,看是否会出现 kernel 选择的 phase change。
  3. 对 Triton 高正确率—中性能 vs CUDA 低正确率—高潜力的 trade-off,做 Pareto frontier 分析,给"agent + 语言"的搭配出一个推荐表。

---

## 8. 总结

FlashInfer-Bench 的核心贡献在于把"LLM 生成 GPU kernel"从单点能力评测推进到端到端可部署闭环:用 FlashInfer Trace schema 统一了 Definition/Workload/Solution/Evaluation 四类对象,基于真实 SGLang 服务流量构建数据集,提供了带防 reward hacking 的健壮评测框架,并通过 `flashinfer_bench.apply()` 实现了对 SGLang/vLLM 的零代码 kernel 替换。其分析揭示了当前 LLM agent 三个共性短板:编译错误占绝大多数、缺乏对新硬件指令(tcgen05 等)的运用、Triton 正确率高而 CUDA 性能上限高的语言权衡。主要局限是 AI 生成的 kernel 端到端尚未稳定超过手写基线、不支持多 GPU 通信 kernel、workload 与硬件覆盖偏窄,因此目前 FlashInfer-Bench 更适合定位为"AI agent kernel 生成的产业级评测与部署基础设施",而非"已经能持续超越人类专家的自动化 kernel 生产线"。
