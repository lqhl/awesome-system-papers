# Reparo: Loss-Resilient Generative Codec for Video Conferencing

**作者**：Tianhong Li, Vibhaalakshmi Sivaraman, Pantea Karimi, Lijie Fan, Mohammad Alizadeh, Dina Katabi

## 1. 背景

视频会议(Zoom、Teams、WebRTC)已是工作生活的核心基础设施,但在公共互联网上跑实时视频依然受困于一个老问题——**丢包**。传统视频 codec(VP8、VP9、H.264、H.265、AV1)用 I-frame + P-frame 的方式压缩,P-frame 依赖前面已解码的帧,因此一个 I-frame 丢失会让后续大量帧无法解码,产生明显的卡顿和质量崩塌。

实时性约束让重传几乎不可行(33 ms/帧,RTT 稍长就来不及),业界主流是 Forward Error Correction (FEC):发送端额外发若干 parity 包,接收端用代数恢复原始包。常见方案包括 ULPFEC、flexFEC(WebRTC 内置)和近期的流式码 Tambur(NSDI '23)。但 FEC 有个根本性矛盾——互联网丢包是**突发且不可预测**的:冗余多了浪费带宽,冗余少了直接解不出帧,而帧间依赖让单点故障级联放大。

与此同时,生成式视觉模型(MAE、MaskGIT、VQGAN、Stable Diffusion)已经能从极少的 token 出发合成出与原图几乎不可分辨的人脸图像。这给"丢包恢复"提供了一条新思路:**不靠冗余包,靠模型生成**。

---

## 2. 要解决的问题

具体到视频会议场景,作者要解决三个交织的痛点:

1. **FEC 冗余比例难以选择**:互联网丢包率随时间剧烈波动,固定 50% 的 parity 在低损时浪费带宽,在高损时仍然解不出来。
2. **帧间依赖放大丢包影响**:即使只有少数包真的丢了,P-frame 链上的一次中断会让接收端在很多帧内一直渲染同一张冻结画面,直到下一个 keyframe 到达——而 keyframe 又因为体积大,本身丢包概率更高。
3. **比特率不可控**:VP9 等传统 codec 的瞬时比特率高度可变(I-frame 远大于 P-frame),与配置的目标比特率经常不一致,容易超过链路容量造成排队丢包。

作者希望设计一个 codec,使得每帧**独立编码**(消除帧间依赖)、**比特率严格恒定**、**对丢包优雅降级**,同时压缩效率不输给传统 codec。

---

## 3. 洞察与设计

**关键洞察**:对于视频会议这种**高度受限的视觉域**(人脸、说话头、室内场景),用一个小规模的视觉 token codebook 就能充分表达所有可能出现的图像内容。一旦图像被映射到 token 空间,丢失的 token 就可以由生成模型基于"剩余 token + 历史帧 token + 该域的视觉先验"重建出来,无需任何冗余字节。换言之,**接收端可以像人脑一样用先验知识"脑补"丢失内容**——给一只眼睛能想象出另一只眼睛,给半个手臂能想象出整个躯干。

基于此,Reparo 由五个模块组成(见 Figure 1):

1. **Encoder (VQGAN)**:把 512×512 的 RGB 帧编码成 32×32 个离散 token,codebook 大小 1024(每个 token 索引 10 bit)。
2. **Packetizer**:确定性地把 token 拆到 4 个包里,**有意把空间相邻的 token 分散到不同包**——丢一整个包后,周围邻居 token 仍在,生成模型恢复起来更容易。位置 (i,j) 的 token 落在第 `2·(i mod 2) + j mod 2` 个包。
3. **Bitrate Controller (Self-drop)**:发送端根据目标比特率,**主动按伪随机种子丢掉一定比例 token**。种子 = `4·frame_idx + packet_idx`,接收端用同种子还原被丢位置。这把"丢包"转化为可控变量。
4. **Loss Recovery Module**:基于 spatio-temporal Vision Transformer (ViT, 20 层、12 heads、768 维、172M 参数),用近 6 帧的所有已收 token 作为上下文,把缺失位置(用 mask token `[M]` 占位)生成出来。空间和时间注意力分两步算,内存复杂度从 O(T²h²w²) 降到 O(Th²w² + T²hw)。
5. **Decoder (VQGAN)**:把恢复后的 token 网格解码成 RGB 帧。

整个 pipeline 的核心抽象就是"**把丢包问题转换成 masked image generation 问题**"。FEC 把问题留在比特/包层做代数恢复;Reparo 把问题抬到 token 空间做语义恢复。

训练上分两阶段:先冻结一切训 VQGAN(用 FFHQ + CelebAHQ + TalkingHeads,~9.5 万图 + 25 小时视频);然后冻结 VQGAN,在 token 上模拟丢包训 ViT。训练时 self-drop rate 从 [0, 0.6] 截断高斯采样,packet drop rate 从 [0, 0.8] 均匀采样,loss 是只在最后一帧缺失位置计算的 cross-entropy。

## 4. 实现细节

| 维度 | 配置 |
|---|---|
| 输入帧 | 3 × 512 × 512,30 fps |
| Token grid | 32 × 32(每个 token 表示 16×16 像素块) |
| Codebook | 1024 entries × 128 channels |
| 每帧包数 | 4(包头 4 字节,载荷 320 字节) |
| 默认比特率 | 311.04 Kbps |
| Self-drop 上限 | 50%(token 维度) |
| Loss recovery 上下文 | 6 帧 spatio-temporal ViT |
| ViT 规模 | 20 块,12 头,d_model=768,172M 参数 |
| Encoder/Decoder | 5 块 ResNet,各含 2 个 residual block,共 ~54M 参数 |
| 框架 | PyTorch |
| 推理硬件 | 单 V100 GPU(发送端、接收端各一)≈ Apple M2 Max GPU |

延迟预算(Table 2):Encoder 14.1 ms + Packetization 0.5 ms + Loss Recovery 17.8 ms + Decoder 13.1 ms ≈ **45.5 ms 总计算延迟**,加上典型 50 ms 网络排队延迟仍在 ITU-T G.1010 推荐的 150 ms 内。

工程上有两个值得注意的细节:
- **VQGAN 用了 OpenImages 上预训练权重做 warm-start**,把训练时间从 ~200 epochs 压到 ~10 epochs。
- **Loss recovery 训练时只对最后一帧的缺失 token 算 loss**,作者引用 MAE 的经验说明对所有 token 算 loss 会反而降低重建质量。

## 5. 实验结果

### 实验设置

- **Baseline**:VP8+ULPFEC、VP8+flexFEC(WebRTC 内置)、VP9+Tambur(NSDI '23 SOTA)。所有 baseline 的 FEC 开销设为 ~50%。
- **数据集**:训练集 FFHQ + CelebAHQ + TalkingHeads(~25 hours);**验证集是 Gemino + TalkingHeads 拼起来的 5 小时、412 段视频、84 个不同主体**——比 Gemino(75 分钟)、Tambur(200 分钟)、GRACE(745 秒)的验证集都大且多样。
- **网络模拟**:GE 信道,bad state 丢包率 25%/50%/75% 对应 Low/Medium/High;另外是 320 Kbps 固定码率瓶颈链路。

### 主要数字

**(1) 视觉质量(worst 10% PSNR,bitrate ~320 Kbps)**

| 损耗等级 | VP9+Tambur | Reparo | Reparo 提升 |
|---|---|---|---|
| Low (5.6% avg loss) | 21.9 dB | 33.4 dB | +11.5 dB |
| Medium (7.4% avg loss) | 16.5 dB | 32.9 dB | +16.4 dB |
| High (9.3% avg loss) | 16.9 dB | 31.6 dB | +14.7 dB |

无丢包时 Reparo PSNR 与 baseline 相当,**丢包韧性不以无损质量为代价**。Figure 6 显示 Reparo 的 PSNR 几乎全部落在 32.5–37 dB 区间内;Tambur 的 worst frames 在高损时跌到 <20 dB。

**(2) 非渲染帧比例(Figure 8)**

| 损耗等级 | VP8+ULPFEC | VP8+flexFEC | VP9+Tambur | Reparo |
|---|---|---|---|---|
| Low | 11.6% | 11.0% | 8.0% | **0.2%** |
| Medium | 22.8% | 21.8% | 13.1% | **0.8%** |
| High | 35.3% | 35.1% | 29.2% | **2.0%** |

Reparo 几乎消除了"卡顿"——即使在高损情况下,> 98% 的帧都能渲染并维持 ≥ 30 dB。

**(3) 速率受限链路(320 Kbps,Figure 11)**

VP9+Tambur 受限于 keyframe 体积大,只能保守地把目标 bitrate 设到 ≤120 Kbps,实际 PSNR ≈ 33.4 dB。Reparo 比特率严格匹配链路容量,达到 ~35 dB。

**(4) Bitrate 可调性(Figure 12)**

通过调整 (t = 联合编码帧数, tokens/frame, codebook size) 三个旋钮,Reparo 可以在 ~25 dB @ 30 Kbps 到 ~36 dB @ 430 Kbps 的曲线上滑动。

## 6. 批判性分析

虽然结果很亮眼,有几处需要审慎看待:

1. **训练域和测试域几乎完全重合**:训练用了 TalkingHeads,验证集也包含 TalkingHeads 的一部分(声称无 overlap,但同一数据集风格分布高度相似)。Reparo 是个**域特化**模型——用 FFHQ/CelebAHQ/TalkingHeads 训练后只能在"近距离单人正面 talking head"上 work。论文也承认如要扩展到多人会议、屏幕共享、户外、不同种族/光照的人脸,需要重训 codebook。**这意味着 PSNR 数字的可推广性远比 VP9 这类通用 codec 弱**,而比较的对象 VP9 显然不享受这种"训练-测试对齐"红利。

2. **"Non-rendered frame" 的定义对 baseline 不公**:作者把 Reparo 中 PSNR < 30 dB 的帧定义为"non-rendered",而 baseline 的 non-rendered 是 codec 真的拒绝输出。然而 baseline 在 non-rendered 区间会**复用上一帧**,某些场景观感未必差到不可接受;Reparo 即便恢复出 PSNR=27 dB 的"模糊脸"也可能伴随 hallucination(生成出错眼睛/嘴型)。**PSNR 不能区分"生成的合理但错误的脸"和"真实的清晰脸"**,LPIPS 也只能反映感知相似性而非语义正确性,缺少身份一致性 / lip-sync 评估。

3. **延迟预算偏紧但写得很乐观**:45.5 ms 算上 50 ms 排队后是 95.5 ms,距离 150 ms 上限只剩 ~55 ms;一旦发送端 GPU 抢占或接收端做个上下文切换就可能爆。论文没有报告 P99 计算延迟和 GPU 抢占下的退化,只给了均值±方差。

4. **可部署性几乎为零**:作者诚实承认必须 V100 / M2 Max 级别 GPU;但视频会议 80% 的实际场景是手机、平板、低端笔电。论文把"未来 GPU 会变强 + 知识蒸馏 + 神经架构搜索"作为答案,但没有任何 prototype 数据支撑这些路径能压到 ARM SoC 可接受的延迟。

5. **未对比生成 codec 同行 GRACE 的最新结果**:GRACE(NSDI '24)和 Reparo 同样用神经 codec 应对丢包,论文只在 Related Work 简单说 GRACE "没有显式 loss recovery + 用 delta coding 有错误传播",但没在表格里给出 GRACE 的具体数字。

6. **比特率严格恒定可能是双刃剑**:GCC 等拥塞控制依赖于 codec 能"主动降码率"避让排队;Reparo 的固定 token 数意味着在突发拥塞时无法立刻把帧大小压到 1/3,只能靠 self-drop 50% 上限内调节,自由度比 VP9 的量化系数小很多。

## 7. AI Infra / MLSys 视角

这篇论文表面是 networking + multimedia,但其方法论对 AI Infra 有几处值得借鉴:

1. **"语义压缩 + 生成补全"作为通用数据传输范式**:同样的思路可以扩展到 LLM 推理场景中的**远程 KV cache 传输**、**多机权重 sharding 同步**、**分布式 RAG 文档块同步**。当传输内容来自一个低维流形(如某个 model class 的 attention pattern、某个 corpus 的语义分布)时,接收端用本地小模型"补全"丢失部分,可能比 ARQ + FEC 更省带宽。可探索方向:**federated/edge inference 中,把激活值用 VQ tokenize 后只传索引,接收端用预训练的"反激活"模型恢复**。

2. **Spatio-temporal attention 拆分技巧**:将 O(T²h²w²) 降到 O(Th²w² + T²hw) 的因子化方式,在 long-context LLM 服务、视频生成模型(Sora 类)的 KV cache 优化中是基础工具。Reparo 的实现细节(20 层叠 ViT 在 32×32×6 grid 上做实时 33ms 推理)是个**端到端 ViT 实时推理 latency budget 的真实参考点**。

3. **"丢包→masked generation"的统一抽象**:这个抽象的反向也成立——MLSys 中常见的**梯度压缩/通信丢失**(top-k SGD、QSGD、PowerSGD)本质也是 masked generation,可以借鉴 Reparo 的 spatio-temporal ViT 思路用 transformer 学习恢复梯度,而不是用统计量近似。

4. **可跟进的研究问题**:
   - **可压缩到 mobile**:用知识蒸馏 + INT4 量化,把 172M ViT 压到 10M 以下,在手机 NPU 上做 30 fps 实时推理,是否还能保持 PSNR 优势?
   - **Open-domain Reparo**:用 SD3/Flux 等通用 image prior 替换 VQGAN,代价是 codebook 变大、bitrate 提升,是否值得?这能直接破解"域特化"的可部署性瓶颈。
   - **拥塞控制协同设计**:GCC 等 RTT-based 拥塞控制是为可变 bitrate codec 设计的,与 Reparo 的固定 bitrate 模型不匹配。重新设计一个为 generative codec 优化的 CC,可能能进一步压低延迟。
   - **Streaming generative codec for screen sharing**:屏幕共享是另一个 video conferencing 长尾场景,内容是文本/UI,用 OCR-aware 的 token 化方案可能很有效。

5. **最有价值的延伸切入点**:把 Reparo 推广到**远程 LLM 推理的 token streaming**——把 LLM autoregressive 生成的 token 流当作"视频帧",在不可靠网络上传输,接收端可以用一个小模型在丢失时基于已收 token 回退/补全。这能让真正分布式的 LLM serving(edge inference + cloud 协作)绕过 TCP 重传带来的延迟尖峰。

---

## 8. 总结

Reparo 是第一个把生成式视觉模型完整接入实时视频会议 codec 的系统工作:用 VQGAN 把帧 tokenize、用确定性 packetizer + self-drop 把丢包/限速转化为可控的 masked generation 问题、用 spatio-temporal ViT 在 token 空间生成缺失内容。在 MIT 自有的 5 小时 talking head 验证集上,worst 10% PSNR 比 SOTA VP9+Tambur 高 11.5–16.4 dB,non-rendered 帧从 8–29% 压到 0.2–2.0%,且严格守住 33ms 实时帧预算。代价是模型必须 V100 级 GPU 才能跑、codebook 域特化(只能用于 talking head)、缺乏对生成质量"语义正确性"的评估。论文的真正贡献不在数字,而在打开"用 generative model 替代 FEC"这条新方向,以及由此引出的"语义层冗余 < 比特层冗余"的设计哲学,值得 AI Infra / 实时通信社区长期跟进。
