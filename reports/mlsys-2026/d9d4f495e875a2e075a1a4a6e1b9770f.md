# BOUTE: Cost-Efficient LLM Serving with Heterogeneous LLMs and GPUs via Multi-Objective Bayesian Optimization

**作者**:Youhe Jiang, Fangcheng Fu, Eiko Yoneki
**会议**:MLSys 2026
**链接**:https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**:[[d9d4f495e875a2e075a1a4a6e1b9770f.pdf]]

---

## 1. 背景

LLM 服务化成本高企,服务商必须在给定延迟与质量要求下同时做两个关键决策:(i) 用哪个模型处理每条查询(模型能力 vs 查询难度);(ii) 模型如何部署到 GPU 资源(资源分配与并行策略)。围绕这两个方向学界/业界分别发展出两条独立路线:

- **异构模型路由(算法视角)**:如 RouteLLM、HybridLLM,用一个轻量 router 给查询打"难度分",简单请求丢给小模型(Llama3.1-8B),困难请求丢给大模型(Llama3.1-70B),通过与模型能力匹配降低总成本。
- **异构 GPU 部署(系统视角)**:如 ThunderServe、Helix、Mélange,用 RTX 5090、4090、PRO 6000 这类相对廉价的消费级/工作站 GPU 补充 H100,降低每小时硬件成本。

两条路线迄今基本是各自优化,但路由决策决定各模型上的系统负载,进而影响部署;部署又决定每个模型的延迟特征,反过来影响路由阈值。本文探索这两者的联合优化。

---

## 2. 要解决的问题

论文将问题拆成三个耦合的子问题:

1. **有效的模型路由**:在异构资源下不同 LLM 在不同 GPU 上的延迟特征不同,路由阈值的最优解依赖于部署方案,不能独立求解。
2. **高效的模型部署**:不同 GPU 类型(算力、显存带宽、显存容量)与不同模型规模存在亲和性,再叠加 (DP, TP, PP) 三维并行搜索空间,单独已是 NP-hard 问题。
3. **算法-系统协同设计**:上述两者相互依赖,构成一个循环优化问题。独立优化路由或部署都会导致次优。更糟的是,决策空间是离散 + 连续混合、无法写成凸优化;加上预算与 GPU 资源的硬约束,需要一个能处理黑盒多目标、带约束、样本高效的求解器。

现有工作要么忽略路由对系统负载的反馈(RouteLLM 用均匀资源分配),要么忽略异构 GPU 带来的路由比例迁移(BOUTE-Homo)。

---

## 3. 洞察与设计

**关键洞察**:异构模型路由与异构 GPU 部署天然互补——小模型在 RTX 5090 上能取得比 H100 低约 33% 的延迟,而大模型在 H100 上能取得比 5090 低约 50% 的延迟(§3 和 Figure 1 的 microbenchmark)。这意味着:(i) 把小模型放到 5090 上能释放出 H100 预算反哺大模型,使大模型容量扩张;(ii) 此时路由分布会从 40/60 迁移到 30/70——即 GPU 异构性会主动改变最优路由比例。因此两种异构性必须联合优化,否则相互之间的收益会被掩盖。

**设计方案**:将联合优化表述为带约束的多目标优化问题,决策变量是 (路由阈值 τ, GPU 分配矩阵 A, 并行策略 P),目标是 Pareto 最优的 (P95 latency, −quality);约束是 GPU 数量与总预算。求解器采用 **MOBO(多目标贝叶斯优化)**框架,分为两阶段:

- **Offline preparation**:用推理任务模拟器离线构建 `⟨部署, 负载⟩ → 系统延迟` 的性能数据库。两阶段模拟——先枚举单副本的 (TP, PP) 组合,再合成多副本 DP 的负载分配搜索,使得 online 阶段只需查表而无需重新仿真。
- **Online optimization**:用高斯过程(GP)作为代理模型,additive kernel 解耦路由主效应、部署主效应和交互项;用 **constrained qNEHVI** 作为采集函数,在反复采样/更新中逼近 Pareto 前沿。

为让 BO 在复杂离散-连续混合空间快速收敛,论文注入了五项**结构化信息(S1–S5)**:
- **S1 Load-fraction encoding**:不用原始阈值做决策变量,改用各模型承载的负载比例。阈值分数分布非均匀,微小扰动会引发跳变;负载比例与延迟近似线性,且天然满足 Σf=1 的线性约束。
- **S2/S3 预算与 GPU 可用性硬约束**:违反的候选直接从搜索空间剔除。
- **S4 输出变换**:latency 取 log、quality 取 logit,稳定 GP 拟合。
- **S5 Model-GPU preference kernel**:把 §3 观察到的模型-GPU 亲和性编码成偏好矩阵 S,并通过指数权重放入 deployment kernel $\tilde{k}_c(\mathbf{c}, \mathbf{c}^*) = w(\mathbf{c}) \cdot w(\mathbf{c}^*) \cdot k_c(\mathbf{c}, \mathbf{c}^*)$,让 GP 早期探索偏向"好"的搭配,但在预算/可用性不满足时仍可被数据覆盖。

## 4. 实现细节

- **代理模型**:BoTorch SingleTaskGP + ModelListGP,分别对 latency、quality 建模。
  - $k_\tau$:ARD Matérn-5/2(路由阈值连续平滑)
  - $k_c$:ARD Matérn-3/2(部署候选离散跳变)
  - $k_\times$:ProductKernel 捕捉交互,权重 ϕ 学习得到通常较小
  - `PreferenceWeightedKernel` 为 $k_c$ 注入 S5 偏好
  - 输出变换:Log+Standardize (latency) / Logit+Standardize (quality)
  - 全部 kernel 用 double precision 运行
- **候选生成(对抗指数爆炸)**:
  - 同构候选:每种 GPU/负载组合下枚举 (DP, TP, PP),用 Pareto-skimming 在 (latency, cost) 空间挑 10–20 个非支配点。
  - 异构候选:以 10–20 个预算档做网格,对每档求解多重选择背包(每种 GPU 最多一个同构候选)最小化延迟,DP 副本间的负载分配通过离线数据库查找。
- **候选剪枝**:显存不足的配置剔除(如 4×5090 部署 70B);TP 限制在机内互联以避 NVLink/PCIe 通信瓶颈(TP ≤ 8 或 4)。
- **协调器**:基于 OpenComputeFramework + libP2P 的 P2P 连接,router 打分 → 选副本(依据离线负载分配结果) → 派发请求。推理后端用 vLLM 部署 Llama3.1-8B/70B。
- **模拟器精度**:simulator 估算 throughput 与真实结果误差 2%–7%(Table 4),足以支撑配置选择。

## 5. 实验结果

**实验平台**:4 类 GPU 服务器,每台 8 卡:H100-80G ($2.64–3.07/h)、RTX PRO 6000-96G ($1.84–2.09/h)、RTX 5090-32G ($0.89/h)、RTX 4090-24G ($0.59/h)。统一 $30/h 预算对比。trace 来自 GSM8K 与 MTBench,总负载 100 req/s。

**端到端性能(Figure 4)**:与 4 类基线(Stand-Alone-Homo / Hetero、RouteLLM、BOUTE-Homo)相比,BOUTE 在相同成本+质量下:

| 对比对象 | P95 延迟最大↓ | 吞吐最大↑ |
|---|---|---|
| Stand-Alone-Homo/Hetero(GSM8K) | 91%(均值 57%) | 90%(均值 55%) |
| RouteLLM(GSM8K) | 66%(均值 50%) | 71%(均值 52%) |
| BOUTE-Homo(GSM8K) | 15%(均值 14%) | 16%(均值 14%) |
| Stand-Alone(MTBench) | — | 157%(均值 115%) |
| RouteLLM(MTBench) | — | 80%(均值 42%) |
| BOUTE-Homo(MTBench) | — | 21%(均值 20%) |

**调度结果解读(Table 1)**:随着质量要求升高,负载与预算均向大模型倾斜;且预算分配不等于负载分配——MTBench-8.3 时小模型承担 61% 负载但只占 24% 预算,大模型占 76% 以防成瓶颈。RTX 5090/4090 基本全给小模型,H100 + PRO 6000 给大模型,符合 §3 的 GPU 偏好观察。

**调度时间与可扩展性(Table 2)**:
- BOUTE:3 GPU 类型/24 卡收敛 23.5s,6 类型/48 卡 1.2 min,近线性扩展。
- 移除结构化信息:BO 迭代次数约为 8×,时间从 <1 min 飙到 4–9 min。
- 移除离线准备:每次 BO 评估都要重跑模拟器,时间 12 min 到 >30 min。

**成本节省(Table 3)**:在相同质量+延迟约束下,BOUTE 比 Stand-Alone 平均省 39.7%,比 RouteLLM 省 38.0%,比 BOUTE-Homo 省 15.0%。整篇摘要给出的峰值是 61% 省钱、平均 38%。

**Pareto 优势(Figure 5)**:BOUTE 在 GSM8K 与 MTBench 的全 quality 区间都严格占优 BOUTE-Homo / BOUTE(w/o structural info)/ RouteLLM。

## 6. 批判性分析

- **"Pareto 最优"几乎只对比自己的降级版本**:Figure 5 的 Pareto 前沿只与 BOUTE-Homo、BOUTE(w/o structural info)、RouteLLM 对比;真正相关的异构 GPU 系统(Helix 的 max-flow、Mélange、ThunderServe)都没上 Pareto 图,仅在相关工作里提一句。对 MLSys 2026 题材而言,这是明显的 baseline 挑拣。
- **模型池深度只有 2**:整篇论文几乎所有实验都只有 Llama3.1-8B + Llama3.1-70B 两档。路由阈值的决策变量被简化成一个标量 f(小模型负载比例),这让 MOBO 的难度被大幅压低。实际服务商常有 4–6 档模型组合,MOBO 收敛时间与 8× 结构化收益是否仍成立没有正面证据。
- **"2.6× latency reduction"的对比组**:最大加速来自 Stand-Alone-Homo(vLLM 跑 70B)这种不做路由的朴素基线。与更强的 RouteLLM 比最多只有 66%,与 BOUTE-Homo 比只有 15%。摘要里直接报最大值而不清楚标注对比对象,容易让人高估 MOBO 的核心贡献。
- **路由器泛化性**:采用 RouteLLM 的路由器,训练数据来自 Chatbot Arena + GPT-4 标注 + MMLU,与测试 trace(GSM8K/MTBench)分布不同。质量保证依赖路由器在这两个 dataset 上的打分准确,论文没做路由器漂移/OOD 实验,而质量约束 qNEHVI 的正确性强依赖于此。
- **"质量"定义单一且可争议**:GSM8K 精度和 MTBench 得分都是聚合指标;MOBO 优化的是 aggregated quality,对尾部(困难子集)质量没有保证。服务商关心的 P99 质量退化不在目标函数里。
- **模拟器误差 2%–7% 的传播**:BO 每次评估都用模拟器的估计值做代理,误差会进 GP 噪声;但论文没分析模拟器误差对最终 Pareto 前沿的偏移——尤其是两个候选延迟差不到 7% 时,MOBO 的排序可能完全被仿真噪声决定。
- **预算约束假设租金恒定**:实验用固定的 GPU 每小时价格,忽略现实中 spot 价格抖动、跨 region 可用性差异——而这些恰是 SpotServe / SkyServe 类工作的核心问题;BOUTE 的"成本节省"结论在动态价格下能否持续不明。
- **"Offline preparation only once per scenario"有隐性假设**:workload trace 分布稳定才成立。trace 漂移时性能数据库需要部分重建,代价论文未量化。
- **公平比较细节**:BOUTE-Homo vs. BOUTE 都使用 MOBO 框架,收益主要来自异构 GPU(~15%);但与 RouteLLM 的比较同时叠加了"路由优化 + 资源分配 + 异构硬件"三重差异,单项贡献分解不够干净。

## 7. AI Infra / MLSys 视角

- **可迁移的核心抽象**:用 **Bayesian Optimization + 结构化先验**解决"离散部署决策 × 连续算法超参"的黑盒联合优化,是一个比启发式 / 线性规划更通用的工具箱。可直接借鉴到:
  - 训练场景的 **并行策略 × 重计算/offload 阈值** 联合搜索(比 Alpa/Galvatron 纯规划式更适合非凸目标)。
  - 推理场景的 **chunked prefill × KV cache eviction × DP 副本数** 联合调优。
  - **Mixture-of-Experts** 的路由温度 + 专家到 GPU 的 placement 联合优化。
- **"结构化信息"是关键**:Load-fraction reparameterization、preference kernel 这些技巧本质是在先验里编码系统知识。对 MLSys 研究者启发:不要指望 BO 自己摸出搜索空间,把 domain insight 塞进 kernel / acquisition 能让 BO 变得 8× 采样高效。
- **值得跟进的 future work**:
  1. **>2 档模型池的扩展**:路由阈值从标量变成 M-1 维 simplex,MOBO 是否仍 1 分钟收敛?或需要 hierarchical BO / NN surrogate 替换 GP。
  2. **与推理具体优化的结合**:BOUTE 把每个 (模型, GPU, 并行) 部署当黑盒,但内部的 chunked prefill / P-D disaggregation 本身也是决策变量——可以把 DistServe/Sarathi-Serve 的内部参数一并纳入搜索空间。
  3. **动态环境下的 online BO**:trace 漂移、GPU 抢占/动态价格(spot),离线数据库过期怎么办?contextual BO 或 Thompson Sampling 变体。
  4. **SLA 感知的 Pareto**:把 P99 质量、TTFT、TPOT 都加入目标,评估 qNEHVI 在 4+ 维 Pareto 上的可扩展性。
  5. **Router-deployment co-training**:目前路由器是预训练的,阈值是 BO 出来的;若允许路由器在反馈中再微调,是否能进一步拉平 Pareto 前沿?
- **最有价值的切入点**:在 BOUTE 基础上做一个**大规模多模型、多租户、动态价格**的 serving benchmark(类似 SpotServe × Helix × BOUTE 三者的统一评测场景),同时公开离线模拟器——这是一个可以支撑多篇 follow-up 的基础设施型贡献。

---

## 8. 总结

BOUTE 把异构模型路由(算法层)和异构 GPU 部署(系统层)首次表达成一个带约束的多目标联合优化问题,并用带结构化先验的 MOBO(load-fraction 编码 + model-GPU preference kernel + constrained qNEHVI)高效求解。相比 Stand-Alone 基线最多 2.57× 降延迟、平均 1.58×;相同质量+延迟要求下平均节省 38% 成本。核心贡献与适用场景清晰:异构 GPU 与多模型并存的生产级 LLM 服务,且 workload 相对稳定的场景。主要局限是模型池只验证到 2 档、与更强异构部署基线(Helix/Mélange)缺少正面 Pareto 对比、未考虑动态价格与路由器分布漂移。从 MLSys 方法论角度,"把 BO 当调度器"这条思路(结构化 kernel + 硬约束 + 离线代理)值得迁移到训练并行搜索、MoE 路由、推理栈多维调优等一系列黑盒联合优化问题。
