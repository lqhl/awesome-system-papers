# Beat the Long Tail: Distribution-Aware Speculative Decoding for RL Training

**作者**：Zelei Shao, Vikranth Srivatsa, Sanjana Srivastava, Qingyang Wu, Alpay Ariyak, Xiaoxia Wu, Ameen Patel, Jue Wang, Percy Liang, Tri Dao, Ce Zhang, Yiying Zhang, Ben Athiwaratkun, Chenfeng Xu, Junxiong Wang

**链接**：https://proceedings.mlsys.org/paper_files/paper/2026
**源文件**：[[f899139df5e1059396431415e770c6dd.pdf]]

## 1. 背景

RL 后训练(RL post-training)已经成为对齐大语言模型的核心环节。以 InstructGPT、DeepSeek-R1 为代表的 RL 训练流程普遍采用「rollout → reward → policy update」三段式循环,其中 rollout 阶段要求对当前 policy 进行自回归解码,生成带标签的轨迹。随着模型规模、上下文长度和采样次数的增长,rollout 阶段的耗时占比急剧上升:作者实测与 VeRL 社区的报告都显示,rollout 通常消耗整个 RL 训练 wall-clock 时间的 70% 以上,远超反向传播与参数更新。

一条看似自然的加速路径是把 LLM serving 领域的加速技术 —— 比如 PD disaggregation、quantization、speculative decoding —— 直接搬到 RL rollout 上。但作者指出,RL rollout 有三个与 serving 显著不同的特性:所有样本必须全部完成推理才能进入下一步;同一批 prompt 会跨 epoch 反复出现;以及 policy model 本身在不断更新。这些差异决定了单纯照搬 serving 方案并不最优。

---

## 2. 要解决的问题

论文针对的核心瓶颈是 **RL rollout 阶段的长尾 straggler 效应**。解码启动时 batch 打满,但短序列会先完成,有效 batch size 快速塌缩,最终几条长序列独占 GPU,使整个 step 的 makespan 由尾部决定(Figure 1:batch size 随时间从 128 跌至 0,在 DAS 之前要跑 ~220 个单位时间)。

现有方案的不足体现在:

- **传统 speculative decoding**(如 EAGLE 系列)针对小 batch 推理服务优化,依赖预训练好的 drafter head。RL 训练中 policy 持续更新,drafter 很快漂移,如果不频繁重训,acceptance rate 会持续走低。
- **并发工作**:SPEC-RL 用历史轨迹作 draft,但引入 lenience 参数,改变了输出分布;FastGRPO 训练一个 neural drafter,显存开销大;RhymeRL 考虑 batch 长度偏斜,但没有按 prompt 难度细化 draft 策略,也没处理 policy drift 造成的 window 问题。
- **放松训练保真度的方案**(truncation、quantization)会牺牲 reward 曲线或在长推理任务中降精度。

目标是:在完全不改变输出分布(即保持 RL reward 曲线与 baseline 一致)的前提下,显著压缩长尾 rollout 时间。

## 3. 洞察与设计

**关键洞察**:RL rollout 相比 serving 具有三个可利用的独特属性——(1)同一批 prompt 会跨 epoch 反复出现,历史轨迹蕴含稳定的 prompt 级模式;(2)由于长序列决定 step makespan,对不同长度的请求投入相同的 draft 预算是浪费,应把算力倾斜给长尾;(3)policy drift 具有局部性,相邻 epoch 的 rollout 相似度高、远距离 epoch 相似度快速衰减(Figure 2 的对角带块结构),这意味着 sliding-window 历史就足够支撑 draft。

基于这三点,DAS 把传统 speculative decoding 做了两个维度的改造(Figure 3 系统总览):

### 3.1 自适应非参数 drafter(Distribution-aware Drafter)

- **用 suffix tree 取代 neural drafter**:在 sliding window 内的近期 rollout 上构建 suffix tree,解码时以当前上下文作为 pattern 做 top-down longest-match,沿匹配路径提出多 token 草稿,由 target 模型并行 verify。验证完成后用 Ukkonen 在线算法 $O(n)$ 增量插入新轨迹。既避开了 neural drafter 的训练/重训成本,也能随 policy 一起演化。
- **按问题分片(per-problem suffix tree)**,配上 prefix trie 做路由。全局 tree 会把不相关问题的模式混在一起 —— Figure 6 显示,global+request tree 的 acceptance 低于 problem-scoped,而且查询和维护代价更大。
- **Sliding window**:实验表明 window=16/32 在 acceptance 和 latency 间取得最好折衷,window=all(全局历史)反而因为陈旧轨迹干扰导致单 token speculative latency 最高。
- **为什么是 suffix tree 而不是 suffix array**:Figure 5 实测 suffix tree 在 1M token 规模下 speculate 时间比 suffix array 快 2–20×,更重要的是 suffix array 动态更新需要局部重建,update 成本相差 3 个数量级。对每轮都要吃新轨迹的 RL 来说,suffix array 基本不可用。

### 3.2 长度感知的 speculation 预算分配(Length-aware Speculation Policy)

作者建立了一个 rollout latency 解析模型:

$$t_{\text{fwd}} = c_{\text{base}} + c_{\text{tok}} n_{\text{toks}}$$

实测 per-forward-pass 延迟与 token 数呈线性关系(Figure 8,平均相对误差 ~12%)。总 latency 则由「基本开销 $c_{\text{base}} N_{\text{fwd}}$」+「token 成本 $c_{\text{tok}} N_{\text{toks}}$」+「常数 $C$」构成。在此基础上用指数饱和的 acceptance 模型 $A_i(p_i) = k_i l_i (1 - e^{-\alpha_i p_i / l_i})$(附录有详细推导)建立一个 n 请求的凸优化问题,得到每条请求最优 draft budget 的闭式解:

$$p_i^* = -\frac{l_i}{\alpha_i}\ln\!\Big(1 - k_i(1 - N_{\text{fwd}}/l_i)\Big),\ \text{for}\ N_{\text{fwd}} < l_i$$

该解给出三条操作性结论:长序列拿更大 draft 预算;长度 $l_i \le N_{\text{fwd}}$ 的短序列直接禁用 speculation;drafter 能力 $k_i$ 弱时预算上限收紧。

运行时不可能直接拿到精确的 $l_i$,所以作者用一个层次化启发式:把 prompt 按历史统计分成 Long/Medium/Short 三档,初始档位由该 prompt 过去 rollout 的长度分布 argmax 决定;生成过程中根据已生成的 partial length $l$ 用贝叶斯后验 $P(c|l, \text{Init}_r)$ 动态升降档。

## 4. 实现细节

- **框架层**:在 VeRL 上做少量改动,sampling 走 vLLM,speculation 路径复用社区的 suffix-tree speculative decoding 实现(基于 SuffixDecoding(Oliaro et al., 2025)的思路),在 rollout 结束后把新轨迹同步回 per-problem 的 suffix tree 和 per-problem 的 prefix trie 中。
- **数据结构**:suffix tree 用 Ukkonen 在线算法,插入 100 个 token 的更新成本保持亚毫秒级;配套的 LCP / enhanced suffix array 只用作对比基线。Prefix trie 用于路由,从 prompt 哈希到对应的 per-problem suffix tree。
- **预算调度**:在每个 rollout step 开始时,根据 sliding window 统计为当前 batch 估算 $c_{\text{base}}$ / $c_{\text{tok}}$ / $\alpha_i$ / $k_i$,对每条请求按 Long/Medium/Short 档位选择 draft budget $p_i$。小模型下(如 1.5B)prefix routing 的 CPU 开销会盖过收益,此时 disable prefix trie,直接查 per-problem suffix tree。
- **Window 管理**:window size 绑定优化器步长(更激进的参数更新 → 更短 window),并对较旧 epoch 的匹配做温和降权。
- **训练配置**:数学 RL 用 DeepSeek-R1-Distill-Qwen-7B,max seq 16K,batch 128×16/8=256,30 steps,$T=0.6$,单节点 8×H100;代码 RL 用 Qwen3-8B,max seq 16K,batch 32×8/16=16,两节点 8×H100 + Ray cluster 做代码执行,基座 RL 算法都是 GRPO。
- **scale**:作者补充说扩展到 ~14B 模型、最多 6 台 8×H100 节点,所有耗时数字均为实际 wall-clock。

其他关键数字:

- **Drafter 对比**(Figure 4):EAGLE-3 在整个训练过程中 average accepted tokens 稳定在 2.3–2.7,几乎没有 growth;DAS 从 ~2.5 上升到 4–5,随 policy 演化还在继续爬升 —— 直接说明自适应 drafter 真的在吃 policy drift 的红利。
- **有效 batch size 退化**(Figure 1):baseline 从 128 跌到 0 大约需要 220 个时间单位,DAS 只要 ~110,说明长尾被显著压扁。
- **Suffix tree vs array**(Figure 5):在 1M token 规模下,suffix tree speculate 延迟 ~0.4 ms,suffix array ~1.0 ms;更新成本差 >1000×。
- **Window 扫描**(Figure 7):window 32 能在 accepted tokens 和 per-token speculative latency 之间取得最好的帕累托点,window=all 反而拉高延迟。
- **长度分布**(Figure 9):按 prompt 统计的 mean vs max generation length 散点图显示最大长度随机爆到 16K 的现象非常普遍,直接证明"长度高度随机,但 prompt 级统计有结构"这一假设。

## 6. 批判性分析

- **速度增益的报告口径不太一致**。正文宣称「up to 50%」,但 conclusion 又说「over 30%」,代码 RL 实际只看到 ~25%。这里差的部分主要来自 math 场景 —— 而 math 的 batch 大(256)、序列极长(16K),恰好是长尾最严重、speculative decoding 最容易赚的情境。在更现实的代码 RL 上收益打对折,作者没深究这件事,更像是把 best case 放 abstract。
- **Acceptance model 的假设比较理想**。公式 (3) 里的 $A_i(p_i) = k_i l_i (1-e^{-\alpha_i p_i/l_i})$ 在附录里被作为「经验观察」带过,但实际上它强烈依赖「每轮 acceptance 指数衰减 + 固定 draft 长度」的假设,而 suffix tree 的匹配长度本身随上下文波动,这个模型是否还能闭式求出 $p_i^*$,论文没做 sensitivity 分析。闭式解在论文里卖相好,实际运行时估 $\alpha_i$、$k_i$ 的噪声怎么传播到调度,没有说清。
- **Length prediction 的方法偏薄**。把长度分成三档、用 argmax 历史分布初始化 —— 作者自己在 Figure 9 里展示的散点其实说明 max generation 对同一 prompt 的方差极大(平均几千、最大顶到 16K),三档分桶是否能稳定捕获这种 heavy-tailed 行为,缺少对 misclassification rate 的量化。更细粒度的预测器(哪怕是 GBDT)可能会显著改善,但这条路被跳过了。
- **per-problem suffix tree 的内存和规模天花板没讨论**。1209 题 × per-problem 一棵 suffix tree,再乘上 sliding window 里 16 条轨迹 × 每条 16K tokens,这在大型 RL 数据集(几万题)上会不会爆内存?论文没有给出对应的 memory footprint 数据。
- **对比基线有些不公平**。Figure 4 拿 EAGLE-3 对比 DAS,但作者承认 EAGLE 需要持续重训才能跟上 policy,实验里并未给 EAGLE 做重训,相当于比了一个"故意不更新的"EAGLE,结论倾向偏乐观。更公平的对照应该是 EAGLE + 定期蒸馏,而不是 frozen EAGLE。
- **与并发工作的差异讲得有点模糊**。RhymeRL 也考虑轨迹相似性与 batch 长度偏斜,SPEC-RL 也用历史轨迹,但论文没有直接做端到端对比实验,只在 related work 里做定性 critique。读者很难判断 DAS 真正的定量优势。
- **章节编号**:第 6 节标题是「CONCLUSION」,但正文在第 5 节之后直接跳到 conclusion,没有单独的 limitation 讨论,这在系统类工作里不常见。

## 7. AI Infra / MLSys 视角

这篇工作刚好踩在 MLSys 当前最热的两个主题上 —— RL post-training 加速 + speculative decoding,值得 AI Infra 研究者认真品读。

**启发点**:

- **Rollout 是一个与 serving 不同的加速战场**。传统 LLM serving 优化 per-request latency,RL rollout 是 makespan 优化问题,所有请求必须同步完成。这提示我们,RL 场景下 scheduling / batching / speculation 都要重新设计,不能直接借鉴 serving 文献里的 goodput 或 SLO 指标。
- **「模型参数动,数据静」的新范式**。与 serving 的「模型参数静,输入动」对偶,RL rollout 的这个独特结构会让一批原本在 serving 场景里不 work 的方法重新变得 attractive(比如非参数 drafter、per-prompt 缓存、offline 构造的索引)。
- **Per-problem index 的一般化**。这种按 prompt 级构建索引的思路,可延伸到:为每个问题缓存 KV-cache、attention sink、prefill state、甚至 tool-call graph;在 agentic workflow 中,per-task 的 memory 可以显著压缩 prompt 重复部分。

**可操作的跟进方向**:

1. **更好的 draft budget 估计器**。用一个轻量 GBDT 或 GRU,以历史轨迹的 (mean, p99, last-epoch length, prompt embedding) 为特征预测本轮长度,在真实 RL loop 上对比三档启发式。作者的线性延迟模型 + 闭式最优预算,其实提供了一个很好的 reward proxy。
2. **把 suffix tree drafter 接到 Agentic RL**。Agentic workflow 中 tool 调用模板高度重复,suffix tree 应该能吃到更多红利。结合 Agent 级 sliding window(比如按 trajectory type 分桶)或是基于 MCTS 的轨迹级重放,可能比 DAS 的 per-problem 更有效。
3. **Off-policy/async RL 下的再验证**。DAS 假设 on-policy,sliding window 是「刚刚的 rollout」;一旦切到 async / off-policy(DeepSeek R1、OpenRLHF 的一些设置),window 的定义会复杂很多。一个研究点是:在 off-policy RL 里 suffix tree 该用 importance sampling 下的多条 policy 的轨迹如何混合。
4. **长度预测 + KV-cache scheduling 的协同设计**。长度预测本身在 vLLM / DistServe 里就能帮助更好的 KV-cache 分配与 eviction。如果 rollout 能获得长度预测,那 speculation budget + KV placement + prefill scheduling 三者可以联合优化。
5. **非参数 drafter 的扩展**:suffix tree 只利用 lexical match。可以做 "embedding-aware suffix index"(例如在 token embedding 空间做 ANN 检索),结合 soft-match 提高 acceptance;也可以把 suffix tree 和 small draft model ensemble,互为补充。
6. **扩展到 multi-modal / diffusion 场景**。VLM 的 RL 后训练同样受长尾影响,如何在视觉 token 上构造类似 suffix tree 的结构,是个比较大胆的方向。

---

## 8. 总结

DAS 把 speculative decoding 针对 RL rollout 做了对症的改造:用 per-problem、sliding-window 的 suffix tree drafter 代替 neural drafter,解决 policy drift 下的 drafter 漂移;用 length-aware 的 draft budget 把算力倾斜给决定 makespan 的长尾序列,解决同步 RL 下"最慢的决定全局"的结构性问题。两者叠加,在 math RL 上实现 ~50%、在 code RL 上实现 ~25% 的 rollout 加速,且完全保持 reward 曲线 —— 这是 RL 加速工作中难得不丢精度的结果。适用场景是 on-policy、prompt 数据集固定、长尾突出的 RL 后训练;在 prompt 数据集极大、off-policy 或 reward 不稳的情境下,其 per-problem + sliding window 假设能走多远,还需要进一步验证。
