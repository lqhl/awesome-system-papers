## 1. 背景

学习型优化器(Learned Optimizer, LO 或 L2O)是过去十年里一个长期被研究、却始终没有进入主流的方向。其核心思想是用一个小的神经网络(通常是几层 MLP,作用于每个参数)来替代 Adam/SGD 的封闭式更新规则,通过元学习(meta-learning)在大量训练任务上得到一个"会优化的优化器"。其中最具代表性的工作是 Google 的 VeLO(Metz et al., 2022b)——它经过约 4000 TPU-月的元训练,据报告可以在不调超参的情况下击败精调的 NadamW + cosine schedule。

然而,尽管 VeLO 的元学习投入巨大、报告性能强劲,**社区里几乎没人真正在用它**。原因不是性能,而是工程门槛:VeLO 只有 JAX 实现,而 PyTorch 占据约 80% 的 ML 社区;预训练好的优化器权重没有标准的分发渠道(对比预训练模型有 HuggingFace Hub);现有 L2O 框架的代码主要服务于 meta-training,对 meta-testing(直接拿来用)不友好;最关键的是,LO 本质上需要对每个参数做一次小 MLP 前向,在大模型上的 per-step overhead 远超 Adam,工程师天然抗拒。

PyLO 这篇论文聚焦于把 LO 从研究 demo 变成可用工具,核心是 PyTorch 集成 + CUDA kernel 加速 + HuggingFace Hub 权重分发。

---

## 2. 要解决的问题

作者把 L2O 难以普及的原因明确归纳成四条:

1. **过度聚焦元训练**:Open-L2O、Google learned_optimization 这些 repo 大量代码服务于训练优化器本身,而绝大多数下游用户只想拿来做 meta-testing(直接当 optimizer 用)。代码冗余、依赖膨胀、入门曲线陡峭。
2. **缺少 PyTorch 实现**:Google 官方 LO 只支持 JAX/Optax;Open-L2O 虽支持 PyTorch 但缺少其他必要功能(如 HF 集成、CUDA 加速)。
3. **优化器权重没有分享机制**:预训练模型可以发到 HuggingFace,但 LO 权重连一个标准的版本化、分发、文档化机制都没有。
4. **per-step overhead 过高**:朴素 PyTorch 实现对每个参数张量需要 74–252 次 kernel launch,显存里要物化 `mn × d_feat` 大小的中间特征张量。在 ViT-B/16 上,naive small_fc_lopt 的 optimizer step 是 756.80 ms,而 Adam 只有 4.90 ms——慢了 150 倍。这种 overhead 让 LO 在生产中根本不可接受。

PyLO 的目标是同时把这四个障碍都拆掉。

---

## 3. 洞察与设计

**关键洞察**:LO 朴素实现的瓶颈不是算法本身,而是 PyTorch 通用神经网络模块对"每个参数张量都跑一个小 MLP"这种特殊计算模式的不适配。具体来说有两点观察:(1)特征构造(从 grad、momentum、second moment 等推导出 39 维特征向量)可以一遍扫完参数完成,无需把全张量物化到 global memory;(2)MLP 的前向传播可以与特征构造融合,中间激活全部留在寄存器里,从而消除整条 pipeline 中所有的 kernel launch overhead 和中间张量分配。换句话说,**memory bandwidth 才是真瓶颈,不是 compute**。

基于这个洞察,PyLO 的设计有两层:

**库层架构**(共四个模块):

- `pylo.optim`:实现 `torch.optim.Optimizer` 接口,管理参数级 accumulator(momentum、second moment、Adafactor row/column factors)、state_dict 序列化、LR 缩放等。
- `pylo.models`:封装 LO 的 MLP 权重和 forward,与 HuggingFace Hub 集成,支持 `from_pretrained` 一行加载。
- `pylo.csrc`:CUDA kernel 实现,核心加速来源。
- `pylo-examples`:把示例任务(ImageNet ViT、FineWeb-EDU GPT-2)与 PyLO 主库解耦,作为 starter kit。

**架构图**(Figure 2):用户写 `from pylo.optim import VeLO; optimizer = VeLO(model.parameters())`,后续与普通 PyTorch optimizer 完全一致,可以叠加 cosine schedule、weight decay 等任何 `torch.optim` 生态的工具。这是最大的可用性进步。

**LO 计算 pipeline**(Figure 3):对每个参数张量 `(m × n)`,先用 `param`、`grad`、`momentum`、`second moment` 及其 row/column factors 构造 `(mn × d_feat)` 的特征矩阵,在参数维度上 reduce 得到归一化统计量,归一化后送入 LO 的 MLP,输出 magnitude 和 direction,合成更新量 `Δθ = direction × exp(magnitude × α) × β`(α=β=0.01)。

## 4. 实现细节

CUDA kernel 设计是论文最有技术含量的部分,采用**两个 fused kernel**的两遍法:

**Kernel 1 — Fused Statistics Collection**

- 单次扫描整个参数张量,在寄存器里实时计算 `d_feat ≈ 39` 维特征向量
- 不物化特征张量,只维护一个 `d_feat` 维 thread-local accumulator,累加特征的平方
- 层次化 reduction:thread → warp(shuffle 指令)→ block(shared memory)→ global(atomic add)
- 每 block 只用 `O(d_feat)` 共享内存,全局也只写 `O(d_feat)` 字
- 这一步合并了原来的 `construct_features()` 和 `compute_squared_average()`

**Kernel 2 — Fused Apply**

- 把归一化统计量 `1/sqrt(E[feat²])` 加载到 shared memory,广播给 block 内所有线程
- 第二次在寄存器里重算特征(用计算换内存带宽)
- 内联 MLP 前向:`hidden = relu(Linear1(features))` → `relu(Linear2(...))` → `Linear3(...)` 输出 magnitude 和 direction
- 直接计算 update 并就地更新 `p[i] -= update`
- 这一步合并了 `construct_features()`、`feature_normalization()`、`apply_lo()`

**内存层级利用**:
- Registers:`d_feat ≈ 39` 维特征向量 + MLP 中间激活(单周期访问)
- Shared memory:归一化统计量,block 内广播
- Global memory:只读写参数、梯度、accumulator

**效果**:kernel launch 次数从 74–252 降到 30–114(Figure 4 显示约 8× 提升),临时显存分配减少 `mn × d_feat` 字。值得注意的是,**第二次重算特征**是有意为之的"compute-for-memory"权衡——典型的 GPU memory-bound kernel 优化套路,只是这次用在了 LO 上。

**分布式优化器步骤**(Section 7):传统 DP 训练做 all-reduce 梯度后,每个 GPU 重复跑一次 optimizer step,这对 Adam 这种轻量 optimizer 无伤,但对 LO 是巨大浪费。PyLO 把它拆成:reduce-scatter 梯度 → 每卡只更新自己负责的参数切片 → all-gather 更新后的参数。在 4 张 H100 上训 125M transformer:small_fc_lopt 节省 31.86 ms,VeLO 节省 18.96 ms,而 Adam 只节省 4 ms——LO 越重,分布式步骤收益越大。

## 5. 实验结果

**主结果(Table 2,A100 80GB):**

| Model | Optimizer | Opt step (ms) | 相对 naive |
|---|---|---|---|
| ViT-B/16 (BS=32) | Adam | 4.90 | — |
| ViT-B/16 (BS=32) | small_fc_lopt (naive) | 756.80 | baseline |
| ViT-B/16 (BS=32) | small_fc_lopt (CUDA) | 99.59 | -86% |
| ViT-B/16 (BS=32) | VeLO (naive) | 585.11 | baseline |
| GPT2-355M (BS=4) | Adam | 20.12 | — |
| GPT2-355M (BS=4) | small_fc_lopt (naive) | 2872.17 | baseline |
| GPT2-355M (BS=4) | small_fc_lopt (CUDA) | 319.14 | -88% |
| GPT2-355M (BS=4) | VeLO (CUDA) | 284.37 | -88% |

**Scaling vs JAX**(Figure 5,GPT-2):JAX 实现在 1B 模型上 OOM(80GB A100);PyLO CUDA 不仅能跑通,而且在 125M/355M 上 step 时间是 JAX 的一半。

**MLP 微基准**(Figure 6):覆盖宽度 32–8192、深度 1–N,naive 实现普遍比 CUDA 慢一个数量级。

**H100 增强版 PyLO-CUDA++**(Figure 9,8192×8192 矩阵):29.96 ms vs PyLO-CUDA 63.28 ms(2.1× 提升);仍然显著高于 Adam 的 1.91 ms 和 Muon 的 23.70 ms。增强手段包括:减少 MLP 权重的 HBM 读、异步显存拷贝、使用 tensor core/WGMMA 指令。

**收敛性**(Table 4):
- ViT-B/16 ImageNet-1K (480 epochs):VeLO 78.45% vs Adam+cosine 77.22% vs μLO 62.14%(μLO 在 65k 步后训练发散)
- GPT-2 355M FineWeb-EDU (10B tokens):VeLO loss 2.89 vs Adam 2.91 vs μLO 3.18

**LRS + weight decay 消融**(Figure 8):
- μLO 加 cosine schedule 后训练稳定性大幅改善,从 65k 步发散延长到完整 150k 步,ImageNet 准确率从 62% 提升到 71%
- VeLO 对 schedule/weight decay 几乎不敏感(其内部已有自适应机制)
- 论文认为 LO 与传统手工技巧组合仍能受益,这与 LO "替代手工启发式"的初衷有微妙张力

**正确性验证**(Appendix E,Figure 17):PyLO 与原 JAX 实现在 5000 步内训练曲线几乎重合,实现等价性确认。

## 6. 批判性分析

**1. "86-88% 加速" 的参照系是个稻草人**:naive PyTorch 实现要发起 74–252 次 kernel launch、物化 `mn × d_feat` 维中间张量,这是任何写过 GPU kernel 的人都会避免的反模式。把它当 baseline 来宣称 8× 加速,本质是"修了一个糟糕的实现"而不是算法贡献。更公允的对比应该是 `torch.compile` 或 inductor 自动 fuse 后的版本,论文没做这个对比。

**2. CUDA 加速后,LO 仍比 Adam 慢一个数量级**:ViT-B/16 上 small_fc_lopt CUDA 的 99.59 ms vs Adam 的 4.90 ms 是 **20× 差距**;H100 上 PyLO-CUDA++ 的 29.96 ms vs Adam 的 1.91 ms 是 **16× 差距**。论文用"batch size 越大,relative overhead 越小"来弱化这一点,但这是**摊销效应**,不是 step time 本身的改善——同一 batch size 下用户付出的真实 wall-clock 仍然是 Adam 的 16–20 倍。这种 overhead 在 inference-bound、显存吃紧的大模型预训练场景里仍然很难接受。

**3. "VeLO 78.45% vs Adam 77.22%"** 的统计意义存疑:1.23% 的 top-1 提升,在 ImageNet ViT-B/16 上属于多 seed 噪音的量级;论文只报告单点结果,没有 confidence interval、没有 multi-seed,也没有把 4000 TPU-月的元训练成本摊到这个收益上做 cost-benefit。

**4. μLO 在 65k 步发散**是被轻描淡写的硬伤:作者归因于"meta-training horizon 只有 1000 步",但这恰恰说明 LO 的泛化能力远弱于其元训练时见过的分布。"加 cosine schedule 才能跑完 150k 步"这种修复方式与 LO 本应"无需手工调度"的卖点相悖——论文里坦诚承认了这点,但没有反思 LO 的根本范式问题。

**5. Per-parameter MLP 评估架构本身是天花板**:每参数 39 维特征 × 3 层 MLP 的计算量,无论怎么 fuse,都比 Adam 的两次乘加重 10–100 倍。如果不能在算法层面把 MLP forward 也"摊薄"到全张量(比如改用一个对全张量做 reduction 后再决定 update 的架构),工程优化的边际收益会越来越小。

**6. Distributed step 的 31.86 ms 节省被独立报告**,但论文没说明这与 Section 7 强调的 "ZeRO 风格分片优化器状态" 之间的差距——他们说"留给 future work",但这是 LO 在大模型时代真正能否替代 Adam 的关键。当前结果只在 4 卡上验证了 reduce-scatter 思路,实际万卡训练场景没有数据。

**7. 缺少与 Muon 的对比**:Muon 是当前最具竞争力的轻量级新优化器,Table 3 出现了它,但 Section 8 的收敛性比较里没有 Muon vs VeLO 的端到端对比,这削弱了 LO 在 2026 年仍然值得追求的论证。

## 7. AI Infra / MLSys 视角

PyLO 是典型的"研究产物 → 生产工具"工程化论文,对 AI Infra 研究者有几点启发:

**1. fuse + 寄存器存特征 + 重算换带宽**这套 GPU kernel 优化模式可迁移性极广。任何"per-element 计算 + 多次 reduction"的结构(比如 RoPE 应用、自定义 normalization、LoRA adapter forward)都可以套用同样的两遍 fused kernel 模板。建议关注 PyLO 的 `csrc` 实现细节,作为 PyTorch custom op 的范例代码。

**2. "Optimizer 也可以从 HuggingFace Hub 下载"是一个被忽视的产品形态**。如果未来有"针对 LLM 预训练任务集元训练的 LO 权重"这种产品,可能会成为继 base model 之后又一类资产。值得跟进的具体研究问题:(a)如何为不同任务集合(vision、code、math)分别训练专家化 LO;(b)如何评估和发布 LO 权重的"训练分布卡片"(类似 model card)。

**3. LO 的分布式步骤是 ZeRO-style sharding 在 optimizer 维度的延伸**,而且因为 LO 是 per-parameter 操作,代价最低的分片只需通信 `d_feat` 维(约 39 个标量)的归一化统计量,这比传统的 all-reduce 要轻得多。这给"超大模型 + 复杂 optimizer"组合提供了一条值得深挖的路径。

**4. Behavior cloning 二阶优化器**(论文提到的 future work):如果能用便宜的 LO MLP 蒸馏 SOAP/Shampoo 这种昂贵的二阶方法,对大模型训练可能是 game changer。这个方向应该是 LO 在 LLM 时代的最强卖点——目前 SOAP 的 wall-clock 开销让它在大模型上难以普及。具体研究问题:用什么样的训练任务分布做 distillation?MLP 容量需要多大?能保留多少二阶信息?

**5. 硬件-优化器协同设计**(论文提到):per-parameter MLP forward 的计算模式与传统矩阵乘有本质差异,可能需要专用 systolic array 或 NPU pattern。这是个值得长期跟踪的硬件方向,虽然短期内不太可能落地。

**6. 切入点建议**:对小实验室来说,最现实的 follow-up 是在 PyLO 基础上做"任务专用 LO 元训练"——比如针对代码模型预训练、agent 强化学习场景,训练一个针对该分布的 LO,在 HF Hub 上发布,用 PyLO 的 CUDA kernel 让它真正可用。元训练成本可以用 μLO 的"宽度无关元训练"方法控制在百卡日量级,而不是 VeLO 的 4000 TPU-月。

## 8. 总结

PyLO 解决了学习型优化器从 2016 年提出至今难以被 PyTorch 社区采用的工程层面障碍:它提供了符合 `torch.optim.Optimizer` 接口的 VeLO/small_fc_lopt 实现、CUDA fused kernel(将 optimizer step 时间从 naive 实现的数百毫秒降到几十到一百毫秒)、HuggingFace Hub 权重分发,以及分布式步骤的初步支持。在 ViT-B/16 ImageNet 上 VeLO 略优于精调 Adam(78.45% vs 77.22%)、在 GPT-2 355M FineWeb 上达到更低 loss,展示了 LO 在实际大规模任务上的潜力。论文的核心系统贡献是把 "per-parameter MLP" 这种特殊计算模式映射到 GPU 内存层级的 fused kernel 模板。

主要局限:即使经过深度优化,LO 的 step time 仍比 Adam 慢 16–20 倍,naive baseline 是稻草人,μLO 训练稳定性问题被轻描淡写,且收敛性提升的统计显著性未充分论证。该论文的真正价值在于**把 LO 从"只能在 Mila/Google 内部跑"变成"任何 PyTorch 用户能 import 即用"**,工程化贡献清晰,适合作为后续 LO 研究的基础设施;但 LO 范式本身能否在 LLM 预训练时代撼动 Adam,这篇论文没有给出决定性证据,仍是开放问题。
