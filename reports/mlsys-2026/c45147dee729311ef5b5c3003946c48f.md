## 一、背景

Learned Optimization（L2O）是近十年来活跃的研究方向，其核心思想是用神经网络（通常是小型 MLP）来替代人工设计的优化器（如 Adam），通过 meta-training 学习一个通用的参数更新规则。VeLO 是目前公开可用的最强 learned optimizer，在无需超参调优的情况下可媲美甚至超越 well-tuned Adam，但其训练耗费了 4000 TPU-months，且基于 JAX 实现。

尽管 learned optimizer 在理论和实验上都展示了巨大潜力，但在实际深度学习社区中几乎无人使用。PyTorch 占据了约 80% 的 ML 社区份额，而现有的 learned optimizer 实现要么绑定在 JAX 生态中，要么与 meta-training 代码深度耦合，缺乏独立使用的便利性。

---

## 二、要解决的问题

现有 learned optimizer 面临四个核心采用障碍：

1. **过度聚焦 meta-training**：现有开源库（Learned Optimization、Open-L2O）将大量代码用于 meta-training，而非优化器的实际部署和使用，导致代码臃肿、依赖复杂，对只想用预训练优化器的用户构成极高门槛
2. **缺乏 PyTorch 实现**：最强的 learned optimizer（VeLO、small_fc_lopt）仅有 JAX 实现，无法与 PyTorch 生态中丰富的训练框架和工具链集成
3. **无法共享优化器权重**：不同于 HuggingFace Hub 上广泛共享的模型权重，learned optimizer 缺乏标准化的权重分享机制，阻碍了社区协作
4. **per-step 计算开销过大**：learned optimizer 需要对每个参数执行一次小型 MLP 前向传播来计算更新，朴素实现会产生数百次 kernel launch，导致训练吞吐量大幅下降，在实际场景中不可接受

---

## 三、洞察与设计

**关键洞察**：learned optimizer 的 per-step 计算瓶颈在于内存带宽而非算力——朴素实现中每个参数张量需要 74-252 次 kernel launch，每次中间结果都要写回 global memory，产生巨大的内存流量。通过将 feature 构建、归一化和 MLP 推理融合到两个 kernel 中，让中间数据全部留在寄存器和 shared memory 中，可以将这个瓶颈彻底消除。

基于此洞察，PyLO 的设计包含四个核心模块：

- **pylo.optim**：遵循 `torch.optim.Optimizer` 接口的优化模块，管理参数状态（momentum、second moment 等 accumulator）、feature 计算、update step，支持 state dict 保存恢复
- **pylo.models**：封装 learned optimizer 的神经网络架构和权重，集成 HuggingFace Hub 实现自动下载和版本管理
- **pylo.csrc**：CUDA 加速核心，实现融合 kernel
- **解耦评估**：通过独立的 PyLO-Examples 仓库提供 ImageNet 和 LM pre-training 的评估示例，保持主库精简

## 四、实现细节

### CUDA 融合 Kernel 设计

PyLO 将 learned optimizer step 从朴素的数百次 kernel launch 压缩为两个融合 kernel：

**Kernel 1（Feature 统计收集）**：单次遍历所有参数，在寄存器中 on-the-fly 计算 feature 并累积其平方值用于归一化。使用层次化 reduction：thread-local accumulator → warp shuffle → shared memory → atomic add to global memory。仅需 O(d_feat) shared memory per block 和 O(d_feat) global memory。

**Kernel 2（融合 Feature 构建 + 网络推理 + 参数更新）**：
1. 将归一化统计量加载到 shared memory
2. 再次在寄存器中构建 feature（trade computation for memory bandwidth）
3. 在寄存器中内联执行 MLP 前向传播（权重通过 `__ldg` cache 读取）
4. 计算 `update = direction × exp(magnitude × α) × β` 并直接更新参数

内存层次利用策略：
- **寄存器**：feature 向量（~39 维）和 MLP 激活值，单周期访问
- **Shared memory**：d_feat 维归一化统计量，每 block 加载一次广播
- **Global memory**：仅读取参数/梯度/状态 buffer，仅写回更新后的参数

### 分布式优化器 Step

在数据并行训练中，将原本的 all-reduce + 冗余 optimizer step 改为 reduce-scatter + 分布式 optimizer step + all-gather，使每个设备只对部分参数执行 optimizer step。在 4×H100 上训练 125M 模型，small_fc_lopt 的 optimizer step 时间从 136.53ms 降至 104.67ms（省 31.86ms），相对 Adam 的开销降至 9%。

### H100 优化（CUDA++）

针对大张量（如 8192×8192，对应 70B 模型的隐层），引入：减少 global MLP weight 读取次数、异步内存拷贝、利用 Tensor Core 和 WGMMA 指令，实现 2.1× speedup over baseline CUDA。

## 五、实验结果

### Optimizer Step 时间

| 模型 | 优化器 | BS/SL | Forward (ms) | Backward (ms) | Opt Step (ms) | 加速比 |
|------|--------|-------|-------------|--------------|--------------|--------|
| ViT-B/16 | Adam | 32/197 | 17.52 | 38.13 | 4.90 | - |
| ViT-B/16 | small_fc_lopt (naive) | 32/197 | 17.52 | 38.13 | 99.57 | - |
| ViT-B/16 | small_fc_lopt (CUDA) | 32/197 | 17.52 | 38.13 | 9.56 | -86% |
| ViT-B/16 | VeLO (naive) | 32/197 | 17.52 | 38.13 | 585.11 | - |
| ViT-B/16 | VeLO (CUDA) | 32/197 | 17.52 | 38.13 | 113.58 | -80% |
| GPT-2 355M | Adam | 4/1024 | 197.41 | 392.29 | 20.12 | - |
| GPT-2 355M | small_fc_lopt (naive) | 4/1024 | 197.41 | 392.29 | 319.14 | - |
| GPT-2 355M | small_fc_lopt (CUDA) | 4/1024 | 197.41 | 392.29 | 28.72 | -88% |
| GPT-2 355M | VeLO (naive) | 4/1024 | 197.41 | 392.29 | 2378.93 | - |
| GPT-2 355M | VeLO (CUDA) | 4/1024 | 197.41 | 392.29 | 284.37 | -88% |

### 与 JAX 实现对比

CUDA 实现比 JAX 原始实现快 2×；更重要的是，JAX 实现在 80GB A100 上无法训练 1B 参数模型（OOM），而 CUDA 实现可以。

### 训练效果

| 优化器 | LM Loss ↓ (355M) | ViT Acc. ↑ (86M) |
|--------|-------------------|-------------------|
| µLO_M | 3.18 | 62.14% |
| VeLO | 2.89 | 78.39% |
| Adam + Cosine | 2.91 | 77.22% |

- VeLO 在 ViT-B/16 ImageNet 上达到 78.39% top-1（Adam 77.22%），在 GPT-2 355M 上 loss 2.89（Adam 2.91）
- µLO_M 因 meta-training horizon 仅 1000 步，在长训练中出现 divergence（65k 步后崩溃）
- 为 µLO_M 添加 cosine schedule 可将稳定训练范围从 65k 扩展到 150k 步，ImageNet 准确率提升到 71%
- VeLO 对 weight decay 和 schedule 不太敏感，但 µLO_M 可从中显著受益

## 六、批判性分析

1. **VeLO 的 overhead 仍然很大**：即使经过 CUDA 优化，VeLO 在 ViT-B/16 (BS=32) 上的 optimizer step 仍需 113.58ms，是 Adam (4.90ms) 的 23 倍。论文通过"增大 batch size 后相对开销减小"来淡化这个问题，但这意味着 learned optimizer 实际上只在大 batch、大模型的场景下才有实用性——而这恰恰是计算资源最紧张的场景

2. **训练效果提升有限**：VeLO 在 ImageNet 上比 tuned Adam 仅高 1.17%（78.39% vs 77.22%），在 LM 上 loss 仅低 0.02（2.89 vs 2.91）。考虑到 VeLO 本身的 meta-training 成本（4000 TPU-months）和额外的 per-step overhead，这个收益的性价比值得质疑

3. **评估规模偏小**：实验仅涉及 ViT-B/16 (86M) 和 GPT-2 355M，而论文声称 CUDA 实现可扩展到 1B 参数——但 1B 仅有 step time 测量，没有完整的训练效果评估。在当前 7B-70B 模型为主流的时代，355M 的评估缺乏说服力

4. **基线不够强**：语言模型实验仅与 Adam + Cosine 对比，未包含 Muon、SOAP 等近期高性能优化器的训练效果对比（虽然 step time 对比中包含了它们）。考虑到 Muon 在社区中展现的强大性能，这个缺失削弱了论文的说服力

5. **µLO_M 的 divergence 问题被轻描淡写**：µLO_M 在 65k 步后训练崩溃，最终只有 62.14% 准确率，论文将其归因于"limited 1000-step meta-training horizon"，但没有讨论这对 learned optimizer 的泛化能力意味着什么——如果 meta-training 的训练步数设置如此关键，那么 learned optimizer "无需调参"的核心卖点就大打折扣

6. **QKV 分离实验值得注意但解释不足**：分离 vs 合并 QKV 矩阵对 learned optimizer 性能有明显影响，这暗示 learned optimizer 对模型架构细节有较高敏感性，但论文未深入分析原因，也未讨论这是否意味着 learned optimizer 的"通用性"存在隐患

## 七、AI Infra / MLSys 视角

**对 AI 系统研究的启发**：

1. **Optimizer-as-a-Service**：PyLO 的 HuggingFace Hub 集成为 "optimizer weight sharing" 开辟了一个新范式。类比 model hub，未来可能出现针对不同任务域（CV/NLP/multimodal）甚至不同训练阶段的专用 learned optimizer，这与 AI Infra 中日益增长的训练配置自动化需求高度契合

2. **CUDA Kernel 融合策略的可迁移性**：论文的核心 CUDA 优化思路——将"per-parameter 的小 MLP 推理"融合为两个 kernel，中间结果全留在寄存器中——这种模式可迁移到其他 per-parameter 操作较重的场景，如 SOAP/Shampoo 等二阶优化器的高效实现

3. **分布式 optimizer step 的设计**：将 all-reduce 拆分为 reduce-scatter + 分布式 step + all-gather 的方案，对 ZeRO-style 训练中优化器开销较大的场景有参考价值。论文也指出 sharded optimizer states 是未来方向

**值得跟进的方向**：

- **Behavior-cloned distillation**：论文提到用 learned optimizer 去蒸馏 SOAP 等昂贵二阶优化器的行为，这是一个高价值方向——如果能用轻量 MLP 近似 SOAP 的更新规则，就能以接近 Adam 的成本获得二阶优化的收益
- **Hardware-optimizer co-design**：针对特定硬件（如 H100 Tensor Core、未来的 custom accelerator）定制 learned optimizer 的架构和 kernel，可能是 AI Infra 层面的差异化机会
- **大规模验证**：在 7B+ 模型上验证 learned optimizer 的效果和 overhead 是该方向走向实用的关键缺口

---

## 八、总结

PyLO 是一个将 learned optimizer（VeLO、small_fc_lopt）引入 PyTorch 生态的工程系统，通过遵循 `torch.optim.Optimizer` 接口、集成 HuggingFace Hub、以及自定义 CUDA 融合 kernel 解决了 learned optimizer 在可用性和性能上的核心障碍。CUDA kernel 将 optimizer step 开销降低 80-88%，分布式方案进一步将相对 Adam 的开销降至 9-13%。在 ViT-B/16 和 GPT-2 355M 上，VeLO 展现了与 tuned Adam 相当甚至略优的性能。但论文的评估规模偏小（最大 355M），VeLO 在小 batch 下的开销仍然显著，且 learned optimizer 的实际性能优势相对 meta-training 成本而言并不突出，该方向在大规模模型训练中的实用价值仍需进一步验证。
