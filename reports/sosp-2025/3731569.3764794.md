# Rearchitecting the Thread Model of In-Memory Key-Value Stores with μTPS

## 一、背景

内存键值存储（In-Memory KVS）是现代数据中心的核心基础设施，支撑分布式客户端对数据的快速、并发、共享访问。随着云网络从 1Gbps 演进到 200+Gbps、RDMA 实现个位数微秒延迟，以及 CXL 内存、Memory-Semantic SSD 等新型存储设备提供百万级 IOPS 和亚微秒延迟，KVS 的线程架构设计面临根本性变革。

用户态数据平面库（DPDK、RDMA libibverbs）采用非抢占式线程架构，线程绑定 CPU 核心、通过 spin-polling 与硬件交互，消除上下文切换开销。在此架构下，Run-to-Completion（RTC）模型成为主流——每个 worker 线程从头到尾处理完整个请求。MICA、FaRM 等系统均采用此模式。

---

## 二、要解决的问题

RTC 模型在极高吞吐（>10M ops/s）下暴露出两个核心问题：

1. **Cache 低效**：一个 KV 操作包含多个子任务（网络轮询/解析、索引遍历、数据拷贝、响应发送），它们的内存访问模式差异巨大。网络缓冲区可通过 DDIO 驻留在 LLC 中，几乎零 cache miss；但索引遍历和数据访问涉及大范围内存空间，是 cache miss 的主要来源。将这些异构子任务打包在单一函数中执行，导致各级 cache 频繁 thrashing，严重降低 CPU 流水线效率。单次 cache miss 引入 50-150ns 延迟，而完成一次 KV 操作仅需几百纳秒。

2. **争用放大**：RTC 下采用 share-nothing 设计虽避免锁，但在 skewed workload 下造成严重负载不均；采用 share-everything 设计虽然负载均衡，但同步开销随线程数增加急剧上升。RTC 模型中不同阶段被串行执行在同一线程上，一个阶段的锁竞争会阻塞该线程上所有其他阶段的执行。

现有工作（ShRing、Iat、CacheDirector）试图通过更好的 cache 分配和数据结构设计来改善 LLC 效率，但不改变线程架构本身，无法从根本上解决子任务间干扰导致的 cache thrashing。

## 三、洞察与设计

**关键洞察**：KV 请求处理的各阶段在 cache 驻留特性和多核可扩展性上存在本质差异——网络缓冲区和热点数据可以完全驻留在 CPU cache 中，而索引遍历和冷数据访问必然产生大量 cache miss；同时，只有索引/数据更新阶段受争用影响，其他阶段高度可扩展。将这两类阶段分离到不同线程池，并分配专用硬件资源（CPU 核心、cache ways），可以独立优化每个阶段。

基于此洞察，μTPS 重新拥抱 Thread-Per-Stage（TPS）架构，但从全新视角出发：不是按功能模块划分，而是按 **cache 驻留性**将所有阶段分为两层：

- **Cache-Resident（CR）层**：管理网络缓冲区和热点 KV 项。使用专用 worker 线程绑定特定 CPU 核心，通过 Intel CAT 分配专用 LLC ways，保持管理的数据量足够小以驻留 cache。采用 FSM 执行模型处理请求——命中热点直接返回，未命中则转发至 MR 层。

- **Memory-Resident（MR）层**：管理完整索引和所有数据项。广泛使用 batching、coroutine-based prefetching 来摊销 cache miss 开销。由于 CR 层已过滤掉热点请求，MR 层的 prefetch 不会浪费在已缓存数据上。

两层通过轻量级 CR-MR Queue（多生产者多消费者、all-to-all 映射、lock-free ring buffer）通信。每个请求紧凑编码为 16 字节。通过 tail pointer piggybacking 机制避免显式完成消息。

配套的三项关键设计：
- **Reconfigurable RPC**：基于 RDMA SRQ 实现单一接收缓冲区，所有 worker 线程通过取模 round-robin 共享，调整线程数只需修改一个全局变量，无需客户端协调。
- **Resizable Cache**：基于 hot set 采样（count-min sketch + min heap），通过 epoch-based 方式原子切换，支持动态调整缓存大小。
- **Auto-tuner**：层次化搜索（trisecting approach）自动调优线程分配、cache 大小和 LLC way 分配，10ms 监控窗口下 0.9 秒完成全部重配置，期间不中断服务。

## 四、实现细节

基于 μTPS 实现了两个 KVS：
- **μTPS-H**：使用 libcuckoo 哈希表索引，支持点查询
- **μTPS-T**：使用 MassTree B+ 树索引，支持点查询和范围查询

关键实现细节：

- **C++20 stackless coroutines**：将 put/get 操作转换为协程，在每次指针解引用前插入 prefetch 和 co_yield，worker 线程作为调度器在多个协程间切换，有效隐藏内存加载延迟。
- **并发控制**：两层均采用 share-everything 设计。8 字节以下数据用原子指令直接更新；更大数据项通过 CAS 获取锁位，读操作 lock-free（版本号校验）。
- **CR-MR Queue**：每对 CR-MR 线程使用专用 lock-free ring buffer，支持批量 push/pop。请求结构 16 字节（8B key + 8B type/size/buf）。
- **范围查询**：CR 层先拷贝缓存的热点项，再将请求转发至 MR 层，MR 层通过完整索引处理并跳过已存在的项。
- **线程重分配**：通过预定义的接收缓冲区 slot 作为同步点，无需阻塞请求处理即可完成线程在两层间的迁移。

## 五、实验结果

**实验平台**：服务端双路 28 核 Intel Xeon Gold 6330（42MB LLC），256GB 内存；两台客户端各双路 16 核 Xeon Silver 4314；Mellanox ConnectX-6 200Gbps RDMA NIC。

**对比系统**：BaseKV（RTC 版本）、eRPC-KV（share-nothing + eRPC）、RaceHash（被动式哈希 KVS）、Sherman（被动式 B+ 树 KVS）。

| 工作负载 | μTPS vs BaseKV | μTPS vs eRPC-KV |
|---------|---------------|-----------------|
| Read-intensive skewed (Tree, YCSB-B/C) | 1.29-1.30× | 显著优于 |
| Write-intensive skewed (Tree, YCSB-A) | 最高 1.45× | 部分场景 eRPC-KV 略高 (≤12%) |
| Scan (YCSB-E, Tree) | 1.33× | 1.59× |
| ETC (Tree, 90% get) | 1.27× | 1.67× |
| Twitter Cluster-12 (skewed, write) | 1.45× | 1.29× |
| Twitter Cluster-19 (skewed, read) | 1.40× | 1.36× |
| Uniform workload | 优势较小 (3-12%) | 部分场景持平 |

**延迟**：μTPS 的 P50 和 P99 延迟与 BaseKV 基本持平，inter-core 通信仅增加约 100ns，通过 batching 进一步摊销。

**Batching 效果**：μTPS-T 提升 51.6%，μTPS-H 提升 93.7%。

**Auto-tuner**：工作负载变化后 0.9 秒完成重配置，吞吐提升 20%，期间无停机。

## 六、批判性分析

1. **Speedup 范围跨度过大**：整体 speedup 1.03-5.46× 中，5.46× 仅出现在特定极端场景（大 value + skewed + tree index），而 uniform workload 下提升仅 3%。论文标题和摘要给出的 speedup 范围容易让读者产生过高期望。

2. **Uniform workload 下优势微弱**：当工作负载均匀分布时，CR 层的 hot set 机制无法发挥作用，μTPS 退化为纯粹增加了 inter-stage 通信开销的 TPS。作者虽承认了这一点，但以 "even minor reductions in latency can lead to significant cost savings at scale" 一笔带过，缺乏定量论证。

3. **Hash index 场景收益有限**：使用哈希索引时（μTPS-H），由于哈希查找本身 cache miss 较少，μTPS 的 cache 优化空间受限，多数场景提升仅 3-9%。这意味着对 Memcached 等主流哈希 KVS，μTPS 的实际价值有限。

4. **Write-intensive 场景的 cache coherence 问题**：论文承认 put 操作会导致 CR 层和 MR 层之间的 cache coherence traffic，在小 value 场景下甚至会让 μTPS 劣于 eRPC-KV。这是 TPS 架构跨核数据共享的固有问题，论文未给出有效解决方案。

5. **实验平台单一**：仅在一种 CPU（Xeon Gold 6330）上评测，42MB LLC 是一个较关键的硬件参数。在不同 LLC 大小、不同 cache 结构（如 AMD EPYC 的 non-inclusive cache）上的表现未知。

6. **Auto-tuner 的搜索开销**：虽然声称 0.9 秒完成重配置，但 trisecting 搜索需要实际运行并测量每种配置的性能，在搜索过程中系统可能运行在次优配置下。对于负载快速变化的场景，这个延迟是否可接受未充分讨论。

7. **与 eRPC 集成的缺失**：作者提到将 μTPS 与 eRPC 集成可以进一步提升性能，但未实现。考虑到 eRPC-KV 在部分场景优于 μTPS，这一组合的缺失是实验完整性的遗憾。

## 七、AI Infra / MLSys 视角

1. **KV Cache 管理的启发**：LLM 推理系统中的 KV cache 管理面临类似的 cache 层次问题。μTPS 将热点数据与冷数据分层管理的思路，可以借鉴到 PagedAttention 等 KV cache 系统中——将高频访问的 KV cache 块固定在 GPU L2/shared memory，冷块放在 HBM 或 host memory。

2. **Disaggregated inference 的线程模型**：在 prefill-decode disaggregation 场景中，prefill 和 decode 阶段的计算特性差异巨大（compute-bound vs memory-bound），μTPS 按资源特性分阶段的思路可以启发更细粒度的硬件资源分配策略。

3. **Auto-tuner 对 serving 系统的借鉴**：LLM serving 系统需要动态调整 batch size、并行度等参数以适应变化的请求模式。μTPS 的 trisecting auto-tuner 提供了一种轻量级在线搜索方案，可以替代目前常用的静态配置或基于模型的预测。

4. **可能的研究方向**：
   - 将 μTPS 的分层思想应用于 GPU 上的 KV cache serving：将 attention 计算的索引查找和数据搬运分离到不同的 CUDA stream/kernel
   - 在 CXL-based disaggregated memory 场景下，μTPS 的 cache-resident/memory-resident 分层可以自然映射为 local DRAM/CXL memory 的分层管理

---

## 八、总结

μTPS 提出了一种面向高速内存 KVS 的新型线程架构，核心思想是按 cache 驻留性将请求处理分为 cache-resident 和 memory-resident 两层，配合 reconfigurable RPC、resizable cache 和 auto-tuner 实现动态适配。在 skewed workload + tree index 场景下效果显著（最高 5.46× 加速），但在 uniform workload 或 hash index 场景下收益有限。该工作的主要价值在于重新审视了 TPS 架构在非抢占式环境下的可行性，并提供了一套完整的工程实现方案，但其适用性高度依赖于工作负载的倾斜程度和索引结构的复杂度。
