## 一、背景

内存键值存储（KVS）是现代数据中心的基础设施，支撑着分布式系统中快速、并发的数据共享访问。随着网络硬件的快速演进（200Gbps RDMA、单位微秒级延迟），以及 DPDK、RDMA 等用户态数据面技术的普及，KVS 进入了每秒数千万次操作的高吞吐时代。

在线程架构层面，现有系统大致分为两类：
- **抢占式（Preemptive）**：操作系统调度，多线程时间片复用，适合慢速设备（HDD、GbE）。RocksDB、HBase、Cassandra 等采用 Thread-Per-Stage（P-TPS）模式，模块化清晰，但对快速设备的延迟不敏感。
- **非抢占式（Non-Preemptive）**：线程绑定 CPU core，busy polling，消除上下文切换。MICA、FaRM 等高性能 KVS 采用 Run-to-Completion（NP-TPQ）模式——每个 worker 线程从头到尾处理完整请求。

NP-TPQ 虽然能充分利用高速硬件，但其 monolithic function 执行方式在极高吞吐量下（>10M ops/s）带来了 cache thrashing 和锁竞争问题，成为性能瓶颈。

---

## 二、要解决的问题

**核心问题：非抢占式 Run-to-Completion 架构的 cache 低效与争用放大**

1. **Cache 不友好**：KVS 请求处理包含多个异构子任务（网络 polling、index lookup、data copy、response），各阶段的内存访问模式差异巨大。例如，网络 buffer polling 只需访问小范围缓冲区（NIC 通过 DDIO 直接写入 LLC），而 index traversal 和 data copy 需访问大范围内存空间，极易驱逐前者缓存的数据，导致 cache thrashing。实测显示，NP-TPQ 下 LLC miss rate 高达 33%，而 TPS 的 network 阶段可降至 2%。

2. **争用放大**：在 skewed workload 下，share-nothing（SN）设计出现负载不均，share-everything（SE）设计因竞争同一热点 key 的锁而随线程数增加性能急剧下降。两者均无法兼顾负载均衡与低争用。

3. **NP-TPS 从未被认真实现**：非抢占式 Thread-Per-Stage（NP-TPS）理论上能同时解决上述两个问题，但工业界和学术界普遍认为它无法充分利用高速硬件（因跨线程通信开销），故从未被系统性实现和验证。

---

## 三、核心设计

μTPS 的关键洞察：**KVS 请求处理阶段不应按功能边界拆分（传统 TPS 的思路），而应按 cache 驻留性拆分**——将 cache-resident 的无争用阶段与 memory-resident 的高争用阶段分离到不同线程池，并为每层分配独立的硬件资源（CPU core、LLC way）。

### 双层线程架构

**Cache-Resident（CR）层**：
- 管理网络 buffer polling/parsing、热点 KV item 的命中处理
- 分配独立 worker 线程并绑定 CPU core
- 使用 Intel CAT 分配专用 LLC way，确保热点数据不被驱逐
- 热点集（hot set）以有序数组（树型索引）或直接复用 hash 表管理

**Memory-Resident（MR）层**：
- 管理完整 index 结构和数据项的 lookup + data copy
- 广泛使用 batching、coroutine prefetching 摊薄 cache miss 代价
- 采用 share-everything 设计 + 细粒度锁（8B 原子操作，大于 8B 用 CAS + version）

### 请求流程
1. CR 层 worker 从网络 recv buffer 拉取请求并解析
2. 若命中热点 → 直接在 CR 层处理并返回响应
3. 若未命中 → 通过 CR-MR Queue 转发至 MR 层
4. MR 层完成 index traversal + data copy 后，通知 CR 层发送响应

μTPS 与传统 TPS 的三大区别：
- 任务分配依据 cache 驻留性而非功能模块；
- 利用现代 NIC（200Gbps）的高速能力，设计专用 RPC 和 queue；
- 线程调度由存储软件自身管理（非 OS scheduler），支持快速重配置。

## 四、实现细节

### Reconfigurable RPC
核心思路是在服务端维护**单一共享 recv buffer**（通过 RDMA SRQ 实现），所有客户端请求 DMA 进同一队列。Worker i 只处理 `slot mod n == i` 的请求，调整线程数时只需修改全局变量 `n`，无需通知客户端。响应 buffer 则每 worker 独立持有（64KB，可复用）。相比 FaRM-RPC 的每客户端每线程独立 buffer，内存占用大幅降低。

### Resizable Cache
采用 hot-set 方法而非 LRU：后台线程用 count-min sketch + min heap 采样并跟踪热点（实现中保留 10K 项），用 epoch-based 方法原子切换 hot set。cache 大小可动态调整（heuristic 试探），防止过大 hot set 因 CR 层 miss 惩罚过高反而拖累性能。

### CR-MR Queue
All-to-all 映射：每对 (CR worker, MR worker) 之间一个独立的 lock-free ring buffer。CR 侧按 round-robin 分发到 MR worker；MR 侧扫描所有 CR 侧队列。每个请求紧凑编码为 **16 字节**（key 8B、type+size 4B、buf 4B），用 tail pointer 推进代替显式完成通知。批处理减少 push/pop 频率。

### Auto-tuner
监控吞吐量，触发自动配置（线程分配、cache 大小、LLC way 分配）。线程分配与 cache 大小联动（因为 cache 大小影响 CR/MR 层负载比），用 linear probe 搜索 cache size，用 **trisecting（三等分）** 方式快速收敛线程分配（利用性能曲线单峰凸性）。LLC way 分配独立调优。整个重配置过程约 0.9 秒，不阻塞请求处理。

### 实现规模
实现了两套 KVS：μTPS-H（libcuckoo 哈希索引，支持点查）、μTPS-T（MassTree 树型索引，支持点查+范围查询）。核心代码基于 C++20 stackless coroutine（`co_wait`/`co_yield`/`co_return`）实现批量 prefetch-coroutine 调度。

## 五、实验结果

**实验平台**：服务端 2× 28-core Intel Xeon Gold 6330（42MB LLC/CPU）、256GB RAM、Mellanox ConnectX-6 200Gbps NIC；2个客户端节点通过 200Gbps RDMA 交换机互联；Ubuntu 20.04，28核单 NUMA 节点。

**基线系统**：BaseKV（同μTPS但RTC架构）、eRPC-KV（eRPC + share-nothing）、RaceHash（被动 RDMA KVS，hash）、Sherman（被动 RDMA KVS，B+树）

| 场景 | μTPS vs BaseKV |
|------|---------------|
| 读密集 skewed，树型索引（YCSB-B/C） | +1.30×（平均） |
| 写密集 skewed，树型索引 | 显著优势（BaseKV hash 因锁竞争崩溃） |
| Scan（YCSB-E） | μTPS-T +33.1%（vs BaseKV），+58.9%（vs eRPC-KV） |
| Twitter Cluster-12（skewed+写密集） | μTPS-T +44.5% vs BaseKV |
| Twitter Cluster-19（skewed+读密集） | μTPS-T +39.8% vs BaseKV |
| 均匀 workload | 优势有限（3%~12%） |
| 总体 speedup 范围 | **1.03× ~ 5.46×**（vs RTC 对照） |

**延迟**：inter-core 通信本身约 100ns，经 batching 摊薄后 P50/P99 延迟与 BaseKV 接近（hash 索引略高，树型索引持平）。

**Batching**：batch size 从 1→20，μTPS-T 提升 51.6%，μTPS-H 提升 93.7%（hash 索引对跨层通信更敏感）。

**Auto-tuner**：workload 变化后约 0.9 秒完成重配置，吞吐提升约 20%。

## 六、批判性分析

**1. "1.03~5.46×"范围跨度过大，最低端几乎没有意义**
论文的 speedup 下界 1.03× 出现在均匀 workload 下，而这正是现实中应用频率最高的场景之一（如缓存服务）。论文承认均匀 workload 下 CR 层热点识别失效，但却将此纳入"1.03×也有价值"的论点中——这是典型的 best-case 数字背书。生产环境中很少有纯 Zipfian 负载，真实 workload 的 skewness 介于两者之间，而论文没有给出 skewness 梯度下的系统性数据。

**2. CR 层 miss 惩罚被低估**
论文在 §5.2 承认：写密集均匀 workload 下，MR 层从 recv buffer 读取数据引发缓存一致性流量，影响 CR 层效率，导致 μTPS 在某些场景（8B/64B 小 item）甚至劣于 eRPC-KV。这一问题的根源在于 CR/MR 层共享 recv buffer 的设计决策，论文提出的解法仅是"集成 eRPC 可改善"——但这是未实现的 future work，属于绕开而非解决问题。

**3. Auto-tuner 的搜索代价被掩盖**
论文声称重配置完成于 0.9 秒，但实验中 workload 变化后先经历约 0.3 秒的性能下降再触发 auto-tuner，而现实中负载变化频率可能远快于 0.9 秒收敛时间。论文引用的文献声称"实际负载变化不频繁"，但这并不适用于所有生产场景（如 flash crowd、流量突增）。

**4. 基线比较缺乏最优化的 TPS 对照**
与 μTPS 对比的 BaseKV 是作者自己实现的 RTC 版本，而非调优后的工业级系统（如最新版 MICA 或 NetKV）。被动式 RDMA KVS（RaceHash、Sherman）的存在是为了说明 CPU-bypass 代价，但这与 μTPS 的设计目标（CPU-involved, high throughput）并不是直接竞争对手，混入对比有凑数之嫌。

**5. 内存开销分析不足**
论文只定性描述 Reconfigurable RPC 减少了 buffer 内存占用，却没有给出与 eRPC、FaRM-RPC 的实际内存使用对比数据，也没有讨论 all-to-all CR-MR queue 随线程数平方增长的内存代价（28 CR × 28 MR = 784 个 ring buffer）。

**6. Intel CAT 的局限性未充分讨论**
Intel CAT 按 cache way 粒度分配（Xeon Gold 6330 有 16 way，每 way ~2.6MB），粒度较粗。论文仅展示"分配给 MR 层的 way 比例"，但未讨论当热点数据超过分配的 LLC way 容量时 CR 层的性能退化，也未评估 CAT 本身引入的额外管理开销。

## 七、AI Infra / MLSys 视角

μTPS 的核心思想——**按数据访问局部性而非功能边界划分线程阶段**——对 AI Infra 领域有较强的迁移价值。

**直接关联：KV Cache 服务的线程架构**
LLM 推理服务中，KV cache 管理本质上是一个高并发键值访问问题，且存在与 KVS 极为相似的异构访问模式：attention 计算访问局部 KV 块（cache-friendly），而 prefix reuse/page table 查找则访问全局内存结构（cache-unfriendly）。μTPS 的 CR/MR 双层架构思路可直接类比到推理 serving 系统中的 memory tier 分层管理（如 vLLM 的 GPU/CPU/SSD 三级 cache）。

**可迁移的设计 insight**：
- **Batched coroutine prefetch**：μTPS 在 MR 层用 C++20 coroutine 实现 batched pointer chasing，这与 FlashAttention 的 tiling + async memory 思路同源，可用于优化 CPU 侧的 embedding lookup 或 sparse feature fetch。
- **Hot-set 识别 + 专用 cache way**：对于 LLM prefix cache 的热点管理，count-min sketch + CAT 的组合可以提供比 LRU 更轻量、更 cache-friendly 的热点追踪方案。
- **Reconfigurable RPC 的单队列设计**：在分布式推理（如 disaggregated prefill/decode）中，单侧 recv queue + round-robin 分发可简化 worker 扩缩容时的协调代价，值得借鉴。

**值得跟进的研究方向**：
- 将 μTPS 的 CR/MR 分层思想应用于 GPU-CPU 混合 KV cache serving，探索在 GPU HBM 中维护 CR 层（热点 token cache）、CPU DRAM 维护 MR 层（冷数据）的可行性。
- 结合 CXL-attached memory 的新形态（论文背景中提到），设计三层 thread 架构（LLC-resident / DRAM-resident / CXL-resident），适配未来 AI 推理系统的内存分层。

---

## 八、总结

μTPS 通过重新审视非抢占式 Thread-Per-Stage 架构，在 in-memory KVS 中成功将 cache-resident 和 memory-resident 阶段解耦，配合 Reconfigurable RPC、Resizable Cache 和 Auto-tuner，实现了在 skewed 和读密集 workload 下 1.03×–5.46× 的吞吐提升。其核心贡献在于证明了 NP-TPS 在高速网络时代的可行性，并提供了一套完整的工程实现。主要局限在于对均匀 workload 帮助有限、写密集小 item 场景存在 cache coherence 代价、以及 auto-tuner 在快速变化负载下的适应性不足。
