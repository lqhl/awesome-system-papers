# Device-Assisted Live Migration of RDMA Devices

**作者**：Artem Y. Polyakov, Gal Shalom, Aviad Yehezkel, Omri Ben David, Asaf Schwartz, Omri Kahalon, Ariel Shahar, Liran Liss（均来自 NVIDIA Corporation）

**链接**：https://doi.org/10.1145/3731569.3764795

## 一、背景

云计算依赖虚拟化技术实现资源的灵活调度，而 Live Migration（LM）是云平台日常运维的核心能力——大型云厂商每月执行数百万次迁移，用于维护、容错、负载均衡和资源整合。近年来，HPC 和 AI 工作负载大规模进入云环境，这类工作负载需要 RDMA 设备提供高性能低延迟通信，并通过 PCIe passthrough（SR-IOV）直接访问硬件以获得裸金属性能。

然而，PCIe passthrough 破坏了虚拟化的核心假设——guest OS 与底层硬件的解耦。设备状态对 hypervisor 不可见，RDMA 设备还持有复杂的命名空间（QP number、memory key）、传输层状态和跨设备 P2P 通信关系，使得 Live Migration 极其困难。现有主流虚拟化平台（VMware ESX、Linux KVM/QEMU）在启用 passthrough 时直接禁用 LM 功能。

---

## 二、要解决的问题

1. **RDMA 命名空间迁移**：RDMA 对象标识符（QP number、memory key）由设备分配，软件无法在目标设备上精确复现，导致现有方案必须在 guest OS 或中间件中做运行时标识符翻译，引入 3-9% 的运行时开销并需要修改租户软件栈。
2. **连接状态同步**：现有方案需要 drain 所有 in-flight WQE 或全局协调所有远程 peer，引入不可控延迟（取决于网络拥塞和消息大小），且单条被中止的 WQE 可能对应 GB 级数据传输。
3. **跨设备一致性**：AI 训练场景中 RDMA NIC 与 GPU 通过 PCIe P2P（GPUDirect）直接通信，迁移时必须保证多个 passthrough 设备间的状态一致性——这个问题此前从未被解决。
4. **对租户透明**：云厂商通常无法修改租户软件栈，任何需要修改 guest OS 或 RDMA 中间件的方案都无法在生产环境部署。
5. **firmware 滚动升级兼容**：集群维护需要在不同固件版本的设备间迁移，现有方案缺乏兼容性机制。

## 三、洞察与设计

**关键洞察**：RDMA 设备的内部状态虽然复杂，但可以在设备层面作为黑盒整体提取和恢复——不需要逐个 RDMA 对象序列化，也不需要理解状态语义。设备自身知道哪些状态是可重建的、哪些是过时的（如拥塞控制状态在迁移后不再相关），因此设备辅助可以做到精确的状态蒸馏（distillation），生成最小化的可重定位快照。

基于此洞察，论文提出 12 项 Device Assist（DA）原则并设计了完整的迁移方案：

**网络透明性**（DA1-DA3）：设备精确保留 RDMA 命名空间（QP number、memory key）和本地/远程连接状态，消除与远程 peer 的任何协调需求。利用指数退避超时机制在迁移 downtime 期间保持远程连接存活。

**数据包级别静默**（DA4）：不 drain 整个通信队列，而是在数据包粒度挂起处理——重传大小固定且可忽略，避免了浪费 GB 级已完成的传输。

**状态蒸馏**（DA5）：不精确捕获全部微架构状态，而是识别出可重建状态（如活跃 QP 列表可从 producer/consumer index 恢复）和过时状态（如传输超时定时器、拥塞控制状态、QoS 调度 credit），将其排除出镜像。

**黑盒状态提取**（DA6）：将 VF 状态作为不透明二进制块批量提取，避免逐对象遍历的开销和复杂性。

**两阶段挂起/恢复**（DA12）：解决多设备 PCIe P2P 一致性问题。suspend-active 阶段停止发起新 DMA 事务但继续响应 incoming 请求；suspend-passive 阶段封存状态。利用 PCIe 写顺序保证，通过 LCA 路径分析证明所有 in-flight P2P 事务在 passive 阶段前必定到达目标设备。

**流水线与 pre-copy**（DA8, DA10）：设备镜像支持分块流水线传输（save/transfer/load 并行），将 downtime 从三阶段之和降低到最慢阶段的耗时。pre-copy 阶段预传输 ICM 布局并预分配内存页。

## 四、实现细节

基于 NVIDIA ConnectX-7 200Gbps 网络适配器实现，支持 InfiniBand 和 Ethernet/RoCE。

**设备固件**：约 6K LOC 固件代码实现迁移 API。VF 状态主要存储在 Interconnect Context Memory（ICM）中，ICM 按 VF 隔离分区。suspend-active 时依次断开 embedded switch 连接、停止发送队列、flush in-flight 数据包（含 DMA 写和 CQE 生成）、完成 control-path 命令、禁用 DMA mastering。suspend-passive 时 flush 设备缓存、蒸馏运行时状态（排除可重建的 run list、过时的拥塞控制/QoS 状态/传输定时器）。

**镜像格式**：ICM 内容剥离位置相关引用（VF 内部标识符、物理端口索引），生成可重定位镜像。通过 ImageBlock-Save/Load 迭代器接口分块传输。

**兼容性**：migration tag 包含 ICM 布局版本、feature set 版本和资源容量版本。采用宽松策略——ICM 布局版本需严格匹配，feature/capacity 版本目标端 >= 源端即可，支持滚动升级。

**VFIO 驱动扩展**：约 3K LOC 扩展 Linux VFIO 驱动，引入模块化的 vendor-agnostic 迁移基础设施（mlx5-vfio-pci 插件），已合入 Linux 6.7。

**QEMU 扩展**：约 1K LOC，集成 VFIO 迁移能力，支持 device pre-copy 和流水线镜像传输优化，已合入 QEMU 8.1。

**脏页限速**：利用 ConnectX 流量整形功能限制 incoming RDMA 流量速率，控制设备对 host 内存的脏页速率以确保 pre-copy 收敛。

## 五、实验结果

**实验平台**：3 节点集群，每节点 96 核 AMD EPYC 9654、128GB 内存、NVIDIA L40S GPU、ConnectX-7 200Gbps NIC。RoCEv2 协议，QEMU/KVM 虚拟化，OOB 通道 16Gbps。每 VM 分配 10 核 + 8GB 内存。

| 实验项 | 关键结果 |
|--------|---------|
| 批量状态创建 vs Verbs（100K 对象） | QP: ImageLoad 2.5s vs Create+Connect 15s（6x 加速）；MR: ImageLoad 0.1s vs Create 37.75s（>370x 加速） |
| 迁移 downtime（100K QP/CQ） | 基线 ~1s；pre-copy 优化后 ~250ms（75% 降低） |
| 迁移 downtime（100 QP/CQ） | 基线 ~60ms；pre-copy 优化后 ~45ms（25% 降低） |
| 运行时性能影响 | RTT ≈4μs 与裸金属一致，迁移前后无性能退化 |
| 迁移期间观测到的 downtime | RTT 探测 310ms（匹配 QEMU 报告的 308ms），网络重配置额外 81ms |
| RDMA 脏页限速 | 18Gbps 不收敛；15Gbps 收敛但耗时 99.7s；1Gbps 收敛耗时 31s |
| NAS Parallel Benchmarks（MPI） | RDMA passthrough 相比 para-virtual TCP 增加约 150ms downtime，完整性验证全部通过 |
| NCCL Allreduce（GPU + RDMA） | 1GB 向量 500 次迭代，迁移后带宽完全恢复，一致性检查通过 |

## 六、批判性分析

1. **OOB 通道瓶颈被低估**：论文承认 16Gbps OOB 通道与 200Gbps NIC 吞吐的不匹配，但实验中 100K QP 的镜像传输仍是 downtime 的主要瓶颈（395MB 镜像）。pre-copy 优化主要减少了 ICM 分配开销而非传输开销，流水线仅带来额外 3% 改善。随着 400G/800G NIC 部署和更大规模 RDMA 资源使用，这个问题会更加严重，论文的 pre-copy 优化效果可能不足。

2. **脏页限速的实用性存疑**：将 RDMA 带宽从 18Gbps 限制到 1Gbps 才能实现快速收敛——对于 AI 训练等带宽敏感工作负载，这意味着 pre-copy 期间性能严重退化。论文没有评估限速对应用层性能的影响，也未讨论何时启动限速、限速多久这些运维策略。

3. **实验规模偏小**：仅使用 3 节点、2 VM 的配置，远不及生产环境中数千节点的规模。论文声称方案无需全局协调因此可扩展，但未验证大规模并发迁移场景下指数退避超时的行为——当集群中多个节点同时迁移时，累积的 timeout 可能导致应用层可见的延迟波动。

4. **GPU 迁移细节缺失**：NCCL 实验声称同时迁移 RDMA NIC 和 GPU（vGPU），但论文完全没有描述 GPU 状态迁移的实现和开销，仅笼统地说"利用相同的 passthrough 迁移基础设施"。GPU 状态（显存、计算上下文）的迁移复杂度远高于 NIC，这里的省略让人无法判断端到端方案的完整性。

5. **连接保持机制脆弱**：指数退避超时是一种 best-effort 机制——如果 downtime 超过最大退避窗口（论文未说明具体值），连接仍会断开。论文在 Discussion 中提出的 NACK 方案更优雅，但尚未实现，当前方案在长 downtime 场景下的鲁棒性未经验证。

6. **与现有方案缺乏直接对比**：论文指出 MigrOS 和 MigrRDMA 代码未公开因此无法直接比较，但可以在相同硬件上实现基线方案（如基于 Verbs 的逐对象迁移）进行定量对比，而不是仅靠 Table 2 的 bulk vs individual creation 微基准间接说明优势。

## 七、AI Infra / MLSys 视角

1. **AI 训练集群的迁移能力是刚需**：大规模 AI 训练作业运行数天到数周，期间需要节点维护、滚动升级、故障恢复和负载均衡。本文首次实现了 RDMA+GPU passthrough VM 的透明 LM，直接解决了"accelerated cloud"的核心运维瓶颈。

2. **GPUDirect/PCIe P2P 一致性方案可迁移**：两阶段 suspend/resume 和 PCIe 拓扑 LCA 分析的形式化方法具有通用性。随着 NVLink、CXL 等新型互连的普及，类似的多设备一致性问题会在更多场景出现（如 NVSwitch 连接的多 GPU 拓扑）。论文也明确指出该技术适用于 NVLink。

3. **对 checkpoint/restart 的启发**：设备辅助的黑盒状态蒸馏思路可以借鉴到 AI 训练的 checkpoint 场景——当前 checkpoint 通常只保存模型参数和优化器状态，但通信库（NCCL）的内部状态（连接、buffer 注册）在恢复时需要从头重建，如果能用类似的设备辅助方式快速恢复 RDMA 通信状态，可以显著降低 checkpoint 恢复延迟。

4. **值得跟进的方向**：
   - **设备状态 pre-copy 扩展到 ICM 脏页追踪**：论文在 Discussion 中提出但未实现，将 downtime 从正比于总资源量降低到正比于活跃工作集大小，对大规模 AI 训练 VM（可能有数十万 QP）至关重要。
   - **GPU 状态的设备辅助迁移**：论文仅用 vGPU 做了初步验证，真正的 GPU passthrough 迁移（含显存、CUDA context、NVLink 状态）是更大的挑战，也是更大的机会。
   - **RDMA-based OOB 通道**：用 RDMA 本身传输迁移镜像，可以将 OOB 带宽从 16Gbps 提升到 200Gbps+，从根本上解决镜像传输瓶颈。

---

## 八、总结

本文提出了首个设备辅助的 RDMA 设备透明 Live Migration 方案，通过 12 项设备辅助原则实现了命名空间保留、数据包级静默、黑盒状态蒸馏和两阶段多设备一致性。基于 NVIDIA ConnectX-7 的实现已合入 Linux 6.7 和 QEMU 8.1 并在生产环境可用（GA）。实验表明即使在 100K QP 高资源利用率下仍可实现亚秒级 downtime，迁移前后无运行时性能开销。主要局限在于 OOB 通道带宽瓶颈、脏页限速对应用性能的影响，以及缺乏大规模并发迁移验证。该方案对 AI 训练集群运维具有重要实践价值，其设计思路对 GPU 迁移和新型互连一致性问题具有参考意义。
