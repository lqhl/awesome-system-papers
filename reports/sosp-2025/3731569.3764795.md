# Device-Assisted Live Migration of RDMA Devices

## 论文基本信息

- **标题**: Device-Assisted Live Migration of RDMA Devices
- **作者**: Artem Y. Polyakov, Gal Shalom, Aviad Yehezkel, Omri Ben David, Asaf Schwartz, Omri Kahalon, Ariel Shahar, and Liran Liss
- **会议**: SOSP 2025
- **Session**: Data Centers
- **PDF**: 3731569.3764795.pdf

## 研究背景

虚拟化是云计算的关键支撑技术，实现了物理资源与用户工作负载之间的解耦。其核心优势之一是透明迁移（Live Migration, LM）——在 VM 执行过程中将其从一个物理服务器迁移到另一个。这项技术被云服务商广泛用于维护、容错、负载均衡和资源整合。

随着 HPC（高性能计算）和 AI 工作负载向云端迁移，RDMA（Remote Direct Memory Access）设备因其低延迟、高带宽的通信能力而变得不可或缺。然而，要保证裸金属级性能，这些工作负载通常需要通过 PCIe SR-IOV（Single Root I/O Virtualization）将 RDMA 设备直通（Passthrough）给 VM，这打破了 guest OS 与底层硬件之间的解耦，导致传统 LM 方案无法工作。现代 hypervisor（如 VMware ESX 和 Linux KVM/QEMU）在启用设备直通后默认禁用 LM。

RDMA 迁移面临三大独特挑战：
1. **RDMA 命名空间问题**：RDMA 标识符由设备分配，软件无法在目标系统上精确重建（QP 编号、远程密钥等是设备内部的）
2. **传输状态封装**：RDMA 连接的状态封装在设备内部，in-flight 消息的处理需要与所有远程对端协调
3. **多设备一致性问题**：当 VM 拥有多个直通设备（如 RDMA NIC + GPU）时，设备间的 PCIe P2P 通信增加了状态一致性保证的复杂性

## 要解决的问题

如何在不对 guest 软件或 RDMA 协议栈进行修改的前提下，实现 RDMA 设备对 VM 的透明迁移，同时将迁移 downtime 控制在可接受范围内，并维持所有现有连接的完整性？

## 核心贡献

- **设备辅助迁移原则**：提出 12 条设备辅助迁移原则（DA1-DA12），涵盖命名空间保留、本地连接保留、远程连接保留、包级静默处理、黑盒状态提取等关键设计维度。
- **通用设备迁移 API**：定义了设备迁移的查询、设备控制和镜像访问三类 API 接口，可被 hypervisor 标准化使用。
- **NVIDIA ConnectX-7 实现**：基于 NVIDIA ConnectX-7 网卡实现了完整的设备辅助 LM，支持 InfiniBand 和 RoCEv2 协议。
- **PCIe P2P 一致性协议**：提出两阶段 Suspend/Resume 机制处理跨设备的 PCIe P2P 通信一致性问题。
- **子秒级 Downtime**：对于高 RDMA 资源利用率的工作负载，实现 sub-second downtime，且迁移后性能无下降。

## 主要研究方法

论文首先系统分析了现有 RDMA 迁移方案的局限性：
- 软件方案（如 MigrRDMA、DMTCP）依赖 RDMA API 的非标准扩展或 guest 修改
- 运行时标识符翻译引入显著开销（3-9%）
- IB Verbs API 的对象级序列化效率低下
- 连接排空（draining）导致不必要的同步延迟

基于此，论文论证了设备辅助是实现透明、高效 RDMA 迁移的根本途径，并提出了 12 条设计原则作为系统化指导。

## 设计与实现

**设备辅助迁移原则**（§3）：

- **DA1: RDMA 命名空间保留**：精确重建目标设备上的 RDMA 命名空间（QP 编号、远程密钥等），消除对标识符翻译和远程协调的需求。
- **DA2: 本地连接保留**：保留 QP 的本地端点标识，无需在迁移时重新建立连接。
- **DA3: 远程连接保留**：通过指数退避超时保持与远程对端的连接，避免主动通知。
- **DA4: 包级静默处理**：通过访问设备内部状态（当前期望包序号、传输操作码、虚拟 RDMA 地址）实现包级粒度的静默，而非连接级排空。
- **DA5: 放松一致性组件**：迁移后不必要的微架构状态（过时的传输超时、已失效的拥塞控制状态）无需传输。
- **DA6: 黑盒状态提取**：VF 状态被视为黑盒，避免对象级遍历，改用批量镜像转储。
- **DA7: 镜像兼容性跟踪**：通过设备迁移"标签"（vendor-specific 位序列）跟踪固件版本兼容性，支持滚动升级。
- **DA8-DA9: Pre-copy 支持**：设备内部跟踪脏页面（ICM dirty pages）和设备脏页率节流。
- **DA10: 镜像块接口**：分块迭代式镜像访问，避免大内存分配延迟。
- **DA11: Post-copy 支持**：设备可在 post-copy 阶段持续处理页面错误。
- **DA12: 两阶段 Suspend/Resume**：将挂起/恢复操作分解为 Active 和 Passive 两阶段，确保 PCIe P2P 一致性。

**多设备 Suspend/Resume 协议**（§4）：

当 VM 拥有多个直通设备时，设备间可能存在 PCIe P2P 通信。传统的立即挂起方案无法保证一致性，因为挂起的 VF 可能仍在接收来自活跃 PCIe 对端的请求。两阶段协议的关键创新是：
- Suspend-Active：通知设备停止发起新的 DMA 事务，完成 in-flight 非 Posted 事务
- Suspend-Passive：密封设备状态，准备保存镜像

通过 Posted 事务的传递性质（Posted 请求不能被绕过），Active 阶段完成后，所有 in-flight Posted 事务已传递到目标，Passive 阶段可以安全保存一致镜像。

**ConnectX-7 实现**（§6）：

ConnectX-7 包含 PCI 接口、嵌入式交换机（Embedded Switch）和 VF 状态（RDMA NIC 逻辑 + 接口）。VF 状态中的 ICM（Internal Context Memory）是迁移的核心对象，其包含 RDMA 命名空间、对象关系和传输进度信息。

实现通过固件升级（FW 28.41.1000）添加迁移支持，约 6K 行固件代码。镜像加载优化方面，ICM 分配是 downtime 的主要来源，预分配和流水线化可将 100K QP/CQ 场景的 downtime 减少 75%。

**VFIO 扩展**（§6.3）：扩展 Linux VFIO 驱动，通过 mlx5-vfio-pci 插件桥接通用基础设施与 ConnectX-7 PF 驱动。

## 主要实验结果

**Bulk 状态重建**（§7.2.1）：加载镜像 bulk 创建在 100K QP 场景下比对象级创建快 ~37 倍（2.5 秒 vs. 约 93 秒），验证了黑盒状态提取和批量镜像操作的优势。

**Downtime 分解**（§7.2.2）：
- 基础方案：100K QP/CQ 时 downtime 约 308ms，镜像加载主导
- Pre-copy 优化后：100K QP 场景减少 75%，降至约 77ms
- 小规模（4 QP）场景：downtime 约 2ms
- 无 VF 场景（纯 VM 迁移）：约 1ms

**Peer 观察性能**（§7.2.3）：使用 ib_write_lat/bandwidth/message_rate 测试评估迁移对通信 peer 的影响：
- Bare-metal 性能在迁移前后保持一致
- 仅在 downtime 时刻观察到 RTT 尖峰（约 310ms），之后迅速恢复
- 网络重配置（gARP）在实验中引入了约 81ms 的额外延迟（实验中 TCPdump 观察到目标 VM 在 81ms 内即开始接收数据包）

**RDMA 节流**（§7.2.4）：设备 Dirty Rate 节流对于高吞吐量工作负载的收敛至关重要：
- 当 RDMA 吞吐量超过 OOB 通道带宽（18 Gbit/s）时，pre-copy 无法收敛
- 严格的节流级别（1 Gbit/s）虽然收敛最慢，但最终完成迁移

**并行应用迁移**（§7.3）：使用 NPB（NAS Parallel Benchmarks）测试 MPI 通信性能：
- BT、EP、CG、MG、SP 基准测试中，RDMA 迁移增加约 150ms downtime
- 所有基准测试的 NPB 完整性验证均通过，迁移后 MPI 执行时间增加轻微
- NCCL Allreduce 基准测试验证了多设备迁移场景，迁移后带宽完全恢复

## 潜在问题 / 局限性

1. **NVIDIA ConnectX-7 特定实现**：整个设计和实现完全针对 NVIDIA ConnectX 网卡，缺乏对其他厂商 RDMA 硬件的评估。虽然论文声称 API 是通用的，但缺乏在非 NVIDIA 硬件上的验证。

2. **滚动升级中的迁移标签匹配**：loose policy 允许目标 VF feature/capacity 版本高于或等于源端，但"higher version = additional features" 的假设可能在某些边界情况下失败，特别是 feature 新增影响资源容量分配的场景。

3. **网络重配置延迟**：实验中观察到的 ~80ms 网络重配置延迟在生产环境中可能更复杂。生产网络依赖 gARP、SDN 控制器或 IB LID reprogramming，论文未评估大规模网络的真实重配置时间。

4. **RDMA Throttling 与性能的双刃剑**：严格的节流（1 Gbit/s）虽然使迁移收敛，但会直接影响应用性能。对于延迟敏感型 HPC 工作负载，这种节流可能难以接受。

5. **800Gbit/s NIC 的 OOB 瓶颈**：论文明确指出，随着 800Gbit/s NIC 进入市场，OOB 通道带宽差距将成为更大问题。虽然提到了用 RDMA 作为 OOB 的方案，但缺乏具体设计和评估。

6. **加密连接的 NACK 方案**：论文讨论了加密连接场景下 NACK 方案的不适用性，但未提供该场景的完整解决方案。

7. **缺乏与迁移时间线各部分开销的系统性消融分析**：论文报告了各部分的数字，但未像系统消融论文（如 Mage）那样清晰地展示每个优化设计决策的独立贡献。

8. **实验设置规模**：所有实验在 3 台服务器节点的小规模设置下进行，未涉及更大规模的 HPC/AI 集群迁移场景。

## 未来工作

- 探索 Downtime 优化：将未来设备迁移 downtime 与当前活动工作集大小成正比（而非镜像大小）
- Negative Acknowledgement (NACK) 机制：引入特殊 NACK 通知远程对端迁移正在进行，而非简单超时等待
- 加速 OOB 通道：使用 RDMA 本身作为 OOB 通道以匹配高速 NIC

## 个人评注

Device-Assisted Live Migration of RDMA Devices 是 SOSP 2025 中最具工业实践意义的工作之一——由 NVIDIA 团队撰写，基于 ConnectX-7 固件实现，并在真实的 HPC 和 AI 基准测试上评估。这篇论文的核心贡献在于：它首次系统地解决了 RDMA 设备迁移问题，而这一问题在 HPC/AI 云计算趋势下正变得越来越重要。

论文的 12 条设备辅助迁移原则具有较好的可扩展性，API 的设计也较为合理。特别是黑盒状态提取（DA6）和镜像兼容性跟踪（DA7）的设计，反映了对生产环境中固件升级场景的深入理解。两阶段 Suspend/Resume 协议对于多设备一致性问题的处理也展示了扎实的技术深度。

不过，作为一个高度针对特定硬件（ConnectX-7）的实现，其"通用 API"在实际中能被其他厂商采用的程度存疑。在 GPUDirect 和多设备 P2P 通信日益重要的背景下，仅评估 RDMA NIC + GPU 组合（而非纯 GPU 或其他加速器）可能也限制了结果的普遍性。此外，论文的表述和结构更接近工程实践报告而非学术论文，在理论分析和系统性消融方面相对薄弱。

总体而言，这是 RDMA 设备迁移领域的一个重要的实践里程碑，为后续研究提供了有价值的设计原则和 API 框架。
