# Quilt: Resource-aware Merging of Serverless Workflows

**作者**：Yuxuan Zhang, Sebastian Angel（University of Pennsylvania）
**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles）
**链接**：https://doi.org/10.1145/3731569.3764830
**源文件**：[3731569.3764830.pdf](../../papers/sosp-2025/3731569.3764830.pdf)

---

## 一、背景

Serverless 计算允许开发者将应用拆分为多个小函数（workflow），由平台负责调度、扩缩容和资源管理。这种模式继承了微服务架构的灵活性：每个函数可以用不同语言编写、独立测试、独立部署，平台也能更细粒度地调度资源。

然而，serverless workflow 中函数间的调用本质上是 HTTP 请求：需要经过 API gateway、controller 路由、TCP 握手、序列化/反序列化，甚至可能触发 cold start。对于执行时间仅为几十毫秒的短函数，调用开销可能占据总延迟的大部分。AWS Lambda 上一个 warm no-op 函数的中位调用延迟就有 10.4ms，而 20% 的 Lambda 函数执行时间不到 100ms。

---

## 二、要解决的问题

1. **调用开销过高**：Serverless workflow 中每次函数间调用都需要经过网络（HTTP 请求→API gateway→controller→worker），引入序列化、网络延迟、排队延迟等开销，对短函数尤为严重。

2. **Cold start 链式放大**：一个 workflow 中如果多个函数同时需要 cold start，延迟会叠加放大。

3. **现有合并方案的局限**：
   - 现有工作（WiseFuse、Faastlane、Fusionize）只支持单一解释型语言（如 Python/JavaScript），无法处理编译型语言（Rust、C++、Go）
   - 现有方案要么忽略资源约束导致合并后函数过大、难以调度，要么需要开发者手动指定合并策略
   - Nightcore 等 co-location 方案需要替换现有平台，无法透明兼容

4. **资源碎片化**：如果简单地将所有函数合并为一个大进程，它需要的 CPU/内存过多，导致 worker 上的剩余资源无法被利用，造成严重的资源碎片化。

---

## 三、洞察与设计

**关键洞察**：Serverless 函数之间的交互完全通过 REST API 进行，数据类型只有 JSON 编码的字符串——这意味着在 LLVM IR 层面合并不同语言的函数时，只需要处理字符串类型的转换，而不需要解决完整的跨语言内存模型兼容问题。同时，同一 tenant 的同一 workflow 内的函数本就共享信任域（类似于同一应用内的库函数），function-level isolation 是不必要的。

基于这两个洞察，Quilt 的设计包含三个核心模块：

### 1. 透明 Profiling
- 在 API gateway 前部署 nginx ingress controller + OpenTelemetry 进行分布式追踪，收集 caller-callee 关系和调用频率
- 使用 cAdvisor + InfluxDB 收集每个函数的 CPU 和内存使用
- 通过 Kubernetes token 实现 profiling 的动态开关，避免持续开销
- 构建加权 call graph，边权反映调用频率

### 2. 约束感知的合并决策
- 将合并问题建模为非不相交的图聚类问题：给定 call graph（rDAG），找到 k 个子图，使跨子图的边权重之和最小，同时满足每个子图的 CPU 和内存约束
- 精确解：遍历所有可能的 k 和 root set，对每个 candidate root set 求解 ILP（使用 Gurobi），适用于小规模 call graph（≤20 节点）
- 近似解：提出 Downstream Impact Heuristic（DIH），基于节点下游子图的资源需求选择 root，在保持接近最优解质量的同时大幅提升速度

### 3. 基于 LLVM IR 的跨语言合并
- 将不同语言（C、C++、Rust、Go、Swift）的函数编译到 LLVM IR
- 通过 RenameFuncPass 解决命名冲突，MergeFuncPass 将远程调用替换为本地函数调用
- DelayHTTP pass 延迟 libcurl 初始化，避免不必要的库加载
- 使用 Implib.so 延迟加载不常用的 shared library

## 四、实现细节

**代码规模**：1.8K 行 C++（LLVM passes）+ 1.7K 行 Bash/Python（编排管道）。

**编译管道**（10 步）：
1. 前端编译器将源代码编译为 LLVM IR（利用 cargo/rustc nightly 将 libstd 编译为 bitcode）
2. RenameFuncPass：重命名同名函数避免冲突
3. llvm-link：合并 caller 和 callee 的 bitcode
4. MergeFuncPass：将 `sync_inv("callee", req)` 替换为 `callee(req)` 本地调用，同时改造 callee 函数签名
5. 处理依赖关系和 shared libraries
6. 再次 llvm-link 添加 Rust crates
7. DelayHTTP pass：将 `curl_global_init()` 延迟到实际需要 HTTP 调用时
8. llc 编译为目标代码
9. Implib.so 延迟加载 shared libraries
10. lld 链接生成最终二进制（使用 `-Wl,-gc-sections` 去除无用代码）

**跨语言处理**：
- 不同语言的内存分配器（glibc、jemalloc、Go runtime）通过 mmap 获取独立内存区域，互不干扰
- Go 的 goroutine 栈管理通过保留 Go runtime 的 `__go_go` 入口实现

**条件调用机制**：当实际调用次数超过 profiling 时的预期值时，超出部分退化为远程 RPC 调用，防止资源超限导致 crash。

**平台兼容**：已测试 Fission 1.20.5、OpenFaaS 0.27.10、OpenWhisk 1.0.1，唯一改动是引入一个 Kubernetes token。

## 五、实验结果

**实验环境**：6 台机器集群，3 台 128-core Intel Xeon Platinum 8253（2TB RAM）运行函数，其他机器分别运行 API gateway、存储后端和负载生成器。语言选 Rust，平台选 Fission。

**应用**：DeathStarBench 的 Social Network（SN）、Hotel Reservation（HR）、Movie Review（MR）三个应用。

### 主要结果

| 指标 | 改进幅度 |
|------|---------|
| 中位延迟降低 | 45.63%–70.95%（9/11 workflows） |
| 尾延迟降低（P99） | 15.64%–85.47% |
| 吞吐量提升 | 2.05×–12.87× |
| 合并后二进制体积 | 比原始函数之和小 3.4%–86.7% |

### 对比 Container Merge（CM）基线
- CM 延迟降低 25.89%–31.56%，但在高负载下因多函数共享容器导致 OOM
- Quilt 因合并为单进程，内存利用更高效，不会出现 CM 的 OOM 问题

### 资源约束实验（修改版 nearby-cinema）
- 全部合并：延迟降低 42.13%，但吞吐量因 CPU 超限被 throttle 降低 11.64%
- 按最优策略拆分为 2 组：吞吐量比 baseline 提高 50.75%

### Profiling 与合并开销
| 步骤 | 开销 |
|------|------|
| Profiling | 对延迟和吞吐量几乎无影响 |
| 合并决策（DIH） | ≤200 节点 <0.27s，800 节点 ~3.1s |
| 编译+合并+链接 | ~1.5 分钟（一次性后台操作） |

### DIH 启发式质量
- 在 ≤25 节点的图上，DIH 的 optimality gap 仅 0.0394
- 比简单的 weighted degree 启发式好数百倍

## 六、批判性分析

1. **实验中替换了数据库为 fake calls**：在吞吐量实验（Experiment 2）中，作者用硬编码结果+sleep 替代了真实数据库操作，理由是"数据库是瓶颈，难以观察 Quilt 的效果"。但真实 serverless workflow 中数据库交互无处不在——如果 Quilt 只在数据库不是瓶颈时有效，那么其实际适用场景可能比论文呈现的更窄。

2. **Benchmark 规模有限**：所有评估都基于 DeathStarBench，最大 workflow 仅 15 个函数。虽然作者声称这涵盖了"所有能找到的 benchmark"，但实际生产环境中的 workflow 可能远大于此。DIH 在合成图上测试到 800 节点，但缺乏真实大规模 workflow 的验证。

3. **编译时间不可忽视**：合并一次需要约 1.5 分钟，且每次函数更新都需要重新合并。对于频繁更新的 workflow，这可能是一个实际障碍。论文将此归类为"一次性后台操作"，但没有量化函数更新的频率对总体开销的影响。

4. **故障处理完全缺失**：论文坦承合并后任何函数 crash 会导致整个 workflow crash，且"如何最好地解决这一问题仍是开放问题"。这在生产环境中是一个严重的可靠性退化。

5. **HR 应用的结果被轻描淡写**：在 11 个 workflow 中有 2 个（HR 的 search-handler 和 nearby-cinema）改善有限，因为函数执行时间长达数秒。论文对此一笔带过，但这恰恰说明 Quilt 对计算密集型或 I/O 密集型 workflow 帮助不大。

6. **安全假设过于乐观**：论文假设同一 workflow 内的函数可以共享信任域，但现实中不同团队可能负责同一 workflow 中的不同函数，合并后的进程内没有隔离可能引入安全风险。

7. **仅支持 LLVM 语言**：尽管论文号称支持多语言，但实际只支持能编译到 LLVM IR 的语言。Java、Python（原生）、Node.js 这些 serverless 中最主流的语言都不在支持范围内。

## 七、AI Infra / MLSys 视角

1. **对 AI 推理 pipeline 的启发**：现代 AI 推理服务往往由多个微服务组成（前处理、tokenization、模型推理、后处理、safety filter 等），这些服务之间的调用开销与 serverless workflow 类似。Quilt 的函数合并思路可以启发 AI 推理 pipeline 的端到端优化——将多个轻量级处理阶段合并为单一进程，减少序列化和网络开销。

2. **约束感知调度的借鉴**：Quilt 的 resource-aware graph clustering 算法可以迁移到 AI workload 调度场景。例如，在异构集群中部署由多个模型组成的 compound AI system 时，需要在 GPU 显存约束下决定哪些模型/算子应该 co-locate，这与 Quilt 的问题形式非常相似。

3. **LLVM IR 层的跨框架合并**：AI 领域中，不同框架（PyTorch、TensorFlow、JAX）编译到不同的 IR（如 TorchScript、XLA HLO、StableHLO）。Quilt 在 LLVM IR 层合并的思路与 AI 编译器中 cross-framework optimization 的方向一致，值得跟进。

4. **可操作的研究方向**：
   - 将 Quilt 的合并决策算法适配到 GPU kernel fusion 的约束优化（shared memory 和 register 约束类似于 Quilt 中的 CPU/memory 约束）
   - 探索将 AI serving pipeline 中的 pre/post-processing 函数与模型推理合并，减少 CPU-GPU 数据搬运

---

## 八、总结

Quilt 是一个 serverless workflow 优化器，通过在 LLVM IR 层自动合并 workflow 中的多个函数为单一进程，消除函数间的网络调用开销。其核心贡献包括：（1）约束感知的图聚类算法（ILP + DIH 启发式），在满足平台资源限制的前提下最大化合并收益；（2）基于 LLVM IR 的跨语言函数合并管道，支持 C/C++/Rust/Go/Swift；（3）透明兼容现有平台（Fission、OpenWhisk、OpenFaaS）无需修改。在 DeathStarBench 上实现 45%–71% 的延迟降低和 2×–13× 的吞吐量提升。主要局限在于仅支持 LLVM 语言、缺乏故障隔离、编译开销不可忽视，以及对计算/IO 密集型 workflow 帮助有限。
