# Quilt: Resource-aware Merging of Serverless Workflows

## 一、背景

Serverless 计算已成为主流云服务形态（AWS Lambda、Azure Functions、Google Functions 等），其核心承诺是开发者无需管理服务器——平台负责调度、扩缩容、容错和计费，而开发者只需上传函数代码。当应用逻辑超出单个函数的范围时，开发者会构建 **serverless workflow**：若干函数组成的调用图（call graph），函数间通过调用 API 交互。这种模式天然契合微服务设计理念，每个函数可用不同语言编写、独立测试迭代，平台也能将函数调度到任意有空闲资源的机器上。

然而，serverless workflow 的性能代价不可忽视：函数调用本质上是一次 HTTP 请求——经由 API gateway → 控制器 → 目标 worker → callee 容器，涉及序列化/反序列化、TCP 连接建立、排队延迟，若 callee 容器未就绪还需经历 **cold start**（从远程存储拉取容器镜像）。在 AWS Lambda 上，一次 warm no-op 函数调用的中位延迟为 10.4 ms；20% 的 Lambda 函数执行时间不到 100 ms，这意味着调用开销常常可与计算本身相当甚至更大。

---

## 二、要解决的问题

1. **函数调用开销过高**：每次 serverless 函数调用都引入 API gateway、TCP 握手、序列化等多层开销，对执行时间短（< 数十 ms）的函数尤为致命。

2. **Cold start 放大问题**：调用链上任意一个函数的 cold start 都会拖慢整条 workflow，且 cold start 代价比普通调用开销高出一个数量级。

3. **现有合并方案的局限**：
   - **语言限制**：WiseFuse、Fusionize、Faastlane 只能合并同一解释型语言（如 Python/JavaScript）的函数，无法处理 Rust、Go、C++ 等编译型语言。
   - **资源感知不足**：Fusionize 合并时忽略资源约束；WiseFuse/Faastlane 仅考虑容器大小，未精细建模函数间调用频率对 CPU/内存的影响。
   - **侵入性强**：Nightcore 需要替换现有 serverless 平台，且要求函数显式使用 OS pipe API；Faasm 需要开发者修改代码。

4. **资源碎片化（Resource Fragmentation）**：若将太多函数合并到同一进程，合并后的函数所需 CPU/内存可能超出单个 worker 的可用资源，导致该 worker 剩余资源无法被利用——反而降低整体集群利用率。

---

## 三、核心设计

**Quilt** 是一个运行在 serverless 平台后台的优化器，自动将 workflow 中的函数合并成一个进程，将函数调用从网络 RPC 转化为本地调用（纳秒级，替代毫秒级）。

**三个核心观察**：

1. **信任模型**：同一 tenant 同一 workflow 内的函数没有理由相互隔离——就像应用程序导入库函数一样。Quilt 提供 workflow 级别的隔离（workflow 间隔离，workflow 内不隔离）。

2. **LLVM IR 作为通用中间层**：C、C++、Rust、Swift、Go（via Gollvm）等主流编译型语言均可编译为 LLVM IR，在 IR 层面合并天然实现跨语言合并。

3. **异步合并**：Quilt 不需要在函数上传时立即合并，可先监控 workflow 执行一段时间，在后台完成分析和合并，调度器对合并完全透明——只看到一个"更新的函数"。

**整体流程**：
1. **Profiling**：通过在 nginx ingress controller 注入 OpenTelemetry 模块，透明收集 caller-callee 调用关系和调用频率（存储于 Grafana Tempo）；同时用 cAdvisor 采集每个函数容器的 CPU 时间和峰值内存（存储于 InfluxDB）。
2. **合并决策**：基于调用图和资源 profiling，用约束感知算法将调用图划分为若干子图，每个子图合并为一个进程，目标是在满足 CPU/内存约束的前提下最小化跨子图调用次数。
3. **LLVM 编译合并**：将子图内所有函数编译为 LLVM IR，重命名符号避免冲突，将 HTTP 调用替换为本地函数调用，执行死代码消除、库去重等优化，最终链接为单个可执行文件。
4. **透明替换**：合并后的函数通过平台标准 API 上传，调度器感知不到任何变化。

## 四、实现细节

### 合并决策算法

合并问题被形式化为一个 **约束非不相交图划分问题**（NP-hard）：

- 调用图为有根 DAG（rDAG），每个节点携带基线内存 $m_i$ 和 CPU $c_i$
- 每条边携带归一化调用频率 $\alpha_{i,j} = \lceil w_{i,j}/N \rceil$
- 异步调用要求 $\alpha_{i,j}$ 个并发实例，同步调用只需 1 个实例（但 CPU 按调用次数累积）
- 目标：划分为 $k$ 个连通子图，每个子图满足内存和 CPU 上限 $M, C$，最小化跨子图边权之和

**小图（≤ 20 节点）**：精确求解——两阶段 ILP：Phase 1 枚举候选根集合，Phase 2 用 Integer Linear Programming（Gurobi 求解器）找最优子图分配。

**大图**：Downstream Impact Heuristic（DIH）启发式算法——对每个候选根节点 $j$，综合评估其入边压力 $W_{in}(j)$、下游内存总需求 $M_{ds}(j)$、下游 CPU 总需求 $C_{ds}(j)$，优先选择"下游资源消耗大"的节点作为子图根（即为高资源压力区域提供独立容器，避免其挤爆其他子图）。实验显示 DIH 在最优性 gap 上平均仅 0.039（25 节点），比 weighted degree 启发式好 100 倍以上。

**动态调整**：若分析到调用频率可能超出 profiling 时的预期值，Quilt 将 `sync_inv`/`async_inv` 改写为条件调用——调用次数在阈值内走本地调用，超出则降级为 RPC，保证正确性。

### 编译合并流水线（LLVM-based）

1. 各函数分别编译为 LLVM IR（`rustc --emit=llvm-bc`）
2. **RenameFuncPass**：为函数和全局变量加唯一前缀，避免符号冲突
3. **MergeFuncPass**：将 `sync_inv("callee", req)` 替换为 `callee(req)`；将 callee 函数的 `get_req()`/`send_res()` 接口改写为普通函数参数/返回值
4. `llvm-link` 合并多个 IR 模块
5. **DelayHTTPPass**：将 `curl_global_init()` 等 HTTP 库初始化延迟到实际需要 RPC 时才执行，允许后续以 lazy loading 方式加载 libcurl（若所有调用都被合并则完全不加载）
6. `llc` 编译为目标代码 + `lld` 链接为最终 binary

**跨语言合并**：通过 shim 层实现——Layer 1（`caller2c`，用 caller 语言编写）将参数从 caller 的字符串类型转换为 C `char*`；Layer 2（`c2callee`，用 callee 语言编写）将 `char*` 转换为 callee 的字符串类型，再调用实际函数。由于 serverless 函数间只通过 JSON string 传递数据，跨语言互操作只需处理字符串类型转换。

**实现规模**：1,800 行 C++（LLVM pass）+ 1,700 行 Python/Bash（编译流水线、profiling 管理）

## 五、实验结果

### 实验环境

- 6 台机器的集群：3 台 128 核 Intel Xeon Platinum 8253 / 2TB RAM 运行 serverless 函数，其余机器运行 API gateway、Tempo、InfluxDB、workload generator
- 1 Gbps 网络，~200 μs RTT
- Serverless 平台：Fission 1.20.5；语言：Rust
- 负载生成：wrk2（closed-loop HTTP）
- Benchmark：DeathStarBench（Social Network / Movie Review / Hotel Reservation）

### 主要结果

| 指标 | 结果 |
|------|------|
| 中位延迟降低 | 45.63% – 70.95%（9/11 workflows） |
| 尾延迟（P99）降低 | 15.64% – 85.47% |
| 吞吐量提升 | 2.05× – 12.87× |
| vs Container Merge（CM）延迟 | Quilt 比 CM 进一步降低 ~34%（sync）|
| 合并 binary 大小 | 比原函数 binary 之和小 3.4% – 86.7%（1 个例外大 9%）|
| Profiling 开销 | 可忽略不计（no-op 函数延迟/吞吐几乎不受影响）|
| 合并决策时间（DIH 启发式） | ≤ 0.27 秒（200 节点），3.10 秒（800 节点）|
| 编译合并时间 | ~1.5 分钟（主要是编译和链接，不依赖函数数量而主要取决于依赖库大小）|
| DIH 最优性 gap | 0.039（25 节点），远优于 weighted degree 启发式 |

**关键发现**：
- Container Merge（CM）虽能改善延迟，但在高负载下会超出内存限制导致容器被杀；Quilt 因为二进制更小、不重复加载运行时和库，可在相同资源下安全运行。
- 对执行时间本身就很长（秒级）的 workflow，合并效果有限——调用开销相对可忽略。
- 盲目合并所有函数可能超出 CPU 限制并触发 throttling，导致吞吐量下降；Quilt 的约束感知合并可将 workflow 划分为多个子图，避免 throttling，实现最优吞吐。

## 六、批判性分析

**实验规模偏小，代表性存疑**：
- 集群仅 6 台机器，函数数量最多 15 个（Movie Review 的 compose-review workflow）。实际生产 serverless 环境往往有数百个函数、数十台 worker，资源碎片化和调度压力在小集群上难以体现。论文承认最大测试 workflow 仅 15 个函数，对"大图"启发式的评估依赖随机生成图，而非真实生产 workload。

**合并时间约一分钟，但未讨论如何处理期间的版本漂移**：
- 合并需要约 1.5 分钟，论文将此归咎于编译依赖库，但未详细说明在此期间若函数被更新（代码变更、配置变更），Quilt 如何保证一致性、以及如何避免合并中途失效。

**动态调用频率适应机制存在正确性隐患**：
- 当调用频率超过 profiling 预期时，Quilt 通过条件判断将超出部分降级为 RPC。但论文以 `fan_out_function` 为例说明 46.7% 的请求可能超出预期——这意味着接近一半的请求在理论上会产生"部分本地、部分远程"的混合调用模式，其对性能的影响没有量化实验支持。

**对跨语言合并的评估十分有限**：
- 论文声称支持 C、C++、Go、Rust、Swift 等语言混合合并，但评估中主要使用 Rust 单一语言，跨语言场景仅在 §7.6 作简要描述，缺乏系统性的延迟、正确性和内存安全方面的评估。

**Workflow 级隔离的安全性讨论不够深入**：
- 论文以"opt-in"为由轻描淡写了将不同函数合并到同一地址空间的安全风险。一旦某个函数存在内存安全漏洞（如 C/C++ 的 buffer overflow），整个 workflow 进程都面临被攻陷的风险。Section 8 仅简短提及可用 Intel MPK 实现函数级内存隔离，但未实现，属于 future work。

**Cold start 问题处理得不完整**：
- 论文主要优化 warm 调用路径。对于 cold start，Quilt 合并后的 binary 反而更大（单一进程包含所有函数代码），cold start 时需要从远程加载更大的文件，可能加剧 cold start 延迟。论文没有专门的 cold start 对比实验。

**竞争系统基线选取不公平**：
- Container Merge（CM）是论文自行实现的简单基线（在容器内部署一个"internal API gateway"转发调用），并非任何已发表系统的原版实现，难以作为公平的性能对比基准。Nightcore、Faastlane 等系统没有出现在实验对比中。

---

## 七、总结

Quilt 提出了一种**资源感知的 serverless workflow 函数合并**方案，通过 LLVM IR 层面的跨语言合并，将 serverless 函数调用从毫秒级 HTTP RPC 优化为纳秒级本地调用，同时用约束感知的图划分算法（ILP + Downstream Impact 启发式）避免合并后超出容器资源限制导致的 throttling 或内存溢出。其透明性（无需修改 serverless 平台、无需开发者干预）和多语言支持（C/C++/Rust/Go/Swift）是相较于现有工作的主要亮点。主要局限在于：合并时间约 1 分钟（不适合频繁更新的函数）、对执行时间长的函数收益有限、安全隔离尚未完整实现、评估规模偏小、以及对 cold start 的影响未深入分析。
