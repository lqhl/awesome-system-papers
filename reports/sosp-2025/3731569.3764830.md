# Quilt: Resource-aware Merging of Serverless Workflows

## 1. 论文基本信息

- **标题**: Quilt: Resource-aware Merging of Serverless Workflows
- **作者**: Yuxuan Zhang, Sebastian Angel (University of Pennsylvania)
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764830
- **代码**: https://github.com/eniac/quilt

## 2. 研究背景

Serverless 计算（FaaS）平台让开发者上传单个函数的代码，无需管理服务器，由提供商负责 placement、函数发现、请求路由、负载均衡、故障恢复和按需计费。Serverless 的优势在于灵活性——提供商可以将函数放在任何有空闲资源的地方。

**Serverless Workflow 的开销问题**：当应用需要多个函数协作时（workflows），每个函数调用另一个函数实际上是通过 HTTP 请求实现的。典型调用路径：Caller -> API Gateway -> Controller -> Worker（创建容器 -> 运行函数 -> 返回结果）。这个过程中引入的 overhead 包括：
1. **序列化/反序列化**：JSON 编码/解码
2. **网络延迟**：TCP 握手、libcurl session 建立
3. **队列延迟**：Controller 调度开销
4. **冷启动**：容器需要从远程存储加载（runtime、库、函数代码），可能需要数秒

对于短生命周期函数（Meta XFaaS 平台的大量函数），频繁的函数调用会累积大量 overhead。AWS Lambda 的 warm no-op 函数中位调用延迟为 10.4 ms，而 67% 的 Lambda@Edge 函数执行时间低于 20 ms——overhead 可能与实际执行时间相当。

**现有方案的局限性**：
- Nightcore：要求所有函数在同一台机器上且需要开发者指定共置哪些函数
- SONIC：聚焦于减少数据移动，需要修改现有平台
- WiseFuse、Faastlane、Faasm、Fusionize：要么依赖特定解释语言，要么忽略资源约束

## 3. 要解决的问题

**核心问题**：如何在保持 serverless 平台灵活性和多语言支持的同时，通过合并 workflow 中的函数来消除函数间网络调用的 overhead，同时满足提供商的资源约束？

具体挑战：
- **合并的负面效应**：将所有函数合并到一个进程可能导致资源碎片化——并行函数或大数据量函数合并后需要过多 CPU 或内存，使 placement 困难
- **多语言支持**：现代 serverless 应用越来越多使用编译型语言（Rust、C、C++、Swift、Go），这些语言的函数合并比解释型语言更复杂
- **透明度要求**：合并对 serverless 平台和开发者都应该是透明的，无需代码修改
- **资源约束**：提供商对每个函数容器有 CPU 和内存限制，合并方案必须尊重这些约束

## 4. 核心贡献

1. **Constraint-aware Merging**：提出考虑资源约束的函数合并问题建模，在改善性能的同时满足提供商的 CPU 和内存限制。
2. **LLVM-IR 级别的函数合并**：通过将不同语言的函数编译到统一的 LLVM IR，实现跨语言（Rust、C、C++、Swift、Go）函数合并。
3. **透明化工作流发现**：通过分布式追踪（OpenTelemetry + Grafana Tempo）自动发现函数调用图，无需修改平台或开发者代码。
4. **DAG clustering 优化算法**：将函数合并问题形式化为非不相交图的聚类问题，提出 Downstream Impact Heuristic（DIH）快速近似求解。
5. **生产级实现**：在三个开源 serverless 平台（Fission、OpenWhisk、OpenFaaS）上验证，无需修改这些平台的调度器。

## 5. 主要研究方法

### 5.1 Workflow 发现与 Profiling
通过分布式追踪自动发现 caller-callee 关系，无需开发者介入：
- 在 API Gateway 前放置 nginx ingress controller，配置 OpenTelemetry 模块记录 trace
- 收集 caller-callee 信息（调用频率），构建有向加权 DAG
- 通过 cAdvisor 收集每个容器在 profiling window 内的累计 CPU 时间和峰值内存使用，存储到 InfluxDB

### 5.2 函数合并问题建模
**问题形式化**：将 call graph G = (V, E) 聚类为 k 个连通有向无环图（rDAG）子图 G_1, ..., G_k，每个子图满足资源约束。

**约束条件**：
- 每个子图必须是连通 rDAG（确保单一入口点）
- CPU 约束：$\sum c_u + \sum \alpha_{i,j} \cdot c_j \leq C$（包含异步调用的资源放大）
- 内存约束：$m_u + \sum m_j + \sum (\alpha_{i,j} - 1) \cdot m_j \leq M$

**目标函数**：最小化跨子图边（需要远程 serverless 调用的边）的权重之和。

### 5.3 最优求解与启发式算法
- **最优求解**：枚举所有候选根集 + ILP 求解，适用于小图（<= 20 个节点）
- **Downstream Impact Heuristic (DIH)**：启发式选择根节点。核心思想：如果一个节点是通往大、资源密集子图的网关，让它作为根可以让该子图独立成组，避免违反内存/CPU 约束。

### 5.4 编译与合并流程
**LLVM-IR 编译管道**：
1. 源文件编译到 LLVM IR（Rust 用 rustc+nightly，其他语言用对应编译器）
2. **RenameFunc Pass**：重命名 callee 函数，避免命名冲突
3. **llvm-link**：链接 caller 和 callee 的 bitcode
4. **MergeFunc Pass**：将 sync_inv() 调用转换为本地函数调用，处理类型转换
5. **DelayHTTP Pass**：延迟 HTTP 库的初始化（curl_global_init）
6. **Implib.so**：延迟非频繁使用共享库的加载
7. 最终链接为二进制，应用 -Wl,-gc-sections 优化

**跨语言合并**：所有语言通过 LLVM IR 统一表示。类型转换通过 JSON 字符串的简单 shim 处理（因为 serverless 函数通过 REST API 交互，输入输出总是 JSON 字符串）。

## 6. 设计与实现

### 6.1 资源感知的合并决策
提供者向 Quilt 提供可用资源约束，Quilt 的算法决定最优合并分组。在合并函数数量和资源效率之间取得平衡。

### 6.2 Representativeness 处理
对于数据依赖 fan-out（如 `for i in 0..num { async_inv(...) }`）：
- 如果实际调用数量 <= profile 的边界：使用本地调用
- 如果超过：fallback 到远程 RPC

这保证了正确性和弹性。

### 6.3 容器合并（CM）基线对比
论文实现了容器级合并作为对比——所有函数放在同一容器但不同进程，通过内部 API gateway 路由。这避免了冷启动但保留了 HTTP overhead 和序列化开销。

### 6.4 实现栈
- 1.8K 行 C++（LLVM passes）
- 1.7K 行 Bash/Python（编译和 profiling pipeline）
- 使用 Gurobi 12.0.1 求解 ILP
- 集成：nginx、OpenTelemetry Collector、Grafana Tempo、InfluxDB、cAdvisor

## 7. 主要实验结果

### 7.1 延迟改善
在 DeathStarBench 的 9 个 workflow（Social Network、Hotel Reservation、Movie Review）上测试：
- **Quilt 降低中位延迟 45.63%-70.95%**
- **降低 P99 延迟 15.64%-85.47%**（9 个 workflow 中的 9 个）
- HR 应用的两个 workflow 改善有限，因为它们包含耗时较长的函数，overhead 改善不明显

### 7.2 吞吐量和资源效率
在 compose-post workflow（SN 应用）上测试（将数据库替换为 fake calls 以隔离 Quilt 效果）：
- CM 相比 baseline 降低延迟 31.56%（sync）和 25.89%（async），但不改善吞吐量
- CM 在高负载下由于容器内存限制导致问题（需要 256MB vs 128MB）
- Quilt 在相同资源下（20 containers）大幅改善吞吐量和延迟

### 7.3 资源效率
- **吞吐量提升 2.05x-12.87x**
- 合并消除了重复的容器、runtime 和库的 overhead

### 7.4 平台兼容性
在 Fission（主要测试平台）、OpenWhisk 和 OpenFaaS 上验证，只需在 Kubernetes 中添加一个 one-bit token，无需修改平台调度器。

## 8. 潜在问题/局限性

1. **LLVM 支持的语言有限**：虽然声称 LLVM IR 支持 C、C++、D、Go (via Gollvm)、Haskell、Kotlin、Nim、OCaml、Objective-C、Python (via Codon)、Rust、Scala、Swift、Zig 等，但这些编译器到 LLVM IR 的质量参差不齐，某些语言的 Codegen 质量可能影响性能。
2. **合并时间开销**：论文提到合并大约需要一分钟，这对于需要频繁重新合并的动态 workload 可能是瓶颈。虽然提到了动态重新合并的触发条件（workload 变化、函数更新），但没有量化重新合并的频率和影响。
3. **外部服务依赖**：如果函数通过 SQS 等外部服务交互（而非直接调用），Quilt 无法合并这些外部交互。
4. **故障处理**：当 workflow 是单一进程时，任何函数崩溃都变成 workflow 崩溃。如何优雅处理部分失败是一个未解决的开放问题。
5. **安全和信任模型**：合并意味着同一 workflow 中的函数共享地址空间，这与传统的 per-function 隔离模型不同。论文提到了敏感函数不应合并，但没有提供自动检测机制。
6. **性能可变性**：LLVM 优化 pass 的编译时间不均匀，可能导致冷启动延迟的不可预测性增加。
7. **跨租户安全**：合并发生在同一租户的 workflow 内部，但论文未讨论恶意函数可能通过共享地址空间攻击其他函数的风险。

## 9. 未来工作

1. **新语言支持**：扩展到更多 LLVM IR 目标语言，以及探索非 LLVM 语言（如 JavaScript、Python）的合并可能性。
2. **合并优化**：减少合并编译时间，使动态重新合并更实用。
3. **自适应合并策略**：根据运行时性能自动触发重新合并。
4. **跨租户安全增强**：在合并框架中增加更强的安全隔离。
5. **更丰富的资源模型**：考虑 CPU 亲和性、NUMA 感知等更复杂的资源约束。

## 10. 个人评注

**Quilt 是一篇思路清晰、工程实现扎实的论文**，它抓住了 serverless workflows 中一个被长期忽视但实际上影响巨大的问题——函数间 HTTP 调用的 overhead。

论文最有意思的洞察是**将函数合并问题形式化为图的聚类问题**——这个建模本身就揭示了问题的本质：合并不是"越多越好"，而是需要在函数间网络调用的节省和资源碎片化的代价之间取得平衡。DIH 启发式虽然理论上可能不是最优的，但其"下游影响"的直觉非常合理且实用。

**批评性思考**：
- **延迟数字的上下文中位偏差**：虽然 Quilt 改善了 45-70% 的中位延迟，但这些测试使用的是函数执行时间以 ms 计的 DeathStarBench。对于极短执行时间（< 1 ms）的函数，overhead 改善可能比例上更大。但对于长时间函数（如 ML 推理），overhead 改善的绝对值可能微不足道。
- **CM 基线的实现质量**：论文实现的 CM 基线使用"内部 API gateway"进行进程间路由，这可能不是工业界实际采用的方案。如果现有平台有更高效的进程间通信机制，Quilt vs CM 的差距可能没那么显著。
- **"无需修改"的声明需谨慎**：虽然 Quilt 不需要修改 serverless 平台，但它需要修改函数的实现——函数必须声明 `can_be_merged`。这实际上是开发者层面的契约，只是比 Nightcore 等方案侵入性更低。
- **可扩展性未充分验证**：论文测试的 workflow 最多 15 个函数。对于包含数百个函数的真实 serverless 应用（如复杂的数据处理 pipeline），合并算法的可扩展性和优化时间未被讨论。
- **与 vLLM、Serverless GPU inference 等新兴场景的脱节**：论文仅考虑了 CPU-bound 函数。对于 GPU 函数或需要特殊硬件的函数，合并策略可能完全不适用。

总体而言，这是一篇适合 serverless 平台开发者和云原生架构师阅读的论文。它提供了对 serverless workflows 性能问题的系统化诊断和可行的工程解决方案。对于想深入 serverless 性能的实践者，其中的 profiler 设计（第 3 节）和编译管道设计（第 5 节）尤其值得参考。
