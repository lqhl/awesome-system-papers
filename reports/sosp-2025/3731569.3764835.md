# Mitigating Application Resource Overload with Targeted Task Cancellation

**作者**：Yigong Hu (Boston University), Zeyin Zhang (Johns Hopkins University), Yicheng Liu (University of Michigan / UCLA), Yile Gu (University of Washington), Shuangyu Lei (University of Michigan), Baris Kasikci (University of Washington), Peng Huang (University of Michigan)
**会议**：SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
**链接**：https://doi.org/10.1145/3731569.3764835
**源文件**：[[3731569.3764835.pdf]]

---

## 一、背景

现代软件系统为了最大化资源利用率，通常运行在接近峰值吞吐量的状态。然而，这种高利用率使系统对突发负载极为脆弱——短暂的需求尖峰就可能导致大量 SLO 违规。除了经典的 receive livelock 问题外，应用级资源（如数据库的 table lock、buffer pool、线程池）的争用也会造成严重的过载。一个长时间持有关键资源的请求可能阻塞大量其他请求，导致整体系统性能急剧下降。

传统的过载控制机制主要依赖全局信号（如队列长度、排队延迟），无法洞察单个请求对应用内部资源的影响，因此在面对应用级资源过载时效果有限。

---

## 二、要解决的问题

1. **Admission control 的盲目性**：Breakwater、SEDA 等机制依赖全局排队信号，无法区分"肇事请求"和"受害请求"，结果往往大量丢弃无辜请求而非真正垄断资源的请求，严重损害应用可用性。
2. **Performance isolation 的局限性**：pBox 等系统通过动态资源配额隔离请求，但无法取消已经持有关键资源的问题请求，不能从严重的资源过载中恢复。
3. **Protego 治标不治本**：Protego 监控每个请求的锁等待时间，丢弃等待超时的请求——这些是锁争用的受害者，而非制造争用的根源。
4. **请求行为的高度可变性**：不同请求对应用资源的消耗差异极大（如 MySQL 中简单的点查询 vs. 大表 dump 查询），使得预测哪些请求会垄断资源极其困难。

## 三、洞察与设计

**关键洞察**：现代软件中 76% 的应用已经内置了任务取消机制（如 Go 的 Context、Java 的 thread interrupt、C++ 的 stop_token），其中 95% 提供了由开发者精心设计的安全取消入口（cancellation initiator）。这意味着可以直接复用应用已有的取消逻辑来安全地终止问题请求，而无需从头构建通用的取消机制。

基于这一洞察，论文提出 Atropos 框架，其核心策略是**主动取消垄断资源的"肇事请求"（culprit），而非丢弃被阻塞的"受害请求"（victim）**。

Atropos 的设计包含以下关键组件：

- **Cancellable Task 抽象**：将所有应用活动（用户请求和后台任务）统一建模为可取消任务，作为取消操作的基本单元。
- **Application Resource 抽象**：统一同步资源、队列资源和内存资源三类应用级资源，每类资源支持 get/free/wait 三种操作，通过 contention level（争用程度）和 resource gain（取消收益）两个无量纲指标来量化。
- **Runtime Manager**：持续追踪每个任务的资源使用，通过轻量级 API（getResource/freeResource/slowByResource）记录资源获取、释放和等待事件。
- **Overload Estimator**：当检测到端到端性能违反 SLO 时，计算各资源的 contention level 和各任务的 resource gain。Resource gain 使用未来资源使用量（而非当前持有量）来估算，避免偏向即将完成的长请求。
- **Multi-objective Cancellation Policy**：借鉴多目标优化（MOOP），通过非支配集（non-dominated set）和标量化（scalarization）方法，在多种资源争用并存时选择全局最优的取消目标。

## 四、实现细节

Atropos 分别用 C/C++（4,002 行）、Java（3,534 行）和 Go（2,106 行）实现，集成到 6 个大型应用中：

| 应用 | 语言 | 类别 | 代码规模 | 集成代码量 |
|------|------|------|---------|-----------|
| MySQL | C/C++ | 数据库 | 2.23M SLOC | 74 行 |
| PostgreSQL | C/C++ | 数据库 | 1.49M SLOC | 59 行 |
| Apache | C/C++ | Web 服务器 | 198K SLOC | 30 行 |
| Elasticsearch | Java | 搜索引擎 | 3.29M SLOC | 65 行 |
| Solr | Java | 搜索引擎 | 961K SLOC | 47 行 |
| etcd | Go | KV 存储 | 244K SLOC | 22 行 |

关键实现细节：
- **资源追踪**：通过在应用代码中插入 getResource/freeResource/slowByResource API 调用来追踪资源使用。每个 API 仅记录一个 (value, rscType, eventType) 元组和时间戳。
- **时间戳优化**：正常负载下采样时间戳并复用给同一区间内的所有事件，过载时切换为逐事件记录。
- **进度估算**：使用 GetNext 模型 `Progress(i) = k/N`（k 为已处理行数，N 为预计总行数），结合 MySQL 的 rows_examined 等内部变量。
- **公平性保障**：每个任务最多被取消一次，重新执行时标记为不可取消，防止饥饿。
- **资源识别启发式**：枚举全局变量 → 过滤非资源变量 → 静态分析使用点 → 判断是否跨任务共享 → 资源类型特定检查（如 LOCK 检查临界区、MEMORY 检查写系统调用）。

## 五、实验结果

实验在 Azure 虚拟机上进行（16 核 vCPU，64 GB DRAM，160 GB SSD，Ubuntu 20.04），复现了 16 个真实应用资源过载场景。

### 主要性能对比

| 指标 | Atropos | Protego | pBox | DARC | PARTIES |
|------|---------|---------|------|------|---------|
| 平均归一化吞吐量 | **96%** | 50.7% | 53.9% | 36.3% | 37.8% |
| 平均归一化 p99 延迟 | **1.16x** | 1.88x | 较差 | 较差 | 较差 |
| 平均丢弃率 | **<0.01%** | ~25% | — | — | — |

### SLO 维护
- 在 20% 延迟增长阈值下，16 个案例中 14 个成功维持 SLO，平均延迟增长仅 10.2%
- 剩余 2 个案例（case 3 和 case 12）因存在多个问题请求、取消间隔限制，延迟增长分别为 23% 和 26%

### 多目标策略有效性
- Multi-objective 策略在 8/16 个案例中优于单资源启发式策略
- 在 6/16 个案例中优于使用当前资源用量（而非未来预测）的策略

### 运行时开销
- 正常负载：吞吐量下降平均 0.59%（最大 1.95%），p99 延迟增加平均 0.21%
- 过载负载（仅追踪，不取消）：吞吐量下降平均 7.09%，p99 延迟增加平均 8.12%

## 六、批判性分析

1. **集成成本被低估**：论文强调代码修改仅需 22–74 行，但承认识别应用资源是最耗时的部分（MySQL 耗时约 7 天）。这种人工标注成本在实际部署中是主要障碍，且论文提出的启发式方法（枚举全局变量 + 静态分析）并未经过系统性评估。

2. **进度估算的脆弱性**：resource gain 的计算依赖"剩余资源需求与剩余工作量成正比"的假设，论文也承认这是一个强假设。对于非均匀资源访问模式的请求（如先扫描后聚合），这个假设可能严重偏离实际。论文虽然讨论了误判的代价"只是取消了次优请求"，但频繁的误取消会增加重试开销和整体延迟。

3. **基线对比存在不对称性**：Protego、pBox、DARC、PARTIES 各自设计目标不同（锁争用、资源隔离、调度优化），将它们统一与 Atropos 在 16 个精心挑选的应用资源过载场景中比较，对这些系统并不完全公平。例如 DARC 和 PARTIES 本身不是为应用级资源过载设计的。

4. **单节点限制**：论文明确承认 Atropos 主要面向单节点应用，对分布式系统的扩展仅停留在"future work"层面。现代服务大多是分布式微服务架构，一个请求的资源垄断可能跨越多个节点。

5. **Apache 案例暴露了方法论边界**：Apache 中 PHP 脚本不支持应用级取消，被迫使用 pthread_cancel 这种 Atropos 自身标记为"粗粒度且可能不安全"的方式。这说明 76% 应用支持取消的统计数据并不意味着所有关键路径都可安全取消。

6. **过载检测的滞后性**：Atropos 依赖端到端性能（吞吐量下降 + 延迟超 SLO）来触发取消，这本质上是事后响应。论文声称"proactive"但实际上在检测到性能劣化后才介入，真正前置的资源监控可能更有价值。

---

## 七、总结

Atropos 提出了一种新颖的过载控制思路：通过主动取消垄断应用资源的"肇事请求"来缓解资源过载，而非传统方法中丢弃无辜的"受害请求"。系统利用现代软件中已广泛存在的任务取消机制，通过统一的资源抽象和多目标取消策略，在 6 个大型应用的 16 个真实过载场景中实现了 96% 的基线吞吐量和 <0.01% 的请求丢弃率。其主要局限在于需要人工标注应用资源（成本较高）、进度估算依赖强假设、以及缺乏分布式系统支持。开源地址：https://github.com/OrderLab/Atropos。
