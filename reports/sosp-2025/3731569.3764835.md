# Mitigating Application Resource Overload with Targeted Task Cancellation

**作者**：Yigong Hu（Boston University / UCLA）、Zeyin Zhang（Johns Hopkins University）、Yicheng Liu（University of Michigan）、Yile Gu（University of Washington）、Shuangyu Lei（University of Michigan）、Baris Kasikci（University of Washington）、Peng Huang（University of Michigan）

## 一、背景

现代软件为了最大化资源利用率和吞吐量，通常在接近峰值负载的条件下运行，这使系统非常容易受到过载（overload）的影响。一旦负载出现短暂尖峰，就可能引发大量 SLO 违规。传统的过载控制关注的是系统级资源（CPU、网络队列），依赖全局信号（如排队延迟）来限流或拒绝请求。

然而现代应用（数据库、搜索引擎、键值存储等）广泛依赖**应用级资源（application-level resources）**——如表锁、buffer pool、内部线程队列——这些资源由应用自身管理，对操作系统不可见。当这类资源被少数"问题请求"（culprit）垄断时，大量无辜请求（victim）受牵连，系统整体吞吐骤降、尾延迟爆炸。

---

## 二、要解决的问题

**核心矛盾**：传统过载控制无法有效应对应用级资源过载，原因如下：

1. **准入控制（Admission Control）**（如 Breakwater、SEDA）依赖全局排队延迟，无法感知哪些请求正在垄断特定应用资源，结果是无差别地丢弃大量"受害者"请求，而不是真正的"元凶"。

2. **性能隔离（Performance Isolation）**（如 pBox）为每个请求分配资源配额或动态重分配，但不会取消正在执行的请求。当问题请求已经持有关键资源（如表锁），重新分配无济于事。

3. **Protego**（针对锁竞争）虽然能检测锁等待并取消请求，但取消的是锁等待时间接近 SLO 的**受害者**，而非持锁垄断资源的**元凶**，导致高丢弃率和低吞吐。

**具体 Pain Points**：
- MySQL buffer pool 过载：少量"dump 查询"（占比 0.01%）可将最大吞吐从 25K QPS 降至 12K QPS
- MySQL 表锁过载：一个 backup 查询与 scan 查询的微妙交互，可将吞吐从 25K 降至 11K QPS
- 问题请求的行为高度可变且难以事先预测，只有在运行时才能观测其真实资源影响

## 三、核心设计

**Atropos** 的核心原则：**主动识别并取消垄断资源的元凶请求，而非拒绝被它阻塞的受害者**。

系统由四个组件构成：

### 3.1 Cancellable Task 抽象
所有应用活动（用户请求、后台任务）均抽象为"可取消任务"（cancellable task）。开发者通过 `createCancel` / `freeCancel` 划定任务边界，通过 `setCancelAction` 注册应用自定义的取消回调（如 MySQL 的 `sql_kill`）。Atropos 利用应用已有的取消机制（76% 的主流开源软件已内置任务取消支持），确保取消的安全性和一致性。

### 3.2 应用资源抽象
统一三类应用资源：

| 类型 | 竞争度（Contention Level） | 资源收益（Resource Gain） |
|------|--------------------------|-------------------------|
| **LOCK**（同步资源） | 等待时间 / 总执行时间 | 当前持锁时间 × 剩余工作比例 |
| **MEMORY**（缓存/缓冲） | 驱逐率（eviction ratio） | 当前占用内存 × 剩余工作比例 |
| **QUEUE**（线程队列） | 队列等待时间 / 实际执行时间 | 预期未来线程消耗时间 |

开发者通过 `getResource` / `freeResource` / `slowByResource` API 上报每个任务的资源使用情况。

### 3.3 过载检测与 Estimator
Runtime Manager 持续追踪每个可取消任务的资源使用；当端到端性能违反 SLO 时，Estimator 被激活，计算每个任务在每种资源上的竞争度和资源收益，并对不同类型资源的竞争度做归一化（以执行时间百分比表示），使其可比较。

### 3.4 多目标取消策略（Multi-Objective Cancellation Policy）
受多目标优化（MOOP）中非支配集概念启发：
1. **计算非支配集**：找出在所有资源维度上均不劣于其他任务的候选任务集
2. **标量化**：用各资源的竞争度作为权重，加权求和各任务的资源收益，选择总收益最大的任务取消

```
total_gain(task) = Σ_r  contention_level(r) × resource_gain(task, r)
```

### 3.5 公平性机制
每个任务最多被取消一次（避免饥饿），取消后标记为不可取消并安排重试；只有在资源持续可用后才重新执行被取消的任务。

## 四、实现细节

Atropos 以三种语言实现：
- **C/C++**：用户态库，应用直接链接，4,002 行
- **Java**：`CancellableTask` 基类，应用任务继承，3,534 行
- **Go**：集成进 Go runtime，直接追踪 goroutine 等待时间，2,106 行

集成到六个大型应用的代码改动极少（22–74 行），但**手动标注应用资源是主要工作量**：MySQL 约需一名研究生 7 天，PostgreSQL/Elasticsearch/Solr 各需 4–5 天。作者总结了一个加速启发式：应用资源通常是全局变量，可通过枚举全局变量 + 静态分析使用点 + 人工确认共享语义来定位。

取消决策需在微秒级完成，因此 Estimator 采用"比例假设"（proportional assumption）估算剩余资源使用量，而非精确预测模型。

## 五、实验结果

**实验环境**：Microsoft Azure VM（16 vCPU、64GB DRAM、160GB SSD、Ubuntu 20.04）

**Benchmark**：16 个真实世界应用资源过载案例，覆盖同步资源（8 例）、线程池（3 例）、内存（3 例）、系统资源 CPU/IO（2 例）

### 主要性能对比（所有 16 个案例平均）

| 系统 | 归一化吞吐 | 归一化 p99 延迟 | 平均丢弃率 |
|------|-----------|----------------|---------|
| **Atropos** | **96%** | **1.16×** | **<0.01%** |
| Protego | 50.7% | 1.88× | ~25% |
| pBox | 53.9% | — | — |
| DARC | 36.3% | — | — |
| PARTIES | 37.8% | — | — |

### SLO 达成率
在 20% 延迟增幅的 SLO 目标下，16 个案例中 14 个完全达成；剩余 2 个（case3: 23%，case12: 26%）因存在大量噪声请求、取消间隔限制影响恢复速度而轻微超限。

### 运行时开销
- 正常负载：吞吐下降均值 0.59%（最大 1.95%），p99 延迟增加均值 0.21%（最大 1.55%）
- 过载条件（仅追踪，不取消）：吞吐下降均值 7.09%（最大 8.12%），p99 延迟增加均值 8.12%（最大 16.14%）

## 六、批判性分析

**1. 手动标注负担被低估**

论文宣传集成仅需"22–74 行代码"，但实际上识别所有应用资源需要数天至一周的人工分析（MySQL 7天）。这一隐性成本在 paper 中被淡化，不适合作为"低集成开销"的主要论据。新应用的资源注释质量也会直接影响 Atropos 的有效性，但论文没有讨论注释不完整时的降级行为。

**2. 比例假设的适用边界模糊**

Estimator 用"当前已使用时间 × 剩余比例"估算未来资源占用，前提是资源使用量与工作量进度线性相关。对于 MySQL dump 查询（I/O bound）或 Elasticsearch 嵌套聚合（动态扩展内存占用）等非线性场景，这一假设可能严重失准。论文虽承认此问题，但没有量化误预测频率及其对取消决策的实际影响。

**3. 开销测量方法存在设计缺陷**

在过载场景下测量开销时，论文"禁用了取消动作"以隔离追踪开销。但真实过载下，取消动作本身（触发 `sql_kill`、处理取消回调等）会带来额外开销，且取消后的重试也会消耗资源。实际过载开销被低估。

**4. Apache 的 pthread_cancel 方案安全性存疑**

当 PHP 脚本执行时，Apache 内置取消机制无法终止脚本，Atropos 退而使用 `pthread_cancel`（系统级线程取消）。论文声称安全性由 Apache write log 保证，但 `pthread_cancel` 是异步信号，线程可能在任意点终止，包括持有内部 mutex 的时刻。这一声明过于乐观，实际部署风险未被充分讨论。

**5. 评估规模有限，泛化性存疑**

仅 6 个应用、16 个人工复现的过载案例——尽管这些都是真实 bug，但它们由作者精心挑选和复现，可能存在选择偏差。没有讨论"Atropos 识别错误元凶"的失败案例频率，也没有评估在混合过载场景（多种资源同时竞争）下的鲁棒性。

**6. 分布式场景完全缺失**

现代微服务架构中单个用户请求跨多个节点，Atropos 当前仅支持单节点。作者将分布式扩展留作 future work，但这恰恰是真实生产场景中最普遍的部署形态，限制了实际应用价值。

## 七、AI Infra / MLSys 视角

Atropos 的核心思想与 LLM 推理服务中的若干重要问题高度契合，有较强的迁移价值：

**可迁移的设计思路**：
- **KV Cache 作为 MEMORY 资源**：LLM 推理中 KV cache 是关键的共享内存资源，少量长序列请求（如 64K token 的文档摘要）可能垄断 KV cache，导致其他短请求无法分配到 page。Atropos 的"资源增益"估算（基于剩余生成 token 数预估未来 KV cache 占用）可以直接对应 vLLM 等系统中的 preemption 决策。
- **主动取消 vs. 抢占**：vLLM 当前的 preemption 策略（swap/recompute）是被动的——只有当 KV cache 不足时才触发，且通常基于 FIFO 或启发式。Atropos 式的"提前识别并主动取消垄断资源的请求"可以将过载恢复时间大幅缩短。
- **GPU compute queue 作为 QUEUE 资源**：连续 batch 推理中，超长请求占用 GPU 时间过久，阻塞其他请求出队。Atropos 的队列竞争度建模（等待时间/执行时间）可用于指导 continuous batching 中的请求中断决策。

**值得跟进的研究问题**：
1. 在 LLM 推理引擎（vLLM、SGLang）中，如何定义和实现"应用级资源"（KV cache pages、GPU SM 占用、decode batch slot）？现有 preemption 逻辑能否被 Atropos 式框架统一？
2. 多目标取消策略能否与 SLO-aware 调度（如 Orca、Sarathi）结合，在 TTFT 和 TBT 两类 SLO 目标之间做 Pareto 最优的取消决策？
3. 分布式推理（Pipeline Parallelism、Tensor Parallelism）中，"取消"信号如何跨节点/跨 stage 传播并保证一致性——这正是 Atropos 留下的 open problem。

---

## 八、总结

Atropos 提出了一种新颖的应用级资源过载控制思路：主动识别并取消垄断关键资源的"元凶"请求，而非无差别限流或丢弃受害者请求。通过统一的可取消任务抽象和多目标取消策略，Atropos 在六个大型真实应用（MySQL、PostgreSQL、Apache、Elasticsearch、Solr、etcd）的 16 个真实过载场景中，实现了 96% 吞吐保持、1.16× p99 延迟上界和低于 0.01% 的丢弃率，显著优于 Protego、pBox、DARC、PARTIES。主要局限在于：需要人工标注应用资源（成本不低）、比例假设在非线性负载下可能失准、以及目前仅支持单节点部署。
