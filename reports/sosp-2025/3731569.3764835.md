# Mitigating Application Resource Overload with Targeted Task Cancellation

## 论文基本信息
- **标题**: Mitigating Application Resource Overload with Targeted Task Cancellation
- **作者**: Yigong Hu, Zeyin Zhang, Yicheng Liu, Yile Gu, Shuangyu Lei, Baris Kasikci, and Peng Huang
- **会议**: SOSP 2025
- **Session**: Reliability and Performance
- **PDF**: 3731569.3764835.pdf

## 研究背景

现代软件系统在高负载下运行以最大化资源利用率，但当需求短时激增时，系统容易陷入 overload 状态，导致大量服务级别目标（SLO）违约。传统 overload 控制机制分为两大类：admission control（通过限流或降载来控制进入系统的请求）和 performance isolation（通过资源配额来隔离请求）。然而，这两类方法在应对 application-level resource overload 时效果有限——admission control 假设 overload 由总需求导致，缺乏对单个请求行为的洞察；performance isolation 采用静态资源划分，无法适应高度可变的工作负载，导致低资源利用率和高尾延迟。

Application resource（应用程序定义的资源，如数据库的 buffer pool、table lock 等）是应用程序内部维护的逻辑抽象，它们封装了底层系统资源（如内存、同步原语）来提供更高层次的功能。这类资源 overload 的特点是单个请求可能长时间持有资源并阻塞其他请求。例如，一个长运行的 scan query 可能持有 table lock 数百秒，阻塞后续所有写请求。问题的核心在于：一个请求对应用资源的影响取决于它与其他请求之间微妙且不可预测的交互，而不同请求访问资源的方式差异巨大。

## 要解决的问题

如何在 application resource overload 场景下，在维持高 SLO 达成率的同时，最小化请求丢弃数量？

具体来说：现有的 overload 控制机制依赖全局信号（如队列延迟）来调整准入请求量，但这些信号无法准确预测哪些请求会垄断关键资源。因此，admission control 往往不加区分地丢弃大量 victim 请求（在 overload 真正解决之前根本无法被服务的请求），而不是主动识别并取消造成资源争用的 culprit 请求（culprit request）。Performance isolation 机制虽然动态调整资源分配，但无法直接丢弃正在执行的请求，因此无法有效缓解已造成资源争用的 problematic requests 造成的 overload。

## 核心贡献

- 提出一种基于选择性运行时请求取消的 novel overload 控制机制，通过主动识别并取消垄断关键资源的 culprit 请求来缓解 application resource overload，而非拒绝 victim 请求。
- 开发 Atropos，一个通用的、resource-agnostic 的框架，通过 per-task 资源使用追踪、多目标取消策略和内置安全取消机制来选择性取消 culprit 请求。
- 在六种大规模应用（MySQL、Apache、PostgreSQL、Elasticsearch、Solr、etcd）中实现 Atropos，涵盖三种编程语言（C/C++、Java、Go），并在 16 个真实世界 application resource overload 场景中进行评估。
- Atropos 相比 state-of-the-art 解决方案显著提升性能：维持 96% 的基线吞吐量，p99 尾延迟控制在非 overload 情况的 1.16 倍以内，而请求丢弃率低于 0.01%。

## 主要研究方法

**核心观察**：大多数现代应用程序（76% 在研究的 151 个流行开源项目中）已经实现了自定义取消逻辑来安全终止正在执行的请求。应用程序通过暴露 cancellation initiator 函数，允许开发者在 checkpoint 处检查取消标志、清理关键内部状态并保留不变量后再终止请求。

**Per-task 资源使用追踪**：Atropos 将应用程序的所有活动（包括用户请求和后台任务）分组为可取消任务（cancellable task），每个任务关联唯一的 task ID。通过在资源使用关键点插入 `getResource`、`freeResource` 和 `slowByResource` API，追踪每任务对三类 application resources 的使用：synchronization resources（受同步原语保护的资源）、memory resources（应用管理的内存池或缓存）、queue resources（应用管理的任务队列）。

**Contention Level 和 Resource Gain 指标**：
- **Contention Level**：per-resource 指标，量化资源的争用严重程度。对于 synchronization resource，定义为请求等待获取资源的时间占总执行时间的比例；对于 memory resource，定义为平均 eviction ratio（evictions / gets）；对于 queue resource，定义为在队列中等待时间与执行时间的比例。为使不同类型资源的 contention level 可比较，Atropos 将其归一化为请求在给定资源上损失的执行时间比例。
- **Resource Gain**：per-task 指标，估计取消任务后可释放多少资源。定义为当前资源持有量乘以剩余 workload 比例（即 `1 - Progress`），其中 Progress 通过 GetNext 模型估算（已处理行数 / 预期总行数）。

**Multi-objective Cancellation Policy**：采用非支配集（non-dominated set）来识别在所有资源上 cancellation gain 最高的任务，然后通过 scalarization 聚合各资源的 weighted gain 来选择最优取消目标。使用 contention level 作为权重，反映"在高拥塞资源上减少争用带来更大性能提升"的直觉。

## 设计与实现

Atropos 包含四个核心组件：

1. **Per-task Resource Usage Tracking**：Task Manager 为每个可取消任务分配唯一 task ID 并维护映射关系。Per-task Resource Usage Tracing 通过轻量级 API 在资源使用关键点注入追踪逻辑，并在检测到潜在 overload 时动态切换到高精度时间戳记录。

2. **Overload Detection**：使用与 Breakwater 类似的方法，持续监控应用吞吐量和延迟。当延迟超过 SLO 但吞吐量保持平稳，表明可能发生了资源 overload。检测到后通知 Atropos Estimator 验证具体瓶颈资源。

3. **Resource Overload Estimation**：Estimator 计算每种资源的 contention level 和每任务-资源对的 resource gain。对于 synchronization resource，gain 定义为未来资源持有时间；对于 memory resource，gain 定义为当前内存使用量乘以剩余进度比例；对于 queue resource，gain 定义为任务在队列中的预期等待时间。

4. **Multi-objective Policy Engine**：首先通过 Algorithm 1 识别非支配任务集（不被任何其他任务在所有资源上严格优于），然后计算每个候选任务的 total weighted gain，选择最大值对应的任务进行取消。

5. **Task Cancellation Handling**：Atropos 静态地为每个可取消任务注入 `setCancelAction` 回调函数，该函数调用应用程序的内置取消机制。对于没有内置取消支持的应用程序，提供可选的库级取消标志（使用 pthread_cancel），但默认禁用以避免不安全终止。

**公平性保障**：每个任务最多被取消一次；重新执行的任务被标记为 non-cancellable，防止饥饿；对于后台任务，设置最大等待阈值并保证重执行。

**实现**：Atropos 以 C/C++、Java 和 Go 三种语言实现，分别提供 user-space 库、CancellableTask 类和 Go runtime 集成。核心实现约 2,106-4,002 行代码。集成工作主要是在应用资源使用关键点注入 Atropos 的 API（平均约 50-74 行代码），而识别所有 application resources 本身是最耗时的步骤。

## 主要实验结果

**16 个真实世界 overload 场景的评估**：

- **Throughput**：Atropos 平均维持 96% 的基线吞吐量，显著优于 Protego（50.7%）、pBox（53.9%）、DARC（36.3%）和 PARTIES（37.8%）。
- **Tail Latency**：Atropos 平均将 p99 尾延迟控制在非 overload 情况的 1.16 倍；Protego 平均 1.88 倍，但无法处理非 synchronization 类型的资源争用；pBox、DARC 和 PARTIES 在约束尾延迟方面效果有限。
- **Drop Rate**：Atropos 平均请求丢弃率低于 0.01%，而 Protego 由于必须丢弃 victim 请求，丢弃率约 25%。

**Multi-objective Policy 有效性**：在 16 个案例中，multi-objective policy 在 8 个案例中一致优于基于单一最拥塞资源的启发式策略，在 6 个案例中优于使用当前资源使用量而非预测未来 gain 的策略。

**Overhead**：Atropos 在正常负载下引入平均 0.59% 的吞吐量降低（最大 1.95%）和 0.21% 的 p99 延迟增加（最大 1.55%）；在 overload 条件下吞吐量降低 7.09%（最大 8.12%），p99 延迟增加 8.12%（最大 16.14%）。

## 潜在问题 / 局限性

**1. 依赖应用程序内置取消支持**：虽然研究显示 76% 的流行应用已有取消逻辑，但剩余 24% 和不支持用 initiator 的应用无法安全使用 Atropos。系统级取消（pthread_cancel）虽然提供了后备方案，但被明确标记为"potentially unsafe"且仅在脚本运行在应用核心逻辑外部时才安全（如 Apache PHP 脚本场景），这限制了适用范围的普遍性。

**2. Progress 估算的强假设**：Resource gain 的计算依赖"任务剩余资源需求与其剩余 workload 成比例"这一假设。论文承认这是一个 strong assumption，且指出对于没有 rows_examined 和 estimatedRows 等内部指标的应用，准确的进度估算面临挑战。虽然声称即使预测不准确后果只是取消一个 suboptimal request，但长期反复取消错误请求可能导致饥饿和 SLO 违约。

**3. Single-node 限制**：Atropos 主要为单节点应用设计。虽然论文提到分布式扩展（将 child task 与 root request 关联并传播取消信号），但承认这是 future work，目前不支持分布式系统中的取消传播和故障处理（如崩溃、超时、网络分区）。

**4. 过度保守的 unsafe region 检测**：编译器自动插桩的 unsafe region 存在假阳性（论文在实验中禁用了 Redis 的 unsafe region 来提高恢复成功率），这表明当前静态分析工具在精确识别不一致状态边界方面仍有不足。对于需要更强正确性保证的应用，需要额外启用 cross-check validation 机制。

**5. 评估的覆盖范围**：实验在 Azure 虚拟机上进行，可能无法完全反映物理机环境下的性能特征；16 个真实世界场景虽然涵盖了多种资源类型，但每个应用仅覆盖 1-4 个案例，统计意义有限。

## 未来工作

- **分布式扩展**：将 Atropos 的取消机制扩展到分布式系统，支持跨节点传播取消信号和处理分布式故障。
- **更精确的 progress 估算**：探索不依赖应用程序内部指标的资源使用预测方法。
- **改进的静态分析**：提升 unsafe region 自动识别精度，减少假阳性。
- **与在线学习结合**：根据工作负载动态调整取消策略参数。

## 个人评注

Atropos 的核心贡献在于识别了 application resource overload 这一被忽视但实际广泛存在的问题，并巧妙地利用了应用程序已有的取消支持基础设施。这种"hardware/software co-design"式的思路——不重新发明轮子，而是接入现有机制——是工程上非常实用的做法。

Multi-objective cancellation policy 从多目标优化的角度建模取消决策，并引入 contention level 作为权重，是一个有理论支撑的设计。但实际效果（在 16 个案例中约一半有明显优势）表明，该策略的收益取决于资源的相互依赖程度，对于仅涉及单一资源的 overload 场景，简化策略可能同样有效。

实验中 Atropos 的性能优势明显，尤其在 drop rate 方面。但值得注意的是，Protego 的设计目标本身就是降低尾延迟而非最大化吞吐量，两者存在设计目标的差异。更公平的比较应该控制设计目标一致。此外，论文声称 Atropos 在"16 个真实世界 application resource overload 场景"中有效，但这些场景实际上是人工构造的（"we reproduced"），而非真实的生产故障，这可能高估了方法在真实故障场景下的有效性。

总体而言，这是一篇工程扎实、实用性强的论文。其价值不仅在于 Atropos 本身，更在于揭示了 application-level resource contention 这一普遍但被忽视的问题，以及通过 selective cancellation 来解决 overload 的新思路。
