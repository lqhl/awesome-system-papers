# Tock: From Research to Securing 10 Million Computers

## 一、背景

嵌入式系统无处不在，从传感器网络到数据中心的硬件信任根（root-of-trust）芯片，再到笔记本电脑和汽车系统。这些系统通常运行在资源极度受限的微控制器上（~100kB RAM，无虚拟内存），传统嵌入式 OS（如 FreeRTOS、NuttX、Zephyr）采用单一保护域设计，所有组件共享内存空间，缺乏隔离机制。一个有 bug 的驱动或恶意应用可以破坏整个系统。

与此同时，Rust 语言的兴起为系统软件提供了内存安全和类型安全的可能性。Tock 是最早完全用 Rust 编写的 OS 内核之一，始于 2015 年，最初面向城市传感器网络平台。经过十年发展，Tock 已部署在数千万台设备上，包括 Google 的 OpenSK（FIDO 2FA 设备）、Ti50（Chromebook 硬件信任根）、数据中心服务器的安全协处理器，以及汽车和航天系统。

---

## 二、要解决的问题

1. **嵌入式系统缺乏隔离**：传统嵌入式 OS 所有组件（驱动、应用）运行在同一保护域，无法防止组件间的相互干扰。在安全关键场景（如硬件信任根）中，这是不可接受的。

2. **资源受限下的多程序执行**：在仅有几十 KB RAM、无虚拟内存的微控制器上，需要安全地运行多个相互不信任的应用，同时避免动态内存分配带来的资源耗尽风险。

3. **用 Rust 构建 OS 的工程挑战**：Rust 的所有权模型和借用检查器与传统 OS 设计模式（循环引用、异步回调、与非 Rust 用户态的交互）存在根本性冲突，早期实现中存在 unsoundness。

4. **学术研究系统向生产部署的过渡**：如何在保持学术研究平台特性的同时，满足工业用户对安全性、可靠性和功能完整性的需求。

---

## 三、洞察与设计

**关键洞察**：Rust 的所有权类型系统不仅可以提供内存安全，还可以作为一种零运行时开销的隔离机制——通过编译期类型检查来强制执行内核扩展的权限边界，从而在没有虚拟内存的微控制器上实现细粒度的组件隔离。

基于这一洞察，Tock 的核心设计包含四个层次：

1. **Capsules（内核扩展）**：使用 Rust 类型系统隔离的半可信内核模块。禁止使用 `unsafe` 代码，只能通过显式的安全 API 访问硬件和进程内存。编译期强制隔离，零运行时开销。

2. **硬件隔离的用户态进程**：通过 MPU（Memory Protection Unit）实现硬件级隔离，支持抢占式调度，可运行任意语言（C、Rust 等）编写的应用。进程间互不信任。

3. **无堆内核 + Grants 机制**：内核不使用全局堆，所有动态分配放在进程的内存区域中（通过 Grants），确保一个进程不能耗尽其他进程的资源。

4. **全异步架构**：从内核到系统调用接口全部采用异步设计（split-phase asynchrony），支持单栈执行多个并发操作，最大化低功耗睡眠时间。

## 四、实现细节

### Interior Mutability 解决循环引用

OS 组件间天然存在循环依赖（如文件系统 ↔ 存储驱动），Rust 的所有权模型不允许循环的可变引用。Tock 选择使用 interior mutability（`Cell`/`RefCell`），允许通过共享不可变引用修改内部状态，代价是部分操作需要额外的运行时检查。

### 系统调用 ABI 重设计（Tock v2.0）

原始 `allow`/`subscribe` 系统调用将用户态缓冲区/回调的所有权直接交给 capsule，导致 capsule 可以无限持有用户态引用，破坏 Rust 安全保证。v2.0 引入 **swapping 语义**：每次调用返回之前共享的缓冲区/回调，由内核（而非 capsule）管理这些资源。Capsule 只能通过临时的闭包引用访问，无法获取所有权。这一改动导致核心内核循环完全重写。

### SubSlice 缓冲区管理

设计 `SubSlice` 类型解决异步 API 中 `'static` 生命周期缓冲区的子集传递问题：允许各层独立操作缓冲区子集，同时保留恢复完整缓冲区的能力。结合 const 泛型参数，在编译期验证缓冲区大小需求。

### MMIO 抽象

通过 Rust 宏系统提供 DSL，将硬件数据手册中的 MMIO 规范直接映射为类型安全的数据结构，每个寄存器地址包装为唯一类型，自动生成位移操作代码。

### Capabilities 机制

使用零大小的 marker trait 实现编译期能力系统：敏感 API（如终止进程）需要传入特定 capability 类型作为参数，只有受信任的平台初始化代码能创建这些 capability。运行时零开销。

### 处理 unsafe 边界的 soundness 问题

- 用户态可通过两次 `allow` 共享重叠缓冲区，破坏 Rust 的 aliasing XOR mutability 不变量。解决方案：将共享缓冲区类型从 `&mut [u8]` 改为 `&[Cell<u8>]`，放松编译器对内容稳定性的假设。
- 零长度缓冲区的空指针问题触发 niche filling 优化导致 unsoundness。解决方案：运行时检查 + 使用非空人工指针。

### 代码规模

经过十年发展，内核代码量显著增长，但 `unsafe` 代码块数量保持稳定（约 200 个 unsafe 块 vs 超过 10 万行内核代码）。

## 五、实验结果

本文是一篇经验报告（experience paper），没有传统的性能基准实验。主要的量化数据包括：

| 指标 | 数据 |
|------|------|
| 项目历史 | 10 年（2015-2025） |
| 活跃设备数 | 数千万台 |
| 贡献者 | 至少 400 人 |
| 主要部署 | Google OpenSK (2FA), Ti50 (Chromebook), 数据中心 RoT, 汽车/航天系统 |
| unsafe 代码增长 | 内核代码量增长 10 倍以上，unsafe 块数量基本不变 |
| 主要版本 | Tock 1.0 → Tock 2.0（系统调用 ABI 完全重设计） |
| 分支/放弃案例 | Oxide 放弃 Tock 转而开发 Hubris；Ti50 早期 fork 后逐渐脱离主线 |

## 六、批判性分析

1. **缺乏定量性能评估**：作为一个部署在数千万设备上的 OS，论文没有提供任何性能数据——没有系统调用延迟、上下文切换开销、内存占用对比、编译时间等指标。读者无法判断 Tock 的类型安全隔离在实践中的代价有多大。

2. **"数千万设备"的含义模糊**：标题声称"Securing 10 Million Computers"，但论文未清楚说明这些设备中有多少运行主线 Tock vs. 已经深度 fork 的版本（如 Ti50）。如果大部分部署来自已脱离主线的 fork，那么这个数字对于评估 Tock 项目本身的成功有多大意义？

3. **异步设计的代价被低估**：论文承认 Oxide 因异步复杂性放弃了 Tock，Ti50 因此 fork，但将此描述为"不同应用场景的权衡"。实际上，两个最重要的早期采纳者都因为同一个设计决策产生了重大分歧，这说明异步设计可能是一个系统性的架构问题，而非简单的场景不匹配。

4. **学术管理模式的挑战被美化**：论文在 Section 6 将学术主导描述为主要是优势（长期视野、免费劳动力），但同时承认硬件测试框架拖了"数年"才完成、平台可能"数周到数月"处于不可用状态。对于安全关键系统，这种维护水平是否可接受？

5. **外部依赖问题缺乏解决方案**：论文指出第三方库的信任问题是"open research problem"，但 Tock 已在生产环境中为密码学库做了例外。这种逐案例外的方式是否可持续？论文没有讨论供应链攻击的具体威胁模型。

6. **与同类系统缺乏对比**：论文没有与 Hubris、Zephyr、seL4 等系统在安全性、性能、易用性上做任何定量或定性的系统性对比。

---

## 七、总结

Tock 是一个历经十年、从学术研究走向大规模工业部署的嵌入式安全操作系统。其核心贡献在于：(1) 利用 Rust 类型系统实现零开销的内核扩展隔离（capsules）；(2) 无堆内核 + Grants 机制实现资源隔离；(3) 积累了大量用 Rust 构建 OS 的实践经验，包括 interior mutability、系统调用 ABI 的 soundness 修复、unsafe 边界管理等。论文适合对 Rust OS 开发、嵌入式安全、以及学术开源项目管理感兴趣的读者。主要局限在于异步架构的复杂性导致重要用户流失，以及作为经验报告缺乏定量评估数据。
