## 一、背景

Tock 是一个用 Rust 编写的嵌入式操作系统，起源于 2015 年前后的学术研究项目。其最初目标是在资源极度受限的微控制器（约 100 KB RAM、不足 1 MB 非易失存储）上实现安全的多道程序设计。彼时嵌入式 OS 领域（FreeRTOS、Zephyr 等）普遍采用 C 语言编写，所有组件共享同一地址空间，驱动程序可任意访问系统内存，安全隔离几乎为零。

Rust 语言的出现，以及 ARM Cortex-M 系列 MCU 对硬件内存保护（MPU）的逐步支持，使得构建一个兼具隔离性与极低开销的嵌入式 OS 成为可能。Tock 是最早将 Rust 系统性地应用于 OS 内核的项目之一，早于 Linux 内核引入 Rust 支持（2022 年）数年。

---

## 二、要解决的问题

1. **嵌入式 OS 缺乏隔离**：传统嵌入式框架（FreeRTOS/NuttX/Zephyr）无驱动隔离，一个 bug 可导致整个系统崩溃或被攻陷；
2. **多道程序设计资源开销**：在 64 KB 级别的 MCU 上实现多进程隔离，硬件 MMU 不可用，必须依赖 MPU 或语言级隔离；
3. **Rust 语言与 OS 设计的结构性冲突**：Rust 的所有权/借用模型与 OS 常见的循环引用、异步回调、共享内存等模式存在根本性张力；
4. **学术 OS 的可持续开源生态**：如何在学术优先（发表导向）与产业需求（产品时间线）之间维持一个活跃的开源社区；
5. **Sound Rust userspace 的 ABI 设计**：原始系统调用接口语义与 Rust 内存安全不兼容，导致 Rust userspace 库存在 unsound 问题。

## 三、核心设计

Tock 的核心架构分为四类组件（见论文 Figure 2）：

**1. Capsules（内核扩展）**
- 用 Rust safe 代码实现的内核模块，编译时禁止使用 `unsafe`；
- 依赖 Rust 类型系统实现隔离，编译期强制，几乎零运行时开销；
- 仅能访问自身状态，通过显式 safe API 与系统其余部分交互；
- 可信级别：仅被信任保证活跃性（不 panic/busy-wait），不被信任访问控制。

**2. 硬件隔离的 Userspace Processes**
- 使用 MPU 硬件隔离，支持 C/Lua 等任意语言编写的应用；
- 通过狭窄系统调用接口与内核交互；
- 进程间相互不信任，不可互相抢占资源。

**3. 无堆（Heapless）内核 + Grants**
- 内核不使用全局堆，所有动态分配置于对应进程的内存区域中；
- Grants 机制：进程相关内核状态从进程内存分配，进程退出时自动回收，防止应用耗尽共享内核资源。

**4. 全异步架构（Split-phase Asynchrony）**
- 参考 TinyOS 的 split-phase 模式，整个内核事件驱动、单栈；
- 系统调用接口也完全异步：subscribe（注册回调）→ command（触发操作）→ yield（等待完成）；
- 内核利用 Rust `interior mutability` 处理组件间循环引用。

**Tock v2.0 的关键重设计**：将 `allow`/`subscribe` 系统调用改为 **swapping 语义**——调用时返回旧值，确保 userspace 始终持有引用的唯一所有权，从根本上解决 Rust userspace soundness 问题。

## 四、实现细节

**Interior Mutability 的取舍**：内核组件间使用 `Cell`/`RefCell`（interior mutability）允许循环引用，绕过 Rust 独占可变引用限制。代价是部分状态修改引入运行时检查，且需开发者手动保证可重入安全。

**SubSlice 抽象**：为支持异步操作中的 buffer 子集传递，引入 `SubSlice` 类型，允许各层以"仿佛 buffer 只有有效数据长度"的视角操作，同时保留对完整 buffer 的所有权，操作完成后可完整返还。

**MMIO DSL**：使用 Rust 宏系统提供 domain-specific language，将硬件 datasheet 中的内存映射寄存器规格直接编码为类型，自动生成位操作代码，避免手写位移代码的错误。

**编译时 Capabilities**：用零大小类型（Zero-Sized Types）实现特权 API 访问控制——`ProcessMgmtCap` 等 marker trait 只能在平台初始化时创建，传入需要特权的驱动，无法在 capsule 中凭空获得，编译期强制。

**编译时组合验证**：用 Rust const generics 和 trait 约束表达驱动层间的能力需求（如 SPI active polarity），驱动栈配置错误在编译期报类型错误。

**Unsafe 的管控**：内核核心代码量十年间增长约 10 倍，但 `unsafe` block 数量保持平稳（约 200 个），通过 crate 级别禁止 `unsafe` 来划定安全边界。

## 五、实验结果

本文是一篇**经验报告（experience paper）**，无传统性能基准测试，主要通过定性分析和量化统计描述 Tock 的演进。

| 指标 | 数据 |
|------|------|
| 项目起始时间 | 2015 年 |
| 活跃部署规模 | 数千万设备（tens of millions） |
| 代码贡献者 | 400+ 人 |
| 内核代码行数（LOC） | 约 10,000 行（2024 年，见 Figure 5） |
| unsafe blocks 数量 | 约 200 个（十年基本稳定） |
| 主要部署场景 | Google OpenSK（FIDO 2FA）、Chromebook Ti50（hardware root of trust）、数据中心服务器安全协处理器、汽车/航天系统 |
| 主要支持架构 | ARM Cortex-M（原始）、RISC-V、x86（实验性）|

**重要演进里程碑**（Figure 1）：
- 2016 年：Signpost 城市传感器网络部署
- 2019 年：Google OpenSK 发布
- 2021 年：Tock v2.0（重写系统调用 ABI）
- 2023 年：Tock 进入 Chromebook 量产（Ti50/Pluton）
- 2025 年：形式化验证隔离（TickTock，SOSP '25 另一篇论文）

## 六、批判性分析

**1. "数千万台设备"的说法缺乏量化支撑**
论文标题和摘要反复提及"10 million computers"，但正文从未解释这一数字的来源、统计口径（活跃用户？累计出货？）。Chromebook 出货量确实大，但 Tock 在每台 Chromebook 上的角色仅是 security co-processor（Ti50）固件，而非主 OS。这个数字有一定标题党嫌疑。

**2. 对失败案例的处理过于轻描淡写**
Oxide（Hubris 的前身）和 Ti50 两个重要采用者均在几个月内分叉或放弃了 Tock。论文将其归因于异步 API 的"不匹配"，但未深入分析为何 Tock 的设计哲学与生产级 root-of-trust 场景存在如此根本的矛盾。Ti50 至今仍维护独立分支，这对"open source community"叙事有一定削弱。

**3. 工程积压问题被过于乐观地呈现**
Section 6.1 承认多个"已知问题"（hardware-in-the-loop 测试缺失、外部依赖信任问题、异步 API 复杂度）长期悬而未决，最终需要外包给全职工程师或至今仍是"open research problem"。这说明学术主导模式在工程质量上存在系统性短板，而论文将其定性为"挑战"而非根本限制，略显回避。

**4. Rust 类型系统的局限被坦诚但未充分展开**
Section 5.4 指出 Rust 对逻辑正确性无能为力（timer 虚拟化、内存保护子系统均出现过 subtle bug），需要额外形式化验证。这是重要的 insight，但只用了一段话带过，对"为什么 Rust 对这类 bug 无效"的机制分析不够深入。

**5. 与同类系统的横向比较不足**
论文提到了 Theseus（全 Rust OS）、RedLeaf 等系统，但几乎没有做直接比较（性能、代码规模、unsafe 比例、安全事件记录）。以"经验报告"为由回避系统性比较，削弱了结论的说服力。

---

## 七、总结

Tock 是一个历时十年、从学术研究演进为千万级量产部署的嵌入式 OS 成功案例。其核心贡献在于：(1) 系统性地将 Rust 类型系统用于嵌入式内核隔离，无需 MMU 即可实现编译期驱动隔离；(2) 通过 Grants、SubSlice、Capabilities 等类型级抽象解决了嵌入式 OS 的资源安全和 API 正确性问题；(3) 以 swapping 语义重构系统调用 ABI，解决了 Rust userspace soundness 问题。主要局限在于全异步架构与顺序状态机应用模式的阻抗失配，以及学术主导模式在工程持续性上的先天不足。本文对希望在嵌入式或安全敏感场景中使用 Rust 构建系统软件的研究者和工程师有重要参考价值。
