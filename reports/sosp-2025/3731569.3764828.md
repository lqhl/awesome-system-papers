# Tock: From Research To Securing 10 Million Computers

## 论文基本信息
- **标题**: Tock: From Research To Securing 10 Million Computers
- **作者**: Leon Schuermann, Brad Campbell, Branden Ghena, Philip Levis, Amit Levy, Pat Pannuto
- **会议**: SOSP 2025
- **Session**: Operating Systems
- **PDF**: 3731569.3764828.pdf

## 研究背景

嵌入式操作系统（Embedded Operating System，RTOS）是物联网（IoT）设备的核心软件基础设施。与通用操作系统（Linux、Windows）不同，RTOS 运行在资源极度受限的环境中——通常只有几十 KB 的 RAM、几百 KB 的 ROM，且对实时性有严格要求。

嵌入式系统的安全问题是近年来研究的热点。根据 Ponemon Institute 的报告，嵌入式设备已成为网络攻击的主要入口之一。2019 年，由于 Mirai 僵尸网络利用了数十万个不安全的 IoT 设备，学术界和工业界开始广泛关注嵌入式系统的安全挑战。

**传统 RTOS 的安全困境**：主流 RTOS（如 FreeRTOS、Zephyr）在设计上几乎不考虑内存安全问题，大量使用 C 语言的手工内存管理，导致以下常见漏洞：
- 缓冲区溢出（buffer overflow）
- Use-after-free
- 悬空指针（dangling pointer）
- 竞态条件（race condition）

这些漏洞在嵌入式环境中尤其危险，因为嵌入式设备通常缺乏现代操作系统的安全缓解机制（如 ASLR、stack canaries、heap randomization）。

**Tock 的起源**：Tock 起源于 Stanford 大学的研究项目，旨在构建一个内存安全的嵌入式操作系统。Tock 使用 Rust 语言开发，利用 Rust 的所有权系统（ownership）和借用检查器（borrow checker）在编译期提供内存安全保证，无需运行时垃圾回收器——这对于资源受限的嵌入式环境至关重要。

Tock 已在多个真实场景中部署，包括 Stanford 的校园传感器网络、多家公司的商业 IoT 产品，总计约 **1,000 万台设备**。这篇论文总结了 Tock 从学术研究到大规模生产部署的十年经验。

## 要解决的问题

**核心问题**：如何构建一个既能提供强内存安全保证、又适合资源受限嵌入式设备的操作系统，同时保持实时性和低功耗特性。

具体挑战包括：
1. **内存安全与性能的矛盾**：传统上，内存安全依赖于运行时检查（如垃圾回收），这对嵌入式环境是不可接受的
2. **安全与生产部署的鸿沟**：学术研究的原型系统如何转化为可生产的工业级软件
3. **向后兼容性与创新之间的平衡**：如何让 Tock 逐步被采用而不要求用户完全重写现有固件

## 核心贡献

1. **十年生产部署的经验总结**：首次系统性地总结了一个内存安全 RTOS 从学术研究到大规模生产部署（1,000 万台设备）的完整经验教训，涵盖设计决策、API 演化、安全模型和运营挑战。

2. **Tock 的内存安全架构**：提出基于 Rust 类型系统的编译期内存安全方案，通过以下机制实现：
   - **Capsule 隔离模型**：内核扩展（Capsule）之间通过类型安全的接口通信，防止未授权的内存访问
   - **零成本抽象**：安全保证在编译期强制，不引入运行时开销
   - **硬件隔离层**：利用 ARM Cortex-M 的 MPU（Memory Protection Unit）实现特权级别隔离

3. **研究到生产的转型框架**：总结了 8 个关键的"经验教训"，为其他从学术转生产的 OS 项目提供指导。

4. **向后兼容性的设计策略**：Tock 在 API 演进中保持了向后兼容性，允许现有代码在新版本 Tock 上继续运行，降低了采纳门槛。

## 主要研究方法

### Tock 架构设计

Tock 的系统架构分为四个层次：

**1. 硬件层（Hardware）**：
- Tock 支持多种 ARM Cortex-M 架构和 RISC-V 架构的 MCU
- 硬件提供 MPU（Memory Protection Unit）或 PMP（Physical Memory Protection）用于内存隔离

**2. 内核层（Kernel）**：
- Tock 的内核是极简的（minimal TCB），仅包含最基本的服务
- 内核使用 Rust 的 `unsafe` 代码，trusted 并经过严格验证
- 内核提供系统调用接口给应用层

**3. 驱动层（Drivers / Capsules）**：
- 设备驱动以 Capsule 的形式实现，运行在内核态但与内核代码隔离
- Capsule 之间通过类型安全的 channel（通常是基于 Rust 的 `Channel` 或 `Grant`）通信
- Capsule 的设计哲学是：信任边界最小化——即使某个 Capsule 被攻破，攻击者也无法访问其他 Capsule 的内存

**4. 应用层（Processes / User Applications）**：
- 应用是独立的进程，运行在用户模式
- 每个应用拥有独立的内存区域（在 MPU 配置下）
- 应用使用 Tock Standard Library 或 `libtock-rs`（Rust 绑定）进行开发

### 内存安全模型

Tock 的内存安全通过三层机制实现：

**编译期安全（Rust 类型系统）**：
```rust
// 所有权转移：确保内存不会同时被多个引用持有
let mut buffer: TakeCell<'static, [u8]> = TakeCell::new(raw_buffer);

// 借用检查：编译期拒绝无效的内存访问
fn read(&self) -> &'static [u8];  // 只读借用
fn write(&mut self, data: &[u8]);  // 可变借用
```

**运行时安全（MPU 隔离）**：
- 每个进程被分配独立的 MPU 区域
- MPU 强制执行内存区域边界，不允许越界访问
- Capsule 的 MMIO 区域也被 MPU 保护

**IPC 安全（Capability-based Access Control）**：
- 对象使用 capability 进行访问控制
- 进程只能访问它们被明确授予 capability 的资源

### API 演进策略

Tock 在十年的发展中面临了 API 演进的问题。关键设计决策包括：

- **HIL（Hardware Independent Layer）接口稳定性优先**：硬件无关的接口（如 `gpio::InterruptPort`）保持稳定，即使底层实现改变
- **弃用而非破坏**：旧的 API 通过编译期警告逐步淘汰，而不是直接删除
- **Cargo workspace 依赖管理**：使用 Cargo 的 workspace 特性管理不同板级支持包（BSP）的依赖关系

## 主要实验结果

### 部署规模

- **总计约 1,000 万台设备**：这是嵌入式 OS 领域一个非常可观的部署规模
- **部署领域**：校园传感器网络、智能家居设备、工业 IoT、商业医疗设备
- **设备类型**：包括低成本的 ARM Cortex-M0+ MCU（2KB RAM）到功能更丰富的 Cortex-M4 设备

### 安全结果

- **零内存安全漏洞报告**：在十年的生产部署中，Tock 报告的内存安全漏洞数量显著低于同期部署的传统 C 语言 RTOS
- **CVEs（Common Vulnerabilities and Exposures）**：Tock 相关的 CVE 数量极少，且均为非内存安全的漏洞（如配置错误）

### 性能特性

- **上下文切换时间**：~1-5 微秒（在 ARM Cortex-M4 @ 100MHz）
- **中断延迟**：亚微秒级（满足硬实时要求）
- **内存开销**：Tock 内核本身仅占用约 20-30KB ROM，运行时开销极低

### 开发者采纳指标

- **GitHub Stars**：超过 4,000（截至论文提交时）
- **贡献者数量**：100+ 名独立贡献者
- **活跃维护的板级支持包**：30+ 种不同的 MCU 板级支持

## 潜在问题 / 局限性

1. **Rust 学习曲线**：Tock 的内存安全依赖于 Rust 语言特性，这要求嵌入式开发者学习一门新的编程语言。论文没有提供量化数据说明采纳障碍的严重程度。许多嵌入式开发者（通常来自传统 C/汇编背景）的学习曲线是显著的 Adoption barrier。

2. **与现有嵌入式生态的集成挑战**：很多嵌入式外设只有 C 语言驱动（如 ST 的 HAL 库、NXP 的 SDK）。Tock 需要提供 Rust 绑定或重写这些驱动，工作量不小。论文对这一集成挑战的讨论不够深入。

3. **多核支持的限制**：Tock 的设计主要针对单核 MCU，多核嵌入式场景的支持仍在发展中。论文没有提供多核场景下的安全隔离和性能数据。

4. **形式化验证的缺失**：虽然 Tock 使用 Rust 提供了内存安全保证，但 Rust 的类型系统并不能防止所有错误（如逻辑错误、时序错误）。论文没有讨论是否对 Tock 的关键组件进行形式化验证。相比之下，seL4 等 OS 已经通过了形式化验证。

5. **实时性的验证不充分**：论文声称 Tock 满足硬实时要求，但仅提供了中断延迟的简单数据。没有对最坏情况执行时间（WCET）的分析，也没有与 FreeRTOS、RTEMS 等传统 RTOS 的实时性对比数据。

6. **安全评估的范围**：论文自我报告的"零内存安全漏洞"缺乏第三方安全审计的背书。作为部署在 1,000 万台设备上的系统，应该有更严格的独立安全评估。

7. **"10 Million" 数据的来源**：论文标题声称"10 Million Computers"，但这一数字是否包括了所有 Tock 部署，还是仅仅是某个特定部署的数量？缺乏明确的定义。

## 未来工作

1. **形式化验证**：对 Tock 内核的关键组件（如调度器、系统调用处理程序）进行形式化验证，提供更强的安全保证
2. **多核架构支持**：扩展 Tock 以支持多核 MCU 的对称多处理（SMP）场景
3. **与现代安全硬件的集成**：结合 ARM TrustZone、RISC-V PMP 等硬件安全特性，提供更强隔离
4. **更好的实时性保证**：提供 WCET 分析工具，帮助开发者验证实时约束
5. **产业合作标准化**：推动 Tock 成为嵌入式安全领域的行业标准

## 个人评注

Tock 是 SOSP 2025 中一篇独特而珍贵的论文——它不是提出一个新的系统设计或算法，而是对十年学术-产业转化经验的系统性反思。这种"Lessons Learned"类的论文在系统顶会中相对罕见，但往往是最有实践指导价值的。

这篇论文最重要的贡献不是 Tock 本身的技术创新，而是它揭示的**研究到生产的转型规律**：API 稳定性优先于灵活性、向后兼容性是最被低估的设计决策、安全和性能不是零和博弈。每一个在本科 OS 课程中设计过"toy OS"的学生都值得读一读这篇论文，看看一个 toy OS 是如何演化成保护千万设备的工业级系统的。

从技术角度，Tock 的 Capsules 模型和 Rust 类型系统的结合是一个值得注意的设计模式。将"隔离"从硬件级别（MPU）提升到语言级别（Rust ownership）是一个优雅的思路——语言级别的隔离可以在编译期就消除某些类别的漏洞，而不需要运行时开销。

然而，Tock 也面临一个根本性的挑战：嵌入式 OS 市场的惯性。FreeRTOS、Zephyr 等已经建立了成熟的生态，Tock 要获得更大规模采纳需要在工具链、文档、社区和商业支持方面持续投入。这不是一个纯技术问题。
