# SAND: A New Programming Abstraction for Video-based Deep Learning

**作者**：Juncheol Ye, Seungkook Lee, Hwijoon Lim（KAIST）；Jihyuk Lee（Chung-Ang University）；Uitaek Hong（KAIST / Maum.AI）；Youngjin Kwon, Dongsu Han（KAIST）

## 一、背景

Video-based Deep Learning（VDL）已成为现代 AI 系统的核心基础设施。Sora、Runway Gen-2 等文生视频模型需要用数百万小时视频做训练；GPT-4V、Gemini 等多模态大模型大量依赖视频预训练；YouTube、TikTok 则用 VDL 做内容审核。VDL 任务覆盖视频分类、时序定位、自监督表征学习、视频生成等。

VDL 的核心挑战在于：视频数据被高度压缩存储（如 H.264、VP9），而训练时需要对每个 sample 执行解码 → 帧选择 → 数据增强的完整预处理流水线。每个 epoch 都必须重新执行这一流程，且帧选择是随机的，导致跨 epoch 几乎没有可复用的数据。

---

## 二、要解决的问题

**1. 预处理流水线极其复杂，开发负担沉重**

Meta 的 SlowFast 项目，仅预处理代码就超过 2200 行，是模型训练代码（700 行）的 3 倍以上。开发者需要手动管理视频解码、帧选取、增强操作、不同数据源适配等所有细节。

**2. 预处理是训练速度的瓶颈，导致 GPU 严重闲置**

- CPU 预处理耗时是 GPU 训练的 2.2x–6.5x，GPU 利用率仅 12–35%
- GPU 硬件解码器（如 NVDEC/DALI）虽能减轻 CPU 压力，但仍比 GPU 训练慢 1.3x–2.7x，且占用 GPU 显存（1080p 下 batch size 从 24 降到 16，吞吐下降 9.1%），还多消耗 2.6x 能量

**3. 重复解码，跨任务完全无共享**

每个 epoch 开始时解码一次帧就立刻丢弃，不同 job（如超参搜索中并发的 4 个任务）各自独立解码同一份视频，解码量随任务数线性增加。PyTorch、TensorFlow 没有任何系统级机制在独立 job 间共享解码对象。

**4. 全量缓存不可行**

Kinetics-400 解码后需约 83.5 TB，而典型云实例只有 3 TB 本地存储，远程存储（EBS）带宽又远不足（所需 55.8 Gbps vs 实际 3–8x 不足）。

---

## 三、核心设计

SAND 的核心洞察：VDL 训练可以从**存储层抽象**中受益——把训练数据对象（压缩视频、解码帧、增强帧、训练 batch）当作一等公民，暴露给用户的是虚拟的 **view**，底层系统负责实际的对象管理和调度。

### View 抽象

View 是对预处理流水线中间产物的虚拟化封装。用户通过 POSIX API（`open`/`read`/`getxattr`/`close`）访问 view，路径格式为 `/{task}/{epoch}/{iteration}/view`。SAND 实现为 FUSE 文件系统，无缝集成到 Linux VFS，与 PyTorch DataLoader 等任意框架兼容。

SlowFast 从 2254 行预处理代码 → 仅 8 行。

### View Materialization Planning（视图物化规划）

**抽象视图依赖图（Abstract View Dependency Graph）**：每个任务从配置文件生成一个 DAG，节点是 view 类型（视频文件、解码帧、增强帧、训练 batch），边是操作（解码、增强）。

**具体对象依赖图（Concrete Object Dependency Graph）**：跨任务合并抽象图，形成 epoch-wise 的统一图。关键技术：
- **共享帧池（Shared Frame Pool）**：用所有任务帧步长的 GCD 构建统一采样网格，随机选帧，各任务从同一解码帧池采样 → 跨任务帧级别复用
- **共享增强窗口（Shared Augmentation Window）**：确定性操作（如 resize）自然可共享；随机裁剪则选取能覆盖所有任务最大裁剪需求的共享窗口，各任务在其中取子区域 → 空间变换后的帧可跨任务复用

### 存储约束下的对象图剪枝（Object Graph Pruning）

在存储预算内，贪心地决定缓存哪些中间层节点。从叶节点（训练 batch）出发，自底向上：若将某父节点替换其所有叶子能净节省存储且不增加过多重计算，则"折叠"该子树。候选父节点按子树边权重（重计算代价）从小到大排序，优先剪枝代价最小的。

### Priority-Based Materialization Scheduling（优先级调度）

两类线程池：
- **Demand-feeding 线程**：处理当前迭代必须的数据，优先级最高
- **Pre-materialization 线程**：提前生成未来 epoch 的训练对象

调度策略：以 deadline（距 GPU 需要该 batch 的剩余迭代数）逆比例分配优先级，最紧迫的任务最高优先。当内存使用超过 80% 时，切换为 Shortest Job First（SJF）策略，优先清理未处理边最少的线程，防止内存溢出。

## 四、实现细节

- **文件系统层**：基于 FUSE 库实现 SAND 文件系统，挂载在 Linux VFS 之上，拦截 POSIX 系统调用
- **视频解码器**：libvpx（VP8/VP9）、openh264（H.264），按文件扩展名选择
- **增强操作**：libtorch-cpu、OpenCV
- **帧/增强帧缓存**：uint8 类型，用 libpng 做无损压缩后持久化到磁盘
- **缓存驱逐**：存储使用率超过预算 75% 时触发，优先驱逐已用完且不再需要的对象，其次驱逐 deadline 最远的对象
- **具体对象依赖图生成**：对 300 帧视频，元数据图约几百节点（数十到百 KB），生成耗时毫秒级
- **故障恢复**：所有未剪枝对象持久化到文件系统，重启时从配置文件重建依赖树，扫描磁盘已有对象，仅重计算缺失部分
- **自定义增强扩展**：通过 RPC 服务机制支持外部进程中运行用户自定义增强函数，避免依赖冲突

## 五、实验结果

**实验平台**：GCP A2 实例，NVIDIA A100 GPU，12 vCPU/GPU，3 TB NVMe 本地 SSD

**模型与数据集**：
- SlowFast、MAE（视频动作识别，Kinetics-400，约 350 GB，250K 视频）
- HD-VILA（视频描述，100K 视频，720p）
- BasicVSR++（视频超分辨率，1080p YouTube 视频）

**基线**：on-demand CPU（PyAV + CPU PyTorch）、on-demand GPU（NVIDIA DALI）

| 场景 | vs CPU 训练时间 | vs GPU 训练时间 | vs CPU GPU 利用率 | vs GPU GPU 利用率 |
|------|--------------|--------------|-----------------|-----------------|
| 单任务训练 | **2.4x–5.6x** 加速 | **1.4x–1.7x** 加速 | 2.5x–5.7x | 1.4x–1.7x |
| 超参搜索（4x A100） | **2.9x–10.2x** 加速 | **1.4x–2.8x** 加速 | 3.1x–**12.3x** | 1.8x–**2.9x** |
| 多异构任务（SlowFast+MAE） | **5.3x–6.2x** 加速 | **1.7x–2.5x** 加速 | 5.4x–8.3x | 1.7x–2.5x |
| 分布式训练（远程存储） | **5.2x** 加速 | — | 5.2x | — |

**代码量对比**：

| 工程项目 | 官方仓库预处理 LoC | 使用 SAND 后 |
|---------|----------------|------------|
| SlowFast | 2254 行 | **8 行** |
| HD-VILA | 297 行 | **7 行** |

**其他关键数据**：
- 预处理操作量：在多任务场景下，解码操作减少 **50.3%**，随机裁剪增强减少 **33.1%**
- 无调度 vs 有优先级调度：后者平均迭代时间快 **42.6%**
- 图剪枝（1.5 TB 存储）：相比无剪枝方案，重计算开销降低 **25%**
- 能耗：vs CPU 基线节省 **42%–82%**；vs GPU 基线节省 **15%–38%**

## 六、批判性分析

**1. "Ideal" 基线定义模糊，夸大了对比收益**

作者以"所有训练 batch 已预存、无 GPU stall"定义 ideal case，并声称 SAND 接近 ideal。但这个 ideal 忽略了：预存所有 batch 本身就需要一次性大量 I/O 写入（相当于离线预处理）。作者虽然解释过为什么不能全量缓存（存储不够），但 ideal 基线本质上代表"无限存储 + 无限预计算时间"，把 SAND 衬托得接近上界，实际上 SAND 距 ideal 仍有 5%–14% 差距未被充分解释。

**2. 单任务场景中与 CPU 基线的对比存在误导性**

单任务下 SAND 比 CPU 快 2.4x–5.6x 的收益，在很大程度上来自于"预解码 + 缓存"这一直接优化，而非 view 抽象本身带来的架构创新。这与朴素缓存方案（naive caching）的区别仅在于：naive 只缓存解码帧（3 TB 存储只能覆盖 <4% 数据），而 SAND 通过图剪枝找到更优的缓存粒度。但作者没有系统评估在存储更充足的场景下 naive caching 与 SAND 的差距是否还显著。

**3. 随机性保持的验证过于单薄**

论文通过对比训练 loss 曲线来证明 SAND 的随机化策略不影响模型收敛（Figure 20），但只在单一模型（SlowFast）的一次训练中展示，且曲线仅覆盖约 3000 步。对于数据增强对最终精度高度敏感的自监督学习（MAE、BYOL），没有提供充分的统计显著性验证。

**4. 实验规模偏小，工业场景代表性不足**

最大实验仅用 2 个 A100 GPU（分布式场景），而实际 VDL 训练往往需要数十乃至数百 GPU。在大规模 DDP 场景下，SAND 的调度器和 FUSE 元数据操作是否会成为新的瓶颈，论文完全未讨论。此外，分布式实验只测了 SlowFast 一个模型，样本量不足。

**5. FUSE 的开销未被量化**

SAND 基于 FUSE 实现，而 FUSE 本身会引入额外的用户-内核态切换开销，特别是在高频小 I/O 场景下影响显著。论文中没有任何 FUSE overhead 的 profiling 数据，也没有讨论若将其实现为内核文件系统能带来多少额外收益。

**6. 超参搜索场景的优势存在特殊前提**

超参搜索中多任务共享同一数据集，这是 SAND 最有利的场景，物化规划收益最大（12.3x GPU 利用率提升）。但作者没有量化"数据集共享程度"对收益的敏感性——如果不同超参 job 使用不同数据采样策略，共享帧池能否依然有效？

## 七、AI Infra / MLSys 视角

本文直接针对 AI 系统基础设施，是 MLSys 核心研究方向之一，以下是可迁移的关键 insight：

**1. "存储层即计算层"的编程模型值得借鉴**

SAND 将预处理管线隐藏在文件系统接口之后，让应用层只感知到"批次数据"而不感知解码、增强细节。这与数据库的 view 抽象高度类似。这一思路可推广到其他需要复杂数据预处理的 AI 场景（如图神经网络的子图采样、点云处理），用统一的虚拟化文件系统接口封装特定领域的预处理。

**2. 跨 job 中间结果共享是 AutoML / HPO 系统的低垂果实**

超参搜索和多任务学习中，多个 job 往往共享同一数据集，但现有系统完全无此感知。SAND 证明了在系统层面协调帧共享可以带来 10x 级别的收益。这为 Ray Tune、Optuna 等 HPO 框架的数据层优化提供了直接的研究方向：何时共享、如何保持统计一致性是核心问题。

**3. DAG-based 预处理规划可与 LLM 推理服务结合**

LLM 推理中的多模态预处理（视频帧提取、OCR、音频转文字）同样涉及高成本的解码操作，且多个并发请求可能处理同一视频。SAND 的具体对象依赖图和剪枝策略可以为推理引擎的多模态预处理缓存提供方法论。

**4. Future Work 方向**

- **GPU 端的 view 抽象**：将 SAND 的调度机制与 GPU prefetch/streaming 结合，在 NVDEC 解码后直接将帧放入 pinned memory，避免 CPU→GPU 数据搬运
- **在线学习场景**：SAND 当前假设数据集相对静态，如何在持续变化的数据流（如直播内容）上维护 view materialization plan 是开放问题
- **与 Disaggregated Storage 架构集成**：论文提到远程存储（GCP Filestore）场景，但带宽受限。如何在 disaggregated 架构（存算分离）下做智能预取和局部缓存是值得研究的系统设计问题

---

## 八、总结

SAND 通过在文件系统层引入 view 编程抽象，将视频深度学习的预处理流水线系统化管理：对外提供 POSIX 兼容的虚拟化接口（大幅降低开发复杂度），对内实现跨任务/跨 epoch 的中间对象复用（解码操作减少 50%+）和存储感知的优先级调度（消除 GPU stall）。在单任务、超参搜索、多任务、分布式四类场景下均取得显著加速（最高 10.2x），GPU 利用率提升最高 12.3x。主要局限在于实验规模偏小（最多 2 GPU）、FUSE 开销未量化、且在极大规模或高度动态的数据场景下适用性尚待验证。
