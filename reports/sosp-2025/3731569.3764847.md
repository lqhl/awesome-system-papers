# SAND: A New Programming Abstraction for Video-based Deep Learning

**作者**：Juncheol Ye, Seungkook Lee, Hwijoon Lim (KAIST), Jihyuk Lee (Chung-Ang University), Uitaek Hong (KAIST / Maum.AI), Youngjin Kwon, Dongsu Han (KAIST)

**链接**：https://doi.org/10.1145/3731569.3764847

## 一、背景

视频深度学习（Video-based Deep Learning, VDL）正在成为 AI 领域的核心技术，驱动着从文本生成视频（Sora、Gen-2）、多模态基础模型（GPT-4V、Gemini）到大规模内容审核（YouTube、TikTok）等众多应用。VDL 训练的规模和数据量持续增长，但视频数据的高度压缩特性使得预处理成为训练流水线中的关键瓶颈。

视频预处理流水线涉及解码压缩视频流、帧采样、数据增强（裁剪、缩放、旋转等）等多个复杂步骤。以 Meta 的 SlowFast 项目为例，仅预处理代码就超过 2,200 行，是模型训练代码的两倍以上。在云环境中，CPU 预处理延迟是 GPU 训练时间的 2.2-6.5 倍，导致 GPU 利用率下降 65-88%。即使使用 GPU 硬件解码器（如 NVDEC），预处理时间仍超过训练时间 1.3-2.7 倍，且会占用宝贵的 GPU 显存。

---

## 二、要解决的问题

1. **预处理流水线过于复杂**：开发者需要手动管理视频解码、帧选择、数据增强等全部流程，涉及多种输入源（S3、GCP Filestore、流式数据）、帧采样策略和增强操作，工程负担极重。

2. **重复解码导致严重开销**：由于视频编解码的帧间依赖性，提取少量帧需要解码大量相关帧，且解码后的帧在每个 epoch 结束后被丢弃。跨 epoch 和跨任务（如超参搜索中的多个 job）的重复解码造成计算资源的线性增长。

3. **GPU 严重空闲**：CPU 预处理跟不上 GPU 训练速度，GPU 大量时间处于等待数据的 stall 状态。云实例每 GPU 仅 12 vCPU，远不够消除瓶颈。

4. **缓存全部帧不可行**：Kinetics-400 数据集解码后约 83.5 TB，远超云 GPU 实例的本地存储容量（典型 3 TB SSD），远程存储的带宽也不足以支撑训练所需的 55.8 Gbps 吞吐。

5. **现有框架缺乏系统级支持**：PyTorch、TensorFlow 等框架不提供跨 job 的解码对象共享机制，每个训练任务独立进行全部预处理。

## 三、洞察与设计

**关键洞察**：视频深度学习的预处理流水线可以被建模为存储级别的抽象——将训练数据对象（编码视频、解码帧、增强帧、训练 batch）作为 first-class entity，通过文件系统接口暴露。这样系统就能获得全局视角来识别跨任务、跨 epoch 的重复操作，并通过中间对象的缓存与复用来消除冗余计算。

基于这一洞察，SAND 的核心设计包含三层：

### View 抽象

借鉴数据库中 view 的概念，SAND 引入 view 作为编程抽象，将视频预处理的各阶段封装为虚拟化对象。用户通过 POSIX 文件系统接口（open/read/getxattr/close）访问 view，无需了解底层预处理细节。SAND 通过 Linux VFS（基于 FUSE 实现）暴露这些 view，路径格式为 `/{task_name}/{epoch}/{iteration}/view`。用户只需编写一个 YAML 配置文件描述整个预处理流水线（数据集路径、采样策略、增强操作），即可将数千行预处理代码缩减到不到 10 行。

### View Materialization Planning

SAND 将配置文件转换为 abstract view dependency graph（描述预处理步骤的依赖链），再基于多个任务的抽象图生成统一的 concrete object dependency graph 作为物化计划。关键在于跨任务的节点合并：当多个任务共享相同的视频数据集或帧采样时，SAND 合并对应节点以实现复用。为了在最大化复用的同时保持训练正确性，SAND 设计了两个协调机制：

- **Shared frame pool**：通过 GCD 统一所有任务的帧采样步长，在公共采样网格上随机选帧，确保时间随机性的同时实现帧级复用。
- **Shared augmentation window**：对于随机裁剪等空间随机操作，选择一个足够大的共享随机窗口，各任务在其中选取各自所需区域，保持空间随机性。

### Pre-Materialization 与调度

SAND 以 k 个 epoch 为单位构建物化计划，解码一次后缓存帧供多个 epoch 复用。通过 object graph pruning 算法在存储预算内选择性缓存——自底向上贪心地用父节点替换叶节点，优先保留重用频率高、重新计算成本大、存储开销适中的对象。运行时采用 priority-based materialization scheduling，动态分配线程优先级：数据喂入线程最高优先级，预物化线程按 deadline（距离被 GPU 需要的剩余迭代数）排序，内存压力大时切换为 SJF 策略。

## 四、实现细节

- **文件系统**：基于 FUSE 库实现 SAND 文件系统，拦截 POSIX 系统调用，提供 view 抽象。
- **解码器**：使用 libvpx 和 openh264 根据文件扩展名选择解码器。
- **增强操作**：使用 libtorch-cpu 和 OpenCV 执行各种增强操作。
- **缓存与压缩**：帧和增强帧以 uint8 类型表示，使用 libpng 进行无损压缩后缓存。物化对象优先保留在内存中（如果当前或近期迭代需要），否则存储到磁盘。
- **存储管理**：当存储使用超过 75% 阈值时，按优先级淘汰：(1) 已使用且未来不再需要的对象；(2) deadline 最远的对象。
- **容错**：所有未剪枝的对象持久化到文件系统。重启时通过三步恢复：重建依赖图、扫描磁盘已有对象、确定最优恢复点仅重新计算缺失对象。
- **可扩展性**：支持自定义增强操作，通过 RPC 服务机制在独立进程中执行外部库，避免依赖冲突。
- **配置**：提供五种分支类型（single、conditional、random、multi、merge）来表达复杂的增强流水线。

## 五、实验结果

实验在 GCP A2 实例（NVIDIA A100 GPU，12 vCPU/GPU，3 TB NVMe SSD）上进行，覆盖四个模型：SlowFast、MAE（视频动作识别）、HD-VILA（视频字幕）、BasicVSR++（视频超分辨率）。

### 单任务训练

| 指标 | vs CPU baseline | vs GPU baseline (DALI) |
|------|----------------|----------------------|
| 训练时间加速 | 2.4×–5.6× | 1.4×–1.7× |
| GPU 利用率提升 | 2.5×–5.7× | 1.4×–1.7× |

朴素缓存（缓存所有解码帧至 3 TB 上限）仅带来 2.7% 加速，因为随机帧选择导致缓存命中率极低（不足 4%）。

### 超参搜索（4 GPU 并行，Ray Tune + ASHA）

| 指标 | vs CPU baseline | vs GPU baseline |
|------|----------------|----------------|
| 搜索时间加速 | 2.9×–10.2× | 1.4×–2.8× |
| GPU 利用率提升 | 3.1×–12.3× | 1.8×–2.9× |

与 ideal case 仅差 5-14%。

### 多异构任务训练（SlowFast + MAE，2 GPU）

| 指标 | vs CPU baseline | vs GPU baseline |
|------|----------------|----------------|
| 训练时间加速 | 5.3×–6.2× | — |
| GPU 利用率提升 | 5.4×–8.3× | 1.7×–2.5× |

### 分布式训练（2 节点，远程 Filestore 存储）

SlowFast 模型相比 CPU baseline 加速 5.2×，SAND 通过本地缓存将网络带宽需求降至 baseline 的 3%。

### 其他结果

- **代码量**：SlowFast 预处理从 2,254 行降至 8 行，HD-VILA 从 297 行降至 7 行。
- **物化规划**：多任务场景下解码操作减少 50.3%，随机裁剪操作减少 33.1%。
- **图剪枝**：1.5 TB 存储下重计算开销降低 25%，3 TB 下降低 10%。
- **线程调度**：priority-based scheduling 相比无调度方案提升 42.6%。
- **能耗**：相比 CPU pipeline 降低 42-82%，相比 GPU pipeline 降低 15-38%。

## 六、批判性分析

1. **实验规模偏小**：所有实验在 1-4 个 A100 GPU 上进行，最大仅 2 节点分布式。对于实际大规模训练（数十到数百 GPU），SAND 的 FUSE 文件系统开销、元数据管理开销和调度复杂度是否仍可忽略不计，缺乏验证。

2. **存储假设较为乐观**：论文假定有 3 TB 本地 NVMe SSD，但 pre-materialization 的收益高度依赖本地存储容量。对于存储更受限的场景（如共享集群、Spot 实例），收益可能大幅缩水。论文虽有 1.5 TB 的对比，但未探讨存储极端不足时的退化表现。

3. **baseline 选择不够充分**：仅与 on-demand CPU 和 DALI GPU 对比，未与 CoorDL、FusionFlow 等近期同类优化工作进行直接比较。这些系统也针对数据预处理瓶颈，缺少与它们的对比削弱了论文的说服力。

4. **FUSE 开销未充分讨论**：FUSE 是用户态文件系统，每次 I/O 涉及内核/用户态切换。论文声称元数据开销"可忽略"，但未给出 FUSE 本身的微基准测试数据。在高频小 I/O 场景下（如大量小帧文件的缓存读写），FUSE 开销可能不可忽略。

5. **Shared frame pool 的随机性保证存疑**：论文用 GCD 统一采样步长来构建 shared frame pool，声称保持了各任务的时间随机性。但当不同任务的帧需求差异较大时，GCD 可能产生非常细粒度的采样网格，导致 shared pool 中大量帧仅被少数任务使用，复用率下降。论文仅展示了帧选择 CDF 和 loss 曲线重合，未深入分析不同任务配置下复用率的变化。

6. **配置文件的表达能力限制**：论文宣称用 YAML 配置替代数千行代码，但仅展示了相对标准的增强流水线。对于需要自定义复杂逻辑（如条件性增强、依赖外部模型的增强）的场景，YAML + 五种分支类型是否足够灵活，以及 RPC 扩展机制引入的延迟开销，均未充分评估。

## 七、AI Infra / MLSys 视角

1. **预处理瓶颈的普遍性启示**：SAND 揭示了一个被广泛忽视的问题——在 GPU 算力快速增长的背景下，数据预处理（尤其是涉及解压缩的场景）越来越成为训练瓶颈。这一观察不仅适用于视频，也适用于医学影像、点云、基因组学等领域。AI Infra 系统设计应将数据预处理作为一等公民纳入考量。

2. **View 抽象的可迁移性**：将训练数据管道建模为依赖图并在存储层面进行全局优化的思路，可以推广到 LLM 训练中的数据处理（如 tokenization 缓存、数据混合策略的中间结果复用）以及多模态模型训练中的跨模态数据协调。

3. **跨 job 数据共享的系统支持**：SAND 在超参搜索和多任务训练中展示的跨 job 数据复用能力，对 AutoML 平台和模型开发平台有直接借鉴价值。当前 MLSys 中缺乏系统级的跨 job 中间数据共享机制，这是一个值得跟进的方向。

4. **值得探索的 follow-up 方向**：
   - 将 pre-materialization 思想应用于 LLM 的数据预处理流水线（tokenization、data packing 等）
   - 在 GPU 集群调度器中集成数据预处理感知的调度策略（co-locate 共享数据集的任务）
   - 探索 GPU Direct Storage 与 SAND 类系统的结合，绕过 CPU 和 FUSE 开销

---

## 八、总结

SAND 提出了一种面向视频深度学习的 view-based 编程抽象，通过将预处理流水线建模为可优化的依赖图，在存储层面实现跨 epoch、跨任务的中间对象复用，从而大幅减少冗余解码和预处理开销。在单任务训练、超参搜索、多任务训练和分布式训练等场景中，SAND 实现了 1.4×-10.2× 的训练加速和高达 12.3× 的 GPU 利用率提升，同时将预处理代码从数千行压缩到不到 10 行。其主要局限在于实验规模较小（最多 4 GPU）、对本地存储容量有一定依赖、以及 FUSE 用户态文件系统在大规模场景下的可扩展性有待验证。
