## 一、背景

内存管理子系统（MM）是操作系统的核心组件，负责管理内存资源、编程 MMU 硬件（页表和 TLB）。随着多核服务器核数的迅速增长（今天的服务器已有数百乃至数千核），MM 的并发性能成为应用扩展性的关键瓶颈，同时并发 bug 也带来严峻的安全威胁。

自 SunOS（1986）起，主流操作系统的 MM 设计一直沿用**两层抽象**：软件层（如 Linux 的 VMA 树，记录进程地址空间中的虚拟内存区域）和硬件层（页表）。这一设计在过去为支持多样化 MMU 硬件（段式、哈希页表等）和高级内存语义（按需分页、写时复制）提供了良好的可移植性。

CortenMM 是北京大学 Asterinas 产品 OS 项目的一部分——该项目旨在构建一个从零开始用 Rust 编写的生产级、Linux ABI 兼容的通用 OS。

---

## 二、要解决的问题

**性能瓶颈**：Linux 内存管理在多线程应用下是严重的扩展性瓶颈。关键问题在于两层抽象导致了复杂的锁协议：`mmap_lock`（粗粒度）、VMA lock（细粒度）、页表锁（分多个层次），并发的 mmap/munmap/page fault 操作需要跨两个抽象层同时协调锁，造成无谓竞争。官方 Linux 文档用了近 5000 字描述这些加锁规则，仍难以正确实现。

**并发 Bug 泛滥**：性能优化使加锁逻辑愈发复杂，极易引入微妙的并发 bug。Linux 仅在 2023 年 4 月引入细粒度 per-VMA 锁后，过去两年就已出现 **10 个 CVE**（其中 9 个可导致系统崩溃，5 个可导致信息泄露或权限提升）。

**核心矛盾**：两层抽象的设计初衷（支持多样化 MMU 硬件、支持高级内存语义）在现代环境中已不再成立——主流 ISA（x86、ARM、RISC-V）均统一采用多级 radix tree 页表，与软件层抽象的数据结构形态差异极大，反而加剧了同步复杂性。

---

## 三、核心设计

**关键洞察**：软件层抽象（VMA 树）对现代 OS 已不再必要。主流 ISA 的 MMU 差异已经足够小，可以用语言特性（如 Rust trait / C 宏）来处理，无需再维护一套独立的软件层数据结构。因此可以**彻底消除软件层抽象**，仅保留硬件层抽象（页表）。

**单层抽象设计**：CortenMM 将每个页表页（PT page）与一个**辅助页描述符**（page descriptor）关联，描述符中包含：
- 一把保护该 PT page 的锁
- 一个**按 PTE 偏移索引的元数据数组**，存储高级语义所需的最小状态（虚拟页状态：Invalid、PrivateAnon、Mapped、Swapped 等，以及 COW 相关 bit、文件映射的 fd/offset 等）

元数据数组按需分配，随对应 PT page 一起释放。

**事务性接口**：CortenMM 引入事务性接口作为编程 MMU 的唯一方式：
```
AddrSpace::lock(range) → RCursor
RCursor::query(addr)
RCursor::map(addr, page)
RCursor::mark(range, status)
RCursor::unmap(range)
```
调用方首先通过 `lock(range)` 指定虚拟地址范围并获取 `RCursor`，之后通过 RCursor 执行任意组合的基本操作，所有操作在事务内**原子执行**。

**两种锁协议**：
- **CortenMM_rw**：基于 readers-writer 锁。从页表根开始向下遍历，找到覆盖指定范围的最低级 PT page（"covering PT page"），先加读锁向下探索，到达 covering PT page 后升级为写锁。简单直观，但读锁开销较高。
- **CortenMM_adv**：基于 RCU + MCS spin-lock。遍历阶段完全无锁（lock-free），加锁阶段先锁 covering PT page，再 DFS 锁其所有子 PT page。通过 RCU 处理 unmap 时的 use-after-free 竞争（被 unmap 的 PT page 标记为 `stale`，其他线程在加锁后检测到 stale 则重试）。

**并发语义**：操作同一范围的并发事务串行化；操作不相交范围的事务并行执行。

## 四、实现细节

- **实现规模**：8028 行 safe Rust + 122 行 unsafe Rust；核心事务接口 829 LOC，CortenMM_adv 225 LOC，CortenMM_rw 153 LOC。

- **系统集成**：CortenMM 是 Asterinas OS 的 MM 模块，提供与 Linux 完全相同的系统调用接口（mmap、munmap、mprotect、msync 等），已实现 219/336 个最常用系统调用，可运行 JVM 和 MySQL。

- **物理内存管理**：借鉴 Linux buddy allocator + slab allocator；借鉴 Linux struct page 设计来存储物理页的附加元数据。

- **优化 1：per-core 虚拟地址分配器**：每个核独立管理一段私有虚拟地址空间，消除并发 mmap 时的地址分配竞争。

- **优化 2：TLB shootdown**：并行 TLB flush + early acknowledgement；支持 lazy TLB shootdown（LATR 方案）——unmapped 页被 push 到 per-CPU buffer，在 timer interrupt 或 reschedule 时批量处理。

- **锁实现**：CortenMM_rw 使用 BRAVO-pfqlock（phase fair queued lock + BRAVO 偏向读优化）；CortenMM_adv 使用 preemption-based RCU + MCS lock。

- **可移植性**：通过 Rust trait 抽象 ISA 差异（类似 Linux 用 C 宏），移植到 RISC-V 仅需 252 行，支持 Intel MPK 仅需 82 行，均少于 Linux。

- **支持特性**：on-demand paging、COW、swap、file-backed mapping、reverse mapping、huge page（4KB/2MB/1GB）；尚不支持 NUMA policy 和 ARM（在开发中）。

## 五、实验结果

**实验环境**：双路 AMD EPYC 9965 服务器，每路 192 核（共 384 核），512GB DRAM × 2；跑在 VM 中（因 Asterinas 缺部分驱动），禁用超线程和 turbo boost。对比基线：Linux 6.13.8、RadixVM、NrOS。

**单线程微基准**（mmap/mmap-PF/PF/unmap-virt/unmap）：

| 操作 | CortenMM_adv vs Linux | CortenMM_rw vs Linux |
|---|---|---|
| mmap | **-3.1%**（略慢，因初始化更多 PT page） | -19.2% |
| mmap-PF | **+46.8%** | +22.4% |
| PF | **+53.6%** | +28.4% |
| unmap-virt | **+76.9%**（Linux 需拆分 VMA 节点） | +56.0% |
| unmap | **+7.8%** | +18.5% |

**多线程微基准**（384 核）：
- 低竞争（各线程访问私有区域）：CortenMM_adv 线性扩展，outperform Linux **33×（PF）到 2270×（unmap-virt）**
- 高竞争：CortenMM_adv 超过 64 线程后扩展性下降（末级 PT page 竞争），但仍 outperform Linux **3×（PF）到 1489×（unmap）**

**真实应用**：
| 应用 | 说明 | CortenMM_adv vs Linux（峰值） |
|---|---|---|
| JVM 线程创建 | 模拟 Android 应用启动 | **+32%**（384 核） |
| metis | map-reduce，1.6GB 文本 | **+26×**（384 核） |
| dedup（ptmalloc） | 频繁 unmap | **+2.69×**（64 线程） |
| psearchy（ptmalloc） | 文件索引 | **~+2×**（64 线程） |
| PARSEC 其他 | 非 MM 密集型 | 持平（无退化） |

**LMbench（fork/exec）**：fork 慢 17.7%（需遍历页表），fork+exec 快 23%（page fault 处理更快），shell 持平。

**内存开销**：CortenMM 与 Linux 相近；理论上限（全部 PTE metadata 填满）仅额外增加约 2%，远优于 RadixVM（复制页表，开销显著）。

**形式验证开销**：约 8 人月，proof:code ≈ 5.2:1，Verus 验证时间 < 20 秒。

## 六、批判性分析

**1. VM 环境的实验有效性存疑**

论文承认实验在虚拟机中进行，理由是 Asterinas 缺部分驱动。这是一个重要的限制：VM 的内存管理语义、cache coherence 行为与裸机可能存在差异，在 384 核极端场景下尤为明显。作者仅以"我们不认为会影响性能结论"轻描淡写带过，缺乏对 VM 开销的分析或对比实验。

**2. 高竞争场景的扩展性局限被低调处理**

论文标题强调"高性能"，但高竞争场景下（多线程共享同一内存区域），CortenMM_adv 在超过 64 线程后便失去扩展性。这是 CortenMM 的系统性限制：末级 PT page 成为全局热点锁。RadixVM 在高竞争 PF 场景下反而优于 CortenMM（per-core 独立页表避免了 cache coherence 竞争）。

**3. 关键基线缺失：MGLRU 和 folio 相关优化**

Linux 近年来（5.18+ 及 6.x）引入了 folio、MGLRU 等重大内存管理改进。测试使用 Linux 6.13.8，但似乎未专门调优，且禁用了所有缓解措施（KPTI 等）。尽管这对 MM 性能有一定合理性，但没有讨论这些选择对结论泛化性的影响。

**4. fork 性能退化未被充分讨论**

fork() 慢 17.7% 的问题对 Java 应用、容器场景（大量 fork+exec）有重要影响。文章仅用"fork+exec 快 23% 所以没问题"来规避这个问题，但 fork 本身（含 CoW 语义完整复制地址空间）在实际系统中是非常常见的操作路径。

**5. 形式验证范围有限但表述较模糊**

验证覆盖范围仅限于"core part"（事务接口的加锁协议 + RCursor 操作的功能正确性），而 swap、reverse mapping、物理内存分配等均未验证。更重要的是，验证代码与实际运行代码**未链接**——Verus 版本是单独移植的，需人工确保两份代码一致。这是一个重大的可靠性隐患，文中虽有提及但未给出保障机制。

**6. 内存语义完备性**

Table 2 显示 CortenMM 不支持 NUMA policy（"×"），而 NUMA 感知对大型服务器的性能至关重要。384 核 EPYC 本身就是 NUMA 架构，但实验结果未讨论 NUMA 效应对 CortenMM 的影响。

## 七、AI Infra / MLSys 视角

CortenMM 与 AI Infra / MLSys 的直接交集较浅，但有若干值得关注的借鉴价值：

**1. 大规模推理/训练系统中的 MM 瓶颈**

AI 推理系统（vLLM、Triton 等）和训练框架（PyTorch、DeepSpeed）在 CPU 端频繁调用 `mmap`/`munmap`（如 KV cache 管理、内存池、`torch.cuda.empty_cache()` 的 CPU 侧映射）。Linux MM 的扩展性瓶颈在高并发场景下可以显著影响端到端吞吐。CortenMM 的思路提示：**在自定义 AI 系统 OS 层或 userspace 内存管理库中，消除软件层抽象的中间层开销是一个值得探索的优化方向**。

**2. 事务性内存接口对 CUDA Unified Memory 的启发**

CortenMM 的事务性接口（原子执行一批 map/unmap/mark 操作）对设计 GPU-CPU 统一内存管理有借鉴价值。当前 CUDA Unified Memory 的 page fault 机制在多线程下同样有串行化问题，类似的 transactional + lock-free traversal 思路可能有助于提升其并发性能。

**3. 形式验证 + Rust 对 AI 系统内核组件的适用性**

大型 AI 集群对系统正确性要求极高（一个内存 bug 可能导致 8000 卡训练任务崩溃）。CortenMM 展示了用 Verus 对 Rust 内核代码做半自动形式验证的可行性，8 人月、5.2:1 的 proof:code ratio 说明成本不算天文数字。**这一路径对 AI infra 中的核心路径（如分布式内存管理、NVLink 通信层）的可信度提升有参考价值**。

**Future Work 方向**：
- 将 CortenMM 的设计思路迁移到 GPU 驱动层的虚拟地址管理（如 NVLink fabric manager）
- 探索在 AI 推理引擎中用 userspace 单层地址抽象（mmap + custom page descriptor）替代 Linux MM 的可行性
- 研究 CortenMM 风格的 transactional interface 是否适合管理 HBM/CXL 等异构内存拓扑

---

## 八、总结

CortenMM 提出了一个干净利落的操作系统内存管理新设计：通过观察到现代 ISA 已统一采用多级 radix tree 页表，彻底消除软件层 VMA 抽象，仅保留硬件层页表，并在其上设计事务性接口和形式验证的锁协议。这一"sweeping simplicity"既带来了显著的性能提升（比 Linux 快 1.2×-26×），又为形式化验证核心并发代码创造了条件（已验证加锁协议正确性）。主要局限在于：高竞争下末级页表仍是热点，不支持 NUMA policy，验证代码与实现代码存在链接缺口，且实验全在 VM 中进行。CortenMM 是 Asterinas OS 项目的组成部分，代表了工业级操作系统向"correctness-first + clean-slate"方向迈出的有价值一步。
