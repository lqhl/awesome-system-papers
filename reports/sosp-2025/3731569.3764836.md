## 一、背景

操作系统的内存管理（MM）负责管理内存资源和编程 MMU 硬件（页表和 TLB），是 OS 最核心的子系统之一。现代多核服务器通常拥有数百个核心，共享内存多线程是利用这些核心的主流方式，因此 MM 必须高效地处理来自多个线程的并发请求。同时，MM 的正确性至关重要——并发 bug 可导致严重的安全漏洞。

自 1986 年 SunOS 以来，几乎所有主流 OS（Linux、FreeBSD、Solaris、Windows、Fuchsia、鸿蒙等）的内存管理都采用**两层抽象设计**：1）软件层抽象（如 Linux 的 VMA 树），表示进程的虚拟内存区域；2）硬件层抽象（页表）。这种设计的初衷是提高跨 MMU 硬件的可移植性并支持按需分页等高级语义。

---

## 二、要解决的问题

两层抽象设计带来了两个根本性问题：

1. **可扩展性瓶颈**：正确同步两个截然不同的复杂数据结构需要复杂的细粒度并发控制。Linux 使用四种不同的锁（mmap_lock、VMA lock、粗粒度页表锁、细粒度页表锁），锁定规则极其复杂（官方文档长达 5000 字）。即使经过多年优化，Linux MM 仍然是多线程应用的严重可扩展性瓶颈，例如影响 Android 应用启动、Google Fibers 线程创建、TCP zero-copy 等重要场景。

2. **并发正确性问题**：复杂的锁定协议极易引入细微的并发 bug。Linux 在 2023 年 4 月引入 per-VMA lock 后的两年内，已产生 10 个 CVE（9 个可导致系统崩溃，5 个可导致信息泄露或权限提升）。

3. **学术方案的不足**：RadixVM、NrOS、Bonsai 等学术方案虽然提出了更好的数据结构或并发控制，但可扩展性仍不理想，且功能支持不完整（如 RadixVM 不支持 COW 和 page swapping，NrOS 不支持按需分页）。

---

## 三、洞察与设计

**关键洞察**：软件层抽象对面向主流 ISA（x86、ARM、RISC-V）的现代 OS 已不再必要。原因有二：（1）与过去 MMU 格式多样化（段式、哈希页表等）不同，当今主流 ISA 统一使用多级 radix tree 页表，硬件间的微小差异可通过语言特性（如 C 宏或 Rust trait）屏蔽，不需要额外的软件抽象层；（2）虽然按需分页等高级语义需要在 MMU 之外存储额外状态，但这不需要一个独立的、与硬件层截然不同的抽象层。

基于此洞察，CortenMM 采用**单层抽象设计**：

- **数据结构**：去除 VMA 树，直接在页表上操作。每个页表页（PT page）关联一个页描述符，包含一把锁和一个 per-PTE 元数据数组（按需分配），用于存储高级语义所需的最少信息（如交换设备信息、文件映射偏移等）。

- **事务接口**：设计了统一的 `AddrSpace::lock(range) → RCursor` 接口作为操作 MMU 的唯一方式。RCursor 提供四种基本操作（query、map、mark、unmap），事务内的所有操作原子执行。

- **锁定协议**：设计了两种协议：
  - **CortenMM_rw**：基于读写锁，从页表根到叶子遍历，找到完全覆盖指定范围的最低级 PT page（covering PT page），获取其写锁。简单但读操作需要获取锁。
  - **CortenMM_adv**：基于 RCU 的无锁遍历 + 互斥锁。遍历阶段无需任何锁，锁定阶段锁定 covering PT page 及其所有后代。用 RCU 处理并发 unmap 导致的 PT page 释放竞争（标记 stale 状态并重试）。

- **并发控制语义**：事务内操作原子执行；操作重叠内存区域的事务序列化，操作不相交区域的事务并行执行。两种协议本质上都是两阶段锁（2PL），保证原子性。

## 四、实现细节

- **编程语言**：CortenMM 用 Rust 实现，是 Asterinas OS 的一部分（一个旨在替代 Linux 的生产级 OS）。非 MMU 操作代码强制使用 safe Rust（`#![deny(unsafe_code)]`），防止数据竞争和绕过事务接口直接访问 MMU。

- **系统调用实现**：mmap、munmap、mprotect 等系统调用通过事务接口实现，代码极其简洁（图 8）。例如 mmap 仅需锁定范围 → query 检查 → mark 设置状态；页错误处理查询虚拟页状态后按需 map 物理页、执行 COW 等。

- **per-PTE 元数据数组**：存储每个 PTE 对应的辅助信息（匿名页权限、文件映射的 fd/offset、交换设备/块号等），按需分配，随 PT page 一起释放。

- **可移植性**：使用 Rust trait（`PageTableEntryTrait`）抽象不同架构的 PTE 格式差异。移植到 RISC-V 仅需 252 行代码（Linux 需 699 行），支持 Intel MPK 仅需 82 行（Linux 需 273 行）。

- **形式化验证**：使用 Verus（基于 Rust 的验证框架）验证：1）两种锁定协议的互斥正确性；2）基本操作（map、unmap、mark、query）的功能正确性；3）页表的 well-formed tree 不变量。验证采用分层规约（AtomicSpec → AtomicTreeSpec → WFTreeSpec），proof-to-code ratio 为 5.2:1，总计约 8 人月工作量，Verus 可在 20 秒内完成验证。

- **TLB shootdown 优化**：利用 per-PTE 元数据中的未使用位标记 COW 等状态，避免不必要的 TLB shootdown。

## 五、实验结果

**实验平台**：双路 AMD EPYC 9965，每路 192 核（共 384 核），1TB DRAM，禁用超线程和 turbo boost，在 VM 中运行。

**基线**：Linux 6.13.8（禁用 KPTI 等缓解措施）、RadixVM、NrOS。

### 单线程微基准测试

| 操作 | CortenMM_adv vs Linux | CortenMM_rw vs Linux |
|------|----------------------|---------------------|
| mmap | -3.1% | -19.2% |
| mmap-PF | +46.8% | +22.4% |
| PF | +53.6% | +28.4% |
| unmap-virt | +76.9% | +56.0% |
| unmap | +7.8% | +18.5% |

mmap 略慢是因为 CortenMM 提前分配页表页，但 mmap-PF（含页错误）时反而更快。

### 多线程微基准测试（384 核）

- **低争用**：CortenMM_adv 几乎线性扩展，超越 Linux 33×（PF）到 2270×（unmap-virt）。
- **高争用**：CortenMM_adv 超越 Linux 3×（PF）到 1489×（unmap）。

### 真实应用

| 应用 | 结果 |
|------|------|
| JVM 线程创建（384核） | CortenMM 超越 Linux 32% |
| metis map-reduce（384核） | CortenMM_adv 超越 Linux 26×，超越 RadixVM 1.24×（128核） |
| dedup（ptmalloc，64线程） | CortenMM_adv 超越 Linux 2.69× |
| psearchy（ptmalloc，64线程） | CortenMM 超越 Linux ~2× |
| PARSEC 其他 | 无额外开销 |

### 内存开销

CortenMM 与 Linux 内存开销相当。即使满配元数据数组，理论上界也仅翻倍但仍在 2% 以内。RadixVM 因页表复制有更大开销。

### 移植性

| 特性 | CortenMM | Linux |
|------|----------|-------|
| RISC-V | 252 LoC | 699 LoC |
| Intel MPK | 82 LoC | 273 LoC |
| Intel TDX | 368 LoC | 471 LoC |

## 六、批判性分析

1. **fork 性能回退被弱化**：CortenMM 在 fork 上比 Linux 慢 17.7%，这是因为去除 VMA 树后需要遍历整个页表才能定位所有内存区域。论文仅在附录性质的 LMbench 测试中提到这一点，但 fork 在实际工作负载（容器启动、进程管理等）中非常常见，这是一个非平凡的限制。论文通过 fork+exec（快 23%）和 shell（持平）来淡化这一问题，但这些是 fork 的后续操作收益弥补了 fork 本身的劣势。

2. **验证的有限性**：论文标题声称"Strong Correctness Guarantees"，但验证存在明显局限：（a）仅验证了事务接口的核心部分，未覆盖系统调用实现、物理页分配等其他组件；（b）验证代码与实际内核代码分开编译（因 nightly Rust 兼容性问题），靠手动保证两者一致；（c）假设顺序一致性内存模型，未考虑 ARM 的弱内存序。这些局限使"strong correctness guarantees"的说法有所夸大。

3. **评估在 VM 中进行**：所有实验在虚拟机中运行（因缺少裸机驱动），论文声称"不影响性能结论"但未提供支持证据。VM 中的 TLB 行为、内存延迟特性与裸机可能存在差异。

4. **不支持 NUMA 策略**：Table 2 显示 CortenMM 不支持 NUMA policy，在大型多 socket 系统上这可能是重要缺陷，但论文未讨论这一限制的影响。

5. **真实应用覆盖面**：声称 1.2×–26× 的提升范围跨度极大。26× 来自 metis（一个特殊的 map-reduce benchmark，分配 8MB chunk 且不归还内核），大多数 PARSEC 应用提升接近 0。标题给出的印象比实际适用范围更广。

6. **tcmalloc 的对冲作用**：dedup 和 psearchy 的评估表明，使用 tcmalloc 后 Linux 的性能差距大幅缩小。现代生产环境普遍使用 tcmalloc/jemalloc 等分配器，这削弱了 CortenMM 在实际部署中的价值——相当一部分收益可以通过用户态分配器策略获得。

## 七、AI Infra / MLSys 视角

1. **对大模型推理系统的潜在价值**：vLLM、TensorRT-LLM 等推理引擎大量使用 mmap 管理 KV cache 和模型权重的内存映射。CortenMM 在 mmap/munmap 上的多核扩展性提升（特别是在高并发请求场景下）可能显著减少推理引擎的内核态开销。

2. **GPU 内存管理的借鉴**：CortenMM 的"去除中间抽象层、直接操作硬件页表"的思路，可以迁移到 GPU 统一虚拟内存（UVM）管理中。当前 CUDA UVM 的页面迁移和错误处理同样面临类似的两层抽象问题。

3. **事务接口的设计启发**：CortenMM 的事务接口将并发控制与操作解耦的设计，对 AI 系统中的资源管理器（如 GPU 显存分配器、分布式共享内存管理）有参考价值。这种模式可以简化在多 GPU/多节点场景下的内存管理正确性保证。

4. **形式化验证在系统软件中的实践**：CortenMM 展示了用 Verus/Rust 对并发系统代码进行形式化验证的可行性（8 人月，5.2:1 proof-to-code ratio），这对 AI Infra 中关键路径代码（如 collective communication、gradient synchronization）的正确性保证有参考意义。

5. **值得跟进的方向**：（a）将单层抽象思路应用到异构内存管理（CPU-GPU 统一地址空间）；（b）在 CortenMM 基础上实现高效的大页（huge page）动态管理，对 AI 训练的内存局部性有直接价值；（c）结合 CortenMM 的页表锁定协议设计更高效的 RDMA 内存注册/注销机制。

---

## 八、总结

CortenMM 提出了一个关键洞察：现代 OS 内存管理系统中的软件层抽象（如 VMA 树）已不再必要，因为主流 ISA 的 MMU 格式已趋于统一。基于此，CortenMM 采用单层抽象设计，直接在页表上操作并通过事务接口和分层锁定协议实现高效的并发控制。这一设计同时简化了形式化验证的可行性。在 384 核机器上，CortenMM 在内存密集型工作负载上显著优于 Linux（最高 26×），同时不影响其他应用性能。主要局限包括不支持非 radix tree 页表的 ISA、fork 性能回退、不支持 NUMA 策略，以及形式化验证的覆盖范围有限。该工作作为 Asterinas OS 的一部分，展示了从零设计 OS 子系统以同时解决性能和正确性问题的可能性。
