# CortenMM: Efficient Memory Management with Strong Correctness Guarantees

## 论文基本信息

- **标题**: CortenMM: Efficient Memory Management with Strong Correctness Guarantees
- **作者**: Junyang Zhang, Xiangcan Xu, Yonghao Zou, Zhe Tang, Xinyi Wan, Kang Hu, Siyuan Wang, Wenbo Xu, Di Wang, Hao Chen, Lin Huang, Shoumeng Yan, Yuval Tamir, Yingwei Luo, Xiaolin Wang, Huashan Yu, Zhenlin Wang, Hongliang Tian, and Diyu Zhou
- **会议**: SOSP 2025
- **Session**: OS Memory Management
- **PDF**: 3731569.3764836.pdf
- **奖项**: Best Paper Award

## 研究背景

内存管理系统（Memory Management, MM）位于任何操作系统的核心位置，负责管理内存资源并编程 MMU（内存管理单元）硬件——即页表和 TLB。现代多核处理器依赖共享内存多线程来充分发挥硬件算力，而 MM 必须高效处理来自多个线程的并发请求。此外，由于 MM 在安全方面的关键角色，其中的并发 bug 可能导致严重后果，包括系统崩溃、信息泄露和权限提升。

然而，尽管经过数十年的开发，现代内存管理系统在性能和正确性两方面都面临严峻挑战。Linux 的内存管理即使经过大量优化（如 per-VMA locks、RCU-safe maple tree 等），对于多线程应用仍是著名的可扩展性瓶颈。Android 应用启动变慢、Google Fibers 线程创建效率低下、TCP 零拷贝性能退化等真实案例都指向这一瓶颈。更糟糕的是，2023 年 4 月 Linux 引入细粒度并发控制后，仅在两年内就产生了 10 个 CVE，其中 9 个可导致系统崩溃，5 个可引发更严重的安全漏洞（如信息泄露和权限提升）。

这一现状的根本原因在于：大多数操作系统采用两层抽象设计——软件层抽象（如 Linux 中的 VMA 树）和硬件层抽象（页表）。这一设计可追溯至 1986 年的 SunOS，初衷是提高对不同 MMU 硬件的移植性并支持高级内存语义（如按需调页）。然而，为了保证移植性，软件层抽象的数据结构必须通用化，无法与硬件层抽象的数据结构趋同。正确地同步两个截然不同的复杂数据结构本身就是一个极具挑战性的问题，导致了复杂的锁规则和微妙的并发 bug。

## 要解决的问题

核心研究问题是：**如何同时实现内存管理系统的高性能和强同步正确性保证？**

具体而言，本文旨在解决以下子问题：

1. **性能问题**：传统两层抽象设计引入了软件层（如 VMA tree）的不必要竞争，即使页表层可以并行操作，线程在无关内存区域上的操作也会因为 VMA 层的锁竞争而无法扩展。
2. **正确性问题**：两层抽象的复杂锁规则即使对经验丰富的内核开发者也难以掌握，历史上已经导致大量并发 bug 和安全漏洞。
3. **可验证性问题**：现有内存管理系统的并发控制逻辑过于复杂，难以进行形式化验证，而仅依赖测试又不足以保证正确性。

## 核心贡献

1. **洞察贡献**：揭示了内存管理性能低下和并发 bug 的根本原因在于两层抽象设计，并指出对于现代主流 ISA（x86、ARM、RISC-V 均使用相似的多级 radix tree 页表），软件层抽象已经不再必要。
2. **事务接口**：提出了一种高效且经过形式化验证的 MMU 操作事务接口，包含四个基本操作（query、map、mark、unmap），未来工作可以在此基础上构建。
3. **CortenMM 系统**：设计并实现了 CortenMM，一个全功能的内存管理系统，在现代 MMU 上提供高性能同时提供强同步正确性保证，适合作为 Linux 的直接替代方案。
4. **形式化验证**：利用 Verus 对 CortenMM 的核心并发代码进行了形式化验证，证明了基本操作的函数正确性和两种锁协议的互斥正确性。
5. **评估验证**：在 384 核机器上进行了全面评估，证明 CortenMM 在真实基准测试中比 Linux 快 1.2× 到 26×。

## 主要研究方法

本文采用了 clean-slate 设计方法，结合了系统设计、编程语言技术和形式化验证三条路线。

**关键设计洞察**：现代主流 ISA（x86、ARM、RISC-V）统一采用多级 radix tree 页表作为 MMU 格式，操作系统代码已经使用 C 宏或 Rust trait 来屏蔽硬件差异，而非依赖软件层抽象。这说明两层抽象不再必要。消除软件层抽象后，每个页表页（PT page）只需要关联一个页描述符（page descriptor），包含该 PT 页的锁、该 PT 页本身，以及一个 per-PTE 元数据数组，按需分配。

**事务接口设计**：受数据库事务两阶段锁启发，CortenMM 提出以事务作为编程 MMU 的唯一方式。调用者首先调用 `AddrSpace::lock(range)` 指定一个虚拟内存区域，返回一个 `RCursor` 对象；然后用 `RCursor` 指定任意组合的四个基本操作（query、map、mark、unmap），CortenMM 在指定范围内原子执行所有操作。这种设计将并发控制与操作本身解耦，简化了正确性推理。

**两种锁协议**：
- **CortenMM rw**：基于读者-写者锁的简单版本，线程从页表根向下遍历，读取锁获取覆盖范围最低的 PT 页，然后释放读锁并获取写锁。
- **CortenMM adv**：基于 RCU 的高级版本，遍历阶段无锁执行，仅在锁定阶段获取锁，支持更好的可扩展性。使用 RCU monitor 处理 PT 页 unmapping 时的 use-after-free 问题。

**形式化验证**：使用 Verus（一种基于 SMT 的半自动 Rust 验证器）验证了核心并发代码。验证包含三个层次的自指证明：Atomic Tree Spec → Atomic Spec → 互斥属性。验证工作量为约 8 人月，代码行数 4868 行（规格）vs 1769 行（实现），证明与代码比率为 5.2:1。

## 设计与实现

**系统架构**：CortenMM 属于更大的 Asterinas OS 项目（一个从零开始开发的生产级操作系统）。核心部分约 130K 行代码（不含驱动），已实现 219/336 个最常用的 Linux 系统调用。Asterinas 提供与 Linux 相同的系统调用接口，能够运行 JVM 和 MySQL 等大型应用。

**页描述符结构**：每个页表页对应一个页描述符，包含：1) 保护自身的锁；2) 对应的 PT 页；3) per-PTE 元数据数组（按需分配和释放）。元数据数组编码各种虚拟页状态（Invalid、Mapped、PrivateAnon、Swapped 等），支持按需调页、COW、交换等高级语义。

**事务接口的 Rust 实现**：`AddrSpace::lock()` 返回 `RCursor`，后者实现了 `query()`、`map()`、`mark()`、`unmap()` 四个基本操作，通过 Rust 的 `Drop` trait 在析构时自动释放所有已获取的锁。

**高级内存语义支持**：
- **按需调页**：mmap 时仅在元数据数组中记录状态和访问权限，实际页表条目在 page fault 时填充。
- **Copy-on-Write**：每个虚拟页维护 shared bit 和 writable bit 两个额外位，fork 时设置 shared bit 并将页设为只读，写错误触发 COW。
- **反向映射**：页描述符记录指向文件对象或 AddrSpace 的指针，支持反向映射。

**系统调用处理**：mmap、munmap、mprotect、page fault handler 均通过事务接口实现，代码简洁直观。page fault handler 在事务内执行复杂的状态转换（检查、COW 处理等）。

**关键优化**：
- **per-core 虚拟地址分配器**：每个核心拥有私有地址空间份额，避免分配/释放时的竞争。
- **并行化 TLB shootdown**：CortenMM 并行化所有核心上的 TLB flush，支持 lazy TLB shootdown（munmap 时将刷新任务推送到 per-CPU 缓冲区）。
- **ARM 支持**：当前 OS 的 ARM 支持尚在开发中，预期移植简单，因为 ARM 符合 CortenMM 对页表格式的假设。

**实现规模**：8028 行安全 Rust + 122 行 unsafe Rust。核心事务接口 829 行，其中 CortenMM rw 153 行、CortenMM adv 225 行。

## 主要实验结果

**实验环境**：双插槽 AMD EPYC 9655，384 核（每插槽 192 核），1TB DRAM。禁用超线程和 turbo boost，运行在虚拟机中（OS 缺乏部分驱动）。

**单线程微基准测试**：
- CortenMM adv 在 4/5 项操作上优于 Linux：mmap-PF (+46.8%)、PF (+53.6%)、unmap-virt (+76.9%)、unmap (+7.8%)；仅 mmap 有 -3.1% 的小幅退化（因为需要分配和初始化页表页）。
- NrOS（不支持按需调页）和 RadixVM 的性能与先前报告一致。

**多线程微基准测试（384 核）**：
- **低竞争场景**：CortenMM adv 在所有工作负载上接近线性扩展，PF 优于 Linux 33×，unmap-virt 优于 Linux 2270×。
- **高竞争场景**：CortenMM adv 在 64 线程后不再扩展（因最末级 PT 页竞争），但在 384 核时仍优于 Linux：PF 3× 到 unmap 1489×。
- **与 RadixVM 比较**：RadixVM 在高竞争 PF 场景优于 CortenMM adv（per-core 私有页表避免缓存一致性流量），但 RadixVM 内存开销严重，且在 128 核后崩溃。CortenMM adv 在 128 核时优于 RadixVM 1.24×。

**真实应用基准测试**：
- **JVM 线程创建（384 核）**：CortenMM adv/rw 均优于 Linux 32%，归因于 page fault handler 的可扩展性瓶颈。
- **metis（384 核）**：CortenMM adv 优于 Linux 26×（CortenMM rw 15×），per-core 虚拟页分配器和高级 TLB shootdown 提供小幅收益。CortenMM adv 优于 RadixVM 1.24×（128 核，RadixVM 之后崩溃）。
- **dedup（ptmalloc）**：Linux 在 16 线程后无法扩展，CortenMM adv 在 64 线程时优于 Linux 2.69×。使用 tcmalloc 后两者均可扩展到 64 线程，但以更高内存使用为代价。
- **psearchy**：ptmalloc 下 CortenMM adv/rw 在 64 线程时优于 Linux ~2×；tcmalloc 下 Linux 性能改善但仍不及 CortenMM。

**内存开销**：CortenMM 与 Linux 内存开销相近。RadixVM 因页表复制而有显著额外开销。

**LMbench（需要枚举地址空间的操作）**：fork 时 CortenMM 比 Linux 慢 17.7%（需要遍历页表而非 VMA）；fork+exec 时快 23.0%（page fault 处理更快）；shell 基准测试两者相近。

**验证成本**：Verus 验证约 8 人月，代码行数 4868 行规格 + 1769 行实现，验证与代码比率 5.2:1。Verus 在 20 秒内完成验证。

**可移植性**：
- RISC-V：CortenMM 需要 252 行额外代码，Linux 需要 699 行。
- Intel MPK：CortenMM 需要 82 行，Linux 需要 273 行。
- Intel TDX：CortenMM 需要 368 行，Linux 需要 471 行。
- RISC-V 虚拟机中 32 线程性能差异与 x86-64 环境类似。

## 潜在问题 / 局限性

1. **ARM 支持缺失**：CortenMM 当前 OS 的 ARM 支持仍在开发中，尚未实际移植。虽然论文声称 ARM 符合设计假设（contiguous bit、break-before-make rule 不需要改变设计），但缺乏实际验证。这是一个重大缺口，考虑到 ARM 在移动和服务器市场的广泛使用。

2. **NUMA 策略支持缺失**：CortenMM 运行在 NUMA 系统上，但当前缺乏 NUMA 策略（如内存放置优化）。论文计划在 per-PTE 元数据数组中存储 NUMA 策略状态，但这尚未实现。对于 NUMA 敏感的 workload，这可能限制性能优势。

3. **地址空间枚举操作劣势**：fork 等必须遍历整个地址空间的操作，CortenMM 比 Linux 慢 17.7%，因为 Linux 可以直接从 VMA 树读取区域信息，而 CortenMM 需要遍历整个页表。这是消除软件层抽象的直接代价。

4. **形式化验证的局限性**：论文承认验证未与未验证代码链接（因 Rust nightly 特性冲突），且物理页建模为简单线性数组（而非真实 machine model）。验证覆盖了核心事务接口和锁协议，但物理页分配器、驱动等组件不在验证范围内。

5. **与其他工作的比较不完整**：论文主要与 RadixVM 和 NrOS 比较，但 RadixVM 在 128 核后崩溃，无法在完整 384 核上比较；NrOS 不支持按需调页，限制了功能对等性。此外，论文未与更近期的高级锁设计（如 Bonsai tree、scalable range locks）进行比较。

6. **单节点内存管理**：对于 NUMA 系统，缺少 NUMA-aware 内存策略，可能无法充分发挥硬件能力。

7. **验证方法的可扩展性**：8 人月的验证工作量对于生产系统来说仍然较高，验证与代码比 5.2:1 意味着每行代码变更都需要相应的证明更新，实际维护成本可能较高。

8. **时序报告偏差**：论文在单线程基准测试中宣称 CortenMM adv 优于 Linux 7.8% 到 76.9%，但 mmap 操作本身慢了 3.1%。虽然论文辩称 mmap 后通常需要 page fault 来真正分配页表，但这种选择性强调可能掩盖了某些操作的实际退化。

9. **公平性讨论不足**：论文未充分讨论在高度竞争场景下锁协议的公平性。在锁模式切换期间（MCS → Futex 队列），可能存在短期的非公平窗口。

## 未来工作

1. **ARM 完整支持**：移植 CortenMM 到 ARM 架构，验证 contiguous bit 和 break-before-make rule 不需要改变设计。
2. **NUMA 感知内存管理**：实现 NUMA 策略，将策略状态编码到 per-PTE 元数据数组中，优化内存放置。
3. **与其他同步原语的集成**：将 Preemption Monitor 技术应用于读写锁、条件变量、barrier 等其他同步原语。
4. **扩展验证范围**：将形式化验证扩展到更多组件，包括物理页分配器和与其他 OS 组件的链接。
5. **与其他 MMU 格式的兼容性**：探索将单层抽象设计扩展到非多级 radix tree 页表的 ISA。
6. **与现有操作系统的集成**：探索将 CortenMM 的核心思想（消除软件层抽象、事务接口）以更小改动的方式集成到 Linux 等成熟 OS 中。

## 个人评注

CortenMM 是一篇出色的 SOSP 2025 论文，荣获 Best Paper Award 实至名归。本文的核心洞察——"对于现代主流 ISA，软件层抽象已不再必要"——既简洁又具有深远意义。过去数十年，操作系统社区一直在两层抽象的框架内修修补补，每次性能优化都带来新的并发 bug。CortenMM 通过大胆消除软件层抽象，以更简单的设计同时解决了性能和正确性两个问题，这种"做减法"的思路令人耳目一新。

形式化验证的引入是本文的另一亮点。将 Verus 应用于 MMU 并发控制的验证，不仅提供了比测试更强的正确性保证，也展示了 Rust + SMT 验证在实际系统代码中的可行性。8 人月的验证投入虽然不小，但考虑到内存管理在系统安全中的关键地位，这是一项值得的投资。

然而，本文也存在一些值得关注的局限性。最主要的是 ARM 支持尚未实现，而 ARM 是移动和服务器市场的关键架构。此外，NUMA 策略缺失和 fork 操作的性能劣势也值得在实际部署中考虑。总体而言，CortenMM 为内存管理系统的未来设计提供了一个有价值的参考框架：对于追求极致性能和形式化保证的场景，单层抽象设计是值得认真考虑的方向。
