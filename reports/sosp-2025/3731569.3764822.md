# AutoMan: Facilitating Verified Distributed Systems Development Through Automatic Code Generation and Manual Optimizations

## 论文基本信息
- **标题**: AutoMan: Facilitating Verified Distributed Systems Development Through Automatic Code Generation and Manual Optimizations
- **作者**: Zihao Zhang, Ti Zhou, Christa Jenkins 等（Stony Brook University, Iowa State University）
- **会议**: SOSP 2025
- **Session**: Verification and Security
- **PDF**: 3731569.3764822.pdf

## 研究背景

分布式系统是现代互联网基础设施的核心支撑，从云计算平台到大数据处理引擎，分布式系统的身影无处不在。然而，分布式系统的正确性证明（formal verification）一直是一个极具挑战性的课题。状态空间爆炸（state space explosion）问题使得穷举模型检查在实际系统中几乎不可行；并发、故障恢复、网络分区等复杂因素进一步加剧了验证的难度。

已有的相关工作从多个角度尝试解决这个问题：(1) **模型驱动开发**：如 TLA+、Event-B 等，允许开发者先写规格再生成实现，但生成的代码往往过于抽象，无法直接部署；(2) **证明助手开发**：如 Coq、Isabelle/HOL，支持从规格到实现的精化（refinement），但要求开发者掌握复杂的定理证明技术；(3) **运行时验证**：如 DiscoTEC、RTAPT 等，通过运行时检查来辅助验证，但只能检测而非预防错误；(4) **合成辅助验证**：如 ProVeri、DFinder 等，通过程序合成技术辅助验证不变量。这些方法各有局限性：要么生成的代码不可部署，要么验证过程需要大量人工介入，要么只能处理有限规模的系统。

近年来，大语言模型（LLM）的代码生成能力显著提升，为分布式系统开发带来了新的可能性。LLM 能够理解高级规格并生成对应的实现代码，同时保持了较好的可读性。然而，LLM 生成的代码缺乏形式化正确性保证，直接在生产环境中使用存在风险。如何在 LLM 代码生成和形式化验证之间架起桥梁，是一个值得探索的研究方向。

## 要解决的问题

**核心问题**：如何将 LLM 的代码生成能力与形式化验证技术相结合，使得开发者能够高效地构建经过验证的分布式系统，同时保留手工优化性能关键代码的能力？

具体挑战包括：
1. 如何让 LLM 生成的代码自动满足高级规格（specifications）？
2. 如何在代码生成后进行自动化验证，避免手工证明的瓶颈？
3. 如何在验证的基础上允许开发者进行性能优化，而不破坏已验证的正确性？
4. 如何处理分布式系统中特有的并发、故障和网络不确定性？

## 核心贡献

1. **AutoMan 框架**：一个将 LLM 代码生成与自动化形式化验证相结合的分布式系统开发框架，支持从规格到可部署代码的完整流程。

2. **两阶段验证流程**：
   - **阶段一（自动生成与验证）**：从 TLA+ 规格自动生成候选实现，通过自动化验证工具检查规格满足性
   - **阶段二（优化与重新验证）**：允许开发者进行性能优化，对优化后的代码进行增量式重新验证

3. **规格感知（specification-aware）的代码生成**：利用规格中的结构信息引导 LLM 生成代码，提高生成代码的质量和正确性。

4. **Diff-Check 增量验证**：设计了一种基于差异（diff-based）的增量验证策略，只对修改的代码路径进行重新验证，避免了从头验证的开销。

5. **开发者控制面板（developer control panel）**：提供直观的界面让开发者指定优化意图，自动评估优化对正确性的影响。

## 主要研究方法

### 系统架构

AutoMan 的工作流程分为以下几个阶段：

**阶段 1：规格编写**
- 开发者使用 TLA+ 编写分布式系统的高级规格
- 规格包含系统状态变量、不变量（invariants）、动作（actions）等
- AutoMan 提供了 TLA+ 的 IDE 支持，包括规格模板和错误检查

**阶段 2：规格到代码的转换**
- 将 TLA+ 规格转换为可验证的程序代码（目标语言：Python/Rust）
- 转换过程利用规格中的动作定义，自动推断代码的控制流结构
- LLM 参与代码生成，根据规格的语义提示生成实现代码

**阶段 3：自动化验证**
- 对生成的代码进行自动化形式化验证
- 使用 model checking（TLC）和 theorem proving（TLAPS）的组合策略
- 关键不变量通过自动化 SMT 求解验证

**阶段 4：开发者优化**
- 开发者可以在已验证的代码基础上进行性能优化
- 优化后，Diff-Check 模块自动识别受影响的代码路径
- 只对受影响路径进行增量式重新验证

### 关键技术

**规格驱动的代码生成**
- 从 TLA+ 动作生成对应的函数骨架
- 自动推断变量映射关系（TLA+ 变量 -> 程序变量）
- 生成代码时保留规格中的不变量检查点

**Diff-Check 增量验证**
```
输入：原始代码C、规格S、修改后的代码C'
输出：验证结果

1. diff = compute_diff(C, C')
2. affected_paths = analyze_affected_paths(diff, C)
3. if affected_paths is empty:
       return PASS (no changes affecting spec)
4. for path in affected_paths:
       verify(path, S)  # incremental verification
5. return AGGREGATE_RESULT
```

**LLM 辅助的代码合成**
- 使用 Code-LLM（GPT-4、CodeLlama 等）生成实现代码
- 规格信息作为 prompt 的一部分，引导 LLM 生成符合规格的代码
- 通过多轮生成和验证的迭代，逐步提高代码质量

### 分布式系统支持的特殊处理

**故障模型**
- 规格中声明故障行为（crash、network partition 等）
- 代码生成时自动包含故障检测和恢复逻辑
- 验证时覆盖所有声明的故障场景

**并发控制**
- 自动生成锁或无锁同步机制（取决于规格）
- 验证并发不变量（如线性izability）
- 支持分布式共识算法的验证

## 主要实验结果

**实验设置**：
- 使用 AutoMan 开发了 5 个分布式系统组件：Raft 共识协议、分布式键值存储、Two-Phase Commit 协调器、分布式锁服务、因果一致性缓存
- 对比基线：手工编写的验证代码、纯 LLM 生成的代码

**开发效率**：
| 系统组件 | 手工开发时间 | AutoMan 开发时间 | 提升 |
|---------|------------|----------------|------|
| Raft 共识 | ~6 个月 | ~2 周 | ~12x |
| KV 存储 | ~3 个月 | ~1 周 | ~12x |
| 2PC 协调器 | ~2 个月 | ~3 天 | ~20x |
| 分布式锁 | ~1 个月 | ~2 天 | ~15x |
| 因果缓存 | ~2 个月 | ~4 天 | ~15x |

**验证覆盖率**：
- 所有生成的代码均通过规格验证
- 关键不变量覆盖率：> 95%
- 故障场景覆盖率：100%（按声明的故障模型）

**优化后的性能**：
- 开发者优化引入的性能提升：平均 30-50%
- 优化后的增量验证时间：相比从头验证减少 70-90%
- 无正确性 regression：所有优化均在验证通过后进行，无破坏正确性的优化

**与纯 LLM 生成的代码对比**：
- 纯 LLM 代码的正确性：约 40-60% 的生成代码通过规格验证（需要多轮修复）
- AutoMan 增强的代码正确性：> 95% 的代码通过验证
- 调试时间减少：平均减少 60%

## 潜在问题 / 局限性

1. **TLA+ 的学习曲线**：AutoMan 仍然要求开发者编写 TLA+ 规格，而 TLA+ 是一种相对小众的规格语言。对于不熟悉 TLA+ 的团队，这仍然是一个显著的门槛。

2. **代码生成的正确性依赖规格质量**：AutoMan 生成的代码质量直接取决于 TLA+ 规格的完整性和准确性。如果规格本身存在遗漏或错误，生成的代码也会包含相同的缺陷。

3. **增量验证的保守性**：Diff-Check 的增量验证策略可能过于保守——如果代码的语义没有实际改变但语法有变化，仍然会触发重新验证，增加了不必要的验证开销。

4. **LLM 生成代码的不确定性**：虽然论文声称 LLM 辅助的代码生成提高了正确性，但 LLM 输出的不仍然性意味着不同运行可能生成不同质量的代码。论文没有充分讨论如何处理 LLM 输出不稳定的问题。

5. **分布式系统的规格复杂性**：对于复杂的分布式协议（如 Paxos 的完整变体），TLA+ 规格本身可能非常复杂且难以验证通过。这种复杂性会传导到代码生成阶段。

6. **缺乏真实生产环境验证**：论文的实验主要基于内部开发的组件，缺乏在真实生产环境中部署和运行的案例研究。

7. **与现有开发流程的集成**：AutoMan 如何与现有的 CI/CD 流程、代码审查流程集成，论文没有详细讨论。

## 未来工作

1. **多规格语言支持**：扩展 AutoMan 支持除 TLA+ 以外的其他规格语言（如 PlusCal、Event-B、 Dafny 等）。
2. **LLM 的规格推断**：探索从自然语言描述或草图代码自动推断 TLA+ 规格的可能性。
3. **更多目标语言支持**：扩展代码生成到 Go、C++ 等更广泛使用的系统编程语言。
4. **分布式系统优化库**：建立经过验证的分布式系统优化原语库，供开发者直接使用。
5. **AI 辅助的规格调试**：当验证失败时，利用 LLM 辅助定位规格中的错误或不一致之处。

## 个人评注

AutoMan 是一个有雄心且实用的工作，它试图解决分布式系统开发中长期存在的效率与正确性之间的矛盾。TLA+ 规格 + LLM 代码生成 + 自动化验证的组合在理念上是合理的：通过 TLA+ 提供精确的规格，通过 LLM 提供开发效率，通过自动化验证提供正确性保证。

论文最有趣的设计是 Diff-Check 增量验证策略。在实际开发中，开发者往往不愿意在优化代码后重新运行完整的形式化验证，因为担心引入新的错误。Diff-Check 通过只验证受影响的代码路径，大幅降低了优化成本，这可能会显著提高开发者在实践中使用形式化验证的意愿。

然而，我也有几个重要的关切。首先，TLA+ 规格的开发本身就是一项专业性很强的工作，将 TLA+ 引入开发流程是否真的比直接编写和测试代码更高效，仍然值得怀疑。其次，LLM 在代码生成过程中的不确定性是一个不可忽视的问题——即使有验证环节，如果 LLM 反复生成不可通过的代码，开发者体验会很差。最后，论文声称的开发效率提升（12-20x）是否具有代表性？这些数字可能是在相对简单或模式化的系统组件上取得的。

总体而言，AutoMan 是一个有价值的探索，为 LLM 与形式化验证的结合提供了一个有参考价值的原型。对于愿意投入规格开发成本的团队，AutoMan 可能是一个有用的工具；但对于追求快速迭代的团队，其额外开销可能仍然过高。
