# AutoMan: Facilitating Verified Distributed Systems Development Through Automatic Code Generation and Manual Optimizations

**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles）
**链接**：https://doi.org/10.1145/3731569.3764822

## 一、背景

分布式系统是托管关键服务的基础设施，但即使经过严格测试，其设计和实现仍然极易出错，容易产生难以发现和复现的微妙 bug。形式化方法能提供比传统测试更强的正确性保证。目前有两种主流方法：（1）形式化验证（如 IronFleet），通过 refinement-based verification 保证实现正确，但需要大量专家工作量；（2）自动编译规约到实现（如 PGo），降低了开发工作量，但牺牲了严格的正确性保证——除非编译器本身被形式化证明是语义保持的。

TLA 风格的状态机规约在工业界和学术界被广泛采用（过去 15 年 OSDI/SOSP 中提供形式化规约的 10 个系统中有 9 个使用 TLA），包括 Amazon S3、DynamoDB、CosmosDB 等生产系统。Dafny 作为支持 refinement verification 的验证语言，在 IronFleet 中证明了其实用性。

---

## 二、要解决的问题

1. **形式化验证的高人力成本**：以 IronFleet 为例，手动实现 Multi-Paxos 需要约 8100 行代码，证明工作量巨大。交互式定理证明器（如 Coq）的 proof-to-code 比率高达 7.79–11.5×。
2. **自动编译方法的弱保证**：PGo 等工具能自动生成实现代码，但无法提供形式化正确性保证（除非证明编译器语义保持），且生成代码性能较差。
3. **两者难以兼得**：如何在降低人力成本的同时，保持形式化正确性保证和合理的性能？

---

## 三、洞察与设计

**关键洞察**：

1. **状态机 refinement 的结构天然支持自动化而不牺牲正确性**：TLA 状态机由独立的 action 组成，refinement 步骤中每个 action predicate 独立连接到对应的实现函数。这种结构将实现和验证分解为独立单元，使得工具可以逐 action 自动生成代码和 refinement proof obligations，且这些 obligations 通常简单到可以被 SMT solver 自动 discharge。
2. **分布式系统的性能通常由少数关键组件决定**：以状态机复制（SMR）为例，控制面（leader election、recovery）占代码量 76%–90% 但不影响稳态性能，数据复制面虽然代码量小却主导系统性能。

基于这两个洞察，AutoMan 的设计哲学是：先用机械化工具生成一个 correct-by-construction 的实现，然后选择性地对关键组件进行手动优化。整个工作流是四层 refinement 结构：$S_0 \leftarrow S_1 \leftarrow I_0 \leftarrow I_1$。

**工作流三步走**：
1. **自动翻译**（§3）：translator 将 Dafny TLA 规约中的每个 action predicate 自动翻译为 functional implementation + refinement proof obligations，生成 $I_0$。
2. **增量优化**（§4）：开发者根据 profiling 或领域知识，选择性地手动优化性能关键部分，生成 $I_1$。
3. **集成**（§4.3）：将 auto-generated 和 manually optimized 代码通过统一的 refinement 框架集成，保证端到端正确性。

**translator 设计要点**：
- 输入：Dafny TLA 规约 + 用户提供的 mode annotation（`+` 表示输入，`-` 表示输出）
- 五阶段流水线：Parser → Annotator → ModeValidator → Checker → CodeGenerator
- Mode checking 解决 TLA 规约中隐式的输入/输出区分、灵活的关系约束、非确定性等挑战
- 自动生成 Abstract 函数和 Valid 谓词用于建立实现类型与规约类型的对应关系

## 四、实现细节

**Translator（OCaml 实现）**：
- **Sanity Checking**：检查注解与规约匹配、禁止输出变量上的析取和存在量词（在 guard/contract 中允许）、禁止不支持的 Dafny 构造
- **Functionalizability Checking**：确保每个输出变量有且仅有一个候选赋值（assignment completeness & uniqueness）；建立依赖顺序；支持对集合类型的全称量词更新（需符合 ∀i :: P(i) ⟹ expr 模式）
- **Code Generation**：将 predicate 的候选赋值映射为局部变量声明，等式变为赋值，谓词调用变为函数调用，全称量词变为 collection comprehension
- **Refinement Scaffolding 生成**：自动生成 `requires`（输入有效性）、`ensures`（输出有效性 + refines 原规约）子句

**手动优化的典型模式**：
- **消除冗余遍历**：用辅助数据结构（hash set、indexed map）替代全称/存在量词产生的线性遍历
- **利用数据属性**：利用排序性等隐含语义属性，将线性搜索优化为二分搜索或直接索引
- **高效数据类型**：将 immutable 类型替换为 mutable 类型，避免频繁拷贝重构

**优化代码验证**：使用 ghost variable 镜像 mutable state 的演化，将正确性推理与命令式副作用解耦。每个 optimized action 独立验证后可无缝替换 auto-generated 版本。

## 五、实验结果

**案例研究**：Multi-Paxos、PBFT、Sharded KV Store、CausalMesh。

### 人力减少

| 系统 | $I_0$ 自动生成 (LoC) | $I_0$ 手动 (LoC/时间) | $I_1$ 手动 (LoC/时间) | 总手动 (LoC) | 对比基线 (LoC) | 减少比例 |
|------|--------|---------|---------|---------|---------|---------|
| AutoManRSL | 2,119 | ~200 / 4h | ~2,200 / 1周 | ~2,400 | IronRSL ~8,100 | $I_0$: 97%, $I_1$: 70% |
| AutoManKV | 1,487 | ~80 / 2h | ~1,100 / 3天 | ~1,180 | IronKV ~2,700 | $I_0$: 97%, $I_1$: 56% |
| AutoManPBFT | 2,430 | ~440 / 6h | ~2,400 / 1周 | ~2,840 | 无对应基线 | — |
| AutoManCausalMesh | 1,120 | ~110 / 4h | ~700 / 2天 | ~810 | 无对应基线 | — |

### 性能

| 系统 | $I_0$ 性能 | $I_1$ 性能 | 对比基线 |
|------|-----------|-----------|---------|
| Multi-Paxos | 峰值吞吐 = IronRSL 的 36% | 峰值吞吐 = IronRSL 的 97%（2.7× $I_0$） | IronRSL |
| PBFT | — | 2.04× $I_0$ 峰值吞吐 | 无手动基线 |
| Sharded KV | 90%+ IronKV 吞吐（无显著瓶颈） | ≈ IronKV（+8%） | IronKV |
| CausalMesh | — | 1.92× $I_0$（但仅为 Rust 版的 ~21%） | 原始 Rust 实现 |

- **故障恢复**：AutoManRSL-$I_0$、$I_1$ 和 IronRSL 均在 ~100ms 内完成 leader 故障恢复
- **vs PGo**：单线程 PaxosKV-$I_1$ 超越了多线程 PGo RaftKV 的吞吐
- **优化效果**：Multi-Paxos 中瓶颈 action 的 CPU 占用从 79% 降至 18%；PBFT 中从 61.2% 降至 18.2%

## 六、批判性分析

1. **CausalMesh 性能差距过大**：AutoManCausalMesh-$I_1$ 仅为原始 Rust 实现吞吐的约 21%（4.7× 差距），论文将此归因于 Rust 使用了 FxHashMap 和异步运行时，但这本质上说明 Dafny/C# 作为目标语言在性能敏感场景下的局限性。这个差距是否足以影响实际部署价值？论文未深入讨论。

2. **"70%–97% 减少"的衡量标准值得商榷**：论文用 LoC 衡量努力减少，但 LoC 不等于开发难度。手动优化的 ~2,200 行代码（Multi-Paxos $I_1$）涉及理解瓶颈、设计优化、编写 refinement proof，难度可能远高于同等行数的常规实现代码。此外，编写规约本身的工作量（IronRSL 的规约约 970+220 行）未被计入 AutoMan 的"人力成本"中。

3. **不支持存在量词描述状态转换的 action**：Multi-Paxos 有 2 个、PBFT 有 4 个 action 因使用存在量词而无法自动翻译，需要手动实现。论文轻描淡写了这一限制，但在更复杂的协议中，这类 pattern 可能更常见。

4. **不支持多线程**：论文承认不支持生成多线程程序，这在实际分布式系统中是严重局限。与 PGo 的对比中，PGo 的 RaftKV 利用多 goroutine 获得了更高的 CPU 利用率，而 AutoMan 生成的代码是单线程的。公平对比应在同等并行度下进行。

5. **案例研究的代表性有限**：四个案例均为经典的 consensus/replication 协议，且规约直接来自或改编自 IronFleet。对于更复杂的实际系统（如涉及复杂状态转换、外部交互、多层抽象的系统），AutoMan 的适用性尚未验证。

6. **translator 的 Dafny fragment 限制**：translator 仅支持 Dafny 的一个子集（禁止类、抽象模块、复杂泛型），且对 predicate 的约束模式有严格要求。论文声称这个 fragment "expressive enough"，但仅通过四个案例来支撑这一论断说服力有限。

---

## 七、总结

AutoMan 提出了一种混合方法论，通过自动代码生成降低从 TLA 规约到实现的人力成本（70%–97%），同时通过 refinement-based verification 保持端到端的形式化正确性保证。其核心思想——自动生成大部分代码、选择性手动优化关键路径——在 Multi-Paxos 等经典协议上展现了实用性，优化后性能可达手动实现的 97%。主要局限包括不支持多线程、仅覆盖 Dafny 子集、部分含存在量词的 action 仍需手动实现，以及在目标语言（C#）性能不佳的场景下与原生实现差距较大。
