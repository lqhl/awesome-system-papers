## 一、背景

OS 级别的 checkpoint and restore (C/R) 是操作系统的基础原语，广泛用于集群管理中的进程迁移、serverless 的快速冷启动、以及周期性容错。其核心优势在于对应用完全透明——云厂商无需了解租户作业的内部实现即可完成迁移。

CPU 侧的并发 C/R（在 checkpoint/restore 数据拷贝期间允许进程继续执行）已经研究了数十年，利用 page table 的 dirty bits、copy-on-write、on-demand restore 等机制实现。然而，GPU 侧的并发 C/R 一直未被实现。随着 GPU 成为 AI 训练和推理的核心，C/R 过程中 GPU 停顿造成的性能损失日益严重：Microsoft 报告超过 3.9% 的 GPU 用户受迁移停顿影响；Llama2-13B 推理的 restore 停顿达 6.2 秒，是 TTFT 的 31 倍；训练中 checkpoint 时间占迭代时间的 46–87%。

---

## 二、要解决的问题

1. **GPU 缺乏并发 C/R 的硬件支持**：CPU 可以通过 page table dirty bits 追踪写入、通过 copy-on-write 隔离并发写入、通过 present bits 实现 on-demand restore。GPU 没有这些机制——没有硬件 dirty bits，数据路径绕过 OS 直接访问显存。

2. **现有系统是 stop-the-world 方式**：NVIDIA cuda-checkpoint 和 Singularity 都需要停止 GPU 执行后才能拷贝数据。GPU 数据量巨大（如 Llama2-13B 推理占 55GB 显存），通过 PCIe 4.0 拷贝至少需要 1.7 秒。

3. **GPU context 创建开销巨大**：restore 前需要创建 GPU context（编译 kernel、配置虚拟内存等），开销与数据拷贝相当（3.1 秒 vs 1.7 秒），形成恢复瓶颈。

4. **正确性保证困难**：并发 checkpoint 时，进程可能覆盖未 checkpoint 的数据；并发 restore 时，kernel 可能读取尚未恢复的数据。追踪 GPU 执行的 read/write set 是确保正确性的关键，但用户自定义 kernel 的代码对 OS 不透明。

---

## 三、洞察与设计

**关键洞察**：与 CPU 执行对 OS 完全黑盒不同，GPU 的执行由细粒度的 GPU API 调用（如 CUDA API）组成，这些调用经过 OS 中介。每个 API 调用触发细粒度的 GPU 状态修改，因此 OS 可以通过拦截这些 API 来追踪其 read/write set。更关键的是，虽然用户自定义的 opaque kernel 代码不可知，但每个 kernel 通常服务于明确的计算目的，其访问的数据地址直接编码在 OS 可见的 kernel launch arguments 中——因此可以通过分析 launch arguments 来推测（speculate）kernel 访问的 buffer。

基于此洞察，PHOS 的核心设计分为三层：

**Validated Speculation 追踪机制**：将 GPU API 分为四类——(1) 内存拷贝（cudaMemcpy，write set 明确）；(2) 通信 kernel（ncclBroadcast，write set 明确）；(3) 语义明确的计算 kernel（cublasSgemm，write set 在 spec 中定义）；(4) opaque 用户 kernel（通过 launch arguments 推测 write set）。对于第 4 类，将 mutable pointer 类型的参数与进程已分配的 buffer 地址范围比对，命中即标记为写入。同时对 kernel binary 进行一次性的 PTX 级 instrumentation，生成 twin kernel 用于运行时验证推测是否正确。

**并发 Checkpoint 协议**：
- Soft Copy-on-Write (CoW)：在 t1 时刻 quiesce 后恢复执行，并发拷贝期间若 kernel 要写入未 checkpoint 的 buffer，先将其拷贝到备份位置再允许写入，保证 checkpoint 反映 t1 的状态。
- Soft Recopy：并发拷贝期间追踪所有 dirty buffer，拷贝完成后 re-quiesce 并重新拷贝 dirty buffer，保证 checkpoint 反映 t2（拷贝完成时）的状态。

**并发 Restore 协议**：允许进程在数据尚未完全恢复时执行。执行 kernel 前检查其 read set 是否已恢复——若未恢复则先拷贝所需 buffer 再执行，类似 CPU 的 on-demand paging。同时用 GPU context pool 预创建 context 以消除 context 创建延迟。

## 四、实现细节

- **代码量**：54,839 LoC（C++ 和 Rust），不含 CUDA GPU driver 扩展框架、通信库和 CRIU 集成。
- **API 拦截**：通过 LD_PRELOAD 扩展 CUDA GPU API（因 CUDA 闭源）。frontend library 嵌入 GPU driver 和 toolkit 中，拦截所有 GPU API 调用。
- **Speculation 实现**：使用 clang 提取 kernel 函数签名，过滤出 mutable pointer 参数；对于 C struct 类型参数保守地将所有 8 字节 chunk 视为潜在 buffer 指针。
- **Validation 实现**：PTX ISA 级 instrumentation，每种 kernel binary 只 instrument 一次。instrumented twin kernel 在每条 write 指令前插入地址范围检查，失败时将违规地址写入预分配的 PHOS managed CPU buffer。
- **Coordinated Checkpoint**：先拷贝 CPU 数据再拷贝 GPU 数据，缩短 GPU dirty window。
- **Prioritized PCIe Transfer**：checkpoint 拷贝以 4MB chunk 为单位，每个 chunk 之后检查是否有应用 DMA 请求待执行，若有则让路。
- **GPU Context Pool**：PHOS daemon 在启动时预创建 CUDA、cuBLAS context 和 NCCL group communicator。应用创建 context 时直接从 pool 分配。pool 运行在独立进程空间，应用通过 IPC 访问（IPC 开销在典型 AI 应用约 9%）。
- **CPU C/R**：基于 CRIU，支持 checkpoint 到 SSD、DRAM 或通过 RDMA 到远程 DRAM。
- **多 GPU 支持**：quiesce 扩展到所有进程的 CPU 和 GPU；live migration 用 GPUDirect RDMA 直接从源 GPU buffer 拷贝到目标 GPU buffer。

## 五、实验结果

**平台**：A800 服务器，8× NVIDIA A800 (80GB HBM, 400Gbps NVLink)，2× Intel Xeon Gold 6348 (56 cores)，1TB DRAM，100Gbps RDMA，CUDA 11.3。

**基线**：NVIDIA cuda-checkpoint、Singularity（state-of-the-art stop-the-world GPU C/R，作者在自己代码库中实现并调优）。

**评测工作负载**：

| 工作负载 | 模型 | 模式 |
|---------|------|------|
| ResNET-152M | 152M 参数 | 训练/推理 |
| PPO-336M | 336M 参数 | 训练 |
| Stable-Diffusion-1B | 1B 参数 | 训练/推理 |
| Llama2-13B | 13B 参数 | 训练(多GPU)/推理 |
| Llama3.3-70B | 70B 参数 | 推理(多GPU) |

**关键结果**：

| 场景 | 指标 | PHOS vs Singularity |
|------|------|-------------------|
| Checkpoint 停顿 | Llama2-13B Training | 185ms vs 3.2s（减少 70–160%） |
| 容错 GPU 浪费时间 | 各训练负载 | 节省 22–86% |
| 最优 checkpoint 频率 | Llama2-13B | 279次/小时 vs 67次/小时 |
| Live Migration 停顿 | Llama2-13B Training | 3.3s vs 10.2s |
| Live Migration 停顿 | Llama3.3-70B Inference | 3.7s vs 12.35s |
| Serverless 冷启动 | 推理负载平均 | 比 Singularity 快 16×，比 cuda-checkpoint 快 24× |
| Llama2-13B 推理启动 | Serverless | 622ms |
| Runtime Validation 开销 | 各工作负载 | 1–12% slowdown |
| Instrumented kernel 占比 | Llama2-13B Inference | 仅 12% |
| Speculation 失败率 | 全部常见 GPU 应用 | 0 failure |

**Speculation 可行性研究**：在 Rodinia、Parboil、vLLM、TVM、FlashInfer 等多样化 GPU 应用上测试，共 804 个 kernel、307,217 个实例，仅 Rodinia 中 1 个老旧 kernel 的 20 个实例发生推测失败（kernel 读取了 global variable 引用的 buffer，未出现在 launch arguments 中）。

## 六、批判性分析

1. **Speculation 失败处理过于简单**：当前策略是丢弃 checkpoint 并回退到 stop-the-world 方式重试。对于 restore 失败，甚至回退到初始状态重做 stop-the-world restore。作者承认这是"simple retry strategy"并留作 future work，但这意味着在新型 kernel（如使用 indirect access）的场景下，系统可能退化为 stop-the-world 性能，却仍承担了 speculation + validation 的额外开销。

2. **Speculation 可行性评估的覆盖面有偏**：Table 3 的成功率看似很高（804 个 kernel 中仅 1 个失败），但测试的应用以 AI 工作负载为主，这些应用天然倾向于使用规范的 buffer 访问模式。对于 HPC、科学计算、图形渲染等领域的 GPU kernel，indirect access 和 shared memory 的使用更为普遍，speculation 的可行性可能显著下降。

3. **Context Pool 的 IPC 开销被淡化**：论文提到 context pool 运行在独立进程空间，应用通过 IPC 调用 GPU API，开销最高达 9%。这个开销在 restore 之后的整个应用生命周期内持续存在，对于长时间运行的训练任务，累积的性能损失可能相当可观，但论文未给出长期运行场景的分析。

4. **CoW 协议的显存压力**：soft CoW 需要在 GPU 显存中预留空间（最多 2GB），对于显存紧张的大模型训练（如 Llama2-13B 已占用绝大部分显存），这个额外开销虽然论文分析了影响不大（无 buffer 时仅多 9.1% stall），但在更大模型或更紧张的显存场景下可能成为瓶颈。

5. **基线对比的公平性**：cuda-checkpoint 被描述为"extremely slow"且无法分析源码，但论文自己实现了 Singularity 作为主要对比基线。自己实现的基线是否能代表 Singularity 的最佳性能存疑——尽管作者声称做了仔细调优。

6. **多进程一致性依赖用户 hint**：容错场景下跨进程的全局一致 checkpoint 需要用户提供 hint（如在每次训练迭代的 forward pass 前），这削弱了"对应用完全透明"的声明。

## 七、AI Infra / MLSys 视角

1. **对 GPU checkpoint 研究的启发**：PHOS 证明了通过 API 拦截 + argument speculation 可以在不修改硬件、不修改应用的情况下实现 GPU 并发 C/R。这个方法论可以推广到其他需要追踪 GPU 内存访问的场景，如 GPU 内存管理、显存压缩、GPU memory oversubscription 等。

2. **对 LLM 推理服务的价值**：622ms 的 Llama2-13B 冷启动时间对 serverless GPU inference 非常有意义。当前 vLLM 等推理框架的冷启动受限于 model loading 和 CUDA context 初始化，PHOS 的 context pool + concurrent restore 思路可以直接集成到推理框架中优化冷启动。

3. **与 user-level checkpoint 的对比**：论文指出 PHOS 甚至优于 torch.checkpoint（user-level），这暗示 OS-level C/R 在 emerging training frameworks（如 RLHF、agent training）中可以作为零成本的容错方案，替代需要侵入式修改代码的 user-level 方案。

4. **值得跟进的方向**：
   - **GPU dirty bits 的硬件支持**：论文证明了并发 GPU C/R 的价值，GPU 厂商有动力在未来硬件中加入 dirty bits 支持（类似 GPU snapshot 论文的模拟研究），这将大幅简化实现并提升性能。
   - **与 disaggregated memory / CXL 的结合**：checkpoint 数据如果可以通过 CXL 以更高带宽传输到远程内存，PHOS 的并发 C/R 优势将进一步放大。
   - **面向 MoE 模型的优化**：MoE 模型的稀疏激活特性意味着 checkpoint 时只需保存被激活 expert 的状态，speculation 机制可以用于识别哪些 expert buffer 被修改。

---

## 八、总结

PHOS 是首个支持 GPU 并发 checkpoint 和 restore 的 OS 级系统，通过 validated speculation（基于 GPU API launch arguments 推测 kernel 的 read/write set，辅以 binary instrumentation 验证）将 CPU 侧成熟的并发 C/R 技术（CoW、recopy、on-demand restore）移植到 GPU 上。在 A800 服务器上的评测表明，PHOS 在容错、live migration、serverless 冷启动三个场景均实现了数量级的性能提升。主要局限在于 speculation 失败处理机制简单、context pool 引入持续的 IPC 开销、以及全局一致 checkpoint 仍依赖用户 hint。
