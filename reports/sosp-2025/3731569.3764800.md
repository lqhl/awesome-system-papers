# How to Copy Memory? Coordinated Asynchronous Copy as a First-Class OS Service

## 论文基本信息

- **标题**: How to Copy Memory? Coordinated Asynchronous Copy as a First-Class OS Service
- **作者**: Jingkai He, Yunpeng Dong, Dong Du, Mo Zou, Zhitai Yu, Yuxin Ren, Ning Jia, Yubin Xia, and Haibo Chen
- **会议**: SOSP 2025
- **Session**: OS Memory Management
- **PDF**: 3731569.3764800.pdf
- **奖项**: Best Paper Award

## 研究背景

内存复制（Memory Copy）是现代操作系统和应用中无处不在的操作，贯穿于系统调用、进程间通信（IPC）以及用户态应用程序的各个层面。在内存密集型和 I/O 密集型工作负载中，内存复制性能成为关键瓶颈。以 KV 存储、代理服务器、存储服务为例，内存复制消耗的 CPU 周期高达 66.2%；在 Google 数据中心的全系统层面，复制操作消耗了 4%-5% 的总周期数。

尽管学术界和工业界已经为优化内存复制付出了大量努力，但现有方案仍然面临显著的局限性。硬件加速方案（如 SIMD 指令和 DMA）无法被应用程序和内核充分利用率——内核因为保存/恢复 SIMD 寄存器状态的开销过高而无法使用 AVX，而用户态应用则因为 DMA 需要特权操作（MMIO）而难以利用。零复制（Zero-Copy）方案依赖页重映射或共享内存，存在安全风险（TOCTTOU 攻击）、页对齐要求、对多副本场景支持不足等问题。例如 Linux zero-copy send() 仅对大于等于 10KB 的消息有效；zIO 需要大于等于 16KB 才能带来收益。然而生产环境中的数据分布表明：Twitter memcached 请求中 95.1% 不超过 10KB，阿里云块服务的请求中 69.8% 在 4KB-10KB 之间。这说明现有的优化方案与实际数据分布存在严重错配。

## 要解决的问题

论文的核心问题是：**如何将异步内存复制作为一个一等（first-class）操作系统服务来提供，从而在保持正确性和安全性的前提下，充分挖掘硬件能力并实现系统级的整体优化？**

具体而言，面临三个关键挑战：
1. **从同步到异步**：如何充分利用异步复制带来的性能收益，同时保持与同步复制相同语义？
2. **从函数到 OS 服务**：如何充分利用 SIMD/DMA 等硬件能力，同时以最小额外开销实现全局视图优化？
3. **从单一客户端到多客户端**：如何确保资源隔离、公平性和正确性？

## 核心贡献

- **首次提出将内存复制作为独立 OS 服务的概念**：将异步复制抽象为 OS 级别的一等服务（类似于文件系统和网络），提供 amemcpy() 和 csync() 编程原语，而非分散在各个库函数中。
- **Copy-Use 流水线设计**：利用"从复制完成到数据首次使用之间的时间窗口"（Copy-Use Window），实现复制与计算的流水线重叠。小型复制（1KB）场景下，异步复制可将吞吐量提升最高 13 倍。
- **硬件能力充分利用**：通过piggyback 调度器协调 AVX 和 DMA 异构复制单元并行执行，结合地址转换缓存（ATCache）降低 DMA 虚拟地址转换开销，吞吐率提升最高 158%。
- **跨特权层复制吸收（Copy Absorption）**：利用全局视图识别跨用户态/内核态的冗余中间复制，将其合并为"短路"直接复制，Redis 等场景下可消除不必要的中间副本。
- **资源公平调度**：基于 cgroup 扩展的 Copier 调度器，以复制长度而非 CPU 时间片作为资源单位，确保多客户端场景下的公平性与隔离性。
- **主动故障处理**：通过 VMA 和页表预取、锁映射等机制，将复制过程中的页故障从关键路径中移除。

## 主要研究方法

论文采用系统研究的经典方法：通过系统性测量揭示问题的普遍性和严重程度，再提出针对性解决方案。

**测量分析阶段**：使用 perf 工具对 Linux 上多种常用应用（Redis、zlib、OpenSSL、Nginx、libpng、ffmpeg）和 HarmonyOS 5.0 智能手机上的系统服务进行 CPU 周期分析，量化复制操作在其中的占比。实验揭示了 Copy-Use Window 的普遍存在——在 Protobuf、Redis、Binder IPC、OpenSSL 等场景中，Copy-Use Window 通常是实际复制时间的 2-10 倍，为异步优化提供了充足空间。

**方案验证阶段**：对 Copier 进行了全面评估，包括微基准测试（复制吞吐率、系统调用延迟）、应用基准测试（Redis、TinyProxy、Protobuf、OpenSSL、zlib、Avcodec）以及在商业手机操作系统 HarmonyOS 5.0 上的生产部署验证。

**形式化验证**：使用 rely-guarantee 模拟关系（RGSim）证明 amemcpy+csync 的语义与同步 memcpy 在单线程和多线程上下文中的语义等价性，确保正确性。

## 设计与实现

**Copier 架构**包含以下几个核心组件：

**1. 队列抽象（Queue-based Abstractions）**：
- 为每个进程维护三组 CSH（Client-Service Handler）队列：CopyQueue（异步复制任务）、SyncQueue（优先级调整/任务同步）和 HandlerQueue（完成回调处理）。
- 队列实现为无锁环形缓冲区（基于 fetch-and-add），支持高吞吐率提交（单队列超过 130K 任务/秒）。
- 提供 segment-based copy：将大型复制任务分割为固定大小的段（segment），以位图（bitmap）跟踪每个段的完成状态，实现细粒度的 Copy-Use 流水线。

**2. 依赖追踪（Dependency Tracking）**：
- **顺序依赖（Order Dependency）**：通过系统事件（如 syscall trap 和 return）作为 barrier 指示器，追踪跨用户态/内核态队列的任务顺序。
- **数据依赖（Data Dependency）**：通过反向遍历 CopyQueue 并比较源/目的地址区间，判断任务间的数据依赖关系，防止 Out-of-Order 执行导致的数据错误。

**3. Piggyback 调度器**：
- 将 DMA 子任务"piggyback"到 AVX 任务上并行执行：先批量提交 DMA 子任务到设备队列，再执行 AVX 子任务，最后确认 DMA 完成。避免了 CPU 等待 DMA 完成而浪费周期。
- 对于小于 12KB 的任务，采用 i-piggyback（任务内部分配）；对于小任务，采用 e-piggyback（跨任务合并）。
- ATCache（Address Translation Cache）：缓存虚拟地址到物理地址的转换结果，利用应用端地址高度局部性（Redis 超过 75% 的地址重复率）将 DMA 地址转换开销降低 2%-11% 的吞吐率提升。

**4. 复制吸收（Copy Absorption）**：
- Layered Absorption：利用 segment 位图判断已完成的段是否被修改，动态选择从最新数据源复制（可能是中间缓冲区而非原始源），合并 K→I 和 I→D 为 K→D 直连。
- LazyCopy：允许将中间复制任务标记为最低优先级，仅作为复制吸收的"协调者"而非实际执行者。

**5. 资源管理与公平调度**：
- Copier 调度器基于 CFS（完全公平调度器）策略，按总复制长度分配服务优先级。
- cgroup 扩展：以复制长度作为资源单位（copier.shares），兼容现有 OS 生态。
- 主动故障处理：通过 VMA 和页表预取锁定映射，避免在 Copier 自身上下文中触发页故障。

**实现**：基于 Linux 5.15.131（Copier-Linux），约 2000 行代码；同时集成到华为 HarmonyOS 5.0（Hongmeng 内核）。提供了 libCopier 开发库、CopierSanitizer 调试工具和 CopierGen 自动移植工具链。

## 主要实验结果

**微基准测试**：
- 复制吞吐率：Copier 相比内核默认 ERMS 提升最高 158%（4KB 数据），相比用户态 AVX2 提升最高 38%（无缓冲区重复时）。在 75% 缓冲区重复率下，吞吐率提升 63%（对比 ERMS）和 32%（对比 AVX2）。
- send()/recv() 系统调用：Copier 使 recv 延迟降低 16%-92%（batch 模式下降低 55%-93%），send 延迟降低 7%-37%。
- Android Binder IPC：Copier 将端到端延迟降低 9.6%-35.5%（消息数量 10-800 范围内）。
- CoW 处理：Copier 将 2MB 页的每次页故障平均阻塞时间降低 71.8%，4KB 页降低 8.0%。

**应用基准测试**：
- **Redis**：相比 baseline，Copier 将 SET 延迟降低 2.7%-43.4%，GET 延迟降低 4.2%-42.5%；P99 尾延迟分别降低 5.9%-33.4% 和 5.59%-47.8%；吞吐率提升 2.4%-50.0%（SET）和 4.2%-32.0%（GET）。相比 zIO（16KB 阈值），Copier 在中小型数据（4KB-64KB）场景下全面胜出。
- **TinyProxy 代理**：吞吐率提升 7.2%-32.3%，归因于 copy absorption 将三次复制合并为一次。
- **Protobuf**：接收和反序列化平均延迟降低 4%-33%。
- **OpenSSL（AES-GCM）**：SSL_read() 延迟降低 1.4%-8.4%。
- **zlib**：压缩速度提升最高 18.8%（256KB 数据，deflate_fast()）。
- **Avcodec（HarmonyOS）**：视频解码延迟每帧降低 3%-10%，播放丢帧率降低最高 22%，能耗仅增加 0.07%-0.29%。

**性能分解**：
- 小型复制（1KB）：异步复制贡献主要收益（可完全重叠）。
- 大型复制（256KB）：硬件加速和复制吸收同样发挥重要作用。

**全系统资源利用**：在 4 核限制场景下，当存在空闲核时 Copier 同时优化延迟和吞吐率；当核心完全利用时（Redis 8KB/16KB 值），延迟仍降低 17.4%-18.8%，但吞吐率因 polling 开销下降 4.3%-6.5%。对于 copy chains 场景（如 TinyProxy），即使满载也能提升吞吐率 7.7%。

**开发成本**：使用 CopierSanitizer 和工具链，研究生需要 1-2 周移植复杂应用（Redis、TinyProxy），1-2 天移植简单应用（zlib、Protobuf）。

## 潜在问题 / 局限性

**1. 基准比较的局限性**：
论文主要与 Linux 默认 ERMS、io_uring batch 和 zIO 进行比较，但与直接使用 AVX+DMA 手动优化的用户态 memcpy 实现（而非通过 OS 服务调用）的比较较少。在用户态可以直接使用 AVX 的场景下，Copier 的优势主要来自异步性和 copy absorption，而非硬件利用效率。

**2. 异步编程负担**：
尽管提供了工具链，csync 的正确使用仍然需要开发者理解 Copy-Use 语义并手动插入同步点。论文承认"过度频繁的 csync（如逐字节 csync 或重复同步同一数据）可能导致性能下降"，但未给出具体的阈值指导。虽然基于实践总结了四条指南（直接数据访问、缓冲区释放、外部库调用、外部线程可见性），但缺乏自动化的最优 csync 插入策略。

**3. Polling 开销**：
Copier 的 io_uring SQPOLL 模式会消耗 CPU 周期。论文坦诚当 CPU 资源完全利用时，对于延迟敏感应用有收益，但对吞吐敏感应用可能带来 4%-6.5% 的吞吐率下降。这在实际部署中需要根据场景权衡，且当前缺乏自动决策机制（是否启用 Copier）来适应工作负载变化。

**4. Copy-Use Window 依赖性**：
Copy-Use Window 的有效性取决于具体应用的数据访问模式。论文主要验证了顺序访问模式，对于随机访问或访问模式不规律的应用，Copier 的收益可能有限甚至为负。论文在 §4.6 承认"Copier 不适合随机访问数据的应用"，但缺乏对访问模式自动识别和动态回退到同步复制的机制。

**5. 与现有优化方案的叠加效果**：
Copier 的 copy absorption 机制与 zIO 的 on-demand copy 优化存在一定功能重叠。在同时使用两者时（例如在内核中集成 Copier 的同时应用使用 zIO），是否能进一步叠加收益，或者存在干涉，论文未做讨论。

**6. 商业部署成熟度**：
虽然在 HarmonyOS 5.0 上有实验性部署，但 Copier 的生产部署需要修改 OS 内核（约 2000 行代码）并管理独立的 kthread，其稳定性、与其他内核子系统的交互（如 NUMA、内存压缩、swap 等）在论文中未充分讨论。

**7. 实验平台略显陈旧**：
论文使用 Xeon E5-2650 v4（Broadwell，2016年发布）和 Kirin 9000S（2023年），未在最新硬件平台（如 Sapphire Rapids、Zen 5）上验证。SIMD 能力（AVX-512 vs AVX2）和 DMA 引擎（Intel DSA vs I/OAT）在不同代际上的表现差异可能影响 Copier 的相对收益。

## 未来工作

- **硬件原语集成**：将 Copier 的核心能力进一步集成到 CPU ISA 内存复制原语或内存控制器功能中，降低 polling 的 CPU 消耗。
- **更广泛的应用场景**：探索 Copier 在文件 I/O、设备虚拟化、分层内存管理、解聚内存（disaggregated memory）等场景的应用。
- **安全增强**：在互不信任的组件之间提供安全高效的数据传递方法，扩展 Copier 在 LionsOS 等安全操作系统中的应用。
- **自动化移植工具 CopierGen**：当前仅支持基本数组场景，未来需要支持复杂应用（如涉及指针传递的场景）。

## 个人评注

**总体评价**：这是一篇扎实的系统论文，获得了 SOSP 2025 Best Paper Award，实至名归。论文的核心贡献——将异步复制提升为一等 OS 服务的思想——具有重要的范式意义。Copy-Use Window 的洞察简单但深刻：大多数应用在复制完成和数据使用之间存在天然的时间间隔，这一观察为异步化提供了坚实的性能基础。

**亮点**：
1. **问题定义精准**：没有泛泛地谈"内存复制很慢"，而是通过系统性测量揭示了现有优化方案的适用范围（仅对大消息有效）与实际数据分布（中小消息占主流）之间的根本矛盾。
2. **工程完整度高**：不仅提出了设计，还提供了完整的工具链（libCopier、CopierSanitizer、CopierGen）和生产级部署验证（HarmonyOS 5.0），而非停留在原型阶段。
3. **形式化验证**：通过 rely-guarantee 模拟关系证明语义等价性，为异步编程模型的正确性提供了理论保障，这是一个值得称赞的做法。

**不足**：
论文最大的遗憾在于对"何时不应该使用 Copier"缺乏自动决策机制。在 CPU 完全利用的场景下，Copier 的 polling 开销可能得不偿失，但这一决策目前留给应用开发者手动判断。未来工作如果能实现基于启发式的自动启用/禁用 Copier，将大幅提升其可用性。

**对领域的影响**：Copier 的思想可能会启发更多 OS 基础服务的异步化重构——将那些原本在关键路径上阻塞的操作（不仅是内存复制，还可能是地址空间操作、权限检查等）转化为可流水线化的一等服务。这一范式转变的潜力值得持续关注。
