# How to Copy Memory? Coordinated Asynchronous Copy as a First-Class OS Service

**作者**：Jingkai He, Yunpeng Dong, Dong Du, Mo Zou, Zhitai Yu, Yuxin Ren, Ning Jia, Yubin Xia, Haibo Chen（上海交通大学 / 华为技术有限公司）

## 一、背景

内存拷贝（memory copy）是现代操作系统中普遍存在的性能瓶颈，广泛存在于系统调用（send/recv）、IPC、用户态应用等场景。Google 数据中心中约 4-5% 的 CPU 周期消耗在内存拷贝上。对于 I/O 密集型和内存密集型应用（如 Redis、代理服务器、存储服务），拷贝可占用高达 66.2% 的 CPU 周期。

现有的优化方案主要分为两类：硬件加速拷贝（SIMD、DMA）和 zero-copy（页面重映射/共享内存）。然而，它们各自存在局限性，无法作为通用解决方案。

---

## 二、要解决的问题

1. **硬件能力未被充分利用**：Linux 内核无法使用 SIMD（如 AVX）进行拷贝，因为保存/恢复寄存器状态的开销过大（数 KB）；用户态应用无法使用 DMA，因为需要特权操作（MMIO）。
2. **Zero-copy 方法适用范围有限**：要求页对齐、仅支持 ≥10KB（Linux zero-copy send）或 ≥16KB（zIO）的大消息、不支持多副本场景、存在 TOCTTOU 安全风险、共享缓冲区管理复杂。
3. **缺乏全局视角的拷贝优化**：现有方案各自为战，针对特定场景，无法跨特权级、跨地址空间进行全局拷贝优化和冗余消除。
4. **同步拷贝阻塞计算**：传统 memcpy 是同步的，数据拷贝期间应用完全阻塞，无法利用拷贝与使用之间的时间窗口。

---

## 三、洞察与设计

**关键洞察**：在拷贝密集型应用和内核服务中，普遍存在 "Copy-Use 窗口"——即数据被拷贝完成到首次被使用之间存在充分的时间间隔（通常是拷贝耗时的 2-10 倍）。这是因为程序通常批量拷贝数据但逐片使用。利用这个窗口，可以将拷贝从关键路径上移除，实现异步拷贝与计算的重叠。

基于此洞察，论文提出 **Copier**——一个将内存拷贝提升为一等 OS 服务的系统，核心设计包括：

### 1. 队列式异步抽象（CSH Queues）
- **CopyQueue**：客户端提交异步拷贝任务，支持 segment 粒度的进度更新，实现细粒度的 copy-use pipeline
- **SyncQueue**：支持 out-of-order 执行（任务提升），解决 FIFO 队列的 head-of-line blocking
- **HandlerQueue**：委托式后处理，拷贝完成后自动执行回调（如释放源缓冲区）

### 2. 依赖追踪
- **顺序依赖**：利用 syscall trap/return 事件作为 cross-queue barrier 指示器，在用户态和内核态队列间建立正确的执行顺序
- **数据依赖**：通过反向遍历 CopyTask 并比较内存区域来检测重叠，确保 SyncTask 的正确性

### 3. Piggyback 调度器
将 DMA 任务搭载（piggyback）到 AVX 任务上并行执行，重叠 DMA 拷贝和 AVX 拷贝，避免空等 DMA 完成。利用异步任务队列的特性，将多个小拷贝融合到同一轮 piggybacking 中执行。

### 4. 分层拷贝吸收（Layered Copy Absorption）
利用全局视图识别并消除冗余的中间拷贝。数据在拷贝链 A→B→C 中，如果 B 在被拷贝到 C 之前未被修改的部分可以直接从 A 拷贝到 C，跳过中间步骤。

### 5. 公平调度与隔离
基于 cgroup 扩展，以拷贝长度为资源单位实现客户端间的公平性和隔离。设计主动故障处理（proactive fault handling），避免在 Copier 上下文中触发页面错误。

## 四、实现细节

- **Copier-Linux**：基于 Linux 5.15.131 实现，Copier 作为独立内核线程运行，使用一个专用 CPU 核心
- **编程接口**：`amemcpy(dst, src, n, handler)` 提交异步拷贝，`csync(addr, n)` 在使用前同步数据
- **工具链**：
  - **libCopier**：用户态库，封装高层 API
  - **CopierSanitizer**：基于 AddressSanitizer 的 bug 检测工具，用影子内存追踪未 csync 就访问的数据
  - **CopierGen**：基于 LLVM/MLIR 的实验性编译器，自动在 IR 层插入 csync
- **适配场景**：网络栈 send/recv、CoW 故障处理、Android Binder IPC、HarmonyOS 5.0 视频编解码
- **segment 粒度**：拷贝被分割为固定大小的 segment，通过 bitmap descriptor 追踪每个 segment 的完成状态
- **形式化验证**：使用 RGSim（rely-guarantee simulation）证明 async copy + csync 与 sync copy 的语义等价性

## 五、实验结果

实验平台：2× Xeon E5-2650v4 (2.9GHz)，128GB DDR4，Linux 5.15.131。智能手机实验使用华为 Mate 60 Pro（Kirin 9000S + HarmonyOS 5.0）。

| 场景 | 基线 | Copier 提升 | 备注 |
|------|------|-------------|------|
| 拷贝吞吐量（4KB） | ERMS | +55%（对比 ERMS），+33%（对比 AVX2） | 无缓冲区复用时 |
| Redis SET 延迟 | Linux baseline | 降低 2.7%–43.4% | 8 并行客户端 |
| Redis GET 延迟 | Linux baseline | 降低 4.2%–42.5% | 对比 zIO 提升 1.6× |
| Redis vs zIO | zIO | zIO 仅对 GET ≥4KB 有效（最多 20%），SET 需 ≥64KB | Copier 全面优胜 |
| TinyProxy 吞吐量 | Linux baseline | 提升 7.2%–32.3% | zIO 最多 11.6% |
| send() 延迟 | 正常 syscall | 降低 7%–37% | 配合 io_uring batching 可达 27%–59% |
| recv() 延迟 | 正常 syscall | 降低 16%–92% | 配合 batching 可达 55%–93% |
| Binder IPC 延迟 | Android Binder | 降低 9.6%–35.5% | 10–800 条 1KB 字符串 |
| CoW 故障处理 | Linux CoW | 阻塞时间降低 71.8%（2MB 页）/ 8.0%（4KB 页） | |
| Protobuf 反序列化 | 基线 | 降低 4%–33% | |
| OpenSSL AES-GCM 解密 | 基线 | 降低 1.4%–8.4% | |
| HarmonyOS 视频解码 | 基线 | 延迟降低 3%–10%，帧丢失减少最高 22% | 能耗仅增加 0.07%–0.29% |

资源受限场景（4 核全部占满）：Copier 仍可降低 Redis 延迟 17-19%，但吞吐量下降 4-7%（因 polling 和 task 提交的开销）。

## 六、批判性分析

1. **专用核心的代价被轻描淡写**：Copier 需要一个专用 CPU 核心运行拷贝服务。在核心全部被占用时，吞吐量反而下降 4-7%。论文主要强调延迟改善，但对吞吐量损失的分析不够深入。在核心数少的嵌入式/移动设备上，专用一个核心的代价更大。

2. **应用移植成本的现实挑战**：虽然论文称修改量适中（14-94 行代码），但需要"研究生级别的开发者花 1-2 周"移植一个 Redis，这对实际部署推广是个显著障碍。CopierGen 编译器工具目前只支持基础场景（如数组），复杂情况（如指针传递）留作 future work。

3. **评估基线与场景选择偏向性**：
   - 服务器使用的是较老的 Xeon E5-2650v4（2016 年），较新的处理器可能在 ERMS/FSRM 上有显著改进
   - 实验中 zIO 的阈值被设为 4KB（原文建议 16KB），可能不是 zIO 的最优配置
   - 大部分应用评估使用特定的消息大小范围，未展示不同工作负载混合下的表现

4. **Copy-Use 窗口的通用性未充分验证**：论文选取的 8 个场景都有显著的 Copy-Use 窗口，但没有讨论哪些重要场景不存在这种窗口。对于计算密集度低、拷贝后立即使用数据的场景（如简单的内存数据库查询），Copier 的异步优势可能很小。

5. **安全性论证不完整**：论文声称 Copier 避免了 TOCTTOU 风险，但 Copier 本身引入了新的并发窗口——在数据被异步拷贝但尚未被 csync 之前，如果应用代码有 bug 提前访问了数据，可能导致使用未初始化或部分拷贝的数据。CopierSanitizer 只是一个调试工具而非运行时保护。

6. **与 io_uring 的关系模糊**：io_uring 已经提供了异步 I/O 框架，Copier 与 io_uring batching 组合使用时效果很好，但论文没有充分讨论为什么不直接在 io_uring 框架内扩展拷贝优化，而要另起一个独立的 OS 服务。

## 七、AI Infra / MLSys 视角

1. **GPU/NPU 内存拷贝优化的启发**：Copier 的异步拷贝 + 全局调度思路可以迁移到 AI 系统中 CPU-GPU/GPU-GPU 的数据传输场景。当前 CUDA 的异步 memcpy 已经是异步的，但缺乏 Copier 式的全局视图优化和拷贝吸收。在 LLM 推理的 KV cache 管理中，频繁的内存搬运可能受益于类似的 segment 粒度 pipeline 和冗余消除。

2. **分布式训练中的通信优化**：Copier 的 piggyback 调度器——将异构拷贝单元（AVX + DMA）融合执行——与分布式训练中 computation-communication overlap 的思路异曲同工。可以探索在 NCCL/Gloo 等集合通信库中引入类似的全局拷贝调度服务。

3. **推理引擎的数据搬运**：LLM serving 系统（如 vLLM）中的 paged attention 涉及大量 KV cache 的拷贝和重组。Copier 的分层拷贝吸收可以用于优化 prefix caching、beam search 等场景中的冗余数据移动。

4. **值得跟进的研究方向**：
   - 将 Copier 思想扩展到 GPU 内存管理，设计 GPU 上的异步拷贝调度服务
   - 在 RDMA 场景下引入类似的全局拷贝视图和吸收优化
   - 探索在 AI 推理框架中利用 Copy-Use 窗口做 prefetch/预拷贝决策

---

## 八、总结

Copier 首次将内存拷贝重构为一等 OS 服务，通过异步拷贝抽象利用 Copy-Use 窗口隐藏拷贝延迟，通过 piggyback 调度器融合 AVX 和 DMA 的硬件能力，通过分层拷贝吸收消除冗余拷贝。系统在 Redis 上实现最高 1.8× 加速，在多个应用和内核服务上展示了显著改善。主要局限在于需要专用 CPU 核心、应用移植需要一定的开发投入，以及在 CPU 核心全部饱和时吞吐量可能下降。该工作已被集成到华为 HarmonyOS 5.0 中，并已开源。
