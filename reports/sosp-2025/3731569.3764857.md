# GoFS: Managing Scalable Direct Storage Accesses for GPUs with GPU-Orchestrated Filesystem

## 1. 论文基本信息

- **标题**: Managing Scalable Direct Storage Accesses for GPUs with GoFS
- **作者**: Shaobo Li, Yirui Eric Zhou, Yuqi Xue, Yuan Xu, and Jian Huang
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764857
- **代码**: 未提及开源

## 2. 研究背景

**GPU Direct Storage 的兴起**：随着 GPU 加速计算在智能数据处理（智能查询、图分析、LLM RAG）中的广泛应用，存储瓶颈问题日益突出。传统方法需要 host CPU 先从 SSD 读取数据到 host 内存，再通过 cudaMemcpy 传输到 GPU——这不仅引入了冗余的数据拷贝，还浪费了宝贵的 CPU 周期。

为解决这一问题，现代 GPU 和 NVMe SSD 支持 GPU Direct Storage (GDS)，通过 PCIe peer-to-peer (P2P) 通信，实现 GPU 与 SSD 的直接数据交换。

**现有方案的局限性**：
1. **NVIDIA cuFile**：host CPU 仍处理所有文件系统操作（索引数据块），只在 DMA 时将目标地址设为 GPU device memory——文件系统管理本身成为瓶颈
2. **BaM**：完全移除了 host CPU 参与，GPU 直接作为 block device 管理 SSD，但需要应用显式管理存储设备，缺乏通用性
3. **GeminiFS**：假设 GPU 应用有可预测的 I/O 访问模式且大部分是只读的——这在实际中不成立

核心问题：如何在保持文件系统通用性（POSIX API、通用元数据管理）的同时，实现 GPU 对 SSD 的直接访问？

## 3. 要解决的问题

**核心问题**：如何设计一个 GPU 编排的文件系统，实现：
1. **可扩展性**：充分利用 GPU 数百个 SM 的并行性扩展元数据和数据 I/O 管理
2. **易用性**：提供 POSIX API，兼容现有程序
3. **数据一致性**：支持 host 和 GPU 对共享 SSD 的访问一致性
4. **保护机制**：在 GPU 程序和文件系统之间提供内存隔离和访问控制

## 4. 核心贡献

1. **GPU 编排文件系统架构**：提出 GoFS——首个 GPU 编排的文件系统，完全将存储管理 offload 到 GPU，在 GPU memory 中管理核心文件系统结构（inode/dentry、block management、data pointers），无需 host CPU 参与控制路径和数据路径。
2. **GPU 友好的元数据管理优化**：Range Lock for inode（替代 mutex）、Per-SM block bitmap、Level-synchronous parallelism for data pointer traversal。
3. **Primary-Secondary 一致性模式**：GoFS Daemon (GPU) 作为 primary，GoFS Client (host) 作为 secondary，在保证数据一致性的同时提供灵活访问。
4. **跨平台兼容性**：兼容现有 host-based 文件系统（F2FS），无需修改 on-disk 文件组织。

## 5. 主要研究方法

### 5.1 GPU 架构与执行模型分析
- GPU 由数百个 Streaming Multiprocessors (SMs) 组成
- 每个 SM 有多个 SIMD 单元（CUDA cores）、private L1 cache、software-managed shared memory
- 所有 SM 共享 global L2 cache 和 off-chip DRAM
- 执行层次：Thread -> Warp (32 threads) -> Thread Block -> Kernel
- 内存访问特点：global memory 访问需要 coalesced 访问以获得高带宽

### 5.2 系统设计目标
- **Scalability**：利用 GPU massive parallelism
- **Programmability**：提供 POSIX API
- **Data Consistency**：CPU 和 GPU 间的数据一致性
- **Protection**：GPU 程序与文件系统的隔离

## 6. 设计与实现

### 6.1 系统架构
GoFS 包含三个组件：
1. **GoFS Daemon**（GPU 端，5.5K LOC CUDA）：管理 in-memory 文件系统元数据，执行数据 I/O 访问
2. **GoFS Client**（host 端，0.8K LOC C/C++ FUSE）：拦截文件系统调用
3. **libgofs**：GPU 程序的用户空间库

### 6.2 Range Lock for Inode
- 用范围锁替代 inode 互斥锁，实现细粒度并发控制
- Ring buffer 结构存储 I/O 请求范围
- Warp-level reduction 原语并行化冲突检查
- 接近 O(1) 复杂度（vs 传统 interval tree 的 O(log n)）

### 6.3 Per-SM Block Bitmap
- 每个 SM 维护独立的 block bitmap，消除 SM 间的分配竞争
- 当任一 SM 的空闲块比例低于阈值（5%）时触发全局重分配
- Thread block 内 coalesced 分配操作

### 6.4 Batched Node (bnode)
- 跟踪同一目录下所有打开的文件集合
- 支持批量打开和批量操作，减少元数据开销

### 6.5 Level-Synchronous Parallelism
- Data pointer tree 的两级并行遍历：元数据遍历 + 数据传输
- 避免 load imbalance 和 warp divergence

### 6.6 Zero-Copy I/O
- DMA 直接将数据传输到用户数据缓冲区，无需 intermediate copies
- 在 GPU memory 维护多个 NVMe 队列服务并行 I/O 请求
- 根据 I/O 请求大小自动扩展 I/O 线程数

### 6.7 Crash Consistency
- Log-structured F2FS 基础，提供 crash consistency
- Primary-Secondary 模式：GPU Daemon active 时作为 primary，host 作为 secondary

### 6.8 访问控制
- Cryptographic signature 验证用户身份
- GPU 虚拟内存提供文件系统 vs 应用的内存保护

## 7. 主要实验结果

### 7.1 综合性能提升
- **平均性能提升 1.61 倍**（相比 state-of-the-art GPU 存储访问方案）
- 在不同 SSD 数量下展现了良好的扩展性

### 7.2 测试应用
- Graph Analytics
- Deep Learning Queries (Vision, Text, Audio)
- GNN Training
- LLM-based RAG System

### 7.3 硬件配置
- NVIDIA A100 GPU with GPUDirect Storage
- 16-core Intel Xeon
- Multiple 2TB Samsung 990 Pro SSDs

## 8. 潜在问题/局限性

1. **与 Host 文件系统的互操作性**：虽然声称"无需修改 on-disk 文件组织"，但 GoFS 和 host 文件系统（如 F2FS）之间的元数据同步机制在并发修改场景下可能存在一致性问题。
2. **GPU 内存压力**：GoFS 在 GPU memory 中管理所有 in-memory 元数据结构。对于超大目录（数百万文件），元数据可能超过 GPU memory 容量。
3. **CUDA 依赖性**：GoFS 完全基于 CUDA 编写，不支持 AMD ROCm 或其他 GPU 平台。这在 AMD GPU 日益流行的当下是一个重要限制。
4. **调试和可观测性挑战**：在 GPU 端运行文件系统增加了调试复杂度。GPU crash 的诊断和恢复比 host 端更困难。
5. **与其他 GPU 存储解决方案的对比不完整**：论文主要对比了 cuFile 和 BaM，但与新兴的 GPU 存储抽象（如 NVIDIA Magnum IO）和其他 GPU 文件系统（如 GPFS）的对比缺失。
6. **Primary-Secondary 一致性的语义**：GoFS 声称提供 Primary-Secondary 模式的一致性，但这与传统文件系统的 POSIX 语义（sequential consistency）可能不完全等价。
7. **安全性验证**：虽然提到了 cryptographic signature 和内存保护，但具体的攻击面和威胁模型未详细讨论。
8. **多租户支持**：多个 GPU 应用共享 SSD 时，QoS 和资源隔离问题未讨论。

## 9. 未来工作

1. **支持更多 GPU 平台**：扩展到 AMD ROCm、Intel GPUs 等。
2. **多租户资源隔离**：在共享 SSD 的多用户场景下实现公平的资源分配。
3. **更丰富的文件系统语义**：符号链接、ACL、配额管理等。
4. **与现有分布式存储集成**：支持 Ceph、HDFS 等分布式存储后端。

## 10. 个人评注

**GoFS 是一篇针对特定硬件特性的深度工程优化论文**，它抓住了 GPU Direct Storage 这一新兴但快速发展的硬件能力，针对其软件栈缺失（文件系统层）提出了系统化的解决方案。

论文最有价值的贡献是**对 GPU 存储访问的全面系统化分析**——从 cuFile 的 host CPU bottleneck，到 BaM 的通用性缺失，再到 GeminiFS 的假设限制，清晰揭示了每个现有方案的权衡。这使得 GoFS 的设计决策更加有说服力。

**批评性思考**：
- **"1.61x 平均性能提升"需要谨慎解读**：这个数字是相对于"state-of-the-art GPU 存储访问方案"（应该是 cuFile 或 BaM）的，但没有明确说明基准线和测试条件的公平性。不同应用的 I/O 模式差异巨大，1.61x 可能不是均匀的。
- **Range Lock 的 O(1) 声称有些误导**：虽然 warp-level reduction 确实很快，但锁的获取和释放本身仍然需要原子操作，在高并发下可能出现锁竞争。实际复杂度取决于 warp 内的冲突率。
- **Per-SM Bitmap 的 5% 阈值是经验值**：论文没有给出如何确定这个阈值的系统化方法，也没有评估不同工作负载对这个阈值敏感性的影响。
- **F2FS 作为基础文件系统的选择值得商榷**：F2FS 是针对 flash 的日志结构文件系统，设计目标是优化 SSD 的写入模式。但在 GPU 存储访问场景中，读操作可能占主导。GoFS 基于 F2FS 的 on-disk 格式是否是最优选择未充分讨论。
- **与 Magma/Alluxio 等分布式缓存层的关系未讨论**：在实际生产环境中，GPU Direct Storage 通常与分布式缓存层配合使用。GoFS 与这些层的交互和一致性协议未讨论。

总体而言，这是一篇对 GPU 存储系统工程师和存储系统研究者有价值的论文。它的工程实现细节（Range Lock、Warp-level reduction）对于理解 GPU 上的高效并发控制很有参考意义。读者应该关注其假设条件和工程权衡的讨论。
