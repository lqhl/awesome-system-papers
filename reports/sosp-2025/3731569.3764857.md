## 一、背景

GPU 加速计算已成为大规模智能数据处理的主流范式——图分析、深度学习查询、GNN 训练、LLM-based RAG 等应用都依赖 GPU 处理海量数据集。然而，数据需要从 SSD 搬运到 GPU 内存，这一过程始终是性能瓶颈。

传统路径是：CPU 从 SSD 读取数据 → host memory → cudaMemcpy → GPU memory，存在冗余拷贝和 CPU 资源浪费。为此，现代 GPU 和 NVMe SSD 支持 **GPU Direct Storage（GDS）**，通过 PCIe P2P DMA 直接在 GPU memory 和 SSD 之间传输数据，绕过 host memory。

但现有 GDS 解决方案仍然依赖 host CPU 管理文件系统（inode、block 分配、元数据查询），GPU 在数据路径上仍受限于 host 端的控制路径，无法充分利用 GPU 的大规模并行性。

---

## 二、要解决的问题

**核心矛盾**：GPU 拥有数千个计算核心可并行发起 I/O 请求，但现有 GDS 方案的文件系统管理仍依赖 CPU，CPU 成为新的扩展瓶颈。

具体问题：

1. **cuFile（NVIDIA 官方）**：host CPU 处理所有文件系统操作（文件索引、block 管理），GPU 只做数据搬运。CPU 成为瓶颈，扩展性差，随机 4KB I/O 吞吐仅 0.44 GBps。

2. **GPUfs**：GPU 线程通过 RPC 调用 host 文件系统，每次请求需往返 CPU，在小 I/O 场景下 RPC 开销显著（比 Basic 差 1.2–1.6×）。

3. **GeminiFS**（最新 SOTA）：将文件元数据预加载到 GPU memory，GPU 负责数据 I/O。但依赖"可预测 I/O 模式 + 只读"假设：元数据须预先从 host 加载，写操作受限；大数据集（如 404 GB 元数据的 IIR）会溢出 GPU memory（仅 40 GB），导致频繁开关文件和 host 元数据访问开销。

4. **BaM**：GPU 直接管理裸块设备，完全绕过文件系统，应用程序需自己管理存储，开发负担重。

**缺口**：缺乏一个通用的、可扩展的、支持读写和不可预测 I/O 模式的 GPU-side 文件系统。

---

## 三、核心设计

**GoFS**（GPU-orchestrated File System）：将文件系统管理完全卸载到 GPU，包括控制路径和数据路径，同时与 host 侧 F2FS 共享同一块 SSD。

### 系统架构

GoFS 由三个组件组成（见 Figure 2）：

- **GoFS Daemon（GPU 端）**：以独立进程运行在 GPU 上，持续监听来自用户 GPU kernel 的文件系统请求。管理 in-memory 文件系统元数据和 NVMe 队列，仅占用 1 个 SM（空闲时），I/O 繁忙时动态扩展。
- **GoFS Client（Host 端）**：FUSE 模块拦截 host 端文件系统调用；当 daemon 运行时，与 GPU daemon 协作以 primary/secondary 模式保持一致性；daemon 不运行时，退化为普通 F2FS。
- **libgofs**：提供 GPU 应用调用 GoFS API 的库接口，包括标准 POSIX API 和扩展的批量 API。

### 与 F2FS 的关系

GoFS **不修改 on-disk 文件系统格式**，复用 F2FS 的磁盘布局（log-structured），仅重新设计 in-memory 数据结构。host 与 GPU 可协同管理同一块 SSD，以 GPU daemon 为 primary，host client 为 secondary。

## 四、实现细节

### 4.1 元数据管理（§3.3）

**Scalable inode 访问**（解决粗粒度锁问题）：
- 用**范围锁（range lock）**替换传统 mutex，基于环形缓冲区实现。每个 slot 存储 I/O state（1B）、file offset（8B）、access size（8B）。
- 范围冲突检测通过 **warp-level reduction primitives** 并行化，时间复杂度从 O(log n) 降至近似 O(1)。
- 同一 thread block 内的线程共享一个范围锁，因为 GPU 应用通常按空间局部性组织线程。

**bnode（batched node）结构**（解决大量小文件的元数据开销）：
- 追踪同一目录下一批已打开文件，记录文件数、总大小、以及每个文件的 name hash、filename、size、inode 号、数据指针。
- `batch_open()` 并行读取目录下所有子项；`batch_read/write()` 批量处理，将元数据操作合并（父 inode 只更新一次），消除不必要的锁。
- 对比无 batch API：多文件读/写吞吐分别提升 1.67×/1.38×。

**Per-SM block bitmap**（解决集中式 block 分配竞争）：
- 为每个 SM 分配专属 bitmap，消除 SM 间竞争。当某 SM 剩余空闲 block < 5% 时，重新平衡分配。
- Thread block 内所有线程协作计算总分配需求，由单线程（thread 0）统一操作 bitmap，消除 warp 内竞争。

**Level-synchronous 数据指针遍历**（解决负载不均和 branch divergence）：
- 两阶段流程：
  1. 元数据阶段：按树的层级并行遍历所有数据指针，用 barrier 同步确保同层同时处理，消除 branch divergence。
  2. 数据阶段：并行 fetch 所有数据块，最大化 SSD 带宽。
- 受 GPU 图遍历算法启发（level-synchronous BFS）。

### 4.2 数据 I/O（§3.4）

- **Multiple NVMe queues**：默认创建 SSD 支持的最大队列数（Samsung 990 Pro：16 队列，数据中心 Intel Optane：128 队列），queue depth 为 2048。
- **静态调度**：按 SM 数量均分 NVMe 队列，无运行时调度开销。
- **Zero-copy**：DMA 直接写入用户 buffer，无 page cache。对 GPU 应用而言 page cache 通常无益（流式访问、数据集过大、吞吐优先）。
- **Dynamic parallelism**：根据请求大小自动调整 I/O 线程数。提供 sync 和 async 两种模式。

### 4.3 崩溃一致性（§3.5）

GoFS 基于 F2FS 的 log-structured 特性，数据和 node blocks 均 out-of-place 写入，通过更新 NAT 表传播变更。定期触发 checkpoint，刷入所有 dirty metadata。崩溃恢复直接复用 host F2FS 栈，扫描 checkpoint region 回滚到最新一致状态，无需 GPU 参与。

### 4.4 数据保护（§3.6）

GPU 无多特权环，GoFS 通过以下方式实现隔离：
- **虚拟内存隔离**：daemon 进程（"kernel space"）管理文件系统元数据和 NVMe 队列，用户进程（"user space"）无法访问 daemon 内存。通过 CUDA MPS 让用户进程和 daemon 共存于不同 SM。
- **HMAC 签名认证**：host GoFS client 用 HMAC-SHA256 对 (GroupID, UserID, nonce) 签名，生成不可伪造的用户身份标识。用户每次调用 GoFS API 时携带签名，daemon 验证后放行。

### 4.5 实现规模

| 组件 | 代码量 | 语言 |
|------|--------|------|
| GoFS Daemon | 5.5K LoC（含 2.4K 数据结构） | CUDA C++ |
| libgofs | 1.4K LoC | CUDA C++ |
| Host Client | 0.8K LoC（含 0.2K FUSE 修改） | C++ |
| **合计** | **~7.9K LoC** | |

## 五、实验结果

### 实验环境

- CPU：16-core Intel Xeon W5-3435X
- GPU：NVIDIA A100（40GB）+ GPU Direct Storage
- SSD：2TB Samsung 990 Pro × 多块（可 RAID0）
- OS：Ubuntu 20.04，Linux 5.4.0，CUDA 12.4

### 基线

| 方案 | GPU 控制程度 | 特点 |
|------|-------------|------|
| Basic | 无（CPU F2FS + cudaMemcpy） | 数据经 host memory 中转 |
| GPUfs | 低（RPC to host） | GPU 线程通过 RPC 调用 host FS |
| cuFile | 低（数据路径 GPU，控制路径 CPU） | 官方 GDS，host CPU 管控 FS |
| GeminiFS | 中（元数据 host，数据 GPU） | 元数据预加载，依赖可预测访问模式 |
| **GoFS** | **高（全 GPU）** | 本文方案 |

### 微基准（单 SSD）

| 测试 | GoFS | 对比 SOTA（GeminiFS）|
|------|------|---------------------|
| 顺序读 | 5.5 GBps（接近 SSD 峰值 6.9 GBps） | 略优 |
| 顺序写 | 6.5 GBps（接近 SSD 峰值 7.5 GBps） | 略优 |
| 随机读 | 5.1 GBps（接近裸设备峰值 5.4 GBps） | **1.4× 优于 GeminiFS** |
| 随机写 | 6.1 GBps（近似顺序写，因 log-structured） | **1.6× 优于 GeminiFS** |
| 多文件读 | — | **15.5× 优于 cuFile** |
| 多文件写 | — | **4.6× 优于 cuFile** |

cuFile 顺序读仅 0.44 GBps，受 host 软件栈开销严重拖累。

### 真实应用（平均 1.61× 提升）

| 应用 | GoFS vs Basic | GoFS vs GeminiFS |
|------|-------------|-----------------|
| 图像检索 IIR | — | **2.5×** |
| 音频检索 MIR | — | **2.7×** |
| 文本检索 TIR | — | 1.4× |
| RAG（LLM + 3.6TB 向量库） | 1.6× | 1.2× |
| 图分析 BFS/CC | 1.34–1.76× | 1.2× |
| GNN 训练 | — | **1.54×** |
| 数据集预处理（1 SSD） | **1.16×** vs Host-Only | **2.3×**（GeminiFS 反而比 Host-Only 慢 2×） |
| 数据集预处理（4 SSD） | **3.16×** vs Host-Only | — |

### 多 SSD 扩展性

GoFS 实现近线性吞吐扩展：
- 4 SSD：顺序读 **20.4 GBps**，顺序写 **22.1 GBps**
- GeminiFS 在超过 2 块 SSD 时因 warp-level 并行度不足无法继续扩展（顺序读/写除外）
- Basic 受 host 软件栈限制，4 SSD 仅达 7.8 GBps

### GPU 内存占用

峰值场景（batch size 65536 的智能查询）：**278 MB**（其中 263 MB 为 inode cache），对比 40 GB GPU 内存可忽略不计。

## 六、批判性分析

**1. 单 GPU、单平台的局限被轻描淡写**

论文所有实验均在 A100 上进行，多 GPU 支持被推迟到 future work。而实际 AI 推理/训练集群普遍是 8 卡乃至更多卡，GoFS 在多 GPU 场景下的数据一致性协调（多个 daemon 实例间的元数据同步）完全未被探讨，直接断言"可以部署在每块 GPU 上管理本地 SSD"而不说明代价。

**2. GeminiFS 的比较存在不公平之处**

数据集预处理实验中，GeminiFS 需要将文件转换为专有 GVDK 格式，这一额外转换开销被计入总时间，造成 GoFS 大幅领先（GeminiFS 比 Host-Only 还慢 2 倍）。这一对比更多反映了 GeminiFS 格式转换的代价，而非 GoFS 自身的优势。

**3. cuFile 的基线不公平**

cuFile 随机 4K I/O 吞吐仅 0.44 GBps，远低于其应有性能，部分原因可能是实验配置（cuFile 使用 ext4，GoFS 用 F2FS）或未针对 cuFile 进行充分调优。用一个"配置较差"的对手来衬托性能优势，说服力有限。

**4. 只报告"平均"掩盖了场景差异**

1.61× 的平均提升中，不同应用的差异极大：IIR 提升 2.5×，而顺序访问的工作负载（如 Basic 情况下的顺序读）GoFS 仅有微小优势。将结构差异很大的工作负载平均化，会高估在所有场景的通用收益。

**5. 崩溃一致性的恢复路径未实测**

论文声称复用 F2FS 栈进行崩溃恢复，"恢复开销不是关键路径"，但没有任何崩溃恢复测试数据。GPU daemon 异常退出后的一致性保证是否真正可靠，无法从论文中得出结论。

**6. 时钟同步的精度代价被低估**

GPU 侧时钟每 10 分钟与 CPU 同步一次，最大偏差 1368 μs。论文引用 Windows Time Service（毫秒到秒级）作为对比来论证这"足够了"，但对于依赖文件修改时间的 Make 等工具，若 GPU 在一次同步周期内频繁写文件，时间戳偏差可能导致正确性问题——论文没有深入分析此类边缘情况。

**7. 背景 GC 的触发时机存在竞争**

GoFS 通过监控 `PROF_SM_OCCUPANCY` 判断 GPU 空闲后再触发背景 GC。在真实生产中，GPU 利用率很少跌到"仅 daemon 在运行"的水平，这意味着背景 GC 实际上很难触发，只能依赖前台 GC。前台 GC 在磁盘使用率低于 5% 时触发，可能影响时延敏感型应用。

## 七、AI Infra / MLSys 视角

**与 AI Infra 的直接关联**

GoFS 的核心应用场景本身就是 AI Infra：GNN 训练（GraphSAGE on 3.2TB WebGraph）、LLM RAG（Llama2-13B + 3.6TB 向量库）、视觉/音频/文本智能查询，以及 ImageNet 数据集预处理。这些都是 AI 系统研究的核心工作负载。

**对 AI Infra 研究的启发**

1. **数据加载瓶颈的解法**：当前 ML 框架的 data loader（PyTorch DataLoader、tf.data）仍依赖 CPU 做 I/O，GoFS 的 GPU-native 文件系统方案为 data loader 加速提供了新路径。batch_open/batch_read API 与 ML 框架的 Dataset 抽象高度契合，具备直接集成可能性。

2. **GPU 内存扩展（tensor offloading）的基础设施**：论文中提到 GoFS 可用于 DNN 训练中的显存扩展（将临时 tensor offload 到 SSD），如 FlashNeuron 等工作。GoFS 的零拷贝 DMA + 高并行 NVMe 队列可以显著提升 tensor swap 带宽，尤其在多 SSD RAID0 配置下（4 SSD 达 22 GBps 写入）可以覆盖大模型的激活/梯度 offloading 需求。

3. **RAG 系统的存储后端**：GoFS 对 RAG 向量库的随机小 I/O（ANN graph traversal）提升 1.2–1.8×，且 GPU 可直接管理向量数据库的读取，避免了 CPU→GPU 的数据传输，对 online inference serving 的 latency 有直接收益。

4. **GPU-native 并发数据结构的设计范式**：range lock + warp-level reduction、per-SM bitmap、level-synchronous tree traversal 等设计，提供了一套在 GPU 上实现并发系统软件的参考范式，可迁移到 GPU-side 调度器、缓存管理器等 AI Infra 组件的设计中。

**值得跟进的方向**

- **与 PyTorch/JAX data pipeline 集成**：将 GoFS 的 batch API 封装为 `torch.utils.data.Dataset` 后端，直接服务 GPU 训练的数据加载，消除 CPU 数据加载成为瓶颈的情形（尤其是 GNN 等图数据）。
- **多 GPU 协同存储**：分布式训练场景下，每块 GPU 管理本地 SSD 并协调元数据一致性，是 GoFS 最重要的扩展方向，也是目前最大的空白。
- **KV cache offloading in LLM serving**：LLM 推理的 KV cache 卸载到 SSD（如 InfiniStore、CacheGen）目前依赖 CPU 做数据管理，GoFS 的 GPU-native 零拷贝路径可以显著降低 KV cache swap 延迟。

---

## 八、总结

GoFS 是首个将文件系统管理（包括控制路径和数据路径）完全卸载到 GPU 的系统，通过 range lock、bnode、per-SM bitmap、level-synchronous 数据指针遍历等针对 GPU 架构设计的并发优化，在保持 F2FS 磁盘兼容性的前提下，实现了近 SSD 理论峰值的 I/O 吞吐，以及多 SSD 的线性扩展。对于包含大量文件元数据操作和随机小 I/O 的 GPU 工作负载（图分析、GNN 训练、RAG），GoFS 相比现有最优方案可获得 1.2–2.7× 的端到端提升。主要局限在于目前仅支持单 GPU、F2FS 格式、多 GPU 扩展有待实现，且部分评测中的 baseline 设置不够公平。
