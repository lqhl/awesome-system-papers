# Managing Scalable Direct Storage Accesses for GPUs with GoFS

**会议**：SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
**链接**：https://doi.org/10.1145/3731569.3764857

---

## 一、背景

随着 GPU 加速计算在智能数据处理领域的广泛应用（图分析、智能查询、GNN 训练、LLM-based RAG 等），存储 I/O 成为日益严重的瓶颈。传统方式下，数据需要经过 host CPU 从 SSD 读到主机内存，再通过 cudaMemcpy 传到 GPU 显存，存在冗余数据拷贝和 CPU 开销。

NVIDIA GPU Direct Storage (GDS) 允许 GPU 通过 PCIe P2P DMA 直接与 NVMe SSD 通信，绕过 host 内存。然而，现有 GDS 方案（cuFile、GPUfs、BaM、GeminiFS）仍然存在对 host CPU 的依赖或功能上的局限性：

- **cuFile**：host CPU 仍需处理文件系统操作（索引、访问控制等），成为可扩展性瓶颈
- **GPUfs**：通过 RPC 将 GPU 的文件操作委托给 host 文件系统，开销大
- **BaM**：允许 GPU 直接管理 NVMe 队列，但将 SSD 暴露为裸块设备，应用需自行管理存储
- **GeminiFS**：将文件元数据预加载到 GPU 内存，但假设 I/O 模式可预测且为只读，不适用于通用场景

---

## 二、要解决的问题

1. **Host CPU 瓶颈**：现有 GPU Direct Storage 方案的控制路径（元数据管理、块分配、路径解析）仍依赖 host 文件系统，host CPU 成为可扩展性瓶颈
2. **GPU 并行性未被充分利用**：CPU 文件系统的数据结构和并发机制（mutex、RCU 等）无法映射到 GPU 的 SIMD 层级线程模型（warp → thread block → kernel）
3. **缺乏通用性**：GeminiFS 假设可预测 I/O 和只读访问，BaM 不提供文件系统抽象，无法支持多样化 GPU 应用（随机访问、写操作、海量小文件）
4. **GPU 上缺乏系统软件基础设施**：无 OS 支持、无 kmalloc、有限的同步原语和工具库

---

## 三、洞察与设计

**关键洞察**：GPU 的大规模并行能力（数千 CUDA core、上百 SM）不仅可以用于计算加速，也可以用来加速文件系统本身的元数据管理和数据 I/O——前提是将文件系统的核心数据结构重新设计为"GPU-friendly"的形式，充分利用 GPU 的 bulk-synchronous parallel 计算范式。

基于此洞察，GoFS 将整个文件系统栈（元数据管理 + 数据 I/O）完全卸载到 GPU 上运行，提供 POSIX API，与 host F2FS 共享相同的 on-disk 格式。核心设计包括：

### 架构
- **GPU-side daemon**：管理 in-memory 文件系统元数据和 NVMe 队列，以持久 kernel 运行在 GPU 上
- **Host-side client**：基于 FUSE 拦截 host 端文件操作，与 GPU daemon 协调（primary/secondary 模式）
- **libgofs**：用户态库，提供 GPU 应用与 daemon 间的 IPC

### 可扩展元数据管理
- **Range lock 替代 mutex**：用 ring buffer 实现的 range lock 替代传统 inode mutex，支持对同一文件不同区域的并发访问；利用 warp-level reduction 并行化冲突检测，从 O(log n) 降至近 O(1)
- **Batched node (bnode)**：针对海量小文件场景，追踪同一目录下所有打开文件的集合，合并元数据操作（父 inode 只需更新一次），消除不必要的锁
- **Per-SM bitmap**：每个 SM 维护独立的块位图，消除 SM 间的分配竞争；thread block 内合并块分配为单次操作

### 可扩展数据 I/O
- **Level-synchronous data pointer 遍历**：受 GPU 图遍历算法启发，分两阶段（metadata stage + data stage），同一层所有节点并行处理，消除负载不均和分支发散
- **Zero-copy I/O**：不维护 page cache，数据通过 DMA 直接传入用户缓冲区
- **Automatic data-parallel I/O**：通过 CUDA dynamic parallelism 自动根据请求大小缩放 I/O 线程数

## 四、实现细节

- **GPU daemon**：5.5K LoC CUDA C++，其中数据结构（哈希表、ring buffer、树）占 2.4K LoC；基于 libnvm 实现 NVMe 直接访问
- **libgofs**：1.4K LoC，提供应用与 daemon/client 交互接口
- **Host client**：0.8K LoC C++，基于 FUSE 拦截文件系统调用；修改 0.2K LoC 内核代码
- **On-disk 格式**：完全兼容 F2FS，不修改 on-disk layout
- **时钟同步**：GPU 端利用 `globaltimer` 寄存器作为本地计时器，每 10 分钟与 CPU 时钟校准（最差偏差 1368μs）
- **访问控制**：host client 使用 HMAC-SHA256 对 user/group ID + nonce 签名，GPU daemon 验证签名防止身份伪造
- **内存保护**：利用 GPU virtual memory 隔离 daemon 和用户进程；daemon 独占一个 SM 监听请求，用户进程通过 CUDA MPS 使用其余 SM
- **垃圾回收**：daemon 周期性检查可用空间，前台/后台 GC；后台 GC 利用 DCGM 监控 GPU 利用率，在空闲时触发
- **NVMe 队列**：默认创建 SSD 支持的最大队列数（Samsung 990 Pro: 16 que列，Intel Optane: 128），队列深度 2048

### 扩展 API
- `readv/writev`：向量化读写
- `batch_open/batch_close`：批量打开目录下文件
- `batch_read/batch_write`：批量读写 bnode 中的文件

## 五、实验结果

**测试平台**：16-core Intel Xeon W5-3435X, 64GB DDR5, NVIDIA A100 (40GB), Samsung 990 Pro 2TB SSD, Ubuntu 20.04, CUDA 12.4

**基线**：Basic (F2FS + cudaMemcpy), GPUfs, cuFile, GeminiFS

### 微基准测试（单 SSD）

| 指标 | GoFS | 对比最优基线 |
|------|------|-------------|
| 顺序读 | 5.5 GB/s | ~1.10× vs GeminiFS |
| 顺序写 | 6.5 GB/s | ~1.03× vs GeminiFS |
| 随机读 | 5.1 GB/s | 1.4× vs GeminiFS |
| 随机写 | 6.1 GB/s | 1.6× vs GeminiFS |
| 多文件读 | — | 15.5× vs best baseline |
| 多文件写 | — | 4.6× vs best baseline |

- GoFS 接近 SSD 裸设备峰值吞吐（顺序 6.9-7.5 GB/s，随机读 5.4 GB/s）
- GoFS 完全不消耗 host CPU 核心，其他基线需要 8-16 CPU 核才能接近峰值

### 应用性能

| 应用 | GoFS 加速比（vs 各基线平均） |
|------|---------------------------|
| 智能查询 (IIR/MIR/TIR) | 6.2×/7.5×/21.3×/2.1× vs Basic/GPUfs/cuFile/GeminiFS |
| RAG (Llama2-13B + 3.6TB vectorDB) | 1.4-1.8× vs GeminiFS/Basic/GPUfs |
| 图分析 (BFS/CC) | 1.53× vs Basic (avg), 1.2× vs GeminiFS |
| GNN 训练 (GraphSAGE, 3.2TB WebGraph) | 1.54× vs GeminiFS |
| 数据集预处理 (ImageNet) | 1.16-3.16× vs Host-Only (随 SSD 数量增加) |

### 多 SSD 扩展性

| SSD 数量 | 顺序读 | 顺序写 |
|----------|--------|--------|
| 1 | ~5.5 GB/s | ~6.5 GB/s |
| 4 | 20.4 GB/s | 22.1 GB/s |

GoFS 实现近线性吞吐扩展；GeminiFS 在 2 SSD 后无法继续扩展（除顺序读写）；Basic 最高 7.8 GB/s（4 SSD）。

### GPU 显存占用
最大场景（智能查询 batch=65536）仅占 278MB，其中 263MB 为 inode 缓存。

## 六、批判性分析

1. **单 SSD 顺序读写的优势边际**：GoFS 在单 SSD 顺序读写上仅比 GeminiFS 快 3-10%，在这类简单场景下，将整个文件系统搬到 GPU 上的复杂性价比存疑

2. **FUSE 开销未充分讨论**：host-side client 基于 FUSE 实现，而 FUSE 本身有非平凡的性能开销。当 host 端频繁访问文件（如 primary/secondary 模式切换时），FUSE 可能成为新瓶颈，但论文未量化这一开销

3. **实验配置的局限性**：
   - 仅在单个 A100 上测试，未验证多 GPU 场景
   - Samsung 990 Pro 是消费级 SSD（仅支持 16 队列），与数据中心场景差距较大
   - GeminiFS 使用 ext4 而 GoFS 使用 F2FS（log-structured），随机写的优势部分来自文件系统本身而非 GoFS 的设计

4. **应用场景偏向 I/O 密集型**：选取的应用都是存储 I/O 密集的（海量小文件、随机访问），对于计算密集但偶尔访问存储的典型 ML 工作负载（如 DNN 训练），GoFS 的实际收益可能有限，但论文未正面讨论此类场景

5. **Crash consistency 依赖 host 恢复**：GoFS 声称提供 crash consistency，但恢复时需要回退到 host F2FS 栈执行。如果 GPU daemon 崩溃时有 in-flight 写入，论文未详细分析数据丢失的边界情况

6. **Per-SM bitmap 负载均衡假设**：初始化时按 free block 数量均匀分配，但运行过程中不同 SM 的写入量可能差异很大。虽然有 5% 阈值触发重分配，但重分配的频率和开销未量化

7. **Daemon 占用 SM 的开销被淡化**：同步模式下可能占用 16 个 SM（占 A100 总 108 个 SM 的 ~15%）用于 I/O polling，这对计算密集型负载的影响不可忽略

## 七、AI Infra / MLSys 视角

### 启发与借鉴价值

1. **GPU Direct Storage 文件系统化**：GoFS 证明了在 GPU 上运行完整文件系统栈的可行性，这对 AI Infra 中的 checkpointing、数据加载、KV cache offloading 等场景有重要参考价值。未来的 LLM serving 系统可以考虑将 checkpoint I/O 和 KV cache 换页操作完全卸载到 GPU 端

2. **Batch API 设计思想**：bnode 和 batch_open/batch_read 的设计对 ML 数据管道高度相关——训练数据集通常由同一目录下的大量小文件组成（ImageNet、AudioSet 等），batch API 可大幅减少元数据开销

3. **Zero-copy + 自动并行化 I/O**：GoFS 的自动 data-parallel I/O 和 zero-copy 设计思路可以集成到现有 ML 数据加载框架（如 PyTorch DataLoader、DALI）中，特别是对于 out-of-core GNN 训练和 RAG 系统

### 可迁移的技术

- **Per-SM 资源分区**：per-SM bitmap 的设计模式可推广到 GPU 内存分配器（如 vLLM 的 PagedAttention 块管理），减少并发分配竞争
- **Level-synchronous 树遍历**：可用于加速 GPU 上的索引结构遍历（如 B-tree、radix tree），适用于 GPU 数据库和向量检索引擎
- **GPU 端 NVMe 队列管理**：可直接用于 LLM checkpoint offloading（ZeRO-Infinity 类方案）和 tensor rematerialization

### 值得跟进的 Future Work

1. **多 GPU 分布式文件系统**：论文仅讨论了单 GPU 方案，但现代 AI 训练通常涉及多节点多 GPU。将 GoFS 扩展为分布式文件系统（跨 GPU 数据一致性）是关键方向
2. **与 KV cache offloading 集成**：将 GoFS 用作 LLM serving 中 KV cache 到 SSD 的换页后端，利用 zero-copy 和自动并行化减少 prefill/decode 阶段的延迟
3. **GPU 内存扩展器优化**：论文提到可用于 DNN 训练的 GPU 内存扩展（tensor offloading），但未实验验证——这是一个直接可操作的研究点

---

## 八、总结

GoFS 是首个完全在 GPU 上运行的文件系统，通过将元数据管理和数据 I/O 全部卸载到 GPU，消除了 GPU Direct Storage 对 host CPU 的依赖。其核心贡献在于为 GPU 的 SIMD 并行模型重新设计了文件系统的关键数据结构（range lock、per-SM bitmap、level-synchronous pointer traversal、batched node），并保持了与 host F2FS 的 on-disk 兼容性。在多种 GPU 应用上平均提升 1.61×，在多 SSD 场景下实现近线性扩展。主要局限在于单 SSD 顺序访问场景优势有限、仅在单 GPU 上验证、且 daemon 的 SM 占用对计算密集型负载有潜在影响。
