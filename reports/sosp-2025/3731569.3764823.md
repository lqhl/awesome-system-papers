## 一、背景

大型语言模型（LLM）推理服务的核心瓶颈是 GPU 显存容量。为提升吞吐量，推理系统需要并发处理尽可能多的请求（batching），而每个请求在生成过程中都需要在 GPU 上维护完整的 KV cache。PagedAttention（vLLM 的核心内存管理机制）通过将 KV cache 分割为固定大小的 page 来消除碎片化，是目前最广泛采用的解决方案。

然而，现代 LLM 架构正在迅速走向**异构化**：不同层使用不同的注意力机制（全注意力、滑动窗口注意力、Mamba 状态空间模型、局部注意力等），不同类型的 token（文本 token、图像 token）有不同的 embedding 大小，多模型推理（如 speculative decoding）也会产生不同尺寸的 KV cache。这种异构性使得 PagedAttention 的两个核心假设——固定大小 embedding、全注意力——不再成立，导致严重的内存浪费和低效。

---

## 二、要解决的问题

**问题1：异构 embedding 导致内存碎片化**

PagedAttention 使用统一 page 大小，无法适应不同层/不同 token 类型的 embedding 大小差异。以 Llama 3.2 11B Vision 模型为例：
- 32 个全注意力层需要为文本 token 存储 KV cache
- 8 个交叉注意力层只需要为图像 token 存储 KV cache
- 文本 token 的 KV cache 大小是图像 token 的 4 倍

若用 PagedAttention 统一分配，会造成高达 **79.6%** 的内存浪费（MMMU-pro 数据集）。简单的替代方案（Max Page 方案、静态分区）要么仍有大量浪费，要么无法适应动态负载变化。

**问题2：异构注意力机制使 prefix caching 效率低下**

不同注意力机制对 prefix cache 的依赖不同：
- 全注意力层需要缓存所有 prefix token 的 KV cache
- 滑动窗口注意力只需要缓存最近若干 token（window size 内）
- Mamba 层只依赖最后一个 token 的状态

用全注意力的 LRU 策略管理所有层，会导致：
1. 低命中率（eviction 策略不匹配各层的实际访问模式）
2. batch size 与 prefix cache 命中率之间存在 trade-off（为最大化 batch size 只缓存活跃 token，则无法做 partial prefix hit）
3. 跨层 cache 命中依赖性（任何一层 cache miss 都需要全层重算）

## 三、核心设计

Jenga 提出了一套**基于 layer property 的异构内存管理框架**，核心设计分为两个维度：

### LCM Allocator：消除 embedding 大小差异导致的碎片化

Jenga 使用两级内存分配结构：
- **底层（Large Page）**：page 大小为所有可能 embedding 大小的最小公倍数（LCM）。例如，若各层 embedding 大小为 2KB 和 3KB，则 large page 大小为 6KB。
- **顶层（Small Page）**：每个 large page 内部按实际 embedding 大小划分 small page，不同层类型使用不同的 small page allocator。

LCM allocator 是 slab allocator 的特例，LCM 大小保证 large page 可以被任意层类型整除，从而在多种 embedding 大小共存时将内部碎片降至接近零。

### 层属性感知的 Prefix Caching：自定义 eviction 和 cache hit 策略

Jenga 将每种注意力层的行为抽象为两个接口：
- `active_pages(req, prefix_len)`：返回生成该长度 prefix 所需的 page 集合（决定哪些 page 是"活跃的"）
- `possible_prefix(req, is_hit)`：给定当前 cache 状态，返回该层所有有效 prefix（决定 cache hit 规则）

基于这两个接口，Jenga 实现了：
1. **自定义 LRU eviction**：只更新活跃 page 的 last access time，滑动窗口外的 token 具有更早的时间戳，优先被 evict；跨层使用统一 last access time，保证 eviction 均衡
2. **自定义 cache hit 检测**：各层独立判断有效 prefix，取所有层的最长公共有效 prefix 作为命中前缀

### Common Page Pool：平衡 batch size 与 prefix cache hit rate

Jenga 引入独立的 **Common Page Pool**，专门存储高概率被复用的 page（即预测的 common prefix 所对应的 page）。这类 page 不会因扩大 batch size 而被 evict，从而解决了扩大 batch 导致 cache 命中率下降的问题。

Common prefix 预测基于经验观察：若请求 A 与前一分钟内的请求 B 共享 prefix，则该 prefix 有 81% 概率在未来继续出现。Pool 大小通过模拟调度、最小化预测执行时间来确定（约 1000 pages 即可覆盖大多数场景）。

## 四、实现细节

- 用约 **4,000 行 Python 代码** 实现在 vLLM 之上，用户无需额外配置
- Jenga 自动从模型结构中解析所有可能的 embedding 大小，初始化内存管理系统
- 支持的层类型：全注意力、滑动窗口注意力、Mamba、Llama 4 局部注意力、VLM 交叉注意力、视觉 embedding cache
- 视觉 embedding cache 处理：分两种模式——allocate-on-demand（chunked prefill 完成后释放视觉 embedding）和 fully-allocated（将 KV cache 复用视觉 embedding 空间，使视觉 embedding cache 几乎不占额外显存）
- Speculative decoding 支持：LCM page 大小自动设为 draft model 和 target model embedding 大小的 LCM
- 执行时间估算模型（用于确定 common page pool 大小）：通过对不同 batch 配置 profiling + 线性回归得到参数

关键数据（Table 1，以 Gemma-3 27B 为例）：
- 滑动窗口层 embedding 大小：1664 KB/token
- 全注意力层 embedding 大小：320 KB/token
- LCM page 大小：无需手动指定，自动计算

**实验平台**：NVIDIA H100 80GB（主要）和 L4 24GB GPU

**基线**：vLLM v0.8.3、SGLang、TGI，以及两个扩展方案（Static Partition、Max Page）

| Llama 3.2 Vision | 1.71× | 2.16× |

## 六、批判性分析

**1. 吞吐量数据存在选择性问题**

论文主要报告的是"对 Jenga 最有利"的异构模型（Llama 3.2 Vision、Gemma-3 等），对全注意力模型（Llama 3.1）只给出了一个"无损"结论，但没有详细数字。实际上 Jenga 的双层分配结构比 PagedAttention 多一层间接寻址，在全注意力场景下理论上应有轻微开销，论文对此语焉不详。

**2. Common Page Pool 大小的确定方法过于依赖离线模拟**

论文使用模拟调度来确定最优 pool 大小，但真实负载存在突发性和分布漂移，离线确定的大小在生产环境中未必最优。论文提到"约 1000 pages 足够"，但这个结论是基于有限数据集得出的，泛化性存疑。

**3. Common Prefix 预测的精度未充分验证**

论文引用了 81% 的命中率（来自 Mooncake trace），但这个数字的统计背景不清晰——是在什么样的负载分布下测试的？对于非 chatbot 类型的工作负载（如 batch inference）是否仍然成立？论文的实验主要集中在 chatbot 和 QA 场景，对其他场景的泛化性没有系统验证。

**4. 实验基线不够公平**

论文对比的 Static Partition 和 Max Page 是论文自己实现的简单基线，而不是某个实际系统。与 SGLang、TGI 的对比只做了 batch size 对比（Figure 16），而没有端到端吞吐量对比，原因是"这些引擎只支持很少几个测试模型"——这在一定程度上回避了可能不利的比较。

**5. LCM page 大小可能在极端情况下非常大**

若某模型有多种差异较大的 embedding 大小，LCM 可能非常大，导致内存浪费。论文对此仅一笔带过（"2-3 种 embedding 大小"），缺乏对极端情况的分析。

**6. 与 Mamba 层相关的 speculative decoding 评估缺失**

Figure 20 中 Ministral（包含滑动窗口层）是唯一真正的异构模型，但为了与 vLLM 公平比较，关闭了 prefix caching，导致低估了 Jenga 的实际优势。

## 七、AI Infra / MLSys 视角

**核心 insight 的可迁移性**

Jenga 的最大贡献是将"层属性"（layer property）作为一等公民引入内存管理，通过 `active_pages` 和 `possible_prefix` 两个接口将内存管理策略与模型架构解耦。这种**接口抽象思路**对 AI Infra 领域有很强的启发价值：
- 当新型注意力机制（如 RetNet、RWKV、GLA 等）不断涌现时，只需为新层类型实现两个接口，即可自动获得最优内存管理
- 类似的抽象思路可以推广到 KV cache 卸载（CPU/disk offload）策略和 KV cache 压缩策略的个性化设计

**对 LLM 训练系统的启发**

Jenga 关注推理，但 LCM allocator 的思路对训练中的激活值内存管理也有参考价值：混合精度训练、MoE 模型中不同专家的激活大小不同，类似的两级分配思路可以减少训练中的显存碎片。

**值得跟进的研究方向**

1. **多机/多节点场景下的异构 KV cache 管理**：当前 Jenga 仅限于单节点。在 disaggregated prefill-decode（DistServe 场景）中，不同节点的 KV cache layout 可能不同，跨节点的 LCM page 迁移协议是开放问题。
2. **动态层类型识别**：某些 MoE 模型在运行时动态决定使用哪种注意力机制（如 DBRX），Jenga 的静态层属性抽象可能需要扩展。
3. **Common Page Pool 的在线自适应**：将 pool 大小的确定从离线模拟改为在线强化学习或自适应控制，以应对分布漂移。
4. **与 KV cache 量化/压缩的联合优化**：Jenga 解决了碎片化和 cache 命中率问题，但对 KV cache 本身的大小没有减少。将 Jenga 与 FP8 量化 KV cache 或 KV cache 蒸馏结合，是提升内存效率的下一个自然方向。

---

## 八、总结

Jenga 针对现代异构 LLM（混合全注意力、滑动窗口注意力、Mamba 等）在 GPU 内存管理上的痛点，提出了基于 LCM 的两级内存分配器和层属性感知的 prefix caching 框架，有效解决了 PagedAttention 在异构场景下的碎片化和低命中率问题。在 vLLM 上的实现以约 4000 行 Python 代码实现了平均 1.46× 的吞吐量提升和最高 83% 的显存利用率改善，并支持 Llama 4 的 10M+ 超长上下文。其核心价值在于将内存管理策略与模型层类型解耦的接口抽象，随着 LLM 架构持续异构化，这一设计思路的重要性将进一步凸显。主要局限是实验主要针对对 Jenga 有利的异构模型，全注意力场景和生产环境中的鲁棒性需要更多验证。
