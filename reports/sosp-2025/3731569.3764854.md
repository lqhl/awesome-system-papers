# Tiga: Accelerating Geo-Distributed Transactions with Synchronized Clocks

## 一、背景

地理分布式 OLTP（在线事务处理）系统是云基础设施和在线服务的基石。这类系统将数据分片（shard）以实现扩展性，并跨数据中心复制数据以容忍故障。为了提供强一致性保证（strict serializability），系统需要同时运行并发控制协议（如 2PL）和共识协议（如 Multi-Paxos），两者都会引入额外的消息轮次。在跨地域部署中，每一次额外的 wide-area round-trip time (WRTT) 都代价巨大（数十到数百毫秒）。

近年来，时钟同步技术取得了显著进步：Huygens 可实现微秒级甚至纳秒级同步精度，Google Cloud 默认的 chrony 服务也能稳定在 ~4.5ms 误差。这为基于时间戳的事务排序提供了新的机会。

---

## 二、要解决的问题

1. **延迟过高**：传统分层设计（并发控制 + 共识分离）需要多次 WRTT 才能提交事务，例如 2PL+Paxos 通常需要 3+ WRTT。
2. **现有合并协议的局限**：已有的合并协议（如 Tapir、Janus）虽然将并发控制和共识合并，但其 1-WRTT fast path 仅在事务不冲突（commutative）时有效。一旦事务在不同 server 上以不同顺序到达，就需要回退到慢路径（2+ WRTT），且需要昂贵的图算法（依赖追踪与环检测），严重影响吞吐。
3. **Timestamp inversion 陷阱**：简单的时间戳排序只能实现 serializability，无法保证 strict serializability（即丢失了外部一致性/linearizability 的部分）。跨分片的间接依赖关系可能导致实时顺序被违反。
4. **部署灵活性不足**：许多协议要求 coordinator 与 server 共置（co-locate）才能获得最优延迟，限制了实际部署场景。

---

## 三、洞察与设计

**关键洞察**：与其乐观地依赖事务的到达顺序（到达顺序在跨地域场景下经常不一致），不如利用同步时钟主动（proactively）为每个事务分配一个未来时间戳，使事务在到达所有 server 之前就已确定全局顺序。由于现代时钟同步精度（微秒级）远小于跨地域传输延迟（数十毫秒），添加的 headroom 可以有效掩盖异构网络延迟，让绝大多数事务在所有 server 上以一致的时间戳顺序被处理。

基于此洞察，Tiga 的核心设计包括三个方面：

1. **合并并发控制与共识（Consolidated Protocol）**：两者本质上都是在 server 间建立一致顺序，Tiga 将其统一为单层协议，避免重复协调开销。

2. **Proactive Ordering with Synchronized Clocks**：Coordinator 在提交事务时，基于测量的 one-way delay (OWD) 计算一个未来时间戳 `t = t_send + max(OWD to super quorum) + Δ`。Server 收到事务后在 priority queue 中缓冲，直到本地时钟超过时间戳才释放执行。这样大多数情况下所有 server 都能以一致的时间戳顺序处理事务。

3. **最小化 Server 协调开销**：Tiga 为每个 shard 指定一个 leader，leader 之间通过 timestamp agreement 确认时间戳一致性。在 full replication 部署下，所有 leader 可共置于同一 region（仅 LAN 开销）。对于 partial replication，Tiga 提供 detective approach（先执行后验证）和 preventive approach（先 agreement 后执行）两种模式，根据部署拓扑自动选择。

**避免 Timestamp Inversion**：当不同 leader 对同一事务使用了不同时间戳时，Tiga 通过两轮 timestamp exchange 确保所有 leader 达成一致，并在确认前阻止冲突事务的释放，从而保证 strict serializability。

## 四、实现细节

- **数据结构**：每个 server 维护 priority queue（按时间戳排序缓冲事务）、log list（已提交事务序列）、rMap/wMap（记录已释放事务的读写集时间戳，用于冲突检测）、sync-point 和 commit-point。
- **冲突检测**：事务到达时，server 将其时间戳与 rMap/wMap 中的记录比较。若时间戳小于已释放的冲突事务，leader 将其时间戳更新为当前本地时钟时间；follower 则等待 leader 的同步指令。
- **Optimistic Execution**：Leader 在时间戳到期后立即执行事务（不等待 timestamp agreement），执行结果通过 fast-reply 发送给 coordinator。Follower 仅记录日志不执行。
- **Quorum 要求**：Fast path 需要 super quorum（1 + f + ⌈f/2⌉），类似 Fast Paxos，确保 leader 故障恢复时能区分已提交和未提交事务。
- **Timestamp Agreement**：Leader 间交换各自使用的时间戳，取最大值作为 agreed timestamp。分三种情况：Case-1（一致，0.5 WRTT）、Case-2（本 leader 正确但需确认其他 leader 已更新，1 WRTT）、Case-3（本 leader 时间戳过小，需撤销执行并重新排队）。
- **Log Synchronization & Slow Path**：Leader 将 agreed log 同步给 follower，follower 更新后发送 slow-reply。事务在任一 shard 上 fast-committed 或 slow-committed 即可提交。
- **故障恢复**：基于 view-based 协议，view manager 检测 leader 故障并触发 view change。新 leader 从 f+1 存活 server 重建 log，恢复时间 ~3.8 秒。
- **实现基础**：基于 Janus 代码库，使用相同的 RPC 库和运行时环境，额外实现了 Detock 和 Calvin+ 作为对比基线。
- **Checkpoint 机制**：Server 定期对 commit-point 之前的 log 做 checkpoint，加速故障恢复。

## 五、实验结果

**实验环境**：Google Cloud，3 个 region（South Carolina、Finland、Brazil），n2-standard-16 VM，数据跨 3 region 复制。另有 Hong Kong 作为 remote coordinator region。

**基线**：2PL+Paxos、OCC+Paxos、Tapir、Janus、Calvin+、Detock、NCC、NCC+（共 8 个）。

### MicroBench（skew=0.5，低竞争）

| 指标 | Tiga | 最佳基线 | 提升 |
|------|------|---------|------|
| 最大吞吐 | 157.3K txns/s | Calvin+ 119.6K | 1.3× |
| P50 延迟（接近饱和） | 最低 | — | 1.4–4.6× 优于各基线 |

### MicroBench（固定 8K txns/s，变化 skew）

随 skew 增大（竞争加剧），除 Calvin+ 外所有基线性能急剧下降。Tiga 在 skew=0.99 下仍保持最低延迟，Calvin+ 延迟比 Tiga 高 33%。

### TPC-C

| 协议 | 吞吐 (K txns/s) |
|------|----------------|
| Tiga | 21.6 |
| Detock | 13.3 |
| Janus | 10.8 |
| Calvin+ | 6.1 |
| 2PL+Paxos | 2.1 |
| OCC+Paxos | 0.9 |
| NCC | 0.86 |

Tiga 在 TPC-C 下吞吐 1.6–3.5× 优于基线，延迟 1.5–3.7× 更低。

### 其他实验

- **故障恢复**：Leader 故障后 ~3.8 秒恢复到相同吞吐水平。
- **Leader 分离 vs 共置**：Leader 分离时 Tiga 吞吐下降 9.7%，但仍优于所有基线。
- **Headroom 敏感性**：Tiga 的自动 headroom 估计接近最优，减小导致更多 rollback，增大导致不必要等待。
- **不同时钟**：Chrony 和 Huygens 性能相近（同步误差远小于跨 region 延迟），ntpd 略差，badly synchronized clock 显著恶化。

## 六、批判性分析

1. **Super quorum 的实际代价被轻描淡写**：Fast path 要求 super quorum（1+f+⌈f/2⌉ = 1+f+⌈f/2⌉），当 f=1 时需 3/3 个副本响应（即零容错）。这意味着任何单个 follower 的临时慢响应都会导致退回 slow path，论文未充分讨论在真实网络抖动下 fast path 的实际命中率。

2. **实验规模偏小**：3 shard / 6 shard 的配置远小于生产级系统（如 Spanner 的数千分片）。随着分片数增加，multi-shard 事务的 timestamp agreement 涉及更多 leader，其 LAN/WAN 开销可能不再 negligible。论文未展示大规模分片下的可扩展性。

3. **Headroom 估计依赖稳定网络**：Tiga 的 proactive ordering 依赖准确的 OWD 估计。论文在稳定的 Google Cloud 内部网络上评估，但未讨论在公网、跨云或网络波动较大的场景下 headroom 估计的鲁棒性。Bad-Clock 实验展示了时钟不准的影响，但未测试 OWD 本身剧烈波动的情况。

4. **与 Spanner 的比较缺失**：论文定位为 "geo-replicated transactional databases such as Google Spanner" 的改进，但实验中未直接与 Spanner（或 CockroachDB、TiDB 等生产系统）对比。Table 4 的理论比较不能替代实际性能对比。

5. **Interactive transaction 支持依赖外部技术**：Tiga 原生只支持 one-shot stored procedure，对 interactive（multi-shot）事务依赖 decomposition technique（引用 [70]），实际适用范围和性能代价未充分评估。TPC-C 中 interactive 事务的比例有限，不足以代表所有 OLTP workload。

6. **Timestamp agreement 的阻塞效应**：当 priority queue 头部事务正在进行 timestamp agreement 时，后续所有冲突事务被阻塞。在高竞争 + leader 分离的场景下，这种阻塞可能级联放大，论文虽然提到了但未深入分析其最坏情况行为。

---

## 七、总结

Tiga 提出了一种利用同步时钟主动排序事务的地理分布式事务协议，将并发控制与共识合并为单层协议，在大多数场景下实现 1-WRTT 提交延迟，同时保证 strict serializability 和容错。核心创新在于通过 proactive timestamp assignment 和 headroom 机制避免了传统协议中因到达顺序不一致而导致的冲突回退。实验表明 Tiga 在吞吐和延迟上显著优于 8 个基线协议。主要局限包括：实验规模较小、super quorum 对 fast path 可用性的影响、以及对稳定网络环境的依赖。该工作适用于具有良好时钟同步基础设施的云环境中地理分布式数据库场景。
