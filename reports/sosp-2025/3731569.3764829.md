# IC-Cache: Efficient Large Language Model Serving via In-context Caching

**作者**：Yifan Yu (UIUC)、Yu Gan (Google)、Nikhil Sarda (Google)、Lillian Tsai (Google)、Jiaming Shen (Google)、Yanqi Zhou (Google)、Arvind Krishnamurthy (Google & UW)、Fan Lai (UIUC)、Henry M. Levy (Google & UW)、David E. Culler (Google)

## 一、背景

大语言模型（LLM）已在聊天机器人、代码生成、数学推理等各类应用中取得显著成功，但以规模化方式提供 LLM 服务面临严峻挑战。以 DeepSeek-R1（671B 参数）为代表的顶级模型需要数百块 GPU 支撑，单次请求延迟可达数秒，服务成本比传统 ML 推理高出数个量级。

现有 LLM 服务系统的优化工作主要集中在两个方向：（1）提升系统吞吐量，如连续批处理（Orca）、PagedAttention（vLLM）、分离式 prefill/decode（DistServe/Splitwise）；（2）降低调度延迟，如基于请求难度的模型路由（RouteLLM）。然而，一个被忽视的互补机会是：**利用历史请求之间天然的语义相似性**。

作者的分析发现，在 MS MARCO（100 万请求）、Natural Questions（30 万请求）、LMSys-Chat（100 万请求）三个真实数据集中，超过 70% 的请求在历史请求中能找到余弦相似度超过 0.8 的语义近似对，这远高于随机请求对的 0.5 相似度基准。

---

## 二、要解决的问题

**语义缓存的局限**：现有的语义缓存方案（如 GPT-Cache、Databricks）直接复用历史响应，导致严重质量下降——在代码生成和数学推理任务中，win rate 从 50% 骤降至 18%，因为任何上下文不匹配都可能导致偏题回答。

**小模型能力不足**：简单地将请求路由到小模型虽然省成本，但质量损失难以接受。例如 Gemini-1.5-Flash 相比 Gemini-1.5-Pro 的平均响应分数低 0.39（在 -3 到 +3 的七分制中），win rate 仅 35%。

**峰值负载下的 SLO 保障**：实测 Azure LLM 服务 trace 显示，负载波动剧烈，峰谷比最高达 25×，即使是高度优化的专有平台也会出现严重的延迟抖动。

**核心矛盾**：如何在**不损害响应质量**的前提下，通过复用历史数据把请求卸载到小模型，实现吞吐和延迟的实质性改善？

---

## 三、核心设计

IC-Cache 的核心洞察是：**不直接复用历史响应，而是将大模型服务过的历史 request-response 对作为 in-context examples，拼接到新请求的 prompt 前，借助 in-context learning 能力让小模型"模仿"大模型的推理轨迹和回答风格**。

系统由三个组件构成：

### Example Selector（示例选择器）
目标是高效找到对当前请求最有帮助的历史示例组合。

- **两阶段选择**：Stage 1 用文本嵌入的余弦相似度做轻量级预筛选，通过 K-Means 聚类（K=√N）控制搜索成本；Stage 2 用一个轻量级 proxy 模型（如 TinyBERT，参数量仅为 Qwen2.5-7B 的 0.2%）预测每个候选示例对当前请求的端到端帮助度。
- **动态示例数量**：示例过多会增加 prefill 延迟并可能超出 context window，IC-Cache 通过在线采样周期性地评估不同帮助度阈值下的效率收益，自适应选择最优示例数量。

### Request Router（请求路由器）
目标是根据请求复杂度、示例质量和当前系统负载，动态决定将请求发给哪个模型。

- **上下文多臂老虎机（Contextual MAB）**：将路由问题建模为 MAB，每个"臂"对应一个候选模型（小模型+示例 或 大模型不加示例）。Router 模型仅 50 万参数，持续从用户反馈（点赞/点踩）在线更新。
- **负载感知偏置**：用 EMA 跟踪系统负载，负载超出阈值时通过 tanh 函数平滑地降低大模型的选择得分，增加对小模型的偏向，无需重训 Router。
- **选择性反馈收集**：只对 Router 输出置信度接近均匀分布的"不确定"请求主动征求用户反馈，兼顾探索效率和反馈成本。

### Example Manager（示例管理器）
目标是离线提升示例质量、在线管理缓存大小。

- **代价感知示例重放（Cost-aware Replay）**：定义每个示例 e 的提升潜力 G(e) = (1 - 归一化响应质量) × 归一化模型代价。G(e) 高的示例（响应质量差但用大模型生成代价高）被优先重放，即在离线时用大模型再次生成更好的响应并替换。
- **背包式缓存淘汰**：将缓存管理建模为一维背包问题，每个示例的"重量"是其文本大小，"价值"是其预期效率收益，最大化缓存总价值。
- **明文缓存**：100 万条 LMSys-Chat 示例仅需约 1GB 内存（A100 的 1%），且明文格式跨模型通用。

## 四、实现细节

- **代码规模**：约 3,000 行代码，支持 vLLM、HuggingFace Runtime、LangChain 三个主流框架，仅需少量代码集成。
- **后端架构**：Example Retriever、Request Router、Example Manager 各自运行在独立进程中，通过 gRPC 通信，支持水平扩展。
- **相似度搜索**：使用 GPU 加速的 FAISS 库实现高吞吐向量检索。
- **Router 实现**：基于 JAX，内置优先级重放 buffer 和 Thompson Sampling 算法。
- **容错**：各组件定期 checkpoint 状态；若 Retriever 或 Router 发生故障，请求自动绕过直接发到推理后端，保证服务连续性。
- **隐私**：提供访问控制 API；支持用 spaCy 在客户端本地移除 PII；对有严格隐私要求的场景，支持用差分隐私（DP）合成的示例替代真实历史示例。

## 五、实验结果

**实验平台**：16 块 NVIDIA A100 GPU，请求到达模式来自 Microsoft Azure LLM 服务 trace。

**模型**：Gemini-1.5-Pro/Flash（专有）、DeepSeek-R1、Qwen2.5、Gemma-2、Phi-3（开源）。

**数据集**：Alpaca、LMSys-Chat、OpenOrca、MS MARCO、Natural Questions、WMT-16、NL2Bash、Math500。

**基线**：w/o IC-Cache（纯 vLLM）、RouteLLM、LongRAG、SemanticCaching。

| 指标 | 结果 |
|------|------|
| 吞吐提升（vs. 大模型） | 1.4–5.9× |
| TTFT/端到端延迟降低 | 28–71% |
| 质量损失 | 无（部分任务小模型超越大模型） |
| 相同吞吐下质量提升（vs. RouteLLM） | 4–16% |
| 相同质量下吞吐提升（vs. RouteLLM） | 2.3×（Natural Questions，50% win rate 目标） |

**缓存效率**：Translation 任务中仅需约 12,056 个示例（<20MB）即可接近饱和性能；Code Generation 仅需约 2,022 个示例。

**DP 隐私**：使用 DP 合成示例后质量轻微下降，但仍显著优于无 IC-Cache 的基线。

## 六、批判性分析

**1. 70% 相似度的数据基础存疑。**
论文声称 70% 的请求有语义相似对，但这一结论基于余弦相似度 > 0.8 的阈值，而 0.8 这个阈值的选取本身缺乏充分论证。更关键的是，语义相似不等于功能等价——两个表述相近但意图不同的请求（如"解释 X"vs."比较 X 和 Y"）被选为示例可能反而有害。论文的"semantic similarity vs. helpfulness"弱相关实验（图 7）恰恰说明了这一点，但没有进一步量化到底有多少比例的"相似请求"实际上能产生有帮助的示例。

**2. 对用户反馈的依赖是一个隐含假设。**
Router 的训练和 Example Manager 的 G(e) 计算都依赖用户反馈（thumbs up/down）。但在实际部署中，绝大多数用户不提供显式反馈。论文提到"即使 1% 采样率也能获得充足数据"，但对冷启动阶段（历史数据稀少时）的性能没有深入分析，也没有讨论反馈噪声的影响。

**3. 评测循环性问题。**
论文用 LLM-as-a-judge 评估质量（DeepSeek-R1 评 Gemini 的输出，Gemini 评 DeepSeek 的输出），同时这些大模型也是 IC-Cache 要从中卸载流量的目标模型。这产生了一个微妙的循环：用大模型的标准来评判"小模型是否充分模仿了大模型"，结论对大模型本身定义的质量标准天然有利，未必代表真实用户满意度。

**4. SFT 基线对比不公平。**
论文用域外 SFT（Alpaca 上的 OOD 测试）对比 IC-Cache，而 IC-Cache 天然适合动态分布变化（在线更新）。这一对比对 SFT 不公平，更公平的基线应是在同分布数据上持续微调或 LoRA 适配的小模型。

**5. 实验规模偏小。**
整个实验在 16 块 A100 上进行，而生产级 LLM 服务往往涉及数百至数千块 GPU、多地域部署、数十亿参数的模型。系统的分布式 gRPC 架构在大规模下的通信开销、FAISS 检索延迟、MAB 全局状态同步等问题在论文中未得到充分验证。

**6. "小模型超越大模型"结果被过度渲染。**
论文多处强调"2B 模型在 MSMARCO 上 win rate 超过 50%，超越 27B 模型"，但 MSMARCO 是一个高度重复的搜索查询数据集，天然有利于 IC-Cache（相似请求极多）。这一结论不能推广到更多样化、创造性更高的任务。

## 七、AI Infra / MLSys 视角

**对 LLM 服务系统的启发**：IC-Cache 提出了一个新颖的"capability augmentation"范式，与 prefix caching、KV cache 复用等现有优化正交，可以叠加使用。其核心贡献在于把 in-context learning 从模型能力提升工具转化为系统效率工具，这是一个值得关注的视角转换。

**可迁移的设计思路**：
- **两阶段选择 + proxy model**：粗筛（高效但低精度）+ 精排（低效但高精度）的级联设计在 retrieval 系统中广泛使用，IC-Cache 将其引入 LLM serving 的 example selection，与 RAG 系统的设计有相通之处，但目标不同（不是补充知识，而是转移能力）。
- **MAB 路由**：相比基于分类器的路由，MAB 对数据分布变化更鲁棒，且不需要提前标注训练集，适合在线学习场景。这个思路对"多模型混合部署、动态流量分配"这类工程问题有直接参考价值。
- **负载感知偏置 + tanh 平滑**：用 tanh 而非 step function 来处理过载信号，防止路由决策震荡，是一个简单实用的工程技巧。

**值得跟进的方向**：
- **IC-Cache + speculative decoding**：能否用小模型+高质量示例来为大模型做 speculative decoding，既利用了示例的能力提升效果，又节省了 token 生成开销？
- **跨任务 example 泛化**：当前 IC-Cache 的 example pool 是任务内的，是否可以研究跨任务的示例迁移？例如数学推理的示例是否能提升代码生成的质量？
- **与 KV cache prefix sharing 的联合优化**：IC-Cache 在 prompt 前拼接示例，这意味着相同示例集合的请求可以共享 KV prefix cache。如何联合优化 example routing 和 KV cache 调度，是一个有实际价值的研究问题。
- **冷启动问题**：IC-Cache 依赖大量历史数据，新部署场景下如何用少量数据实现 bootstrap？可借鉴 few-shot learning 和 data-efficient RL 的思路。

---

## 八、总结

IC-Cache 提出了一种新的 LLM serving 优化范式：将历史 request-response 对作为 in-context examples，在不修改模型权重的情况下实现小模型的实时能力增强，从而将请求自适应地卸载至小模型，降低延迟和成本。系统通过两阶段 example 选择、MAB 请求路由和代价感知 example 管理三个组件，在 Gemini、DeepSeek、Qwen 等多个模型家族上实现了 1.4–5.9× 吞吐提升和 28–71% 延迟降低，且不损害响应质量。其主要局限在于：对用户显式反馈的依赖、冷启动问题未深入讨论、实验规模偏小（16 A100），以及"小模型超越大模型"的结论在高相似度数据集上才成立。
