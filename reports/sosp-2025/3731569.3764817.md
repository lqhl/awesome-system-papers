# Ghost in the Android Shell: Pragmatic Test-oracle Specification of a Production Hypervisor

## 一、背景

开发能够稳健提供安全保障的系统代码一直极具挑战性。传统软件开发实践不足以保证安全性，而完整的形式化验证（如 seL4、CertiKOS、SeKVM 等项目）虽然近年来取得了许多成功，但仍面临重大的工程障碍：

- 需要专家级技能和专用工具（如定理证明器），且工具往往处于活跃开发中
- 通常要求代码以特定语言或受限方言编写
- 维护负担沉重——每次软件更新都需要调整证明
- 存在阶梯式的投入/回报曲线——需要大量前期投入，最终才能获得定理证明的回报

与此同时，更轻量级的形式化方法虽然早在 1970 年代就已被提倡，但至今仍未得到充分探索和部署。

pKVM（Protected KVM）是 Google 为 Android 开发的 hypervisor，旨在隔离 Android Linux 内核（host）与处理敏感数据的 guest 虚拟机，防止内核被攻破后影响 VM，反之亦然。pKVM 自 Android 13 起部署，使用 C 和 Arm 汇编编写，运行在 Arm EL2 特权级别，具有高并发性，且专为实际安全和性能目标设计，而非为验证而设计。

---

## 二、要解决的问题

1. **完整形式化验证的高门槛与生产代码之间的鸿沟**：pKVM 是用传统方法（C 语言、Linux 内核开发流程）编写的生产级 hypervisor，无法直接适用现有形式化验证工具链。

2. **缺乏实用的中间方案**：在"完全不做规约"和"完整形式化证明"之间，缺少一种既能提供有意义的正确性保障、又不需要专家工具和专业知识的轻量级方法。

3. **Hypervisor 规约的特殊困难**：
   - 实现与底层 Arm-A 硬件架构规范深度交织（页表管理、地址翻译）
   - 高并发性——多硬件线程并发运行在 hypervisor 中，使用锁和微妙的 ownership 机制
   - 需要 loose specification（如 host 内存的 mapping-on-demand 和 OOM 错误的不确定性）
   - 运行在 EL2 bare-metal 环境——无法使用常规覆盖率和测试工具
   - 过于随机的测试会导致系统崩溃
   - C 语言本身是极差的规约语言（缺少纯计算子语言、归纳数据类型、模式匹配、参数多态）

## 三、洞察与设计

**关键洞察**：全功能正确性规约可以用实现语言本身（C）编写为可执行的 test oracle，嵌入到生产代码中与实现一起运行和检查——无需任何专用形式化工具或语言。尽管 C 在表面上是一个极差的规约语言，但通过适当的编程风格（morally pure functions），完全可以写出清晰、可读的规约代码。

### 核心设计

**Reified Ghost State（具化的幽灵状态）**：定义一组 C 数据结构作为 pKVM 具体状态的数学抽象。Ghost state 使用简单的数学结构（有限映射、选项类型等）表达，抽象掉实现细节（指针结构、页表的 Arm 架构表示、内存管理等）。

**抽象函数（Abstraction Functions）**：用 C 实现的可计算函数，从 pKVM 的具体状态计算出 ghost state。关键之一是将具体页表完整遍历，转换为从虚拟地址到物理地址/权限的有限映射（finite map）。

**规约函数（Specification Functions）**：对每个异常处理器（hypercall 或其他异常），定义一个纯函数，从 pre-state ghost state 计算出期望的 post-state ghost state。运行时比较期望 post-state 与实际记录的 post-state 是否相等。

**遵循 Ownership 结构**：Ghost state 的结构镜像了 pKVM 的锁/ownership 机制。每个受锁保护的组件在 ghost state 中封装在 option type 中，只在对应锁被持有时才记录。这避免了引入大锁改变并发行为。

**处理非确定性**：
- OOM 错误的 loose specification：规约函数参数化实现的返回值
- Host 共享内存的非确定性读取：参数化实际读取的值，运行时从实现中记录

**测试基础设施**：
- "hyp-proxy" 内核补丁——将 pKVM API 暴露给用户空间测试
- 自定义覆盖率工具——在 EL2 环境实现 GCOV 兼容的覆盖率收集
- 手写测试（41 个）+ 随机测试（用抽象模型引导生成，约 200,000 hypercalls/小时）

## 四、实现细节

**Ghost State 数据结构**：
- `ghost_state` 结构体包含：`ghost_pkvm`（pKVM 的 Stage 1 页表抽象映射）、`ghost_host`（host 的 Stage 2 注解和共享映射）、`ghost_vms`（guest VM 元数据数组）、`ghost_globals`（初始化常量）、`ghost_cpu* locals[]`（每 CPU 本地状态）
- `mapping` 类型：用有序链表实现的有限映射，支持空映射、单例映射、映射加减法、合并等操作
- `abstract_pgtable`：将映射与页表内存足迹结合，用于检查分离性不变量

**插桩方式**：
- 在锁获取/释放点插入 ghost state 记录调用（`#ifdef CONFIG_NVHE_GHOST_SPEC`）
- 在异常处理器入口/出口记录线程本地状态
- 几乎所有代码隔离在独立的 `ghost/` 目录的 `.h` 和 `.c` 文件中

**内存管理**：
- 在 EL2 使用简单的 arena allocator，内存足迹与 pKVM 其余部分物理隔离
- 可增长的组件（ghost VM、ghost vCPU）使用简单的 malloc 实现

**规约函数示例**（`host_share_hyp`）：
1. 从 ghost pre-state 读取 hypercall 参数（寄存器 x1）
2. 检查权限——目标页必须由 host 独占拥有
3. 克隆 pre-state 中 host 和 pKVM 的映射到 post-state
4. 构造抽象映射属性（权限、内存类型、page state）
5. 更新 post-state 映射
6. 写入返回码到寄存器

**代码规模**：
- pKVM 本身约 11,000 LoC
- 规约总计约 14,000 LoC：hypercall/trap 规约 2,600 + 抽象记录函数 1,300 + 抽象数据类型 4,500 + 配置/diff/打印等

## 五、实验结果

| 指标 | 数值 |
|------|------|
| pKVM 代码量 | ~11,000 LoC |
| 规约代码量 | ~14,000 LoC |
| 手写测试数 | 41 个（19 正常路径 + 22 错误路径） |
| 规约函数覆盖率 | 92%（459/497 行） |
| host_share_hyp 覆盖率 | 100%（排除不可达代码） |
| 随机测试吞吐 | ~200,000 hypercalls/小时（QEMU, Mac Mini M2） |
| 最长随机测试运行 | 24 小时 |
| 随机测试发现的规约错误 | 9 个（均与微妙的错误场景相关） |
| 启动时间开销 | 3.2x（1.49s → 4.76s） |
| 手写测试开销 | 11.5x（1.07s → 12.3s） |
| 内存开销 | ~18 MB |
| 总投入 | ~1 人年（vs pKVM ~30 人年开发） |

### 发现的 Bug

| Bug | 描述 | 发现方式 |
|-----|------|---------|
| 1 | 内部分配器（memcache）topup 路径缺少对齐检查，恶意 host 可清零内存 | 阅读代码（写规约过程中） |
| 2 | memcache topup 缺少大小检查，可能触发非法左移 | 阅读代码 |
| 3 | vCPU load/init 缺少同步，允许 relaxed race 访问未初始化内存 | 阅读代码 |
| 4 | host page fault 时，pKVM 对 host 并发修改虚拟映射不够健壮，可能导致 hypervisor panic | 运行规约检查 |
| 5 | 初始化 pKVM 虚拟线性映射时，在物理内存很大的设备上可能与 IO 映射重叠 | 阅读代码 |

## 六、批判性分析

1. **Bug 发现主要来自阅读代码而非运行规约**：5 个 bug 中只有 1 个通过实际运行规约检查发现，其余 4 个在编写规约时通过阅读代码发现。这在一定程度上削弱了"可执行规约"作为测试工具的核心卖点——真正的 value 更多来自"写规约逼迫深入理解代码"的副作用，而非运行时检查本身。

2. **覆盖范围有明显局限**：论文不涉及设备直通（device passthrough）、Arm GIC、IOMMU，也不覆盖 side-channel、liveness。这些恰恰是 hypervisor 安全性中最棘手的部分。论文对此的解释是"底层架构规范复杂且不完全清晰"，但这也暴露了该方法在面对真正复杂的硬件交互时的局限性。

3. **规约代码量超过了被规约的代码**：14,000 LoC 规约 vs 11,000 LoC 实现。作者称这是"lightweight"方法，但 1.27x 的规约/实现代码比率以及~1 人年的投入，对于传统开发团队来说并不算轻量。

4. **规约嵌入在被规约对象中的循环依赖**：规约运行在 pKVM 自身之上，依赖 pKVM 的部分正确性。虽然作者认为"bug 恰好掩盖自身"不太可能，但这确实是一个理论上的盲区——尤其是对于安全关键代码。

5. **并发覆盖不完整**：论文承认无法处理释放并重取锁的 hypercall 的分阶段执行，也无法约束 EL0/EL1 对页表的隐式访问与 pKVM 更新之间的竞争。这些恰恰是并发 bug 最容易出现的地方。

6. **随机测试的有效性证据不足**：虽然报告了 200,000 hypercalls/小时和 24 小时运行，但没有给出发现了什么 bug 或达到了什么状态空间覆盖。9 个"规约错误"不等于实现 bug。Synthetic bug testing 也只是简要提及，没有量化结果。

7. **可维护性声称需更强证据**：虽然提到跨 Android 版本成功移植，但 Android 15 移植"in progress"（截至 2025 年初），且作者承认 ownership 结构变更需要"对应的 ghost state 结构变更"——这正是形式化验证维护负担问题的缩影。

---

## 七、总结

本文展示了一种用实现语言（C）编写全功能正确性规约并作为 test oracle 运行时检查的轻量级方法，并将其应用于 Google 的生产级 hypervisor pKVM。通过 reified ghost state、跟踪 ownership 结构的抽象函数、以及纯函数风格的规约函数，该方法无需任何专用形式化工具即可提供有意义的正确性保障。论文在 pKVM 中发现了 5 个真实 bug，证明了可行性。然而，该方法的主要价值更多来自编写规约时对代码的深入理解，而非运行时检查；其覆盖范围有限（不含设备、GIC、完整并发），规约代码量超过实现代码，且维护成本随实现演进不可忽视。总体而言，这是一个介于无规约和完整形式化验证之间的有价值的中间地带，但"lightweight"一词需要放在与完整形式化验证比较的语境下理解。
