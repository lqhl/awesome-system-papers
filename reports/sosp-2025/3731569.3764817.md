## 一、背景

系统软件的安全保证一直是个难题。传统开发实践（测试、代码审查）难以覆盖并发、特权代码中的微妙缺陷；而完全形式化验证（如 seL4、CertiKOS）虽然能给出数学级别的正确性保证，但代价极高：需要专业形式化工具（Coq/Isabelle）、专业工程师技能、代码往往要为验证而特别设计，且维护成本随着代码迭代急剧上升。

在这两个极端之间存在一个探索不足的中间地带：**可执行规范 + 运行时检查（test-oracle specification）**——用程序语言本身写出期望行为的规范，在测试时与实现对比。这一思路可追溯至1970年代，但在生产系统软件中几乎无人实践。

本文的研究对象是 **pKVM（Protected KVM）**，Google 为 Android 开发的 hypervisor，负责隔离 Android Linux 内核（host）和受保护的 guest 虚拟机。pKVM 部署于 Android 13+，运行在 ARM 的 EL2 特权级，使用 ARM Stage 2 地址翻译实现内存隔离。它用 C 和 ARM 汇编编写，高度并发，且完全按照生产工程而非验证友好的方式设计——是一个极具代表性的挑战性目标。

## 二、要解决的问题

**主要挑战**：如何以较低成本为 pKVM 这样的生产 hypervisor 建立有意义的功能正确性规范？

具体难点如下：

1. **规范与底层硬件架构紧耦合**：pKVM 的行为依赖 ARM-A 的页表格式和地址翻译机制，规范必须能正确描述硬件隐式行为（如页表遍历）。

2. **高并发**：多个硬件线程可同时运行在 hypervisor 中，共享状态受细粒度锁保护，任何时刻都无法安全地对完整状态拍快照。

3. **规范必须保持"宽松"（loose）**：部分行为本质上不确定，例如 OOM 错误、按需映射（mapping-on-demand）的精确范围——过于精确的规范会变成过拟合（over-fitting）。

4. **pKVM 在 EL2 裸机运行**：无法从用户空间直接访问其 API，标准测试工具（GCOV 等）也不可用。

5. **随机测试会崩溃整个系统**：pKVM 的安全模型假定 host 可能是恶意的，随意构造的 hypercall 序列在历史依赖意义上可能导致 host 内核 crash，使测试无法推进。

6. **规范语言是 C**：C 缺乏归纳数据类型、参数多态、纯函数抽象等有利于写规范的特性。

## 三、核心设计

### 3.1 总体思路

核心方案是：用 C 写一套**可执行规范（reified ghost state + specification functions）**，链接进 pKVM 二进制，在运行时将每次 exception handler 的「期望后状态」与「实际观测后状态」进行比较。

整个方案分三层：

- **Ghost state（幽灵状态）**：对 pKVM 具体状态的数学抽象，用 C 数据结构表示有限映射（finite partial maps）。
- **Abstraction functions（抽象函数）**：从 pKVM 具体状态（页表指针、寄存器等）计算出 ghost state。
- **Specification functions（规范函数）**：纯函数，从 pre-ghost-state 计算出期望的 post-ghost-state。

运行时流程：
1. 进入 exception handler 时记录 pre-ghost-state
2. 执行完毕后记录 post-ghost-state
3. 用 spec function 从 pre-state 计算期望 post-state
4. 比较期望 post-state 与实际 post-state，不一致则报错

### 3.2 Ghost State 的结构

Ghost state 的结构刻意模仿 pKVM 的锁所有权结构（ownership discipline）：

```c
struct ghost_state {
    struct ghost_pkvm pkvm;     // pKVM 自身的 Stage 1 映射
    struct ghost_host host;     // host 的 Stage 2 映射（两个抽象映射：annot + shared）
    struct ghost_vms vms;       // 每个 guest VM 的元数据和 Stage 2 映射
    struct ghost_globals globals;
    struct ghost_cpu* locals[NR_CPUS];  // 每个物理 CPU 的线程局部状态
};
```

每个受锁保护的字段用 `option` 类型（C 里用 `bool present` 模拟）表示——只有在持锁时才"存在"，否则为 absent。

页表被抽象为**有序链表实现的有限区间映射**（finite partial maps），支持 empty、singleton、union、subtract 等操作，完全剥离了 ARM 页表树的内部结构。

### 3.3 处理并发

在 pKVM 加锁/解锁的点插桩，记录对应状态分量。ghost state 使用独立的 arena allocator，内存与 pKVM 其余部分隔离。规范不引入大锁，不改变 pKVM 的并发可观察行为。

### 3.4 处理宽松规范

对两类不确定性：
- **OOM 错误**：将 spec function 参数化，传入实现的实际返回值；spec 允许任意 hypercall 以 `-ENOMEM` 失败。
- **按需映射**：host Stage 2 的 ghost state 只记录上下界（必须/可以映射的范围），而非精确状态。
- **共享内存读取**：pKVM 用 `READ_ONCE` 读取 host 共享内存，这些值被记录进 `ghost_call_data` 传给 spec function。

## 四、实现细节

### 4.1 规范的侵入性

规范代码几乎全部隔离在新增的 `ghost/` 目录下，主 pKVM 代码中只有少量 `#ifdef CONFIG_NVHE_GHOST_SPEC` 守护的调用点。构建直接使用 Linux 内核的正常构建过程，在 QEMU 下运行。

### 4.2 抽象函数

页表抽象函数遍历整个 ARM 页表树（而非仅查询特定地址），将树结构翻译为有限映射。为了支持 ARM 的 block entry（大页），抽象函数使用 `extend_mapping_coalesce` 操作，尽量合并相邻映射片段。

### 4.3 测试基础设施

- **hyp-proxy**：一个内核补丁，将 pKVM 的 hypercall API 和所需内存管理暴露给 user space，测试用 OCaml 库封装。
- **覆盖率**：重新工程化 GCOV 的 linker 初始化和数据传输，使覆盖率数据可以从 EL2 传递到 EL0 用户空间。
- **手写测试**：41 个，其中 19 个测试无错误路径，22 个测试错误路径，少量测试高并发+锁。`__pkvm_host_share_hyp` 的实现代码（非 unreachable 部分）达到 100% 行覆盖；规范函数整体覆盖 92%（459/497 行）。
- **随机测试**：使用极简抽象模型（分配内存池、共享集合、VM 集合）引导随机 API 调用生成，避免触发 host crash，在 QEMU（Mac Mini M2）上运行，约 200,000 次 hypercall/小时，最长单次运行 24 小时，发现 9 处规范错误。

### 4.4 规模与代价

| 指标 | 数值 |
|---|---|
| pKVM 实现代码（含 KVM 共享部分） | ~11,000 行 |
| 规范代码（hypercall spec + abstraction） | ~3,900 行 |
| 抽象数据类型 + 基础设施 | ~4,500 行 |
| 规范总计 | ~14,000 行 |
| 总投入人力 | ~1 人年 |
| Boot 运行时开销 | 3.2x（1.49s → 4.76s） |
| 手写测试运行时开销 | 11.5x（1.07s → 12.3s） |
| 内存额外占用 | ~18 MB |

## 五、实验结果

### 5.1 找到的 pKVM Bug

| # | 描述 | 发现方式 |
|---|---|---|
| 1 | memcache topup 路径缺失对齐检查，允许恶意 host 清零内存 | 阅读代码 |
| 2 | memcache topup 缺失 size 检查，可能触发非法左移 | 阅读代码 |
| 3 | vCPU load/init 缺少同步，可能引发 relaxed race 导致访问未初始化内存 | 阅读代码 |
| 4 | host page fault 时 pKVM 不能健壮处理 host 并发修改其虚拟映射，可能导致 hypervisor panic | **规范测试** |
| 5 | 初始化时 pKVM 虚拟线性映射可能与 IO 映射重叠（大内存设备） | 阅读代码 |

5 个 bug 中，只有 bug 4 是通过运行规范发现的；其余 4 个是在深读代码以理解和撰写规范的过程中发现的。

### 5.2 规范自身 Bug

随机测试额外发现了规范本身的 9 处错误，主要集中于微妙错误场景，促进了与 pKVM 开发者的沟通澄清。

## 六、批判性分析

**亮点**：
- 方法论诚实：论文明确指出 4/5 个 pKVM bug 是通过阅读代码（而非运行规范）发现的。这是难得的诚实——在很多类似工作中，这类"副作用"发现往往被夸大为方法本身的贡献。
- 规范即思考工具的论断有说服力：写规范迫使作者深入理解实现的所有权模型，这本身就是价值。

**疑问与批评**：

1. **规范比实现还大**：规范代码约 14,000 行，超过 pKVM 实现的 11,000 行。对于声称"轻量级"的方法，这是一个明显的尴尬。虽然规范包含大量基础设施代码，但维护代价不可忽视——论文承认需要追踪实现的锁结构变化。

2. **1 人年的成本被低估了**：论文声称总投入约 1 人年，但作者团队是顶尖的形式化方法专家（剑桥 REMS 组），他们能以专业直觉快速找到关键不变量。声称"普通开发者可以做类似的事"缺乏充分论证——规范写作对领域认知和代码理解的要求远超一般测试工作。

3. **规范的正确性依赖于规范本身**：论文承认，如果 pKVM 的 bug 破坏了 ghost state，可能导致规范错误被掩盖。虽然作者认为这"不太可能"，但这是一个循环依赖：用来测试 pKVM 的规范链接在 pKVM 内部运行。

4. **"功能正确性"定义范围有限**：规范不覆盖设备隔离（GIC、IOMMU）、侧信道、活性（liveness），而这些对 hypervisor 安全至关重要。论文将这些归为"limitations"，但在安全背景下，侧信道和设备隔离不是小问题。

5. **规范测试的区分能力有限**：随机测试运行 200,000 次 hypercall/小时，仅找到 1 个实现 bug（其余 9 个是规范 bug）。在 24 小时的最长运行中，找到 bug 的密度相当低。对于并发相关的深层 bug，随机测试的覆盖能力存疑。

6. **"松散规范"与测试精度的矛盾**：为了应对不确定性，规范对部分行为（OOM、按需映射范围）保持宽松，这降低了规范的判别能力——一些错误实现行为也可能被认定为合法。论文对这个 trade-off 的分析较浅。

---

## 七、总结

本文为 Google pKVM hypervisor 构建了一套用 C 编写的可执行功能正确性规范，作为 test oracle 在测试时与实现进行运行时比较。核心贡献在于展示了如何应对生产 hypervisor 的多重挑战：与 ARM 架构紧耦合的规范、细粒度并发所有权、宽松行为的函数式表达，以及在 EL2 特权级环境下的测试基础设施。方法论上处于完全形式验证（高保证/高成本）和常规测试（低成本/弱保证）之间的空白地带，投入约 1 人年，代价远低于全验证，但发现了 5 个真实 bug，并迫使开发者深入理解实现的所有权结构。主要局限在于规范体积接近实现本身、依赖专家知识难以推广，以及覆盖范围不含设备隔离和侧信道。适合用于：并发低层系统代码（hypervisor、OS 内核）希望超越传统测试但又不愿承担全验证成本的场景。
