# Pie: A Programmable Serving System for Emerging LLM Applications

**作者**：In Gim, Zhiyao Ma, Seung-Seob Lee, Lin Zhong（耶鲁大学）
**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles）
**DOI**：https://doi.org/10.1145/3731569.3764814
**源文件**：[3731569.3764814.pdf](../../papers/sosp-2025/3731569.3764814.pdf)

---

## 一、背景

LLM 应用已远超简单文本补全的范畴，逐渐演化为包含复杂推理策略（Tree-of-Thought、Graph-of-Thought、Recursion-of-Thought）和 agentic 工作流（ReACT、CodeACT、multi-agent Swarm）的系统。这些新型应用需要：精细的 KV cache 控制、可定制的 token 生成过程、以及与外部工具/代码/API 的紧密集成。

然而现有 LLM serving 系统（vLLM、TGI、SGLang）均建立在**单体式（monolithic）prefill-decode 循环**之上：系统对所有请求统一施加全局 KV cache 策略，生成过程封闭不可干预，外部交互需要绕回客户端处理。这一架构对于现代 AI 应用已显得过于僵化。

---

## 二、要解决的问题

作者归纳出三个核心限制（R1-R3）：

**R1：KV cache 缺乏应用级控制。** 现有系统用全局启发式策略（如 LRU 驱逐、prefix caching）管理 KV cache，无法按请求粒度做 allocation/eviction/reuse 决策。Graph-of-Thought 等技术需要在运行时根据推理树结构动态决定哪些 KV cache 块保留或复用，全局策略无法胜任。

**R2：生成过程不可定制。** speculative decoding、parallel decoding、MCTS 等技术要求偏离标准的单 token/步解码流程，但现有系统将其作为全局开关实现，无法按请求粒度启用或混合使用。

**R3：工作流与推理割裂。** Agentic 工作流每次工具调用都需将控制权交还客户端，再以新请求重新提交更新后的上下文，既产生网络往返延迟，又因服务端无状态而丢失 KV cache，迫使重新 prefill。

---

## 三、核心设计

Pie 的核心思路是：**将应用控制逻辑从推理引擎解耦出来**，通过两个架构转变实现可编程性：

1. **分解单体生成循环**：将 prefill-decode 流程拆解为独立的细粒度 handler——embed（输入嵌入）、forward（Transformer 前向计算）、sample（token 采样）——通过 API 对外暴露。

2. **Inferlet 编程模型**：用户提供名为 inferlet 的程序，通过调用上述 API 自由编排生成流程。Inferlet 可以：
   - 显式管理 KV cache（alloc/dealloc/import/export KvPage）
   - 编排自定义生成序列（满足 R2）
   - 在生成流中直接执行任意计算和 I/O（满足 R3）

Inferlet 采用 **WebAssembly（Wasm）** 执行，兼顾轻量沙箱隔离、低启动延迟和跨语言支持（C++、Rust、Python 等均可编译到 Wasm）。

**三层架构**：
- **Application layer**：执行 inferlet，通过 API 调用与系统交互
- **Control layer**：事件分发、批次调度器（adaptive batching）、资源虚拟化（KvPage 虚地址映射到物理地址）
- **Inference layer**：API handler，将批量 API 调用转为 GPU kernel 调用（基于 PyTorch + FlashInfer）

## 四、实现细节

**API 设计（共 42 个 API）**：
- 18 个核心 API 用于 LLM 前向计算和资源管理（embed/forward/sample 三类）
- 24 个 API 用于运行时管理、inferlet 间通信、I/O 操作
- API 通过 Trait 组织（类似 Rust trait），支持模型能力的扩展和版本兼容

**关键抽象**：
- `Embed`：token 嵌入序列，按 token 粒度分配，支持单 token 操作
- `KvPage`：连续 KV cache 块（遵循 PagedAttention），每块 8-32 个 token；inferlet 持有虚拟指针，控制层负责物理映射
- `CommandQueue`：batch scheduler 通过 queue 感知 API 调用间的依赖关系，据此决策最优 batching

**批量调度策略**：混合 K-only（按队列长度）和 T-only（按等待时间）的 adaptive 策略，GPU 空闲时立即触发 batch 形成。

**支持库**：用 Rust 编写，提供 async/await 运行时、高层抽象（如 `Context` 自动管理 KvPage 生命周期）、采样方法（top-k、temperature）等，减少 inferlet 开发的模板代码。

**规模**：支持库约 728 行代码；典型 inferlet（如 Tree-of-Thought）约 100-200 行代码，编译后 Wasm 二进制约 130-175 KB。

## 五、实验结果

**实验环境**：GCP g2-standard-32 实例，NVIDIA L4 GPU（24GB），Llama 3 系列模型（1B/3B/8B），BF16 精度。与 vLLM v0.6.0、SGLang v0.4.4、LMQL v0.7.3、StreamingLLM 对比，均使用 FlashInfer GPU 后端保证公平。

**Agentic 工作流（ReACT/CodeACT/Swarm）**：

| 工作流 | 延迟（Pie vs 基线） | 吞吐提升 |
|--------|---------------------|---------|
| ReACT（8次外部 I/O） | 降低 15% | 提升 30% |
| CodeACT（8次代码执行） | 有所降低 | 有所提升 |
| Swarm（32次 agent 通信） | 有所降低 | 有所提升 |

**多层优化叠加（agentic 工作流）**：通过 KV cache 保留（#1）+ 并发 API 调用（#2）+ KV cache 掩码（#3）三级优化叠加，吞吐相比 vLLM baseline 提升 **3.5×**。

**标准任务（文本补全等）**：
| 模型规模 | Pie TPOT | vLLM TPOT | 开销 |
|----------|----------|-----------|------|
| 8B | 65.59ms | 64.06ms | 2.39% |
| 3B | 32.01ms | 30.30ms | 5.64% |
| 1B | 18.75ms | 16.83ms | 11.41% |

**高级推理策略（ToT/RoT/GoT/SKoT）**：Pie 延迟降低最高 28%，吞吐提升最高 34%。

**批量调度策略对比（128 个并发 inferlet）**：

| 策略 | Requests/s |
|------|-----------|
| Eager（无 batching） | 5.61 |
| K-only | 30.09 |
| T-only | 78.11 |
| Adaptive | **84.85** |

**Inferlet 启动延迟**（最高 896 并发）：warm start 10-50ms，cold start 35-81ms，相对于每 token 生成延迟（10-60ms）可忽略不计。

## 六、批判性分析

**实验规模局限**：全部评估均在单张 NVIDIA L4（24GB）GPU 上进行，只用了 Llama 3 1B/3B/8B 这类中小模型。论文完全回避了多 GPU / 多节点部署场景，而这正是作者在 Discussion 章节承认的重大未解问题（分布式调度、KvPage locality、SLO 保障）。实际生产部署通常是 70B/405B 级模型 + 多节点，结论的可迁移性存疑。

**Agentic 工作流对比不公平**：baseline 是"Python 脚本调用 vLLM/SGLang API Server"，而非这些系统的原生优化实现。对于 agentic 场景，vLLM 和 SGLang 并非没有 KV cache 跨轮保留的解决思路（如 prompt caching、prefix caching），但论文没有尝试在 baseline 中应用这些优化。15-30% 的提升数字可能高估了系统设计本身的贡献。

**3.5× 吞吐提升的"人工"成分**：这个数字来自一个具有非常特定特征的 agentic 工作流（有高频 API、fire-and-forget API、单次调用 API 各一类），三层优化恰好完美匹配。作者承认对于外部交互次数少于 2 次的工作流，与 baseline 无性能差异。这类基准设计有 cherry-pick 之嫌。

**性能开销被低估**：主要开销来自推理层 API 调用的 Python 单线程反序列化（100-300 μs/call，大量并发时显著），作者承认 C++/Rust 原生实现可改善，但仍未完成完整评估。论文只提供了 Python+PyTorch 版本的性能数据。

**安全性问题轻描淡写**：Inferlet 可访问 token 分布（logits）、可发起网络请求，在多租户场景下存在侧信道泄漏和 DoS 风险。论文仅一段话承认这是"超出范围的问题"，但在 multi-tenant LLM serving 场景下，这实际上是一个阻碍商业化的核心阻碍，不应被轻易略过。

**Wasm 的局限性未充分讨论**：论文对比 Wasm vs 容器 vs 原生进程时一笔带过，但 Wasm 目前对 SIMD、多线程等特性的支持仍不完整，且对 Python 编写的 inferlet（需经 wasmtime 解释）性能影响未量化。

## 七、AI Infra / MLSys 视角

**核心 insight 的可迁移性**：Pie 的"inferlet 作为 first-class 服务单元"思路，与 exokernel 的哲学一脉相承——系统提供安全的低层抽象，将策略决策完全交给应用。这对 AI Infra 研究有重要启发：KV cache 管理本质上是一个需要全局视角（系统）+ 局部知识（应用）协同的问题，Pie 给出了一种解耦方式。

**对 speculative decoding / MCTS 推理的意义**：Pie 的设计使得 per-request 开启 speculative decoding、或基于推理树动态调整 beam width 成为可能，而不需要修改服务系统内核。这对 MCTS 驱动的 test-time compute scaling（类 o1 的推理）有直接价值。

**值得跟进的研究方向**：
1. **分布式 Inferlet 调度**：当前控制层是单节点瓶颈，如何设计跨节点的 KvPage placement/migration 策略，同时保持 inferlet 编程模型的简洁性，是直接可做的系统研究。
2. **Inferlet 感知的 SLO 保障**：不同 inferlet 的 KV cache 需求差异极大（agentic vs. 批量推理），如何在满足 per-inferlet SLO 的同时优化整体 GPU 利用率？
3. **大模型适配**：评估 70B+ 参数模型 + 张量并行场景下，细粒度 API 调用的跨 GPU 通信开销是否会成为新瓶颈。
4. **Inferlet 安全隔离**：在 token distribution 访问和网络 I/O 方面设计 capability-based 安全模型，这本身是一个有价值的系统安全研究课题。

---

## 八、总结

Pie 将 LLM serving 中长期耦合的"推理执行"与"应用控制逻辑"拆分，通过将单体生成循环分解为细粒度 API、并以 Wasm inferlet 委托控制权，使得应用可以在不修改 serving 系统的情况下实现定制 KV cache 管理、自定义解码策略和紧耦合 I/O 集成。在 agentic 工作流场景下性能显著优于 vLLM/SGLang，标准任务开销 2-12%。主要局限在于：评估规模局限（单卡小模型）、分布式支持缺失、安全模型不成熟，以及 Python 推理层的性能天花板。
