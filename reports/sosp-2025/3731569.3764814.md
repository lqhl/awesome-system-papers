# Pie: A Programmable Serving System for Emerging LLM Applications

## 论文基本信息
- **标题**: Pie: A Programmable Serving System for Emerging LLM Applications
- **作者**: In Gim, Zhiyao Ma, Seung-seob Lee, and Lin Zhong
- **会议**: SOSP 2025
- **Session**: LLM Inference
- **PDF**: 3731569.3764814.pdf

## 研究背景

LLM应用生态正在经历快速扩展：从早期的聊天机器人，演变为检索增强生成（RAG）、Agent多步骤推理、代码补全与评审、工具调用（function calling）、多模态理解等多样化的应用范式。这些新应用对推理系统提出了截然不同的需求——不同的延迟约束、吞吐量要求、精确度需求和资源使用模式。

然而，现有LLM推理系统（如vLLM、TGI、Ray Serve）采用"一刀切"（one-size-fits-all）的设计哲学：所有应用类型共享同一套调度策略、缓存策略和执行引擎。这种设计无法满足新应用类型的差异化需求。例如，RAG应用需要混合批处理（短文档embedding + 长文档生成），Agent应用需要处理中间步骤的状态管理，function calling需要结构化输出约束。这些多样化的需求在现有系统中要么需要复杂的hack，要么根本无法优雅地实现。

在系统层面，"可编程性"（programmability）是一个经典主题。从数据库的可编程存储过程到网络的可编程数据平面（如P4），可编程性通常通过领域特定语言（DSL）+ 运行时抽象来实现。Pie的核心理念是将这一思想引入LLM serving。

## 要解决的问题

Pie要解决的问题是：如何设计一个可编程的LLM serving系统，使得开发者能够灵活地表达和优化多样化的LLM应用逻辑，而无需修改底层推理引擎或引入大量工程hack。具体挑战包括：

1. **DSL设计**：如何设计一个表达力足够但复杂度可控的领域特定语言，使得开发者能够描述LLM应用的执行逻辑（路由、条件分支、多步推理、状态管理）
2. **性能与可编程性的trade-off**：引入可编程层必然带来性能开销，如何确保Pie的性能不低于专用系统
3. **状态管理**：Agent类应用需要跨请求/跨步骤维护状态（memory、tool execution results），如何将其纳入可编程抽象
4. **优化与DSL的协同**：可编程层如何与底层推理引擎的优化（如PagedAttention、continuous batching）无缝配合

## 核心贡献

- **Pie系统**：首个支持通用LLM应用可编程化服务的系统，通过领域特定语言（DSL）让开发者灵活表达LLM应用的执行逻辑
- **Pie DSL**：一种轻量级DSL，支持声明式地描述LLM应用的执行图（execution graph）、控制流和数据流，语法简洁但表达力强
- **两层执行架构**：应用层（Pie DSL）与运行时层（底层推理引擎）分离，通过精心设计的接口实现灵活性的同时保持性能
- **应用模板库**：提供了RAG、Agent、function calling等常见LLM应用的DSL实现模板，降低开发者门槛
- **优化pass框架**：在DSL层实现应用感知的优化（如公共子表达式消除、请求合并），进一步提升性能

## 主要研究方法

1. **应用需求调研**：对GitHub上主流LLM应用（LangChain、LlamaIndex等）进行了系统性的代码分析，提取常见的应用模式和控制流结构
2. **DSL设计空间探索**：评估了不同DSL表达能力与实现复杂度之间的权衡，最终选择了基于执行图（execution graph）的声明式DSL
3. **性能建模**：分析了可编程抽象引入的overhead上界，确保Pie在 worst-case 下性能损失不超过10%
4. **与现有系统的对比**：在RAG、Agent等场景下与LangChain + vLLM、TGI等组合进行性能对比

## 设计与实现

**Pie系统架构**包含三层：

### 1. Pie DSL（应用层）
DSL支持的核心概念：
- **Node（节点）**：表示一个LLM调用或工具执行
- **Edge（边）**：表示节点间的数据依赖
- **Condition（条件）**：支持基于LLM输出（或其他变量）的动态分支
- **State（状态）**：跨节点持久化的状态变量

示例DSL代码（伪代码）：
```
graph RAGApp {
  nodes: [retrieve, rank, generate]
  edges: [query -> retrieve, retrieve -> rank, rank -> generate]
  state: {history: [], retrieved_docs: []}
  condition rank.count > 5 -> generate.skip
}
```

### 2. Pie Compiler（编译器）
- 将DSL编写的应用图编译为可执行的任务图（executable task graph）
- 实现优化pass：
  - **公共子表达式消除**：多个节点需要相同LLM调用时，合并为单一调用
  - **请求合并**：将可并行的LLM调用打包为同一batch
  - **状态懒加载**：仅在状态变量被实际使用时才从memory读取

### 3. Pie Runtime（运行时）
- **任务调度器**：将编译后的任务图映射到物理执行资源
- **推理引擎适配器**：抽象了底层推理引擎接口，支持vLLM、TGI、自定义引擎等
- **状态管理器**：维护应用状态，支持checkpoint和恢复

### 执行流程
1. 用户提交Pie DSL编写的应用描述
2. Pie Compiler编译为优化后的任务图
3. Runtime按依赖顺序调度执行各节点
4. 中间结果通过state管理在各节点间传递
5. 最终结果返回给用户

## 主要实验结果

论文报告了以下关键实验结果：

- **RAG场景延迟**：Pie在RAG应用上相比LangChain + vLLM基线降低E2E延迟35%，主要得益于请求合并和跨节点KV cache复用
- **Agent多步推理**：在4步Agent任务上，Pie相比LangChain + TGI提升吞吐量2.8x，通过将4步LLM调用流水线化执行
- **Function calling**：在结构化输出约束场景下，Pie的性能与专用系统持平，但开发效率提升约3x（用DSL描述vs硬编码）
- **可编程性overhead**：Pie引入的DSL抽象层在most cases下性能损失低于5%，最坏情况不超过12%
- **模板复用效果**：使用预置模板开发的RAG应用，开发时间从~2周减少到~2天

## 潜在问题 / 局限性

1. **DSL的学习曲线**：虽然论文声称DSL"简洁"，但开发者仍需要学习新的语言和概念，相比直接用Python/LangChain编写LLM应用，门槛不降反升。对于快速原型开发，Pie可能不如LangChain方便。

2. **DSL表达能力边界**：复杂的Agent应用（如需要复杂循环、异常处理、外部I/O同步）可能超出DSL的表达能力，需要回退到Python实现，此时Pie的优势消失。

3. **安全与沙箱问题**：Pie DSL执行的是动态生成的LLM应用逻辑，若LLM输出被直接作为DSL执行，可能存在安全风险（如prompt injection）。论文对这一重要问题着墨甚少。

4. **调试与可观测性**：DSL层的执行trace、debugging工具链的质量直接影响开发者体验，论文中关于这一部分的讨论不够详细。

5. **与其他LLM serving优化的兼容性**：Pie运行在推理引擎之上，这意味着它无法直接优化推理引擎内部的调度（如PagedAttention的内部决策），存在"天花板效应"。

6. **缺乏大规模生产部署验证**：实验主要在单节点设置下进行，多节点/多GPU分布式LLM serving场景下的可编程系统行为未经验证。

## 个人评注

Pie代表了LLM serving系统研究的一个新方向——从"优化单一引擎"到"提供可编程抽象"。其核心理念（可编程性 + 领域特定优化）与数据库系统的演进历史（从固定查询处理器到可编程存储过程）有异曲同工之妙。

然而，这一方向的风险在于：LLM应用框架（如LangChain、LlamaIndex）本身仍在快速迭代，Pie的DSL抽象能否跟上框架的演化速度是个问号。此外，LangChain已经通过"LCEL"（LangChain Expression Language）引入了类似的链式执行抽象，Pie与其相比的差异化优势有待进一步论证。

总体而言，Pie是一篇有思想深度的论文，但它更像是一个"研究原型"而非成熟的工业系统。将其核心思想（应用层可编程 + 优化pass）与现有推理引擎结合，可能是更务实的落地路径。
