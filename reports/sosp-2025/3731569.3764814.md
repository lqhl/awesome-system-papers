# Pie: A Programmable Serving System for Emerging LLM Applications

**作者**：In Gim, Zhiyao Ma, Seung-seob Lee, Lin Zhong（Yale University）
**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles）
**链接**：https://doi.org/10.1145/3731569.3764814
**源文件**：[3731569.3764814.pdf](../../papers/sosp-2025/3731569.3764814.pdf)

---

## 一、背景

LLM 的使用已经远远超越了简单的文本补全。现代 LLM 应用涉及 token 级别到 workflow 级别的复杂策略（Tree-of-Thought、Graph-of-Thought、agentic workflows），需要与外部工具交互（代码执行、API 调用、符号求解器），并需要处理实时用户事件（音频、视觉）。当前主流 LLM serving 系统（vLLM、SGLang、TGI）都建立在一个**单体的 prefill-decode 循环**之上，以 prompt 为基本服务单元，采用全局策略管理 KV cache，且将推理与外部操作隔离。

---

## 二、要解决的问题

现有 serving 系统在三个方面存在根本性不足：

1. **KV cache 管理隐式且不可控（R1）**：系统采用全局 LRU 驱逐或 prefix caching 等隐式策略，无法满足 Tree-of-Thought、Graph-of-Thought 等需要显式、细粒度控制 KV cache 分配/驱逐/复用的高级推理策略。例如，vLLM 曾因 beam search 的 KV cache 管理复杂度过高而考虑移除该功能。

2. **解码过程僵化不可定制（R2）**：单体循环假设每步生成一个 token，难以支持 speculative decoding、parallel decoding、MCTS-based generation、grammar-constrained decoding 等新型解码方法。这些方法只能作为系统级开关，无法按请求灵活配置。

3. **工作流集成差（R3）**：系统假设"闭环"生成过程，agentic workflow 中的外部工具调用需要返回控制权给客户端，引入网络往返延迟，且 KV cache 在请求间被丢弃，导致昂贵的重新 prefill。

---

## 三、洞察与设计

**关键洞察**：应用特定的控制逻辑可以被高效地从核心推理引擎中解耦出来并在引擎外部执行，前提是提供正确的细粒度接口。现有系统的问题根源在于应用控制逻辑与核心执行引擎在固定架构模式中的紧耦合。

基于这一洞察，Pie 做了两个根本性的架构转变：

**1. 拆解单体循环为细粒度处理器（Handlers）**：将传统的 prefill-decode 循环分解为独立的阶段——embed、forward、sample，每个阶段暴露为可调用的 API。

**2. 将端到端控制委托给用户程序（Inferlets）**：用户编写的 inferlet 程序通过 API 调用编排这些 handlers，实现自定义的 KV cache 策略、生成逻辑和 I/O 集成。

**核心抽象**：
- **Embed**：表示 token embedding 序列，按 token 粒度分配
- **KvPage**：表示 KV cache 的连续块（8-32 tokens），遵循 PagedAttention 设计
- **Command Queue**：抽象 API 调用的逻辑序列，为 batch scheduler 提供依赖关系和优先级信息

**三层架构**：
- **Application Layer**：使用 WebAssembly 运行时执行和隔离 inferlets
- **Control Layer**：管理全局资源池、虚拟地址映射，批量调度 GPU API 调用
- **Inference Layer**：执行底层 GPU 计算，包含各类 API handler

## 四、实现细节

- **代码规模**：13,650 行代码（cloc），其中核心系统和 support library 为 11,640 行 Rust，GPU 侧 API handler 为 Python
- **Wasm 运行时**：使用 wasmtime，支持 WASI 提供网络 I/O 等系统接口，通过 pooled allocation 预分配虚拟内存支持最多 1,000 个并发实例
- **API 体系**：共 42 个 API，18 个用于 LLM 前向传播和资源管理，24 个用于运行时管理、inter-inferlet 通信和 I/O
- **Trait 系统**：类似 Rust 的 trait 机制组织 API（Forward、InputText、InputImage、Tokenize、OutputText 等），支持模型能力的扩展
- **Batch Scheduler**：实现 work-conserving 策略，支持垂直批处理（同一 queue 内相同类型的连续命令）和水平批处理（不同 queue 间相同类型的命令）
- **GPU 后端**：使用 PyTorch + FlashInfer GPU kernel library，通过 ZeroMQ IPC 与 control layer 通信。另提供 C++/CUDA 原生实现（端到端延迟降低 10-30%）
- **Support Library**（728 行 Rust）：提供 Context 抽象、采样方法、停止条件、fork-join 并行等高级封装
- **已实现的 inferlet**：涵盖 text completion、ToT、RoT、GoT、SKoT、prefix caching、modular caching、EBNF decoding、beam search、watermarking、speculative decoding、Jacobi decoding、attention sink、windowed attention、ReACT/CodeACT/SWARM agent 等（详见 Table 2）

## 五、实验结果

**实验设置**：GCP G2 实例（g2-standard-32），NVIDIA L4 GPU（24GB），Llama 3 模型（1B/3B/8B），BF16 精度。Pie、vLLM、SGLang 均使用 FlashInfer GPU 后端以确保公平比较。

### Agentic Workflows（1B 模型）

| 工作流 | Pie 延迟 | vs vLLM 延迟降低 | vs vLLM 吞吐提升 |
|--------|---------|-----------------|-----------------|
| ReACT（8次 I/O） | 4.27s | ~15% | ~30% |
| CodeACT（8次 I/O） | 3.18s | 显著 | 显著 |
| Swarm（32次 I/O） | 6.14s | 显著 | 显著 |

### Deliberate Prompting 策略

延迟降低最高 28%，吞吐提升最高 34%（vs SGLang/vLLM）。ToT、RoT、GoT、SKoT 全面优于 baseline。

### 应用级优化叠加效果

在 agentic workflow 上叠加三层优化（KV cache 复用 + 并发 API 调用 + KV cache 清理），最终实现 **3.5× 吞吐提升**（vs vLLM baseline）。

### 标准任务性能

| 模型大小 | vLLM TPOT | Pie TPOT | 开销 |
|---------|-----------|----------|------|
| 8B | 64.06ms | 65.59ms | 2.39% |
| 3B | 30.30ms | 32.01ms | 5.64% |
| 1B | 16.83ms | 18.75ms | 11.41% |

### 系统开销

- Inferlet 启动延迟：冷启动 35-81ms，热启动 10-50ms（对比每 token 生成 10-60ms，可忽略）
- API 调用开销：control layer 处理 <30μs，inference layer 处理 10-300μs
- 主要开销来源：缺乏 pipelined sampling（+1.32ms/token），是编程模型的"机会成本"

### Batching 策略对比

| 策略 | 吞吐（requests/s） |
|------|-------------------|
| Eager（无 batching） | 5.61 |
| K-only（固定大小） | 30.09 |
| T-only（超时） | 78.11 |
| Adaptive（work-conserving） | **84.85** |

## 六、批判性分析

1. **实验硬件规模过小**：仅使用单块 NVIDIA L4（24GB）进行评估，这是一款中低端推理 GPU。论文在 Discussion 中承认 control layer 的可扩展性是开放问题（多 GPU 节点的负载均衡、KvPage locality、SLO 保障），但未提供任何多卡/多节点实验数据。对于一个声称面向"下一代 LLM serving"的系统，缺乏大规模部署验证是显著不足。

2. **模型规模有限**：最大仅测试 8B 模型，而实际生产中 70B+ 模型才是主流。虽然论文论证了模型越大开销占比越小，但未验证在 tensor parallelism 等分布式推理场景下 Pie 架构是否仍然成立。

3. **baseline 比较的公平性值得商榷**：在 agentic workflow 对比中，baseline 使用"best-effort optimizations"的 Python 脚本与 vLLM/SGLang API 交互，但未使用 SGLang 的 fork/join 等已有的程序化抽象来优化 deliberate prompting 策略。这可能低估了现有系统的实际能力。

4. **编程复杂度被轻描淡写**：论文承认 API 优先考虑细粒度可编程性而非简易性，但表中很多 inferlet 仅 40-100 行代码可能具有误导性——这些是 Rust 代码，需要理解 Wasm 编程模型、异步 API、资源的手动分配/释放。实际开发门槛远高于使用 vLLM/SGLang 的 Python API。

5. **资源竞争处理过于简单**：当 KvPage 资源不足时，直接终止最近创建的 inferlet（FCFS 策略）。这在多租户场景下显然不可接受，论文将更复杂的策略留作 future work。

6. **安全模型不完整**：将推理控制权交给用户程序并允许网络 I/O 显著扩大了攻击面（侧信道泄露、DoS、模型提取等），论文仅在 Discussion 中简单提及，未提出具体的安全机制。

## 七、AI Infra / MLSys 视角

**启发与借鉴价值**：

- **"服务程序而非 prompt"的范式**值得 AI Infra 领域深思。随着 LLM 应用从简单文本补全演化为复杂的 agentic workflow，将 serving 系统的基本服务单元从 prompt 提升为程序是一个自然且有前景的方向。这与 SGLang 的发展方向一致，但 Pie 走得更远。

- **细粒度 KV cache 控制 API** 对于实现 context caching、prefix sharing、attention pattern 定制等优化至关重要。vLLM/SGLang 目前通过系统内部机制实现这些功能，但 Pie 证明了将控制权暴露给应用层可以解锁更多优化空间（如 3.5× 的吞吐提升）。

**可迁移的技术与 insight**：

- Command Queue 抽象提供了一种优雅的方式来表达 API 调用间的依赖关系和优先级，这对于任何需要 batching 异构请求的 serving 系统都有参考价值。
- Trait 系统实现 API 可扩展性的方法，可用于设计支持多模态、多架构的统一 serving 接口。

**值得跟进的 future work**：

1. **分布式 Pie**：如何将 inferlet 编程模型扩展到多 GPU/多节点，特别是 KvPage 的跨节点迁移和分布式 batch scheduling。
2. **Pie + 大模型（70B+）的 tensor/pipeline parallelism 集成**：验证细粒度 API 在分布式推理中的可行性和性能。
3. **将 Pie 的可编程性理念融入现有系统**：论文指出 retrofitting 等同于重建 Pie 架构，但渐进式的、粗粒度的可编程性层是否可行？这是更务实的研究方向。
4. **智能资源管理**：基于 inferlet 的执行模式预测进行 KV cache 预分配和调度优化。

---

## 八、总结

Pie 提出了 LLM serving 的可编程范式，通过将单体生成循环拆解为细粒度 API handlers 并将控制权委托给用户程序（inferlets），实现了对 KV cache、解码过程和 I/O 的端到端编程控制。其在标准任务上仅引入 3-12% 的延迟开销，在 agentic workflows 和高级推理策略上则显著优于 vLLM/SGLang（延迟降低 1.1×-2.4×，吞吐提升 1.3×-3.4×）。主要局限在于仅在单 GPU/小模型上验证、编程门槛较高、资源管理和安全机制不完善。Pie 的核心贡献在于证明了将推理控制权交还给应用层可以解锁显著的性能优化空间，为下一代 LLM serving 系统指出了可编程性的发展方向。
