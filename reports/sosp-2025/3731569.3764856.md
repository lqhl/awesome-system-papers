# TickTock: Verified Isolation in a Production Embedded OS

## 一、背景

Tock 是一个面向微控制器的嵌入式操作系统，已被部署在 Google Security Chip (GSC)、Microsoft Pluton 2 等安全关键系统中，作为硬件安全模块和可信平台模块的基础。与传统操作系统类似，Tock 的安全保证根植于隔离性：内核空间与用户空间分离，多个不受信任的应用程序在相互隔离的环境中运行。

Tock 采用 Rust 编写内核，利用 Rust 的类型系统和内存安全性在内核组件之间提供语言级隔离。但用户应用程序可以用任意语言编写（包括 C/C++），且目标硬件（资源受限的微控制器）缺乏 MMU，无法使用虚拟内存进行隔离。因此，Tock 依赖 Memory Protection Unit (MPU) 来确保每个用户进程只能访问自己的内存区域。

---

## 二、要解决的问题

1. **MPU 配置复杂且易错**：MPU 硬件对区域大小和对齐有严格约束（如 ARM Cortex-M 要求区域大小为 2 的幂，起始地址按区域大小对齐），内核必须在这些约束下正确配置 MPU 以实施进程隔离。Tock 的原始设计将进程内存布局逻辑与硬件约束纠缠在一起，导致代码复杂且容易引入安全 bug。

2. **中断和上下文切换的正确性**：中断处理程序和上下文切换代码用内联汇编编写，必须确保 MPU 配置正确、CPU 执行模式正确切换。微小的遗漏（如忘记将 CPU 切换到非特权模式）就会完全破坏隔离保护。

3. **内核视图与硬件实际配置不一致**：Tock 的 monolithic MPU 抽象在分配内存后丢弃了中间结果，导致内核认为的进程内存布局与 MPU 硬件实际执行的布局之间存在分歧（disagreement），进而引入重复计算和潜在 bug。

4. **已有多个静默破坏隔离的 bug**：验证过程中发现了多个此前未知的 bug，包括 MPU 配置逻辑错误（允许进程访问内核 grant 内存）、中断汇编遗漏模式切换、整数溢出导致的内核崩溃等。

---

## 三、洞察与设计

**关键洞察**：Tock 原始的 monolithic MPU 抽象将内核的进程内存管理需求与底层 MPU 硬件约束纠缠在一起，这种纠缠既是代码复杂性的根源，也是隔离 bug 的根源。如果将两者解耦——用一个细粒度的抽象分别处理"硬件区域的创建与配置"和"进程内存的逻辑布局"——就能同时消除纠缠（entanglement）和分歧（disagreement），使代码更简单、更易验证、更高效。

基于这一洞察，作者设计了 TickTock，一个 Tock 内核的重新设计 fork，核心架构包括三层：

1. **Granular MPU 抽象**：将 MPU 接口拆分为 `RegionDescriptor`（抽象单个硬件区域的属性，如起始地址、大小、权限）和 `MPU` trait（提供创建、更新、配置区域的方法）。内核的进程分配器只与抽象的 Region 交互，不需要了解 subregion、对齐等硬件细节。

2. **Flux 形式化验证**：使用 Flux（基于 SMT 的 Rust refinement type checker）在编译时验证隔离性。验证分四层：(a) 为 MPU 接口的方法添加 pre/post-condition 合约；(b) 验证内核逻辑视图（AppBreaks 数据结构的不变量）符合 Tock 内存模型；(c) 验证逻辑视图与 MPU 硬件配置一致；(d) 验证各架构的 MPU 驱动正确实现合约。

3. **FluxArm**：为 ARMv7-M 汇编开发的可执行形式化语义，将 ARM 的 ASL 规范 lift 到 Rust 并用 Flux 合约定义语义，从而验证中断处理和上下文切换代码保持隔离不变量。

## 四、实现细节

- **代码规模**：TickTock 共 22,131 行 Rust 代码，3,603 行 Flux 注解（约 16% 的注解/代码比），覆盖 2,581 个函数。
- **Trusted Computing Base**：125 个函数标记为 `#[trusted]`（Flux 不验证其实现与合约的一致性），其中 14 个因 SMT solver 限制（相关引理在 Lean 中交互式证明），14 个因 Flux 工具问题，17 个为 proof-specific ghost state 代码。
- **Associated Refinements**：利用 Flux 的 associated refinement 机制，在 trait 层面定义抽象的 `start`、`size`、`is_set`、`overlaps`、`can_access` 等 refinement，各硬件驱动提供具体实现。`can_access` 标记为 `#[final]`，由其他 refinement 组合定义。
- **硬件语义编码**：ARM Cortex-M 的 MPU region 由 `rbar`（base address register）和 `rasr`（region attributes register）两个 32-bit 寄存器表示，refinement 直接对寄存器位进行建模（如 `start` = `rbar & 0xFFFF_FFE0`）。
- **Lean 辅助证明**：对于 SMT solver 无法处理的位运算事实（如"足够大的 2 的幂对齐到 8 字节"），编码为 trusted lemma 并在 Lean 4 中用归纳法证明。
- **支持架构**：ARMv7-M（所有 Cortex-M 平台）和 RISC-V 32-bit（3 个平台）。
- **发现的 bug**：共 6 个破坏隔离的 bug + 1 个 DoS bug，均已向 Tock 上游报告。

## 五、实验结果

**平台**：Nordic NRF52840dk（ARM Cortex-M）+ QEMU（RISC-V）

**功能正确性**：在 21 个 Tock 上游测试应用上进行差分测试，TickTock 与 Tock 行为一致（5 个预期差异来自内存布局或传感器数据）。

**性能对比**（CPU cycles，ARM Cortex-M）：

| 操作 | TickTock | Tock | 差异 |
|------|----------|------|------|
| allocate_grant | 641 | 1,290 | **-50.3%** |
| brk | 845 | 1,079 | -21.7% |
| build_readonly_buffer | 116 | 145 | -20.0% |
| build_readwrite_buffer | 78 | 118 | -34.0% |
| create | 638,545 | 634,137 | +0.7% |
| setup_mpu | 98 | 91 | +8.1% |

**上下文切换**：TickTock 32,740 cycles vs Tock 32,640 cycles，仅 0.3% 开销。

**内存使用**：TickTock 分配 7,780 字节（5.60% 未使用），Tock 分配 8,192 字节（3.08% 未使用），差异主要来自初始 padding 策略不同。

**验证时间**：

| 组件 | 函数数 | 总时间 | 最大单函数 | 平均 | 标准差 |
|------|--------|--------|-----------|------|--------|
| Kernel (Monolithic) | 660 | 5m19s | 4m57s | 0.48s | 11.36s |
| Kernel (Granular) | 791 | **36s** | 8s | 0.05s | 0.39s |
| Interrupts | 95 | 2m34s | 2m3s | 1.63s | 12.82s |

Granular 重设计将内核验证时间从 5 分 19 秒降至 36 秒。整个项目验证约 3 分钟，可集成到 CI 流水线。

## 六、批判性分析

1. **验证范围有限**：TickTock 只验证了进程隔离（进程不能访问内核或其他进程的内存），但没有验证内核的功能正确性（如调度、IPC、syscall 语义等）。论文标题 "Verified Isolation" 是准确的，但读者容易高估其保证范围——例如，内核中非 MPU 相关的 unsafe 代码仍可能引入安全问题。

2. **TCB 较大且分散**：125 个 trusted 函数、67 个 FluxArm lifting 函数、138 行硬件规范、Flux 工具本身、Rust 编译器——这些都在 TCB 内。特别是 69 个 Flux-Std 函数中有 65 个是 trusted 的，这部分的可信度完全依赖于手工审查。论文对此讨论较少。

3. **RISC-V 验证未在真实硬件上评估**：所有性能基准测试仅在 ARM 上进行，RISC-V 仅在 QEMU 上做了功能测试。考虑到 RISC-V 的 PMP 与 ARM MPU 机制差异较大，RISC-V 平台的实际性能影响未知。

4. **验证的可持续性**：论文声称 TickTock 是 Tock 的 fork，但没有讨论如何与上游 Tock 保持同步。随着 Tock 持续演进，维护一个 verified fork 的工程成本可能很高。如果验证注解与代码紧耦合，每次上游变更都需要重新验证。

5. **微基准测试的代表性**：`allocate_grant` 的 50% 加速主要来自消除了 monolithic 抽象中的重复计算，这是设计改进而非验证带来的收益。论文在呈现时将验证和设计改进的效果混在一起，读者可能误以为验证本身带来了性能提升。

6. **FluxArm 的完整性**：FluxArm 只建模了 Tock 使用的 ARMv7-M 指令子集，而非完整的 ISA。如果未来 Tock 使用了新指令，需要扩展 FluxArm，这个过程本身的正确性依赖于人工将 ARM ASL 正确 lift 到 Rust。

---

## 七、总结

TickTock 通过重新设计 Tock 嵌入式 OS 的 MPU 抽象（从 monolithic 到 granular），并使用 Flux refinement type checker 进行形式化验证，首次在生产级嵌入式 OS 中实现了机器检查的进程隔离保证。验证过程发现了 Tock 中 6 个破坏隔离的已有 bug。TickTock 性能与 Tock 相当甚至更优，验证注解与代码的比例约 16%，整体验证时间约 3 分钟。主要局限在于验证仅覆盖进程隔离属性、TCB 仍较大、且作为 fork 与上游同步的长期可持续性存疑。
