# TickTock: Verified Isolation in a Production Embedded OS

**作者**：Vivien Rindisbacher, Evan Johnson, Nico Lehmann, Tyler Potyondy, Pat Pannuto, Stefan Savage, Deian Stefan, Ranjit Jhala（UCSD，Evan Johnson 在 NYU）
**会议**：SOSP '25（ACM SIGOPS 31st Symposium on Operating Systems Principles，2025 年 10 月）

**源文件**：[3731569.3764856.pdf](../../papers/sosp-2025/3731569.3764856.pdf)

## 一、背景

Tock 是一个用 Rust 编写的微控制器操作系统，被部署在安全关键系统中——包括 Google Security Chip（GSC，为 Google 的硬件安全模块提供动力）和 Microsoft Pluton 安全处理器（TPM 功能提供者）。Tock 的安全保证根植于进程隔离：内核与用户空间分离，多个不受信任的应用程序相互隔离。

与传统 OS（Linux）或安全微内核（seL4）不同，Tock 用 Rust 编写内核，以语言层面的类型安全和内存安全隔离内核组件（Capsules）。但 Tock 的用户进程可以用任意语言（包括 C/C++）编写，而且目标设备（低端微控制器）通常**没有 MMU**，无法依靠虚拟内存实现进程隔离，只能依赖**内存保护单元（MPU）**。

---

## 二、要解决的问题

**MPU 配置极其困难，历史上已出现多个静默修复的 isolation 漏洞。**具体挑战：

1. **硬件约束复杂**：ARMv7-M Cortex-M MPU 要求区域大小必须是 2 的幂次（最小 32 字节），起始地址必须对齐到区域大小；区域可以划分为 8 个等大小的子区域（subregion），可单独启用/禁用。

2. **内核逻辑与硬件约束耦合**：原始 Tock 的 monolithic MPU 抽象将进程内存布局逻辑和硬件约束纠缠在一起，导致代码复杂且容易出错。

3. **Kernel 视图与硬件执行存在不一致**：`allocate_app_mem_region` 在计算完进程和 grant 内存的边界后，将中间结果丢弃，只返回 start/size，使得调用方无法验证 MPU 的实际配置是否符合预期。

4. **中断与上下文切换的汇编代码难以验证**：Tock 内核是单线程事件驱动的，context switch 由 inline assembly 实现，稍有疏漏就会破坏隔离。

5. **已知存在多处 isolation 漏洞**：已有公开 CVE/PR 修复了 3 处漏洞，而作者通过形式化验证又发现了 7 处新漏洞。

## 三、核心设计

TickTock 是 Tock 的 fork，通过三项贡献消除 isolation 漏洞：

### 1. 粒度化 MPU 抽象（Granular MPU Abstraction）

将 monolithic MPU 接口拆分为两个解耦的抽象：

- **RegionDescriptor trait**：描述单个连续内存区域的逻辑属性（start、size、overlaps），抽象掉 subregion、alignment 等硬件细节。
- **MPU trait（新）**：只暴露 `new_regions`、`update_regions`、`configure_mpu` 三个方法，与进程内存布局无关，仅处理硬件约束。

进程分配器（process allocator）基于 RegionDescriptor 实现，**不关心底层硬件约束**，使同一套分配代码可复用于所有架构（ARMv7-M 和 RISC-V）。

**解决"纠缠"问题**：kernel 请求"至少 app_size 大小的最多两个连续区域"，MPU 抽象内部处理 power-of-two 约束，返回实际的 RegionDescriptor。Grant 内存自然放置在 process-accessible heap 末尾之后。

**解决"不一致"问题**：AppBreaks 结构体保存了精确的 MPU 硬件执行布局的指针，kernel 和 MPU 对进程内存布局的视图始终一致。

### 2. 形式化验证（使用 Flux）

Flux 是基于 SMT 的 Rust 精化类型检查器，支持不变量（invariants）、前置/后置条件（pre/post conditions）、精化类型（refinement types）。

验证分四层：
1. **MPU 接口的精化合约**：使用 associated refinements 为 new_regions/update_regions 写出精确的后置条件，描述返回的区域确实允许访问指定内存范围。
2. **Kernel 逻辑视图的正确性**：在 AppBreaks 数据结构上指定不变量（`app_break < kernel_break`，`memory_start <= app_break` 等），Flux 静态验证这些不变量在所有创建/更新路径上都成立。
3. **逻辑视图与 MPU 配置的对应**：在 AppMemoryAllocator 上指定不变量，确保 MPU regions 数组与 AppBreaks 中的逻辑布局一致（can_access_flash, can_access_ram, cannot_access_other）。
4. **架构特定 MPU 驱动的正确性**：为每个驱动（ARMv7-M Cortex-M、RISC-V PMP）的 MPU region 结构体写 associated refinement 实现（如 `start(r)` = `r.rbar & 0xFFFF_FFE0`），Flux 验证具体驱动代码正确设置了每一位。

### 3. FluxArm：中断与上下文切换的验证

将 ARM Architecture Specification Language（ASL）提升到 Rust，写出 ARMv7-M ISA 的可执行形式化语义，每条指令用 Flux 合约精确描述其对 CPU 状态的影响。

用 FluxArm 验证：
- 定时器中断处理程序（sys_tick_isr）执行后 CPU 处于特权模式
- context switch 的完整控制流：switch_to_user_part1 → process 执行 → preempt 中断 → switch_to_user_part2，验证进入用户态时 CPU 处于非特权模式，返回内核时处于特权模式，所有 callee-saved 寄存器正确恢复。

## 四、实现细节

- **代码规模**：22,131 行 Rust 源码 + 3,603 行 Flux 注解，覆盖 2,581 个函数。
- **可信计算基（TCB）**：125 个函数被标记为 `#[trusted]`（Flux 不验证其实现）：14 个因 SMT 求解器限制（但在 Lean 中交互式证明）、14 个因 Flux 工具 bug、17 个 proof-specific ghost 代码、6 个被认为 out of scope。
- **Lean 辅助证明**：部分涉及位运算和模运算的事实（如"充分大的 2 的幂次对 8 字节对齐"）SMT 求解器无法处理，改为在 Lean 4 中通过对自然数二进制结构的归纳证明，然后以 trusted lemma 方式引入 Flux。
- **架构支持**：ARMv7-M（所有 Tock 支持的平台）和 3 个 RISC-V 32-bit 平台。
- **AppBreaks 结构体**：新增，保存 memory_start, memory_size, app_break, kernel_break, flash_start, flash_size 等精确边界指针，并带 Flux 不变量。

## 五、实验结果

**正确性（差分测试）**：在 21 个 Tock 上游测试应用上对比 TickTock 和 Tock，5 个结果不同（均为预期差异：测试内存布局或读取传感器数据）。ARM 平台在真实硬件（Nordic NRF52840dk）上测试，RISC-V 在 QEMU 上测试。

**性能（ARM CPU cycles）**：

| 方法 | TickTock | Tock | 差异 |
|------|---------|------|------|
| allocate_grant | 641 | 1,290 | **-50%**（TickTock 更快） |
| brk | 845 | 1,079 | **-22%** |
| build_readonly_buffer | 116 | 145 | **-20%** |
| build_readwrite_buffer | 78 | 118 | **-34%** |
| create | 638,545 | 634,137 | +0.7% |
| setup_mpu | 98 | 91 | **+8%**（TickTock 略慢） |

- **Context switching**：Tock 32,640 cycles vs TickTock 32,740 cycles，差距 **0.3%**。
- **内存使用**：TickTock 分配 7,780 字节（Tock 8,192 字节），两者 grant 区域接近（1,200 vs 1,284），差异主要来自 Tock 预留更多 padding。

**验证时间**：

| 组件 | 函数数 | 总时间 | 最长单函数 | 平均 |
|------|--------|--------|-----------|------|
| TickTock (Monolithic) | 660 | 5m19s | 4m57s | 0.48s |
| TickTock (Granular) | 791 | **36s** | 8s | **0.05s** |
| Interrupts | 95 | 2m34s | 2m3s | 1.63s |
| **Total** | — | **~3min** | — | — |

粒度化重构使 kernel 验证时间从 5 分钟降到 36 秒；原始代码超过 90% 的验证时间消耗在 `allocate_app_mem_region` 一个函数上。

## 六、批判性分析

**1. Trusted 代码规模不小，且部分原因令人担忧**

125 个 trusted 函数中，14 个是因 Flux 工具 bug 而无法验证——这意味着形式化保证存在工具层面的漏洞，而论文并未详细说明这些函数的安全关键程度。论文声称"formally verified isolation"，但 TCB 的边界其实相当宽泛（还包括 Rust 标准库、Rust 编译器、Flux 本身）。

**2. 性能实验仅在 ARM 上进行，RISC-V 被排除**

论文以"QEMU 不反映真实硬件性能特征"为由放弃 RISC-V 性能评估。但 TickTock 支持三个 RISC-V 平台，完全没有性能数据使 RISC-V 实现的可用性存疑。

**3. 内存使用对比语境不清**

TickTock 使用 7,780 字节，Tock 使用 8,192 字节，论文声称"当配置 TickTock 加上 padding 后未使用内存接近 Tock"。但这个"padding"是用户可配置的还是需要手动调整？实际部署中内存浪费的影响在资源受限设备上不容忽视，论文轻描淡写地带过了。

**4. Differential testing 的有效性有限**

21 个测试应用来自 Tock 上游发布测试套件（release test suite），覆盖面明显不足。对于 isolation 属性这种 safety property，差分测试几乎无法发现 Tock 和 TickTock 之间的语义差异——isolation bug 通常需要恶意进程才能触发，而这些测试均为良性应用。

**5. 中断验证的可信度依赖 FluxArm 的正确性**

FluxArm 本身有 67 个函数被标记为 trusted（对应 ARM ISA 语义的 lifting），加上 60 行 ARM spec 和 78 行 RISC-V spec 均为 trusted。实际上，最底层的 ISA 语义由人工编写，未经机器检验。如果 FluxArm 对某条指令的语义建模有偏差，整个中断验证链就会失效。

**6. 论文标题"Production"有些夸大**

Tock 确实用于 Google GSC 等产品，但 TickTock 是 Tock 的 fork，两者在内存布局上存在差异，且 TickTock 尚未被上游合并（论文中也提到了）。"在生产 OS 中实现验证隔离"的表述容易让读者误解 TickTock 本身已在生产中部署。

---

## 七、总结

TickTock 通过将 Flux 精化类型验证器引入 Tock 这一真实微控制器 OS，在实践中证明了以适中的标注代价（3.5K KLOC 注解 / 22K LOC 代码）可以形式化保证进程 isolation。核心贡献是一个"验证引导的"粒度化 MPU 抽象重构：通过解耦 kernel 内存布局逻辑和硬件约束，使代码更简单、验证更快（5 分钟 → 36 秒），同时在过程中发现了 7 个已有代码中的 isolation 漏洞。主要局限在于 TCB 仍然依赖工具链（Flux、Rust 编译器）和人工编写的 ISA 语义，且性能评估仅覆盖 ARM 平台。这项工作为"将自动化验证器增量地应用于现有生产系统"提供了一个颇具说服力的案例研究。
