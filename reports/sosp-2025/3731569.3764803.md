# Unlocking True Elasticity for the Cloud-Native Era with Dandelion

**作者**：Tom Kuchler, Pinghe Li, Yazhuo Zhang, Lazar Cvetković, Boris Goranov, Tobias Stocker, Leon Thomm, Simone Kalbermatter, Tim Notter, Andrea Lattuada, Ana Klimovic（ETH Zurich, MPI-SWS）

## 一、背景

云计算的核心价值之一是**弹性（elasticity）**：平台能够按需自动分配和释放资源，使可用资源随时与实际负载匹配，从而避免过度预置。Serverless/FaaS（Function-as-a-Service）平台是弹性计算的最新形态，理论上能在请求到达时按需启动函数沙箱，但受限于当前沙箱启动延迟（Firecracker MicroVM 用快照仍需 >10ms，冷启动更高），平台不得不预热大量空闲沙箱常驻内存。

与此同时，云原生应用的开发方式正在发生变革：现代应用越来越多地通过 REST API 与云存储、AI 推理、数据库等外部服务交互，而不依赖传统 POSIX 本地接口。这一趋势为重新设计云平台接口提供了机会。

---

## 二、要解决的问题

**核心问题：现有 FaaS 平台无法实现"真正的弹性"，根源在于沙箱启动太慢。**

具体体现：

1. **内存过度预置**：以 Azure Functions trace 为例，Knative 自动伸缩策略为使 97% 的请求命中热沙箱，平均需要维持 **16 倍于实际活跃请求所需** 的内存（2619MB vs 109MB），DRAM 占服务器成本的主导，代价高昂。

2. **性能方差大**：即便有快照优化，冷启动请求延迟仍比热启动高出数倍，tail latency 对少量冷启动请求极度敏感（p99 随冷启动比例呈指数上升）。

3. **根源分析**：沙箱速度慢的根本原因是 POSIX 兼容的计算环境需要加载 Guest OS 镜像（按需分页 >8ms）、重建 Guest-Host 网络连接，而这些都是为了支持 POSIX 接口所必须的，并非函数计算本身的需求。Wasm 虽启动更快，但商用平台为安全仍添加 namespace/seccomp 等机制，再次限制了弹性。

---

## 三、核心设计

**Dandelion 的关键洞察**：cloud-native 时代的应用与云平台的交互已经从文件/socket 级别的 POSIX 接口演变为 REST API 级别的高层接口。重新设计应用与平台的接口，去掉 POSIX 依赖，就可以彻底去掉沙箱对 Guest OS 和网络栈的依赖，从而实现 100 μs 级冷启动。

### 编程模型

Dandelion 将应用表达为 **计算函数（compute functions）** 和 **通信函数（communication functions）** 组成的 DAG（有向无环图）：

- **计算函数**：不可信的用户代码片段，接受声明式输入集合，产出声明式输出集合。**纯函数，不允许发出 syscall**，不依赖 Guest OS 或网络栈。输入输出通过内存映射的虚拟文件系统传递，标准 libc 文件操作被重定向到 userspace（dlibc/dlibc++），无需 syscall。
- **通信函数**：由 Dandelion 平台实现（如 HTTP 函数），用户可调用但不可修改。负责与远程云服务（存储、AI 推理服务、数据库等）交互。通信函数受信任，允许调用 syscall。

DAG 的边描述数据流向，支持 `all`/`each`/`key` 三种数据分发语义，类似 Spark/Timely 的 DSL。

### 执行系统设计

计算函数与通信函数的分离使 Dandelion 得以实现三项关键优化：

1. **快速冷启动**：计算函数沙箱不需要 Guest OS 和虚拟网络设备，可以使用极轻量的隔离机制（KVM 轻量 VM、Linux 进程 + ptrace、CHERI 硬件能力、rWasm 软件隔离），在 100μs 级完成沙箱创建和函数执行，使**每个请求都按需冷启动**成为可能。

2. **协作式网络 I/O**：通信函数每节点只运行一个异步 runtime（基于 green threads），而非每沙箱一个网络栈，显著降低上下文切换开销。

3. **弹性 CPU 核分配**：计算函数独占专用 CPU 核并运行至完成（无抢占，无 context switch）；通信函数使用过量订阅的核。Dispatcher 根据系统中计算与 I/O 函数数量动态调整 CPU 核分配比例。

## 四、实现细节

- 实现语言：**~12K 行 Rust**（其中仅 2K 行直接涉及隔离和用户代码交互），TCB 极小，明显小于 Firecracker（~68K 行）、gVisor（~38K 行 Go）。

- **四种隔离 backend**：
  - **KVM backend**：利用硬件虚拟化（Intel VT-x），每个计算函数运行在无 Guest 内核的轻量 VM，使用恒等 Guest 虚拟/物理地址映射；受 Virtines 启发复用 KVM 结构避免 VM 启动开销。
  - **Process backend**：每函数独立进程，通过共享内存传递数据，ptrace 拦截并阻断 syscall。
  - **CHERI backend**：利用 ARM Morello CHERI 硬件能力扩展，函数作为线程在同一进程内运行，硬件能力指针强制内存隔离；无需 spawn 新线程在关键路径上。
  - **rWasm backend**：将用户 Wasm 代码转译为安全 Rust 代码，由 Rust 编译器在编译期保证内存安全，无需运行时 Wasm VM。

- **Dispatcher**：用 green threads 协调 DAG 执行，将非控制流任务（加载代码、数据传输、函数执行）offload，避免瓶颈。

- **通信引擎**：每引擎独占一个 kernel thread + 独立异步 runtime。HTTP 函数仅验证有限字段（HTTP method、协议版本、URI 前缀），攻击面极小。

- 目前支持 C/C++ SDK 开发计算函数，提供自定义 dlibc/dlibc++ 库；通信函数目前仅支持 HTTP，计划扩展。

## 五、实验结果

### 沙箱创建延迟（Morello 板，1x1 matmul，0% 热请求）

| Backend | Marshal | Load from disk | Transfer input | Execute | Total |
|---------|---------|---------------|---------------|---------|-------|
| CHERI | 12μs | 29μs | 2μs | 5μs | **89μs** |
| rWasm | 15μs | 147μs | 2μs | 20μs | 241μs |
| Process | 12μs | 54μs | 6μs | 371μs | 486μs |
| KVM | 30μs | 194μs | 2μs | 536μs | 889μs |

在 Linux 5.15 标准内核上：rWasm=109μs，Process=539μs，KVM=218μs。

对比：Firecracker 冷启动 >150ms，快照恢复仍限制在 ~120 RPS；Wasmtime（池化 1000 实例）峰值 7000 RPS；HyperLight Wasm 平均 9.1ms 冷启动。

### 计算函数吞吐（128×128 int64 matmul，16 核服务器）

- Dandelion KVM：峰值约 4800 RPS，延迟低且稳定
- Firecracker（97% 热请求）：峰值约 3000 RPS（快照），超过 2800 RPS 后不稳定
- Wasmtime：峰值约 2600 RPS，因代码生成效率低导致更高延迟

### 混合负载多路复用（I/O 密集 + 计算密集）

| 系统 | 图像压缩 avg 延迟 | 相对方差 | 日志处理 avg 延迟 | 相对方差 |
|------|----------------|---------|----------------|---------|
| Dandelion | **18.2ms** | **1.3%** | **27.9ms** | **2.9%** |
| Firecracker（97% hot）| 20.4ms | 389% | 25.6ms | 1495% |
| Wasmtime | 53.3ms | 6.1% | 28.9ms | 79.2% |

### Azure Functions Trace（100 函数，进程隔离 backend）

- Dandelion 平均提交内存：**109MB**（vs Firecracker + Knative：2619MB）
- 内存节省 **96%**
- p99 端到端延迟比 Firecracker 低 **46%**

### 弹性查询处理（SSB/TPC-H，~700MB 数据，EC2 m7a.8xlarge）

- 比 AWS Athena 延迟低 **40%**，成本低 **67%**

## 六、批判性分析

1. **实验规模有限，与商用系统对比不公平**：与 AWS Athena 的对比在单节点 EC2 上进行，且作者明确指出"没有运行在相同硬件或相同 operator 实现"上。这个比较缺乏控制变量，更像是概念验证而非严格基准测试。大规模分布式场景（>7GB 数据）需要多节点 Dandelion，但论文对此场景的性能描述极为简略。

2. **编程模型的表达能力问题被轻描淡写**：论文将"不支持需要细粒度共享内存/大量状态同步的应用"列为 non-goal，但这恰恰排除了大量真实云应用（在线事务处理、游戏、实时流计算）。现有 FaaS 应用迁移到 Dandelion 需要重写，迁移成本完全未被讨论。

3. **数据拷贝开销被掩盖**：函数间数据传递目前通过拷贝完成（作者承认是 future work）。在数据密集型应用中，多跳 DAG 的数据拷贝累积开销可能显著。论文 §7.4 的组合开销实验（2-16 phases）虽然数字看起来可接受，但输入数据只有 64KiB，不能代表实际大规模数据处理场景。

4. **安全性分析偏定性，缺乏正式证明**：论文声称通过拒绝 syscall 最小化攻击面，但 ptrace 本身作为 syscall 拦截机制是有开销的，且 ptrace 的安全性在某些场景下有已知绕过（如进程注入）。CHERI 和 rWasm 的安全边界分析虽然有理论依据，但没有针对已知攻击的实证测试。

5. **CPU 核弹性调度控制器细节不透明**：论文声称动态调整 compute/communication 核分配比例，但对控制器算法的描述很少。实验中核数变化是手动展示的，没有说明控制器在什么条件下做决策、反应延迟如何、能否处理突发流量混合变化。

6. **与 SigmaOS 等近期工作的对比缺失**：SigmaOS（SOSP '24）也放弃了 POSIX 兼容性、为 cloud-native 应用定制接口，与 Dandelion 的思路高度相关，却只在相关工作中一笔带过，没有定量比较。

## 七、AI Infra / MLSys 视角

Dandelion 对 AI Infra 有若干值得关注的借鉴价值：

**直接相关性**：
- 论文本身展示了一个 **Text2SQL agentic AI workflow** 在 Dandelion 上的运行案例（调用 Gemma-3-4b-it LLM 推理服务），证明 DAG 编程模型可以自然表达 AI pipeline。
- AI 推理服务天然是 REST API，通信函数模型完美契合；LLM 推理延迟高，前处理/后处理的计算函数可以用超轻量沙箱快速弹起。

**可迁移的设计思路**：
1. **计算/通信分离 + 协作调度**：AI serving 系统中 prefill 与 decode 阶段、CPU preprocessing 与 GPU compute 阶段的分离调度问题，与 Dandelion 的 compute-comm split 有异曲同工之处。Dandelion 的协作调度思路可以启发 AI serving 中的 continuous batching 策略改进。
2. **声明式数据流 DAG**：AI pipeline（RAG、multi-agent、compound AI systems）本质上是 DAG，现有系统（LangChain 等）的编排层与底层执行系统割裂。Dandelion 的 co-design 思路——让编程模型主动暴露数据依赖给运行时——在 AI 推理编排中有很大潜力。
3. **极轻量隔离用于 UDF**：AI 应用中常有用户提供的处理逻辑（特征工程、自定义评估函数）需要安全隔离执行。Dandelion 100μs 级别的沙箱方案比 MicroVM 更适合高频、短时的 UDF 场景。

**值得跟进的研究方向**：
- 将 Dandelion 的 DAG 模型扩展到 **stateful AI pipeline**（带 KV cache reuse、session context 的对话系统）
- 在多节点分布式 AI inference 场景中验证 compute-comm 分离调度的收益
- 探索 Dandelion 风格的接口用于 **serverless fine-tuning**（LoRA adapter 的快速弹起与隔离执行）

---

## 八、总结

Dandelion 通过将 FaaS 编程模型重新设计为"纯计算函数 + 平台提供通信函数"的 DAG，彻底去除了沙箱对 Guest OS 和网络栈的依赖，实现了 100μs 级别的冷启动，使得每请求按需冷启动成为可能。在 Azure Functions trace 上，内存占用比 Knative 自动伸缩减少 96%；对弹性查询处理，比 AWS Athena 延迟低 40%、成本低 67%。主要局限在于编程模型要求重写应用（不兼容现有 POSIX 代码）、数据拷贝开销在大规模数据处理中未经充分验证、以及分布式多节点场景评估不足。
