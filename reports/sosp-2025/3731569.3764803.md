# Dandelion: Unlocking True Elasticity for the Cloud-Native Era

## 1. 论文基本信息

- **标题**: Unlocking True Elasticity for the Cloud-Native Era with Dandelion
- **作者**: Tom Kuchler, Pinghe Li, Yazhuo Zhang, Lazar Cvetkovic, Boris Goranov, Tobias Stocker, Leon Thomm, Simone Kalbermatter, Tim Notter, Andrea Lattuada, Ana Klimovic (ETH Zurich & MPI-SWS)
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764803
- **代码**: https://github.com/eth-easl/dandelion

## 2. 研究背景

弹性（Elasticity）是云计算的核心价值——系统能够根据负载变化自动伸缩资源配置，使可用资源与当前需求尽可能匹配。IaaS 提供比本地部署更强的弹性（VM 启动时间以十秒计），Serverless/FaaS 则更进一步（函数启动时间以百毫秒计），根据调用负载自动伸缩。

**当前 FaaS 的弹性假象**：尽管 FaaS 平台被宣传为弹性服务，但即使采用快照等优化，VM/容器启动时间仍在毫秒到百毫秒量级，远高于单个请求的持续时间。因此，生产 FaaS 平台必须预配置大量空闲 sandbox 来减少冷启动概率。例如，Knative 在运行 Azure Functions trace 时，**97% 的请求在预热 sandbox 中执行**（warm starts），但这导致平台 commit 了 **16 倍于实际需要的内存**。

预配置的根本原因：POSIX-like sandbox 环境需要加载 guest OS 快照（> 8ms）和配置 guest-host 网络连接——这两项开销无法通过简单的性能优化消除。

**与 Cloud-Native 趋势的矛盾**：现代应用开发越来越多采用云原生方式——使用 REST API 与云服务（存储、分析、AI 推理）交互，而非依赖 POSIX 文件系统接口。这意味着对传统 POSIX 接口的强兼容性可能已经不再是必要的。

## 3. 要解决的问题

**核心问题**：如何通过重新设计云应用接口，消除 guest OS 和网络栈初始化的 overhead，使每个请求都能按需冷启动，从而实现真正的弹性？

具体挑战：
- **冷启动延迟的本质障碍**：即使 minimal KVM 实例可以 52 us 启动，但加载 hello-world 函数到 Firecracker MicroVM 仍需超过 10 ms——大部分时间花在加载 guest OS 快照和建立 guest-host 连接上
- **内存过配置的巨大代价**：DRAM 占服务器成本的 30-50%，大量预热 sandbox 导致严重的资源浪费
- **冷启动对尾延迟的影响**：少量冷启动请求的额外延迟在交互式应用中显著影响用户体验（log scale 效果）

## 4. 核心贡献

1. **云原生编程模型**：提出 Dandelion——一种声明式的云原生编程模型，将应用表达为纯计算函数（Pure Compute Functions）和通信函数（Communication Functions）的 DAG，替代传统的 POSIX-based 接口。
2. **真正的弹性**：通过消除 guest OS 需求，Dandelion 实现 sandbox 在 **100 us 量级**（最快可达 90 us）冷启动，使按需创建 sandbox 成为可能。
3. **内存节省 96%**：相比 Knative autoscaling，运行 Azure Functions trace 时内存过配置降低 96%。
4. **多语言支持**：提供 C 和 C++ 的 SDK，以及 Python 解释器。
5. **多种隔离后端支持**：KVM、Linux 进程、CHERI 内存能力、rWasm 四种不同安全 trade-off 的隔离机制。

## 5. 主要研究方法

### 5.1 冷启动延迟分析
- 加载 minimal Firecracker MicroVM 快照：> 8 ms（主要是 demand paging 和 guest-host 连接建立）
- 即使使用快照优化，总开销仍在数十毫秒量级
- 这些开销与 POSIX-like 环境强相关——POSIX 要求网络栈、线程管理等 OS 服务的初始化

### 5.2 云原生编程模型洞察
**关键观察**：
- 纯计算函数不需要 OS 支持：不需要 guest OS、网络栈、线程管理。分配独立内存区域->加载输入->通过标准 C/C++ 库（dlibc/dlibc++）处理文件读取/写入（无 syscall）->设置输出
- 通信函数由平台实现：HTTP 通信等 I/O 操作由 Dandelion 平台提供，用户无法修改
- DAG 模型使数据依赖明确：通信函数支持 HTTP，可访问云存储、AI 推理等

### 5.3 通信-计算分离设计
- **纯计算函数**：执行用户代码片段，输入输出是声明的数据集。无需 OS 支持，通过 Dandelion 自定义的内存管理消除 syscalls
- **通信函数**：Dandelion 平台实现，允许与外部服务交互（REST API）。用户只能调用，不能修改实现

### 5.4 协作式网络 I/O
- 为所有计算函数提供协作式网络运行时（per-node 而非 per-sandbox）
- 根据系统中计算函数 vs. 通信函数的数量弹性调整 CPU core 分配
- 对通信函数进行 CPU over-commit，对计算函数 dedicated cores

## 6. 设计与实现

### 6.1 dlibc 和 dlibc++ 设计
- 提供内存分配、文件系统操作（内存映射虚拟文件系统）、基础工具函数
- 底层使用 Dandelion 设置的特殊数据结构指向输入集和输出集
- 函数通过 mmap/mprotect/socket 等 syscall 的 stub 实现（返回适当错误码而非崩溃）

### 6.2 HTTP 通信函数
- 接收标准化 JSON 输入
- 验证和 sanitize 输入以防止恶意请求
- 发起 GET/PUT/POST/DELETE 请求
- 返回响应给 composition 继续处理

### 6.3 隔离后端实现
- **KVM**：快速启动（约 100 us 级别），强隔离
- **Linux 进程**：最轻量，但隔离最弱
- **CHERI**：硬件内存能力，实现内存安全隔离（< 90 us）
- **rWasm**：Wasm-based 隔离

### 6.4 适用场景
- 数据转换管道（图像压缩、视频转码）
- 分布式日志处理
- CI/CD 任务
- 弹性查询处理（包括不可信 UDF 执行）
- **Agentic AI workflows**

### 6.5 非适用场景
- 大规模状态同步的应用（如 OLTP、在线游戏）
- 依赖细粒度多线程和高性能共享内存的 AI 训练

## 7. 主要实验结果

### 7.1 Sandbox 启动时间
- Dandelion：100 us 量级
- CHERI：< 90 us
- Firecracker（快照）：10+ ms
- **提升超过 100 倍**

### 7.2 内存效率
在 Azure Functions trace 上测试（Knative autoscaling 作为基线）：
- Knative commit 了 16 倍于实际需要的内存
- Dandelion **降低内存过配置 96%**
- 内存使用与活跃请求数紧密匹配

### 7.3 尾延迟
- 消除了快照预热相关的尾延迟 spikes
- 95-99% hot 时 Firecracker 仍有明显尾延迟（由冷启动导致）
- Dandelion 在各种 hot 比例下保持稳定低延迟

### 7.4 查询处理对比
- 相比 AWS Athena serverless 查询服务：**降低延迟 40%，降低成本 67%**（短查询）
- 查询处理中的冷启动开销被完全消除

### 7.5 执行时间方差
- 消除了冷启动导致的执行时间大幅波动
- 在按需创建 sandbox 的场景下性能差异仅在 2-3 个数量级内（vs. 3-4 个数量级）

## 8. 潜在问题/局限性

1. **编程模型的迁移成本**：Dandelion 的编程模型与传统的 POSIX 应用完全不同。开发者需要将现有应用重写为"纯计算 + 通信函数"的 DAG 形式，这是一个实质性的工程负担。
2. **外部服务依赖的简化处理**：Dandelion 将所有外部服务交互简化为 HTTP REST API。但现代应用大量使用 gRPC、GraphQL、WebSocket 等多种协议，以及共享状态、事件流等复杂交互模式。
3. **状态管理的缺失**：Dandelion 针对无状态函数设计。对于需要状态管理的应用（如数据库连接池、缓存等），需要在应用层面或通过额外的通信函数实现。
4. **调试和可观测性挑战**：当计算函数崩溃或行为异常时，由于 sandbox 的短暂性和分布式特性，调试可能非常困难。
5. **安全模型的信任边界**：纯计算函数假设共享地址空间是安全的，但这一信任边界需要开发者明确遵循规范。缺乏强制机制。
6. **与现有 FaaS 生态的兼容性**：Dandelion 需要完全重写应用，无法渐进迁移。对于已有大量 FaaS 应用的组织，迁移成本可能不可接受。
7. **长期运行任务的支持**：Dandelion 主要针对短时请求优化。对于需要长时间运行的后台任务（如长时间训练任务），其编程模型和资源管理策略可能不适用。

## 9. 未来工作

1. **自动分解工具**：自动将现有云原生应用分解为纯计算和通信函数，减少迁移负担。
2. **更多通信函数支持**：gRPC、S3 特定 API、GraphQL 等。
3. **状态管理原语**：为需要状态的应用提供轻量级状态管理机制。
4. **更丰富的隔离后端**：探索 SGX 等硬件安全隔离技术。
5. **性能优化**：进一步减少 sandbox 创建和销毁的 overhead。

## 10. 个人评注

**Dandelion 是一篇有思想深度的论文**，它不仅仅是一个工程实现，更是对 serverless 计算本质的重新思考——"如果我们从零开始设计云应用接口，而不受 POSIX 兼容性的约束，弹性可以达到什么程度？"

论文最核心的洞察是**POSIX-like 接口与弹性之间的根本矛盾**：为了提供 POSIX 兼容性，FaaS 平台需要加载完整的 guest OS 环境和网络栈，这本身就需要毫秒级的初始化时间。这个时间远大于许多函数的执行时间（可能只有几十毫秒），导致要么预热 sandbox（浪费内存）要么忍受冷启动（影响延迟）。Dandelion 的解决方案是改变接口语义——用 HTTP-based 的通信函数替代 POSIX syscalls，从根本上消除了对 guest OS 的需求。

**批评性思考**：
- **"96% 内存节省"需要语境**：这个数字是相对于 Knative aggressive autoscaling 的内存 commit 而言的。相对于完全不预配置的基线（每次请求冷启动），Dandelion 的内存使用当然更低，但这是否意味着它是更实用的方案？实际上 Knative 的预配置策略是在"冷启动延迟"和"内存成本"之间的工程权衡，Dandelion 只是选择了另一端。
- **编程模型的实用性**：DAG + 纯计算函数 + 通信函数的模型非常优雅，但在实践中，许多云原生应用并不是从一开始就按这个模型编写的。论文的 SQL 查询处理和日志处理例子相对规整，但更复杂的应用（如需要迭代处理、动态分支、跨请求状态累积的）如何映射到这个模型未充分讨论。
- **与现有 FaaS 生态的竞争**：AWS Lambda、Google Cloud Functions 等已有成熟的开发者生态、监控工具、CI/CD 集成。Dandelion 的"破坏性创新"在实践中面临巨大的生态壁垒。
- **"Agentic AI workflows"作为 target workload 很有前瞻性**：但论文未详细讨论 LLM 调用、超时处理、流式输出等实际 AI 工作流的挑战。
- **dlibc 的完整性令人担忧**：通过 stub 实现替代 syscalls（mmap、socket、threading），虽然声明这些功能"不需要"，但实际上许多实用库依赖这些功能。如何处理这些依赖是一个未解决的工程挑战。

总体而言，这是一篇值得关注的论文，因为它挑战了 FaaS 领域的核心假设。对于想思考云计算未来方向的架构师和研究者，这是一篇启发性的工作。但对于实际从业者，其编程模型的迁移成本和与现有生态的兼容性是需要认真考虑的实际问题。
