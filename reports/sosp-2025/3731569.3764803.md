## 一、背景

弹性（elasticity）是云计算的核心价值主张：平台应能快速按需分配和释放资源，使资源使用与负载精确匹配。Serverless / FaaS 平台将弹性推向了新的高度——通过在 10ms 到 100ms 内启动沙箱来自动扩缩容。

然而，即使是当前最先进的 FaaS 平台也远未实现"真正的弹性"。为了避免冷启动的高延迟，平台必须在内存中预置大量空闲沙箱（hot sandboxes）。以 Azure Functions trace 为例，Knative 自动扩缩策略下平台平均提交的内存是实际活跃请求所需的 16 倍。DRAM 是服务器成本的主要组成部分，这种过度预置直接导致了高昂的运营成本。同时，少数需要冷启动的请求仍会引发显著的尾延迟（tail latency）波动。

Cloud-native 应用开发的兴起提供了重新设计云应用接口的机会：现代应用越来越多地通过 REST API 与各种云服务（存储、数据库、AI 推理）交互，而非依赖完整的 POSIX 环境。

---

## 二、要解决的问题

1. **冷启动延迟过高**：即使使用 Firecracker snapshot，恢复一个 MicroVM 仍需 >10ms（其中 >8ms 花在 demand paging guest OS 状态和重建 host-guest 网络连接上），这对执行时间仅为数十毫秒的短函数来说开销过大。
2. **内存过度预置**：为减少冷启动概率，平台预置大量热沙箱，平均提交内存是活跃负载的 16×，浪费昂贵的 DRAM 资源。
3. **高性能波动性**：即使 97% 的请求是热启动，剩余 3% 的冷启动仍导致极高的尾延迟（p99 可达热启动延迟的 10-100×）。
4. **POSIX 接口的历史包袱**：当前沙箱需要完整的 guest OS 和虚拟网络设备来提供 POSIX-like 环境，这是启动慢、资源消耗大的根本原因。

---

## 三、洞察与设计

**关键洞察**：Cloud-native 应用本质上由两类操作组成——纯计算逻辑和与外部服务的通信——如果将两者显式分离并用不同的机制执行，就可以让纯计算函数运行在无需 guest OS 的轻量级沙箱中，从根本上消除冷启动瓶颈。

基于这一洞察，Dandelion 提出了一种声明式的 cloud-native 编程模型：

- **应用表示为 DAG**：节点分为 **compute functions**（纯计算，无系统调用）和 **communication functions**（平台提供的可信 I/O 函数，如 HTTP 通信）。
- **纯计算函数**在轻量级沙箱中执行，仅需内存隔离，无需 guest OS、网络栈或线程支持。输入/输出通过内存映射的虚拟文件系统传递，全程无 syscall。
- **通信函数**由平台实现（受信任），使用协作式网络 I/O（green threads），不需要沙箱隔离。
- **动态 CPU 核心分配**：control plane 基于 PI 控制器监控 compute/communication 队列增长率差异，每 30ms 动态调整两类引擎的 CPU 核心数。

Dandelion 提供自定义 DSL 来描述 DAG 组合，支持 `all`、`each`、`key` 三种数据分发模式。Compute function 通过 dlibc/dlibc++ 链接，提供用户空间的内存文件系统接口，无需系统调用即可完成文件读写。

## 四、实现细节

- **实现语言与规模**：~12K 行 Rust 代码（含测试），其中仅 ~2K 行直接涉及隔离和用户代码交互。
- **四种隔离后端**：
  - **KVM**：轻量级 VM，无 guest kernel，identity mapping，复用 KVM 结构避免 VM setup 开销。冷启动 ~889μs（Morello）/ ~218μs（默认 Linux kernel）。
  - **Linux process**：每个函数一个进程，用 shared memory 传递上下文，ptrace 拦截 syscall。冷启动 ~486μs。
  - **CHERI**：利用 Arm CHERI 硬件能力（capability-based addressing）在单地址空间内线程级隔离。冷启动 ~89μs。
  - **rWasm**：将 Wasm 编译为 safe Rust，再编译为 native shared library。软件隔离，冷启动 ~241μs。
- **Dispatcher**：使用 green threads 协调 DAG 执行，管理内存 context 的分配与回收，offload 代码加载和数据传输。
- **通信引擎**：每个引擎独占一个 CPU 核心，运行异步 runtime + green threads 并行处理多个请求。输入数据会进行 HTTP 协议级别的验证。
- **集群管理**：扩展 Dirigent 实现多节点负载均衡。
- **语言支持**：C/C++ SDK（dlibc/dlibc++），Python 通过编译 CPython 解释器支持。计划扩展到 LLVM 兼容语言。

## 五、实验结果

实验平台：双路 Intel Xeon E5-2630 v3（16 核），256 GiB DRAM；Arm Morello（4 核，16 GiB）；CloudLab d430 节点。

### 沙箱创建延迟（1×1 matmul, Morello, 0% hot）

| 后端 | 总延迟 |
|------|--------|
| CHERI | 89 μs |
| rWasm | 241 μs |
| Process | 486 μs |
| KVM | 889 μs |
| Firecracker (snapshot) | >10 ms |
| gVisor | 更差于 FC snapshot |
| Hyperlight Wasm | 9.1 ms |

### 计算性能（128×128 matmul, 16 核, 97% hot for FC）

| 系统 | 峰值吞吐 | 延迟特性 |
|------|----------|----------|
| Dandelion KVM | 4800 RPS | 低且稳定 |
| Firecracker snapshot | 3000 RPS | 高负载后不稳定 |
| Wasmtime | 2600 RPS | 较高 unloaded latency |

### 混合负载（图像压缩 + 日志处理）

| 系统 | 图像压缩 avg/p99 | 日志处理 avg/p99 | 变异系数 |
|------|------------------|------------------|----------|
| Dandelion | 18.2ms / 19.6ms | 27.9ms / 30.6ms | 1.3% / 2.9% |
| Firecracker | 20.4ms / — | 25.6ms / — | 389% / 1495% |
| Spin/Wasmtime | 53.3ms / — | 28.9ms / — | 6.1% / 79.2% |

### 弹性查询处理（Star Schema Benchmark, 700MB, EC2）

Dandelion vs AWS Athena：延迟降低 **40%**，成本降低 **67%**。

### Azure Functions Trace（100 函数, 20 分钟）

- 内存使用：Dandelion 平均 109 MB vs Firecracker 2619 MB（**减少 96%**）
- p99 延迟降低 **46%**

### Agentic AI（Text2SQL workflow）

端到端 ~2s（5 步），LLM 推理占 61%。一位无 Dandelion 经验的硕士生在数小时内完成了应用移植。

## 六、批判性分析

1. **编程模型的限制被低估**：论文要求开发者将应用手动分解为纯计算和通信函数的 DAG，并使用专有 DSL。这对现有应用的移植成本很高（Text2SQL 例子虽简单，但复杂业务逻辑的分解远非显然）。论文提到可以通过 continuation 自动分解，但这仅是"future work"，实际可行性未验证。

2. **基线比较不完全公平**：Dandelion 的 KVM 后端与 Firecracker 的比较中，Dandelion 省略了 guest OS 和网络栈的启动，但这正是因为其编程模型不同——这更像是在比较两种不同的编程范式，而非同类系统的工程优化。论文标题暗示是"平台优化"，但实质是"接口重新设计"带来的收益。

3. **安全模型的实际强度存疑**：CHERI 后端仅在 Arm Morello 开发板上验证（4 核），这是一块实验性硬件。Process 后端依赖 ptrace 拦截 syscall，已知存在 TOCTOU 竞态问题。rWasm 后端信任 Rust 编译器的安全保证——如果编译器有 bug 则隔离失效。论文的安全分析（§8）主要是定性讨论，缺乏对实际攻击向量的量化评估。

4. **生态系统和语言支持有限**：目前仅支持 C/C++ 和 Python（通过编译 CPython）。实际 FaaS 工作负载中大量使用 Node.js、Go、Java 等语言，论文未讨论支持这些语言的难度。dlibc/dlibc++ 是自定义实现，其与真实 C/C++ 代码的兼容性未充分验证。

5. **实验中的 compute-intensive 负载偏好**：大部分微基准测试使用矩阵乘法——这恰好是纯计算、无状态的理想负载。对于需要大量内存分配、复杂数据结构、或依赖第三方库的真实函数，性能表现可能大不相同。

6. **与 Athena 的比较缺乏深度**：Dandelion 在 EC2 上运行与 Athena 比成本，但 Athena 是托管服务（含运维、容错、查询优化等），两者并非同一抽象层次。论文也承认这一点，但仍将其作为核心实验之一展示。

## 七、AI Infra / MLSys 视角

1. **对 AI 推理 serving 的启发**：Dandelion 将计算与通信分离、动态调整 CPU 核心分配的思路，可以直接借鉴到 LLM serving 系统中。LLM 推理的 prefill 阶段是计算密集型，decode 阶段涉及大量 KV cache 内存操作和 attention 计算的交替——类似的计算/通信分离和资源动态调配思路可以优化 GPU 利用率。

2. **轻量级隔离用于多租户推理**：在多租户 AI 推理场景下（如 API 服务商同时服务多个客户），Dandelion 的轻量级沙箱方案（特别是 CHERI 和 rWasm 后端）为实现微秒级隔离切换提供了参考。这对于 GPU 上的多租户 kernel 隔离（如 MIG 的软件替代方案）有潜在借鉴价值。

3. **Agentic AI workflow 的执行引擎**：论文的 Text2SQL 实验展示了将 agentic 工作流分解为计算函数和通信函数的可行性。随着 compound AI system 的兴起，需要一个高效的执行引擎来协调 LLM 调用、检索、工具调用和自定义计算逻辑——Dandelion 的 DAG 执行模型提供了一个有趣的架构模板。

4. **值得跟进的方向**：
   - 将 Dandelion 的 compute/communication 分离思路应用到 GPU kernel scheduling（计算 kernel vs 通信 kernel 的动态核心分配）
   - 探索 CHERI-like 能力在 AI accelerator 内存隔离中的应用
   - 基于 DAG 编程模型构建 agentic AI workflow 的自动优化器（函数融合、pipeline 并行、数据局部性优化）

---

## 八、总结

Dandelion 通过重新设计云应用的编程接口——将应用分解为纯计算函数和通信函数的 DAG——从根本上消除了 FaaS 冷启动的主要瓶颈（guest OS 启动和网络配置）。其轻量级沙箱可在 100μs 量级冷启动，使每个请求都创建新沙箱变得可行，从而将内存过度预置减少 96%，尾延迟降低 46%。但这些收益的代价是要求开发者适应新的编程模型，且当前语言生态和自动化移植支持尚不成熟。该系统最适合数据流式应用（日志处理、查询、图像处理）和新兴的 agentic AI 工作流。
