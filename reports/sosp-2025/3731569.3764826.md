## 一、背景

现代计算机系统中，vendor firmware（厂商固件）运行在最高特权级别——RISC-V 的 M-mode、Arm 的 EL3——负责硬件初始化、平台管理和系统调用接口（SBI）。与此同时，Trusted Execution Environment（TEE）技术正在蓬勃发展，SGX、TrustZone、RISC-V Keystone、CCA 等方案均依赖一个"security monitor"作为 root of trust，保护 enclave 或 confidential VM 不受不受信任的 OS/hypervisor 侵害。

然而，当前几乎所有平台上，security monitor 与 vendor firmware 共存于同一最高特权级，毫无隔离。Vendor firmware 动辄几十万乃至百万行 C 代码（如 Cavium ThunderX-1 固件超过 100 万行），漏洞频出，一旦被攻破即可绕过整个 TEE 安全模型。seL4 等高保证系统直接假设 firmware 可信，不是因为疏忽，而是因为固件天然具有高特权、不可移植、且往往是闭源二进制这些特性。

随着 RISC-V 在服务器领域的崛起及多租户云安全压力增大，这一问题亟待解决。

---

## 二、要解决的问题

1. **固件与安全监控器共处同一特权级**：vendor firmware 中的漏洞可直接攻破 TEE security monitor，令整个平台安全保证失效。
2. **已有方案需要修改固件**：Dorami 等方案需要对固件进行 binary scanning 和代码修改，适配成本极高，厂商接受意愿低。
3. **Arm EL3 的特权隔离不彻底**：Arm TrustZone 等方案虽有额外特权级，但 vendor firmware 仍比 security monitor 更具特权，后者必须信任前者。
4. **固件 DMA 威胁**：firmware 可通过 DMA 绕过内存隔离访问 OS 内存。

核心问题：**能否在不修改固件二进制的前提下，安全且高效地将 vendor firmware 降权（de-privilege），并将其从 TCB 中移除？**

## 三、核心设计

### Virtual Firmware Monitor（VFM）概念

VFM 是一类新型系统软件，将 vendor firmware 运行在用户态（U-mode），通过软件模拟的方式提供一个虚拟 M-mode（vM-mode），完全复用经典的 trap & emulate 虚拟化技术。

```
经典虚拟化：       固件虚拟化：
U-mode: App        U-mode: Firmware（vM-mode）
S-mode: VMM        S-mode: OS
M-mode: Firmware   M-mode: VFM + Security Monitor
```

VFM 有两个子系统：
- **固件虚拟化子系统**（必须）：拦截所有特权指令和寄存器访问，软件模拟执行
- **Fast path offloading 子系统**（可选）：将高频 trap 操作直接在 VFM 中处理，绕过虚拟化固件

### RISC-V M-mode 的可虚拟化性

按 Popek & Goldberg 形式化定义，RISC-V M-mode 是**经典可虚拟化**的：所有"sensitive"指令（修改或依赖特权状态的指令）都会 trap。而 Arm EL3 则不满足——`cpsid` 指令在用户态执行时被静默忽略而不是 trap，无法用经典 trap & emulate 虚拟化。

### Fast Path Offloading 策略

对 VisionFive 2 平台的测量表明，99.98% 的 Linux boot 期间 M-mode trap 仅由 5 类操作引起：读取 time 寄存器、配置 timer deadline、misaligned load/store、IPI、remote fence。这些均是 RISC-V 架构中对未实现硬件特性的软件模拟，具有可移植性。Miralis 直接在 VFM 中实现这五类操作，每个约 10–100 行代码，将 world switch 频率降至约 1.17 次/秒。

### 隔离策略（Policy Modules）

Miralis 采用可扩展的策略模块设计：`PolicyModule` trait 定义 7 个可选方法（固件 ecall/trap/world switch、OS 侧对应方法、中断处理），策略模块可获得高优先级 PMP 条目用于定制内存保护。三个内置策略：

| 策略 | 目标 | 主要机制 |
|------|------|---------|
| Firmware Sandbox | 保护 OS 不受恶意固件侵害 | 锁定固件内存范围，屏蔽 OS 内存/PCIe/MMIO |
| Keystone Policy | 提供 enclave 支持 | 用 Rust 重写 Keystone SM 作为 policy module |
| ACE Policy | 支持 Confidential VM | 移植 ACE monitor，co-location 方式共享 M-mode 控制 |

## 四、实现细节

**Miralis** 用 Rust 编写，运行在 RISC-V M-mode，总代码量 **6.2k LoC**：

| 子系统 | 代码量 |
|--------|--------|
| 指令模拟器（CSR decode + emulate） | 2.7k LoC |
| 硬件接口层 | 1.1k LoC |
| MMIO 设备模拟（virtual CLINT 等） | 430 LoC |
| Fast path offloading | 190 LoC |
| 其他（world switch、PMP virt 等） | 1.8k LoC |

**关键技术点**：
- **CSR 虚拟化**：维护 84 个 CSR 的 shadow copy，固件执行期间不安装到物理寄存器；world switch 时同步物理/虚拟 CSR 状态
- **PMP 虚拟化**：物理 PMP 条目按优先级多路复用（Miralis 保护 > policy entries > vPMP entries > 默认全局访问），无需影子页表
- **MPRV 模拟**：固件启用 MPRV 位时，Miralis 通过 execute-only PMP 拦截所有 load/store 并模拟内核/用户虚拟地址访问
- **Interrupt 虚拟化**：虚拟 CLINT 多路复用 timer 和软件中断，强制委托非 M-mode 中断至 OS
- **DMA 防护**：IOPMP 不可用时，屏蔽固件对所有 DMA-capable MMIO 区域的访问

**形式验证**框架：
- 将官方 RISC-V Sail 模型翻译为 Rust（2K 行 OCaml Sail→Rust 编译器后端）
- 用 Kani Rust model checker 进行符号执行
- 验证"faithful emulation"（特权指令模拟正确性）和"faithful execution"（PMP 配置正确性）
- 共覆盖 2.7k LoC（43% 代码库），发现并修复 **21 个 bug**，包括 PMP 越界写、虚拟中断丢失、PC 溢出等

## 五、实验结果

**评估平台**：

| 平台 | CPU | 核数 | 频率 | RAM |
|------|-----|------|------|-----|
| VisionFive 2 | StarFive U74（顺序流水线） | 4 | 1.5 GHz | 4 GB |
| HiFive Premier P550 | SiFive P550（乱序超标量，H-mode） | 4 | 1.8 GHz | 16 GB |

**基础开销**：

| 操作 | VisionFive 2 | P550 |
|------|-------------|------|
| 指令模拟（单条特权指令） | 483 cycles | 271 cycles |
| World switch 往返 | 2704 cycles | 4098 cycles |

**Fast path 效果**（VisionFive 2）：

| 操作 | Native (OpenSBI) | Miralis | Miralis no-offload |
|------|-----------------|---------|-------------------|
| 读 time CSR | 288 ns | 208 ns | 7.26 µs |
| IPI | 3.96 µs | 3.65 µs | 39.8 µs |

**应用负载（Miralis vs Native，fast path 开启，均无额外开销）**：
- CoreMark-Pro（CPU）：0 overhead（world switch 0.479/s）
- IOzone（磁盘 I/O）：持平或略好（+0.x%）
- Memcached（网络）：p50 延迟 263 ns vs 279 ns（Miralis 略快）
- Redis、MySQL、GCC：无明显差异
- Boot time：48.0s vs 47.5s（1% overhead）

**无 fast path 时开销**：CoreMark-Pro +1.9%，IOzone +10.6%，Memcached 延迟 2×，boot time +29%

**Keystone enclave**：平均 ~1% 额外开销，与原始 Keystone 结果一致

## 六、批判性分析

**1. RISC-V 局限性被严重低估**

论文花大量篇幅证明 RISC-V M-mode 是经典可虚拟化的，但 Arm EL3 不满足 Popek & Goldberg 条件，只在 Discussion 中一笔带过（提出了 paravirtualization 和 ISA 扩展两个"展望"）。而现实是：绝大多数生产服务器（AWS Graviton、Azure Ampere、Neoverse 系列）都是 Arm 平台，Intel x86 也被明确排除。整篇论文的核心贡献对当前主流服务器硬件没有直接适用性，这是一个不小的 gap，论文没有诚实面对。

**2. "零开销"依赖 fast path，而 fast path 依赖对固件行为的先验知识**

论文强调"不需要修改固件"是核心优势，但 fast path offloading 实际上需要了解固件会发起哪些常见操作并将其在 VFM 中重新实现。作者辩称这些操作都是 RISC-V 开放标准规定的，但这只在固件遵守 SBI 规范时成立——对于不合规或私有固件，fast path 可能失效，性能将大幅下降（无 fast path 时 Memcached 开销达 2×）。

**3. DMA 保护的安全漏洞被轻描淡写**

Security Analysis 章节坦承：在不支持 IOPMP 的平台（即评估使用的所有平台）上，Miralis 会屏蔽固件对 DMA 设备的访问，但对 **OS 发起的 DMA 攻击毫无防护**。这意味着 Firmware Sandbox 策略在实践中的威胁模型是不完整的——一个被 compromised 的 OS 仍可通过 DMA 读写任何物理内存。这不是边缘情况，而是实际部署中的核心风险。

**4. ACE 策略仅在 QEMU 上验证**

论文声称支持 Confidential VM，但 ACE policy 只在 QEMU 上测试（"无法提供有意义的性能比较"）。对于一个号称生产级实现的系统，CVM 支持缺乏真实硬件验证是一个明显缺陷。

**5. 形式验证覆盖范围的误导**

论文说"验证了 43% 的代码库"，但 assembly、device drivers、fast path offloading 均在 TCB 之内且未被验证。Sandbox 和 Keystone 两个策略模块也未被验证（只有 ACE 移植了已验证代码）。端到端安全保证依赖未验证的组件，这与论文的形式方法定位存在落差。

**6. 微基准性能 ≠ 安全策略开销**

大量实验在"firmware sandbox policy"下进行，但 sandbox policy 本身对 enclave/CVM 场景并不适用。Keystone 实验使用的是 RV8 微基准，非现实负载。不同策略的组合开销（同时启用 sandbox + ACE 时的实际影响）没有被量化。

## 七、AI Infra / MLSys 视角

VFM 技术与 AI 基础设施的交汇点主要在**机密计算（Confidential Computing）**方向：

- **AI 推理的 TEE 场景**：保护模型权重不被不信任的云平台 operator 读取是当前 confidential ML 的核心需求。Miralis 通过将 vendor firmware 移出 TCB，使 TEE 安全边界更纯净，对 Keystone/ACE 类型的 enclave 有直接价值。
- **VFM 作为 AI 加速器安全基础**：随着 GPU/NPU firmware 复杂度上升（如 NVIDIA GPU firmware 同样运行在片上微处理器上），VFM 的思路理论上可以扩展到异构加速器的 firmware 隔离，但这需要加速器级别的指令集可虚拟化支持，目前不存在。
- **O(N+M) 维护模型的工程价值**：作者提到将安全监控器实现为 Miralis policy module 可将跨平台维护成本从 O(N×M) 降至 O(N+M)。对于需要在多种 RISC-V 设备上部署 AI 推理 TEE 的场景，这是真实的工程收益。

值得跟进的方向：如何将 VFM 的形式验证框架（faithful emulation criteria + Kani）迁移到验证 GPU/NPU 固件接口的正确性——GPU firmware 的安全验证目前几乎是空白领域。

---

## 八、总结

本文提出 Virtual Firmware Monitor（VFM）概念，并实现了首个 RISC-V VFM——Miralis（6.2k LoC Rust）。核心贡献是将经典虚拟化理论（Popek & Goldberg）应用于固件特权级，在无需修改固件二进制的前提下将 vendor firmware 降权至用户态，配合 fast path offloading 实现零性能开销，并通过轻量级形式验证（Kani + RISC-V Sail）发现 21 个 bug 提升实现可靠性。主要局限在于：目前仅支持 RISC-V（Arm EL3 不可直接虚拟化）、DMA 防护依赖 IOPMP（现有平台均不支持）、ACE 策略缺乏真实硬件验证。该工作对 RISC-V 生态的 TEE 安全架构有重要价值，但在 Arm/x86 主导的生产服务器市场的适用性仍需解决架构层面的根本挑战。
