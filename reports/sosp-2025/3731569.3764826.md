# The Design and Implementation of a Virtual Firmware Monitor

**作者**：Charly Castes (EPFL), François Costa (ETH Zurich), Neelu S. Kalani (EPFL), Timothy Roscoe (ETH Zurich), Nate Foster (Cornell and Jane Street), Thomas Bourgeat (EPFL), Edouard Bugnion (EPFL)

**链接**：https://doi.org/10.1145/3731569.3764826
**源文件**：[[3731569.3764826.pdf]]

## 一、背景

现代系统安全越来越依赖 Trusted Execution Environments (TEEs)，如 enclaves 和 Confidential VMs。TEE 的核心是运行在最高特权级的 security monitor，负责隔离可信与不可信环境。然而，在当前大多数系统中，security monitor 与厂商固件 (vendor firmware) 共存于同一最高特权级（RISC-V 的 M-mode、Arm 的 EL3），彼此之间没有任何隔离。

厂商固件代码量巨大（如 Cavium ThunderX-1 的 Arm 固件超过一百万行 C 代码，包含自定义标准库、调度器甚至 Lua 解释器），且通常以闭源二进制形式提供。固件中的 bug 或漏洞可以完全破坏整个平台的安全性——包括 TEE 提供的所有保护。即使是 seL4 这样经过形式化验证的高保证系统，也直接假设固件是正确的。

---

## 二、要解决的问题

1. **固件与 security monitor 的特权纠缠**：当前 TEE 部署中，security monitor 和厂商固件运行在相同的最高特权级，固件的任何漏洞都会直接危及 security monitor 的安全保证，将整个固件代码纳入了 TCB。

2. **修改固件不现实**：厂商固件通常是闭源的、不可修改的二进制。Dorami 等先前工作需要对固件进行二进制扫描和修改，面临严重的部署障碍——如果厂商不配合，问题就无法解决。

3. **跨平台维护成本高**：当前维护 N 个 security monitor × M 个硬件平台需要 O(N×M) 的工程量，缺乏一个可复用的基础设施来解耦固件虚拟化与安全策略实现。

---

## 三、洞察与设计

**关键洞察**：厂商固件虽然运行在最高特权级，但其绝大多数功能并不需要不受限的特权访问——它主要是对未实现的硬件特性进行软件模拟。在 RISC-V 的 VisionFive 2 平台上，99.98% 的 M-mode traps 只有五种原因（读时间寄存器、配置 timer deadline、非对齐访存、IPI、remote fence），且这些都是对 RISC-V 标准中可选硬件特性的通用模拟，具有跨平台可移植性。

基于这一洞察，论文提出了 **Virtual Firmware Monitor (VFM)** 这一新类别的系统软件：

- **固件虚拟化**：利用经典的 trap & emulate 技术，在不需要额外硬件扩展的情况下，将固件从最高特权级降级到用户态运行。VFM 运行在 M-mode，创建一个虚拟 M-mode (vM-mode)，固件在其中执行时所有特权指令都会 trap 到 VFM 进行模拟。

- **Fast Path Offloading**：对最常见的五种操作（读时间、设置 timer、非对齐访存、IPI、remote fence），VFM 直接处理而不经过虚拟化固件，将 boot 期间的 world switch 从高频降低到仅 1.17 次/秒。

- **可扩展的隔离策略**：VFM 的虚拟化机制与安全策略解耦，通过 policy module 接口支持自定义隔离策略（固件沙箱、enclave、Confidential VM）。

- **经典虚拟化理论适用性**：论文验证了 RISC-V 的 M-mode 满足 Popek & Goldberg 的虚拟化要求（所有敏感指令都是特权指令），而 Arm 的 EL3 不满足（如 cpsid 指令的行为依赖特权级但不会 trap）。

## 四、实现细节

**Miralis** 是论文实现的第一个 VFM，用 Rust 编写，运行在 RISC-V M-mode，总计 6.2k 行代码：

| 模块 | 代码量 |
|------|--------|
| 指令模拟器 | 2.7k LoC |
| 硬件接口 | 1.1k LoC |
| MMIO 设备模拟 | 430 LoC |
| Fast path offloading | 190 LoC |
| 其他 | 1.8k LoC |

**CPU 虚拟化**：
- 维护 CSR 的 shadow copy，固件执行时虚拟 CSR 不安装到物理寄存器
- 支持 12 条特权指令和 84 个 CSR 的模拟
- World switch 时执行 CSR 保存/恢复和 TLB flush

**PMP 虚拟化**：
- 在物理 PMP 寄存器上复用虚拟 PMP 条目，Miralis 自身的 PMP 规则优先级更高
- 使用专用 PMP 条目模拟 M-mode 的默认全内存访问权限
- 通过 execute-only PMP 条目模拟 MPRV bit 行为（允许固件使用内核/用户虚拟地址访问数据）

**中断与 MMIO 虚拟化**：
- 强制所有非 M-mode 中断委托给 OS，仅虚拟化 M-mode 中断
- 虚拟化 CLINT（timer 和软件中断），其他设备（PLIC、cache controller 等）无需模拟
- 通过 PMP 保护 MMIO 区域，拦截固件对 DMA 设备的访问

**形式化验证**：
- 使用 Kani Rust model checker 对指令模拟和内存隔离进行穷举符号执行
- 将 VFM 规范表达为已有高质量 ISA 可执行规范（Sail model）的函数
- 在开发中发现并修复了 21 个 bug（虚拟中断丢失、PC 溢出、越界访问等）
- 验证覆盖 43% 的代码库

**三种隔离策略**：
1. **Firmware Sandbox**：限制固件只能访问分配的小内存区域，阻止访问 OS 内存和大多数 MMIO 设备
2. **Keystone Enclave**：将 Keystone security monitor 作为 policy module 移植，支持安全 enclave
3. **ACE Confidential VM**：支持 Confidential VM，将固件排除出 TCB

## 五、实验结果

**评估平台**：

| | VisionFive 2 | HiFive Premier P550 |
|---|---|---|
| 核心数 | 4 | 4 |
| 频率 | 1.5 GHz | 1.8 GHz |
| RAM | 4 GB | 16 GB |
| 核心类型 | U74 顺序执行 | P550 乱序超标量 |
| Linux 内核 | 5.15 | 6.6 |

**基本开销**：

| 操作 | VisionFive 2 | Premier P550 |
|---|---|---|
| 指令模拟 | 483 cycles | 271 cycles |
| World switch 往返 | 2704 cycles | 4098 cycles |

**Fast path 效果**（VisionFive 2）：

| 操作 | Native (OpenSBI) | Miralis | Miralis no-offload |
|---|---|---|---|
| read time | 288 ns | 208 ns | 7.26 μs |
| IPI | 3.96 μs | 3.65 μs | 39.8 μs |

**微基准测试**：CoreMark-Pro、IOzone、Memcached 延迟均与 Native 无差异（world switch 仅 0.479 次/秒）。禁用 fast path 后：CoreMark-Pro 1.9% 开销，IOzone 10.6% 开销，Memcached 延迟翻倍。

**应用基准测试**（Redis、Memcached、MySQL、GCC）：Miralis（含 fast path）在两个平台上均无性能下降，部分网络负载场景甚至比 Native 快 1.2-7.6%（因 fast path 实现略优于 OpenSBI）。禁用 fast path 后 Redis 在 P550 上开销达 259%。

**启动时间**：Miralis 48.0s vs Native 47.5s（1% 开销）；无 fast path 时 61.3s（29% 开销）。

**Keystone Enclave**：在 VisionFive 2 上 RV8 benchmark 平均 1% 开销，与原始 Keystone 结果一致。

**固件兼容性**：成功虚拟化了 VisionFive 2、Premier P550 和 Star64 三个平台的未修改厂商固件，以及 RustSBI 和 Zephyr RTOS。

## 六、批判性分析

1. **Arm 适用性存疑**：论文核心理论依赖 Popek & Goldberg 虚拟化要求，但明确指出 Arm EL3 不满足。论文对此只给出了两个"we envision"级别的解决方案（paravirtualization 或未来架构修改），但 Arm 是服务器和移动端的主流架构，x86 也被排除在外。VFM 目前仅适用于 RISC-V，而 RISC-V 在服务器市场的份额极小，这严重限制了论文的实际影响力。

2. **Fast path 本质上是将固件功能重新实现在 VFM 中**：论文声称无需修改固件，但 fast path offloading 实际上是在 VFM 中重新实现了固件最常用的功能。虽然这些功能基于 RISC-V 标准因此具有可移植性，但这模糊了"不修改固件"和"不需要固件"之间的界限。没有 fast path 时性能开销高达 259%，说明 VFM 的"零开销"声明严重依赖于这一"绕过固件"的设计。

3. **验证覆盖率有限**：形式化验证仅覆盖 43% 的代码库，排除了汇编代码、设备驱动和 fast path offloading。然而 fast path 是性能关键路径且直接处理 99.98% 的 traps，其正确性至关重要但未被验证。

4. **DMA 防护的现实困境**：在没有 IOPMP 支持的平台上（即论文评估的所有平台），Miralis 通过阻止固件访问 DMA 设备来防御 DMA 攻击，但承认对来自 OS 的 DMA 攻击无能为力。这意味着在 Confidential VM 场景下（OS/hypervisor 不可信），DMA 是一个未解决的安全漏洞。

5. **评估平台代表性不足**：两个评估平台都是低端嵌入式 RISC-V 板（4 核、1.5-1.8 GHz），与服务器场景差距巨大。论文未讨论在更复杂的 RISC-V 服务器平台（更多核心、更复杂的固件）上 VFM 的可扩展性问题。

6. **ACE 策略仅在 QEMU 上验证**：Confidential VM 策略只在模拟器上运行，无法提供有意义的性能数据，削弱了论文关于 VFM 支持 CVM 的声明力度。

---

## 七、总结

本文提出了 Virtual Firmware Monitor (VFM) 这一新的系统软件类别，通过经典的 trap & emulate 虚拟化技术将厂商固件从最高特权级降级到用户态运行，从而将固件从 TEE security monitor 的 TCB 中移除。其实现 Miralis 仅 6.2k 行 Rust 代码，在两个商用 RISC-V 平台上成功虚拟化了未修改的厂商固件且无性能开销，并支持 enclave 和 Confidential VM 等安全策略。但其适用范围目前仅限于 RISC-V 架构，且"零开销"高度依赖 fast path offloading 对常见操作的重新实现。
