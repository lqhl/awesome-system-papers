# Scalable Address Spaces using Concurrent Interval Skiplist

**作者**：Tae Woo Kim, Youngjin Kwon, Jeehoon Kang（KAIST / FuriosaAI）
**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles）
**链接**：https://doi.org/10.1145/3731569.3764807
**源文件**：[[3731569.3764807.pdf]]

## 一、背景

操作系统内核通过虚拟内存管理系统管理进程的地址空间，核心操作包括：Fault（处理页错误）、Alloc（通过 mmap() 分配地址区间）和 Modify（通过 munmap()、mprotect() 等修改映射）。Linux 使用 mmap_lock 这一粗粒度读写锁来同步这些操作——Fault 以读模式获取锁（或通过 per-VMA locking 避免获取），但 Alloc 和 Modify 必须以写模式获取，导致它们被串行化执行。

随着多核处理器核数不断增加以及现代 malloc() 实现（如 jemalloc、tcmalloc）大量使用 mmap() 创建独立 arena，mmap_lock 已成为"内存管理子系统中最棘手的争用点之一"。实验表明，Apache web server 在高线程数下最多有 90% 的执行时间浪费在等待 mmap_lock 上。

---

## 二、要解决的问题

1. **Alloc 和 Modify 操作的串行化**：Linux 6.8.0 虽已引入 per-VMA locking 使 Fault 可以并行，但 Alloc（mmap）和 Modify（munmap/mprotect）仍需获取 mmap_lock 写锁，无法并行执行。
2. **现有方案不够实用**：RadixVM 是唯一能并行化 Alloc/Modify 的方案，但其基于 radix tree 的设计不适合 RCU、采用 per-page 粒度的元数据导致内存开销过大、且地址空间分配策略会快速耗尽地址空间（247 字节空间在 90 秒内耗尽）。
3. **应用层 workaround 有显著缺陷**：多进程替代多线程需要大量 IPC 和架构重构；大块 mmap() 增加内存碎片；不做 munmap() 会占用大量虚拟内存。

---

## 三、洞察与设计

**关键洞察**：地址空间操作的锁定区间是动态的——操作需要锁定的区间取决于地址映射的当前状态（如 munmap 需要锁定目标区间及其相邻间隙），传统的"先遍历确定区间、再加锁"的两步方法存在根本性的竞态条件，而将遍历和锁定统一到同一数据结构的同一操作中可以消除这一竞态。

基于这一洞察，论文设计了 **concurrent interval skiplist**，一种新的并发数据结构，核心特点：

- **统一映射与锁定**：将 interval map 和 locking 机制整合到同一数据结构中，通过 Lock(start, end) 操作同时完成遍历和区间锁定。
- **节点粒度的区间锁定**：在 level-0 链表上通过 CAS 操作对节点的 LOCKED 标志进行锁定，支持对任意动态区间的细粒度锁定。
- **RCU 安全的原子区间更新**：通过 Swap 操作原子地将旧节点替换为新节点（read-copy-update 方式），lock-free 的 Query 遍历保持线性化。

在此数据结构基础上，论文提出了完整的可扩展地址空间设计：

1. **两级锁定方案（Two-Level Locking）**：使用 per-core 读写锁实现全局锁（GR/GW 模式），结合 interval skiplist 的区间锁实现局部锁（LR/LW 模式），优雅地支持 fork()/exit() 等全局操作与并行局部操作的共存。
2. **可扩展的 Alloc 策略**：重新设计进程地址空间布局引入多 arena，配合 skiplist 的层级结构支持 per-thread arena 的快速分配。
3. **可扩展计数器**：自适应地在全局计数器接近限制时逐步减少 per-core 计数器的使用，兼顾扩展性和资源限制的严格执行。

## 四、实现细节

- 基于 **Linux 6.8.0** 实现，约 **10K 行代码**。
- 支持 POSIX 接口，对应用透明，无需修改应用程序。
- 通过 Linux Test Project (LTP, 版本 20240524) 测试验证，结果与 Linux 6.8.0 一致。使用 KASAN 进行额外压力测试。
- 支持匿名内存和文件映射内存（ramfs、tmpfs、ext4）。
- 所有关键操作（page fault、mmap、munmap、mprotect、mremap、常见 madvise 标志）均已并行化。
- Interval skiplist 的关键实现：
  - 基于 Harris lock-free linked list 扩展，新增 LOCKED 和 INVALIDATED 标志位。
  - Swap 操作：锁定区间内节点 → 准备新节点 → 更新前驱链接（提交并解锁） → 标记旧节点 INVALIDATED。
  - Skip links 的批量高度调整避免重复遍历。
- 渐进式适配策略：对于未测试的文件系统或未适配的 Modify 操作，回退到 GW 模式（全局写锁），确保正确性。
- 代码开源：https://github.com/kaist-cp/interval-vm

## 五、实验结果

**实验平台**：双路 Intel Xeon Gold 6248R（3.0GHz，48 核 96 线程），384GiB DRAM，4TB NVMe SSD。

### 数据结构微基准测试（用户空间，interval skiplist vs maple tree）

| 操作 | 单线程延迟对比 | 峰值吞吐量对比 |
|------|---------------|---------------|
| Query | +35% | 0.77× |
| Alloc | +4% | **22.9×** |
| Map | −49% | **5.28×** |

### 地址空间微基准测试（IntervalVM vs Linux）

| 测试 | IntervalVM 峰值加速比 |
|------|---------------------|
| Alloc (mmap) | **13.1×** |
| Alloc+Fault+Modify | **10.4×** |

### LMbench 延迟测试

| 操作 | Linux (μs) | IntervalVM (μs) | 开销 |
|------|-----------|-----------------|------|
| null syscall | 0.094 | 0.093 | −0.5% |
| page fault | 0.200 | 0.206 | +3.2% |
| fork+exit | 271 | 330 | +21.6% |
| mmap+fault+munmap | 6675 | 6890 | +3.2% |

### 宏基准测试（IntervalVM vs Linux 峰值吞吐量）

| 应用 | 加速比 | 说明 |
|------|--------|------|
| Apache（单进程） | **4.53×** | HTTP 静态文件服务 |
| Apache（默认多进程） | **3.19×** | 3-12 进程 × 25 线程 |
| LevelDB | **4.49×** | readrandom 查询 |
| Metis MapReduce | **1.47×** | 倒排索引，4GiB 输入 |
| Psearchy | **1.27×** | 并行文本索引 |

PARSEC 测试中，VM 密集型工作负载（dedup 1.32×，vips 1.16×）有明显提升，非 VM 密集型工作负载差异在 2% 以内。

## 六、批判性分析

1. **fork+exit 延迟开销显著**（+21.6%）：论文以"多线程性能提升可以弥补"轻描淡写地带过，但在 fork-heavy 的工作负载（如 shell 脚本、CGI 服务）中这可能是不可忽视的退化。论文未评估此类场景。

2. **Query 性能退化**：单线程 Query 延迟 +35%、峰值吞吐量仅 0.77×。由于 page fault 处理本质上是 Query 操作，这意味着所有场景下的 page fault 延迟都会略有增加。论文承认了这一点但未深入分析其对 fault-heavy 但非 mmap-heavy 的工作负载的影响。

3. **NUMA 问题未解决**：在 48 核附近出现明显的性能下降，论文归因于"Linux 的 NUMA 相关开销"并声称在单路机器上不存在此问题。但现实中多路 NUMA 机器正是最需要可扩展性的场景，这个问题不应被回避。

4. **RadixVM 对比的公平性**：关闭了 RadixVM 的 per-core page table 和 core-tracking shootdown 功能进行对比，理由是这些功能与地址空间修改"largely orthogonal"。但这些功能本身就是 RadixVM 设计的一部分，关闭后的性能不代表 RadixVM 的真实水平。同时承认 RadixVM 有"significant bugs"导致无法运行宏基准测试，这让对比的可信度打折。

5. **文件系统覆盖有限**：仅测试了 ramfs、tmpfs 和 ext4，对未测试的文件系统回退到全局写锁。论文暗示"大多数文件系统不需要修改"，但未提供系统性的分析来支撑这一论断。

6. **Metis 和 Psearchy 的加速比有限**（1.47× 和 1.27×）：考虑到 mmap_lock 在这些应用中浪费了 60% 和 41% 的时间（Figure 1），理论上的加速空间远大于实际结果，说明还存在其他瓶颈未被解决。

## 七、AI Infra / MLSys 视角

1. **GPU 内存管理的启发**：AI 推理系统（如 vLLM 的 PagedAttention）需要频繁分配和释放 KV cache 块，其内存管理器面临与 mmap_lock 类似的争用问题。Concurrent interval skiplist 的设计思路——统一映射与锁定、RCU 安全的区间更新——可以迁移到 GPU 内存分配器中，改善多请求并发场景下的内存管理效率。

2. **分布式训练中的虚拟内存**：大模型训练中的 memory offloading（如 DeepSpeed ZeRO-Offload）依赖大量 mmap()/munmap() 在 CPU 和 GPU 内存间搬运数据。IntervalVM 的并行化设计可以直接加速这类场景，尤其是在多 worker 共享同一进程时。

3. **可扩展计数器的通用价值**：论文提出的自适应 per-core 计数器机制（接近限制时逐步收敛到全局计数器）在 AI 系统中有广泛应用场景，如分布式训练的梯度累积计数器、推理系统的 token 配额管理等。

4. **值得跟进的方向**：
   - 将 interval skiplist 应用于 GPU unified memory 的地址空间管理
   - 在 RDMA 场景下评估并行化 mmap() 对 memory registration 的加速效果
   - 探索 interval skiplist 在用户态内存分配器（如 jemalloc 的 arena 管理）中的应用

---

## 八、总结

本文提出了首个实用的可扩展地址空间设计 IntervalVM，核心创新是 concurrent interval skiplist——一种将区间映射与细粒度锁定统一的并发数据结构，支持 RCU 安全的 lock-free 遍历和并行区间更新。配合两级锁定方案、多 arena 分配策略和自适应计数器，在 Linux 6.8.0 上实现了 Alloc/Modify 操作的真正并行化。在 VM 密集型应用上取得了 1.27×–4.49× 的显著加速，但在 fork 开销（+21.6%）和 NUMA 场景下存在不足。该工作解决了一个长期存在的内核可扩展性难题，设计思路对内核开发和并发数据结构领域都有重要参考价值。
