## 一、背景

操作系统内核通过地址空间管理虚拟内存，核心操作分三类：
- **Fault**：处理缺页异常，查询地址映射并更新页表；
- **Alloc**：通过 `mmap()` 分配地址区间，被现代 `malloc()` 实现（jemalloc、tcmalloc 等）大量使用；
- **Modify**：通过 `munmap()`、`mprotect()`、`mremap()` 等修改已有映射。

地址映射（address map）是内核维护的一个区间 map，Linux 6.8 采用 RCU 安全的 B-树（maple tree）实现。随着多核处理器核心数不断攀升，内存密集型应用（Web 服务器、KV 存储、MapReduce 框架）中线程对 `mmap()` 和 `munmap()` 的调用愈发频繁，地址空间成为关键性能瓶颈。

---

## 二、要解决的问题

**核心问题**：`mmap_lock`（Linux 中的粗粒度读写锁）将 Alloc 和 Modify 操作串行化，严重限制多线程扩展性。实测显示，在 48 核机器上：Apache 浪费约 90% 时间等待 `mmap_lock`，Metis 约 60%，Psearchy 约 41%，LevelDB 约 40%。

论文识别了五个关键可扩展性挑战，其中多数此前文献未曾讨论：

1. **动态锁定区间（§3.1）**：地址空间操作需锁定的范围不固定——操作前不知道需要锁哪些区间（如 `munmap()` 可能跨越多个 VMA），无法预先细粒度加锁。

2. **可扩展且 RCU 安全的区间更新（§3.2）**：区间更新需要原子性地覆盖多个连续节点。RCU 更新需要"复制-替换"祖先节点，若树的 branching factor 大（如 maple tree 的 10–16，radix tree 的 128–512），复制代价高；且区间更新需同时修改多个叶节点，天然不适合现有 RCU 数据结构。

3. **全局锁与局部锁并存（§3.3）**：某些操作（如 `fork()`、`execve()`）需要锁住整个地址空间（全局锁），而大多数操作只需锁住特定区间（局部锁），两种模式必须高效共存。

4. **Alloc 策略的扩展性（§3.4）**：`mmap()` 分配时需线性扫描寻找空闲区间，多线程竞争同一起始地址导致严重争用。

5. **资源限制计数器的扩展性（§3.5）**：`RLIMIT_AS` 等资源限制需要原子地更新全局计数器，在高线程数下成为瓶颈。

## 三、核心设计

### 系统概述：IntervalVM

论文提出 **IntervalVM**，即以并发区间跳表为核心、在 Linux 6.8.0 上实现的可扩展地址空间设计。

### 核心数据结构：并发区间跳表（Concurrent Interval Skiplist）

区间跳表将**区间映射**与**锁机制**统一在单一数据结构中，支持：
- **RCU 安全的无锁遍历**（用于 Fault 的第一阶段）；
- **节点粒度的细粒度锁定**（用于 Alloc/Modify 并发执行）；
- **原子 Swap 操作**：将旧节点集合原子替换为新节点集合，处理区间更新中的"动态边界"问题。

跳表的 Lock 操作锁定与目标区间重叠的所有节点及其 level-0 前驱。Swap 操作先处理旧节点（打上 INVALIDATED 标记），再插入新节点，最后原子提交——解决了"动态锁定区间"问题。

### 两级锁定方案（§5.1）

为同时支持全局锁和局部锁，提出基于 **per-core 读写锁**的混合粒度锁：

| 模式 | 含义 | 实现方式 |
|------|------|---------|
| GR（全局读） | 读锁整个地址空间 | 读取所有 per-core 锁 |
| GW（全局写） | 写锁整个地址空间 | 写取所有 per-core 锁 |
| LR（局部读） | 读锁特定区间 | 读取当前核的 per-core 锁 + 区间跳表中对应的区间锁 |
| LW（局部写） | 写锁特定区间 | 写取当前核的 per-core 锁 + 区间跳表中对应的区间锁 |

操作以渐进强度尝试加锁：先无锁执行（仅 Fault），失败则 LR/LW，最终才退化为 GR/GW。

### 可扩展 Alloc 策略（§5.3）

将地址空间划分为 64 GiB 的 **per-core arena**（最多 128 个，占 256 TiB 地址空间的 4%）。每个核优先在私有 arena 中分配，arena 满时才使用共享区域。arena 之间通过**分隔符节点（separator nodes）**在跳表中隔离，高层级节点负责跨 arena 遍历，低层级节点处理 arena 内部遍历，减少插入时跨 arena 的争用。

### 可扩展资源限制计数器（§5.3）

采用自适应策略：平时用 per-core 缓冲聚合更新（类似 `percpu_counter`），当全局计数器接近上限（剩余余量 < batch_size × core 数）时，自动切换为直接更新全局计数器，兼顾扩展性与严格限制。

## 四、实现细节

- 在 Linux 6.8.0 上实现，约 **10K 行代码**。
- 支持 POSIX 接口，对应用完全透明，无需修改应用程序。
- 通过 Linux Test Project（LTP v20240524）测试，结果与原版 Linux 一致（少数依赖内核特定地址空间布局假设的测试用例除外）。
- 支持匿名内存和文件映射内存（ramfs、tmpfs、ext4 已测）。
- 关键操作（page fault、mmap、munmap、mprotect、mremap、madvise with MADV_FREE/MADV_DONTNEED）均已并行化。
- 部分 `madvise` 标志暂时仍依赖全局锁，但设计上可扩展。
- 代码开源：https://github.com/kaist-cp/interval-vm.git

## 五、实验结果

**实验平台**：双路 Intel Xeon Gold 6248R（3.0 GHz，48 核，96 线程），384 GiB DRAM，4 TB NVMe SSD，Ubuntu 24.04。

**对比基线**：Linux 6.8.0、RadixVM（禁用 per-core 页表及 core-tracking shootdown 以公平比较）。

### 数据结构微基准（用户态，区间跳表 vs. maple tree）

| 操作 | 延迟对比 | 峰值吞吐量对比 |
|------|---------|-------------|
| Query | +35% 延迟（跳表更慢） | 0.77× |
| Alloc | +4% 延迟 | **22.9×** |
| Map（删除） | **-49%** 延迟 | **5.28×** |

### LMbench（单线程延迟）

| 测试 | Linux | IntervalVM | 开销 |
|------|-------|-----------|------|
| page fault | 0.200 μs | 0.206 μs | +3.20% |
| mmap+fault+munmap | 6675 μs | 6890 μs | +3.22% |
| fork+exit | 271 μs | 330 μs | **+21.6%** |
| null syscall | 0.0938 μs | 0.0933 μs | -0.53% |

### 多线程吞吐量微基准（峰值，双路机器）

| 基准 | IntervalVM vs. Linux | IntervalVM vs. RadixVM |
|------|---------------------|----------------------|
| Alloc（mmap） | **13.1×** | 1.07× |
| Alloc+Fault+Modify | **10.4×** | **5.22×** |

### 真实应用宏基准（峰值吞吐量提升）

| 应用 | vs. Linux | vs. RadixVM |
|------|---------|------------|
| Apache（单进程） | **4.53×** | N/A |
| Apache（默认配置） | **3.19×** | N/A |
| LevelDB | **4.49×** | N/A |
| Metis | **1.47×** | **1.18×** |
| Psearchy | **1.27×** | N/A |
| PARSEC（非 VM 密集型） | 约 ±2% | N/A |

## 六、批判性分析

**fork 性能退化被轻描淡写**：`fork+exit` 延迟增加 21.6%（双路机器），在单路机器上也增加 15.2%。fork 是 Unix 生态中极常见的系统调用（Web 服务器 prefork 模式、shell 等），但论文仅将其归结为"跳表节点数更多导致遍历更慢"，并未提供优化方向。对于 fork 密集型工作负载，IntervalVM 可能反而更慢。

**实验基线不完全公平**：论文禁用了 RadixVM 的 per-core 页表和 core-tracking shootdown 功能（以此为由：Linux 没有这些特性，且这些特性引入 bug 导致宏基准不可靠）。但这两个特性正是 RadixVM 的核心优化之一，禁用后的 RadixVM 并不代表其真实性能，比较结果过于有利于 IntervalVM。

**Alloc 微基准的 13.1× 夸大了实际收益**：`mmap()` 只分配地址，不包含 fault，此基准在实际应用中是最理想的场景。实际应用（如 Apache 3.19×、LevelDB 4.49×）的提升远小于此，说明 mmap_lock 只是诸多瓶颈之一。

**NUMA 相关性能下降未深入分析**：在约 48 线程时（超过单路核心数进入跨 NUMA 域），IntervalVM 吞吐量出现临时下降，RadixVM 在此区间短暂超过 IntervalVM。论文虽指出这是 Linux 的 NUMA 开销，但 IntervalVM 对该问题的应对方案未作说明，实际生产中双路或多路服务器是常见场景。

**"已测试文件系统"假设的脆弱性**：IntervalVM 的并行化仅对"已确认不依赖地址空间实现细节"的文件系统生效（ramfs、tmpfs、ext4）。对于其他文件系统（如 btrfs、f2fs、NFS），关键路径仍退化为全局锁。这一限制对于存储密集型场景影响显著，但论文将其放在未来工作中一笔带过。

**10K LOC 的工程难度风险**：论文未讨论对内核维护性的影响——Linux 内核本身对 patch complexity 要求极高，如此规模的并发设计能否被上游接受是重大问号。

## 七、AI Infra / MLSys 视角

IntervalVM 与 AI Infra 的关联体现在以下几个维度：

**LLM 推理中的内存管理**：现代推理系统（vLLM、SGLang 等）大量使用 `mmap()` 进行 KV cache、权重文件的内存映射，以及频繁的 `munmap()` 进行内存回收。在高并发请求下，这些系统的内存管理操作与 IntervalVM 所解决的问题高度重合——尤其是 Continuous Batching 场景中，KV cache 的动态分配和释放频率极高。

**分布式训练中的共享内存**：多进程分布式训练（如 PyTorch DDP/FSDP）依赖 shared memory 进行梯度聚合和参数同步，`mmap()` 是底层实现。训练过程中频繁的 activation checkpointing 和 offloading 也会触发大量地址空间操作，IntervalVM 的提升对这类场景有直接价值。

**可迁移的设计思路**：
- **区间数据结构 + 锁的统一**：AI 推理系统自研的内存池（如 vLLM 的 block manager）本质上也是区间管理，将锁机制内嵌到数据结构中而非外加粗粒度锁，是值得借鉴的设计模式。
- **per-core arena 策略**：减少多线程 allocator 争用的思路与 jemalloc/tcmalloc 的设计一脉相承，可应用于 AI 框架的内存池设计。

**值得跟进的 future work**：
1. 在 GPU 统一内存（CUDA Unified Memory）场景中，CPU-GPU 协同的地址空间管理是否面临类似的并发瓶颈？IntervalVM 的思路能否扩展到 GPU 驱动的虚拟地址管理（如 `nouveau_uvmm`，论文中已提到但未深入）？
2. 在 LLM 推理引擎中，将 block-level KV cache 管理替换为并发区间跳表，能否在高并发请求下提升内存分配效率？

---

## 八、总结

IntervalVM 提出了第一个实用的可扩展地址空间设计，通过并发区间跳表将映射与锁机制统一，配合两级混合粒度锁、per-core arena 和自适应计数器，实现了 Fault、Alloc、Modify 三类操作的全面并行化。在真实应用上相比 Linux 6.8 获得 1.27–4.53× 的吞吐量提升，且对非 VM 密集型负载几乎无额外开销。主要局限在于 `fork` 性能退化约 20%、对未经测试的文件系统仍退化为全局锁，以及实际上游内核接受的工程难度。
