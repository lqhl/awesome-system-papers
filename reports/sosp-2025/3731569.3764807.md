# Scalable Address Spaces using Concurrent Interval Skiplist

## 论文基本信息

- **标题**: Scalable Address Spaces using Concurrent Interval Skiplist
- **作者**: Tae Woo Kim, Youngjin Kwon, and Jeehoon Kang
- **会议**: SOSP 2025
- **Session**: OS Memory Management
- **PDF**: 3731569.3764807.pdf
- **奖项**: 无

## 研究背景

操作系统内核的虚拟内存管理系统通过地址空间（address space）管理进程的虚拟内存，其核心操作包括三类：Fault 操作（页错误处理）、Alloc 操作（通过 mmap() 分配地址区间）和 Modify 操作（通过 munmap()/mprotect() 修改映射）。这些操作在现代多核系统上面临严重的可扩展性瓶颈。

在 Linux 内核中，这些操作被一个粗粒度锁——mmap_lock（读写锁）——序列化。虽然 Linux 6.8 引入了 per-VMA 锁，允许 Fault 操作与 Alloc/Modify 操作并行执行，但 Alloc 和 Modify 操作本身仍然必须获取 mmap_lock 的写锁，导致它们在高并发场景下被串行化。这一问题早已被业界认识到——mmap_lock 被 LWN（Linux Weekly News）描述为"内存管理子系统中最难解决的竞争点之一"。

实际测量表明，这个问题在现代多核系统上非常严重。在双路 48 核机器上，Apache Web 服务器在 96 线程时浪费了高达 90% 的执行时间等待 mmap_lock；LevelDB 浪费 40%、Metis MapReduce 框架浪费 60%、Psearchy 文本索引浪费 41%。即使 Linux 6.8 已支持 per-VMA 锁，这些应用的 mmap_lock 竞争仍然显著。

已有的研究努力包括：RadixVM（基于 sv6 研究内核的实现，唯一能并行化 Alloc 和 Modify 的方案）、Linux per-VMA 锁、以及多项 range locking 的内核补丁。然而这些方案要么不实用（如 RadixVM 依赖的 radix tree 不适合 RCU、需要简化的启发式分配策略导致地址空间快速耗尽、使用 per-page 元数据造成巨大内存开销），要么无法充分并行化操作。

## 要解决的问题

**核心问题**：如何设计一个实用且可扩展的地址空间方案，能够并行化 Fault、Alloc 和 Modify 操作，同时兼容真实内核的实现约束（RCU 支持、合理的内存开销、生产级可靠性）？

具体挑战包括：
1. **动态锁定区间**：操作所需的锁定范围与地址映射的动态状态相关，而非操作本身的固定范围。
2. **可扩展的 RCU-safe 区间更新**：现有树结构（如 radix tree）在区间跨多节点时，RCU 更新代价高昂。
3. **全局操作**：fork()/exit() 等操作需要遍历整个地址空间，需要高效的全局锁定机制。
4. **Alloc 策略竞争**：传统 first-fit 策略导致所有并发 Alloc 在同一位置竞争。
5. **资源限制**：全局资源计数器的同步和 cacheline bouncing 限制。

## 核心贡献

- **Concurrent Interval Skiplist**：一种新的并发区间数据结构，将映射功能与锁定机制统一集成，支持并行区间操作的 RCU-safe 无锁遍历。与现有基于红黑树或 B 树（maple tree）的方案不同，通过 node-granular 锁定和 read-copy-update（RCU）风格的原子交换，实现跨多个连续节点的原子更新。
- **两层混合粒度锁定**：提出 GR/GW/LR/LW 四种锁定模式，通过 per-core 锁实现本地锁，通过 interval skiplist 的 interval lock 实现范围锁，两者结合实现高效的全局锁定。
- **可扩展 Alloc 策略**：per-core arenas（将地址空间分为多个 64GiB 的 per-core arena）+ separator node 分层 skiplist 组织，减少分配竞争。
- **自适应资源限制计数器**：结合 percpu_counter 缓冲和直接全局更新的自适应策略，在 93.75% 利用率前使用 per-core 缓冲，此后才直接更新全局计数器，实现严格限制实施与高吞吐率的兼得。
- **Linux 6.8.0 完整实现**：约 10K 行代码，完全兼容 POSIX 接口，对应用程序透明无需修改。

## 主要研究方法

**挑战识别**：论文首先系统性地分析了现有地址空间设计的五个可扩展性挑战，这些挑战在此前的工作中未被完整讨论。

**数据结构和算法设计**：基于 Harris 的 lock-free linked list 扩展到 interval skiplist，引入 LOCKED 和 INVALIDATED 标志位支持 node-granular interval locking 和 RCU-safe 的 Swap 操作。

**形式化正确性**：提供了 Lock 操作的正确性引理（Lemma B.1 和 Lemma B.2）和 Swap 操作的线性化点证明。

**完整系统实现**：在 Linux 6.8.0 上实现约 10K 行代码，通过 Linux Test Project 全部测试，额外使用 KASAN 进行压力测试。

**多平台评估**：在双路 Intel Xeon Gold 6248R（48 核）和单路 AMD EPYC 7543（32 核）两种架构上分别评估。

## 设计与实现

**Concurrent Interval Skiplist**（核心数据结构）：

接口包括标准的 Query(start, end, value)、Map(start, end, value)、Alloc(start, end, length, value)，以及新增的 Lock(start, end)、Unlock(start, end) 和 Swap(start, end, nodes)。

```
Node 结构：
- start, end: 区间边界
- height: 节点层高（随机决定）
- next[MAX_HEIGHT]: 原子指针数组（每层一个）

Lock 操作：
- 在 level-0 锁定所有与目标区间重叠的节点及其前驱
- 使用 CAS 设置 LOCKED 标志位
- 处理动态前驱变化（其他线程的并发插入）

Swap 操作（原子替换跨区间节点）：
- 锁定所有旧节点
- 新节点准备：继承或调整 height
- 通过前驱的 level-0 指针的 CAS 实现原子替换
- 旧节点标记 INVALIDATED（对 Query 可见但对更新操作不可达）
```

**锁粒度策略**：

论文提出两层混合粒度锁定，替代单一粗粒度锁：

- **GR（Global Read）**：读取所有 per-core 锁，适用于 fork()/exit() 等需要遍历整个地址空间的操作
- **GW（Global Write）**：写入所有 per-core 锁，适用于不支持细粒度锁的文件系统操作
- **LR（Local Read）**：仅获取本核心的 per-core 锁，适用于本地操作
- **LW（Local Write）**：获取本核心 per-core 锁 + interval skiplist interval lock，适用于大多数 Alloc/Modify 操作

每种操作首先尝试 LR/LW（最快路径），失败时回退到 GR/GW（兜底路径）。

**可扩展 Alloc 策略**：

- **Per-core Arenas**：将地址空间的一小部分（小于 4%，x86-64 上约 256TiB 可用地址空间中分配 128 × 64GiB = 8TiB）划分为 64GiB 的 per-core arenas
- **Separator Node 分层**：separator node 具有不低于阈值的固定高度，确保高层 skiplist 连接不同 arena，使跨 arena 的分配不会相互干扰
- **分配提示（Hint）**：每个 arena 维护一个分配提示指针，指向最后成功分配的位置；munmap() 后提示向后移动优先复用已释放区域
- **分配流程**：优先在自身 arena 分配，arena 满后回退到共享非 arena 区域

**自适应资源限制计数器**：

- 使用 percpu_counter 缓冲 per-core 更新
- 每当缓冲达到 batch size（全局限制 / 16 / 核心数）时刷新到全局计数器
- 当剩余 margin 小于 batch_size × 核心数时，停止使用 percpu_counter，直接更新全局计数器
- 临界值约在全局限制的 93.75% 处触发切换

**Fault 操作处理**（三级降级）：

1. **无需地址空间锁**：直接处理（现代 Linux 6.8 的默认路径）
2. **LR + interval lock**：获取本核心 per-core 锁 + 目标区间的 interval lock（页表分配、元数据更新等需要同步时）
3. **GR**：回退到原始方法，获取所有 per-core 锁（罕见场景，如未适配的文件系统）

## 主要实验结果

**数据结构微基准测试**（用户空间，48 核 Intel）：

| 操作 | Maple Tree 延迟 | Interval Skiplist 延迟 | 提升 |
|------|--------------|---------------------|------|
| Query | 基准 | +35% | 略差 |
| Alloc | 基准 | -4%（更快）| 4% 改善 |
| Map | 基准 | -49%（更快）| 显著改善 |

吞吐量方面：Query 峰值 0.77x（略低），Alloc 峰值 22.9x（显著提升），Map 峰值 5.28x（显著提升）。maple tree 完全无法扩展（受全局锁限制），interval skiplist 随核心数线性扩展。

**地址空间微基准测试**（LMbench）：

| 测试 | Linux | IntervalVM | 开销 |
|------|-------|-----------|------|
| fork+exit | 271 μs | 330 μs | +21.6% |
| page fault | 0.200 μs | 0.206 μs | +3.2% |
| mmap+fault+munmap | 6675 μs | 6890 μs | +3.2% |
| ctxsw 2p/0k | 3.55 μs | 3.48 μs | -2.0% |

关键观察：fork/exit 延迟因遍历时间更长而增加（maple tree 每个节点存储多个 key-value 对，访问节点数更少），但这是以牺牲并行扩展性为代价的。page fault 延迟增加因 Query 操作的 35% 延迟开销，但 mmap+fault+munmap 总延迟仅增加 3.2%，说明优化的收益大于开销。

**吞吐率**（Alloc 基准测试）：
- IntervalVM 峰值：13.1x 加速（vs Linux）；1.07x（vs RadixVM）
- IntervalVMw/o Arena 和 IntervalVMw/o Per-core Stats 均无法有效扩展，验证了两项优化的必要性
- Alloc + Fault + Modify 基准测试：IntervalVM 峰值 10.4x（vs Linux），5.22x（vs RadixVM）

**真实应用评估**（多核可扩展性）：

| 应用 | 提速倍数 | 相比 RadixVM |
|------|---------|-------------|
| Apache（单进程）| 4.53x | — |
| Apache（默认配置）| 3.19x | — |
| LevelDB | 4.49x | — |
| Metis MapReduce | 1.47x | 1.18x |
| Psearchy | 1.27x | — |

消融分析表明，Fault、Alloc 和 Modify 三项优化的并行化都是 Apache 在多线程场景下达到峰值吞吐的必要条件——禁用任一项都会显著限制可扩展性。

**LMbench 延迟开销**（值得关注的负面结果）：
fork+exit 增加 21.6%（因遍历时间增加）、mmap+fault+munmap 增加 3.2%（因 Query 延迟增加）。论文认为这一开销"margin"但值得，因为多核性能收益远大于单次操作延迟开销。

**PARSEC 基准测试**：
VM 密集型工作负载（dedup 1.32x、vips 1.16x）有明显提升；非 VM 密集型工作负载性能差异在 2% 以内，证明 IntervalVM 对非 VM 密集应用无负面影响。

## 潜在问题 / 局限性

**1. fork()/exit() 性能退化不可忽视**：
IntervalVM 将 fork+exit 延迟增加了 21.6%（从 271μs 到 330μs）。fork 是许多服务器应用的常见操作（如 fork-exec 模式、nginx/Apache 的进程创建），这一退化在高频 fork 场景（如微服务容器化环境）下可能成为瓶颈。论文以"margin overhead"一笔带过，但未提供在实际 fork 密集工作负载下的端到端性能评估。

**2. Query 操作性能反而下降**：
interval skiplist 的 Query 操作延迟比 Linux 的 maple tree 高 35%，峰值吞吐率仅为 maple tree 的 0.77x。这是设计上的根本权衡——skiplist 的 O(log n) 遍历涉及多层指针追逐，而 maple tree 的宽节点（10-16 个 key-value 对/节点）更好地利用了缓存局部性。论文通过指出"Alloc 和 Map 是当前的主要瓶颈"来辩护这一权衡，但随着 mmap_lock 竞争被解决，Query 性能可能成为新的瓶颈。

**3. RadixVM 比较存在不公**：
论文禁用了 RadixVM 的 per-core pagetable 和 core-tracking shootdown 功能（因为"这些功能引入了阻止宏基准测试可靠运行的显著 bug"），但这些功能可能对 RadixVM 在某些场景下的性能至关重要。此外 RadixVM 基于 sv6 研究内核而非 Linux，其鲁棒性和生产适用性本就存疑。以此为基准可能高估了 IntervalVM 的相对改进。

**4. 未支持的文件系统操作**：
部分 madvise flags（如 MADV_FREE、MADV_DONTNEED 以外的）和非标准操作仍然依赖全局锁（GR/GW）。论文认为"容易扩展"，但缺乏实际实现和评估，可能在未来成为限制。

**5. Per-core Arenas 的地址空间消耗**：
128 × 64GiB = 8TiB 的 per-core arenas 占用了 256TiB x86-64 可用地址空间的约 4%。虽然论文认为"可接受"，但对于地址空间受限的场景（如 32 位系统或特定 ASLR 配置），这一开销可能不可忽视。

**6. RCU 垃圾回收延迟**：
interval skiplist 使用 RCU 进行无锁遍历和原子更新，但旧节点的回收依赖于 RCU 宽限期（grace period）。在 Linux 中，RCU 宽限期可能需要数毫秒，在此期间旧节点内存无法释放。对于频繁分配/释放 VMA 的工作负载（如高频率 mmap/munmap），RCU 垃圾回收可能积累大量待释放内存。

**7. 仅在单一 NUMA 配置上测试**：
论文主要在双路 Intel（NUMA 节点 = 2）上评估，未在更多 NUMA 节点（如 4 节点 AMD EPYC）上验证 per-core arenas 和资源限制计数器的扩展性。

## 未来工作

- **隐藏瓶颈探索**：分析地址空间锁定被解决后暴露的新瓶颈。

## 个人评注

**总体评价**：这是一篇工程深度和理论贡献兼备的优秀论文，探讨了一个 Linux 内核领域长期悬而未决的问题——mmap_lock 的竞争。论文的核心贡献——concurrent interval skiplist——在算法层面（统一映射与锁定、node-granular interval locking）和系统层面（两层混合粒度锁定、per-core arenas、自适应计数器）都有实质性的创新。

**亮点**：
1. **挑战识别的完整性**：论文识别并分析了五个此前未被完整讨论的可扩展性挑战（动态锁定区间、RCU-safe 区间更新、全局操作、Alloc 策略竞争、资源限制），这些分析为后续研究提供了重要的参照。
2. **工程完整性**：在 Linux 6.8.0 上实现约 10K 行代码，通过 Linux Test Project 测试，提供了开源代码（https://github.com/kaist-cp/interval-vm.git），展示了研究级原型到生产级实现的桥梁。
3. **与 RadixVM 的批判性比较**：论文不仅指出 RadixVM 的不足，还详细分析了其根本原因（radix tree 不适合 RCU、per-page 元数据开销、简化启发式的地址空间耗尽问题），为该领域的后来者提供了重要的经验教训。

**不足**：
论文最大的遗憾是 Query 操作性能的下降。这是一个根本性的权衡——skiplist 的 O(log n) 结构天然不如扁平化的 B 树（maple tree）友好。如果未来应用的工作负载发生变化（从 Alloc/Modify 密集转向 Query 密集），IntervalVM 的性能可能反而不如 Linux 原生实现。此外，fork/exit 的 21.6% 延迟增加在某些场景下可能是不可接受的代价，需要更细致的工作负载依赖性分析。

**对领域的影响**：Concurrent interval skiplist 的设计——将功能数据结构与同步机制统一集成——可能对其他内核并发数据结构的设计有启发意义。其 node-granular locking + RCU 的组合模式，或可推广到文件 inode 锁、块设备请求队列等其他存在粗粒度锁瓶颈的内核子系统中。
