# µFork: Supporting POSIX fork Within a Single-Address-Space OS

**作者**：John Alistair Kressel（University of Manchester）、Hugo Lefeuvre（University of British Columbia）、Pierre Olivier（University of Manchester）
**会议**：SOSP '25（ACM SIGOPS 31st Symposium on Operating Systems Principles，2025年10月）
**DOI**：https://doi.org/10.1145/3731569.3764809
**源文件**：[3731569.3764809.pdf](../../papers/sosp-2025/3731569.3764809.pdf)

---

## 一、背景

单地址空间操作系统（Single-Address-Space OS，SASOS）将 OS 内核与所有用户程序共置于同一地址空间，从而获得显著的轻量化收益：无需页表切换的快速上下文切换、低延迟的安全域切换、极低的内存占用等。早期的 SASOS（如 Opal、Mungi）利用这一设计简化了进程间通信。近年来，随着云计算（Function as a Service、边缘计算、机密计算）的兴起，以 Unikraft 为代表的现代 unikernel 型 SASOS 再度受到关注，它们通过消除用户/内核隔离层进一步压缩开销。

然而，SASOS 一直难以进入主流——核心障碍是对多进程 POSIX 应用的支持缺失。研究显示，GitHub 上最受欢迎的 50 个 C 语言仓库中有 46%、最流行的 50 个 Debian 软件包中有 50% 依赖 `fork`。

---

## 二、要解决的问题

**根本矛盾**：POSIX `fork` 的语义要求为子进程创建一个独立地址空间，而 SASOS 的设计原则是只有一个地址空间——两者在定义上不兼容。

现有方案均存在明显取舍：

| 方案 | 代表系统 | 问题 |
|------|---------|------|
| 段相对寻址 | Angel、Mungi | 需大幅修改编译器和工具链，现代系统几乎不可行 |
| OS-as-a-process（依赖 hypervisor/host fork） | Nephele、KylinX、Graphene | 重新引入多地址空间，丧失 SASOS 轻量化优势 |
| 放弃隔离 | OSv、Junction | 安全性不可接受 |
| SASOS 内部引入多页表 | Iso-Unik | 同样损失轻量化 |

因此，业界缺乏一个同时满足以下四项目标的方案：
- **(R1) 轻量 fork**：不重新引入多地址空间，保持快速 IPC、低延迟上下文切换和低内存占用；
- **(R2) 透明兼容**：应用无需修改；
- **(R3) 强隔离**：µprocess 间及 µprocess-kernel 间的隔离等同于传统 POSIX 进程；
- **(R4) 灵活性**：适配不同 SASOS 的信任模型和设计目标。

## 三、核心设计

µFork 提出在单一地址空间内模拟 POSIX 进程（称为 **µprocess**），通过将父 µprocess 的内存复制到地址空间中的另一位置来实现 `fork`。这带来两个核心挑战：

**挑战 C1：绝对内存引用的重定位**
子进程内存复制后，其中指向父进程内存区域的绝对指针必须重定向到子进程自身区域。在运行时可靠识别"哪个内存位置是指针"是个难题——普通整数可能被误判为指针。

**挑战 C2：单地址空间内的隔离**
传统进程依赖独立页表实现隔离，SASOS 中必须用其他机制在同一地址空间内隔离 µprocess。

### 六大设计构件

1. **µprocess 抽象**：每个线程关联一个 µprocess ID（PID），fork 创建新 PID 的新线程，语义与 POSIX 一致。

2. **CHERI 实现隔离（C2）**：利用 CHERI 硬件能力（capability）的单调性——能力的权限和内存边界只能缩小不能扩大，µprocess 无法伪造更高权限的能力来访问其他进程内存。

3. **CHERI 标签识别指针（C1）**：CHERI 为每个内存位置维护一个不可伪造的单比特 tag，指针存在时 tag 有效。fork 时扫描子进程内存中 tag 有效的位置即可准确识别所有绝对引用，并将其重定位到子进程区域。

4. **位置无关代码（PIC）减少重定位量**：将应用编译为 PIC/PIE 后，绝大多数内存引用相对于栈指针、基指针或程序计数器（PC），无需重定位；只有极少数绝对引用需要处理。

5. **Copy-on-Pointer-Access（CoPA）**：标准 Copy-on-Write（CoW）无法直接用于 µFork——子进程以读模式访问含绝对引用的页面时，也必须触发拷贝并重定位，否则子进程会使用仍指向父进程的过期指针。
   - 朴素方案：Copy-on-Access（CoA）——任何访问都触发拷贝。
   - 优化方案：**CoPA**——仅在以下两种情况触发拷贝：（a）父或子对页面执行写操作；（b）子进程从页面加载一个能力（指针）。CoPA 利用 CHERI 提供的页表扩展位（capability-load fault），在加载指针时触发 fault，无需扫描整页。非指针的读访问则允许共享，大幅减少不必要的复制。

6. **参数化隔离**：针对不同信任模型（对抗型 vs. 非对抗型），可选择性启用/禁用 TOCTTOU 保护和 kernel 数据校验，兼顾安全与性能。

### 内存布局

内核和应用以 PIC/PIE 编译，每个 µprocess 被分配连续的虚拟地址区域。全局偏移表（GOT）位于各 µprocess 区域内，fork 时主动拷贝 GOT 并更新其中的绝对引用，确保符号查找正确。

## 四、实现细节

- **基础平台**：Unikraft unikernel + ARM Morello 开发板（CHERI 硬件实现）。
- **对 Unikraft 的改造**：
  - 新增 per-µprocess 内核状态：文件描述符表、task struct、PID、调度器支持、per-µprocess 堆。
  - 通过 linker script 区分应用代码和内核代码，将两者置于连续虚拟地址区域。
  - 系统调用通过 sealed kernel code capability 实现无陷阱（trapless）调用（EL1 级别执行，利用 CHERI system permission bit 防止 µprocess 执行特权指令）。
- **CoPA 实现**：CHERI 的 capability-load-fault 页表位，触发 fault 后：①将子页表项指向空闲物理页；②拷贝物理页；③以 16 字节（CHERI capability 大小）步长扫描新页，重定位所有有效 tag 的引用。
- **TOCTTOU 防护**：内核在检查和使用用户传入指针前，先将其复制到内核内存，防止并发修改。
- **SMP 支持**：Unikraft 当前以"big kernel lock"实现 SMP，应用代码可并发执行，内核代码串行化。

## 五、实验结果

**平台**：ARM Morello 开发板（4 × ARM v8.2-A @ 2.5GHz，16GB RAM）。µFork 运行于 bhyve hypervisor 之上，CheriBSD 23.11 裸机运行（给予 CheriBSD 保守优势）。Nephele 仅有 x86_64 实现，以其论文数据为参考。

### Fork 延迟与内存（微基准，Hello World）

| 系统 | Fork 延迟 | 内存/进程 |
|------|---------|---------|
| µFork | 54 µs | 0.13 MB |
| CheriBSD | 197 µs | 0.29 MB |
| Nephele | 10.7 ms | 1.60 MB |

µFork 比 CheriBSD 快 **3.7×**，比 Nephele 快 **198×**，内存分别节省 **2.2×** 和 **12.3×**。

### Redis 快照（数据库保存）

| 数据库大小 | µFork 存储时间 | CheriBSD 存储时间 | 加速比 |
|-----------|-------------|----------------|--------|
| 100 KB | 1.8 ms | 3.4 ms | 1.9× |
| 100 MB | 109 ms | 158 ms | 1.4× |

CoPA vs CoA vs 全量同步拷贝（100 MB 数据库）：

| 策略 | Fork 延迟 | 内存消耗 |
|------|---------|---------|
| 全量同步拷贝 | 23.2 ms | 144 MB |
| CoA | 283 µs | 101 MB |
| CoPA | 260 µs | 6 MB |

CoPA 将 fork 延迟压缩至同步拷贝的 **1/89**，内存降至 **1/24**。

### FaaS 函数吞吐（Zygote 预热 + MicroPython）

- 单核：µFork 函数吞吐比 CheriBSD 高 **24%**（fork 延迟驱动）
- TOCTTOU 保护开销可忽略（实验不涉及密集系统调用）

### Nginx 多 Worker

- 受 Unikraft SMP 成熟度限制，µFork 仅能稳定运行单核
- 单核限制下，µFork 比单核 CheriBSD 吞吐高 **9%**
- TOCTTOU 保护开销约 **6.5%**

### IPC（Unixbench Context1，100K 轮次管道）

- µFork：245 ms，CheriBSD：419 ms（得益于无陷阱系统调用）

## 六、批判性分析

**1. CHERI/Morello 平台的成熟度问题被轻描淡写**
论文承认 CHERI/Morello 硬件软件栈尚不成熟，在 pure-capability 模式下存在不可忽视的性能开销，并引用分析称"未来硬件可将开销降至 1.8-3%"。但实验中 µFork 并非裸机运行而是运行于 bhyve hypervisor 之上，而 CheriBSD 则裸机运行——这一不对等对比对 µFork 构成不利因素，作者虽然承认这点，却反称这给了 CheriBSD"保守优势"。实际上，这使所有绝对性能数字的解读都需要打折扣。

**2. 静态堆是一个严重的实用性限制**
每个 µprocess 拥有一个静态分配的固定大小堆，这大幅简化了 CHERI capability 边界管理，但也意味着在编译时就必须确定每个进程的最大内存需求——对真实应用场景（尤其是 Redis 这类内存数据库）并不现实。论文在实验时将 Redis 数据库尺寸人为设置为适配静态堆，这使得 CoPA 的内存节省数字（6MB vs 101MB）同时也反映了静态堆带来的膨胀，而非真实 CoPA 效率。

**3. Nginx 评估不完整**
SMP 问题导致 Nginx 多核数据无法呈现，论文仅展示单核结果。而 Nginx 使用 fork 的核心场景恰恰是多核并发——这个实验实际上未能验证 µFork 在最典型 fork 使用场景（R2+R3 多进程 web 服务）下的真实竞争力。将"展示兼容性"作为实验目标而非性能，掩盖了这一不足。

**4. 未评估真实特权分离场景**
论文列举了 fork 的六大使用模式（U1-U6），其中 U3（特权分离，如 OpenSSH、qmail）是最具安全价值的场景。但实验仅覆盖了 U2+U4（Redis）、U2+U5（FaaS/Zygote）、U5（Nginx），对安全隔离实际效果未做端到端评估。

**5. Morello 专用性**
CoPA 依赖 CHERI 特有的 capability-load fault 机制，论文在讨论中承认"没有其他已知机制可以实现 CoPA"——这意味着整个方案高度依赖 CHERI 硬件生态，而 CHERI 目前仅有学术/早期商业实现，短期内无法移植到主流服务器平台。

---

## 七、总结

µFork 是首个在真正单地址空间 OS 中支持完整 POSIX `fork` 语义的方案，同时保持了 SASOS 的轻量化优势和强进程隔离。其核心创新是将 CHERI 的硬件内存标签和 capability 机制分别用于解决绝对内存引用重定位（Copy-on-Pointer-Access）和进程间隔离两大挑战。原型基于 Unikraft + ARM Morello，在 fork 延迟（54 µs，3.7× 快于 FreeBSD/CHERI）、内存效率和 FaaS 吞吐上均显著优于现有方案。

主要局限在于：深度依赖 CHERI 专用硬件（短期可移植性差）、静态堆限制了实际部署灵活性、SMP 成熟度不足制约了多核并发场景的完整评估，以及基于 hypervisor 运行与 CheriBSD 裸机运行的基准对比存在系统性不公平。这项工作适合对 SASOS/unikernel 有实际需求（如 FaaS、机密计算）且愿意采用 CHERI 平台的场景，对于主流服务器部署仍需等待 CHERI 生态成熟。
