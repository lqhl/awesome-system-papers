# µFork: Supporting POSIX fork Within a Single-Address-Space OS

**作者**：John Alistair Kressel (The University of Manchester), Hugo Lefeuvre (The University of British Columbia), Pierre Olivier (The University of Manchester)
**会议**：SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
**链接**：https://doi.org/10.1145/3731569.3764809
**源文件**：[[3731569.3764809.pdf]]

---

## 一、背景

单地址空间操作系统（SASOS）将 OS 内核与所有用户程序放置在同一个地址空间中，从而获得轻量化优势：优化的上下文切换、快速的安全域转换、低内存开销以及高效的 IPC。早期的 SASOS（如 Opal、Mungi）利用这一设计简化进程间通信和协调。近年来，随着虚拟化技术的发展，unikernel 等现代 SASOS 在 FaaS、边缘计算和机密计算等高性能低资源消耗领域日益流行。

然而，SASOS 面临一个根本性障碍：无法支持大量使用 POSIX fork 的多进程应用程序。fork 是 POSIX 系统中最古老且最普遍的进程创建机制，46% 的 GitHub 上最流行的 C 仓库和 50% 的最流行 Debian 包都使用了 fork。Redis、Nginx、OpenSSH、Apache httpd、qmail 等广泛使用的应用程序都依赖 fork 实现并发、隔离、copy-on-write 快照等关键功能。

---

## 二、要解决的问题

SASOS 的核心设计——单一地址空间——与 fork 的语义根本冲突：fork 要求为子进程创建一个新的地址空间，而 SASOS 只有一个地址空间。

现有解决方案均存在明显缺陷：

1. **段相对寻址方案**（Angel、Mungi）：需要所有内存引用相对于基址寄存器，但现代编译器和工具链无法完整支持，需要大量修改编译器、JIT 运行时和手写汇编。
2. **OS-as-a-process 方案**（Nephele、KylinX、Graphene）：通过虚拟化/宿主机实现 fork，但重新引入了多个地址空间，丧失了 SASOS 的轻量化优势。
3. **Iso-Unik 方案**：在 SASOS 中引入页表重新实现多地址空间，同样损害轻量性。
4. **仅支持 fork+exec**（OSv、Junction）：只覆盖 fork 的部分用例，且有的方案放弃了进程隔离。

核心挑战在于：如何在单一地址空间内实现完整的 POSIX fork 语义，同时保持轻量性、隔离性和透明性？

---

## 三、洞察与设计

**关键洞察**：在单一地址空间中 fork 子进程的内存必须位于不同位置，因此需要重定位子进程中指向父进程内存的绝对引用（指针）。CHERI 硬件的 tagged memory 机制能够在运行时可靠地识别内存中的所有指针（每个指针都有一个硬件设置的 validity tag），从而高效地完成指针重定位；同时 CHERI 的 capability 机制提供了轻量级的地址空间内隔离，无需引入多个地址空间或昂贵的特权级切换。

基于这一洞察，µFork 的设计包含六个核心构建块：

1. **µprocess 抽象**：每个线程关联一个 µprocess ID，fork 创建新线程并分配新 PID，语义等同于 POSIX fork。
2. **CHERI capability 隔离**：利用 CHERI 的 capability bounds 将每个 µprocess 限制在其专属内存区域内，实现地址空间内的进程隔离。
3. **CHERI tag 重定位**：fork 时扫描子进程内存，通过 CHERI tag 识别绝对内存引用，将其重定位到子进程的内存区域。
4. **Position-Independent Code（PIC）**：大多数内存引用相对于栈/基址/程序计数器，无需重定位，减少 fork 开销。
5. **Copy-on-Pointer-Access（CoPA）**：传统 CoW 无法直接用于 µFork（子进程读取包含绝对引用的页也需要触发拷贝和重定位）。µFork 提出 CoPA 优化——内存可以以只读模式共享，仅当子进程加载指针或任一进程写入时才触发页拷贝，非指针的读操作不触发拷贝。
6. **参数化隔离**：根据不同威胁模型（对抗性隔离、非对抗性故障隔离、无隔离）提供可配置的隔离级别。

## 四、实现细节

µFork 基于 Unikraft SASOS 实现，运行在 ARM Morello 平台上的 CHERI 硬件，使用 bhyve 虚拟机管理程序运行于 CheriBSD 之上。

**核心实现**：
- **代码量**：共修改 7 KLoC 内核代码——4,230 LoC 用于 CHERI 和 bhyve 支持，3,000 LoC 用于 µFork 本身
- **CHERI 移植**：将 Unikraft 移植到 CHERI pure-capability 模式，关键修改包括早期引导代码初始化 CPU capability 特性、虚拟内存分配器适配 CHERI 16 字节指针对齐、内核代码中指针算术替换为显式指针操作
- **CoPA 实现**：利用 CHERI 额外的页表权限位，当子进程从共享页加载 capability 时触发 fault，执行三步操作：(1) 更新子进程页表指向新物理页，(2) 拷贝页内容，(3) 以 16 字节为步长扫描页面，通过 CHERI tag 识别并重定位绝对引用
- **µprocess 间隔离**：基于 CHERI capability 的单调性（bounds 只能缩小不能扩大）确保 µprocess 无法伪造越界 capability；CoPA 确保所有可能泄露 capability 的场景都触发拷贝和重定位
- **µprocess-内核隔离**：通过 sealed capability 实现无 trap 的系统调用入口；利用 CHERI system permission bit 阻止用户代码执行特权指令；内核验证并拷贝用户传入的缓冲区防御 TOCTTOU 攻击
- **内存布局**：每个 µprocess 拥有连续的虚拟地址空间区域，包含私有的静态堆（build-time 可配置大小）、独立的 GOT 表

**SMP 支持**：Unikraft 当前使用"大内核锁"支持 SMP，应用代码可并发但内核代码串行化执行，完整 SMP 优化正在社区开发中。

## 五、实验结果

实验平台：ARM Morello 开发板，4 核 ARMv8.2-A @ 2.5GHz，16GB RAM。对比系统：CheriBSD（原生 pure-capability 模式）和 Nephele（基于 VM 的 fork）。

### 微基准测试

| 指标 | µFork | CheriBSD | Nephele |
|------|-------|----------|---------|
| fork 延迟（hello world） | **54 µs** | 197 µs (3.7×) | 10.7 ms (198×) |
| 每进程内存占用 | **0.13 MB** | 0.29 MB (2.2×) | 1.6 MB (12.3×) |
| Unixbench Spawn（1000次 fork+exit） | **56 ms** | 198 ms | - |
| Unixbench Context1 IPC（100k 交互） | **245 ms** | 419 ms | - |

### Redis 快照

| 数据库大小 | µFork save time | CheriBSD save time | 加速比 |
|-----------|----------------|-------------------|--------|
| 100 KB | 1.8 ms | 3.4 ms | 1.9× |
| 100 MB | 109 ms | 158 ms | 1.4× |

- fork 延迟方面 µFork 比 CheriBSD 快 5-10×
- CoPA vs. 全拷贝：fork 延迟降低最高 89×；CoPA vs. CoA：延迟降低最高 1.18×
- 内存消耗：100MB 数据库下 µFork 仅 6 MB vs CheriBSD 56 MB

### FaaS（MicroPython Zygote）

- µFork 函数吞吐量比 CheriBSD 高 **24%**（得益于更低的 fork 延迟）
- TOCTTOU 保护开销可忽略

### Nginx 多 Worker

- 受限于 Unikraft 的 SMP 支持不成熟，µFork 仅在单核上测试
- 单核下 µFork 比 CheriBSD 高 **9%** 的请求吞吐
- TOCTTOU 保护的吞吐开销为 6.5%

## 六、批判性分析

1. **实验平台的局限性严重影响结论的普适性**：ARM Morello 是一个开发板而非量产硬件，论文自己承认 CHERI/Morello 的纯 capability 模式存在"非 negligible 的开销"，且作者声称未来硬件可将开销降至 1.8-3%——这是一个未经验证的乐观假设。整个评估基于一个 4 核 2.5GHz 16GB 的开发板，与实际生产环境差距巨大。

2. **CheriBSD 虚拟化 vs. 原生的不公平比较**：µFork 运行在 bhyve 虚拟化之上，而 CheriBSD 原生运行。作者声称这给了 CheriBSD "保守优势"，但实际上虚拟化对 µFork 的 I/O 相关测试（如 Nginx）影响可能很大，使得比较结果难以解读。

3. **Nginx 实验不完整**：由于 Unikraft SMP 支持不成熟，Nginx 只能在单核测试。对于一个声称支持 fork 并发（U2）的系统，无法展示多核并发性能是一个重大缺失。作者将此归咎于 Unikraft 而非 µFork，但这仍然意味着当前系统无法真正发挥 fork 并发的优势。

4. **静态堆设计的实用性问题**：每个 µprocess 使用 build-time 配置的静态堆，这对于实际应用（尤其是内存需求动态变化的场景）严重不够灵活。论文中 Redis 全拷贝时 136.7MB 中有 136.7MB 是静态堆，说明这种设计会带来严重的内存浪费。

5. **地址空间碎片化问题被轻描淡写**：每个 µprocess 占用连续的虚拟地址区域，大量 fork 后的碎片化问题只是一句"64位地址空间很大"带过，提出的压缩和 size class 方案都推到了 future work。

6. **CHERI 硬件依赖限制了实际部署**：µFork 的核心机制（tag-based 指针识别、CoPA、intra-address-space 隔离）深度依赖 CHERI。虽然论文讨论了替代方案（其他硬件 memory tagging、shadow memory），但这些替代方案要么需要编译器插桩（性能开销未知），要么无法支持 CoPA 优化，实际可行性存疑。

7. **与 Nephele 的比较不直接**：Nephele 是 x86_64 平台，µFork 是 ARM Morello，两者的数字来自不同硬件和论文，不具备直接可比性。

## 七、AI Infra / MLSys 视角

1. **FaaS 冷启动优化的启示**：µFork 的 Zygote fork 模式——预热一次运行时，fork 出多个实例——与 AI 推理服务中的模型加载优化思路相似。AI 推理框架（如 vLLM、TensorRT-LLM）可以借鉴类似的"fork-from-warm-state"模式来加速多实例部署，尤其是在 FaaS 式的 serverless inference 场景中。

2. **CoPA 对 AI 工作负载的潜在价值**：AI 推理中存在大量只读的模型权重数据，CoPA 的"读数据不拷贝、读指针才拷贝"机制可以有效减少多实例共享模型权重时的内存开销。这与当前 vLLM 等系统中的 KV cache 共享、模型权重共享等优化方向高度吻合。

3. **轻量级进程隔离用于多租户推理**：在多租户 AI 推理场景中，不同用户的请求需要隔离，但传统进程隔离开销太大。µFork 的 µprocess 模型（54µs fork、0.13MB 内存开销）提供了一种极轻量的隔离思路，值得在 AI 推理服务的多租户隔离设计中探索。

4. **值得跟进的方向**：将 µFork 的地址空间内隔离思路应用于 GPU/加速器内存管理（如在单一 GPU 地址空间内隔离多个推理实例），这需要结合 GPU 侧的 capability 或 memory tagging 机制，是一个有挑战但有价值的研究方向。

---

## 八、总结

µFork 提出了一种在单地址空间操作系统中实现完整 POSIX fork 语义的新方法，利用 CHERI 硬件的 tagged memory 实现指针识别与重定位，利用 capability 机制实现轻量级进程隔离，并创新性地提出 Copy-on-Pointer-Access 优化减少内存拷贝。在 ARM Morello 平台上的评估表明，µFork 在 fork 延迟（54µs，比传统 fork 快 3.7×）、内存占用（0.13MB/进程，低 2.2×）和 IPC 性能上均显著优于 CheriBSD 和 Nephele。主要局限在于对 CHERI 硬件的深度依赖（当前仅有开发板级别硬件）、静态堆设计的灵活性不足，以及 SMP 支持不成熟导致多核并发场景未能充分验证。
