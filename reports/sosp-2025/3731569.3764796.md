# Prove It to the Kernel: Precise Extension Analysis via Proof-Guided Abstraction Refinement

**作者**：Hao Sun, Zhendong Su（瑞士联邦理工学院 ETH Zurich）
**会议**：SOSP 2025（ACM SIGOPS 第 31 届操作系统原理研讨会）
**DOI**：https://doi.org/10.1145/3731569.3764796
**源文件**：[3731569.3764796.pdf](../../papers/sosp-2025/3731569.3764796.pdf)

## 一、背景

Linux eBPF 子系统允许用户空间向内核注入专用扩展（extension），广泛用于性能 profiling、安全监控、文件系统管理、自定义调度等场景。Meta 在生产服务器上运行超过一百个 eBPF 扩展，Google、Cloudflare 也大量依赖 eBPF。

由于 eBPF 扩展在内核空间执行，来源却是不可信的第三方，Linux 内核内置了一个静态 verifier，在加载时通过抽象解释（abstract interpretation）分析扩展的所有可能控制流路径，验证内存安全、执行终止、以及合法的内核交互。

verifier 使用 interval domain（跟踪变量值域范围）和 tristate domain（跟踪寄存器每一位的状态）两种轻量抽象域，二者均支持线性时间分析，以满足内核对复杂度和运行时开销的严格约束。

---

## 二、要解决的问题

**核心矛盾**：verifier 的精度不足，导致大量安全 eBPF 程序被错误拒绝（false rejection），严重限制内核可扩展性。

具体问题：

1. **抽象域天生过近似**：interval 和 tristate domain 在每条指令处进行局部过近似（local over-approximation），丢弃精确计算信息。例如，`r2 &= 0xf` 后左移一位，verifier 只能得出 `r2 ∈ [0, 30]`，但实际上最低位恒为 0，只有 16 种可能值。
2. **变量关系无法跟踪**：verifier 不能感知变量间的依赖关系。若两个寄存器来自同一源值，对其中一个施加约束后，另一个的范围不会随之收紧。
3. **开发者负担沉重**：开发者需要借助添加冗余检查、内联汇编、加倍内存分配等 workaround 来绕过 verifier 的误判，例如 Elastic 项目被迫为每个 CPU 核分配 256 KiB 而实际只需 128 KiB。
4. **现有改进的局限**：引入更精确的 Octagon（$O(n^3)$）或 Polyhedra（$O(2^n)$）等抽象域复杂度过高；Zone domain（PREVAIL）虽改进了精度，但增加了 verifier 的复杂度和运行时开销，可能引入新的安全攻击面。

---

## 三、核心设计

**BCF（eBPF Certificate Framework）**：证明驱动的抽象精化（proof-guided abstraction refinement）。

**关键洞察**：不在 verifier 内部引入更复杂的分析，而是将复杂推理解耦到用户空间，通过形式化证明在内核空间验证精化结果的正确性——"证明给内核看"。

整体流程分三步：

**Step 1：精化条件生成（Refinement Condition Generation）**
- 当 verifier 在某条指令处无法继续（检测到潜在越界等安全违规），不直接拒绝，而是触发精化
- 从当前失败点向后进行反向分析（backward analysis），定位目标寄存器的定义起点，仅分析相关后缀（suffix），避免分析整个程序
- 对该后缀做符号跟踪（symbolic tracking），用符号变量精确表示寄存器的所有可能值（如 `r1.off = (sym & 0xf) + (0xf - (sym & 0xf))`）
- 将安全检查的约束条件（如 `r1.off + 1 ≤ 16`）编码为精化条件，发送到用户空间

**Step 2：用户空间证明生成（User Space Proof Generation）**
- 用户空间调用 SMT solver（cvc5）对精化条件求解
- 若条件可满足，生成形式化证明；若不可满足，返回反例，verifier 拒绝该扩展
- 证明以 BCF 二进制格式编码（紧凑的 u32 方案），平均大小 541 字节

**Step 3：内核空间证明检验（Kernel Space Proof Check）**
- verifier 接收证明后，对每条证明规则线性扫描验证（linear time）
- 证明检查器支持 45 条原始规则（Boolean、等式、位向量理论），完备且独立于用户空间工具链
- 验证通过后，verifier 采用精化后的抽象继续分析

**架构图**（简述）：内核空间保持简单高效的抽象解释 + 轻量证明检查器；用户空间负责重量级的 SMT 推理。二者通过 `bpf()` 系统调用的扩展字段（5 个新增字段）和共享 buffer 通信。

## 四、实现细节

| 组件 | 语言 | 代码行数 | 位置 |
|------|------|---------|------|
| Verifier（含 BCF 扩展） | C | 1,663 | 内核空间 |
| Proof Checker | C | 2,337 | 内核空间 |
| uapi（共享接口） | C | 190 | 共享 |
| Loader（bpftool/libbpf 扩展） | C | 349 | 用户空间 |
| Solver（cvc5 扩展） | C++ | 1,837 | 用户空间 |
| **合计** | | **7,366** | |

**关键实现要点**：

- **反向分析**：复用 verifier 已有的 `backtrack_insn()` 例程，用整数掩码维护寄存器集合，通过位操作增删寄存器
- **符号跟踪**：集成到 `do_check()` 分析阶段，仅在精化触发时激活，不影响标准分析路径；借用 verifier 的分支历史（jump history）确定精确路径后缀；当 verifier 的范围信息显示寄存器在 `[u32_min, u32_max]` 内时，将符号变量位宽收窄到 32 位以简化表达式
- **证明格式**：基于 u32 紧凑编码；表达式算符编码在首个 4 字节单元；子表达式通过相对偏移引用；结论由 checker 重新计算，不包含在证明中（减小证明大小）
- **系统调用接口**：仅扩展 `BPF_PROG_LOAD` 命令，新增 5 个字段（`bcf_fd`, `bcf_buf`, `bcf_buf_size`, `bcf_buf_true_size`, `bcf_flags`），无需新系统调用

**已知局限（当前实现）**：
- 栈状态跟踪不完整：仅支持寄存器大小的栈溢出（stack spill），其他大小被保守标记为无界；不影响健全性，因为此类条件无法生成证明
- 新的 solver 证明规则需要对应更新 loader 端的格式转换（内核 checker 保持稳定）

## 五、实验结果

**实验平台**：AMD EPYC 9654 96 核处理器（双线程），756 GiB 内存，Linux v5.15，QEMU 6.2.0 + KVM，最小化 Debian 镜像

**数据集**：512 个真实世界 eBPF 对象，来自 Cilium、Calico、BCC、xdp-project 等 46 个流行项目，用 Clang-13 至 Clang-21、-O1 至 -O3 多种配置编译，大小 0.5~376.2 KiB（均值 118.1 KiB）

### 精度提升

| 指标 | 结果 |
|------|------|
| 原 verifier 接受数 | 0 / 512（数据集定义为全部被误拒） |
| BCF 接受数 | 403 / 512（78.7%） |
| 106 个源程序中全部通过的 | 75 个 |

剩余 109 个未接受的程序原因：
- 精化未触发（rejection point 尚未 instrument）：4 个（0.8%）
- 当前实现的符号跟踪局限导致条件不成立：82 个（16.0%）
- 触达百万指令上限（循环）：23 个（4.5%）

对比 PREVAIL（Zone domain）：因 Windows 特定设计导致兼容性问题，不足 1% 的程序可加载，无有效比较。

### 开销指标

| 指标 | 最小值 | 均值 | 最大值 |
|------|--------|------|--------|
| 精化触发次数 / 程序 | 1 | 446 | 16,048 |
| 符号跟踪指令数 | 7 | 102 | 373 |
| 精化条件大小（字节） | 88 | 836 | 2,128 |
| 证明大小（字节） | 136 | 541 | 46,296 |
| 证明检查时间（μs） | 31 | 48.5 | 1,845 |
| 总分析时长（秒） | 0.7 | 9.0 | 182.0 |

- 内核空间分析占总时间 79.3%，用户空间推理占 20.7%
- 99.4% 的证明小于 4096 字节（一个内存页）
- 平均 102 条指令的符号跟踪后缀，仅占总分析指令数的 3.4%

## 六、批判性分析

**数据集构造存在选择偏差**：
论文的 512 个"被误拒"程序，绝大多数是通过对同一源程序使用不同编译器版本和优化级别生成的变体，而非真正在野的被拒程序（手工收集到的仅 9 个）。这种编译器多样性驱动的方法虽然合理，但生成的 bytecode 模式未必代表真实用户遇到的典型被拒场景。尤其是部分拒绝点可能专门因为 Clang 某些版本产生的特定指令序列才触发，对一般用户的实际体验提升有多大，论文缺乏说明。

**与主要竞争对手的对比严重不足**：
PREVAIL 是最相关的比较基准（同样针对 verifier 精度问题），但论文以"Windows 特定设计的兼容性问题"为由，放弃了有效对比（不足 1% 可加载）。这个理由可疑——一篇声称显著提升精度的论文，理应花更多工程努力完成公平比较，或至少选取能运行的子集做对比。

**平均 9 秒的加载时间被轻描淡写**：
论文声称"加载时间开销可接受，且仅在加载时发生一次"，但最大 182 秒的分析时间对于需要动态加载 eBPF 程序的场景（如 Kubernetes 容器启动时的安全策略加载）是显著瓶颈。论文提出的缓存方案（证明随扩展一起分发）虽然合理，但缓存命中率、缓存失效策略等均无实验支撑。

**精化触发次数最大 16,048 次**：
均值 446 次精化/程序，最大 16,048 次，且论文将极端值归因于循环展开——这表明对循环密集型程序，BCF 的效果会显著退化，而循环恰恰是复杂 eBPF 程序的常见模式（如 XDP 中的包处理循环）。论文将循环支持列为 future work，但未讨论这在实践中影响多大比例的程序。

**16% 的失败归因于"工程问题"存疑**：
82 个程序（16%）因实现局限（主要是栈状态跟踪不完整）而生成的精化条件不成立（solver 返回反例）。论文声称这些都可通过进一步工程努力解决，但栈溢出在复杂 eBPF 程序中普遍存在，这并非小问题。论文未定量分析这些失败案例中有多大比例涉及栈操作。

**soundness 依赖 SMT solver 的正确性**：
BCF 的安全性建立在 cvc5 solver 生成正确证明的假设上，以及内核证明检查器的实现正确性上。尽管 checker 仅 2337 行且逻辑较简单，但一旦 checker 有 bug，攻击者可构造恶意 eBPF 程序配合伪造证明绕过 verifier——这一安全风险在论文中几乎未被提及。

---

## 七、总结

BCF 提出了一种巧妙的架构分离思路：将 eBPF verifier 的精度提升问题转化为"内核做轻量证明检查，用户空间做重量级 SMT 推理"的协作模式，在不增加内核复杂度的前提下，将真实世界 512 个被误拒的安全程序中的 78.7% 成功接受。实现相对紧凑（7,366 行），无需新系统调用，对标准分析路径无影响。

主要局限：对循环密集型程序效果有限；栈状态跟踪尚不完整；与最相关竞争者的对比实验缺失；加载时间在极端情况下可达 3 分钟，对动态加载场景有实际影响。该工作为 eBPF 可扩展性迈出了重要一步，但离生产级全面部署还需更多工程投入。
