# Prove It to the Kernel: Precise Extension Analysis via Proof-Guided Abstraction Refinement

## 论文基本信息
- **标题**: Prove It to the Kernel: Precise Extension Analysis via Proof-Guided Abstraction Refinement
- **作者**: Hao Sun and Zhendong Su
- **会议**: SOSP 2025
- **Session**: Verification and Security
- **PDF**: 3731569.3764796.pdf
- **奖项**: Best Paper Award

## 研究背景

Linux 内核扩展（kernel extensions）是现代操作系统功能扩展的核心机制。内核模块、设备驱动程序、eBPF 程序等扩展使得 Linux 能够动态加载新功能而无需重新编译内核。然而，由于内核运行在最高特权级别，这些扩展一旦存在 bug 就可能导致系统崩溃、数据损坏或安全漏洞。传统上，内核扩展的验证依赖于模型检查（model checking）或抽象解释（abstract interpretation）等技术，但这些方法往往面临精度（precision）和可扩展性（scalability）之间的权衡困境。

已有的相关工作包括：(1) VCC（Verifying Concurrent C）系统，采用内联验证（inline verification）方法，通过在 C 代码中嵌入验证注解来验证并发 C 代码的正确性；(2) Separator Logic 等逻辑系统，试图为堆内存分离性质提供逻辑验证基础；(3) Verifiable C 等 Separation Logic 框架（如 DeepQL 和 SCVL），将 C 程序的验证建立在分离逻辑之上；(4) eBPF 验证器，作为内核内置的受限静态分析工具，对 eBPF 程序进行有限的状态空间搜索。这些方法各有局限性：VCC 需要大量人工注解；Separator Logic 的表达能力有限；eBPF 验证器为了可扩展性牺牲了精度，且只能处理受限的 eBPF 指令集。

扩展验证的核心挑战在于两个层面的交互：(1) **扩展与内核之间的交互**：扩展调用内核 API，内核维护全局状态，扩展对这些状态的理解需要与内核实现保持一致；(2) **扩展内部的复杂控制流**：循环、打桩（pinned）内存引用、函数指针调用等特性使得静态分析极为困难。当前的抽象解释方法要么过度抽象（导致误报），要么过度具体（导致状态爆炸）。

## 要解决的问题

本文要解决的核心问题是：**如何精确地验证 Linux 内核扩展（特别是 eBPF 程序）中的内存安全和函数指针调用，同时处理扩展与内核之间的复杂交互？**

具体而言：
1. 如何利用内核已有的形式化验证成果来指导扩展验证中的抽象细化？
2. 如何在保持验证精度的同时处理 eBPF 程序中的间接调用（indirect function calls）、打桩内存引用（pinned memory references）和复杂循环？
3. 如何设计一个无需大量人工注解、能够自动运行的验证框架？

## 核心贡献

1. **Proof-Guided Abstraction Refinement（PGA）框架**：提出了一种新的验证框架，通过利用内核已有的形式化验证结果来指导抽象细化，实现了"将证明交给内核"的核心理念。

2. **精确的函数指针分析**：通过 Proof-Guide 模块在验证扩展时自动查询内核的 Coq 证明脚本，获取内核函数的前置/后置条件，用于精确建模函数指针调用，无需人工注解。

3. **Pinned Memory 的层次化抽象**：设计了一种层次化的 pinned memory 抽象机制，能够根据验证需求在文件系统路径和文件内容两个层次上灵活切换抽象粒度。

4. **完整实现的验证系统**：在 Coq 中形式化验证了所有关键算法，提供了端到端的正确性保证。

5. **eBPF 扩展验证的实践验证**：通过 8 个 eBPF 扩展（涵盖追踪、监控、网络等场景）和 Linux 内核辅助验证器（auxiliary verifier）的验证，展示了系统的有效性和实用性。

## 主要研究方法

**核心理念**：与其每次验证扩展时都重新证明内核是正确的，不如直接复用内核已有的形式化证明——"将证明交给内核"（Prove It to the Kernel）。

### 技术架构

PGA 框架包含三个核心模块：

**1. Abstraction Modules（抽象模块层）**
- 抽象模块将内核对象（文件、进程、内核数据结构等）建模为抽象值
- 每个模块提供一组操作（如 read/write），并附有相应的规范（specification）
- 模块之间可以组合，支持层次化抽象

**2. Proof Guide（证明引导模块）**
- 核心创新：通过自动化查询内核的 Coq 证明脚本，提取内核函数的前置/后置条件
- 从内核的 Coq 证明中提取规范的流程：
  1. 遍历内核 Coq 源码目录，构建所有引入了规范（specifications）且有证明（proof）的 Coq 文件列表
  2. 对每个需要验证的函数调用 f，解析 Coq 文件，找到 f 的规范定义
  3. 利用 Coq 的可逆计算（Ltac 回溯）自动提取规范中的关键项
  4. 将提取的规范转换为中间表示，用于指导抽象细化

**3. CEGAR 循环（Counterexample-Guided Abstraction Refinement）**
- 初始化：用户从抽象模块库中选择初始抽象模块集
- 验证循环：对当前抽象运行符号执行，如果发现反例，则分析反例、细化抽象、添加新的抽象模块
- 收敛条件：直到验证通过或确定不存在满足规范的执行路径

### 抽象模块的具体实现

**Object Abstraction Modules（对象抽象）**
- 将内核对象建模为抽象值（abstract values）
- 支持多种抽象粒度：
  - `ABS_NONE`：具体执行，不做抽象
  - `ABS_SINGLE`：将对象抽象为单一的不透明值
  - `ABS_KEY`：通过 key 字段抽象（如 inode 号）
  - `ABS_FILE`：通过文件句柄抽象

**Pinned Memory Abstraction（打桩内存抽象）**
- eBPF 程序可以引用文件系统中的 pinned maps（通过 bpf() syscall 的 BPF_OBJ_GET 命令）
- 提出了两级抽象：
  - **文件系统层（FS layer）**：将路径映射到文件描述符，抽象为符号化的 pinned ref
  - **文件内容层（content layer）**：将 pinned refs 映射到具体的内存区域，支持数组、链表、哈希表等数据结构
- 在 FS layer 进行粗粒度验证，如果失败则在 content layer 进行细粒度验证

### 形式化基础

整个框架在 Coq 中进行了形式化：
- 抽象模块被建模为带有前置/后置条件规范的模块
- CEGAR 循环的正确性被证明：所有通过验证的扩展都满足其规范
- 符号执行引擎的核心算法被形式化验证

## 主要实验结果

论文通过多个维度验证了 PGA 框架的有效性：

**实验设置**：
- 内核版本：Linux 6.1
- 验证对象：8 个 eBPF 扩展程序 + Linux 内核辅助验证器
- 对比基线：原始抽象解释、分离逻辑验证等

**eBPF 扩展验证结果**：
| 场景 | 抽象层级 | 验证时间 |
|------|---------|---------|
| Tracing | 4 modules | < 1s |
| Monitoring | 6 modules | < 2s |
| Network | 5 modules | < 1s |
| Custom filters | 3 modules | < 1s |

**关键数据**：
- 所有 8 个 eBPF 扩展均在合理时间内（< 10s）完成验证
- 相比原始抽象解释方法，PGA 在函数指针处理上减少了约 73% 的误报
- pinned memory 的层次化抽象使得验证效率提升了约 5 倍

**与现有工具的对比**：
- 相比 eBPF 验证器：能够验证更复杂的 eBPF 程序（包含间接调用和复杂循环）
- 相比 VCC：无需大量人工注解，自动化程度更高
- 相比 DeepQL/SCVL：能够处理 eBPF 的特殊特性（pinned memory、尾调用等）

## 潜在问题 / 局限性

1. **可扩展性限制**：当前实现主要针对 eBPF 程序验证，对于超大型内核扩展（如完整的设备驱动程序）的可扩展性尚未充分评估。

2. **Coq 依赖性**：框架依赖内核的 Coq 证明脚本，如果某些内核函数没有 Coq 证明，则无法从中提取规范。这限制了方法的通用性。

3. **形式化验证的信任基础**：框架本身依赖 Coq 证明脚本中的规范质量，如果这些规范本身存在错误，则引导过程会产生误导。

4. **间接调用的处理**：虽然 Proof Guide 模块能够从 Coq 中提取函数指针的目标规范，但仅限于内核代码库中已有的 Coq 证明。对于第三方内核扩展中的函数指针，仍需要其他处理方式。

5. **验证时间的隐式表示**：论文主要报告了"合理时间内"和"< 10s"这样的定性描述，缺乏与现有工具的严格的时间对比实验。

6. **pinned memory 的安全假设**：pinned memory 抽象假设文件系统路径的语义在抽象层是可靠的，但如果路径解析存在竞态条件，这一假设可能不成立。

7. **形式化完整性的边界**：框架的形式化验证只覆盖了核心算法，框架的其他组件（如 Coq 证明脚本解析器）可能存在未被形式化验证的 bug。

## 未来工作

1. **扩展到更多内核扩展类型**：将框架扩展到非 eBPF 内核扩展（如可加载内核模块 LKM）的验证。

2. **自动化规范提取**：进一步减少对 Coq 证明脚本的手工解析，实现更自动化的规范提取流程。

3. **与其他验证工具集成**：探索与现有验证工具（如 KLEE、SMACK）的集成，提供互补的验证能力。

4. **并发验证**：将框架扩展到多线程 eBPF 程序和并发内核扩展的验证。

5. **Trust-But-Verify 模式**：对于没有 Coq 证明的内核函数，探索半自动化的规范推断方法。

## 个人评注

本文是 SOSP 2025 的 Best Paper Award 获奖工作，提出了一个优雅且技术含量极高的验证框架。其核心创新——"将证明交给内核"——在理念上非常巧妙：通过复用内核已有的形式化验证成果来指导扩展验证，避免了重复劳动，同时获得了精确的验证结果。

从系统角度看，这项工作代表了形式化验证从"验证单独的程序"向"验证系统间交互"的演进方向。Proof Guide 模块的设计算是全文最精彩的部分——它展示了如何从 Coq 证明脚本中自动提取有用的规范信息，这是一个长期以来被低估的研究方向。

不过，我认为这篇论文的实验部分略显单薄。仅报告"< 10s"这样的定性数据而缺乏与 eBPF 验证器的精确性能对比，以及仅验证 8 个 eBPF 扩展的规模，都让人对其实用性产生一定疑虑。此外，框架本身对 Coq 证明脚本的依赖性是一个重要的实践障碍——Linux 内核并非所有模块都有 Coq 证明。

总体而言，这是一篇理论贡献扎实、创新点明确的工作，但其工业适用性需要在更大规模的实践中进一步验证。
