# Prove It to the Kernel: Precise Extension Analysis via Proof-Guided Abstraction Refinement

**作者**：Hao Sun, Zhendong Su（ETH Zurich）
**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles）
**链接**：https://doi.org/10.1145/3731569.3764796
**源文件**：[[3731569.3764796.pdf]]

---

## 一、背景

eBPF 是 Linux 内核中广泛使用的扩展机制，允许用户态程序向内核注入安全的功能扩展，应用于性能分析、安全监控、文件系统管理、网络策略等场景。Meta、Google、Cloudflare 等公司在生产环境中大规模部署了 eBPF 扩展。

为确保安全性，内核内置了一个静态验证器（verifier），基于抽象解释技术对 eBPF 字节码进行分析。验证器使用 interval domain 和 tristate domain 等轻量级抽象域来追踪寄存器值范围，以线性时间完成分析。然而，这些抽象域在每一步解释中都会引入 over-approximation，导致精度信息快速丢失，大量安全的扩展程序被错误拒绝（false rejection）。

---

## 二、要解决的问题

1. **验证器精度不足**：interval domain 和 tristate domain 在算术运算（尤其是移位、位运算后）会丢失大量精度信息，无法追踪变量间的关系，导致安全程序被错误拒绝。例如，`r2 = r1 & 0xf; r3 = 0xf - r2` 后，验证器无法推断 `r2 + r3 = 0xf`，而是 over-approximate 为 `[0, 30]`。

2. **精度-复杂度困境**：更精确的抽象域（如 Octagon $O(n^3)$、Polyhedra $O(2^n)$）会增加内核的复杂度、攻击面和运行时开销，在内核环境约束下不可行。

3. **开发者负担**：验证器的错误拒绝迫使开发者进行大量代码重构，有时甚至需要编写内联汇编或分配双倍内存来"取悦"验证器，造成资源浪费和开发效率低下。

4. **编译器多样性问题**：不同编译器版本和优化级别会产生不同的字节码模式，验证器往往只能接受特定编译配置下的产物，限制了编译器选择的灵活性。

---

## 三、洞察与设计

**关键洞察**：生成精确证明（proof）是计算密集型的（NP-complete），但验证一个已有证明的正确性可以在线性时间内完成。因此可以将复杂的精度推理卸载到用户态，而内核只需执行高效的证明检查（proof checking），从而在不增加内核复杂度的前提下大幅提升验证精度。

基于此洞察，作者提出了 **BCF（eBPF Certificate Framework）**，一种 proof-guided abstraction refinement 技术：

1. **按需触发**：验证器照常执行高效的抽象解释，仅在遇到潜在错误时触发 refinement，而非直接拒绝扩展。

2. **反向分析（Backward Analysis）**：从错误点反向追踪，确定需要符号跟踪的路径后缀（suffix），只分析与目标寄存器及其依赖相关的指令，利用程序局部性大幅缩短分析范围。

3. **符号跟踪（Symbolic Tracking）**：在确定的后缀上收集精确的符号表达式，无信息损失地表示所有可能的寄存器值。

4. **Refinement Condition 生成**：将"符号表达式的所有可能值都在 refined abstraction 范围内"形式化为 refinement condition。

5. **用户态证明生成**：将 refinement condition 委派给用户态 SMT solver（cvc5）求解，生成形式化证明。

6. **内核态证明检查**：内核接收证明后，通过线性时间的 proof checking 验证其正确性，确保零信任。

## 四、实现细节

BCF 的实现涉及 7,366 行 C/C++ 代码，分布在以下组件：

| 组件 | 语言 | 代码量 | 位置 |
|------|------|--------|------|
| Verifier 扩展 | C | 1,663 行 | 内核态 |
| Proof Checker | C | 2,337 行 | 内核态 |
| uapi 接口 | C | 190 行 | 共享 |
| Loader | C | 349 行 | 用户态 |
| Solver 扩展 | C++ | 1,837 行 | 用户态 |

关键实现要点：

- **系统调用接口**：仅在 `BPF_PROG_Load` 命令中新增 5 个字段（`bcf_fd`、`bcf_buf`、`bcf_buf_size`、`bcf_buf_true_size`、`bcf_flags`），无需新增系统调用。
- **二进制编码格式**：基于 u32 的紧凑编码，符号表达式的操作符编码在首个 4 字节单元中，嵌套表达式通过相对偏移引用，证明步骤的结论由 checker 计算而非显式编码，减小传输体积。
- **反向分析**：复用验证器已有的 `backtrack_insn()` 例程，使用整数 bitmask 维护寄存器集合。
- **符号跟踪**：集成在验证器的 `do_check()` 分析阶段，仅在 refinement 时启用，利用验证器的 range 信息将符号变量降至 32 位以简化表达式。
- **Proof Checker**：支持 45 条原始证明规则（Boolean、equality、bit-vector 理论），验证分三阶段：格式/类型检查、规则应用计算结论、与存储的 refinement condition 比对。
- **当前限制**：栈状态跟踪不完整（仅支持寄存器大小的 stack spill），不影响 soundness 但可能导致 refinement condition 过弱。

## 五、实验结果

**实验平台**：AMD EPYC 9654 96 核处理器，756 GiB 内存，Linux v5.15，QEMU/KVM 虚拟化。

**数据集**：512 个真实世界 eBPF 程序（来自 Cilium、Calico、BCC、xdp-project 等 46 个项目），使用多种编译器（Clang-13 到 Clang-21）和优化级别（-O1 到 -O3）编译，均为安全但被当前验证器错误拒绝的程序。

| 指标 | 结果 |
|------|------|
| 接受率 | 403/512（78.7%） |
| 完全接受的源程序 | 75/106 |
| 平均证明大小 | 541 bytes |
| 证明检查时间 | 平均 48.5 μs（范围 31–1,845 μs） |
| 平均分析总时间 | 9.0 秒 |
| 内核态分析占比 | 79.3% |
| 用户态推理占比 | 20.7% |
| 99.4% 证明 | < 4,096 bytes |
| Refinement 触发频率 | 平均 446 次/程序 |
| 符号跟踪长度 | 平均 102 条指令（占总指令 3.4%） |
| Refinement condition 大小 | 平均 836 bytes |

**未接受程序的原因**：
- 4 个（0.8%）：refinement 未触发（尚未覆盖的拒绝点）
- 82 个（16%）：实现限制导致 refinement condition 不成立
- 23 个（4.5%）：达到百万指令上限

## 六、批判性分析

1. **数据集构造方法的公正性**：数据集通过编译器多样性自动生成——同一安全源程序用不同编译配置编译后被拒绝即视为 false positive。这种方法虽有合理性，但存在偏差：它主要暴露的是编译器差异导致的字节码模式问题，而非验证器在真实开发中最常遇到的 false rejection 场景。论文提到手动搜索只找到 9 个直接被拒绝的程序实例，说明数据集中绝大多数（503/512）是人为构造的。

2. **21% 的未接受率被低估**：论文声称 82 个因实现限制被拒绝的程序"可以通过更多工程努力解决"，但栈状态跟踪的不完整性是设计层面的问题（非寄存器大小的 spill），这在实际 eBPF 程序中很常见（编译器频繁进行 stack spill），修复可能比论文暗示的更困难。

3. **Load time 开销讨论不充分**：论文提到平均分析时间为 9.0 秒，最长达 182 秒，但对于需要频繁加载 eBPF 程序的生产场景（如 Cilium 容器网络），这个开销是否可接受未充分讨论。虽然提到了 proof caching 可以缓解，但这是未实现的优化。

4. **与 PREVAIL 的对比不公平**：论文以 PREVAIL 的 Windows 兼容性问题为由，仅加载了不到 1% 的程序，实质上放弃了与唯一可比基线的有效对比。

5. **Solver 的隐含依赖**：BCF 的正确性不依赖 solver，但其实用性完全依赖 cvc5 能生成 BCF 格式的证明。论文未讨论 solver 生成证明的可靠性和覆盖率——如果 solver 无法处理某些条件类型，系统就退化为原始验证器。

6. **安全性论证的假设**：论文声称 forged proof 不可能通过检查，但 proof checker 本身有 2,337 行内核代码，这本身就是新增的攻击面。论文未充分讨论 proof checker 自身的 bug 可能带来的安全隐患。

---

## 七、总结

本文提出了 BCF，一种 proof-guided abstraction refinement 技术，通过将复杂的精度推理卸载到用户态、内核仅执行线性时间的证明检查，在不增加内核复杂度的前提下大幅提升了 eBPF 验证器的精度。在 512 个被错误拒绝的真实 eBPF 程序上，BCF 成功接受了 403 个（78.7%），证明检查开销极低（平均 48.5 μs、541 bytes）。该方法的核心价值在于利用"生成证明难、验证证明易"的计算不对称性，优雅地解决了内核验证器的精度-复杂度困境。主要局限在于栈状态跟踪不完整、与 SMT solver 的耦合、以及循环密集程序的处理。
