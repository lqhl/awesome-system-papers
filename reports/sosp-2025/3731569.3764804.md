## 一、背景

随着 NVMe PCIe 5.0 SSD 的普及，全闪存服务器（all-flash server）已成为企业私有存储和云计算存储后端的主流选择。单块 PCIe 5.0 SSD 可达 2,500K IOPS、14 GB/s 带宽，单机可安装 16–24 块，提供 PB 级容量。为充分释放这类硬件性能，业界广泛采用 SPDK 等用户态轮询（busy-polling）存储栈，通过专用 CPU 核心 100% 轮询来降低延迟。

然而，高性能的代价是高能耗。一台 16 块 PCIe 5.0 SSD 的 1U 服务器在峰值负载下整机功耗高达 940W，CPU 单独在空载状态已耗 134W，轮询状态下飙升至 245W（1.82× 空载）。更严重的是，CPU 升温还会带动风扇从 18K RPM 猛增至 28K RPM，产生级联效应。另一方面，来自 Google、Meta、Alibaba 的真实云负载显示，I/O 压力极不稳定，频繁发生短暂突发（burst）——在 30 分钟内最多出现 82 次 burst，峰值之外大量 CPU 算力被空转浪费，浪费能量高达实际所需的 3.4×。

## 二、要解决的问题

**核心矛盾**：如何在保住 SPDK 级别高性能的同时，大幅降低全闪存服务器的能耗？

现有四类省电方案均有明显缺陷：

1. **Linux 中断模式**：空载时省电，但重负载下因系统调用/上下文切换开销反而比 SPDK 耗更多能量，且尾延迟显著更高。
2. **Governor（CPU P-state 调频）**：通过降低核心频率节省功耗，但 CPU 频率从最低档恢复到最高档需要 >450 μs（Phase-Locked Loop 锁定延迟），面对突发 I/O 响应迟缓，尾延迟是 SPDK 的 3×，IOPS 仅有 1/3。
3. **Dynamic Scheduling（线程动态迁移）**：用 CPU cycle 估算负载然后迁移线程。但在微秒级调度窗口内可用 cycle 极少，负载估算不准确，线程被反复迁移（稳定负载下 60 秒内迁移超百万次），带来 >800 μs 额外延迟；软件唤醒依赖 epoll/interrupt，引入 27 μs 上下文切换开销。
4. **Hybrid Polling**：核心在睡眠/轮询之间交替，性能接近 SPDK，但因核心独立且频繁地在低功耗与高性能状态间切换，无法长时间保持睡眠，省电效果有限。

五条关键观察总结：中断上下文切换影响效率（O1）、硬件调频存在数百 μs 过渡延迟（O2）、微秒粒度下 cycle 计数难以准确检测 burst（O3）、软件唤醒引入 25+ μs 开销（O4）、频繁状态转换限制省电效果（O5）。

## 三、核心设计

Sandman 是一个构建在 SPDK 之上的调度框架，通过四条设计准则应对上述问题：

- **D1：让核心进入浅层睡眠而非降频**：C-1 浅睡眠退出延迟仅 3 μs（vs. P-state 降频 450 μs），保持随时可响应的能力。
- **D2：避免系统调用和中断唤醒**：用 CPU 硬件的 cache-coherence 机制（`monitorx/mwaitx` 用户态等待指令）代替 kernel 中断，唤醒无需上下文切换。
- **D3：让兄弟核心（sibling hyper-thread）一起睡眠更长时间**：将线程集中到更少的核心，同一物理核的两个逻辑核同时休眠，最大化省电窗口。
- **D4：从网络队列入口检测 burst 而非 CPU cycle**：直接统计 RDMA RX 队列的入站 I/O 请求数，在微秒级精准识别突发，绕过 cycle 计数不准的问题。

**系统架构**：一个 main core + 多个 worker core，均以轮询模式运行；I/O thread 是轻量级用户态线程，封装一组任务，组织为环形链表轮询执行，可在核间无缝迁移。

**两层调度粒度**：
- **粗粒度（1 秒）**：监控资源浪费，将空闲 I/O thread 迁回 main core，把空闲核心推入浅睡眠，优先配对兄弟核同时入睡。
- **细粒度（10 μs）**：通过 Workload Variation Detection Model 检测 burst：维护入站 I/O 请求的移动平均（MA）和标准误（SE），构造 95% 置信区间；当某 thread 的入站 I/O 超出置信区间上界，立即唤醒一个空闲核并分配整核给该 thread。

## 四、实现细节

**数据平面**：基于 SPDK NVMe-oF 层，使用 SPDK 用户态 NVMe 驱动直接操作 SSD，使用 RDMA InfiniBand 用户态库（rdma-core）操作 NIC，全程轮询模式。

**控制平面扩展**（在 SPDK 调度框架基础上）：
- 新增细/粗粒度调度事件及统计采集模块（282 LoC）
- 修改 I/O poller 以上报 RDMA RX 队列入站请求数（192 LoC）
- 扩展 reactor event queue 以支持新调度机制（234 LoC）
- 新增用户态等待指令抽象层，替换 SPDK 原有 kernel-based 机制（128 LoC）
- Burst detection model 模块（192 LoC）
- 新调度器（884 LoC，核心逻辑）

**睡眠唤醒机制**：sleeping core 通过 `monitorx` 监控 event queue 的下一个可用 entry 地址，然后 `mwaitx` 进入浅睡眠。当 main core 向该地址写入调度事件时，cache-coherence 协议自动触发唤醒，整个过程零系统调用、零中断。

**核心选择策略**：burst 时优先唤醒 sibling 逻辑核（避免唤醒新物理核），空闲整合时优先让兄弟对一起入睡。

**代码规模**：总计约 1700 LoC 新增/修改代码。

## 五、实验结果

**实验平台**：AMD EPYC 9454P（48 核，3.65 GHz）、756 GB DRAM、16× Samsung PM1743 3.84TB PCIe 5.0 SSD、Mellanox ConnectX-6 200 Gbps RDMA NIC × 2，Ubuntu 22.04，Linux 6.8.7，SMT 开启。

### 稳定负载（4KB 随机读，10K–10240K IOPS）

| 方案 | CPU 功耗 | 系统功耗 | 尾延迟（P99.9） |
|------|---------|---------|--------------|
| SPDK | 最高 | 最高 | 最低（基准） |
| Sandman | 接近 Governor/Dynamic Scheduling | 接近 Governor | 仅比 SPDK 高 4.8%，最接近 SPDK |
| Hybrid Polling | 介于 SPDK 与 Sandman 之间 | 同左 | 接近 SPDK |
| Governor | 低 | 低 | 高出 SPDK 161.5%（5210K IOPS 处） |
| Dynamic Scheduling | 低 | 低 | 超过 Linux（>80K IOPS 后急剧恶化） |
| Linux | 低负载省电，高负载反超 SPDK | 同左 | 持续偏高 |

### Burst 负载（峰值 1 秒注入）

- Sandman 系统级功耗降低最高 **39.38%**（vs. SPDK）
- 尾延迟和 IOPS 与 SPDK 持平，远优于 Governor（尾延迟 3×）和 Dynamic Scheduling

### 应用基准

- **RAID-5 Flash Array**：Sandman 在 5 类 RAID-5 操作中均达到与 SPDK 相当的吞吐量和延迟，同时功耗优于 SPDK
- **RocksDB + YCSB**：6 类工作负载下，Sandman 同时实现高性能和低能耗，优于其他方案

### 真实云工作负载（Alibaba / Tencent block-level traces）

| 对比 | 能耗节省 |
|------|--------|
| Sandman vs. Linux | **30.23%** |
| Sandman vs. SPDK | **33.36%** |
| 月能耗（Alibaba） | Sandman 最低，约 400 kWh vs. SPDK 约 600 kWh（目测） |

Sandman 延迟分布与 SPDK 最接近，而 Governor/Dynamic Scheduling 虽省电但延迟代价显著。

### 关键微基准

- Burst 检测准确率：稳定负载下 93.45%–95.78% 避免不必要迁移；burst 检测准确率 97.84%
- 调度算法开销：每 10 μs 间隔总计 2.07 μs（main core 占 16.6% CPU 时间）
- Thread 迁移延迟：106.5 ns

## 六、批判性分析

**实验规模的代表性局限**：论文所有实验都在两台直连的服务器上完成，网络规模极小（仅 2 节点、2 个 200 Gbps 端口直连）。真实数据中心环境下，多跳网络、多租户竞争、网络拥塞等因素可能打破 NIC RX queue 入站 I/O 与实际 CPU 需求之间的假设关系——Sandman 的 burst 检测模型建立在"网络队列能精准反映负载"的前提上，但多跳延迟下入站 I/O 可能出现波动，影响检测准确率。

**主核心成为潜在瓶颈**：所有调度决策和 idle thread 都集中在 main core 上。论文承认 main core 运行调度算法时 CPU 开销达 16.6%，最坏情况下若 main core 还要处理活跃线程会损失 16.6% IOPS。虽然作者声称全峰值的情况在实测中"很罕见"，但这仅凭文献引用支持，缺乏论文自身实验数据验证。

**burst 检测模型对参数敏感性含混**：论文展示了置信区间（CI）95% 作为默认设置，但未深入分析不同负载模式（如写密集、混合读写、大块 I/O）下模型的稳定性。真实负载（Alibaba/Tencent）的突发形态与合成 burst workload 差异显著，置信区间是否仍然适用缺乏严格验证。

**硬件依赖未充分讨论**：`monitorx/mwaitx` 仅在 Intel 4th Gen Xeon 和 AMD 3rd Gen EPYC 以上平台可用。对于覆盖面广泛的存量服务器，Sandman 回退到软件中断，此时性能优势缩水，但论文对回退场景的量化分析非常简略。

**能耗对比的基线选择存在倾向性**：论文将 SPDK（满核满频轮询）作为性能基准，但这是一个刻意选择的最差能耗基准；更公平的对比应包含"按需扩缩"的工业级方案（如 Azure/AWS 自有存储栈）。与 Hybrid Polling 相比，Sandman 的功耗改进在应用基准中明显收窄，作者将其归因于应用 SSD 利用率低，但这恰恰说明论文主要场景——极高 IOPS 利用率——的代表性值得商榷。

**可持续性叙事略显过度**：论文标题和摘要多次强调 sustainability，但实验中未直接测量 PUE、碳排放折算，只是用能耗间接映射，"绿色存储"的表述力度超出实验证据支撑。

## 七、AI Infra / MLSys 视角

Sandman 聚焦于全闪存存储服务器的能耗优化，其核心思路对 AI 系统基础设施有多处直接迁移价值。

**对 AI 训练/推理存储层的启发**：大模型训练集群（如 GPU 集群搭配 NVMe-oF 存储节点）中，数据加载 I/O 具有典型的 burst 特征——一个训练 step 前集中读取 batch 数据，随后几乎无 I/O。当前存储侧通常以满配 SPDK 运行，造成大量能耗浪费。Sandman 的调度框架可直接应用于此类场景。

**用户态等待指令作为低开销同步原语**：`monitorx/mwaitx` 的 cache-coherence 唤醒机制本质上是一种零系统调用的硬件通知原语，在 AI Infra 场景下（如 KV cache 管理、Parameter Server、流水线调度中的生产者-消费者同步）有潜在应用价值，可替代部分 spin-wait 或 futex 开销。

**细粒度 burst 检测的可迁移性**：基于入站队列请求数构建置信区间的 burst 检测思路，可推广到推理服务（inference serving）中的请求 batching 策略优化——动态决定何时开始 batch 推理、何时让 GPU 进入低功耗状态，是 LLM 推理系统（如 vLLM、SGLang）节能的潜在方向。

**可跟进的研究方向**：
- 将 Sandman 框架移植到 DPU 场景的 AI 存储加速（论文已提及但未实现），量化 BlueField/IPU 上的能耗收益
- 将类似的 "shallow-sleep + queue-based burst detection" 思路应用于 GPU Streaming Multiprocessor 级别的功耗管理，探索推理 idle 阶段的 GPU 低功耗调度
- 结合 AI workload 的周期性规律（mini-batch boundary），设计预测式而非响应式的睡眠/唤醒策略

---

## 八、总结

Sandman 是一个运行于 SPDK 之上的存储调度框架，通过三项机制——利用 `monitorx/mwaitx` 指令实现无中断浅睡眠唤醒、基于网络入站队列的微秒级 burst 检测、兄弟核配对协同睡眠——同时实现高性能与高能效。在 16× PCIe 5.0 NVMe SSD 的真实平台上，相比 SPDK 节省最高 33.36% 能耗，性能差异在 5% 以内。主要局限在于硬件依赖（新一代 CPU）、单节点实验规模较小，以及 main core 集中调度的潜在扩展瓶颈；但其核心设计思路对 AI Infra 场景中的存储与计算资源能耗优化具有较高借鉴价值。
