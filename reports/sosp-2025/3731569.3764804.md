# Sleeping with One Eye Open: Fast, Sustainable Storage with Sandman

## 论文基本信息
- **标题**: Sleeping with One Eye Open: Fast, Sustainable Storage with Sandman
- **作者**: Yanbo Zhou, Erci Xu, Anisa Su, Jim Harris, Adam Manzanares, Steven Swanson (UC San Diego, Shanghai Jiao Tong University, Samsung Semiconductor)
- **会议**: SOSP 2025
- **Session**: Storage and Databases
- **PDF**: 3731569.3764804.pdf

## 研究背景

现代全闪存存储服务器虽然提供了卓越的性能（>2,500K IOPS，>14 GB/s 吞吐，>120 TB 单盘容量），但其高能耗问题日益突出，已成为数据中心 CapEx 和碳排放的重要来源。高能耗源于三个相互强化的因素：

**R1：处理能力需求高**。饱和单个 NVMe PCIe 5.0 SSD（2500K IOPS）需要约 3 个逻辑核，相比饱和 SATA SSD 增加了 32 倍的资源需求。

**R2：轮询模式的高功耗**。高性能存储栈（如 SPDK）采用轮询模式，CPU 必须以 100% 利用率运行在高频率，导致功耗是空闲态的 **1.82 倍**。这进而引发级联效应——CPU 温度升高，风扇转速从 18K RPM 提升到 28K RPM，整体功耗进一步攀升。

**R3：真实工作负载的突发性**。来自 Google、Meta、Alibaba 的生产环境 trace 均表明 I/O 突发（burst）频繁且短暂。这意味着系统为峰值预留的资源大部分时间都在浪费——实际分析显示，浪费的能量可达需求能量的 **3.4 倍**。

## 要解决的问题

如何设计一个调度框架，使现代存储服务器能够同时实现：
1. 高性能：在突发工作负载下保持低延迟和高吞吐
2. 节能：在低负载时让核心进入休眠状态，减少能耗

现有方案各有缺陷：Linux 中断在低负载时省电但高负载时功耗反而更高（上下文切换开销导致 CPU 效率低）；Governor（CPU 频率调节）延迟高（频率切换需要 450us 以上）；Dynamic Scheduling 受困于软件唤醒开销（27us）和负载估计不准确；Hybrid Polling 因频繁在睡眠和激活态间切换而无法最大化省电效果。

## 核心贡献

- **全面评估**：首次系统性地评估现代全闪存服务器在各节能方案下的性能和能耗表现
- **问题识别**：识别了实现高性能和节能双重目标的五大挑战
- **四个设计准则**：D1（睡眠核心而非降低频率）、D2（避免系统调用和中断）、D3（核心协同睡眠更长）、D4（微秒级突发检测）
- **Sandman**：结合快速资源缩放机制、资源监控和 I/O 突发检测策略的调度框架
- **关键创新**：结合缓存一致性机制与轻量级线程作为唤醒方法；通过分析 NIC 队列的 I/O 而非传统 CPU 周期计数来检测突发

## 主要研究方法

作者首先构建了一个动机性研究，在真实硬件（双服务器，各 16 NVMe PCIe 5.0 SSD + 200 Gbps RDMA NIC）上对比了五种方案（SPDK、Linux 中断、Governor、Dynamic Scheduling、Hybrid Polling）在稳定负载和突发负载下的功耗与性能。

通过详尽的性能分解，作者识别出五个关键观察（O1-O5），每个观察都指向一个具体的系统瓶颈，从而推导出设计准则。

## 设计与实现

### 设计准则

- **D1：睡眠核心而非降低频率**。硬件从浅层睡眠（C1，退出延迟 3us）恢复比从低频状态（P-N，退出延迟 450us）快 150 倍。因此应优先使用浅睡眠而非降低频率。
- **D2：避免系统调用和中断**。唤醒睡眠核心的软件开销（上下文切换）高达 27us，应通过硬件机制（如缓存一致性）触发唤醒。
- **D3：核心协同睡眠**。频繁在低功耗和高性能态间切换反而耗能——应让多个核心一起睡更长时间。
- **D4：微秒级突发检测**。传统基于 CPU 周期的负载估计不准确——应在 I/O 队列层面检测突发。

### Sandman 架构

Sandman 基于 SPDK 构建，包含三个核心组件：

1. **快速资源缩放机制**：
   - 将核心置于浅层睡眠（C1）而非降低频率（P-N）
   - 利用缓存一致性（cache coherence）信号作为唤醒触发——无需系统调用
   - 核心集体进入/退出睡眠，避免频繁切换

2. **资源监控策略**：
   - 每 10us 采样一次系统状态
   - 跟踪活跃工作线程数、待处理 I/O 数等指标
   - 决策是否缩放资源（增减活跃核心数）

3. **I/O 突发检测**：
   - 从 NIC 队列分析入站 I/O 而非 CPU 周期
   - 检测窗口：10us（微秒级粒度）
   - 识别突发模式后迅速扩展资源

### 调度机制

工作核心将 I/O 请求提交到 NIC 队列后进入睡眠。数据包到达时，通过缓存一致性信号唤醒工作核心。这种机制避免了传统中断驱动的软件开销，同时保证了快速响应。

## 主要实验结果

### 实验环境
- AMD EPYC 9454P 48 核处理器（单插槽，4 NUMA 节点，3.65 GHz max / 400 MHz min）
- 756 GB DRAM
- 16 × Samsung PM1743 3.84 TB SSD（PCIe 5.0）
- Mellanox ConnectX-6 RDMA NIC（2 × 200 Gbps）

### 稳定负载（16 SSD，4KB 随机读）

- **Sandman 功耗**比 SPDK 低 **39.38%**（系统级），同时尾延迟仅差 **4.8%**
- Governor 功耗最低，但尾延迟比 SPDK 高 161.5%（5120K IOPS 时）
- Dynamic Scheduling 在 IOPS > 160K 后尾延迟急剧恶化
- Hybrid Polling 功耗和性能均与 SPDK 接近，未能实现显著节能

### 突发负载（单 SSD，突发 100% 最大 IOPS 持续 1 秒）

- **系统功耗**：Sandman 达到最低（与 Governor 相当），比 SPDK 低 **39.38%**，比 Hybrid Polling 低 41.34%
- **尾延迟**：Sandman 匹配 SPDK；Governor 尾延迟是 SPDK 的 3 倍；Dynamic Scheduling 次之
- **IOPS**：Sandman 达到 SPDK 的水平；Governor 仅为 SPDK 的 1/3

### 各机制贡献（burst 负载）

- Scale Frequency（D1）：+17.69% 系统功耗降低
- Sleep Cores（D2+D3）：额外 +22.41% 降低
- Detect Queues（D4，NIC 队列检测突发）：额外 +16.03% 降低
- No Interrupts（D2 避免中断）：额外 +25.13% 降低

### 调度算法开销

- 统计填充：79ns/次（仅占每次调度事件 CPU 周期的 0.78%）
- 算法执行：主核 1.99us/次（占 16.60%）
- 线程迁移：106ns/次（占 1.05%）

### 应用级验证（LevelDB）

Sandman 相比 SPDK 实现 **22% 能耗降低**，同时吞吐量相当。

### 真实云 trace

在 Alibaba 块存储 trace 下，Sandman 比 Linux 省 **30.23%** 能量，比 SPDK 省 **33.36%** 能量，同时延迟分布与 SPDK 相当。

## 潜在问题 / 局限性

1. **仅 AMD 平台验证**：所有实验在 AMD EPYC 处理器上进行，Intel 平台的缓存一致性机制行为可能不同（论文仅在 Figure 5 中简要测试了 Intel SPR 的频率切换开销）
2. **依赖 RDMA/NIC 队列分析**：Sandman 的突发检测依赖 RDMA NIC 队列。在不使用 RDMA 的场景（如本地 SSD）下，可能需要额外的适配
3. **仅评估了 NVMe-oF 场景**：本地 SSD 场景下能否复用相同机制？论文未涉及
4. **突发检测窗口固定为 10us**：是否对所有负载模式都是最优？缺乏敏感性分析
5. **风扇转速控制的间接效应**：论文观察到风扇对 CPU 活动的级联效应，但 Sandman 未控制风扇——这意味着在风扇转速可管理的环境中效果可能打折
6. **与其他突发检测方案的对比不足**：未与 Shinjuku、TinyQuanta 等微秒级调度器进行突发检测维度的对比

## 个人评注

Sandman 是一项面向实际问题的工作——现代全闪存服务器的高能耗问题确实被低估了，但它正在随着数据中心规模扩大而变得越来越紧迫。论文的动机性研究设计扎实，通过对五种现有方案的详尽对比，清晰地揭示了每种方案的核心缺陷。

最有价值的 insight 是"O5：频繁切换限制省电"——这不是显而易见的，因为它意味着最简单的动态调节方案（Hybrid Polling）反而效果最差。解决方案（让核心一起睡更长时间）在直觉上也成立。

不过，论文的弱点在于**移植性验证不足**——所有实验均在 AMD 平台上进行，且仅针对 NVMe-oF 场景。对于更广泛的应用场景（如本地 SSD 存储服务器），Sandman 的核心机制是否仍然有效需要进一步验证。此外，Sandman 的评估主要在单存储节点上进行，未涉及分布式存储系统中的协调问题。
