# Sleeping with One Eye Open: Fast, Sustainable Storage with Sandman

**作者**：Yanbo Zhou (UC San Diego), Erci Xu (Shanghai Jiao Tong University), Anisa Su (Samsung Semiconductor), Jim Harris (Samsung Semiconductor, now at NVIDIA), Adam Manzanares (Samsung Semiconductor), Steven Swanson (UC San Diego)

## 一、背景

现代全闪存服务器（all-flash server）凭借最新 NVMe PCIe 5.0 SSD（单盘超 2,500K IOPS、14 GB/s 带宽、120+ TB 容量）已成为企业存储和云存储后端的主流选择。然而，释放这些 SSD 的性能潜力需要大量 CPU 资源：饱和一块 PCIe 5.0 NVMe SSD 至少需要 3 个逻辑核心，相比 SATA SSD 增加了 32 倍。为追求极致性能，业界广泛采用 SPDK 等 busy-polling 模式的用户态存储栈，导致 CPU 始终以 100% 利用率高频运行，无论实际负载高低，功耗均维持在峰值水平（CPU 功耗为空闲状态的 1.82 倍），并引发风扇等附属组件的级联功耗增长。

与此同时，来自 Google、Meta、Alibaba 等的真实工作负载表明，存储 I/O 具有频繁的波动和突发特征。在 30 分钟窗口内可出现多达 82 次 I/O burst，实际所需计算能力远低于峰值预留，浪费的能量可达实际需求的 3.4 倍。这为节能提供了巨大空间。

---

## 二、要解决的问题

现有节能方案均无法同时实现高性能和高能效：

1. **Linux 中断模式**：轻负载时节能，但上下文切换开销导致高负载下延迟显著增加，甚至功耗反超 polling 模式（CPU 效率低下）。
2. **Governor（CPU 频率调节）**：通过 P-state 降低 CPU 频率节能，但硬件频率切换延迟超过 450 μs，无法及时响应 I/O burst，尾延迟是 SPDK 的 3 倍。
3. **Dynamic Scheduling（动态线程调度）**：通过核间线程迁移减少活跃核心数，但依赖 CPU cycle 计数估算负载在微秒尺度下不准确（60 秒内线程迁移超百万次），且软件中断唤醒开销达 27 μs。
4. **Hybrid Polling（混合轮询）**：在 sleep/active 间交替，但由于各核心独立且短暂地进入低功耗态后立即唤醒，频繁状态切换限制了节能效果。

核心挑战归纳为五点：(O1) 中断模式的上下文切换开销；(O2) 硬件频率/功耗状态转换延迟高达数百微秒；(O3) 微秒尺度下基于 CPU cycle 的 burst 检测不准确；(O4) 软件唤醒路径中系统调用和中断引入 25+ μs 开销；(O5) 频繁的低功耗/高性能状态切换阻止核心长时间休眠。

## 三、洞察与设计

**关键洞察**：现代处理器提供的非特权用户态 wait 指令（monitorx/mwaitx）可以利用 cache coherence 协议让 CPU 核心进入浅睡眠状态（C-1），并在目标内存地址被写入时自动唤醒（退出延迟仅 3 μs），无需系统调用或中断。这意味着可以将核心调度问题转化为"让核心一起睡、睡得更久"的问题，同时通过网络队列中的 incoming I/O 计数（而非 CPU cycle）在微秒级精确检测 burst。

基于上述洞察，Sandman 遵循四条设计准则：

- **D1: 让核心睡眠而非降频**——浅睡眠（C-1）退出延迟仅 3 μs，而降频（P-N）需 450+ μs。
- **D2: 避免系统调用和中断**——利用 monitorx/mwaitx 通过 cache coherence 唤醒，无需经过内核。
- **D3: 让核心一起睡、睡得更久**——优先将任务合并到更少的核心，让 sibling 逻辑核心成对休眠。
- **D4: 从网络队列测量 burst**——直接计数 NIC RX 队列的 incoming I/O 请求，而非用 CPU cycle 间接估算。

**系统架构**：Sandman 将核心分为一个 main core（运行调度器）和多个 worker core。调度采用双粒度策略：

- **粗粒度（1 秒）监控资源浪费**：收集 core load 统计，将 idle 核心的线程合并到 healthy 核心，优先让 sibling 核心对成对休眠。
- **细粒度（10 μs）检测 I/O burst**：基于 Moving Average 和 Confidence Interval 模型分析网络队列 I/O 计数，当某线程的 polled I/O count 超过置信区间上界时，立即唤醒一个 sleeping 核心并分配该线程。

## 四、实现细节

Sandman 基于 SPDK 实现，主要包含以下组件：

- **轻量级 I/O 线程**：复用 SPDK 的 reactor/thread 框架，I/O 线程作为用户级轻量线程组织在 ring list 中，通过 round-robin 方式执行。线程可通过从源核心 ring list 移除、插入目标核心 ring list 完成迁移（耗时 106.5 ns）。

- **浅睡眠与即时唤醒**：空闲核心通过 monitorx 设置对 event queue 下一可用 entry 的地址监控，然后通过 mwaitx 进入 C-1 浅睡眠。当调度器向该 event queue 写入调度事件时，cache coherence 协议自动检测到 cache line 变为 modified 状态，目标核心立即唤醒（3 μs）。

- **Workload Variation Detection Model**：计算历史调度周期内网络队列 I/O 计数的 Moving Average (MA) 和 Standard Error (SE)，构建 95% Confidence Interval（CI = MA ± 1.96 · SE）。I/O 计数超过 CI 上界即判定为 burst。稳定负载下准确率 93.45%-95.78%，burst 检测准确率 97.84%。

- **核心选择策略**：合并线程时优先选择 healthy 核心；burst 时优先唤醒 sibling 核心（避免唤醒更多物理核心）。主核心调度算法每 10 μs 运行一次，耗时 2.07 μs（CPU 开销 16.6%），但通过策略将活跃线程优先分配给 worker 核心。

- **代码规模**：在 SPDK 基础上新增约 1,912 行 C 代码（调度器 884 LoC、burst 检测模型 192 LoC、统计收集 282 LoC、NIC 队列轮询器扩展 192 LoC、event queue 扩展 234 LoC、wait 指令抽象 128 LoC）。

## 五、实验结果

**实验平台**：两台 1U 服务器，各配备 AMD EPYC 9454P 48 核处理器、756 GB DRAM、16 块 Samsung PM1743 3.84 TB PCIe 5.0 SSD、Mellanox ConnectX-6 200 Gbps RDMA NIC，通过 RDMA 直连。对比方案：SPDK（busy polling）、Linux interrupts、Governor、Dynamic Scheduling、Hybrid Polling。

| 实验场景 | 关键结果 |
|---------|---------|
| **稳定负载（4KB 随机读）** | Sandman 功耗与 Governor/Dynamic Scheduling 相当，显著低于 SPDK/Linux/Hybrid Polling；尾延迟仅比 SPDK 高 4.8% |
| **Burst 负载** | Sandman 系统功耗比 SPDK 降低最高 39.38%，尾延迟和 IOPS 与 SPDK/Hybrid Polling 相当 |
| **RAID-5 Flash Array** | 五种典型操作下功耗显著降低，性能与 SPDK 相当 |
| **RocksDB + YCSB** | 六种 YCSB 工作负载下均实现节能且保持高性能 |
| **Alibaba 真实 trace（24h）** | 能耗比 Linux 低 30.23%，比 SPDK 低 33.36%，延迟分布与 SPDK 接近 |
| **Tencent 真实 trace（24h）** | 结论一致：Sandman 兼顾低能耗和低延迟 |

**Ablation study**：
- Sleep cores（替代频率调节）：尾延迟降低 41.34%
- 网络队列 burst 检测（替代 CPU cycle 估算）：额外降低 25.13%
- 用户态 wait 指令（替代中断唤醒）：再降低 17.69%

## 六、批判性分析

1. **能耗测量粒度粗糙**：功耗通过 IPMI 以 1 秒粒度采集系统级功耗，但 Sandman 的核心优势在微秒级调度。1 秒采样无法揭示微秒级功耗波动的真实情况，可能掩盖瞬时功耗尖峰。

2. **Burst 检测模型的局限未充分讨论**：95% Confidence Interval 模型假设 I/O 到达近似稳态分布，但真实工作负载可能存在长程依赖、周期性模式等非平稳特征。论文仅展示了简单 burst 模式（5% baseline + 瞬时拉满），对更复杂的多级 burst、渐进式负载增长等场景未做评估。

3. **主核心成为潜在瓶颈**：调度算法在主核心每 10 μs 运行一次，占用 16.6% CPU 周期。论文承认"worst case"下会影响该核心上活跃线程的 IOPS，但以"peak load rarely happens"轻描淡写。在多租户云环境中，多个租户同时发起 burst 并非罕见，此时主核心的调度开销可能导致连锁反应。

4. **硬件依赖性**：Sandman 依赖 Intel 4th Gen Xeon / AMD 3rd Gen EPYC 及以上处理器的 monitorx/mwaitx 指令。虽然论文提到旧平台可回退到软件中断，但回退后本质上退化为 Dynamic Scheduling，性能优势大打折扣。论文未量化回退方案的实际表现。

5. **评估规模受限**：所有实验在两台服务器上进行。在大规模分布式存储集群中，跨节点的负载均衡、网络拥塞等因素可能与节点级节能策略产生冲突（如 Sandman 让部分核心休眠可能导致跨节点 tail latency 增加），但论文未讨论这些交互效应。

6. **节能收益的绝对值**：虽然 33.36% 的能耗降低看起来显著，但这是相对于 SPDK busy-polling 这一极端基线的结果。在实际部署中，如果已使用 Hybrid Polling 等方案，Sandman 的增量收益会小得多。

## 七、AI Infra / MLSys 视角

1. **AI 训练/推理的存储后端节能**：大规模 AI 训练集群中，存储节点（如 checkpoint 存储、数据加载服务器）通常采用 NVMe-oF over RDMA 架构，与本文的评估场景高度匹配。AI 工作负载的 I/O 模式天然具有强烈的 burst 特征（如每 N 步 checkpoint 写入、prefetch 读取），Sandman 的 burst 检测和快速资源扩缩能力可以直接应用于此场景。

2. **GPU Direct Storage 场景的延伸**：当前论文聚焦 CPU 端的存储栈节能。随着 GPU Direct Storage (GDS) 的普及，部分 I/O 路径绕过了 CPU，但 NVMe-oF target 端仍需 CPU 处理。将 Sandman 与 GDS 结合，在 GPU 直接访问存储时让 CPU 核心深度休眠，是一个值得探索的方向。

3. **DPU/IPU 上的应用**：论文在 Discussion 中提到 Sandman 适用于 DPU 场景（如 NVIDIA BlueField），因为 DPU 的 SoC 核心同样运行 SPDK 处理存储功能。AI Infra 中 DPU 越来越多地承担数据路径处理，Sandman 的节能策略可以降低 DPU 的功耗和散热压力。

4. **可迁移的技术 insight**：利用 cache coherence 协议（monitorx/mwaitx）实现微秒级低开销核心唤醒的思路，可以迁移到 AI Infra 中其他需要快速资源扩缩的场景，如 inference serving 中的 batching 调度器（在请求稀疏时让部分核心休眠，请求到达时立即唤醒）。

5. **Future work 方向**：(a) 将 Sandman 的调度策略与 AI workload 的可预测性结合——AI 训练的 I/O 模式比通用存储更规律，可以用模型预测取代 Confidence Interval 的被动检测；(b) 在 AI 推理场景中，将 Sandman 的 burst 检测从网络队列扩展到 GPU kernel launch queue，实现计算+存储的协同节能。

---

## 八、总结

Sandman 是一个面向现代全闪存存储服务器的调度框架，通过三个关键设计——基于 cache coherence 的浅睡眠快速唤醒机制、双粒度（秒级资源监控 + 微秒级 burst 检测）调度策略、以及 sibling 核心成对休眠策略——在 SPDK 基础上实现了高达 39.38% 的功耗降低和 33.36% 的能耗降低，同时保持与 busy-polling 基线相当的性能（corner case 下差异不超过 5%）。其核心贡献在于证明了通过软硬件协同（利用现代 CPU 的 user wait 指令和 cache coherence 协议），可以在不牺牲微秒级存储性能的前提下大幅降低存储栈的能耗。主要局限在于对特定 CPU 指令集的依赖、单节点实验规模、以及对复杂非平稳 burst 模式的处理有待进一步验证。
