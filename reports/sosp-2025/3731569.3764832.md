# Orthrus: Efficient and Timely Detection of Silent User Data Corruption in the Cloud with Resource-Adaptive Computation Validation

## 论文基本信息
- **标题**: Orthrus: Efficient and Timely Detection of Silent User Data Corruption in the Cloud with Resource-Adaptive Computation Validation
- **作者**: Chenxiao Liu, Zhenting Zhu, Quanxi Li, Yanwen Xia, Yifan Qiao, Xiangyun Deng, Youyou Lu, Tao Xie, Huimin Cui, Zidong Du, Harry Xu, Chenxi Wang (UCAS, UCLA, UCBerkeley, Peking University, Tsinghua University)
- **会议**: SOSP 2025
- **Session**: Reliability and Performance
- **PDF**: 3731569.3764832.pdf

## 研究背景

随着数据中心规模扩大，CPU 错误已成为影响云服务可靠性的重要因素。Google 将这类 CPU 描述为"mercurial"——其计算行为不再完全可预测。Alibaba Cloud 在测试超过百万颗处理器后发现，3.61‱ 的处理器表现出能够导致静默数据损坏（Silent Data Corruption, SDC）的计算错误。这类错误的特点是：CPU 可能产生错误结果但程序仍正常完成，不触发硬件警告或应用程序崩溃，因此传统容错机制（如 checkpoint/recovery）对其无效。

SDC 后果极为严重：云服务商（如 Google、AWS、Alibaba）将其视为 catastrophic 级别问题。一个典型场景是：银行查询账户余额，若返回错误的数值，不仅需要赔偿客户、面临监管罚款，还可能引发漫长的法律诉讼。更棘手的是，现有的检测手段存在根本性缺陷。传统离线 CPU 测试（如每三个月运行一次测试用例）只能检测 mercurial core，无法检测已发生的用户数据损坏——损坏可能在测试执行前就已发生。Checksum 虽然常用，但只能检测数据在传输或存储过程中的 bit-flip 错误，无法检测 CPU 在计算过程中产生的错误（如 Listing 2 中 hash 计算出错导致返回错误数据）。

## 要解决的问题

如何在生产环境中，以低开销（low overhead）、及时（timely）地检测由 post-installation CPU 错误导致的静默用户数据损坏（SDC），同时保证对计算资源的高效利用（resource-adaptive）？

具体挑战包括：
1. **在线验证开销**：Replication-based Validation（RBV）需要完整重放整个应用，开销超过 100%；Instruction-level Validation（ILV）需要 cycle-by-cycle 同步，开销约 50 倍，均不适合生产环境。
2. **控制路径与数据路径的交织**：CPU 错误可能发生在控制路径代码中，改变执行流，导致错误的函数被调用，checksum 无法检测此类错误。
3. **资源约束**：生产环境资源有限，验证开销需要严格控制，且需要随可用资源动态调整。

## 核心贡献

- 提出一种基于控制路径与数据路径分离的混合检测策略：对不修改用户数据的控制路径使用 checksum，对执行数据操作的数据路径使用异步 re-execution validation。
- 实现 Orthrus：一个通过轻量级标注（annotations）和编译器支持，让开发者识别数据路径操作符，并在不同 core 上异步验证这些操作的系统。
- 引入 versioned memory 机制，使得验证可以在 out-of-order 模式下执行，消除 APP 和 VAL 之间的依赖关系，显著提升验证吞吐量。
- Resource-adaptive 调度：Orthrus 通过自适应采样、动态 core 分配和 work-stealing，在有限资源下最大化 SDC 覆盖率，同时维持低开销（平均 ~4%）。

## 主要研究方法

**关键观察 1：云应用的代码路径分离**
云应用程序的代码通常呈现清晰的控制路径（control path）与数据路径（data path）分离：控制路径负责调度、分发请求等管理逻辑，不直接操作用户数据；数据路径包含用户自定义的数据处理函数（如 map、reduce、shuffle）和数据操作符（如 hash table 查询、B+ tree 插入）。数据路径代码结构简单、可重入，适合 re-execution 验证。

**关键观察 2：CPU 错误的可重现性**
研究表明，CPU 错误与特定指令高度相关，一旦某 CPU 在某函数中出错，该错误会以一定频率持续在同一函数中复现。这一特性使得采样策略可以优先验证长时间未验证的操作符，提高覆盖率效率。

**Hybrid 检测机制**：
- **控制路径**：使用 CRC-16 checksum 检测数据完整性。当数据对象进入数据路径时计算 checksum，在数据对象通过控制路径返回客户端时验证 checksum。
- **数据路径**：通过 re-execution 验证。数据路径操作符（closure）的输入、输出和所有生成的 data versions 被记录在 closure log 中，验证器在另一个 core 上重新执行闭包并比较结果。

**Versioned Memory**：所有用户数据对象通过 `OrthrusPtr` 访问，更新操作创建新的 data version（out-of-place），而非 in-place 修改。版本化使得验证器可以重放与原始执行完全相同的内存视图，且 APP 和 VAL 之间完全解耦，支持 out-of-order 验证。

**Sampling-based 验证**：当验证资源受限时，Orthrus 优先验证：(1) 长时间未验证的 closure（基于 caller 上下文）；(2) 包含 FP/vector 指令的 closure（CPU 错误高发区域）。验证延迟反馈触发采样率动态调整。

## 设计与实现

Orthrus 包含以下核心组件：

**1. 用户数据标注与编译器支持**
开发者只需做两件事：(1) 用 `#pragma user-data` 标注表示用户数据结构的类（如 HashMap、Tree）；(2) 用 `#pragma closure` 标注数据操作符函数（如 get、set、map）。编译器自动识别用户数据对象的分配点，将 `new` 替换为 `OrthrusNew`（分配到 versioned memory），将指针替换为 `OrthrusPtr`（支持版本化访问）。

**2. OrthrusPtr 和版本化**
`OrthrusPtr<T>` 提供 `load()` 和 `store()` 方法。`load()` 返回只读数据；`store()` 总是创建新的 data version 并记录在 closure log 中。版本化完全消除 APP 和 VAL 间的状态依赖，VAL 可在任何时间验证任意 closure log。

**3. Closure Log**
Closure 执行结束后生成 log，包含：closure ID、input 版本、output 版本、系统调用记录结果、时间戳。Log 足够自包含，验证器可以仅凭 log 重放 closure 的完整执行。

**4. 验证器（Validator）**
Validator 进程使用 Shenango 用户级线程 runtime 构建，支持微秒级 core 重新分配。Scheduler 将 idle core 分配给验证任务，优先选择与 APP 在同一 NUMA node 但不同物理 core 的 core（共享 L3 cache 但计算单元隔离）。Work-stealing 机制平衡验证负载，减少尾延迟。

**5. Safe Mode（可选）**
默认配置下验证不阻塞结果返回。启用 Safe Mode 后，只有已完成验证的 closure 结果才返回给用户，适用于对数据一致性要求极高的场景。由于 SDC 罕见，论文报告 Safe Mode 的性能开销很小（< 2%）。

**6. Memory Reclamation**
Versioned memory 会增加内存消耗。Orthrus 使用近似垃圾回收算法：当验证器完成某 closure 的验证后，扫描所有活跃 closure 的起始时间，回收"可见窗口"（visible window）在最早活跃 closure 之前的 data versions。实验显示该算法将内存开销降低至 ~20%。

## 主要实验结果

**应用性能**：
- Orthrus 平均引入约 4% 的执行时间开销和 25% 的内存开销。相比之下，RBV 引入约 2.0× 执行时间开销和 2.1× 内存开销。
- Memcached-Orthrus 吞吐量是 Memcached-RBV 的 1.6 倍，因为 Orthrus 使用共享内存 log 传递而 RBV 需要跨服务器通信。Phoenix-Orthrus 吞吐量仅降低 < 2%，而 Phoenix-RBV 降低 51%。

**验证延迟**：
- Orthrus 平均验证延迟为 1.6 µs（Memcached）、234 ms（Phoenix）、22.6 µs（Masstree）、7.7 µs（LSMTree），比 RBV 低 2-3 个数量级。
- 高速验证来自三个因素：(1) Orthrus 支持 out-of-order 验证（版本化），RBV 必须顺序验证；(2) Orthrus 只验证数据路径，RBV 重放整个程序；(3) Orthrus 使用共享内存通信，无需网络同步。

**SDC 覆盖率（双倍验证资源）**：
- RBV 检测 98.3%-99.8% 的 SDC；Orthrus 检测 97.2%-98.9% 的 SDC。
- Orthrus 未检测到的 SDC 主要来自：(1) 控制路径中的错误（checksum 检测不到的情况）；(2) 系统调用中的错误（VAL 不重放 syscalls）；(3) 极低概率的 double-error（两个 core 产生相同错误）。

**不同资源下的覆盖率**：
- 单个验证 core：Orthrus 平均检测 86.7% 的 SDC，比随机采样高 1.41 倍。
- 两个验证 core：91%；四个验证 core：96%。

## 潜在问题 / 局限性

**1. 无法检测 masked errors**：论文坦然承认 Orthrus 无法检测不影响最终计算结果的 masked errors（如 Listing 1 中分支条件计算出错但不影响分支走向）。这是设计上的取舍，因为 masked errors 不影响用户数据，但可能影响部分计算结果的正确性。

**2. 控制路径错误的检测盲区**：即使使用 checksum，CPU 错误发生在控制路径影响执行流时（如比较指令错误导致调用了错误的函数），checksum 可能无法检测。虽然论文认为这类错误"extremely low probability"，但没有提供具体数据支持。

**3. 系统调用的验证盲区**：VAL 不重放系统调用（socket read、mutex 等），而是使用记录的返回值。如果 CPU 错误发生在系统调用本身（如 `write` syscall 返回错误值），Orthrus 无法检测。论文辩称系统调用只占执行指令的 0.04%，概率极低，但未考虑 CPU 错误可能集中在特定指令类型的问题。

**4. 评估的代表性局限**：实验使用的应用（Memcached、Masstree、LSMTree、Phoenix）主要是 in-memory 数据结构和 MapReduce 类应用，可能无法代表更广泛的云应用类型。复杂应用（如包含外部存储、网络通信的微服务）的适用性未被验证。

**5. Double-error 场景**：如果 APP 和 VAL 所在的两颗 core 以完全相同的方式产生错误（极低概率但理论上可能），Orthrus 将无法检测。虽然论文承认这一点，但未量化此风险的量级。

**6. 采样覆盖的随机性**：在资源受限环境下，自适应采样虽然优先验证未验证和 FP/vector 密集的 closure，但仍存在统计意义上的检测盲区，无法保证任何时刻的 SDC 都能被检测。论文称其为"best-effort"工具，这是诚实的定位，但也意味着 Orthrus 不能替代 RBV 在高安全要求场景下的作用。

**7. 开发者标注负担**：虽然论文声称"fewer than 20 lines of code needing modification"，但实际需要对应用程序有较深理解（哪些是用户数据类、哪些是 closure），且编译器仅支持 C/C++，对其他语言的应用（如 Go、Rust）需要重新实现。

## 未来工作

- 将 Orthrus 扩展到更多应用类型（分布式系统、包含持久化存储的应用等）。
- 探索自动推断控制路径与数据路径边界的方法，减少开发者标注负担。
- 研究降低 double-error 概率的方法（如多核投票）。
- 将采样策略与 CPU 错误率估计结合，实现更智能的资源分配。

## 个人评注

Orthrus 解决的是一个越来越重要但一直被忽视的问题——云规模下的 CPU 静默计算错误。其核心技术洞察——利用应用代码的控制路径/数据路径分离来降低验证开销——是一个优雅且实用的设计选择。Versioned memory + out-of-order validation 的组合显著降低了验证延迟，这是论文最关键的技术贡献。

然而，Orthrus 的设计哲学是"practicality first"——接受 best-effort 的覆盖率，换取生产环境可接受的低开销。这种权衡在云环境中是合理的，但用户需要清楚地理解 Orthrus 能做什么、不能做什么。论文坦诚的局限性讨论值得肯定。

实验结果显示了显著的优势（1.9× faster than RBV），但需要注意的是，RBV 作为 comparison baseline 本身是一个高开销方案。更有意义的比较可能是：在相同的资源预算下（如同样的 1 个额外 core），Orthrus vs 什么都不做的覆盖率是多少？论文给出了 87% 的数字（单 core），但没有给出在相同条件下 RBV 的表现。

总体而言，Orthrus 代表了云可靠性领域一个重要且实用的发展方向。它不是银弹，但在云服务提供商重视成本与可靠性平衡的背景下，Orthrus 提供了一个切实可行的中间路线。
