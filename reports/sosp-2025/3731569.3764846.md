# COpter: Efficient Large-Scale Resource-Allocation via Continual Optimization

## 一、背景

资源分配（Resource Allocation）是现代计算系统的核心问题——将有限的资源（GPU、网络带宽等）分配给竞争性的请求（训练任务、网络流等）。许多系统采用数学规划方法，将资源分配建模为线性规划（LP）或混合整数线性规划（MILP），借助商业求解器（CPLEX、Gurobi）求解。

然而，随着基础设施规模的爆炸式增长——深度学习集群从数千 GPU 扩展到 10 万+ GPU——现有求解器在大规模问题上面临严重的可扩展性瓶颈。例如，将 Sia 调度器的 MILP 从 10k GPU 扩展到 25k GPU，求解时间增长约 100×，导致在 1 分钟调度轮次内能按时完成的问题比例从 85% 骤降至 15%。

实际系统不得不在「频繁全局优化」和「实时调度截止时间」之间艰难取舍：Meta 的 RAS 每小时才做一次优化，MAST 每天一次，其余时间依赖启发式 fast-path。

---

## 二、要解决的问题

1. **编译开销巨大且重复浪费**：每轮调度都需要从零构建约束矩阵，即使问题只有微小变化。在 25k GPU 实验中，CVXPY 构建 CPLEX 模型耗时中位数 226s，而求解仅需 11s——编译成本反超求解成本。
2. **求解器无法有效复用历史计算**：Simplex 和 Interior-Point 方法依赖的矩阵分解（basis/barrier factorization）在问题微调后必须重建，前一轮的所有计算努力被丢弃。warm-start 在理论上可行但实际收益有限——ℓ₂ 距离小不代表 Simplex 的多面体顶点路径短，也不代表 Interior-Point 的 central path 近。
3. **MILP 整数化的组合爆炸**：Branch-and-cut 在大规模问题上需要求解指数级多的子 LP，成为端到端运行时的主要瓶颈，且运行时不可预测（90th 和 100th 百分位之间可达 30× 差异）。
4. **问题分区（POP）的质量-速度权衡**：POP 通过随机分区并行求解子问题来提速，但子问题之间缺乏全局协调，导致分配质量下降（如 Sia 场景中 POP 使平均 JCT 增加 11–17%）。

## 三、洞察与设计

**关键洞察**：大规模资源分配问题在相邻调度轮次之间是**缓慢演化**的——在足够短的轮次间隔（2–5 分钟）内，绝大多数资源和请求保持不变（<0.01% 的变量改变值，仅少量变量被添加/移除），最优解之间的 ℓ₂ 距离也很小。然而，现有方法将每轮视为独立问题，完全忽略了这种跨轮次的结构性。

基于这一洞察，COpter 提出 **Continual Optimization** 范式——将轮次式资源分配重新建模为一系列相互关联的优化问题序列，目标是使总端到端求解时间依赖于问题的「路径长度」（path length）P_η(T) 和 P_x(T)，而非每轮问题的绝对规模。

COpter 的三大核心设计：

1. **差分问题更新接口（Differential Interface）**：不再每轮重新编译整个约束矩阵，而是通过 `add-request`、`remove-request`、`add/remove-resources` 等操作对矩阵进行 in-place 增量修改。采用 List-of-List（LoL）稀疏矩阵表示替代传统 CSR/CSC，在修改效率和访问延迟之间取得平衡。

2. **无分解、可高效 warm-start 的 LP 求解器**：采用 Proximal Point Algorithm（PPA）作为核心求解算法，通过对偶坐标下降 + 活跃集策略实现。PPA 不依赖矩阵分解，仅使用稀疏矩阵-向量乘法和极少内部状态，因此（a）问题变化时无需重建分解，（b）上一轮的解可以直接作为高质量初始化点，且 PPA 能可证明地从 ℓ₂ 距离近的初始化中获益。

3. **轻量级整数化 Shim**：观察到 PPA（和 Simplex）求解 LP 松弛后，≥99.99% 的变量值已经是 0 或 1，仅有 ≤0.01% 为分数值。因此用简单的 problem-specific 启发式（如贪心选最大权重配置）即可快速恢复可行整数解，完全绕过 Branch-and-cut。

## 四、实现细节

- **稀疏矩阵存储**：LoL 格式，行操作（添加/删除约束）通过指针操作 O(1) 完成；列操作（添加/删除变量）因矩阵稀疏只影响少量行，可简单并行化。
- **PPA 实现**：基于对偶坐标下降（dual coordinate descent）+ 活跃集策略（active set），仅使用稀疏矩阵-向量原语。利用问题和解的稀疏性加速计算。
- **Shim 设计**：
  - **GPU 调度（Sia）**：对每个 job，选择 LP 松弛解中权重最大的 configuration，在不违反 GPU 容量约束的前提下分配；无法分配则本轮跳过。
  - **Shard 负载均衡**：将 LP 松弛的分数解四舍五入为二值解，快速局部修正恢复约束可行性。
  - **WAN TE**：纯 LP 问题，无需整数化。
- **与 POP 组合**：对于 COpter 仍无法处理的超大问题，可先用 POP 分区，再对每个子问题应用 COpter。
- 求解器使用少量 CPU 线程即可处理百万级变量的问题。

## 五、实验结果

COpter 在三个领域进行了评估：

### GPU 集群调度（Sia Policy）

| 指标 | COpter vs 商业求解器 | COpter vs POP |
|------|---------------------|---------------|
| 求解加速 | 57–83× | 1.5–30× |
| 平均 JCT | 仅增加 <1%（vs LP*） | POP 增加 11–17% |
| Makespan | 可比 | POP 增加 6% |
| 运行时可预测性 | 90th–100th 百分位仅 2–3× 差异 | POP 达 30× 差异 |
| 最大问题规模 | 1100 万变量，70.4s | - |

### Shard 负载均衡

| 配置 | 方法 | 运行时 | 负载不均衡 | Shard 移动 |
|------|------|--------|-----------|-----------|
| 1024 shards, 128 servers | COpter | 最快 | 满足 <10% 约束 | 最少（超越最优） |
| 同上 | Exact (MILP) | 基线 | 完美 | 较多（振荡） |
| 2048 shards, 256 servers | Exact | 数小时/轮 | - | - |
| 同上 | COpter | 比 LP-Relaxed 快 2.8× | 满足约束 | 最少 |

COpter 和 LP-Relaxed 出现了「超最优」现象——由于 LP 松弛 + Shim 的时间稳定性，避免了 Exact 解的删除-重建振荡。

### WAN 流量工程

| 拓扑 | 流量分布 | COpter 加速 | COpter 流量分配质量 |
|------|---------|-------------|-------------------|
| Kdl | Poisson | 远超 5 分钟截止线 | >99.9% 最优 |
| ASN | Poisson | <1 分钟 | 所有方法中最高 |
| Kdl | Bimodal | <1 分钟 | 最高 |
| ASN | Bimodal | 30× vs POP | 比 POP 多 1.5% 流量 |

### 收益归因（10k GPU，Sia LP 松弛）

| 技术 | 平均加速 |
|------|---------|
| 稀疏感知自定义求解器 | 5× |
| 差分问题更新 | 3.5×（叠加） |
| 高效 warm-start | 1.5×（叠加） |
| **总计** | **24×**（LP），预计 24–72×（MILP） |

## 六、批判性分析

1. **「缓慢演化」假设的适用边界未充分讨论**：论文的所有理论保证和加速比都依赖于 α≪1, β≪1 的假设。但现实中存在突发事件——大规模节点故障、流量突增、批量任务提交——这些场景下路径长度会骤增。论文没有系统性地评估 COpter 在这些 regime 下的退化程度，仅提到「允许 burst，只要不太频繁」。

2. **Shim 的质量保证缺乏理论支撑**：轻量级整数化是 COpter 绕过 Branch-and-cut 的关键，但其正确性完全依赖经验观察（LP 松弛解 ≥99.99% 已是整数）。论文未给出任何关于何时 LP 松弛会产生大量分数解的分析，也未讨论当分数变量比例显著增加时 Shim 的退化行为。

3. **PPA 求解器的收敛精度问题**：First-order 方法以收敛慢到高精度解著称。论文声称 PPA 有「有限步收敛」，但这依赖于特定参数选择和问题结构。在约束紧的场景（如 GPU 几乎满载），微小的次优性可能导致可行性问题，但论文对求解精度的敏感性分析不足。

4. **实验基线选择的公平性**：在 WAN TE 实验中，LP-All 使用 Gurobi 的 8 线程配置，而 COpter 使用「几个 CPU 线程」。如果给商业求解器更多并行资源或使用最新版本的分布式求解能力，差距可能缩小。论文也未与 Teal、DOTE 等 learning-based 方法做端到端对比。

5. **LoL 稀疏矩阵的缓存效率代价**：论文承认 LoL 格式牺牲了缓存友好的连续内存布局，但未量化这在大规模问题上的实际性能影响。随着问题规模继续增长，缓存效率的损失可能侵蚀部分增量更新带来的收益。

6. **问题建模的通用性**：三个 case study 都是经典的、约束矩阵高度稀疏的 LP/MILP。对于约束更密集或非线性目标的资源分配问题，COpter 的适用性不明。

## 七、AI Infra / MLSys 视角

1. **对大规模 GPU 集群调度的直接价值**：COpter 能在 25k GPU 集群上实现 1 分钟轮次的全局优化，这对当前 10 万+ GPU 的超大集群意义重大。频繁全局优化已被证明能显著提升利用率和降低 JCT（Sia、RAS 等工作的核心发现），COpter 让这一理想在实际规模下变得可行。

2. **与现有调度框架的集成机会**：COpter 的差分接口设计天然适合事件驱动的调度架构——每当 job 到达/完成/故障时，只需增量更新问题而非重建。可以探索将 COpter 集成到 Kubernetes 调度器、Rebalancer 等框架中，作为可插拔的求解后端。

3. **训练/推理混合负载调度**：当前大模型训练和推理服务共享 GPU 集群成为趋势。推理负载波动快，训练负载相对稳定——这恰好符合 COpter 的「缓慢演化」假设（大部分分配不变，仅推理部分频繁微调）。这是一个值得探索的应用场景。

4. **可操作的 future work**：
   - **异构加速器调度**：将 COpter 扩展到 GPU/TPU/专用加速器混合集群的 MILP 调度，评估 Shim 在更复杂整数约束下的表现
   - **分布式 COpter**：当前 COpter 在单机少量 CPU 线程上运行，探索将 PPA 的坐标下降分布式化以处理更大规模问题
   - **自适应轮次间隔**：根据路径长度的实时估计动态调整调度间隔——变化大时缩短间隔、增加求解预算，变化小时拉长间隔

---

## 八、总结

COpter 提出了 Continual Optimization 范式，将轮次式资源分配从独立问题序列重新建模为相互关联的优化序列，通过差分更新接口、无分解 PPA 求解器和轻量级整数化三项技术，在 GPU 调度、Shard 负载均衡和 WAN 流量工程三个领域实现了 57–83× 的求解加速和优于 POP 的分配质量。其核心适用条件是问题的「缓慢演化」特性——在大规模基础设施中这是常态。主要局限在于 Shim 的质量保证依赖经验、PPA 的高精度收敛特性需要更多验证、以及对突发变化场景的鲁棒性有待深入研究。
