# COpter: Efficient Large-Scale Resource-Allocation via Continual Optimization

**作者**：Suhas Jayaram Subramanya（Microsoft / CMU）、Don Kurian Dennis（Meta / CMU）、Virginia Smith（CMU）、Gregory R. Ganger（CMU）
**会议**：SOSP '25（ACM SIGOPS 31st Symposium on Operating Systems Principles，2025年10月，首尔）
**DOI**：https://doi.org/10.1145/3731569.3764846
**源文件**：[3731569.3764846.pdf](../../papers/sosp-2025/3731569.3764846.pdf)

---

## 一、背景

现代大规模计算系统中，资源分配（Resource Allocation, RA）是核心问题——GPU 集群调度需要将数万块 GPU 分配给并发训练任务，WAN 流量工程需要将流量分配到链路以最大化吞吐或最小化延迟，弹性数据库需要将 shard 负载均衡到服务器集群。学术界和工业界已广泛采用数学规划方法（LP / MILP）来建模这些问题，商业求解器（如 CPLEX、Gurobi）提供了最优化保证。

然而，随着基础设施规模快速膨胀——深度学习集群 GPU 数量从 2019 年的数千块增长到如今的 10 万块以上——现有求解方法面临严峻的扩展性挑战：求解时间随问题规模急剧增长，已无法满足生产系统对实时调度的需求。当前应对策略（降低调度频率、问题分区 POP）不得不在质量与延迟之间妥协。

---

## 二、要解决的问题

**三个核心瓶颈**：

1. **重编译开销巨大**：传统方法每轮从头构建约束矩阵。在 25k GPU 集群实验中，使用 CVXPY 构建 CPLEX 模型耗时中位数达 226 秒，而求解本身仅需 11 秒——编译开销反而是主要瓶颈。一旦有少量资源变动（新 job 到来或 GPU 故障），整个约束矩阵必须完全重建。

2. **求解器无法有效利用轮间相似性**：资源分配问题在连续两轮之间通常变化极小（图 2 显示 25k GPU 集群中每轮变化的变量数 < 0.01%）。然而，Simplex 和 Interior-Point 方法维护的内部分解（矩阵因式分解、基）对问题的微小改动极为敏感，无法从上一轮的计算成果中高效继承。

3. **MILP 整数化阶段的组合爆炸**：大规模 MILP 求解器依赖 branch-and-cut，随问题规模的指数级搜索开销使其在 25k GPU 量级几乎不可用。将 10k GPU 集群扩展到 25k 时，求解时间增加约 100 倍。

现有替代方案（POP 分区、降低调度频率、提前终止）只能缓解而非根本解决问题，且以牺牲分配质量或全局最优性为代价。

## 三、核心设计

COpter 提出**持续优化（Continual Optimization）**范式，将轮次制资源分配问题重新建模为一组相互关联的优化问题序列，而非独立的单轮问题实例。其目标是让求解的总时间与问题的"演化路径长度"（path length）成比例，而非与问题规模的幂次成比例。

**三大技术创新**：

### 1. 差分问题更新接口（Differential Problem Update Interface）

COpter 为约束矩阵 $A$ 维护一个 List-of-List（LoL）稀疏表示，支持以下原语：
- `add-request(id, num_vars)`：在矩阵中追加列，更新受影响约束行
- `remove-request(id)`：删除对应列及相关约束行
- `add/remove-resources(id, count)`：修改右端向量 $b$

LoL 表示牺牲了 CSR/CSC 的缓存友好性，换取了 O(1) 行级增删和稀疏感知的列操作，实测降低编译时间 30×。

### 2. 无因式分解、可高效热启动的 LP 求解器

抛弃 Simplex / Interior-Point（均依赖矩阵分解，分解失效于问题变化），选用**近端点算法（Proximal Point Algorithm, PPA）**：
- PPA 将 LP 转化为一系列无约束二次规划（$\ell_2$ 收缩），内部状态简单且不依赖因式分解
- PPA 可被证明从接近最优的初始点出发时加速收敛（provable warm-start benefit）
- PPA 迭代自然收敛到极点，实验中约束矩阵的 LP 松弛解有 ≥ 99.99% 的变量为 0 或 1，天然适合后续整数化
- 通过对偶坐标下降结合 active set 策略实现，仅使用稀疏矩阵-向量操作，少量 CPU 线程即可高效运行

### 3. 轻量整数化 Shim

针对 MILP 问题，在 LP 松弛求解后用问题特定的 shim 启发式方法恢复可行整数解：
- GPU 调度 shim：对每个 job 选权重最高的配置（不超 GPU 容量）
- Shard 负载均衡 shim：贪心删除超出内存容量的 shard 副本，负载比例重新分配
- 有意优先恢复可行性而非最优性，毫秒级完成，绕过了 branch-and-cut 的指数搜索

**与 POP 结合**：对于过大的问题，COpter 可与 POP 配合，先分区，每个子问题再用 COpter 独立加速。

## 四、实现细节

- **约束矩阵存储**：LoL 稀疏格式，行操作通过指针操作完成，列操作因矩阵稀疏性仅影响少数行并可并行化
- **PPA 实现**：对偶坐标下降 + active set，仅使用稀疏矩阵-向量乘法，状态极简，便于热启动
- **Shim 设计**：每种应用场景定制，目标是毫秒级快速恢复可行二值解
- **实验平台**：2-socket AMD EPYC 7742 64 核处理器 + 1TB DDR4；求解器限制 8 线程（超过 8 线程无显著加速）
- **评估方式**：基于真实生产 trace 的 trace-driven 仿真

## 五、实验结果

### GPU 集群调度（Sia 策略 MILP）

| 指标 | LP*（商业 LP 求解器） | POP-16 | COpter |
|------|------|------|------|
| 平均 JCT（10k GPU） | 0.35h | 0.41h | 0.36h |
| Makespan（10k GPU） | 29.3h | 31.0h | 29.4h |
| 求解时间 p99（10k GPU） | 233.4s | 2.9s | 6.5s |
| 求解时间 p99（25k GPU） | 2277s | 66.5s（超截止） | 40.3s |

- COpter 比 LP* 快 **30-40×**，分配质量相当
- POP 在 25k GPU 时超过 60 秒截止时间，且平均 JCT 和 makespan 劣于 COpter
- COpter 运行时间可预测（90th/100th 百分位仅 2-3× 差异），而 POP 因 MILP 不确定性有 30× 以上波动

### Shard 负载均衡

- COpter 比 LP-Relaxed（同求解器但无热启动）快 **2.8×**
- 相比 Exact（商业 MILP 求解器）快 **57-83×**，负载均衡质量相当甚至更优（"super-optimality"现象）
- POP-8/16 虽快，但无法控制跨子问题的负载不均衡

### WAN 流量工程

- 在 ASN 拓扑（大规模）上比 POP-128 快 **30×**，同时多分配 1.5% 流量
- 流量分配质量达到最优的 99.9%，而 POP-128 在 Bimodal 分布下需要多天才能完成单轮
- LP-All（全量 Gurobi）在 ASN 拓扑上每轮超过 24 小时，实际不可用

### 各组件加速归因（10k GPU 集群 LP 松弛）

| 技术 | 平均加速倍数 |
|------|------|
| 稀疏感知无因式分解求解器 | **5×** |
| 差分问题更新接口 | **3.5×** |
| 热启动 | **1.5×** |
| **总计** | **~24×** |

## 六、批判性分析

**1. 实验规模依赖 trace-driven 仿真，非真实集群验证**

论文所有实验均通过仿真完成，理由是"25k GPU 集群对学术研究不可访问"。这是合理说明，但仿真的工作负载是将真实 trace 的 job 映射到 10 个"代表性 job"，大幅简化了真实系统的多样性。Sia 原论文本身也是仿真评估，但多套管假设的叠加可能使结果与生产差距更大。

**2. 热启动增益被低估，实际收益取决于应用场景**

论文将 warm-start 的贡献标注为 1.5×，而差分更新接口贡献 3.5×。但在负载均衡实验（shard/server 集合不变）中，差分更新几乎无收益，热启动才是主要来源。实验场景的选取可能略微高估了差分更新的普遍价值。

**3. Shim 的"super-optimality"解释值得怀疑**

论文将 LP-Relaxed 和 COpter 在负载均衡中优于 Exact 的现象解释为 LP 解的"隐式稳定性"——shim 减少了 shard 来回移动的震荡。但这更多是问题建模的人工产物（删除副本无惩罚），而非真正意义上的"优于最优"。用一个有建模缺陷的问题来展示"超越最优"，会让读者误以为 LP 松弛本身就更好。

**4. POP 对比中的线程数设置存在疑点**

作者将 POP 的每个子问题限制为单线程，通过数学估算 64 核并行运行时间。这种估算隐含了完美的负载均衡假设，而真实场景中 MILP 子问题运行时不可预测（论文自己指出 30× 的百分位差异），理想化的并行估算可能高估了 POP 的有效性。

**5. 适用范围限制被轻描淡写**

COpter 明确不适用于无状态函数（serverless）、数据库查询调度等"快速变化"场景。但这些场景恰恰是当前 AI 推理服务的重要模式（token-level scheduling、prefill-decode 分离后的快速请求调度）。论文对边界案例的处理（α 和 β 接近 1 时）缺乏充分讨论。

## 七、AI Infra / MLSys 视角

**直接相关性**

GPU 集群调度（Sia 策略）本身就是核心 AI Infra 问题。COpter 将 Sia 的 MILP 求解从分钟级降到秒级，直接使能更高频率的全局调度，论文实验已证明对 JCT 和 makespan 有实质改善。

**可迁移的技术 insight**

1. **"问题演化缓慢"是通用 insight**：LLM 推理集群的负载分配（per-request routing、KV cache placement）、分布式训练的动态资源重分配（Elastic Training）本质上也是缓慢演化的 RA 问题——绝大多数请求/任务在相邻轮次延续，COpter 的范式同样适用。

2. **PPA 的天然整数性是 bonus**：LP 松弛解自然趋于二值（≥ 99.99%），意味着无需 branch-and-cut 就能直接得到高质量整数解。这对 AI 集群中大量二值决策（任务放或不放）极具价值。

3. **差分接口设计思路**：在线调度系统中，约束变化（新 job、GPU 故障）频繁但局部，差分更新接口的设计思路可推广到其他基于规划的系统组件（如数据流编排、模型并行切分的在线重规划）。

**值得跟进的方向**

- **LLM 推理服务中的应用**：将 COpter 应用于 disaggregated prefill-decode 系统（如 Mooncake、Splitwise）的全局负载均衡和 KV cache 迁移决策，这些问题同样是慢变 MILP，且当前缺乏高效全局优化器
- **与神经网络启发式方法的结合**：Teal（WAN TE）用 RL 做快速在线分配，COpter 提供高质量全局解作为监督信号或安全回退，二者互补
- **多集群 / geo-distributed 场景**：MAST（OSDI'24）做全球多集群调度，其 MILP 同样面临扩展性挑战，continual optimization 范式在多数据中心场景下的路径长度特性值得研究

---

## 八、总结

COpter 通过"持续优化"范式将轮次制资源分配问题从"每轮独立求解"重新建模为"利用轮间相似性摊薄求解开销"，结合差分矩阵接口、PPA 热启动求解器和轻量 shim 三项技术，在 GPU 调度、负载均衡和 WAN 流量工程三个场景上实现了 57–83× 的求解加速，同时不牺牲分配质量。其主要局限在于对"慢变"假设的强依赖——在无状态请求密集型场景（serverless 推理等）效果有限——以及所有评估均基于仿真而非生产环境验证。对于从事 AI 集群调度和资源管理的研究者，COpter 提供了一套可直接落地的高效求解器框架，且其核心思想对在线调度系统有广泛的迁移价值。
