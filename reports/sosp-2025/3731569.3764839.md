# Sailor: Automating Distributed Training over Dynamic, Heterogeneous, and Geo-distributed Clusters

**作者**：Foteini Strati*, Zhendong Zhang, George Manos, Ixeia Sánchez Périz, Qinghao Hu, Tiancheng Chen, Berk Buzcu, Song Han, Pamela Delgado, Ana Klimovic（ETH Zurich, MIT, HES-SO）

## 一、背景

大规模 ML 训练对 GPU 的需求持续增长，但公有云和企业集群中高端同构 GPU（如 A100、H100）的可用性严重受限。数据中心通常部署了多代、多类型 GPU，分布在不同的可用区和地理区域。然而，主流分布式训练框架（Megatron-LM、DeepSpeed）假设同构集群和统一的节点间带宽，导致模型开发者无法充分利用异构资源。同时，电力和冷却限制了单个数据中心可部署的 GPU 数量，下一代超大模型可能需要跨多个可用区训练。使用旧 GPU 还能减少 embodied carbon 排放。

---

## 二、要解决的问题

1. **配置搜索空间爆炸**：异构 GPU 类型和跨区域部署使得资源分配与并行策略的联合搜索空间呈指数增长。现有系统要么不联合优化资源分配和并行化计划（Aceso、Galvatron），要么搜索时间过长（Metis 需要数小时），不适合动态环境。
2. **模拟器不准确**：现有 planner 的内存和迭代时间估计严重偏差——Varuna 遗漏优化器、通信等内存开销导致 OOM；FlashFlex 使用理论 FLOPS 预测运行时间误差高达 69%；多数系统忽略异构环境中的 straggler 效应和 per-GPU 内存差异。
3. **训练框架不支持异构配置**：Megatron-LM 等框架假设全局统一的并行度和 microbatch 大小，无法为不同 GPU 类型分配不同的 TP 度和 microbatch size 以实现负载均衡。同时缺乏弹性重配置能力以应对资源动态变化。

---

## 三、洞察与设计

**关键洞察**：在异构集群中，资源分配和并行化策略必须联合优化——固定资源拓扑再搜索并行策略，或反过来，都会错过全局最优。而通过将 pipeline 各 stage 的资源分配问题分解为可复用子问题，利用动态规划结合领域启发式剪枝，可以在秒级内完成搜索。

Sailor 是一个端到端的异构分布式训练系统，由四个组件组成：

1. **Profiler**：在每种 GPU 节点上进行单节点 profiling，收集每层的前向/反向/更新时间、参数量、激活内存等；同时测量不同节点对之间的网络带宽并拟合多项式函数。对于有重复层的模型（如 Transformer），只 profile 一个代表层，开销仅需几分钟。

2. **Planner**：联合搜索资源分配和 3D 并行化策略（DP/PP/TP + microbatch size），支持用户定义的优化目标（最大吞吐 / 最小成本）和约束（预算 / 最低吞吐）。核心技术：
   - **启发式剪枝（H1-H6）**：限制 TP 在节点内（H1）、提前排除 OOM 配置（H2）、按递减/递增顺序搜索 DP 度（H3/H4）、将 DP 通信限制在单 region 内而 PP 可跨 region（H5）、合并同 region 的 zone（H6）
   - **动态规划**：将每个 pipeline stage 的资源分配建模为子问题，目标是最小化迭代时间（包括 straggler 和同步开销），通过复用中间结果高效求解

3. **Simulator**：准确模拟异构配置的内存占用（包括模型参数、优化器状态、激活、通信 buffer、碎片化等）和迭代时间（建模 compute、communication、pipeline bubble、straggler），平均误差仅 4.5%。

4. **Training Framework**：基于 Megatron-DeepSpeed 扩展，支持异构并行度（不同 stage 可有不同 TP 度）、异构 microbatch size、容错与弹性重配置。

## 四、实现细节

- **Profiling**：使用 PyTorch hooks 收集每层的计算时间和内存信息，CUDA Events 进行精确 GPU 计时，PyTorch CUDA memory allocator 追踪内存分配。网络 profiling 使用 NCCL 后端的 PyTorch collectives，变化消息大小并拟合多项式。
- **动态规划求解**：`solve_dp()` 函数为每个 stage 生成所有合法的 GPU 类型组合，为每个组合找到下一个可用 region，递归地为后续 stage 分配剩余资源。引入成本约束时，因为迭代时间依赖于未知的 straggler stage，采用迭代近似：先假设当前 stage 是 straggler，计算剩余预算，若找到解则检查实际 straggler 是否一致，不一致则调整预算重新迭代。
- **框架改造**：在 Megatron-DeepSpeed 上新增支持——每个 pipeline stage 可配置独立的 TP 度和 GPU 类型，不同 stage replica 可使用不同 microbatch size。弹性重配置流程：controller 调用 planner（~0.1s）→ worker cleanup（~3s）→ 广播新拓扑（~1.25s）→ 重建 NCCL 通信组（~4.5s）→ 重建模型/优化器/dataloader（~2.5s），总计约 11s（小规模）。
- **开源**：https://github.com/eth-easl/sailor

## 五、实验结果

**实验模型**：OPT-350M、GPT-Neo-2.7B
**GPU 类型**：A100-40GB、V100、GH200
**环境**：Google Cloud 多 zone/region，以及模拟器大规模评估

### Simulator 准确性

| Planner | 内存估计平均误差 | 迭代时间估计平均误差 |
|---------|-----------------|---------------------|
| Varuna | ~95% | 28% |
| Piper | ~80% | 47% |
| FlashFlex | ~60% | 69% |
| Metis | ~25% | 28% |
| **Sailor** | **~5%** | **4.5%** |

### 同构集群（A100 only）

- Sailor 吞吐比最优 baseline（DTFM）提升 1.15×，比 Aceso 提升最高 5.7×

### 异构集群（A100 + V100）

| 场景 | vs AMP | vs FlashFlex | vs Metis |
|------|--------|-------------|----------|
| 50/50 比例 | 1.9× | 2.03× | 1.15× |
| 25/75 比例 | 1.57× | 1.55× | 1.39× |

- Sailor 不产生任何 OOM 配置，而 Metis 在 GPT-Neo 上产生 20-68 个无效 OOM plan

### 跨地域分布

- 比 DTFM 吞吐提升 5.9×，成本降低 9.48×
- Sailor 发现只用 1 个 region 内所有 zone 即最优，不必跨 region

### 成本优化

- 最小化成本场景：比次优 baseline（Galvatron）降低 40% 成本
- 吞吐约束下：比所有 baseline 高 1.65-3× 吞吐，同时满足预算约束

### 搜索时间

| Planner | 128 A100+384 V100 搜索时间 |
|---------|--------------------------|
| Metis | 300s（上限截断） |
| FlashFlex | 222.64s |
| AMP | 86.41s |
| **Sailor** | **17.4s** |

## 六、批判性分析

1. **仅支持 1F1B 调度**：Planner 和 Simulator 只支持 1F1B pipeline schedule，不支持 Interleaved 1F1B、Zero Bubble 等更先进的调度策略。对于追求极致性能的场景，这是显著局限——1F1B 的 pipeline bubble 比例较高，而异构环境中 bubble 的影响更为严重。
2. **模型规模偏小**：核心实验使用 OPT-350M 和 GPT-Neo-2.7B，属于小模型。对于 7B+ 甚至 70B+ 模型，搜索空间和内存建模的复杂度会显著增加。3 种 GPU 类型 256 GPU/type 的搜索时间已达 4900 秒（~82 分钟），可扩展性存疑。
3. **不支持 MoE 模型**：论文明确指出 profiling 方法仅适用于 dense layers，MoE 模型因动态负载被留作 future work。这在当前 MoE 模型日益流行的趋势下是一个重要缺失。
4. **弹性重配置的 NCCL 初始化瓶颈**：论文承认在千卡级别 NCCL 初始化可能需要分钟级时间，但仅在 16 GPU 上展示了 ~11s 的重配置时间，缺乏大规模验证。
5. **实际 GPU 实验规模有限**：真实硬件实验最大仅 24 GPU（8 A100 + 16 V100），大规模结果全部依赖模拟器。虽然模拟器误差低，但并未在数百 GPU 上验证端到端训练的正确性和稳定性。
6. **成本模型简化**：成本计算基于 GPU 小时价格 + 数据传输费用，未考虑 spot instance 的抢占风险、实际定价波动等。
7. **启发式的最优性丢失**：H5（DP 通信限制在单 region）和 H6（合并同 region zone）虽然加速了搜索，但可能在某些拓扑下剪掉最优解。论文未量化这些启发式导致的性能损失。

## 七、AI Infra / MLSys 视角

1. **联合优化资源分配和并行策略的范式值得借鉴**：当前大部分 AI Infra 的训练调度系统将资源分配和并行策略视为两个独立问题。Sailor 证明了联合优化的价值——在异构环境中，仅优化其一会导致显著的性能损失。这一思路可以扩展到训练集群调度器（如 Kubernetes-based ML scheduler）中。

2. **Simulator 的设计思路可迁移到推理系统**：Sailor 的内存和时间模拟器精度达到 ~5%，其建模方式（分层 profiling + 多项式网络带宽拟合 + per-stage 内存追踪）可以借鉴用于 LLM 推理系统的容量规划和 auto-scaling 策略选择。

3. **可跟进的研究方向**：
   - 将 Sailor 的规划框架扩展到支持 Zero Bubble、Chimera 等先进 pipeline schedule，以及 sequence parallelism、context parallelism 等新型并行策略
   - 将异构训练规划与 MoE 的 expert parallelism 和动态路由结合
   - 将类似的联合优化方法应用于异构推理集群的 prefill-decode 分离调度
   - 在 spot instance 场景下，将 Sailor 的快速重规划能力与抢占预测模型结合，实现 proactive migration

4. **最有价值的切入点**：将 Sailor 的动态规划 + 启发式搜索框架推广到支持更多并行维度（EP、SP、CP）和更先进的 pipeline schedule，使其成为通用的异构训练配置搜索引擎。

---

## 八、总结

Sailor 是一个面向异构、跨地域、动态可用资源的分布式训练自动化系统，通过联合优化资源分配和 3D 并行策略，结合高精度模拟器和高效的动态规划搜索算法，在秒级时间内找到近优配置。在同构、异构和跨地域场景中分别实现 1.15-5.9× 的吞吐提升，同时支持成本约束优化和弹性重配置。主要局限在于仅支持 1F1B schedule、不支持 MoE、大规模实际硬件验证不足，以及搜索时间在 GPU 类型数增多时增长较快。
