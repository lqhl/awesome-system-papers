# Sailor: Automating Distributed Training over Dynamic, Heterogeneous, and Geo-distributed Clusters

**作者**：Foteini Strati, Zhendong Zhang, George Manos, Ixeia Sánchez Périz, Qinghao Hu, Tiancheng Chen, Berk Buzcu, Song Han, Pamela Delgado, Ana Klimovic（ETH Zurich, MIT, HES-SO）

**源文件**：[3731569.3764839.pdf](../../papers/sosp-2025/3731569.3764839.pdf)

## 一、背景

大规模 ML 模型训练对 GPU 资源的需求呈指数级增长（2020–2025 年模型规模增大约 1200×，而单 GPU 显存仅增长 8×）。公共云和企业数据中心中高端 GPU（如 A100、H100）的供给长期紧张，用户常常无法在单一可用区内申请到足够数量的同类 GPU。与此同时，数据中心内存在大量不同代次、不同规格的 GPU，分布在多个地理区域。然而，主流分布式训练框架（Megatron-LM、DeepSpeed）均假设同构集群，导致异构 GPU 资源难以被有效利用。

---

## 二、要解决的问题

**P1：配置搜索空间爆炸**
异构 GPU 类型、跨区域拓扑、多维并行策略（DP/PP/TP）及微批大小的组合使搜索空间呈指数级增长。现有 planner（Metis、FlashFlex、Atlas、DTFM）或搜索时间过长（几分钟到几小时），或仅优化并行策略而不联合优化资源分配，无法适应动态变化的资源可用性。

**P2：模拟器精度不足**
现有系统的显存占用估算误差高达 25–95%，频繁推荐导致 OOM 的配置；迭代时间估算也忽视了通信-计算重叠、straggler 效应和异构网络带宽，误差达 28–69%。

**P3：训练框架不支持异构计划**
Megatron、DeepSpeed 等框架假设各 pipeline stage 使用相同的并行度，无法支持每个 stage 配置不同 TP 度（这对负载均衡至关重要）。此外，现有框架在资源可用性变化时重配置速度慢，难以适应动态环境。

---

## 三、核心设计

Sailor 由三个核心组件构成：**Profiler**、**Planner**、**Simulator**，加上改造后的 **Distributed Training Framework**。

### Profiler
- **模型 profiling**：对每种 GPU 类型各运行一个节点，采集每层的 forward/backward/update 耗时（不同 microbatch size 和 TP 度），以及参数量、激活内存、中间状态内存。利用 PyTorch hooks + CUDA Events 进行测量。
- **集群 profiling**：测量任意两种节点类型之间的网络带宽（不同消息大小下），拟合多项式函数，覆盖 peer-to-peer 和 collective 通信。

### Planner
输入：资源配额（每种 GPU 类型/可用区的最大数量）、训练任务规格、优化目标（最大吞吐量或最小成本）和约束（预算上限或吞吐下限）。

**搜索空间剪枝启发式（H1–H6）**：
- **H1**：TP 限制在单节点内，不跨节点做 tensor parallel
- **H2**：基于 stage 显存下限预先计算最小 TP 度，提前剪除 OOM 配置
- **H3**：优化吞吐时，从最大 DP 度开始递减搜索，直到吞吐不再增长
- **H4**：优化成本时，从最小 DP 度开始递增搜索，直到满足吞吐约束
- **H5**：DP 通信限制在单 region 内（低带宽跨区域 DP 性能差），PP 可跨 region
- **H6**：同一 region 内多个 zone 视为单 zone 处理，降低搜索复杂度

**动态规划（DP）**：对给定 pipeline 并行度 P 和 DP 度 D，用 DP 为每个 stage 分配最优 GPU 资源组合，最小化迭代时间（考虑 straggler 效应）。带预算约束时，通过"假设当前 stage 为 straggler"的近似方法迭代求解。

### Simulator
- **显存估算**：$M_{peak} = M_{model} + M_{activation}$，逐 worker 分析（考虑 layer 分区、stage 编号、TP 度、microbatch size），可检测 OOM
- **迭代时间估算**：$T_{iter} = \max(T_{ppi}) + T_{sync} + T_{update}$，基于 1F1B pipeline 调度公式，利用 profiling 数据估算通信时间（peer-to-peer 和 collective）
- **成本估算**：$C_{iter} = C_{comp} + C_{comm}$，其中 $C_{comm}$ 包括跨 zone/region 的数据传输费用

### Distributed Training Framework
基于 Megatron-DeepSpeed 改造，支持：
- **异构并行计划**：各 pipeline stage 可配置不同 TP 度，每个 rank 可属于不同的 tensor-parallel group
- **弹性重配置**：资源可用性变化时，planner 重新规划（~0.1s），清理 NCCL 通信组（~3s），广播新拓扑（~1.25s），重新初始化（~4.5s + 2s + 0.5s）

## 四、实现细节

- 代码开源：https://github.com/eth-easl/sailor
- 框架基于 Megatron-DeepSpeed，修改支持 heterogeneous rank topology
- 使用 PyTorch CUDA memory allocator 跟踪显存，使用 CUDA Events 计时
- 网络带宽：使用 PyTorch collectives（NCCL backend）测量不同消息大小下的带宽，拟合多项式
- 模型 profiling 仅需几分钟（针对 LLM 的重复 transformer 层，只 profile 一个 instance）
- 支持任意 GPU 类型（视为黑盒计算单元），扩展新 GPU 类型只需重新 profile
- 当前仅支持 1F1B pipeline 调度，不支持 activation offloading/rematerialization（留作 future work）
- MoE 模型（层负载动态变化）的 profiling 留作 future work

## 五、实验结果

**实验平台**：
- 公共云：GCP，A100-40GB 和 V100-16GB VM
- 本地集群：4× Grace-Hopper per node（最多 32 节点）；异构集群：2×8 Titan-RTX + 3×8 RTX-2080 + 2×8 RTX-3090
- 模型：OPT-350M，GPT-Neo-2.7B，global batch size = 2048，seq len = 2048

**模拟器精度**：

| Planner | 显存估算误差 | 迭代时间误差 |
|---------|------------|------------|
| Piper | ~95% | ~60% |
| Varuna | ~80% | ~47% |
| Aceso | ~70% | ~37% |
| Metis | ~30% | ~28% |
| FlashFlex | ~20% | ~69% |
| **Sailor** | **~0%** | **4.5%** |

**同构集群吞吐（vs Baselines，128 A100）**：
- Sailor 搜索时间 < 1 秒，比 Aceso 快 200×，比 Metis 快 300×
- 吞吐比最近基线（DTFM）高 1.15×，比最差基线（Aceso）高 5.7×

**异构集群吞吐（A100 + V100，1 zone）**：
- 相比 AMP、FlashFlex、Metis，吞吐提升 1.1–2.87×
- 成本降低最多 2.67×
- 搜索时间 < 1 秒 vs Metis 300 秒

**地理分布式（4–5 zones，2 regions，A100）**：
- 吞吐比 DTFM 高 5.9×
- 成本比 DTFM 低 9.48×

**成本优化场景**：
- 场景 1（最小化成本，约束吞吐 ≥ 0.2 it/s）：比第二名节省 40% 成本
- 场景 2（最大化吞吐，约束成本 ≤ 1.2 USD/iter）：比最近基线高 1.65–3× 吞吐

**搜索时间（GPT-Neo-2.7B，128 A100 + 128 V100）**：

| 方法 | 搜索时间 |
|------|---------|
| 纯 DP（1 种 GPU）| 几小时 |
| DP + 启发式（1 种 GPU）| 0.25 秒 |
| DP + 启发式（2 种 GPU）| 5 秒 |
| DP + 启发式 + 成本约束（2 种 GPU）| 20 秒 |

## 六、批判性分析

**实验规模受限，大规模验证依赖模拟器**：论文真实硬件实验局限于小规模集群（最多 32 节点、24 GPU 的异构设置），大规模结论（128–512 GPU、5 zones）完全依赖 Sailor 自己的模拟器验证。模拟器的 4.5% 误差在 homogeneous 场景下测量，但异构场景的端到端验证样本极少，存在自我证明（self-referential）的风险。

**模型覆盖太窄**：实验只用了 OPT-350M 和 GPT-Neo-2.7B 两个相对较小的模型。现代实际训练任务（GPT-4、LLaMA-3 级别，数百亿到千亿参数）是否适用完全未验证。论文回避了这一点，也未分析搜索空间随模型规模的增长趋势。

**3 种 GPU 类型搜索时间骤增**：scalability 实验显示，256 GPU/type 下，1/2/3 种 GPU 类型的搜索时间为 0.3/6.2/4900 秒——第 3 种 GPU 类型使搜索时间增加了 800×。这对真实数据中心（存在 3–5 种主流 GPU 型号）是严重限制，论文轻描淡写地提了一下却没有解决方案。

**弹性重配置开销被低估**：论文报告的重配置时间（~12 秒总计，16 个 V100）在更大规模下被指出"NCCL 初始化在数千 GPU 上可能需要数分钟"，但随后说"现有方法可以集成进 Sailor"——这是一个未解决的关键工程挑战，论文没有给出量化分析。

**基线对比不公平**：Sailor 联合优化资源分配 + 并行策略，而所有基线只优化并行策略（资源拓扑由用户固定为 4-GPU VM）。这个差异没有被控制变量单独分析，无法区分"联合优化本身的收益"和"更好的模拟器"带来的收益。

**异步训练被完全排除**：论文将 DiLoCo、SWARM、CocktailSGD 等异步/去中心化方法归为"正交工作"，但这些方法在极低带宽的跨区域场景下可能更实用，论文没有讨论两类方案的适用边界。

## 七、AI Infra / MLSys 视角

**核心 insight 的迁移价值**：Sailor 的三个核心贡献——联合优化资源分配与并行策略、精确的逐 worker 显存模拟、基于 DP + 启发式的快速搜索——都可以迁移到 AI Infra 的其他场景：

1. **推理系统中的异构部署**：Helix 和 HexGen 已在推理中探索，但都忽略了 geo-distributed 场景的通信成本。Sailor 的成本函数（$C_{comm}$）和 H5/H6 启发式直接可以迁移，用于在多云/多 zone 上放置推理副本和 KV cache。

2. **Fine-tuning 场景**：LoRA 等 PEFT 方法改变了显存分布（减少了 activation 但引入 adapter），Sailor 的逐 layer profiling + 逐 worker 显存模型可以适配，指导在异构集群上高效做 fine-tuning。

3. **动态批处理和弹性推理**：Sailor 的弹性重配置机制（planner → cleanup → broadcast → reinitialize）对推理系统中的 SLO-aware 弹性扩缩容有直接借鉴意义，但需要大幅降低重配置延迟。

**值得跟进的方向**：
- **支持更多 GPU 类型**：搜索时间随 GPU 类型数指数增长是最大瓶颈，探索贪心/近似算法（如进化算法、beam search）来突破 3 种以上 GPU 类型的搜索瓶颈
- **异构 MoE 训练**：MoE 模型的负载不均匀（expert 激活稀疏），与 Sailor 的异构 pipeline 负载均衡思路天然契合，是高价值的延伸方向
- **与 activation checkpointing / offloading 集成**：这两个技术是现代大模型训练的标配，Sailor 目前不支持，是重要的工程缺口
- **多租户场景**：Sailor 目前针对单一训练任务，扩展到多租户 GPU 集群调度（考虑任务优先级、抢占）是更大的研究机会

---

## 八、总结

Sailor 是首个将资源分配与并行策略联合优化的异构分布式训练系统，通过精确的逐 worker 显存/迭代时间模拟和 DP + 启发式的快速搜索（< 1 秒对应 128 GPU），在同构、异构和地理分布式场景下均超越现有 planner，吞吐提升 1.1–5.9×，成本降低最多 9.5×。主要局限是超过 2 种 GPU 类型时搜索时间骤增、大规模实验依赖自有模拟器验证、不支持 MoE 和 activation offloading，且弹性重配置在万卡规模下的延迟仍是开放问题。
