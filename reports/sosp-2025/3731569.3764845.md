# Coyote v2: Raising the Level of Abstraction for Data Center FPGAs

**作者**：Benjamin Ramhorst (ETH Zurich), Dario Korolija (AMD Research), Maximilian Jakob Heer (ETH Zurich), Jonas Dann (ETH Zurich), Luhao Liu (ETH Zurich / University of Tokyo), Gustavo Alonso (ETH Zurich)

## 一、背景

随着 CPU 性能扩展遇到瓶颈，数据中心日益依赖硬件特化（GPU、TPU、FPGA 等）来满足多样化工作负载的性能需求。FPGA 因其可编程性和高性能，在数据中心中扮演双重角色：既作为网络虚拟化等任务的加速器，也作为新硬件设计的原型平台。Microsoft Azure Boost、Amazon AQUA、Alibaba Fidas、Baidu Kunlun 等生产系统均采用了 FPGA。

然而，将 FPGA 集成到更大的系统中仍然极具挑战。FPGA 通常被当作原始设备使用，每个项目需要从零开发所有基础设施服务（网络、I/O、主机通信等）。研究表明，约 75% 的开发精力花在基础设施而非应用本身，且这些基础设施投入通常紧耦合于特定应用，难以复用。

FPGA shell 旨在提供共享抽象和基础设施，但现有 shell（包括商业和学术）仍存在关键功能缺失：服务不可运行时重配置、用户接口不够通用、缺乏应用流水线支持等。

---

## 二、要解决的问题

1. **服务静态不可重配置**：现有 shell 的服务层（网络栈、内存管理等）在初始化时加载后不可动态重配置，切换服务（如从 TCP/IP 切到 RDMA）需要重启 FPGA，中断服务。

2. **用户接口不够通用**：大多数 shell 仅提供单条数据流到主机内存，导致多输入/输出应用（如向量加法需要消费两个向量）需要在软件中手动打包/解包数据流，繁琐且易错。对于神经网络推理等场景，某些 shell（如 AmorphOS）还要求先将数据从主机内存拷贝到 FPGA HBM，引入不必要的延迟。

3. **缺乏多租户应用流水线**：现有 shell 不支持透明的多用户应用流水线（application pipelining）。对于 AES CBC 加密、LLM 推理等存在数据依赖的流水线工作负载，无法通过同时服务多个请求来减少硬件空闲时间。

4. **缺乏通用中断接口**：只有少数商业 shell 提供中断接口，但实际工作负载中应用可能遇到各种异常状态（畸形数据、超时），需要主机 CPU 与 FPGA 之间更紧密的交互。

---

## 三、洞察与设计

**关键洞察**：将 FPGA shell 的服务层从静态层分离出来，作为可独立动态重配置的中间层，既能大幅简化静态层（使其仅负责 CPU-FPGA 链路），又能实现服务和应用的独立运行时重配置，同时不牺牲性能——这一分层设计类似于传统 OS 将设备驱动与内核分离的思路。

基于此洞察，Coyote v2 采用三层层级化模块架构：

1. **静态层（Static Layer）**：最底层，负责 CPU-FPGA 通信链路（基于 XDMA over PCIe），提供四种通道：Shell 控制（BAR 映射）、Host 流式通道（直接数据流）、迁移通道（大缓冲区搬运，如模型权重）、工具通道（重配置比特流加载、writeback、中断）。静态层被封装在 AXI4 标准接口之后，不处理数据，仅路由。

2. **动态层（Dynamic/Services Layer）**：包含可重配置的共享服务——MMU/TLB（支持可配置页大小如 1GB 大页、共享虚拟内存）、网络栈（RoCEv2 兼容的 RDMA 栈 BALBOA）、多租户公平共享（信用机制 + 分组交织）等。

3. **应用层（Application Layer）**：包含多个并行 vFPGA，每个 vFPGA 通过统一的通用接口（多条 AXI4 并行流用于 host/card/net 数据、DMA 发送/完成队列、控制总线、中断通道）与下层交互。引入 cThread（Coyote Thread）概念，类似 OS 线程，多个 cThread 可共享同一 vFPGA 流水线，实现透明的应用流水线。

动态层和应用层均可通过 ICAP 进行部分重配置，无需停机。如果重配置失败，旧配置自动保留（fail-safe）。应用层还实现了 per-vFPGA 的信用系统，防止单个不信任应用对整个系统产生背压。

## 四、实现细节

- **重配置控制器**：通过优化的 ICAP 接口实现，充分利用 ICAP 带宽（AMD UltraScale+ 设备上约 800 MB/s），远超传统 AXI HWICAP（19 MB/s）和 MCAP（145 MB/s）。比特流从主机内存通过 PCIe 和专用 XDMA 通道加载。

- **设备驱动**：Linux 内核组件，管理 FPGA 外设、内存映射、动态分配、页错误处理和部分重配置。通过标准系统调用（open、close、mmap、ioctl）与用户空间交互。

- **MMU/TLB**：混合实现——TLB 用片上 SRAM 实现快速查找，页表管理在主机驱动侧。支持可配置的关联度、页大小（含 1GB 大页）、NRU 驱逐策略。通过外部贡献扩展支持 GPU 内存，实现 FPGA-GPU 直接数据搬运。

- **内存条带化**：数据缓冲区跨多个 HBM bank 分区，最大化吞吐。

- **公平共享**：在带宽受限链路（PCIe、网络）上实现分组化（默认 4KB 块）+ round-robin 交织 + per-stream 信用机制。

- **软件 API**：C++ 实现，提供 cThread 抽象类，支持内存分配、控制寄存器读写、DMA 触发、RDMA QP 管理、内核调用等。通过 Python 集成 hls4ml 框架，可用不到 10 行 Python 代码编译部署神经网络到 FPGA。

- **案例：流量嗅探器**：作为可重配置服务实现，在网络栈和 CMAC 之间插入过滤器，支持从主机配置过滤规则，捕获数据存入 HBM 后同步回主机导出为 PCAP 文件。

- **开源**：代码托管在 GitHub（https://github.com/fpgasystems/Coyote），已有学术界和工业界贡献。支持 AMD Alveo U250、U55C、U280 等多种 FPGA。

## 五、实验结果

实验平台为 AMD Alveo U55C（系统时钟 250 MHz，HBM 时钟 450 MHz）和 Alveo U250。

| 实验 | 关键结果 |
|------|---------|
| HBM 吞吐扩展 | 并行 HBM 通道数增加时吞吐近线性增长，6 通道约 75 GB/s |
| 合成时间 | App flow 比 Shell flow 减少 15%–20% 合成时间（如 RDMA+AES 从 ~220 min 降至 ~180 min） |
| Shell 重配置延迟 | 内核延迟 51.6–85.5 ms，总延迟（含磁盘读取）536–929 ms；对比 Vivado 全量重编程 55,922–71,418 ms，快约两个数量级 |
| 多租户 AES ECB | 1–4 个 vFPGA 间带宽公平分配，累积吞吐恒定（~12 GB/s），无仲裁开销 |
| AES CBC 流水线 | 单 cThread 饱和于 280 MB/s；8 个 cThread 线性扩展至约 2 GB/s，空闲时间降低最高 7× |
| HyperLogLog | 与 Coyote v1 性能相当，资源占用略高（~10%），支持按需重配置（加载仅 57 ms） |
| 神经网络推理 | 对比 hls4ml+PYNQ 基线，Coyote v2 后端推理吞吐提高约一个数量级，资源占用相当 |

## 六、批判性分析

1. **神经网络推理基线不公平**：论文承认 PYNQ 基线"未完全优化"，因其需先将数据从主机内存拷贝到 FPGA HBM 再消费，且 PYNQ 的 Python 控制开销较大。但论文仍将"一个数量级"的加速作为主要卖点展示。实际上这主要是基线实现质量的差异，而非 Coyote v2 架构本身的优势。一个优化过的 Vitis 流（使用 host streaming）可能会大幅缩小差距。

2. **实验规模和工作负载代表性有限**：所有实验均在单卡上进行，缺乏多卡、多节点场景的评估。工作负载（AES、HyperLogLog、小型神经网络）虽能展示系统功能，但与真实数据中心负载（大模型推理、大规模网络功能卸载）差距较大，难以判断系统在生产环境中的表现。

3. **资源开销分析不充分**：论文提到 HyperLogLog 场景下资源利用率约 10%，但未系统评估三层架构本身引入的资源开销（静态层 + 动态层占用了多少 LUT/FF/BRAM）。对于 FPGA 资源紧张的场景，这一开销可能成为制约因素。

4. **cThread 机制的通用性被高估**：论文以 AES CBC 为例展示 cThread 的流水线填充能力，但 AES CBC 是一个理想场景（每个 cThread 完全独立、无共享状态）。论文承认有状态应用需要"应用特定的状态跟踪"，但未给出任何有状态应用的实际案例或评估，cThread 在复杂有状态场景下的实用性存疑。

5. **可靠性和故障恢复讨论薄弱**：论文提到如果损坏的比特流导致动态重配置失败，旧配置将保留。但未讨论重配置过程中正在处理的请求如何处理、重配置失败的检测机制、以及长期运行中部分重配置的可靠性问题。

6. **与 SmartNIC/DPU 的对比缺失**：论文多次提到 Coyote v2 可作为 SmartNIC 替代，但未与任何商用 SmartNIC（如 Mellanox BlueField、AMD Pensando）进行性能或功能对比。

## 七、AI Infra / MLSys 视角

1. **FPGA 作为 AI 网络枢纽的潜力**：论文在 future work 中提到将 Coyote v2 作为连接 CPU、GPU、DPU 的分发中心，支持梯度压缩等 collective 通信 offload。这与当前 AI Infra 中网络瓶颈问题高度相关——在大规模分布式训练中，通信开销越来越成为瓶颈，FPGA 作为可编程网络设备可以实现定制化的 collective 操作（如 AllReduce with compression），且 Coyote v2 已集成 RoCEv2 RDMA 栈和 ACCL+ collective 引擎。

2. **hls4ml 集成的启发**：论文展示了通过不到 10 行 Python 代码在 FPGA 上部署神经网络推理的能力。这种"类 GPU 编程体验"的方向对 FPGA 在 AI 推理中的采用至关重要。但当前仅支持 hls4ml 能编译的小模型，距离 LLM serving 等主流 AI Infra 需求差距很大。

3. **可迁移的设计思路**：
   - **三层分离 + 动态重配置**：在 AI 推理服务中，不同阶段（prefill vs decode、不同模型）可能需要不同的硬件配置，Coyote v2 的动态服务重配置思路可以迁移到 AI 加速器的运行时资源管理。
   - **cThread 流水线填充**：与 GPU 中通过 batching 提高利用率的思路类似，cThread 机制通过多客户端交织减少流水线气泡，这一概念可用于 FPGA-based LLM serving 中的 continuous batching。
   - **共享虚拟内存 + GPU 直连**：Coyote v2 支持 FPGA-GPU 直接数据搬运，这对 CPU-GPU-FPGA 异构推理管线有价值。

4. **值得跟进的方向**：
   - 基于 Coyote v2 实现 FPGA-based 的 KV cache offload（利用 HBM + 网络栈实现分布式 KV cache 管理）
   - 探索 FPGA 作为 AI 训练中 collective 通信的 in-network 加速器（已有 ACCL+ 基础）
   - 将 cThread 流水线机制与 LLM serving 的 continuous batching / speculative decoding 结合

---

## 八、总结

Coyote v2 是一个开源 FPGA shell，通过创新的三层层级化架构（静态层、动态服务层、应用层）显著提升了数据中心 FPGA 的抽象层级。其核心贡献在于：将服务从静态层分离到可动态重配置的中间层，实现服务和应用的独立运行时重配置（比全量重编程快约两个数量级）；提供统一的多流通用接口和 cThread 抽象，支持多租户公平共享和应用流水线；通过 RoCEv2 RDMA 栈、共享虚拟内存、GPU 直连等服务将 FPGA 集成为数据中心的一等公民。主要局限在于实验规模较小、工作负载不够复杂、有状态应用支持不足，距离生产级部署仍有距离。
