# Coyote v2: Raising the Level of Abstraction for Data Center FPGAs

## 论文基本信息

- **标题**: Coyote v2: Raising the Level of Abstraction for Data Center FPGAs
- **作者**: Benjamin Ramhorst, Dario Korolija, Maximilian Jakob Heer, Jonas Dann, Luhao Liu, and Gustavo Alonso
- **会议**: SOSP 2025
- **Session**: ML and FPGA
- **PDF**: 3731569.3764845.pdf

## 研究背景

FPGA（Field-Programmable Gate Array）在数据中心的应用由来已久。与 CPU 相比，FPGA 提供可定制的数据路径和流水线，能够在特定 workloads 上实现数量级的性能提升；与 ASIC 相比，FPGA 的可重配置性允许在部署后更新功能，降低了硬件开发和迭代成本。AMD 的 Alveo 系列（如 U55C、U280、U250）是面向数据中心场景的 FPGA 加速卡，在金融计算、机器学习推理、网络处理、基因组学等领域有广泛应用。

然而，FPGA 的编程门槛一直是制约其广泛采用的核心障碍。传统的 FPGA 开发使用硬件描述语言（HDL，如 Verilog、VHDL），要求开发者具备数字电路设计的专业知识——理解时钟域交叉、流水线寄存器布置、BRAM 端口分配等底层细节。即便是采用高层次综合（High-Level Synthesis, HLS）工具（如 Xilinx Vitis HLS、Intel OpenCL SDK）来用 C/C++ 编写 FPGA 代码，开发者仍然需要手动管理内存层次结构、数据流并行性和硬件资源约束。

**Coyote v1** 是 ETH Zurich 的前期工作，提出了一个数据流式（dataflow-based）的 FPGA 编程抽象。Coyote 程序由处理元素（Processing Elements, PEs）和连接它们的 FIFO 通道构成，类似于空间计算（spatial computing）中的 kernel 编程范式。Coyote v1 已经在 AMD Alveo U280 上验证了其可行性，但存在两个核心限制：

1. **缺乏硬件-软件接口抽象**：v1 的 PE 只能访问本地 BRAM，无法直接与 host CPU 或其他 FPGA kernels 进行内存交互
2. **抽象层次仍不够高**：PE 的内部实现仍然需要大量 RTL 细节

## 要解决的问题

如何在保持 FPGA 性能优势的同时，将编程抽象提升到接近软件工程师熟悉的层次，同时保证抽象不泄露（abstraction without leaking）——即开发者无需理解底层硬件细节，但编译器能够生成高效的硬件实现？

Coyote v2 的核心目标是：**将 FPGA 编程的抽象层次从 RTL/PE-level 提升到 kernel-level，使得开发者能够像编写 GPU kernel 一样编写 FPGA 加速器。**

## 核心贡献

1. **Hardware-Software Interface Design**：v2 引入了一组新的硬件-软件接口原语（HW/SW interface），允许 FPGA kernels 与 host CPU、其他 kernels 以及外部 DRAM 进行标准化的高带宽通信。

2. **Raised-level Primitives**：提出了三个高层抽象原语——Streams（流）、Memories（内存）和 Control（控制），使得开发者可以用声明式的方式描述数据通路，而非显式管理硬件资源。

3. **Composable Kernels**：基于新的抽象原语，v2 支持 kernel 级别的组合（composition）。多个 Coyote kernels 可以组合成更大的 accelerator，支持分块开发和模块化测试。

4. **端到端编译流程**：从高层 DSL（领域特定语言）到 AMD Alveo 比特流的完整编译器实现，支持自动资源分配、调度和代码生成。

5. **在 AMD Alveo U55C 和 U280 上的验证**：在 8 个实际 kernels（加密、ML、图处理、数据库）上进行了评估，验证了抽象的通用性和编译后硬件的性能。

## 主要研究方法

**High-level Primitives**

Coyote v2 的三个核心原语设计如下：

1. **Streams**：表示数据流管道。Stream 封装了 FIFO 的概念，但以生产者-消费者接口暴露给开发者：
   ```cpp
   // Producer writes to stream
   stream_out.push(data);

   // Consumer reads from stream
   auto data = stream_in.pop();
   ```
   底层实现自动管理 FIFO 深度、流控（flow control）和背压（backpressure）机制。

2. **Memories**：表示 BRAM/URAM 端口管理的高层抽象。开发者声明 Memory 的访问模式（顺序、随机、滑动窗口），编译器负责分配合适的 BRAM 端口数量和 bank 冲突避免：
   ```cpp
   // Declare a sliding-window memory
   Memory<int> weights(SLIDING_WINDOW, window_size);

   // Compiler auto-schedules port allocation
   auto val = weights.read(addr);
   ```
   与 v1 的手工 BRAM 端口分配相比，Memory 原语将这一复杂性自动化。

3. **Control**：表示控制流和数据路径条件的高层抽象。Control 原语封装了状态机、分支选择和循环展开决策：
   ```cpp
   // Data-dependent control
   Control::branch(condition, then_kern, else_kern);
   // Loop with II (Initiation Interval) hint
   Control::pipeline<II=1>(loop_body);
   ```

**Kernel Composition**

v2 引入了一个组合框架，允许将多个 kernels 连接成更大的 accelerator：

```
[Kernel A] --stream--> [Kernel B] --memory--> [Kernel C]
    |                    |                     |
  input               internal             output
```

组合后的 kernel 作为一个整体被编译器处理，自动处理内部通信的物理实现（intra-FPGA streaming 或 shared BRAM）。

**HW/SW Interface**

v2 的硬件-软件接口设计包括：
- **Host-to-FPGA**：通过 XDMA（PCIe Direct Memory Access）的高效数据传输，支持零拷贝（zero-copy）API
- **FPGA-to-FPGA**：通过 Alveo 的 NoC（Network-on-Chip）进行 kernel 间通信，无需经过 host 内存
- **FPGA-to-DRAM**：通过 AXI4 协议访问 DDR/HBM，支持 burst 传输优化

## 设计与实现

Coyote v2 的编译流程如下：

```
[User DSL Code (.cy))]
         ↓
+------------------------------------------+
|     Coyote v2 Frontend                   |  (DSL parser, type checker)
+------------------------------------------+
         ↓
+------------------------------------------+
|     Coyote IR (Intermediate Representation)| (HW-independent IR)
+------------------------------------------+
         ↓
+------------------------------------------+
|     Resource Allocator                    |  (BRAM ports, DSP slices, LUTs)
+------------------------------------------+
         ↓
+------------------------------------------+
|     Scheduler                             |  (II optimization, pipeline balancing)
+------------------------------------------+
         ↓
+------------------------------------------+
|     AMD Backend (Vitis HLSL + RTL)        |  (code generation)
+------------------------------------------+
         ↓
[AMD Alveo Bitstream (.xclbin)]
```

**DSL Frontend**：基于 Scala 实现，提供类型安全的 DSL，支持 streams、memories 和 control 的组合语法。

**Resource Allocator**：根据每个 kernel 的资源需求和 FPGA 目标芯片的物理约束（DSP 数量、BRAM 大小、LUT 深度），自动分配硬件资源。

**Scheduler**：负责循环流水线的 II（Initiation Interval）优化。对于每个 pipeline loop，scheduler 分析循环携带依赖（loop-carried dependencies），计算最小 II，并在可能的情况下插入寄存器来达到目标 II。

## 主要实验结果

Coyote v2 在 8 个 kernels 上进行了评估，覆盖加密、机器学习、图处理和数据库等应用领域：

| Kernel | 应用领域 | 手写 RTL 性能 | Coyote v2 性能 | 生产力提升 |
|--------|---------|-------------|--------------|---------|
| AES-256 | 加密 | 100% | 94% | 4.2x fewer lines |
| SHA-256 | 加密 | 100% | 91% | 3.8x fewer lines |
| GEMM (16x16) | ML | 100% | 89% | 5.1x fewer lines |
| BFS (Graph) | 图处理 | 100% | 87% | 4.7x fewer lines |
| Sort (merge) | 数据库 | 100% | 85% | 6.2x fewer lines |
| Conv-3x3 | ML | 100% | 93% | 4.9x fewer lines |
| FFT | 信号处理 | 100% | 88% | 3.5x fewer lines |
| PageRank | 图处理 | 100% | 86% | 5.8x fewer lines |

**关键发现**：
- 所有 kernels 达到手写 RTL 性能的 85-94%（平均 90%）
- 代码行数平均减少 4.5x（开发者生产力显著提升）
- 编译时间平均为 12 分钟（端到端，从 DSL 到比特流）
- **vs HLS (Xilinx Vitis HLS)**：Coyote v2 在相同代码行数下，性能平均高出 15%（得益于更智能的调度和资源分配）

## 潜在问题 / 局限性

1. **性能损失 6-15% 的实际意义**。论文报告 Coyote v2 达到手写 RTL 性能的 85-94%，但"手写 RTL"的参考基准质量如何？这可能是一个 strawman——如果手写 RTL 没有经过充分优化（auto-tuned），则这个对比意义有限。论文未说明参考 RTL 是否经过了 post-place-and-route 优化或 RTL-level 的性能调优。

2. **编译时间 12 分钟是一个被低估的成本**。对于需要快速迭代的开发场景（特别是调试阶段），12 分钟的端到端编译时间意味着每次代码修改都需要等待 12 分钟才能看到结果。这与 CPU/GPU 开发中"秒级"或"分钟级"的迭代周期形成鲜明对比。论文未讨论增量编译（incremental compilation）或编译缓存的可能性。

3. **抽象泄露（Abstraction Leakage）的边界不清晰**。Coyote v2 承诺开发者无需理解底层硬件，但 Memory 原语中的"访问模式声明"（顺序、随机、滑动窗口）本质上仍然需要开发者理解 BRAM 的 bank 结构。论文未充分讨论在何种场景下开发者仍然需要深入理解硬件才能写出高效代码。

4. **与其他 HLS 工具的比较不够全面**。论文仅与 Vitis HLS 进行了简单对比，但未涉及 Intel FPGA SDK for OpenCL、C++ for FPGA（Intel oneAPI）、MaxCompiler（Maxeler）等工业级工具。这些工具在各自生态中都有一定的用户基础和优化积累。

5. **Kernel Composition 的可扩展性存疑**。当组合多个 kernels 时，编译器需要处理内部通信、流水线平衡和资源共享。随着 kernel 数量增加，编译复杂度和运行时调度决策可能变得难以管理。论文未提供关于"支持多少个 kernels"或"何时组合会开始影响性能"的量化数据。

## 未来工作

1. **支持 AMD Versal ACAP 系列**：Versal 架构引入了 AI Engine（AIE）阵列和可编程片上网络（NoC），需要扩展 Coyote v2 的后端以支持这种异构 FPGA 架构。

2. **自动化 kernel 分割**：当前需要开发者手动决定如何将算法划分为多个 kernels。未来可以引入自动化的算法分析和分割算法。

3. **多-FPGA 支持**：扩展 HW/SW 接口到多 FPGA 节点，支持跨 FPGA 的 kernel 分布和通信。

4. **与高层框架集成**：支持从 PyTorch、TensorFlow 或 ONNX 模型直接编译到 Coyote v2 kernels，降低 ML 开发者使用 FPGA 的门槛。

## 个人评注

Coyote v2 的核心价值在于将 FPGA 编程的生产力提升——减少代码量同时保持接近硬件的性能。这在 FPGA 领域是持续追求的目标，但也是最难实现的目标。过去的 HLS 工具虽然提升了抽象层次，但往往以性能损失或限制性编程模型为代价。

从技术深度看，Memory 原语的设计是论文最有价值的部分——自动化的 BRAM 端口分配和 bank 冲突避免解决了 FPGA 开发中一个最繁琐且易错的工程问题。如果这个机制足够鲁棒，它可以为开发者节省大量手工调优的时间。

不过，论文的实验设置有些保守。8 个 kernels 都是相对规则的计算模式（加密、矩阵乘法、FFT），这些恰好是 HLS 工具表现最好的场景。对于不规则的数据访问模式（如稀疏图操作中的随机内存访问），Coyote v2 的抽象是否仍然有效，尚不清楚。

从行业视角看，FPGA 在数据中心的主流应用仍然是微软 Azure 的 Catapult 项目和 AMD/Xilinx 的部分固定功能加速器。Coyote v2 要真正推动 FPGA 的普及，需要在易用性和性能上同时取得突破——目前它更多是面向 FPGA 专家的工具，而非降低门槛的入门级产品。
