# Coyote v2: Raising the Level of Abstraction for Data Center FPGAs

**作者**：Benjamin Ramhorst (ETH Zurich)、Dario Korolija (AMD Research)、Maximilian Jakob Heer (ETH Zurich)、Jonas Dann (ETH Zurich)、Luhao Liu (ETH Zurich / University of Tokyo)、Gustavo Alonso (ETH Zurich)

## 一、背景

数据中心硬件专用化趋势日益明显，GPU、TPU 等加速器已大规模部署以满足 ML 等工作负载的性能需求。在此背景下，FPGA 凭借其可重配置性和高性能，在数据中心扮演双重角色：一方面作为网络虚拟化、SmartNIC 等功能的 offload 加速器（如 Microsoft Azure Boost、Amazon AQUA、阿里巴巴 Fidas），另一方面作为探索下一代加速器设计的原型平台。

然而，将 FPGA 集成到更大系统中依然困难重重。每个项目往往需要从零开始开发网络栈、I/O、主机通信等基础设施，约 75% 的开发时间消耗在这些重复性基础设施上，而非应用本身。现有 FPGA Shell 的进展虽然显著，但仍存在明显短板。

---

## 二、要解决的问题

作者归纳出现有 FPGA Shell 的三大核心不足：

1. **服务不可动态重配置**：现有 Shell（包括前作 Coyote）的服务（网络栈、内存控制器等）固化在静态层，切换服务（如从 TCP/IP 换成 RDMA、更改 MMU 配置）必须将 FPGA 整体下线重新烧录，无法在线服务。

2. **缺乏多租户与应用流水线支持**：现有 Shell 通常仅支持单用户单数据流，无法有效利用现代 FPGA 富余的计算/内存/网络带宽（如 AMD Alveo V80 有 2.5M LUTs、800G 网络、32GB HBM）。具有数据依赖的流水线应用（如 AES CBC、LLM token 生成）因无法并发处理多请求而导致硬件大量空闲。

3. **应用接口不够通用**：主流 Shell 仅提供单一 host 数据流，神经网络推理需要多输入（权重+激活），向量加法需要多向量并行输入，开发者不得不在软件侧手动打包/拆包，繁琐且易错。此外大多数 Shell 缺乏通用中断接口，难以处理异常、超时等真实工作负载中的突发情况。

## 三、核心设计

Coyote v2 采用三层分层硬件架构：

```
┌──────────────────────────────────────┐
│  Application Layer (vFPGAs)          │  用户逻辑，可独立重配置
│  vFPGA #0 | vFPGA #1 | ... | vFPGA N│
├──────────────────────────────────────┤
│  Dynamic Layer (Services)            │  服务层，可在线重配置
│  HBM/DDR MMU | RDMA | TCP/IP | ...  │
├──────────────────────────────────────┤
│  Static Layer                        │  固定层，仅负责 PCIe 链路
│  XDMA/QDMA | PCIe | ICAP            │
└──────────────────────────────────────┘
```

**关键设计决策**：

- **服务从静态层迁移到动态层**：静态层精简为仅提供 PCIe 链路（XDMA/QDMA），不处理数据，从而可提供预路由锁定的检查点（routed and locked checkpoint），大幅缩短应用综合时间。服务层可通过 ICAP 动态加载，无需 FPGA 下线。

- **通用应用接口（Generic vFPGA Interface）**：每个 vFPGA 暴露多路并行 AXI4 Stream，覆盖 host 内存、card 内存（HBM/DDR）和网络三个数据面，同时包含控制总线（AXI4-Lite 内存映射到用户空间）、中断通道（eventfd 机制）、DMA 请求/完成队列（vFPGA 可直接发起 DMA，无需 CPU 介入）。

- **cThread 软件抽象**：类比 OS 进程（vFPGA）与线程（cThread），多个 cThread 可并发映射到同一 vFPGA 流水线，利用流水线并行消除因数据依赖造成的空闲。每个 cThread 通过 AXI TID 字段携带唯一标识，round-robin 仲裁器保证公平调度。

- **信用机制（Credit System）**：针对 vFPGA 可能产生的背压问题，按流（host/card/network）独立实现信用计数，请求仅在目标队列有足够空间时才转发，将背压限制在单 vFPGA 而非全系统。

## 四、实现细节

**硬件**：
- 支持 AMD FPGA：Alveo U250、U55C、U280（UltraScale+ 系列）
- 静态层提供预编译、预路由的 DCP 检查点，应用综合时直接链接，跳过静态层和服务层的重新综合
- ICAP 控制器优化为使用 AXI Stream 接口，通过 PCIe 专用 XDMA 通道从 host 内存加载 bitstream，实测吞吐达 ~800 MB/s（对比 AXI HWICAP 的 19 MB/s、MCAP 的 145 MB/s）
- MMU/TLB：TLB 用片上 SRAM 实现快速查找，MMU 其余部分在 host 驱动侧实现；支持可配置页大小（最大 1 GB 巨页）、可配置关联度、NRU 换页；支持内存条带化（striping）跨多 HBM bank
- 网络栈 BALBOA：100G RoCEv2 兼容，与 Coyote v2 的 MMU/TLB 集成，直接操作虚拟地址

**软件**：
- Linux 内核驱动：管理内存映射、页错误、动态重配置；标准系统调用接口（open/close/mmap/ioctl）
- C++ 用户态 API（cThread 类）：封装内存分配（getMem 支持 huge pages）、CSR 读写（setCSR/getCSR）、DMA 触发（invoke）、RDMA QP 管理
- Python 集成：通过 hls4ml CoyoteAccelerator backend，10 行 Python 代码即可完成从 Keras 模型到 FPGA 推理的全流程

## 五、实验结果

**测试平台**：AMD Alveo U55C / U250，系统时钟 250 MHz，HBM 时钟 450 MHz

| 实验 | 主要结论 |
|------|---------|
| HBM 吞吐 vs. 通道数 | 随通道数线性增长，趋于饱和（内存虚拟化开销）；旁路 MMU 可达更高峰值 |
| 综合时间（App Flow vs. Shell Flow） | App Flow 减少综合时间 **15%–20%**（目标 Alveo U250，含 RDMA shell） |
| Shell 动态重配置延迟 | 内核态：51–85 ms；含磁盘读取总延迟：536–929 ms；vs. Vivado 全量重编程：**55,000–71,000 ms**（快约 **2 个数量级**） |
| Multi-tenant AES ECB | 带宽在 vFPGA 间公平分配，累计吞吐恒定（~12 GB/s on U55C with XDMA） |
| AES CBC + cThreads | 单 cThread：~280 MB/s；8 cThreads：~1.8 GB/s，**线性扩展**，硬件空闲时间降低约 7× |
| HyperLogLog | 与 Coyote 基线性能相当，资源利用率稍高（约 10%，仍有大量余量） |
| 神经网络推理（hls4ml） | 相比 PYNQ 基线吞吐高约 **1 个数量级**，资源利用率相当 |

## 六、批判性分析

**神经网络推理比较存在不公平性**：论文明确承认 PYNQ 基线不是最优实现——PYNQ 需要先将数据从 host 内存复制到 FPGA HBM，而 Coyote v2 直接从 host 流式传入。这一根本性架构差异使得"吞吐高一个数量级"的结论很大程度上是与 suboptimal baseline 比较的结果，而非系统设计本身的优势。实验 caption 虽然提及这一点，但主文仍以此作为"优势"的主要论据。

**合成时间改善幅度有限**：15%–20% 的综合时间减少，在 FPGA 动辄 4–6 小时的综合周期面前确实有帮助，但核心受益场景（"锁定 shell 后只重综合应用"）要求 shell 配置基本固定，这在实际多租户环境中未必成立。且论文仅测了三个 shell 配置，样本偏少。

**商业 Shell 无性能对比**：Feature 对比表 (Table 1) 非常全面，但所有性能实验均以前作 Coyote [34] 为基线，从未与 Vitis XRT Shell、Intel OneAPI 等商业 Shell 做性能比较。对于一篇声称优于商业方案的论文，这是明显的实验设计不足。

**cThread 隔离保证较弱**：论文类比 OS 进程/线程模型，但明确指出同一 vFPGA 内的 cThread 共享地址空间，隔离责任由应用自行保证（而非 Shell）。在多租户场景中，恶意或有缺陷的用户逻辑可能破坏同 vFPGA 内其他 cThread 的数据，这一限制被轻描淡写。

**规模和真实部署缺失**：所有实验均在单卡（1–4 个 vFPGA）上进行，无多节点、无大规模真实负载、无与 SmartNIC 或 DPU 的协同实验。论文的"数据中心 FPGA"定位与实验的单卡 microbenchmark 规模之间存在明显落差。

**ICAP 吞吐的条件依赖**：800 MB/s 的 ICAP 吞吐针对 AMD UltraScale+ 器件，其他平台（如 Xilinx 7 系列）可能差异显著。论文虽声称支持多款 AMD FPGA，但可移植性实验缺失。

## 七、AI Infra / MLSys 视角

**对 AI 系统研究的借鉴价值**：

1. **cThread 与 LLM Continuous Batching 的同构性**：cThread 通过 AXI TID 字段将多个独立请求交织到同一流水线，本质上是 FPGA 层面的 continuous batching。这与 LLM 推理中用 PagedAttention + continuous batching 填充计算流水线的思路完全同构，值得在 FPGA 加速 LLM 推理时直接采用。

2. **服务层动态重配置 → AI Infra 弹性**：在推理系统中，不同模型/任务可能需要不同的网络拓扑（全连接 vs. 稀疏、INT8 vs. FP16），Coyote v2 的动态服务重配置允许在不下线设备的情况下切换计算 kernel，这对多模型共享 FPGA 资源的场景极具价值。

3. **FPGA-GPU 直连 DMA**：论文提及通过扩展 MMU 支持 GPU 内存直接访问（peer-to-peer DMA），这为构建无 CPU 瓶颈的 GPU-FPGA 推理流水线提供了基础设施——例如 FPGA 做前处理（tokenization、量化）后直接将数据送入 GPU HBM。

4. **可跟进的研究方向**：
   - 将 Coyote v2 的 cThread 流水线机制用于 speculative decoding：draft model 和 target model 分别映射到不同 vFPGA，互相通过 RDMA 传递 KV cache
   - 利用动态服务重配置实现 FPGA 上的 MoE（Mixture of Experts）专家路由：根据请求特征在线切换激活的专家子网络 kernel
   - 探索 FPGA 作为 AI networking hub 的角色：Coyote v2 的 RoCEv2 栈 + GPU 直连 + FPGA 计算能力可实现 gradient compression/all-reduce offload

---

## 八、总结

Coyote v2 是一个开源 FPGA Shell，核心贡献是将服务层从静态层剥离，实现了三层分层架构，支持服务和应用的运行时动态重配置（比全量重编程快约 2 个数量级），同时提供多路并行应用接口和 cThread 软件抽象以消除流水线空闲时间。适用场景包括需要多租户、弹性服务配置的数据中心 FPGA 部署，以及探索 FPGA-GPU 异构加速的研究原型。主要局限在于实验规模偏小、关键性能对比选用了不公平的基线，且商业 Shell 的性能对比缺失。
