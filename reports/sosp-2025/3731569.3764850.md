## 一、背景

大语言模型（LLM）的训练需要在数千乃至数万张 GPU 上进行分布式并行执行。为此，工程师需要使用数据并行（DP）、张量并行（TP）、流水线并行（PP）等复杂技术的组合，通常称为 3D Parallelism。最新的 LLM（如 Llama 3 405B、DeepSeek-V3 671B）的训练成本高达数百万美元，历时数周乃至数月。

分布式训练系统（如 Megatron-LM、DeepSpeed、nnScaler）通过自动并行化框架将逻辑模型转换为多设备执行计划，但这一过程本质上极易引入错误。更危险的是，并行化 bug 往往是"静默"的——训练看似正常运行，但实际产生了错误的梯度更新，导致模型质量受损，而发现这些 bug 可能要等到数周训练之后。

---

## 二、要解决的问题

### 并行化 bug 普遍存在且难以发现

对 MegatronLM（26 个）、DeepSpeed（28 个）、nnScaler（25 个）的 commit 日志和 GitHub issue 分析显示，三大系统均存在大量并行化特有的 bug，涵盖算子变换错误、调度错误、通信错误等多类。

### 传统测试手段失效

- 浮点计算的数值漂移（尤其是 mixed-precision 训练）使得无法用数值对比区分正常误差与真实 bug
- 全规模训练只能跑一次，无法获得额外的参考基准
- 缩小规模测试容易漏掉只在全规模下才触发的 bug

### 直接形式化验证不可扩展

LLM 动辄数千亿参数，对应的计算图有数百万个算子和张量，直接在全图上做形式化等价验证会使 SMT solver 遭遇指数级复杂度爆炸，即便单个元素访问的符号表达式比较也无法终止。

---

## 三、核心设计

TrainVerify 的核心思路是：**不验证整个训练系统栈，只验证并行化执行计划（execution plan）与逻辑模型之间的等价性**——即"并行化等价（Parallelization Equivalence，PE）"。

**并行化等价定义**：对于任意输入 $x$，并行化 DFG $G_p$ 中的每个逻辑张量的值等于其在逻辑 DFG $G_l$ 中对应张量通过特定聚合操作（如 AllReduce 求和、Concatenate）的结果。

为实现这一目标，TrainVerify 设计了三个关键机制：

### 1. 符号化数据流图（Symbolic DFG，sDFG）

- 将逻辑图和并行化图中的张量替换为符号实数（$\mathbb{R}$）元素的符号张量，消除浮点数值噪声
- 重写 PyTorch 算子（MatMul、AllReduce 等）为支持符号操作数的等价定义
- 重建完整训练迭代，包括 forward、backward、optimizer step 和 loss/gnorm 计算（PyTorch 自动微分只记录 forward，需要额外补全）
- 通过**Lineage**元数据记录逻辑张量与其并行化子张量之间的映射关系（索引映射 + 聚合方式）

### 2. 分阶段验证（Staged Verification）

- 利用流水线并行的直觉：模型可按层分解为若干 Stage，每个 Stage 独立验证
- 若每个 Stage 的 $G_l$ 与 $G_p$ 子图等价，且相邻 Stage 的输入/输出等价，则整体模型等价——链式证明
- 以 Lineage 驱动图对齐与 Stage 划分，Stage 之间可并行求解（Process Pool）
- 支持 approximate equivalence 配置（如 LocalBatchNorm 近似 GlobalBatchNorm、MoE routing 限制子集）

### 3. 形状规约（Shape Reduction）

- DNN 算子具有 SIMD 特性：同一 kernel 函数反复作用于不同数据元素，验证一个代表性形状即可扩展至全规模
- 在保持 shape alignment constraints（如 MatMul 中 $M/K/N$ 维度一致性）和 semantic intactness constraints（如 $K \geq 2$）的前提下，用整数规划（Integer Quadratic Optimization）求解每个张量每个维度的最小可行规约形状
- 形式化证明了在规约形状上的并行化等价可以扩展到原始全尺寸形状（利用 SIMD 函数的 affine dependency mapping 性质）

## 四、实现细节

- **集成框架**：TrainVerify 集成于 nnScaler，以模块化接口分离 DFG 来源和求解器后端，理论上支持任何能提供 SSA 计算图和 Lineage 的并行化框架（如 StableHLO、XLA auto-sharding）
- **求解器**：使用 Z3 SMT solver；针对表达式相等的常见情形，先用 `z3.Tactic("solve-eqs")` 做快速表达式比较，等价则短路，不等价才落回完整 SMT 验证（hybrid equivalence checking）
- **Lazy Symbolization**：符号变量和 Z3 表达式仅在 Stage Worker 内实例化，避免主进程中 Python `fork` 的 copy-on-write 开销和 Z3 context table 的容量限制
- **算子重写规模**：40 个算子，约 500 行代码，32 人工开发小时；依赖 NumPy 和 Python 内置操作符模拟 PyTorch 语义
- **并行求解**：最多 30 个并发 Stage Worker；大规模模型（如 DS-V3-671B）受内存约束降至 10 个

## 五、实验结果

### 实验平台
- DFG 生成：4 × NVIDIA A6000 GPU 机器（通过 nnScaler）
- 验证：Azure 实例，32-core Intel Xeon Platinum 8473C CPU，1.34 TB 内存

### 真实模型验证结果

| 模型 | 规模 | DP | TP | PP | 端到端时间 |
|---|---|---|---|---|---|
| Llama3-8B | 32 层 | 512 | 1 | 1 | 0.2 h |
| Llama3-70B | 80 层 | 16 | 8 | 4 | 2.4 h |
| Llama3-405B | 126 层 | 64 | 8 | 16 | 8.0 h |
| DeepSeek-V3-16B | 27 层 | 16 | 4 | 2 | 0.4 h |
| DeepSeek-V3-236B | 60 层 | 16 | 8 | 4 | 2.4 h |
| DeepSeek-V3-671B | 61 层 | 32 | 8 | 8 | 9.0 h |

### 可扩展性

- **对张量形状不敏感**：验证时间与 global batch size、hidden dim、sequence length、attention heads 无关（因形状规约）
- **对并行度线性增长**：增加 PP/DP/TP/micro-batch 时，验证时间近似线性增长
- **Stage 并行加速**：8-GPU Llama3-8B 下，并行求解比串行快约 5×

### Bug 检测

- 从 MegatronLM、DeepSpeed、nnScaler 中选取 14 个真实 bug 案例，全部在 1 分钟内被检测到
- 在 nnScaler 中发现 3 类新 violation（C1：分片不可分片维度；C2：违反 SSA 约定；C3：backward 图中存在悬空张量）

## 六、批判性分析

### 验证代价被轻描淡写

论文将 8–9 小时的验证时间描述为"acceptable"，理由是训练本身需要数周。但实际工程场景中，形式化验证是否会成为开发迭代瓶颈并未讨论。每次修改并行化策略后都需要重跑验证，高频迭代场景下 8 小时的代价并不轻。

### 覆盖范围存在明显盲区

论文明确将以下问题排除在外：kernel 库正确性、通信库正确性、buffer 管理（内存对齐、连续性）、内存布局 bug。而这些恰恰是分布式训练中非常常见的一类问题（Table 1 中 communication 类 bug 有相当一部分与此相关）。论文暗示这些可由其他工具覆盖，但并未展示组合使用的完整验证覆盖率。

### 实验基线过于单一

可扩展性实验仅使用 Llama3-8B 作为基础模型，且运行在相对小规模（DP/TP/PP 度均较小）下。对于 D3（DS-V3-671B）这样的极端情形，main process stall 问题已经出现，但论文并未讨论 Stage Worker 内存溢出后的 fallback 策略。

### 新发现 bug 价值存疑

C2 类 bug（违反 SSA 约定）被论文自己承认"observed cases are mathematically equal"，实际上并不会导致错误训练，只是潜在脆弱点。C3 类 bug（悬空张量）同样被说明在现实中"happen to be not reflected"。这些发现更像是代码质量问题而非会影响训练正确性的 bug。

### 与 MegatronLM 的集成成本被回避

论文承认 TrainVerify 不能直接应用于 MegatronLM 这类 code-based 并行化系统（需要 SSA 图 + Lineage），仅提及"可通过 PyTorch FX tracing + 手动/自动标注"来支持，没有任何实验验证这条路径的可行性和成本。

## 七、AI Infra / MLSys 视角

本文直接针对分布式 LLM 训练系统的正确性验证，对 AI Infra 研究具有高度相关性。

**核心启发：**
- 将"并行化正确性"的验证问题从运行时检测（runtime monitoring）提升到编译期（execution plan 生成后、训练执行前）的静态形式化验证，是方法论层面的重要转变。这启示我们：训练系统的可信度保证不一定要依赖大量昂贵的 sanity check 运行，而是可以通过 plan-level 的符号推理来实现。
- **Shape Reduction** 的思路值得迁移：SIMD 结构允许在"代表性规模"上做验证并外推，这种 dimensionality reduction 思路也可以用于其他大规模系统属性验证（如通信拓扑正确性、内存访问模式分析）。

**可迁移的技术方向：**
- **推理系统的等价性验证**：KV cache 管理、PagedAttention、prefill-decode 拆分等优化会引入类似的并行化等价问题。TrainVerify 的方法论可以延伸到推理引擎的 plan-level 验证。
- **自动并行化的可信度**：nnScaler、Alpa 等框架自动搜索并行策略，TrainVerify 的集成使得搜索出的 plan 可以自动验证，形成"搜索-验证"闭环。这是工业级 AutoParallel 框架的重要缺失环节。
- **MoE 路由正确性**：论文中对 MoE approximate equivalence 的处理是一个有趣的起点，Expert Parallelism 下的路由逻辑正确性验证是一个尚未充分解决的问题。

**值得跟进的 future work：**
1. **自动化 operator 重写**：目前需要手动重写 40 个算子，能否通过 program synthesis 或 LLM 辅助自动化？
2. **增量验证**：当并行化策略局部修改时，能否复用已验证的 Stage 结果，避免全图重验？
3. **验证感知的 plan 搜索**：在自动并行化搜索过程中，将 verification feasibility 作为约束或目标函数之一。

---

## 八、总结

TrainVerify 首次为分布式 LLM 训练提供了 plan-level 的形式化正确性保证，通过符号化 DFG、分阶段并行验证和形状规约三项技术，成功将验证扩展到 Llama3-405B 和 DeepSeek-V3-671B 等前沿模型。其主要局限在于：验证时间随规模增长（最大模型需 9 小时）、覆盖范围不含 kernel 和 buffer 层 bug、与非 nnScaler 框架的集成需要额外工程投入。这项工作为构建可信分布式训练系统提供了一条新的技术路线。
