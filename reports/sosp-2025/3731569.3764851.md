# Tai Chi: A General High-Efficiency Scheduling Framework for SmartNICs in Hyperscale Clouds

## 1. 论文基本信息

- **标题**: Tai Chi: A General High-Efficiency Scheduling Framework for SmartNICs in Hyperscale Clouds
- **作者**: Bang Di, Yun Xu, Kaijie Guo, Yibin Shen, Yu Li, Sanchuan Cheng, Hao Zheng, Fudong Qiu, Xiaokang Hu, Naixuan Guan, Dongdong Huang, Jinhu Li, Yi Wang, Yifang Yang, Jintao Li, Hang Yang, Chen Liang, Yilong Lv, Zikang Chen, Zhenwei Lu, Xiaohan Ma, Jiesheng Wu (阿里巴巴)
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764851

## 2. 研究背景

超大规模云提供商（AWS Nitro、阿里云 CIPU、Azure SmartNIC）使用 SmartNIC 来卸载 data-plane 服务（ DPDK、SPDK ）和 control-plane 任务。SmartNIC 集成了少量通用处理器核心（ARM 或 x86）和可编程 I/O 硬件加速器（FPGA 或 ASIC），通过 PCIe 设备形式提供。

**当前架构的问题**：为保证 Data Plane (DP) 的 SLO（延迟、IOPS），云提供商按 DP 峰值负载静态划分 CPU 资源——这导致 DP 服务在 99% 的运行时间内有 **67.5% 的 CPU 周期处于空闲**。与此同时，Control Plane (CP) 任务（VM 创建/销毁、设备管理、性能监控、CSP 编排）的 SLO（如 VM 启动时间）持续恶化——在高实例密度下，VM 启动时间超过 SLO 目标 3.1 倍，CP 任务执行时间退化 8 倍。

现有方案（Shenango、Caladan、Concord、Skyloft、Vessel）的局限性：
- **C1**: 忽视 Control Plane SLO——CP 任务需要严格 SLO，与最佳努力（best-effort）任务本质不同
- **C2**: CP 的 ms 级非抢占例程导致 DP 尾延迟 spikes——CP 任务持有 spinlock 时，DP 服务被迫等待
- **C3**: 对 CP 代码的大规模修改不切实际——生产环境中 CP 生态系统包含 300-500 个异构任务（C、Python、Java、Bash、Rust）
- **C4**: 与 SmartNIC 硬件不兼容——依赖新硬件特性（如 UINTR）的方案缺乏现代 SmartNIC CPU 支持
- **C5**: 传统调度开销不可忽视——在资源受限的 SmartNIC 上，额外 CPU 消耗不可接受

## 3. 要解决的问题

**核心问题**：如何在不修改 CP 任务代码、不引入显著 DP 性能损失的前提下，利用 DP 服务的空闲 CPU 资源来加速 CP 任务执行，同时满足两类任务的 SLO？

具体挑战包括：
- SmartNIC 仅提供 8-16 个 ARM CPU（如 NVIDIA Blue Field-3），资源极为受限
- CP 任务包含 ms 级非抢占例程（如 spinlock 最长 67 ms），阻止 OS scheduler 及时响应突发 DP I/O
- 现有方案要么需要侵入性代码修改，要么无法满足严格 SLO 要求

## 4. 核心贡献

1. **生产环境特征分析**：首次对 SmartNIC 上生产环境中的 DP 服务和 CP 任务进行了详细分析，揭示了 67.5% CPU 空闲率和 ms 级非抢占例程的普遍存在。
2. **混合虚拟化框架**：提出 Tai Chi——一种硬件-软件协同设计的混合虚拟化框架，在单一 OS 内统一物理 CPU 和虚拟 CPU，同时保持原生 DP-CP IPC 语义。
3. **微秒级调度精度**：通过引入 vCPU preemptibility 和硬件-软件协同设计的 workload probe，实现了微秒级调度精度，消除了 ms 级非抢占例程导致的 DP 延迟 spikes。
4. **零代码修改的透明度**：通过统一 IPI 编排器（Unified IPI Orchestrator），使 vCPU 对 OS 表现为物理 CPU，无需修改 CP 任务代码。
5. **跨平台兼容性**：支持主流 SmartNIC 平台（NVIDIA Blue Field-3、Intel IPU、阿里云 CIPU、Azure SmartNIC），并兼容 DPDK 和 SPDK。

## 5. 主要研究方法

### 5.1 生产环境分析
- **CPU 利用率**：收集数百个计算节点上 DP 服务（网络和存储子系统）每秒 CPU 利用率数据，持续 12 小时（约 120 万条记录）。发现 99.68% 的 CPU 利用率值低于 32.5%，即 67.5% 的空闲周期。
- **非抢占例程分布**：在数十个计算节点上追踪非抢占例程，12 小时内检测到超过 45.6 万个超过 1ms 的非抢占例程（94.5% 持续 1-5 ms），最长达到 67 ms。在大规模生产环境中，每个 ms 级的 DP 延迟 spikes 都是不可接受的。
- **实例密度影响**：随着实例密度增加（4 倍基线），CP 任务执行时间退化 8 倍，VM 启动时间超过 SLO 目标 3.1 倍。

### 5.2 虚拟化作为解决方案
关键观察：
- SmartNIC 支持硬件辅助虚拟化（Intel VT-x / ARM 扩展），提供可抢占的 vCPU context
- vCPU 可以在任何时刻被外部事件（VM-exit）中断，可用于隔离 DP 服务和 CP 任务

传统虚拟化方案的局限性：
- **Type-1（Xen）**：所有工作负载共享同一 Guest OS，DP 服务运行在 vCPU 上引入虚拟化税（7% 性能下降），vCPU 切换延迟 ~2 us
- **Type-2（QEMU+KVM）**：DP 和 CP 隔离在不同 OS，破坏原生 IPC 语义，且 Guest OS 消耗额外 CPU 和内存（25.9% 性能下降）

### 5.3 混合虚拟化设计
Tai Chi 的核心设计：
1. **Hybrid Virtualization**：vCPU 和 pCPU 共享原生 SmartNIC OS，vCPU 对 OS 表现为额外物理 CPU，无需修改 OS 调度器
2. **Workload Probe**：硬件-软件协同设计，精确预测 I/O 工作负载到达时机，提供 vCPU 切换的调度窗口
3. **统一 IPI 编排器**：拦截和模拟 vCPU 和 pCPU 之间的 IPI，保持原生 CP-DP IPC 语义

## 6. 设计与实现

### 6.1 架构设计
Tai Chi 采用两层架构（Figure 7a）：
- vCPU 由 Tai Chi 虚拟化为额外物理 CPU，暴露给 SmartNIC 原生 OS
- OS 将任务调度到所有 CPU（包括 vCPU 和 pCPU），无需修改
- CP 任务在 vCPU 上执行，可被微秒级抢占
- DP 服务直接在 pCPU 上运行，无虚拟化层

### 6.2 隐藏调度延迟
SmartNIC 提供 I/O 预处理窗口（2.7 us 进行硬件预处理 + 0.5 us DMA 写入共享内存），Tai Chi 利用这个 3.2 us 窗口提前主动抢占 CP 的 vCPU，从而隐藏 2 us 的 vCPU 上下文切换延迟。

### 6.3 Workload Probe 设计
- 可编程 I/O 加速器在 I/O 包到达时产生信号
- Tai Chi 利用此信号提前感知 I/O 工作负载，在 DP 处理开始前预留调度窗口
- 关键指标：I/O 包处理的 2.7 us 硬件预处理 + 0.5 us DMA 写入，提供了足够的预测和抢占时间

### 6.4 实现细节
- **统一 IPI 编排器**：1:1 映射 guest 物理地址和 host 物理地址，确保 vCPU 和 pCPU 间一致的内存视图
- **内存保护**：利用 GPU 虚拟内存机制实现文件系统（Tai Chi Daemon）和普通 GPU 应用之间的内存隔离
- **访问控制**：使用加密算法为每个用户进程生成唯一不可伪造的签名（signature），Daemon 验证签名以控制文件访问

## 7. 主要实验结果

### 7.1 CP 性能提升
- VM 启动时间降低 **3.1 倍**
- CP 任务执行时间降低 **8 倍**
- 在高实例密度下（4 倍基线），CP 性能提升显著

### 7.2 DP 性能影响
- DP 服务平均开销仅 **0.7%**（vs. Type-1 的 7% 和 Type-2 的 25.9%）
- 保持 DP SLO 合规

### 7.3 调度开销
- 消除了 ms 级延迟 spikes（原先由 CP spinlock 持有导致）
- 实现微秒级调度精度

### 7.4 三年生产部署验证
- 在顶级云提供商的超大规模生产环境中部署
- 跨多种 SmartNIC 平台验证兼容性

## 8. 潜在问题/局限性

1. **Workload Probe 的硬件依赖性**：Tai Chi 依赖 SmartNIC 的可编程 I/O 加速器来提前感知 I/O 工作负载，这可能不适用于所有 SmartNIC 实现。
2. **vCPU 数量的资源开销**：每个 CP 任务需要 vCPU 上下文，vCPU 数量的增加可能带来额外的内存开销（在 8-16 个 CPU 的 SmartNIC 上不可忽视）。
3. **与现有安全机制的兼容性**：虽然 Tai Chi 声称提供了内存保护和访问控制，但与 SmartNIC 上的其他安全机制（如 TrustZone、安全启动）的交互未详细讨论。
4. **调试和可观测性挑战**：vCPU 和 pCPU 混合调度可能使性能调试和问题排查变得复杂。
5. **自适应调度策略缺失**：Tai Chi 似乎是静态的调度策略，没有讨论如何根据负载动态调整 vCPU/pCPU 分配比例。
6. **未讨论能耗影响**：CP 任务在 vCPU 上的频繁抢占和上下文切换可能增加功耗，这在电池供电的边缘 SmartNIC 场景中可能成为问题。

## 9. 未来工作

1. **动态 vCPU 资源调整**：根据负载动态调整分配给 CP 任务的 vCPU 数量。
2. **多租户支持扩展**：在 SmartNIC 级别的资源隔离下支持更多租户场景。
3. **与其他虚拟化技术的集成**：探讨与容器、轻量级 VM 等其他隔离技术的协同。
4. **能耗优化**：结合 DVFS 等技术优化调度策略的能耗效率。

## 10. 个人评注

**Tai Chi 是一篇来自工业界的扎实工程论文**，解决了超大规模云基础设施中一个被长期忽视但影响显著的问题——SmartNIC 上 DP 和 CP 资源的静态划分导致的 CPU 浪费。

论文最值得称道的是其**从传统虚拟化方案的局限性出发，逐步推导出混合虚拟化架构的推理过程**：从 Type-1 和 Type-2 各自的问题（虚拟化税 vs. IPC 破坏），到 SmartNIC 虚拟化支持的发现，再到"暴露 vCPU 为额外物理 CPU"这个关键洞察，最终通过 Workload Probe 隐藏 vCPU 切换延迟。整个推理链条清晰、逻辑严密。

**批评性思考**：
- 论文的"微秒级调度"声称有些模糊：虽然 vCPU 切换本身是微秒级的，但整个调度决策（workload probe + 抢占决策 + 上下文切换）是否也保持在微秒量级未充分评估。
- 3.1 倍 VM 启动改善的数字需要谨慎看待——这是在特定高密度场景下相对于静态划分的改进，但相对于完全优化方案（如果存在的话）的改进幅度未讨论。
- "zero code modifications"的声明可能过于绝对：虽然 CP 任务本身无需修改，但 OS 层的 IPI 拦截和模拟逻辑（Unified IPI Orchestrator）实际上是相当深的内核级修改，只是这些修改被封装在了 Tai Chi Daemon 中。
- 论文未讨论与 eBPF、智能网卡上运行的其他服务（如安全监控、网络功能虚拟化）的共存问题。
- 最关键的未回答问题：67.5% CPU 空闲是"浪费"还是"必要的预备能力"？如果突发流量瞬间达到峰值，这些空闲 CPU 是用于吸收突发还是真的空闲？

总体而言，这是一篇针对特定工业场景的深度定制解决方案，适合云基础设施工程师和网络功能虚拟化研究者关注。对于通用操作系统社区，其价值在于展示了如何通过硬件-软件协同设计突破传统虚拟化的性能-灵活性权衡。
