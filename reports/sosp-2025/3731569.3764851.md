# Tai Chi: A General High-Efficiency Scheduling Framework for SmartNICs in Hyperscale Clouds

**作者**：Bang Di, Yun Xu, Kaijie Guo, Yibin Shen, Yu Li, Sanchuan Cheng, Hao Zheng, Fudong Qiu, Xiaokang Hu, Naixuan Guan, Dongdong Huang, Jinhu Li, Yi Wang, Yifang Yang, Jintao Li, Hang Yang, Chen Liang, Yilong Lv, Zikang Chen, Zhenwei Lu, Xiaohan Ma, Jiesheng Wu（Alibaba Group）

## 一、背景

主流云服务商（AWS、Azure、Alibaba）广泛采用 SmartNIC（如 AWS Nitro、Alibaba CIPU、NVIDIA BlueField-3）将数据面（DP）服务和控制面（CP）任务从主机 CPU offload 到专用硬件上。SmartNIC 上的 DP 服务（DPDK/SPDK）负责高性能 I/O 处理，CP 任务则负责设备管理（VM 创建/销毁）、性能监控、以及与集群管理系统的 CSP 编排交互。

为了避免 DP 和 CP 相互干扰，SmartNIC 上的 CPU 资源被静态划分给两类工作负载。由于 SmartNIC CPU 数量极为有限（NVIDIA BlueField-3 仅有 8–16 个 ARM 核），这种静态划分导致了双重问题：DP 服务按峰值负载预留资源，造成大量 CPU 闲置；而随着实例密度不断提高，CP 任务 CPU 越来越不够用，VM 启动延迟等关键 SLO 频繁违约。

---

## 二、要解决的问题

**核心矛盾**：DP 服务在 99% 的运行时间内有 67.5% 的 CPU 周期闲置，但 CP 任务却面临严重的 CPU 短缺，在 4 倍实例密度下 VM 启动时间超出 SLO 目标 3.1 倍。

直接把 CP 任务调度到 DP 的空闲 CPU 上行不通，原因有五（论文称为 C1–C5）：

1. **C1：忽视 CP SLO**。现有系统将共同调度的任务视为低优先级 best-effort 任务，而 CP 任务有严格 SLO 要求（如 VM 启动时间），需要区别对待。
2. **C2：CP 中的 ms 级不可抢占例程**。CP 任务频繁进入内核执行 spinlock、设备初始化等操作，持锁时间最长达 67ms，远超 DP µs 级 I/O 处理延迟，直接导致 DP 尾延迟飙升。
3. **C3：CP 生态系统的侵入性修改代价极高**。生产环境中有 300–500 个异构 CP 任务（C/Python/Java/Bash/Rust），逐一修改不现实。
4. **C4：SmartNIC 硬件不兼容**。依赖新硬件特性（如 x86 的 UINTR）的方案在 SmartNIC ARM 核上无法运行。
5. **C5：调度开销不可忽视**。SmartNIC CPU 资源极度紧张，传统调度方法（如 Shenango、Caladan 的专用轮询线程）会占用至少一个 CPU，大幅降低 DP 吞吐天花板。

---

## 三、核心设计

TaiChi 的核心思路是**硬件-软件协同设计的混合虚拟化（Hybrid Virtualization）**：将 CP 任务运行在 vCPU 上，将 DP 服务运行在 pCPU 上，同时让两者共享同一个 SmartNIC 原生 OS，保留 DP-CP 之间的原生 IPC 语义（共享内存、信号、管道、文件系统访问）。

**三大组件**：

### 1. vCPU 调度器（vCPU Scheduler）

- **DP-to-CP 调度**（yield）：软件负载探针检测到 DP CPU 空闲时，向目标 CPU 投递专用 softirq，在 softirq handler 中切换到 vCPU 上下文执行 CP 任务。
- **CP-to-DP 调度**（preempt）：硬件负载探针在 I/O 预处理窗口内触发中断，使 vCPU 发生 VM-exit，恢复 DP 执行。
- **自适应 vCPU 时间片**：初始 50µs，根据 VM-exit 原因动态调整（timeslice 到期 → 倍增；硬件探针触发 → 重置为 50µs），减少不必要的 VM-exit。
- **锁安全性**：当 CP 任务持锁时被抢占，调度器立即将其重新调度到空闲 DP pCPU，确保前向推进，避免死锁。

### 2. 统一 IPI 编排器（Unified IPI Orchestrator）

直接在 vCPU 和 pCPU 之间发送 IPI 不可行（跨越虚拟化边界）。统一 IPI 编排器通过 hook 内核的 `x2apic_send_IPI` 函数，拦截所有 IPI 并根据目标 CPU 状态路由：
- 目标是 pCPU → 通过 MSR 写直接注入；
- 目标是 vCPU → 通过 posted-interrupt 技术注入；
- 源是 vCPU 发出 IPI → 先 VM-exit，再由调度器重发。

vCPU 被注册为 OS 的 native CPU（通过 CPU ID、LAPIC ID 元数据），CP 任务通过标准 CPU affinity（cgroup）绑定到 vCPU，**零代码修改**。

### 3. 硬件-软件协同负载探针（Workload Probe）

**软件探针（自适应 yield 算法）**：监控 DP 服务的连续空轮询次数（empty polling count），超过阈值则判定为空闲，通知 vCPU 调度器。阈值根据 VM-exit 原因动态调整（timeslice 到期 → 减小阈值；假阳性 → 增大阈值）。

**硬件探针**：利用 SmartNIC 可编程 I/O 加速器的 I/O 预处理窗口（约 3.2µs：2.7µs 硬件预处理 + 0.5µs DMA 写入）。加速器在开始处理 I/O 包时，若目标 CPU 处于 V-state，则异步触发 IRQ，诱发 VM-exit 让 DP 恢复执行，**在 I/O 预处理窗口内完成 vCPU 抢占，将 2µs 虚拟化调度延迟完全隐藏**。

## 四、实现细节

- **软件模块**：约 5,800 行 Linux 内核模块，实现混合虚拟化框架。
- **硬件模块**：约 30 行，修改可编程 I/O 处理加速器，实现硬件负载探针。
- 利用 Intel VT-x / ARM 虚拟化扩展（Intel VT-x 的 Posted-Interrupt、IPIv 等特性）降低 VM-exit 开销。
- DP 服务通过调用 `notify_idle_DP_CPU_cycles` API 通知空闲（修改 < 10 行 DPDK 代码），CP 任务零修改。
- 内存视图一致性：vCPU 与 pCPU 之间 GPA 到 HPA 1:1 映射，消除地址空间差异。
- SmartNIC 平台兼容性：支持 NVIDIA BlueField-3、Intel IPU、Alibaba CIPU、Azure SmartNIC。

## 五、实验结果

**实验环境**：Alibaba IaaS 生产环境，SmartNIC（12 CPU，200Gb/s）+ AMD EPYC Genoa 主机（96 CPU@2.7GHz，1TB DRAM），VM（96 vCPU，384GB RAM），Linux 5.10。

**基线**：静态资源分配（DP 8 个 pCPU，CP 4 个 pCPU），即当前生产 SOTA。

### CP 性能提升（Q1）

| 并发 CP 任务数 | Baseline | TaiChi | 提升 |
|:-:|:-:|:-:|:-:|
| 32 | 基准 | 4x 更快 | **4x** |
| 生产（高实例密度） | 超 SLO 3.1x | SLO 内 | **3.1x 改善** |

### 混合虚拟化开销（Q2）

| 方案 | 网络开销（tcp_crr） | 存储开销（fio IOPS） |
|:-:|:-:|:-:|
| TaiChi（DP 在 pCPU） | **0.2%** | **0.06%** |
| TaiChi-vDP（DP 在 vCPU，模拟 Type-1） | 8% | 6% |
| 传统 QEMU+KVM（Type-2） | 26% | 25.7% |

### 硬件负载探针效果（Q3）

| 方案 | 最小 RTT | 平均 RTT | 最大 RTT | Mdev |
|:-:|:-:|:-:|:-:|:-:|
| Baseline | 26µs | 30µs | 38µs | 5µs |
| TaiChi | 27µs | 30µs | 38µs | 5µs |
| TaiChi w/o HW probe | 32µs | 37µs | **115µs** | 9µs |

### DP 整体性能（Q4）

全套 netperf/sockperf/MySQL/Nginx 基准，TaiChi 平均 DP 开销 **0.7%**，最高 1.92%（tcp_stream avg_tx_pps）。

### 生产验证（Q5）

TaiChi 在阿里云生产环境**持续运行超过 3 年**，用户零 I/O SLO 违约投诉。

## 六、批判性分析

**基线选择过于保守**：论文以"静态资源分配"作为唯一基线，并以此为由拒绝比较 Shenango/Caladan 等现有系统（理由是它们无法在 SmartNIC 上部署）。这个说法没有经过实验验证——论文没有展示"如果强行部署 Caladan/Shenango 会发生什么"，读者只能接受作者的论断。Table 1 的比较也主要停留在定性层面。

**硬件探针的依赖假设过于理想**：TaiChi 的核心创新之一是利用 3.2µs I/O 预处理窗口隐藏 2µs vCPU 调度延迟。这个窗口是 Alibaba 自研 SmartNIC（CIPU）上的测量结果，但论文声称兼容 NVIDIA BlueField-3 和 Intel IPU——不同平台的预处理窗口大小可能差异显著，30 行硬件修改是否能直接迁移缺乏证明。

**合法的 CP 任务绑定问题被轻描淡写**：论文说 CP 任务只需通过 CPU affinity 绑定到 vCPU 即可，"零代码修改"。但生产中 300–500 个异构任务的 affinity 配置本身就是一项运维工程，论文没有讨论任何配置失误的风险（例如 CP 任务意外绑到 pCPU 上破坏 DP 隔离）。

**锁安全机制的概率估计不够严谨**：论文以 $L^M$（其中 $L$ 为 DP pCPU 繁忙概率）论证死锁概率极低，但未给出具体数值，也没有说明高负载场景下（DP 利用率接近 32.5% 上界时）这个概率的实际量级。

**实验规模偏小**：单台 SmartNIC + 一台主机的 micro-benchmark，无法代表"hyperscale"场景。生产数据虽然提到 3 年部署经验，但具体的机器数量、故障场景、SLO 达标率等数据均未披露，可信度依赖信任背书而非数据透明度。

**CP 性能实验的工作负载过于合成**：synth_cp 被设计为每个任务执行 50ms，但真实 CP 任务的时间分布远非如此均匀，论文缺乏真实 CP 任务（如 VM 创建全链路）在受控实验中的延迟分布数据。

## 七、AI Infra / MLSys 视角

SmartNIC 在 AI Infra 中越来越重要——RDMA 网络（用于分布式训练的 all-reduce、parameter server 通信）、NVMe-oF 存储加速（用于训练数据 pipeline）以及向量化 I/O（用于 embedding 服务）都依赖 SmartNIC DP 服务。TaiChi 的若干设计思路对 AI 系统有直接借鉴价值：

**混合虚拟化调度思路的迁移**：AI 训练中的 prefetching、checkpointing、日志等 CP 类任务同样面临与 DP 网络/存储 I/O 竞争资源的问题。TaiChi 的 hybrid virtualization 框架为在同一 SmartNIC 上共同调度计算密集型 AI 任务提供了参考架构。

**自适应 Yield 算法**：TaiChi 的软件负载探针中，根据 VM-exit 原因动态调整轮询阈值的思路，与 GPU 内核 poll-based 通信优化（如 NCCL 的 spin-wait）存在相似性，可以探索类似的自适应策略降低通信延迟的长尾。

**硬件预处理窗口的利用**：AI Infra 中的 RDMA NIC 同样有硬件预处理流程（CQ 轮询前的 doorbell 处理、WQE 解析等），是否存在类似的可预测时间窗口用于隐藏软件调度延迟，是一个值得探索的研究方向。

**Future work 方向**：论文在第 9 节提到集成可编程硬件（如 I/O pipeline 的 packet metadata）实现多维度空闲检测，以及 cache/TLB 隔离——这两点对 AI 推理服务中 latency-sensitive 请求与 batch 请求的混部场景同样适用。

---

## 八、总结

TaiChi 通过硬件-软件协同设计的混合虚拟化框架，解决了 SmartNIC 上 DP 服务与 CP 任务无法高效共调度的核心问题。其关键创新在于：将 CP 任务封装在可抢占的 vCPU 上下文中以突破 ms 级不可抢占例程，同时利用 SmartNIC I/O 预处理窗口主动隐藏 2µs 虚拟化调度延迟，并通过统一 IPI 编排让 vCPU 对 OS 完全透明（零代码修改）。经过三年阿里云生产验证，TaiChi 在 DP 开销仅 0.7% 的代价下将 VM 启动时间提升 3.1 倍。主要局限在于强依赖 SmartNIC 可编程加速器的特定硬件特性，跨平台移植成本和非均匀负载下的稳健性仍有待在更大规模和更多平台上验证。
