# Tai Chi: A General High-Efficiency Scheduling Framework for SmartNICs in Hyperscale Clouds

**作者**：Bang Di, Yun Xu, Kaijie Guo, Yibin Shen, Yu Li, Sanchuan Cheng, Hao Zheng, Fudong Qiu, Xiaokang Hu, Naixuan Guan, Dongdong Huang, Jinhu Li, Yi Wang, Yifang Yang, Jintao Li, Hang Yang, Chen Liang, Yilong Lv, Zikang Chen, Zhenwei Lu, Xiaohan Ma, Jiesheng Wu (Alibaba Group)

## 一、背景

主流云服务商（AWS Nitro、Azure SmartNIC、阿里巴巴 CIPU）广泛采用 SmartNIC 来卸载数据平面（DP）服务（如 DPDK、SPDK）和控制平面（CP）任务（如设备初始化、性能监控、集群编排）。为避免干扰，DP 和 CP 之间通常采用静态 CPU 分区策略：DP 服务按峰值负载预留 CPU 以保证 I/O SLO。

然而，随着实例密度（VM density）持续增长——服务器 CPU 和 VM 数量增速远超 SmartNIC CPU 增速——CP 任务面临越来越严重的资源不足问题。生产环境数据显示，在 4 倍基线密度下，VM 启动时间超 SLO 3.1 倍，而 DP 服务 99% 的运行时间内有 67.5% 的 CPU 周期处于空闲状态。

---

## 二、要解决的问题

1. **CP 资源匮乏与 SLO 违反**：静态分区导致 DP 大量 CPU 空闲，但 CP 任务在高密度场景下资源不足，VM 启动等关键 SLO 频繁违约。
2. **非抢占式内核例程导致 DP 延迟尖刺**：如果直接将 CP 任务调度到 DP 空闲 CPU 上，CP 任务中大量 ms 级非抢占式内核例程（如 spinlock）会阻塞 DP 的 µs 级 I/O 处理，造成严重的尾延迟。
3. **CP 生态系统复杂、难以修改**：生产环境有 300-500 个异构 CP 任务（C/Python/Java/Bash/Rust），大规模代码修改不现实。
4. **SmartNIC 硬件兼容性**：现有调度方案依赖 UINTR 等新硬件特性，SmartNIC CPU 不支持。
5. **调度开销不可忽视**：SmartNIC 只有 8-16 个 ARM CPU，传统调度方案占用额外 CPU 资源不可接受。

---

## 三、洞察与设计

**关键洞察**：SmartNIC 的可编程 I/O 加速器在 DP 服务处理 I/O 包之前有一个约 3.2µs 的预处理窗口（2.7µs 硬件预处理 + 0.5µs DMA 写入）；利用这个窗口可以提前触发 vCPU 上下文切换，从而将虚拟化带来的 2µs 调度延迟完全隐藏在 I/O 预处理过程中。

基于此洞察，Tai Chi 提出**混合虚拟化**（Hybrid Virtualization）架构：

- **vCPU 与 pCPU 共享同一 OS**：将 CP 任务封装在 vCPU 上下文中运行，DP 服务直接在物理 CPU 上运行。vCPU 注册为 OS 的"原生 CPU"，对 CP 任务完全透明，无需代码修改。
- **统一 IPI 编排器**（Unified IPI Orchestrator）：拦截并路由 vCPU 与 pCPU 之间的 IPI，使两者在同一 OS 内实现原生 IPC 语义（共享内存、信号、管道等）。
- **软硬件协同工作负载探针**（Workload Probe）：
  - **软件探针**：自适应 yielding 算法，通过监控 DP 服务的连续空轮询次数检测 CPU 空闲，动态调整阈值。
  - **硬件探针**：部署在可编程 I/O 加速器中，在 I/O 预处理阶段检测目标 CPU 状态，若为 V-state 则异步触发中断，提前将 vCPU 切回 pCPU 上下文。

## 四、实现细节

- **整体规模**：软件部分约 5,800 行，作为 Linux 内核模块实现；硬件部分约 30 行，修改可编程 I/O 加速器。
- **vCPU 调度器**：基于 softirq 实现上下文切换。pCPU→vCPU：通过 round-robin 选择 vCPU，发送专用 softirq 激活 vCPU 上下文。vCPU→pCPU：保存 vCPU 状态，恢复 pCPU 状态，退出 softirq。
- **自适应 vCPU 时间片**：初始 50µs，若 vCPU 时间片超时触发 VM-exit 则翻倍（最大化空闲利用），若被硬件探针触发 VM-exit 则重置为 50µs。
- **锁上下文安全处理**：若 CP 任务持有 spinlock 时被抢占，立即将该 vCPU 重新调度到另一个空闲 DP pCPU 上继续执行，避免死锁。若无空闲 DP pCPU（概率为 L^M，极低），则调度到 CP 专用 pCPU。
- **统一 IPI**：拦截内核 `x2apic_send_IPI` 函数，根据源/目标 CPU 状态路由 IPI。
- **DP 服务集成**：仅需在 DP 服务的轮询循环中添加 <10 行代码调用 `notify_idle_DP_CPU_cycles` API。
- **CP 任务部署**：通过标准 CPU affinity（如 cgroup）绑定到 vCPU，零代码修改。
- **利用 Posted-Interrupt 技术**最小化 vCPU VM-exit 开销。

## 五、实验结果

**环境**：阿里巴巴 IaaS 生产环境，SmartNIC 12 CPU，主机 AMD EPYC 96 CPU，DP 8 pCPU + CP 4 pCPU（baseline 静态分区）。

| 指标 | Baseline | Tai Chi | 改善/开销 |
|------|----------|---------|-----------|
| CP 任务执行时间（32 并发） | 1x | ~0.25x | **4x 加速** |
| VM 启动延迟（4x 密度，生产） | 3.1x SLO | 1x SLO | **3.1x 改善** |
| 网络吞吐（tcp_crr） | baseline | -0.2% | 几乎无开销 |
| 存储 IOPS（fio） | baseline | -0.06% | 几乎无开销 |
| DP 综合平均开销 | — | — | **0.7%**（峰值 1.92%） |
| MySQL 吞吐 | baseline | -1.56% avg | 轻微开销 |
| Nginx 请求/秒 | baseline | -0.51% avg | 轻微开销 |

**硬件探针效果**（ping RTT）：

| 方案 | Min(µs) | Avg(µs) | Max(µs) | Mdev(µs) |
|------|---------|---------|---------|----------|
| Baseline | 26 | 30 | 38 | 5 |
| Tai Chi | 27 | 30 | 38 | 5 |
| Tai Chi w/o HW probe | 32 | 37 | 115 | 9 |

**虚拟化方案对比**：Type-1（Xen 式）平均 7% 网络 + 6% IOPS 开销；Type-2（QEMU+KVM）平均 26% 网络 + 25.7% IOPS 开销；Tai Chi 仅 0.2% 网络 + 0.06% 存储开销。

已在阿里云生产环境部署超 3 年，无用户报告 I/O SLO 违反。

## 六、批判性分析

1. **Baseline 选择的局限性**：论文承认现有学术调度系统（Caladan、Shenango、Concord、Skyloft、Vessel）无法直接部署在 SmartNIC 上，因此选择静态分区作为 baseline。这虽然合理，但也意味着论文回避了与这些系统在公平条件下的直接性能对比。读者无法判断 Tai Chi 的混合虚拟化方案在通用场景下相对这些系统的优劣。

2. **CP 性能改善的归因**：4x 加速主要来自将 DP 空闲 CPU 资源分配给 CP，这本质上是增加了 CP 可用 CPU 数量。更有意义的对比应该是：如果直接给 CP 分配更多静态 CPU（减少 DP 预留），性能差距是否依然显著？论文未做这一消融实验。

3. **DP 开销在极端场景下的表现**：论文报告 DP 利用率在 30%（p99 生产场景）下测试，但未充分评估 DP 利用率接近峰值时的表现。cache/TLB 污染在高 DP 负载下可能显著放大，0.7% 的平均开销可能不具代表性。

4. **硬件探针的通用性**：硬件探针依赖可编程 I/O 加速器的约 30 行修改，论文声称兼容 BlueField-3、Intel IPU、CIPU 等主流平台，但仅在阿里巴巴 CIPU 上做了实际验证。跨平台适配的工程难度被轻描淡写。

5. **自适应算法缺乏理论分析**：yielding 阈值和 vCPU 时间片的自适应调整均基于启发式规则（翻倍/重置），缺乏收敛性分析或最优性保证。在工作负载模式快速变化的场景下，这种简单启发式是否足够鲁棒？

6. **3 年生产部署的数据较少**：对于一个声称已大规模部署 3 年的系统，论文仅给出了 VM 启动时间一个生产指标，缺少长期运行的故障率、运维复杂度、边界案例等生产运营洞察。

---

## 七、AI Infra / MLSys 视角

1. **GPU SmartNIC 调度的启发**：随着 GPU 集群规模扩大，DPU/SmartNIC 在 AI Infra 中承担越来越多的角色（RDMA 网络管理、存储 I/O、集合通信加速）。Tai Chi 的混合虚拟化思路可以迁移到 GPU 集群的 DPU 调度场景——在 DPU 上同时运行 RDMA 数据路径和训练任务的控制操作（checkpoint、弹性扩缩容），利用空闲 RDMA 处理周期加速控制面。

2. **推理系统的 DP/CP 协调**：LLM 推理服务中存在类似的 DP（token generation）和 CP（模型加载、KV cache 管理、请求调度）分离。Tai Chi 的 µs 级抢占机制可以启发推理系统中 prefill/decode 阶段的 CPU 资源动态分配。

3. **硬件预处理窗口的思想**：利用硬件流水线中的"预处理窗口"来隐藏软件调度延迟，这个设计范式可以推广到 AI 加速器的调度——例如利用 GPU kernel launch 延迟或 DMA 传输延迟来隐藏调度开销。

4. **可跟进方向**：在异构计算场景（CPU + GPU + DPU）中设计统一的混合虚拟化调度框架，协调 AI 训练/推理的控制面任务与数据面 I/O，是一个有价值的研究方向。

---

## 八、总结

Tai Chi 提出了一种面向 SmartNIC 的混合虚拟化调度框架，将 CP 任务封装在 vCPU 中运行于 DP 空闲 CPU 上，通过统一 IPI 编排器实现 vCPU/pCPU 同 OS 共存与原生 IPC，并利用硬件工作负载探针在 I/O 预处理窗口内隐藏虚拟化切换延迟。该系统在阿里云生产环境部署 3 年以上，实现了 VM 启动时间 3.1x 改善、平均仅 0.7% 的 DP 开销，且对 300-500 个异构 CP 任务无需代码修改。主要局限在于强依赖 SmartNIC 的可编程 I/O 硬件能力，以及自适应调度算法缺乏理论保证。
