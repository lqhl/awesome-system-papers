# cache_ext: Customizing the Page Cache with eBPF

## 论文基本信息
- **标题**: cache_ext: Customizing the Page Cache with eBPF
- **作者**: Tal Zussman, Ioannis Zarkadas, Jeremy Carin, Andrew Cheng, Hubertus Franke, Jonas Pfefferle, and Asaf Cidon
- **会议**: SOSP 2025
- **Session**: Storage and Databases
- **PDF**: 3731569.3764820.pdf

## 研究背景

Linux 操作系统的 page cache 是现代计算基础设施的核心组件，通过减少对存储设备的频繁访问来提升应用程序性能。然而，Linux page cache 采用的 LRU（近似最近最少使用）驱逐策略是一种"一刀切"（one-size-fits-all）的设计——对于扫描密集型（scan-heavy）工作负载、多核系统、以及具有特殊访问模式的数据库和键值存储系统，这种策略往往表现不佳。

早在 1981 年，Michael Stonebraker 就批评过 OS buffer cache 的驱逐策略无法满足数据库需求。几十年间，尽管研究社区提出了大量自适应驱逐策略（如 ARC、LHD、S3-FIFO、MGLRU 等），但这些策略很难被集成到 Linux 内核中——修改内核代码需要深厚的内核知识，且上游变更必须适用于运行在 Linux 上的所有应用程序。例如，Google 花费多年才将 MGLRU 上游，且至今未在所有 Linux 发行版中默认启用。

现有的一些定制化尝试（如 fadvise()、madvise()）语义模糊，实际行为高度依赖内核实现，无法真正解决根本问题。部分应用选择自己实现用户空间的缓存层（如 RocksDB、LevelDB），但这需要显著的开发工作量，且难以在不同进程间共享内存。

## 要解决的问题

如何让应用程序能够在不修改内核代码的情况下，自定义 Linux page cache 的驱逐策略，以匹配各自工作负载的独特访问模式？具体而言：

1. **可扩展性**：现代 NVMe SSD 支持数百万 IOPS，定制化策略必须具有低开销
2. **灵活性**：需要支持多种复杂数据结构（如 LRU、LFU、ARC、S3-FIFO、MGLRU 等）
3. **隔离性**：多租户场景下，不同应用程序的策略不应相互干扰，同时应允许应用间共享内存
4. **安全性**：用户自定义策略返回的 folio 引用必须是有效的，否则可能导致内核崩溃或安全漏洞

## 核心贡献

- **cache_ext**：一个灵活的、可扩展的、安全的 eBPF 框架，用于在 Linux page cache 中实现自定义驱逐策略
- **一套完整的策略实现库**：包括经典策略（LFU、MRU、FIFO）和前沿策略（LHD、S3-FIFO、MGLRU），以及应用感知策略（GET-SCAN）和准入过滤器
- **用户空间库**：使开发者能轻松实验策略创新
- **详尽的评估**：跨越多种工作负载，证明自定义策略可实现最高 70% 的吞吐量提升和 58% 的 P99 延迟降低

## 主要研究方法

作者首先测量了将 page cache 事件通知用户空间的性能开销（Table 1），发现即使用户空间不做任何实际处理，仅通过 eBPF tracepoint + ring buffer 下发事件，YCSB 等工作负载就会出现 16-20% 的性能下降。这促使作者决定将策略逻辑实现在内核中，而非用户空间。

通过借鉴 sched_ext（Linux 的 eBPF 可扩展调度器框架）的设计思路，cache_ext 利用 struct_ops 和 kfuncs（kernel functions exposed to eBPF）将策略函数注入到 page cache 的关键代码路径中。

## 设计与实现

### 4.1 策略：内核还是用户空间？

通过 micro-benchmark 分析（Table 1），作者发现即使用户空间不做任何实际处理，eBPF tracepoint + ring buffer 的开销就高达 16-20%。因此 cache_ext 选择将策略逻辑实现在内核中作为 eBPF 函数，利用 eBPF 已被证明能在网络和存储等性能关键领域匹配内核性能的优势。

### 4.2 接口设计

**策略函数（Policy Functions）**：cache_ext 暴露了 5 个 hook 点——policy_init、evict_folios、folio_added、folio_accessed、folio_removed。这些 hook 通过 eBPF 的 struct_ops 机制注入内核，每次触发时调用对应的 eBPF 程序。

**驱逐列表 API（Eviction List API）**：核心接口是一组链表操作 kfuncs：
- `list_create()` / `list_add()` / `list_del()` / `list_move()`：管理可变长度的 folio 链表
- `list_iterate()`：遍历链表，支持"simple"和"batch scoring"两种模式

这些链表由内核管理，通过 per-policy hashtable（registry）建立 folio 指针到链表节点的映射。list_iterate() 支持在遍历过程中决定是否驱逐（simple 模式）或对 N 个 folio 打分后选择 C 个分数最低的（batch scoring 模式，用于 LFU 等策略）。

### 4.3 隔离（cgroup）

cache_ext 扩展了 eBPF struct_ops 以支持 per-cgroup 的 struct_ops，使得每个 cgroup 可以拥有独立的驱逐策略。这与容器化部署模式天然契合——每个容器运行在自己的 memory cgroup 中，可以定制自己的 page cache 策略。

进程间仍然可以访问彼此的 page cache 页并受益于共享内存，但驱逐决策是 per-cgroup 的。

### 4.4 安全性

**Valid Folios Registry**：内核维护一个哈希表，记录当前有效的 folio 指针。当策略提出驱逐候选 folio 时，内核通过 registry 验证每个候选的有效性，防止无效指针导致内核崩溃。

**驱逐降级（Eviction Fallback）**：如果策略提出的候选 folio 少于内核要求的数量，内核会回退到默认策略补充驱逐。

**kfunc 边界检查**：list kfuncs 对输入参数进行边界检查并强制循环终止条件。

### 4.5 策略实现

作者在 cache_ext 上实现了 8 种策略（按复杂度递增）：

| 策略 | eBPF LoC | 用户空间 LoC |
|------|---------|-------------|
| FIFO | 56 | 131 |
| MRU | 101 | 101 |
| LFU | 215 | 110 |
| S3-FIFO | 287 | 157 |
| GET-SCAN | 324 | 112 |
| LHD | 367 | 165 |
| MGLRU | 689 | 105 |

每种策略仅需数百行代码，远少于在内核中直接实现。

## 主要实验结果

### YCSB（LevelDB, 10GiB cgroup）

- **LFU 策略**表现最佳，相比默认 Linux 策略提升 **37% 吞吐量**，P99 延迟降低 **55%**
- LHD 和 S3-FIFO 也显著优于默认策略和 MGLRU
- 吞吐量与磁盘 I/O 呈反向关系——好的策略减少磁盘访问

### Twitter 缓存 traces

- **没有单一策略在所有集群上都最优**：LHD 在 cluster 34 领先默认 13%、领先 MGLRU 30%；LFU 在 cluster 52 领先默认 13%、领先 MGLRU 34%；但 MGLRU 在 cluster 17/18 上最优
- 证明了"一刀切"策略的局限性和定制化的必要性

### 文件搜索（ripgrep, 1GiB cgroup）

- MRU 策略比默认 LRU 和 MGLRU 快近 **2 倍**
- 因为文件搜索本质上是顺序扫描，MRU 策略恰好匹配

### 混合 GET/SCAN 工作负载

- GET-SCAN 策略实现 **70% 更高吞吐量** 和 **57% 更低 P99 延迟**
- `fadvise()` 系列接口几乎无效

### 隔离性验证

- 定制化配置（YCSB 用 LFU，文件搜索用 MRU）比全局策略（都用 LFU 或都用 MRU）分别提升 YCSB 49.8% 和文件搜索 79.4%

### 开销测量

- CPU 开销：no-op cache_ext 策略在 5-30GiB cgroup 下仅 **0.17%-1.66%**
- 内存开销：valid folios registry 占用 cgroup 内存的 **0.4%-1.2%**
- 端到端影响：cache_ext 实现的 MGLRU 与原生内核 MGLRU 相比平均仅慢 **1%**

## 潜在问题 / 局限性

1. **eBPF 验证器限制**：eBPF 不支持浮点运算，LHD 等依赖概率分布的策略需要用整数缩放近似，可能影响精度
2. **Reconfiguration 的用户空间路径**：LHD 的 reconfiguration（每 2^20 次操作触发一次）通过 ring buffer 通知用户空间，然后调用 BPF_PROG_TYPE_SYSCALL 程序执行。这引入了用户空间通信路径，虽然 reconfiguration 频率低，但仍可能影响精确度
3. **cgroup 粒度的隔离**：如果两个 cgroup 频繁访问相同的文件，一个 cgroup 的驱逐决策可能影响另一个 cgroup 的性能。作者承认这是"罕见情况"，但未量化风险
4. **实验规模**：所有实验在单台机器上进行，缺乏大规模分布式场景验证
5. **安全模型**：依赖 root 权限加载策略，与 sched_ext 一样需要 privileged policy loader
6. **MGLRU 性能问题**：论文显示 MGLRU 在某些工作负载下甚至不如默认 LRU，但未深入分析原因

## 个人评注

cache_ext 是一项扎实且工程化程度很高的工作。它成功地将 eBPF 的灵活性带入了 Linux page cache 这一核心子系统。核心设计思路——借鉴 sched_ext 的 struct_ops 模式，在内核中运行策略而非用户空间——是正确的选择，因为实验数据清楚地表明用户空间下发的开销是不可接受的。

论文最有价值的 insight 是"没有万能策略"（Takeaway 2）：即使在同一个应用的不同数据集上，最优策略也可能不同。这强调了可实验性和快速部署的重要性，cache_ext 通过降低策略开发门槛（几百行 eBPF 代码而非数千行内核代码）很好地解决了这一问题。

GET-SCAN 策略展示了应用感知策略的潜力——只需 324 行 eBPF 代码就能实现业务级别的优先级区分。这对于运行混合工作负载的服务器特别有价值。

不过，论文在对比维度上有所欠缺——它没有与 P2Cache（同期工作）进行详细对比，也没有在真实大规模部署中验证。此外，论文声称"挑战了 MGLRU 的必要性"，但 MGLRU 是为通用场景设计的，而 cache_ext 的价值恰恰在于让特定应用可以选择更适合自己的策略，而非完全替代 MGLRU。
