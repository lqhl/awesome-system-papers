# cache_ext: Customizing the Page Cache with eBPF

**作者**：Tal Zussman*, Ioannis Zarkadas* (Columbia University), Jeremy Carin (Columbia University), Andrew Cheng (Columbia University), Hubertus Franke (IBM Research), Jonas Pfefferle (IBM Research), Asaf Cidon (Columbia University)

**链接**：https://doi.org/10.1145/3731569.3764820
**源文件**：[[3731569.3764820.pdf]]

## 一、背景

OS page cache 是几乎所有存储密集型应用的性能关键组件，通过缓存磁盘数据减少 I/O 操作。Linux 内核默认使用 LRU 近似算法（双列表：active list + inactive list）作为 page cache 的驱逐策略。然而，自 1981 年 Stonebraker 就指出 buffer cache 的 one-size-fits-all 驱逐策略无法满足数据库等异构工作负载的需求。

近几十年来，caching 研究社区在非 OS 场景（如 key-value store、CDN）中提出了大量创新驱逐算法（LHD、S3-FIFO、ARC 等），但这些算法极难被集成到 Linux page cache 中，原因有二：(1) 修改 Linux page cache 需要深厚的内核知识，与 memory management、filesystem 等关键路径深度耦合；(2) upstream 到 Linux 主线极为困难——Google 的 MGLRU 策略花了数年才被合并，且至今未在所有发行版中默认启用。

与此同时，eBPF 技术在 Linux 中迅速发展，已被成功应用于网络（XDP）、调度（sched_ext）、存储（XRP）等领域的策略自定义，为 page cache 自定义提供了新的技术基础。

---

## 二、要解决的问题

1. **驱逐策略僵化**：Linux page cache 的 LRU 近似算法对 scan-heavy、skewed access 等常见工作负载表现不佳。现有的 `fadvise()`/`madvise()` hint 接口语义模糊、行为依赖内核版本、且仍受限于底层 LRU 结构，实测中往往无法产生预期效果。

2. **自定义代价过高**：在内核中实现新驱逐策略需要大量 kernel hacking，且 upstream 过程漫长（MGLRU 的例子）。应用自行实现 userspace cache（如 RocksDB block cache）虽可行，但需要预设缓存大小、难以共享内存、且通常仍依赖 page cache 作为二级缓存。

3. **多租户隔离**：page cache 是全局共享的，一个应用的策略不应干扰其他应用。

4. **安全性**：自定义策略返回的 folio 指针可能无效，若不加验证将导致内核崩溃或安全漏洞。

---

## 三、洞察与设计

**关键洞察**：大多数缓存驱逐算法（无论是经典的 LRU/MRU/LFU，还是前沿的 LHD/S3-FIFO/ARC/MGLRU）都可以用"一组可变大小的链表 + 作用于链表的策略函数"这一统一抽象来精确或近似实现。这意味着不需要为每种算法设计专门的内核接口，只需提供通用的链表操作 API 和事件回调，就能覆盖绝大多数驱逐策略。

基于这一洞察，cache_ext 的核心设计包括：

- **策略以 eBPF 程序运行在内核态**：避免 userspace dispatch 带来的高频事件同步开销（实测 userspace 方案导致 16-21% 性能下降）。利用 eBPF struct_ops 机制暴露 5 个 hook 点：`policy_init`、`evict_folios`、`folio_added`、`folio_accessed`、`folio_removed`。

- **Eviction List API**：提供 `list_create`、`list_add`、`list_move`、`list_del`、`list_iterate` 等 kfunc，支持策略创建任意数量的可变大小链表。链表节点存储 folio 指针，实际 folio 仍由内核 page cache 管理。支持"简单模式"（回调决定 skip/evict）和"批量评分模式"（回调返回分数，选最低 C 个驱逐）。

- **per-cgroup 隔离**：扩展 struct_ops 支持 cgroup 粒度的策略绑定，每个 cgroup 可运行独立驱逐策略，互不干扰，同时保留 page cache 的跨进程共享能力。

- **Valid Folios Registry**：内核维护一个 per-policy 哈希表，记录所有合法 folio 指针。驱逐候选返回时先查表验证，防止恶意/错误 eBPF 程序返回非法指针。内核还实现 fallback 机制：若策略未能提供足够候选，则回退到默认 LRU 策略。

## 四、实现细节

- **内核修改量**：约 2000 行代码。其中核心 page cache 修改仅 210 行（hook 点 + 批量驱逐），verifier 相关 80 行，cgroup 代码 80 行，per-cgroup struct_ops 支持 220 行（内核）+ 75 行（libbpf）。Eviction list kfuncs 750 行，registry 操作 580 行。

- **Eviction List 数据结构**：由于 eBPF 现有 map 类型不能同时满足有序存储和随机访问（如 `BPF_MAP_TYPE_QUEUE` 不支持中间删除，`BPF_MAP_TYPE_HASH` 不维护顺序），cache_ext 在内核侧实现了自定义链表结构，通过 kfunc 暴露给 eBPF。每个策略维护一个 folio→list node 的哈希表实现 O(1) 随机定位。

- **批量驱逐**：每次驱逐最多提案 32 个 folio（`candidates[32]`），减少 hook 调用频率。

- **浮点运算限制**：eBPF 不支持浮点操作，LHD 等需要浮点的策略通过大常数缩放整数运算近似。

- **LHD 重配置**：LHD 需要周期性更新统计分布，通过 ring buffer 通知 userspace 触发 `BPF_PROG_TYPE_SYSCALL` 程序在内核中执行重配置，避免 userspace 频繁 syscall。

- **已实现策略**（代码量见下表）：

| 策略 | eBPF LoC | Userspace LoC |
|------|----------|---------------|
| Admission filter | 35 | 262 |
| FIFO | 56 | 131 |
| MRU | 101 | 101 |
| LFU | 215 | 110 |
| S3-FIFO | 287 | 157 |
| GET-SCAN | 324 | 112 |
| LHD | 367 | 165 |
| MGLRU | 689 | 105 |

## 五、实验结果

**平台**：CloudLab c6525-25g，16-core AMD Rome CPU，128GB 内存，480GB SSD，Linux v6.6.8，Ubuntu 22.04。禁用 SMT、swap、ASLR，CPU pinning。

### YCSB (LevelDB, 100GiB DB, 10GiB cgroup)

| 工作负载 | 最佳 cache_ext 策略 | vs Default | vs MGLRU |
|----------|-------------------|------------|----------|
| YCSB A | LFU | +37% throughput | 更大优势 |
| YCSB B-F | LFU | 显著提升 | 显著提升 |
| Uniform | LFU | 显著提升 | 显著提升 |
| P99 latency | LFU | 降低最高 55% | — |

LHD 和 S3-FIFO 也优于 Linux 默认策略；MRU 在 YCSB 上表现最差（符合预期）。

### Twitter 生产 Traces

没有单一策略在所有 cluster 上最优：LHD 在 cluster 34 上 +13%/+30%（vs Default/MGLRU），LFU 在 cluster 52 上 +13%/+34%，但 MGLRU 在 cluster 17/18 上占优。MGLRU 在 cluster 24 频繁 OOM。

### File Search (ripgrep, 1GiB cgroup)

cache_ext MRU 策略比 Default 和 MGLRU 都快近 **2×**，因为 LRU 在 scan 场景下存在经典病态行为。

### GET-SCAN 混合负载 (LevelDB)

应用感知策略 vs Default：GET throughput **+70%**，P99 latency **-57%**。SCAN throughput 仅下降 18%。`fadvise()` 各选项几乎无效，MGLRU 甚至更差。

### Admission Filter (RocksDB, uniform R/W)

过滤 compaction 线程的 folio 进入 page cache：P99 latency 降低 **17%**（2.61ms → 2.16ms）。

### 框架开销

| 指标 | 数值 |
|------|------|
| CPU overhead (no-op policy, fio) | ≤ 1.7% |
| Memory overhead (registry) | 0.4% - 1.2% of cgroup memory |
| MGLRU cache_ext vs native | 平均 1% throughput 下降（harmonic mean 0.99） |

### 隔离实验

per-cgroup tailored 策略（YCSB 用 LFU + file search 用 MRU）vs baseline：YCSB +49.8%，file search +79.4%。全局单一策略会严重损害不匹配的工作负载。

## 六、批判性分析

1. **评估工作负载偏窄**：实验主要围绕 LevelDB/RocksDB + YCSB 和 file search，缺乏对数据库（PostgreSQL/MySQL）、ML 训练/推理、多媒体等实际生产场景的验证。论文声称 cache_ext 适用于广泛场景（包括 Android），但没有提供相应证据。

2. **"没有银弹"的论述与实验矛盾**：论文强调"no one-size-fits-all"，但 YCSB 实验中 LFU 几乎全面胜出，这是因为 Zipfian 分布天然利好频率策略。这个结果更多证明了"选对策略很重要"，而不是证明 cache_ext 的通用性。真正有说服力的是 Twitter traces 实验，但篇幅较少。

3. **策略选择问题被回避**：cache_ext 降低了策略实现门槛，但没有解决"用户如何知道该用哪个策略"这个核心问题。论文只说"可以实验"，但在生产环境中反复试错代价不低。

4. **安全模型的局限性**：加载 cache_ext 策略需要 root 权限，这在多租户云环境中是显著限制。论文提到可以像 sched_ext 一样用 privileged loader 缓解，但未实现。

5. **并发开销被低估**：eviction list 的锁粒度是 per-bucket，但在高 IOPS 场景下（论文自己强调的百万级 IOPS），folio 频繁插入/删除/移动可能导致锁竞争。论文只测了 no-op policy 的 CPU overhead，没有测试 LHD 等复杂策略在极端 IOPS 下的 overhead breakdown。

6. **与 P2Cache/PageFlex 的比较不够公平**：论文将 P2Cache 和 PageFlex 定位为功能受限的竞争者，但两者是"concurrently published work"，且论文没有在相同工作负载上进行直接性能对比。

7. **MGLRU 在 cache_ext 上的实现差异**：cache_ext 版 MGLRU 使用 ghost entries 做 refault detection（而非内核原生的 shadow entries），且 aging 操作用 eBPF spinlock 序列化，这些实现差异可能影响 1% overhead 数字的可信度。

## 七、AI Infra / MLSys 视角

1. **ML 训练/推理数据加载**：大规模训练的数据 pipeline（如 PyTorch DataLoader 读取大量训练样本）和推理系统的模型加载（论文引用了 `torch.load` 和 Milvus chunk cache）都重度依赖 page cache。cache_ext 的 application-informed policy 机制可以区分 prefetch 数据和热点数据，避免大批量数据加载时的 cache pollution。

2. **Checkpoint 和模型序列化**：ML 训练的 checkpoint 写入和恢复是典型的大文件顺序 I/O，容易冲掉 page cache 中的热数据。cache_ext 的 admission filter 模式可以直接过滤 checkpoint 线程的 page 进入 cache。

3. **混合推理工作负载**：类似 GET-SCAN 场景，推理系统中长 context prefill（scan-like）和短 request decode（point-like）可以用不同优先级的 page cache 策略，减少 KV cache 或模型权重被 prefill 流量驱逐。

4. **可跟进的方向**：
   - **ML-based page cache policy**：论文在结论中提到但未实现。用轻量级 ML 模型（如 learned index 风格）预测 page access pattern，通过 cache_ext 部署。
   - **GPU/NPU memory hierarchy integration**：当前 cache_ext 只管 CPU page cache，但 AI 系统中 GPU memory / host memory / SSD 的三级缓存调度问题类似，insight 可迁移。
   - **分布式训练的 IO 调度**：在多 worker 共享存储的场景下，per-cgroup 隔离可防止不同训练任务互相干扰 page cache。

---

## 八、总结

cache_ext 是一个基于 eBPF 的 Linux page cache 自定义框架，通过 struct_ops 回调 + eviction list kfunc API 的设计，允许应用以数百行 eBPF 代码实现自定义驱逐策略（LFU/LHD/S3-FIFO/MGLRU 等），无需修改内核。框架以 per-cgroup 粒度隔离策略，通过 valid folios registry 保障安全。实验显示自定义策略可带来最高 70% throughput 提升和 58% 尾延迟降低，框架自身开销低于 2%。主要局限在于策略选择缺乏自动化指导、评估工作负载覆盖有限、以及 root 权限要求限制了多租户部署。
