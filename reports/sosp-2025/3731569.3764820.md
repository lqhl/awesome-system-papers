# cache_ext: Customizing the Page Cache with eBPF

**作者**：Tal Zussman, Ioannis Zarkadas, Jeremy Carin, Andrew Cheng（Columbia University）；Hubertus Franke, Jonas Pfefferle（IBM Research）；Asaf Cidon（Columbia University）

**源文件**：[3731569.3764820.pdf](../../papers/sosp-2025/3731569.3764820.pdf)

## 一、背景

操作系统页缓存（page cache）是现代系统性能的核心组件，通过将热数据保留在内存中来减少磁盘访问。Linux 页缓存默认采用 LRU 近似算法（基于 active/inactive 双链表），这一设计在许多通用场景下工作良好。

然而，随着 NVMe SSD 的普及（支持数百万 IOPS、极低延迟），存储设备已不再是性能瓶颈，页缓存的命中率成为决定应用性能的关键因素。与此同时，现代数据中心的工作负载愈发多样化——从 key-value store（RocksDB、LevelDB）、数据库（PostgreSQL、MySQL）、分布式文件系统，到 ML 训练/推理系统，各类应用的访问模式差异极大，单一的 LRU 策略无法做到最优。

eBPF 作为 Linux 内核的可编程扩展机制，已在网络、调度（sched_ext）、安全等领域证明了其安全性与高性能，为页缓存定制化提供了新的技术路径。

---

## 二、要解决的问题

**核心痛点**：Linux 页缓存的 LRU 策略是"一刀切"的，无法适应多样化工作负载的需求，但修改内核页缓存极其困难。

具体问题：
1. **LRU 对特定工作负载天然不适合**：大范围扫描（scan-heavy workload）会污染缓存，导致热点数据被驱逐；MRU 策略在文件扫描场景更优；LFU 策略在 Zipfian 分布的 key-value 场景更优。
2. **现有内核接口不足**：`fadvise()`/`madvise()` 接口语义不透明、行为依赖内核版本、常常不符合预期，实验显示对大多数工作负载几乎没有实际帮助。
3. **修改内核代价极高**：即使是 Google 提出的 MGLRU 也花了数年才被合并进上游，且至今未在所有发行版默认启用；内核改动需要深厚的内核知识并影响所有应用。
4. **用户空间缓存的局限性**：需要预先配置大小、难以跨进程共享内存、实现复杂。
5. **现有 eBPF 方案局限**：P2Cache 只支持单队列 LRU/MRU；PageFlex 主要关注 mmap 访问和 swap/prefetch，不处理 file-based eviction；FetchBPF 只定制预取策略，不涉及驱逐。

---

## 三、核心设计

**cache_ext** 是一个基于 eBPF 的 Linux 页缓存定制框架，允许开发者在不修改内核的前提下，为特定 cgroup 实现自定义的页缓存驱逐策略。

**四项关键设计 insight**：

1. **策略在内核中运行（非用户空间）**：现代 SSD 每秒产生数百万个页缓存事件，用户空间 dispatch 架构（通过 ringbuffer 通知用户空间）引入高达 20.6% 的性能开销，代价不可接受。cache_ext 将策略作为 eBPF 函数运行于内核中，避免频繁的内核/用户空间同步。

2. **灵活的驱逐列表抽象（eviction list API）**：研究发现几乎所有缓存算法（LRU、LFU、ARC、S3-FIFO、MGLRU 等）都可以用一个或多个有序链表来表达。cache_ext 提供 variable-sized eviction lists 的 kfunc API（`list_create`、`list_add`、`list_move`、`list_del`、`list_iterate`），支持两种迭代模式：简单模式（逐个判断保留/驱逐）和批量评分模式（选择得分最低的 C 个候选）。

3. **cgroup 粒度的隔离**：利用 Linux 现有的 per-cgroup 页缓存列表机制作为隔离边界，每个 cgroup 可独立部署自己的驱逐策略而不相互干扰，同时仍能共享跨进程的内存页（shared memory）。为此扩展了 eBPF struct_ops 以支持 per-cgroup 策略加载。

4. **有效 folio 注册表（valid folios registry）**：eBPF 策略通过返回 folio 指针来提议驱逐候选，若指针无效则可能导致内核崩溃。cache_ext 维护一个 per-policy 的哈希表注册表，在驱逐候选被接受前验证 folio 指针的合法性。

**整体架构**：用户程序通过 eBPF struct_ops 注册策略函数，由内核在五类事件（policy_init、evict_folios、folio_added、folio_accessed、folio_removed）发生时回调。策略维护自己的驱逐列表并通过 eviction_ctx 批量提议候选，内核验证后执行实际驱逐；不足的候选由默认策略兜底。

## 四、实现细节

**eBPF 技术选型**：
- 使用 `struct_ops` 暴露策略函数接口（类似 sched_ext），最小化 verifier 修改量；新增 admission filter 等扩展只需 15 行 verifier 相关代码
- 关键操作通过 kfuncs 暴露给 eBPF，绕过 eBPF maps 的局限性（map 无法同时支持有序遍历和随机访问）
- 迭代接口 `list_iterate()` 接受回调函数，由 cache_ext 在内核中管理锁和并发安全

**eBPF 限制的工程处理**：
- eBPF 不支持浮点运算：LHD 中将浮点值乘以大常数近似计算
- eBPF 暂无可同时支持有序性和随机访问的内置 map：list API 由内核管理，通过 kfuncs 暴露
- LHD 的周期性重配置（reconfiguration）通过 ringbuffer 通知用户空间，由用户空间调用 `BPF_PROG_TYPE_SYSCALL` 程序在内核中执行 EWMA 更新

**代码规模**：
- 内核改动约 2000 行：210 行页缓存核心（eBPF hooks + eviction candidate batching）、80 行 verifier、220 行 cgroup 支持、750 行 eviction list kfuncs、580 行注册表
- 各策略 eBPF 代码量：admission filter 35 行，FIFO 56 行，MRU 101 行，LFU 215 行，S3-FIFO 287 行，GET-SCAN 324 行，LHD 367 行，MGLRU 689 行

**实验平台**：CloudLab c6525-25g，16 核 AMD Rome CPU，128 GB 内存，480 GB SSD，Ubuntu 22.04，Linux v6.6.8

## 五、实验结果

### YCSB（LevelDB，10 GiB cgroup，100 GiB 数据库）

| 策略 | vs. Linux 默认 | vs. MGLRU |
|------|---------------|-----------|
| LFU（cache_ext） | 最高 +37% 吞吐、-55% P99 延迟 | 更大幅度提升 |
| LHD（cache_ext） | 接近 LFU | 正向提升 |
| S3-FIFO（cache_ext） | 正向提升 | 正向提升 |
| FIFO（cache_ext） | 略低于默认 | 略超 MGLRU |
| MRU（cache_ext） | 低于默认（符合预期）| - |

### Twitter 生产 traces（5 个集群，LevelDB）

- 不存在对所有工作负载都最优的单一策略
- LHD 在 cluster 34 超过默认策略 13%、超过 MGLRU 30%
- LFU 在 cluster 52 超过默认策略 13%、超过 MGLRU 34%
- MGLRU 在某个集群导致 OOM 错误（吞吐为零）

### 文件搜索（ripgrep，1 GiB cgroup，约 70% 覆盖内核源码）

- cache_ext MRU 策略：**接近 2× 快于 Linux 默认和 MGLRU**（两者都受 LRU scan 病理影响）

### 应用感知策略（GET-SCAN，LevelDB，99.95% GET + 0.05% SCAN）

| 指标 | cache_ext vs. 默认 |
|------|-------------------|
| GET 吞吐 | **+70%** |
| GET P99 延迟 | **-57%** |
| SCAN 吞吐 | -18%（可接受的代价） |
| fadvise() 选项 | 几乎无帮助 |

### Admission Filter（RocksDB，过滤 compaction 线程页面）

- P99 延迟降低 17%（2.61ms → 2.16ms），吞吐无明显变化

### 隔离实验（双 cgroup：YCSB-C + 文件搜索）

- 定制策略（YCSB 用 LFU + 文件搜索用 MRU）vs. 默认全局策略：**YCSB +49.8%，文件搜索 +79.4%**

### 开销

| 项目 | 数值 |
|------|------|
| CPU 开销（no-op 策略，fio randread） | **最高 1.7%** |
| 内存开销（注册表哈希表） | 0.4%（空）~ 1.2%（满） |
| cache_ext MGLRU vs. 原生内核 MGLRU | 平均 -1% 吞吐 |

## 六、批判性分析

**1. 工作负载代表性存疑**

YCSB 实验使用固定 Zipfian 分布——LFU 在此场景几乎是"作弊"（分布固定，频率信息天然可用）。论文自己也承认这一点，但 Twitter traces 结果表明真实场景中没有一种策略能普遍最优，这与 LFU 在 YCSB 上的亮眼表现形成反差，削弱了"cache_ext 能显著提升性能"的一般性结论。

**2. 性能提升来源混淆**

论文将 LFU 策略的性能提升与 fadvise() 的无效性并列，但两者的差异很大程度上来自"知道访问频率"这一信息优势，而不仅仅是"更灵活的框架"。实验并未控制信息优势，使得"框架灵活性"的价值被高估。

**3. 应用感知策略的假设条件苛刻**

GET-SCAN 策略要求应用将 SCAN 线程 PID 显式注册到 eBPF map 中，需要修改应用代码。在实际部署中，这要求应用开发者深度参与缓存策略的实现，与"无需修改内核"的核心卖点存在张力——只是把改动从内核移到了应用层。

**4. 隔离的本质局限被轻描淡写**

论文承认 cgroup A 的关键页面可能被 cgroup B 驱逐，并以"这种情况在实践中很少发生"轻描淡写。然而在多租户数据中心环境下，不同应用共享热点文件（如 shared libraries、shared config files）的场景相当常见，此时 per-cgroup 隔离失效，跨 cgroup 的缓存污染问题未被充分讨论。

**5. 安全模型的残留风险**

需要 root 权限才能加载策略，论文建议通过 systemd 的 privileged policy loader 缓解，但这只是一种工程上的绕道，eBPF 程序的安全边界依然值得持续关注（verifier bypass 漏洞在历史上有先例）。

**6. 与 P2Cache 的横向对比不完整**

论文将 P2Cache 列为并发工作，指出其仅支持单队列 LRU/MRU，但没有在相同实验设置下进行直接性能对比。这使得"cache_ext 优于 P2Cache"的隐含结论缺乏实证支持。

## 七、AI Infra / MLSys 视角

**1. ML 训练/推理系统的直接相关性**

ML 推理（如 vLLM 的 KV cache 管理）和训练（模型权重的 checkpoint 加载、数据预处理 pipeline）都面临与数据库类似的缓存污染问题。例如，PyTorch `torch.load` 和 Milvus chunk cache（论文中已引用）都依赖页缓存，而大批次的 prefetch 扫描容易驱逐关键权重页面。cache_ext 的 admission filter 机制直接可以用于隔离 ML 数据加载的 background IO。

**2. 可借鉴的 eBPF 扩展机制**

sched_ext 已被 MLSys 社区用于自定义 GPU kernel 的调度策略。cache_ext 提供了类似的范式：**通过 eBPF struct_ops 将系统策略的"热路径"与"决策逻辑"解耦**。这一模式可以推广到 ML 系统的其他可定制点，如 NUMA-aware 内存分配、GPU 显存驱逐策略（CUDA UVM）等。

**3. 多租户 AI 集群的隔离需求**

在 AI 超算集群中，不同 job 共享节点的 CPU 内存（用于 pin memory、host-side cache 等），per-job 的页缓存策略隔离是一个真实需求。cache_ext 的 cgroup-based 隔离天然对应容器化的 AI 训练 job，值得实际部署验证。

**4. Future Work 方向**

- **ML-based 动态策略**：论文结论提到 ML-based 缓存策略（如 Baleen、LRB），cache_ext 为在内核中运行轻量级 ML 推断（如简单的线性模型或决策树）提供了基础设施，值得探索。
- **与 GPU/NVLink 内存层级的协同**：随着 CXL 内存的普及，OS 页缓存将管理更异构的内存层级，cache_ext 的框架可以扩展到 CXL 设备的缓存放置策略。
- **KV cache 感知的驱逐策略**：将 LLM 推理的 KV cache 访问模式（token-level locality）注入页缓存驱逐决策，是一个可操作的研究问题。

---

## 八、总结

cache_ext 提出了一个基于 eBPF 的 Linux 页缓存定制框架，通过 struct_ops 钩子和 eviction list kfunc API，允许开发者以数百行 eBPF 代码实现任意自定义驱逐策略，并以 cgroup 为粒度实现多租户隔离。在 key-value store、数据库、文件搜索等场景下，定制策略可带来 38%~70% 的吞吐提升和高达 58% 的尾延迟降低，而框架本身开销不超过 2%。主要局限在于：需要 root 权限、应用感知策略需要修改应用代码、跨 cgroup 的缓存共享场景下隔离保证较弱。该框架对 AI Infra 系统具有直接借鉴价值，尤其在多租户 AI 集群的缓存隔离和 ML 数据加载优化方面。
