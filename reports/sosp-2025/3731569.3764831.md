# Running Consistent Applications Closer to Users with Radical for Lower Latency

**作者**：Nicolaas Kaashoek（Princeton University）、Oleg A. Golev（Sentient Foundation）、Austin T. Li（Cornell University）、Amit Levy（Princeton University）、Wyatt Lloyd（Princeton University）

**源文件**：[3731569.3764831.pdf](../../papers/sosp-2025/3731569.3764831.pdf)

---

## 一、背景

云基础设施正在发生根本性变化：Amazon、Microsoft 等超大规模云厂商在全球各地新建数据中心，Akamai、Cloudflare 等 CDN 提供商向用户提供边缘部署选项，众多企业也出于隐私和成本考虑转向本地集群。这些新执行位置（near-user locations）理论上能让应用部署得离用户更近，从而大幅降低端到端延迟。

然而，具有强一致性需求的应用——社交媒体（需要有序的帖子和消息）、订票服务（需要防止双重预订）、在线论坛等——无法直接利用这些新位置。强一致性应用通常将数据存储在单个主数据中心，将应用移至近用户节点会导致每次存储操作都需要跨越大量网络延迟；而若在多地部署强一致存储副本，则受 PRAM 不可能定理约束，读写延迟之和必须大于副本间最大距离，地理复制带来的协调开销反而可能比集中部署更差。

---

## 二、要解决的问题

1. **移动应用而不移动数据**：将应用部署到近用户位置，但存储仍在主数据中心，每次存储访问都需要一次完整的跨地区网络往返，性能往往比完全集中部署更差。

2. **地理复制存储**：使用 Amazon DynamoDB Global Tables 或 Google Spanner 等强一致的地理复制存储，受 PRAM 不可能定理约束，协调开销大，实验显示多数情况下延迟比集中部署更高。

3. **核心矛盾**：现有方案要么牺牲强一致性以换取低延迟，要么维持强一致性但放弃了近用户部署带来的延迟收益。如何同时提供强一致性和近用户低延迟，是本文的核心问题。

---

## 三、核心设计

Radical 是一个支持强一致性应用在近用户位置运行的框架，其核心思路是：**将强一致性协调的延迟与应用的投机执行并行重叠**，从而掩盖跨地区网络往返的开销。

**架构**：

- **Near-user location**：运行应用的边缘位置，包含 Runtime（执行 serverless functions）和 Storage Library（访问本地 eventually consistent 缓存）。
- **Near-storage location**：主数据中心，运行 LVI Server，负责处理来自 near-user locations 的 LVI 请求；同时托管主存储系统（DynamoDB/BigTable/CosmosDB）和备份函数。

**三大核心机制**：

1. **静态分析（Static Analysis）**：在函数注册时，分析器对函数 `f` 进行符号执行与依赖分析，自动提取出 `f_rw`——一个接受相同输入、返回该函数将访问的读/写集合的辅助函数。Serverless functions 的无状态性质使所有存储访问都是显式的，大大简化了分析。

2. **LVI 协议（Lock-Validate-WriteIntent）**：每次函数调用时，Runtime 先运行 `f_rw` 获取读/写集，同时向 near-storage 发送单一 LVI 请求，并在本地对缓存数据**投机执行** `f`。LVI 请求在 near-storage 端完成以下操作：
   - 按读/写集获取读写锁（避免死锁，按字典序获取）
   - **Validate**：比较 near-user 缓存中各 key 的版本号与主存储中的版本号；若一致，则投机执行有效
   - **WriteIntent**：若写集非空，提前在主存储创建 WriteIntent 记录，设置计时器；写操作随后通过 followup 异步发回，由 near-storage 应用

3. **确定性重执行（Deterministic Re-execution）**：若 followup 未到达（near-user 故障或网络丢失），near-storage 定时器触发，在主数据中心重新执行该函数。函数必须编译为 WebAssembly 子集，不允许使用定时器或随机数等非确定性来源，以确保重执行结果与原始执行完全一致。

**延迟优化**：LVI 请求的延迟与投机执行并行，当函数执行时间 ≥ `lat_nu↔ns`（near-user 到 near-storage 的往返延迟）时，LVI 请求不在关键路径上，延迟收益最大化。

## 四、实现细节

- **Near-user Runtime**：约 1000 行 Rust，基于 AWS Lambda Rust runtime，管理缓存、执行 `f_rw` 和 WebAssembly 函数、通过 Lambda Extension 发送 followup。
- **LVI Server**：约 2000 行 Go，运行于 EC2 t3.2xlarge（8 vCPU，32 GiB 内存）；锁存储于内存表并持久化到磁盘；写 intent 存于 DynamoDB；Replicated 版本使用 3 节点 etcd 集群跨可用区存锁。
- **静态分析器**：基于 Eunomia（~8000 行 Python），修改/新增约 2000 行，增加了识别存储调用、返回符号变量状态和依赖关系的能力；使用 WasmTime 作为 WebAssembly 运行时。
- **应用函数**：用 Rust 编写并编译到 `wasm32-unknown-unknown`，任何可编译至 WebAssembly 的语言均可。
- **每个 Lambda 函数分配 2 GB 内存**，以确保投机执行与 LVI 请求能并行运行（获得 2 个 vCPU）。

**依赖访问（Dependent Accesses）处理**：若某读取的 key 依赖于另一读取的结果，`f_rw` 运行时会对本地缓存执行这些前置读取以确定后续 key，验证步骤负责捕获缓存过期导致的错误。

**外部服务**：若函数需调用外部服务（如支付 API），该服务必须支持幂等性机制（如 Stripe 的 IdempotencyKey），以应对函数可能被执行两次的情况。

## 五、实验结果

**实验平台**：5 个 AWS 数据中心（VA/CA/IE/DE/JP），主存储和 LVI Server 在 Virginia。

**基准应用**（5 个，共 27 个 serverless functions，本文重点分析 3 个）：

| 应用 | 函数数量 | 代表函数执行时间 |
|------|---------|----------------|
| Social Media（Diaspora 风格） | 5 | 16ms – 213ms |
| Hotel Reservation（DeathStarBench） | 6 | 13ms – 272ms |
| Forum（Lobsters 风格） | 5 | 16ms – 212ms |

**Near-user 到 near-storage 往返延迟**：

| 位置 | VA | CA | IE | DE | JP |
|------|-----|-----|-----|-----|-----|
| lat_nu↔ns (ms) | 7 | 74 | 70 | 93 | 146 |

**主要结果**：

| 指标 | 结果 |
|------|------|
| 端到端延迟改善（vs 集中部署基线） | 28–35% |
| 达到最优下界的比例 | 84%（Forum）/ 88%（Social Media）/ 89%（Hotel）|
| LVI 验证成功率 | ~95% |
| 基础设施成本增加 | 约 31%（添加 LVI Server + ScyllaDB 后）|

- Virginia 本地（lat_nu↔ns = 7ms）略慢于基线，因为引入了 `f_rw` 执行和 LVI 协议开销。
- 执行时间 < lat_nu↔ns 的函数（如 forum-interact 16ms < 70ms）基本无收益，但最多与直接访问 near-storage 持平，不会比基线更差。
- 带复制 LVI Server（etcd）时，每个 lock 增加约 2.3ms，最低受益执行时间从 20ms 提升至约 16+2.3*L ms。

## 六、批判性分析

**1. 实验基线选择存在明显偏差。**
论文刻意不与 DynamoDB Global Tables 做比较，理由是"该功能不在所有 region 可用"，并援引自己的实验数据说明 geo-replication 比集中部署更差。但这个结论依赖于他们自己设计的测试应用（100ms 计算 + 单次存储访问），而不同应用的存储访问模式差异很大。回避与 Spanner 等生产级别强一致 geo-replicated 系统的正面对比，使论文宣称的优势缺乏充分支撑。

**2. Singleton LVI Server 是一个严重的工程隐患。**
本文评估全程使用单点 LVI Server，第 5.6 节才讨论复制版本，结果显示引入 etcd 后每个 lock 增加 2.3ms，且现实中锁顺序获取（串行）使延迟进一步放大。论文声称"batching 可优化"，但并未实现和测量，这是一个不诚实的留白。

**3. 延迟收益的来源被混淆。**
论文将 28–35% 的延迟改善呈现为 Radical 的优势，但实验的一个重要变量是：baseline 请求从 near-user 发到 Virginia Lambda 再访问 DynamoDB，而 Radical 在 near-user 本地执行函数并访问缓存（即使验证失败也在 Virginia 本地重执行）。部分延迟改善可能仅仅来自 near-user Lambda 比跨区调用 Virginia Lambda 更快，而非 LVI 协议本身的贡献。

**4. 应用限制被轻描淡写。**
Radical 要求应用：① 分解为 serverless functions；② 编译为确定性 WebAssembly；③ 外部服务调用支持幂等性；④ 执行时间 ≥ ~20ms。这几个限制组合起来会排除相当多真实应用。论文仅用自己实现的 27 个函数验证，选择的都是 Radical 效果最好的场景（hotel reservation 最大收益），而未对分析失败的 case 进行统计分析。

**5. 缓存冷启动问题被一笔带过。**
论文承认缓存失效时 LVI 请求必然失败，靠版本号逐渐填充缓存，但对冷启动期间的延迟惩罚和实际可用窗口没有量化。在边缘节点频繁调度、函数实例生命周期短的 Lambda 环境下，这可能是常态而非异常。

**6. 仅报 median，p99 数据暴露了更多问题。**
图 4 中 p99 bar 显示 Radical 的尾延迟（whisker）比基线更宽，如 Hotel Booking：Radical 270ms vs 基线 229ms（median），但 p99 差距更明显。锁竞争和验证失败（5%）在高 skew 工作负载下可能带来比 median 数据更差的 p99 表现，这对延迟敏感应用至关重要。

## 七、AI Infra / MLSys 视角

Radical 的问题域（强一致性 + 近用户低延迟）与 AI Infra 中的若干新兴场景存在关联：

**潜在迁移价值**：

- **有状态 Agent 服务**：LLM Agent 需要访问一致的状态存储（工具调用历史、记忆数据库、会话状态）。若 Agent 推理服务部署在全球边缘节点，Radical 的 LVI 思路——本地投机执行 + 单次跨地区一致性检查——可为 Agent memory backend 提供参考。
- **RAG 系统中的索引一致性**：检索增强生成（RAG）系统的向量数据库通常集中部署，近用户推理节点需要频繁访问。LVI 风格的"预取 + 投机检索 + 版本验证"有潜力降低检索延迟同时保证索引一致性。
- **静态分析提取读写集**：论文中对 serverless function 的符号执行思路——自动提取 `f_rw` 函数——对 LLM 推理的 KV cache 访问预测有一定借鉴意义（预测 attention pattern 以提前 prefetch）。

**局限性**：AI 推理请求通常不满足"确定性"要求（temperature sampling 本质上非确定），也不易编译为 WebAssembly，因此 Radical 的整体框架不能直接套用于 LLM serving。但其**协调延迟与计算并行重叠**的核心思想，以及**写意图（write intent）+ 确定性重执行**的容错机制，值得在 AI serving 基础设施设计中参考。

---

## 八、总结

Radical 提出了一个让强一致性应用能够在近用户位置运行的框架，其核心创新是 LVI 协议——通过静态分析预提取读/写集，将单次协调请求与应用的投机执行并行执行，从而在不牺牲 Linearizability 的情况下隐藏跨地区网络延迟。在真实 AWS 多区域部署中，Radical 实现了 84–89% 的最优延迟改善，端到端延迟降低 28–35%，成本增加约 31%。主要局限在于：应用必须是确定性 WebAssembly serverless 函数、LVI Server 仍是潜在单点瓶颈、对执行时间较短（<20ms）的函数收益有限，以及实验未与同类强一致 geo-replicated 系统做充分的横向比较。
