# Radical: Running Consistent Applications Closer to Users with Lower Latency

## 1. 论文基本信息

- **标题**: Running Consistent Applications Closer to Users with Radical for Lower Latency
- **作者**: Nicolaas Kaashoek, Oleg A. Golev, Austin T. Li, Amit Levy, Wyatt Lloyd (Princeton University, Cornell University, Sentient Foundation)
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764831
- **代码**: 未提及开源

## 2. 研究背景

**新型边缘基础设施的涌现**：超大规模云提供商（Amazon、Microsoft）和 CDN 提供商（Akamai、Cloudflare）正在全球范围内开设新数据中心、边缘 Point of Presence (PoP) 和本地集群。这些基础设施使得将应用部署到更靠近用户的位置成为可能——理论上应该能降低端到端延迟。

**强一致性应用的困境**：然而，社交媒体、预订网站、论坛等依赖强一致性（如 Linearizability）的应用，无法轻易利用这些新的部署位置：
1. **远程数据访问**：如果新位置没有数据副本，每次存储访问都需要跨地域往返，导致更高延迟
2. **全局复制协调**：如果有数据副本，PRAM 不可能性结果告诉我们——为保证强一致性，读和写延迟之和必须大于副本间的最大距离

**当前方案的局限性**：
- **集中式部署**：应用和数据都在单一数据中心，用户远端延迟高（东京到弗吉尼亚单程约 180 ms）
- **地理复制部署**：每个位置都有数据副本，但由于 PRAM 约束，所有访问都必须协调，延迟反而更高

这导致了一个性能鸿沟：即使有了新的边缘基础设施，强一致性应用仍然无法获得延迟收益。

## 3. 要解决的问题

**核心问题**：如何在保证 Linearizability 的前提下，让强一致性应用也能利用新的部署位置（边缘数据中心、PoP）来降低用户感知延迟？

具体挑战：
- **PRAM 不可能性**：无法同时获得"每个副本本地读取"和"全局写顺序一致"——必须做出权衡
- **单次请求协调**：LVI 协议必须以单次请求完成所有必要的协调
- **Late Reads**：读取在 speculation 执行中期发生，需要在 LVI 请求中验证缓存版本
- **Speculative Writes**：Speculation 成功后需要写入，但失败时不能真的写入存储

## 4. 核心贡献

1. **Radical 框架**：首个允许强一致性应用在靠近用户的位置运行的框架，通过 speculation 和新型 LVI 协议提供 Linearizability。
2. **LVI（Lock-Validate-WriteIntent）协议**：单次请求中完成锁获取、版本验证和写意图设置，协调执行位置、缓存和主存储。
3. **Static Analysis**：通过符号执行静态分析函数，提前确定 read/write set。
4. **可达最优延迟改善的 84-89%**：评估显示 Radical 在三个真实 microservices（社交媒体、酒店预订、在线论坛，分解为 15 个 serverless 函数）中达到理论最大延迟改善的 84-88%。
5. **仅需 1.3 倍基线成本**：增加缓存的开销仅为基础设施成本的 1.3 倍。

## 5. 主要研究方法

### 5.1 PRAM 不可能性分析
从理论上分析了地理复制系统中的延迟下界：任何强一致性（Linearizability）系统在地理分布设置下，读和写延迟之和必须大于副本之间的最大物理距离。这意味着不可能同时获得"每个副本本地读取"和"全局一致的写顺序"。

### 5.2 Static Analysis 提取 read/write set
关键洞察：Serverless 函数天然无状态，每次对存储的访问都是显式的——这使得静态分析成为可能。

符号执行流程：
1. 当 client 注册函数 f 时，Radical 运行静态分析器提取 f_rw
2. f_rw 接收与 f 相同的输入，返回该次执行的 read/write set
3. 分析器通过符号执行，跟踪函数执行路径中的所有存储访问调用
4. 对每个访问，推导在输入上需要满足的约束和依赖关系

### 5.3 Deterministic Replay
为了支持 write intent 的确定性重放，Radical 要求函数必须是确定性的。实现方式：通过编译限制为 WebAssembly 的子集。

### 5.4 Write Intent 与 Timer
Write intent 是在 near-storage 位置设置的追踪对象，记录哪个执行可能需要写入。如果 followup 未到达，定时器触发确定性重放。

## 6. 设计与实现

### 6.1 系统架构
- **Near-User Location**：包含 Radical Runtime（speculative 执行）和存储库（最终一致缓存）。可以是附近数据中心、边缘 PoP 或本地集群
- **Near-Storage Location**：包含 LVI Server（处理 LVI 请求和 followup）、Primary Storage（提供 Linearizability 和持久性）、Backup Functions（验证失败时执行）

### 6.2 LVI 协议流程
```
1. Client 请求到达 near-user 位置
2. Radical 调用 f_rw(input) 获取 read/write set
3. 同时从缓存获取本地版本号
4. (a) Speculative 执行 f(input) 访问缓存
   (b) 发送 LVI 请求到 near-storage 位置
5. LVI Server 获取锁 + 验证版本
6. (a) 验证成功：设置 write intent，启动 timer
       (b) 验证失败：执行 backup 函数
7. Near-user 位置收到响应，更新缓存
8. Near-user 执行返回后发送 followup（包含 speculative writes）
9. Near-storage 应用 writes，释放锁
```

### 6.3 版本管理和缓存一致性
- 每个数据项存储 (value, version)
- LVI 请求携带 near-user 缓存中的版本号
- 版本不匹配时验证失败，触发 near-storage 执行
- 缓存不要求持久性——不匹配的版本号通过 LVI 请求逐渐恢复

### 6.4 Read-Only 事务优化
对于只读操作，LVI 协议简化为验证步骤：如果所有读取的版本都是最新的，near-user 执行直接返回结果，无需写入协调。

### 6.5 Static Analysis 实现
- 基于符号执行的函数分析
- 跟踪输入到存储访问的约束传播
- 为每个输入参数生成具体的 read/write set

## 7. 主要实验结果

### 7.1 延迟改善
在 5 个地理位置（VA、CA、IE、DE、JP）测试三个应用：
- **Radical 实现最优可能延迟改善的 84-88%**
- 绝对延迟改善：28-35%（不同应用和位置）
- 基线（集中式部署 vs 地理复制）：延迟改善有限甚至为负（地理复制更慢）

### 7.2 适用场景阈值
- 仅当 handler 执行时间 >= **20 ms** 时，Radical 才有收益
- 对于极短 handler（< 1 ms），协议开销可能超过收益

### 7.3 成本开销
- 添加缓存的开销：约 **1.3 倍**基线基础设施成本
- 缓存不需要高可用——丢失后通过 LVI 请求逐渐恢复

### 7.4 真实应用验证
三个应用分解为 15 个 serverless 函数：
- **Social Media**：post handler、follow handler、timeline read handler 等
- **Hotel Reservation**：search、booking、cancel 等
- **Online Forum**：post read/write、thread 等

静态分析成功提取了所有 handler 的 read/write set。

## 8. 潜在问题/局限性

1. **Determinism 的强要求**：Radical 要求函数必须是确定性的，这在实践中是一个严格的限制。实现确定性需要开发者遵循特定规范或使用受限的编程模型（WebAssembly 子集）。非确定性操作（如使用 wall-clock time、random number）如何处理未充分讨论。
2. **Static Analysis 的完整性**：符号执行的 termination 和覆盖率问题可能导致某些 code path 未被分析到。如果 f_rw 失败，handler 必须在 near-storage 位置执行，失去延迟优势。
3. **Write Intent 的持久性问题**：如果 near-storage 位置发生灾难性故障（如所有副本同时丢失），write intent 可能丢失，导致数据不一致。虽然论文提到主流存储系统通常能承受大多数非灾难性故障，但这个"灾难"的定义和风险管理未深入讨论。
4. **Cache Invalidation 的效率**：在高写入负载下，near-user 缓存会频繁失效，每次 miss 都需要 LVI 验证。在写入密集型工作负载中，Radical 可能无法提供显著延迟收益。
5. **Cold Cache Bootstrap**：初始缓存为空时，所有请求都会触发 LVI 验证并失败。论文提到 persistent 缓存可以缓解，但如何平衡缓存大小和覆盖范围未讨论。
6. **与现有分布式事务协议的比较未进行**：Radical 与 2PC、Saga 等分布式事务协议的关系和 trade-off 未讨论。
7. **Multi-tenant 安全性**：多个租户共享 near-user 缓存时的隔离问题未讨论。
8. **20 ms 阈值的主观性**：这个阈值是基于实验测量的，但没有给出如何为特定应用确定此阈值的系统化方法。

## 9. 未来工作

1. **支持非确定性函数**：探索如何在保持正确性的前提下支持包含非确定性操作的函数。
2. **动态阈值调整**：根据运行时性能自动调整 20 ms 阈值。
3. **Multi-region 存储支持**：支持 DynamoDB Global Tables、Google Spanner 等多区域强一致性存储作为 Primary Storage。
4. **Write-behind 和 write-through 策略**：根据工作负载特征自适应选择缓存更新策略。
5. **容灾增强**：处理更极端的故障场景。

## 10. 个人评注

**Radical 是一篇理论深度和系统实现良好结合的论文**，它从 PRAM 不可能性结果出发，通过精心设计的 LVI 协议和 static analysis，绕过（或巧妙处理）了这个理论限制。这是一个教科书式的"理论与系统协同设计"的案例。

论文最有意思的洞察是**PRAM 不可能性不是障碍而是信息来源**：论文巧妙地认识到 PRAM 约束要求读和写延迟之和必须大于物理距离，于是采取的策略不是试图违反这个约束，而是通过"重叠"来隐藏开销——将 LVI 请求与 speculative 执行并行，利用执行时间覆盖协调延迟。

**批评性思考**：
- **"84-88% 的最优可能延迟改善"数字需要深入理解**：这是相对于"如果存储和执行都在 near-user 位置"的理论最优而言的。但这个"理论最优"本身假设了 PRAM 不可能性不存在（即存储是本地的且强一致的）——这是一个实际上无法达到的上界。因此，84-88% 的数字虽然听起来不错，但其基准线的选择有些模糊。
- **Static Analysis 的局限性可能被低估**：符号执行在实践中可能遇到路径爆炸、非终止等问题。对于复杂的 handler（如包含网络调用、文件系统操作、外部 API 交互），静态分析的有效性可能低于论文暗示的水平。
- **"仅需 1.3 倍成本"的成本模型过于简化**：这个数字只考虑了缓存的存储成本，但没有考虑缓存一致性管理、LVI Server 的计算开销、备份函数的管理成本等。
- **Determinism 要求的重要性可能被低估**：在现实中，许多应用有意或无意地依赖非确定性（时间戳、随机数、硬件计数器）。强制确定性可能会显著限制 Radical 的适用范围。
- **与"读写分离"优化方向的对比缺失**：现代分布式系统（如 RITAM、RAMP-Fiction）采用"读写分离"策略来减少强一致复制的开销。Radical 与这些方案的关系和 trade-off 未讨论。

总体而言，这是一篇高水平的分布式系统论文，适合分布式系统研究者和云基础设施架构师阅读。它的理论框架（LVI 协议）和系统实现都有深度，但读者应该关注其假设条件（确定性、handler 执行时间 > 20ms）的实际限制。
