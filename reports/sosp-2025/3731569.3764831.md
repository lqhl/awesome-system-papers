# Running Consistent Applications Closer to Users with Radical for Lower Latency

**作者**：Nicolaas Kaashoek (Princeton University), Oleg A. Golev (Sentient Foundation, 研究完成于 Princeton), Austin T. Li (Cornell University, 研究完成于 Princeton), Amit Levy (Princeton University), Wyatt Lloyd (Princeton University)

## 一、背景

云基础设施正在全球范围内扩展——超大规模云厂商（AWS、Azure）不断开设新的数据中心，Cloudflare、Akamai 等提供边缘部署点（edge PoP），同时越来越多的企业出于隐私和成本考虑转向本地集群（on-premises）。这些新的部署位置理论上可以让应用程序离用户更近，从而降低端到端延迟。

然而，对于需要强一致性（strong consistency）的应用——如社交网络、预订系统、论坛——将它们部署到离用户更近的位置反而不能降低延迟。如果数据存储仍在中心数据中心，每次存储访问都需要长距离往返；如果使用 geo-replicated 存储系统（如 Spanner、DynamoDB Global Tables），PRAM 不可能性结果告诉我们，强一致性要求读写延迟之和必须大于副本间最大距离，因此跨区域协调的开销会抵消靠近用户的好处。

---

## 二、要解决的问题

1. **中心化部署的延迟瓶颈**：应用虽然与数据共置在同一数据中心，但远端用户到该数据中心的网络延迟很高（如东京用户访问弗吉尼亚数据中心）。

2. **分布式部署的协调开销**：将应用部署到多个位置后，若数据仍在中心位置，每次存储操作都需要跨区域往返，延迟被放大（单个用户请求通常触发多次存储操作）。若使用 geo-replicated 存储，全局协调的开销更高——实验显示全球表的单次访问延迟已经超过中心化部署。

3. **核心矛盾**：强一致性需要协调，协调需要通信延迟，但这个延迟阻塞了应用执行，即使绝大多数情况下协调结果是"无冲突"。

## 三、洞察与设计

**关键洞察**：对于 serverless 函数形式的应用，可以通过静态分析在执行前确定函数将访问的存储项集合（read/write set），从而将一致性协调压缩为一次单程请求，并与应用的投机执行并行进行——用投机执行的时间来"隐藏"协调延迟。

基于这一洞察，Radical 的设计包含三个核心机制：

**架构**：系统分为 near-user location（靠近用户的边缘位置，含 runtime + 本地缓存）和 near-storage location（靠近主存储的数据中心，含 LVI server + primary storage）。

**LVI 协议（Lock-Validate-WriteIntent）**：
1. 客户端请求到达 near-user location，先运行 $f_{rw}$（静态分析导出的函数）获取 read/write set
2. 同时发起两个并行操作：(a) 用本地缓存投机执行函数 $f$；(b) 将 read/write set 及本地版本号作为 LVI request 发送到 near-storage location
3. Near-storage location 获取锁 → 验证版本号 → 若成功则设置 write intent → 返回成功
4. 若验证成功，将投机执行结果返回用户，随后异步发送 write followup 将写入应用到主存储
5. 若验证失败（缓存陈旧），在 near-storage location 直接执行函数并返回结果

**静态分析**：基于符号执行和依赖分析，从 serverless 函数 $f$ 中自动提取 $f_{rw}$。对于依赖读结果的后续读（dependent accesses），先在本地缓存执行前置读来确定后续 key。

**确定性重执行**：若 write followup 未按时到达（near-user location 故障），near-storage location 通过 write intent 触发确定性重执行。函数需编译为确定性 WebAssembly 子集以保证重执行结果一致。

## 四、实现细节

- **Near-user runtime**：~1000 行 Rust，基于 AWS Lambda Rust runtime，管理本地缓存、执行 $f_{rw}$ 和 WebAssembly 函数、与 LVI server 通信。使用 Lambda extension 发送 followup 请求。
- **LVI server**：~2000 行 Go，运行在 EC2 t3.2xlarge 上（8 vCPUs, 32 GiB），处理 LVI 请求、验证、锁管理、write intent、followup。锁存储在内存中并持久化到磁盘；复制版本使用 3 节点 etcd 集群。
- **静态分析器**：基于 Eunomia（~8000 行 Python），增改 ~2000 行，支持识别存储调用并提取符号变量状态和依赖关系。
- **函数编译**：Rust → wasm32-unknown-unknown target → WasmTime 运行时执行。WasmTime 配置为禁止定时器和随机数源以保证确定性。
- **存储**：DynamoDB 作为 primary storage，版本号附加在数据项上，write intent 存储在单独的表中。Near-user cache 也使用 DynamoDB（为实验控制变量；实际可用 ScyllaDB 等更快的存储）。
- **锁**：读写锁，按 key 字典序获取以避免死锁。
- **Benchmark 应用**：将 Diaspora（社交媒体）、Lobsters（论坛）、DeathStarBench Hotel Reservation 等 5 个应用分解为 27 个 serverless 函数，全部成功通过静态分析。

## 五、实验结果

**实验环境**：AWS 全球 5 个数据中心（VA、CA、IE、DE、JP），DynamoDB primary 在 VA。每个 Lambda 函数分配 2GB 内存（2 vCPUs）。

**Near-user 到 Near-storage 往返延迟**：

| 位置 | VA | CA | IE | DE | JP |
|------|-----|-----|-----|-----|------|
| RTT (ms) | 7 | 74 | 70 | 93 | 146 |

**端到端延迟改善**：

| 应用 | Baseline (ms) | Radical (ms) | 改善 | 最大可能改善的达成率 |
|------|-------------|------------|------|-----------------|
| Hotel Booking | 317 | 229 | ~28% | 89% |
| Social Media | 270 | 194 | ~28% | 88% |
| Forum | 234 | 154 | ~34% | 84% |

**关键发现**：
- LVI 协议验证成功率在高 skew 负载下约 95%
- 执行时间 ≥ 20ms 的函数从 Radical 获益最大（LVI 延迟被完全隐藏）
- 距离主存储越远的位置获益越大；VA 本地有轻微开销
- 复制 LVI server 每个锁增加约 2.3ms，总增加 3+2.3×L ms
- **成本**：Radical 部署总成本约为 baseline 的 1.3 倍（$1413 vs $1077/月）

## 六、批判性分析

1. **验证成功率的乐观性**：论文报告 95% 的验证成功率，但实验使用的是 zipf 0.99 的 skew 分布，且写比例极低（Social Media 中 Post 仅 0.5%、Follow 仅 0.5%）。对于写密集型或低 skew 负载，验证失败率可能大幅上升，此时 Radical 反而增加延迟（锁获取+验证+near-storage 执行），论文未充分探讨这一场景。

2. **静态分析的普适性存疑**：论文声称所有 27 个函数都通过了静态分析，但这些函数是作者自己用 Rust 重写的简化版本，而非直接分析原始 Ruby on Rails 应用。实际应用的逻辑复杂度（动态分派、ORM 生成的查询、条件写入等）远超 benchmark 中的 serverless 函数。将现有应用迁移到 Radical 的工程成本被低估。

3. **函数执行时间的人为控制**：多个函数使用 pbkdf2 密码哈希来"填充"执行时间（Login 函数 213ms），这恰好使执行时间远超 LVI 延迟。如果去掉这些计算密集型操作，很多函数的实际执行时间可能低于 20ms，Radical 的收益将大幅缩水。

4. **单点 LVI server**：实验中 LVI server 是单例，虽然论文讨论了复制方案，但复制版本显著增加延迟（每个锁 2.3ms），对于涉及多个 key 的函数影响更大。论文未在复制配置下重新评估端到端性能。

5. **确定性约束的实用性**：要求函数编译为确定性 WebAssembly 子集（不能使用定时器、随机数、非确定性系统调用）限制了适用范围。论文轻描淡写了这一限制（"none of which relied on a source of non-determinism"），但现实应用中 UUID 生成、时间戳、随机采样等非确定性操作极为常见。

6. **与外部服务交互的限制**：Radical 要求所有外部服务提供幂等性机制，并且函数可能被执行两次。这对于支付、消息推送等有副作用的服务是显著约束，论文将其归为"开发者责任"但未评估实际负担。

7. **缓存冷启动问题被淡化**：新部署或故障恢复后缓存为空，所有 LVI 请求必然验证失败。论文提到可用持久化缓存缓解，但未量化冷启动期间的延迟退化程度和持续时间。

## 七、AI Infra / MLSys 视角

Radical 的核心技术——投机执行 + 静态分析预测访问集合 + 单程协调——对 AI Infra 有以下启发：

1. **分布式推理的 KV Cache 一致性**：多副本 LLM serving 场景中，不同副本的 KV cache 状态可能不一致。Radical 的"先投机执行后验证"模式可以借鉴——在本地 KV cache 上投机执行推理，同时与权威副本验证 cache 一致性，验证失败时回退。

2. **Disaggregated inference 的延迟隐藏**：在 prefill-decode 分离架构中，decode 节点访问远程 KV cache 的延迟是瓶颈。可以借鉴 Radical 的思路，通过静态分析 attention pattern 预测需要的 KV cache 条目，提前发起预取并与计算重叠。

3. **Serverless ML inference 的优化**：Radical 直接运行在 AWS Lambda 上的实现方式，为 serverless ML inference（如模型按需加载、自动扩缩容）提供了一致性保证的参考方案。当多个 serverless 推理实例共享模型参数或状态时，LVI 协议的思路可以确保一致性而不牺牲延迟。

4. **可跟进的研究方向**：
   - 将静态分析扩展到 DNN 计算图，预测 tensor 访问模式以优化分布式训练的通信调度
   - 在 parameter server 架构中，使用类 LVI 的投机读取机制——worker 用本地缓存的参数投机计算梯度，同时验证参数版本，减少同步开销

---

## 八、总结

Radical 通过将应用的投机执行与单次 LVI 协调请求并行进行，使得需要强一致性的应用能够部署到靠近用户的位置并获得 28–35% 的延迟改善（达到理论最优的 84–89%）。其核心贡献在于将一致性协调压缩为一个可以被计算延迟"隐藏"的单程请求。但该方案对应用有严格要求——必须可分解为无状态 serverless 函数、可静态分析、可确定性重执行——这限制了其在复杂现实应用中的直接适用性。适用于读多写少、函数执行时间中等以上（≥20ms）、且可接受 WebAssembly 运行时约束的 geo-distributed 场景。
