# Fast End-to-End Performance Simulation of Accelerated Hardware–Software Stacks

**作者**：Jiacheng Ma（EPFL）、Jonas Kaufmann（MPI-SWS）、Emilien Guandalino（EPFL）、Rishabh Iyer（EPFL / UC Berkeley）、Thomas Bourgeat（EPFL）、George Candea（EPFL）

## 一、背景

现代计算系统对硬件加速器的依赖日益增强，从数据中心的机器学习推理、视频处理、协议缓冲区序列化，到各类基础设施任务，加速器无处不在。无论是软件开发者还是芯片微架构师，都需要通过全栈仿真（full-stack simulation）来评估设计决策对端到端性能的影响——模拟从应用软件到 OS 再到硬件（处理器、内存、加速器）的完整系统行为。

现有主流工具链（如基于 gem5 + RTL 仿真器的 SimBricks 框架）以高保真度为设计目标，对系统中每一个组件都进行精确的周期级建模。这种方案最初是为微架构师量身定制的：他们需要窥探硬件内部每个时钟周期的状态。然而，随着加速器被越来越多地集成进软件栈，需要依赖全栈仿真的用户群体已扩展至系统开发者——对他们而言，继承来的高度可见性（fine-grained visibility）带来的只是不对等的性能开销。

---

## 二、要解决的问题

全栈仿真的核心痛点是**速度极慢**：仿真 1 秒真实执行，通常需要数小时墙钟时间（约 10,000× 的减速比）。这迫使开发者进入"批处理模式"——把多个微基准测试打包提交，等待数小时乃至数天的结果，如同用穿孔卡片编程。

具体问题包括：

1. **CPU 仿真开销巨大但价值有限**：gem5 对宿主 CPU 进行逐周期仿真，而对于系统开发者来说，CPU 的微架构细节并非关注点。
2. **加速器仿真粒度过细**：RTL 仿真器（Verilator、VCS）在门控级/寄存器传输级建模加速器，精度高但极慢；gem5 中的加速器模型精度较差。
3. **组件间同步代价高**：现有框架（SimBricks）采用锁步（lock-step）同步，迫使整个仿真以最慢的子模拟器的速度推进。
4. **无法支持交互式开发**：慢速仿真导致开发者无法实时探索硬件/软件的设计空间，软硬件协同设计（co-design）效率极低。

## 三、核心设计

本文提出**极简主义原则（Minimality Principle）**，并将其分解为两部分：

> (1) 对可用组件直接原生执行，只仿真不可用组件；
> (2) 对不可用组件，只对性能关键的方面做周期精确仿真，其余仅保证功能正确。

围绕这一原则，作者提出两个核心组件：

### NEX（Native Execution Orchestrator，原生执行编排器）

NEX 取代 gem5 负责宿主侧的执行与时间管理。其核心思路是：**软件直接在宿主 CPU 上原生运行**，仅在软件尝试与仿真加速器交互时才暂停并进行同步。

- **Epoch-Based Scheduling（EBS）**：NEX 将虚拟时间分成固定大小的 epoch（默认 1µs），应用线程在每个 epoch 内原生执行；所有线程完成当前 epoch 后，才推进到下一个 epoch。NEX 调度器基于 Linux eBPF sched-ext 框架实现，在用户空间感知虚拟时钟。
- **三种同步模式**：
  - *Eager synchronization*：每个 epoch 边界都与加速器仿真器进行锁步同步，精确但开销大；
  - *Lazy synchronization*：仅在应用线程尝试通过 MMIO 或 DMA 与加速器交互时才同步。NEX 运行时通过 mprotect() 保护共享内存，利用 segmentation fault 捕获交互事件；
  - *Hybrid synchronization*：在 lazy 同步的基础上叠加周期性同步，用于支持加速器中断（interrupt）的场景。
- **时间扭曲（Time Warping）**：为支持开发用例，NEX 提供三种控制虚拟时间的机制：
  - *CompressT*：将某段代码的虚拟时间压缩，模拟"潜在加速器"的效果；
  - *SlipStream*：以较大 epoch 快速跳过不重要的代码段（如初始化阶段）；
  - *JumpT*：使代码块在零虚拟时间内执行，用于插桩探针，不影响仿真时序。

### DSim（Accelerator Di-Simulator，加速器双轨仿真器）

DSim 将加速器的仿真解耦为两条独立轨道（di-simulation）：

- **性能轨道（Performance Track）**：基于 Latency Petri Net（LPN）抽象——将加速器的微架构行为抽象为带延迟的 Petri 网，只捕获流水线阶段和资源竞争等性能关键特性，无需逐时钟周期模拟每根信号线。LPN 是对相关 OSDI'24 工作的复用。
- **功能轨道（Functionality Track）**：用标准功能仿真重现加速器与外部环境的所有交互（控制寄存器更新、DMA 时序），确保 DSim 从外部黑盒视角与 RTL 仿真器不可区分。

两轨在 DMA 发起等关键时间点偶尔同步，从而确保外部可观测的时序正确。

**模块化组合**：NEX 和 DSim 可以与 gem5、RTL 仿真器自由组合（通过 SimBricks 共享内存通信协议），形成 gem5+DSim、NEX+RTL、NEX+DSim 等不同精度/速度权衡的配置。

## 四、实现细节

- **NEX 调度器**：基于 Linux eBPF sched-ext（scx）框架，在内核中实现 EBS 策略；使用 per-CPU 的 core-local timer interrupt 精确控制线程在 epoch 边界切换。
- **MMIO/共享内存拦截**：加速器驱动在共享内存区域调用 mprotect()，NEX 在 segfault handler 中捕获事件，完成寄存器读写并恢复线程执行；支持通过 LD_PRELOAD 劫持 clock_gettime() / gettimeofday() 使其返回虚拟时间。
- **DMA 仿真**：NEX 内置 DMA 仿真器，对来自加速器的 DMA 请求进行独立处理；lazy 同步模式下 DMA 仿真器与加速器仿真器锁步，宿主侧自由推进。
- **DSim 适配层**：提供抽象基类（含 RegRead/RegWrite/ExecuteEvent/DmaComplete 回调），DSim 模型只需覆写对应回调；zero-cost DMA（访问宿主内存，不占用虚拟周期）通过第二条无时间戳的 SimBricks 通道实现。
- **FastForward 扩展**：对 SimBricks 协议增加了 FastForward 原语，当加速器仿真器处于空闲时，NEX 可强制跳过其时钟，减少不必要的同步消息。
- **互补调度策略（Complementary Scheduling）**：在超额订阅（oversubscribed）场景中，NEX 在 EBS 之上实现类 Linux CFS 的 vruntime 优先级调度，选择哪些线程在每个 epoch 内执行。
- **代码规模**：NEX 和 DSim 开源，项目主页：https://dslab.epfl.ch/research/perf

## 五、实验结果

**实验平台**：48 核 Intel Xeon Gold 6248R（2 路，每核固定 3GHz）；加速器通过 PCIe（400ns 单程延迟）或片上互连（4ns）连接。

**评测加速器**：

| 加速器 | 领域 | 工作负载 |
|--------|------|----------|
| Apache VTA | 深度学习推理 | ResNet-18/34/50, YOLO-v3-tiny |
| Protoacc | RPC 消息序列化 | HyperProtoBench |
| JPEG Decoder | 图像解码 | Flickr / Div2k 数据集 |

**仿真精度**（与 gem5+RTL 及 FPGA 真实执行对比）：

| 基准 | 平均误差 | 最大误差 |
|------|----------|----------|
| 与 FPGA 对比（VTA，FPGA-1） | 4.3% | 9.9% |
| 与 FPGA 对比（VTA，FPGA-2） | 7.1% | 11.4% |
| 与 gem5+RTL（VTA） | 3.5% | 7.3% |
| 与 gem5+RTL（Protoacc） | 9.0% | 13.8% |
| 与 gem5+RTL（JPEG） | 9.5% | 11.5% |
| 全部（gem5+RTL 作基准） | 7%（平均） | 14%（最大） |

**仿真速度提升**（相比 gem5+RTL）：

- NEX+DSim 总体达到 **6× 到 879×** 的加速比；
- 计算密集型基准（如 YOLO-v3-tiny）最高可达 978×；
- DMA 密集型基准（如 HyperProtoBench）提升较小（约 6×）。

**各组件贡献**：
- NEX 单独替换 gem5（NEX+RTL）：2× 到 157× 加速；
- DSim 单独替换 RTL（gem5+DSim）：在加速器负载高时贡献约 2×；
- NEX+DSim 协同效果最优，最高达 gem5+RTL 最好单组件的 92× 以上。

**Epoch 配置影响**：epoch 越长，仿真越快但误差越大；1µs 是精度与速度的推荐折衷点。

## 六、批判性分析

1. **误差基准的公平性存疑**：论文将 gem5+RTL 既作为精度对比的"基准真值"，又作为速度对比的基准。然而作者自己也承认，gem5 对 CPU 的建模并不完全准确（§6.5 指出 gem5 在 benchmark 上的平均误差达 13%，最大 37%）。这意味着 NEX+DSim 的"7% 误差"是相对于一个本身存在较大误差的基准，与真实硬件的偏差可能被低估。

2. **FPGA 验证范围有限**：仅对 VTA 进行了 FPGA 实机验证，Protoacc 和 JPEG 解码器的实机验证结论依赖 gem5+RTL 这一间接基准。这削弱了对后两者精度声称的说服力。

3. **LPN 的构建成本被轻描淡写**：DSimの 精度高度依赖 LPN 的质量，而 LPN 本质上需要开发者手工建模加速器的微架构性能特征。论文引用了自己之前的 OSDI'24 工作，但对 LPN 构建所需的专业知识和工作量几乎没有量化说明，可能让读者低估这一前提条件的门槛。

4. **oversubscribed 场景精度较差**：论文坦承，当应用线程数超过虚拟核数时，NEX 的互补调度与 Linux CFS 存在显著差距（LU benchmark 误差达数倍）。这是一个相当常见的部署场景，但该问题在主体实验中被回避——相关数据仅放在 §6.6 配置影响分析中。

5. **内存竞争无法建模**：Lazy 同步模式不追踪 CPU 侧的全部内存访问，因此无法模拟 CPU 与加速器共享末级缓存（LLC）的资源竞争。对于内存带宽敏感型应用，这可能导致系统性误差。

6. **开源加速器限制评测覆盖面**：由于 DSim 需要访问加速器实现内部信息（以构建 LPN），评估范围仅限于三款开源加速器，无法代表工业级专有加速器（如 Google TPU、NVIDIA GPU）的复杂性。

## 七、AI Infra / MLSys 视角

本文与 AI 系统基础设施研究高度相关。

**直接价值**：全栈仿真器的核心用户之一就是深度学习加速器（论文用 VTA/ResNet/YOLO 作为主要评测对象）。NEX+DSim 将仿真时间从数小时压缩到数分钟乃至数秒，对 AI 芯片的软硬件协同设计流程有直接意义——尤其是当前各大厂商（Meta MTIA、Google TPU、Microsoft Azure DPU）都在进行 in-house 加速器开发的背景下。

**可迁移的设计思想**：

- **极简仿真原则**：只仿真不可用的组件，运行可用的组件——这一思路可以迁移到 AI 训练/推理系统的性能建模中，例如在只有部分 GPU 资源的情况下，对未来节点规模进行性能预测。
- **Di-Simulation 解耦**：性能轨道与功能轨道解耦是一个具有普适性的设计模式，类似于 AI 系统研究中"算子性能模型"（roofline model、analytical cost model）与"正确性模型"的分离。
- **LPN 抽象的可扩展性**：LPN 作为一种表达流水线竞争的形式化方法，可以研究其在 transformer 算子调度（attention、FFN 流水线）或 PD 分离推理引擎建模中的应用潜力。

**值得跟进的方向**：

- **为 GPU/NPU 构建 LPN 模型**：当前工作限于小型开源加速器，能否为 NVIDIA A100/H100 的 SM 架构构建近似 LPN？这是最有价值也最有难度的延伸。
- **与 AI 训练仿真器的集成**：将 NEX+DSim 与集合通信仿真器（如 SimAI、ASTRA-sim）结合，实现训练通信-计算 overlap 的端到端建模。
- **混合精度仿真**：对关键路径算子使用高精度仿真，对非关键路径使用 CompressT/JumpT 加速，实现自适应精度-速度权衡。
- **推理引擎 prefill-decode 分离场景**：两阶段计算特性不同（prefill 计算密集、decode 带宽/延迟敏感），正好契合 NEX 的 epoch 粒度同步机制，可用于模拟 PD 分离后的端到端延迟。

---

## 八、总结

本文提出了 NEX+DSim，一套面向系统开发者的轻量级全栈仿真框架。其核心贡献是将"只仿真必须仿真的部分"的极简主义原则付诸实现：NEX 令软件在宿主 CPU 上原生运行，仅在与加速器交互时介入同步；DSim 通过性能/功能双轨解耦，以 LPN 高效近似加速器的微架构时序行为。在三款加速器（VTA、Protoacc、JPEG）上，NEX+DSim 实现了相对 gem5+RTL 基准 6×~879× 的加速比，平均仿真误差约 7%，将全栈仿真从批处理模式推向交互式开发。主要局限在于：精度依赖 LPN 质量（需人工建模）、内存竞争无法建模、过载场景调度精度有限，以及当前仅支持开源加速器的评测范围。
