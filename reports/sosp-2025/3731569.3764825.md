## 研究背景

硬件加速已成为现代计算系统提升性能的关键手段。GPU、TPU、NPU 等加速器已被广泛应用于深度学习、JPEG 编解码、协议处理等领域。然而，硬件加速的软件栈开发面临着根本性的困境：**真实硬件难以获得**（FPGA 原型成本高、RTL 仿真极慢），而**现有全栈模拟器性能差**（gem5 等系统模拟器比真实硬件慢 4 个数量级），导致开发者难以快速迭代。

当前 state-of-the-art 的全栈模拟方案（如 SimBricks）将 gem5（CPU 模拟器）与 RTL 仿真器组合使用。这种方案虽然准确，但存在两个核心瓶颈：
1. **gem5 模拟 CPU 微架构的固定开销巨大**：即使在纯加速场景下，软件栈中的大部分代码仍在 CPU 上运行
2. **加速器与 CPU 的同步开销**：Lock-step 同步要求所有模拟器同步推进，导致系统整体受制于最慢的模拟器

开发者希望在不牺牲准确性的前提下大幅加速模拟，以便在合理时间内完成涉及长时间尺度（如操作系统内存管理、页面迁移、堆压缩）的系统研究。

## 要解决的问题

如何在保持高模拟精度的同时，将硬件加速软件栈的端到端模拟速度从现有 state-of-the-art 的水平提升数个数量级，使得交互式开发和快速设计空间探索成为可能？

具体挑战包括：
1. **准确性与速度的根本矛盾**：高准确性需要低层次的时钟周期模拟，但开销巨大
2. **系统范围的同步**：CPU 与加速器必须就虚拟时间达成一致
3. **功能模拟与性能模拟的耦合**：传统方案将两者绑定，难以独立优化
4. **不同模拟模式的模块化组合**：开发者可能需要混合使用不同模拟器

## 核心贡献

- 提出 **Minimalist Full-Stack Simulation** 理念：开发者愿意放弃部分硬件事件粒度（换取模拟减速因子的大幅降低），以换取快速回答端到端性能问题的能力
- 设计并实现 **NEX（Native Execution Orchestrator）**：协调 CPU 本地执行与加速器模拟，通过 epoch-based 同步和 lazy synchronization 实现高效协同
- 设计并实现 **DSim（Accelerator Di-Simulator）**：将加速器模拟解耦为性能轨道（基于 Latency Petri Nets）和功能轨道，通过 zero-cost DMA 实现两者的高效同步
- 在三个硬件加速栈（深度学习 VTA、JPEG 解码、Protobuf 序列化）上评估：NEX+DSim 比 gem5+RTL **快 6-879 倍**，模拟精度平均误差仅 **7%**（最大 14%）

## 主要研究方法

**核心观察 1：不需要模拟 CPU 微架构**
对于硬件加速软件栈，开发者真正关心的是：软件与加速器交互时的端到端性能，而非 CPU 内部的微架构行为。因此，可以让 CPU 软件**本地原生执行**（native execution），仅模拟加速器相关的交互（MMIO、共享内存、DMA）。

**核心观察 2：Latency Petri Nets (LPN) 捕获足够但不冗余的性能信息**
LPN 是一种有向数据流图，建模数据如何流经硬件电路以及每个处理阶段的时钟周期数。LPN 捕获延迟、流水线、并行和背压等关键性能特征，但不建模每个时钟周期的门级和线路变化。这恰好是性能模拟所需的最少信息。

**核心观察 3：功能与性能的解耦**
加速器的功能正确性（产生正确的计算结果）与性能特征（消耗多少时钟周期）可以分别模拟，然后通过带时间戳的 DMA 请求同步。

**NEX 同步机制**：

| 同步模式 | 描述 | 优点 | 缺点 |
|---------|------|------|------|
| Eager | 每个 epoch 边界 CPU 与加速器 lock-step | 实现简单 | 开销大（固定同步成本） |
| Lazy | 加速器仅在 CPU 尝试交互时才追赶 | 开销低 | 无法建模 CPU-加速器内存竞争 |
| Hybrid | Lazy + 周期性中断同步 | 兼顾速度和中断支持 | 仍有周期性同步开销 |

**DSim 的双轨道架构**：

- **性能轨道（Performance Track）**：运行 LPN，输出每个请求消耗的周期数（虚拟时间）
- **功能轨道（Functionality Track）**：运行功能模拟器（可以是现有开源模拟器），输出加速器对内存的所有访问
- **同步机制**：功能轨道的 DMA 请求记录在 FIFO 队列中，性能轨道在每个时间点从队列中取出对应 tag 的预记录请求，将 LPN 的时间戳与功能数据组合，产生正确带时间戳的 DMA

## 设计与实现

**NEX Orchestrator 架构**：

```
Application 1/2 → NEX Scheduler (Linux eBPF sched-ext)
                       ↓
              NEX Runtime (user-space)
                  ↓              ↓
         MMIO/SharedMem    DMA/Interrupt
           Handlers          Handlers
                  ↓              ↓
         Accelerators Simulators
                  ↓              ↓
         Interconnect + Cache + Memory Simulators
```

**NEX Scheduler（基于 eBPF sched-ext）**：
- 实现 Epoch-Based Scheduling (EBS) 策略
- 覆写 OS 内核调度器，控制所有线程
- 维护全局虚拟时间，线程在 epoch 边界同步
- 物理时间与虚拟时间对齐：线程被抢占的时间 = epoch_duration + delta（标定常数）

**NEX Runtime（用户空间）**：
- 使用 mprotect() 分配共享内存区域，触发 segmentation fault 作为事件拦截机制
- MMIO 通过 memory-mapped I/O 处理；共享内存通过 task buffer 处理
- 拦截 gettimeofday() 和 clock_gettime()，返回虚拟时间

**Tick Mode**：
- 批量多个访问并通过非法指令触发单次 trap，减少 trap 开销
- 需要对加速器驱动做小幅修改

**NEX 时间扭曲功能**：

- **CompressT**：按给定因子压缩时间，允许开发者探索将某代码段卸载到加速器的潜在收益
- **JumpT**：代码段在零虚拟时间内执行，用于性能分析和 what-if 分析
- **SlipStream**：快速穿越无趣的代码段（如初始化代码），在内部使用大 epoch duration

**DSim Di-Simulator**：

- **LPN 工具链**：使用 lpnlang Python 包原型化加速器模型，编译为 C++ 模拟器
- **功能模拟器**：使用加速器已有的开源功能模拟器（如 Apache TVM 中的 VTA 功能模拟器）
- **Zero-Cost DMA**：允许功能模拟器执行 DMA 而不影响虚拟时间
- **模块化组合**：Interconnect、Cache、Memory 模拟器可分层堆叠，通过统一 request/response 接口组合

**模块化接口**：

| 组合模式 | CPU 设计探索 | 加速器设计探索 | 模拟减速 | 可见性 |
|---------|-------------|---------------|---------|--------|
| gem5 + RTL | 支持 | 支持 | 5,582-23,970× | 全栈跟踪 |
| gem5 + DSim | 支持 | 支持 | 2,766-21,833× | 减少 |
| NEX + RTL | 不支持 | 支持 | 630-3,740× | 减少 |
| **NEX + DSim** | **不支持** | **支持** | **36-253×** | **减少** |

## 主要实验结果

**模拟精度（表 3）**：

| 基准 | 基准来源 | 平均误差 | 最大误差 | E2E 延迟范围 |
|------|---------|---------|---------|-------------|
| VTA | FPGA-1 | 4.3% | 9.9% | 71ms-1822ms |
| VTA | FPGA-2 | 7.1% | 11.4% | 48ms-1506ms |
| VTA | gem5+RTL | 3.5% | 7.3% | 47ms-700ms |
| Protoacc | gem5+RTL | 9.0% | 13.8% | 240µs-21ms |
| JPEG | gem5+RTL | 9.5% | 11.5% | 527ms-1955ms |

- 与 FPGA 基准相比：平均误差 **6%**，最大误差 **12%**
- 与 gem5+RTL 基准相比：平均误差 **7%**，最大误差 **14%**
- 论文指出，业界认为高达 20% 的误差率是可接受的

**模拟速度（图 3）**：

- NEX+DSim 比 gem5+RTL **快 6-879 倍**
- 计算密集型基准（Yolo-v3-tiny、ResNet 模型）加速最高
- 数据传输密集型基准（HyperProtoBench）加速较低（NEX 仍需模拟 DMA 请求响应）
- 具体加速示例：
  - JPEG-JPEG-2：x56 加速（gem5+RTL: 47s → NEX+DSim: 0.8s）
  - VTA-VTA-resnet18-4: x978 加速（gem5+RTL: 9.2h → NEX+DSim: 34s）

**开发用例验证**：
- JPEG + 8 加速器 + 软件后处理（matrix_filter_2d）：初始延迟 3,233ms
- CompressT 10× 分析：潜在加速到 667ms（整体 4.8×）
- JumpT 精确测量后发现：实际内存访问限制导致上限为 855ms（整体 3.78×）
- 进一步探索 VTA 设计空间：PCIe 延迟 400ns→4ns（on-chip）+ LLC→L2 DMA 服务：将延迟从 677ms 降至 146ms

**组件分解（Fig.4 & Fig.5）**：
- 单独替换 gem5 为 NEX：2-157× 加速
- 单独替换 RTL 为 DSim：2× 加速（加速器密集型）
- NEX+DSim 组合：最高 92× 加速
- 精度损失主要来自 NEX 的本地执行（而非 DSim）

## 潜在问题 / 局限性

**1. CPU 设计探索不支持**
NEX 的设计明确不支持 CPU 微架构设计探索——这是其设计选择的核心限制。NEX 无法模拟 CPU 微架构变化对系统性能的影响，因为它根本不模拟 CPU。对于需要探索不同 CPU 配置的场景，仍需使用 gem5。

**2. NEX 内存竞争建模缺失**
Lazy synchronization 无法建模 CPU 与加速器之间的内存竞争，因为 NEX 不追踪 CPU 的所有内存访问（仅追踪与加速器交互的访问）。虽然这是性能取舍，但对于评估加速器对内存子系统影响的研究，这一限制可能至关重要。

**3. 虚拟地址转换开销未建模**
NEX 尚未计入加速器 DMA 的虚拟地址转换开销（I/O TLB）。虽然这不影响正确性（DMA 使用虚拟地址仍被正确模拟），但忽略了真实硬件中 I/O TLB 未命中带来的性能开销。

**4. LPN 开发的先验知识要求**
DSim 依赖 LPN 模型来捕获加速器性能。LPN 需要访问加速器设计（由硬件工程师编写），或由 DSim 用户事后编写。虽然论文声称硬件工程师可在 3 小时内构建 LPN，但这仍需要硬件设计知识的介入。

**5. 仅支持开源加速器**
论文坦承，由于 LPN 需要访问加速器实现内部细节，当前的评估仅限于开源加速器（VTA、Protoacc、JPEG）。对于封闭源码的商业加速器，使用 DSim 需要额外的逆向工程工作。

**6. 评估的代表性局限**
三个评估加速器（VTA、Protoacc、JPEG）都是相对简单的加速器，可能无法代表更复杂的商业加速器（如现代 GPU 或 TPU）。复杂加速器的 LPN 模型构建难度和数据流特性可能与这三个案例显著不同。

**7. Epoch duration 的敏感性**
Epoch duration 对模拟精度和速度有显著影响，且最优值取决于工作负载特性。论文给出了 1µs 作为经验最优值，但未提供自动选择机制。

## 个人评注

NEX 的核心洞察——"在足够好的精度下，开发者真正需要的是速度而非完美准确性"——是对全栈模拟领域长期存在的精度执念的一种务实突破。论文没有试图让 NEX 模拟一切，而是明确划定了模拟范围：本地执行 CPU 代码，仅模拟加速器相关的交互。这种 minimalism 不是偷工减料，而是深思熟虑的设计选择。

LPN 的应用是论文最优雅的技术贡献之一。Latency Petri Net 将电路性能建模提升到抽象层次——既足够详细以捕获流水线、并行和背压，又足够抽象以避免时钟周期级的计算开销。这种抽象层次恰好匹配了"从黑盒角度无法区分"的需求。

最令人印象深刻的是开发用例的展示。NEX+DSim 使开发者能够在数分钟内完成原本需要数小时 gem5+RTL 模拟的设计空间探索。以 JPEG 的 what-if 分析为例：开发者可以先探索"如果矩阵过滤器被卸载到加速器会发生什么"（CompressT），然后通过 JumpT 精确测量当前瓶颈，最后根据结果设计新的加速器配置——整个过程在分钟级别完成，而非小时级别。

然而，NEX 的适用范围是明确的：它服务于**已有或正在设计的加速器的软件开发/硬件协同设计**，而非 CPU 微架构探索。对于 CPU 设计探索，gem5 仍然是唯一的选择。论文的 Table 1 坦诚地揭示了这一限制，这是诚实的研究态度。

从工程角度看，NEX+DSim 的模块化设计值得称道。开发者可以根据需求选择不同的模拟器组合——NEX+DSim 用于快速迭代，gem5+DSim 用于需要 CPU 模拟但不需要 RTL 精度的场景，gem5+RTL 用于最高精度要求。这种渐进式的精度/速度权衡是务实且实用的。

总体而言，NEX 代表了全栈模拟领域的一个重要转折点。它不是要取代 gem5，而是为快速设计空间探索提供了一个高效替代方案。在硬件加速日益普及的背景下，这种能够支撑交互式开发的模拟能力将变得越来越重要。
