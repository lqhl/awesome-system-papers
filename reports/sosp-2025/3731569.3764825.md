## 一、背景

现代计算系统越来越依赖硬件加速器（如深度学习加速器、视频处理、压缩/加密加速器等）来提升性能。开发这些加速器集成的软硬件栈需要反复进行全栈仿真（full-stack simulation），即同时模拟硬件（处理器、内存、加速器）和软件（应用程序、操作系统、库）的运行。

当前的全栈仿真工具（如 gem5 + RTL 仿真器）虽然能提供精确的性能估计和详细的硬件执行 trace，但速度极慢——仿真 1 秒的真实执行通常需要数小时的 wall-clock 时间（约 10,000× 的减速）。这迫使开发者采用"批处理模式"开发：将微基准测试打包后等待数小时才能看到结果，类似于 1960 年代的打孔卡编程方式，严重影响开发效率。

---

## 二、要解决的问题

1. **全栈仿真速度太慢**：gem5 + RTL 仿真器对系统的每个组件都进行 cycle-accurate 模拟，包括 CPU 微架构、内存层次、加速器门级细节等，产生巨大的计算开销。
2. **开发者无法交互式迭代**：由于仿真需要数小时，软件和硬件开发者无法快速评估设计变更对系统性能的影响，不得不以低效的 batch-mode 方式工作。
3. **可见性与速度的失配**：传统仿真器是为微架构师设计的，提供 cycle 级的硬件细节可见性。而系统软件开发者并不需要这些低层细节，但仍被迫承受这些细节带来的仿真开销。

---

## 三、洞察与设计

**关键洞察**：对于系统软件开发者而言，全栈仿真中绝大部分的仿真开销来自对已有组件（如 CPU）的不必要模拟和对加速器非性能关键方面的过度精细模拟。如果仅模拟不可用的组件，并且对不可用组件也只 cycle-accurate 地模拟性能关键的方面，就可以在保持足够精度的同时实现数量级的加速。

基于这一"最小化原则"（minimality principle），作者设计了两个核心组件：

### NEX（Native Execution Orchestrator）
NEX 体现了最小化原则的第一部分：**运行可用组件的原生执行，仅模拟不可用组件**。具体设计：
- 软件直接在真实 CPU 上原生执行（而非在 gem5 中模拟），避免了 CPU 微架构仿真的巨大开销
- NEX 调度器基于 Linux eBPF 的 sched-ext 扩展实现，采用 epoch-based scheduling (EBS) 策略，将执行分为微秒级的 epoch
- 提供两种同步模式：eager synchronization（锁步同步）和 lazy synchronization（仅在软件尝试与加速器交互时才同步），后者大幅减少不必要的同步开销
- 对于使用中断的加速器，提供 hybrid synchronization（在 lazy 基础上叠加周期性同步）
- 提供三种时间控制机制：CompressT（模拟假设性加速）、SlipStream（快进不感兴趣的代码段）、JumpT（在零虚拟时间内执行代码）

### DSim（Di-Simulator）
DSim 体现了最小化原则的第二部分：**对不可用组件仅 cycle-accurate 模拟性能关键方面**。核心设计是将加速器仿真解耦为两条独立轨道：
- **性能轨道**：基于 Latency Petri Net (LPN) 抽象，计算加速器处理每个请求所需的 cycle 数。LPN 仅捕获流水线、并行度、延迟和反压等性能关键特征，不模拟每个时钟周期的门级/信号级细节
- **功能轨道**：使用标准功能仿真器计算加速器的正确输出结果，确保硬软件栈的功能正确性
- 两条轨道通过 DMA 请求的标签匹配机制进行同步：功能仿真提供 DMA 内容，LPN 提供精确时间戳

NEX 和 DSim 可独立使用，也可组合使用，并通过 SimBricks 共享内存通道与 gem5 或 RTL 仿真器模块化集成。

## 四、实现细节

**NEX Runtime**：
- 通过 mprotect() 内存保护机制拦截应用线程对加速器共享内存/MMIO 区域的访问（产生 segfault，被 NEX 通过 ptrace 捕获）
- 时间虚拟化通过 LD_PRELOAD 覆写 gettimeofday() 和 clock_gettime()
- 支持 tick mode，让驱动批量处理多次访问后触发一次 trap，减少 mid-epoch trap 带来的不精确性
- NEX 调度器通过 core-local timer interrupt 精确控制每个 epoch 的执行时长（epoch duration + 校准常数 δ）

**NEX Scheduler (EBS)**：
- 基于 Linux eBPF sched-ext 实现
- 线程在 epoch 边界调度，确保 epoch i 的所有同步事件解决后才允许进入 epoch i+1
- 线程固定在核上运行整数倍 epoch（π = N·e），减少微架构干扰
- 过载场景下支持互补调度策略（complementary scheduling policy），模拟目标系统的调度行为

**DSim 性能轨道**：
- 使用 lpnlang Python 包原型设计加速器 LPN 模型，编译为 C++ 仿真器
- LPN 是有向数据流图，模拟数据在硬件中的流动和每个处理阶段的 cycle 数

**DSim 功能轨道同步**：
- 先运行功能仿真器获取完整 DMA trace（使用 zero-cost DMA 读取宿主内存）
- 每个 DMA 请求按 tag 存入 FIFO 队列（如 LOAD_INPUT, LOAD_WEIGHT 等）
- LPN 推进时发出带时间戳的 DMA 请求，从对应 tag 队列中出队预录 DMA 内容

**模块化接口**：通过 SimBricks 库的共享内存通道实现 NEX↔DSim、NEX↔RTL、gem5↔DSim 的组合，还扩展了 SimBricks 协议添加 FastForward 原语减少空闲时的同步消息。

## 五、实验结果

### 评估目标
三种开源加速器：JPEG 解码器、Apache VTA（深度学习）、Protoacc（Protobuf 序列化）。

### 仿真精度（NEX+DSim vs 基线）

| 基线 | 加速器 | 平均误差 | 最大误差 | 最小误差 |
|------|--------|---------|---------|---------|
| FPGA-1 | VTA | 4.3% | 9.9% | 1.1% |
| FPGA-2 | VTA | 7.1% | 11.4% | 2.6% |
| gem5+RTL | VTA | 3.5% | 7.3% | 1.7% |
| gem5+RTL | Protoacc | 9.0% | 13.8% | 1.9% |
| gem5+RTL | JPEG | 9.5% | 11.5% | 8.3% |

整体：平均 7% 误差，最差 14%（对比 gem5+RTL）。

### 仿真速度

| 配置 | 仿真减速范围 |
|------|-------------|
| gem5+RTL | 5,582×–23,970× |
| gem5+DSim | 2,766×–21,833× |
| NEX+RTL | 630×–3,740× |
| NEX+DSim | 36×–253× |

NEX+DSim 相对 gem5+RTL 实现 **6×–879× 加速**，将仿真时间从数小时/数十分钟降至数秒。计算密集型 benchmark 加速更显著（如 VTA matmul 达 978×）。

### 组件贡献分解
- 仅替换 gem5 为 NEX（NEX+RTL）：2×–157× 加速
- 仅替换 RTL 为 DSim（gem5+DSim）：在加速器负载较重时效果明显（如 matmul 达 2×）
- 两者组合效果远超单独使用，最高达单独最优组件的 92×

### Epoch 参数影响
1µs epoch duration 是精度与速度的最佳平衡点（更小的 epoch 因微架构 flush 开销反而增加误差）。

## 六、批判性分析

1. **评估局限于开源加速器**：由于 DSim 依赖 LPN（需要加速器内部设计信息），评估仅限于三个开源加速器（JPEG、VTA、Protoacc）。这些加速器的规模和复杂度远低于工业界实际使用的加速器（如 GPU、TPU、NPU），无法证明该方法在真实大规模加速器上的可行性和精度。

2. **CPU-加速器内存竞争无法建模**：NEX 因原生执行 CPU 指令而无法追踪所有 CPU 内存访问，因此无法模拟 CPU 与加速器之间的内存竞争。论文将此作为 limitation 轻描淡写，但在实际系统中（尤其是共享 LLC 的 on-chip 加速器场景），内存竞争可能是性能的关键瓶颈。

3. **过载场景精度大幅下降**：当线程数超过核心数时，SP 和 LU benchmark 的误差分别高达 55% 和 128%。论文将此归因于互补调度策略与 Linux CFS 的差异，但过载场景在实际数据中心中极为常见，这一限制不容忽视。

4. **驱动修改的成本被低估**：论文声称对驱动的修改是"最小的"，但实际上需要修改 MMIO 映射、添加 tick mode 标注、以及可能的 SlipStream/JumpT 标注等。对于复杂的工业级驱动栈，这些修改的工程成本可能远高于论文所述。

5. **NEX 自身的 10–20× 基线减速**：即使不模拟加速器，NEX 本身因频繁内核切换和每 epoch 线程管理带来 10–20× 减速。对于 CPU 密集型且与加速器交互较少的场景，这一固有开销削弱了 NEX 的实际价值。

6. **尾延迟精度存疑**：论文在 §6.8 报告 Protoacc 的 p90 延迟平均误差为 20%，但 Protoacc-bench1 误差不成比例地大（因为 p90 延迟低于 10µs 时真实 CPU 方差占主导）。对尾延迟敏感的场景（如在线服务），这种不稳定性是一个严重问题。

## 七、AI Infra / MLSys 视角

1. **对 AI 加速器仿真的启发**：NEX+DSim 的最小化原则可直接应用于 AI 加速器（如 NPU、TPU）的全栈仿真。当前 AI 系统开发者在评估训练/推理系统设计时同样面临仿真过慢的问题。LPN 抽象特别适合建模 AI 加速器中常见的流水线、数据流和反压行为。

2. **CompressT 用于加速器选型分析**：CompressT 的假设性加速功能为 AI Infra 团队提供了一种轻量级的 what-if 分析方法——在不实现完整 offload 的情况下评估将特定计算卸载到加速器的端到端收益，可用于早期的加速器选型和系统架构决策。

3. **可迁移的设计思路**：性能-功能解耦（di-simulation）思路可迁移到 AI 推理引擎的性能建模中。例如，在 vLLM 等系统的开发中，可以用类似 LPN 的抽象建模 KV cache 管理、batch scheduling 等子系统的性能行为，而不需要完整运行整个推理流程。

4. **值得跟进的方向**：
   - 为 GPU/TPU 等大规模 AI 加速器构建 LPN 模型，验证 DSim 在这些复杂架构上的精度和速度
   - 将 NEX 的 epoch-based 同步机制扩展到多加速器异构系统（如 CPU + GPU + NPU 混合训练/推理集群）
   - 结合 NEX+DSim 与 AI compiler（如 TVM、XLA）的性能模型，实现从算子到全栈的端到端性能预测

---

## 八、总结

本文提出了 NEX+DSim 全栈仿真框架，通过最小化原则（原生执行可用组件 + 仅 cycle-accurate 模拟性能关键方面）实现了相比 gem5+RTL 基线 6×–879× 的仿真加速，同时保持平均 7%、最差 14% 的精度。该框架将硬件加速栈的开发从 batch-mode 推进到 interactive-mode，使开发者能在数秒内完成之前需要数小时的全栈仿真。主要局限在于无法建模 CPU-加速器内存竞争、过载场景精度不足，以及仅在开源小规模加速器上验证，尚未证明在工业级复杂加速器上的可行性。
