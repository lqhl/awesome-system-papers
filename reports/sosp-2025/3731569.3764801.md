# Demeter: A Scalable and Elastic Tiered Memory Solution for Virtualized Cloud via Guest Delegation

## 一、背景

云计算基础设施以虚拟机（VM）为核心，而传统 DRAM 的容量增速远落后于 CPU 核心数增速——过去十年 CPU 核心数增长了 10 倍，但旗舰服务器处理器支持的最大内存容量仅增长了约 2.67 倍。为此，Azure、Google、Facebook 等主要云厂商已开始引入**分级内存架构（Tiered Memory Architecture）**：以有限的快速内存（FMEM，通常是 DRAM）搭配大容量慢速内存（SMEM，如 PMEM、CXL.mem），兼顾性能与容量，并可将内存成本降低约一半。

分级内存需要由软件进行**分级内存管理（TMM）**，即通过访问跟踪、热度分类、数据迁移三步流水线将热数据保留在 FMEM。现有内核级 TMM 系统（TPP、Memtis、Nomad 等）已相当成熟，但针对虚拟化云环境的 TMM 研究相对不足，且已有设计普遍依赖 hypervisor 进行管理，存在严重性能问题。

---

## 二、要解决的问题

**问题一：基于 hypervisor 的 TMM 引发大量 TLB 刷新**

虚拟化环境下内存访问需经过二维（2D）地址翻译：Guest 虚拟地址（gVA）→ Guest 物理地址（gPA）→ Host 物理地址（hPA），涉及 GPT（Guest Page Table）和 EPT（Extended Page Table）两层。现有 hypervisor 方案（RAMinate、vTMM 等）通过扫描 PTE.A/D bit 追踪访问，每轮扫描后需 TLB flush 以清位并捕获下次访问。由于 hypervisor 无法获知 gVA，只能执行开销极大的全量 EPT 失效（`invept`），导致 TLB flush 次数是 Guest 端方案的 4.7 倍，执行时间是 2.5 倍。

**问题二：hypervisor 无法使用 PEBS 追踪 Guest 内存访问**

PEBS（Processor Event-Based Sampling）是 Intel 硬件提供的高效访问采样机制，已被 HeMem、Memtis 等内核级系统证明优于 PTE.A/D 扫描。然而在虚拟化环境中，PEBS 无法穿越虚拟化边界向 hypervisor 提供 Guest 的访问样本，导致 hypervisor 方案错失这一关键优化路径。

**问题三：直接在 Guest 内复用已有 TMM 方案缺乏可扩展性**

在多租户云环境中，一台物理机运行数个乃至数十个 VM，若每个 VM 内各自运行 TPP 或 Memtis，管理开销随 VM 数量线性叠加。在 36 核系统上运行 9 个 VM 时，TPP 消耗约 4.5 个核，Memtis 也消耗约 1.25 个核，严重影响 CPU 出租率和 TCO。

**问题四：云弹性与 TMP 的兼容**

云环境需要支持内存的动态弹性扩缩（过提交、按需调整）。已有 VirtIO balloon 等机制不具备分级内存感知能力，在扩缩过程中会混淆 FMEM/SMEM，导致 FMEM 严重不足。

---

## 三、核心设计

Demeter 提出**Guest 委托（Guest Delegation）**范式：将整个 TMM 流水线（访问跟踪、热度分类、页面迁移）下放到 Guest VM 内执行，Hypervisor 仅负责**分级内存供给（TMP）**。

### 3.1 两大核心洞察

1. **委托给 Guest 可消除 hypervisor 端的昂贵 PTE.A/D 扫描和 TLB flush**：Guest 内可获取完整 gVA，使用精确的单地址 TLB 失效（`invvpid`），大幅减少 flush 次数。
2. **EPT-friendly PEBS 在 Guest 内可用且隔离良好**：PEBS v5 修复了一个架构 bug（EPT page fault 可能打断 PEBS 写入导致宕机），Guest PEBS 使用 vmcs.debugctl 中的 Guest 私有缓冲区，不同 VM 的采样结果天然隔离，无信息泄漏风险。

### 3.2 高效可扩展的 Guest TMM

**基于范围的热度分类（Range-based Hotness Classification）**：在 Guest 虚拟地址空间（而非物理地址空间）运行，利用线段树（Segment Tree）结构迭代分裂热点区域。初始只有 heap 和 mmap 两个大范围；如果某范围的访问次数显著高于邻居，则从中间一分为二，最小粒度为 2 MiB（与 hugepage 对齐）。每轮 epoch（默认 500ms）对访问计数衰减减半以实现冷却。这一设计在 Guest 虚拟地址空间保留了最完整的局部性信息（物理地址空间因 OS 懒分配而破坏了空间局部性）。

**可扩展的 EPT-friendly PEBS**：
- 使用 `MEM_TRANS_RETIRED.LOAD_LATENCY` 事件（延迟阈值 64ns），媒介无关，同时支持 PMEM 和 CXL.mem
- 固定采样频率（sample period = 4093），避免动态调频引发 PMI overshoot
- 在**进程切换**时批量 drain PEBS 缓冲区，通过无锁 MPSC（Multi-Producer Single-Consumer）channel 送入范围分类器，完全消除专用轮询线程

**平衡页面迁移（Balanced Page Relocation）**：将晋升候选（SMEM 中的热页）和降级候选（FMEM 中的冷页）配对，一一交换而非顺序迁移。避免了传统方案先腾出空间再填入的两步操作，不触发 kswapd 或直接回收，防止级联降级。

### 3.3 弹性 TMP：Demeter Balloon

- **NUMA 节点暴露**：通过 ACPI 虚拟 NUMA 表，在 VM 启动时将 FMEM 和 SMEM 分别表示为两个虚拟 NUMA 节点，Guest 内核可感知分级拓扑。
- **Double Balloon**：为每个 NUMA 节点各配一个 balloon，每个 balloon 均支持页粒度的膨胀/收缩，最大容量等于总内存的 100%，可灵活调节 FMEM/SMEM 比例。
- **全异步架构**：基于 VirtIO + workqueue + `epoll()`，balloon 请求异步处理，不阻塞关键路径。
- **QoS 统计上报**：通过 VirtIO 统计队列将 Guest 内存使用情况（按层分类的利用率、访问模式、内存压力指标）上报 hypervisor，支持机器级或集群级内存调度策略。

## 四、实现细节

Demeter 基于 Linux Kernel v6.10 和 Cloud Hypervisor v36 实现：

- **Hypervisor TMP**：扩展 VirtIO memory balloon，新增 FMEM/SMEM 双镜像结构。约 1,000 行 Rust（hypervisor）+ 1,000 行 C（driver）。
- **Guest TMM**：作为独立 Linux 内核模块实现，约 8,000 行 C，无需修改内核主线，可跨内核版本集成。

关键实现细节：
- PEBS 采样直接工作在 Guest 模式，样本包含 gVA，无需任何地址翻译即可送入范围分类器
- 范围树的热度排名以平均访问频率为主，以范围创建时间为次，同时利用时间局部性
- 迁移时通过 `unmap → swap contents → remap` 的三步批量操作，最小化页表锁争用和 TLB flush 次数
- EPT-friendly PEBS 通过 vmcs.debugctl 字段切换，由 Guest 完全控制，主机无需干预

## 五、实验结果

**实验平台**：双路 Intel Xeon 8360Y（36 核/路），4×32 GiB DDR4-3200 DRAM + 4×128 GiB Intel Optane PMem 200；另有基于远端 NUMA 内存模拟的 CXL.mem。每个 VM 配置 4 vCPU、16 GiB 分级内存，默认 FMEM:SMEM = 1:5。

**基准比较**：TPP-H（hypervisor 端 TPP）、TPP（Guest 端）、Memtis、Nomad

### 5.1 关键微基准

| 方案 | TLB flush（单地址） | TLB flush（全量） | GUPS 耗时（s） |
|------|------|------|------|
| TPP-H | 62,289,626 | 20,214,840 | 896.35 |
| TPP-G | 17,707,154 | 0 | 353.91 |
| Demeter | 9,305,363 | 0 | 299.57 |

| 访问跟踪方案 | CPU 开销（s） | %CPU | 采用者 |
|------|------|------|------|
| EPT-friendly PEBS | 5.937 | 0.64% | Demeter |
| PTE.A/D bits | 27.814 | 3.08% | TPP-H |
| PML-based | 135.410 | 14.61% | vTMM |

- **可扩展性**（9 个 VM）：Demeter 始终控制在 0.2 核以内，TPP ≈ 4.5 核，Memtis ≈ 1.25 核。
- **Demeter Balloon**：与静态分配性能相当，比 VirtIO balloon+TPP 高 68% 吞吐量。
- **平衡迁移**：仅消耗 TPP 迁移开销的 28%，且无级联降级。

### 5.2 真实应用（7 个工作负载）

| 工作负载 | 访问特征 | Demeter vs TPP | Demeter vs TPP-H |
|------|------|------|------|
| btree / bwaves | 均匀分布 | ≤20% 提升 | ~10–20% 提升 |
| XSBench / LibLinear | 静态热点 | >40% 提升 | ~20% 提升 |
| Silo（OLTP） | 动态热点 | ≥10% 提升 | 最高 2× 提升 |
| graph500 / PageRank | 幂律分布 | 次优（PageRank 慢 60%） | 多数场景超越 |

- **综合结果**（9 个 VM）：相比 TPP（次优 Guest 方案）平均提升 **28%**；相比 TPP-H（hypervisor 方案）最高提升 **2×**，平均提升 **16%**。
- **P99 尾延迟**（Silo）：相比 TPP 降低 **23%**（45.2ms → ~35ms）。

## 六、批判性分析

**优势被选择性呈现**：论文在 PageRank 工作负载上承认 Demeter 比 TPP-H 慢 60%，原因是图工作负载的访问模式极度分散（幂律分布），范围分类优势无法发挥。但作者将此归因于"独特挑战"而非方案局限，未深入分析能否改进。这暗示 Demeter 在稀疏随机访问负载下的适用性存疑。

**基线构造存在不对称性**：论文使用自己构造的 TPP-H（hypervisor 端 TPP + KVM MMU notifier）作为 hypervisor 方案的代表，因为现有 hypervisor 方案（RAMinate、vTMM 等）源码不公开。TPP-H 是否准确反映了工业级 hypervisor TMM 的水平尚存疑义。

**实验规模较小**：评测平台为单机 36 核，最多 9 个 VM，每个 VM 仅 4 vCPU 和 16 GiB 内存。真实云环境中 VM 密度可能更高（单机 100+ VM），Demeter balloon 的异步机制和 VirtIO 通信开销在极高密度下是否仍能保持线性扩展未被证实。

**文件页缓存排除在外**：Demeter 的 gVA 范围管理不覆盖 file page cache（由 OS 在物理地址空间管理）。作者以"放入 SMEM 也比 I/O 快"为由轻描淡写，但对于 I/O 密集型工作负载（如数据库），这可能是一个显著局限。

**参数敏感性图（Figure 9）选择了对 Demeter 有利的范围**：虽然结论称参数对性能影响不大，但图示的"稳定区间"仍较为宽泛，未明确生产环境下参数调优的成本。

**Guest Delegation 的安全假设乐观**：论文仅简要讨论了 token-bucket 限速、主机强制终止异常 VM 等防御手段，但对恶意 Guest 通过大量请求 balloon 操作来干扰主机响应速度的攻击面未做完整分析。

## 七、AI Infra / MLSys 视角

本文与 AI Infra 的关联性在于：大型模型训练/推理节点的内存往往是瓶颈，CXL.mem 等内存扩展技术正在被 AI 系统社区积极探索。以下几点对 AI Infra 研究有参考价值：

**1. 分级内存管理中虚拟地址空间的局部性优势**

论文的核心 insight——Guest 虚拟地址空间保留的局部性信息优于物理地址空间——在 AI 训练场景中同样适用。大模型训练中不同 tensor 具有高度不同的访问热度（参数、激活、梯度各异），而物理分配通常打乱了这种结构性局部性。基于 VMA（Virtual Memory Area）级别的热度追踪是一个值得移植的思路。

**2. PEBS 在 AI 工作负载热度追踪中的潜力**

训练框架（PyTorch、JAX）的内存访问模式高度规律（按 layer、按 batch），PEBS 的 `MEM_TRANS_RETIRED.LOAD_LATENCY` 事件可以用于精确识别哪些 tensor 长期驻留慢速内存，触发 prefetch 或 offload 策略。这比 vLLM/Mooncake 等现有 KV cache 管理依赖的启发式更为精准。

**3. CXL.mem 扩展下的推理内存管理**

LLM 推理中 KV cache 是 SMEM 的天然候选（访问频率低于 model weights），Demeter 的 balanced relocation 机制（无临时缓冲区的一对一页面交换）可以减少推理过程中 KV cache 换入换出的延迟抖动，有助于降低 P99 尾延迟。

**4. 值得跟进的研究方向**

- 将 Guest Delegation 原则应用于 AI 训练 VM：在 VM 内部感知 tensor 生命周期，主动将历史 batch 的参数梯度降至 CXL.mem，减少 DRAM 峰值压力
- 结合 PEBS 与 AI 框架 profiling（如 PyTorch Profiler）构建联合热度信号，做跨层 tensor 的精细分级放置
- 探索 Demeter balloon 机制用于 GPU 显存 + Host DRAM + CXL.mem 三级分层的可行性（GPU UVM 场景）

---

## 八、总结

Demeter 提出"Guest 委托"范式，将分级内存管理整体下放至 Guest VM，仅由 Hypervisor 负责内存弹性供给。核心贡献包括：首次在虚拟化环境中正确使用 EPT-friendly PEBS 做访问采样、在 Guest 虚拟地址空间进行基于范围的热度分类以保留局部性、以及消除临时页分配的平衡迁移机制。在 7 种真实工作负载上，Demeter 相比 hypervisor 方案提升最高 2×，相比最佳 Guest 方案平均提升 28%，CPU 管理开销在 9 VM 场景下仅为竞品的十分之一。主要局限在于：散乱访问模式（如图计算 PageRank）下存在性能倒退，以及 file page cache 不在管理范围内。Demeter 代码已开源，适合作为云厂商 vendor OS 的内核模块集成，是目前虚拟化分级内存领域最系统化的工作之一。
