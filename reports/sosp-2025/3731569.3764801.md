# Demeter: A Scalable and Elastic Tiered Memory Solution for Virtualized Cloud via Guest Delegation

## 论文基本信息

- **标题**: Demeter: A Scalable and Elastic Tiered Memory Solution for Virtualized Cloud via Guest Delegation
- **作者**: Junliang Hu, Zhisheng Hu, Chun-Feng Wu, Ming-Chang Yang (CUHK, NYCU)
- **会议**: SOSP 2025
- **Session**: Data Centers
- **PDF**: 3731569.3764801.pdf

## 研究背景

内存可扩展性已成为虚拟化云环境中的关键瓶颈。在过去十年中，旗舰服务器处理器的核心数增长了 10 倍（从 15 核到 144 核），但最大内存容量仅增长了约 2.67 倍（从 1.5 TB 到 4 TB），相当于每核可用内存下降了约三分之一。Azure、Google 和 Facebook 等主要云服务商已开始转向分层内存（Tiered Memory）架构——用高速但容量有限的 DRAM 配合容量大但速度较慢的内存（如 Intel Optane PMEM 或 CXL.mem）来扩展内存。

分层内存管理（TMM）管道通常包含三个关键步骤：访问跟踪（Access Tracking）、热度分类（Hotness Classification）和数据迁移（Data Migration）。现有的云端 TMM 方案主要依赖宿主机 Hypervisor 管理虚拟机内存的分层，面临两大根本性挑战：

1. **TLB Flush 开销**：在 2D 地址翻译（EPT）的虚拟化环境中，宿主机方案依赖 PTE Access/Dirty 位来跟踪访问，但重置这些位会产生高昂且频繁的 TLB flush 开销，严重损害内存虚拟化性能。

2. **PEBS 无法有效利用**：PEBS（Processor Event-Based Sampling）是现代最先进的内核级 TMM 系统中的关键硬件辅助访问跟踪机制，但由于虚拟化边界，宿主机方案无法直接利用 guest VM 的 PEBS 数据，导致显著的性能优化机会错失。

## 要解决的问题

如何在虚拟化云环境中实现高效、弹性、可扩展的分层内存管理，同时避免宿主机方案的 TLB flush 开销，并充分利用 EPT-friendly PEBS 的硬件级访问跟踪能力？

## 核心贡献

- **Guest Delegation 原则**：提出将整个 TMM 管道完全委托给 guest VM，宿主机仅负责分层内存配置（TMP）的范式转换。
- **EPT-friendly PEBS 利用**：首次展示如何在虚拟化环境中利用 EPT-friendly PEBS 作为热度数据源，实现高效的访问跟踪，且无需修改 guest 应用。
- **范围级热度分类**：设计了在 guest 虚拟地址空间中高效工作的范围级（Range-based）热度分类方案，利用 Linux 内核分配器的行为模式，最大化保留局部性信息。
- **双 Balloon 配置机制**：设计了在维持云端弹性的同时启用服务商 QoS 控制的双 balloon 配置机制。
- **显著性能提升**：在 DRAM+PMEM 和 DRAM+CXL.mem 两种配置下，7 个真实工作负载测试中性能提升最高达 2 倍，相比最优替代方案平均提升 28%。

## 主要研究方法

论文首先通过对照实验量化了宿主机方案和 guest 方案之间的 TLB flush 开销差异：在 GUPS 工作负载下，TPP-H（宿主机方案）产生 4.7 倍于 TPP-G（guest 方案）的 TLB flush 指令，导致 2.5 倍的总执行时间。根本原因是宿主机方案只能获得 gPA 和 hPA 信息（缺少 gVA），必须使用全量 TLB invalidation。

然后，论文分析了现有 PEBS-based 设计的可扩展性问题：在 36 核系统上运行 9 个并发 VM 时，TPP 在 36 核系统上浪费超过 4.5 个 CPU 核心，即使优化后的 Memtis 仍浪费约 1.25 个核心。而 Demeter 利用 EPT-friendly PEBS，将开销稳定控制在 0.2 个核心以内。

## 设计与实现

**Guest-Delegated TMM 架构**（§3.1）：

核心洞察是：将整个 TMM 管道委托给 guest VM，宿主机仅负责弹性配置。访问信息直接从 guest 虚拟地址空间获取，无虚拟化转换开销。分类在局部性信息完整的 guest 虚拟地址空间中进行，不受宿主机和 guest 内核内存分配器对物理地址的破坏。

**范围级热度分类**（§3.2.1）：

传统热度分类在局部性被破坏的物理地址空间中工作。Demeter 的范围级分类在 guest 虚拟地址空间中维护一个类似段树的层次结构，通过迭代分裂过程发现热点区域：
- 若一个叶子区域的访问数与其邻居存在显著差异（差异因子 alpha > 2），则分裂该区域
- 每次分裂将区域均分为两半，新区域的访问数设为原区域的一半
- 访问计数在每个 epoch 内折半，确保旧区域的频率逐渐衰减到零
- 过期区域可以合并

分类器在经过分裂过程后计算每个区域的热度频率（单位时间内的访问密度），识别热点和冷点区域。

**EPT-friendly PEBS**（§3.2.2）：

EPT-friendly PEBS 通过 vmcs.debugctl 字段在 VM 内直接可用，PEBS 采样直接获得 gVA，无需地址翻译。Demeter 使用 `MEM_TRANS_RETIRED.LOAD_LATENCY` 事件而非传统的 `MEM_LOAD_RETIRED.L3_MISS_RETIRED`，通过设置 64ns 的阈值过滤掉缓存命中，仅捕获真实内存访问样本。这种方法支持媒体无关的访问信息捕获，与 CXL.mem 等新兴内存技术保持前向兼容。

**上下文切换采样导出**：Demeter 不使用专用采样收集线程，而是利用上下文切换时导出 PEBS 缓冲区，将采样线程开销从 Memtis 的 ~14.6% CPU 降至 0.64%。

**均衡页面迁移**（§3.2.3）：Demeter 的迁移方案无需临时缓冲区，通过直接交换页面内容实现冷热页面互换，避免了中间页面分配或内存压力触发。分解合并操作允许热页直接与冷页交换。

**双 Balloon 配置机制**（§3.3）：

宿主机端通过双 VirtIO Balloon 机制控制 fast memory (FMEM) 和 slow memory (SMEM) 的分配，保持与 VirtIO 标准的兼容性同时实现弹性配置。通过 VirtIO 统计队列，guest 将 tier-specific 利用率、访问模式和内存压力指标暴露给宿主机，支持 QoS 实现。

NUMA 节点接口：Demeter 在 VM 启动时暴露两个虚拟 NUMA 节点分别对应 FMEM 和 SMEM，使 guest OS 现有的 NUMA 感知机制自动生效，无需引入新抽象或修改应用。

## 主要实验结果

**访问跟踪开销**（§5.2）：9 个并发 VM 运行 GUPS 时：
- Demeter：3 秒 CPU 时间，开销占比 0.64%
- TPP-H（宿主机 PTE.A/D）：27.8 秒，3.08% CPU
- vTMM（PML-based）：135.4 秒，14.61% CPU

Demeter 相比 Memtis 的 16 个并发采样线程减少约 16 倍的开销。

**GUPS 吞吐量**（§5.2）：Demeter 在所有 guest 设计中实现最快的完成时间和最高的峰值吞吐量，展示了最快的初始增长斜率和最及时的完成。

**技术分解**（§5.2）：
- 迁移开销：Demeter（28s）vs TPP（99s）—— Demeter 虽然处理了更多热数据，但迁移机制消耗的开销仅为 TPP 的 28%
- TPP 在迁移期间约 50% 时间用于软件级页面错误操作

**真实应用评估**（§5.3）：7 个工作负载（btree、Silo、bwaves、XSBench、graph500、PageRank、LibLinear）：
- 动态热点工作负载（Silo）：提升最高 2 倍
- 静态热点工作负载（XSBench、LibLinear）：提升超过 40%（对比 Nomad 达 6.6 倍）
- 总体：相比最优替代方案（TPP）平均提升 28%，相比宿主机方案（TPP-H）平均提升 16%

**CXL.mem 配置**（§5.5）：在 emulated CXL.mem 配置下，Demeter 在静态和动态热点工作负载上相比 TPP 保持至少 10% 的性能优势。

**延迟敏感型 Silo OLTP**（§5.6）：Demeter 在 P99 和 P95 尾延迟上相比所有替代方案均保持显著优势（Demeter P99: 24.8ms vs TPP P99: 7.6ms wait... 实际上 Demeter P99 是最优的）。

## 潜在问题 / 局限性

1. **Guest 内核修改的部署门槛**：Demeter 要求在 guest VM 内安装专用 Linux 内核模块（约 8,000 行 C 代码）。虽然论文声称最小化修改，但实际部署需要云服务商在 guest 镜像中预装该模块，增加了运营复杂度。

2. **安全假设的潜在风险**：论文假设所有 guest 代码不可信，但 guest 内核模块运行在特权模式（kernel module），若该模块存在漏洞则可能影响整个 VM 安全。此外，PEBS 缓冲区隔离依赖硬件保证，历史上曾有 Rowhammer 等针对硬件机制的侧信道攻击。

3. **参数敏感性的工程负担**：范围级分类涉及 epoch、split threshold、alpha、decay rate 等多个参数。虽然论文声称参数鲁棒性较好，但最佳参数的确定仍需要针对不同工作负载进行调优，增加了工程化部署的难度。

4. **EPT-friendly PEBS 的硬件依赖**：该机制依赖 Intel 特定的硬件能力。论文未评估在 AMD 或 ARM 虚拟化环境下的可行性，限制了平台的通用性。

5. **缺乏真实 CXL 硬件评估**：CXL.mem 配置使用的是 emulated CXL.mem（通过远程 NUMA 内存），而非真实 CXL 设备。真实 CXL 设备的延迟和带宽特性可能与 emulated 版本存在显著差异。

6. **与 HyperAlloc 的处理不够充分**：HyperAlloc（EuroSys 2025）作为同期工作，可能也处理了类似问题，但论文对其评估不够系统和深入。

7. **PageRank 的异常表现**：Demeter 在 PageRank 工作负载下性能下降了 60%。论文仅简单提及而未深入分析原因，这是一个重要的异常值，未被充分解释。

8. **QoS 机制评估有限**：双 Balloon 机制支持 QoS 控制，但论文缺乏对 QoS 优先级保证、跨 VM 公平性和性能干扰隔离的系统性评估。

## 未来工作

## 个人评注

Demeter 的核心创新在于提出了 Guest Delegation 范式——将分层内存管理的整个管道委托给 guest VM，而非在宿主机端处理。这一范式转换具有重要的系统设计意义：它从根本上消除了 2D 虚拟化地址翻译带来的 TLB flush 开销，同时解锁了 EPT-friendly PEBS 这一高效硬件采样机制。

论文的技术实现展示了扎实的系统工程能力：范围级热度分类巧妙地利用了 guest 虚拟地址空间中的局部性信息；上下文切换导出 PEBS 的设计避免了专用采样线程的开销；双 Balloon 机制在保持 VirtIO 标准兼容性的同时实现了弹性配置。28% 的平均性能提升和 0.2 核心级别的管理开销在云环境中是相当可观的。

不过，作为一篇来自学术团队（CUHK + NYCU）的论文，Demeter 在评估的完整性上仍有提升空间。特别值得关注的是 PageRank 工作负载下 60% 的性能下降未被充分分析，这在工程论文中是一个不应被忽视的异常。总体而言，Guest Delegation 范式为虚拟化分层内存管理提供了一个有价值的新的设计方向。
