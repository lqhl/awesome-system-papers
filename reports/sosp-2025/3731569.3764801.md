# Demeter: A Scalable and Elastic Tiered Memory Solution for Virtualized Cloud via Guest Delegation

## 一、背景

随着云计算基础设施的规模不断扩大，DRAM 的容量扩展速度远落后于 CPU 核心数的增长——过去十年 CPU 核心数增长了 10 倍（15→144），而最大内存容量仅增长约 2.67 倍（1.5→4 TB），每核可用内存下降了约三分之一。为应对这一挑战，Azure、Google、Meta 等主要云厂商开始部署分层内存（Tiered Memory）架构，使用 PMEM 或 CXL.mem 作为慢速内存层（SMEM）来扩展 DRAM 快速内存层（FMEM）的容量。

分层内存管理（TMM）需要完成三个关键步骤：❶ 访问追踪（tracking）、❷ 热度分类（classification）、❸ 数据迁移（migration）。内核级 TMM 已有大量研究（TPP、Memtis、Nomad 等），但虚拟化云环境中的 TMM 主要依赖 hypervisor 层实现，面临严重的性能瓶颈。

---

## 二、要解决的问题

现有 hypervisor-based TMM 方案存在两个根本性问题：

1. **TLB flush 开销巨大**：在 2D 地址翻译（gVA→gPA→hPA）的虚拟化环境中，hypervisor 需要通过重置 PTE.A/D 位来追踪访问热度，这会触发大量代价高昂的 TLB flush。由于 hypervisor 无法获取 gVA 信息，只能使用全量 TLB 失效（invept），导致比 guest-based 方案多 4.7× 的 TLB flush 指令和 2.5× 的执行时间。

2. **无法利用 PEBS 硬件采样**：Processor Event-Based Sampling（PEBS）是内核级 TMM 中已被验证的高效访问追踪机制（如 Memtis），但此前学术界普遍认为 PEBS 无法在虚拟化环境中使用（跨越虚拟化边界）。hypervisor-based 方案因此无法利用这一硬件能力，只能依赖低效的软件扫描。

3. **可扩展性差**：直接将内核级 TMM（如 TPP、Memtis）移植到 guest 内部，随 VM 数量增加会造成大量 CPU 浪费——9 个 VM 场景下 TPP 浪费 4.5 个核，Memtis 浪费 1.25 个核。

---

## 三、洞察与设计

**关键洞察**：❶ 将 TMM 完全委托给 guest 可以避免 hypervisor 层昂贵的 PTE.A/D 扫描和破坏性的 TLB flush；❷ PEBS 在虚拟化环境中实际上是可用且安全隔离的——PEBS v5 修复了此前的 EPT page fault 架构缺陷，PEBS buffer 通过 vmcs.debugctl 字段实现了 VM 间的硬件级隔离；❸ guest 虚拟地址空间（gVA）保留了最完整的空间局部性信息，而物理地址空间的局部性被内核页分配器破坏。

基于以上洞察，Demeter 将 TMM 的三个阶段全部委托给 guest VM，hypervisor 仅负责分层内存的弹性供给（Tiered Memory Provisioning, TMP）。系统架构包含三个核心组件：

### 1. Range-based 热度分类
在 gVA 空间上使用 segment tree 结构，通过迭代式区间分裂识别热点区域。初始化时建立两个大区间（heap 和 mmap 区域），排除代码/数据/栈段。每个 epoch（500ms）收集 PEBS 样本后，检查叶节点是否需要分裂——当某区间访问量显著高于相邻区间时（显著性因子 α = Δaccess / (τ_split · vcpu) > 2），将其二分。最小分裂粒度为 2 MiB。访问计数每 epoch 衰减一半以适应动态变化。

### 2. EPT-friendly PEBS 采样
使用 MEM_TRANS_RETIRED.LOAD_LATENCY 事件（而非传统的 L3 cache miss 事件），通过 MSR_PEBS_LD_LAT_THRESHOLD 寄存器过滤 cache hit（阈值设为 64ns），实现介质无关的访问追踪。采用固定采样频率（1/4093）+ 进程上下文切换时收集样本的方式，消除了专用采样线程和 PMI 中断开销。样本通过 lock-free MPSC channel 送入热度分类器。

### 3. Double Balloon 弹性供给
通过两个 VirtIO balloon（分别对应 FMEM 和 SMEM 层）实现 per-tier 精细控制。利用 NUMA 节点接口向 guest 暴露两个虚拟 NUMA 节点。采用全异步架构（VirtIO + workqueue + epoll），host 保持 QoS 控制能力。

---

## 四、实现细节

- **平台**：基于 Linux KVM hypervisor，guest 端实现为 `demeter.ko` 内核模块
- **Balanced Page Relocation**：采用一对一平衡交换策略——先遍历热区间找到应提升的 SMEM 页（promotion list），再从最冷区间找到等量应降级的 FMEM 页（demotion list），然后批量执行 unmap→swap contents→remap，避免临时页分配和内存回收触发
- **PEBS 配置**：利用 vmcs.debugctl 字段控制 guest-private PEBS buffer，硬件在 VM-entry/exit 时自动切换
- **NUMA 暴露**：通过虚拟化 ACPI 表向 guest 暴露两个 NUMA 节点，用 NUMA distance 传递层级性能差异
- **Balloon 通信**：VirtIO 队列 + eventfd + epoll，host 发送 inflate/deflate 请求，guest 异步执行并回报页地址
- **代码开源**：已在 Zenodo 公开发布

## 五、实验结果

### 实验平台
- 36 核系统，36 GiB DRAM + 无限 PMEM（或模拟 CXL.mem）
- 最多 9 个并发 VM，每 VM 分配等量资源

### 关键指标

| 对比维度 | Demeter vs. 竞争方案 |
|---------|---------------------|
| 访问追踪开销（CPU） | 0.64% vs. PTE.A/D 3.08% vs. PML 14.61% |
| 采样收集 CPU 时间 | 3s vs. Memtis 49s（16× 降低） |
| TLB flush 次数 | 9.3M vs. TPP-H 62.3M（6.7× 降低），无全量 flush |
| 可扩展性（9 VM） | 稳定在 0.2 核以内 |

### 真实工作负载性能（DRAM+PMEM，9 VM）

| 工作负载 | vs. TPP | vs. Memtis | vs. Nomad | vs. TPP-H |
|---------|---------|-----------|----------|----------|
| btree | +10% | +10% | +10% | +10% |
| bwaves | +10% | +10% | +20% | +10% |
| graph500 | +10% | +100%+ | +100%+ | -— |
| liblinear | +60% | +20% | +140%+ | +20% |
| pagerank | -— | +100%+ | +260%+ | -60% |
| silo | +60% | +60%+ | +400%+ | +100%+ |
| xsbench | +40% | +40%+ | +560%+ | +20% |

- **整体**：vs. hypervisor-based (TPP-H) 平均提升 16%（几何平均）；vs. 次优 guest-based (TPP) 平均提升 28%
- **尾延迟**：Silo P99 延迟降低 23%
- **CXL.mem 场景**：在有明确热点的工作负载上保持 10%+ 优势

## 六、批判性分析

1. **PageRank 场景的明显劣势**：Demeter 在 PageRank 上比 TPP-H 慢 60%，这是一个显著的退步。论文将此归因于 power-law 访问模式下热冷数据的细粒度交错，但未深入分析为何 range-based 分类在这种场景下表现特别差，也未提出针对性的改进方案。这暴露了 range-based 方法对空间局部性强假设的脆弱性。

2. **CXL.mem 评估使用模拟而非真实硬件**：虽然论文声称支持 CXL.mem，但实验使用的是远端 NUMA 内存模拟，而非真实 CXL 设备。真实 CXL 设备的延迟特性、带宽波动和一致性协议开销可能与 NUMA 模拟存在显著差异。

3. **固定参数的普适性存疑**：虽然灵敏度分析显示参数在一定范围内稳定，但所有评估都使用相同的参数组合（epoch=500ms, α=2, τ_split=15, sample period=4093, latency threshold=64ns）。在生产环境中不同硬件配置、不同负载混合下，这些参数是否仍然有效值得质疑。论文建议"管理员根据负载特征微调"，实际上将调参复杂度转嫁给了用户。

4. **QoS 策略未实现**：论文声称 Demeter 支持 QoS 控制，但实际上 QoS 策略的设计被标注为"future exploration"。实验中所有 VM 使用固定的 FMEM/SMEM 比例，完全没有验证多租户场景下的公平性和优先级管理。

5. **安全分析比较表面**：论文声称 guest 代码被视为不可信，但 guest 可以通过伪造统计信息或恶意 balloon 操作影响 host 的资源分配决策。虽然提到了 "token-bucket rate limiter" 作为缓解措施，但这只是一个建议，并未实现和验证。

6. **与内核级 TMM 的对比不完整**：论文的核心对比基准 TPP-H 是作者自行实现的 hypervisor 版本（因现有方案无公开代码），其实现质量和优化程度存疑。vTMM 等系统仅通过间接方式评估了访问追踪原语，未进行端到端对比。

## 七、AI Infra / MLSys 视角

1. **LLM 推理的 KV Cache 分层管理**：Demeter 的 range-based 热度分类思路可直接应用于 LLM 推理中的 KV cache 管理。当 KV cache 超出 GPU 显存时，可借鉴 guest delegation 思路让推理引擎（而非系统层）根据 attention pattern 的局部性信息自主决定哪些 KV cache 放在 GPU HBM、哪些放在 CPU DRAM 或 CXL 内存。

2. **分布式训练的内存弹性**：Demeter 的 double balloon 弹性供给机制启发了分布式训练中的动态内存管理。训练任务在不同阶段（forward/backward/optimizer step）的内存需求差异显著，可借鉴类似的弹性机制实现训练节点间的内存借贷。

3. **CXL 内存池化场景下的 TMM**：随着 CXL 3.0 内存池化的发展，多租户共享 CXL 内存池的场景会越来越普遍。Demeter 的"管理权委托给消费者"这一设计哲学在内存池化场景下更有价值——让每个 GPU 或加速器节点自主管理其分配到的分层内存，避免集中式管理的瓶颈。

4. **可操作的研究方向**：
   - 将 EPT-friendly PEBS 技术应用于 GPU 虚拟化场景中的显存-主存分层管理
   - 结合 workload profiling（如 LLM 的 layer-wise access pattern）设计自适应参数调优策略，取代当前的静态配置
   - 探索 range-based 分类在 graph-structured 数据（如 GNN 训练）上的改进，解决 power-law 分布下的性能退化问题

---

## 八、总结

Demeter 提出了虚拟化环境中分层内存管理的"guest delegation"范式，将 TMM 的全部三个阶段委托给 guest VM，hypervisor 仅负责弹性供给。其核心贡献包括：发现并利用了 EPT-friendly PEBS 在虚拟化环境中的可用性和隔离性、设计了基于 gVA 空间的 range-based 热度分类以保留空间局部性、以及通过 double balloon 实现弹性供给。在 7 个真实负载上比 hypervisor-based 方案提升最高 2×、比次优 guest-based 方案平均提升 28%。主要局限在于对空间局部性较弱的工作负载（如图计算 PageRank）效果不佳，以及 QoS 策略和安全防护尚未在生产级别验证。
