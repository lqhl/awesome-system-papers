## 一、背景

WebAssembly (Wasm) 是一种可移植的低级字节码格式，最初用于在浏览器中安全高效地执行 C/C++/Rust 等语言编写的程序。由于其沙箱执行、内存安全和接近原生的性能等特性，Wasm 已被推广到浏览器之外的众多领域，包括机器学习、边缘计算、IoT、区块链和高性能计算等。美国联邦政府近期也推动云原生服务采用 Wasm 以提升安全性。

WebAssembly System Interface (WASI) 是使 Wasm 代码在浏览器外运行的关键接口，类似于系统调用，它为 Wasm 程序提供访问文件、时钟、网络连接等系统资源的能力。WASI 已在大多数主流独立 Wasm 运行时中实现，是 Wasm 生态系统扩展的基石。

然而，正确实现 WASI 非常困难：WASI 函数语义复杂、规范描述模糊且不完整；实现高度依赖宿主 OS 内核，不同平台间存在语义差异；WASI 仍处于快速演进阶段，版本频繁更新。WASI 实现中的缺陷可导致数据损坏、沙箱逃逸等严重安全问题（如 CVE-2024-38358、CVE-2024-51745）。

## 二、要解决的问题

现有 Wasm 运行时测试工具（wasm-smith、WASMaker、WADIFF）主要针对 Wasm 指令层面，几乎不涉及 WASI 函数。专门测试 WASI 的工具（DrWASI、Wasix）也存在明显不足：

1. **无法探索深层系统状态**：DrWASI 生成的测试用例仅包含简单、孤立的 WASI 函数调用，无法通过一系列有依赖关系的调用到达深层系统状态。传统灰盒测试（如 AFL）不理解 WASI 函数间的语义关系（依赖、前置条件、资源生命周期），只能盲目探索输入空间。白盒分析因 Wasm 运行时语言多样性（C、C++、Rust、Go、Java、Swift）而不可行。

2. **无法避免误报和已知 bug**：差异测试中，不同运行时的 WASI 支持程度不同、规范存在 under-specified 和 implementation-defined 行为，导致大量误报。已发现但尚未修复的 bug 会反复触发，浪费测试周期。现有工具没有机制来过滤这些情况。

3. **无法适应 WASI 的快速演进**：现有框架（如 syzkaller）的核心控制逻辑与测试用例生成紧耦合，难以跟上 WASI 频繁的版本更新和提案变更。

## 三、洞察与设计

**关键洞察**：WASI 函数的行为可以通过对系统资源（如文件描述符、socket）的抽象建模和实时追踪来理解，而无需访问或分析具体的 WASI 实现代码。通过在 WASI 规范上添加轻量级语义标注（资源类型、输入约束、输出效果），就能自动生成有依赖关系的、语义丰富的 WASI 函数调用序列，探索深层系统状态。

基于此洞察，WASIT 的设计包含三个核心阶段：

**阶段一：规范增强（Specification Augmentation）**
- 设计了一种领域特定语言（DSL），与 WASI 原有的 witx 接口描述语言兼容
- 通过 `@resource` 标注将基础数据类型提升为资源类型（如文件描述符带有 offset、flags 等属性）
- 通过 `@input` 标注定义函数的输入约束（用量词无关的一阶逻辑布尔表达式表示）
- 通过 `@output` 标注描述函数执行后的资源状态变更

**阶段二：资源抽象与追踪（Resource Abstraction and Tracking）**
- 维护一个全局抽象系统状态，包含所有活跃的系统资源
- 为每个运行时维护独立的资源上下文，通过 lowering（抽象→具体）和 lifting（具体→抽象）操作隐藏不同运行时间的差异（如文件描述符的实际整数值不同）
- 函数执行后根据输出效果更新抽象状态

**阶段三：约束编码与求解（Constraint Encoding and Solving）**
- 使用 SMT 求解器自动化函数调用生成和状态转换
- 输入约束编码器：将输入约束转为 SMT 公式，通过 eager instantiation 将资源引用转为对当前活跃资源的隐式量词，确保可判定性
- 通过多次求解（加入 blocking clause）生成多样化的参数值
- 输出约束编码器：根据执行结果求解资源更新

**解耦架构**：核心控制逻辑与 WASI 函数调用生成分离，使得 WASI 规范更新时只需修改标注而非框架代码。

## 四、实现细节

- 约 6.7k 行 Rust 代码实现主体框架（含 DSL），外加一个 C 语言编写的 WASI 函数执行器
- 基于 WASI specification version 0.1（preview1），官方规范 1301 行 s-expression 代码，手动添加约 170 行 DSL 标注
- WASI 函数执行器以 RPC agent 的形式嵌入每个 Wasm 运行时内部

关键实现细节：
- **初始状态归一化**：不同运行时的初始沙箱状态不同（如 Wasmer 以虚拟文件系统根开始，其他运行时可能预开多个目录），WASIT 通过 runtime-tailored 的重配置将其对齐
- **处理不完整执行**：某些 WASI 函数可能部分执行后就返回（如 fd_write 只写入部分数据），执行器会透明地重试直到完成，并聚合中间结果
- **执行结果交叉检查**：
  - 非确定性结果（如时钟）只检查完成一致性，不比较具体值
  - 隐式结果通过对每个运行时沙箱文件系统快照的递归遍历和比较来检测

## 五、实验结果

测试了 6 个主流 Wasm 运行时：

|--------|------|------|-------------|-------------------|---------|-------------|
| Node.js | 20.18.0 | C | 691 | 5 | 6 | 111k |
| WAMR | 1.2.3 | C | 127 | 8 | 6 | 5.3k |
| WasmEdge | 0.13.3 | C++ | 97 | 16 | 6 | 9.1k |
| Wasmer | 4.2.4 | Rust | 177 | 27 | 7 | 19.6k |
| Wasmtime | 30.0.0 | Rust | 456 | 41 | 8 | 16.2k |
| Wazero | 1.5.0 | Go | 152 | 11 | 5 | 5.3k |

**Bug 发现**：4 个月间歇性测试，发现 48 个新 WASI 特有 bug：
- 41 个已确认，37 个已修复，3 个 CVE（含 Wasmer 沙箱逃逸和 WAMR 沙箱逃逸）
- 15 个 bug 潜伏超过 4 年（如 WAMR 的 CVE 自 v1.0 起就存在）
- Bug 涵盖所有 6 个运行时，跨 Linux/macOS/Windows 三个平台
- 23 个 bug 在 3 天内修复，6 个在数小时内修复

## 六、批判性分析

1. **误报实验的公平性问题**：10 分钟的对比实验中，WASIT 仅生成 1 条调用序列而其他工具生成了数千条。这个时间窗口对 WASIT 极为有利——它在短时间内什么也没发现（包括 bug），而其他工具因为快速生成大量浅层调用而暴露了它们在误报处理上的弱点。如果延长测试时间，WASIT 的误报率是否仍为 0% 值得怀疑。

2. **标注工作量被低估**：论文声称标注规范只需约 10 person-hours 且仅 170 行 DSL 代码，但这不包括 bug 分流和与开发者讨论的时间。在实际使用中，每发现一类新的误报或规范歧义，都需要人工分析并编写新的约束，这是一个持续的人力成本。论文没有充分讨论这种 on-going maintenance 的负担。

3. **仅针对 WASI 0.1**：实现基于 WASI preview1，而 WASI 0.2 已经发布。论文强调 WASIT 的解耦架构使其容易适应新版本，但没有提供任何适配 WASI 0.2 的实际证据。考虑到 WASI 0.2 引入了全新的 Component Model，适配难度可能远超论文所暗示的。

4. **覆盖率测量时间过短**：仅测试 100 分钟就因磁盘空间不足停止，这个理由显得不够严谨。覆盖率随时间的增长曲线（是否存在饱和）才是更有意义的指标，但论文未提供。

5. **资源深度指标的实际意义不明确**：WASIT 达到了 1310 的最大资源深度，但论文没有分析这些极深的调用序列中有多少比例实际发现了 bug。如果绝大多数深层调用只是"合法但无趣"的序列，那么追求极致深度的价值有限。

6. **差异测试的固有局限被轻描淡写**：差异测试要求至少有一个"正确"的实现作为 oracle，但当所有运行时对某一 under-specified 行为都做出相同的错误假设时，WASIT 无法发现这类共性 bug。论文几乎没有讨论这一根本性局限。

---

## 七、总结

WASIT 是首个面向 WASI 实现的规范驱动差异测试框架，通过三项创新——动态资源抽象与追踪、规范增强 DSL、解耦系统架构——解决了深层状态探索、误报过滤和快速演进适配三大挑战。在 6 个主流 Wasm 运行时中发现 48 个新 bug（含 3 个 CVE），其中多个为存在数年的深层语义 bug，验证了方法的有效性。其核心技术（轻量级资源建模 + SMT 约束求解 + 差异测试）可推广到其他资源中心的 API 测试场景。主要局限在于仅支持 WASI 0.1、需要持续的人工标注维护、以及差异测试对共性 bug 的盲区。
