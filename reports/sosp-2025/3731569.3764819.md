# WASIT: Deep and Continuous Differential Testing of WebAssembly System Interface Implementations

## 论文基本信息
- **标题**: WASIT: Deep and Continuous Differential Testing of WebAssembly System Interface Implementations
- **作者**: Yage Hu, Wen Zhang, Botang Xiao, Qingchen Kong, Boyang Yi, Suxin Ji, Songlan Wang, and Wenwen Wang
- **会议**: SOSP 2025
- **Session**: Bugs
- **PDF**: 3731569.3764819.pdf

## 研究背景

WebAssembly（Wasm）最初作为浏览器中的沙箱执行技术出现，但其特性——沙箱隔离、内存安全、近原生性能——使其在浏览器之外的应用场景（边缘计算、物联网、区块链、高性能计算等）中获得了广泛应用。WASI（WebAssembly System Interface）是 Wasm 访问系统服务的关键接口，定义了 Wasm 程序访问文件、时钟、网络连接等系统资源的函数规范。

随着 WASI 在各运行时（Node.js、WAMR、WasmEdge、Wasmer、Wasmtime、Wazero）中的广泛实现，以及 WASI 规范本身的快速演进（32 个活跃提案，6 个月内发布 3 个版本），WASI 实现的正确性面临严峻挑战。WASI 实现 bug 可能导致文件损坏、 sandbox escape 等严重后果。然而，WASI 固有的复杂性（函数行为依赖系统状态、规范仅提供模糊描述、多样化的实现生态系统）使得传统测试方法难以有效应对。

## 要解决的问题

1. **深层系统状态探索**：WASI 函数之间存在复杂的资源和数据依赖关系（如 path_open 返回 fd 后，fd_read/fd_write 才能使用），如何生成深层、有效的 WASI 函数调用序列？
2. **误报过滤**：Differential testing 在多个实现间比较时，由于实现成熟度不同，未实现的功能会被误报为 bug。如何过滤这些无意义的差异？
3. **规范快速演进**：WASI 规范频繁更新，如何让测试框架平滑地适应这些变化，而无需大规模重写？

## 核心贡献

- **首个 specification-driven differential testing 框架**：通过增强 WASI 规范（添加资源类型提升、输入约束和输出效果注释），实现深层的、有效的 WASI 函数调用生成
- **实时资源抽象与追踪**：提出动态资源抽象和追踪机制，使测试框架能够理解 WASI 函数之间的资源依赖关系，生成有意义的调用序列
- **领域特定语言**：设计了用于规范增强的 DSL，可以过滤无意义参数值和已知的 bug，避免浪费测试资源
- **解耦架构**：将测试控制逻辑与 WASI 函数调用生成分离，确保框架能够平滑地适应 WASI 规范的快速演进
- **发现 48 个新 bug**：在 6 个主流 Wasm 运行时中发现 48 个 WASI 特定 bug，41 个已确认，37 个已修复，3 个已分配 CVE

## 主要研究方法

### 实时资源抽象与追踪

**资源类型系统**：将 WASI 规范中原生的简单 handle 类型"提升"为带属性的资源类型。例如，`$fd`（文件描述符句柄）被提升为包含 offset、flags、type、path 等字段的结构化资源类型。这使得 WASIT 能够理解文件描述符的语义属性。

**抽象系统状态**：维护一个跨所有 Wasm 运行时共享的抽象系统状态，包括当前可用的资源（如已打开的文件描述符、网络 socket）及其属性。这个状态在每个 WASI 函数调用后根据输出效果更新。

**资源上下文**：每个运行时维护自己的资源上下文（resource context），记录从全局抽象资源到具体本地值的映射。Lift/Lower 操作在抽象资源引用和具体运行时值之间进行转换，从而隐藏不同运行时之间的无害差异（如文件描述符编号不同）。

### 领域特定语言（DSL）

**资源类型提升语法**：`@resource` 注解允许声明新的资源类型及其字段：
```
(typename $fd (handle)
  + (@resource (record
    + (field $offset $filesize)
    + (field $flags $fdflags)
    + (field $type $filetype)
    + (field $path string))))
```

**输入约束语法**：`@input` 注解定义函数的有效调用条件，使用一阶逻辑表达式：
```
(@input (@and
  (@value.eq (@record.field (param $fd) $type)
              (@variant.const $filetype $regular_file))
  ...))
```

**输出效果语法**：`@output` 注解定义函数的副作用，用于更新抽象系统状态：
```
(@output (@value.eq
  (@int.const (@record.field (param $fd') $offset))
  (@int.const (result $ok))))
```

### SMT 约束求解

将输入约束编码为 SMT 公式，使用 Z3 求解器查找满足约束的参数值。如果约束不可满足，则跳过该函数调用。对于可满足的情况，随机选择一个满足实例来准备调用。

### 解耦架构

将测试框架分为两层：
- **Spec Layer**：规范增强、约束编码、SMT 求解
- **Execution Layer**：WASI 函数执行、跨运行时比较、反馈收集

两层之间通过明确定义的接口通信，使得对 WASI 规范的更新主要影响 Spec Layer，Execution Layer 保持稳定。

## 主要实验结果

**Bug 发现**（4 个月间歇性测试）：
- 6 个运行时共发现 48 个 WASI 特定 bug
- 41 个已确认，37 个已修复，3 个 CVE
- 涉及 fd_pwrite、path_open、fd_seek、fd_filestat_set_times 等多个函数
- 涵盖 macOS、Linux、Windows 三个平台
- 15/37 个已修复 bug 在运行时中潜伏超过 4 年

**深度状态探索**：
- WASIT 能在超过 50% 的测试运行中生成超过 100 个依赖的 WASI 函数调用序列
- 最长序列达到 tens of thousands 个调用
- 相比之下，Wasix（无状态随机生成）仅生成最多 5 个调用的序列

**代码覆盖率**：
- WASIT 在所有 Wasm 运行时中实现最高代码覆盖率
- Node.js: 1216 vs WASIT-syzkaller 1204
- WAMR: 403 vs WASIT-syzkaller 385
- WasmEdge: 490 vs WASIT-syzkaller 438
- Wasmtime: 156 vs WASIT-syzkaller 153

**误报率**：
- 10 分钟对比测试：Wasix/DrWASI/WASIT-syzkaller 报告的 inconsistencies 100% 是误报（1620/715/1662 个），而 WASIT 为 0 个
- 论文共手工添加约 170 行 DSL 注解来消除这些误报

## 潜在问题 / 局限性

1. **手工规范增强的工作量**：虽然论文声称"manageable"（约 170 行 DSL 注解），但 WASI 有 32 个活跃提案和 3 个主要版本。对于持续演进的规范，维护这些注解的成本可能快速累积。论文未提供注解随规范演进的更新频率数据。

2. **跨平台差异的系统性**：WASI 实现中的 bug 有相当一部分源于不同 host OS 平台（Linux、macOS、Windows）之间的行为差异。WASIT 目前通过 per-runtime/per-platform 资源上下文来处理这些差异，但这种方案的扩展性如何？当测试的运行时和平台组合增加时，注解数量是否线性增长？

3. **SMT 求解的可扩展性**：使用 Z3 求解输入约束和输出效果更新。论文未讨论在超长 WASI 调用序列（tens of thousands）时 SMT 求解的性能表现。随着序列增长，约束数量增加，求解时间可能成为瓶颈。

4. **Differential Testing 的根本局限**：Differential testing 只能发现多个实现之间的不一致，无法发现所有实现共同犯错的 bug（即"wrong consensus"问题）。如果所有 Wasm 运行时都错误地实现了某个 WASI 函数行为，WASIT 无法检测。

5. **与 DrWASI/Wasix 比较的可信度**：论文在多个对比实验中声称 DrWASI 和 Wasix 的结果是 100% 误报（0 个真 bug）。但 DrWASI 和 Wasix 是否被正确配置和运行？作者承认 DrWASI 无法适配 Node.js，这可能表明这些工具的配置需要特殊适配，而 WASIT 本身是专门为 WASI 设计的。

6. **SMT solver 的 soundness**：使用 Z3 编码 WASI 语义，如果 Z3 在某些边界情况下返回错误的 sat/unsat 结果，可能导致假阳性或假阴性。论文未讨论这种风险。

7. **规范本身可能包含错误**：如果被增强的 WASI 规范本身包含错误，那么测试可能无法发现这些错误导致的 bug。这引出了一个根本问题：规范的正确性由谁来保证？

## 未来工作

1. 开发自动化或半自动化的规范增强注解生成，减少手工工程投入
2. 将 WASIT 的方法扩展到其他资源中心化的 API（如 POSIX 系统调用、Docker API）
3. 开发自动化的规范一致性检查，确保注解与规范的一致性
4. 处理"wrong consensus"问题：通过参考实现或形式化规范来检测所有实现共同的错误

## 个人评注

WASIT 解决了一个极具挑战性的测试问题：具有深层状态依赖、快速演进规范和多实现生态的系统接口。三个技术创新——实时资源抽象、DSL 注解过滤、解耦架构——形成了一个完整的解决方案。特别是实时资源抽象，使得测试能够生成深层、有效的 WASI 调用序列（50% 的运行超过 100 个调用），这是其他方法无法企及的。

最令人印象深刻的是误报控制。Wasix/DrWASI/WASIT-syzkaller 的 100% 误报率是一个强有力的对比，证明了规范增强的必要性：没有语义理解，Differential testing 产生的大量"不一致"其实都是无意义的噪音。这不仅是技术问题，更是方法论问题——它告诉我们，在进行 differential testing 时，必须理解被测系统，而不是盲目地生成调用。

48 个 bug 的发现（37 个已修复，3 个 CVE）和 15 个 bug 潜伏超过 4 年的发现，有力地证明了 WASI 实现生态的成熟度差异和测试的必要性。特别值得注意的是，许多 bug 涉及 sandbox escape（绝对路径绕过、符号链接逃逸），这类 bug 直接威胁 Wasm 的安全隔离保证，其严重性不言而喻。
