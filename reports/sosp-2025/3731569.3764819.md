## 一、背景

WebAssembly（Wasm）是一种可移植的低级字节码格式，最初为在 Web 浏览器中安全高效地运行 C/C++/Rust 代码而设计。凭借沙箱执行、内存安全、接近原生性能等特性，Wasm 已被推广到浏览器之外的场景：机器学习（ONNX Runtime Web、TensorFlow.js）、边缘计算、物联网、区块链，乃至高性能计算。美国联邦政府也推动云原生服务采用 Wasm 以提升安全性。

由于 Wasm 本身不提供系统服务访问能力，**WASI（WebAssembly System Interface）** 成为 Wasm 程序在浏览器外运行的关键使能技术。WASI 类似 POSIX 系统调用，定义了一组函数让 Wasm 程序访问文件、时钟、网络等系统资源。各主流 Wasm 运行时（Node.js、Wasmtime、WAMR、Wasmer、WasmEdge、Wazero）均实现了 WASI 支持。

然而 WASI 实现中的缺陷会导致数据损坏、可靠性下降，甚至沙箱逃逸等严重安全漏洞（如 CVE-2024-38358、CVE-2024-51745）。随着 WASI 在安全关键应用中的普及，测试 WASI 实现的正确性变得日益紧迫。

---

## 二、要解决的问题

现有 Wasm 运行时测试方案存在三类核心不足：

**1. 无法探索深层系统状态。** wasm-smith、WADIFF、WASMaker 主要针对 Wasm 指令，几乎不涉及 WASI 函数；DrWASI 和 Wasix 虽针对 WASI，但生成的调用序列简单孤立（资源深度为 1），无法测试多个依赖 WASI 函数调用下的深层语义问题。灰盒模糊测试对 WASI 函数间复杂语义关系（函数依赖、操作前置条件、共享资源生命周期）视而不见。白盒静态/动态分析则因 Wasm 运行时实现语言多样（C/C++/Rust/Go/Java/Swift）而难以规模化应用。

**2. 大量误报导致测试难以持续。** 不同运行时 WASI 实现成熟度不同、规范故意欠规定、行为实现定义各异，差异化测试（differential testing）会产生大量虚假不一致。已发现但尚未修复的 bug 会被反复触发，浪费测试资源，也加重人工分类负担。现有工具对此毫无机制。

**3. WASI 快速演化导致测试框架维护困难。** 现有工具（如 syzkaller 系）将核心控制逻辑与测试用例生成代码紧耦合，WASI 规范每次更新都需大量重构。WASI 目前有 32 个活跃提案，仅过去六个月就发布了三个版本。

## 三、核心设计

WASIT 是首个面向 WASI 实现的规范驱动差异化测试框架，包含三个核心技术：

### 3.1 规范增广（Specification Augmentation）

WASIT 设计了一套与原始 WASI 规范描述语言（witx，一种接口描述语言）兼容的领域特定语言（DSL），用于向 WASI 规范添加三类语义标注：

- **`@resource` 资源类型标注**：将 WASI 基础数据类型（如 `handle`）提升为带结构字段的资源类型（如文件描述符资源，含 offset、flags、filetype、path 等字段），使 WASIT 能够识别和追踪系统资源。
- **`@input` 输入约束标注**：以量词自由的一阶逻辑布尔表达式描述 WASI 函数的调用前置条件，过滤无效参数值（如调用 `fd_seek()` 要求 `$fd` 指向普通文件而非目录）。通过对活跃资源的隐式量词 eager instantiation 避免引入显式量词，保证约束可判定可求解。
- **`@output` 输出效果标注**：描述 WASI 函数执行后对系统资源状态的修改（如 `fd_seek()` 执行后更新文件描述符的 offset 字段）。

整个规范增广工程量约 170 行 DSL 代码，人工标注耗时约 10 人时。

### 3.2 实时资源抽象与追踪（Real-time Resource Abstraction and Tracking）

WASIT 维护一个跨所有被测运行时共享的**全局抽象系统状态**，记录当前所有活跃系统资源（文件描述符、网络 socket 等）及其状态。

为屏蔽不同运行时间具体值的无害差异（如文件描述符整数值不同），WASIT 为每个运行时单独维护一个**资源上下文（resource context）**，记录全局抽象资源与本地具体值的映射关系，并通过两步操作实现转换：
- **Lowering**（下沉）：函数调用前，将抽象资源引用映射为各运行时对应的具体值；
- **Lifting**（上浮）：函数调用后，将具体值映射回抽象资源，更新全局状态。

### 3.3 约束编码与求解（Constraint Encoding and Solving）

WASIT 使用 SMT 求解器自动化测试用例生成和状态转移，包含两个编码器：

- **输入约束编码器**：将当前系统状态和函数输入要求转换为 SMT 公式。对所有可调用函数检查输入约束的可满足性，形成候选函数集；然后通过多次求解（每次加入 blocking clause）生成多样化参数值；
- **输出约束编码器**：将函数输出效果与执行结果转换为 SMT 公式，求解后更新抽象系统状态。

### 3.4 解耦系统架构

WASIT 将核心控制逻辑（测试策略）与 WASI 函数调用的具体生成解耦，使 WASI 规范更新时只需修改 DSL 标注，无需改动核心代码，实现与 WASI 的平滑共同演化。

## 四、实现细节

- **代码规模**：约 6,700 行 Rust 代码（核心测试框架 + DSL 实现）+ C 语言编写的 WASI 函数执行器；
- **WASI 版本**：基于 WASI 规范 0.1（preview1），官方规范共 1,301 行 s-expression 代码，手动添加约 170 行 DSL 标注；
- **执行器架构**：WASI 函数执行器作为 RPC agent 部署在每个被测运行时内部，透明地重试部分执行的 WASI 函数（如 `fd_write()` 因宿主信号中断时）并聚合中间结果；
- **初始状态对齐**：测试开始前对各运行时的初始沙箱状态进行 runtime-tailored 重配置，确保起点一致；
- **执行结果比对**：对非确定性返回值（如 `clock_gettime()`）只比较是否一致完成，不比较具体数值；每次 WASI 函数调用后快照沙箱文件系统，通过递归比对检测文件系统静默差异；
- **测试平台**：Linux（Intel Xeon E5-2697v3，200GB 内存）、Windows 11（Intel Core i7-10700KF，64GB 内存）、macOS 15.4（Intel Core i9，32GB 内存）。

## 五、实验结果

### 5.1 Bug 发现（4 个月间歇性测试）

在 6 个主流 Wasm 运行时中发现 **48 个新的 WASI 实现 bug**：

| 状态 | 数量 |
|------|------|
| 已确认并修复 | 37（多数附带 patch） |
| 已确认但未修复（复杂度高） | 5 |
| Won't Fix（语义理解分歧） | 4 |
| 待确认 | 1 |
| 分配 CVE | 3 |

- 每个被测运行时均有 bug，其中 15/37 已修复 bug 已在运行时中潜伏超过 4 年；
- 37 个已修复 bug 中，23 个在 3 天内修复，6 个在数小时内修复；
- Bug 涵盖三大操作系统平台（Linux/macOS/Windows），体现了跨平台 WASI 实现的一致性挑战。

典型案例：
- **Wasmtime 文件内容损坏 bug**：`path_open(append) → fd_write() → fd_tell()` 返回错误 offset → `fd_pwrite()` 覆写错误位置，根本原因是 Wasmtime 虚拟文件系统层未及时更新文件描述符偏移的内部数据结构；
- **Wazero 文件描述符 offset 重置 bug**：`fd_fdstat_set_flags()` 设置 append flag 时触发文件重新打开，但未正确恢复之前的 offset；
- **Wasmer 沙箱逃逸（CVE）**：`path_open()` 可创建沙箱外文件、symlink 可绕过文件系统沙箱。

### 5.2 深层状态探索能力

| 工具 | 平均资源深度 | 最大资源深度 |

## 六、批判性分析

**1. 仅支持 WASI 0.1，错过了更新版本。** 论文明确表示因实现时 WASI 0.2 尚未稳定而仅支持 0.1，但 0.2 已于近期发布，且 WASI 生态正在快速迁移。文中"平滑共同演化"的解耦架构优势并未在实际 0.1→0.2 迁移中得到验证，说服力存疑。

**2. 规范标注的维护成本被低估。** "约 10 人时完成标注"是初次标注的成本，但随 WASI 持续演化（32 个活跃提案）的持续维护成本几乎没有讨论。论文声称"只需修改标注而无需改动代码"，但未给出实际迁移实例或量化数据。

**3. 误报率对比存在方法论不对等。** Table 5 的对比实验中，WASIT 使用了预先标注好约束的增广规范，而 Wasix/DrWASI 没有等效的过滤机制——这是系统设计差异，而非可直接比较的对等基线。对比结论（0% vs 100%误报）更多反映设计哲学不同，而非能力上的绝对优势。

**4. 代码覆盖率实验受资源限制而截断。** Table 3 仅测试 100 分钟，原因是"覆盖率文件太大撑满磁盘"，这是硬件资源问题而非合理的实验设计截断点。长时间运行下覆盖率优势是否持续扩大、是否存在饱和点，完全未知。

**5. "Won't Fix"类 bug 的语义分歧被轻描淡写。** 4 个 Won't Fix 的 bug（涉及 append flag 的写偏移行为、绝对路径验证等），本质上反映了 WASI 规范欠规定导致各运行时合理分歧——而这恰恰是论文立论的核心挑战。这些 bug 在差异化测试框架下的定性（"bug"还是"实现选择"）缺乏深入讨论。

**6. 差异化测试的内在局限未充分讨论。** 当所有被测运行时都有相同错误实现时，差异化测试无法发现 bug。考虑到多个运行时共享的 wasi-sdk 工具链及相似的 POSIX 语义实现路径，存在共同盲点的可能性没有被评估。

---

## 七、总结

WASIT 是首个规范驱动的 WASI 实现差异化测试框架，通过实时资源抽象与追踪、SMT 约束求解和解耦架构三项创新，解决了深层系统状态探索不足、误报泛滥、框架难以维护等长期难题。在 6 个主流 Wasm 运行时上发现 48 个新 bug（含 3 个 CVE），其中多个漏洞已潜伏 4 年以上。主要局限在于目前仅支持 WASI 0.1 且规范持续演化的维护成本尚待实践检验；差异化测试方法固有的无法发现共同错误实现的盲点也值得关注。该框架的设计思路对其他资源中心型 API（POSIX 系统调用、各类运行时接口）的测试具有直接借鉴价值。
