# Pesto: Cooking up High Performance BFT Queries

## 论文基本信息
- **标题**: Pesto: Cooking up High Performance BFT Queries
- **作者**: Florian Suri-Payer, Neil Giridharan, Liam Arzola, Shir Cohen, Lorenzo Alvisi, Natacha Crooks (Cornell University, UC Berkeley, UCSD)
- **会议**: SOSP 2025
- **Session**: Storage and Databases
- **PDF**: 3731569.3764799.pdf

## 研究背景

拜占庭容错（BFT）数据库为分布式存储提供了应对恶意攻击和硬件故障的能力，但现有 BFT 数据库面临严重的性能瓶颈。

**SMR（State Machine Replication）分层设计的低效**。最常见的设计模式是将数据库功能分层叠加在 BFT 共识之上（SMR-based BFT），但这导致了两个核心问题：
1. 共识层需要对**所有**操作进行全序排列，即使这些操作本身不冲突——这放弃了工作负载固有的并行性
2. 对于范围查询（range query），必须（至少在逻辑上）锁定相关键的范围——导致高 abort 率和低吞吐

**Basil 的开创性工作**。Basil 是一个无序（order-free）的 BFT KV-store，它将并发控制、两阶段提交和复制整合为单一低延迟层。事务由客户端管理执行，GET 操作从 quorum 获取带 Commit-Proof 的响应，PUT 操作通过高效的两次提交协议完成。然而 Basil 存在根本局限：**仅支持 GET 操作**——复杂的分析查询必须被重新改写，这增加了开发者负担，且对于涉及中间结果大小的查询，协调成本与中间结果大小成正比。

## 要解决的问题

如何在 BFT 数据库中高效支持 **完整 SQL**（包括范围查询、JOIN、聚合等复杂查询），同时保持 Byzantine 容错的安全保证？

核心挑战在于：
1. **范围查询的并发控制**：传统 OCC 协议需要对查询涉及的所有键加锁，导致高 abort 率
2. **正确性 + 并行性的平衡**：完整顺序执行保证正确性但失去并行性；而宽松的一致性模型又不满足实际需求

## 核心贡献

- **Pesto**：首个支持完整 SQL 的高性能 BFT 数据库，提供完整 TPC-C、AuctionMark、SEATS 支持
- **客户端驱动的快照协议**：确保查询结果在参与副本间一致，无需对所有操作全序
- **谓词乐观并发控制**：借鉴 precision lock 的洞察——一致性仅需针对查询的特定谓词，而非整个数据库
- **性能追赶无复制系统**：TPC-C 吞吐追平 Peloton 和 PostgreSQL，比传统 SMR-BFT 设计快 **2.3 倍**

## 主要研究方法

作者首先分析了 SMR-based BFT 设计的根本低效来源，然后借鉴 Basil 的 order-free 思路，将其扩展到支持 SQL 查询。关键洞察是：**查询时，一致性仅需针对该查询的特定谓词**，而非整个数据库。

## 设计与实现

### 关键洞察：谓词级一致性

与 Basil 类似，Pesto 不对所有操作进行全序，但 Basil 的关键局限在于对 GET 操作的"谓词锁"扩展——它需要对查询谓词覆盖的所有键进行逻辑锁定。Pesto 的核心创新在于：它不需要锁定读取状态本身，只需确保查询结果的一致性。

### 客户端驱动的快照协议

当客户端执行查询时：
1. **检查是否需要协调**：客户端向副本发送查询请求
2. **被动验证**：大多数情况下，副本的回复已经是相互一致的，无需额外协调
3. **主动解决**：当回复不一致时，客户端动态地在相关副本间建立共同快照

### 谓词乐观并发控制

受 precision lock 启发，Pesto 提出了一种新颖的乐观谓词检查：
- 仅中止违反查询语义的并发事务，而非所有并发事务
- 将一致性要求从"读取状态"放松到"查询结果"
- 这允许高并发度，同时确保查询结果的正确性

### 架构

Pesto 在 Basil 的 KVS 架构基础上构建，继承了 Basil 的高效两段提交协议：
1. **客户端侧执行**：事务执行在客户端管理
2. **写入缓冲**：PUT 操作在本地缓冲
3. **两段提交**：通过高效的两次多播完成验证、2PC 决策和复制
4. **查询处理**：集成 Peloton SQL 引擎，处理复杂查询

### 容错与恢复

- **副本故障容忍**：n = 5f + 1 配置，容忍 f 个故障副本
- **客户端故障恢复**：协作式 fallback 协议允许其他客户端终止进行中的事务
- **Byzantine 独立性**：确保没有拜占庭参与者可以单方面决定任何操作的结果

## 主要实验结果

### 实验环境
- m510 机器（8 核 2.0 GHz CPU, 64 GB RAM, 10 GB NIC, 0.15ms 延迟）
- CloudLab 部署
- 评估配置：f=1（Peloton-SMR: n=4；Pesto: n=6；Postgres-PB: n=2）

### TPC-C（20 warehouses）

**吞吐量**：
- **Pesto: 1784 tx/s**，与无复制 Peloton（1777 tx/s）和 PostgreSQL（1781 tx/s）**相当**
- 比 Peloton-HS（758 tx/s）高 **2.3 倍**，比 Peloton-Smart（785 tx/s）高 **2.3 倍**
- 比 Postgres-PB（1257 tx/s）高 **1.4 倍**
- CRDB（6 分片，1033 tx/s）仅达到 Pesto 的 **58%**

**延迟**：
- Pesto 延迟比 Peloton 和 PostgreSQL 仅高 **<1.5 倍**
- 比 Peloton-HS 低 **3.9 倍**，比 Peloton-Smart 低 **2.7 倍**

**关键原因**：Pesto 点读操作（GET）仅需从 quorum（f+1）个副本获取响应，这允许负载均衡，甚至超过无复制系统的吞吐。

### AuctionMark（复杂 JOIN + 低冲突）

- Pesto 吞吐与无复制系统持平（差异 <1.4 倍）
- 延迟比 Peloton-HS 低 **5 倍**，比 Peloton-Smart 低 **3 倍**
- 由于范围查询增多（减少点读负载均衡优势），吞吐量提升受限（1.1 倍）

### SEATS（高比例范围查询和跨表 JOIN）

- Pesto 吞吐与无复制系统持平（差异 <1.22 倍）
- 延迟比 Peloton-HS 低 **4.6 倍**，比 Peloton-Smart 低 **3.4 倍**

### 分片扩展性

- 2 分片：1.64 倍吞吐提升
- 3 分片：2.21 倍吞吐提升
- 3 分片 Pesto（使用更多机器用于复制）比 CRDB 6 分片（无复制）高 **2.91 倍**

### Micro-benchmark（YCSB 风格）

- Pesto 的点读性能随并发读副本数线性提升
- 范围查询：Pesto 显著优于 Basil 的 KVS 设计

## 潜在问题 / 局限性

1. **查询延迟最坏情况**：客户端驱动的快照协议在需要主动解决时可能导致较高的查询延迟，论文未深入分析最坏情况下的延迟分布
2. **分片 + 跨分片事务**：虽然支持分片，但跨分片事务的协调开销在高冲突场景下可能成为瓶颈
3. **副本数量开销**：n=5f+1 的配置相比 SMR-based 的 n=3f+1 增加了 67% 的副本数，增加了资源开销
4. **仅支持单语句事务**：论文未明确说明对嵌套事务或存储过程的支持情况
5. **静态分片**：Pesto 依赖预先分片，不支持动态负载均衡
6. **与 Basil 的对比有限**：论文中 Basil 仅作为微基准对比，缺乏在真实 SQL 负载上的详细对比
7. **复制模型选择**：作者承认选择了"full replication"而非"partial replication"以简化设计，partial replication 场景下的性能未验证

## 未来工作

- 支持部分复制（partial replication）以减少资源开销
- 探索自适应的谓词锁粒度
- 与更先进的 SQL 优化器集成
- 研究与链上执行（on-chain execution）的集成

## 个人评注

Pesto 是 BFT 数据库领域的一项重要进展。它成功地将 Basil 的 order-free 洞察扩展到了完整的 SQL 工作负载，证明了"无需全序也能保证安全"这一核心思想具有更广泛的应用价值。

最令人印象深刻的结果是 **Pesto 在 TPC-C 上追平了无复制的 PostgreSQL**——这意味着 Byzantine 容错的开销在实践中几乎可以忽略不计。这对于需要 BFT 保证的生产系统来说是一个重要突破。

然而，论文的弱点在于**对复杂查询场景的验证不够深入**。TPC-C 虽然是标准基准，但它并不代表现代 OLTP 应用的全部特征（例如缺乏复杂的跨表 JOIN）。SEATS 和 AuctionMark 虽然包含 JOIN，但作者主要聚焦在吞吐和平均延迟上，对尾延迟和最坏情况分析不足。

此外，n=5f+1 的副本配置相比传统的 3f+1 意味着 67% 的额外开销，这在成本敏感的生产环境中可能是一个重要考量。
