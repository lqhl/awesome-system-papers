# Pesto: Cooking up High Performance BFT Queries

**作者**：Florian Suri-Payer（Cornell University）、Neil Giridharan（UC Berkeley）、Liam Arzola（Cornell University / UC San Diego）、Shir Cohen（Cornell University）、Lorenzo Alvisi（Cornell University）、Natacha Crooks（UC Berkeley）

## 一、背景

去中心化应用正在金融、医疗、土地登记、机密计算等领域广泛探索，它们的核心是 Byzantine Fault Tolerant（BFT）共识协议——提供一个完全有序、防篡改的日志，分布在相互不信任的参与方之间。将此日志物化为数据存储是自然需求，但难以高效实现。

主流中心化应用期望数据库具备三项能力：(i) 交互式事务（interactive transactions，优于存储过程）；(ii) 丰富的查询语言（SQL）；(iii) 水平扩展（跨分片）。然而现有 BFT 数据库系统要么在有限 KVS 接口下实现高性能，要么在全 SQL 接口下性能极差，两者难以兼得。

---

## 二、要解决的问题

**现有方案的主要缺陷：**

1. **SMR 层叠方案（DB on top of BFT consensus）**：将 Peloton/Postgres 叠加在 HotStuff/PBFT 之上。缺点是：所有操作必须全序排序，消除工作负载的天然并行性；交互式事务每一步都需多轮共识通信，延迟极高；跨分片时两阶段提交（2PC）再叠加共识，协调开销巨大。

2. **受限 KVS 接口方案（Basil）**：Basil 避免了全序，通过将并发控制、复制和 2PC 融合为单层实现高性能，但仅支持简单的 GET/PUT 接口，无法表达 JOIN、聚合、范围扫描等查询。把这类查询翻译为 KVS 操作需要客户端发出海量读请求（如一个简单 JOIN 可能需要一百万次 GET），开销与中间结果大小成正比。

**核心挑战：**
- 如何在不牺牲 Basil 性能优势的前提下，保证任意复杂查询结果的正确性（有效性、新鲜性、完整性）？
- 如何将并发控制扩展到范围查询而不引发大量中止？

## 三、核心设计

Pesto 的关键洞察：**对查询结果的一致性要求只需针对该查询的谓词所涉及的行，而非整个数据库状态。**

### 3.1 不一致复制 + 按需快照同步

Pesto 放弃全序，允许副本状态不一致（inconsistent replication）。当客户端执行范围查询时，若副本返回结果不一致，则触发**快照同步协议**：客户端动态地在各副本之间就"当前查询所涉及的行"建立公共快照（common snapshot），而非同步整个数据库状态。

- **快照内容**：仅包含满足查询谓词的"活跃行"（active rows）对应的事务 ID 集合，确保原子性。
- **两条执行路径**：
  - **Eager Path**：若收到 f+1 个结果与读集（Q-READ）匹配的副本回复，直接返回结果（多数情况下无需快照）。
  - **Snapshot Path**：若 eager path 失败，客户端收集快照投票（SS-VOTE），过滤出至少 f+1 个副本认可的事务 ID，提议快照（SS-PROP），副本补齐缺失数据后统一执行查询。

### 3.2 语义感知的乐观并发控制（Semantic OCC）

借鉴精度锁（precision locking），Pesto 引入谓词感知的冲突检测：

- **活跃读集（ARS）**：仅包含满足查询谓词的行；被动读集中的行不参与冲突检测。
- 并发写入仅在其影响查询谓词结果时才构成冲突（即写入的列值满足查询 filter predicate）。
- **写单调性（Write Monotonicity）**：每次写操作必须携带该表的当前最大时间戳（table version）。副本只检查 P.table_v 到 ts_T 之间的写操作是否与查询谓词冲突，避免全量扫描历史事务。

### 3.3 提交协议

继承 Basil 的提交设计，并扩展支持范围查询的语义 CC：
- 两阶段提交（2PC）由客户端驱动，聚合各分片的提交/中止投票。
- **快速路径**（5f+1 票全部 commit）：单轮通信完成提交，占比约 97%。
- **慢速路径**：需额外一轮将决策持久化到日志分片。
- 需要 **n = 5f+1** 个副本（相比 SMR 的 3f+1），以保证 Byzantine 独立性（Byzantine Independence）。

## 四、实现细节

- **语言与框架**：C/C++，基于 Basil 开源实现扩展；SQL 层复用 Peloton（基于 Postgres 的全功能开源 SQL 引擎）。
- **网络**：Protobuf + TCP。
- **密码学**：ed25519 椭圆曲线签名、HMAC-SHA256 消息认证、Blake3 哈希。
- **数据结构**：每个事务维护 ReadSet、DepSet（未提交依赖）、PredSet（查询谓词）、WriteSet。版本（version）包含列数据和元数据（事务 ID、时间戳、提交状态）。
- **事务 ID**：以事务内容的密码学哈希作为 ID，防止 Byzantine 客户端篡改内容。
- **副本恢复**：继承 Basil 的协作恢复协议（cooperative fallback），允许任意客户端终结未完成的事务。
- **开源**：原型及所有基线系统均已开源于 GitHub（`fsuri/Pequin-Artifact`）。

## 五、实验结果

**实验平台**：CloudLab m510 机器（8核 2.0GHz CPU，64GB RAM，10Gb NIC，0.15ms ping）。f=1 故障容忍（Pesto: 5 副本，SMR 基线: 4 副本，Postgres-PB: 2 副本）。

### 主要对比系统

| 系统 | 类型 | 说明 |
|------|------|------|
| Pesto | BFT SQL DB | 本文系统 |
| Peloton | 无复制 SQL DB | Pesto SQL 层基础 |
| Peloton-HS | BFT SMR | Peloton + HotStuff |
| Peloton-Smart | BFT SMR | Peloton + BFT-SMaRt |
| Postgres | 无复制 生产级 SQL | 对照 |
| Postgres-PB | 主备复制 | Postgres 原生主备 |
| CRDB | 分布式 SQL | CockroachDB，6分片 |

### TPC-C（20仓库，高争用，点读为主）

| 系统 | 吞吐量 (tx/s) | 相对 Pesto |
|------|--------------|-----------|
| Pesto | 1784 | 1x |
| Peloton（无复制） | 1777 | ≈1x |
| Postgres（无复制） | 1781 | ≈1x |
| Peloton-HS | 758 | 0.42x |
| Peloton-Smart | 785 | 0.44x |
| Postgres-PB | 1257 | 0.70x |
| CRDB（6分片） | 1033 | 0.58x |

- Pesto 延迟比 Peloton-HS 低 **3.9x**，比 Peloton-Smart 低 **2.7x**。
- Pesto 97% 的事务走快速路径（单轮提交）。

### AuctionMark / SEATS（高比例范围查询与 JOIN）

- Pesto 与无复制 Peloton 吞吐相近（AuctionMark 1.36x 差距，SEATS 1.22x 差距）。
- 延迟比 SMR 基线低 3x–5x。

### 分片扩展性（TPC-C）

| 分片数 | Pesto (tx/s) | 扩展比 |
|--------|-------------|--------|
| 1 | 1784 | 1x |
| 2 | 2934 | 1.64x |
| 3 | 3949 | 2.21x |

- 3 分片下 Pesto 吞吐为 Basil KVS（4862 tx/s）的 ~0.81x，但提供完整 SQL 接口。

### 范围读 vs 点读（YCSB 微基准，10M 行）

- 范围读在 10k 行结果集下比点读实现低 **16.6x** 的延迟。
- 带谓词过滤（1/100 命中率）可进一步降低 **110x**。

### 压力测试（强制 Snapshot Path）

- 强制 eager 失败（U-FailEager）：吞吐 -9%，延迟 +1.38x。
- 模拟强不一致（U-Incon，1/3 副本延迟写入）：吞吐 -5%（同步开销被初始写入省略抵消）。
- 高争用 Zipfian 负载下，Snapshot Path 代价更大（-32% 至 -48%），因扩大了冲突窗口。

### 副本故障（f=1 宕机）

- 无 progress 中断（无 leader 依赖）。
- 均匀负载：吞吐 -14% 至 -24%，延迟 +1.59x 至 +2.7x。
- 高争用 Zipfian：吞吐 -5%，影响极小。

## 六、批判性分析

### 1. 实验基线不完全公平

论文对 Peloton-SMR 采用了"显式非故障容忍"的配置——允许副本自由并行执行并只让主副本响应客户端，这并非合法的 BFT 实现，作者自称是"理想上界"。这种设置让 Pesto 与一个不正确的基线相比，使 2.3x 吞吐提升的对比意义打折扣，读者无法得知"真正严格的 SMR + 并行执行"下的差距。

### 2. 副本数量代价被轻描淡写

Pesto 需要 **5f+1** 个副本（SMR 只需 3f+1），即容忍 1 个故障需要 5 台机器。论文对这一运营成本增幅（67% 更多机器）几乎一笔带过，也未讨论这在实际部署中（如广域网）意味着更高的延迟和带宽成本。

### 3. 微基准 vs 端到端覆盖不均

TPC-C 以点读为主（恰好是 Pesto 的强项），而 AuctionMark/SEATS 的范围查询压力才更能体现 Pesto 的真实代价。在这两个负载上，Pesto 与无复制 Postgres 的差距达 1.94x，但论文并未深入分析这一差距的来源（范围读大 quorum、更多签名验证、快照路径等各占多少？）。

### 4. 写单调性约束的实际影响未充分评估

写单调性要求事务时间戳大于所有之前该表的写入时间戳，并引入 grace 窗口来容忍时钟偏差和延迟提交。但论文未提供在高争用或时钟偏差大时，因单调性违规导致的中止率数据，这在广域网或异构集群中可能是显著的性能瓶颈。

### 5. 快照路径在高争用下代价陡增

Zipfian 负载下强制 Snapshot Path 导致吞吐下降 **32%–48%**，这说明 Pesto 对于热点数据密集型 OLTP 场景（电商、秒杀等）并不友好。论文未提供针对这一场景的缓解策略。

### 6. 安全性证明局限于附录

论文将所有形式化安全证明放在补充附录中，且表示"省略了若干繁琐细节"。对于一个号称提供 Byz-serializability 保证的系统，这让独立验证其正确性存在较高门槛。

---

## 七、总结

Pesto 是一个高性能 BFT 数据库，通过放弃全序复制、引入按需快照同步和语义感知的乐观并发控制，将 SQL 查询能力引入 Basil 的高性能 BFT KVS 框架。在 TPC-C 等主流 OLTP 基准上，Pesto 吞吐接近无复制 Postgres/Peloton，并比传统 SMR-based BFT 方案提升 2.3x 吞吐、降低 2.7x–3.9x 延迟。其主要适用场景是需要 SQL 表达能力的去中心化应用（金融、医疗等合规数据共享）；主要局限在于需要 5f+1 个副本（部署成本高）、高争用下 Snapshot Path 代价陡增，以及写单调性约束在广域部署中的潜在风险。
