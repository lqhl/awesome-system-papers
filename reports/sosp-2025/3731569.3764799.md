## 一、背景

去中心化应用在金融、医疗、土地登记、机密计算等领域日益受到关注，其核心依赖 Byzantine Fault Tolerant (BFT) 共识协议来保证数据一致性和防篡改。然而，现有 BFT 数据存储系统在性能和表达能力之间存在根本性矛盾：

- **基于 SMR 的 BFT 数据库**（如在 HotStuff/BFT-SMaRt 上层叠数据库引擎）概念简单，但需要全序化所有操作，丧失了工作负载内在的并行性，且交互式事务需要多轮共识协调，延迟极高。
- **集成式 BFT KVS**（如 Basil）通过免排序、客户端驱动的设计实现了高性能，但仅支持简单的 GET/PUT 接口，无法高效处理 join、scan、aggregation 等 SQL 查询。
- 区块链系统仅支持 stored procedure 形式的 smart contract，不提供交互式事务或 SQL。

现实中大多数集中式应用使用 SQL 数据库，期望交互式事务、丰富查询语言和水平扩展能力。将这些应用去中心化时，要么忍受低性能的全 SQL 兼容，要么接受高性能但受限的 KVS 接口。

---

## 二、要解决的问题

1. **如何在不一致复制的 BFT 设置下保证任意 SQL 查询的正确性？** Basil 的免排序设计使副本状态可能不一致，客户端提交复杂查询（如 join、scan）时，不同副本可能产生不同结果，无法简单地通过比对 f+1 个匹配响应来验证结果的 validity、freshness 和 integrity。

2. **如何将乐观并发控制扩展到通用 SQL 查询？** 传统 OCC 处理 range query 时需要逻辑锁定可能满足查询谓词的所有 key 范围，导致高 abort rate 和低吞吐。在 Byzantine 设置下锁机制更不可行（恶意客户端可拒绝释放锁）。

3. **如何在支持全 SQL 的同时保持 Basil 级别的性能？** 即在不引入全序排序的前提下，实现 Byz-serializability 和 Byzantine independence。

## 三、洞察与设计

**关键洞察**：在响应一个查询时，一致性只需要在该查询的特定谓词涉及的数据上成立，而不需要在整个数据库上成立。

基于这一观察，Pesto 的设计围绕两个核心机制展开：

### 按需快照同步协议（Snapshot Synchronization）

- 副本默认使用不一致复制（inconsistent replication），不强制全序化。
- 对于 range read，客户端向 3f+1 个副本发送查询请求。如果能收集到 f+1 个匹配的结果（eager path），直接完成；否则进入 snapshot path。
- Snapshot path 中，客户端从副本的 snapshot vote（每个副本报告其读取行对应的事务 ID 集合）中筛选出至少 f+1 个副本认可的事务 ID，合成一个 snapshot proposal，要求副本同步到该一致状态后重新执行查询。
- 快照仅同步查询涉及的"活跃行"（active rows，即满足查询谓词的行），而非整个数据库状态。

### 语义感知乐观并发控制（Semantic CC）

- 受 precision lock 启发，Pesto 提出基于谓词的 OCC 检查：仅当并发写操作影响了查询结果时才判定冲突。
- 具体做法：验证阶段检查并发事务的写是否落入查询谓词的"活跃行"范围内，只有写入会改变查询结果的才算冲突。
- 结合 write monotonicity（带宽限窗口）来限制需要检查的并发事务范围，避免检查历史上所有事务。

### 整体架构

- **客户端驱动、无 leader**：事务由客户端协调，读写独立并行，无单点瓶颈。
- **事务处理两阶段**：执行阶段（point read 单轮完成，range read 可能需要快照同步）+ 提交阶段（prepare 投票 + 2PC 决策 + 异步 writeback）。
- **副本数 n=5f+1**，保证 Byzantine independence——拜占庭参与者无法单方面决定任何操作的结果。
- SQL 引擎基于 Peloton（开源 SQL 数据库），提供完整 SQL 兼容性。

## 四、实现细节

- **语言与基础**：C/C++ 实现，基于 Basil 开源代码扩展。网络层使用 Protobuf + TCP，认证使用 ed25519 数字签名和 HMAC-SHA256，哈希使用 Blake3。
- **SQL 引擎**：适配 Peloton（基于 Postgres 的开源 SQL 数据库），支持完整 SQL 命令（BEGIN, SELECT, INSERT, DELETE, UPDATE, COMMIT, ABORT）。
- **数据结构**：
  - Version：每个写操作生成唯一版本，包含列数据 + 元数据（写入事务 ID、时间戳、提交状态）。
  - Transaction：维护 ReadSet、DepSet（对 prepared 版本的依赖）、PredSet（查询谓词，用于 Semantic CC）、WriteSet。
  - 时间戳 ts_T = (local_time, ClientID, seq-no)，在 BEGIN 时客户端生成。
- **Semantic CC 算法**（Algorithm 1）：
  - 对每个谓词 P，检查时间戳在 [P.table_v - grace, ts_T] 范围内的并发写入。
  - 仅检查写入是否落入谓词 P 的活跃行范围（而非整个读集合），大幅减少冲突判定。
- **提交协议**：
  - Fast path（5f+1 commit votes）：单轮完成，97% 的 TPC-C 事务走此路径。
  - Slow path（3f+1 commit votes）：需额外一轮到 S_log 分片持久化决策。
  - Abort path：f+1 abort votes 即可。
- **Recovery**：继承 Basil 的 cooperative fallback 协议处理客户端故障。
- 源代码公开于 https://github.com/fsuri/Pequin-Artifact。

## 五、实验结果

**实验平台**：CloudLab m510 机器（8 核 2.0GHz CPU，64GB RAM，10GB NIC，0.15ms ping），f=1（Pesto 6 副本，SMR 基线 4 副本）。

### 主要基准测试结果

| 工作负载 | Pesto | Peloton (未复制) | Postgres (未复制) | Peloton-HS | Peloton-Smart | Postgres-PB | CRDB |
|----------|-------|-----------------|------------------|------------|---------------|-------------|------|
| TPC-C 吞吐 (tx/s) | 1784 | 1777 | 1781 | 758 | 785 | 1257 | 1033 |
| TPC-C 延迟改善 vs HS/Smart | — | — | — | 3.9x 更高 | 2.7x 更高 | — | — |

- **TPC-C**：Pesto 吞吐匹配未复制的 Peloton 和 Postgres，是 Peloton-HS 的 2.3x，延迟降低 2.7x-3.9x。97% 事务走 fast path（单轮提交）。
- **AuctionMark**：Pesto 在未复制 Peloton 的 1.36x 以内，延迟较 SMR 基线降低 3x-5x。
- **SEATS**：Pesto 在未复制 Peloton 的 1.22x 以内，延迟较 SMR 基线降低 3.4x-4.6x。

### 分片扩展性（TPC-C）

| 分片数 | Pesto (tx/s) | CRDB (tx/s) |
|--------|-------------|-------------|
| 1 | 1784 | 400 |
| 2 | 2934 | 1033 |
| 3 | 3949 | 1357 |

### Range Read 性能

- Range read 协议在扫描 10K 行时比 point-read 实现延迟降低 16.6x，带条件谓词时降低 110x。
- TPC-C 的 Stock-level 事务（scan 密集）延迟比 Basil 的 point-read 实现降低 11x。

### 压力测试与故障容忍

- 人为强制 snapshot path（每次事务均失败 eager path）：均匀负载吞吐下降约 9%，延迟增加 1.38x。
- 人为模拟 1/3 副本不一致：均匀负载吞吐下降约 5%；Zipfian 高竞争负载下降 48%（因冲突窗口扩大）。
- f=1 副本故障：均匀负载吞吐下降 14%-24%，无进度中断（不像 SMR 依赖 leader）。

## 六、批判性分析

1. **副本数量开销被轻描淡写**：Pesto 需要 n=5f+1=6 个副本（f=1），而经典 BFT 仅需 3f+1=4 个。50% 更多的副本意味着显著的硬件成本和运维复杂度增加，但论文几乎未讨论这一代价，仅在模型部分一笔带过。

2. **基线对比不完全公平**：Peloton-SMR 基线被明确配置为"非容错"模式（允许并行执行、单副本响应），作者声称这是给基线的"最大慷慨"（upper bound），但这实际上使基线既不容错也不具备 BFT 特性，比较意义有限。与真正的 BFT SQL 数据库（如果存在的话）的比较缺失。

3. **实验规模偏小**：所有实验仅在 f=1（6 副本）下进行，未展示 f=2 或更大规模的表现。BFT 系统的真正挑战在于规模扩大后密码学开销和通信复杂度的增长，论文回避了这一问题。

4. **Zipfian 高竞争下性能退化严重**：当人为引入不一致时，Zipfian 负载吞吐下降 48%，这暴露了 snapshot 同步机制在真实高竞争场景下的脆弱性。论文将此归因于"冲突窗口扩大"，但未提出改进方案。

5. **SQL 兼容性的实际覆盖范围不明**：论文声称"full SQL compatibility"，但实际基于 Peloton（一个学术原型数据库），未测试复杂的嵌套子查询、CTE、窗口函数等现代 SQL 特性。"full SQL"的说法可能过于乐观。

6. **Fast path 超时策略的工程问题**：论文承认 fast path 和 slow path 可以并行执行以避免超时延迟，但选择了"先等 fast path 超时再走 slow path"的保守策略。在 f=1 故障下，这导致延迟增加 2.7x（Failure-FP），实际部署中需要更精细的策略。

7. **与 Basil 的关系**：Pesto 大量继承 Basil 的设计（客户端驱动、2PC、recovery 等），真正新贡献主要是 snapshot 同步和 Semantic CC。论文应更清晰地界定增量贡献的边界。

---

## 七、总结

Pesto 是一个高性能 BFT SQL 数据库，通过放弃全序化、采用按需快照同步和语义感知 OCC，在保证 Byz-serializability 和 Byzantine independence 的同时，实现了接近未复制数据库的性能。其核心贡献在于证明了"查询一致性只需在查询谓词涉及的数据上成立"这一洞察可以同时解决 BFT 下任意 SQL 查询的正确性保证和高效并发控制两个问题。主要局限包括 5f+1 的副本开销、仅在小规模（f=1）下验证、以及在高竞争场景下 snapshot 同步的性能退化。适用于对 SQL 兼容性有刚需的去中心化应用场景（如金融、医疗数据共享）。
