# Aeolia: A Fast and Secure Userspace Interrupt-Based Storage Stack

**作者**：Chuandong Li, Ran Yi, Zonghao Zhang (Peking University / Zhongguancun Laboratory), Jing Liu (Microsoft Research), Changwoo Min (Igalia), Jie Zhang, Yingwei Luo, Xiaolin Wang (Peking University / Zhongguancun Laboratory), Zhenlin Wang (Michigan Technological University), Diyu Zhou (Peking University / Zhongguancun Laboratory)

## 一、背景

现代 NVMe SSD（如 Samsung Z-NAND、Kioxia XL-Flash、Intel 3D XPoint）已经能够实现微秒级延迟和百万级 IOPS，存储介质的巨大性能提升对存储栈提出了新的挑战。现有高性能存储栈分为两大阵营：用户态 polling-based（如 SPDK）和内核态 interrupt-based（如 Linux io_uring）。两类方案在设计空间中将两个正交维度耦合在一起：用户态 vs. 内核态、polling vs. interrupt，使得设计空间中"用户态 + interrupt"这一象限始终未被探索。

---

## 二、要解决的问题

1. **Polling-based 用户态栈（SPDK）无法高效共享资源**：多个不可信任务无法安全共享磁盘（缺乏可信中介）；当多任务共享 CPU 时，polling 无法与线程调度器协调，导致高尾延迟。

2. **Interrupt-based 内核栈性能上限有限**：内核栈存在固有的 layering 开销（syscall、VFS、JBD）和多核可扩展性瓶颈（VFS 粗粒度锁），即便经过大量优化仍无法匹配用户态方案的性能。

3. **现有用户态文件系统（uFS）受限于 IPC 和 polling 模型**：uFS 通过独立进程 + 专用线程处理文件系统请求，IPC 开销高（~400ns）；polling 的事件驱动模型复杂化了并发控制，限制了多核可扩展性（每个文件绑定到单一线程）。

4. **设计空间中"用户态 + interrupt"被认为不可行**：此前没有将 user interrupt 用于存储设备的先例，且用户态栈天然缺乏保护共享和调度协调能力。

---

## 三、洞察与设计

**关键洞察**：与传统观点（polling 显著优于 interrupt）相反，polling 相比 interrupt 仅带来边际的 I/O 性能提升。此前归因于 interrupt 的大部分开销实际来自不合理的内核线程调度策略（eager sleep 导致 1.8μs 开销），而非 interrupt 机制本身（仅 0.6μs）。通过引入 active checking 调度策略，interrupt 可以达到接近 polling 的性能水平。同时，polling 的高 CPU 占用反而限制了文件系统的多核可扩展性。

基于上述洞察，Aeolia 选择"用户态 + interrupt"作为设计点，整个系统由三个组件构成：

- **AeoKern**（内核模块）：负责硬件配置、资源分配（NVMe queue pairs）、维护访问权限。
- **AeoDriver**（库设备驱动）：用户态直接与磁盘交互，利用 **user interrupt**（Intel Sapphire Rapids 起支持的硬件特性）将存储中断直接送达用户态，绕过内核。通过将 UPID 映射到 AeoDriver 地址空间来解决"用户态无法写 UPID"的难题。
- **AeoFS**（库文件系统）：基于 AeoDriver 构建的 POSIX-like 文件系统，提供低延迟和优秀的多核可扩展性。

三大设计支柱：

1. **Protected sharing（MPK 保护的可信实体）**：利用 Memory Protection Keys（MPK）在进程地址空间内创建受保护的可信实体（trusted entities），AeoDriver 和 AeoFS 的可信层运行在专用保护域中，通过 WRPKRU 指令切换（仅 ~48 cycles），既实现了安全共享又避免了 IPC 开销。进入可信实体仅需约 40ns。

2. **Coordinated scheduling（sched_ext 协调调度）**：利用 sched_ext（Linux 6.12 引入的 eBPF-based 用户态调度框架），Aeolia 在 eBPF maps 中维护与 EEVDF 一致的调度状态，可信实体在调度决策点读取该状态决定是否 yield，仅在必要时进入内核切换线程。

3. **Eager integrity checking（热切完整性检查）**：AeoFS 继承 Trio 的 state separation（core state vs. auxiliary state），但改为由可信层在每次元数据操作时即时检查完整性（而非 Trio 的 lazy checking），代价仅为每次操作额外 85 cycles 的域切换开销。

## 四、实现细节

- 基于 Linux 6.12.20 内核实现，AeoKern 3992 行、AeoDriver 1889 行、AeoFS 11870 行，共 17751 行代码。
- **User interrupt 复用**：将磁盘中断、其他设备中断和 UIPI 配置为共享同一中断向量，中断处理器通过检查 NVMe completion queue 和 PIR 栈位来区分来源。UIPI 会导致一次 spurious interrupt（已知限制）。
- **Out-of-schedule interrupt 处理**：当目标线程未运行时，中断送入内核（通过分配不同 user interrupt vector 使其与当前 UINV 不匹配），内核修改目标线程的 saved register/stack context 以插入用户态中断处理帧，避免额外的 0.6μs 重投递开销。
- **AeoFS 文件系统状态**：core state（superblock、block/inode bitmap、data blocks、journaling）由可信层管理；auxiliary state（page cache 用 radix tree + range lock、directory cache 用 resizable chained concurrent hash table、inode cache 用 per-entry RW lock）由非可信层管理，支持细粒度并发。
- **Per-thread journaling**：使用 rdtsc 时间戳，fsync 时锁定所有 per-thread journal 区域、按时间戳合并同 block 事务后提交。
- **I1 不变量（代码签名）** 未实现：当前直接将可信实体内存映射到专用保护域，作者认为无固有技术挑战，仅需额外工程量。
- **安全验证**：手工构造 96 种攻击用例（访问违规 + 文件系统损坏），Aeolia 全部成功防御。

## 五、实验结果

**实验环境**：128-core Intel Xeon Platinum 8592、Intel Optane SSD P5800X（选择 Optane 是因为其低延迟放大了 interrupt 开销，代表最坏情况）、Ubuntu 22.04、Linux 6.12.20，关闭超线程/turbo boost/省电模式。

### AeoDriver 性能

| 指标 | AeoDriver vs. POSIX | AeoDriver vs. SPDK |
|------|---------------------|---------------------|
| 4KB 单线程吞吐 | 1.54× 提升 | 接近持平 |
| 512B 单线程延迟 | 降低 48% | 高 18.2%（最坏情况） |
| 多线程（4KB）| 最高 1.18× 提升 | 持平，均 8 线程饱和磁盘 |

### 协调调度

| 场景 | AeoDriver vs. SPDK/iou_poll |
|------|----------------------------|
| LC + compute 任务（单核） | 尾延迟改善 8.18× – 291.72× |
| LC + TP 任务（单核） | 尾延迟改善 1.11× – 250.5× |
| vs. POSIX/io_uring | 吞吐提升 1.3× – 3.7×，尾延迟降低 9.8% – 48.9% |

### AeoFS 文件系统

| 工作负载 | AeoFS vs. ext4 | AeoFS vs. f2fs | AeoFS vs. uFS |
|----------|---------------|----------------|---------------|
| 4KB 单线程读写 | 最高 12.6× | 最高 12.8× | 最高 4× |
| 2MB 64 线程写 | 19.1× | 28.9× | 8.4× |
| 元数据（open/stat/create/delete） | 最高 7.1× | 最高 10.6× | 最高 21.3× |
| LevelDB | 最高 2.9× | 最高 3.4× | 最高 8.2× |
| Filebench（vs. ext4/f2fs） | 最高 3.1× / 6.6× | — | — |
| Filebench（uFS 配置） | — | — | 最高 1.33× |

**文件共享场景**：当多个应用并发更新同一文件时，AeoFS 仍优于 ext4/f2fs（1.5×–1.9×），但落后于 uFS（uFS 集中式设计避免了同步开销）。

## 六、批判性分析

1. **I1 安全不变量未实现**：代码签名和特权启动流程是保护模型的关键环节，论文声称"无固有技术挑战"但未实现且未提供任何可行性评估。这意味着当前实现中，恶意代码可以在启动阶段加载被篡改的可信实体，整个安全模型的根基存在实质性缺口。

2. **安全验证方法偏弱**：仅使用 96 个手工构造的攻击用例验证安全性，既无形式化证明也无 fuzzing/自动化测试。对于声称实现"protected sharing"的系统而言，这样的验证不够充分。论文也未使用 CrashMonkey 等框架验证 crash consistency。

3. **SPDK 对比可能不公平**：实验选择 Optane SSD（~3μs 延迟）作为"最坏情况"，但这恰好最大化了 interrupt 开销的占比。在更高延迟的普通 NVMe SSD 上，AeoDriver 与 SPDK 的差距会更小，也就是说实验同时也是 Aeolia 相对优势最不明显的场景。论文对此的呈现有些两面取巧。

4. **文件共享场景是实质性短板**：多应用并发更新同一文件/目录时 AeoFS 落后于 uFS，论文将其归为"library FS 的通用限制"一笔带过，但这在多租户/容器化场景中是核心需求，实际应用中可能频繁遇到。

5. **sched_ext 依赖带来的局限被低估**：sched_ext 在 Linux 6.12 才引入，生态尚不成熟。Aeolia 需要在 eBPF 中完整重新实现 EEVDF 调度策略并保持与内核同步，长期维护成本和正确性保证均未讨论。如果内核调度策略更新，eBPF 中的镜像实现可能产生不一致。

6. **UIPI spurious interrupt**：与 UIPI 共存时产生的 spurious interrupt 被列为限制但未量化其实际影响。在 UIPI 频繁的场景（如用户态线程调度库）中，这可能带来可观的额外开销。

7. **硬件依赖范围**：需要 Intel Sapphire Rapids（user interrupt）+ Skylake（MPK）+ sched_ext，实际部署受硬件限制。虽然论文提到 RISC-V 和 ARM 也有类似特性，但均未验证。

## 七、AI Infra / MLSys 视角

1. **推理服务的存储栈优化**：LLM 推理服务（如 vLLM）在 KV cache 换入换出、模型权重加载等场景需要高性能存储访问。Aeolia 的用户态中断机制可以降低 prefill/decode 阶段的存储访问延迟，同时其协调调度能力允许推理任务与 GPU 数据传输任务在同一 CPU 上高效共存。

2. **Checkpoint 写入加速**：大规模训练的 checkpoint 写入是关键瓶颈。AeoFS 的高多核可扩展性（64 线程下 2MB 写入 19.1× vs. ext4）直接利好分布式 checkpoint 写入场景。eager integrity checking 的低开销（85 cycles）也意味着不会显著增加 checkpoint 延迟。

3. **MPK-based 隔离的启发**：AI 推理框架中经常需要在同一进程内隔离不同租户的数据。Aeolia 展示的 MPK + trusted entity 方案（40ns 进入开销）可以迁移到推理引擎中实现租户间的内存隔离，比进程级隔离轻量得多。

4. **sched_ext 用于 GPU 任务调度**：sched_ext 通过 eBPF 暴露调度状态的方式值得 AI Infra 借鉴——可以用类似方法让 GPU runtime 感知 CPU 调度状态，实现 CPU-GPU 协同调度，减少 kernel launch 和 data transfer 的调度延迟。

5. **潜在 future work**：将 Aeolia 的用户态中断技术扩展到 NIC，构建统一的用户态 I/O 栈（论文 §10 已提及），对 RDMA-based 分布式训练通信框架（如 NCCL）有直接价值。

---

## 八、总结

Aeolia 填补了存储栈设计空间中"用户态 + interrupt"这一空白象限，通过 user interrupt 实现用户态直接处理存储中断、MPK 实现进程内可信实体隔离、sched_ext 实现用户态与内核调度协调，在不牺牲资源共享和安全性的前提下达到了接近 SPDK 的 I/O 性能。其上层文件系统 AeoFS 在多核可扩展性上大幅超越 ext4/f2fs/uFS。主要局限在于小 I/O 尺寸下仍略慢于 polling、多应用并发共享文件的开销较高、安全模型中代码签名部分未实现，以及对特定硬件特性（Intel Sapphire Rapids user interrupt、MPK、sched_ext）的依赖。
