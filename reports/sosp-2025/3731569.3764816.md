# Aeolia: A Fast and Secure Userspace Interrupt-Based Storage Stack

**作者**：Chuandong Li, Ran Yi, Zonghao Zhang, Jing Liu, Changwoo Min, Jie Zhang, Yingwei Luo, Xiaolin Wang, Zhenlin Wang, Diyu Zhou（北京大学 / Zhongguancun Laboratory、Microsoft Research、Igalia、Michigan Technological University）

## 一、背景

现代 NVMe SSD（如 Samsung Z-NAND、Kioxia XL-Flash、Intel Optane）已能实现微秒级延迟和数百万 IOPS，远超传统存储设备。这对存储软件栈的效率提出了极高要求。

当前高性能存储栈分为两大阵营：**基于 polling 的用户态栈**（如 SPDK）和**基于中断的内核态栈**（如 Linux io_uring）。这两个维度（用户态/内核态 × polling/中断）被长期捆绑在一起，形成了两个对角点，中间的"用户态 + 中断"组合被普遍认为不可行。此外，两类方案各有天然缺陷：polling-based 用户态栈难以安全共享磁盘与 CPU，内核中断栈有难以消除的软件开销，两者都缺乏高性能文件系统支持。

---

## 二、要解决的问题

**1. Polling 的性能误区**：传统观点认为 polling 比中断快很多，但作者分析发现，内核中断栈慢主要源于糟糕的线程调度策略（任务发出 I/O 后立即进入睡眠，再被唤醒要经过多次上下文切换），而非中断机制本身（中断开销仅 0.6μs）。通过引入"active checking policy"（有其他可运行任务时才睡眠），io_uring 中断模式与 polling 模式的延迟差距从 2.8μs 缩减至 0.9μs。

**2. Polling 限制文件系统扩展性**：SPDK/uFS 等 polling-based 方案为控制 CPU 开销，必须用少量专用 worker 线程处理文件系统请求，导致应用必须通过 IPC（≥400ns）访问文件系统，且 polling 本身的事件驱动模型极难支持多核并发。

**3. 用户态栈缺乏安全共享机制**：多个不信任的任务无法安全共享磁盘（无可信中介），且无法协调内核调度器（语义鸿沟）。现有方案要么引入新硬件，要么用独立特权进程（如 uFS）来解决，代价高昂。

**4. 高性能文件系统缺失**：现有 polling-based 用户态方案（uFS）需 IPC，内核文件系统有 VFS 层开销和粗粒度锁，均无法实现低延迟 + 高多核扩展性的统一目标。

## 三、核心设计

Aeolia 是一个**基于中断的用户态存储栈**，占据此前被视为不可行的设计空间新点（用户态 + 中断），实现四项关键属性：高 I/O 性能、协调调度、受保护共享、高性能文件系统。

系统由三个组件构成（见 Figure 6）：
- **AeoKern**：内核模块，负责初始化硬件（分配 NVMe queue pairs、配置 user interrupt 寄存器、维护访问权限）
- **AeoDriver**：用户态库驱动，直接提交 I/O 请求并通过 user interrupts 接收完成通知；同时充当访问权限的可信实体
- **AeoFS**：基于 AeoDriver 的 POSIX 库文件系统，含可信层和不可信层

**三大技术支柱**：

**① 用户态存储中断（User Interrupts for storage）**：利用 Intel Sapphire Rapids 起引入的 user interrupt 硬件特性，将 NVMe 完成中断直接投递到用户空间，绕过内核。关键洞察：NVMe 中断完成与 user IPI 的差异在于 UPID 中 PIR 字段的填写。Aeolia 通过将 UPID 内存区域映射到 AeoDriver 地址空间，允许用户态中断处理器直接写 UPID，无需陷入内核。

**② 进程内隔离（MPK-based trusted entities）**：使用内存保护键（MPK/PKRU）在同一地址空间内创建可信实体，无需内核切换（WRPKRU 仅 48 cycles）。维护两条不变式：启动时用代码签名验证可信实体身份；运行时通过拦截 mmap/mprotect 阻止不可信代码注入 WRPKRU 指令或自修改代码。

**③ 协调调度（sched_ext + active checking）**：借助 Linux 6.12 引入的 sched_ext（eBPF-based 可扩展调度框架），在用户空间中实现与内核 EEVDF 调度器一致的策略。Aeolia 通过 mmap eBPF maps 读取调度状态（run queue、vruntime、deadline 等），仅在"必要时"通过 sched_yield() 让出 CPU，避免不必要的内核穿越。对调度决策点的安排（I/O 提交后、中断处理返回前）与内核调度器保持一致。

## 四、实现细节

**User interrupt 的挑战与解法**：NVMe 中断原本由内核处理，用户中断硬件未为设备中断设计。Aeolia 的解法：AeoKern 将 UPID 映射到 AeoDriver 地址空间，AeoDriver 中断处理器在被调用后直接重写 UPID.PIR 字段，使硬件能持续识别后续中断。设备中断与 UIPI 共享同一中断向量，通过检查 NVMe 完成队列或栈上保存的 PIR 位来区分来源（UIPI 会产生一个 spurious interrupt，是已知限制）。

**Out-of-schedule 中断处理**：当目标线程不在运行时，Aeolia 将中断投递到内核（正确设置 reschedule flag），而非现有 Intel patch 的掩码方案（会丢失即时调度通知）。为将中断"转交"给目标线程，Aeolia 修改目标线程的保存寄存器和栈上下文，插入用户中断处理器的栈帧，使线程从内核返回后立即执行中断处理器。

**AeoFS 文件系统状态结构**：
- 核心状态（磁盘）：superblock、inode/block bitmap、inode table、数据块、journaling 区域（类似 ext4）
- 辅助状态（内存）：per-core 文件描述符分配器、radix tree 页缓存（含 readers-writer range lock）、concurrent hash table 目录项缓存、inode 缓存

**Eager 完整性检查**：不可信层所有修改核心状态的操作（cache miss 读取核心状态、创建/删除/重命名文件等）均须通过可信层接口。可信层验证权限、路径合法性（目录树不成环、无悬挂文件等），每次切换可信实体仅额外 85 cycles。

**Per-thread journaling**：以 rdtsc 时间戳标记事务，fsync 时锁定所有 per-thread journal 区域，合并写同一块的事务（按时间戳排序），再统一 commit。

**代码规模**：AeoKern 3,992 LOC，AeoDriver 1,889 LOC，AeoFS 11,870 LOC，总计 17,751 LOC。运行于 Linux 6.12.20 + Ubuntu 22.04，测试平台为 128 核 Xeon Platinum 8592 + Intel Optane P5800X SSD（Optane 是最坏情况：低延迟最大化中断开销影响）。

## 五、实验结果

**AeoDriver 单线程性能（vs POSIX / SPDK）**：

| I/O 大小 | AeoDriver vs POSIX（吞吐） | AeoDriver vs POSIX（中位延迟） | AeoDriver vs SPDK |
|----------|---------------------------|-------------------------------|-------------------|
| 512B 读  | 2×                        | -48%                          | -10.7% 吞吐（中断开销占主导）|
| 8KB 读   | 1.54×                     | -36%                          | 相近              |
| 大 I/O   | 1.1×–1.36×                | -10%–27%                      | 相近或略好        |

**协调调度（vs polling-based SPDK）**：
- 单核跑 LC 任务 + 计算密集任务：AeoDriver 尾延迟优于 iou_poll/SPDK 8.18×–291.72×
- 单核跑 LC + TP 任务：尾延迟优于 SPDK 1.11×–250.5×，总吞吐优于 POSIX 1.3×–3.7×

**AeoFS 单线程文件系统性能**：

| 操作     | vs ext4  | vs f2fs  | vs uFS   |
|----------|----------|----------|----------|
| 4KB 读写 | 12.6×    | 12.8×    | 3.96×–4× |
| 2MB 读写 | 1.6×     | —        | —        |
| 元数据   | 7.1×     | 10.6×    | 21.3×    |

**AeoFS 多线程扩展性（64 线程 2MB 写）**：
- vs ext4：19.1×
- vs f2fs：28.9×
- vs uFS：8.4×

**LevelDB 宏观基准**：AeoFS 优于 ext4、f2fs、uFS 2.87×–8.19×。

## 六、批判性分析

**1. "Polling 不如中断"的论点夸大了**：论文核心 Claim 之一是"polling 仅比中断有微小优势"，但这建立在加入 active checking policy 之后（iou_opt）。论文并未追问：active checking policy 为什么在内核中不已经是默认策略？若它真的有效，为何 Linux 主线没有采用？实际上，active checking 会显著增加 CPU 空转时间，在多租户或低负载场景下是否合理值得怀疑。论文对比的是 Optane（<4μs 延迟），在更典型的 PCIe SSD（10–100μs）上结论是否仍然成立未被验证。

**2. 与 SPDK 的性能差距被轻描淡写**：对于 512B 以下的小 I/O，AeoDriver 比 SPDK 慢 10.7%（吞吐）、18.2%（延迟），论文解释为"中断开销（0.6μs）在总延迟（3.2μs）中占比较大"。但实际工作负载中小 I/O 占比可达 40%–50%（4KB 以下），而 4KB 仍有约 6% 的吞吐差距。"over 95% of requests exceed 4KB"援引的是 Alibaba block trace，未必代表所有场景。

**3. 安全模型的实现是不完整的**：论文明确承认 I1 不变式（代码签名 + 特权启动进程）未实现，仅用"直接将内存映射到保护域"替代，认为"没有本质挑战"。但这恰恰是安全方案的关键部分——启动链的正确性往往是最难且 bug 最多的地方。96 个攻击测试是在这个不完整的实现下进行的，其安全性论证因此存在明显漏洞。

**4. sched_ext 依赖带来的可部署性问题**：sched_ext 是 Linux 6.12（2024 年 11 月）才合并的功能，当前生产环境几乎没有部署。Aeolia 的协调调度整个依赖于此，在旧内核上无法正常工作。论文未讨论回退策略。

**5. 实验基线选择存疑**：uFS 是研究原型（2021 年论文），而 ext4 和 f2fs 是成熟内核文件系统。对比对象不在同一"用心优化"的起跑线上。Filebench 等宏观基准的配置也仅用默认参数，缺乏对各文件系统的针对性调优。

**6. 多文件/目录并发写退化问题轻描淡写**：论文承认"多个应用并发更新同一文件或目录"会有额外开销，称之为"library filesystem 的通用限制"。但这对于数据库等高并发场景是一个实质性障碍，论文只字未提定量分析。

## 七、AI Infra / MLSys 视角

Aeolia 的核心技术对 AI Infra 研究具有以下参考价值：

**1. User Interrupts 用于 AI 训练/推理 I/O 路径**：大模型训练中 checkpoint 写入、数据加载（DataLoader）的 I/O 路径是性能瓶颈。Aeolia 展示的用户态 NVMe 直接访问 + 中断通知机制，可在不引入 SPDK 式 CPU spinning 的前提下获得接近 SPDK 的吞吐，对 KV cache offload（将 KV cache 卸载到 NVMe）等场景有直接参考意义。

**2. MPK 用于 GPU/加速器驱动隔离**：AI 推理系统中常见多租户场景（多个 LoRA 权重对应不同业务方共享 GPU）。Aeolia 的进程内 MPK 隔离技术可迁移至用户态 GPU 驱动（如 libcuda bypass 方案），实现在同一进程地址空间内安全隔离不同租户的 CUDA queue 和内存操作，无需切换进程或内核态。

**3. sched_ext 的 AI 场景扩展**：AI 推理服务中延迟敏感任务（在线推理）与吞吐密集任务（批处理预填充）混跑是典型场景。Aeolia 展示了通过 sched_ext 暴露调度状态、在用户空间做 yield 决策的框架，对设计 AI serving 专用的混合调度策略有启发——尤其是 continuous batching 场景下 prefill 与 decode 的 CPU 时间协调。

**4. 值得跟进的方向**：
- 将 Aeolia 机制扩展到 RDMA NIC，实现用户态 RDMA completion 直接投递（类似于 user interrupt for NVMe，但针对网络），减少分布式训练中 AllReduce 的中断处理延迟
- 研究 AeoFS eager integrity checking 机制在 AI checkpoint 文件系统中的应用：checkpoint 写入要求崩溃一致性，而现有方案（如 PyTorch DCP）依赖内核文件系统，开销大
- 基于 MPK 的推理引擎内 model weight 隔离：多租户推理中不同租户的 LoRA adapter 权重共享 GPU host 内存，可借鉴 Aeolia 的可信实体模型做细粒度访问控制

## 八、总结

Aeolia 通过利用 user interrupts、MPK 进程内隔离和 sched_ext 三项新兴 Linux/硬件特性，首次实现了兼顾高 I/O 性能、受保护多任务共享和协调调度的用户态中断存储栈，填补了此前被视为不可行的设计空间。AeoFS 在多核场景下对 ext4/f2fs 实现了高达 19.1× 的吞吐提升。主要局限在于小 I/O 场景下与 SPDK 仍有差距、强依赖较新内核功能（sched_ext，Linux 6.12+）、安全模型关键实现缺失，以及多进程并发写同一目录时的性能退化问题。该系统对用户态存储栈的安全设计具有重要参考价值，但距离生产部署还需补充工程工作。
