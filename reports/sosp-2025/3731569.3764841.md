# Fawkes: Finding Data Durability Bugs in DBMSs via Recovered Data State Verification

**作者**：Zhiyong Wu, Jie Liang*, Jingzhou Fu, Wenqian Deng, Yu Jiang* (清华大学 KLISS/BNRist 软件学院; 北航软件学院)
**会议**：SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
**链接**：https://doi.org/10.1145/3731569.3764841
**源文件**：[[3731569.3764841.pdf]]

## 一、背景

数据库管理系统（DBMS）是现代软件基础设施的核心组件，承载着海量关键数据。数据持久性（Data Durability）是 DBMS 的基本要求——一旦数据被提交（committed），即使发生电源故障、进程崩溃或磁盘错误等意外故障，数据也应保持完整且可恢复。为实现这一目标，DBMS 实现了 WAL（Write-Ahead Logging）、Checkpoint、Redo/Undo Logging 等复杂的持久性和恢复机制。

然而，这些机制的实现极其复杂，实践中频繁出现实现缺陷，导致数据丢失、数据不一致、日志损坏甚至系统不可用等严重问题。作者将这类缺陷定义为**数据持久性 Bug（Data Durability Bugs, DDBs）**。现有的测试方法——无论是人工测试还是自动化故障注入工具（如 Jepsen、Mallory）——都难以有效检测 DDBs，因为它们缺乏对文件系统/内核级调用的精确故障注入能力，且无法验证崩溃恢复后的数据完整性。

---

## 二、要解决的问题

1. **现有故障注入工具不精确**：Jepsen、CrashFuzz 等工具设计面向分布式系统，随机注入故障，无法精确命中 DBMS 内部文件系统或内核级调用的关键代码路径——而 86% 的 DDBs 恰恰发生在这些调用期间
2. **缺乏对持久性关键路径的系统性探索**：现有工具倾向于触发常见或浅层路径上的故障，遗漏隐藏在少用 SQL 特性或复杂内部状态中的微妙 bug
3. **崩溃恢复后的数据验证困难**：判断 DBMS 是否正确恢复需要理解预期的恢复后状态，但由于 checkpoint 和 WAL 重放的复杂性，计算恢复后的预期数据状态是一个挑战
4. **现有工具只能检测系统不可用**：传统工具的正确性检查粒度太粗（如仅确认系统可用性或分布式一致性），无法发现数据丢失、数据不一致等更细微的 DDBs

---

## 三、洞察与设计

**关键洞察**：86% 的数据持久性 Bug 仅在 SQL 数据修改语句执行文件系统调用或内核级系统调用时才能被可靠触发；同时，DDBs 涉及 37 种不同的 SQL 语法特性，需要将故障注入点与 SQL 功能相关联才能系统性地覆盖持久性关键路径。

基于这一洞察，作者设计了 Fawkes 测试框架，包含三个核心组件：

### 1. Context-Aware Fault Injection（上下文感知故障注入）
- 通过编译时上下文分析建立 DBMS 函数间的调用依赖图
- 当调用链最终到达 OS 基础库（如 glibc 的 `read`/`write`/`malloc`）时，标记该代码区域为故障注入点
- 维护 **Fault Location Bitmap** 精确记录每个注入点的位置
- 采用 **library-based injection**：hook 标准 C 库、文件系统库、JVM 等底层库，嵌入自定义故障逻辑，实现一次性部署

### 2. Functionality-Guided Fault Triggering（功能引导的故障触发）
- 维护 **Fault-Functionality Table**：记录源代码文件与 SQL 功能的映射关系
- 监控故障注入点的覆盖情况，优先选择覆盖不足的注入点
- 根据覆盖不足的注入点所关联的 SQL 功能，引导工作负载生成器生成针对性的 SQL 语句
- 支持 7 种故障类型：电源故障、内存耗尽、内部关闭命令、进程被杀、内核崩溃、磁盘 I/O 故障、软件异常

### 3. Checkpoint-Based Data Graph Verification（基于检查点的数据图验证）
- 构建**数据图**捕获 DBMS 的元数据状态（表、列、行数、约束），而非存储完整数据集
- 崩溃后，基于最近 checkpoint 回滚数据图，再根据恢复日志中需重放的 SQL 语句修正数据图
- 对比恢复后的 DBMS 实际元数据与预期数据图，检测四类问题：数据丢失（缺失的表/行/约束）、元数据不一致、实体数据不一致、日志损坏和系统不可用

---

## 四、实现细节

- 整体代码规模：约 10K 行 C++ + 5K 行 Rust + 4K 行 Bison/Flex，覆盖工作负载生成器、故障注入器、故障触发器和数据状态验证器
- 故障注入器：修改了 Glibc 和 JVM 库，约 3K 行 C 代码 + 4K 行 Java 代码
- 工作负载生成器：基于 SQLsmith 扩展，使用各 DBMS 的官方语法文件（Flex/Bison）适配方言
- 数据生成：创建含 10-100 个随机列的表，随机添加索引（BTREE）和外键约束
- Bug 复现：记录完整的工作负载序列、故障注入点、故障类型和 DBMS 状态，用确定性触发器替换瞬态条件，支持精确重放
- 部署方式：DBMS 和 Fawkes 运行在同一本地网络的 Docker 容器中

## 五、实验结果

### 测试目标
8 个广泛使用的 DBMS：MySQL、MariaDB、PostgreSQL、IoTDB、TDengine、GridDB、CnosDB、OpenGemini

### 主要结果（两周持续测试）

| 指标 | 数值 |
|------|------|
| 发现的未知 DDBs 总数 | 48 |
| 已修复 | 16 |
| 分配 CVE | 8 |
| 数据丢失类 | 20 |
| 数据不一致类 | 13 |
| 日志损坏类 | 7 |
| 系统不可用类 | 8 |

### 与现有工具对比（72 小时）

| 工具 | 检测 Bug 数 | 覆盖分支数 |
|------|-----------|-----------|
| Jepsen | 2 | 174,604 |
| CrashFuzz | 4 | 216,985 |
| Mallory | 6 | 218,135 |
| CrashTuner | 1 | 188,810 |
| **Fawkes** | **29** | **320,848** |

Fawkes 比最佳基线多检测 23-28 个 bug，覆盖分支多 47%-84%。Fawkes 独有发现的 bug 主要是数据丢失、数据不一致和日志损坏，其他工具仅能检测系统不可用。

### 消融实验

| 配置 | 72h Bug 数 |
|------|-----------|
| Fawkes_mal（随机注入 + Jepsen 验证） | 2 |
| Fawkes_i（+ 上下文感知注入） | 5 |
| Fawkes_i+t（+ 功能引导触发） | 8 |
| Fawkes_all（+ 数据图验证） | **29** |

### 历史 Bug 重发现
两周内重新发现了 43 个已知 DDBs 中的 39 个（91%），第一周即发现 34 个（79%）。

### 开销
持续故障注入使测试用例执行量减少 64.8%，数据图分析减少 2.8%，但两者对 bug 发现至关重要。

## 六、批判性分析

1. **前置研究的选择偏差**：Motivation study 仅基于 4 个 DBMS 的 43 个 bug，其中 86% 与文件系统/内核调用相关这一关键发现直接决定了 Fawkes 的设计方向。如果这个比例在更广泛的 DBMS（如向量数据库、图数据库）中不成立，Fawkes 的核心假设就会动摇，但论文未对此做敏感性分析。

2. **对比实验不够公平**：Jepsen、CrashFuzz、Mallory、CrashTuner 原本设计用于分布式系统，将它们适配到单节点 DBMS 场景并与专为此设计的 Fawkes 对比，基线天然处于劣势。论文未讨论这种不对称性。

3. **数据图验证的完备性存疑**：Fawkes 仅验证元数据（表、列、行数、约束）而非完整数据内容。对于行值被部分修改但行数正确的情况（如 UPDATE 导致的值错误），仅通过"重放 DML 语句后检查行是否存在"的验证方式可能遗漏微妙的数据损坏。

4. **测试环境局限性**：所有实验在 Docker 容器中运行（10 CPU 核 + 32 GiB 内存），与生产环境差异较大。特别是 Docker 的存储驱动和 I/O 行为可能影响文件系统调用的故障注入效果，但论文未讨论。

5. **可扩展性未充分评估**：论文提到 Fawkes 的故障注入会导致测试吞吐量下降 64.8%，但未讨论随着 DBMS 代码规模增长，故障注入点数量爆炸时的可扩展性问题。

6. **CVE 的实际影响被夸大**：8 个 CVE 听起来很有影响力，但论文未说明这些 CVE 的实际利用难度。在生产环境中触发这些 DDBs 可能需要极特殊的时序条件，实际安全威胁可能低于 CVE 评分暗示的级别。

---

## 七、总结

Fawkes 针对 DBMS 数据持久性 Bug 这一被忽视但极关键的问题，提出了一套完整的检测框架：通过上下文感知故障注入精确命中文件系统/内核调用路径，通过功能引导的故障触发系统性覆盖持久性关键路径，通过基于检查点的数据图验证检测恢复后的数据完整性问题。在 8 个主流 DBMS 上发现 48 个未知 DDBs，显著优于现有工具。主要局限在于核心假设（86% 与文件系统调用相关）的泛化性尚未充分验证，且元数据级别的验证可能遗漏部分数据损坏。该工作为 DBMS 持久性测试提供了一个有效的自动化方案，但主要适用于单节点 DBMS 场景。
