# Fawkes: Finding Data Durability Bugs in DBMSs via Recovered Data State Verification

## 论文基本信息
- **标题**: Fawkes: Finding Data Durability Bugs in DBMSs via Recovered Data State Verification
- **作者**: Zhiyong Wu, Jie Liang, Jingzhou Fu, Wenqian Deng, and Yu Jiang
- **会议**: SOSP 2025
- **Session**: Bugs
- **PDF**: 3731569.3764841.pdf

## 研究背景

数据库管理系统（DBMS）的数据持久性（data durability）是其最核心的特性之一：一旦事务提交，即使发生宕机、断电或磁盘错误，已提交的数据也必须保持完整。现代 DBMS 通过 Write-Ahead Logging (WAL)、Checkpoints、Redo/Undo Logging 等复杂机制来实现这一保证。然而，这些机制的实现代码极其复杂，涉及文件系统调用、内核级操作和恢复逻辑的精细协作——正是在这些复杂的交叉区域，bug 悄然滋生。

现有的 DBMS 测试方法主要关注 crash consistency（如 Jepsen）、crash recovery（如 CrashFuzz）和 DBMS 内部逻辑错误（如 SQLancer），但对数据持久性 bug（DDB）缺乏专门的有效测试手段。DDB 的独特之处在于：它需要特定的故障时机（在 SQL 操作执行过程中恰好发生 crash）和精确的恢复后数据状态验证——而现有工具通常无法在不触发 crash 的情况下精确注入这些故障。

## 要解决的问题

1. DDB 的特征和根因是什么？目前缺乏系统性的研究来理解这些 bug 的表现形式、触发条件和根本原因
2. 如何有效地检测 DBMS 中的 DDB？现有工具在覆盖率和 bug 类型上都有显著不足
3. 如何在 DBMS crash 后自动验证数据的正确性？

## 核心贡献

- **首个系统性 DDB 研究**：对 4 个主流 DBMS（PostgreSQL、MySQL、IoTDB、TDengine）中的 43 个真实 DDB 进行了深度分析，揭示了 DDB 的四类表现形式（data loss 33%、data inconsistency 31%、log corruption 20%、system unavailability 16%）、根因（72% 来自 crash recovery 或 data flushing 逻辑缺陷）以及触发条件（86% 的 DDB 在 SQL 语句执行过程中涉及文件系统调用或内核级系统调用时触发）
- **Fawkes 框架**：提出基于 recovered data state verification 的 DDB 测试框架，包含三个核心技术创新
- **发现 48 个新 DDB**：在 8 个主流 DBMS（新增 GridDB、CnosDB、OpenGemini）中发现了 48 个之前未知的 DDB，其中 16 个已修复，8 个分配了 CVE

## 主要研究方法

### DDB 实证研究

通过关键词搜索（"durability", "recovery", "reliability" 等）从 4 个 DBMS 的 issue tracker 和 commit log 中收集了 43 个真实的 DDB 案例，手工分析每个案例的 bug 报告、开发者讨论和代码修复。最终揭示了：
- **Manifestations**：33% 表现为 data loss，31% 表现为 data inconsistency，20% 表现为 log corruption，16% 表现为 system unavailability
- **Root Causes**：72% 来自 crash recovery 或 data flushing 逻辑缺陷（如缺少 fsync 调用、写入顺序不当、WAL replay 跳过关键数据块），16% 来自并发处理错误，12% 来自 checkpoint 管理错误
- **Triggering Conditions**：四步触发过程（workload generation、checkpoint execution、fault-induced crash、revealing anomalies after recovery），其中 86% 的 DDB 仅在 SQL 语句执行期间发生文件系统或内核级调用时触发
- **Involved SQL Grammar**：37 种不同的 SQL 语法特性，涉及 INSERT、UPDATE、DELETE、ALTER TABLE、CREATE TIMESERIES 等

### Fawkes 框架设计

**1. Context-Aware Fault Injection（上下文感知故障注入）**

不同于传统的随机故障注入或粗粒度的 coverage-guided 注入，Fawkes 通过编译时静态分析建立 DBMS 函数调用到操作系统基础库（如 glibc）的调用依赖图，精确识别所有涉及文件系统或内核调用的代码区域作为故障注入点（fault injection sites）。这确保了故障注入能够命中真正触发 DDB 的关键代码路径。

**2. Functionality-Guided Fault Triggering（功能引导故障触发）**

维护 fault-injection site coverage 和 fault-functionality table，记录源文件与其关联的 SQL 功能（如 ALTER、INSERT）之间的映射关系。通过优先选择低覆盖率的 fault injection site 并生成针对性的 SQL 工作负载，实现对未探索执行路径的高效覆盖。相比随机、brute-force、coverage-guided 和 deep-priority 方法，功能引导策略能更高效地捕获 fault injection site 与罕见 SQL 功能之间的关联。

**3. Checkpoint-Based Data Graph Verification（基于 checkpoint 的数据图验证）**

通过数据图（data graph）表示 DBMS 的元数据状态（表、列、行数、约束等），在 crash 前后对比数据的 committed 状态与 recovered 状态，自动检测 data loss 和 data inconsistency。具体过程：
- 在 SQL 执行期间持续更新数据图
- Crash 时记录最后一个 checkpoint 和之后未提交的 SQL 语句
- Recovery 后，根据 WAL 和 checkpoint 重建 expected data graph
- 与实际 recovered data graph 对比，发现不一致

## 主要实验结果

**整体结果**（4 个月测试）：
- 8 个 DBMS 共发现 48 个新 DDB
- 16 个已修复，8 个已分配 CVE（6 个 CVSS > 7.5）
- 6 个 DDB 在生产环境中潜伏超过 5 年

**与现有工具比较**（72 小时对比）：
- 相比 Jepsen：Fawkes 多发现 27 个 bug，覆盖多 84% 的 branches
- 相比 CrashFuzz：多发现 25 个 bug，覆盖多 48% 的 branches
- 相比 Mallory：多发现 23 个 bug，覆盖多 47% 的 branches
- 相比 CrashTuner：多发现 28 个 bug，覆盖多 70% 的 branches

**DDB 重发现率**：
- 第一周重发现 34/43 (79%)，两周后达到 39/43 (91%)

**消融实验**：
- 完整 Fawkes 检测 29 个 bug
- 无功能引导：仅 5 个 bug
- 无上下文感知注入：仅 8 个 bug
- 仅随机故障注入：仅 2 个 bug

## 潜在问题 / 局限性

1. **研究范围相对集中**：43 个 DDB 案例仅来自 4 个 DBMS，且主要集中在 PostgreSQL、MySQL、IoTDB、TDengine。虽然这些是主流系统，但结论是否适用于图数据库、向量存储等不同架构的 DBMS 需要谨慎。

2. **测试环境的真实性**：Fawkes 主要在 QEMU/Docker 环境中运行，使用自定义的 glibc/JVM 库注入故障。在真实的物理服务器、真实的磁盘故障（而非模拟的内存分配失败）、真实的电源故障等场景下的有效性未充分验证。

3. **故障类型的覆盖**：虽然论文提到了 7 种故障类型（power failure、memory exhaustion、internal shutdown、process killed、kernel crash、disk I/O failure、software exception），但这些是否涵盖了真实生产环境中的所有关键故障模式值得商榷。特别是磁盘介质的部分写入故障（partial write）或存储控制器的 silent corruption 未被涵盖。

4. **数据图验证的完整性**：数据图验证聚焦于元数据（表结构、约束、行数），但未明确说明如何验证数据的具体值是否正确。例如，如果某个 UPDATE 语句的结果在 crash 后部分持久化，数据图如何检测？论文的表述主要关注 row count 和 metadata consistency，对数据值的精确验证说明不足。

5. **与 Jepsen 的不公平比较**：Jepsen 是一个专注于分布式系统一致性的测试框架，而 DDB 关注的是单节点 DBMS 的 crash recovery。Fawkes 与 Jepsen 的比较可能在某种程度上不公平，因为两者的设计目标本就不同。论文声称 "existing tools designed for verifying distributed node correctness" 无法 addressing single-node issues，但 Jepsen 的核心贡献恰恰不是这一点。

6. **误报率未明确报告**：虽然声称能够检测 bug，但 Fawkes 自身的误报率（false positive rate）未在论文中明确报告。这对于一个测试工具来说是一个重要的指标。

7. **checkpoint 频率对测试效率的影响**：论文提到降低 checkpoint 频率会降低测试效率，但未深入分析最优的 checkpoint 配置策略。这是一个重要的工程调参问题。

## 未来工作

1. 将 Fawkes 扩展到分布式 DBMS 的数据持久性测试
2. 将功能引导的工作负载生成与 grammar-based SQL 生成相结合，提升测试覆盖率
3. 开发更精细的数据值级别验证能力，不仅验证元数据还验证具体数据值
4. 扩展到更多的 DBMS 架构和更多的故障类型

## 个人评注

Fawkes 是一项扎实、实证驱动的工作。43 个真实 DDB 的深度分析是这篇论文最宝贵的贡献——它让我们首次系统性地理解了这类 bug 的模式。72% 的 DDB 来自 crash recovery 或 data flushing 逻辑缺陷这一发现尤其发人深省：这意味着即便在 WAL 和 checkpoint 等成熟机制之上，bug 仍然广泛存在。

框架的三个技术创新——上下文感知故障注入、功能引导触发、checkpoint 数据图验证——形成了一个紧密耦合的系统。消融实验清晰地证明了每个组件的必要性，尤其是功能引导触发，相比纯随机注入能多发现约 20 倍的 bug。

但最令人印象深刻的是实际影响力：48 个新 bug、16 个修复、8 个 CVE——这是实打实的工程贡献，而非理论工作。值得注意的是，许多 bug 的修复时间极短（有的仅 2 小时），这说明这些 bug 其实并不难修复，只是之前的测试工具根本没有覆盖到这些代码路径。这恰恰凸显了工具驱动测试的价值：发现问题往往比解决问题更难。
