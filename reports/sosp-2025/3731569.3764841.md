# Fawkes: Finding Data Durability Bugs in DBMSs via Recovered Data State Verification

**作者**：Zhiyong Wu（清华大学）、Jie Liang*（北京航空航天大学）、Jingzhou Fu（清华大学）、Wenqian Deng（清华大学）、Yu Jiang*（清华大学）

**源文件**：[3731569.3764841.pdf](../../papers/sosp-2025/3731569.3764841.pdf)

## 一、背景

数据库管理系统（DBMS）是现代软件基础设施的核心组件，管理着大量关键业务数据。数据持久性（Data Durability）是 DBMS 的基本保证：一旦事务提交，其数据必须在任何意外故障（掉电、进程崩溃、磁盘错误等）后依然完整可恢复。

为实现这一保证，DBMS 普遍实现了 Write-Ahead Logging（WAL）、Checkpoint、ARIES 等机制：先将操作记录到日志，再通过周期性 checkpoint 将脏页刷盘，崩溃后从最近 checkpoint 回放日志恢复已提交数据。这些机制在理论上是正确的，但实现极为复杂，现实中常出现实现缺陷，导致已提交数据在崩溃恢复后丢失或不一致——作者将这类缺陷称为 **Data Durability Bugs（DDBs）**。

---

## 二、要解决的问题

**DDB 的理解与检测均不充分：**

1. **缺乏系统研究**：DDB 的表现形式、根本原因、触发条件缺乏深入的实证研究，导致检测方法缺乏针对性设计。

2. **现有测试方法局限性大**：
   - **手工测试**：劳动密集、覆盖率低，难以发现隐藏在文件系统调用深处的 DDB。
   - **随机故障注入工具**（Jepsen、Mallory、CrashFuzz 等）：为分布式系统设计，随机注入故障往往错过与特定执行状态绑定的 DDB；正确性检验粗粒度（只检查系统可用性），无法发现单节点 DBMS 的数据丢失和数据不一致。

3. **三大技术挑战**：
   - 如何精确地在文件系统/内核调用点注入故障？
   - 如何系统性地覆盖鲜少执行但 durability-critical 的代码路径？
   - 如何在崩溃恢复后准确验证数据完整性（预期恢复状态难以计算）？

---

## 三、核心设计

作者首先对 43 个真实 DDB 进行了深度研究（来自 PostgreSQL、MySQL、IoTDB、TDengine），得出若干关键发现：

- **表现形式**：数据丢失（33%）、数据不一致（31%）、日志损坏（20%）、系统不可用（16%）
- **根本原因**：72% 源于崩溃恢复或数据刷盘逻辑的缺陷
- **触发模式**：四步序列——初始数据创建 → checkpoint 执行 → 故障注入崩溃 → 崩溃恢复后验证
- **关键发现**：86% 的 DDB 只有在 SQL 语句正在执行文件系统调用或内核调用时才能可靠触发

基于以上发现，作者设计了 **Fawkes**，包含三大核心组件：

### 1. Context-Aware Fault Injection（上下文感知故障注入）

通过编译期调用依赖图分析，识别所有最终调用 OS 基础库（如 glibc 文件系统接口）的代码路径，标记为**故障注入点（fault injection sites）**。用库劫持（library hooking）方式拦截 `open`、`read`、`write`、`malloc` 等调用，在运行时动态注入故障（掉电模拟、内存耗尽、磁盘 I/O 错误等 7 类）。

维护 **Fault Location Bitmap** 追踪各注入点的覆盖状态。

### 2. Functionality-Guided Fault Triggering（功能引导的故障触发）

构建 **Fault-Functionality Table**：将故障注入点所在源文件与其对应的 SQL 功能（INSERT、ALTER、CREATE JSON、外键约束等）关联。

测试时优先选择低覆盖率的注入点，并根据该点对应的 SQL 功能反向引导 workload 生成器（基于 SQLsmith 改造），生成能触达这些路径的 SQL，系统性覆盖 durability-critical 的代码分支。

### 3. Checkpoint-Based Data Graph Verification（基于 checkpoint 的数据图验证）

- **数据图构建**：追踪所有 SQL 执行，构建元数据图（表、列、行数、约束），而非存储完整数据集（开销过大）。
- **数据图修正**：崩溃后，根据恢复日志找到最近 checkpoint，将图回滚到 checkpoint 时刻，再用日志中记录的待重放 SQL 更新图，计算出预期恢复状态。
- **状态对比验证**：将恢复后 DBMS 的实际元数据与预期图对比，检测数据丢失（缺失表/行/约束）、数据不一致（列类型错误、行值错误）、日志损坏（恢复错误信息）、系统不可用（恢复异常）。

## 四、实现细节

- 代码规模：约 10k 行 C++（工作负载生成器、故障触发器、数据图验证器）+ 5k 行 Rust + 4k 行 Bison/Flex（SQL 语法文件适配）
- 故障注入器：修改 Glibc 和 JVM 库，约 3k 行 C + 4k 行 Java 的自定义动态库
- SQL 生成器：基于 SQLsmith，适配了 PostgreSQL、MySQL、MariaDB、IoTDB、TDengine 等各自的官方语法文件（Bison/Flex 格式）
- 数据生成：随机创建含 10～100 列的表，随机施加 BTREE 索引、外键约束，周期性填充数据
- 故障类型支持 7 种：掉电、内存耗尽、内部 shutdown 命令、进程强杀、内核崩溃、磁盘 I/O 失败、未处理软件异常
- Bug 复现：记录完整的 workload 序列、注入点、注入时机，用确定性触发器替换随机条件，保证可复现

## 五、实验结果

**测试对象**：PostgreSQL、MySQL、MariaDB、IoTDB、TDengine、GridDB、CnosDB、OpenGemini（8 个 DBMS）

### 主要结果（两周测试）

Fawkes 共发现 **48 个此前未知的 DDB**，其中 16 个已修复，8 个被分配 CVE 编号。

### 与 baseline 对比（72 小时）

| 工具 | 发现 DDB 数 | 覆盖代码分支数 |
|------|------------|--------------|
| Jepsen | 2 | 174,604 |
| CrashFuzz | 4 | 216,985 |
| Mallory | 6 | 218,135 |
| CrashTuner | 1 | 188,810 |
| **Fawkes** | **29** | **320,848** |

Fawkes 比 Jepsen / CrashFuzz / Mallory / CrashTuner 多发现 27 / 25 / 23 / 28 个 bug，分支覆盖率分别高出 84% / 48% / 47% / 70%。

### 消融实验（72 小时）

| 配置 | DDB 数 | 分支覆盖 |
|------|--------|---------|
| Fawkes_mal（随机注入，仅检测不可用） | 2 | 178,460 |
| Fawkes_i（+上下文感知注入） | 5 | 233,177 |
| Fawkes_i+t（+功能引导触发） | 8 | 326,899 |
| Fawkes_all（+数据图验证） | 29 | 320,848 |

数据图验证引入约 2.8% 运行开销（分支减少 1.8%），但额外发现 21 个 bug。

### 历史 bug 重发现（两周）

对 43 个已知 DDB 进行重发现实验，两周内成功重现 39 个（**91%**），首周达 34 个（79%）。

## 六、批判性分析

**1. "86% 触发条件"发现的泛化性**

论文将 86% DDB 需在文件系统调用时注入故障作为核心设计依据。但该统计来自 4 个 DBMS 的 43 个 bug，样本集相对偏小，且作者自认会偏向 fault-induced 类型的 bug（logic bug 被排除）。这一比例是否能泛化到所有 DBMS 架构（内存数据库、列存、图数据库等）并未论证。

**2. 48 个 bug 的质量参差不齐**

表 2 中 48 个 bug 有 28 个仍处于 "Confirmed" 状态（未修复），开发者的确认速度和态度因项目而异。8 个 CVE 主要集中在相对小众的 DBMS（IoTDB、TDengine、MariaDB），PostgreSQL 和 MySQL 各仅发现 1-2 个，说明对成熟 DBMS 效果一般。

**3. baseline 比较不公平**

论文将 Jepsen、CrashFuzz 等分布式系统测试工具作为 baseline，这些工具本来就不是为单节点 DBMS DDB 设计的。文中也承认"这些工具无法检测数据丢失和不一致"，这等于在一个自己占有结构优势的赛道上跑比赛，72 小时的 bug 数差距（2 vs 29）大部分来自检测能力的本质差异，而非算法效率的优劣。

**4. 开销分析的问题**

表 7 显示持续故障注入使测试用例执行次数减少 64.8%（140 万 vs 407 万），这是相当大的吞吐损失。论文将其定性为"可接受的开销"，但没有分析在此吞吐下 Fawkes 是否比简单运行更多测试用例的随机工具更高效，即"单位时间发现 bug 数"的比较缺失。

**5. 数据图只追踪元数据**

为控制开销，Fawkes 的数据图只记录行数、约束等元数据，而非实际数据值。这意味着某些数据不一致（如行存在但数值被错误恢复）需要依赖 DML 重放后验证，覆盖并不完整，论文对此仅轻描淡写。

**6. Fault-Functionality Table 的维护成本**

该 Table 需要根据文档/代码手工或半自动构建，论文未说明构建成本，也未讨论代码演化时 Table 是否需要同步更新，这影响工具的实际可维护性。

---

## 七、总结

Fawkes 是针对 DBMS 数据持久性 bug（DDB）的自动化测试框架，通过对 43 个真实 DDB 的系统研究找到设计依据，提出三个互补机制：上下文感知故障注入（定点 hook 文件系统/内核调用）、功能引导触发（覆盖引导 + SQL 语义驱动的 workload 生成）、基于 checkpoint 的数据图验证（计算预期恢复状态并对比）。在 8 个主流 DBMS 上发现 48 个此前未知 DDB，91% 历史 bug 可重现，分支覆盖率和 bug 检出数显著优于现有工具。主要局限是对成熟大型 DBMS（PostgreSQL/MySQL）的效果有限，baseline 选取存在结构性优势，且数据图仅追踪元数据、持续故障注入开销较大。
