## 一、背景

随着 LLM 在模型规模和输入序列长度上不断增长，单个算子（尤其是 Attention 和 GEMM）的计算与内存需求已远超单 GPU 的承载能力。例如 Llama-3 70B 的 KV cache 就需要 282GB，远超 H100 的 80GB HBM。因此多 GPU 算子设计不仅是性能优化，更是大规模模型训练和推理的基本需求。

然而，多 GPU 算子优化目前高度依赖手工调优。仅过去两年就有超过 20 篇论文针对 Attention 和 Linear 两个算子提出不同的手工优化方案（如 RingAttention、Ulysses、USP、LoongTrain 等）。这些方案紧密耦合于特定硬件和模型配置，难以在新设置下复用，且随着新一代硬件（如 NVLink 72 互联的 B100）出现，手工调优变得越来越不可行。

现有的多 GPU 编译器（如 Alpa、Centauri、torch.compile）在 LLM 算子优化上表现不佳，持续落后于手工实现。

---

## 二、要解决的问题

1. **局限的内存模型**：现有多 GPU 编译器采用 local-memory-centric 执行模型，假设所有输入数据必须在计算前完全存在于每个 GPU 的本地内存中。这导致编译器默认采用同步执行模式——共享输入被完全复制到每个设备，所有设备按相同顺序执行，浪费宝贵的 HBM 容量。

2. **设计空间受限**：由于上述假设，编译器无法探索利用远程 GPU 内存作为共享数据存储的异步执行模式。这限制了计算-通信重叠、更深层 tiling 等优化机会。

3. **缺乏统一抽象**：现有编译器缺乏将计算、内存和通信统一在一个调度空间中的抽象，难以表达涉及远程数据复用或跨设备调度的结构化模式。

4. **手工方案不可泛化**：每种手工优化方案（Ring、Ulysses、USP 等）只在特定配置下最优，面对多维度的配置组合（GPU 数量、网络拓扑、算子参数），人工逐一调优不可行。

---

## 三、洞察与设计

**关键洞察**：远程 GPU 内存可以被视为内存层次结构中的一个一等（first-class）可调度层——与本地 HBM 同等对待。在这种抽象下，设备间通信不再仅用于交换算子间的中间结果，而是用于在设备之间访问共享输入数据。这使得编译器能够通过让不同设备在时间上错开对共享数据的访问（shifted asynchronous schedule），将数据存储在由所有 GPU 聚合的更大远程内存池中，按需传输到本地设备。

基于这一洞察，Mercury 设计了以下核心组件：

**CommIR（Communication IR）**：一种基于循环的中间表示，扩展了传统 tensor compiler 的循环 IR，引入四个关键变换原语：
- **Parallelize**：将循环迭代分配到设备网格的特定层级，实现工作负载划分
- **Shift**：将本地循环的索引相对于并行循环进行偏移，引入异步访问模式，使不同 rank 在不同时间步访问共享数据
- **Shard**：将 buffer 分片到不同 worker，每个 rank 持有不相交的部分
- **Replicate**：在所有参与并行循环的 worker 间复制 buffer

这四个原语统一支持标准的 intra-GPU tiling 和高级的 inter-GPU 调度模式。通过对任意循环维度组合应用这些变换，CommIR 能表达所有已知的手工优化策略（Context Parallel、Ulysses、RingAttention、USP、LoongTrain、TreeAttention 等），并能发现人工设计尚未探索的新策略（如 Shift Reduce、Hybrid Pattern 等）。

**分阶段设计空间搜索**：将搜索分为计算调度（tiling、reordering）和通信调度（parallelize、shift、shard、replicate）两个阶段，结合硬件 mesh 配置约束，减少搜索空间。

**代码生成管道**：通过符号分析 CommIR 上的循环索引变换和 buffer 注释，自动推导 P2P 或 collective 通信模式，并将本地计算部分 lower 到 TorchInductor，可选用 FlashAttention 等优化库替换匹配的子图。

## 四、实现细节

- **DSL**：基于 PyTorch 前端扩展的 Python-like DSL，核心抽象包括 Axis（循环变量）、Buffer（通过 `match_buffer` 绑定形状和存储语义）、Grid（定义迭代空间，支持 spatial/reduction 标注）
- **变换原语实现**：计算原语通过结构化重写规则改写循环嵌套树；通信原语以注释形式挂在循环和 buffer 节点上，延迟到 lowering 阶段再物化为通信代码
- **Patch 机制**：支持将匹配的子图替换为预优化库调用（如 FlashAttention、cuDNN），通过子图模式匹配实现
- **通信代码生成**：P2P 通信通过符号偏移公式推导 sender/receiver rank；collective 通信（AllGather、ReduceScatter、AllReduce）通过分析 buffer 分片/复制注释和聚合语义自动合成
- **Inter-Operator Resharding**：维护分布式算子配置数据库，通过 DAG 上的全局搜索（Algorithm 1）找到最优 sharding 组合，最小化算子执行延迟 + resharding 通信开销
- **实现栈**：CUDA 12.6、NCCL 2.26.2、PyTorch 2.8（TorchInductor）
- **Auto-tuner 收敛时间**：每个算子约 10 分钟内完成调优

## 五、实验结果

### 实验平台

| 配置 | L4 | A100 | H100 |
|------|-----|------|------|
| FP16 TFLOPs | 242 | 312 | 1979 |
| HBM | 24GB | 40GB | 80GB |
| 内存带宽 | 300 GB/s | 1555 GB/s | 3350 GB/s |
| 节点内互联 | PCIe | NVLink | NVLink |
| 节点内带宽 | 64 GB/s | 600 GB/s | 900 GB/s |
| 节点间带宽 | 50 Gbps | 50 Gbps | 100 Gbps |

### 主要结果

| 场景 | Mercury 表现 |
|------|-------------|
| Attention 算子（H100 2×4, MHA BS=16） | 最高 4× speedup over baselines |
| 跨所有 Attention/GEMM 基准 | 平均 1.56× speedup over SOTA 手工设计 |
| 网络拓扑适应性（多种 node×GPU 配置） | 平均 2.91× speedup |
| 序列长度扩展（32K → 2M tokens） | 持续优于所有 baseline，2M 时其他方案 OOM 而 Mercury 仍可运行 |
| 模型级（Llama3-8B/70B, 2×4 / 4×2 H100） | 相比 3D Parallel 最高 1.62× 性能提升 |

### 关键发现

- Mercury 在所有硬件平台（H100、A100、L4）和所有算子配置上一致取得最优性能
- GQA 场景下 Ulysses 因依赖 head-wise 分区而性能下降，Mercury 自动适应
- 在复杂混合拓扑（如 2×4、4×2）中优势更为显著
- 2M token 时 Mercury 通过激进 shard KV cache 避免 OOM，其他方案均失败
- 模型级优化中，resharding 开销的大幅减少是性能提升的关键因素

## 六、批判性分析

1. **Auto-tuner 的可扩展性隐忧**：论文承认 10 分钟/算子的调优时间可能随算子复杂度和 mesh 拓扑增大而增长，但没有给出具体的渐近复杂度分析。对于实际部署中可能有数十种不同算子配置的场景，调优总时间可能不可忽视。

2. **搜索空间剪枝的隐含假设**：论文将 parallelize 和 shift 与对应的 shard/replicate 捆绑在一起以减少搜索空间，承认这"理论上可能排除某些有效的 trade-off"。虽然声称"评估的工作负载中没有出现这种模式"，但这恰恰意味着这个简化可能在未来遇到的新算子上失效。

3. **评估基线的公平性**：与 USP 的比较报告的是"USP 设计空间中的最优结果"，但 USP 本身的模板是为通用性设计的，而非为每个具体配置手工极致优化。真正公平的比较应该是与针对每个配置单独编写的最优手工 kernel 对比。

4. **实验规模有限**：模型级评估仅做了单个 Transformer 层的基准测试，batch size 仅为 1，序列长度仅 4096。这是一个非常小的设置，难以反映实际训练/推理场景中的端到端收益。论文没有报告完整模型的训练 throughput 或推理延迟。

5. **对 fused kernel 的回避**：论文明确将 fused distributed operators（如 Flux、Comet、TileLink）列为 future work，但这些正是工业界实际部署中的 SOTA 方案。Mercury 生成的非 fused 算子在实际系统中的竞争力存疑。

6. **静态算子限制**：Mercury 目前仅支持静态算子，不支持 MoE 等动态路由算子。虽然论文提到了可能的扩展方向，但考虑到 MoE 在现代 LLM 中的普及，这是一个重要的功能缺失。

7. **Speedup 数据分散性大**：4× speedup 仅出现在特定最优配置（MHA BS=16 on H100），而在许多配置下（尤其是 GEMM、单层级拓扑）提升要小得多。"平均 1.56×"这个数字的 variance 较大，论文没有充分讨论在哪些场景下提升有限以及原因。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **远程内存作为一等调度资源的思路**：这个抽象超越了传统的"通信是算子间结果交换"的视角，对设计下一代分布式推理引擎有重要参考价值。特别是在 KV cache 越来越大的长上下文推理场景中，将远程 GPU 内存纳入统一调度可以实现更灵活的 KV cache 管理。

2. **循环变换统一计算与通信**：CommIR 的 shift 原语优雅地将异步通信模式编码为循环索引偏移，这种思路可以迁移到其他需要计算-通信重叠的场景，如 pipeline parallelism 的 micro-batch 调度。

3. **自动化搜索 vs 手工模板**：Mercury 的成功再次验证了在足够大的设计空间上进行自动搜索可以超越人类专家的直觉。这对 AI Infra 工具链的发展方向有启示——投入在搜索基础设施上可能比投入在单个手工优化上更有长期价值。

### 值得跟进的方向

1. **将 CommIR 扩展到 fused kernel 场景**：论文明确列为 future work，也是最有价值的延伸。将 shift 原语的语义与 tile-level 的 compute-communication fusion 结合，有可能同时获得 Mercury 的搜索灵活性和 Flux/TileLink 的 fusion 性能。

2. **动态算子支持**：将 CommIR 扩展到 MoE 的 dynamic routing、speculative decoding 等场景，需要在 IR 层面引入条件执行和动态形状支持。

3. **与 cost model 结合加速调优**：当前的 profiling-based tuning 在大规模场景可能太慢，将 CommIR 的结构化信息与 learned cost model 结合是一个务实的改进方向。

4. **跨层/跨算子的全局优化**：当前的 graph-level search 仍然是简单枚举，对于深度模型中的 resharding chain 优化，可以引入动态规划或 ILP 求解。

---

## 八、总结

Mercury 提出了将远程 GPU 内存作为一等可调度资源的编译器抽象 CommIR，通过 parallelize、shift、shard、replicate 四个变换原语统一表达计算、内存和通信调度，自动搜索最优的多 GPU 算子执行策略。在 Attention 和 GEMM 算子上，Mercury 能自动复现甚至超越 RingAttention、Ulysses、USP 等手工优化方案，平均获得 1.56× speedup。其主要局限在于目前仅支持静态算子、未覆盖 fused kernel 场景，且模型级评估的规模较小。Mercury 最适合作为 AI Infra 编译器栈的中间层，连接上层计算图优化与下层单 GPU kernel 编译。
