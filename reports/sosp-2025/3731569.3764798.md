## 一、背景

随着 LLM 在模型规模和输入序列长度上持续增长，注意力（Attention）和 GEMM 等核心算子的计算和内存需求已超出单个 GPU 的承载能力。例如，Llama-3 70B 的 KV cache 在 32K 上下文时即高达 282 GB，远超 NVIDIA H100 的 80 GB HBM。多 GPU 算子设计因此不再只是性能优化，而是大规模模型训练和推理的基本前提。

现代多 GPU 系统拥有异构互联拓扑：NVLink mesh 提供约 900 GB/s 的节点内带宽，而 RoCE/InfiniBand 节点间带宽仅约 100 Gbps，差距超过 70 倍。如何在这样的层级拓扑中高效调度计算与通信，是该领域的核心挑战。

---

## 二、要解决的问题

**现有方案均建立在"本地内存中心"的执行模型上**，即所有输入数据必须在本 GPU 的 HBM 中完全就绪后才能开始计算，设备间通信只是交换中间结果的机制。这导致：

1. **设计空间狭窄**：现有手工优化方案（RingAtten、Ulysses、USP、LoongTrain 等）超过 20 篇论文仅针对 Attention 和 Linear 两个算子提出 ad-hoc 方案，相互之间难以泛化，强烈依赖特定硬件和模型配置。
2. **共享输入被全量复制**：同步调度下每个 GPU 都保存完整的共享输入（如 KV activation），浪费 HBM 并限制 tiling 深度。
3. **现有编译器无法表达异步模式**：学术编译器（Centauri、CoCoNet、Alpa）要么依赖模板，要么仅支持同步通信模式；工业编译器（torch.compile）多 GPU 支持简单且性能落后于手工实现。
4. **工程成本极高**：每次新硬件、新模型配置都需重新手工调优，随着 NVLink 72 等新硬件出现愈发不可行。

---

## 三、核心设计

Mercury 的核心洞察是：**将远端 GPU 内存视为内存层级中可显式调度的一等公民**，与本地 HBM 并列管理。设备间通信由此成为访问共享输入的手段，而不仅是交换中间结果的机制。这一抽象极大地扩展了可探索的调度空间。

### CommIR：统一计算、内存与通信的循环 IR

CommIR 扩展了传统的循环基 IR（如 TVM），引入四种变换原语：

| 原语 | 作用 |
|------|------|
| **Parallelize(loop, mesh_level)** | 将循环维度分配到指定网络层级的设备上 |
| **Shift(local_loop, parallel_loop)** | 偏移本地循环索引，使各设备以错开时间步访问共享数据，引入异步 P2P 通信 |
| **Shard(buffer, loop)** | 将缓冲区切分到各设备 |
| **Replicate(buffer, loop)** | 将缓冲区复制到各设备 |

**Shift 原语的关键作用**：将同步调度（设备同时访问相同的数据块）变为异步调度（设备错开访问数据块，数据可以仅存在于聚合的远端内存池中，按需传输）。这样既减少了单设备 HBM 占用，又天然实现了计算与通信 overlap。

**Collective 通信自动合成**：从 Shard/Replicate 注解出发，Mercury 通过规则推断出 AllGather、ReduceScatter、AllReduce 等集合通信；无法用 collective 表达时降级为 P2P。

### 系统架构

```
DSL (Python) → CommIR 解析 → 计算调度（Tile/Reorder/Patch）
                           → 通信调度（Parallelize/Shift/Shard/Replicate）
                           → 代码生成（通信 kernel + TorchInductor 本地 kernel）
                           → Auto-Tuner（设计空间搜索）
```

Mercury 定位为编译器中间层：上接计算图优化（Alpa 等），下连 TorchInductor/FlashAttention 等 kernel 库。

## 四、实现细节

**DSL**：基于 PyTorch frontend 扩展，引入 Axis、Buffer（match_buffer API）、Grid 三个抽象。循环变量携带分布元数据（mesh 层级映射、shift 偏移）。"srs"等注解指定 spatial/reduction 语义，影响通信模式。

**CommIR 变换**：通过结构化重写规则遍历循环树，变换可组合、可多趟执行（referential transparency）。Patch 原语实现子图替换（如将内层循环替换为 FlashAttention 调用），通过 pattern-to-kernel 规则注册。

**代码生成两阶段**：
1. **通信 kernel 合成**：静态分析循环索引变换推导 P2P 的 send/receive 对；对带 Shard/Replicate 注解的缓冲区推导 collective 操作类型（基于聚合语义 + buffer 布局规则匹配）。
2. **本地计算 lowering**：CommIR 保留循环层次结构，自然对接 TorchInductor；compute-intensive 区域可选调用 FlashAttention patch。

**Inter-Operator Resharding**：构建算子 DAG，枚举各算子的 sharding 配置组合，通过全局搜索（Algorithm 1）最小化 per-operator 执行时延 + 边上 resharding 通信时延之和。

**Auto-Tuner**：分两阶段——先搜索本地计算调度（tile、reorder），再搜索通信调度（parallelize、shift 组合）。受 mesh 大小约束剪枝，静态检查内存可行性。实测每个算子约 10 分钟完成调优。代码开源于 https://github.com/ChandlerGuan/mercury_artifact。

## 五、实验结果

### 测试平台

| GPU | TFLOPs@FP16 | HBM | 节点内带宽 | 节点间带宽 |
|-----|-------------|-----|------------|------------|
| H100 | 1979 | 80 GB | 900 GB/s (NVLink) | 100 Gbps |
| A100 | 312 | 40 GB | 600 GB/s (NVLink) | 50 Gbps |
| L4 | 242 | 24 GB | 64 GB/s (PCIe) | 50 Gbps |

配置：2×4（2 节点 × 4 GPU）或 4×2，RoCE 互联。

### Operator Benchmark（vs. Ring/Ulysses/USP/AsyncTP/Inductor）

| 指标 | 结果 |
|------|------|
| Attention 平均 speedup vs. USP+Ulysses | 1.56× |
| H100 MHA (BS=16) 最高 speedup | **4×** |
| GEMM (AG, BS=16, A100) speedup | 1.9× |
| 跨拓扑平均 speedup | **2.91×** |

- Ulysses 在 GQA（head 数少）时性能显著下降，Mercury 不受此限制
- USP 的设计空间（CommIR 表示）仅是 Mercury 全空间的一个窄子集

### 模型级评估（Llama3-8B / 70B，序列长 4096，BS=1）

Mercury 在 2×4 和 4×2 H100 配置下均比 3D Parallel（DP+TP+CP）显著降低时延（归一化后约 0.6~0.8×），提升达 **1.62×**，同时减少 resharding 开销。

### 序列长度扩展性（MHA，2×4 H100）

- 从 32K 扩展到 2M tokens，Mercury 始终优于所有基线
- **2M token 时其他基线 OOM，Mercury 通过激进 sharding KV/output tensor 正常运行**

## 六、批判性分析

**优点明确，但有几处值得深究：**

1. **Tuning 时间仅 10 分钟——数据来自特定算子，未必可泛化**。论文承认"搜索成本可能随算子复杂度或 mesh 拓扑增大"，但对复杂多算子模型（如 MoE）的调优代价完全未评估。对于 NVLink 72、B100 等新硬件，是否需要重新 profile 全部候选？

2. **模型级对比只选了 3D Parallel 作为 baseline，没有对比专用系统（如 Megatron-LM）**。Megatron 在 sequence parallel + 算子融合方面有大量优化，是更有说服力的对比点。

3. **设计空间分析图（Fig.13）只展示了 MHA on 2×4 H100 这一种配置**。作者声称发现"手工设计未曾探索的新策略"，但仅有一个算子/配置的证据，说服力有限——新策略在 GEMM 上是否也优于手工？

4. **Shift 原语的限制被轻描淡写**："shifting without sharding produces no semantic change"，因此 parallelize 和 shift 被捆绑在一起，可能排除了某些 selective shard 的有效 trade-off，只是"目前评估的 workload 中没有体现"。

5. **只在 MHA/GQA/GEMM 三种算子上评估**，对 Flash Decoding、Sparse Attention、MoE 路由等近年关注的算子没有讨论。论文将其列为 future work，但这些算子恰是 CommIR Shift 原语最难直接复用的场景。

6. **图表排版较差，Fig.7、Fig.9 等因 PDF 提取混乱，实际论文中的关键数据（speedup bar 的具体数值）依赖视觉判读而非表格**，复现对比困难。

## 七、AI Infra / MLSys 视角

Mercury 是 SOSP 2025 中与 MLSys 最直接相关的论文之一，以下从 AI Infra 研究者视角评估：

**核心 insight 的迁移价值**

"将远端 GPU 内存视为可调度内存层级"这一抽象高度可迁移：
- 用于 **KV cache 卸载与预取**的调度：现有系统（如 vLLM）将 CPU 内存视为 KV cache 的 swap 空间，但调度粒度粗。CommIR 的 Shift+Shard 思路可启发更细粒度的 KV block prefetch pipeline。
- 用于 **disaggregated prefill-decode** 场景（PD 分离架构）：P2P KV 传输的调度与 Mercury 的 shift primitive 高度同构，可借鉴其编译器化的思路而非手工设计 transfer protocol。

**值得跟进的 future work**

1. **Fused kernel 支持**：Mercury 目前不支持 Flux/Triton-Distributed 风格的 tile 级通信-计算融合，这是目前性能上的天花板（论文明确列为开放问题）。在 CommIR 上引入 tile-level pipeline primitive 是最直接的延伸方向。
2. **Cost model 替代 profiling**：当前 auto-tuner 依赖实测，调优 10 分钟。引入 analytical cost model（类似 roofline + alpha-beta 通信模型）可将搜索加速并支持无硬件推断。
3. **MoE / Dynamic routing 支持**：Comet 等已在探索，CommIR 的 shift primitive 如何扩展到 ragged tensor 上是可操作的研究问题。
4. **与 FlashAttention-3 / Triton 的深度集成**：Mercury 目前通过 Patch 调用 FA，但 FA 的 intra-kernel pipeline 与 Mercury 的 inter-kernel 调度是正交的，联合优化空间值得探索。

---

## 八、总结

Mercury 通过引入 CommIR 这一将远端 GPU 内存纳入调度空间的循环 IR，从根本上打破了现有多 GPU 编译器"本地内存中心"的限制，实现了对 Attention 和 GEMM 算子自动生成高效分布式执行策略，平均超过手工调优方案 1.56×，在 2M token 序列长度等极端内存压力场景下展现出明显优势。其主要局限在于：当前仅支持 MHA/GQA/GEMM 等静态算子，不支持 tile 级融合 kernel，调优成本在复杂算子上尚未充分评估；此外，模型级对比 baseline 选取保守，缺乏与 Megatron-LM 等成熟系统的正面比较。
