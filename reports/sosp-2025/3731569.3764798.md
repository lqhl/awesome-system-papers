# Mercury: Unlocking Multi-GPU Operator Optimization for LLMs via Remote Memory Scheduling

## 1. 论文基本信息

- **标题**: Mercury: Unlocking Multi-GPU Operator Optimization for LLMs via Remote Memory Scheduling
- **作者**: Yue Guan, Xinwei Qiang, Zaifeng Pan, Daniels Johnson, Yuanwei Fang, Yuke Wang, Wanlu Li, Adnan Aziz, and San Diego
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764798
- **代码**: https://github.com/ChandlerGuan/mercury_artifact

## 2. 研究背景

**LLM 的计算和内存需求爆炸**：随着 LLM 规模增大和输入序列增长（如 32K tokens），单个算子（尤其是 attention 和 GEMM）的计算和内存需求超出了单个 GPU 的容量。例如，Llama-370B 的 KV cache 需要 282 GB，远超 H100 GPU 的 80 GB HBM。

**Multi-GPU 算子优化的手工困境**：过去两年内，超过 20 篇论文针对 attention 和 linear 两个算子提出了不同的手工优化设计。这些手工优化与特定硬件和模型配置高度耦合，随着 NVIDIA B100 等新硬件和更长上下文场景的出现，手工优化变得越来越不切实际。

**现有 Multi-GPU Compilers 的不足**：
- **学术编译器**：尚未发现包含 recent hand-optimized multi-GPU 算子设计的设计空间
- **工业编译器**：如 torch.compile，仅提供简单的 multi-GPU 支持，性能普遍低于手工实现

**根本原因**：现有编译器采用"local-memory-centric"执行模型——假设所有输入必须在计算前完全加载到每个 GPU 的本地内存。这导致 inter-device 通信被限制为"算子之间交换中间结果"，迫使编译器默认使用 fully-synchronized 执行模式：共享输入在所有设备间完全复制，计算在所有设备间严格同步。

## 3. 要解决的问题

**核心问题**：如何设计一个自动化的 multi-GPU 算子编译器，能够：
1. 探索比手工设计更大的设计空间
2. 自动复现甚至超越 SOTA 手工优化的性能
3. 泛化到不同硬件配置（不同 GPU 数量、互联拓扑）和算子配置（不同 head count、sequence length）

具体挑战：
- 缺乏统一 abstraction 同时建模计算、内存和通信
- 难以表达 remote memory 作为共享存储资源的调度模式
- 自动生成高效 collective primitives 的复杂性

## 4. 核心贡献

1. **CommIR**：首个 loop-based 中间表示，将 remote GPU memory 作为 memory hierarchy 的第一等公民，统一建模计算、内存和通信。
2. **Modular Compiler**：通过 parallelize、shift、shard、replicate 四个 structured transformation 原语，自动生成高效的 multi-GPU 算子执行计划。
3. **Automated Collective Synthesis**：通过 CommIR 的 transformation passes，自动生成 collective communication（如 ring-style pass）而非依赖固定模板。
4. **SOTA 性能超越**：相比 USP 和 Ulysses 等 SOTA 手工设计，**平均 1.56x speedup**；相比 model-level 3D-parallel，real LLM 工作负载上最高 **1.62x 性能提升**。

## 5. 主要研究方法

### 5.1 现有编译器的分析
- 现有编译器的 local-memory-centric 执行模型限制了优化空间
- 手工优化（如 Ring Attention、Ulysses）的核心洞察未被编译器抽象捕获

### 5.2 Remote Memory as First-Class Abstraction
关键洞察：将 remote GPU memory（其他 GPU 的 HBM）视为 memory hierarchy 的第一等公民，类比 local HBM。这使得 inter-device 通信从"中间结果交换"重新定义为"共享数据的访问"。

### 5.3 CommIR 设计
CommIR 扩展传统 loop-based IR，增加了通信驱动的 transformation 原语：

- **parallelize**：在 loop 维度上的并行化
- **shift**：时间偏移——设备错开对共享数据的访问
- **shard**：数据分片——不同设备处理数据的不同部分
- **replicate**：数据复制——在多设备间复制数据

### 5.4 Shift Asynchronous Schedule
关键设计：设备错开对共享数据的访问时间，实现 temporal decoupling：
- 允许共享输入在汇聚的 remote GPU memory pool 中暂存
- 按需传输到本地，减少 local memory 压力
- 启用更好的 compute-communication overlap

这个 schedule 构成了 Ring Attention 和 Ulysses 等 recent hand-optimized operators 的基础，但实现更为灵活。

## 6. 设计与实现

### 6.1 CommIR 核心抽象
```
Loop Nest with Comm Primitives:
  For i in parallel_dim {       // parallelize
    For j in inner_dim {
      Send/Receive operations    // shift, shard
      Compute on local data
    }
    AllReduce/AllGather         // replicate
  }
```

CommIR 将 loop nest 与通信操作统一表示，使得 transformation passes 可以同时优化计算和数据移动。

### 6.2 Transformation Passes
- **parallelize**：在指定 loop 维度上引入设备级并行
- **shift**：引入循环偏移，实现异步时间错位
- **shard**：将数据分配到不同设备
- **replicate**：在设备间复制数据

这些 transformation 是 structured 的——它们保持程序的结构性质，使得编译器可以安全地应用和组合。

### 6.3 自动 Collective Synthesis
关键创新：通过结构化的 transformation，Mercury 可以**自动合成 collective 通信模式**：
- 例如，在 loop 维度上应用 shift transformation，自动生成 ring-style pass
- 无需手动编写 custom kernel 逻辑

### 6.4 Auto-Tuning
对 CommIR 候选方案进行 auto-tuning，选择最优 schedule：
- 对每个候选方案自动生成代码
- 在目标硬件上实际测量性能
- 选择最优方案

### 6.5 代码生成
Lowering 到：
- **Lower-level tensor compilers**：cuBLAS、cuDNN 等
- **通信库**：NCCL
- **代码生成**：CUDA kernel

### 6.6 与编译器栈的集成
Mercury 作为 compiler stack 的中间层：
- 上游：计算图优化（operator fusion、intra-operator resharding）
- 下游：lower-level tensor compilers 和 kernel 库

## 7. 主要实验结果

### 7.1 性能对比
- 相比 **USP（手工 SOTA）**：平均 **1.56x speedup**
- 相比 **Ulysses（手工 SOTA）**：性能提升显著
- 相比 **model-level 3D-parallel**：real LLM 工作负载上最高 **1.62x 性能提升**

### 7.2 跨配置泛化
- 不同 context length：32K 到更长
- 不同硬件平台：不同 GPU 数量、互联拓扑
- 不同网络配置：不同带宽

### 7.3 设计空间探索
Mercury 能够：
- 自动复现 Ring Attention 和 Ulysses 的性能
- 发现手工设计遗漏的更优策略

## 8. 潜在问题/局限性

1. **Auto-tuning 的搜索成本**：虽然 CommIR 提供了结构化的 transformation space，但 auto-tuning 仍然需要实际测量每个候选方案的性能。对于大型模型和多样化硬件配置，搜索空间的大小和测量成本可能成为瓶颈。
2. **与算子融合（Operator Fusion）的交互**：LLM 推理中的算子融合（如 FlashAttention 与后续 linear layer 的融合）对性能至关重要。Mercury 与 operator fusion 的关系未详细讨论。
3. **静态 vs 动态调度**：Mercury 的 scheduling 是静态的——基于 compile-time 信息。但在 LLM inference 中，动态 batching、speculative decoding 等动态因素对性能影响很大。静态 schedule 如何适应这些动态因素？
4. **与 NCCL 库的耦合**：虽然 Mercury 自动生成 collective patterns，但最终仍然依赖 NCCL 库。NCCL 的实现细节（如 ring vs tree topology）如何与 Mercury 的 transformation 交互未讨论。
5. **内存占用的 tradeoff**：Shift asynchronous schedule 减少了 local memory 压力，但需要在 remote memory 中保留更多数据。对于多租户场景，remote memory 的共享和隔离问题未讨论。
6. **调试和可预测性**：当 Mercury 生成的 schedule 性能不如预期时，调试过程可能非常困难——涉及 compiler transformation、hardware configuration 和 workload characteristic 的复杂交互。
7. **与 Paged Attention 的兼容性**：vLLM 等推理系统使用的 paged attention 管理 KV cache。Mercury 如何与 paged attention 的 memory 管理交互？
8. **编译时间的 overhead**：Mercury 的 compile-time 包括 CommIR transformation、auto-tuning 和代码生成。对于 production deployment，compile-time 是否可接受？

## 9. 未来工作

1. **动态调度增强**：将 runtime 信息纳入 schedule 选择。
2. **与 Operator Fusion 的深度集成**：支持算子间的协同优化。
3. **更多通信原语**：扩展到 GPUDirect Storage 等新型互联。
4. **跨框架集成**：与 PyTorch、TensorRT、vLLM 等推理框架的更紧密集成。
5. **硬件自适应编译**：根据运行时硬件状态（如 GPU 温度、功耗）自适应调整 schedule。

## 10. 个人评注

**Mercury 是一篇具有架构意义的编译器论文**，它抓住了 multi-GPU LLM 算子优化的核心矛盾——手工优化的高性能和编译器抽象的灵活性之间的鸿沟——并通过巧妙的 CommIR 设计提供了跨越这一鸿沟的路径。

论文最有价值的贡献是**"Remote Memory as First-Class Abstraction"这一设计决策**：通过将 remote GPU memory 提升为 memory hierarchy 的第一等公民，Mercury 使得编译器可以探索"将数据留在 remote memory 中按需访问"和"将数据复制到 local memory 以减少访问延迟"之间的精细权衡。这比手工设计者的离散选择（要么完全复制如 Ulysses，要么完全 remote 如某些 P2P 方案）提供了更连续的设计空间。

**批评性思考**：
- **"1.56x speedup"超越 USP 的基准需要澄清**：USP 本身是一个手工设计的方案，Mercury 能够超越它说明自动化的 design space 探索确实有用。但 USP 的性能是否已经是手工设计的最优？如果 Mercury 的目标是一个更强的基线（如经过充分优化的 USP），1.56x 的改善更有意义。
- **CommIR 的 expressiveness 边界**：四个 transformation 原语（parallelize、shift、shard、replicate）是否足够表达所有可能的 multi-GPU 算子优化？对于未来可能出现的新硬件互联（如 NVLink 5.0）和新算子（如新的 attention variant），CommIR 是否需要扩展？
- **Auto-tuning 的可扩展性**：随着 GPU 集群规模增大（从 8 到 64+ GPU）和 context length 增加，搜索空间的大小可能爆炸性增长。如何在合理时间内完成 tuning 是一个实际挑战。
- **与现有 compiler stack 的集成成本**：Mercury 作为 compiler stack 的中间层，需要与上游（PyTorch、JAX）和下游（CUDA、ROCm）都有集成。这在实际部署中的工程成本可能被低估了。
- **"发现手工设计遗漏的更优策略"的具体例子缺失**：论文声称 Mercury 能发现手工设计遗漏的策略，但没有给出具体例子和性能数据来证明这一声称。
- **与 training 的关系未讨论**：论文主要关注 inference，但 training 的 multi-GPU 优化同样重要。Mercury 的方法是否可以泛化到 training 场景？

总体而言，这是一篇对编译器研究者和 ML 系统架构师有重要价值的论文。CommIR 的设计提供了一个优雅且实用的 abstraction，使得复杂的 multi-GPU 优化可以被系统化地表达和探索。对于想构建更智能的 LLM 编译器的实践者，Mercury 提供了一个值得深入研究和扩展的基础框架。
