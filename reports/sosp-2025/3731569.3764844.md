## 一、背景

嵌入式系统无处不在，但其硬件设计以成本为导向，安全特性往往被牺牲。传统嵌入式设备通常没有 MMU（内存管理单元），只有简单的 MPU（内存保护单元），支持的隔离域数量极少（通常只有 8 个），隔离粒度粗糙。与此同时，IoT 设备越来越多地接入互联网，面临严峻的安全威胁——Mirai 等僵尸网络已控制数十万 IoT 设备，关键基础设施也频繁遭到攻击。

嵌入式软件生态还有其特殊性：多供应商审计需求、二进制形式的硬件驱动、复杂的软件供应链以及责任归属问题。这些因素使得构建安全可靠的嵌入式系统异常困难。CHERI（Capability Hardware Enhanced RISC Instructions）capability 架构为解决这些问题提供了硬件基础，但此前的 CHERI 系统主要针对大型 64 位系统，不适用于资源受限的嵌入式设备。

---

## 二、要解决的问题

1. **嵌入式设备缺乏细粒度内存保护**：现有 MPU/TrustZone 方案只支持粗粒度隔离（8 个域），无法实现组件级别的安全隔离，导致大量过度授权。

2. **内存安全缺失**：嵌入式软件大量使用 C/C++ 编写，空间和时间内存安全漏洞（use-after-free、缓冲区溢出等）是最主要的安全威胁来源。

3. **现有隔离方案的接口硬化不足**：先前的自动化隔离工作（ACES、TZ-DATASHIELD 等）侧重于自动拆分内存和插入域切换，但未解决隔离组件间接口漏洞（interface vulnerabilities）的问题，隔离效果大打折扣。

4. **供应链攻击防护缺失**：嵌入式固件审计能力薄弱，无法系统性地检测恶意代码注入或违反策略的行为（如 xz/liblzma 供应链攻击所示）。

5. **共享堆在嵌入式系统上不可行**：MPU 的限制使得对象级别的内存共享在廉价设备上不切实际，导致每个组件必须预分配最坏情况所需的全部内存，浪费 SRAM。

## 三、洞察与设计

**关键洞察**：在没有 MMU 的嵌入式系统上，CHERI capability 可以作为唯一的隔离机制，同时实现细粒度的空间/时间内存安全和组件隔离——其面积和功耗开销可以控制在与现有 MPU 方案相当的水平，因此可以部署在廉价设备上。

基于这一洞察，CHERIoT 采用硬件-软件协同设计（hardware-software co-design）方法：

**硬件层（CHERIoT ISA）**：
- **无 MMU 设计**：纯 CHERI capability 隔离，消除 MMU 带来的不确定延迟，适合实时应用
- **Load filter**：在 capability 加载到寄存器时检查 revocation bit，已释放对象的 capability 立即失效，实现时间内存安全
- **Revoker**：异步扫描全部内存，使已释放对象的 capability 失效，完成后内存可安全复用
- **扩展的 capability 权限**：`permit-load-mutable`（深度不可变）、`permit-load-global`（深度不可捕获），支持安全的对象委托

**OS 层（CHERIoT RTOS）**：
- **混合隔离模型**：compartment（代码边界隔离）+ thread（流隔离），形成细粒度的故障容忍边界
- **共享堆**：基于 CHERI capability 实现对象级共享，配合 quota 系统控制资源使用
- **Opaque objects**：基于硬件 sealing 机制实现不透明对象引用，减少组件内部状态，简化故障恢复
- **接口硬化 API**：系统性地解决信息泄露、TOCTOU、输入验证等接口漏洞
- **固件审计**：链接器生成 JSON 报告，支持 Rego 策略语言进行机械化合规检查

**TCB 设计**：仅 4 个组件——loader（仅启动时运行，之后擦除）、switcher（355 条汇编指令）、allocator（3.1K LoC）、scheduler（1.6K LoC），每个组件只被信任执行特定安全属性。

## 四、实现细节

**Switcher**：355 条 RISC-V 汇编指令，11 个入口点。负责上下文切换、compartment 调用/返回、一级 trap 处理。每个线程有专属的 trusted stack（仅 switcher 可访问），存储 context switch 的寄存器保存区和每次 compartment 调用的帧。Compartment 调用时 switcher 解封 sealed capability、清零非参数寄存器、截断栈 capability、归零新栈内存后跳入被调用方。

**Allocator**：3.1K LoC C++，16 个入口点。管理共享堆的空间/时间内存安全：
- 释放对象时设置 revocation bit，load filter 立即使旧 capability 不可用
- 采用 quarantine 机制批量等待 revoker 完成扫描后才复用内存
- 每次 `malloc`/`free` 操作最多移除固定数量的 quarantine 对象以满足软实时约束
- 所有分配在释放时归零，防止信息泄露

**Opaque Objects 与 Token API**：由于硬件只支持 7 种 sealing type，token API compartment 在一种硬件 sealing type 上虚拟化出无限多的 virtual sealing type。Sealed object 包含一个受保护的 header（存储 virtual type）和 payload。

**Allocation Capabilities 与 Quota**：静态不透明对象，逻辑上与 compartment 解耦。支持 quota delegation——服务端 compartment 可用调用方的 allocation capability 分配内存，避免调用方通过重复调用 API 耗尽服务端配额。Sealed allocation API 结合 opaque objects 防止调用方提前释放被调用方正在使用的对象。

**错误处理**：
- Global error handler：compartment 定义 `compartment_error_handler()` 处理同步 fault
- Scoped error handler：基于 `setjmp`/`longjmp` 实现 try-except 风格，仅 6 条指令，near-zero 非错误路径开销
- Micro-reboot：5 步流程——阻止新线程进入、回卷现有线程、释放堆数据、重置全局变量、可选持久状态存储

**审计工具**：链接器生成 JSON firmware report，描述每个 compartment 的 import/export table、MMIO 访问、quota 等信息。配合 Rego 策略语言，可声明式地检查 compartment 间依赖关系、设备访问权限、quota 总和等策略。

整个 OS（含 TCB、核心 API、C/C++ 标准库、网络栈、设备驱动）约 13K LoC C++/C + 920 LoC RISC-V 汇编。

## 五、实验结果

实验平台：Arty A7-100T FPGA，33 MHz，256 KiB SRAM，基于 Ibex RISC-V core 的 CHERIoT 实现。

**代码与数据占用**：

| 组件 | 代码大小 | 数据大小 |
|------|---------|---------|
| Base System (Loader + Switcher + Allocator + Scheduler) | 25.9 KB | 3.7 KB |
| Base + Network Stack (含 TCP/IP, TLS, MQTT 等) | 151.8 KB | 20.4 KB |
| 每个额外 compartment 开销 | 83 B | — |

**性能微基准测试**：

| 操作 | 延迟 (CPU cycles) |
|------|-------------------|
| 空 compartment 调用（round-trip） | 209 |
| Compartment 调用 + 256B 栈清零 | 452 |
| 最坏情况（1 KiB 双向栈清零） | 1,284 |
| 中断延迟 | 1,028 (31 μs @ 33 MHz) |
| Unseal opaque object | 44.8 |
| 检查指针有效性 | 44 |
| Ephemeral claim | 182 |
| Scoped handler 非错误路径 | 87 |

**内存分配器吞吐**：1 KiB 以上 buffer 达到 ~5 MiB/s，足够支撑 10 Mbit 网络连接。

**硬件开销**：CHERIoT core 比 16-entry PMP 增加约 4.5% 面积，CoreMark bare metal 性能开销 20.65%（其中 load filter ~8%，33-bit 内存总线 ~8%）。

**端到端案例**：JavaScript 应用通过 MQTT over TLS 连接 IoT 云后端，13 个 compartment，总内存 243 KB（代码 182 KB + 数据 28 KB + 堆 33 KB）。TCP/IP 栈 micro-reboot 在 0.27 秒内完成恢复。全程 52 秒 CPU 平均利用率 46.5%。

**源码兼容性**：FreeRTOS TCP/IP (~25K LoC)、BearSSL (~30K LoC)、TPM reference stack (60K LoC)、Microvium JS engine (~6K LoC) 均可移植运行，核心代码无需修改，仅需编写 wrapper（624–1.7K LoC）实现接口硬化和 fault tolerance。

## 六、批判性分析

1. **缺乏可比基线**：作者承认"没有可比的基线系统"，因此所有性能和内存评估都是绝对数字或与 Tock（一个用 Rust 编写的嵌入式 OS）的粗略对比。没有在相同硬件上与 MPU-based 隔离方案进行公平对比——这使得 compartment 调用开销（209 cycles）是否"可接受"缺乏客观参照。与 Donky（2,136 cycles）的对比跨越了完全不同的硬件架构和使用场景。

2. **硬件依赖与部署鸿沟**：整篇论文的安全保证建立在 CHERIoT 硬件之上，但截至论文发表时商业硅片仍未量产（"commercial silicon expected in 2025"），所有实验在 FPGA 上以 33 MHz 运行。论文声称面积开销仅比 PMP 多 4.5%，但这是在 Ibex core 上的数据——在不同的嵌入式 SoC 上的集成成本未知。从 FPGA 原型到大规模量产部署之间存在巨大鸿沟。

3. **TCB "去特权化"的实质**：论文强调 TCB 采用最小权限原则，但 allocator（3.1K LoC, 16 入口）仍然"trusted for heap memory safety"，其被攻破可影响机密性、完整性和可用性。Scheduler 被信任的是可用性。将 TCB 的信任分散到不同属性并不等于减小了 TCB——bug 的实际影响仍然严重。

4. **Wrapper 成本被低估**：论文称 wrapper 是实现 CHERIoT 安全性的关键手段，但 wrapper 本身是手工编写的安全关键代码（TCP/IP wrapper 1.7K LoC），其正确性直接影响隔离效果。论文没有讨论 wrapper 的验证策略，也没有量化 wrapper 中的接口硬化代码覆盖了多少潜在的接口漏洞。

5. **Micro-reboot 的实用性存疑**：论文展示了 TCP/IP 栈 micro-reboot 在 0.27 秒内完成，但这是一个"Ping of Death"人工注入的简单场景。对于有复杂跨 compartment 状态依赖的真实应用，5 步 micro-reboot 流程中"回卷所有线程"和"释放所有堆数据"的副作用可能导致级联故障。论文未评估 micro-reboot 对其他 compartment 正在进行的操作的影响。

6. **审计系统的局限性**：Rego 策略审计只能检查静态的 compartment 依赖关系和权限，无法检测运行时的逻辑攻击（论文也承认无法防御不触发 trap 的逻辑 bug）。liblzma 案例研究中"CHERIoT 会使攻击极其困难"的论证带有假设性——因为 CHERIoT 尚未在真实供应链攻击场景中被测试。

## 七、AI Infra / MLSys 视角

本文主要面向嵌入式安全领域，与 AI Infra 的直接关联有限，但以下几点值得关注：

1. **硬件-软件协同设计方法论**：CHERIoT 的核心价值在于展示了"为特定安全属性定制硬件原语，再在其上构建最小 OS 抽象"的方法论。这与 AI Infra 中为 LLM 推理定制硬件（如 Groq TSP、Cerebras WSE）的思路一致——先识别关键操作的瓶颈，再通过硬件-软件协同优化解决。

2. **Compartmentalization 对多租户 AI 推理的启发**：CHERIoT 的细粒度 compartment 隔离和 quota 系统可以启发多租户 LLM 推理服务的资源隔离设计——例如在共享 GPU 内存上实现请求级别的 KV cache 隔离，防止一个租户的恶意请求影响其他租户。

3. **Capability-based 内存管理**：CHERIoT 的 capability 模型为"谁可以访问哪块内存"提供了硬件级别的追踪和强制执行。这对 AI 推理系统中日益复杂的内存管理（如 PagedAttention 中的 block table、prefix caching 中的共享 KV blocks）有参考价值——用 capability 替代软件层面的引用计数可能简化内存安全保证。

---

## 八、总结

CHERIoT RTOS 通过硬件-软件协同设计，在没有 MMU 的廉价嵌入式设备上首次实现了完整的空间/时间内存安全、细粒度 compartment 隔离、接口硬化和固件审计能力。其核心贡献是展示了 CHERI capability 在嵌入式场景下的可行性——base system 仅 25.9 KB 代码，compartment 调用开销 209 cycles，硬件面积增加约 4.5%。系统已移植 FreeRTOS TCP/IP、BearSSL、TPM 等真实组件并支持 micro-reboot 故障恢复。主要局限在于依赖尚未量产的定制硬件，且所有评估均在 FPGA 原型上完成，距离真实嵌入式产品部署仍有距离。
