## 一、背景

嵌入式系统（IoT 设备、工控系统）面临严峻的安全困境：为控制物料成本，这类设备普遍不配备 MMU，无法使用传统的虚拟内存隔离机制；但与此同时，IoT 设备接入互联网的需求日益增加，使其成为高价值攻击目标。Mirai 等僵尸网络已控制数十万台 IoT 设备，针对基础设施的攻击每年持续增长。

嵌入式软件的特殊性使问题更加复杂：多供应商协作、二进制形式分发的软件组件、日益复杂的软件供应链，以及合规认证的约束，共同构成了一个安全设计的"死结"——既需要隔离，又难以重写。

CHERI（Capability Hardware Enhanced RISC Instructions）是剑桥大学提出的硬件能力架构，能够在指针级别强制执行内存安全约束。CHERIoT 是专门为低成本嵌入式系统裁剪的 CHERI 实现，商业硅片预计 2025 年推出。本文展示与 CHERIoT 硬件协同设计的 RTOS。

---

## 二、要解决的问题

**1. 粗粒度隔离的局限**：现有嵌入式安全方案（基于 MPU 或 TrustZone）只能提供粗粒度隔离，无法在代码边界级别实现最小权限。MPU 的区域数量有限，且故障恢复能力弱。

**2. 缺乏完整内存安全**：时间内存安全（use-after-free、double-free）在 MMU-less 系统上难以实现，现有 CHERI 系统依赖 MMU 特性来撤销悬空指针。

**3. 接口加固缺失**：自动化隔离方案专注于插入隔离边界，但对隔离边界处的接口漏洞（信息泄漏、混淆代理攻击等）缺乏系统化防御。

**4. 供应链攻击难以审计**：固件通常包含来自多个供应商的二进制组件，运行时难以检测是否存在越权调用关系。

**5. 资源约束严苛**：目标设备仅有数十至数百 KB SRAM，任何安全机制都必须在极度受限的内存预算下运行。

## 三、核心设计

论文基于五条高层原则（P1–P5）构建 CHERIoT RTOS，并与 CHERIoT 硬件进行硬软件协同设计（co-design）：

**硬件层创新**（来自配套硬件论文，本文直接使用）：

- **无 MMU 的 CHERI 能力**：CHERIoT 是唯一不依赖 MMU 的 CHERI 实现，所有指针均为 CHERI capability，硬件在每次内存访问时检查边界与权限，实现确定性空间内存安全。
- **堆时间内存安全**：通过两个新硬件特性实现。*Load Filter*：每个 8 字节堆粒度关联一个撤销位，释放对象时置位；之后每次从内存加载 capability 时，CPU 检查该位，若已置位则清除 CHERI tag，使 capability 失效。*Revoker*：后台异步扫描所有内存中的 capability，撤销指向已释放对象的 capability，完成后清除撤销位，允许内存复用。
- **更丰富的 sealing 和 delegation**：增加 `permit-load-mutable`（强制深度不可变性）和 `permit-load-global`（强制深度无捕获）两种 capability 权限，使跨信任边界的对象传递可以精确控制访问语义。Sentry capability 携带中断使能/禁止语义，强制结构化的中断编程模型。

**OS 层设计**：

- **混合隔离模型**：Compartment（代码边界的静态隔离抽象）+ Thread（跨 compartment 的执行流）的混合模型，以代码粒度实现最小权限，同时支持跨 compartment 的线程运行。
- **最小 TCB**：运行时 TCB 仅含 4 个组件：Loader（引导完成后自我擦除）、Switcher（上下文切换 + 首级 trap 处理，355 条汇编指令）、Allocator（共享堆管理，3.1K LoC）、Scheduler（1.6K LoC）。没有任何 TCB 组件拥有全部内存访问权限。
- **共享堆 + 配额系统**：统一共享堆降低嵌入式设备"每组件最坏情况预留"的内存总量，通过 Allocation Capability 关联配额，实现跨 compartment 的安全共享和配额执行。
- **静态隔离模型**：Compartment 和 Thread 在 build-time 固定，linker 生成人可读/机可解析的 JSON 报告，支持离线审计策略（通过 Rego 策略语言验证）。

## 四、实现细节

**TCB 组件规模**：
- Loader：1.9K LoC，引导后擦除自身
- Switcher：350 LoC（355 条汇编），11 个入口点
- Allocator：3.1K LoC，16 个入口点
- Scheduler：1.6K LoC，15 个入口点

**关键 API**：

| API | 核心思路 |
|-----|---------|
| Opaque Objects（§3.2.1） | Virtual sealing type 实现运行时密封对象，实现类型安全的跨 compartment 对象传递 |
| Allocation Capabilities & Quotas（§3.2.2） | 将配额与 compartment 解耦，支持多配额、配额委派 |
| Synchronization & Communication（§3.2.4） | 基于单一 futex 原语构建去特权化的多线程 API |
| Interface Hardening（§3.2.5） | 包括信息泄漏防护（内存置零）、Claim/Ephemeral Claim（防 TOCTOU）、入口点检查 |
| Error Handling（§3.2.6） | 三级错误处理：无 handler（解绕线程）、全局 handler、Scoped handler（基于 longjmp/setjmp，仅 6 条指令） |

**Allocator 的配额撤销机制**：
- 释放对象进入 Quarantine，等待一次完整的 Revoker 扫描后才能复用
- 每次 malloc/free 尝试从 quarantine 移除固定数量的对象，保证软实时约束
- Allocator 持有堆的特权 capability，其 load 操作绕过 Load Filter，避免性能开销

**移植现有代码**：
- FreeRTOS TCP/IP stack（38KB，23% 为 wrapper 代码）
- BearSSL TLS（56KB，8% wrapper）
- SNTP（4.2KB，47.2% wrapper）
- MQTT（11KB，28% wrapper）
- Microvium JavaScript 引擎（~6K LoC，仅修改 114 LoC 变为 shared library）
- MS TPM 2.0 参考实现（仅需一个注解即可隔离运行）

## 五、实验结果

**实验平台**：Arty A7-100T FPGA 板，33MHz，256KiB SRAM。编译选项 `-Oz`（优先代码尺寸）。

**代码和内存占用**：

| 系统配置 | Code Size | Data Size |
|---------|-----------|-----------|
| Base System（4 个 TCB 组件） | 25.9KB | 3.7KB |
| Base + Network Stack | 151.8KB | 20.4KB |
| 每增加一个 Compartment 的基础开销 | 83B | — |

- Loader 引导完成后擦除，仅保留 18.4KB
- 网络栈配置含 TLS + MQTT 时总 SRAM 用量 173.6KB，适配常见联网 IoT SoC

**性能**（核心 API 延迟，CPU cycles）：

| 操作 | 延迟 |
|------|------|
| Compartment call | ~209 cycles |
| Library call | ~6 cycles |
| Unseal an object | 44.8 cycles |
| Ephemeral claim | 182 cycles |
| Heap claim + unclaim | 3714 cycles |
| Scoped handler (non-error path) | 87 cycles |
| Fault and unwind（Global Handler） | 413 cycles |

**网络吞吐**：
- 缓冲区 > 1KiB 时，吞吐约 5MiB/s，足以支撑 10Mbit 网络连接
- 缓冲区 < 32KiB 时，吞吐受 compartment call 延迟主导；> 32KiB 时受 Revoker 频率主导

**端到端 Case Study**：一个 JavaScript IoT 应用（Microvium + MQTT over TLS + TCP/IP），连接私有 IoT 后端接收通知并控制 LED。观测到一次 micro-reboot（0.27s）。

## 六、批判性分析

**1. 缺乏公平的基线比较**：论文明确承认"目前没有可比较的基线系统"，因为现有嵌入式平台不支持细粒度隔离+内存安全。这使得性能数字缺乏参照，读者难以判断 209 cycles 的 compartment call 开销究竟是多还是少。实际上，相比 seL4 微内核的 IPC 延迟（通常数百至数千 cycles），这个数字并不差，但论文没有这样的比较。

**2. 评估平台代表性存疑**：实验在 33MHz FPGA 上进行，而商业 CHERIoT 硅片运行在 250MHz+。FPGA 与 ASIC 在延迟特性、cache 行为等方面差异显著。论文中 Revoker 扫描 1MiB SRAM 需要 1.5ms 是在 250MHz 下估算的，但实际 FPGA 实验的时序未被清晰分离讨论。

**3. Revoker 的实时性影响被轻描淡写**：论文承认大缓冲区（>80KiB）时 Revoker 成为瓶颈，并出现 malloc 阻塞直到 sweep 完成的情况（"病理性且不现实"）。但对于硬实时系统，任何不确定延迟都是严重问题。论文将其归类为"不现实场景"，但 256KiB 设备上 80KiB 缓冲区并非极端情况。

**4. Wrapper 比例差异悬殊且未充分讨论**：SNTP 的 wrapper 占 47.2%，意味着移植成本接近重写一半代码。论文声称移植成本"相当于移植到任何新嵌入式平台"，但这个类比可能过于乐观——CHERIoT 要求对接口语义有深刻理解，普通嵌入式开发者未必能正确实现。

**5. 供应链审计能力被高估**：审计的有效性依赖 linker 报告的准确性，而 linker 本身需要信任。论文假设 TCB 是 bug-free 的，但 Allocator（3.1K LoC，16 个入口点）在嵌入式安全系统中算相当大的 TCB 组件。此外，通过函数指针或运行时动态行为绕过静态分析的供应链攻击无法被此机制检测。

**6. 能耗和芯片面积未评估**：CHERI tag bit 对每个指针增加存储开销，Revoker 后台扫描持续消耗功耗——这对电池供电 IoT 设备是关键指标，但论文完全没有涉及。

---

## 七、总结

CHERIoT RTOS 是首个在 MMU-less 低成本嵌入式设备上同时实现完整内存安全（空间+时间）、细粒度故障容忍隔离、接口加固和供应链审计支持的操作系统，通过与 CHERIoT 硬件的深度协同设计达成这一目标。系统基础组件仅占用 25.9KB，实现了对 FreeRTOS 生态代码的低成本移植。主要局限在于依赖专有硬件（商业化进度未知）、缺乏可信基线比较、Revoker 在极端内存使用下的实时性影响，以及对能耗的完全忽略。对于需要在成本受限设备上部署可审计安全固件的场景（工控、医疗 IoT），这是目前最接近生产级的安全嵌入式 OS 设计。
