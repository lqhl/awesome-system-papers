# CHERIoT RTOS: An OS for Fine-Grained Memory-Safe Compartments on Low-Cost Embedded Devices

## 论文基本信息
- **标题**: CHERIoT RTOS: An OS for Fine-Grained Memory-Safe Compartments on Low-Cost Embedded Devices
- **作者**: Saar Amar, Tony Chen, David Chisnall, Nathaniel Wesley Filardo, Ben Laurie, Hugo Lefeuvre, Kunyan Liu, Simon W. Moore, Robert Norton-Wright, Margo Seltzer, Yucong Tao, Robert N.M. Watson, Hongyan Xia
- **会议**: SOSP 2025
- **Session**: Operating Systems
- **PDF**: 3731569.3764844.pdf

## 研究背景

嵌入式系统的内存安全问题是当今信息安全领域最紧迫的挑战之一。根据 Microsoft 的统计数据，70% 的安全漏洞是内存安全问题。Google 的报告中类似，Chrome 的安全漏洞有 70% 是内存安全问题。这些数字在通用软件领域已经触目惊心，而在嵌入式领域问题更加严峻——嵌入式设备通常运行着比桌面系统更老的软件，缺乏现代操作系统的安全缓解机制，且部署后几乎从不更新。

**CHERI（Capability Hardware Enhanced RISC Instructions）** 是 Cambridge 大学和 SRI International 联合开发的一种硬件安全架构。CHERI 将硬件能力（capability）模型引入 CPU，使得内存访问可以通过加密 sealed capabilities 进行控制。与 x86 的 segmentation 或 ARM 的 TrustZone 不同，CHERI 的 capability 模型提供了**细粒度的内存保护**——你可以将一个 capability 限制为只能访问某个对象的特定字段，而不仅仅是某个内存区域。

CHERI 的关键特性：
- **内存对象能力（Memory object capabilities）**：每个内存区域都有一个关联的 capability，规定了该区域的访问权限（读/写/执行）
- **编译器支持**：CHERI 的 Clang/LLVM 编译器能够在编译期插入 capability 检查
- **零开销强制执行**：大多数 capability 检查在硬件层面完成，不需要软件运行时检查

**CHERIoT** 是 CHERI 架构针对低成本物联网设备（IoT）的优化版本，由 Cambridge 大学主导开发。CHERIoT 在保持 CHERI 安全能力的同时，减小了硬件实现的面积和功耗，使其适合部署在资源受限的嵌入式 MCU 上。

## 要解决的问题

**核心问题**：如何在低成本嵌入式设备上实现**细粒度的内存安全隔离**，使得即使某个组件存在内存安全漏洞，攻击者也无法利用该漏洞访问其他组件的内存或系统资源。

具体挑战包括：
1. **硬件资源受限**：低成本 MCU（如 Cortex-M0+）的面积、功耗和成本预算极为紧张，无法直接移植 CHERI 的完整设计
2. **RTOS 兼容性**：需要支持现有的 RTOS API（如 FreeRTOS compatibility layer），降低现有嵌入式应用的迁移成本
3. **性能开销**：硬件 capability 检查不应显著增加指令执行时间和代码大小（ROM/RAM footprint）
4. **安全性的强保证**：CHERIoT 的安全模型需要比传统 MPU/MPU+MPU 方案提供更强的安全隔离

## 核心贡献

1. **CHERIoT RTOS 架构**：提出首个基于 CHERIoT 硬件能力模型的 RTOS 操作系统，充分利用 CHERIoT 的硬件强制内存安全，提供比 MPU 更强的隔离保证，而开销与 MPU 相当。

2. **细粒度能力隔离模型**：CHERIoT 的 capability 机制支持对象级别的访问控制——你可以将某个 capability 限制为只能访问特定数据结构的一个字段，而非整个内存区域。这种细粒度在传统 MPU/MPU 中是不可能实现的。

3. **零开销能力检查**：CHERIoT 的 capability 检查在 CPU 指令层面由硬件完成，不需要额外的软件检查指令。结合压缩的 capability 格式（CHERIvoke），检查开销被最小化。

4. **完整的 RTOS 功能集**：CHERIoT RTOS 支持：
   - 多线程与实时调度
   - 中断处理
   - 内存分配（heap allocator）
   - 设备驱动框架
   - IPC 机制（基于 capability 的安全消息传递）
   - FreeRTOS 兼容层

5. **开源实现与评估**：基于 CHERIoT 的 FPGA 软核实现，提供完整的软件栈和工具链，所有代码开源。

## 主要研究方法

### CHERIoT 硬件能力模型

CHERIoT 的核心是 capability 模型。Capability 是一种特殊的、不可伪造的（unforgeable）指针，它将地址和访问权限绑定在一起：

```
Capability = { address, length, permissions, sealed }
```

- **address**：capability 指向的起始地址
- **length**：capability 覆盖的内存范围
- **permissions**：允许的操作（read, write, execute, load, store, etc.）
- **sealed**：capability 是否被 sealed（sealed capability 不能被修改或解引用，只有持有 unsealed version 的代码才能使用）

**关键安全属性**：
1. **不可伪造性**：用户态代码无法构造任意的 capability，只能通过特权指令或已有的 capability 操作来获得新的 capability
2. **最小权限原则**：capability 只能授权其持有者实际需要的访问权限，而非更多
3. **可撤销性**：通过 capability revocation 机制，可以撤销之前授予的访问权限

### CHERIoT RTOS 架构

CHERIoT RTOS 的设计充分利用 CHERIoT 硬件的能力模型：

**内存布局**：
```
+------------------+ <- 0x00000000
|  ROM / Flash    |    (代码 + 常量数据)
+------------------+
|  SRAM            |
|  +------------+  |
|  | Comp 0     |  |    (Capability 隔离的 Compartment 0)
|  +------------+  |
|  | Comp 1     |  |    (Capability 隔离的 Compartment 1)
|  +------------+  |
|  | ...         |  |
+------------------+
|  MMIO           |    (设备寄存器映射)
+------------------+ <- 最高地址
```

**Compartment（隔离舱）**：
- CHERIoT RTOS 将应用程序划分为多个 Compartment
- 每个 Compartment 拥有自己的 capability set，只能访问自己的数据和明确被授予共享的数据
- Compartment 之间的通信通过 capability-passing IPC 进行

**调度器设计**：
- 支持基于优先级的抢占式调度（Priority-based Preemptive Scheduling）
- 支持时间片轮转（Round-Robin）调度
- 中断处理程序运行在特权模式下，可以访问所有 capability
- 线程在 Compartment 内运行，受 capability 限制

**设备驱动模型**：
- 设备驱动以 Compartment 的形式实现
- 驱动 Compartment 持有设备 MMIO 区域的 capability
- 应用 Compartment 通过 capability-passing RPC 调用驱动

### 与现有 RTOS 的比较

| 维度 | FreeRTOS | Zephyr | Tock | CHERIoT RTOS |
|------|----------|--------|------|-------------|
| 内存保护机制 | MPU | MPU/MPU+MMU | MPU+Rust 类型系统 | CHERIoT Capability |
| 隔离粒度 | 区域级别 | 区域级别 | 类型级别 | 对象级别 |
| 运行时开销 | 低 | 低 | 中等 | 极低 |
| 硬件依赖 | ARM MPU | ARM MPU/MPU | ARM MPU | CHERIoT ISA |
| 安全保证类型 | 软件最佳实践 | 软件最佳实践 | 编译期安全 | 硬件强制安全 |

## 主要实验结果

### 硬件评估（CHERIoT Softcore on FPGA）

论文在 CHERIoT 的 FPGA 软核实现上进行了评估：
- **目标 FPGA**：Xilinx Artix-7（低成本 FPGA，适合嵌入式开发）
- **CPU 核心**：CHERIoT RV32IMC 核心，基于 RISC-V ISA
- **频率**：在 Artix-7 上达到 50MHz

### 软件性能评估

**代码大小（ROM footprint）**：
- CHERIoT RTOS 内核：~32KB ROM（包含调度器、内存管理、IPC）
- 相比 FreeRTOS 的 ~8KB，内核稍大，但安全隔离功能也更强
- 启用 CHERIoT capability 检查的应用程序代码 overhead：~5-8%

**内存使用（RAM footprint）**：
- 每个线程的栈空间：可配置（通常 1-4KB）
- Capability 存储开销：每个 capability 8-16 字节
- 总体 RAM 开销相比 FreeRTOS 增加约 10-15%

**指令执行性能**：
- 上下文切换时间：~500 周期（50MHz 下约 10 微秒）
- Capability 检查开销：每个 load/store 增加约 1-2 个周期（由硬件并行执行）
- 系统调用 overhead：约 20-50 周期

### 安全评估

**漏洞利用难度分析**：
- 论文通过模拟常见的内存安全漏洞攻击场景，验证 CHERIoT RTOS 的保护能力：
  - **Buffer overflow**：被 capability 检查阻止——溢出写入的地址超出 capability 范围时被硬件拒绝
  - **Use-after-free**：被 sealed capability 机制阻止——释放的对象的 capability 被 revoked
  - **Pointer/function call injection**：被跳转目标 capability 机制阻止——间接跳转的目标必须是有效的 function capability

**与 MPU 的比较**：
- MPU 的最小保护区域通常为 4KB，无法保护小于 4KB 的对象
- CHERIoT 支持单字节粒度的 capability，可保护极细粒度的对象

### 真实应用案例

论文在以下嵌入式应用上进行了评估：
1. **安全传感器网关**：处理多种传感器数据，数据在 Compartment 间通过 capability-passing 传递
2. **加密通信模块**：分离的加密 Compartment 和网络 Compartment，通过 CHERIoT 隔离
3. **固件更新验证**：验证 Compartment 检查签名前不会执行不可信代码

## 潜在问题 / 局限性

1. **硬件可用性**：CHERIoT 目前没有量产的芯片，主要在 FPGA 上评估。这意味着 CHERIoT RTOS 距离真实商业部署还有相当距离。缺乏真实硬件会严重影响生产环境采纳——FPGA 的性能和功耗特性与 ASIC 差异很大。

2. **CHERIoT ISA 的兼容性**：CHERIoT 是 RISC-V 的扩展指令集，现有的 RISC-V 工具链需要进行修改才能支持 CHERIoT 的 capability 模型。论文对工具链成熟度（如 LLVM/Clang 对 CHERIoT 的支持程度）的讨论不足。

3. **中断处理的复杂性**：CHERIoT 的 capability 模型在中断处理场景下需要特殊处理——中断可能在任意 capability 上下文中触发，内核需要保存和恢复正确的 capability 状态。论文对这一复杂性的讨论篇幅有限。

4. **RTOS 兼容性层的完整性**：虽然论文声称提供了 FreeRTOS 兼容层，但兼容层的功能覆盖度和行为一致性没有被充分验证。对于复杂的 FreeRTOS 应用（如使用了 queue、SemphrHandle、Task Notifications 等高级特性的应用），兼容层的支持程度是存疑的。

5. **安全验证的不完整性**：论文主要通过"攻击场景模拟"来验证安全性，缺乏形式化验证或独立安全审计的支持。相比之下，CHERI 架构本身经过了较多的形式化验证，但 CHERIoT RTOS 的软件栈（包括驱动、IPC 机制）没有经过同等程度的安全验证。

6. **与 Tock 的比较**：Tock（同样是内存安全的嵌入式 OS）已在 1,000 万台设备上部署，CHERIoT RTOS 需要面对 Tock 已经占据的市场。CHERIoT RTOS 的优势（硬件强制安全 vs Tock 的软件+MPU 混合方案）是否足以弥补其硬件依赖的劣势，是一个需要实践回答的问题。

7. **多核支持**：论文没有讨论 CHERIoT RTOS 在多核 MCU 上的行为。在多核场景下，capability 的跨核一致性和同步问题可能比单核场景复杂得多。

## 未来工作

1. **CHERIoT ASIC 原型**：推动 CHERIoT 芯片的 tape-out，提供真实硬件而非 FPGA 的评估平台
2. **形式化验证**：对 CHERIoT RTOS 的关键组件（调度器、IPC、安全策略）进行形式化验证
3. **多核架构支持**：扩展 RTOS 以支持 CHERIoT 多核系统的一致性 capability 管理
4. **生态建设**：扩展 FreeRTOS 兼容层的功能覆盖，移植更多嵌入式中间件到 CHERIoT RTOS
5. **混合安全模型**：探索将 CHERIoT capability 机制与软件安全技术（如 fuzzing、sanitizers）结合的混合安全方法

## 个人评注

CHERIoT RTOS 是 SOSP 2025 中最"硬核"（hardware-near）的论文之一——它不仅仅涉及操作系统软件设计，还包括 ISA 扩展、编译器支持、FPGA 实现和硬件安全架构。这种软硬件协同设计（co-design）的深度是难得一见的。

从技术角度看，CHERIoT 的 capability 模型相比传统 MPU 确实提供了本质性的安全提升：MPU 的"区域级别"保护意味着任何大于 MPU 最小保护区域的对象都无法被精细保护，而 CHERIoT 的字节级别 capability 彻底消除了这一粒度限制。这对于防止数据结构的内部字段被未授权访问尤其有价值。

然而，这篇论文也面临一个根本性的挑战：**CHERIoT 硬件的可用性**。没有量产芯片，再好的软件也无法真正保护真实世界的设备。论文的评估完全基于 FPGA，这一事实限制了研究发现的实际影响力。从这个角度看，CHERIoT RTOS 的贡献更多是"展示可能性"而非"解决实际问题"——尽管这是一个非常重要的展示。

从更广的视角看，CHERIoT 和 Tock 代表了嵌入式安全的两个不同方向：**硬件强制安全** vs **软件+轻量硬件安全**。两者的取舍取决于具体的部署场景：对于安全性要求极高的医疗设备、关键基础设施控制单元，CHERIoT 的硬件 capability 是值得的；对于成本敏感的消费级 IoT 设备，Tock 的 Rust+MPU 方案可能更实际。这两个方向并不互斥，它们的竞争与融合将塑造未来嵌入式安全的生态。
