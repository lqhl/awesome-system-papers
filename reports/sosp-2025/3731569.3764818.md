## 一、背景

GPU 已成为数据中心 AI 工作负载的核心基础设施，但利用率普遍偏低。微软报告其 GPU 平均利用率仅 52%，阿里巴巴更低至 10%。Meta 内部推理服务分析显示，SM 利用率最低可降至 15% 以下，带宽利用率也仅有五分之一左右。

造成低利用率的原因是多方面的：单任务独占 GPU 时等待通信的 idle 时间、小 batch size 导致并行度不足、流量负载动态波动导致过度 provision，以及某些 memory-bound 模型天生的 SM 低效率。

与此同时，GPU 功耗已超过 1000W/卡（H100/B100），成本持续攀升，低利用率已经是不可持续的状态。

对比 CPU 侧，操作系统通过廉价的上下文切换实现了高效的时分复用、资源隔离、功耗管理和透明性。GPU 侧缺乏类似机制——NVIDIA 提供的 MPS/MIG 要么隔离粒度过粗，要么配置开销过高（MIG 重配置需要 >5 秒），无法满足动态多租户需求。

---

## 二、要解决的问题

**核心矛盾**：现有 GPU 多租户方案在透明性、细粒度控制、隔离性和高利用率之间无法兼顾。

1. **透明性缺失**：大多数软件方案需要修改 ML 框架（PyTorch/TVM）或应用代码，随着框架版本迭代难以维护，也无法在复杂生产环境中部署。

2. **粒度过粗**：MPS 允许多应用共享 GPU，但调度粒度是整个 inference request 或 training batch，导致：
   - Head-of-Line (HoL) blocking：长任务阻塞高优先级短任务
   - 低利用率：无法利用某应用空闲期的 TPC 资源
   - 严重的 P99 尾延迟劣化（实验显示 MPS 的尾延迟可达理想情况的 5-13x）

3. **缺乏硬件 right-sizing**：内核在启动时声明资源需求，但不同 kernel 对 TPC 数量的扩展性差异极大。全量分配导致大量计算单元空转浪费，但现有系统无法在运行时动态调整单个 kernel 的 TPC 分配。

4. **粗粒度功耗管理**：当前 GPU 设备级 DVFS 假设单一负载，多租户场景下 memory-bound 和 compute-bound kernel 混合时，无法实现精细化调频节能。

## 三、核心设计

LithOS 将 GPU OS 的理念引入 ML 基础设施，以 **TPC（Texture Processing Cluster）** 为基本调度粒度——比 GPC 细、比 SM 粗，是透明性和控制粒度的最优平衡点。

**架构概览**：LithOS 运行在 CPU 上，通过动态链接库 `LibLithOS` 拦截 CUDA Driver API（最低公共层，无需修改框架/运行时/编译器）。它维护跨应用的系统全局 GPU 状态视图，将内核提交与 GPU 执行解耦，从而获得真正的调度控制权。

**四大核心机制**：

1. **TPC Scheduler（空间调度 + TPC Stealing）**
   - 为每个应用分配 TPC 配额（quota），保证高优先级应用的计算资源
   - 在线延迟预测模块估算每个 kernel/atom 的执行时长，驱动 TPC Stealing 决策
   - TPC Stealing：将低优先级/空闲应用的 TPC 动态借用给高优先级任务，避免资源浪费
   - 通过限制 outstanding work（100μs 窗口）和硬件 stream 优先级，在 stealing 时最小化 HoL blocking

2. **Kernel Atomizer（透明内核原子化）**
   - 无需访问源码或 PTX，通过修改 QMD（Queue Meta Data）结构注入 Prelude kernel
   - Prelude kernel 根据 `block_idx` 范围决定是否执行原始 kernel 代码，将一个大 kernel 分割为多个 atom（thread block 子集）
   - 支持最多 64 个 atom；对于 CUDA Graph，可在图创建阶段拦截并分解为子图
   - 效果：缩短单个调度单元的时间（从几十 ms 降至 ~500μs），大幅减少 HoL blocking，允许 TPC 分配在内核执行中途动态调整

3. **硬件 Right-Sizing**
   - 对每个 kernel 拟合 Amdahl 定律形式的扩展曲线：$l = m/t + b$（基于全量 TPC 和单 TPC 两个采样点）
   - 用户/管理员指定 `latency_slip` 参数（如允许 10% 性能损失），系统据此计算每个 kernel 的最小 TPC 分配
   - 对占用率（occupancy）做过滤，避免对无法有效利用多 TPC 的 kernel 过度分配

4. **透明 DVFS 功耗管理**
   - 对每个 kernel 建模频率敏感性（$s = k / (f_{max}/f_{th} - 1)$），加权聚合后计算目标频率
   - memory-bound kernel 对频率不敏感，可大幅降频节能；compute-bound kernel 保持高频
   - 保守策略：学习期内先以最高频收集数据，逐步收紧，避免频繁切换（当前 GPU 切换延迟约 50ms）

## 四、实现细节

- **语言与规模**：约 5000 行 Rust（不含 CUDA Driver API 自动生成的 interposal 代码）
- **支持架构**：Ampere（A30、A100）、Hopper（H100）、Ada Lovelace（L4）
- **TPC 映射**：基于逆向工程扩展了 `libsmctrl`，增加了对 Hopper TPC masking layout 的支持；通过 QMD 数据结构识别并动态分配 TPC，新架构适配通常在数天内完成
- **构建于 MPS 之上**：利用 MPS 实现多 CUDA context 的并发执行，LithOS 在其上添加细粒度调度层
- **特殊 kernel 处理**：
  - 包含 `grid_group::sync()` 的跨块同步 kernel：屏蔽原子化和 stealing，通过欺骗 `cuDeviceGetAttribute` 返回可用 SM 数量维持正确性
  - Persistent kernel、CUDA Graph：分别做特殊处理
- **Interposition 架构**：CUDA Driver API 是"narrow waist"，拦截少量核心调用（如 `cuLaunchKernel`），其余自动生成。避免了跨地址空间 marshaling，维护成本低
- **在线延迟预测**：通过 ordinal index（批次内第 k 个 kernel）唯一标识 DFG 中的算子，支持动态 input 下的准确延迟预测

## 五、实验结果

**测试平台**：1x NVIDIA A100 SXM4（108 SM，40GB HBM），Lambda Labs 云实例，Ubuntu 22.04，CUDA 12.6，PyTorch 2.3，TensorRT 10.1

**基线**：NVIDIA 官方方案（Time slicing、MPS、Stream Priority、MIG）和研究系统（TGS、REEF、Orion）

### Inference-Only 多租户（2 HP + 1 BE）

| 指标 | LithOS vs MPS | LithOS vs 最佳 SotA |
|------|--------------|---------------------|
| 尾延迟（P99）| **13×** 更低 | **4×** 更低 |
| 聚合吞吐 | — | **1.3×** 更高 |
| SLO 达成率 | 100%（MPS 仅 45%）| 100% |

MIG 和 Thread Limits 能达到 SLO，但无法支持 BE 任务，聚合吞吐降至 0.58–0.71。LithOS 实现 SLO 100% 达成的同时聚合吞吐达到 1.0。

### 混合推理-训练多租户（1 HP Inference + 1 BE Training）

| 指标 | LithOS vs MPS | LithOS vs 最佳 SotA |
|------|--------------|---------------------|
| HP 尾延迟（P99）| **4.7×** 更低 | **1.18×** 更低 |
| 聚合吞吐 | — | **1.35×** 更高 |

TGS 受限于其恒定到达率假设（生产流量有明显日夜变化），REEF 则对 BE 任务节流不足（尾延迟高达 8.93x ideal）。

### 硬件 Right-Sizing

| 指标 | 数值 |
|------|------|
| GPU 容量节省（均值） | **26%** |
| GPU 容量节省（最高） | **51%**（DLRM） |
| P99 延迟增加（latency slip=1.1） | **<4%** |
| 吞吐降低 | **<4%** |
| 扩展曲线 R² 值 | 0.92–0.99 |

### DVFS 功耗管理

| 指标 | 数值 |
|------|------|
| GPU 能耗节省（均值） | **26%** |
| GPU 能耗节省（最高） | **46%** |
| P99 延迟增加（latency slip=1.1） | **<7%** |

### Overhead

LithOS interposition 开销仅 **4%**（原子化额外增加 <1%），低于 Orion（6%），与 TGS/REEF（~2%）相当。

## 六、批判性分析

**1. 单卡实验，生产规模存疑**

全部实验在单块 A100 上完成，而论文的 motivation 来自 Meta 生产集群（8卡 H100 节点）。在多卡场景下，TPC-level 调度与 NVLink 通信、集体通信原语（AllReduce、AllGather）的交互完全没有讨论。大模型训练（如 Llama 3 finetuning）通常是多卡 tensor/pipeline parallel 的，单卡 finetuning 实验无法代表真实 training workload 的复杂性。

**2. MPS 作为基础层引入了关键假设**

LithOS 构建在 MPS 之上，但 MPS 本身在某些场景下存在稳定性和隔离性问题（论文中也承认 MPS 的 SLO 达成率仅 45%）。LithOS 实际上是在 MPS 的基础上叠加 TPC 调度层，两层机制的交互复杂性和潜在冲突未被充分分析。

**3. 延迟预测的 BE 任务误预测率较高**

HP 任务的误预测率为 0.9%/0.38%（尾延迟 49/31μs），但 BE 任务误预测率高达 14%/11%。论文以"BE 任务优先级低，可接受更高误预测"一笔带过。然而 TPC Stealing 的正确性依赖于对 BE 任务执行时长的准确估计——高误预测率可能导致 stealing 决策错误，进而引发意外 HoL blocking。实验结果中 BE 任务的尾延迟数据基本未呈现。

**4. Prelude kernel 的正确性边界未充分讨论**

论文声称通过修改 QMD 注入 Prelude kernel 可以透明处理任意 CUDA kernel，但原子化实际上重启了多次 kernel launch，对依赖 warp 内全局状态、使用 shared memory 跨 block 通信的 kernel 正确性存在风险。论文承认对"cross-block sync kernel"做了特殊处理，但生产级闭源库（如 cuDNN、cuBLAS）中类似 pattern 的覆盖程度不清晰。

**5. 对比基线的公平性存疑**

REEF 和 Orion 是作者自己重新实现的（原始代码与特定 CUDA 版本绑定无法直接使用），且 REEF 被简化为"HP 任务运行时不启动 BE 任务"，Orion 被简化为"HP kernel 竞争时不启动 BE kernel"。这些简化实现是否与原论文等效，无法验证。

**6. 能耗实验的粒度限制**

DVFS 实验的功耗通过 `nvidia-smi` 每 100ms 采样一次。论文也承认这是 nvidia-smi 支持的最小粒度。对于执行时间较短的模型（如 BERT 推理一次可能只有几十 ms），100ms 采样间隔会引入显著误差，能耗数字的精度存疑。

## 七、AI Infra / MLSys 视角

LithOS 直接针对 AI Infra 的核心痛点，具有很强的研究借鉴价值：

**关键 insight 与迁移价值**：

- **CUDA Driver API 作为 OS 控制点**：以 CUDA Driver API 为"narrow waist"进行 interposition 是一个工程可行的思路，可在不修改 PyTorch/TF/JAX 的前提下植入调度逻辑。这一模式对于需要在现有 ML stack 上透明添加系统功能的研究（如显存压缩、通信调度）有参考价值。

- **核内调度粒度下移**：从"以请求/batch 为粒度"到"以 thread block 为粒度"的调度跨越，是 GPU OS 思维的核心贡献。类似地，在 LLM 推理系统中将 prefill/decode 分离到 thread block 粒度的调度可能带来新的优化空间。

- **在线 kernel 扩展性建模**：Amdahl 曲线 + 两点采样的轻量建模方法，无需离线 profiling 即可实现 per-kernel TPC right-sizing，这一思路可延伸到 MoE 模型专家选择的计算资源动态分配、Speculative Decoding 中 draft/verify 阶段的资源差异化调度。

**值得跟进的 future work 方向**：

1. **多卡场景扩展**：如何将 TPC-level 调度与 AllReduce 等集体通信原语协同？在 ring-based 通信中，某些 GPU 的计算单元可提前释放给其他租户——如何安全实现？

2. **与 FlashAttention / Triton 自定义 kernel 的兼容性**：FlashAttention 的 kernel 设计对 SM 分配非常敏感（fused kernel 依赖特定 tile 大小），Kernel Atomizer 的原子化策略如何与之协同而不破坏性能？

3. **LLM 推理专项优化**：论文中 LLM 推理实验基于静态 trace，未覆盖 continuous batching（vLLM 等）场景。在 continuous batching 中，每次调度的 batch 组成动态变化，TPC right-sizing 模型的收敛速度和准确性是研究问题。

4. **与内存虚拟化的结合**：LithOS 目前专注计算和功耗，GPU 内存仍是多租户的重要瓶颈。将 TPC Scheduler 与页式 GPU 内存管理结合，实现计算+内存的协同虚拟化，是 GPU OS 方向的自然延伸。

---

## 八、总结

LithOS 是第一个将操作系统思想系统性地引入 GPU 多租户管理的工作，以 TPC 为调度粒度，通过透明 Kernel Atomizer 实现 thread block 级调度，结合在线延迟预测驱动 TPC Stealing、硬件 right-sizing 和 DVFS，在不修改任何 ML framework 的前提下显著提升 GPU 利用率和能效。实验结果令人印象深刻（13x 尾延迟改善 vs MPS，26% 容量和能耗节省）。主要局限在于：单卡验证难以代表多卡生产场景，Prelude 注入机制的通用性存在边界，且 BE 任务的延迟预测误差较高。该工作为 GPU OS 研究提供了坚实基础，尤其在多租户 LLM 推理集群中有明确的落地价值。
