## 一、背景

GPU 已成为数据中心不可或缺的计算资源，但利用率普遍低下——微软报告仅 52%，阿里巴巴低至 10%，Meta 的推理服务利用率可低于 30%，Llama 3 训练的 GPU 利用率约 40%。随着 GPU 功耗超过 1000W/卡，这种低利用率在经济和能源上都不可持续。

现有 GPU 共享方案要么缺乏透明性（需修改 ML 框架或应用），要么粒度太粗（MIG 按 GPC 级别分区、MPS 缺乏隔离），导致 head-of-line (HoL) blocking、资源浪费和性能干扰。CPU 领域的操作系统通过时间片和细粒度调度解决了类似问题，但 GPU 上缺少对等的 OS 层抽象。

---

## 二、要解决的问题

1. **GPU 多租户调度粒度太粗**：现有方案（MIG、MPS、时间片）以整个推理请求或 kernel 为调度单位，无法充分利用 GPU 内部的并行资源，导致 HoL blocking 和低利用率。
2. **缺乏透明性**：大多数研究方案需要修改 ML 框架、编译器或应用源码，在快速演变的 ML 生态中难以大规模部署。
3. **静态资源分配**：当前系统不考虑不同 kernel 的计算强度和并行度差异，以整个 job 为单位分配资源，无法随工作负载特征动态调整。
4. **功耗管理缺失**：设备级 DVFS 假设单一工作负载，在多租户场景下效率低下；现有 DVFS 方案依赖离线 profiling，缺乏透明性。

---

## 三、洞察与设计

**关键洞察**：GPU 中不同 kernel 的并行扩展行为差异极大——有些 kernel 用少量 TPC 就饱和，有些则能从更多 TPC 中持续受益；同样，不同 kernel 对频率缩放的敏感度也截然不同（compute-bound vs memory-bound）。因此，以 TPC（Texture Processing Cluster）为粒度进行逐 kernel 的动态资源分配和功耗调节，能够在不牺牲性能的前提下大幅提升利用率和能效。

基于这一洞察，LithOS 提出了一套 GPU 操作系统设计：

- **TPC Scheduler**：以单个 TPC 为粒度进行空间调度，支持 TPC Stealing——当高优先级任务的 TPC 空闲时，动态借给低优先级任务使用，实现细粒度资源复用。
- **Kernel Atomizer**：在不修改源码或 PTX 的情况下，透明地将 kernel 拆分为更小的 thread block 子集（atoms），减少 HoL blocking，允许执行过程中重新配置 TPC 分配。
- **Hardware Right-Sizing**：基于 Amdahl 定律的轻量级模型（$l = m/t + b$），在线预测每个 kernel 的 TPC 扩展曲线，动态确定最少所需 TPC 数量。
- **Transparent Power Management**：基于 kernel 序列的频率敏感度建模，自动选择合适的 DVFS 频率，无需离线 profiling。

LithOS 在 CUDA Driver API 层进行拦截，对上层 ML 栈完全透明。

## 四、实现细节

- **语言与规模**：约 5000 行 Rust 代码（不含宏生成的 CUDA Driver API 拦截代码）。
- **拦截架构**：通过动态链接库 LibLithOS 替代原生 CUDA 库，在 Driver API 层（最低公共接口）拦截，支持 PyTorch、TensorFlow、JAX、TensorRT、cuDNN 等不修改。
- **TPC 控制**：扩展逆向工程库 libsmctrl，通过修改 QMD（Queue MetaData）结构实现动态 TPC 映射。支持 Ampere（A30、A100）、Hopper（H100）、Ada Lovelace（L4）架构。
- **Kernel 原子化**：通过修改 QMD 的程序地址注入 Prelude 逻辑，在不改变原始 kernel 资源配置的前提下实现 thread block 分片。支持 CUDA Graphs（拦截图创建 API 拆分为子图）。
- **特殊 kernel 处理**：对使用 cross-block 同步（如 `grid_group::sync()`）或 persistent kernel 的情况，禁用 stealing 和 atomization。
- **运行基础**：构建在 MPS 之上以支持并发 GPU 上下文执行。
- **延迟预测**：以 kernel 在 batch 中的序号作为标识符，区分同一 kernel 函数的不同调用场景，实现准确的在线延迟预测。

## 五、实验结果

**实验平台**：NVIDIA A100 (SXM4, 40GB)，108 SMs，Ubuntu 22.04，CUDA 12.6，PyTorch 2.3，TensorRT 10.1。

**基线**：Time slicing、MPS、Stream Priority、MIG、TGS、REEF、Orion。

### 推理多租户（Inference-only Stacking）

| 指标 | LithOS vs MPS | LithOS vs 最佳 SotA |
|------|--------------|-------------------|
| P99 尾延迟 | 降低 13× | 降低 4×（vs Orion） |
| SLO 达标率 | 100% | 100%（MPS 仅 45%） |
| 聚合 goodput | — | 提升 1.3× |

### 混合推理-训练多租户（Hybrid Inference-Training Stacking）

| 指标 | LithOS vs MPS | LithOS vs 最佳 SotA |
|------|--------------|-------------------|

| 训练吞吐 | 提升 34× | 提升 1.35×（vs TGS） |

## 六、批判性分析

1. **单 GPU 评估的局限**：所有实验在单块 A100 上完成，未评估多 GPU/多节点场景。在分布式训练中，cross-node 通信、集合操作的同步模式可能使 TPC Stealing 和 Atomization 的效果大打折扣。论文声称的"数据中心 GPU 效率"目标与单卡评估之间存在明显断裂。

2. **逆向工程依赖的可持续性风险**：TPC 控制和 QMD 结构修改依赖对 NVIDIA 闭源驱动的逆向工程。论文声称"新架构的逆向工程往往在几天内完成"，但这种说法缺乏对 NVIDIA 可能在未来架构中主动封堵此类接口的考量。系统的核心机制建立在供应商随时可能破坏的非公开接口上。

3. **内存带宽隔离被低估**：论文主要聚焦计算资源（TPC）和功耗管理，对 HBM 带宽竞争仅简单提到"4–13% 的性能提升"。在实际 LLM 推理中（高度 memory-bound），带宽争用可能是比计算争用更严重的问题。

4. **Right-Sizing 模型过于简化**：使用两点拟合（全 TPC 和单 TPC）的 Amdahl 定律模型来插值 kernel 扩展曲线，虽然平均 R² 较高，但 Llama finetuning 的 R² 仅 0.92。对于 kernel 行为复杂的新兴工作负载（如 MoE、speculative decoding），两点模型的适用性存疑。

5. **基线比较的公平性**：REEF 和 Orion 因原始代码绑定特定 CUDA 版本，作者不得不重新实现。重新实现的基线可能未完全还原原系统的优化效果，这使得 LithOS 的性能优势存在被高估的可能。

6. **BE 任务吞吐牺牲被轻描淡写**：Kernel Atomization 引入 10% 的 BE 吞吐下降，图 21 显示在大 batch size 下 BE 任务被严重抢占。论文将此描述为"LithOS 优先保障 HP 工作负载"，但对于需要 GPU 时间的训练任务，这种牺牲可能不可接受。

## 七、AI Infra / MLSys 视角

**启发与借鉴价值**：

- LithOS 展示了在 CUDA Driver API 层进行透明拦截的可行性和有效性，这一架构模式对构建生产级 GPU 虚拟化、调度和监控系统有直接参考价值。约 5000 行 Rust 即可实现核心功能，工程成本可控。
- TPC 级别的细粒度空间调度为 AI Infra 中的 GPU 分时复用提供了新思路。当前 MIG 的 GPC 级分区在大规模部署中粒度过粗（例如 H100 仅 8 GPC），而 TPC 级别（H100 有 72 TPC）提供了 9× 的分区精度提升。

**可迁移的设计思路**：

- **Kernel-level right-sizing** 的思想可以应用于推理服务的 auto-scaling：不是以模型或请求为单位分配 GPU 资源，而是根据各 operator 的实际扩展特性动态分配。
- **序列感知的 DVFS** 可以集成到 vLLM 等推理引擎中，在 prefill（compute-bound）和 decode（memory-bound）阶段自动切换频率策略。

**值得跟进的研究方向**：

1. **多 GPU / 多节点扩展**：将 LithOS 的 TPC Stealing 与集合通信（NCCL）的空闲期结合，在 all-reduce 等待期间将 TPC 借给推理任务。
2. **与 KV Cache 管理的协同**：将 TPC right-sizing 与 PagedAttention 等显存管理技术结合，实现计算和内存资源的联合优化。
3. **Prefill-Decode 分离调度**：利用 LithOS 的 atomization 机制，在同一 GPU 上实现 prefill 和 decode 的细粒度空间共享，替代目前常见的 chunked prefill。

---

## 八、总结

LithOS 是首个面向 GPU 的操作系统级多租户管理方案，通过 TPC 级空间调度、Kernel Atomization、动态 hardware right-sizing 和透明 DVFS 四大机制，在对 ML 栈完全透明的前提下显著提升了 GPU 利用率和能效。其推理尾延迟相比 MPS 降低 13×，容量节省 26%，能耗节省 26%。主要局限在于依赖 NVIDIA 闭源驱动的逆向工程、仅在单 GPU 上验证、对内存带宽隔离关注不足。该工作为 GPU OS 研究开辟了新方向，但距离生产部署仍需解决跨卡扩展和供应商兼容性问题。
