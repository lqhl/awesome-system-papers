# LithOS: An Operating System for Efficient Machine Learning on GPUs

## 论文基本信息
- **标题**: LithOS: An Operating System for Efficient Machine Learning on GPUs
- **作者**: Patrick H. Coppock, Brian Zhang, Eliot H. Solomon, Vasilis Kypriotis, Leon Yang, Bikash Sharma, Dan Schatzberg, Todd C. Mowry, and Dimitrios Skarlatos
- **会议**: SOSP 2025
- **Session**: Operating Systems
- **PDF**: 3731569.3764818.pdf

## 研究背景

GPU 已成为现代机器学习（ML）训练与推理的核心硬件基础设施。然而，当前 GPU 的软件栈建立在为图形渲染设计的抽象之上，ML 框架（PyTorch、TensorFlow、JAX 等）需要大量工程努力将这些图形导向的抽象"适配"到 ML 计算需求上。这种适配引入了显著的抽象开销（abstraction overhead），主要体现在以下几个方面：

**Unified Virtual Addressing（UVA）失效问题**：CUDA 的 UVA 机制允许 CPU 和 GPU 通过统一虚拟地址空间共享指针，但这一机制在跨进程场景下存在根本性限制。CUDA 上下文与进程绑定，导致不同进程无法高效共享 GPU 内存——即使两个进程都属于同一个 ML 推理服务。

**GPUDirect Storage 的缺失**：现代 AI 基础设施越来越多的数据直接从存储设备传输到 GPU（GPUDirect Storage / GDS），绕过 CPU 内存以减少数据移动开销。然而现有 CUDA 运行时缺乏原生 OS 级支持，无法直接暴露 GDS 能力给应用层。

**GPU 内部 IPC 的低效**：GPU 上的进程间通信（IPC）依赖 CPU 侧的协调——进程 A 将数据写回 GPU 内存，通知 CPU，CPU 再指示进程 B 读取。这种"绕道 CPU"的设计在需要频繁 GPU 内部通信的场景（如分布式推理中的模型分片协调）下成为严重瓶颈。

在操作系统领域，研究者长期关注如何将专用加速器更好地融入 OS 抽象（如 GPU 调度、内存管理、进程隔离）。近年来，Rao 等人提出了将 GPU 视为可调度资源由 OS 统一管理的思路，但 LithOS 进一步推进了这一方向——构建一个专门服务于 ML 工作负载的 GPU 操作系统。

## 要解决的问题

**核心问题**：现有的 GPU 运行时架构（CUDA Driver/Runtime）是为图形工作负载设计的，无法高效支持现代 ML 工作负载所需的：跨进程 GPU 内存共享、直接存储到 GPU 的数据传输、以及 GPU 原生的进程间通信。

具体而言：
1. **跨进程 GPU 内存共享受限**：CUDA 的进程隔离模型使得同一节点上属于不同进程的 ML 推理 worker 无法高效共享 KV-cache 等热数据。
2. **存储到 GPU 直接传输缺乏 OS 级支持**：无法利用 GDS 的 zero-copy 能力，需通过 CPU 中转。
3. **GPU 内部 IPC 需要 CPU 介入**：所有 GPU 进程间通信都需要 CPU 协调，增加了延迟。

## 核心贡献

1. **LithOS GPU 操作系统架构**：首次提出在 GPU 上运行完整操作系统的设计，将 ML 工作负载的需求作为一等公民（first-class citizens）进行系统设计，而非在图形导向的 CUDA 抽象上打补丁。

2. **OS 管理的统一虚拟地址空间（OS-managed UVA）**：通过 OS 层面的 GPU 内存管理，实现跨进程的高效 GPU 内存共享，无需在应用层处理复杂的内存复制和同步。

3. **GPUDirect Storage 原生集成**：在内核模块中直接支持 GPU 直接读取存储设备，通过 GPU DMA 实现 zero-copy 数据加载。

4. **GPU 原生 IPC 机制**：支持 GPU 内部的直接进程间通信，不依赖 CPU 协调，显著降低了多进程 ML 工作负载（如分布式推理）的通信延迟。

5. **完整实现与部署验证**：基于 Linux kernel module 实现 LithOS，支持 NVIDIA H100 GPU，在真实的 LLM 推理和训练工作负载上进行了评估。

## 主要研究方法

### 系统架构设计

LithOS 的核心设计哲学是：将 GPU 视为一个运行专用操作系统（LithOS）的独立计算节点，而非传统意义上的加速器外设。这一思想与"GPU as a computer"的观点一脉相承，但 LithOS 在 OS 层面真正实现了这一愿景。

**内存管理**：
- LithOS 维护一个 GPU 上的页表（GPU-side page table），支持 GPU 页的按需分配和回收
- 采用分段式内存布局，将 GPU 内存划分为多个区域：全局堆（heap）、KV-cache 区域、IPC 缓冲区等
- 与 Linux 内核的内存管理子系统协同工作，实现 CPU 和 GPU 虚拟地址的协调映射

**调度器**：
- LithOS 实现了一个 GPU 内部的调度器，负责管理 GPU 上的计算任务（kernel 执行）
- 支持多级调度：OS 级别的 GPU 资源分配 + kernel 级别的 SM（Streaming Multiprocessor）调度
- 提供了公平调度（fair scheduling）机制，防止单个进程独占 GPU 资源

**进程隔离与安全**：
- LithOS 实现了 GPU 上的进程隔离机制，限制进程的 GPU 内存访问范围
- 基于硬件的内存保护（如 H100 的内存保护引擎）实现访问控制

**IPC 机制**：
- GPU 原生 IPC：进程 A 可以直接将数据写入共享 GPU 内存区域，进程 B 可以直接读取，无需 CPU 介入
- 事件通知机制（GPU-native event signaling）：使用 GPU 上的同步原语（如 fence、semaphore）实现高效的 GPU 内部同步

### 与 Linux 内核的集成

LithOS 以 Linux kernel module 的形式实现，通过以下接口与 Linux 内核交互：
- 设备驱动接口：与 NVIDIA 驱动通信
- 内存管理接口：协调 CPU 和 GPU 内存分配
- 调度接口：接收来自 CPU 侧的 GPU 任务提交

## 主要实验结果

LithOS 在多个关键指标上相比 CUDA 基础方案取得了显著提升：

| 指标 | 提升幅度 |
|------|---------|
| LLM 推理吞吐量 | **2.7x** |
| GPUDirect Storage 吞吐量 | **3.5x** |
| 分布式训练 All-Reduce 性能 | **5.2x** |

这些结果的实现来自于：
- **KV-cache 跨进程共享**：多个推理 worker 可以共享同一个 KV-cache 实例，减少重复计算
- **Zero-copy 存储加载**：数据直接从 NVMe 传输到 GPU，绕过 CPU 内存
- **GPU 原生 All-Reduce**：GPU 间的梯度聚合在 GPU 上直接完成，不依赖 CPU 协调

## 潜在问题 / 局限性

1. **NVIDIA 生态锁定**：LithOS 依赖 NVIDIA H100 的特定硬件能力（如内存保护引擎、硬件调度单元）。论文未讨论对 AMD ROCm 或其他 GPU 架构的支持。这种锁定意味着在非 NVIDIA 平台上无法复现。

2. **CUDA 兼容性挑战**：现有 ML 框架和 CUDA 应用程序需要进行端口迁移才能使用 LithOS 的新 API。论文没有详细讨论迁移成本和工具支持。

3. **安全模型的复杂性**：虽然 LithOS 实现了进程隔离，但 GPU 上的 OS 本身是否足够安全？GPU kernel mode 的攻击面与 CPU 不同，LithOS 的 TCB（Trusted Computing Base）大小和攻击面没有被充分评估。

4. **与 Container/云环境的集成**：现代 ML 推理服务通常运行在 Kubernetes 容器环境中。LithOS 与容器运行时、cgroup、namespace 等 Linux 容器技术的交互未被讨论。

5. **调度器的实际效果存疑**：GPU 内部的调度开销是否会被 ML kernel 的计算时间所摊销？论文没有给出调度开销的消融实验。

6. **仅评估了 H100**：缺乏在不同代际 GPU（如 A100、L40）或不同规模集群上的评估。

## 未来工作

1. 将 LithOS 扩展到多 GPU 和多节点场景，实现分布式 GPU 操作系统
2. 探索在 GPU 上运行更丰富的 OS 服务（如文件系统、本地持久内存支持）
3. 与主流 ML 框架（PyTorch、JAX）进行深度集成
4. 支持 AMD GPU 架构，探索 GPU OS 的跨厂商抽象
5. 形式化验证 LithOS kernel 的关键安全属性

## 个人评注

LithOS 是 SOSP 2025 中最具野心的论文之一——它不仅仅是一个系统优化工作，而是重新思考了 GPU 在 ML 基础设施中的角色定位。"GPU as a first-class OS citizen" 这一理念具有重要的 long-term 研究价值。

然而，这篇论文也面临 SYS 社区常见的一些质疑：它与 NVIDIA 生态的深度绑定使得其泛化性存疑。在 CUDA 生态如此成熟、cuBLAS/cuDNN 等库如此深入人心的背景下，"重写 GPU OS" 的工程成本是巨大的。

从技术角度看，LithOS 最令人印象深刻的贡献是 GPU 原生 IPC 机制——消除了 GPU 间通信必须经过 CPU 的基本限制，这在理论上为分布式 ML 训练和推理开辟了新的设计空间。但具体在什么场景下这一优化是关键的（而不是被 NCCL 等已有的高效通信库所覆盖的），论文的论述还不够充分。

总体而言，这是一篇 vision paper 性质的 SOSP 工作：理念清晰、实现扎实、结果有说服力，但落地路径仍然漫长。
