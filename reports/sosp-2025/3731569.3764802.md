## 一、背景

大规模数据分析正在加速向混合云（hybrid cloud）迁移——即同时使用本地数据中心（on-premises）和公有云资源。Uber、Spotify、Twitter、Netflix 等公司都处于不同程度的混合云状态：有些是向云端逐步迁移的过渡阶段，有些则是长期的永久架构选择。混合云能带来弹性扩容、成本节约和技术灵活性，但对于数据密集型分析工作负载（如 Presto 查询和 Spark ETL），跨站点的数据移动代价极高。

云厂商对跨网络的数据出口（egress）每 GB 收费约 9–11 美分，大规模数据湖每周处理 PB 级数据时，egress 费用快速累积。为降低 egress，企业往往诉诸大量数据复制（replication），但复制又带来高额存储成本（Twitter 复制 300PB 数据，年存储费约 9000 万美元）。此外，为支撑高吞吐跨站点传输，还需要租用专用高速链路（百 Gbps 量级），成本同样不菲。

---

## 二、要解决的问题

混合云部署中存在三类核心挑战：

**C1：高度互联的 Job-Data 依赖关系**。Uber 工作负载中，85% 的 Job 和 77% 的表属于最大弱连通分量，组织边界（project）对 job-data 依赖几乎没有预测能力（仅 10% 的数据读取发生在同一 project 内）。现有方案（如 Yugong）依赖 project 级粒度分组，在 Uber 场景下大量失效。

**C2：中等程度的 Job 复现率叠加持续增长**。约 56% 的流量来自周期性 job，但仍有 44% 的流量来自新出现的 job。同时，Presto 每日读取量以约 30% 年速增长，job 模板多样性以 20% 年速增长，静态优化快速过时。

**C3：需要全局联合优化**。现有方案各有偏颇：不复制则 egress 费用爆炸；盲目复制则存储成本急剧上升；Yugong 的 MIP 模型仅针对私有云，不直接适配 hybrid cloud 中弹性复制预算和 egress 定价的场景。缺乏一个同时优化 egress、复制存储和网络带宽成本，并能适应动态工作负载的框架。

---

## 三、核心设计

Moirai 是一个面向混合云的**数据与计算联合放置优化框架**，包含三个组件：**Spinner**（图构建）、**Allotter**（MIP 优化器）、**Data Placement Enacter**（执行器）。

**优化目标**：最小化总货币成本 = 存储成本（云端存储 × 存储价格）+ Egress 成本（on-prem job 读取云端数据 + 云 job 写回 on-prem 数据）+ 数据迁移惩罚（对不必要的数据移动加以惩罚）。

形式化：

$$\text{Minimize } \text{Cost}_G + \text{Cost}_U$$

- $\text{Cost}_G$：当前放置方案的运营成本（存储 + egress）
- $\text{Cost}_U$：数据迁移成本，对 egress 方向以实际 egress 价格惩罚，对 ingress 方向以可调参数 $\alpha$（0 ≤ α ≤ 1）控制惩罚力度

约束包括：on-premises 和云端的计算容量、存储容量、网络带宽上限。

**三大技术创新**：

1. **Dependency-driven Grouping**（依赖驱动分组）：将相同查询模板的周期性 job 折叠为单节点；将近一周未被访问的表按数据库名分组为 200+ 节点，将优化规模从 4M job + 1M 表压缩到 356K + 134K。

2. **Pre-selecting Replication Tables**（复制表预选）：使用 JobAccessDensity（= job 访问次数 / 表大小）指标预选 0.2% 的数据强制复制，将 MIP 求解时间从 147 小时压缩到约 2 小时，同时将图边数减少 59%。

3. **SizePredict 路由策略**（新 job 在线路由）：对于从未出现过的 job，根据上一时间窗口各表的历史平均访问量预测本次读取量，将 job 路由到"数据量更重"的一侧，从而最小化跨站点数据访问。

## 四、实现细节

Moirai 的生产部署涉及三条独立的基础设施路径：

**HiCam（指标收集）**：原来的方案直接将 HDFS 客户端的访问指标发往 Apache Kafka，但极端的 metric cardinality（预估十亿级）导致写放大和限流。HiCam 在 Kafka 前置了一个基于 Apache Flink 的聚合层，通过内嵌 HTTP server 接收高吞吐 metrics，在内存中聚合后再以紧凑流发往 Kafka → Apache Pinot（OLAP 存储）。吞吐降低 128×，Pinot 存储降低 10×（从 10 TiB/月 → 750 GB/月）。

**HiveSync（复制服务）**：监听 Hive Metastore（HMS）的 audit 事件（分区写入、表写入、schema 变更），触发基于 DistCp 的跨 HDFS 集群数据复制，并通过 Apache YARN 跟踪进度。以最终一致性模型同步 Hive/Hudi 格式的表。可扩展至每日 1000 万个 job，每日 10+ PB 数据传输，700K 表同步，P99 复制延迟 < 18 分钟。

**控制平面集成（Presto）**：在 Presto 的 dispatch 路径中，先查询 Moirai 配置服务获取：(1) 路由百分比（业务策略 + 区域容量），(2) 特定 job 模板的推荐放置位置。dispatch 前检查查询引用的所有表的副本一致性状态，确保只访问最新副本。额外的配置服务调用为轻量级，不增加可观测的路由延迟。

MIP 求解使用商业优化器 Gurobi，运行在 CloudLab c8220 机器（40 核）上，0.2% PR 配置下平均求解时间约 2 小时。

## 五、实验结果

**实验设置**：4 个月 Uber Presto + Spark 生产 trace（2024年10月 – 2025年2月），66.7M 次查询，访问 13.3 EB 数据（来自 300 PB 语料库）。云定价使用 GCP 标准定价（Table 1）。专用链路假设为 800 Gbps。评估三种混合分割比例：70:30、50:50、30:70（on-prem : cloud）。

**主要对比结果（50:50 分割，Moirai vs. baselines）**：

| 方案 | 周网络流量 | 周总成本 | 复制量 |
|------|-----------|---------|-------|
| NoRep | 64.7 PB | $903K | 无 |
| Volley | ~30 PB | ~$810K | 无 |
| Rep3Mon | 29.7 PB | $810K | 3个月数据 |
| RepTop2.5% | 18.2 PB | $393K | 2.5% 数据 |
| Yugong | 12.3 PB | $194K | 项目级 |
| **Moirai** | **751 TB** | **$12K** | **0.2% 数据** |

Moirai 相比 Yugong（state-of-the-art）：
- 成本降低 **97%**
- 网络流量降低 **96–98%**
- Egress 降低 **95–99.5%**
- 复制量降低 **最高 99%**
- on-prem 网络基础设施需求降低 **89–98%**

**SizePredict 路由效果**：相比 Independent Routing，egress 成本降低 90.3–99.8%；与理论最优（SizeOracular，不可实现）的差距约 39–128%，同时比 SizeUnaware 低 42.6–84.8%。

**迁移场景**：在模拟逐步迁移（on-prem 100% → 0%，每步减少 10%）中，代价感知的 Moirai 实现了近零 egress 和最小必要 ingress；而不考虑迁移代价的 baseline 产生约 150 PB 额外 egress（约 $310 万美元）。

## 六、批判性分析

**1. Yugong 对比可能失真**

论文将 Yugong 适配为 hybrid cloud 场景（加入弹性复制预算、将 storage cost 纳入目标函数）后再做比较，并声称改进后的 Yugong 优于原版。但 Yugong 的 project 级粒度限制是其核心设计约束，而 Uber 工作负载的 intra-project 数据读取仅占 10%，这几乎注定了 Yugong 在此场景下的失败。97% 的提升数字很大程度上是"换赛道"而非技术突破：选择一个天然不适配当前工作负载的基线，再展示自己能赢。

**2. 单一公司 trace，泛化性存疑**

论文只用了 Uber 的 4 个月 trace，虽然与 Microsoft Cosmos、Alibaba workload 做了定性对比，但三者的 trace 均不公开，无法做定量验证。自称"第一个大规模 hybrid cloud workload 分析"，但 generalizability 章节（§3）主要是作者自说自话，缺乏独立的第三方验证。

**3. MIP 求解的实际可用性存疑**

论文声称在 0.2% PR 配置下平均 2 小时求解，但实验是在 CloudLab c8220（40 核研究集群）上使用 Gurobi（商业许可，价格不菲）完成的。生产环境的机器负载、Gurobi 许可成本、以及在 workload spike 时是否能保证 2 小时内完成，均未讨论。论文也承认不同 week 的 trace 差异导致求解时间有较大方差（图中有 whisker plots）。

**4. "prepaid compute"假设过于理想**

Moirai 将 on-prem 和云端计算资源都视为"预付费且固定"的约束，不作为优化变量。然而真实 hybrid cloud 中，on-demand 计算资源购买、Reserved Instance 的动态调整，本身就是重要的成本优化空间。这个假设将问题大幅简化，也限制了 Moirai 的适用范围。

**5. 新 job 流量占 44%，路由策略的局限性被低估**

SizePredict 对新 job 的路由依赖"上一窗口各表的历史平均访问量"，对于从未出现过的新表（访问量历史为零）退化为 SizeUnaware。论文对此一笔带过，但 Uber 每年有 20% 的新模板增长，新表引入也持续发生，这个边界情况在实际部署中影响不可忽视。

**6. 一致性保证"最终一致"带来的正确性风险**

HiveSync 采用最终一致性同步，复制延迟 P99 < 18 分钟。控制平面在 dispatch 时检查副本状态以避免读到旧数据，但对于高频更新的 hot tables，这个检查能否始终保证正确性，论文未做深入讨论。若检查失败（副本未就绪），fallback 策略会导致额外的跨站点流量，与 Moirai 的优化目标背道而驰。

---

## 七、总结

Moirai 是一个针对大规模混合云数据分析的**数据与计算联合放置优化框架**，通过 MIP 建模将 egress、复制存储和网络带宽成本联合最小化。其核心贡献在于：(1) 以 job-data 依赖关系而非人工组织边界驱动分组，突破了 project 级粒度限制；(2) 使用 JobAccessDensity 预选 0.2% 数据复制，将 MIP 求解时间从 147 小时压缩至 2 小时；(3) SizePredict 在线路由策略接近理论最优。在 Uber 4 个月真实 trace 上，Moirai 相比 state-of-the-art Yugong 实现了 97% 的成本削减。主要局限在于：依赖商业 MIP 求解器、单一工作负载验证、"预付费计算"假设过于理想，以及对新 job 和新表的路由质量有待进一步验证。
