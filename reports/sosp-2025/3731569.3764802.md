# Moirai: Optimizing Placement of Data and Compute in Hybrid Clouds

## 1. 论文基本信息

- **标题**: Moirai: Optimizing Placement of Data and Compute in Hybrid Clouds
- **作者**: Ziyue Qiu, Hojin Park, Jing Zhao, Yukai Wang, Arnav Balyan, Gurmeet Singh, Yangjun Zhang, Suqiang (Jack) Song, Gregory R. Ganger, George Amvrosiadis (Carnegie Mellon University & Uber)
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764802
- **代码**: https://github.com/eniac/Moirai (intend to release)

## 2. 研究背景

混合云（Hybrid Cloud）部署结合了本地数据中心和公有云资源，已成为大型组织的主流架构选择。Spotify、Twitter、Netflix、Uber 等公司均处于渐进式云迁移过程中，混合状态可能持续数年甚至成为永久架构选择。然而，混合云部署面临三大核心成本挑战：

1. **云端出口费用（Egress Fees）**：主流公有云（AWS/Azure/GCP）的出口费用为 8.7-11.0 美分/GB，处理 PB 级数据湖时成本迅速累积——仅传输 1 PiB 数据就可能花费高达 $115,000。
2. **数据复制成本（Replication Costs）**：为降低出口费用，企业往往采用数据复制策略，但这同样代价高昂。例如，Twitter 将 300 PB 数据复制到云端，按 Google Cloud 存储定价每年需花费约 $9000 万。
3. **专线网络成本（Dedicated Network Link Costs）**：800 Gbps 专线每年成本约 $160 万，还需额外支付流量费用。

当前方法的局限性明显：不复制数据的方案（NoRep）虽然节省存储，但出口费用极高；重复制方案（Rep3Mon）虽然降低出口费用，但存储成本大幅增加；阿里巴巴的 Yugong 虽然建模了项目级placement和复制，但依赖人工组织边界划分，无法适应 Uber 工作负载中高度跨项目数据共享的特征。

## 3. 要解决的问题

**核心问题**：如何在混合云环境下，同时优化数据placement和计算（job）placement，最小化总 dollar 成本（出口费用 + 复制存储费用 + 网络基础设施费用），同时满足资源约束（on-premises 计算/存储/网络容量限制）？

具体挑战包括：
- **C1: 高度 Job-Data 互联性**：Uber 工作负载中，85% 的 jobs 和 77% 的 tables 属于最大弱连通分量，跨项目数据共享比阿里巴巴更强——仅 10% 的 job 数据读取发生在项目内部。
- **C2: 中等 Job 重复率 + 持续增长**：保守估计仅 56% 的流量来自 recurring jobs，每日新增约 31K 个 job templates，Presto 日读取量每天增长 142 TB。
- **C3: 动态资源约束**：Uber 的混合云处于渐进式迁移中，on-premises 基础设施不断变化，需要 placement 策略能够持续适应。

## 4. 核心贡献

1. **首个大规模混合云分析**：对 Uber 4 个月（2024年10月-2025年2月）的 Presto 和 Spark 工作负载进行了详细分析，涵盖 6670 万查询和 13.3 EB 数据访问，并计划公开发布 trace。
2. **Moirai 优化框架**：提出数据+Job 联合placement的 MIP 建模方法，包含 egress 费用、复制存储费用和网络基础设施费用的精确建模，并将数据迁移成本纳入优化目标。
3. **Dependency-aware Job Routing**：提出 SizePredict 策略，基于历史 per-table 访问量预测新 job 的数据访问量，将其路由到数据量更充足的一侧。
4. **生产验证**：在 Uber 真实基础设施上验证了方案的可行性，并描述了部署到生产的具体步骤（HiCam 监控服务、HiveSync 复制服务等）。
5. **开源承诺**：计划开源 Moirai 模拟器代码和 traces。

## 5. 主要研究方法

### 5.1 工作负载分析
- 从 Uber 生产环境收集 4 个月的 job 执行数据：job metadata（ID、启动时间、持续时间、CPU消耗、query template ID）、job ownership、per-table 数据访问详情（每次读取/写入字节数）、所有 table 的大小（总计 300 PB）。
- 构建 Job-Data 二部图 G = (V, E)，其中 V 包含 m 个 jobs 和 n 个 tables，边的权重为读取字节数 r_{i,j} 和写入字节数 w_{i,j}。
- 分析揭示：85% jobs 属于最大连通分量，仅 10% 数据读取发生在项目内，每日新增 31K job templates。

### 5.2 优化问题建模
**决策变量**：
- y_i：job routing（0=on-prem, 1=cloud）
- op_j：table 是否在 on-prem
- cl_j：table 是否在 cloud
- 可通过 op_j + cl_j >= 1 建模三态（on-prem / cloud / replicated）

**目标函数**：
$$\text{Minimize } Cost_G + Cost_U$$

其中 $Cost_G$ = 存储成本 + Egress 成本 + Ingress 成本（relaxed penalty），$Cost_U$ = 重配置惩罚成本（penalty of data movement）。

**约束条件**：
- On-premises 和 cloud 的计算容量约束
- 存储容量约束：$\sum s_j \cdot op_j \leq L_{storage}$
- 网络带宽约束：涉及 cross-site 读写流量

### 5.3 可扩展性优化
**Dependency-driven Grouping（基于依赖关系的分组）**：
- 将具有相同 query template 的 recurring jobs 合并为一个节点（356K jobs -> 134K tables -> 356K after grouping）
- 将未被访问的 tables 按数据库名分组（而非全部合并为一个大节点）
- 4M+ jobs 减少到 356K；1M+ tables 减少到 134K

**Pre-selecting Replication Tables（预选复制表）**：
- 问题规模：3^134K * 2^356K ~ 10^193 个配置，纯 MIP 求解需 7+ 天。
- 评估 5 种指标：AccessTrafficVolume、JobAccessFrequency、InverseDatasetSize、AccessTrafficDensity、**JobAccessDensity**。
- JobAccessDensity 表现最佳：直接最小化边数，0.2% 数据预复制即可将优化时间从 147 小时缩短到 2 小时。

### 5.4 Dependency-aware Routing
对于 recurring jobs：直接按 Data Placement Enacter 的决策路由。
对于新 jobs（占流量 44%）：使用 **SizePredict** 策略——预测每个 table 的访问量（基于上一窗口的平均值），将 job 路由到数据量更大的一侧。

## 6. 设计与实现

### 6.1 系统架构
Moirai 包含三个核心组件（三位希腊命运女神的名字）：
- **Spinner**：从访问日志生成 Job-Data Graph
- **Allotter**：基于 Gurobi 的 MIP solver，输出最优 job scheduling policy 和 data placement
- **Enactor**：通过 Job Scheduler 和 Data Placement Enacter 执行决策

### 6.2 数据移动建模
Moirai 惩罚双向数据迁移（cloud -> on-prem 的 egress 和反向的 ingress），引入松弛参数 alpha（0<=alpha<=1）控制 ingress 惩罚力度。当 alpha=1 时，ingress 视为与 egress 同等昂贵。

### 6.3 部署基础设施
- **HiCam**：基于 Apache Flink 的轻量级聚合层，接收来自 HDFS 客户端的高吞吐指标流，将吞吐量降低 128 倍，存储降低 10 倍以上（750 GB/月），P99 延迟可忽略。
- **HiveSync**：支持一次性和持续复制的服务，使用 DistCp 复制 HDFS 数据，通过 HMS 审计事件触发，P99 复制延迟 < 18 分钟，可扩展到每日 1000 万 jobs、10 PB 数据传输、70 万 tables 同步。

## 7. 主要实验结果

### 7.1 成本与流量降低
在三种混合比例（70:30、50:50、30:70 on-prem:cloud）下评估：
- **Moirai 相比所有 baseline 降低 95%+ 成本和 94%+ 流量**
- 相比 NoRep：降低 99% 成本
- 相比 Rep3Mon：降低 98.5% 成本
- 相比 RepTop2.5%：降低 95% 成本
- **相比 Yugong：降低 97-98% monetary costs 和 96-98% 流量**
- 关键数据（50:50 split）：Moirai 周度成本仅 $12K（Egress $8K + Replication $3K + Network $1K），而 Yugong 为 $810K，NoRep 为 $1.2M。

### 7.2 数据Placement优化
- PR0.2%（复制前 0.2% 数据）达到最佳成本-效率平衡
- Moi-JobDist 变体捕获了 Moirai 绝大部分改进（gap 从 1863% 缩小到 84-168%），说明 joint optimization 是主要收益来源
- 相比仅优化 top traffic-heavy jobs（1% Job），PR0.2% 在节省 364-724% 成本的同时保持可接受的优化速度

### 7.3 Job Routing
- SizePredict 相比 Independent Routing 降低 egress 成本 90.3-99.8%
- SizePredict 相比 SizeUnaware 降低 42.6-84.8%
- SizePredict 与 SizeOracular（下界）相比，差距在 2 倍以内

### 7.4 网络使用
- Moirai 的 P95 带宽经常低于 Yugong 的平均带宽
- Yugong 需要比 Moirai 高 8 倍的专线带宽，导致 8 倍高的专线成本

### 7.5 迁移场景
- 从 100% on-prem 到 0% 的完整迁移中，Moirai 实现接近零的 egress 和最低必要的 ingress
- Redistribution cost unaware 方法产生 ~450 PB egress（$3.1M），而 Moirai 接近零

## 8. 潜在问题/局限性

1. **Trace 代表性问题**：分析仅基于 Uber 一家公司的 4 个月数据，虽然与 Microsoft Cosmos 和阿里巴巴 trace 有相似性，但可能不完全代表其他行业。
2. **MIP 求解器依赖**：使用 Gurobi 商业求解器，虽然预复制策略将优化时间缩短到 2 小时，但在没有商业求解器许可的环境中可能难以复现。
3. **项目级 grouping 的局限性**：论文指出项目级 grouping 对 Uber 不适用，但这一发现可能与 Uber 的特殊组织结构相关，不一定适用于所有企业。
4. **Ingress penalty 的保守性**：alpha=1 的设置将 ingress 视为与 egress 同等昂贵，但实际场景中许多云提供商的 ingress 是免费的，这种保守设置可能导致次优决策。
5. **Yugong 实现的不完整性**：由于 Yugong 闭源，论文的实现可能无法完全反映原始系统的全部设计决策。
6. **仅针对批处理 analytics**：Moirai 针对 Presto 和 Spark 的批处理工作负载设计，未讨论流处理或实时分析场景。
7. **单一云区域**：论文限制在单个云区域 + on-premises 的设置，未考虑多区域和合规性约束（如数据主权）。

## 9. 未来工作

1. **Per-job deadline constraints**：将 per-job 延迟约束纳入优化框架。
2. **多区域/多云扩展**：通过增加每 table/job-region pair 的二元变量，将 Moirai 扩展到多区域设置。
3. **ML 工作负载 placement**：类似 MAST 的设计，为 GPU 利用率最大化设计 ML 训练任务的 placement。
4. **一次性批量数据传输优化**：替代长期规划式优化，针对一次性大规模数据传输做专门优化。

## 10. 个人评注

**Moirai 是一篇极具工业价值的论文**，它基于 Uber 真实的 4 个月生产数据揭示了混合云成本优化中一个长期被忽视但影响巨大的问题——仅 10% 的数据读取发生在项目内部，这意味着依赖项目边界的现有方法（如 Yugong）在实际部署中会产生巨大的次优性。

论文最值得称道的贡献是 **JobAccessDensity 指标**的发现：这个小而巧妙的指标（jobs 数量 / table 大小）直接度量了"每个存储单位的连接密度"，恰好反映了那些小但被广泛共享的 table（如配置表、字典表），这些 table 在优化搜索空间中会产生最多的边。通过 0.2% 的预复制比例，Moirai 将优化时间从 147 小时压缩到 2 小时，使得在线优化成为可能。

**批评性思考**：
- 97% 的成本降低数字令人印象深刻，但需要注意的是，这个对比中的 Yugong 是经过论文改进的版本（原始 Yugong 缺少 egress 费用建模和动态存储预算），直接对比的公平性值得商榷。
- 论文声称 Moirai 是"首个大规模混合云分析"，但实际上 Spotify、Twitter、阿里巴巴等公司都有内部分析和方案，只是未公开发表。Moirai 的贡献在于将分散的工业实践系统化并公开发表。
- HiCam 和 HiveSync 作为部署基础设施的讨论很有价值，但这些组件的详细设计在正文中被大幅压缩，许多工程细节只能从附录中窥见。
- 一个有趣的潜在问题是：如果竞争对手（如阿里巴巴）获取了 Uber 的 trace 并针对其优化自己的方案，会发生什么？这提示了 trace 发布的敏感性和潜在风险。

总体而言，这是一篇将严肃的工业问题、系统性分析和工程实现良好结合的论文，适合所有关注云成本优化和分布式数据管理的从业者深入阅读。
