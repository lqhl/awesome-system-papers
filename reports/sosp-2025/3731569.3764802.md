# Moirai: Optimizing Placement of Data and Compute in Hybrid Clouds

**作者**：Ziyue Qiu (CMU/Uber), Hojin Park (CMU), Jing Zhao (Uber), Yukai Wang (Uber), Arnav Balyan (Uber), Gurmeet Singh (Uber), Yangjun Zhang (Uber), Suqiang (Jack) Song (Uber), Gregory R. Ganger (CMU), George Amvrosiadis (CMU)

**链接**：https://doi.org/10.1145/3731569.3764802
**源文件**：[3731569.3764802.pdf](../../papers/sosp-2025/3731569.3764802.pdf)

## 一、背景

混合云（Hybrid Cloud）已成为大型企业的主流部署模式。Uber、Twitter、Spotify、Netflix 等公司在向公有云迁移的过程中，长期处于"部分本地、部分云端"的混合状态——Spotify 的迁移持续了两年，Uber 预计五年。在这种架构下，大规模数据分析工作负载（如 Presto、Spark）需要频繁跨站点访问数据，产生高昂的 egress 费用（GCP 约 11¢/GB）、专线成本（800Gbps 链路年费约 $160 万）和数据复制存储费用。如何在混合云中合理放置数据和计算任务以最小化成本，是一个至关重要但极具挑战的优化问题。

---

## 二、要解决的问题

现有方案在混合云场景下均存在明显不足：

1. **无复制方案（NoRep）**：如 Spotify 早期做法，数据随机分区不复制，egress 费用爆炸式增长。
2. **全量复制方案（Rep3Mon）**：如 Twitter 做法，复制最近 3 个月数据到双端，存储成本极高（Twitter 300PB 复制到云端年费约 $9000 万）。
3. **Yugong（阿里巴巴）**：state-of-the-art，但依赖项目级（project-level）人工组织边界做 placement，在 Uber 这类跨组织数据共享频繁的环境下效果差（Uber 仅 10% 的数据读取发生在项目内部）；使用固定复制预算而非灵活优化；缺乏对新 job 的路由指导。
4. **所有方案都未能联合优化 job 路由与 data placement**，无法适应工作负载的持续增长和动态变化。

---

## 三、洞察与设计

**关键洞察**：在大规模数据湖环境中，job 和 table 之间存在高度互联但结构化的依赖关系——通过分析 query template 的历史数据访问模式，可以自动发现比人工组织边界更优的 job-data 分组，并且只需复制极少量（0.2%）但被高密度访问的关键 table，就能大幅降低优化复杂度和跨站点流量。

基于此洞察，Moirai 设计了一个完整的优化框架：

1. **Spinner**：从 job 执行日志构建 job-table 二部图，记录每个 job 对每张 table 的读写字节量。
2. **Allotter**：基于 Mixed-Integer Programming (MIP) 模型，联合优化 job 路由（每个 job 在本地还是云端执行）和 data placement（每张 table 在本地、云端还是双端复制），目标函数包含 egress 费用、存储费用和网络基础设施费用，同时约束计算容量、存储容量和网络带宽。
3. **Dependency-driven Grouping**（§4.4）：将相同 query template 的重复 job 合并为单节点，未访问的 table 按 database 分组，将 400 万 job 降至 35.6 万、100 万+ table 降至 13.4 万。
4. **Pre-selecting Replication**（§4.5）：用 Job Access Density（job 访问次数 / table 大小）指标预选 0.2% 的 table 做复制，将搜索空间从 10^210,193 降低到 Gurobi 可在约 2 小时内求解。
5. **Size Predict 路由策略**（§4.6）：对新 job，基于其声明的 table 依赖和历史平均访问量预测数据量，将 job 路由到数据量更大的一侧。
6. **Data Movement 感知**：在目标函数中加入 egress/ingress 惩罚项，避免频繁重新分区时的不必要数据搬迁。

系统以周为周期运行优化循环，也支持按需触发（如资源约束变化时）。

## 四、实现细节

- **MIP 模型**：二元变量 $y_i$（job 路由）、$op_j$/$cl_j$（table 在 on-prem/cloud 的存在性），约束包括计算容量、存储容量和网络带宽限制。目标函数 $Cost_G + Cost_U$ 包含存储成本、egress 成本和数据移动惩罚。
- **Gurobi MIP solver** 在 CloudLab c8220 机器（40 核）上运行，完整优化约 2 小时（使用 Job Access Density 预选后）。
- **HiCam**：基于 Apache Flink 的轻量级聚合层，用于收集 HDFS 文件系统级别的数据访问日志。解决了直接写 Kafka 的写放大和高基数问题，将吞吐量降低 128×，存储降低 10×。
- **HiveSync**：复制服务，监听 Hive Metastore 审计事件，使用 DistCp 跨 HDFS 集群复制数据。支持 1000 万日任务、10PB 日传输、70 万表同步，P99 复制延迟 < 18 分钟。
- **Presto 控制面集成**：在路由层查询配置服务获取 Moirai 的 job template placement 决策，检查 table 副本状态，引入的额外延迟可忽略不计。
- 工作负载数据：Uber 4 个月 trace，66.7M Presto queries + Spark jobs，访问 13.3EB 数据，总数据 300PB。

## 五、实验结果

实验基于 Uber 4 个月 Presto/Spark 生产 trace，假设 800Gbps 专线、GCP 定价模型。

### 核心对比（50%:50% 混合分割）

| 方案 | 周流量 | 周成本 | 相对 Moirai 成本 |
|------|--------|--------|-----------------|
| NoRep | 112.3PB | ~$1.2M | ~100× |
| Volley | 64.7PB | ~$903K | ~75× |
| Rep3Mon | 29.7PB | ~$810K | ~67× |
| RepTop2.5% | 18.2PB | ~$393K | ~33× |
| Yugong | 12.3PB | ~$194K | ~16× |
| **Moirai** | **751TB** | **~$12K** | **1×** |

### 关键结果

- **成本降低 97%+**（相比 Yugong），包括 95–99.5% egress 减少、99% 复制减少、89–98% 网络基础设施需求减少。
- **仅复制 0.2% 数据**（约 600TB），远低于 Rep3Mon 的数月全量复制。
- **Size Predict 路由**比 Independent Routing 降低 90.3–99.8% 的 egress 成本，接近理想的 Size Oracular（通常在 2× 以内）。
- **网络带宽**：Moirai P95 流量通常低于 Yugong 平均流量，带宽需求仅为 Yugong 的 1/8。
- **迁移场景**：从 100% on-prem 迁移到 0%，Moirai 实现近零 egress 和最小必要 ingress，而不感知迁移成本的方案产生额外 150PB egress（$310 万）。
- **优化耗时**：Pre-replication 将优化时间从 147 小时降至约 2 小时。

## 六、批判性分析

1. **单一 trace 源的泛化性**：所有评估基于 Uber 一家公司的 trace。虽然论文对比了 Microsoft Cosmos 和 Alibaba 的公开数据，但这些 trace 均不公开，对比只能基于论文中报告的统计量。Moirai 在 Uber 特有的高互联度、低项目内聚性场景下表现极好，但在 Alibaba 那样项目内聚度更高（33% 项目内数据读取 vs Uber 10%）的环境中，Yugong 的优势可能被低估。

2. **Yugong 对比的公平性存疑**：Yugong 是闭源的，论文自行在 Moirai 基础上重新实现了 Yugong，并声称做了两处"改进"。这意味着评估中的 Yugong 并非原始系统，且所谓改进是否完整还原了其设计意图无法验证。

3. **静态假设与现实的距离**：模型假设计算和网络资源是预付费的（prepaid reservations），不纳入优化目标。但在实际中，预付费资源的购买决策本身就是优化问题的一部分，Moirai 只优化了 egress/存储/网络这一层，忽略了预付费决策与 placement 决策的耦合。

4. **生产部署缺乏验证**：论文标题提到"toward deployment"但实际只完成了 trace-driven simulation。Section 6 描述的部署基础设施（HiCam、HiveSync、Presto 控制面）是独立工作，Moirai 优化器本身尚未上线。真实部署中可能遇到的问题（如 MIP 求解器的鲁棒性、数据一致性影响、workload 预测误差累积）未经验证。

5. **周级粒度的局限**：Moirai 按周重新优化，但 Uber 50% 的周 job 是新出现的。虽然 Size Predict 处理新 job 效果不错，但论文未讨论在一周内 workload 突变时系统的响应能力。

6. **优化时间 vs 实时性**：即使优化到 2 小时，对于快速变化的 workload，这仍然是非实时的。论文未充分讨论优化延迟对成本的影响。

## 七、AI Infra / MLSys 视角

1. **对 AI 训练/推理的直接借鉴**：Moirai 的 job-data 联合优化思路可直接迁移到大规模 AI 训练场景。当训练数据分布在多个数据中心时（如跨区域预训练数据集），类似的 MIP 模型可以优化训练数据的 placement 和训练任务的调度，减少跨区域数据传输。

2. **Checkpoint 和模型权重的放置**：大模型训练中，checkpoint 的存储和恢复是关键开销。Moirai 的"选择性复制"思路（仅复制高访问密度的 0.2% 数据）可启发 checkpoint 分层存储策略——高频访问的 checkpoint 热副本放在本地 NVMe，低频的放在远端对象存储。

3. **混合部署的 AI 推理**：企业将部分推理负载放在私有 GPU 集群、部分 burst 到云端 GPU，本质上是混合云场景。Moirai 的 dependency-aware routing 可扩展为 KV cache 感知的推理请求路由——将请求路由到已缓存相关 KV cache 的节点。

4. **MAST 的互补性**：论文提到 MAST 是针对 ML 训练的类似系统，但专注 GPU 利用率和抢占策略。Moirai + MAST 的结合——Moirai 做数据层优化、MAST 做计算层优化——可能是一个值得探索的方向。

5. **可操作的 future work**：(a) 将模型扩展到 GPU/TPU 混合集群的训练任务调度；(b) 在推理场景中引入 latency SLO 约束替代吞吐量约束；(c) 研究模型 fine-tuning 场景下 base model + adapter 的联合放置优化。

---

## 八、总结

Moirai 是一个面向混合云数据分析的 job 和 data 联合放置优化框架，核心贡献在于：(1) 基于 job-data 依赖关系而非人工组织边界做细粒度分组；(2) 用 Job Access Density 指标预选极少量（0.2%）table 做复制以大幅降低 MIP 求解复杂度；(3) Size Predict 路由策略有效处理新 job。在 Uber 4 个月 trace 上相比 Yugong 降低 97%+ 成本。主要局限在于仅有 trace-driven 评估、对 Uber 特定 workload 特征的依赖、以及尚未完成生产部署验证。
