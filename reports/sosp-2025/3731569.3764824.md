# Mantle: Efficient Hierarchical Metadata Management for Cloud Object Storage Services

**作者**：Jiahao Li (USTC/Baidu), Biao Cao (Baidu), Jielong Jian (Baidu), Cheng Li (USTC), Sen Han (USTC), Yiduo Wang (USTC), Yufei Wu (USTC), Kang Chen (Tsinghua), Zhihui Yin (Baidu), Qiushi Chen (Baidu), Jiwei Xiong (Baidu), Jie Zhao (Baidu), Fengyuan Liu (Baidu), Yan Xing (Baidu), Liguo Duan (Baidu), Miao Yu (Baidu), Ran Zheng (Baidu), Feng Wu (USTC), Xianjun Meng (Baidu)

## 一、背景

云对象存储服务（COSS）如 Amazon S3、Azure Blob Storage、Google Cloud Storage 已成为云环境中的主要存储基础设施，支撑大规模数据分析和机器学习工作负载。据研究，约 68% 的 AWS 应用使用 S3，而分布式文件系统仅占 4%。全球云对象存储市场预计 2028 年达到 136.5 亿美元。

现代工作负载（数据分析、ML 训练和推理）频繁并发访问深层嵌套的目录层次结构中的小对象，对元数据服务的延迟和吞吐量提出了极高要求。元数据访问在某些场景下占据总执行时间的 70% 以上，路径解析（lookup）又占元数据操作延迟的 63%–91%。

---

## 二、要解决的问题

1. **路径解析效率低下**：现有 DB 表驱动的 COSS 元数据服务需要逐级遍历路径，每一级都需要一次 RPC 交互。生产环境中平均路径深度达 10-12 级，最深 95 级，导致严重的多轮 RPC 开销。

2. **目录更新高竞争**：并发目录修改操作（mkdir、dirrename）更新同一目录的属性元数据时，触发分布式两阶段提交事务中的大量事务冲突和重试。极端场景下（如 Spark 查询数百子任务原子 rename 到共享输出目录），竞争导致吞吐量下降 99.4%-99.7%。

3. **已有优化不适用于 COSS**：DFS 中的元数据缓存依赖紧耦合客户端（COSS proxy 层是无状态的）；并行路径解析在高并发下反而退化；单分片事务仅解决简单操作，无法处理跨目录 rename 等复杂场景。

---

## 三、洞察与设计

**关键洞察**：COSS 中目录元数据（用于路径解析的 access metadata）相对于对象元数据占比极小（目录仅占 8%-18%），且每个目录的 access metadata 仅约 80 字节，可以用一个单节点的内存索引完整缓存单个命名空间的所有目录元数据，从而将分布式多轮路径解析转化为单 RPC 本地查找；同时，生产环境中目录 rename 主要发生在叶子节点附近，高层路径前缀高度稳定，可以安全地缓存。

基于此洞察，Mantle 采用 inclusive 两层架构：

- **IndexNode**：每个命名空间一个单节点服务器，仅存储轻量的目录 access metadata（pid、name、id、permission、lock bit），提供 single-RPC 路径解析和 rename 的环路检测。
- **TafDB**：可扩展的分片数据库，存储所有完整元数据（access + attribute），跨命名空间共享，处理对象操作和目录属性操作。

这种 fine-grained 的元数据划分和职责分工使得 IndexNode 不处理对象操作的重负载，而 TafDB 充分利用 scale-out 能力。

## 四、实现细节

### TopDirPathCache
- IndexNode 内部的哈希表缓存，存储截断路径前缀（去掉最后 k=3 级）到目录 ID 和聚合权限的映射
- 仅缓存距叶子节点 k 级以上的稳定路径前缀，内存消耗仅为全缓存的 12%
- 利用 Lazy-Hybrid 方式沿路径交集计算权限

### Invalidator 机制
- **PrefixTree**：无锁 radix tree，重建缓存路径的目录树结构，支持范围查询
- **RemovalList**：无锁 skiplist，记录正在修改的目录路径
- 后台线程定期轮询 RemovalList 并使用 PrefixTree 做范围清除，lookup 请求先检查 RemovalList 避免读取过期缓存

### Follower/Learner Read
- IndexNode 基于 Raft 复制，将 lookup 请求分发到 follower 和 learner 节点
- Follower 先向 leader 查询最新 commitIndex，等待本地 applyIndex 追上后执行本地路径解析
- 缓存失效通过 Raft log 同步到所有副本

### Delta Record（解决目录更新竞争）
- 替代 in-place 更新，对目录属性的修改以 append-only 的 delta 记录写入 TafDB
- 复合键：(pid, /_ATTR, timestamp)，消除对同一目录属性行的写冲突
- 后台异步 compaction 合并 delta 到主记录
- 仅在检测到持续竞争时动态启用

### Cross-Directory dirrename
- 由 IndexNode 统一协调，通过 IndexTable 中的 lock bit 用单 RPC 完成锁获取和环路检测
- 避免分布式锁的多轮 RPC 开销
- 环路检测：从源目录和目标目录的最近公共祖先到目标目录逐级检查 lock 状态

### Raft Write 优化
- 批量 Raft 提交减少 fsync 频率
- Follower write offloading 分担写入压力

### 容错
- Raft 自动 leader 选举处理元数据服务器故障
- Proxy 故障时客户端重连其他 proxy，基于 UUID 保证幂等性
- 标准 2PC 恢复处理事务提交阶段的 proxy 崩溃

## 五、实验结果

**部署**：53 台物理服务器（21 台元数据服务，32 台客户端），每台 128GB DRAM，25Gbps 网络。

**对比基线**：Tectonic（DB 表方式）、InfiniFS（并行路径解析）、LocoFS（分层设计），均为忠实复现。

### 应用级性能

| 指标 | Tectonic | InfiniFS | LocoFS | Mantle |
|------|----------|----------|--------|--------|
| Analytics 完成时间（无数据访问） | 71.3s | 17.8s | 12.7s | 3.9s |
| Audio 完成时间（无数据访问） | 90s | 70s | 71s | 42s |
| Analytics 完成时间（含数据访问） | 71.7s | 17.9s | 13.5s | 4.8s |
| Audio 完成时间（含数据访问） | 132s | 115s | 112s | 69s |

Mantle 将 Spark Analytics 作业完成时间缩短 63.3%–93.3%，Audio 预处理缩短 38.5%–47.7%。

### 元数据操作性能

- Lookup 延迟降低：vs Tectonic 83.9-89.0%，vs InfiniFS 80.0-84.2%，vs LocoFS 16.4-74.5%
- 目录修改吞吐提升：vs Tectonic 1.20-20.9×，vs InfiniFS 1.16-116.0×，vs LocoFS 2.87-80.78×
- 10 级路径深度下 lookup 延迟仅为 1 级的 1.09×（Tectonic 6.82×，InfiniFS 6.4×）

### 可扩展性

- 命名空间从 1B 扩展到 10B 条目，吞吐保持稳定
- 2048 线程 + follower + learner：objstat 达 1.89M ops/s
- mkdir 达 58.8K ops/s，dirrename 达 38.0K ops/s（高竞争场景）

### 生产部署

- 已在百度对象存储（BOS/百度沧海存储）部署超 1.5 年
- 3 个集群，19 个内部命名空间，管理数十亿对象
- 日均元数据请求量达数百亿

## 六、批判性分析

1. **IndexNode 单点瓶颈未根本解决**：虽然通过 follower read、TopDirPathCache 等优化缓解了 CPU 压力，但 IndexNode 本质上仍是 per-namespace 的单节点设计。论文自己也承认其扩展性受限于 IndexNode 的 CPU 资源。当命名空间规模进一步增长或并发量更高时，需要增加 learner 节点甚至重新分片，而论文对此仅提及 RDMA 作为 PoC，缺乏系统性的横向扩展方案。

2. **基线复现的公平性存疑**：三个基线系统（Tectonic、InfiniFS、LocoFS）均为非公开系统的重新实现，虽然论文声称性能与原论文一致，但复现实现中的工程优化程度、参数调优、以及是否充分利用了原系统的所有优化（如 InfiniFS 的 AM-Cache 在元数据缓存评估中才启用），可能影响对比的公平性。特别是 Tectonic 被设定为"放宽一致性、不使用分布式事务"，这与生产 Tectonic 的真实行为可能有差异。

3. **Delta record 的读放大被轻描淡写**：delta record 虽然消除了写竞争，但 dirstat 操作需要扫描所有 delta 记录才能计算准确结果。论文仅提到"仅在持续竞争时动态启用"来缓解，但缺乏对 delta 积累速度、compaction 延迟、以及在高频读+高频写混合场景下实际影响的量化分析。

4. **元数据缓存的评估结论有局限**：论文在 §6.5 中发现为 InfiniFS 和 Mantle 添加元数据缓存后 Audio 工作负载显著改善，但全文设计中主动放弃了 proxy 端缓存方案。考虑到 COSS proxy 虽然无状态但可以引入分布式缓存层（如 Redis），这一设计决策的论证不够充分。

5. **生产部署数据的选择性呈现**：生产环境峰值吞吐（175-400K lookup/s、9-24K mkdir/s）远低于实验室评估的极限数据，说明实际工作负载尚未真正压测系统极限。同时论文未提供故障恢复的实际生产数据（如 leader 选举延迟、服务中断时间）。

---

## 七、AI Infra / MLSys 视角

1. **AI 训练数据预处理的元数据瓶颈**：论文明确指出自动驾驶模型数据预处理中，元数据访问占总执行时间 70% 以上。这表明在大规模 AI 数据流水线中，元数据服务的性能直接影响 GPU 利用率和训练效率。Mantle 的 single-RPC lookup 设计对于加速数据加载阶段有直接价值。

2. **Checkpoint 和模型存储的启示**：论文提到生产中部署了模型 checkpointing 工作负载。在大规模分布式训练中，checkpoint 写入涉及大量并发目录创建和文件写入，Mantle 的 delta record 机制可以有效减少 checkpoint 目录的元数据竞争。

3. **可迁移的设计思路**：
   - **Access metadata 与 attribute metadata 的分离**：这一 fine-grained 元数据划分思想可迁移到 AI Infra 中的模型仓库、特征存储等场景，将频繁查询的索引信息与较少访问的详细属性分开服务
   - **Delta record + 异步 compaction**：类似 LSM-tree 的思想，可用于高并发写入的训练日志、metrics 收集等场景
   - **TopDirPathCache 的"距叶子 k 级"策略**：利用工作负载特征（叶子节点变化频繁、上层稳定）进行自适应缓存，对 KV cache 管理、模型权重缓存等有借鉴意义

4. **值得跟进的方向**：
   - 将 IndexNode 与 RDMA 结合实现更高的 single-node 路径解析吞吐（论文 PoC 显示可从 500K 提升到 1M ops/s）
   - 探索将 IndexNode 的概念应用到 AI 模型元数据管理（如 model registry 的版本树查询优化）
   - 在 AI 数据湖场景中，结合数据 locality 信息将元数据与数据调度联合优化

---

## 八、总结

Mantle 是百度沧海存储团队为云对象存储设计的新型层次化元数据服务，通过 inclusive 两层架构（轻量 IndexNode + 可扩展 TafDB）实现了 single-RPC 路径解析和低竞争目录修改。其核心创新在于 fine-grained 的元数据划分（access vs attribute）、TopDirPathCache 的稳定前缀缓存策略、delta record 消除写竞争、以及利用 Raft follower/learner 扩展读吞吐。系统已在百度生产环境部署超 1.5 年，管理数十亿对象。主要局限在于 IndexNode 的单节点 CPU 瓶颈和 per-namespace 的扩展模式，对于超大规模命名空间的横向扩展能力有待验证。
