## 研究背景

现代硬件严重依赖增加 CPU 核心数量来提升性能，这意味着大多数高性能应用都是多线程的。随着核心数增长，线程竞争锁的激烈程度也随之增加。根据 Amdahl 定律，当并发线程数量超过可用硬件上下文（hardware contexts，即超线程或非 SMT 架构下的核心）时，线程不断 busy-wait（忙等待），导致临界区被频繁抢占，critical path 上的进度被严重阻塞——这就是所谓的 **oversubscription（超订阅）问题**。

锁是保证线程互斥执行临界区的基本构件。现有锁算法主要分为两类：

- **阻塞锁（Blocking Locks）**：等待线程通过系统调用（如 Linux 的 Futex）在内核中睡眠。阻塞锁在 oversubscription 下不会发生性能崩塌，但需要付出上下文切换的高昂代价，在非超订阅场景下性能远逊于自旋锁。
- **自旋锁（Spinlocks）**：等待线程在一个共享变量上 busy-wait。自旋锁在无超订阅时性能出色，但在 oversubscription 下性能会崩塌一到四个数量级，因为等待线程占用了太多硬件上下文，频繁抢占持锁线程的 CPU。

为了兼顾两者，研究者提出了 **spin-then-park（先自旋后阻塞）** 锁，如 POSIX 锁：先忙等待一段时间，再阻塞。然而自旋时间的选取依赖启发式 heuristics，效果不稳定。其他方案如 MCS-TP（时间戳自旋锁）、Malthusian 锁、u-SCL 等也都在不同程度上依赖启发式参数，无法从根本上解决问题。

## 要解决的问题

**核心问题**：现有所有结合自旋与阻塞的方案都依赖启发式（heuristics）来判断何时从自旋切换到阻塞，这些启发式本质上是对调度器行为的黑盒估计，无法精确获知何时发生了持锁线程被抢占的情况，从而导致：

1. **超订阅下的性能崩塌**：自旋锁（如 MCS、Shuffle lock）在 oversubscription 时性能可能比纯阻塞锁差 30000 倍。
2. **启发式调参困难**：最佳自旋超时取决于硬件、负载特征和调度行为，无法找到一个普适的参数值。

**根本挑战**：如何在不修改内核的前提下，精确检测持锁线程何时被抢占，从而在恰好需要的时候（持锁线程被抢占时）让等待线程从自旋切换为阻塞，而不是依赖任何启发式估计。

## 核心贡献

1. **低开销的临界区抢占检测技术**：通过 eBPF 钩住 OS 调度器的 `sched_switch` tracepoint，在每次上下文切换时精确判断被抢占的线程是否正在持有锁（即是否在临界区代码中）。这是首个无需修改内核即可系统性检测临界区抢占的方案。
2. **新型锁算法**：设计了一个高效的混合锁算法，利用上述检测信息，在检测到临界区被抢占时精确地将所有等待线程从自旋切换为阻塞，从而释放 CPU 资源让持锁线程尽快恢复执行。
3. **完整系统实现与评估**：在 Linux 上实现了 FlexGuard，使用 LiTL 库通过 LD_PRELOAD 机制替换现有应用的 POSIX 锁。在 LevelDB、PARSEC Dedup、SPLASH2X Raytrace 和 Streamcluster 等真实应用中，FlexGuard 在非超订阅场景下吞吐量提升 1-6 倍，在超订阅场景下提升最高 5 倍。

## 主要研究方法

### 临界区抢占检测（Preemption Monitor）

研究团队利用 **eBPF** 技术在内核调度器层面进行精准检测。具体做法是：将一个 eBPF 处理程序挂载到 `sched_switch` 每次上下文切换事件上，在事件触发时判断被抢占的线程 `prev` 是否正在持有锁。

检测需要覆盖三种情况：

1. **应用程序临界区代码**：通过 per-thread 计数器 `cs_counter`（每获取一个锁加 1，释放一个锁减 1）判断。如果 `prev.cs_counter > 0`，则 `prev` 至少持有一个锁，处于临界区。
2. **lock() 函数内部持锁部分**：在 `at_break`（CAS 成功后）和函数末尾之间的代码中，虽然 `cs_counter` 还未增加，但线程已经持有了锁。通过比较抢占地址（preemption address）是否落在 `at_break` 和函数末尾之间的代码区间来判断。
3. **unlock() 函数内部释放部分**：在 `unlock()` 函数的 `at_store` 标签（实际执行 `L = UNLOCKED` 的位置）之前，线程仍持有锁。类似地通过抢占地址判断。

对于情况 1 和 2，还需要区分：在 `XCHG` 指令之后（`at_xchg` 和 `at_break` 之间），需要读取 `prev` 线程的 `RCX` 寄存器值（x86 架构下 `XCHG` 结果存放于此），如果值为 `UNLOCKED` 则表示锁已被获取，线程确实持锁。

检测到持锁线程被抢占后，处理程序设置 `prev.is_cs_preempted = True` 并原子地增加全局计数器 `num_preempted_cs`。

### 锁算法设计

FlexGuard 的锁算法受 Shuffle lock 的获取机制启发，设计目标是最小化资源竞争并快速唤醒被抢占的线程。锁在两种模式间动态切换：

- **Busy-waiting 模式**：`num_preempted_cs == 0`，表示没有持锁线程被抢占。此时使用 MCS 队列组织等待线程，减少缓存行竞争；MCS holder 在单变量锁上自旋。
- **Blocking 模式**：`num_preempted_cs > 0`，表示有持锁线程被抢占。此时等待线程立即阻塞在单变量锁上（通过 Futex），MCS 队列被绕过，等待线程直接竞争单变量锁。

锁的数据结构仅 12 字节（4 字节锁值 + 8 字节 MCS 队尾指针），每个线程只需一个 MCS 节点（所有锁共享），内存开销极小。

Fast path：线程首先尝试 TATAS 快速获取单变量锁（如果锁空闲则直接进入临界区），否则进入 slow path。

Slow path 分为两阶段：
- **Phase 1（MCS 入队等待）**：仅在 busy-waiting 模式执行。线程加入 MCS 队列并自旋等待成为队首。如果在此期间检测到 `num_preempted_cs > 0`（进入 blocking 模式），立即跳入 Phase 2。
- **Phase 2（获取单变量锁）**：在 busy-waiting 模式通过 CAS 自旋获取单变量锁；在 blocking 模式则通过 Futex 阻塞等待。

## 设计与实现

### eBPF Preemption Monitor

eBPF 处理程序通过 `sched_switch` tracepoint 挂载到内核调度器，不需要修改内核代码。处理程序读取被抢占线程的栈地址、寄存器值（通过 `bpf_get_task_stack()` 和 `bpf_get_task_registers()`），与 lock/unlock 函数中的汇编标签地址范围比对，结合寄存器值判断是否在临界区。关键地址通过 GCC 的 `&&label` 语法在用户空间代码中嵌入，eBPF 程序通过 BPF global 变量访问这些值。

`num_preempted_cs` 计数器是系统级别的全局变量（BPF global 变量），因为来自不同锁的等待线程都可能抢占持锁线程，跨进程的全局计数确保调度决策的一致性。实验表明，按锁独立的计数器性能反而更差。

### 锁算法实现

锁算法使用 C 语言针对 x86 架构实现。关键实现细节：

- 使用 inline assembly 确保 `XCHG` 指令的返回值存入 `RCX` 寄存器，供 eBPF 处理程序读取。
- 在 `lock()` 和 `unlock()` 函数中插入 GCC 汇编标签（`at_xchg`、`at_break`、`at_store` 等），eBPF 处理程序通过标签地址识别临界区代码范围。
- `cs_counter` 是 per-thread 变量，用于快速判断线程是否持有任何锁。
- `num_preempted_cs` 作为 eBPF global 变量，用户空间锁算法和 eBPF 处理程序均可访问，无额外同步开销。

### 与 LiTL 库的集成

使用 LiTL（Lightweight NUMA-aware Threading Library）通过 LD_PRELOAD 机制替换应用中所有 POSIX mutex、spinlock 和 rwsem 锁函数，实现零代码修改即可将 FlexGuard 应用于现有应用。eBPF Preemption Monitor（111 行）和锁算法（428 行）合计仅约 540 行代码。

### 正确性证明 Sketch

论文提供了正确性论证：

- **互斥性（Mutual Exclusion）**：FlexGuard 的不变式是"持锁线程必持有单变量锁"。无论在哪种模式下，获取单变量锁的方式（busy-waiting 或 blocking）不影响互斥属性的继承。
- **活性（Liveness）**：阻塞线程通过 Futex 机制等待，且只有在看到 `LOCKED_WITH_BLOCKED_WAITERS` 值时才阻塞，解锁时必唤醒一个等待线程（`futex_wake(&lock.val, 1)`），因此最终所有阻塞线程都会被唤醒。
- **公平性（Fairness）**：在 busy-waiting 模式由 MCS 队列保证顺序；在 blocking 模式由 Futex 队列保证顺序。模式切换期间可能出现短暂的非 FIFO 顺序，但实验表明长期公平性仍然良好（fairness factor < 0.58）。

## 主要实验结果

实验在两台机器上进行：Intel Xeon Gold 5320（26 核 104 超线程）和 AMD EPYC 9754（128 核 512 超线程），运行 Debian Linux kernel 6.9。

### 微基准测试（Shared-memory-access）

关键发现：在 Intel 104 硬件上下文的系统上，使用 140 个线程竞争同一把锁（访问两个缓存行），FlexGuard 的临界区执行时间比纯阻塞锁低 **92%**，比次优方案（MCS-TP）低约两个数量级。当系统从非超订阅（< 104 线程）过渡到超订阅（> 104 线程）时，所有纯自旋锁（MCS、POSIX、Shuffle lock）都经历了严重的性能崩塌，而 FlexGuard 保持稳定，性能跌幅远小于其他方案。

在 AMD 512 硬件上下文的系统上，结果类似，FlexGuard 临界区执行时间比纯阻塞锁低 **100%**，无任何性能崩塌。

### Hash Table 微基准测试

使用 100 个桶（100 把锁）的哈希表，Zipfian 分布访问模式。FlexGuard 在所有线程数下都取得了最高吞吐量，性能随线程数增加保持稳定，而其他自旋锁在超订阅下性能剧烈下降。与 POSIX 锁相比，FlexGuard 在 Intel 上平均吞吐量高出数倍。

### 数据库索引（PiBench on B+-Tree，LevelDB）

- **PiBench on B+-Tree**（16M 锁，14 把高竞争）：FlexGuard 在非超订阅下平均吞吐量是 POSIX 的 **4.2 倍**，在超订阅下是 **3.4 倍**。u-SCL 在此基准上因锁数量过多而崩溃。
- **LevelDB readrandom**：FlexGuard 在非超订阅下平均比 POSIX 快 **67%**，在超订阅下快 **25%**。
- **LevelDB fillrandom**：FlexGuard 在非超订阅下平均比 POSIX 快 **14%**，在超订阅下快 **11%**。

### PARSEC Dedup 和 SPLASH2X

- **Dedup**（最多 266K 锁）：FlexGuard 在非超订阅下平均比 POSIX 快 **24.7%**，在超订阅下快 **38.3%**。MCS、MCS-TP 和 Malthusian 因每锁每线程一个节点的设计在高锁数量下出现严重性能问题。
- **Raytrace**（45 把锁，1 把高竞争）：FlexGuard 在 Intel 非超订阅下平均比 POSIX 快 **4%**，超订阅下快 **21%**；在 AMD 上最高达到 **2 倍**吞吐量提升。
- **Streamcluster**（单锁竞争）：FlexGuard 在 Intel 独立基准上最高比 POSIX 快 **3.9 倍**；在 AMD 上平均比 POSIX 快 **20%**，最高 **3.5 倍**。

### 调度器开销（Hackbench）

开启 FlexGuard Preemption Monitor 后，Hackbench（650 线程，管道通信，压力测试调度器）的执行时间增加**不足 1%**，说明 eBPF 处理程序的性能开销可以忽略不计。

### 公平性分析

在 104 线程满载的 oversubscription 场景下（锁在两种模式间切换 72 次/秒），FlexGuard 的长期公平性因子（Fairness Factor）保持在 **0.58 以下**，与 MCS 的公平性相当，远优于 Malthusian（0.90）和 Shuffle lock（0.77）。

### 可运行线程数分析

在 140 线程竞争同一锁的实验中，MCS 锁始终保持所有 140 个线程处于 runnable 状态（busy-waiting），导致频繁的相互抢占；纯阻塞锁只有约 1 个 runnable 线程（持锁者），导致每次锁交接都需要完整的上下文切换；FlexGuard 在非超订阅期间保持适当数量的 runnable 线程（~30-60 个），在超订阅时减少到个位数，实现了自旋锁的快速锁交接和阻塞锁的低抢占干扰之间的平衡。

## 潜在问题 / 局限性

1. **eBPF 依赖**：FlexGuard 依赖 Linux eBPF 基础设施。虽然 eBPF 在现代 Linux 系统中已广泛可用，但该方案无法直接移植到不支持 eBPF 的操作系统（如 macOS、Windows、部分嵌入式系统）。作者指出理论上可迁移到其他实现了 Futex 类原语和类似 eBPF 跟踪机制的操作系统，但实际工作量不可忽视。

2. **Streamcluster 场景下的性能下降**：FlexGuard 在 Streamcluster 的 Intel 独立基准测试中，在某些并发线程配置下性能反而低于 POSIX（最高低 82%）。原因是 FlexGuard 的 busy-waiting 行为额外引入了超订阅，加剧了非持锁线程被抢占的频率，延迟了 barrier 的完成。这揭示了 FlexGuard 在 barrier 密集型工作负载中需要进一步优化的方向。

3. **模式切换期间的不公平性**：在 busy-waiting 模式向 blocking 模式切换时，线程执行 `mcs_exit()` 的顺序不受 MCS 队列约束，导致短暂的非 FIFO 顺序。虽然长期公平性可接受，但可能对严格的公平性需求场景（如实时系统）造成影响。

4. **临界区抢占的延迟感知**：eBPF Preemption Monitor 通过 `sched_switch` tracepoint 触发，依赖于上下文切换的发生。如果调度器在持锁线程的时间片耗尽后仍未进行切换（虽然实际中罕见），FlexGuard 可能无法立即感知抢占。不过一旦切换发生，检测是精确的，不依赖任何超时。

5. **内存开销**：虽然每个锁仅需 12 字节，但每个线程需要一个全局 MCS 节点（所有锁共享）。在大量线程的高竞争场景下，MCS 节点的缓存竞争仍是潜在瓶颈（好在 FlexGuard 的 blocking 模式可以规避这一问题）。

6. **内核版本兼容性**：eBPF tracepoint 的稳定性在不同内核版本间可能存在差异。虽然 `sched_switch` 是成熟稳定的 tracepoint，但内核内部实现的细节变化可能要求调整 eBPF 代码。

## 未来工作

1. **Barrier 支持**：FlexGuard 目前专注于锁，论文明确指出需要在 barrier（同步屏障）场景下进行适配。Streamcluster 的实验结果已证明这是当务之急。
2. **扩展到其他同步原语**：将 FlexGuard 的方法扩展到读写锁（reader-writer locks）、条件变量（condition variables）等其他同步原语，改进标准库中的实现。
3. **NUMA-aware 锁集成**：将 FlexGuard 的精确抢占检测与 NUMA 感知的锁算法（如 Shuffle lock、H-CLH、Lock cohorting）结合，在多 NUMA 节点场景下同时优化本地访问和抢占检测。
4. **虚拟化环境支持**：将 Preemption Monitor 扩展到支持检测虚拟 CPU 抢占检测，适配虚拟机和容器化部署场景。
5. **Delegation Locks 集成**：FlexGuard 可与 delegation-based 锁（如 TCLocks、ffwd）结合使用，进一步减少同步开销。
6. **内核锁优化**：Linux 内核内部也使用大量自旋锁，user-space 锁的优化成果可能反过来启发内核自旋锁的改进，特别是在虚拟化环境中。

## 个人评注

FlexGuard 是一项极具工程价值的系统研究工作，核心洞察非常清晰：**与其猜测何时应该从自旋切换到阻塞，不如直接问调度器发生了什么**。eBPF 的成熟使得这一"问调度器"的想法在不需要修改内核的前提下成为现实，这是近年来 OS 系统研究中最有实用价值的进展之一。

论文的方法论令人印象深刻：不依赖任何启发式参数，而是构建了一个精确的感知-反应系统——eBPF 监控精确感知抢占事件，用户空间锁算法立即做出反应。这种"精确感知 + 即时响应"的设计哲学比启发式调参更优雅、更健壮、更具可移植性。

从工程角度看，FlexGuard 的实现非常克制：仅 111 行 eBPF 代码 + 428 行锁算法 + LiTL 库的 LD_PRELOAD 集成，使得零代码修改应用现有程序成为可能。这极大地降低了工业界采用的门槛——不需要重写应用、不需要修改内核，只需要部署一个 BPF 程序和一个替换库。

实验设计也值得称赞：不仅测试了标准微基准，还覆盖了 LevelDB、Dedup、Raytrace、Streamcluster 等多个真实应用，并分别测试了独立运行和并发竞争两种场景，全面地验证了方案的有效性。

获奖方面，FlexGuard 获得了 SOSP 2025 的 **Distinguished Artifact Award**，说明其 Artifact（代码仓库、实验环境）的可复现性和可验证性得到了社区的高度认可。这是继 2021 年 "The Case for Writing Dynamic Kernel Modules in Rust" 和 2023 年 "dm: dynamic policy replication" 之后，OSDI/SOSP 会议上又一篇因系统工作完整性而获奖的研究。

总体而言，FlexGuard 属于"问题本身很经典（自旋锁的 oversubscription 性能崩塌），但解决方案极具创新性（eBPF 精确感知 + 自适应模式切换）"的类型，对高性能服务器应用、数据库内核等场景有直接的实用价值。
