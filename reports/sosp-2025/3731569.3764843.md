# KTransformers: Unleashing the Full Potential of CPU/GPU Hybrid Inference for MoE Models

## 1. 论文基本信息

- **标题**: KTransformers: Unleashing the Full Potential of CPU/GPU Hybrid Inference for MoE Models
- **作者**: Hongtao Chen, Weiyu Xie, Boxin Zhang, Jingqi Tang, Jiahao Wang, Jianwei Dong, Shaoyuan Chen, Ziwei Yuan, Chen Lin, Chengyu Qiu, Yuening Zhu, Qingliang Ou, Jiaqi Liao, Xianglin Chen, Zhiyuan Ai, Yongwei Wu, and Mingxing Zhang
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764843
- **代码**: https://github.com/kvcache-ai/ktransformers

## 2. 研究背景

**MoE 模型的时代**：Mixture-of-Experts (MoE) 大语言模型通过条件计算（每次仅激活部分 experts）显著降低了计算需求。DeepSeek-V3/R1 等模型达到了 SOTA 开源权重性能，引发了对本地部署的广泛需求。

**MoE 的稀疏激活特性**：MoE 模型非常适合两种部署场景：
1. **大规模云部署**：高并发（每秒数万个请求），频繁的 expert 激活提高硬件利用率
2. **本地部署**：低并发（单请求或少批量），稀疏 expert 激活大幅减少内存访问开销

**本地部署的核心挑战**：GPU 显存限制——即使是最先进的 GPU（H100 80GB），也无法容纳整个 671B DeepSeek-V3。CPU/GPU 混合推理利用 CPU/DRAM 的大容量低成本和 GPU/VRAM 的高带宽，是有前景的解决方案。

**现有混合方案的局限性**：Fiddler 等前期工作证明了基于 arithmetic intensity 的 partition 可以减少 GPU 内存需求。但在 671B DeepSeek-V3/R1 的真实评估中，性能严重受限：
- Prefill 阶段：仅 70.02 tokens/秒
- Decode 阶段：仅 4.68 tokens/秒
- GPU 利用率：低于 30%

**两大效率瓶颈**：
1. **Prefill 阶段 CPU 计算利用不足**：MoE prefill 处理长 prompts（多个 experts 频繁激活），现有方案使用通用 SIMD 指令，未充分利用 AMX 硬件扩展
2. **Decode 阶段低效 CPU-GPU 协调**：decode phase 每次仅激活少数 experts，执行时间极短（数毫秒），导致同步开销超过计算本身

## 3. 要解决的问题

**核心问题**：如何在资源受限的本地硬件（单 GPU + 多 CPU）上高效运行大规模 MoE 模型（如 671B DeepSeek-V3/R1）？

具体挑战：
- **AMX 优化缺失**：现有方案未充分利用 Intel AMX 指令，导致 CPU 端计算效率极低（理论峰值的 7%）
- **CPU-GPU 同步瓶颈**：短 kernel 执行时间使得传统同步方法（阻塞等待）开销极大
- **低下的并行性**：CPU 和 GPU 利用率都极低，浪费计算资源

## 4. 核心贡献

1. **AMX 优化的 Arithmetic Intensity-Aware Hybrid Inference Kernel**：通过分析不同任务的 arithmetic intensity（AI），选择性地使用 AMX 指令（高 AI 任务，如 prefill 阶段）或轻量 AVX-512（低 AI 任务，如 decode 阶段），配合 block-wise quantization、64-byte alignment、tiling-aware submatrix access。
2. **Asynchronous CPU-GPU Task Scheduling**：基于 advanced CUDA Graph 的异步调度，将整个 decode phase 封装为单个 CUDA Graph 实例，减少 kernel launch 开销，实现 CPU 和 GPU 计算的 overlap。
3. **Expert Deferral 机制**：通过重构执行流水线，将部分 experts（deferred experts）延迟到下一层的 attention 计算期间并行处理，提高 CPU 和 GPU 并行性至接近 100%。
4. **Trillion-parameter 规模支持**：在单台服务器（单 GPU + 多 CPU）上支持万亿参数级别的 MoE 模型。
5. **广泛采用**：已在上百台机器上使用，被开源社区和工业团队广泛采用。

## 5. 主要研究方法

### 5.1 系统级性能分析
- **CPU 计算分析**：使用 Intel AMX kernel vs PyTorch AMX kernel 的 microbenchmark 对比，发现 1.69-4.30x speedup
- **CPU-GPU 协调分析**：通过 profiling 发现 decode phase CPU 利用率 < 75%，GPU 利用率 < 30%

### 5.2 AMX Kernel 设计
- **Block-wise Quantization**：对 experts 进行块级量化，减少内存带宽需求
- **64-byte Alignment**：配合 AMX tile 加载的内存对齐要求
- **Tiling-aware Submatrix Access**：优化 AMX tile 访问模式，提高 cache locality

### 5.3 Expert Deferral 分析
在 DeepSeek-V3 的案例中，Expert Deferral 将 CPU/GPU 利用率从 74%/28% 提升到 **100%/37%**，decode 吞吐量提升 33%。

关键设计：在每个 MoE layer 内，仅处理部分 experts（immediate experts），其余 deferred experts 与下一层的 attention 计算并行处理。

## 6. 设计与实现

### 6.1 Arithmetic Intensity-Aware Kernel
- 高 AI 任务（prefill 长 prompts）使用 AMX 指令集，充分利用 VNNI/AMX 硬件加速
- 低 AI 任务（decode 短 prompts）默认使用轻量 AVX-512 内核，避免 AMX 的 setup overhead
- 通过离线 profiling 确定每个 layer 的 AI 值

### 6.2 Throughput-Preserving NUMA-Aware Tensor Placement
- 多 socket CPU 系统中的 NUMA-aware tensor placement
- 确保 tensor 分配在访问它的 socket local memory
- 避免跨 NUMA 访问的额外延迟

### 6.3 Asynchronous CPU-GPU Scheduling
- 利用 CUDA Graph 将整个 decode phase 封装为单个可执行单元
- 避免为每个 layer 和 batch size 创建单独的 CUDA Graph 实例
- 通过 CUDA-based spinning 实现异步 CPU-GPU 通信

### 6.4 Expert Deferral 流水线
```
传统流水线：
  Layer N: Attention + MoE (All Experts Sequential)
  Layer N+1: Attention + MoE (All Experts Sequential)

Expert Deferral 流水线：
  Layer N: Attention + MoE (Immediate Experts)
                    ↓ 与 Layer N+1 Attention 并行执行
            MoE (Deferred Experts)
```

### 6.5 实现规模
- 11,000 行 C++（性能关键组件）
- 2,000 行 Python（集成脚本）
- 作为 HuggingFace-style transformer inference 的 drop-in replacement

## 7. 主要实验结果

### 7.1 Microbenchmark
- AMX kernel：相比 PyTorch AMX kernel **1.69-4.30x speedup**
- 相比 PyTorch AVX-512 kernel：显著改善

### 7.2 Prefill 性能
- **4.62-19.74x speedup** 相比现有系统

### 7.3 Decode 性能
- **1.25-4.09x speedup** 相比现有系统
- Expert Deferral 带来额外的 **1.45x 吞吐提升**

### 7.4 准确率影响
- 在 HumanEval、MBPP、GSM8K、StrategyQA、LiveBench 等 benchmark 上，**平均准确率下降不超过 0.5%**

### 7.5 CPU/GPU 利用率
- Expert Deferral 将 CPU 利用率从 <75% 提升到接近 **100%**
- GPU 利用率从 <28% 提升到 **37%**

### 7.6 生产采用
- 在数百台机器上部署使用
- 开源社区广泛采用
- 支持多种 MoE 模型架构

## 8. 潜在问题/局限性

1. **AMX 硬件依赖**：KTransformers 的核心 AMX 优化依赖 Intel 硬件扩展。对于 AMD EPYC（支持 AVX-512 但不支持 AMX）或 Apple Silicon（不支持 AMX）的用户，无法获得相同的性能收益。
2. **DeepSeek-V3 特定优化**：Expert Deferral 机制针对 DeepSeek-V3 的 shared experts + routed experts 架构设计。对于其他 MoE 架构（如 Switch Transformer、Hash Layer），deferral 策略可能需要重新调整。
3. **模型量化精度损失**：虽然论文声称平均准确率下降不超过 0.5%，但这是在特定 benchmark 上的测量。对于对精度更敏感的应用（如代码生成、数学推理），0.5% 的下降可能累积为显著的质量问题。
4. **CUDA Graph 的局限性**：将整个 decode phase 封装为单个 CUDA Graph 依赖于静态 tensor shapes。在 dynamic batching 或 speculative decoding 等动态场景下，CUDA Graph 的适用性可能受限。
5. **Expert Deferral 的调度开销**：Deferred experts 与下一层 attention 的并行调度引入了额外的协调开销。对于极短 prompts（decode phase 本身就很快），这个开销可能超过收益。
6. **单 GPU 配置的通用性**：论文专注于单 GPU + 多 CPU 配置。对于多 GPU 设置（tensor parallelism、pipeline parallelism），KTransformers 的设计需要如何配合未讨论。
7. **与 vLLM、TGI 等推理服务框架的集成**：KTransformers 作为 HuggingFace drop-in replacement，但与生产推理服务的集成（continuous batching、paged attention 等）未讨论。

## 9. 未来工作

1. **多 GPU 支持**：扩展 Expert Deferral 到 tensor parallelism 和 pipeline parallelism 设置。
2. **Speculative Decoding 集成**：将 Expert Deferral 与 speculative decoding 结合。
3. **动态 batching 优化**：为 dynamic batching 场景优化 AMX kernel。
4. **更多硬件支持**：AMD ROCm 上的 AMX-equivalent 优化。
5. **Expert Deferral 的自适应策略**：根据运行时 performance 自动调整 immediate vs deferred experts 的比例。

## 10. 个人评注

**KTransformers 是一篇来自开源社区并经过广泛生产验证的系统论文**，它针对 MoE 模型本地推理这一日益重要的场景，从系统层面识别和解决了多个关键瓶颈。

论文最有价值的贡献是**Expert Deferral 机制**——这个洞察极其简洁但深刻：与其等待所有 experts 都计算完再进行下一层，不如将 experts 分批处理，让 deferred experts 与下一层的 attention 计算并行。这个"流水线并行"的思想与 GPU 训练中的 sequence parallelism 和 pipeline parallelism 有异曲同工之妙，但针对的是推理的混合 CPU-GPU 设置。

**批评性思考**：
- **"4.62-19.74x speedup"的基准线不够清晰**：这个对比是相对于什么？现有系统的具体定义未明确。如果"现有系统"是 Fiddler 或其他混合推理框架，那么 Fiddler 本身可能也有优化空间，直接对比可能不公平。
- **AMX kernel 的 7% 理论峰值利用率**是一个令人震惊的数字：这个低利用率是否完全归因于"suboptimal memory layouts"？还是有更深层的原因（如 quantization 不支持、kernel fusion 不足）？论文没有给出完整的根因分析。
- **Expert Deferral 的准确率影响**讨论不足：0.5% 的平均下降是在综合 benchmark 上的结果。对于特定任务（尤其是 MoE 模型的 expert routing 机制对某些输入可能路由到完全不同的 experts），deferred vs immediate 的选择是否会影响模型行为？
- **NUMA-aware placement 的讨论过于简洁**：多 socket CPU 系统中的 NUMA 效应是复杂的——不仅仅是"分配到 local memory"，还包括跨 socket 访问的延迟差异、CPU cache 共享等。论文的方案是否考虑了所有这些因素？
- **与现有推理优化的叠加效果**：KTransformers 优化了 MoE layer 的执行，但未讨论与 paged attention、continuous batching 等其他推理优化技术的交互。在实际部署中，这些优化如何配合？
- **开源影响力可能被高估**：论文声称"已在上百台机器上使用"，但没有具体数据（如实际处理的请求量、节省的成本）。这可能是一种营销声明而非严格的工程验证。

总体而言，这是一篇实用价值很高的论文，适合 LLM 推理工程师和 MoE 模型部署研究者阅读。Expert Deferral 机制是一个值得深入理解和实验验证的创新点。
