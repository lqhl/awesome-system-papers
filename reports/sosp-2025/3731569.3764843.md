## 一、背景

Mixture-of-Experts（MoE）大语言模型（如 DeepSeek-V3/R1、Qwen2 系列）凭借条件计算稀疏性，在保持高性能的同时大幅降低了每 token 的计算量，成为当前最具竞争力的开放权重模型架构。然而，MoE 模型参数量极大（671B 参数级别），在本地部署时面临严峻的 GPU 显存瓶颈。

CPU/GPU 混合推理是解决这一矛盾的有效途径：将 MoE 的 routed experts 常驻 CPU/DRAM，利用 CPU 大容量、低成本内存承载绝大多数参数，同时借助 GPU 处理 attention 和 shared experts 等高算术密度任务。先前工作（尤其是 Fiddler）已验证了这一思路的可行性，但在真实大模型（671B DeepSeek-V3）上仍严重受制于 CPU 计算瓶颈和 CPU-GPU 同步开销。

本文聚焦「资源受限的本地单服务器部署」场景（低并发，如单个用户请求），该场景下 MoE 稀疏激活的特性最能发挥价值。

## 二、要解决的问题

### 1. CPU 计算严重欠优化（prefill 阶段）

Prefill 阶段一批处理大量 token，每个 expert 被高频激活，属于高算术密度（ARI）任务，理论上可以充分利用 Intel AMX 等先进指令集。但现有 PyTorch 通过 oneDNN 调用 AMX 时，实测只能达到 AMX 理论峰值（73.7 TFLOPS）的约 **7%**，根因在于内存布局与 AMX tile 寄存器不匹配，导致缓存效率低下。

### 2. CPU-GPU 同步开销过高（decode 阶段）

Decode 阶段每步只处理 1 个 token，CPU/GPU 的 kernel 执行时间极短（毫秒级甚至更短），传统同步方式下：
- Fiddler 每 token 触发 7,000+ CUDA kernel launch，平均延迟 16µs，仅 launch overhead 就占 GPU 执行时间的 **73%**
- Llama.cpp 优化后降至约 3,000 次，但 launch overhead 仍占 **21%**
- CUDA Graph 在 CPU/GPU 混合场景下因动态 tensor shape 和跨设备同步点而难以直接应用，现有框架频繁将 graph 碎片化

### 3. NUMA 感知缺失（CPU-CPU 协调）

现代服务器多为双路 CPU，跨 socket 内存访问延迟和带宽劣于本地访问。Fiddler 和 Llama.cpp 均未区分 NUMA 拓扑，导致 MoE 层解码在双路机器上仅比单路快 **16%**，远低于理论上限。

### 4. CPU 与 GPU 并行度不足

传统 Transformer 的 attention → MoE → attention 严格串行依赖，导致 CPU 计算完成后 GPU 才能启动 attention，双方轮流空闲。实测 DeepSeek-V3 在混合推理下 CPU 利用率仅 **74%**，GPU 利用率仅 **28%**，CPU-GPU 重叠执行时间只占总时间的 5%。

## 三、核心设计

KTransformers 是一个专为异构 CPU/GPU 硬件设计的高性能 MoE 推理系统，核心思路是「充分榨干 CPU 和 GPU 的每一分算力，并最大化二者并行」。

### 3.1 算术密度感知的混合推理内核

- **Prefill 阶段（高 ARI）**：使用 Intel AMX 指令集，配合专为 AMX tiling 设计的内存布局（64 字节对齐、block-wise 量化、tile-aware submatrix 访问模式），充分利用 L1/L2/L3 缓存层次，实现 21.3 TFLOPS，比 PyTorch AMX baseline 快 **3.98×**
- **Decode 阶段（低 ARI）**：切换为 AVX-512 内核，因为 decode 阶段是 vector-matrix multiplication，AMX 全 tile 处理反而引入过多开销；实测在 ≤4 tokens/expert 时 AVX-512 优于 AMX
- **动态自适应**：运行时根据每个 expert 分配的 token 数（即 ARI）在 AMX 和 AVX-512 间动态切换

### 3.2 异步 CPU-GPU 任务调度

利用 `cudaLaunchHostFunc` 将 CPU 侧的「submit routed-expert 任务到无锁队列」和「等待 CPU 结果」两个同步点内嵌进 CUDA stream，从而将整个 decode 过程封装进 **单个 CUDA Graph 实例**，彻底消除 kernel launch overhead，decode 阶段提速最高 **1.23×**。

### 3.3 NUMA 感知张量并行

不采用 Expert Parallelism（整个 expert 分配给一个 socket），而是对每个 expert 的权重矩阵按列/行方向在两个 socket 间切分，各 socket 本地计算后用 reduce-scatter 合并。消除几乎所有跨 socket 内存访问，decode 阶段提速最高 **1.63×**。

### 3.4 Expert Deferral（专家延迟执行）

核心 insight：Transformer 的残差连接赋予模型对「延迟中间计算」的鲁棒性。

将第 *k* 层的 routed experts 分为两类：
- **Immediate Experts**：输出立即喂给第 *k+1* 层 attention，遵循标准流程
- **Deferred Experts**：推迟到第 *k+2* 层 attention 之后才汇入，其计算可与第 *k+1* 层的 attention（GPU 侧）完全并行

形式化：启用 Expert Deferral 后，第 *k* 层 MoE 输出变为：

$$O_k = I_k + S_k(I_k) + R_k^{\text{imm}}(I_k) + R_{k-1}^{\text{def}}(I_{k-1})$$

注意：Expert Deferral **仅在 decode 阶段**使用。Prefill 阶段 token 覆盖面广，延迟执行会导致内存访问量翻倍，反而成为瓶颈。

## 四、实现细节

- **代码规模**：11,000 行 C++ 扩展（性能关键路径）+ 2,000 行 Python（集成层），通过 pybind11 导出
- **与 HuggingFace 无缝集成**：KTransformers 以「模块注入框架」替换 PyTorch 模块，用户无需修改模型代码，通过 YAML 配置文件声明替换规则（正则名称匹配 + 类名匹配 + 设备 + 量化参数）
- **量化支持**：CPU 侧 Int8/Int4 对称 group-wise 线性量化，Int4 tile 打包进 Int8-sized blocks 并用 SIMD intrinsics 解包；GPU 侧接入 Marlin kernel（mixed-precision）和 FlashInfer MLA attention
- **Fused MoE 算子**：将 Gate/Up/Down 三个 projection 融合为两个 fused batch（Gate+Up 无依赖可合并），加上动态任务调度（lock-free task queue），prefill 阶段因此额外提速最高 **1.83×**
- **Expert Deferral 配置策略**：确保至少 2 个 immediate experts（维持模型稳定性），并尽量少延迟以充分利用 CPU；DeepSeek-V3 BF16 模式下配置为 5 immediate + 3 deferred，Int4 模式下为 2 immediate + 6 deferred
- **开源**：https://github.com/kvcache-ai/ktransformers，已在数百台机器上生产部署

## 五、实验结果

**实验平台**：双路 Intel Xeon Platinum 8452Y（各 36 核，各 1TB DDR5，单路内存带宽 220 GB/s，跨路 125 GB/s）；GPU 分别配置 NVIDIA A100 40GB 和 RTX 4080 16GB，均通过 PCIe 4.0（32 GB/s）连接

**评测模型**：

| 模型 | 简称 | 总参数 | GPU 参数 | CPU 参数 | MoE 层数 |
|------|------|--------|----------|----------|---------|
| DeepSeek-V3-0324 | DS-3 | 671B | 17B | 654B | 58 |
| DeepSeek-V2.5-1210 | DS-2 | 236B | 13B | 223B | 59 |
| Qwen2-57B-A14B | QW-2 | 57B | 8B | 49B | 28 |

**对比基线**：Fiddler（PyTorch），Llama.cpp（C++，扩展了 expert-level offloading）

### Prefill 性能（batch=1，prompt 32~8192 tokens）

| 模型 | 最高加速比 vs Fiddler | 最高加速比 vs Llama.cpp |
|------|----------------------|------------------------|
| DS-3 BF16 | ~5× | ~19.74× |
| DS-2 BF16 | ~8× | ~15× |
| QW-2 BF16 | ~10× | ~12× |

总体：**4.62–19.74×** prefill 加速（含量化模型，相对于两个基线中更慢的那个）

### Decode 性能（prompt=32 tokens）

| 模型 | vs Fiddler（无 ED） | vs Llama.cpp（无 ED） | vs Llama.cpp（含 ED） |
|------|--------------------|-----------------------|-----------------------|
| DS-3 BF16 | 2.42× | 1.25× | 1.66× |
| DS-2 BF16 | 4.09× | 1.76× | 2.56× |
| QW-2 BF16 | ~3× | ~1.5× | ~2× |

### Expert Deferral 效果（DS-3 DeepSeek-V3 BF16）

- CPU 利用率：74% → **100%**
- GPU 利用率：28% → **37%**
- Decode 吞吐提升：**+33%**（vs 不启用 ED）

### 精度影响（Expert Deferral，量化模型）

| 模型配置 | HumanEval | MBPP | GSM8K | StrategyQA |
|---------|-----------|------|-------|------------|
| DS-3 (8+0，无 ED) | 83.0 | 71.2 | 94.8 | 83.0 |
| DS-3 (2+6，含 ED) | 83.0 | 70.2 | 95.2 | 82.9 |
| DS-2 (6+0) | 80.5 | 67.6 | 93.3 | 79.7 |
| DS-2 (2+4) | 82.5 | 66.8 | 92.8 | 80.4 |

Expert Deferral vs Expert Skipping（DS-3 LiveBench，6 experts affected）：
- Expert Deferral 平均精度下降：**0.5%**
- Expert Skipping 平均精度下降：**13.3%**

## 六、批判性分析

### 1. 单 batch=1 场景的局限性

论文所有实验均限于 batch size=1（本地单用户场景），这是 KTransformers 的目标场景，无可厚非。但现实中本地服务也可能有多并发请求（如 llama.cpp 的多用户模式）。在 batch size > 1 时，Expert Deferral 的效果是否仍然显著？prefill 阶段 AMX 的相对优势是否会因 GPU 成为瓶颈而消失？论文对此完全没有讨论。

### 2. Expert Deferral 的理论依据偏弱

论文将 Expert Deferral 的可行性归因于残差连接的鲁棒性，但并未提供正式的理论证明或深入分析。精度损失在某些 LiveBench 子任务（如 Instruction Following、Data Analysis）上最高达 **8-18%**（见 Figure 13，8 deferred experts 配置），论文对此只是通过「使用尽量少的延迟 experts」来规避，而非真正解决。

### 3. 实验规模和硬件代表性不足

论文只在单一服务器（两种 GPU 配置）上测试，无法评估系统在不同 PCIe 代（如 PCIe 5.0）、不同 CPU 微架构（AMD EPYC、ARM Neoverse）上的泛化性。AMD 同样有 AMX 类似指令（VNNI），但论文未讨论可移植性。

### 4. prefill 与 decode 的加速比悬殊引发疑问

prefill 最高加速 19.74×（相对 Llama.cpp），但 decode 最高仅 4.09×（相对 Fiddler）。如此大的差距主要来自 Llama.cpp 在 prefill 上原本就很差（因其 BF16 CUDA kernel 缺失，只能用 FP16 替代），这个对比基线选取对结果呈现有放大作用。

### 5. Expert Deferral 在 prefill 不适用的讨论不够深入

论文指出 prefill 时 token 覆盖几乎所有 expert，导致延迟执行会使内存访问量翻倍。这个结论值得质疑：实际生产中 prefill prompt 长度各异，专家覆盖率也不同。对于较短 prompt（如 32-128 tokens），Expert Deferral 在 prefill 阶段的影响如何？论文没有实验支撑。

### 6. 系统实际吞吐数字不够直观

论文大量报告「加速比」，但本地实际 token/s 的绝对值（DS-3 BF16 decode 约 5-6 token/s）其实对用户体验仍然偏慢，尤其对比 multi-GPU 服务端部署的百 token/s 级别。作者在这方面刻意淡化了绝对性能数字。

## 七、AI Infra / MLSys 视角

### 对 AI Infra 研究的启发

**1. CPU 算力被严重低估**

现代服务器 CPU 配备 Intel AMX（峰值 73.7 TFLOPS/socket）后，其计算能力在特定场景下不容忽视。本文展示了通过 AMX tiling-aware 内存布局和 cache-friendly 执行，CPU 实际可达 21.3 TFLOPS（约峰值的 29%），远高于现有框架的 7%。这对「CPU 不能做 LLM inference」的刻板印象是重要修正。

**2. 异构调度的细粒度设计**

Expert Deferral 本质上是一种「计算重排序」技术：通过牺牲少量模型精度，换取跨 layer 的 CPU-GPU 并行度。这种思路可以推广到其他异构场景，如 CPU-NPU 混合推理、GPU-FPGA 协同加速，值得在更一般化的框架下研究。

**3. 单 CUDA Graph 封装动态工作负载的技巧**

将「宿主机回调」通过 `cudaLaunchHostFunc` 内嵌进 CUDA stream，从而在 MoE 这种典型动态 shape 场景下实现完整 CUDA Graph，是值得借鉴的工程技巧，对其他具有 CPU-GPU 异步交互的系统（如 speculative decoding、cascade inference）有参考价值。

**4. NUMA 拓扑感知是「免费午餐」**

双路服务器普及率极高，但主流框架几乎都忽略 NUMA 感知，导致实测性能远低于理论上限。KTransformers 的 NUMA-aware tensor parallelism 方案实现简单（列/行切分 + reduce-scatter），但效果显著（最高 1.63×）。在分布式训练和大模型推理框架中，NUMA 优化是值得系统性研究的低垂果实。

### 值得跟进的 Future Work

1. **Expert Deferral 的自动配置**：当前需要人工调参（几个 immediate、几个 deferred），能否根据实时硬件负载和模型精度需求自动调整？类似 adaptive batching 的思路。
2. **多并发场景的 CPU-GPU 调度**：batch size > 1 时，routed expert 的选择不同，CPU 任务的并发结构更复杂，如何高效调度？
3. **跨架构移植**：AMD EPYC + CDNA GPU 的组合在数据中心更常见，如何将 AMX-specific 优化迁移到 ZNVER 架构？
4. **与 speculative decoding 结合**：CPU 侧可以承载 draft model，GPU 侧运行 target model，Expert Deferral 的异步调度框架天然适合 speculative decoding 场景。
5. **Prefill-decode 分离架构中的应用**：在 disaggregated prefill/decode 系统（如 DistServe、Mooncake）中，CPU/GPU 混合推理如何定位？是否可作为 decode 节点的低成本替代？

## 八、总结

KTransformers 是一个专为本地 CPU/GPU 混合 MoE 推理设计的高性能系统，通过三项关键技术——AMX/AVX-512 自适应 CPU 内核（含 NUMA 感知张量并行）、基于单一 CUDA Graph 的异步 CPU-GPU 调度、以及 Expert Deferral 执行重排序——实现了对最先进大 MoE 模型（671B DeepSeek-V3）的高效本地部署，综合加速比达 1.66–19.74×，精度损失不超过 0.5%。其主要局限在于：（1）仅验证了 batch=1 单用户场景，多并发性能未知；（2）精度损失缺乏理论保证，在部分子任务上风险不可忽视；（3）硬件平台单一，跨架构可移植性待验证。对 AI Infra 研究者而言，本文最有价值的 insight 在于：重新评估 CPU 在高端 MoE 推理中的角色，以及计算重排序（Expert Deferral）作为提升异构并行度的通用手段。
