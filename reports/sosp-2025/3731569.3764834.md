## 一、背景

LLM 正在从生成式应用（ChatGPT、GitHub Copilot）向传统判别式任务渗透。Meta、LinkedIn 等公司已在生产环境中大规模部署 LLM 用于推荐系统、信贷审核、数据标注等场景。这类任务的共同特点是：LLM 只需为每个请求生成**一个 token** 的概率分布（如 Yes/No 的概率），而非多轮解码生成长文本。

此外，prefill-only workload 还出现在以下场景：
- **Embedding 生成**：Qwen3-Embedding 等模型将 `<EOS>` token 的隐层状态作为文档向量，整个推理是 prefill-only 的。
- **Prefill-decode 解耦**：在 disaggregated 推理架构（DistServe、Mooncake）中，prefill 节点上的负载天然是 prefill-only 的。

现有 LLM 推理引擎（vLLM 等）以生成式场景为设计目标，无法高效处理 prefill-only workload。

---

## 二、要解决的问题

**问题 1：KV cache 内存占用限制了最大输入长度（MIL）**

现有推理引擎为所有层存储 KV cache（以支持 decoding 复用）。对于长输入请求（推荐场景中用户画像可达数万 token），这导致 GPU 内存耗尽：
- Qwen-32B（FP8）在 A100 40GB 上，MIL 仅 11,000 tokens。
- 为突破 MIL，现有方案（chunked prefilling、tensor/pipeline parallelism）均以牺牲吞吐量为代价。

简单丢弃 KV cache 也无济于事：实验测量仅带来 1.6× MIL 提升（理论上限 2.41×），因为 MLP 等线性层的临时中间张量（intermediate tensors）才是真正的内存瓶颈——Llama-3.1-8B 中 MLP 中间张量高达 28,672 floats/token，是单层 KV cache（2,048 floats/token）的 14 倍。

**问题 2：调度算法对 JCT（任务完成时间）不感知**

Prefill-only 请求的输出长度恒为 1，JCT 理论上可精确预测，但现有引擎使用 FCFS 等 JCT-agnostic 调度。更严重的是，在 prefix caching 场景中，请求的 prefill 时间随 cache 命中情况动态变化——到达时估算的 JCT 会很快失效，导致调度顺序不优，进一步引发 prefix cache thrashing。

---

## 三、核心设计

PrefillOnly 建立在 vLLM 之上，提出三项核心技术：

**1. Hybrid Prefilling（混合预填充）**

关键洞察：LLM 推理的内存瓶颈来自非 attention 层（MLP/线性层）的中间张量，而非 KV cache 本身。Hybrid Prefilling 的策略是：
- **非 attention 层（线性层）按 chunk 处理**：每次只为一个 chunk 分配中间张量，而非为所有 token 同时分配，大幅降低峰值显存。
- **Attention 层保持完整处理（不 chunk）**：保留 attention kernel 的高效执行（chunked prefilling 会使 attention 性能下降 14%）。

此设计在**单次 forward pass** 内完成 prefill，这是关键：只有单次 forward pass，才能在推理中途丢弃 KV cache 而无需后续 reload。

实现细节：使用 `torch.compile` 修改计算图，将连续线性操作组合为虚拟层后分块执行，配合两项优化——**输出预分配**（避免 concat 导致内存翻倍）和**原地计算**（input/output 形状相同时复用内存）。

**2. Suffix KV Cache Discarding/Offloading**

- 保留 prefix tokens 的 KV cache（用于 prefix caching 命中）。
- 推理**执行过程中**（而非执行后）丢弃或 offload suffix tokens 的 KV cache。
- Hybrid Prefilling 是该技术的使能条件——正因为单次 forward pass 完成 prefill，suffix KV cache 丢弃后无需重算。

**3. Shortest Prefill First with Continuous Prefill Time Estimation**

- 每个调度步骤前，对**等待队列中所有请求**重新估算 prefill 时间（而非仅在到达时估算一次）。
- 动态捕捉 prefix cache 命中变化，将可命中 cache 的请求提前调度，最大化 cache hit rate。
- 用 cache-miss token 数（$n_{input} - n_{cached}$）作为 prefill time 的代理指标（与 A100 上实测 prefill 时间 Pearson 相关系数为 0.987）。
- 防饥饿机制：调度分数 = $T_{prefill}(n_{input}, n_{cached}) - \lambda \cdot T_{queue}$，通过超参数 $\lambda$ 平衡公平性与平均延迟。

---

## 四、实现细节

- 基于 vLLM 实现，新增约 **4,600 行 Python 代码**。
- 使用 `torch.compile` 实现 hybrid prefilling，无需新增自定义 CUDA kernel，可泛化到不同 LLM 架构和硬件。
- Suffix KV cache discarding 复用了 vLLM 中 sliding window attention 的抽象接口。
- 系统使用 ZeroMQ-based RPC 在调度器进程与执行器进程间通信。
- 通过 profile run（用最大长度的合成请求）预估峰值 GPU 内存需求，剩余内存用于 prefix KV cache。
- Suffix KV cache offloading 预留为 future work，当前实现只做丢弃（discard）。

## 五、实验结果

**实验平台**

| 场景 | GPU | LLM 模型 |
|------|-----|---------|
| Low-end | 2× NVIDIA L4 PCIe (24GB) | Llama-3.1-8B |
| Middle-end | 2× NVIDIA A100 PCIe (40GB) | DeepSeek-R1-Distill-Qwen-32B-FP8 |
| High-end | 2× NVIDIA H100 PCIe (80GB) | Llama-3.3-70B-Instruct-FP8 |
| High-end w/ NVLink | 2× NVIDIA H100 NVLink (80GB) | Llama-3.3-70B-Instruct-FP8 |

**数据集**：两类模拟 trace（无真实生产 trace）：
- Post recommendation：20 用户，每用户 50 请求，用户画像 11k–17k tokens，post 150 tokens
- Credit verification：60 用户，每用户 1 请求，输入长度 40k–60k tokens

**主要结果**

| 指标 | 结果 |
|------|------|
| QPS 提升（不增加 avg/P99 延迟） | **1.4–4.0×** vs 所有 baseline |
| MIL 提升（vs PagedAttention） | **3.6–7.9×** |
| MIL 提升（vs Chunked Prefilling） | **最高 8.7×**（A100，Qwen-2.5-32B-FP8）|
| MIL 提升（vs 非并行化 baseline，无吞吐下降） | **最高 5×** |

**最大输入长度对比（单 GPU 等效）**

| 方案 | L4 | A100 | H100 |
|------|-----|------|------|
| PagedAttention | 24k | 11k | 15k |
| Chunked Prefilling | 46k | 17k | 25k |
| Pipeline Parallel | 72k | 38k | 183k |
| Tensor Parallel | 195k | 77k | 238k |
| **PrefillOnly** | **130k** | **87k** | **97k** |

注：Tensor/Pipeline Parallel 虽 MIL 更高，但需要多 GPU 并行推理，存在通信开销，整体吞吐低于 PrefillOnly（尤其无 NVLink 时）。

## 六、批判性分析

**1. 实验完全基于模拟数据，缺乏真实生产 trace 验证**

论文明确承认无法获取真实 trace，整个评估基于作者自行构造的合成数据集。关键参数（用户画像长度、请求到达分布）来自对 X（推特）和信用记录的估算，而非真实 LinkedIn 或银行数据。这使得实验结论的外推性存疑：若真实 workload 的 input 长度分布、prefix 共享率与假设偏差较大，性能提升数字可能截然不同。

**2. Suffix KV cache 丢弃破坏了后续 prefix caching**

当前实现只保留 prefix token 的 KV cache，suffix 部分直接丢弃。这意味着如果未来请求的 prefix 比当前被缓存的 prefix 更长（但仍是当前请求 context 的子集），将无法命中 cache。论文将 offloading（而非 discard）留给 future work，但正是在 suffix offloading 未实现的情况下，某些具有 long, non-shared tail 的 workload 会显著退化。

**3. 未批量处理请求的决策缺乏充分论证**

论文在 §6.1 说 prefill-only workload 是 computation-bound，因此 batching 不提升吞吐。但这一论断仅在请求长度中等时成立——对于短请求密集 workload，batching 可以掩盖 kernel launch 开销，提升 GPU 利用率。论文没有提供实验数据支持"sequential > batching"在所有目标场景中的结论。

**4. 吞吐提升的归因混淆了两类不同 workload**

Post recommendation 和 credit verification 是两类截然不同的 workload（前者受 prefix caching 驱动，后者受 MIL 限制），但论文将二者的提升笼统归结为"1.4–4.0×"，混淆了不同机制的贡献。更严格的做法是分别报告调度优化和 hybrid prefilling 对每类 workload 的独立贡献。

**5. 低 QPS 时性能不如并行化方案**

论文图 6 明确展示，在低 QPS 下 PrefillOnly 延迟高于 tensor/pipeline parallel baseline——因为 PrefillOnly 单 GPU 顺序执行，而并行方案可以利用多 GPU 并行降低单请求延迟。论文对此一笔带过，但对于延迟敏感的 prefill-only 场景（如实时推荐），这是不可忽视的限制。

## 七、AI Infra / MLSys 视角

**对 AI Infra 研究的核心启发**

PrefillOnly 揭示了一个重要但长期被忽视的问题：**LLM 推理引擎的设计假设正在被工业应用打破**。vLLM 等系统的每一个设计决策（全层 KV cache 保留、FCFS 调度、连续 batching）都以生成式 workload 为前提。当这个假设不成立时，整个优化体系需要重新设计。

**可迁移的技术 insight**

1. **中间张量是隐形内存杀手**：MLP 中间张量是单层 KV cache 的 14 倍，这一 profiling 结论在分析任何 LLM 内存问题时都值得优先检查。Hybrid prefilling 的分层差异化处理思路（attention 层不 chunk，线性层 chunk）对 memory-constrained 场景普遍适用。

2. **JCT 可预测性是调度的杠杆**：传统 LLM 调度因输出长度不可知而退化为 FCFS。PrefillOnly 展示了一旦 JCT 可知，shortest-job-first 类调度能带来多大收益——这对 disaggregated inference 架构中 prefill 节点的调度设计有直接参考价值。

3. **Continuous re-estimation 比 one-shot estimation 更优**：prefix cache 状态持续变化，动态重估 JCT 可以显著提升 cache 命中率。这一思路可扩展到 KV cache 复用率预测、动态路由决策等场景。

**值得跟进的 future work 方向**

- **Suffix KV cache offloading**：将被丢弃的 suffix KV cache offload 至 CPU/NVMe，而非直接丢弃，结合 LMCache/Mooncake 可构建更大的 KV cache 层次存储，在多轮判别式 workload 中复用 suffix。
- **Global-level shortest prefill first routing**：论文指出推理引擎只有局部可见性，在多实例部署中，router 层做全局 shortest prefill first routing 可进一步提升整体 cache 命中率和 JCT。
- **混合 generative + prefill-only workload 协同调度**：在 disaggregated inference 中，prefill 节点同时接收来自 generative app 的 prefill 请求和 prefill-only 请求，如何在两类 workload 之间分配资源是一个开放问题。
- **面向 prefill-only workload 的 KV cache 压缩与量化**：prefill-only workload 不需要 KV cache 支持多步解码，对精度要求可能更低，激进压缩（KVQuant 等）的代价/收益比会与生成式场景不同。

---

## 八、总结

PrefillOnly 识别并系统化了一类新兴的 LLM 推理 workload——prefill-only workload（推荐、信贷审核、数据标注等判别式任务），并为其设计了专用推理引擎。核心贡献是 hybrid prefilling（分层差异化 chunking，降低线性层中间张量内存占用，使 MIL 提升 5-8×）和基于连续 JCT 重估的 shortest prefill first 调度（提升 prefix cache 命中率）。系统在 vLLM 基础上实现，在 4 类硬件和 2 类 workload 上实现 1.4-4.0× QPS 提升。主要局限在于实验依赖模拟数据、suffix KV cache offloading 尚未实现，以及低 QPS 时延迟不如并行化方案。
