# PrefillOnly: An Inference Engine for Prefill-only Workloads in Large Language Model Applications

## 论文基本信息
- **标题**: PrefillOnly: An Inference Engine for Prefill-only Workloads in Large Language Model Applications
- **作者**: Kuntai Du, Bowen Wang, Chen Zhang, Yiming Cheng, Qing Lan, Hejian Sang, Yihua Cheng, Jiayi Yao, Xiaoxuan Liu, Yifan Qiao, Ion Stoica, and Junchen Jiang
- **会议**: SOSP 2025
- **Session**: LLM Inference
- **PDF**: 3731569.3764834.pdf

## 研究背景

LLM推理包含两个计算性质截然不同的阶段：prefill阶段（处理输入prompt，计算量与序列长度成正比）和decode阶段（逐token自回归生成，计算量小但依赖链长）。主流推理引擎（vLLM、Hugging Face TGI、TensorRT-LLM）将两个阶段统一对待，设计了大量针对decode阶段的优化（如PagedAttention、continous batching、speculative decoding）。

然而，通过对生产LLM应用的广泛分析，作者发现大量真实应用场景**只需要prefill阶段**，根本不需要decode阶段：

1. **Embedding模型**（如BGE、Cohere Embedding）：将文本编码为向量，仅需forward pass提取[EOS]token或pooled输出
2. **文档 grounding/reranking**：判断文档与查询的相关性，输入-query+document拼接，输出单个logit
3. **文本分类/情感分析**：输入文本通过LLM后直接取某特定token位置的logit
4. **RAG中的检索相关度打分**：判断检索到的段落与query的相关程度

这些prefill-only应用覆盖了生产环境中相当比例的LLM调用（论文称超过30%），但现有推理引擎的decode优化对这些场景完全无效，甚至引入了不必要的复杂度。

## 要解决的问题

本文要解决的核心问题是：现有LLM推理引擎专为decode-heavy场景设计，对prefill-only工作负载进行了大量不必要的抽象和优化，导致prefill-only场景下存在显著的性能和效率损失。具体包括：

1. **KV cache的必要性存疑**：prefill-only场景下，KV cache在单次forward pass后即被丢弃，为其分配的GPU显存完全是浪费
2. **continuous batching的overhead**：prefill-only请求通常是一次性完成，不存在decode阶段的dynamic arrival，batching优化反增调度开销
3. **自回归生成逻辑的冗余**：整个sampler/autoregressive generation模块在prefill-only场景下是纯overhead
4. **attention kernel的decoding优化无效**：FlashAttention等优化的kernel设计考虑了decode阶段逐token计算的特点，对纯prefill的长序列计算并非最优

## 核心贡献

- **PrefillOnly推理引擎**：首个专门针对prefill-only LLM工作负载设计的推理引擎，从系统架构层面重新审视推理优化
- **消除KV cache开销**：通过创新的"streaming prefill"策略，完全避免为prefill-only请求分配KV cache显存，将KV cache显存留给可复用的decode请求
- **单kernel prefill设计**：将多个LLM layer融合为单个GPU kernel，减少kernel launch overhead和中间结果的HBM访问
- **面向prefill的attention优化**：针对长序列prefill的访问模式优化attention kernel（不同于FlashAttention的decode优化方向）
- **生产工作负载的深入分析**：对真实生产环境的LLM应用进行了工作负载分析，揭示了prefill-only场景的普遍性和重要性

## 主要研究方法

1. **生产工作负载分析（Workload Characterization）**：对真实LLM应用进行trace分析，识别出超过30%的请求是prefill-only的，通过profiling确定这些请求的计算瓶颈
2. **瓶颈分析（Bottleneck Analysis）**：识别出KV cache显存占用（可高达40%的GPU显存）、kernel launch overhead和attention kernel对decode的过度优化是主要瓶颈
3. **设计空间探索**：对融合策略、调度策略、memory layout等进行了系统的设计空间探索实验
4. **与现有系统对比**：与vLLM、Hugging Face Transformers、TensorRT-LLM等基线进行公平的性能对比

## 设计与实现

**PrefillOnly核心架构**：

### 1. KV-Cache-Free Forward Pass
- 传统的KV cache设计为在attention层保存中间结果供后续layer使用，但在单次prefill-only请求中，KV cache在forward pass完成后即被丢弃
- PrefillOnly改用"streaming prefill"：每个layer计算完成后将K/V值直接传递给下一layer，不写入独立显存buffer
- 通过寄存器或shared memory传递中间结果（类比CPU的stream processing），将KV cache显存开销降为零

### 2. Fused Single-Kernel Execution
- 将Transformer的多个layer（FFN + attention + residuals）融合为单个CUDA/HIP kernel
- 减少kernel launch overhead：在传统实现中，一个L-layer Transformer需要L次kernel launch，而fused kernel仅需约L/4次（融合一组layer为一个大kernel）
- **层间融合（Inter-layer fusion）**：attention QKV projection + softmax + out projection + FFN融合，减少HBM读写

### 3. Attention Kernel Re-optimization
- 针对长序列prefill优化attention：prefill的attention score矩阵为(seq_len, seq_len)，与decode的(1, seq_len)访问模式完全不同
- 实现了专门针对prefill的flash attention变体，利用GPU shared memory增加tilesize，减少global memory访问

### 4. 轻量级请求调度
- 完全去除continuous batching逻辑，采用简化的static batching
- prefill-only请求之间无需等待彼此（无decode依赖），可以直接并行执行
- 调度器仅负责GPU资源分配，不维护复杂的KV cache索引结构

## 主要实验结果

论文报告了以下关键实验结果：

- **KV cache显存节省**：完全消除KV cache后，在8B模型上将用于decode的KV cache显存空间从~18GB增加到~22GB可用（以A100 80GB为基准），decode吞吐提升22%
- **Prefill延迟降低**：在embedding任务上，PrefillOnly相比vLLM降低prefill延迟2.3x；相比Hugging Face Transformers降低4.7x
- **吞吐提升**：在文档ranking任务（batch of 100 doc-query pairs）上，PrefillOnly相比TensorRT-LLM提升2.1x吞吐量
- **Kernel融合效果**：fused single-kernel设计相比分离kernel减少55%的HBM带宽消耗
- **跨模型泛化**：在LLama-3.1 8B、Mistral 7B、Qwen2.5 7B等多个模型上均取得显著改进

## 潜在问题 / 局限性

1. **KV cache消除的适用边界模糊**：论文声称KV cache在纯prefill中是"无用"的，但忽视了prefill-only请求可能与其他decode请求共享上下文（IC-Cache等系统）的场景。完全去掉KV cache后，prefill-only请求无法参与共享上下文的复用。

2. **与投机解码的不兼容性**：投机解码需要维护一个短的KV cache来进行验证。PrefillOnly去掉KV cache的策略使其无法与speculative decoding结合，这在混合负载场景下可能是个问题。

3. **长序列prefill的显存问题**：对于极长序列（如128K token），即使没有KV cache，中间激活值（intermediate activations）的显存占用仍然很高，streaming策略能否完全解决显存问题存疑。

4. **fused kernel的维护成本**：手写fused kernel需要对每种模型架构定制开发，难以跟随快速迭代的开源模型（如每月都有新模型发布），通用性存疑。

5. **缺少与LightLLM、TextGenerator Inference等专门prefill优化系统的对比**。

6. **实验规模**：仅测试到8B模型，对于更大型号的prefill-only场景（如embedding-only的13B/70B模型）缺乏验证。

## 个人评注

PrefillOnly的核心洞察（"很多LLM应用只需要prefill"）是SOSP 2025 LLM Inference session中最具洞察力的观点之一。作者没有在decode优化上与vLLM/TGI竞争，而是另辟蹊径地开辟了一个被忽视但实际占比很高的场景。这种"正交优化"思维在系统研究中极为难得。

从工程角度，PrefillOnly与IC-Cache形成了有趣的互补——IC-Cache优化了"prefill请求间的共享"，PrefillOnly则优化了"prefill请求自身"的开销。二者结合（PrefillOnly执行 + IC-Cache复用）理论上能带来更大的效率提升，值得期待后续研究。
