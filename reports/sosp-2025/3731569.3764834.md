## 一、背景

LLM 在传统生成式任务（如 ChatGPT、GitHub Copilot、Cursor）之外，越来越多地被用于判别式任务（discriminative tasks），如推荐系统、信用评估、数据标注等。这些场景中，LLM 仅需为每个请求生成一个 output token 的概率分布（如 P(Yes) vs P(No)），即可表达决策偏好。

这类工作负载的兴起源于两个驱动力：（1）LLM 可大幅简化开发流程——无需多轮数据预处理、特征工程和模型调优的跨团队协作，开发者只需修改 prompt 即可迭代；（2）LLM 在适当的 prompt engineering 下能达到甚至超过传统生产模型的决策质量。此外，LLM 用于 embedding 生成（如 Qwen3-Embedding）和 prefill-decode 分离架构中的 prefill 节点也属于此类工作负载。

---

## 二、要解决的问题

现有 LLM 推理引擎（如 vLLM、SGLang）假设输出长度任意，导致在 prefill-only 场景下存在两个核心问题：

1. **GPU 显存浪费导致最大输入长度（MIL）受限**：引擎为所有层存储完整 KV cache，但 prefill-only 请求生成完一个 token 后不需要 decode，这些 KV cache 不会被复用。当输入很长时（如用户画像包含数月浏览历史，可达数万 token），引擎不得不诉诸 chunked prefilling（降低 14% 吞吐且 MIL 提升 <2×）、tensor parallelism（引入昂贵的 all-reduce 通信）或 pipeline parallelism（引入 pipeline bubble），这些方案都牺牲吞吐量。

2. **调度算法不感知 JCT（Job Completion Time）**：传统引擎使用 FIFO 调度，因为生成式请求的输出长度不可预测。但 prefill-only 请求的输出长度固定为 1，JCT 可以被精确估计，这一特性未被利用。即使使用简单的 shortest job first，在 prefix caching 场景下，由于 cache 状态动态变化，到达时估计的 prefill time 会过时，导致 cache 命中率低。

## 三、洞察与设计

**关键洞察**：Prefill-only 请求只生成一个 output token，因此（1）推理过程中生成的 KV cache 不会被后续 decode 复用，可以在计算完成后立即丢弃或卸载，从而大幅降低活跃 GPU 显存占用；（2）输出长度固定为 1，使得每个请求的 JCT 可被精确预测，从而启用经典的 JCT 感知调度策略。

基于这两个洞察，PrefillOnly 引入三项核心技术：

### 1. Hybrid Prefilling（混合预填充）

朴素地丢弃 KV cache 仅能将 MIL 提升约 1.6×，因为 LLM 推理中的 MLP 模块产生的中间张量远大于单层 KV cache（Llama-3.1-8B 中 MLP 中间张量为 28672 floats/token，是单层 KV cache 2048 floats/token 的 14 倍）。

Hybrid prefilling 的方案是：**非 attention 层（线性层）按 chunk 处理，而 attention 层保持完整不分块**。三重好处：
- 与 chunked prefilling 不同，hybrid prefilling 在单次 forward pass 中完成，使得 KV cache 可以在计算后立即丢弃/卸载
- 不分块的 attention 层保持了 attention kernel 的最佳性能
- 按 chunk 处理线性层大幅降低了中间张量的峰值显存（降低 57%）

### 2. Suffix KV Cache Discarding（后缀 KV cache 丢弃）

在保留 prefix token 的 KV cache（用于 prefix caching）的同时，丢弃 suffix token 的 KV cache。这样既能处理更长的请求，又不损失 prefix caching 的加速效果。

### 3. Shortest Prefill First + Continuous Prefill Time Estimation

每次调度决策时，重新估算所有等待请求的 prefill time（而非仅在到达时估算一次）。使用 cache-miss token 数（n_input - n_cached）作为 prefill time 的代理指标（与实际 prefill time 的 Pearson 相关性达 0.987）。通过公式 score = T_prefill(n_input, n_cached) - λ·T_queue 实现公平性，防止长请求饥饿。

## 四、实现细节

- **基于 vLLM 实现**，新增约 4,600 行 Python 代码
- **Hybrid prefilling 通过 torch.compile 实现**：将连续的线性操作分组为一个大的虚拟层，按 chunk 前向传播，并拼接输出。两项优化：
  - Output preallocation：预分配完整输出张量，直接写入各 chunk 输出，避免拼接时的双倍内存开销
  - In-place computation：当输入输出形状一致时，复用输入张量的内存
- **Suffix KV cache discarding 复用 vLLM 中 sliding window attention 的抽象实现**，不引入新的硬件 kernel
- **Profile run**：启动前以最大输入长度运行一次合成请求，测量 GPU 峰值显存，剩余显存分配给 prefix KV cache
- **不批量处理请求**：prefill-only 负载是计算受限而非显存受限，batching 不提升吞吐，因此逐请求串行处理
- **User-ID 路由**：多 GPU 场景下每 GPU 启动一个引擎实例，按 user-id 轮询路由以最大化 prefix cache 命中

两个模拟数据集：帖子推荐（短上下文，重 prefix sharing）和信用评估（长上下文 40K-60K tokens）。

### 主要结果

| 指标 | 结果 |
|------|------|
| QPS 提升 | 在不增加平均和 P99 延迟的前提下，处理最高 **4× 的 QPS** |

## 六、批判性分析

1. **数据集完全模拟，缺乏真实生产验证**：作者承认使用模拟数据集，但声称"workload characteristics 尽可能真实"。然而，模拟数据的请求到达模式（Poisson）、长度分布（正态）和 prefix sharing 模式可能与真实生产环境差异显著。特别是帖子推荐场景中 50 个固定候选帖子的假设过于简化。

2. **不 batching 的设计决策值得商榷**：论文以"prefill-only 是计算受限"为由不做 batching，但这一结论基于当前硬件和模型。当输入长度较短或 GPU 算力足够时（如大批量短请求），batching 仍可能通过提升 GPU 利用率来提升吞吐。作者在 Discussion 中也提到 batching 共享 prefix 的请求可能有益，但未实验验证。

3. **MIL 对比不完全公平**：PrefillOnly 使用单 GPU（suffix cache 丢弃），而 tensor parallel 和 pipeline parallel 使用 2 GPU。MIL 的比较中 PrefillOnly 在 H100 上（97K）远低于 tensor parallel（238K），说明在极长上下文场景下 PrefillOnly 的方案有明显天花板。

4. **Prefix cache 命中率的改进依赖特定的工作负载模式**：连续估计调度在 prefix sharing 模式固定且 cache 空间受限时效果显著，但在 prefix sharing 较弱或 cache 空间充裕的场景下，其优势可能不明显。

5. **仅丢弃不卸载 suffix KV cache**：当前实现直接丢弃 suffix KV cache，后续相同后缀的请求无法复用。虽然 Discussion 中提到可以卸载到 CPU/远端存储，但这是一个重要的性能缺口。

6. **低 QPS 下延迟劣势被轻描淡写**：Figure 6 清楚显示 PrefillOnly 在低 QPS 下的延迟高于 tensor parallel 基线，但论文仅一笔带过。对于延迟敏感的在线服务，这一劣势不可忽视。

## 七、AI Infra / MLSys 视角

1. **Prefill-only 是一个真实且不断增长的工作负载类型**：随着 LLM 在推荐、信用评估等判别式任务中的部署规模扩大，以及 prefill-decode 分离架构的普及，专门优化 prefill-only 推理的需求确实存在。这一观察对 AI Infra 研究者有重要的工作负载定义价值。

2. **Hybrid prefilling 的思路可推广**：将 attention 层和非 attention 层区别对待的策略，不仅适用于 prefill-only 场景。在 speculative decoding、long-context inference 等场景中，类似的"分层差异化处理"思路可能降低显存峰值。

3. **JCT 可预测性是一个被低估的优化维度**：在 prefill-decode 分离架构中，prefill 节点的 JCT 可预测性可以被进一步利用——不仅是节点内调度，还包括跨节点的全局路由和负载均衡。

4. **值得跟进的方向**：
   - **Suffix KV cache offloading + 异步预取**：将丢弃改为卸载到 CPU/远端，结合调度器的请求预测实现预取
   - **共享 prefix 的 batched prefill**：对共享长 prefix 的请求组做 batched prefill（FlashInfer 已有初步支持），可在推荐场景中进一步提升吞吐
   - **与 KV cache 压缩技术的结合**：hybrid prefilling 与 KVQuant、KIVI 等量化技术正交，结合使用可能实现更大的 MIL 提升
   - **Shortest prefill first routing at global level**：将调度从单引擎扩展到全局路由层，结合 prefix cache 状态做全局最优调度

---

## 八、总结

PrefillOnly 是首个专为 prefill-only 工作负载设计的 LLM 推理引擎，通过 hybrid prefilling（非 attention 层分块、attention 层不分块）大幅降低 GPU 显存占用（MIL 提升最高 7.9×），并通过 continuous prefill time estimation 实现 prefix-cache-aware 的 shortest prefill first 调度。在 4 种硬件、3 种模型、2 种工作负载上的评估表明，PrefillOnly 可在不增加延迟的前提下处理最高 4× 的 QPS。该工作的核心贡献在于识别并系统化利用了 prefill-only 工作负载的两个独特属性（KV cache 可丢弃、JCT 可预测），但其评估仅基于模拟数据集，且在极长上下文和低 QPS 场景下仍有局限。
