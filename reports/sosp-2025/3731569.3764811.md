# Proto: A Guided Journey through Modern OS Construction

**作者**：Wonkyo Choe, Rongxiang Wang, Afsara Benazir, Felix Xiaozhu Lin（University of Virginia）
**会议**：SOSP '25: ACM SIGOPS 31st Symposium on Operating Systems Principles，2025 年 10 月
**DOI**：https://doi.org/10.1145/3731569.3764811
**源文件**：[3731569.3764811.pdf](../../papers/sosp-2025/3731569.3764811.pdf)

---

## 一、背景

操作系统课程长期以来是计算机科学本科教育的核心。然而，作者观察到学生对系统软件的兴趣日益下滑——AI 的崛起、系统工作"过于复杂"的刻板印象，以及现代系统软件带来的挫败感，共同导致顶尖北美大学中已有 20/30 所不再将 OS 作为本科必修课。

现有教学 OS（xv6、Pintos、EGOS-2000 等）以"headless"形式为主：无 GUI、只支持终端程序，缺乏吸引力。这些系统将重心放在 OS 概念的传授上，忽略了系统软件与现实世界应用之间激励性的联系——而正是这种联系催生了 UNIX（Space Travel 游戏）、World Wide Web（分享研究信息）等历史性系统项目。

---

## 二、要解决的问题

1. **缺乏吸引力**：现有教学 OS 的课程项目仅限于 shell、文件系统等终端程序，学生难以产生成就感和展示欲。
2. **可演示性差**：大多数教学 OS 仅在模拟器上运行，无法在真实硬件上运行和携带展示。
3. **复杂度管理困难**：构建完整 OS 所需的技术深度，与学生在一个学期（约 150 小时）内能够投入的精力之间存在难以调和的矛盾。
4. **学习路径不清晰**："大爆炸"式的整体构建缺乏清晰的基线和阶段性成果，学生容易迷失。

---

## 三、核心设计

Proto 围绕四条设计原则展开：

- **P1 吸引人的应用**：目标 app 包括旋转 3D 甜甜圈动画、Mario Bros 游戏模拟器、DOOM、音乐播放器、视频播放器、区块链挖矿程序等，均能产生直观的视觉/听觉反馈。
- **P2 可演示性**：面向 Raspberry Pi 3（ARMv8，35 美元）真实硬件，配合 GameHAT 手持扩展板（640p 屏幕、电池、扬声器），支持课堂现场演示。
- **P3 增量原型化**：将完整 OS 拆解为 5 个自包含的递进快照（Prototype 1–5），每个快照引入最小集合的 OS 机制，由目标 app 的需求驱动。
- **P4 最小可行实现**：每个新 OS 特性（syscall、线程、多核调度等）必须直接服务于目标 app，不做超出需求的抽象。

**五个原型的递进关系**：

| 原型 | 别名 | 目标 App | 新增 OS 能力 |
|------|------|---------|------------|
| Prototype 1 | Bare Metal IO | donut（单任务动画） | 帧缓冲、定时器、UART 调试 |
| Prototype 2 | Multitasking | N 个 donut（并发） | 调度器、上下文切换、虚拟定时器 |
| Prototype 3 | User vs. Kernel | Mario NES 模拟器 | 虚拟内存（MMU）、用户/内核分离、syscall |
| Prototype 4 | I/O | MusicPlayer、Mario（带输入）、slider | 文件系统 syscall、DMA 音频、USB 键盘、IPC |
| Prototype 5 | Desktop | VideoPlayer、DOOM、blockchain、launcher | 线程（clone）、信号量、多核、FAT32、窗口管理器 |

**OS 整体架构**：单内核（monolithic），内核运行在 ARMv8 EL1，用户 app 在 EL0。支持进程（独立地址空间）和线程（共享 mm），实现 28 个 syscall（任务管理、文件系统、线程/同步三类）。用户地址空间从 0x0 开始，内核地址前缀为 0xffff。只有用户栈采用按需分页。

## 四、实现细节

**调试支持**：鉴于真实硬件与 QEMU 行为差异（CPU 缓存一致性、未初始化内存、IO 映射地址、并行非确定性），Proto 构建了一套自托管调试机制：
- ARMv8 调试异常（DBGBCR/DBGWCR）实现断点和 watchpoint（~200 LOC）
- 栈回溯器（~600 LOC）
- 受 Linux ftrace 启发的事件追踪环形缓冲区
- GPIO 触发的 FIQ "panic button"，可在内核死锁时仍能 dump 所有核的调用栈

**FAT32 文件系统**：Prototype 5 将 ChaN 的 FatFS（~6K SLoC）移植为主文件系统，替代 xv6fs（xv6 文件系统受限于 270KB 单文件上限，单块 IO 性能低，且与宿主机文件系统不互通）。通过伪 inode 为每个打开的 FAT 文件/目录维护内存对象，并在 VFS 层按路径分派到 xv6fs 或 FatFS。

**窗口管理器**：~800 SLoC，作为内核线程运行（刻意选择，避免实现跨进程共享内存 IPC 的复杂性）。App 通过写 `/dev/surface` 设备文件渲染，WM 定期合成到硬件帧缓冲；追踪 dirty 窗口区域以减少重绘；支持 z-order、半透明浮窗。

**USB 移植**：移植了 Circle/USPi（~10K SLoC 的裸机 USB 栈），仅需少量内核 API（虚拟定时器）即可运行。代价是软件复杂度显著增加，学生不需要完全理解 USB 栈内部。

**性能优化**：内核用 ARMv8 汇编实现 memory move（帧缓冲瓶颈）；用户库用 SIMD 实现 YUV→RGB 转换（视频帧率从 <10 FPS 提升到 ~30 FPS，提升近 3x）；绕过 buffer cache 直接访问 SD 卡驱动进行 FAT32 范围读写（延迟降低 2–3x）。

**代码规模**：
- 内核核心（Prototype 1→5）：约 1K→8K SLoC，含 FAT32/USB 驱动后总计约 33K SLoC
- 用户空间：从几百 SLoC（donut）到 45K SLoC（DOOM）
- 学生每个 lab 约需编写 100–300 SLoC，修改 10–28 个源文件

## 五、实验结果

**测试平台**：Raspberry Pi 3B+（Cortex-A53 四核 1GHz，1GB DRAM）、QEMU on WSL2/VMware。对照系统：xv6-armv8（musl libc）、Ubuntu 22.04（glibc + SDL2）、FreeBSD 14.2。

**内核微基准（Pi3）**：

| 指标 | 数值 |
|------|------|
| getpid() 系统调用延迟 | 3.4 ± 0.04 µs |
| IPC 单向延迟（pipe，1 字节） | 21.0 µs |
| FAT32 读/写吞吐 | 数百 KB/s（受 SD 轮询驱动限制） |
| 启动至内核加载 | 2753 ms |
| 启动至 shell 提示符 | 3186 ms |

**App 吞吐量（FPS，Pi3）**：

| 应用 | Proto | Linux | FreeBSD |
|------|-------|-------|---------|
| DOOM | 61.8 | 31.9 | 51.2 |
| video 480p | 26.7 | 19.0 | 24.4 |
| video 720p | 11.6 | 10.1 | 14.6 |
| mario-sdl | 72.2 | 87.3 | 56.4 |

**多核扩展性**：8 个 mario 实例并发，随核数增加 FPS 近线性增长，4 核时 CPU 利用率持续 >95%。

**内存占用**：单应用运行时 21–42 MB，约为 Pi3 1GB DRAM 的 2–4%。

**功耗与续航（GameHAT）**：空闲时 ~3W，负载时 ~4W；单 18650 电池估算续航 2.6–3.7 小时。

**教学用户研究（N=48，Spring 2025）**：64% 学生选择在真实硬件上实验；四条设计原则（P1–P4）的学习贡献评分均在 4/5 左右；学生开放反馈高度认可应用驱动的激励机制和增量原型结构。

## 六、批判性分析

**1. App 吞吐量对比存在明显的比较不公平问题**
论文声称 Proto 的 DOOM 在 Pi3 上达到 62 FPS，而 Linux 仅 32 FPS，FreeBSD 51 FPS。论文的解释是 Linux/FreeBSD 运行了带有 X server 的完整桌面栈，而 Proto 是裸直接渲染。这一比较前提极不对等——Proto 有专门的、轻量的直接渲染路径，Linux/FreeBSD 承载了完整图形栈的开销。"比生产 OS 快 2x"的结论对读者有一定误导性，并非 OS 自身内核效率更高。

**2. 窗口管理器作为内核线程的设计决策被轻描淡写**
论文选择将 WM 跑在内核线程中，理由是"避免实现跨进程共享内存 IPC"。这一设计牺牲了隔离性（WM bug 可导致内核 panic），且对学生而言掩盖了真实桌面系统（如 Android）中 WM 隔离设计的重要 tradeoff，可能误导学生对现代 OS 架构的理解。

**3. FAT32 绕过 buffer cache 的设计存在一致性风险**
为了弥补 buffer cache 只支持单块操作的性能瓶颈，Proto 直接绕过缓存层与 SD 驱动交互。论文对这一补丁的代价（潜在数据一致性问题、架构内聚性破坏）几乎没有分析。

**4. 教学对照实验缺失**
论文评估了 Proto 的系统性能，但用户研究没有设置对照组（如使用 xv6 或 Pintos 的传统课程），因此无法量化 Proto 的教学增益。N=48 且均来自同一课程，无法支持泛化结论。学生反馈中"实验很难/很痛苦"的问题（真实硬件调试、从基础到实现的陡峭跳跃）与论文对 P2（可演示性）的积极论述存在一定矛盾。

**5. 信号（Signals）未实现导致 GDB 兼容性缺失**
论文虽然承认了这一局限，但低估了其对教学的影响：GDB 是系统软件调试的标准工具，学生在无 GDB 支持的环境中调试内核级 bug 的难度大幅提升，与 P4（最小可行实现服务于 app）的原则存在内在张力。

**6. 仅支持单一硬件平台的脆弱性**
Pi3 停产计划在 2029 年前，论文计划在 2030 年切换到 Pi4。然而历史表明，硬件切换往往会带来显著的重构成本（驱动、cache 行为、外设生态）。论文对这一风险缺乏量化估算。

---

## 七、总结

Proto 是一个面向本科 OS 教学的新型教学操作系统，核心贡献是将 OS 构建与媒体丰富的目标应用（游戏、音视频播放、区块链）深度绑定，通过五个递进自包含的原型引导学生系统地构建现代 OS 特性。系统运行在廉价的 Raspberry Pi 3 真实硬件上，内核核心约 10K SLoC，支持 DOOM（~62 FPS）、480p 视频（~27 FPS）等实用应用，在 Pi3 上与 Linux/FreeBSD 性能相当（但比较条件不完全对等）。主要局限在于仅支持单一硬件平台、信号机制缺失影响调试工具链、窗口管理器内核线程化牺牲隔离性，以及教学效果评估缺少对照实验支撑。Proto 对于希望提升 OS 课程吸引力的教育者是一个值得参考的实践，代码已开源：https://github.com/fxlin/uva-os-main。
