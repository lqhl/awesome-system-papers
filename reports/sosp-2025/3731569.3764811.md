# Proto: A Guided Journey through Modern OS Construction

## 一、背景

操作系统课程是计算机科学教育的核心课程之一，旨在传授抽象、虚拟化、特权分离、并发等核心概念。然而，近年来学生对 OS 及系统软件的兴趣持续下降——AI 领域的主导地位、系统开发被认为过于复杂、以及现代系统软件带来的挫败感都是原因。一个标志性信号是：北美前 30 所顶级大学中有 20 所不再将 OS 作为本科 CS 专业的必修课。

现有的教学 OS（如 xv6、Pintos、EGOS-2000 等）大多是"无头"系统，只支持 shell 和简单终端程序，缺乏引人入胜的应用场景和在真实硬件上的可演示性。这使得学生难以体验"构建一个自己能用的系统"的乐趣——而这恰恰是 UNIX、WWW、TeX 等经典系统项目的初心。

---

## 二、要解决的问题

1. **应用吸引力不足**：现有教学 OS 的目标应用仅限于简单的终端程序，无法激发学生的学习热情和成就感。
2. **可演示性差**：大多数教学 OS 只能在模拟器上运行，少数能运行在真实硬件上的也局限于基本功能，无法作为便携式 demo 展示。
3. **复杂度管理困难**：要支持富应用（游戏、音视频播放）需要大量 OS 机制，但学生在一学期内（约 150 小时）的时间预算有限。
4. **产品级 OS 不适合教学**：直接使用 Linux/Android 教学存在端到端构建体验缺失、代码过于复杂、不适合精简等问题。

---

## 三、洞察与设计

**关键洞察**：如果将"能运行什么样的应用"作为 OS 构建的驱动力，而非"教授什么概念"，就能让每一个 OS 机制的引入都有明确的、学生可感知的目的——当某个 app 跑起来时，学生能直观看到自己实现的 OS 功能的价值。应用本身成为学习动机和进度反馈。

基于这一洞察，Proto 遵循四个设计原则：
- **P1 引人入胜的应用**：目标应用包括 3D 动画（donut）、NES 游戏（Mario）、音乐播放器、视频播放器、DOOM 等，而非简单终端程序。
- **P2 可演示性**：运行在 Raspberry Pi 3（$35 的真实 ARM 硬件）上，可配合 GameHAT 扩展板做便携 demo。
- **P3 增量原型化**：将完整 OS 分解为 5 个自包含的增量快照（Prototype 1-5），每个原型都是可运行的完整系统。
- **P4 最小可行实现**：每引入一个 OS 特性必须直接服务于某个目标 app。

**五个原型的渐进路线**：

| 原型 | 主题 | 目标应用 | 新增 OS 能力 |
|------|------|----------|-------------|
| P1 Baremetal IO | 裸机 IO | 旋转的 donut | framebuffer、UART、timer |
| P2 Multitasking | 多任务 | 多个并发 donut | 调度器、上下文切换 |
| P3 User vs. Kernel | 用户态/内核态 | Mario（无输入） | 虚拟内存、地址空间隔离、syscall |
| P4 Files | 文件抽象 | Mario（有输入）、slider、MusicPlayer | 文件系统、USB 键盘、设备文件、DMA 音频 |
| P5 Desktop | 桌面系统 | DOOM、VideoPlayer、blockchain | FAT32、SD 卡、多核、窗口管理器、线程 |

## 四、实现细节

**硬件平台**：Raspberry Pi 3B（ARMv8 Cortex-A53 四核 1GHz，1GB RAM）。选择单一平台以避免跨平台抽象层的复杂性。

**内核架构**：单体内核，类似 xv6。内核运行在 ARMv8 EL1，用户态在 EL0。支持独立地址空间（用户空间从 0x0 开始，内核空间 0xffff 前缀）。内核用 1MB 块映射物理内存和 IO，用户 app 用 4KB 页，仅用户栈使用 demand paging。共 28 个 syscall。

**关键实现决策**：
- UART 始终同步写（避免异步写带来的锁和环形缓冲区的循环依赖）
- P3 先不引入文件系统，用特殊的无文件 `exec()` 加载 ELF
- USB 键盘使用 USPi 裸机 USB 栈（~10K SLoC），代价是代码复杂但换来可扩展性
- 窗口管理器作为内核线程运行（~800 SLoC），避免共享内存 IPC 的复杂性
- 性能优化：ARM assembly memcpy、NEON SIMD 做 YUV→RGB 转换（视频 FPS 提升 3x）、FAT32 绕过 buffer cache 直接访问 SD 卡（延迟降低 2-3x）

**调试支持**：
- ARM 硬件断点/watchpoint（DBGBCR/DBGWCR）
- 栈回溯器（支持内核和用户态）
- 类 ftrace 的 ring buffer 事件追踪
- GPIO 触发的 FIQ panic 按钮（即使内核死锁也能 dump）

**代码规模**：内核核心 ~8K SLoC（P5），加上 FAT32 和 USB 驱动后约 33K SLoC，与 xv6（10K）、Xinu（8K）等教学 OS 相当。

## 五、实验结果

**微基准测试**（Pi3 平台）：

| 指标 | 数值 |
|------|------|
| syscall 延迟（getpid） | 3.4 ± 0.04 μs |
| IPC 延迟（pipe 单字节） | 21.0 ± 0.00 μs |
| 内核加载时间 | 2753 ± 3 ms |
| 启动到 shell | 3186 ± 7 ms |

与 xv6-armv8 相比：内核开销相当，计算和文件基准更优。与 Linux/FreeBSD 相比：大多数指标在 0.5x-2x 范围内。

**应用基准测试**（FPS，Pi3 平台）：

| 应用 | Proto | Linux | FreeBSD |
|------|-------|-------|---------|
| DOOM | 61.8 | 31.9 | 51.2 |
| Video 480p | 26.7 | 19.0 | 24.4 |
| Video 720p | 11.6 | 10.1 | 14.6 |
| mario-sdl | 72.2 | 87.3 | 56.4 |

Proto 在 DOOM 和视频播放上与生产级 OS 性能可比（0.8x-1.9x）。多核扩展性好，4 核下 8 个 mario 实例和 blockchain miner 均呈线性增长。

**功耗**：idle 约 3W（电池续航 ~3.7h），负载时 ~4W（续航 ~2.6h），适合演示使用。

**教学评估**（N=48，5 分制）：学生对四个设计原则的评分大多在 3-5 分之间。64% 学生选择在真实硬件上实验。学生反馈赞赏"应用驱动的动机"、"增量复杂度"和"自选路线"的任务结构，但也指出真实硬件开发的不便和早期 lab 的学习曲线陡峭。

## 六、批判性分析

1. **单一硬件平台的风险被低估**：论文承认了硬件过时风险并提到"计划 2030 年迁移到 Pi 4"，但 Pi 3 已经是 2016 年的硬件，1GHz 四核 + 1GB RAM 在 2025 年极为落后。更重要的是，ARMv8 的 cache coherency 模型、中断控制器等与现代 ARM 平台（如 Pi 4/5 的 GICv2/v3）有显著差异，迁移工作量可能被低估。

2. **与生产级 OS 的性能对比不公平**：论文声称 Proto 在 DOOM 上达到 61.8 FPS 而 Linux 只有 31.9 FPS，但 Linux 跑在 X server 上而 Proto 用直接渲染。论文虽有说明但仍将数字并列比较，容易误导读者。

3. **教学效果评估的局限性**：仅有一学期（Spring 2025）、一个学校、48 个学生的数据，且是课程结束时的自评问卷（存在 survivorship bias——中途放弃的学生不在样本中）。没有与其他教学 OS（如 xv6 课程）的对照组比较。

4. **复杂度转移而非消除**：USB 栈 10K SLoC、newlib 库代码量巨大（P5 用户态 ~770K SLoC），这些被标记为"不要求学生完全理解"。本质上是将复杂度从"学生需要实现的代码"转移到了"学生需要当黑盒使用的代码"。这种 trade-off 是否真的优于 xv6 的"全部代码可读"哲学，值得商榷。

5. **可复现性问题**：评估依赖视频提交而非自动化测试，这虽然适合演示型项目，但在学术严谨性上不如可自动化验证的评估方式。论文也承认"自动测试自定义 OS 很困难"，但这本身就是一个未解决的问题。

6. **排除的功能影响深远**：不支持网络栈、crash consistency、pthread、signals，这些恰恰是现代 OS 最重要的部分。论文将其定位为"教学 OS"来合理化这些省略，但如果目标是让学生体验"构建真实可用系统的乐趣"，缺少网络支持是一个显著的矛盾。

---

## 七、总结

Proto 是一个面向教学的 ARMv8 操作系统，运行在 Raspberry Pi 3 上，通过"应用驱动"的设计理念将 OS 构建分解为 5 个增量原型，从裸机 IO 到支持 DOOM、视频播放和多核桌面环境。其核心贡献在于将教学 OS 的目标从"教授概念"转向"构建有吸引力的应用"，内核核心保持轻量（~8K SLoC）的同时支持丰富的多媒体应用。初步教学评估显示学生对这种设计反馈积极。主要局限包括单一硬件平台依赖、缺少网络/信号等关键 OS 特性、以及仅有单学期单校的教学数据。
