# eBPF Misbehavior Detection: Fuzzing with a Specification-Based Oracle

**作者**：Tao Lyu, Kumar Kartikeya Dwivedi, Thomas Bourgeat, Mathias Payer, Meng Xu (University of Waterloo), Sanidhya Kashyap — EPFL
**会议**：SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
**链接**：https://doi.org/10.1145/3731569.3764797
**源文件**：[3731569.3764797.pdf](../../papers/sosp-2025/3731569.3764797.pdf)

## 一、背景

eBPF 是 Linux 内核中广泛使用的扩展框架，允许开发者在内核空间安全执行自定义程序。Meta 的每台服务器上运行超过 50 个 eBPF 程序，其在系统追踪、安全策略实施、网络处理等场景中被大规模部署。eBPF 依赖静态验证器（verifier）在程序加载时检查其安全性——包括内存越界、资源泄露、信息泄露等——通过抽象解释和路径枚举的组合算法来实现。

然而，eBPF verifier 本身存在 bug：可能错误拒绝安全程序（可用性问题），也可能错误接受不安全程序（安全性问题）。这些 bug 的根因可归结为四类：RC1（抽象解释不精确）、RC2（安全规则不一致）、RC3（实现错误）、RC4（优化错误）。已有的 fuzzing 工作主要依赖间接的 bug oracle（如 KASAN 内存错误检测、运行时状态不一致），只能发现 RC3/RC4 的部分子集，完全无法检测 RC1/RC2 导致的安全程序被误拒问题。

---

## 二、要解决的问题

1. **Oracle 覆盖不全**：现有 fuzzer 的 bug oracle 只能间接检测运行时错误（如内存越界），无法发现信息泄露、类型混淆等语义错误，更无法检测被错误拒绝的安全程序（因为被拒绝的程序根本不会被执行）。
2. **安全规范缺失**：eBPF 的安全属性缺乏正式规范，散落在邮件列表、代码注释和自测试中，不同开发者对安全规则的理解不一致，导致实现中出现矛盾的安全检查。
3. **抽象解释固有不精确**：verifier 对程序状态做过度近似（over-approximation），即使实现完全正确，也会误拒合法程序。
4. **优化引入复杂性**：路径剪枝等优化显著增加验证算法的复杂度，成为 bug 的高发区。

---

## 三、洞察与设计

**关键洞察**：eBPF 程序的安全性可以被精确地规约为每条指令的前置/后置条件约束，通过 SMT solver 自动推理而非抽象解释来判定，从而构建一个无近似损失的 oracle，与 verifier 的结果交叉比对来发现所有类型的 bug。

基于此洞察，作者设计了 Veritas fuzzing 框架，核心是 SpecCheck 规范化 oracle：

1. **语义规范**：用 Dafny 编码 eBPF 指令集的操作语义，包括动态类型系统（Uninit / Scalar / PtrType / PtrOrNullType），以及算术、数据搬移、内存、控制流四类指令的类型传播规则。
2. **安全属性规范**：从 CIA 模型自顶向下推导出五项安全属性——SP1（控制流安全/终止性）、SP2（内存安全）、SP3（资源安全）、SP4（VM 完整性/r10 只读）、SP5（数据机密性/防指针泄露）。
3. **浅嵌入（Shallow Embedding）**：将具体 eBPF 程序逐指令映射为 Dafny 方法调用，安全属性编码为前置条件，指令语义编码为函数体。Dafny 验证器通过 SMT solver 判定约束是否可满足。
4. **交叉比对**：eBPF verifier 和 SpecCheck 分别独立验证同一程序，结果不一致则标记为 bug——包括 verifier 接受但 SpecCheck 拒绝、verifier 拒绝但 SpecCheck 接受、以及两者都拒绝但原因不同的情况。

## 四、实现细节

- **规范编码**：2000 行 Dafny 代码，覆盖 eBPF ISA RFC 中全部 171 个 op-code（已废弃指令除外），以及 455 个 kernel helper 函数中最常用的 50 个（约 11%）。每条指令平均 3.6 个前置条件、3.7 个后置条件。
- **嵌入过程**：600 行 C++ 实现，对 eBPF 程序的 CFG 做深度优先遍历，将每条指令映射到 Dafny 方法。条件跳转映射为 if 分支，伪函数调用内联展开，循环用有界展开处理。
- **程序生成器**：2100 行 C++，生成随机 CFG 和语法合法的指令序列，程序大小控制在 5-30 条指令。
- **状态采样**：patch Linux 内核在 verifier 验证过程中每隔 N 条指令采样一次 VM 状态（寄存器、栈槽、锁状态），通过 debugfs 导出到用户态。当 verifier 拒绝程序时，取最接近出错指令的采样状态作为 SpecCheck 的初始状态，避免从头验证整个程序。
- **并行架构**：基于 Syzkaller 框架，checker 与 fuzzing 循环异步运行，支持多测试用例并行验证。使用 Dafny CLI V4.6.0 和 Z3 V4.12.1。
- **工程投入**：约 9 个工程师周。

## 五、实验结果

**实验平台**：Ubuntu 22.04.4 LTS，224 核 Intel Xeon Platinum 8276L，754 GB 内存。

### Bug 发现

间歇运行 3 个月，发现 15 个新 bug（其中 13 个由 SpecCheck oracle 发现）：

| 类别 | 数量 | 说明 |
|------|------|------|
| 不安全程序被接受 | 3 | 包括权限提升和 KASLR 绕过 |
| 安全程序被拒绝 | 9 | 包括困扰 sched-ext 开发者数小时的 bug |
| 原子指令滥用 | 1 | 允许在私有内存上使用原子操作 |
| KASAN/UBSAN 检测 | 2 | verifier 自身的内存 bug |

12 个 bug 被确认，8 个已修复。bug #1 和 #2 可被仅拥有 CAP_BPF 的用户利用实现 root 提权和内核指针泄露。

### 与现有工作比较

- 收集了 14 个已有 fuzzer（SEV/BVF/Buzzer/BRF）报告的历史 bug，SpecCheck 全部检测到。
- 将 Veritas 发现的 bug PoC 直接提供给 Buzzer 和 BRF，两者均未能检测到任何一个。

### 性能

| 指标 | 数值 |
|------|------|
| Fuzzing 吞吐 | 23-25 tests/s（224 核） |
| 单测试平均耗时 | ~10 秒（99% 时间在 Dafny 验证） |
| 95.8% 测试 | 5-20 秒内完成 |
| 超时率 | 0.2% |
| 误报率 | 0（三个月内零误报） |
| 分支覆盖 | 32%（3432 个分支，超过 BRF 的 29%） |
| 状态采样节省 | 平均每测试 53 秒，累计 754 CPU-core 小时 |

## 六、批判性分析

1. **Kernel helper 覆盖率极低**：仅覆盖 455 个 kernel helper 函数中的 50 个（11%），而 kernel helper 是 eBPF 与内核交互的核心接口，也是 bug 的重要来源。作者将此定位为"工程量大"，但这实质上限制了 SpecCheck 的实际检测范围——论文没有分析这 11% 的覆盖对 bug 发现率的影响。

2. **吞吐量差距被轻描淡写**：Veritas 的 23-25 tests/s 对比 Buzzer 的 700 tests/s 相差 ~30 倍。论文用"bug-per-test rate 更高"来回应，但这一指标受 oracle 能力和 bug 存量共同影响，不能直接证明低吞吐是合理的权衡。随着容易发现的 bug 被修复，低吞吐可能成为发现新 bug 的瓶颈。

3. **规范正确性的循环论证风险**：论文声称"零误报"来证明规范的正确性，但如果规范本身遗漏了某些安全属性，SpecCheck 会漏报而非误报——漏报是无法通过"零误报"来排除的。availability 属性的形式化被推迟到 future work，这意味着当前规范在理论上是不完整的。

4. **与 verifier 共同演化的维护成本被低估**：Linux eBPF verifier 约 20K LoC 且快速演进。论文提到"用 LLM 草拟 kernel function 规范"作为未来方案，但这只是设想，当前的 9 工程师周已经只覆盖了一小部分。如果规范跟不上 verifier 的更新，SpecCheck 会快速失效。

5. **测试生成器的贡献被低估**：论文强调 oracle 是核心贡献，但 bug 发现依赖生成器和 oracle 的共同作用。论文没有分析哪些 bug 需要特定的程序结构才能触发，也没有评估生成器的多样性是否足够。

6. **"三个月间歇运行"缺乏标准化**：没有报告总 CPU 时间、总测试用例数、以及 bug 发现的时间分布，难以复现或与其他工具公平比较。

---

## 七、总结

本文提出 Veritas/SpecCheck，通过将 eBPF 指令语义和安全属性编码为 Dafny 规范，利用 SMT solver 构建精确的 specification-based oracle，与 eBPF verifier 交叉比对来全面检测四类根因（抽象不精确、规则不一致、实现错误、优化错误）导致的 bug。系统发现了 15 个新 bug，包括可导致权限提升和 KASLR 绕过的严重安全漏洞。核心局限在于 kernel helper 覆盖率低（11%）、规范维护成本高、以及吞吐量相对较低，适用于作为现有 fuzzer 的补充 oracle 而非替代方案。
