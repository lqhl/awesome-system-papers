# eBPF Misbehavior Detection: Fuzzing with a Specification-Based Oracle

## 论文基本信息
- **标题**: eBPF Misbehavior Detection: Fuzzing with a Specification-Based Oracle
- **作者**: Tao Lyu, Kumar Kartikeya Dwivedi, Thomas Bourgeat, Mathias Payer (EPFL), Meng Xu (Waterloo), Sanidhya Kashyap (EPFL)
- **会议**: SOSP 2025
- **Session**: Bugs
- **PDF**: 3731569.3764797.pdf

## 研究背景

eBPF（extended Berkeley Packet Filter）是 Linux 内核的关键扩展框架，允许开发者安全地在内核空间运行自定义程序。其安全性由 eBPF verifier 保证：verifier 对每个 eBPF 程序进行静态分析，确保其满足一系列安全条件（如内存访问边界、无无限循环、不侵犯内核完整性）。随着 Meta 等公司每台服务器运行超过 50 个 eBPF 程序的规模，verifier 的正确性变得前所未有的重要。

然而，verifier 本身是 20K 行 C 代码的复杂程序，结合了抽象解释和路径枚举的启发式算法。在其上快速迭代新特性（每年新增大量指令和内核函数支持）不可避免地引入了 bug。这些 bug 产生两类问题：拒绝安全的 eBPF 程序（可用性问题，开发者需要大量时间调试）和接受不安全的 eBPF 程序（安全问题，可能导致权限提升或信息泄露）。

现有 fuzzing 方法（Syzkiller、Buzzer 等）依赖运行时行为检测 bug（如内存错误），只能发现接受不安全程序的情况。此外，rejected programs 甚至无法运行，所以依赖运行时状态的 oracle 完全无法检测"错误拒绝"问题。

## 要解决的问题

1. 如何检测 eBPF verifier 的所有四类根因 bug（RC1: 不精确的抽象解释；RC2: 不一致的安全规则；RC3: 新特性引入的遗漏检查；RC4: 路径剪枝错误）？
2. 如何构建一个精确的、可扩展的 specification-based oracle？
3. 如何将 specification oracle 与 fuzzing 框架有效结合？

## 核心贡献

- **SpecCheck: 首个基于规范的 eBPF verifier oracle**：系统性地规范了 eBPF 指令语义（包括动态类型系统）和五个安全属性（控制流安全、内存安全、资源安全、VM 不变性、VM 数据安全），使用 Dafny 编码为 per-instruction pre/post-conditions
- **Veritas: 集成 SpecCheck 的 fuzzing 框架**：基于 Syzkaller 构建，利用三个关键洞察（小测试用例优先、SMT solver 辅助验证状态采样、并行验证）实现高效的 bug 检测
- **发现 15 个新 bug**：覆盖所有四类根因，其中 12 个已被确认，8 个已修复；包括可导致权限提升和信息泄露的严重安全 bug
- **全面覆盖**：同时检测错误接受（安全问题）和错误拒绝（可用性问题），这是现有工具无法做到的

## 主要研究方法

### eBPF 语义和安全规范（SpecCheck）

**动态类型系统**：SpecCheck 为 eBPF VM 引入了完整的动态类型系统，包括：
- Uninit（未初始化）、Scalar（标量值）、PtrType（指针，带 memory region 和 offset）、PtrOrNullType（可空指针）
- Per-instruction 类型规则：每个指令如何更新类型状态（load、store、arithmetic、atomic 等各类指令）

**五类安全属性**：
- SP1: 控制流安全（程序必须在有限指令数内终止）
- SP2: 内存安全（VM 内存访问必须在边界内，指针解引用前必须非空）
- SP3: 资源安全（不能无限占用 CPU 或内存）
- SP4: VM 不变性（寄存器 R10 只读）
- SP5: VM 数据安全（禁止读取未初始化数据，禁止通过 map 或 helper 将指针泄露到用户空间）

**Dafny 编码**：每个 eBPF 指令被编码为一个纯函数，包含 pre-conditions（安全属性约束）和 post-conditions（指令语义和类型更新）。使用 Dafny 的原因是其内置的 SMT solver 集成和可追踪的错误报告能力。

### Veritas Fuzzing 框架

**小测试用例优先**：分析发现大多数 bug 可被极小的 eBPF 程序触发（通常少于 20 条指令，少于 10 条执行路径），大程序反而降低了发现效率。这与直觉相反但合乎逻辑：简单程序中的 bug 更容易被 isolation。

**状态采样**：eBPF verifier 在验证过程中会在多个路径分支点采样状态。Veritas 使用 verifier 的状态采样作为 SpecCheck 的初始状态，大幅减少 SMT solver 需要分析的路径深度（平均节省 53 秒/测试用例）。

**并行验证**：将 oracle 检查与 fuzzing 循环异步执行，提高吞吐量。即使 0.2% 的测试超时，也不影响整体的 bug 发现能力。

### Bug 根因分类

论文识别了四类 verifier bug 的根本原因：
- **RC1**: 抽象解释不精确（over-approximate），如不传播数值范围到非对齐内存区域
- **RC2**: 安全规则不一致，如不同指令转换指针到标量的约束不同
- **RC3**: 新特性引入时的遗漏检查，如新指令或内核函数的参数类型检查缺失
- **RC4**: 路径剪枝优化错误，如 CAP_PERFMON 能力的特殊处理逻辑错误应用到无此能力的程序

## 主要实验结果

**Bug 发现**：
- 15 个新 bug，其中 12 个被确认，8 个已修复
- Bug 分布：3 个错误接受（安全问题），9 个错误拒绝（可用性问题），1 个原子操作滥用，1 个内存 bug，1 个未定义行为
- 覆盖所有四类根因

**与现有工具比较**：
- 使用论文提供的 13 个 bug 的精确 PoC，BRF 和 Buzzer 均无法检测其中任何一个
- 即使提供了 PoC，现有 fuzzer 也因为无法触发 PoC 中的精确条件而失败

**性能数据**：
- SpecCheck 规范约 2K 行 Dafny 代码（9 engineer-weeks）
- 每个测试用例平均验证时间 10 秒，95.8% 在 5-20 秒内完成
- 状态采样平均节省 53 秒/测试用例
- 运行 3 个月，发现 15 个 bug

## 潜在问题 / 局限性

1. **规范覆盖的不完整性**：SpecCheck 目前仅覆盖 eBPF ISA 中的 171 个操作码（不包含已废弃的 classic BPF 指令），但 kernel helpers（455 个函数）仅覆盖了约 11%（50 个最常用的）。eBPF 生态系统的快速发展意味着新的指令和 kernel helpers 不断引入，规范需要同步维护。这本质上是一个永无止境的工作。

2. **Dafny 作为规范语言的门槛**：虽然论文认为 Dafny 比完全形式化验证的工具门槛低，但对于普通内核开发者来说，Dafny 仍然是一个陌生的语言。规范的生命力取决于社区能否理解和维护它。

3. **循环处理**：SpecCheck 对含循环的 eBPF 程序使用有界展开（bounded unrolling）。虽然实测表明大多数 bug 可被小程序触发，但对于依赖复杂循环不变量的程序，规范可能无法验证其正确性。

4. **与 SEV/BVF 的理论比较**：论文声称 SEV 和 BVF 无法检测错误拒绝的 bug，但这个结论是通过理论分析而非实际运行得出的。在没有实际运行数据的情况下，这个比较的可信度打折扣。

5. **误报率数据不充分**：论文声称"3 个月运行中无 false alarms"，但没有详细说明如何定义和验证这一点。对于一个依赖 SMT solver 的系统，这个声明需要更多证据支持。

6. **SpecCheck 自身的正确性**：规范本身的正确性如何保证？论文依赖历史 bug 的重发现来验证，但这是一个循环论证——规范是否能检测我们已知的 bug，但不能保证它能检测我们未知的 bug。

7. **只验证 safety properties，不验证 liveness**：SpecCheck 专注于 safety properties，但 liveness（如 progress guarantees）在某些场景下同样重要。

## 个人评注

Veritas + SpecCheck 代表了 kernel 测试领域的一个重大进步：它不仅检测"不正确接受"（安全漏洞），还检测"不正确拒绝"（可用性问题）——后者在实际开发中造成的痛苦可能不亚于前者，但现有工具完全忽略了它。这揭示了一个更广泛的原则：specification-based oracle 是打破"rejected programs have no runtime state"这一困境的唯一途径。

三个关键洞察中，"小测试用例优先"最反直觉。通常认为更复杂的程序能覆盖更多代码、触发更多 bug，但 Veritas 的经验表明 eBPF verifier bugs 恰恰相反——大多数 bug 隐藏在简单程序中。这可能是因为复杂的程序往往被 verifier 以更保守的方式处理，而简单程序中的边界情况更容易被暴露。

15 个 bug、12 个确认、8 个修复——数字本身不算惊人（相比 KNighter 的 92 个或 Fawkes 的 48 个），但考虑到这是在已经经过大量测试的代码库上取得的成果，这已经说明 specification-based oracle 的价值所在：它能发现那些只有在你明确知道"什么应该是正确的"之后才能发现的问题。
