# eBPF Misbehavior Detection: Fuzzing with a Specification-Based Oracle

## 一、背景

eBPF（extended Berkeley Packet Filter）是 Linux 内核提供的一个安全扩展框架，允许开发者在内核中运行受限的自定义程序，广泛用于系统追踪、安全强制、网络处理等场景。Meta 等公司的服务器上每台运行超过 50 个 eBPF 程序，其工业化部署规模相当庞大。

eBPF 安全性的核心保障是 Linux eBPF verifier——一个静态检查器，在程序执行前验证其是否满足内核期望的安全条件（如内存越界访问、资源泄漏、特权信息泄露等）。Verifier 采用抽象解释（abstract interpretation）结合执行路径枚举的方式，对所有可能的执行状态进行保守近似检查。一旦通过验证，程序运行时不再重复安全检查。

---

## 二、要解决的问题

eBPF verifier 本身存在 bug，分为四类根因（RC）：

- **RC1：状态抽象导致的不精确性**——抽象解释的保守近似会拒绝实际上安全的程序（误拒）。例如，verifier 不会将寄存器的数值范围传播到非 8 字节对齐的栈内存，导致合法的数组索引被拒绝。
- **RC2：安全规则不一致**——不同开发者对安全属性的理解存在差异，导致相似指令的验证行为不一致（如原子 AND 与普通 AND 对指针的处理规则相矛盾）。
- **RC3：实现错误**——安全规则实现不完整或有误，既可能导致误拒，也可能导致误接受不安全程序（漏判）。
- **RC4：优化错误**——路径剪枝等优化引入了复杂性，可能引发权限提升或信息泄露漏洞。

**现有 fuzzing 工具的局限**：已有工具（BRF、Buzzer、SEV、BVF）的 bug oracle 仅依赖运行时信号——如 KASAN 内存错误检测器或 verifier 近似状态与运行时状态的标量范围差异——只能间接提示 bug 存在，无法覆盖 RC1、RC2 类误拒问题，也无法检测不产生内存错误的语义类漏洞（RC3/RC4 的部分情况）。

## 三、核心设计

论文提出 **Veritas** fuzzing 框架，其核心是 **SpecCheck**——一个基于规约（specification-based）的 bug oracle。

### SpecCheck 的设计目标

1. **精确性（Precision）**：精确刻画安全 eBPF 程序的集合，避免假阳性。
2. **可追溯性（Trackability）**：当程序不安全时，能够定位到具体违反了哪条约束。
3. **可扩展性（Extensibility）**：新增指令或内核函数只需扩展相应的前置/后置条件。
4. **可推理性（Reasonability）**：规约以纯函数形式编码，便于形式化证明更高层次属性。

### 规约编码

- **eBPF 语义规约**：为每条 eBPF 指令定义操作语义，包含动态类型系统（`Uninit`、`Scalar`、`PtrType`、`PtrOrNullType`），刻画每条指令如何更新寄存器和内存类型。
- **安全属性规约**：基于 CIA 安全模型（机密性、完整性、可用性）系统推导出五条安全属性：
  - SP1：控制流安全（无死循环、无递归）
  - SP2：内存安全（边界内访问）
  - SP3：资源安全（程序必须终止）
  - SP4：VM 完整性（不得写只读寄存器 R10）
  - SP5：数据安全（非特权程序不得泄露指针或未初始化数据）
- **编码语言**：采用 **Dafny** 编写规约，将安全属性编码为前置条件，将指令语义编码为函数体，通过 SMT solver（Z3）自动验证。

### Veritas 工作流

1. 语法生成器生成合法 eBPF 程序作为测试用例。
2. Linux eBPF verifier 对测试用例进行验证（接受/拒绝）。
3. SpecCheck 通过**浅层嵌入（shallow embedding）**将 eBPF 程序逐指令映射为 Dafny 函数调用，并使用 Dafny verifier（Z3）验证其是否满足规约。
4. 两者结果不一致时，标记为 verifier bug。

## 四、实现细节

- **SpecCheck**：用 Dafny 编写，约 2000 行代码（~9 工程周工作量）；嵌入过程用 C++ 实现，约 600 行。
- **覆盖范围**：支持 eBPF ISA RFC 定义的全部 171 个 opcode（排除已废弃的 `BPF_IND`）；内核辅助函数覆盖 455 个中最常用的 50 个（约 11%）。
- **eBPF 程序生成器**：C++ 实现，约 2100 行，生成随机控制流图并按 ISA 语法规则填充指令。
- **状态采样**：对 Linux kernel 打补丁，每隔 N 条指令采样一次 verifier 状态，通过 debugfs 共享至用户态，供 SpecCheck 用作初始状态，大幅降低 SMT 求解代价。
- **并行化**：SpecCheck 异步独立于 fuzzing 主循环运行，多个测试用例并行验证。
- **集成**：基于 Syzkaller fuzzing 框架，复用其 executor 等组件。
- **求解器**：Dafny CLI v4.6.0 + Z3 v4.12.1，超时阈值 900 秒。

## 五、实验结果

**实验平台**：Ubuntu 22.04，224 核 Intel Xeon Platinum 8276L，754 GB RAM。

### Bug 发现结果（表 1 摘要）

| 根因 | Bug # | 指令类型 | 状态 | 后果 |
|------|-------|---------|------|------|
| RC4 | 1 | mov | 已修复 | 权限提升（仅需 CAP_BPF） |
| RC3 | 2 | kfunc call | 已修复 | DoS（内核挂起） |
| RC4 | 3 | store | 已修复 | ASLR 绕过 |
| RC3 | 4 | atomic* | 已修复 | 精度传播错误 |
| RC3 | 5 | atomic_xchg | 已确认 | 栈指针验证失败 |
| RC1 | 6 | store | 已确认 | 标量范围未传播，usability 问题 |
| RC3 | 7 | be32 | 已修复 | 精度反向传播错误 |
| RC3 | 8 | store | 已修复 | 误拒 32-bit 初始化 |
| RC2 | 9 | atomic* | 已确认 | 允许对本地内存进行原子操作 |
| RC2 | 10 | arith ops | 已上报 | 指针转标量指令约束不一致 |
| RC1 | 11 | jumps | 已上报 | 粗粒度指针比较 |
| RC1 | 12 | memory ops | 已确认 | 栈数据追踪不精确 |
| RC1 | 13 | arith ops | 已上报 | 算术结果追踪不准确 |

共发现 15 个 bug（含 2 个内存/UB bug），12 个已确认，8 个已修复。

### 与现有工具对比

- SpecCheck 对收集的 14 个历史 bug PoC **全部检出**（100% 召回），而 BRF 和 Buzzer 即使直接给定 PoC 也**全部漏检**。
- SEV 的 oracle 有根本性缺陷：无法检测被误拒的安全程序（因为被拒绝的程序根本不会执行）。

### 性能

| 指标 | 数值 |
|------|------|
| 测试吞吐量 | 23–25 tests/s（使用全部 224 核） |
| 单测试用例平均耗时 | 10 秒 |
| 95.8% 测试用例耗时 | 5–20 秒 |
| 超时率 | 0.2% |
| 状态采样节省（相比默认设置） | 平均每 test 节省 53 秒，总计节省 754 CPU 核时 |
| 分支覆盖率 | 32%（3432 分支），优于 BRF 的 29% |

## 六、批判性分析

**优点**：
- 提出了 eBPF verifier 四类根因的系统性分类，逻辑清晰，有助于理解现有工具的局限。
- specification-based oracle 的思路本质上是「用规约作为 ground truth 替代运行时 oracle」，对检测语义错误有显著优势，12/13 个新 bug 是无法触发内存错误的「静默语义错误」。
- 13 个新 bug 覆盖了全部四类根因，体现了 holistic 方法的有效性。

**值得审视的地方**：

1. **覆盖率与完整性声明之间的张力**：论文声称「holistic」检测，但 kernel helper 仅覆盖 50/455 个函数（~11%）。涉及未覆盖 helper 的 bug 会被静默跳过，完整性存在明显缺口，但作者并未量化因此漏检了多少 bug。

2. **吞吐量与 bug rate 的权衡过于乐观**：Veritas 的 23–25 tests/s 远低于 Buzzer 的 700 tests/s（约慢 30 倍），作者以「bug-per-test 率更高」为由将此归为优势。但由于总 test 数量大幅减少，能否发现更多 bug 依赖于 PoC 程序本身小且简单的假设，这一假设在面向未知 bug 时未必成立。

3. **状态采样引入的精度损失未充分讨论**：采样会导致 5% 的测试用例（2574 个）检查时间反而更长，作者解释为「识别出了另一条 culprit 指令中更复杂的约束」——这暗示状态采样可能引入错误的初始状态，进而影响 oracle 的精确性，但论文对此未展开分析。

4. **Dafny 规约本身可能有错**：SpecCheck 的 specification 是手写的，共约 2000 行，涉及对 eBPF ISA 的解读。论文仅通过「通过全部 self-tests」和「三个月无假阳性」来间接验证规约的正确性，并未提供对规约自身的形式化证明。规约中的错误会导致 false negative 或 false positive。

5. **RC1（误拒）的漏洞影响被低估**：论文将 RC1 主要定性为「usability issue」，但误拒安全程序会迫使开发者绕过 verifier，可能间接引入安全问题，这一传导路径未被讨论。

## 七、AI Infra / MLSys 视角

eBPF 在 AI 基础设施中的应用正在快速扩展：从 GPU 内存追踪、RDMA 网络监控，到 AI 集群中的流量整形和 BPF-based 调度器（如 sched-ext，论文中也有提及）。随着 AI 系统对低延迟内核扩展的需求增加，eBPF verifier 的正确性将直接影响 AI Infra 场景的安全性。

**对 AI Infra 研究的启发**：

- **可信内核扩展**：在 AI 集群中，eBPF 被用于实现自定义调度、网络 QoS、性能剖析等功能。Veritas 发现的 RC1 类误拒 bug 正是阻碍 sched-ext 等高性能调度器落地的实际障碍，这对面向 AI 工作负载的定制内核扩展有直接参考价值。
- **Specification-based testing 的迁移价值**：「将语义规约编码为 SMT 可验证形式，并与实现进行差异比对」的思路可以迁移到 AI 系统的其他组件——例如，AI 编译器（TVM、XLA、Triton）的 pass 正确性验证，或分布式训练 runtime 的一致性检查。
- **LLM 辅助规约生成**：作者在 Discussion 中提到将 LLM 用于草拟 kernel helper 规约，这是一个值得跟进的研究方向：如何用 LLM 生成、验证并维护 AI 系统关键组件的形式化规约？

**可操作的 future work 方向**：
- 将 SpecCheck 的规约范围扩展到 GPU eBPF（如 NVIDIA BPF 扩展），验证 AI workload 下的 verifier 正确性。
- 探索将 shallow embedding + SMT 的方法用于 ML 编译器中间表示（IR）语义的正确性测试。

---

## 八、总结

本文提出 Veritas/SpecCheck，一个将 eBPF 指令语义和五条安全属性系统编码为 Dafny 规约、并通过 SMT solver 自动验证的 fuzzing 框架。相比依赖运行时 oracle 的现有工具，SpecCheck 能够全面覆盖四类 verifier bug 根因，在三个月的间歇性 fuzzing 中发现了 15 个新 bug，包括可导致权限提升和 KASLR 绕过的严重安全漏洞。主要局限在于：kernel helper 覆盖率仅 11%、吞吐量受限（23–25 tests/s），以及规约本身的正确性依赖人工审核而非形式化证明。该工作对 eBPF 生态的安全保障以及系统软件规约测试方法论均有重要参考价值。
