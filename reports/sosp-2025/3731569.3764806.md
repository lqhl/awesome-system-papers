# HedraRAG: Co-Optimizing Generation and Retrieval for Heterogeneous RAG Workflows

## 一、背景

RAG（Retrieval-Augmented Generation）已成为将 LLM 与外部知识库集成的主流方案，能有效减少幻觉并保护数据隐私。早期 RAG 系统采用简单的两阶段工作流：先检索（Retrieval）再生成（Generation）。然而，随着 RAG 技术的发展，工作流日益复杂和多样化——出现了 multi-hop reasoning、iterative retrieval-generation（IRG）、HyDE（先生成假设再检索）、RECOMP（检索后压缩）等异构工作流模式。

现有系统（如 LangChain、FlashRAG、vLLM+Faiss 组合）将 LLM 推理和向量检索视为独立的模块化组件，缺乏运行时协调和联合优化。LLM 生成运行在 GPU 上，采用 continuous batching 和 token 级动态调度；向量检索运行在 CPU 上，依赖大批量并行搜索。两者执行模式的根本差异导致了资源利用不均和流水线停滞。

---

## 二、要解决的问题

1. **阶段级流水线失配**：异构 RAG 工作流中，生成和检索阶段的数量和持续时间差异大。LLM 生成采用 step-wise continuous batching，而向量检索偏好大批次静态处理。粗粒度的顺序执行导致 CPU-GPU 硬件利用率低下，简单的异步集成又因批次大小不匹配而效果不佳。

2. **请求内语义重复计算**：多轮 RAG 工作流中，相邻检索阶段的 query embedding 具有高度语义相似性，连续生成的部分输出也接近最终结果。现有系统将每个阶段视为独立请求，导致冗余计算和累积延迟，错失了跨阶段优化的机会。

3. **请求间检索访问倾斜**：向量索引的访问呈现严重的热点倾斜——top 20% 的 cluster 承载了超过 69% 的计算量。然而 GPU 内存有限（被 LLM 权重和 KV cache 占据），且热点 cluster 随工作负载动态变化，静态或按需缓存策略无法有效利用这一特征。

---

## 三、洞察与设计

**关键洞察**：异构 RAG 工作流虽然在高层呈现复杂多变的结构，但在三个维度上存在系统性的可利用规律：（1）生成和检索阶段可以被分解为细粒度的子阶段并行流水化；（2）同一请求内相邻阶段之间存在足够强的语义相似性，使得基于部分结果的推测执行具有高准确率；（3）跨请求的向量索引访问呈现稳定的热点倾斜模式，少量缓存即可覆盖大部分计算。

基于上述洞察，HedraRAG 提出了 **RAGraph**——一种面向 RAG 的图抽象，将多样化的 RAG 工作流统一表示为有向图。核心设计包括：

- **RAGraph 抽象**：用 Generation 节点和 Retrieval 节点表示工作流阶段，通过 `add_generation`、`add_retrieval`、`add_edge` 等 API 构建工作流图。与 LlamaIndex、LangChain 等框架兼容。关键区别在于 RAGraph 显式建模了检索和生成的执行不对称性——检索是预定义的固定操作，生成是 token 级的动态多步过程。

- **图变换操作**：定义了节点分裂（node splitting）、重排序（reordering）、边添加（edge addition）和依赖重连（dependency rewiring）四种变换操作，将原始粗粒度顺序工作流转化为可重叠的细粒度子阶段。

- **动态调度器**：在每个调度周期遍历活跃请求的 RAGraph，形成节点 wavefront，依次应用图变换，将优化后的子阶段分发到 CPU-GPU 流水线执行。

## 四、实现细节

**细粒度子阶段流水化（Fine-Grained Sub-Stage Pipelining）**：
- 将生成阶段拆分为若干 decoding step 组成的子阶段，将检索阶段拆分为若干 cluster search 组成的子阶段
- 采用动态时间预算方法（而非固定划分）：以检索请求为基准，增量添加 cluster 直到达到最大时间预算 $m_b$
- $m_b$ 通过建模延迟改善 $\Delta l$ 来自适应计算，平衡子阶段延迟改善与调度开销
- 在 RAGraph 中建模为节点分裂操作

**语义感知搜索优化（Similarity-Aware Search Optimization）**：
- 利用三个局部性观察：（1）$v'$ 的搜索结果倾向包含在 $v$ 的更大 top-k 结果中；（2）$v'$ 的结果也倾向分布在 $v$ 的命中 cluster 集合 $H_v$ 中；（3）$v'$ 的结果倾向在 $C \cap C'$ 中
- **缓存与重排序**：为每次检索缓存 top-20 结果供后续复用；对目标 cluster 集重排序：先搜 $H_v \cap C'$，再搜 $(C - H_v) \cap C'$，最后搜剩余 cluster，实现 ANNS 的提前终止，减少最多 28% 搜索时间
- **推测执行**：支持两种形式——推测生成（用部分检索结果提前开始生成）和推测检索（用部分生成输出提前开始检索）。触发条件基于系统吞吐量利用率 $T_{curr} < \tau T_{max}$
- 在 RAGraph 中建模为节点重排序和推测性边插入

**部分 GPU 索引缓存（Partial GPU Index Caching）**：
- 在 GPU 上分配剩余显存（LLM 权重和 KV cache 之外）缓存热点 cluster
- 通过离线基准测试确定 KV cache 与索引缓存的最优分配比例（公式 2）
- 混合检索引擎：命中 GPU 缓存的 cluster 在 GPU 上搜索，未命中的在 CPU 上搜索，结果合并
- 异步更新：每 50 个子阶段更新一次缓存，避免 PCIe 竞争

**系统实现**：
- 基于 vLLM 0.6.6 和 Faiss 1.9.0 构建
- 生成和检索 worker 分别运行在独立进程中，通过共享消息队列通信
- 扩展 Faiss 支持多步 cluster 分区搜索、step function 接口和异步索引加载
- 提供变长 cluster 搜索接口，支持负载均衡和高效归约

## 五、实验结果

| 维度 | 配置 | 结果 |
|------|------|------|
| **硬件** | AMD EPYC 9534 64核 CPU + NVIDIA H100 80GB GPU | - |
| **模型** | Llama3.1-8B（主要）、Llama2-13B、OPT-30B | - |
| **语料** | Wikipedia ~38M 文档，e5_large 1024维嵌入，IVF4096 索引 | - |
| **数据集** | NQ、2WikiMultiHopQA、HotpotQA | - |
| **在线服务** | vs LangChain/FlashRAG | 延迟降低 2.2×–18.2×，吞吐提升 1.5×–5× |
| **离线执行** | vs LangChain/FlashRAG | 加速 3.5×/1.3× |
| **混合工作流** | 不同工作流并发 | 延迟降低最高 5.6×，吞吐提升 3.3× |
| **大模型** | Llama2-13B、OPT-30B | 一致的 1.5×+ 吞吐提升 |
| **子阶段流水化** | 检索延迟改善 | 1.09×–1.77× |
| **推测执行** | vs RaLMSpec/RAGCache | 延迟加速 1.06×–1.62× |
| **GPU 索引** | 热点缓存 | 加速 1.12×–1.49× |

工作流复杂度越高（如 Multistep、IRG），HedraRAG 的优势越显著。当 nprobe 增大（检索开销增加）时，优化效果也更明显。

## 六、批判性分析

1. **加速范围跨度过大**：论文报告的加速从 1.03× 到 5× 以上，跨度极大。最大加速主要出现在 baseline（LangChain）本身效率很低的场景——LangChain 采用完全顺序执行。与更合理的 baseline（增强版 FlashRAG，作者自行添加了异步并行）比较时，加速通常在 1.3×–2× 范围。论文标题和摘要突出 "up to 5×" 有一定 cherry-picking 之嫌。

2. **推测执行的准确率与收益不匹配**：Figure 19 显示推测准确率在 0.4–1.0 之间波动很大，但论文未详细分析推测失败时的代价。虽然论文声称 "regeneration does not add to the original latency"，但推测失败会浪费 GPU 计算资源，在高负载下可能挤占正常请求的处理能力，这一点未被充分讨论。

3. **实验设置的局限性**：主要实验使用 8B 模型 + 38M 文档语料，检索和生成负载相对均衡。论文自己也承认，"extremely large models paired with small databases tend to shift the performance bottleneck toward LLM inference, making retrieval coordination less impactful"。对于当前主流的 70B+ 模型部署场景，生成瓶颈远大于检索，HedraRAG 的核心优化（检索-生成协调）的价值可能大幅缩水。

4. **缺乏端到端质量评估**：推测执行和语义近似策略可能引入微妙的质量差异。论文仅在一处提到 "nprobe 从 128 增加到 512 提升 5% 准确率"，但未系统评估各优化技术对最终回答质量的影响。对于 RAG 系统，延迟-质量的 tradeoff 至关重要。

5. **动态时间预算的鲁棒性存疑**：公式 (1) 假设检索请求均匀到达各子阶段，这在异构工作流的混合负载下未必成立。论文未讨论该假设被违反时的性能退化情况。

6. **GPU 缓存大小的确定依赖离线 profiling**：公式 (2) 通过离线基准测试确定 KV cache 与索引缓存的分配。当工作负载模式发生显著变化（如从 One-shot 为主切换到 IRG 为主）时，需要重新 profiling，系统的自适应能力有限。

## 七、AI Infra / MLSys 视角

1. **RAG 服务系统的范式转变**：HedraRAG 指出了一个重要趋势——RAG 工作流正从简单的两阶段流水线演变为复杂的异构 DAG。这要求 AI Infra 从"LLM 推理引擎 + 向量数据库"的松耦合架构，走向紧密协调的联合优化系统。RAGraph 的图抽象提供了一种通用的建模方式。

2. **CPU-GPU 异构流水化的普适价值**：论文提出的细粒度子阶段划分和动态时间预算方法，不仅适用于 RAG，也可迁移到其他 CPU-GPU 混合工作负载场景，如带有外部工具调用的 Agent 系统、检索增强的代码生成系统等。

3. **推测执行的启发**：HedraRAG 将推测执行从 LLM decoding（如 speculative decoding）扩展到 RAG 系统的检索-生成交互。核心思路——利用部分结果提前启动下游计算、失败时回滚——可以推广到更多 multi-stage AI pipeline 场景。

4. **值得跟进的方向**：
   - **与 disaggregated inference 的结合**：在 prefill-decode 分离架构下（如 Mooncake、DistServe），如何将 RAG 检索阶段与 prefill/decode 阶段协调？
   - **Agentic RAG 的系统优化**：当 RAG 工作流由 Agent 动态生成（而非预定义）时，RAGraph 的静态图抽象需要扩展为支持运行时图构造和变换
   - **更大规模向量库的 GPU 缓存策略**：当语料库从 38M 增长到数十亿文档时，热点倾斜模式是否依然成立？多级缓存（GPU HBM → CPU DRAM → SSD）的联合管理策略值得研究

---

## 八、总结

HedraRAG 通过 RAGraph 图抽象统一表示异构 RAG 工作流，并利用细粒度子阶段流水化、语义感知推测执行和部分 GPU 索引缓存三项技术，在 CPU-GPU 混合系统上实现了 1.5×–5× 的吞吐提升。系统在多轮、多阶段的复杂 RAG 工作流（如 Multistep、IRG）上优势最为显著，但在生成为主要瓶颈的大模型场景和需要端到端质量保障的生产环境中，其实际收益需要进一步验证。
