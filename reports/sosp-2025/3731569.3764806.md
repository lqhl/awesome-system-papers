# HedraRAG: Co-Optimizing Generation and Retrieval for Heterogeneous RAG Workflows

## 论文基本信息

- **标题**: HedraRAG: Co-Optimizing Generation and Retrieval for Heterogeneous RAG Workflows
- **作者**: Zhengding Hu (UCSD), Vibha Murthy (Rice), Zaifeng Pan (Rice), et al.
- **会议**: SOSP 2025
- **Session**: ML and FPGA
- **PDF**: 3731569.3764806.pdf

## 研究背景

检索增强生成（RAG）系统在实际应用中展现出高度的异构性（Heterogeneity）——不同的工作流在检索和生成之间的耦合程度差异巨大。简单的"检索-拼接到 prompt-生成"流水线只是一种特例。更复杂的 RAG 工作流包括：

- **多跳推理**（Multi-hop Reasoning）：如 CORTON 风格的迭代检索，每次生成都需要基于前一轮的检索结果进行条件判断
- **并行检索分支**（Parallel Retrieval Branches）：如 REPLUG 风格，多个检索查询并行执行，结果汇聚后统一生成
- **条件检索**（Conditional Retrieval）：根据生成中间结果决定是否需要触发额外的检索
- **混合检索-生成**（Hybrid Retrieval-Generation）：检索结果直接作为部分生成输入，而非拼接

现有的 RAG 系统（如 LlamaIndex、LangChain、RAGatouille）将这些不同类型的工作流统一用"检索 + 拼接到 prompt"的模式处理。这种统一抽象导致两个核心问题：（1）系统无法感知工作流的异构性，因此无法针对性地优化执行路径；（2）检索和生成被视为两个独立阶段，缺乏端到端的协同优化机会。

## 要解决的问题

如何在异构 RAG 工作流中实现检索（Retrieval）和生成（Generation）的协同优化，兼顾端到端吞吐量和生成质量？

具体来说，HedraRAG 需要解决：
1. 如何准确建模不同 RAG 工作流中的异构依赖关系？
2. 如何在不知道完整答案的情况下，自适应地决定何时需要检索、何时可以跳过？
3. 如何在保证生成质量的前提下，最大化检索-生成流水线的并行度？

## 核心贡献

1. **Heterogeneous Workflow Graph（HWG）**：一种统一的图表示，将不同类型的 RAG 工作流建模为节点（LLM 调用或检索操作）和边（数据依赖或条件依赖）的异构图，能够同时表达紧耦合（retrieval-then-generate）和松耦合（independent retrieval）的工作流。

2. **Co-optimization of Retrieval and Generation**：不是分别优化检索和生成，而是在 HWG 上联合进行执行调度优化，使得两者可以并行启动、相互预热、相互引导。

3. **Adaptive Retrieval Strategy**：通过轻量级预测器（predictor）判断当前 generation context 是否"足够"回答查询，从而自适应地决定是否触发检索。这避免了不必要的检索开销。

4. **Generation Skipping Mechanism**：当生成中间结果已经包含足够信息时，跳过后续的检索-再生成步骤，直接输出结果。

5. **端到端 4.5x 加速**：在多跳问答和复杂推理任务上，HedraRAG 实现了最高 4.5x 的端到端加速，同时质量损失 < 1%。

## 主要研究方法

**Heterogeneous Workflow Graph（HWG）**

HedraRAG 将 RAG 工作流建模为有向无环图（DAG），其中有两种节点：
- **L 节点**（LLM node）：代表 LLM 生成调用
- **R 节点**（Retrieval node）：代表检索操作

边分为两类：
- **数据依赖边**（Data edge）：实线，从检索结果流向 LLM 输入
- **条件依赖边**（Condition edge）：虚线，表示"如果 LLM 输出满足条件 X，则执行此检索"

```
[HWG Example - Multi-hop Retrieval]

Q → [L1: Generate sub-question] → (condition) → [R1: Retrieve] → [L2: Generate answer]
                                         ↓ (condition false)
                                    [L_direct: Direct answer]
```

**Adaptive Retrieval Predictor**

HedraRAG 训练了一个轻量级的二分类 predictor，输入为当前 generation context（包括对话历史和已有的检索结果），输出为"是否需要更多检索"的概率。当概率低于阈值时，跳过当前检索步骤。

Predictor 的训练使用对比学习：在已有标注数据上，将"需要检索才能回答正确"的 query 和"无需检索即可回答正确"的 query 作为正负样本对进行训练。

**Generation Skipping**

当 LLM 的生成已经包含了完整答案的信号（如明确地回答了问题、输出了结束标记），HedraRAG 可以跳过后续的计划检索步骤，直接进入最终答案生成。这需要 LLM 的置信度估计——HedraRAG 使用 logits 采样来获取 token-level 的置信度分数。

**Joint Scheduling on HWG**

基于 HWG，HedraRAG 的调度器执行以下优化：
1. **并行化**：将没有数据依赖的 L 和 R 节点并行调度（如并行执行多个独立检索）
2. **预热（Prefetching）**：当 L 节点的输出还在计算时，预测其输出中可能涉及的关键实体，并提前发起检索请求
3. **条件剪枝**：当条件依赖边的条件不满足时，剪枝该分支下的所有后续节点

## 设计与实现

HedraRAG 的系统架构包含以下核心组件：

```
[User Query]
      ↓
+------------------------------------------+
|          HWG Builder                     |  (analyzes workflow, builds graph)
+------------------------------------------+
      ↓
+------------------------------------------+
|    HedraRAG Scheduler                    |
|  - Parallel scheduling                   |
|  - Conditional branch pruning            |
|  - Adaptive retrieval trigger            |
|  - Generation skipping                    |
+------------------------------------------+
      ↓                    ↓
+------------+      +-------------------+
|  LLM Pool  |      |  Retrieval Pool   |
| (vLLM/...) |      |  (Vector DB APIs) |
+------------+      +-------------------+
```

**HWG Builder**：接受用户定义的 RAG 工作流描述（API 调用序列或自然语言描述），自动识别 L 和 R 节点及其依赖关系，构建 HWG。目前支持从 LlamaIndex/LangChain pipeline 自动提取工作流图。

**LLM Pool**：管理多个 LLM 实例（支持 vLLM、TGI 等后端），提供生成服务。HedraRAG 从这里获取 logits 用于置信度估计。

**Retrieval Pool**：管理多个检索后端（支持 Chroma、Pinecone、FAISS 等），提供向量检索服务。

**Scheduler**：核心执行引擎，维护一个优先队列，不断调度 HWG 上就绪的节点（所有依赖已满足的节点）到对应的 worker pool。当 L 节点完成时，Scheduler 更新 HWG 状态，触发条件判断，调度新的 R 或 L 节点。

## 主要实验结果

HedraRAG 在 4 个数据集和 5 种 RAG 工作流类型上进行了评估：

| 数据集 | 任务类型 | Baseline E2E 延迟 | HedraRAG E2E 延迟 | 加速比 | 质量损失 |
|--------|---------|------------------|------------------|-------|---------|
| HotpotQA | Multi-hop QA | 8.2s | 1.9s | 4.3x | 0.4% |
| 2WikiMultihopQA | Multi-hop QA | 12.1s | 2.7s | 4.5x | 0.8% |
| PopQA | Single-hop QA | 2.3s | 1.1s | 2.1x | 0.2% |
| ASQA | Long-form QA | 15.7s | 6.2s | 2.5x | 1.2% |

**关键数据**：
- **Adaptive Retrieval**：Predictor 的准确率为 91.3%，有效避免了 34% 的不必要检索调用
- **Generation Skipping**：在可以直接回答的 query 上，跳过机制节省了平均 2.3 次 LLM 调用
- **并行调度收益**：并行检索 + 生成相比串行执行，平均节省 38% 的总延迟

**对比 Baseline**：
- vs LlamaIndex sequential pipeline：2.5-4.8x 加速
- vs LangChain Agent：3.1-5.2x 加速
- vs Fixed-prompt RAG（无迭代检索）：1.2-1.8x 加速（质量显著更高）

## 潜在问题 / 局限性

1. **Predictor 的泛化能力未经充分验证**。Adaptive Retrieval Predictor 是 HedraRAG 的关键组件，但其训练数据来源、规模和质量在论文中描述不够详细。在新领域（与训练数据分布不同的 query 类型）上的准确率可能显著下降，进而影响检索决策的质量。

2. **Generation Skipping 的安全性问题**。跳过检索步骤虽然能提升性能，但如果预测错误（置信度高但实际答案错误），可能导致严重的质量下降。论文声称使用 token-level 置信度，但未提供置信度阈值的选择方法，也未讨论误触发（false positive skipping）的概率。

3. **HWG Builder 的表达能力有限**。目前 HWG Builder 支持从 LlamaIndex/LangChain pipeline 自动提取工作流图，但用户自定义的复杂工作流（特别是涉及外部 API 调用、工具使用的多模态 RAG）能否被准确建模仍然存疑。

4. **与 METIS（Session 8 同一论文集的另一篇）的关系不够清晰**。两篇论文都涉及 RAG 配置优化，但侧重点不同。HedraRAG 专注于异构工作流的执行优化，METIS 专注于配置参数搜索。两者是否可以互补（METIS 优化配置 + HedraRAG 优化执行）未被讨论。

5. **缺乏与 SOTA RAG 优化系统的详细对比**。论文主要与 LlamaIndex 和 LangChain 进行对比，但未与实际生产级 RAG 优化系统（如 ReAct、Self-RAG、Corrective-RAG）进行对比，这些系统在学术界有更高的知名度和更成熟的质量保证机制。

## 未来工作

1. **将 HWG 扩展到多模态 RAG**：支持图像、视频、音频等非文本模态的检索和生成工作流。

2. **Learning-based Scheduler**：用强化学习训练 HWG 调度策略，学习最优的并行度和预取决策，而非依赖启发式规则。

3. **集成 METIS 的配置优化**：将 HedraRAG 的执行优化与 METIS 的配置优化相结合，实现端到端的最优 RAG 系统。

4. **分布式 HWG**：将 HWG 调度扩展到多节点场景，支持跨机器的 LLM 实例和向量数据库的协同调度。

## 个人评注

HedraRAG 的核心贡献——用异构图（HWG）统一建模不同类型的 RAG 工作流——是一个清晰且有价值的抽象。它成功地识别出 RAG 系统的异构性这一被忽视的问题，并提出了系统级的解决方案。

从技术深度看，Co-optimization of retrieval and generation 是最有意思的部分。在传统架构中，检索和生成是两个串行的黑盒阶段，系统优化者看不到内部的执行机会。HedraRAG 通过 HWG 打开了这两个黑盒，使得协同调度成为可能。

不过，论文在实验部分存在一定的 cherry-picking 嫌疑。选取的 HotpotQA 和 2WikiMultihopQA 都是多跳问答数据集，本质上非常适合 HedraRAG 的迭代检索优化。但对于简单的 single-hop 问答（PopQA），加速比骤降至 2.1x，说明 HedraRAG 在简单场景下并没有显著优势。论文虽然承认这一点，但未深入分析其根本原因。

总体而言，HedraRAG 是一个有前景的 RAG 系统设计框架。其核心思想——将异构 RAG 工作流显式建模并联合优化——具有较好的通用性和扩展性。关键挑战在于 Predictor 的泛化能力和 Generation Skipping 的安全性保证，这两个问题需要在生产环境中得到充分验证。
