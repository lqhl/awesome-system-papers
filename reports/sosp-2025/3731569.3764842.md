# Scalable Far Memory: Balancing Faults and Evictions

**作者**：Yueyang Pan, Musa Unal, Yujie Ren, Sanidhya Kashyap（EPFL）；Yash Lala, Seung-seob Lee, Abhishek Bhattacharjee, Anurag Khandelwal（Yale University）

## 一、背景

数据中心内存管理面临结构性矛盾：整体内存利用率普遍偏低，而大规模分析、机器学习等数据密集型应用却频繁突破单机 DRAM 上限。Far memory（远端内存）技术通过高带宽低延迟网络（如 RDMA）将多机内存池化，从而缓解这一矛盾。

page-based far memory 是目前最实用的路线：复用 OS 页换入换出机制，无需修改应用代码，已在 Google、Meta 等超大规模云环境中大规模部署（TMO、Hermit、DiLOS 等）。然而现有工作主要针对低线程数场景优化，在现代多核服务器（数十核）上运行数据密集型应用时性能急剧劣化。

---

## 二、要解决的问题

**核心问题**：现有 page-based far memory 系统无法在高线程数（multi-core）场景下保持可扩展性，导致 far memory 的容量收益在最需要它的场景下反而无法兑现。

具体表现：
- 以 48 线程跑 GapBS（page rank），仅将 10% 内存卸载到远端，Hermit 吞吐下降 73%、DiLOS 下降 51%，而理想系统仅应下降 10%。
- 随线程数增加，故障换入（fault-in）和换出（eviction）两条路径上均出现严重瓶颈：
  1. **TLB shootdown 代价随线程数超线性增长**：IPI 广播到多个核心，IPI 队列延迟在 1→48 线程时增加 33×；NUMA 跨 socket 更使延迟在 28 线程处出现拐点。
  2. **页面计数（page accounting）数据结构竞争**：全局 LRU 列表成为 fault-in 线程与 eviction 线程的争用热点，随线程数增加竞争开销增长 9.6–11.4×。
  3. **内存分配器高尾延迟**：本地 buddy allocator 和远端 swap allocator 均在高并发下因全局锁产生严重竞争，页面在空闲态与使用态之间的流转（page circulation）受阻。
- 当异步 eviction 线程跟不上 fault-in 压力时，现有系统退化为**同步 eviction**（在 fault-in 关键路径上直接驱逐页面），进一步放大 TLB IPI 代价。

---

## 三、核心设计

论文提出 **Mage** 系统，基于三条设计原则解决上述瓶颈：

### P1：Always-Asynchronous Decoupling（永远异步解耦）
- 将 eviction path（EP）完全从 fault-in path（FP）剥离，交由专用 evictor 线程负责。
- FP 线程**禁止**执行同步 eviction；若无空闲页则等待 EP 提供，而非自行驱逐。
- 专用 evictor 线程数固定为 4，既能维持稳定的空闲页供应，又避免过多线程带来的 IPI 竞争。

### P2：Cross-Batch Pipelined Execution（跨批次流水线执行）
- eviction 批次内部各步骤存在依赖（unmap → TLB flush → RDMA write），但步骤间存在大量等待时间（RDMA ACK、TLB ACK）。
- 将 eviction 设计为多批次流水线（multi-stage out-of-order pipeline）：用两个 per-CPU staging buffer（TLB Staging Buffer、RDMA Staging Buffer）重叠不同批次的各阶段，TLB flush 等待期间同时处理下一批次的 unmap，RDMA 等待期间同时处理下一批次的 TLB flush，从而将空闲等待转化为有效工作。
- 批次大小设为 128–256 页时性能最优，可完全用 RDMA 等待延迟掩盖 TLB shootdown 延迟。

### P3：Scalability Prioritization via Coordination Avoidance（以避免同步优先保证可扩展性）
- **Partitioned Page Accounting**：将全局 LRU 列表按 evictor 线程分片（per-CPU partitioned LRU），每个 evictor 维护独立 LRU，轮转扫描；牺牲全局精确性换取消除锁竞争。
- **Dedicated Batched TLB Invalidation**：每次 shootdown 批处理最多 256 个页面，仅由固定数量的 evictor 线程发起，消除多线程并发 IPI 的 APIC 队列拥塞。
- **Boosted Page Circulation**：本地内存分配器采用 per-CPU 空闲页缓存 + 全局 buddy allocator 兜底的层次化设计；远端内存分配采用 VMA-level direct mapping（将本地地址直接映射到远端等偏移地址），消除 swap entry 分配的全局锁。

## 四、实现细节

### MageLnx（基于 Linux 4.15.0）
- 约 17,000 行代码；复用 Hermit 绕过 Linux rmap 层的部分优化。
- 跳过 Linux swap 子系统，使用低竞争 FIFO 队列追踪 in-use 页面（替代 multi-generation LRU）。
- 将地址空间锁（VMA lock）从粗粒度优化为基于 interval tree 的分片锁。
- 直接管理 free page pool，绕过 Linux 内存分配器。
- **注意**：由于 Linux 网络栈开销，MageLnx 网络带宽利用率（139 Gbps）低于 MageLib（181 Gbps）。

### MageLib（基于 OSv unikernel v0.55）
- 核心约 4,234 行代码 + memory node 约 320 行。
- 复用 DiLOS 的 unified page table（替代 swap cache 做并发 fault-in 去重）、linker layer 和低延迟 RDMA 驱动。
- 本地内存分配器改为三级层次：per-core 空闲页缓存 → 共享并发队列 → 全局 buddy allocator，FP 和 EP 走不同分配策略。
- Memory node 以 RDMA one-sided 通信为主，使用 HugeTLB 减少远端 page table walk 代价。
- unikernel 单地址空间特性天然消除 rmap、swap cache 等跨应用组件。

## 五、实验结果

**实验平台**：两台服务器通过 Mellanox BlueField-2 DPU 以 200 Gbps RDMA 互联；每台 dual-socket Intel Xeon Gold 6348（56 核），512 GB 内存，Ubuntu 22.04 + Linux 5.14；MageLnx/MageLib/DiLOS 运行于 QEMU/KVM VM，Hermit 运行于裸金属。

### 吞吐量密集型应用（48 线程）

| 场景 | MageLib | MageLnx | DiLOS | Hermit |
|------|---------|---------|-------|--------|
| GapBS，10% far memory 时吞吐下降 | **15%** | 19% | 51% | 73% |
| GapBS，容忍 30% 吞吐下降可卸载内存比例 | **61%** | ~55% | ~20% | ~15% |
| XSBench，10% far memory 时吞吐下降 | **10%** | 10% | ~28% | ~30% |
| Sequential Scan（with prefetch），10% 时下降 | **6.4%** | - | ~28% | 降级 |

### 延迟敏感型应用（Memcached，24 线程）

| 场景 | MageLib | MageLnx | DiLOS | Hermit |
|------|---------|---------|-------|--------|
| p99 ≤ 200 μs SLO，可卸载内存（相对 Hermit） | +36% | +比 Hermit 更多 | +21% | 基线 |
| 50% far memory 下最大可承载负载（比 Hermit） | +0.64 M ops/s | +类似 | +0.28 M ops/s | 基线 |

### 最大可用吞吐量（sequential read，48 线程）

| 系统 | 网络带宽利用率 | p99 fault 延迟 |
|------|--------------|--------------|
| MageLib | **94%（181 Gbps）** | 12 μs |
| MageLnx | 72%（139 Gbps） | 31 μs |
| DiLOS | 30% | 82 μs |
| Hermit | 14% | 255 μs |

### 回归测试（100% 本地内存，无卸载）

MageLib 相比 Hermit 有 7–9% 性能回退，主要来源于 VM 虚拟化开销（EPT translation、VM exit）和 OSv 用户库成熟度不足；MageLnx 在 Metis 等 syscall 密集阶段因预初始化 far memory 产生额外开销（-20%）。

## 六、批判性分析

**1. 实验公平性问题**

MageLnx/MageLib 运行于 VM（QEMU/KVM），Hermit 运行于裸金属，这一差异影响多项关键对比结果。论文在吞吐量测试（GapBS/XSBench 等）中以 VM 对裸金属，天然引入了额外虚拟化开销（EPT、VM exit）。虽然论文在回归测试中承认了约 8% 的回退，但在吞吐提升的主要实验图中并未特别标注这一差异，可能使读者高估实际收益。

**2. 同步退化问题未彻底解决**

论文核心主张是"永远异步"（always-asynchronous），但实际上 MageLnx 仍受 Linux 网络栈带宽瓶颈限制（139 vs 181 Gbps），说明在极端压力下 EP 仍可能跟不上 FP。论文对"EP 跟不上时系统如何行为"未作正面回答——只说 FP 等待而不同步驱逐，但若 EP 长期供不应求，应用线程会无限阻塞，这与论文强调的低延迟目标矛盾。

**3. 参数固定化的适用性**

4 个专用 evictor 线程作为"甜蜜点"是在特定硬件（200 Gbps NIC）和工作负载上标定的，论文未分析该配置在不同网络带宽、不同 CPU 核数（如 128 核）或不同 working set 大小下的稳健性。

**4. Partitioned LRU 的精度代价**

分片 LRU 以牺牲全局替换精度换取扩展性，论文仅在顺序扫描和随机访问等"极端"工作负载上验证，未测试混合访问模式下替换质量下降是否导致更高 page fault 率或内存抖动（thrashing）。

**5. 与 CXL 的比较缺失**

论文把 CXL 列为"超出本文范围"，但 CXL 正在成为工业界的主流 far memory 路线（Intel、AMD、各大云厂商）。不讨论两者在多核场景下的实际性能差距，使得论文对未来工程选型的指导价值受限。

**6. 评估规模偏小**

实验仅在 2 台服务器（两端各一台 VM）上进行，未验证在多内存节点（memory pool scale-out）、多应用共享内存节点等真实数据中心场景下的表现。

## 七、AI Infra / MLSys 视角

**关联性**：直接相关。ML 训练（PyTorch/TF 大 batch、大模型参数）和推理（vLLM KV cache、大 working set）都是典型的内存受限、多线程数据密集型场景，是论文目标用户之一。

**可迁移的 insight**：

1. **异步解耦原则对 AI 推理系统的借鉴**：vLLM 等系统在 KV cache 管理中存在类似的 page fault（cache miss 换入）与 eviction（prefix cache/block 换出）路径耦合问题。Mage 的 always-asynchronous 设计（专用线程负责换出，推理路径不阻塞）可直接迁移到 KV cache 管理器设计中，减少请求尾延迟。

2. **分批流水线掩盖延迟**：AI 训练中的 gradient offload（将 optimizer state 卸载到 CPU 或 NVMe）同样面临 D2H/H2D 数据搬移与计算之间的耦合问题；Mage 的跨批次流水线技巧（overlap 不同批次的 RDMA 等待）可用于设计更高效的 gradient checkpointing 调度器。

3. **per-CPU 分片数据结构对分布式推理的价值**：多 GPU 推理服务器上，若使用共享 KV cache 或参数缓存，全局锁是常见瓶颈；论文展示的 partitioned LRU + per-core cache 层次化设计是一套成熟的工程模式。

**值得跟进的 future work**：

- 将 Mage 的 eviction pipeline 与 vLLM/SGLang 的 block-level KV cache 管理集成，评估在长上下文推理（128K+ token）场景下的吞吐和延迟改善。
- 探索在 AI 训练中将 optimizer state（Adam 的 m/v）卸载到 far memory 时，Mage 式异步流水线能否使 GPU 利用率接近全本地内存场景。
- 研究 Mage 设计在 CXL 内存扩展卡上的适配：CXL 没有 TLB shootdown 问题，但 page accounting 竞争依然存在，partitioned LRU 是否同样有效？

---

## 八、总结

Mage 是首个同时实现透明 far memory 兼容性与多核可扩展性的 page-based 远端内存系统。其核心贡献在于识别并量化了 fault-in 与 eviction 路径失衡导致的三类瓶颈（TLB coherence、page accounting 竞争、内存分配器竞争），并以"永远异步解耦 + 跨批次流水线 + 协调回避优先"三原则重构了 eviction path 设计。在 48 线程、200 Gbps RDMA 环境下，MageLib 可利用 94% 网络带宽，相较现有系统提升吞吐 1.2–4.2×，将 Memcached p99 延迟降低 94.5%。主要局限在于：实验规模较小（仅两台服务器）、VM 与裸金属对比存在公平性问题、Partitioned LRU 替换精度牺牲的量化不足，以及尚未与 CXL 进行系统对比。
