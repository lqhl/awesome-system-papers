# Scalable Far Memory: Balancing Faults and Evictions

## 论文基本信息

- **标题**: Scalable Far Memory: Balancing Faults and Evictions
- **作者**: Yueyang Pan, Yash Lala, Musa Unal, Yujie Ren, Seung-seob Lee, and Abhishek Bhattacharjee
- **会议**: SOSP 2025
- **Session**: Data Centers
- **PDF**: 3731569.3764842.pdf

## 研究背景

现代数据中心面临严峻的内存管理挑战：虽然服务器平均内存利用率偏低，但数据密集型应用（如大规模分析、机器学习）的内存需求不断增长，经常超出本地 DRAM 容量限制。远端内存（Far Memory）技术——通过 RDMA 将远程服务器内存作为透明扩展——是一种无需修改应用代码即可扩展内存容量的解决方案。

然而，现有的远端内存系统（如 Hermit 和 DiLOS）主要针对低线程数场景优化，在现代多核机器上无法高效扩展。这一"可扩展性悖论"导致了一个关键问题：最需要远端内存支持的数据密集型应用恰恰是那些线程数多、需要高并发内存访问的应用，而现有系统在这些场景下性能严重下降。

论文的分析揭示了三个根本性的性能瓶颈来源：
1. **TLB shootdown 开销**：跨核中断来维护 TLB 一致性随线程数增加而急剧增长
2. **全局数据结构争用**：系统级 LRU 列表在故障调入页面的应用线程和后台淘汰线程之间产生严重争用
3. **内存分配器尾延迟**：本地和远程内存分配器在争用下产生高尾延迟，阻碍了页面帧的高效流转

这三个瓶颈协同作用，导致故障调入（Fault-in）和页面淘汰（Eviction）吞吐量双双下降，且淘汰路径受影响更为严重。

## 要解决的问题

如何设计可扩展的远端内存系统，使其在现代多核机器（高线程数）上高效运行，同时保持远端内存的透明性和兼容性？

## 核心贡献

- **可扩展性分析**：首次系统性地分析了现有远端内存系统在高线程数场景下的性能崩溃问题，识别出三个可扩展性瓶颈（TLB shootdown、全局 LRU 争用、内存分配器争用）。
- **三大设计原则**：提出Always-Asynchronous Decoupling（故障调入与淘汰路径始终异步分离）、Cross-Batch Pipelined Execution（跨批次流水线执行）和 Scalability Prioritization（高线程数场景优先考虑可扩展性而非淘汰精度）三大设计原则。
- **MageLnx 实现**：在 Linux 内核 4.15.0 上实现了 MageLnx（约 17,000 行代码），展示远端内存调页可在通用操作系统上变得可扩展。
- **MageLib 实现**：在 OSv unikernel 上实现了 MageLib（约 4,234 行代码），实现更低的故障处理开销。
- **显著性能提升**：批处理应用吞吐量提升最高 4.2 倍，延迟关键型 Memcached 应用的 P99 延迟降低 94.5%。

## 主要研究方法

论文采用了"理想系统"建模法作为性能基准——理想系统仅考虑数据传输成本，故障调入和淘汰路径的软件开销为零。通过对比 Hermit、DiLOS 与理想系统的性能差距，量化了各瓶颈的相对影响。

论文在两种系统原型上进行了对比评估：
- **Hermit**：多线程异步淘汰设计，针对 Linux 内核优化
- **DiLOS**： unikernel 架构，完全绕过 Linux 内核的内存管理组件

实验使用双 socket Intel Xeon Gold 6348 服务器（每 socket 28 核），通过 QEMU/KVM 虚拟化，禁用超线程以消除干扰。

## 设计与实现

**三大设计原则**：

**P1: Always-Asynchronous Decoupling**：将淘汰路径（EP）的重型操作（如 TLB 一致性维护）完全卸载到专用后台线程，使其脱离应用关键路径。与之前工作的关键区别在于，故障调入路径的线程在本地内存短缺时**不会**执行同步淘汰，而是完全依赖 EP 线程。这一设计最小化了争用开销，避免了 TLB IPI 排队延迟。

**P2: Cross-Batch Pipelined Execution**：利用 RDMA 写和 TLB 刷新的等待时间在批次间进行流水线化。设计了两种每 CPU 分阶段的缓冲结构：
- TSB（TLB Staging Buffer）：保存已解除映射但 TLB 条目可能仍被缓存的页面
- RSB（RDMA Staging Buffer）：保存等待远程内存写完成的页面

每个批次的执行流程为：切片 LRU 列表并解除映射 -> 发送 TLB flush IPI -> 等待 TLB flush 完成 -> 将脏页从 TSB 移动到本地缓冲 -> 发起 RDMA 写 -> 等待 RDMA ACK -> 回收清洁页面。通过跨批次流水线化，等待时间被有效利用。

**P3: Scalability Prioritization**：在高线程数场景下，优先考虑减少同步开销而非淘汰精度。具体措施包括：
- 分区 LRU 设计：每个淘汰线程维护独立的 LRU 列表，通过 CPU ID 哈希均匀分布新页面，有意牺牲全局淘汰准确性以换取低争用
- 多层内存分配器：每核空闲页缓存 -> 共享并发队列 -> 全局 buddy 分配器

**MageLnx 实现**（§5.1）：
- 绕过 Linux Swap 层
- 将粗粒度地址空间锁优化为基于区间树的"分片"
- 使用低争用 FIFO 队列追踪使用中的页面（而非 Linux 的 Multi-Gen LRU）

**MageLib 实现**（§5.2）：
- 基于 OSv unikernel，采用 DiLOS 的统一页表和低延迟 RDMA 驱动
- 三级分配器层次结构

## 主要实验结果

**随机访问模式应用**（§6.2）：GapBS（PageRank）和 XSBench，48 线程测试：
- DiLOS 和 Hermit 在 10% 内存卸载时性能分别下降 51% 和 74%
- MageLib 和 MageLnx 在同样 10% 卸载时仅下降 15% 和 19%
- 若运营商可容忍 30% 性能下降，MageLib 可支持高达 61% 的内存卸载

**顺序扫描应用**（§6.2）：Sequential Scan + Prefetching：
- MageLib 在 10% 卸载时达到理想性能的 93.6%（仅 6.4% 下降）
- 预取有效是因为 Mage 的快速淘汰路径可维持预取产生的高故障调入压力
- DiLOS 和 Hermit 的预取收益有限

**变工作集应用**（§6.2）：GUPS 和 Metis：
- DiLOS 和 Hermit 在工作集切换后严重停顿（超过 2 秒）
- Mage 在相位转换期间仅临时下降至 0.4 Mops/s，持续 1.4 秒后恢复

**延迟关键型 Memcached**（§6.3）：
- 对于 200 us 的 SLO，MageLib 相比 DiLOS 可多卸载 21% 内存，相比 Hermit 多卸载 36%
- 若 SLO 放宽至 220 us，差距增至 40%
- 维持 P99 延迟 200 us 的 SLO 时，Mage 相比 Hermit 可多处理 0.64 M ops/s 负载

**技术分解**（§6.5）：
- 流水线化淘汰：GapBS 额外释放 4.3% 可卸载内存
- 分区 LRU：消除淘汰期间 81.2% 的周期开销
- 多层分配器：每页平均分配时间从 2.4 us 降至 0.5 us（减少 93.1%）

**100% 本地内存性能**（§6.4）：批处理应用在 100% 本地内存下执行时，所有系统均保持接近基线的性能，验证了 Mage 的优化不会对无远端内存场景产生回归。

## 潜在问题 / 局限性

1. **分区 LRU 的淘汰精度牺牲**：有意放弃全局淘汰准确性换取可扩展性的设计选择，在某些场景下可能导致次优的页面选择决策。论文未充分评估这一精度损失对长期运行应用的影响。

2. **仅支持 RDMA 传输**：Mage 依赖 RDMA 进行远程页面传输，未评估其他远端内存技术（如 CXL）下的表现。论文在讨论中承认 CXL 与 RDMA 分页可能长期共存，但未提供具体比较。

3. **评估规模相对有限**：所有实验在双服务器设置下进行，未评估跨多个机架或 Pod 的远端内存系统表现，也未测试更大规模的 VM 集群场景。

4. **缺乏与 CXL 硬件方案的比较**：论文讨论了 CXL 作为替代方案，但缺乏在真实 CXL 硬件上的评估数据，仅有对 pond 的引用讨论。

5. ** unikernel 架构的限制**：MageLib 基于 OSv unikernel，这意味着应用必须针对该平台重新编译或以特殊方式运行，限制了通用性。相比之下，MageLnx 虽然基于 Linux 但修改较深（17k 行代码），部署门槛不低。

6. **GUPS 基准的代表性问题**：GUPS 基准测试是高度人工合成的，其结果能否推广到真实数据处理应用存在疑问。

7. **未解决的跨 NUMA 场景**：实验明确限制了跨 NUMA 通信的影响，但真实大规模部署中 NUMA 效应是不可避免的。

## 个人评注

Mage 是本次 SOSP 2025 Data Centers 论文中实验最详实、可扩展性分析最系统的工作之一。论文的核心价值在于揭示了一个重要但此前未被充分研究的问题：远端内存系统的可扩展性瓶颈，并对三个瓶颈（TLB shootdown、全局 LRU 争用、内存分配器争用）进行了深入分析。

三大设计原则的提炼具有较强的通用性。特别是 Always-Asynchronous Decoupling 和 Cross-Batch Pipelined Execution 的组合——通过彻底分离故障调入和淘汰路径，并将淘汰路径流水线化来隐藏等待开销——这一设计选择清晰且有说服力。分区 LRU 虽然牺牲了精度，但在实践中证明是有效的权衡。

不过，论文的一个重要局限在于缺乏与相关工作的直接对比（如 DAMON-based TMM、CXL 方案、以及Sage 等工作）。在远端内存系统领域，这可能是一个审稿人关注的重点。另一个值得关注的点是 Mage 的两个实现（MageLnx 和 MageLib）采用了不同的架构设计，这增加了系统的复杂度，也使得两种实现之间的公平比较更加困难。

总体而言，Mage 为远端内存系统的可扩展性研究提供了一个扎实的新基线，其设计原则对于后续相关工作具有重要的参考价值。
