# Tempo: Compiled Dynamic Deep Learning with Symbolic Dependence Graphs

## 论文基本信息

- **标题**: Tempo: Compiled Dynamic Deep Learning with Symbolic Dependence Graphs
- **作者**: Pedro F. Silvestre and Peter Pietzuch
- **会议**: SOSP 2025
- **Session**: ML and FPGA
- **PDF**: 3731569.3764840.pdf

## 研究背景

动态深度学习（Dynamic Deep Learning）是指神经网络中计算图的结构在运行时依赖于输入数据值的一类模型。与静态网络（如标准 ResNet、VGG）不同，动态网络的图结构在编译时无法完全确定，必须在推理或训练过程中根据实际数据动态决定。这类产品包括：MoE（Mixture-of-Experts）模型中的稀疏激活路由、递归神经网络（RNN/LSTM）的变长序列处理、带有 early exit 的多出口网络、以及条件计算（Conditional Computation）等。

现有的深度学习框架（PyTorch、JAX）采用 eager execution 模式，即逐条执行操作并立即返回结果。这种模式虽然灵活，支持任意 Python 控制流，但对动态网络存在显著的性能瓶颈：无法进行全局优化（如算子融合、内核调度优化）、无法利用图级并行性、以及每次运行时都需要重新解释计算逻辑。相比之下，静态编译器（如 PyTorch.compile/TorchInductor、XLA、JAX 的 JIT）能够对计算图进行优化，但它们要求在编译时就能完整地刻画计算图——这恰恰是动态网络所不具备的前提。

除了 eager 和静态编译两条路之外，学术界还探索了 tracing-based 动态编译方案（如 functorch、PyTorch Dynamo）。这些方案通过执行一次模型来"tracing"计算图，然后对捕获的图进行优化。但当控制流依赖于运行时值时，tracing 只能捕获一条执行路径，无法覆盖所有可能的分支，导致动态性丢失。

## 要解决的问题

如何设计一个深度学习编译器，能够同时满足两个目标：（1）保留动态网络的运行时灵活性，即允许计算图结构根据输入数据动态变化；（2）获得编译优化带来的性能收益，即通过全局算子融合、并行化调度和内核优化来加速执行。

Tempo 的核心问题是：**如何在运行时动态发现依赖关系的同时，仍然实现接近静态编译的性能？**

## 核心贡献

1. **Symbolic Dependence Graph（SDG）**：一种新的中间表示（IR），将每个操作表示为带符号依赖的节点，运行时通过符号求值（symbolic evaluation）动态解析依赖关系，而非在编译时静态绑定。

2. **Trace and Specialize 编译策略**：分两个阶段处理动态代码——首先 tracing 捕获代码的"骨架"（skeleton），然后在骨架上"编织"动态条件，使编译器能够在静态可分析的区域内应用优化，同时在动态区域内保持灵活性。

3. **动态并行化调度器**：基于 SDG，运行时调度器可以在控制流分支结束后立即并行启动多个依赖路径上的计算，充分利用硬件并行性。

4. **对五种动态神经网络模式的通用支持**：MoE 路由、递归神经网络、早退出、条件计算和变长输入，无需针对每种模式单独设计编译器 pass。

5. **开源实现**：Tempo 在 GitHub 上开源，评估表明其性能可与静态编译器媲美，同时保持对动态控制流的完整支持。

## 主要研究方法

Tempo 的方法论建立在三个关键设计决策之上：

**1. Symbolic Dependence Graph（SDG）**

传统的计算图（如 PyTorch 的 DAG 或 XLA 的 HLO）中，边代表具体的 tensor 数据依赖。但在动态网络中，某些依赖在编译时是未知的——例如 `if routing(x) > 0.5` 中 `routing(x)` 的输出值决定了执行哪条分支。Tempo 的 SDG 将依赖表示为**符号表达式**，而非具体值：

```
Node A: y = linear(x)
Node B: z = attention(y)
SDG edge: B depends on A via "y"
```

当执行到 `if routing(x) > 0.5` 时，routing 的输出是具体的 tensor 值，调度器可以据此决定是否调度 B。这是一个"符号追踪 + 运行时求值"的混合策略。

**2. Trace and Specialize**

Tempo 的编译器首先将 PyTorch eager 代码 tracing 一次，生成一个"骨架图"（skeleton graph），其中动态控制流被替换为占位符。然后，编译器对这个骨架图进行标准优化（如算子融合、死代码消除）。最后，在生成的优化代码中嵌入动态编织逻辑——运行时根据实际条件选择激活哪些计算路径。

**3. Dynamic Parallelism Scheduling**

当执行流到达条件分支的出口时，SDG 调度器能够识别出所有被条件保护的新计算，并立即将它们并行调度到硬件执行单元上。这比 eager 模式的串行执行更高效。

## 设计与实现

Tempo 的系统架构包含以下层次：

```
[PyTorch Eager User Code]
         ↓
+------------------+
|  Tempo Frontend  |  (PyTorch FX tracing + skeleton extraction)
+------------------+
         ↓
+------------------+
|   SDG Builder    |  (builds symbolic dependence graph)
+------------------+
         ↓
+------------------+
|   Optimizer      |  (operator fusion, CSE, dead code elim.)
+------------------+
         ↓
+------------------+
| SDG Code Generator| (generates optimized executable)
+------------------+
         ↓
+------------------+
|  SDG Runtime     |  (symbolic evaluation, dynamic scheduling)
+------------------+
         ↓
[Optimized Execution on GPU/CPU]
```

**Tempo Frontend**：接受 PyTorch eager 代码，通过符号执行（而非值执行）来 tracing，生成 skeleton graph，其中包含控制流结构的占位符。

**SDG Builder**：遍历 skeleton graph，将每个操作封装为带符号依赖信息的节点，构建 SDG。

**Optimizer**：对 SDG 应用一系列优化 pass：
- **算子融合**（Operator Fusion）：将连续的 pointwise 操作合并为单个 kernel，减少内存访问和 kernel launch 开销
- **常量折叠**（Constant Folding）：预计算不依赖动态输入的子图
- **死代码消除**（Dead Code Elimination）：移除不可达的计算路径

**SDG Runtime**：负责运行时执行。关键设计是**符号求值器**（symbolic evaluator）——当执行到动态控制流节点时，求值器计算条件表达式（这是快速的），然后根据结果调度后续的计算。它维护一个就绪队列（ready queue），当多个分支在运行时汇合时，调度器可以将分支内的计算并行发射。

## 主要实验结果

Tempo 的评估覆盖了 5 种动态神经网络模式和 6 个典型模型：

| 模型 | 任务 | 动态性来源 | 加速比（vs Eager） |
|------|------|-----------|-----------------|
| Switch Transformer (8 experts) | LLM 推理 | MoE 稀疏路由 | 4.9x |
| Early Exit ResNet | 图像分类 | 自适应早退出 | 3.2x |
| Recursive Transformer | 树结构处理 | 变长递归 | 2.8x |
| Adaptive Computation Time | 语言建模 | 条件计算步数 | 3.1x |
| Dynamic Mixture of Experts | 推荐系统 | 输入依赖路由 | 4.1x |

**关键对比数据**：
- **vs PyTorch Eager**：Tempo 平均加速 3.3x，最高 4.9x
- **vs PyTorch.compile (TorchInductor)**：Tempo 在动态场景下保持接近性能（差距 < 5%），而 TorchInductor 在动态场景下需要 fallback 到 eager
- **内存占用**：Tempo 的 SDG 表示引入的额外内存开销约为原始模型大小的 8-15%，在可接受范围内
- **编译时间**：Tempo 的编译时间比 TorchInductor 快约 1.5x（因为 skeleton tracing 比完整 tracing 更轻量）

## 潜在问题 / 局限性

1. **性能边界模糊**。论文声称 Tempo 能达到接近静态编译器的性能，但这个结论仅在"动态性可控"的前提下成立。对于高度随机或混沌的动态控制流（如输入驱动的复杂分支树），SDG 的符号求值开销可能显著增加，而优化收益减少。论文没有充分讨论这一边界。

2. **调度开销被低估**。SDG 调度器在每个动态分支点都需要进行符号求值和任务调度。这个开销对于计算密集型模型可能微不足道，但对于轻量级动态网络（如 small MoE），调度开销占比可能达到不可忽视的程度。论文缺少对此的消融实验。

3. **评估场景的选择性**。论文选取的模型都是相对"友好"的动态网络（MoE 路由有固定数量的 experts，早退出网络有预定义的退出点）。对于完全动态的场景（如动态计算图结构每次请求都完全不同），Tempo 的适用性有待验证。

4. **与现有框架的比较不够全面**。论文将 TorchInductor 作为主要竞争对手，但未与 JAX 的 `jit` + `lax.cond` 组合或 TensorFlow 的 `tf.function` + `tf.cond` 进行对比。此外，未对比微软的 DeepSpeed-Inference 或 NVIDIA 的 TensorRT 等工业级推理引擎。

5. **不支持分布式训练**。论文仅讨论推理场景，未涉及训练场景下梯度反向传播和动态计算图共存时的挑战。这限制了 Tempo 在训练场景的适用性。

## 未来工作

1. **扩展到训练场景**：支持动态网络的一阶段训练（而非仅推理），需要解决梯度计算与 SDG 的结合问题。

2. **SDG 的更精细优化**：目前 SDG 仅支持粗粒度的算子融合，未来可以引入 tile-level fusion、kernel auto-tuning 等更细粒度的优化。

3. **多后端支持**：当前实现仅支持 GPU，未来可以扩展到 TPU、CPU 以及异构硬件（CPU+GPU 协同）。

4. **自动化动态性检测**：自动识别代码中的动态控制流，并决定哪些可以 specialization、哪些需要保留为符号求值，降低用户的手动标注负担。

## 个人评注

Tempo 是一项扎实的系统工作，准确地捕捉到了深度学习编译器领域的一个真实痛点：静态编译和动态执行之间的权衡。SDG 的设计颇具创新性——用符号依赖替代具体值来表征动态性，在概念上优雅，且在实现上可行。Trace and Specialize 的两阶段策略也很有启发性，它提供了一种将动态代码"静态化"的通用框架。

不过，论文的贡献更偏向于"增量式"而非"范式转换"。SDG 的核心思想与已有的符号执行（Symbolic Execution）和依赖追踪（Dependency Tracking）技术有相当程度的重叠。论文对这些相关工作的区隔和超越论述得不够清晰。

从实用角度看，Tempo 的实际价值取决于它能否在工业级模型上复现评估结果。如果编译开销可控、优化效果稳定，它有望成为动态神经网络推理的一个重要工具。但目前看来，它更像是一个有前景的研究原型，而非生产级解决方案。
