## 一、背景

深度学习（DL）算法广泛应用于 LLM 推理、强化学习（RL）、扩散模型、状态空间模型等领域。这些算法的计算逻辑天然以**时间步之间的递推关系（recurrence equations）**来定义：某时间步的 tensor 依赖于过去或未来若干时间步的 tensor 值。

当前主流 DL 系统分为两类：
- **Eager（命令式）系统**（PyTorch、TF-Eager）：支持动态 shape，但无法做编译期全局优化和调度
- **Graph-based（声明式）系统**（TensorFlow、JAX）：支持全程序优化，但**要求静态 tensor shape**，无法直接表达动态依赖

这两类系统的根本矛盾导致工程实践中的大量妥协——用 padding/masking 掩盖动态性、将程序拆成多段静态子图、放弃跨时间步的整体优化。

---

## 二、要解决的问题

**问题 1：LLM 推理中的 KV-cache 管理复杂**

Causal attention 中每个时间步 t 依赖 `K[0:t+1]` 的全部历史——这是动态 shape。JAX 需要 pad 到最大序列长度 T，padding 开销随 T 线性增长；不同 attention 类型（causal、windowed、block）需要截然不同的 cache 策略，现有系统（vLLM、SGLang）无法自动推导，需要大量人工工程。

**问题 2：RL 框架的 actor-learner 分离带来冗余计算**

RL 的 loss 函数具有前向（anti-causal）依赖：每个时间步的 return 依赖未来奖励之和。现有 RL 框架将 acting（前向推演）和 learning（梯度更新）拆成两个独立子图，导致：
1. Actor 的前向激活被丢弃，learner 需重新计算 → 前向计算量翻倍
2. Acting 和 learning 必须串行执行（无法并行）
3. 峰值内存高（所有时间步数据必须同时保存）

**问题 3：缺乏对动态依赖的统一优化框架**

Eager 系统无法进行 vectorization、tiling、fusion 等编译优化；graph-based 系统无法表达动态依赖。没有一个系统同时支持"动态性 + 全程序编译优化 + 自动内存管理"。

## 三、核心设计

Tempo 的核心洞见：**DL 算法中的 tensor 隐含了时间维度，将其显式化后，动态依赖就变成了跨时间维度的普通 tensor 索引操作，从而可以用符号化方法进行表达和优化。**

### 3.1 Recurrent Tensors（RTs）——声明式编程模型

RTs 是 Tempo 的用户接口层。一个 RT 除了空间维度（shape）外，还拥有**时间维度（temporal dimensions）**，如 timestep `t`、iteration `i`，构成其 domain。用户用**符号表达式（symbolic expressions）**对时间维度进行索引，声明式地表达动态依赖。例如：

```python
scores = q @ k[0:t+1]   # causal attention：q[t] 依赖 k[0..t]
g = r[b, i, t:T].discounted_sum(0.95)  # REINFORCE：g[t] 依赖未来所有奖励
```

RT 支持：
- **自动 domain 推断**：不需用户手动标注，Tempo 根据操作自动推导 tensor 的 domain
- **Domain 广播与 union**：两个不同 domain 的 RT 交互时，输出 domain 取 union
- **符号化自动微分**：通过反转依赖表达式（φ → φ⁻¹）自动推导梯度的时间归约逻辑

### 3.2 Symbolic Dependence Graphs（SDGs）——中间表示与优化

Tempo 将 RT 程序翻译为 SDG：
- 每个节点（operator）携带 temporal domain Ω
- 每条边带 dependence expression φ，表示 sink[t] 依赖 source[φ(t)]
- 允许 cycles（用于编码 DNN 参数状态）

SDG 上的优化 pass（按顺序）：

| Pass | 功能 |
|------|------|
| **Lifting** | 识别 MergeOp 形成的 recurrent pattern（reduction、scan、stencil），替换为 SumOp/CumSumOp，消除妨碍 vectorization 的循环依赖 |
| **Vectorization** | 将时间维度展开到空间维度，使 operator 执行次数减少但 tensor 更大，增加 SIMD 并行度 |
| **Static Tiling** | 将动态 shape 操作切成静态大小的 tile（加最小 padding），使 code-generation 可行；以 causal attention 为例，将 `K[0:t+1]` 切成 ⌈(t+1)/Z⌉ 个 tile |
| **Fusion** | 识别 domain 相同、无跨域依赖的静态孤岛，融合为单个 DataflowOp，交给 DL 后端 code-generator |

### 3.3 多面体调度（Polyhedral Scheduling）

由于 SDG 是声明式的，Tempo 使用**多面体模型**求解执行顺序：

1. 将 SDG 依赖关系和 domain 约束翻译为整数线性规划（ILP）的合法性约束
2. 通过 Pluto 调度器（经 isl 库）求解 schedule 函数 θ（映射每个时间步到执行时刻）
3. 扫描 schedule 函数，生成命令式 AST

**内存管理调度**同样通过 SDG 增强实现：在 SDG 中加入 Dealloc、Evict、Load 节点及相应依赖边，交给同一多面体调度器统一求解——自动推导出 deallocation 时机、GPU/CPU swap 点、buffer donation（原地复用）机会。

### 3.4 运行时执行

- ~33K Python LoC
- 支持 Torch 和 JAX 两种 DL 后端
- 三种 tensor store 策略：point store（逐点访问）、block store（块访问）、window store（窗口循环访问）
- Kernel wrappers：in-place write（直接写预分配 buffer）、lazy reads（slice 而非 copy）

## 四、实现细节

**RT 的关键操作**：
- 索引符号表达式支持算术、布尔比较、min/max、slice（start:stop:step）、条件索引
- Branching RT 通过 MergeOp 实现（条件选择哪条输入边在时刻 t 激活）
- 状态（DNN 参数）通过 MergeOp cycle 编码，无需 stateful operator

**SDG 节点集合**：
- 44 个无状态 operator，覆盖 elementwise map、reduction、scan、view、spatial indexing
- UDFOp：自定义操作（用于集成 RL 环境、tokenizer）
- MergeOp：条件分支

**静态 Tiling 的 masking 细节**：
- Causal attention 最后一个 tile 可能不满 Z 步，需 padding
- MatMul/Sum 用 0 mask，MaxOp 用 −∞ mask
- Tempo 通过向 runtime 提示预分配 mask 值来进一步消除 padding 开销

**Vectorization 的 cycle 限制**：
- 对 non-trivial cycle（符号索引不是纯 [t] 或常数）不做 vectorization，避免生成不可调度的 SDG

**多面体调度**：
- 通过 isl 库接口 Pluto scheduler
- ILP solving 在大模型下仅需约 2s（因 fusion 和层维度编码大幅缩减图规模）

**编译时间**：约 18s（其中 DL 后端 code-generation ~7s，内存预分配 ~1s，多面体调度和 buffer donation 分析为主要耗时）；随模型层数增加近似常数（层间 temporal dimension 共享优化）。

## 五、实验结果

**硬件**：AMD EPYC 7402P 24-core CPU，384 GB DDR4，NVIDIA RTX A6000 48GB，PCIe Gen4 ×16（32 GB/s）；CUDA 12.8，PyTorch 2.7.1，JAX 0.6.2

### LLM 解码（Llama-3.2-3B）

| 配置 | 结论 |
|------|------|
| Causal attention，B=16，T=2K~16K | T<4K 时 Tempo≈JAX；T≥4K Tempo 开始 tiling，T=16K 时快 43%；JAX 在 T=16K 时 OOM |
| Causal attention，B=4，长序列 | T=32K 时 Tempo 2× JAX；T=65K 时 2.5× |
| Windowed attention，B=16 | Tempo 最高 7× JAX（T=16K）；Tempo 可扩展到 4× 更长序列；JAX/Torch 无法自适应 cache 策略 |

GPU 内存：Tempo 对 window attention 使用循环 buffer，内存常数；JAX/Torch 无论 attention 类型均预分配全量 buffer。

### RL 训练（PPO 为代表）

| 对比基线 | 速度提升 |
|---------|---------|
| vs. RLlib | 最高 **54×** |
| vs. CleanRL（手写优化 PyTorch 实现） | 平均 **2.6×** |
| 峰值内存 | 最高 **16×** 更低 |

原因：Tempo 通过 whole-program compilation 消除了 actor-learner 的前向 pass 重复；向量化 timestep 维度后 backward graph 无需拼接小子图。

### Algorithm-specific scheduling（REINFORCE 变体）

- Monte Carlo（anti-causal 访问）：Tempo 先仿真（持续 evict 到 CPU），仿真结束后再 swap 回 GPU 逐步学习
- 8-step TD（forward window 访问）：Tempo 仅保留最近 n 步观测，8 步延迟后并行 acting+learning，GPU 全程满载
- 64-step TD：略有 GPU 利用率波谷，但整体高于 actor-learner 框架

## 六、批判性分析

**1. 单 GPU 限制掩盖了规模问题**

实验只在单张 RTX A6000（48GB）上进行，模型为 Llama-3.2-3B（较小）。现实生产中的 LLM 推理（70B+，multi-GPU）场景下 Tempo 能否 work 完全未验证。论文虽讨论了分布式扩展的可能路径（tiling → worker 维度 → pipeline/tensor/data parallelism），但未有任何实验支撑。

**2. 编译时间过长，对在线服务场景不友好**

~18s 的编译时间对批量训练可以接受，但对 LLM 推理服务（需要快速启动、动态 batch、变化的序列长度）是明显障碍。论文没有对比 vLLM/SGLang 等推理系统，也没有分析编译时间随序列长度、batch size 变化的情况。

**3. 未支持 FlashAttention，核心 LLM kernel 存在明显性能缺口**

FlashAttention 是当前 LLM 推理的标准高性能 attention kernel，Tempo 不支持它。论文对此的解释是语义复杂性妨碍了 transformation pass。这意味着在实际 LLM workload 上，Tempo 的 attention 实现性能可能远低于 vLLM 等系统——论文的 LLM 加速对比只与 Torch（eager）和 JAX（需要 padding），并非与 FlashAttention-based 系统对比。

**4. RL 基线选取不公平**

Tempo-JAX 和 Tempo-Torch 对比的 RLlib、SampleFactory、RLGames 等系统中，RLlib 不支持 GPU 加速环境（论文注脚说明），这使得对 RLlib 的 54× 加速缺乏参考价值。CleanRL 是最有意义的基线，但 Tempo 对 CleanRL 的优势仅有 2.6× 均值，最高提升也取决于参数配置。

**5. Tile size 仍需手动调参**

论文指出最优 tile size 是"最小化 GPU 利用率达到上限的尺寸"（论文图 18 呈 U 型曲线），但目前需要用户手工设定。这是一个工程完备性的缺口——对不同模型、batch size、序列长度，最优 tile size 不同，且对性能影响显著。

**6. 动态终止条件（T 在运行时决定）未支持**

大量实际场景（LLM 生成 EOS token 提前终止、RL episode 提前终止）需要动态终止，Tempo 目前不支持，必须预先指定 T 的上界。这与"支持动态性"的定位存在矛盾。

## 七、AI Infra / MLSys 视角

**对 LLM 推理系统的启发**

Tempo 将 attention 的动态 KV-cache 依赖形式化为时间维度上的符号表达式，并自动推导出对应的内存管理策略（何时 dealloc、何时 swap）。这种**依赖感知的内存管理**思路对推理系统（vLLM PagedAttention、SGLang RadixCache）有借鉴价值——目前这些系统的 cache 策略是手写的 case-by-case 工程，Tempo 提供了一个自动推导路径。

**对 RL 训练系统的启发**

Tempo 证明了将 actor 和 learner 的计算图统一后，可以消除 forward pass 重复、实现细粒度 acting-learning 流水线并行。当前 RLHF 训练系统（如 OpenRLHF、verl）普遍采用 actor-learner 分离的架构，且存在明显的 activation 重算开销，这是一个值得关注的优化方向。

**多面体模型应用于全程序 DL 调度**

此前多面体模型主要用于 kernel 内部优化（TVM、Tiramisu、Tensor Comprehensions），Tempo 将其提升到全程序级别的调度与内存管理。这对混合精度训练、gradient checkpointing 自动化、分布式流水线调度等问题都有潜在借鉴价值。

**可探索的 future work 方向**

1. **Tempo + FlashAttention**：设计 FlashAttention 作为 Tempo SDG 中的 first-class operator，保留 Tempo 的内存管理能力的同时利用高性能 kernel
2. **分布式扩展**：将 Tempo 的 worker 维度 tiling 实现为 multi-GPU 分布式训练，验证其 pipeline parallelism 路径
3. **动态 T 支持**：结合 speculative 技术（如预测终止时间步）降低动态终止的 GPU/CPU 同步开销
4. **应用于 RLHF 系统**：用 Tempo 的统一图方法替代 RLHF 中 actor/critic/ref-model 的手动 activation sharing，量化 forward pass 消除带来的训练加速

---

## 八、总结

Tempo 提出了一套新的 DL 编程模型（Recurrent Tensors）和编译框架（Symbolic Dependence Graphs + 多面体调度），将 eager 系统的动态表达能力与 graph-based 系统的全程序优化能力统一起来。其核心贡献是将动态 DL 依赖的时间结构显式化，从而支持 vectorization、tiling、fusion 和自动内存管理的全流程编译优化。在 LLM 解码和 RL 训练上验证了显著的性能收益（最高 54× 加速，16× 内存节省）。主要局限在于单 GPU、不支持 FlashAttention 和动态终止、编译耗时约 18s，距离生产级 LLM 推理系统仍有差距，但作为研究原型展示了符号化动态编译的巨大潜力。
