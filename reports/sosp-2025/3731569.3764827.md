# KNighter: Transforming Static Analysis with LLM-Synthesized Checkers

## 论文基本信息
- **标题**: KNighter: Transforming Static Analysis with LLM-Synthesized Checkers
- **作者**: Chenyuan Yang, Zijie Zhao, Zichen Xie (ZJU), Haoyu Li (SJTU), Lingming Zhang (UIUC)
- **会议**: SOSP 2025
- **Session**: Bugs
- **PDF**: 3731569.3764827.pdf

## 研究背景

静态分析是检测操作系统内核等关键系统代码缺陷的重要技术。相比动态测试（如 fuzzing），静态分析可以在不执行程序的情况下覆盖所有可能的执行路径，包括那些在实际运行中很少触发的边界情况。然而，传统静态分析工具（如 Clang Static Analyzer, Smatch）依赖预定义的、基于规则的检查，这些规则需要大量领域专业知识才能开发，且通常局限于特定的 bug 类型，难以扩展到多样化的缺陷模式。

近年来，大语言模型（LLM）在代码分析和 bug 检测方面展现出巨大潜力。然而，直接使用 LLM 扫描大型代码库（如 Linux 内核）面临两个核心挑战：计算成本极高（需要处理数百万行代码），以及上下文窗口长度限制（无法将整个代码库放入提示中）。这使得直接 LLM 扫描在实践中不可行。

KNighter 提出了一个优雅的解决方案：不使用 LLM 直接扫描代码，而是利用 LLM 从历史 patch 中学习 bug 模式，并自动合成专门的静态分析 checker。这些 checker 是轻量级的、可复用的，可以在整个代码库上高效运行，兼具 LLM 的智能和传统静态分析的可扩展性。

## 要解决的问题

1. 如何让 LLM 能够扩展到分析大规模代码库（如 Linux 内核的数千万行代码）
2. 如何自动合成正确的、能够区分 buggy 代码和修复后代码的静态分析 checker
3. 如何降低合成的 checker 的误报率，使其在实际部署中有用
4. 如何验证 LLM 合成的 checker 的语义正确性

## 核心贡献

- **首个 LLM 合成静态分析 checker 的全自动化流水线**：通过多阶段合成管道（bug pattern 分析、检测计划、checker 实现、验证）自动从 patch 生成 Clang Static Analyzer checker
- **自动化的 checker 精炼流程**：通过 bug triage agent 识别误报，并迭代精炼 checker 逻辑，将误报率从约 65% 降至约 32%
- **发现 92 个新漏洞**：在 Linux 内核中发现平均潜伏期 4.3 年的 92 个新 bug，其中 77 个已被开发者确认，57 个已修复，30 个已分配 CVE
- **与现有工具互补**：检测到的 bug 与专家编写的 Smatch 等工具正交，证明了 LLM 从 patch 中学习的独特价值

## 主要研究方法

### 多阶段合成管道

1. **Bug Pattern Analysis**：分析 patch 的 diff 和 commit message，识别 bug 的根本原因（如 "devm_kzalloc 的返回值未检查"）
2. **Detection Plan Synthesis**：基于识别出的 bug pattern，生成结构化的实现计划
3. **Analyzer Implementation**：使用预定义的 Clang Static Analyzer checker 模板，通过 LLM 生成 checker 代码
4. **Checker Repair**：自动修复编译错误（使用编译器错误反馈进行自动调试）
5. **Validation**：在 buggy 代码（patch 前）和 patched 代码上验证 checker，确认识别结果正确

### Bug Triage Agent + Checker Refinement

- 使用 LLM 作为 triage agent，对 checker 生成的报告进行分类（True Positive / False Positive）
- 对于误报案例，专门的 refinement agent 分析原因并调整 checker 逻辑
- 精炼后的 checker 需要满足：(1) 不再对之前的误报案例报警；(2) 仍然能够正确检测原始漏洞

### Few-shot 示例工程

为 LLM 提供了三个手工精心设计的 end-to-end 示例 patch（涵盖 Null-Pointer-Dereference、Use-Before-Initialization、Double-Free 三种类型），共花费约 40 person-hours，这是一次性工程投入。

## 主要实验结果

**Checker 合成质量**（61 个 patch 的评估集）：
- 61% (37/61) 的 patch 生成了 valid checker
- 其中 refined checker 的误报率为约 32.2% (29/90)
- 手工分析 29 个误报，发现三个主要原因：不准确的 bug pattern（5 例）、过于宽泛的 pattern matching（6 例）、触发条件管理错误（18 例）

**Bug 发现能力**：
- 39 个 valid checker 共发现 92 个新 bug（平均每个 checker 2.4 个）
- Bug 类型分布：Null-Pointer-Dereference 最多（36 个），其次是 Integer-Overflow、Buffer-Overflow、Memory-Leak、Use-After-Free 等
- Bug 存活时间：平均 4.3 年，26 个 bug 超过 5 年才被发现
- 影响子系统：drivers（67 个）、sound（10 个）、net（7 个）等

**与现有工具比较**：
- Smatch 在整个内核上运行未检测到 KNighter 发现的任何 true positive bug
- 这证明了 KNighter 学习到的领域知识与现有工具正交

**消融实验**（20 个 sampled patch）：
- 多阶段合成 vs 单阶段：12 vs 8 个 valid checker
- 不同 LLM 比较：O3-mini (12)、GPT-4o (11)、DeepSeek-R1 (11)、Gemini-2-flash (4)

## 潜在问题 / 局限性

1. **适用范围有限**：对高度复杂的 bug 模式（如 Use-After-Free、并发问题）合成困难，因为这些需要状态机推理和多线程代码分析能力——这是当前 LLM 的短板。实验显示 buffer-overflow 和 use-after-free 的成功率最低。

2. **初始工程投入**：需要手工设计 3 个 few-shot 示例（约 40 person-hours），且这些示例针对的是 Clang Static Analyzer 的具体 API 和模式。如何泛化到其他分析框架尚不清楚。

3. **RAG 消融实验的负面结果**：使用 RAG（检索历史 patch）反而降低了合成质量（valid checkers 从 12 降至 8），这令人意外。可能是因为 RAG 检索到的 patch 分散了 LLM 的注意力，降低了提示的质量。

4. **泛化能力存疑**：实验主要集中在 Linux kernel 的特定驱动子系统（drivers 占 67/92）。对于内核其他子系统（如文件系统、网络协议栈）或非内核代码库的泛化效果未经验证。

5. **与 Seal 的比较缺失**：论文提到 Seal 是相关的基于 patch 学习规范的工作，但因为依赖商业工具而未能比较。这使得 KNighter 在同类工作中的定位不够清晰。

6. **CVE 数据的可验证性**：声称 30 个 CVE，但论文未提供具体的 CVE 编号来验证。这些 bug 是否都被分配了 CVE，或者只是 "assigned CVE numbers" 需要进一步确认。

7. **手动审查的工作量**：92 个 bug 中，手工验证每个疑似 bug 报告的工作量未报告。Triage agent 的准确率虽然足够，但假阳性仍占约 32%，在大规模部署时仍需人工介入。

## 未来工作

1. **处理复杂 bug 模式**：开发自动将复杂 bug 报告抽象为形式化状态机表示的能力，从而合成精确的、感知状态的 checker
2. **扩展到其他代码库**：将方法泛化到其他大规模系统代码（如 Android kernel、FreeBSD）
3. **自动化 few-shot 示例生成**：减少手工工程投入，让框架能够自动从代码库中发现和选择有用的示例
4. **集成 RAG 的改进方案**：重新设计 RAG 策略，避免引入的噪声

## 个人评注

KNighter 是一篇极具创新性的工作，它解决了静态分析领域长期存在的一个矛盾：传统工具依赖手工编写的规则，难以扩展；LLM 虽然智能但直接用于大规模代码扫描成本高昂。KNighter 的核心洞察——"用 LLM 合成专门的静态分析工具"而非"用 LLM 做静态分析"——非常优雅地化解了这个矛盾。

然而，这项工作也暴露出当前 LLM 的几个关键局限：难以处理复杂的并发和状态机类 bug、对特定框架 API（如 Clang Static Analyzer）的准确使用存在困难。这提示我们，在可预见的未来，"LLM 辅助"而非"LLM 替代"仍是系统软件开发的主流范式。

最令人印象深刻的是实际 bug 发现的效果。92 个新 bug、平均 4.3 年潜伏期、77 个确认——这些数字证明了方法在真实世界中的有效性。尤其是与 Smatch 的对比，揭示了基于 patch 学习的独特价值：专家工具依赖的是预定义的领域知识，而 KNighter 能够从历史修复中自动提取这些知识。这可能代表了静态分析工具开发的一种新方向。
