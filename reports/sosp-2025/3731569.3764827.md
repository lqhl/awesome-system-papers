# KNighter: Transforming Static Analysis with LLM-Synthesized Checkers

**作者**：Chenyuan Yang（UIUC）、Zijie Zhao（UIUC）、Zichen Xie（浙江大学）、Haoyu Li（上海交通大学）、Lingming Zhang（UIUC）
**会议**：SOSP 2025（ACM SIGOPS 31st Symposium on Operating Systems Principles，2025年10月，首尔）
**DOI**：https://doi.org/10.1145/3731569.3764827
**源文件**：[3731569.3764827.pdf](../../papers/sosp-2025/3731569.3764827.pdf)

---

## 一、背景

操作系统内核的可靠性直接决定上层软件的安全性。Linux 内核代码规模超过 3000 万行，且持续高速演进，长期以来吸引了大量漏洞检测研究。静态分析（static analysis）因其无需实际执行代码即可覆盖所有潜在路径而成为内核安全审计的核心手段，尤其适用于硬件相关驱动、错误路径等难以动态触发的场景。

近年来，LLM 在代码理解、漏洞分析等任务上展现出强大能力，令研究者开始探索将其用于静态分析。然而，将 LLM 直接应用于大规模代码库面临两大天然障碍：上下文窗口限制（无法一次性加载整个内核）和高昂的推理代价（全量扫描成本可能高达数百美元）。

---

## 二、要解决的问题

**传统静态分析的局限**：现有工具（如 Smatch、CRIX、Goshawk 等）依赖人工预定义的规则或形式化模型，开发和维护成本极高，且只能覆盖有限的 bug 类型。面对不断涌现的新漏洞模式，人工编写 checker 的速度远跟不上内核演进速度。

**LLM 直接扫描不可行**：直接用 LLM 扫描 Linux 内核代价高昂、不可扩展。以 `devm_kzalloc` 为例，该函数在内核 5400 余个文件中出现超过 7000 次；若 LLM 每次都要加载相关上下文重复分析，代价是不可接受的。

**核心矛盾**：如何同时做到覆盖广泛 bug 类型（传统方法的弱点）和高效处理百万级代码库（LLM 直接扫描的弱点）？

---

## 三、核心设计

**关键洞见**：与其用 LLM 直接分析代码，不如用 LLM 从历史 patch 中学习 bug 模式，自动生成可复用的静态分析 checker，再以传统方式高效扫描整个代码库。

**整体架构**：KNighter 以 bug-fix patch commit 为输入，输出对应的 Clang Static Analyzer（CSA）checker，分两个阶段运行：

```
Checker Synthesis Phase（checker 合成）：
  1. Bug Pattern Analysis  - LLM 分析 patch 提取 bug 模式
  2. Plan Synthesis        - LLM 生成检测计划（状态管理、回调函数设计）
  3. Checker Implementation - LLM 生成 CSA C++ checker 代码
  4. Checker Validation    - 编译 + 验证：能否区分 buggy/patched 代码

Checker Refinement Phase（checker 精化）：
  1. 用 checker 扫描整个内核代码库
  2. Bug Triage Agent      - LLM 对 bug 报告逐一分类（真阳/假阳）
  3. Checker Refinement    - 针对假阳性迭代改进 checker（最多 3 轮）
```

**Plausible Checker 定义**：满足以下任一条件的 valid checker —— 报告数量 ≤ 20，或采样报告中假阳率 ≤ 1/5。

**对 hallucination 的对策**：每个合成的 checker 须通过 patch-grounded 验证（正确识别 buggy 代码、不误判 patched 代码），通不过则进入最多 10 次的迭代修复循环（语法错误由 repair agent 自动修正）。

---

## 四、实现细节

**目标框架**：Clang Static Analyzer（CSA），基于 path-sensitive symbolic execution，通过 Exploded Graph 追踪程序状态。Checker 以事件驱动方式实现，注册 `checkPostCall`、`checkBranchCondition`、`checkLocation`、`checkBind` 等回调，并可通过自定义 ProgramState map 维护跨路径状态。

**LLM 后端**：默认使用 OpenAI o3-mini；同时支持 GPT-4o、DeepSeek-R1、Gemini-2-flash（对比评估）。

**合成算法要点**：
- **三段式分解**：先分析 bug 模式（文字描述），再生成检测计划（伪代码级别），最后实现完整 CSA checker（C++ 代码）
- **Few-shot 示例**：使用固定的人工精选示例，而非 RAG 动态检索（后者代价翻倍但效果相当）
- **编译验证 + 自动修复**：编译失败时用错误信息驱动 LLM 修复，语义失败（无法区分 buggy/patched）则重新尝试

**规模**：评估集包含 61 条人工筛选的 bug-fix commit（覆盖 10 种 bug 类型），另自动收集 100 条 Null-Pointer-Dereference 相关 commit。实验平台：64 核 / 256 GB RAM / 4×A6000 GPU，Ubuntu 20.04。代码扫描使用 Linux v6.9–v6.15，配置 `allyesconfig`，并行度 `-j32`。

## 五、实验结果

### RQ1：Checker 合成质量

| 指标 | 数值 |
|---|---|
| 评估 commit 数 | 61 |
| 生成 valid checker 数 | 39（63.9%） |
| Plausible checker 数（直接） | 26 |
| 经 refinement 后 plausible 数 | 37（总计） |
| Refinement 成功率 | 84.6%（13 中 11 个） |
| 平均 checker 代码行数 | 125.7 行 |
| 平均合成尝试次数（成功 commit） | 2.4 次（最多 8 次） |
| 合成总耗时 | 15.9 小时 |
| 合成每 commit 成本（o3-mini） | ~$0.24 |

Checker 失败原因分布：59% 为实现错误（编译器内联导致拦截失败）、32% 为计划不准确、9% 为 bug 模式识别不准确。75.8% 的失败表现为语义错误（无法区分 buggy/patched）。

**合成 checker 能力**：37 个 path-sensitive，13 个 region-sensitive，16 个使用高级状态追踪；只有 2 个仅依赖 AST 遍历，说明 KNighter 能合成复杂分析逻辑。

**Bug Triage Agent**：在 79 份采样报告上，TP=7，FP=22，TN=50，FN=0。假阴率为零是关键指标，表明不会漏掉真实 bug。

### RQ2：真实 Bug 发现

| 指标 | 数量 |
|---|---|
| 新发现 Linux 内核 bug | 92 |
| 开发者已确认 | 77 |
| 已修复 | 57 |
| 分配 CVE 编号 | 30 |
| 平均 bug 存活时间 | 4.3 年 |
| 存活超过 5 年的 bug | 26 个 |

Bug 分布：67 个在 drivers 子系统，10 个在 sound，7 个在 net；类型以 Null-Pointer-Dereference 最多。

### RQ3：与 Smatch 的正交性

Smatch 在整个内核上报告 1970 个错误 + 2870 个警告，但**未检测到 KNighter 发现的任何一个真阳性 bug**，两者检测的 bug 类完全不重叠。

### RQ4：消融实验

| 配置 | Valid Checkers | Syntax Errors | Semantics Errors |
|---|---|---|---|
| Default（三阶段，fixed few-shot，o3-mini） | 12 | 28 | 75 |
| 单阶段（无 pattern/plan） | 8 | 52 | 75 |
| RAG few-shot | 12 | 37 | 62 |
| GPT-4o | 11 | 31 | 76 |
| DeepSeek-R1 | 11 | 29 | 66 |
| Gemini-2-flash | 4 | 130 | 44 |

注：表中数字为 20 commit 采样子集上的结果。

## 六、批判性分析

**评估规模偏小**：消融实验仅用了 20 个 commit（从 61 中随机采样），且每种 bug 类型只取 2 个样本，统计功效极为有限。12 vs 8 这样的差异在 20 个样本上能说明的置信度存疑。

**Plausible 阈值的主观性**：Plausible checker 定义为"报告数 ≤ 20 或采样假阳率 ≤ 1/5"。这两个门槛是人为设定的，论文未充分论证其合理性，也未分析阈值选择对最终 bug 发现数量的敏感性。

**Bug triage agent 的假阳问题被轻描淡写**：triage agent 在 79 条报告上有 22 个假阳（57% 的正例预测是错的），但论文着重宣传"零假阴"。这意味着用 KNighter 找到的"bug"中有相当比例需要人工复核，实际工作量未被充分讨论。

**Majority voting 效果存疑**：论文尝试 5-way self-consistency 来改进 triage，结果与 single-sample 相当（t=3 时 7 TP / 24 FP；t=4 时 7 TP / 20 FP vs 原 22 FP），作者对此给出的解释（"TP 预测已高置信，FP 预测随机"）仅是推测，缺乏深入分析。

**对高复杂度 bug 的限制被合理化**：论文承认对 Use-After-Free、concurrency bug 效果差，但将其归因于"LLM 的当前局限性"而非架构缺陷。事实上，这两类 bug 在内核安全中占据极高比例，KNighter 对它们几乎无能为力这一点削弱了其实际覆盖范围。

**Bug 生命周期的统计代表性**：92 个 bug 的平均存活 4.3 年是个引人注目的数字，但这批 bug 来源于 KNighter 的 checker 本身就偏向检测模式明确的 bug 类型（如 NPD），可能系统性地高估了"难发现"漏洞的占比。

**与其他 LLM-based 工具的对比缺失**：论文仅与 Smatch 对比，缺少与同期 LLM-based 静态分析工具（如 Seal、MoCQ 等）的定量对比，正交性论断的说服力因此受限。

## 七、AI Infra / MLSys 视角

**对 LLM Agent 工程的借鉴**：KNighter 是一个"LLM 合成工具而非直接推理"范式的典型案例。其核心洞见——**让 LLM 生成可复用的确定性组件而不是每次端到端推理**——对 AI Infra 领域有直接参考价值。例如，可以将这种思路用于：
- 自动生成性能优化规则（kernel fusion 规则、内存布局策略）
- 从历史调优经验中合成可重用的编译 pass 或算子变换

**LLM 推理代价的系统性规避**：KNighter 以一次性 $0.24/commit 的 LLM 调用代价换取了可复用的静态分析器，大幅摊薄了大规模扫描的边际成本。类似的"一次合成、多次复用"模式在 AI 系统中有广泛适用场景，如 profile-guided optimization、自动调参等。

**Multi-agent 架构设计经验**：三阶段合成（pattern → plan → implementation）+ 独立验证 agent + refinement loop 的组合给 LLM-based 代码生成系统提供了工程参考。特别是 patch-grounded 验证用于对抗 hallucination 的思路，可以推广到任何需要生成可验证代码的场景。

**值得跟进的方向**：
- 将类似框架应用于 GPU kernel 优化：从历史 PR 中学习性能 bug 模式，自动生成静态检测规则（如检测 warp divergence、bank conflict 等模式）
- 探索"checker 合成"在 LLM serving 系统（如 vLLM、SGLang）中的应用：从 issue tracker 中的性能回归 patch 合成 profiling checker

---

## 八、总结

KNighter 提出了一种新范式：利用 LLM 从历史 bug-fix patch 自动合成 CSA 静态分析 checker，而非直接用 LLM 扫描代码库。通过三阶段合成 + patch 验证 + triage 精化的 pipeline，KNighter 在 Linux 内核中发现了 92 个新漏洞（77 确认、57 修复、30 CVE），平均漏洞存活 4.3 年，且检测范围与现有工具 Smatch 完全正交。其主要局限在于对 Use-After-Free 和并发 bug 支持薄弱，以及评估规模偏小导致部分结论说服力不足；但"合成工具而非直接推理"的范式对系统安全和 AI Infra 领域均有重要启示价值。
