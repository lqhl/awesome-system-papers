# KNighter: Transforming Static Analysis with LLM-Synthesized Checkers

**作者**：Chenyuan Yang, Zijie Zhao, Zichen Xie (浙江大学), Haoyu Li (上海交通大学), Lingming Zhang — University of Illinois Urbana-Champaign

**链接**：https://doi.org/10.1145/3731569.3764827
**源文件**：[3731569.3764827.pdf](../../papers/sosp-2025/3731569.3764827.pdf)

---

## 一、背景

操作系统内核（如 Linux）的可靠性和安全性至关重要，而静态分析是检测内核缺陷的核心技术之一——它无需执行代码即可检查所有潜在的执行路径，包括硬件相关的驱动代码、罕见路径和难以复现的配置。然而，大规模系统的静态分析面临双重挑战：需要覆盖**多样的 bug 模式**，同时需要处理**庞大的代码量**（Linux 内核超过 3000 万行）。

传统静态分析器依赖人工预定义的规则和检查器，开发和维护成本高，且只能覆盖有限的 bug 类型。近年来 LLM 展现出从历史 patch 中学习 bug 模式的能力，但直接用 LLM 扫描大型代码库面临上下文窗口限制和高昂的计算成本（扫描一次可能花费数百美元），且 LLM 容易产生幻觉。

---

## 二、要解决的问题

1. **传统静态分析覆盖面有限**：现有的人工编写的 checker（如 Smatch）依赖预定义规则，缺乏对内核特定语义的领域知识（如 `devm_kzalloc` 可能返回 NULL），无法自动适应新出现的 bug 模式。
2. **直接用 LLM 分析不可扩展**：LLM 的上下文窗口无法容纳整个代码库，重复调用成本极高（例如 `devm_kzalloc` 在 5400+ 个文件中出现 7000+ 次），且幻觉问题严重。
3. **Checker 编写复杂度高**：即使是专家，编写 Clang Static Analyzer (CSA) 的 checker 也是困难的工程任务，涉及路径敏感分析、状态管理、回调函数等复杂机制。

---

## 三、洞察与设计

**关键洞察**：与其让 LLM 直接扫描代码来发现 bug，不如让 LLM 从历史 bug-fix patch 中学习 bug 模式，自动合成静态分析 checker——这样可以同时利用 LLM 的 bug 模式学习能力和传统静态分析的可扩展性。Checker 一旦合成就主要消耗 CPU 资源（而非反复调用 LLM），且可以随系统自然演化。

基于这个洞察，KNighter 的设计分为两个阶段：

### Checker 合成（多阶段 pipeline）
1. **Bug Pattern Analysis**：LLM agent 分析输入的 patch commit（包括 diff 和完整函数上下文），提取针对性的 bug 模式。倾向于提取更具体、可操作的模式（而非过于宽泛的模式），以便 LLM 能正确实现。
2. **Plan Synthesis**：基于识别出的 bug 模式，LLM 生成高层级的 checker 实现计划（包含需要的回调函数、状态管理策略等），使推理过程透明可追踪。
3. **Analyzer Implementation + Syntax Repair**：LLM 根据预定义的 CSA checker 模板和 utility 函数库实现 checker。编译错误由专门的 repair agent 自动修复（最多 5 次尝试）。
4. **Validation**：通过差分分析验证 checker——必须在 buggy 版本上报告 bug，在 patched 版本上减少/消除报告。

### Checker 精炼
- 将 valid checker 部署到整个代码库扫描。
- **Bug Triage Agent** 对每份 bug report 进行分类（TP/FP），判断是否与目标 bug 模式匹配。
- **Refinement Agent** 根据识别出的 false positive 迭代修改 checker 逻辑（最多 3 轮），且修改后需再次通过 validation。

---

## 四、实现细节

- **目标框架**：基于 Clang Static Analyzer (CSA)，利用其路径敏感的符号执行引擎和 checker 模板机制。
- **输入数据**：从 Linux 内核收集了 10 类 bug（NPD、Integer-Overflow、OOB、Buffer-Overflow、Memory-Leak、UAF、Double-Free、UBI、Concurrency、Misuse）共 61 个 patch commit。
- **Few-shot 示例**：3 个手工编写的端到端示例（NPD、UBI、Double-Free），耗时约 40 人时（一次性投入）。
- **Utility 函数**：9 个封装了 CSA 底层操作的工具函数（如 `getMemRegionFromExpr`），简化 LLM 的实现任务。
- **LLM 后端**：默认使用 O3-mini。
- **Validation 标准**：checker 须满足 $N_{buggy} > N_{patched}$ 且 $N_{patched} < T_{valid}$（默认 $T_{valid}=50$）。
- **Plausible 标准**：total reports < 20，或抽样 5 个 report 中 FP ≤ 1。
- **Refinement 限制**：每次 scan 限时 1 小时或最多 100 个 warning；采样 5 个 report 供 triage agent 判断。
- **硬件**：64 核 CPU、256 GB RAM、4 × NVIDIA A6000，Ubuntu 20.04。

## 五、实验结果

### Checker 合成（61 commits）

| 指标 | 数值 |
|------|------|
| Valid checker 数量 | 39/61 (63.9%) |
| 合成后直接 plausible | 26/39 |
| 经 refinement 后 plausible | 11/13 (84.6%) |
| 最终 plausible 总数 | 37/39 |
| 平均 checker 代码行数 | 125.7 LOC |
| 路径敏感 checker | 37/39 |
| 区域敏感 checker | 13/39 |
| 高级状态追踪 | 16/39 |
| 平均合成尝试次数（valid checkers） | 2.4 |
| 总合成耗时 | 15.9 小时 |
| 每 commit 成本 | ~$0.24 (O3-mini) |

### Bug 检测

| 指标 | 数值 |
|------|------|
| 新发现 bug 总数 | 92 |
| 开发者确认 | 77 |
| 已修复 | 57 |
| 待审核 | 15 |
| 获分配 CVE | 30 |
| 平均 bug 潜伏时间 | 4.3 年 |
| False positive rate（triage 后） | 32.2% |

- Bug 分布：67 个在 `drivers/` 子系统，10 个在 `sound/`，7 个在 `net/`。
- NPD 是最多的 bug 类型（54 个），其次是 Integer-Overflow（16 个）。
- 26 个 bug 潜伏超过 5 年。

### 与 Smatch 的正交性
Smatch 在整个内核上报告了 1970 个错误和 2870 个警告，但**未能检测到 KNighter 发现的任何 true positive bug**，说明两者检测的 bug 类别互补。

### Ablation 结果（20 commits 子集）

| 变体 | Valid checkers |
|------|---------------|
| Default (O3-mini + multi-stage) | 12 |
| 无 multi-stage（直接合成） | 8 |
| RAG 替代固定 few-shot | 12（但 token 成本 2 倍） |
| GPT-4o | 11 |
| DeepSeek-R1 | 11 |
| Gemini-2-flash | 4（syntax error 130 次 vs 28 次） |

## 六、批判性分析

1. **评估集规模较小且选择有偏**：仅 61 个手工筛选的 patch commits，每类只有 5-8 个，且需要两位作者共同确认。这种精心筛选可能高估了方法的通用性——如果输入的 patch 质量或结构不够理想（如 commit message 不清晰、diff 复杂度高），成功率可能大幅下降。

2. **Few-shot 示例的 40 人时投入被低估**：论文称这是"一次性投入"，但实际上这 3 个精心编写的示例是整个系统效果的关键基础。如果要迁移到其他静态分析框架（如 CodeQL、Semgrep），这个投入需要重新进行，迁移成本未被充分讨论。

3. **False positive rate 的计算方式值得质疑**：32.2% 的 FP 率是在 triage agent 过滤后的 90 个 "bug" label 中计算的。但 triage agent 本身有 22 个 FP（将 non-bug 误标为 bug），0 个 FN。这意味着 triage agent 只是一个宽松的过滤器——实际上是在用大量人工审核来弥补自动化的不足。如果考虑端到端的工作量，仍需人工审核大量报告。

4. **92 个 bug 的来源混杂**：包括初始 61 个 commit 生成的 checker 和额外 100 个自动收集的 NPD commit。后者贡献了 30 个 bug，但这 100 个 commit 的 checker 合成质量和 plausible rate 未单独报告。

5. **Refinement pipeline 的采样策略脆弱**：仅采样 5 个 report 供 triage agent 判断，这个采样量是否能代表整体 FP 分布未被验证。对于产生大量报告的 checker，5 个样本可能严重不足。

6. **与 Smatch 的对比不够公平**：Smatch 是通用工具且有不同的设计目标，KNighter 是针对特定 patch 定制的 checker。更有意义的对比应该是在相同 bug 类型上对比专门针对该类型的工具（如 UBITect 对 UBI、CRed 对 UAF）。

7. **可泛化性声明缺乏实证**：论文声称方法可扩展到其他项目（如 Chromium）和框架（如 CodeQL），但未提供任何实验证据。不同项目的 patch 结构、coding convention 和静态分析框架的 API 差异可能导致方法效果大幅下降。

## 七、AI Infra / MLSys 视角

1. **LLM 作为"元工具"生成器的范式**：KNighter 展示了一种重要的 LLM 使用范式——不是让 LLM 直接完成任务，而是让 LLM 生成可复用的自动化工具。这种范式完全可以迁移到 AI Infra：例如让 LLM 从历史 performance regression 中合成 profiling checker，或从 training failure 日志中合成诊断规则。

2. **Multi-stage synthesis + validation 的方法论**：将复杂生成任务分解为 pattern analysis → plan synthesis → implementation → validation 的 pipeline 设计，适用于 AI 系统中 LLM 生成复杂配置的场景（如自动生成分布式训练的 parallelism strategy checker、内存优化的 correctness checker）。

3. **可操作的 future work**：
   - **AI 框架的 bug checker 合成**：PyTorch/TensorFlow 的 bug-fix commit 同样丰富，可以用类似方法为 AI 框架合成静态分析 checker，检测 shape mismatch、gradient computation error、memory leak 等。
   - **Training/serving pipeline 的 semantic checker**：从生产环境的 incident report 中学习 failure pattern，合成自动化的配置校验和运行时检查。
   - **Model correctness checker**：从 model debugging 经验中合成验证规则，检测常见的 numerical instability pattern。

4. **最有价值的切入点**：将 KNighter 的方法应用于 CUDA/HIP 内核代码的静态分析——GPU 代码的 bug 模式（race condition、shared memory misuse、launch configuration error）与 Linux 内核有类似的复杂性，且 NVIDIA 和 AMD 都有大量历史 bug-fix patch 可供学习。

---

## 八、总结

KNighter 提出了一种新颖的范式：让 LLM 从历史 bug-fix patch 中自动合成静态分析 checker，而非直接用 LLM 扫描代码。通过多阶段合成 pipeline（pattern analysis → plan → implementation → validation）和基于 triage agent 的迭代精炼机制，KNighter 在 Linux 内核上实现了 63.9% 的 valid checker 率，发现了 92 个新 bug（77 个已确认，30 个 CVE），平均潜伏 4.3 年，且与现有人工编写的 Smatch checker 完全互补。主要局限在于对复杂 bug 模式（UAF、concurrency）的处理能力有限，以及向其他框架和项目的可迁移性尚未得到实验验证。
