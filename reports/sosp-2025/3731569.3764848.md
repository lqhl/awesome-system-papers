# Mycroft: Tracing Dependencies in Collective Communication Towards Reliable LLM Training

**作者**：Yangtao Deng（香港中文大学）、Lei Zhang（ByteDance）、Qinlong Wang（ByteDance）、Xiaoyun Zhi（ByteDance）、Xinlei Zhang（ByteDance）、Zhuo Jiang（ByteDance）、Haohan Xu（ByteDance）、Lei Wang（ByteDance）、Zuquan Song（ByteDance Seed）、Gaohong Liu（ByteDance Seed）、Yang Bai（ByteDance）、Shuguang Wang（ByteDance Seed）、Wencong Xiao（ByteDance Seed）、Jianxi Ye（ByteDance）、Minlan Yu（Harvard University）、Hong Xu（香港中文大学）

## 一、背景

大规模 LLM 训练依赖数万块 GPU，通过 DP、PP、TP 等混合并行策略互联，集合通信（Collective Communication）在其中扮演核心角色。RDMA 网络和 400 Gbps NIC 保证了高吞吐低延迟的数据传输，但庞大的集群规模也带来了频繁的故障：Microsoft 报告每 45 分钟发生一次故障，Meta 在 LLaMA 3 预训练的 54 天内出现 419 次中断，ByteDance 每天至少遭遇一次故障。

现有的 Collective Communication Libraries（CCLs，如 NCCL）作为"黑盒"运行，缺乏对内部状态的可观测性，使得故障诊断困难且耗时，最终导致大量 GPU 算力和人力的浪费。如何在运行时快速准确地定位集合通信层的故障根因，是当前 LLM 训练可靠性研究的核心挑战。

---

## 二、要解决的问题

### 1. CCL 的不透明性导致根因分析困难

现有工具分为三类：

- **Op 级别**（Kineto、Chakra、GREYHOUND）：只记录集合操作的起止时间戳，不暴露操作内部状态；当 CollOp 卡住时无法提供有效诊断信息。
- **Kernel 级别**（Nsight Systems、NPKit、NVRx、XPUTIMER）：基于 CUDA kernel trace，粒度过细、开销极高（NPKit 在实验中导致总线带宽下降 2/3；Nsight backtrace 使迭代时间从 1116ms 膨胀至 1900ms）；且通常只能在单机使用。
- **RDMA 级别**（Aegis）：记录 RDMA 层统计信息，但无法跨 GPU 精确追踪异常传播路径。

### 2. 故障传播快、定位难

集合通信中一块 GPU 的异常会在数百毫秒内通过 inter-node dependency 级联至整个训练集群，所有 rank 的症状几乎同时出现，无法从表象区分根因节点和受影响节点。

### 3. 分布式分析开销大

规模达千台机器的训练任务每天产生 TB 级 trace 数据，现有工具难以在秒级内完成跨机器的关联分析和根因定位。

---

## 三、核心设计

Mycroft 的核心思想是在 CCL 层（而非 Op 层或 Kernel 层）引入轻量级分布式追踪，通过捕获集合通信的**控制流和数据依赖**，实现实时灰色故障检测与根因分析。

### Coll 级别追踪的两个维度

- **Flow 级别**：以每条网络流（QP / NCCL channel）为粒度追踪，能发现单条流的拥塞、抖动或故障，而这在 Op 级别的聚合视图中完全不可见。
- **Chunk 级别**：不记录每个 chunk 的起止时间戳（开销太大），而是周期性地聚合关键系统状态：`GPU_ready`（GPU 已准备好的 chunk 数）、`RDMA_transmitted`（已提交 RDMA 发送的 chunk 数）、`RDMA_done`（收到 CQE 完成确认的 chunk 数）。三者的差值可精确揭示瓶颈所在层次（GPU、RDMA 发送、RDMA 接收侧）。

### 触发机制（Trigger）

- 以 sampled rank（每 DP group 至少采样 1 个，全局上限 10 个）作为监测点，而非全量监测，利用"故障快速传播"特性：只要异常传到任意采样节点即可触发。
- 灰色故障触发：采样 rank 持续有 `real-time state log` 但无 `completion log`（CollOp 卡住）。
- 性能问题触发：吞吐下降 50% 或 CollOp 间隔翻倍。

### 依赖驱动的根因分析（Dependency-Driven Root Cause Analysis）

1. 先定位受影响的 Coll group（最先卡住或最滞后的 group）。
2. 在 group 内比较各 rank 的 chunk 状态（`GPU_ready`、`RDMA_transmitted`、`RDMA_done`），找到 MinOp rank 或 MinData rank 作为嫌疑根因。
3. 根据状态组合查 RootCause Table，判断本地原因（GPU 问题、RDMA 问题）还是远端原因（接收方未就绪、接收方失败）。
4. 时间维度：对比 rank 启动/完成时间，识别持续滞后的节点。

### 与其他工具集成

Mycroft 提供被动触发接口，与 py-spy（Python 调用栈 dump）、PyTorch Flight Recorder（CollOp 同步状态）协同工作，共同覆盖数据加载卡死、框架配置死锁等 CCL 层以外的故障。

## 四、实现细节

- **NCCL 插桩**：在 NCCL 2.21.5 的 proxy 线程关键路径上添加不到 10 个 tracepoint，约 1100 行 C++ 代码。
- **无锁共享内存缓冲区**：预分配 512MB 循环缓冲区于宿主机共享内存，tracepoint 以异步方式写入（与 NCCL 内部流对齐），单独的只读 agent 进程读取并通过 Kafka 上传至云数据库，避免锁竞争和背压。
- **后端分析**：约 4000 行 Python 代码运行于单台服务器（<64 CPU 核，<100 GB 内存），作为 always-on 系统持续监控。
- **数据量**：每台机器每次迭代约生成 46.8 KB trace 数据；在 1200 台机器规模下每台约 186 KB/iteration（~3 秒），远低于 Nsight（15 MB/iteration）和 XPUTIMER（0.78 MB/GPU）。
- **生产部署**：2024 年 10 月在 ByteDance 上线，覆盖超过 128 GPU 的所有 LLM 训练任务，同时最多 20 个并发任务。

## 五、实验结果

### 测试环境

- 32 块 NVIDIA A100-80GB-SXM4 跨 4 台机器；intra-host 通过 NVLink/PCIe 互联，inter-host 每机 4 块 ConnectX-6 RNIC
- 工作负载：GPT + Megatron-LM（TP=8, PP=2, DP=2）；CUDA 12.2 + Torch 2.1.0

### 故障注入实验（7 种故障类型）

| 故障类型 | 根因定位方式 | 结果 |
|---|---|---|
| NIC shutdown | 最先停止产生 log 的 rank | 成功定位 |
| NIC 带宽限制 | 最早开始变慢的 rank（RDMA_transmitted > RDMA_done） | 成功定位 |
| PCIe 降速 | 最后完成的 rank（计算慢） | 成功定位 |
| GPU 功率限制 | 最后完成的 rank | 成功定位 |
| 后台计算干扰 | 比对完成时间（影响全部 8 个 rank） | 成功定位 |
| 后台网络流量 | GPU_ready == RDMA_transmitted > RDMA_done，确认网络为瓶颈 | 成功定位 |
| NCCL 延迟注入 | 最晚开始发送的 rank | 成功定位 |

所有故障从注入到根因输出的端到端时延均不超过 13 秒。

### 开销对比

| 工具 | NCCL Test 带宽 | GPT 迭代时间 | CPU 开销 | Trace 数据量 |
|---|---|---|---|---|
| Baseline | 100% | 1116 ms | 10.7% | — |
| **Mycroft** | ≈100% | 1119 ms（+0.3%）| 11.0% | 46.8 KB/iter/host |
| NVRx | ≈100% | 1124 ms | 11.5% | — |
| Nsight CUDA trace | ≈100% | 1125 ms | 11.2% | 15 MB/iter |
| Nsight backtrace | ≈100% | 1900 ms（+70%）| 16.3% | — |
| NPKit | ~33% 带宽 | — | — | — |

### 生产环境（2024 年 11-12 月）

- 检测 13221 次训练中断，**100% 检测率**（与已知异常任务交叉校验）
- 90% 的卡住故障在 **15 秒内**触发告警
- 60% 的根因分析在 **20 秒内**完成
- 已在 8000+ GPU 规模下验证有效，处理时延随规模增长主要来自数据库查询

## 六、批判性分析

### 1. "100% 检测率"的标注方式存疑

论文声称 100% 检测率，但立即承认"难以标注所有生产异常的根因"。这意味着 100% 是通过"与已知异常任务交叉校验"得到的，而非对全量故障的准确率。未知的漏报（false negative）和误报（false positive）率均未量化。这是典型的"仅报 best case"。

### 2. 触发阈值的任意性未充分讨论

触发规则（吞吐下降 50%、interval 翻倍、straggler 超前/滞后 1 秒）均为经验值，论文在 Section 9 中承认这是未来工作，但并未提供任何关于不同工作负载下阈值灵敏度的系统性分析。在 MoE 等通信模式本就不规则的场景中，这些启发式规则的适用性存疑。

### 3. 小规模测试床与实际场景的差距

故障注入实验仅在 32 GPU（4 台机器）上进行，而论文声称能支持数万 GPU。Table 5 的 CPU/内存数据也基于同样小规模环境。虽然 Figure 12 展示了生产中的扩展性曲线，但 8k GPU 以上缺乏实验数据，作者自己也承认 10k GPU 以上可能需要额外优化。

### 4. 与 Nsight 的对比存在不公平之处

论文将 Nsight backtrace 模式的 1900ms 迭代时间与 Mycroft 的 1119ms 相比，但 Nsight backtrace 开启了完整的调用栈追踪，是最重量级的模式。与 Nsight CUDA trace 模式（1125ms，开销与 Mycroft 相当）的差距实际上微乎其微，但论文的图表排版会给读者留下 Nsight 开销极大的错误印象。

### 5. 根因定位的实际精度被高估

论文说"60% 的案例在 20 秒内识别出根因 GPU"，但在 Section 7.4 提到 1253 次根因分析中，705 次（56%）只定位到单个可疑网络流（network flow），其余 44% 的情况需要进一步人工排查。论文对此几乎没有深入说明。

### 6. 不支持完整的端到端可见性

Mycroft 仅覆盖 CCL 层，无法感知应用层意图（如通信计算 overlap、框架级同步语义），因此对于计划内的通信延迟和真实异常存在混淆风险，需要 py-spy 和 Flight Recorder 辅助才能完成完整诊断。

## 七、AI Infra / MLSys 视角

### 核心 Insight 的迁移价值

**"故障传播即可观测性杠杆"**：论文的最大洞见不是技术本身，而是对 LLM 分布式训练的一个关键观察：CCL 层的异常会在数百毫秒内级联至全集群，因此只需采样少量节点（10 个 rank）即可以近似全局告警。这个"以局部采样替代全量监控"的思路对任何大规模分布式 AI 系统的可观测性设计都有参考价值。

### 对推理系统的借鉴

当前 LLM 推理系统（如 vLLM、Sarathi、DeepSeek Inference）在多机多卡场景下同样依赖 NCCL 进行 TP/PP 通信，但目前基本没有 Coll 级别的 runtime 诊断能力。Mycroft 的框架——轻量级 tracepoint + 周期性状态聚合 + 依赖驱动根因分析——可以直接移植到推理服务的可靠性保障中。

### 值得跟进的研究方向

1. **自适应阈值调整**：当前触发规则为静态经验值，对 MoE 等通信模式不规则的模型存在误报风险。研究基于历史 baseline 自动校准检测阈值的方法（类似异常检测中的 STL 分解 + 动态阈值）是一个可操作的研究问题。

2. **跨层根因归因**：Mycroft + py-spy + Flight Recorder 的组合仍依赖人工判断各工具输出，如何构建一个统一的因果图（causal graph）自动关联 CCL 层、框架层、应用层的证据，指向最终根因，是有价值的 future work。

3. **推理场景适配**：推理有独特挑战——请求批次动态变化、prefill/decode 阶段 CollOp 模式差异大、SLO 敏感——需要专门设计适用于 serving 场景的 Coll 级别 tracing 和异常检测框架。

4. **闭环自愈**：目前 Mycroft 只做诊断，输出的是"嫌疑 GPU 列表"。将诊断结果与自动化恢复（如隔离故障 GPU、触发 checkpoint + restart、热替换 rank）结合，实现闭环故障自愈，是下一步自然的工程方向。

---

## 八、总结

Mycroft 是 ByteDance 在生产环境中实际落地的 LLM 训练可靠性系统，通过在 NCCL 代理线程的关键路径上插入极少量 tracepoint，以 Flow 级别和 Chunk 级别的状态聚合代替昂贵的 kernel 级全量追踪，在保持 <1% 训练开销的前提下实现了秒级灰色故障检测和根因定位。其核心贡献在于将 CCL 的内部控制流和数据依赖显式化，并利用"故障快速传播"特性以极少采样节点实现集群级监控。主要局限是可观测性边界仅限于 CCL 层，触发启发式规则对复杂工作负载的泛化性有限，且大规模（>10k GPU）的工程可行性尚需进一步验证。
