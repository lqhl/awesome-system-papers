# Mycroft: Tracing Dependencies in Collective Communication Towards Reliable LLM Training

## 一、背景

大规模 LLM 训练依赖数万张 GPU 协同工作数天甚至数周，采用 Data Parallelism (DP)、Pipeline Parallelism (PP)、Tensor Parallelism (TP) 等混合并行策略。这些并行策略通过集合通信库（CCL，如 NCCL）在 RDMA 网络上进行大规模数据传输。

训练过程中频繁出现硬件和软件故障：Meta 在 LLaMa 3 预训练期间 54 天内经历了 419 次中断，Microsoft 报告平均每 45 分钟一次故障，ByteDance 集群中至少每天一次故障。这些异常导致大量 GPU 资源浪费和训练效率下降。

---

## 二、要解决的问题

1. **CCL 是黑盒**：当前集合通信库缺乏内部可观测性，当 CollOp（集合通信操作）卡住或变慢时，系统开发者和运维人员无法获取足够的内部状态信息来定位根因。

2. **异常传播隐蔽**：由于 CollOp 内部的数据依赖关系，一个 GPU 的异常会快速级联传播到整个通信组乃至整个集群，但从外部观察所有 rank 几乎同时卡住，难以区分根因和受影响节点。

3. **现有工具的不足**：
   - Op-level 工具（Kineto、Chakra、GREYHOUND）粒度太粗，无法暴露 CollOp 内部状态
   - Kernel-level 工具（Nsight、NPKit、NVRx、XPUTIMER）开销大（NPKit 导致总线带宽下降 2/3），缺乏分布式视角，且无法暴露网络层面的问题
   - RDMA-level 工具（Aegis）无法追踪 GPU 侧的异常传播

---

## 三、洞察与设计

**关键洞察**：集合通信操作内部存在精细的控制流和数据依赖关系（intra-node 的 GPU-CPU-NIC 协调、inter-node 的 chunk 级数据同步、computation-communication 的资源竞争），这些依赖关系决定了异常的传播路径。只需在 CCL 的关键路径上记录少量运行时状态（而非完整的 CUDA 执行时间线），就能重建全局状态机，从而快速定位根因。同时，由于异常在毫秒级别传播到整个集群，只需采样少数 rank 即可实现全覆盖的异常检测。

基于以上洞察，Mycroft 的设计包含三个核心组件：

1. **Coll-level 细粒度 tracing**：引入 Flow-level 和 Chunk-level 两层追踪粒度。Flow-level 追踪每条网络流（channel/QP），暴露单条流的异常；Chunk-level 追踪每个数据 chunk 在 GPU copy → RDMA transmit → RDMA done 各阶段的进度，通过聚合而非逐事件记录来降低开销。

2. **采样式主动触发机制**：每个 DP 组至少采样一个 rank（总共不超过 10 个），每 10 秒检测一次。利用异常快速传播的特性，从采样 rank 即可发现全集群异常。

3. **依赖驱动的根因分析**：构建短时间窗口内的全局分布式状态机，通过比较各 rank 的 CollOp 进度（谁最先停止、谁传输最少）和 chunk 状态（GPU_ready vs RDMA_transmitted vs RDMA_done）来逐步缩小根因范围。

## 四、实现细节

- **NCCL 插桩**：在 NCCL 2.21.5 中添加约 1100 行 C++ 代码，不到 10 个 tracepoint，插桩在 NCCL proxy 线程的数据传输关键路径上。

- **数据采集**：每台主机预分配 512MB 固定大小的共享内存循环缓冲区。Tracepoint 写入共享内存，独立 agent 异步读取并通过 Kafka 上传到云数据库。利用 NCCL 内部 stream 进行异步测量，对关键路径几乎零开销。

- **两类 tracepoint**：
  - **completion log**：CollOp 完成时记录，包含起止时间、传输字节数、NIC 信息等元数据
  - **real-time state log**：CollOp 进行中每 100ms 生成一次，记录 GPU_ready / RDMA_transmitted / RDMA_done 三阶段的 chunk 数量

- **触发规则**（Algorithm 1）：采样 rank 无 CollOp 完成 → failure trigger；吞吐量下降 50% 或 CollOp 间隔翻倍 → straggler trigger

- **根因分析**（Algorithm 2）：先定位受影响的通信组，再找 MinOp rank（执行最少操作）或 MinData rank（传输最少数据），最后通过 chunk 状态表（Table 4）判断是 GPU 问题、RDMA 问题还是接收端问题

- **与其他系统集成**：与 py-spy（Python 调用栈采样）和 PyTorch Flight Recorder（CollOp 环形缓冲区）协作，分别覆盖数据加载/检查点卡住和 rank 同步死锁等 CCL 之外的问题

- **后端**：4000 行 Python 代码，部署在单台服务器上，使用不到 64 个 CPU 核心和 100GB 内存，always-on 监控 ByteDance 所有超过 128 GPU 的训练任务

## 五、实验结果

**实验平台**：4 台机器，32 张 NVIDIA A100-80GB-SXM4 GPU，NVLink + PCIe 节点内互联，4 张 ConnectX-6 RNIC 节点间互联。工作负载为 GPT + Megatron-LM（TP=8, PP=2, DP=2）。

**故障注入覆盖 7 种典型故障**：

| 注入类型 | 根因定位方式 |
|---------|------------|
| NIC 关闭 | 最先停止日志生成的 rank |
| NIC 带宽限制 | 最先开始变慢的 rank |
| PCIe 降速 | 完成时间最晚的 rank |
| GPU 功率限制 | 完成时间最晚的 rank |
| 后台计算 | 完成时间最晚的 rank |
| 后台网络流量 | GPU_ready = RDMA_transmitted > RDMA_done |
| NCCL 延迟 | 最晚开始传输的 rank |

**检测效率**：所有注入场景中，从异常发生到告警不超过 13 秒。

**与 Nsight 对比**：Nsight 在 NIC 关闭场景下无法追踪受影响的 ReduceScatter kernel，在 NIC 带宽限制场景下报告所有 rank 几乎同时延迟，均无法定位根因。

**开销对比**：

| 指标 | Baseline | Mycroft | NVRx | Nsight (CUDA trace) | Nsight (backtrace) | NPKit |
|------|----------|---------|------|--------------------|--------------------|-------|
| 迭代时间 | 1116ms | 1119ms (<1%) | 1124ms | 1125ms | 1900ms | - |
| CPU 使用率 | 10.7% | 11.0% | 11.5% | 11.2% | 16.3% | - |
| 日志大小/迭代/机器 | - | 46.8KB | - | 15MB | - | - |

**生产环境（ByteDance，2024年10-12月）**：
- 监控所有超过 128 GPU 的训练任务，最多 20 个并发任务
- 检测到 13,221 次训练中断，100% 中断检测率
- 进行 1,253 次根因分析，其中 705 次定位到单一问题网络流
- 90% 异常在 15 秒内检测，60% 在 20 秒内完成根因分析

## 六、批判性分析

1. **测试规模与生产规模差距大**：故障注入实验仅在 32 GPU（4 台机器）上完成，而生产环境涉及数万 GPU。论文虽展示了生产统计数据，但缺乏在大规模环境下的受控实验验证。特别是 Figure 12d 显示根因分析时间随 GPU 数量增长明显，论文承认超过 10,000 GPU 可能需要去中心化优化但未给出方案。

2. **准确率未量化**：论文明确表示"难以标注所有异常的根因"，因此无法给出误报率和漏报率。100% 检测率是通过"交叉检查所有已知异常任务"得出的，存在选择偏差——只有已知的才能验证。对于被 Mycroft 检测但未被其他方式确认的异常，缺乏验证。

3. **启发式规则的脆弱性**：触发和分析依赖大量可配置阈值（吞吐量下降 50%、间隔翻倍、1 秒 straggler 阈值等），这些参数来自"经验"。论文在 Discussion 中承认不同训练任务可能需要不同阈值，但未提供自动调参方案。对于 communication-computation overlap 场景的误报问题也仅作为 limitation 提及。

4. **NCCL 版本绑定**：系统基于 NCCL 2.21.5 实现，需要修改 NCCL 源码。虽然论文声称设计可推广到其他 CCL，但实际移植工作量（重新定义 metrics、tracepoint、分析规则）未被讨论。每次 NCCL 升级都可能需要重新适配。

5. **根因分析的深度有限**：Mycroft 能定位到"哪个 GPU/NIC 有问题"，但无法进一步诊断底层原因（如具体的硬件故障类型），仍需依赖离线检测或其他工具。论文将此定位为 complementary tool，但这也意味着它只解决了诊断链中的一环。

## 七、AI Infra / MLSys 视角

1. **对 AI Infra 可观测性的启示**：Mycroft 提出的 Coll-level tracing 思路填补了 CCL 可观测性的空白。随着训练规模持续增长（从万卡到十万卡），CCL 层面的可观测性将成为基础设施的刚需。其 chunk-level 状态聚合（而非逐事件追踪）的思路值得推广到其他 AI Infra 组件。

2. **可迁移的设计思路**：
   - **采样检测 + 异常传播**的范式可用于推理场景中的异常检测（如 KV cache 同步、speculative decoding 的验证节点故障）
   - **依赖驱动的根因分析**可推广到更复杂的并行策略（如 Expert Parallelism、Sequence Parallelism）
   - **低开销 tracing 的关键路径插桩方法**（共享内存 + 异步上传）可作为通用的 AI Infra tracing 框架参考

3. **值得跟进的研究方向**：
   - 将 Mycroft 扩展到推理集群的异常检测（推理场景的 CollOp 模式和延迟要求与训练不同）
   - 自动化阈值调优：结合训练任务的特征（模型大小、并行配置、网络拓扑）自动设定检测阈值
   - 与 checkpoint/recovery 系统联动：检测到异常后自动触发最优恢复策略（替换节点 vs 降级运行 vs 从检查点重启）
   - 十万卡规模的去中心化 tracing 和分析架构

4. **最有价值的切入点**：在 Mycroft 的 chunk-level 状态数据基础上构建预测模型——利用历史异常模式预测即将发生的硬件退化（fail-slow），实现从"被动检测"到"主动预防"的升级。

---

## 八、总结

Mycroft 是首个利用集合通信内部依赖关系进行 LLM 训练可靠性诊断的系统。通过在 NCCL 关键路径上插入轻量级 tracepoint（<1% 性能开销，46.8KB/迭代/机器数据量），实现 Flow-level 和 Chunk-level 的细粒度可观测性，配合采样式触发和依赖驱动分析，在 ByteDance 生产环境中实现 90% 异常 15 秒内检测、60% 根因 20 秒内定位。主要局限在于启发式规则依赖人工经验调参、准确率缺乏严格量化、以及无法深入诊断底层硬件故障类型。
