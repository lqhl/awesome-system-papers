# Aegaeon: Effective GPU Pooling for Concurrent LLM Serving on the Market

## 1. 论文基本信息

- **标题**: Aegaeon: Effective GPU Pooling for Concurrent LLM Serving on the Market
- **作者**: Yuxing Xiang, Xue Li, Kun Qian, Yufan Yang, Diwen Zhu, Wenyuan Yu, Ennan Zhai, Xuanzhe Liu, Xin Jin, Jingren Zhou (北京大学 & 阿里巴巴)
- **会议**: SOSP 2025 (ACM SIGOPS 31st Symposium on Operating Systems Principles)
- **链接**: https://doi.org/10.1145/3731569.3764815
- **代码**: 未提及开源

## 2. 研究背景

**Model Market 的崛起**：HuggingFace 等模型市场托管了超过 100 万个模型，从大公司训练的专有模型到针对特定领域微调的模型。在阿里巴巴 Cloud ModelStudio 平台上，处理着来自数千个不同模型的并发推理请求。

**并发 LLM Serving 的核心挑战**：Model market 的工作负载呈现两个显著特征：
1. **高度倾斜的请求分布**：94.1% 的模型仅接收 1.35% 的请求（平均 < 0.2 req/s/GPU），而"热门"模型（DeepSeek、Llama、Qwen）面临请求突发，可能超过预留资源
2. **严重的资源浪费**：为防止请求突发导致 SLO 违规，必须预留大量 GPU 资源。结果：17.7% 的 GPU 资源仅服务 1.35% 的请求

这导致典型 GPU 利用率不足 0.1 req/s/GPU，远低于单模型可达的数 req/s/GPU。

**现有方案的局限性**：
- **Multiplexing（多路复用）**：在每 GPU 上放置多个模型实例，受 GPU 内存限制，通常仅支持 **2-3 个模型/GPU**（14B FP16 模型需 28GB，80GB GPU 最多 2 个）
- **Request-level Auto-scaling**：按请求粒度调整，每次调整涉及 KV cache swap-out、GC、engine reinitialization 等，可能耗时数十秒，无法支持 token-level 的粒度

## 3. 要解决的问题

**核心问题**：如何在满足 token-level SLO（TTFT、TBT）的前提下，最大化 GPU 共享（每个 GPU 服务更多模型），实现真正的 GPU Pooling？

具体挑战：
1. **请求粒度 vs token 粒度**：LLM 推理包含 Prefill 和 Decode 两个阶段，每个阶段有不同的执行时间和 SLO 需求。现有方案按请求粒度调整，无法区分 token-level 的 SLO 差异
2. **Auto-scaling 开销巨大**：Token-level scaling 涉及一系列关键操作（KV cache swap-out、GC、engine reinitialization、KV cache swap-in），这些操作可能耗时数十秒
3. **Head-of-Line Blocking**：当所有 GPU 被活跃模型占满时，新请求必须等待，导致严重 SLO 违规

## 4. 核心贡献

1. **首个 Token-level Auto-scaling 框架**：提出 token 级别的 auto-scaling 方案，每个 token 独立调度和 SLO 优化，而非按请求粒度。
2. **Token-level Scheduler**：针对 Prefill 和 Decode 阶段分别设计调度策略——Prefill 使用 grouped FCFS 最小化 TTFT；Decode 使用 weighted round-robin 最小化 TBT 违约率。
3. **97% Auto-scaling 开销降低**：通过组件复用、显式内存管理、细粒度 KV cache 同步全面优化 scaling 过程。
4. **支持最多 7 个模型/GPU**：相比现有方案（2-3 个模型/GPU）大幅提升。
5. **生产部署验证**：在阿里巴巴 Cloud ModelStudio 部署超过 3 个月，**GPU 资源节省 82%**（从 1192 GPU 降到 213 GPU）。

## 5. 主要研究方法

### 5.1 生产工作负载分析
分析阿里巴巴 Cloud ModelStudio 的真实工作负载：
- **94.1% 的模型接收 1.35% 的总请求**
- **17.7% 的 GPU 资源仅服务 1.35% 的请求**
- 在 3.7 req/s 总请求率下，平均 **46.55/100 个模型处于活跃状态**（request-level scaling 的根本限制）
- 热门模型存在请求突发（exceed reserved resources）

### 5.2 SLO 定义
- **TTFT（Time-To-First-Token）**：首 token 生成的延迟
- **TBT（Time-Between-Tokens）**：连续 token 生成之间的间隔
- **SLO Attainment**：token 生成时间满足 deadline 的比例

### 5.3 请求粒度 vs Token 粒度的分析
Theorem 3.1（论文分析）：即使在低总请求率下（如 3.7 req/s），由于 LLM 请求的长时间执行特性，大量模型会处于活跃状态（46.55/100），这限制了 request-level auto-scaling 的效果。

## 6. 设计与实现

### 6.1 Token-level Scheduler
**Prefill Phase Scheduler**：Grouped FCFS
- 将同时到达的 Prefill 请求分组，共享 KV cache 计算
- 按到达顺序调度，最小化 TTFT

**Decode Phase Scheduler**：Weighted Round-Robin
- 根据 TBT deadline 的紧迫性分配权重
- 防止某些 token 的 TBT 长期落后于其他 token

### 6.2 Token-level Auto-scaling
**Scaling 决策**：每个 token 的调度与 auto-scaling 联合优化
- 当前 token 调度完成后，评估是否需要 scaling
- 考虑 SLO deadline 和 scaling 成本

### 6.3 Scaling 开销优化
Token-level scaling 涉及的操作序列（KV cache swap-out、GC、engine reinitialization、KV cache swap-in）通常耗时数十秒。Aegaeon 提出三项优化：

**组件复用（Component Reuse）**：
- 识别 engine reinitialization 中可复用的组件（如 tokenizer、model config）
- 避免完全重新初始化

**显式内存管理（Explicit Memory Management）**：
- 直接控制 GPU 和 host memory 的分配
- 加速 model loading，减少 fragmentation 和 GC overhead

**细粒度 KV Cache 同步（Fine-grained KV Cache Synchronization）**：
- 在 swapping 和计算之间更好的 overlap
- 解耦传输过程

### 6.4 实现
- 集成到现有推理引擎
- 处理从 1.8B 到 72B 参数的多种模型

## 7. 主要实验结果

### 7.1 吞吐量和请求率
- 相比 ServerlessLLM 和 MuxServe：**维持 2-2.5 倍更高的请求到达率**
- 或在相同请求率下：**1.5-9 倍更高的 goodput**

### 7.2 GPU Pooling 效率
- **支持最多 7 个模型/GPU**（vs. 现有方案的 2-3 个）

### 7.3 生产部署
- 部署超过 **3 个月**
- 服务 1.8B 到 72B 参数的数十个模型
- **GPU 资源从 1192 降到 213（节省 82%）**
- SLO 达成率保持在高水平

## 8. 潜在问题/局限性

1. **Scaling 策略的实时性**：Token-level scheduler 和 auto-scaling 的联合优化是实时的，但 ILP/启发式求解器的收敛时间是否满足 token 级别的响应要求？论文没有量化调度决策的 latency。
2. **多优先级 SLO 的处理**：实际生产中可能有多个 SLO 级别（不同价格的 tier）。Aegaeon 如何处理不同优先级的请求未讨论。
3. **跨模型 KV Cache 的干扰**：多个模型共享 GPU 时，KV cache 的相互干扰可能导致 cache thrashing。Aegaeon 的内存管理如何处理这一问题未详细讨论。
4. **Fault Tolerance**：当一个模型实例失败时，auto-scaling 机制如何处理？KV cache 的恢复和重新同步的成本是多少？
5. **模型加载的冷启动延迟**：虽然优化了 engine reinitialization，但模型从 host memory 加载到 GPU 的延迟仍然存在。对于极其短暂的请求，这个 overhead 可能不可忽视。
6. **与 continuous batching 的兼容性**：Aegaeon 的 token-level 调度与 continuous batching（vLLM 等推理服务使用的核心技术）的交互未讨论。
7. **Scaling 策略的公平性**：当多个模型的请求同时需要资源时，scaling 决策如何保证公平性？是否存在某个模型长期"饿死"的风险？
8. **模型大小的异构性**：不同大小的模型（1.8B vs 72B）共存时的 GPU 内存管理挑战。

## 9. 未来工作

1. **跨模型 KV Cache 优化**：多个模型共享 KV cache 空间时的智能管理。
2. **多优先级 SLO 支持**：为不同 SLA 级别的请求提供差异化服务。
3. **Fault Tolerance 增强**：模型实例失败时的自动恢复机制。
4. **与 Speculative Decoding 的集成**：在 token-level scheduling 框架中支持 speculative decoding。
5. **自适应 Scaling 策略**：基于历史数据的 workload prediction 优化 scaling 决策。

## 10. 个人评注

**Aegaeon 是一篇来自工业界的精准问题诊断和务实解决方案论文**，它基于阿里巴巴 Cloud ModelStudio 的真实生产数据，揭示了 model market 中 GPU 资源利用严重不足的根本原因，并提出了经过大规模验证的解决方案。

论文最有价值的贡献是**Theorem 3.1 的理论分析**——它从排队论角度证明了 request-level auto-scaling 在 LLM serving 中的根本限制：由于请求执行时间长，即使总请求率很低，大量模型也会同时处于活跃状态。这使得 request-level 的 GPU pooling 效果严重受限，而 token-level 的解决方案是必然选择。

**批评性思考**：
- **"82% GPU 节省"数字需要考虑背景**：这个数字是相对于"为每个模型预留独立 GPU"的基线而言的。如果基线本身就极度浪费（17.7% 的 GPU 仅服务 1.35% 的请求），那么显著的资源节省是预期的。实际与更智能的资源预留方案（而非简单的一对一映射）相比，节省幅度可能没那么大。
- **"97% scaling 开销降低"的计算基准不明确**：相对于原始的完全重新初始化过程，减少 97% 意味着开销从数十秒降到亚秒级。这个改善是显著的还是仍有进一步优化空间？
- **Token-level scheduler 的调度延迟未量化**：在 token 生成时间（decode phase 通常 10-100ms/token）的粒度下，调度决策本身的时间是否可以被接受？如果调度决策本身需要毫秒级，它可能成为瓶颈。
- **与 vLLM 的 continuous batching 的关系未讨论**：vLLM 通过 paged attention 和 continuous batching 已经在单模型场景下大幅提高了 GPU 利用率。Aegaeon 与 continuous batching 的关系——是竞争还是互补——是一个重要的未回答问题。
- **Multi-tenant 安全隔离**：多个模型共享 GPU 时，模型权重和 KV cache 之间的安全隔离如何保证？特别是对于包含敏感数据的应用。
- **模型切换的频率和 KV cache 利用率的平衡**：如果一个模型长时间不使用，它的 KV cache 应该被 evict 以便其他模型使用。但频繁的 evict 和 reload 可能反而增加开销。Aegaeon 如何平衡这一 trade-off？

总体而言，这是一篇对 LLM serving 系统工程师和云服务提供商非常有价值的论文。Theorem 3.1 的理论洞察和 82% GPU 节省的生产验证数据，为后续研究提供了坚实的基线和问题定义。
