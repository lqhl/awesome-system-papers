# Aegaeon: Effective GPU Pooling for Concurrent LLM Serving on the Market

## 一、背景

大语言模型（LLM）的爆发式增长催生了以 HuggingFace 为代表的模型市场，其上托管超过百万个模型。阿里巴巴云的 Model Studio 平台同样面对成千上万种模型的并发推理请求。在此场景下，传统做法是为每个模型分配独占的 GPU 实例（dedicated GPU instance），但这带来严重的资源浪费：

- 大量模型属于"长尾"模型（94.1% 的模型仅占 1.35% 的请求量），一直占用着 GPU 但极少被调用；
- 热门模型又存在突发流量（burst），需要额外预留资源应对峰值。

现有针对单模型服务的优化（continuous batching、FlashAttention、PagedAttention 等）在此场景下无法直接解决资源利用率问题，因为单台 GPU 只服务一个模型时本身就处于严重欠载状态。

---

## 二、要解决的问题

### 2.1 现有 GPU 池化方案的局限性

**模型复用（Multiplexing）**：将多个模型同时加载到同一 GPU 上实现时间/空间共享（如 MuxServe、NVIDIA MPS）。受限于 GPU 显存容量，每块 80GB A100 最多容纳两个 14B FP16 模型，通常只能支持 2-3 个模型共享一张 GPU，远未达到充分利用 GPU 的目标。

**自动扩缩容（Auto-scaling）**：按需将模型权重从主机内存或 SSD 加载到 GPU（如 ServerlessLLM、BlitzScale、ParaServe）。理论上可支持更多模型，但存在根本性缺陷：**扩缩容粒度是请求级（request-level）**，只在一个请求完全执行完后才换入下一个模型。

### 2.2 请求级自动扩缩容的根本问题

论文通过分析证明（Theorem 3.1），在泊松到达、平均服务时间为 T、单模型到达率为 λ 的条件下：

$$E[m] = M \cdot (1 - e^{-\lambda T})$$

以真实工作负载（λ=0.037，T=16.79s）为例，100 个模型中平均有 46.55 个处于活跃状态（有正在服务的请求）。这导致系统必须为 46.55 个模型保留 GPU，实际池化效率只有不到 3 个模型/GPU——与 Multiplexing 方案相当。

**根本原因**：LLM 请求执行时间长（十几秒），使得任意时刻都有大量模型处于"活跃"状态。请求级扩缩容无法抢占这些正在执行的请求，新到请求只能等待，造成严重的队头阻塞（Head-of-Line, HOL）。

## 三、核心设计

Aegaeon 提出**Token 级自动扩缩容（token-level auto-scaling）**，在每个 token 生成步骤后即可抢占当前模型，换入其他需要服务的模型，从而将活跃 GPU 实例数量降低到远低于 E[m]，逼近单模型服务时的资源效率。

### 3.1 Prefill-Decode 分离调度

统一调度（prefill + decode 在同一 GPU 上）要么造成 TBT 违规（prefill 优先），要么造成 TTFT 违规（decode 优先）。Aegaeon 将 GPU 池分为两部分：

- **Prefill 实例**：专门执行 prefill 阶段
- **Decode 实例**：专门执行 decode 阶段

### 3.2 Prefill 阶段调度（算法 1）

Prefill 的自动扩缩容代价与执行一批 prefill 任务相当（~0.8s），频繁换模型会大幅增加 TTFT。因此采用**分组 FCFS 调度器**：
- 将同一模型的请求归组，每组最多 8 个请求，尽量减少不必要的模型切换；
- 在 FCFS 大框架下，优先将新请求加入已有同模型分组；
- 按最少负载（total execution + scaling time）分配到不同 prefill 实例。

### 3.3 Decode 阶段调度（算法 2）

Decode 步骤耗时很短（tens of ms），而 TBT 限制相对宽松（100ms for chatbot），累积 n 步可容忍 n(d-t) 的延迟。Aegaeon 利用这个"slack time"进行模型切换：

采用**加权轮转调度器（weighted round-robin）**，每轮为每个模型批次分配时间配额 $q_i$，保证在一轮结束时所有批次均满足 token 级 deadline，同时利用空隙执行模型切换。

## 四、实现细节

Aegaeon 通过三层优化将默认的自动扩缩容开销从 **26.9s（T₀）降低到不足 1s（T₃）**，降幅 97%。

### 4.1 组件复用（Component Reuse，T₀→T₁，节省 80%+）

分析 vLLM 等推理引擎的初始化流程发现，大量组件（分布式执行器 Ray/NCCL、profiling、tokenizer、调度器等）与具体模型无关，可跨模型复用。Aegaeon 在实例启动时初始化一次，后续换模型只需重新加载模型权重和 KV cache。

### 4.2 显式内存管理（Explicit Memory Management，T₁→T₂）

**VRAM 侧**：用 monkey-patch 覆盖 `torch.nn.Parameter` 类，将所有模型权重和 KV cache 的分配统一到启动时一次性预留的**自管理 VRAM Buffer**中，采用 bump allocation 策略。绕过 PyTorch 的 caching allocator，避免 `gc.collect()` + `torch.cuda.empty_cache()` 的碎片整理开销（数秒）。

**DRAM 侧**：
- **Model Cache**：将模型 checkpoint 的原始 tensor chunks 缓存到 host 共享内存，模型切换时直接通过 Stage Buffer（page-locked）多线程分块流水线方式加载到 GPU（<1s）；
- **Unified KV Cache**：针对不同模型的 KV cache shape 差异（见表 1），采用 **slab allocation** 统一管理——每个 slab 固定大小，按 shape 分配给对应的 KV cache 块池，避免跨 shape 的内存碎片。整体碎片率控制在 20% 以下。
- **模型预取（Prefetching）**：调度器可提前预测下一个需要换入的模型，在 prefetch CUDA stream 中异步加载，完全隐藏加载开销（约 50% 的情况下实现近零换模型延迟）。

### 4.3 细粒度 KV Cache 同步（Fine-Grained KV Cache Sync，T₂→T₃）

KV cache 的换入换出需要满足三条数据依赖规则：
1. Inference 前 KV cache 必须已在 GPU 上
2. 新的 transfer 需要等源 blocks 上一次 transfer 完成
3. 新的 transfer 需要目标 blocks 空闲（所有之前的 transfer 已完成）

Aegaeon 使用 CUDA events（`cudaEventRecord/Query/StreamWaitEvent/IpcGetEventHandle/IpcOpenEventHandle`）对每个 KV cache transfer 进行细粒度跟踪，在不阻塞整个数据平面的前提下精确实施上述依赖约束。维护 move list 记录活跃中的 CPU cache blocks，异步 daemon 线程周期性回收。

**代码规模**：调度器 + scaling-efficient 推理引擎，5,700 行 Python + CUDA/C++ 代码，基于 vLLM 作为模型执行后端。

## 五、实验结果

**测试平台**：2 节点 × 8 NVIDIA H800 80GB（NVLINK），2TB DDR5，192 Intel Xeon Platinum 8469C。

**模型**：Qwen、LLaMA、InternLM、Yi 等系列，6B–14B 参数为主。

**基线**：ServerlessLLM、ServerlessLLM+（加 oracle-guided SJF 调度）、MuxServe。

| 指标 | 结论 |
|------|------|
| 最大模型数/GPU | Aegaeon 支持 **7 个模型/GPU**，ServerlessLLM < 3，MuxServe ≤ 2 |
| 请求到达率吞吐 | RPS=0.1 时 **2×** vs ServerlessLLM；RPS=0.5 时 **2.5×** |
| Goodput（90% SLO@RPS=0.1） | 2× higher than ServerlessLLM |
| Goodput（90% SLO@RPS=0.5） | 1.5–9× higher（随模型数增多差距拉大） |
| 自动扩缩容延迟 | ~50% 情况下 **近零**（prefetch 完全隐藏）；最大 **< 1s** |
| 内存碎片率 | Unified CPU KV Cache 总体 **< 20%** |
| 生产部署 GPU 节省 | 从 1,192 块 H20 降至 213 块，节省 **82%** |
| 生产 GPU 利用率 | 从 13.3%–33.9% 提升至 **48.1%**，无 SLO 违规 |

**严格 SLO 场景**：在 0.5× SLO（5s TTFT/50ms TBT）和 0.3× SLO 下 Aegaeon 仍优于两个基线；仅在极严格的 0.2× SLO（2s TTFT/20ms TBT）下，MuxServe 的静态共置优势才超过 Aegaeon（因为自动扩缩容的 slack 空间被完全压缩）。

## 六、批判性分析

**1. 82% GPU 节省数字的可信度存疑**

论文将"从 1,192 GPU 降至 213 GPU"作为核心卖点，但同时承认生产部署中"typically utilizes redundant resources"超过最低需求以应对峰值和容错。这意味着 1,192 是包含冗余的原始配置，而 213 是 Aegaeon 的最终部署数——两者不在同一假设条件下对比，夸大了节省效果。论文没有给出两者在相同冗余策略下的对比数据。

**2. 实验规模偏小**

核心评测仅在 16 块 H800 GPU 上进行（6 prefill + 10 decode），而生产部署用的是 213 块 H20 GPU（跨区域集群）。从 16 到 213 的规模跨越会引入网络延迟、调度复杂度等新问题，论文对此几乎没有讨论。

**3. 生产实验数据粒度不足**

Figure 18（GPU 利用率对比）的 "Before (low load)" 和 "Before (high load)" 是单个实例的利用率，而 "After (Aegaeon)" 是整体系统的利用率，对比基准不统一。论文并未给出 Aegaeon 的 SLO 统计数据（仅说"no observable SLO violations"），缺乏量化。

**4. 调度器优化性假设过于简化**

Theorem 3.1 基于模型到达率为独立同分布泊松过程，而真实工作负载中热门模型的突发性与长尾模型的冷启动之间存在强相关性（比如某个模型突然爆火）。论文承认了 burst 问题，但调度器的分析仍建立在 i.i.d. Poisson 假设上。

**5. 严格 SLO 场景的退化未充分讨论**

在 0.2× SLO 场景下，Aegaeon 不如 MuxServe（Figure 13(c)），但论文将此轻描淡写为"static multiplexing has a place in extremely latency-sensitive scenarios"。实际上这揭示了 token-level auto-scaling 的内在限制：当 slack time 不足时，加权轮转调度器的时间配额分配会变得非常激进，可能引入不稳定性，而论文没有深入分析这个边界条件。

**6. MuxServe 基线可能不公平**

MuxServe 的 placement optimizer 被直接使用，在本文的实验设置下（80GB GPU、14B 模型）天然只能放 2 个模型，这使得 MuxServe 的表现必然受限。如果实验换成参数更小的模型（如 3B/7B）、更大显存的 GPU，Multiplexing 的竞争力会强得多，但论文没有进行这种公平对比。

## 七、AI Infra / MLSys 视角

**核心 Insight 的迁移价值**

Aegaeon 的核心思路——"在 token 粒度而非请求粒度做调度决策"——是一个值得向 AI Infra 更广泛场景借鉴的范式。在多租户推理、模型路由、MoE 专家调度等场景中，同样存在"粒度太粗导致 HOL blocking"的问题，token-level preemption 的思路具有普适性。

**技术迁移点**

- **Self-managed VRAM buffer + bump allocation**：绕过 PyTorch 内存管理直接控制显存布局，这对 KV cache 压缩、speculative decoding 的 draft model 管理等都有直接参考价值；
- **Slab allocation for KV cache**：经典内存管理技术在不同 shape KV cache 管理上的应用，可用于 multi-LoRA serving 中不同 adapter 的 KV cache 隔离；
- **CUDA event 细粒度同步**：在 pipeline parallelism 和 tensor parallelism 的 P-D 分离部署中，需要管理 KV cache 的跨节点传输依赖，Aegaeon 的细粒度 event tracking 机制可以直接移植；
- **模型预取（prefetching）由调度器驱动**：将 schedule 预测与 I/O pipeline 耦合，是减少冷启动延迟的通用技巧，在 serverless inference 和 MoE 动态路由中都有应用空间。

**值得跟进的 Future Work**

1. **更严格 SLO 场景下的自适应策略**：当前 Aegaeon 在严格 SLO 下退化为 MuxServe 水平，如何在 slack time 不足时动态切换到静态共置或混合策略是开放问题；
2. **跨节点（multi-node）token-level auto-scaling**：生产集群跨区域，KV cache 传输延迟远大于节点内 PCIe，如何在网络延迟不可忽略时维持 token-level 的换模型开销仍是挑战；
3. **与 LoRA/Adapter serving 结合**：模型市场中大量模型是基于同一基础模型的 LoRA fine-tune，Aegaeon 的 GPU pooling 可以与共享基础模型权重 + 独立 adapter 的方案（如 S-LoRA）结合，进一步提升资源利用率。

---

## 八、总结

Aegaeon 在并发 LLM 推理（model market）场景中，通过将自动扩缩容从请求粒度细化到 token 粒度，解决了现有方案受活跃模型数瓶颈制约的 HOL blocking 问题。其核心贡献是 token-level 调度器（prefill/decode 分离、分组 FCFS + 加权轮转）与三层扩缩容优化（组件复用、显式内存管理、CUDA event 细粒度同步），将扩缩容开销从 26.9s 压缩至不足 1s。在 16 GPU 测试集群上支持 7 个模型/GPU，比现有方案提升 2–2.5× 吞吐；在阿里云生产环境将 GPU 需求从 1,192 减少到 213（82% 节省）。主要局限是在极严格 SLO（2s TTFT/20ms TBT）场景下不如静态复用，以及实验规模偏小、生产对比数据基准不统一等问题。
