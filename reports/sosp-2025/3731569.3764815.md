# Aegaeon: Effective GPU Pooling for Concurrent LLM Serving on the Market

**作者**：Yuxing Xiang (Peking University), Xue Li, Kun Qian, Yufan Yang, Diwen Zhu, Wenyuan Yu, Ennan Zhai (Alibaba Group), Xuanzhe Liu, Xin Jin (Peking University), Jingren Zhou (Alibaba Group)

**链接**：https://doi.org/10.1145/3731569.3764815
**源文件**：[[3731569.3764815.pdf]]

---

## 一、背景

随着 LLM 的快速发展，模型市场（如 HuggingFace）上已有超过百万个模型。阿里云 Model Studio 作为领先的云推理服务提供商，需要同时服务数千个不同模型的并发推理请求。这些工作负载呈现高度偏斜的长尾分布：94.1% 的模型仅产生 1.35% 的请求，却占用 17.7% 的 GPU 资源（约 30K GPU 中的 5.3K）。即使是热门模型（如 DeepSeek、Llama、Qwen）也面临突发流量问题，导致间歇性的资源浪费。在理想的单模型场景下，每 GPU 可达数个 RPS，而当前并发服务仅实现不到 0.1 RPS/GPU，存在超过 10 倍的优化空间。

---

## 二、要解决的问题

1. **Multiplexing 方案受限于 GPU 显存容量**：每个 80GB GPU 最多容纳 2-3 个 14B 模型（FP16），远不够实现有效的 GPU pooling。

2. **现有 auto-scaling 方案受限于请求粒度**：ServerlessLLM、BlitzScale 等系统在请求级别进行 scaling，导致严重的 head-of-line (HOL) blocking。由于 LLM 请求执行时间长（平均 16.79s），即使总到达率仅 3.7 req/s，100 个模型中平均有 46.55 个处于活跃状态，使得 pooling 效率仅为 ~3 模型/GPU，与 multiplexing 持平。

3. **Token 级别 auto-scaling 的调度复杂性**：不同模型的请求无法 batch 在一起，且 auto-scaling 延迟放大了错误调度决策的惩罚。

4. **Auto-scaling 过程开销巨大**：未优化的情况下，scaling down + scaling up 一个 13B 模型需要数十秒（包括 KV cache swap-out、GC、引擎重初始化、KV cache swap-in 等），使 token 级方案不可行。

---

## 三、洞察与设计

**关键洞察**：现有 auto-scaling 系统的 pooling 效率受限于"活跃模型数"（有至少一个正在服务的请求的模型数），而 LLM 请求的长执行时间使得即使在低到达率下活跃模型数也很高（E[m] = M·(1-e^{-λT})）。如果能在 token 粒度上抢占式地 scale down 当前模型并 scale up 待服务模型，就可以将 GPU 预留数从 O(m) 降至远低于活跃模型数，从根本上打破请求级 auto-scaling 的瓶颈。

基于此洞察，Aegaeon 设计了三个核心组件：

### 1. Prefill/Decode 分离调度
将 GPU 池分为 prefill 实例和 decoding 实例。Prefill 阶段使用 grouped FCFS 调度器：将相同模型的请求分组（最大组大小 8），分派到负载最轻的实例，每次仅执行一个 prefill batch 以减少等待时间。Decoding 阶段使用加权 round-robin 调度器：为每个 batch 分配时间配额，利用 token 流的可缓冲特性积累 slack time 用于 auto-scaling 和服务其他请求。

### 2. 时间配额公式
Decoding 的时间配额通过公式 q_i = n_i·(α - c/(Σn_k)) 计算，其中 α 是 SLO attainment 的倒数估计。该公式在满足 per-token deadline 的前提下，为 auto-scaling 开销留出缓冲窗口。

### 3. 高效抢占式 Auto-Scaling
通过组件复用、显式内存管理和细粒度 KV cache 同步三方面优化，将 auto-scaling 延迟降低 97%。

## 四、实现细节

Aegaeon 基于 vLLM 构建，实现了 5,700 行 Python 和 CUDA/C++ 代码。控制面使用 asyncio，数据面使用 Ray 分发。

### 组件复用（降低引擎重初始化开销）
- **分布式执行器**：跨模型复用 Ray worker 和 NCCL 通信组，避免重复初始化（原需数十秒）
- **Profiling**：缓存模型 profiling 结果（如峰值显存使用），跳过重复 profiling
- **模型加载**：仅重载权重和 tokenizer，复用 worker 进程和通信基础设施
- 优化后引擎重初始化从 13.2s 降至 0.86s（13B 模型）

### 显式内存管理
- **统一 GPU 缓存**：为所有模型的 KV cache 维护统一的 block 池，按 slab 分配不同 shape 的 block，消除碎片化和 GC 开销
- **统一 CPU 缓存**：将模型权重和 KV cache 统一管理在 CPU 内存中，支持 LRU 缓存和预取
- 三条规则保证正确性：CPU block 仅在 GPU 上对应 block 被释放后才可回收；GPU block 仅在 CPU 上的权重/KV cache 传输完成后才可使用；CPU block 在活跃传输期间不可被覆盖

### 细粒度 KV Cache 同步
- 使用 CUDA Event API（cudaEventRecord/Query/StreamWaitEvent）实现跨进程的异步同步
- KV cache swap-in 与 swap-out 可与推理执行重叠，避免阻塞等待
- 通过 IPC 传递 event handle 实现跨实例同步

## 五、实验结果

**测试环境**：2 节点，16 × NVIDIA H800 80GB GPU，2TB DDR5，192 核 Intel Xeon。6 个 prefill + 10 个 decoding 实例。

**模型**：Qwen、Llama、InternLM、Yi 等系列，6B-14B 参数为主，也测试了 72B 模型。

**SLO 设置**：TTFT = 10s，TBT = 100ms。

| 指标 | Aegaeon | ServerlessLLM | MuxServe |
|------|---------|---------------|----------|
| 支持模型数/GPU（RPS=0.1） | 7 | ~3 | 2 |
| 最大 goodput 倍数 vs ServerlessLLM | 1.5-9× | 基线 | - |
| 支持的最大到达率倍数 vs ServerlessLLM | 2-2.5× | 基线 | - |
| Auto-scaling 延迟降低 | 97%（从数十秒到亚秒级） | - | - |
| 内存碎片率 | <20% | - | - |

**生产部署（阿里云 Model Studio）**：
- 集群：213 × H20 GPU（跨区域）
- 服务模型：28 个 1.8-7B 模型（TP=1）+ 19 个 32-72B 模型（TP=4）
- GPU 节省：从 1,192 GPU 降至 213 GPU，**节省 82%**
- GPU 利用率：从 13.3%-33.9% 提升至 48.1%
- 无可观察的 SLO 违反或服务中断

**更严格 SLO 下的表现**：在 0.5× 和 0.3× SLO 下仍优于基线；在 0.2× SLO（2s TTFT/20ms TBT）下不再优于 MuxServe，但仍优于请求级 auto-scaling。

## 六、批判性分析

1. **生产部署规模有限**：虽然声称节省 82% GPU，但 beta 部署仅服务"tens of models"，与论文开头描述的"thousands of different models"场景差距很大。从 1,192 GPU 到 213 GPU 的对比中，原始 1,192 GPU 是否包含冗余资源未详细说明，实际节省比例可能被高估。

2. **Prefill/Decode 实例比例需手动设定**：所有实验固定使用 6 prefill + 10 decoding 实例，未讨论该比例如何根据工作负载自适应调整。这在实际生产中是一个重要的运维问题。

3. **SLO 设定相对宽松**：TTFT = 10s 和 TBT = 100ms 是较宽松的 SLO。论文自己也承认在 0.2× SLO 下不再优于 MuxServe。对于延迟敏感的实时应用（如对话、代码补全），Aegaeon 的优势可能大幅缩水。

4. **模型异构性处理不足**：论文主要测试 6B-14B 模型，72B 模型仅在单独实验中测试。实际生产中模型大小从 1.8B 到 72B 不等且混合部署，不同模型的 auto-scaling 开销差异很大，但论文未详细分析这种异构场景下的调度效果。

5. **Theorem 3.1 的假设过于理想**：假设每个模型的到达率相同（均为 λ），但实际工作负载高度偏斜（94.1% 模型仅占 1.35% 请求）。虽然这个定理主要用于动机分析，但其结论可能不完全适用于真实场景。

6. **与 BlitzScale 等更新基线的对比缺失**：仅与 ServerlessLLM 和 MuxServe 对比，而同期的 BlitzScale（OSDI 2025）和 ParaServe 仅在文字中提及，未进行实验对比。

## 七、AI Infra / MLSys 视角

### 启发与借鉴

1. **Token 级别调度的范式转换**：Aegaeon 证明了从请求级到 token 级 auto-scaling 的可行性和必要性。这一思路可推广到其他多租户 GPU 共享场景，如 MoE 模型的 expert 调度、多 LoRA adapter 的动态切换等。

2. **组件复用的工程思路**：跨模型复用推理引擎组件（NCCL 通信组、Ray worker、profiling 结果）的做法，可以推广到所有需要频繁初始化/销毁推理实例的场景，如 serverless AI、auto-scaling 平台。

3. **统一内存管理**：将模型权重和 KV cache 统一管理在同一 CPU 缓存中，并使用 slab allocator 消除碎片化的设计，对构建通用 LLM serving 平台具有参考价值。

### 可跟进的研究方向

1. **自适应 prefill/decode 比例调整**：当前比例是静态设定的，可以研究基于工作负载特征动态调整的方法。
2. **与 KV cache 压缩技术的结合**：如果 KV cache 可以被压缩（如量化、稀疏化），auto-scaling 的传输开销会进一步降低，可以探索联合优化。
3. **异构模型混合调度**：研究在 1B-100B+ 模型混合部署时的最优分组和调度策略。
4. **与 LoRA 热切换的结合**：在同一基础模型的多个 LoRA adapter 之间切换比完整模型切换更轻量，可以探索分层 pooling 策略。

---

## 八、总结

Aegaeon 是首个实现 token 级别 auto-scaling 的多模型 LLM serving 系统，通过 prefill/decode 分离调度、加权 round-robin 时间配额分配、以及全栈 auto-scaling 优化（组件复用、统一内存管理、CUDA Event 异步同步），将 auto-scaling 延迟降低 97%，实现每 GPU 服务 7 个模型。在阿里云生产环境中部署后节省 82% GPU 资源。系统在宽松到中等 SLO 下表现优异，但在极严格延迟要求下优势减弱，且当前部署规模和模型异构性处理仍有提升空间。
