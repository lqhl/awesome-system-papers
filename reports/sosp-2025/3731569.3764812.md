## 一、背景

PCIe 设备（NIC、SSD、加速器等）在云数据中心的资本和运营成本中占比显著——NIC 和 SSD 各自约 $2,000 的 CapEx，合计约占服务器总成本的 20-40%；在 Azure，NIC 和 SSD 各贡献约 13% 的服务器功耗。然而，这些 PCIe 设备普遍利用率低下。Azure 的生产数据显示，NIC 带宽的 P99.99 利用率仅约 20%，整体 NIC 带宽利用率约 15%，SSD 容量利用率约 67%。

与此同时，CXL (Compute eXpress Link) 内存池技术已经开始在数据中心部署，用于提升内存利用率和降低成本。CXL 内存池为主机间提供了高带宽、低延迟的共享内存通路。

---

## 二、要解决的问题

PCIe 设备利用率低下有三大原因：

1. **资源搁浅（Stranding）**：异构工作负载导致复杂的装箱问题。主机某一维度资源（如 CPU/内存）耗尽后，剩余的 NIC 带宽和 SSD 容量无法被分配。Azure 数据显示 27% NIC 带宽和 33% SSD 容量处于搁浅状态。

2. **分配但未充分利用**：NIC 带宽为应对峰值需求保守分配，网络流量具有高度突发性（P99 利用率不到 3%），大部分时间资源闲置。由于 CPU/内存等其他资源已耗尽，无法在同一主机内超额分配。

3. **冗余 NIC 用于容错**：许多主机配置冗余 NIC 以应对网络故障，但故障概率很低，冗余设备进一步降低了整体利用率。

现有的 PCIe 设备池化方案存在明显不足：
- **PCIe 交换机**：成本高昂（每机架增加约 $80,000），且不灵活，每种交换机仅支持特定设备类型。
- **RDMA 解聚**：无法解聚 NIC 本身，且不支持缺少 P2P DMA 的设备（如加速器），延迟也相对较高。

## 三、洞察与设计

**关键洞察**：CXL 内存池已经因内存池化用例在经济上合理化部署，同样的基础设施投资可以在几乎零额外成本下解锁 PCIe 设备池化功能——CXL 共享内存可作为主机与 PCIe 设备之间的高效数据通路。此外，PCIe 设备通常通过 DMA 绕过 CPU 缓存访问内存，这一特性可以被利用来安全地消除非缓存一致性 CXL 共享内存上大部分的缓存一致性操作开销。

基于此洞察，Oasis 的核心设计包含三个层次：

**1. 通用数据通路**：在 CXL 共享内存上构建通用的 I/O 数据通路，包括：
- I/O 缓冲区分配在共享 CXL 内存中，任意主机的 CPU 和 PCIe 设备均可直接访问
- 利用 PCIe 设备 DMA 绕过 CPU 缓存的特性，在 backend driver 侧消除不必要的缓存行失效和回写操作
- 设计了针对非缓存一致性共享内存优化的消息通道（message channel），通过精心插入缓存行失效指令来"解锁"预取，将消息吞吐量提升 29×（从 3.0 MOp/s 提升到 87.0 MOp/s）

**2. 引擎架构**：采用 frontend driver + backend driver 的架构，类似 VirtIO 的设计：
- Frontend driver 在每台主机上运行，向本地实例提供类型特定的 I/O 接口
- Backend driver 仅在直连设备的主机上运行，通过原生 PCIe 设备驱动（如 DPDK MLX5）操作设备
- 不同设备类型通过添加不同的 Oasis engine 支持

**3. Pod 级别分配器**：集中式控制平面管理实例到设备的映射，处理负载均衡和故障转移，通过 Raft 复制保证高可用。

**NIC 故障转移**：每个 pod 预留一块 backup NIC，实例启动时同时向 backup NIC 注册。NIC 故障时，TX 流量立即切换到 backup NIC（数据包已在共享 CXL 内存中，无需额外拷贝）；RX 流量通过让 backup NIC "借用"故障 NIC 的 MAC 地址来触发交换机更新转发表，实现透明切换。

## 四、实现细节

- 基于 Junction（容器化网络栈）实现网络引擎，约 7,000 行 C++ 代码
- Junction 提供容器运行时和 NIC 虚拟化层，每个容器实例通过 IPC 通道获得虚拟 NIC 接口
- 消息通道使用共享 CXL 内存中的循环缓冲区，默认 8192 个 slot，网络引擎使用 16B 消息，存储引擎使用 64B 消息
- 每条消息最高位保留为 epoch bit，接收方通过检查该位判断是否有新消息
- 接收方消费完一个缓存行的所有消息后失效该缓存行，并在空轮询后失效已预取的缓存行，确保后续预取能获取新数据
- 发送方缓存接收方的消费计数器，仅在缓存值指示所有 slot 已满时才重新读取，减少非一致性读取开销
- 接收方批量更新消费计数器（默认消费通道容量一半后更新）
- 前后端驱动各使用一个 busy polling 核心
- 存储引擎设计类似网络引擎但未实现，使用 64B 消息映射 NVMe 命令字段

## 五、实验结果

**实验平台**：2 台 AMD 主机（EPYC 9825 144 核 + EPYC 9015 8 核），各 768GB DDR5-5600，100Gbps Mellanox CX5 NIC，1 台 CXL 2.0 内存设备（256GB DDR5-4800），Ubuntu 24.04 / Linux 6.8.0。

| 指标 | 结果 |
|------|------|
| 端到端延迟开销 | P50/P90/P99 一致增加 4-7 µs |
| 延迟开销来源 | 主要来自跨主机消息传递，I/O 缓冲区放在 CXL 内存几乎无额外延迟 |
| 应用级影响 | Python HTTP / Rust Rocket / nginx / Tomcat / memcached 均仅增加 4-7 µs |
| NIC 利用率提升 | 两主机共享单 NIC 后，P99.99 聚合利用率从 18% 提升到 37%（2× 提升） |
| 故障转移时间 | UDP: 38 ms，TCP (memcached): 133 ms |
| CXL 带宽消耗 | 空闲 0.2 GB/s，满载（1500B 包）13.5 GB/s（89% 用于包负载） |
| 消息通道吞吐 | 优化后单通道 87 MOp/s，远超 14 MOp/s 的目标 |

## 六、批判性分析

1. **实验规模过小**：仅 2 台主机 + 1 个 CXL 设备的实验配置远不能代表生产环境中 8+ 主机的 pod。论文声称的利用率提升基于生产 trace 的模拟（Figure 2），但端到端性能只在 2 主机上验证，多主机竞争下的性能表现完全未知。

2. **存储引擎仅设计未实现**：论文标题和摘要声称池化"PCIe devices"（复数，包括 NIC 和 SSD），但实际只实现了网络引擎。SSD 的故障语义（涉及持久化数据）远比无状态 NIC 流量复杂，存储引擎的可行性未经验证。

3. **单线程数据通路的局限性被轻描淡写**：论文在 Discussion 中承认使用单 I/O 线程但称"多通道分片设计是直接的扩展"。然而 100/200 Gbps NIC 的线速处理通常需要多核，这并非简单的工程问题——多通道下的同步、负载均衡和缓存行竞争可能显著改变性能特征。

4. **故障转移能力有限**：backup NIC 通过借用故障 NIC 的 MAC 地址实现 RX 重定向，但论文承认此方法无法将故障 NIC 的流量分散到多个 NIC。这意味着 backup NIC 必须预留足够带宽，实际上限制了超额分配的空间。

5. **CXL 设备本身的故障未解决**：论文在 Discussion 中提到 CXL 链路/线缆故障需要冗余拓扑，但留给未来工作。考虑到 CXL 是整个系统的单点依赖，这是一个关键缺陷。

6. **硬件配置不对称**：两台主机的 CPU 差异巨大（144 核 vs 8 核），论文声称 CXL 延迟和带宽"一致"，但这种不对称配置下的实验结果说服力有限。

7. **与生产网络的差距**：论文在 Discussion 中承认单交换机拓扑"vastly oversimplifies production networks"，特别是 VIP/DIP 映射、负载均衡器集成等关键部分均未解决。

## 七、AI Infra / MLSys 视角

1. **GPU 池化的借鉴**：Oasis 的核心思路——利用 CXL 共享内存在软件层面池化 PCIe 设备——可以直接扩展到 GPU 池化场景。当前 GPU 集群同样面临利用率低下的问题（空闲等待、碎片化调度），通过 CXL 池化 GPU 可以实现更灵活的资源分配。不过，GPU 的带宽需求远高于 NIC/SSD（数百 GB/s），需要更多 CXL lanes 或 CXL 3.0。

2. **推理集群中的 NIC 池化**：LLM 推理服务的网络流量同样具有突发性（prefill 阶段密集通信，decode 阶段较少），Oasis 的 NIC 池化方案可以直接应用于推理集群，减少 NIC 成本。

3. **非缓存一致性共享内存上的消息通道优化**：论文提出的通过精心管理缓存行失效来恢复预取效果的技术（29× 吞吐提升），对任何使用 CXL 共享内存进行主机间通信的 AI 系统都有直接价值——如分布式 KV cache、跨节点参数同步等。

4. **值得跟进的方向**：
   - 基于 CXL 的 GPU 显存池化，特别是在 MoE 模型的 expert 级别调度场景
   - 利用 Oasis 的故障转移机制实现 AI 训练中的 NIC 故障快速恢复（当前训练集群中 NIC 故障通常需要重启 job）
   - 将消息通道优化技术应用到分布式推理系统的 KV cache 传输

---

## 八、总结

Oasis 是首个在 CXL 内存池上以纯软件方式实现 PCIe 设备池化的系统，核心贡献在于：（1）论证了已部署的 CXL 内存池基础设施可以近零额外成本复用于 PCIe 设备池化；（2）设计了针对非缓存一致性 CXL 共享内存优化的高性能消息通道；（3）实现了低开销（4-7 µs）的 NIC 池化和快速故障转移（38 ms）。系统适用于多租户云环境中 NIC/SSD 利用率低下的场景。主要局限在于实验规模小、存储引擎未实现、单线程数据通路，距离生产部署还有相当距离。
