# Oasis: Pooling PCIe Devices Over CXL to Boost Utilization

## 论文基本信息

- **标题**: Oasis: Pooling PCIe Devices Over CXL to Boost Utilization
- **作者**: Yuhong Zhong, Daniel S. Berger, Pantea Zardoshti, Enrique Saurez, Jacob Nelson, Dan R.K. Ports, Antonis Psistakis, Joshua Fried, Asaf Cidon (Columbia University, Microsoft Azure, Microsoft Research, UIUC, MIT)
- **会议**: SOSP 2025
- **Session**: Data Centers
- **PDF**: 3731569.3764812.pdf

## 研究背景

现代数据中心服务器中，PCIe 设备（如 NIC 和 SSD）占据了显著的资本支出（CapEx）和运营支出（OpEx）。在 Azure 平台中，NIC 和 SSD 的 CapEx 合计约达服务器总成本的 20-40%，同时各自贡献约 13% 的总服务器功耗。然而，这些 PCIe 设备在大多数时间都处于严重欠利用状态。Azure 生产集群的测量数据显示，平均 33% 的 SSD 容量处于"搁浅"（stranded）状态（即零利用），已分配的 NIC 带宽利用率也仅在 15% 左右。

造成低利用率的三大原因包括：（1）保守的资源分配策略——按峰值需求分配，导致大量资源被预留但闲置；（2）部分设备被预留但从不使用；（3）为应对 NIC 故障而部署的冗余 NIC 进一步拉低了整体利用率。传统的 PCIe 设备池化方案依赖 PCIe 交换机，但部署成本高昂（每机架约 $80,000），且缺乏灵活性，难以带来正向的投资回报率（ROI）。

近年来，CXL（Compute Express Link）内存池技术正在被云服务商广泛采用，用于提升内存利用率和降低成本。CXL Pod 由同一机架内的多台主机共享 CXL 内存设备构成，可动态分配内存。CXL 3.0 及更高版本规范引入了跨主机硬件一致性的支持，但目前尚无 CPU 或 CXL 设备实际支持该特性。

## 要解决的问题

如何利用已部署的 CXL 内存池，以接近零的额外成本实现 PCIe 设备的池化共享，从而在不显著增加性能开销的前提下，提升 NIC 和 SSD 的整体利用率，同时提供透明的高可用故障切换能力？

## 核心贡献

- **首个端到端软件原型**：首次通过实验证明，在当前可用的非一致性 CXL 2.0 设备上，完全可以在软件层面实现 PCIe 设备池化，性能开销可忽略。
- **统一的软硬件协同设计数据路径**：设计了跨 CXL 内存池的 I/O 数据路径，包含 I/O 缓冲区处理优化和非一致性共享内存上的高效消息通道，消息吞吐率提升 29 倍。
- **通用设备引擎框架**：采用类 VirtIO 的设计理念，通过为每类设备添加 Oasis Engine 即可支持不同 PCIe 设备类型（NIC、SSD 等）。
- **生产级实现与评估**：基于 Junction（前沿容器网络栈）实现了 Oasis 网络引擎，在生产级网络包回放测试中，NIC 聚合带宽利用率提升 2 倍，故障切换时间仅 38ms（UDP）和 133ms（TCP）。
- **量化 ROI 分析**：展示了 CXL 池化可同时服务于内存和 PCIe 设备池化，论证了 Oasis 的经济可行性。

## 主要研究方法

研究团队首先通过 Azure 生产集群的测量数据量化了 PCIe 设备低利用率的严重程度：33% 的 SSD 容量搁浅、15% 的 NIC 带宽利用率和 67% 的 SSD 容量利用率。然后，通过模拟分析论证了小规模 Pod 池化的潜力——8 台主机的 Pod 可将搁浅 SSD 容量从 33% 降至 7%，相当于减少 26% 的 SSD 部署量。

在技术路线上，研究团队选择了基于 CXL 共享内存的软方案，而非昂贵的 PCIe 交换机方案。核心设计挑战在于非一致性 CXL 内存上的高效消息通道和 I/O 缓冲区处理。

## 设计与实现

**整体架构**：Oasis 包含控制平面（Pod-Wide Allocator）和数据平面两大部分。数据平面为每类设备提供 Frontend Driver 和 Backend Driver 分离的结构：Frontend Driver 运行在每台主机上，为本地实例提供类型特定接口；Backend Driver 仅运行在直连设备的主机上，通过原生设备驱动（如 DPDK）操作设备。两者通过共享 CXL 内存上的消息通道通信。

**数据路径设计**（§3.2）：核心挑战是处理非一致性 CXL 内存上的 I/O 缓冲区一致性和消息传递。

（1）I/O 缓冲区一致性优化：利用 DMA 通常绕过 CPU 缓存的特性（禁用 DDIO 以规避安全风险），识别出 Backend Driver 端可安全消除大部分缓存行刷新的场景，而 Frontend Driver 端的刷新操作不可省略。

（2）高效消息通道：观察到非一致性内存上 CPU 缓存预取失效的根本原因是——接收方 CPU 缓存中的陈旧缓存行会阻止后续预取新消息。通过周期性失效已消费缓存行和预取缓存行，解决了这一根本问题，消息吞吐从 8.6 MOp/s 提升至 87.0 MOp/s（提升 29 倍）。

**网络引擎**（§3.3）：TX 路径中，实例将数据包写入共享 CXL 内存缓冲区，通过 IPC 通知 Frontend Driver，Frontend Driver 再通过消息通道通知 Backend Driver 由 NIC 执行 DMA 读取。Backend Driver 从不检查 TX 数据包缓冲区，确保了跨主机边界的安全性。RX 路径中，Backend Driver 接收数据包后，通过消息通道通知 Frontend Driver，使用 Flow Tagging（而非检查 RX 缓冲区）识别目标实例。故障切换方面，每个 Pod 预留一个备份 NIC，通过借用故障 NIC 的 MAC 地址实现快速故障转移，备份 Backend Driver 在实例启动时即完成注册。

**存储引擎**（§3.4）：设计与网络引擎镜像，使用 64B 消息（而非 16B），镜像 NVMe 命令格式。存储引擎将 I/O 错误传播给 guest，不透明处理 SSD 故障。

**Pod-Wide Allocator**：集中式控制平面，负责将设备映射到实例，处理负载均衡和故障转移。通过 Raft 复制实现高可用。

## 主要实验结果

**性能开销**（§5.1）：在 Python HTTP、Rust Rocket、nginx、Apache Tomcat 等典型 Web 应用中，Oasis 在 P50、P90 和 P99 延迟上仅增加 4-7 us 的开销，相比典型云网络延迟（50-110 us）可忽略。Memcached 测试中同样观察到 4-7 us 的稳定开销。延迟分解显示，大部分开销来自跨主机消息传递，CXL 内存缓冲区放置本身几乎不产生额外延迟。

**利用率提升**（§5.2）：使用生产环境 NIC 带宽包追踪回放，Oasis 通过多路复用两条主机的网络流量到单一 NIC，P99 延迟保持不变，实现了 2 倍的带宽利用率提升。

**故障切换**（§5.3）：UDP 回显服务器在 NIC 故障后约 38ms 内完成恢复；Memcached（TCP）在约 133ms 内完成 P99 延迟恢复。TCP 恢复时间更长是因为丢失的数据包在客户端累积，切换后需要额外时间传递。

**CXL 链路带宽消耗**：空闲时仅 0.2 GB/s 用于忙轮询；高负载（约 4 MOp/s）时消息通道消耗约 1.5 GB/s。1500B 数据包场景下，89% 的 CXL 链路带宽用于数据包缓冲区访问。

## 潜在问题 / 局限性

1. **CXL 链路故障**：当前方案未处理 CXL 链路/线缆故障，这被作者认为是最常见的 CXL 相关故障类型。需要冗余 CXL Pod 拓扑才能应对，论文将这一整合留作未来工作。

2. **CXL 带宽 QoS 控制**：当 CXL 链路被高带宽用例（如 OLAP 数据库）饱和时，Oasis 的性能可能受损。虽然论文指出当前 8x CXL 链路带宽与 200Gbps NIC 匹配，但未提供动态带宽分配的解决方案。

3. **评估规模有限**：实验仅使用两台主机的小规模设置，未涉及大规模 Pod 的可扩展性验证，也未在真实云生产环境中部署测试。

4. **SSD 引擎未实现**：存储引擎仅完成设计，尚未实现，意味着论文中最具挑战性的部分（跨主机 NVMe 操作）缺乏实验验证。

5. **生产网络集成**：实验拓扑过于简化（单一 Arista 7060X 交换机），未处理 VIP/DIP 映射、真实云负载均衡器集成等生产级挑战。

6. **对比基线选择有限**：主要对比的是 Junction（本地 NIC 使用），缺乏与 PCIe 交换机、多主机 PCIe 设备等替代池化方案的直接性能对比。

7. **NIC 备份资源开销**：每个 Pod 预留一个备份 NIC，虽然比每台主机预留一个冗余 NIC 更优，但仍需要占用实际硬件资源，该开销在评估中未被充分量化。

## 个人评注

Oasis 是 SOSP 2025 Data Centers 论文中技术深度和实用性结合较好的工作之一。其核心洞察——"CXL 内存池已被部署用于内存池化，可同时服务于 PCIe 设备池化"——具有重要的工程价值。技术实现层面，针对非一致性 CXL 共享内存的消息通道优化（解决预取失效问题）展示了扎实的系统功底。

不过，作为一篇来自工业界背景（Microsoft Azure + Microsoft Research + Columbia）的论文，其披露的信息量与顶级工业会议论文（如 OSDI/NSDI 上 Microsoft Research 的工作）相比偏少——特别是具体的 Azure 部署计划、实际 CXL 延迟数据和生产规模评估。38ms 的故障切换时间对于云环境来说是可接受的，但缺少与成熟替代方案（如 RDS/RoCE）的对比。

总体而言，Oasis 的设计原则是合理的，工程实现也是可信的，但其验证的完整性有待加强——特别是存储引擎的缺失和有限规模的评估令人略感遗憾。
