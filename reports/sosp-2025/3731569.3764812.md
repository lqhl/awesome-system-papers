# Oasis: Pooling PCIe Devices Over CXL to Boost Utilization

**作者**：Yuhong Zhong (Columbia University), Daniel S. Berger, Pantea Zardoshti, Enrique Saurez (Microsoft Azure), Jacob Nelson, Dan R. K. Ports (Microsoft Research), Antonis Psistakis (UIUC), Joshua Fried (MIT CSAIL), Asaf Cidon (Columbia University)

## 一、背景

现代数据中心服务器的 PCIe 设备（NIC、SSD、加速器）占据了相当可观的资本支出（CapEx）和运营支出（OpEx）。以 Azure 为例，NIC 和 SSD 各自贡献约 13% 的服务器功耗，两者合计约占服务器总成本的 20-40%。与此同时，CPU 和内存的高利用率研究已相当成熟，而 PCIe 设备利用率问题长期被忽视。

CXL（Compute Express Link）作为新一代互联标准，正被云厂商引入用于构建 CXL 内存池（CXL memory pool），以提升内存利用率和降低成本。CXL 2.0 设备已在市面上出现，可以在一个 CXL pod（同一机架内若干主机共享的 CXL 内存设备）中向多台主机提供共享内存访问。

---

## 二、要解决的问题

**PCIe 设备利用率低**：Azure 生产数据揭示了三层问题叠加：

1. **资源搁置（Stranding）**：由于不同工作负载对资源类型（CPU、内存、SSD、NIC）的需求比例不一，宿主机在某一维度达到上限时，其他资源无法分配给新实例。Azure 实测：27% 的 NIC 带宽和 33% 的 SSD 容量被搁置（零利用率）。

2. **分配后欠利用（Underutilization）**：网络流量具有高度突发性。即使是繁忙机架中最活跃的 4 台主机，聚合 NIC 带宽利用率在 P99.99 也不超过 20%。

3. **冗余 NIC 降低利用率**：为容忍 NIC 故障，部分云厂商为每台主机配备冗余 NIC，正常状态下这些 NIC 基本闲置。

**现有解决方案的不足**：

- **PCIe 交换机**：每机架增加成本高达 $80,000，且每种类型的 PCIe 交换机仅支持特定设备类别，缺乏灵活性。
- **RDMA 解聚合**：无法解聚合 NIC 本身（NIC 是 RDMA 的底层基础），也无法支持缺乏 P2P DMA 的设备类型。

**核心挑战**：CXL 2.0 内存池在主机间**没有硬件缓存一致性**，这使得跨主机的 I/O 缓冲区访问和信令传递面临数据一致性问题。

## 三、核心设计

Oasis 利用 CXL 内存池作为跨主机数据通路，在软件层实现 PCIe 设备池化。架构分为两层：

**数据通路（Common Datapath）**

- **I/O 缓冲区放置在共享 CXL 内存中**：前端驱动（Frontend Driver，位于发出 I/O 的主机）将 TX/RX 缓冲区分配在共享 CXL 内存，PCIe 设备通过 DMA 直接访问这些缓冲区。由于 NIC/SSD 的 DMA 通常绕过 CPU 缓存（DDIO 在多租户云环境中推荐禁用），后端驱动（Backend Driver，位于拥有实际设备的主机）无需发起 CPU 缓存失效操作，大幅降低开销。

- **针对非一致性 CXL 内存的消息通道**：Oasis 设计了一套基于环形缓冲区的消息通道，用于前端–后端之间的 I/O 请求和完成信号传递。关键优化：
  - 接收端消费完一个 cache line 中所有消息后，主动失效该 cache line，使 CPU 预取器能从 CXL 内存获取新消息（"+Invalidate Consumed"）；
  - 预取本身可能带入 stale cache line，进一步在空轮询时对预取的 cache line 也执行失效（"+Invalidate Prefetched"）；
  - 以上两步将消息通道吞吐量从 3.0 MOp/s 提升至 87.0 MOp/s，延迟从 1.2 µs 降至 0.6 µs。

**控制平面：Pod-Wide Allocator**

- 逻辑中心化的服务，维护实例到 PCIe 设备的权威映射；
- 通过可续租（renewable lease）机制处理设备分配、负载均衡和故障转移；
- 状态存储在共享 CXL 内存中，通过 Raft 复制实现高可用；
- 不在 I/O 关键路径上。

**设备引擎（Device Engines）**

Oasis 提供通用数据通路，不同设备类型通过各自的引擎插件扩展：
- **网络引擎（Network Engine）**：基于 Junction 容器网络栈实现 NIC 池化。前端驱动为本地实例提供虚拟 NIC 接口；后端驱动使用 DPDK NVIDIA MLX5 驱动操作实际 NIC 队列对。TX 方向：实例将报文写入 CXL，前端写回缓存后通过消息通道通知后端，后端提交 WQE 给 NIC DMA 读取；RX 方向：NIC 将收包写入 CXL 中的 RX 缓冲区，后端通过消息通道通知前端，前端拷贝到实例本地内存（用于隔离）。
- **存储引擎（Storage Engine）**：设计已完成但未实现，使用 64B 消息（对应 NVMe 命令格式），通过 SPDK NVMe 驱动操作 SSD 队列。

**NIC 故障转移**：每个 pod 预留一个备用 NIC。故障发生时，备用 NIC "借用"故障 NIC 的 MAC 地址发包，触发 ToR 交换机更新 MAC-to-port 映射，实现 RX 流量自动重路由，无需应用感知。

## 四、实现细节

- 网络引擎约 7,000 行 C++，基于 Junction（高性能容器网络栈）实现；
- 实验平台：两台 AMD EPYC 主机 + 一台 CXL 2.0 内存设备，各通过 ×8 CXL lanes 连接，每台主机配备 100 Gbit Mellanox ConnectX-5 NIC；
- Linux 内核 6.8.0，CXL 内存通过 DAX 设备暴露；
- 每台主机为前端和后端驱动各占用 1 个专用轮询核心；
- 消息通道：8192 个槽位，网络引擎用 16B 消息，存储引擎用 64B 消息；epoch bit 机制判断新消息；接收方维护消费计数器，批量更新（默认每消费半个通道容量更新一次）以减少 cache coherence 操作。

## 五、实验结果

### 性能开销

| 应用 | 基线 P50 延迟 | Oasis 额外开销 |
|------|------------|--------------|
| Python HTTP | ~5 µs | +4–7 µs |
| Rust Rocket | ~5 µs | +4–7 µs |
| nginx | ~10 µs | +4–7 µs |
| Apache Tomcat | ~15 µs | +4–7 µs |
| memcached | ~5 µs | +4–7 µs |

- UDP 微基准（75B 和 1500B 报文）均显示 4–7 µs 额外延迟，与报文大小无关；
- 延迟开销主要来自跨主机消息传递（前后端通信），而非 I/O 缓冲区放置在 CXL（几乎零开销）；
- 重负载时 CXL 链路带宽占用：空闲 0.2 GB/s（消息轮询），75B 报文满载 2.3 GB/s，1500B 报文满载 13.5 GB/s（远低于 256 GB/s 的 CXL 链路总容量）。

### 利用率提升

重放 Azure 生产网络包追踪：两台主机共享单个 NIC，P99.99 聚合 NIC 带宽利用率从 18% 提升至 37%（约 2×）；host2 P99 延迟仅增加 1 µs。

### 故障转移

| 场景 | 中断时间 |
|------|--------|
| UDP 故障转移 | 38 ms 报文丢失窗口 |
| TCP（memcached）故障转移 | P99 延迟恢复约 133 ms |

对比参照：实例快照迁移需秒级甚至更长；基于 Raft 的状态复制在主节点失效时选举本身就需要数百毫秒。

## 六、批判性分析

**实验规模过小，说服力存疑**：整篇论文的评估仅使用 2 台主机 + 1 台 CXL 设备。CXL pod 的关键价值在于多主机聚合共享，但 2 台主机的配置无法充分验证扩展性（尤其是消息通道在高并发多实例场景下的表现、pod-wide allocator 的调度延迟）。"只需 2 台主机即可说明问题"这一前提本身值得怀疑——利用率提升的核心逻辑依赖于统计复用，而 2 台主机的统计效应太弱。

**核心 claim 依赖 Azure 内部数据，但复现性为零**：利用率数据（27% NIC stranding、P99.99 仅 20% 利用率）来自 Azure 生产追踪，读者无法验证；文章也未讨论这些数据的代表性（不同业务类型、不同时段差异可能很大）。

**存储引擎"设计了但未实现"**：SSD 池化是论文动机的核心组成部分（33% stranding），但实验评估完全只有 NIC。论文自称"first system to pool PCIe devices"，实际上只评估了一种设备类型。

**故障转移机制的局限被轻描淡写**：Oasis 的 NIC 故障转移依赖借用 MAC 地址通知 ToR 交换机更新端口映射。论文承认这在使用 VIP/DIP 的生产云网络中行不通，需要集成 cloud load balancer。但这不是一个简单的 future work——生产级云网络的负载均衡层本身就是高度复杂的系统，集成难度被严重低估。

**CXL 链路故障未解决**：论文承认 CXL link/cable 故障是最常见的 CXL 故障模式，但将解决方案完全推给 future work。如果 CXL 链路断了，整个池化方案就失效了——这是比 NIC 故障更严重的单点故障。

**"near-zero extra cost"的成本论证存在循环逻辑**：论文的核心经济论点是"CXL 内存池已经因内存利用率收益而有经济价值，因此在此之上叠加 PCIe 池化几乎没有额外成本"。但这一论点的成立前提是 CXL 内存池本身已经部署——而这恰恰是一个尚不普遍的假设。

## 七、AI Infra / MLSys 视角

Oasis 本身针对通用 PCIe 设备（NIC/SSD），与 AI 系统的直接关联在于 GPU/加速器池化。论文的 Oasis 架构设计通过"引擎插件"机制支持新设备类型，理论上可扩展至 GPU 加速器。

**对 AI Infra 的借鉴价值**：

- **GPU 池化**：大型 AI 训练集群中，GPU 内存（HBM）和 NVLink 带宽也存在利用率不均问题。CXL 路由 PCIe 流量的思路可以为 GPU disaggregation 提供低成本的新路径。目前业界主流的 GPU 池化方案（如 Liquid Liqid、NVIDIA GPUDirect）仍依赖 PCIe 交换机或 RDMA；Oasis 的软件方案若能扩展至 GPU，成本优势明显。
- **KV cache 卸载**：LLM 推理中 KV cache 的跨节点卸载目前主要依赖 RDMA 或 NVMe-oF。Oasis 的 SSD 引擎设计方向（CXL 路由 SSD DMA）可以提供比 NVMe-oF 更低的延迟路径。
- **消息通道设计**：Oasis 对非一致性 CXL 内存上高吞吐消息通道的分析（prefetch + selective invalidation）是一个具有普适价值的技术 insight，适用于任何基于 CXL 共享内存的跨主机通信场景（如分布式 KV 存储、参数服务器）。

**值得跟进的方向**：
1. 将 Oasis 扩展至 GPU/加速器，评估 AI 训练/推理中 accelerator 利用率的提升空间；
2. 基于 Oasis 消息通道，探索 CXL 上的低延迟 collective 通信原语（all-reduce、broadcast）作为 RDMA 的替代或补充；
3. 结合 LLM 推理中 disaggregated prefill/decode 场景，评估 CXL 路由 KV cache 的端到端延迟和吞吐收益。

---

## 八、总结

Oasis 是首个基于软件的 PCIe 设备池化系统，利用已部署的 CXL 2.0 内存池作为跨主机 I/O 数据通路，以近乎零额外硬件成本实现 NIC 和 SSD 的动态共享与故障转移。其核心技术贡献是一套针对非一致性共享 CXL 内存的高效消息通道设计（吞吐 87 MOp/s，延迟 0.6 µs）。评估显示 NIC 池化带来 2× 利用率提升，端到端应用延迟开销仅 4–7 µs（典型云网络延迟的 5-10%），NIC 故障转移仅 38 ms。主要局限在于：实验规模仅 2 台主机，SSD 引擎未实现，CXL 链路故障未解决，以及在真实生产网络（VIP/DIP 体系）中的集成路径尚不清晰。
