# DiffKV: Differentiated Memory Management for Large Language Models with Parallel KV Compaction

**作者**：Yanqi Zhang, Yuwei Hu, Runyuan Zhao（Huawei Technologies）；John C.S. Lui（The Chinese University of Hong Kong）；Haibo Chen（Shanghai Jiao Tong University）

## 一、背景

大型语言模型（LLM）在对话、编程、数学推理等领域展现出强大能力，但其推理服务代价高昂。自回归推理中，为避免重复计算，框架将每一步的 key/value 张量缓存在 GPU 显存中，即 KV cache。KV cache 大小与序列长度和并发请求数成正比，在现代长上下文模型（如 128K context window）和 thinking model（DeepSeek-R1、QwQ-32B）大量生成 chain-of-thought 的场景下，KV cache 占用超过 90% 的显存，成为吞吐量的核心瓶颈。

主流缓解手段分为两类：**pruning**（按 attention score 丢弃不重要的 token）和 **quantization**（以低比特表示 KV 向量）。这两类方法均以"一刀切"方式处理所有 token、所有 attention head、以及 key 和 value 向量，忽视了 KV cache 内部的细粒度差异性。

---

## 二、要解决的问题

1. **Key 与 Value 重要性不同**：现有量化方案对 key 和 value 采用相同精度，忽视了 key 向量（通过 softmax 影响所有 token 的注意力权重）比 value 向量（仅影响其自身贡献）发挥更广泛影响的事实。

2. **Token 重要性分布不均**：现有 pruning 方法要么直接丢弃，要么均匀量化。然而 attention score 分布极度不均——少数 token 得分极高，大量 token 得分接近零——应当针对不同重要性采用不同精度。

3. **Per-head 动态稀疏性被忽视**：每个 attention head 在不同请求下有截然不同的稀疏模式，同一 head 在不同 token 序列下所需保留的 critical token 数量差异巨大。现有方法均匀分配内存预算，无法利用 per-head 动态稀疏性。

4. **内存管理的可扩展性**：三个层次的差异化导致每个 head、每个请求的显存需求各不相同，产生高度碎片化的内存分布。即便 Llama3-8B 这类中等规模模型也有数百个 attention head，配合数百并发请求，每推理步需管理数万个异构内存块，若处理不当将完全抵消 KV 压缩带来的收益。

---

## 三、核心设计

DiffKV 提出三层差异化的 KV cache 压缩框架，并配以 GPU 端并行内存管理机制。

### 3.1 三层差异化压缩策略

**层次一：Key/Value 差异化精度**
- Key 向量量化到较高精度（如 INT8），Value 向量量化到较低精度（如 INT4），即 K8V4 或 K4V2。
- 动机来自数学分析：将 attention 改写为 `Σ softmax(QK^T/√d)·|v_j| · (v_j/|v_j|)`，其中 attention score 的数值范围跨 7 个数量级，远大于 value 向量 L2 norm 的 2 个数量级差异，说明 key 对输出贡献更为关键。

**层次二：Token 重要性分级压缩**
- 基于 attention score 将 token 分三档：最重要的存为高精度（K8V4），次重要的存为低精度（K4V2），最不重要的直接剪枝。
- 阈值使用理论平均值 `1/N`（N 为序列长度）的倍数 `αh/N` 和 `αl/N` 来自适应控制，序列越长可压缩越激进，序列越短保留更多 token 以维持质量。

**层次三：Per-head 动态稀疏性**
- 每个 attention head 独立判断 token 重要性、独立分配内存，无需跨 head 强制统一 budget。
- 同一请求的不同 head 可能有截然不同的压缩比，从而充分利用各 head 的真实稀疏模式。

### 3.2 并行 KV Compaction 内存管理

三层差异化压缩导致内存分配模式高度不规则，DiffKV 引入三个 GPU 常驻数据结构：

**Unified Pages**：GPU 显存切分为等大小的 page，每个 page 在分配时动态配置以存储特定精度（如 K8V4 或 K4V2）的 token。单个 page 包含六个段：quantized keys、key 量化元数据（scale/zero point）、quantized values、value 量化元数据、token scores、token positions。

**Circular Free Page List**：一个 GPU 端环形链表管理所有 page ID，通过 `start_ptr`（分配）和 `end_ptr`（回收）两个指针维护可用区域始终连续，从而允许用**并行前缀和（prefix sum）**一次性批量分配或回收所有 head 所需的 page，将复杂度从串行 O(#heads) 降至常数次 GPU kernel。

**Bidirectional Page Table**：每个 attention head 维护一个双向 page table，高精度 page ID 从左侧生长，低精度 page ID 从右侧生长，无需分开维护两套数据结构，元数据开销极低（Llama3-8B 批大小 128 时仅 32MB，而单请求 KV cache 占 1GB）。

### 3.3 自定义 Attention Kernel

针对混合精度 KV cache 设计了可移植的 GPU attention kernel：
- 每个 thread block 处理单个 head 的单个序列；
- Key 处理：使用 `[K_vec×F/K_group, N_tokens, K_group, K_vec]` 布局实现 coalesced 内存访问和向量化读取；
- Value 处理：使用 `[V_F, N_tokens, V_group, V_vec]` 布局沿 token 维度向量化，避免沿特征维度向量化时增加寄存器压力；
- 支持沿序列维度分段并行，适用于超长序列。

## 四、实现细节

- 基于 vLLM 实现，共 4,500 行 CUDA/C++ 代码 + 9,000 行 Python 代码。
- 压缩参数 `αh` 和 `αl` 通过在 MATH 数据集训练集上 profiling 确定，对不同模型（Llama3-8B/70B, Qwen2.5 系列, QwQ-32B）选取各自最优值。
- KV Compaction 每推理步执行一次，覆盖全 batch 所有 layer，以摊销 GPU kernel 启动开销。
- Prompt 阶段：保守分配后执行 planning（每 head 独立计算需求）+ coordination（prefix sum 批量回收多余 page）；
- Generation 阶段：每步每 head 至多分配一个新 page，无需 page 回收（token 数量只增不减），请求结束时批量释放。
- 支持扩展到三层或四层精度（通过增加单向/双向 page table 组合），保留设计正交性。

## 五、实验结果

**实验环境**：NVIDIA L40 GPU（48GB），部分实验在 Ascend NPU 上验证可移植性；多 GPU 并行（Llama3-70B：4×GPU，Qwen2.5-32B/QwQ-32B：2×GPU）。

**评测模型**：Llama3-8B/70B，Qwen2.5-7B/32B，QwQ-32B，R1-Distill-Qwen-14B，R1-Distill-Llama-8B。

**基线**：vLLM（FP16），H2O、SnapKV、DuoAttention（pruning），INT4 KV、KIVI、QAQ、Atom（quantization），Quest（KV partial loading）。

## 六、批判性分析

**1. 压缩比与精度宣称存在选择性报告**

论文核心 claim 是"2.7× 至 5.7× 压缩比，near-lossless 精度"。但实际上：
- 2.7× 对应的是最保守的参数配置（αh=1），5.7× 只在特定模型/任务下成立；
- "near-lossless"以平均 0.3% 降幅定义，掩盖了个别基准上更大的波动（如 HumanEval+ 在 Qwen2.5-7B 的 1.6% 下降不算小）；
- Qwen2.5-7B 因 GQA 的高 queries-per-KV 比（7:1），作者不得不**关闭低精度量化**，这意味着该模型实际上只使用了单层量化（K8V4），而非完整的三层差异化策略——这是一个被轻描淡写的退化情况。

**2. 参数 calibration 的泛化性存疑**

αh 和 αl 在 MATH 训练集上校准，理由是其信息密度高、泛化能力强。但实验显示不同模型、不同任务需要截然不同的 αl 值（Llama3-8B 用 0.02，Qwen2.5-7B 用 0.04，其他用 0）。这说明参数对模型架构/训练数据高度敏感，难以"一次 calibration 搞定所有场景"，实际部署时 calibration 开销不容忽视。

**3. 吞吐量测试场景过于理想**

吞吐量实验全部使用 MATH 数据集（需要长 CoT 生成），这是 DiffKV 最有利的场景——序列越长，KV cache 占比越高，压缩收益越大。对于短序列、chat 场景或 batch size 较小的场景，吞吐量改善可能远不及宣称的 5.4×。论文未提供 short-context 场景的吞吐量对比。

**4. 自定义 attention kernel 性能缺口未充分解释**

K8V8（理论 2× 加速）只实现 1.7× 实际加速，论文归因于量化元数据访问和 dequantization 开销，但对这一 15% 差距没有深入分析。更重要的是，论文未对比 FlashAttention-3 或 FlashInfer 等高度优化的 attention 实现，使得 kernel 性能基准比较偏保守。

**5. 多 GPU 场景的 Compaction 协调开销未讨论**

论文测试了 4 GPU 的 Llama3-70B，但对多 GPU 间 KV Compaction 的协调机制（如 NVLink 带宽、同步开销）未做任何分析，读者无法判断扩展性是否成立。

## 七、AI Infra / MLSys 视角

**对 AI Infra 研究的核心启示**

1. **Key-Value 非对称性是被低估的 insight**：将 attention 分解为 coefficient（由 key 主导）和 unit vector（由 value 主导）的视角，为 KV cache 非对称压缩提供了理论基础。这一分解可以推广：未来 GQA/MLA（Multi-head Latent Attention，DeepSeek-V2）等架构下的压缩策略设计可借鉴此框架。

2. **Per-head 动态 budget 是正确方向**：静态 budget 分配是现有 pruning 方法的主要瓶颈，DiffKV 的 per-head 动态分配思路对于 MoE 模型（不同 expert 激活不同）和 sparse attention 架构同样值得探索。

3. **GPU 端内存管理的 prefix-sum 范式**：Circular Free Page List + parallel prefix sum 是一种通用的 GPU 端动态内存管理模式，不局限于 KV cache，可以迁移到 activation checkpointing、dynamic batching 等有类似碎片化内存问题的场景。

**值得跟进的 future work**

- **与 MLA/GQA 架构深度整合**：DiffKV 在 GQA 下有性能退化（Qwen2.5-7B 被迫关闭 K4V2），探索如何针对 GQA 的 shared KV head 设计专属压缩策略是高价值研究方向。
- **与 speculative decoding 结合**：Speculative decoding 可以大幅提升 token 生成速度，但会引入 KV cache 分叉和回滚，探索 DiffKV 与 speculative decoding 的兼容性（尤其是 draft token 的 KV 如何管理）是潜在切入点。
- **在线 calibration 替代离线 profiling**：当前 αh/αl 需要离线 calibration，对新模型/新 workload 不友好。研究基于实时 attention score 统计的在线自适应参数调整，减少人工干预，是工程上的重要改进方向。
- **KV Compaction 与 continuous batching 的交互**：vLLM 的 continuous batching 下请求动态加入/退出，DiffKV 的 page 分配如何与 preemption/recomputation 高效交互，论文未深入讨论。

## 八、总结

DiffKV 通过三层细粒度差异化（Key/Value 非对称量化、token 分级压缩、per-head 动态稀疏性）将 LLM KV cache 压缩至 20%–37% 的显存占用，同时将精度损失控制在 0.3% 以内，并通过 GPU 端 parallel KV compaction 将内存管理开销压缩至推理总延迟的 1% 以下。系统在 thinking model 场景（QwQ-32B，长 CoT 生成）中取得 5.4× 吞吐量提升，是首个针对 thinking model 系统性评估 KV cache 压缩的工作。主要局限在于：Qwen 等 GQA 模型下策略退化、calibration 参数敏感性高、以及吞吐量评测场景偏向长序列，在 chat 等短序列场景的实际收益仍有待验证。
