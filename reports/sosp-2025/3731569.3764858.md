# Optimistic Recovery for High-Availability Software via Partial Process State Preservation

**作者**：Yuzhuo Jing, Yuqi Mai, Angting Cai, Yi Chen, Wanning He, Xiaoyang Qian, Peter M. Chen, Peng Huang (University of Michigan)
**会议**：SOSP 2025
**链接**：https://doi.org/10.1145/3731569.3764858
**源文件**：[[3731569.3764858.pdf]]

---

## 一、背景

高可用性是大规模部署软件的核心需求，即使短暂的服务中断也会影响大量用户并造成显著的经济损失。生产系统不可避免地会遇到 crash、hang、内存泄漏等软件故障，需要快速且正确地恢复服务。

现有的恢复技术面临一个根本性的二元困境：要么丢弃所有状态（进程重启），保证正确性但恢复时间长；要么保留所有状态（checkpoint），恢复快但可能将 buggy state 一并保留，导致恢复后仍然出错。以 Redis 为例，一个 6GB RDB 文件的加载需要 53.5 秒，之后还需要 361.7 秒才能恢复到 90% 的稳定吞吐量。这种漫长的恢复和 warm-up 时间在生产环境中普遍存在。

---

## 二、要解决的问题

1. **进程重启的高可用性代价**：全量重启需要从磁盘重新加载数据、重放日志、重建缓存，导致长时间的 downtime 和 warm-up period，期间系统实质上不可用。

2. **Checkpoint 的正确性风险**：CRIU 等全量 checkpoint 机制虽然加速恢复，但不区分正常状态和 buggy state，如果 checkpoint 在 bug 发生之后被捕获，恢复后仍会触发同样的故障。

3. **Microreboot 的改造成本**：Microreboot 和 Orleans 等方案要求将应用重构为松耦合的可独立重启组件，对现有大型应用的改造成本过高。

4. **缺乏中间方案**：现有技术要么 preserve all，要么 preserve none，缺少选择性保留部分状态的系统化支持。

## 三、洞察与设计

**关键洞察**：大多数生产环境中的软件故障仅影响临时状态（局部变量、短生命周期的堆对象），不会破坏大型、稳定的全局数据结构。对 6 个流行服务器应用的 64 个真实 bug 的研究表明，87.5% 的故障仅破坏临时状态或完全不破坏任何状态。这种"bug 集中在复杂的控制逻辑中，而大量内存被简单、经过充分测试的数据结构占据"的不对称性，使得选择性状态保留在实践中是可行的。

基于此洞察，PHOENIX 引入了"乐观定制恢复"的新设计点：

- **Fresh Restart with In-memory Preservation**：PHOENIX 不替代应用的默认恢复机制，而是添加一条快速路径——PHOENIX-mode restart。新进程从 `main()` 开始执行（如同正常重启），但选择性地继承上一个进程的部分内存状态。这样既获得了重启的"重置执行"优势（丢弃 transient state），又避免了全量重建的开销。

- **Zero-Copy Transfer**：通过内核级 `preserve_exec` 系统调用，直接操作 page table entries 将选定的内存页从旧进程迁移到新进程的地址空间，无需数据拷贝。保留的页面安装在原始虚拟地址，避免了指针 swizzling 的开销，且兼容 ASLR。

- **Unsafe Region**：用于判断 crash 时保留状态是否一致。开发者（或静态分析工具）标记修改可保留数据的代码区间。如果故障发生在 unsafe region 内，说明数据可能处于部分修改的不一致状态，PHOENIX 回退到默认恢复路径。

- **Cross-Check Validation**：可选的更强正确性保证。PHOENIX 重启后立即开始服务请求（投机执行），同时在后台 fork 一个进程运行默认恢复，比较两者的初始状态。若一致则继续；若不一致则热切换到经过验证的进程。

- **Section-Based Preservation**：引入 `.phx.data` 和 `.phx.bss` ELF sections，开发者用 `phxsec` 宏标注需要保留的静态变量，避免逐个变量手动导出的繁琐工作。

- **Progress Recovery**：对于长时间计算型任务（如 XGBoost），引入 `phx_stage` API 支持基于阶段的恢复，从最近的一致 stage 恢复而非从头重算。

## 四、实现细节

PHOENIX 的实现横跨内核、运行时库、修改版 glibc 和 LLVM 编译器工具。

**内核**：实现了 `preserve_exec` 系统调用，创建空页表后将保留范围的 PTE 从旧页表迁移到新页表，然后加载新的可执行镜像。另有私有系统调用用于保留 `link_map` 数据结构（动态链接器所需）。

**Malloc 集成**：修改 glibc malloc，添加 bookkeeping 追踪 mmap-backed pages（arena 小对象和直接映射大对象）和 brk 范围，支持 over-approximate heap preservation。在 `malloc_chunk` 元数据中增加 marker bit，支持 mark-and-sweep GC 清理未引用的堆对象。

**静态分析工具**：基于 LLVM 构建的分层分析算法，自动标注 unsafe region。将函数执行分为 U（未修改）、M（修改中）、E（修改结束）三个阶段，通过 def-use 分析确定 taint set，递归分析调用链以精确定位修改边界。优先保证 completeness 而非 soundness（标注的 unsafe region 可能偏大但不会遗漏）。

**应用集成**：在 6 个大型应用上集成（Redis、LevelDB、Varnish、Squid、XGBoost、VPIC），平均修改 260.2 行代码（占代码库的 0.52%）。

| 系统 | 代码规模 | 保留状态 | 总修改行数 |
|------|---------|---------|-----------|
| Redis | 140,996 | In-mem KV hashtable | 348 |
| LevelDB | 21,192 | Skiplist memory tables | 312 |
| Varnish | 109,564 | Web page cache objects | 281 |
| Squid | 186,219 | Web page cache objects | 190 |
| XGBoost | 38,906 | Gradients and model | 158 |
| VPIC | 44,773 | Particles and physical fields | 272 |

## 五、实验结果

**实验平台**：Intel Xeon Silver 4114 @ 2.20GHz, 192GB ECC 内存, 480GB Intel SSD, Ubuntu 22.04。

**微基准**：4MB 以下保留状态的重启延迟约 1.20ms（几乎恒定），32MB 为 1.56ms，32GB 为 220.6ms（线性增长）。基线无状态保留的进程重启为 1.02ms。

**真实 Bug 恢复（17 个案例）**：

| 指标 | PHOENIX 表现 |
|------|-------------|
| 恢复成功率 | 16/17（R2 heap corruption 主动回退） |
| Redis downtime | 比 Vanilla 降低 9×，比 Builtin 降低约 50× |
| 恢复后可用性 | 2 秒内恢复 pre-failure 性能 |
| XGBoost | 比 Builtin 早 49.1s 完成，不可用时间降低 19.8× |
| VPIC | 不可用时间降低 76.4× |

**大规模 Fault Injection（8,400 次注入）**：

| 配置 | 成功恢复率 | 额外数据损坏 |
|------|-----------|-------------|
| 含 Unsafe Region | 85.6%（7,190/8,400） | 0 |
| 不含 Unsafe Region | 更高成功率但有损坏风险 | 26 次 |
| Unsafe Region + Cross-Check | 类似成功率，更早检测 bad state | 0 |

**运行时开销**：PHOENIX 平均 2.7%，Builtin 3.1%，CRIU 22.5%。

**内存复用率**：平均 88.4%（Redis 90.4%, Varnish 91.3%, VPIC 83.6%）。

## 六、批判性分析

1. **状态选择方法论的普适性存疑**：论文提出的"保留最大的几个数据类型"方法在 6 个评估应用上有效，但这些应用都有较为清晰的"大型稳定数据 + 小型复杂逻辑"的结构。对于状态更复杂、数据结构间耦合更紧密的应用（如分布式数据库的事务引擎），这种简单的启发式是否仍然适用缺乏验证。

2. **开发者负担被低估**：虽然论文报告平均仅修改 260 行代码，但这需要开发者深入理解应用的状态语义、数据结构的修改路径以及恢复逻辑。LevelDB 的移植需要一名博士生 4 天（其中 2 天用于调试 sequence number 逻辑的正确性问题），Varnish 需要一名本科生一周。这些隐性成本在"行数"指标中无法体现。

3. **Unsafe Region 的精度与覆盖率矛盾**：静态分析工具优先保证 completeness 导致 unsafe region 偏大（Redis 仅 3.9% 时间在修改保留数据，但编译器标注导致 false positive fallback）。关闭 unsafe region 后成功率从 90.1% 提升至 93.4%（Redis），但引入了数据损坏风险。这意味着实际部署中需要在可用性和正确性之间做微妙的权衡。

4. **Cross-Check Validation 的限制未充分讨论**：Cross-Check 假设默认恢复产生的参考状态 $S_r$ 是正确的，但如果默认恢复本身有问题（如从损坏的磁盘文件加载），Cross-Check 会通过但状态实际不正确。此外，投机执行窗口内的错误输出被视为可接受的代价，但对于金融等对正确性极度敏感的场景，这个窗口内的错误可能是不可接受的。

5. **静态分析工具的语言限制**：作者承认 C++ 的精确分析因 STL 内联和不透明内部函数使用而困难。考虑到现代服务器应用大量使用 C++（评估的 6 个应用中有 3 个是 C++），这是一个重要的实用性限制。外部库函数需要手动标注也增加了维护成本。

6. **Fault Injection 的代表性**：注入的故障类型（比较反转、缺失赋值、错误操作数等）是 LLVM IR 级别的合成故障，与真实的软件 bug 的分布可能存在差异。17 个真实 bug 案例虽有说服力，但样本量偏小。

## 七、AI Infra / MLSys 视角

1. **Checkpoint 优化的启发**：大型 LLM 训练中 checkpoint 开销是核心痛点。PHOENIX 的"选择性保留 + 重置执行"思路可以启发训练系统的恢复设计——例如，保留 model parameters 和 optimizer state，但丢弃 activation cache、communication buffers 等临时状态，实现比全量 checkpoint 恢复更快的 warm restart。

2. **推理服务的快速恢复**：vLLM 等推理引擎持有大量 KV cache，其结构与 Redis 的 hashtable 类似（大型稳定数据 + 复杂调度逻辑）。PHOENIX 的 partial state preservation 可以直接应用于推理服务，在 crash 后保留 KV cache 和模型权重，仅重建调度状态，显著减少 cold start 时间。

3. **Progress Recovery 对长训练任务的价值**：`phx_stage` API 的 stage-based recovery 与训练中的 epoch/step 天然对应。相比传统 checkpoint（写入磁盘 + 重放），PHOENIX 的内存级 stage recovery 可以将故障恢复从分钟级降低到秒级，对于大规模训练集群的资源利用率提升有直接价值。

4. **可操作的研究方向**：
   - 将 PHOENIX 的 zero-copy preserve_exec 机制扩展到 GPU 内存（如通过 CUDA UVM 或 GDR），实现 GPU 进程的部分状态保留
   - 在分布式训练场景中结合 PHOENIX 和 lineage-based recovery，实现单节点内存级快速恢复 + 跨节点计算图级 replay
   - 探索 PHOENIX 在 model serving 场景下的 KV cache preservation，量化对 TTFT 和 throughput 的影响

---

## 八、总结

PHOENIX 提出了一种介于"全量丢弃"和"全量保留"之间的乐观恢复方案，通过内核级 zero-copy 页表迁移实现选择性进程状态保留，配合 unsafe region 检测和 cross-check validation 保障正确性。在 6 个大型服务器应用和 17 个真实 bug 上的评估表明，PHOENIX 将恢复时间从分钟级降至亚秒级，同时维持接近 100% 的恢复后性能，运行时开销仅 2.7%。该方案最适合"大型稳定数据 + 复杂控制逻辑"结构的服务器应用，对于状态耦合紧密或频繁修改全局状态的应用效果有限。主要局限在于需要开发者具备对应用状态语义的深入理解，以及静态分析工具对 C++ 支持不足。
