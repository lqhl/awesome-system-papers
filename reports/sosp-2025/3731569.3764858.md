# Optimistic Recovery for High-Availability Software via Partial Process State Preservation

## 论文基本信息
- **标题**: Optimistic Recovery for High-Availability Software via Partial Process State Preservation
- **作者**: Yuzhuo Jing, Yuqi Mai, Angting Cai, Yi Chen, Wanning He, Xiaoyang Qian, Peter M. Chen, Peng Huang (University of Michigan)
- **会议**: SOSP 2025
- **Session**: Reliability and Performance
- **PDF**: 3731569.3764858.pdf

## 研究背景

可用性（Availability）对大规模部署的软件至关重要——即使短暂的停机也会影响大量用户并造成重大经济损失。然而，生产系统不可避免地遭遇各类故障（crash、hang、memory leak）。高可用性不仅要求快速恢复，更要求恢复后系统能够立即以接近正常的性能继续服务。如果系统看起来"可用"但实际上几乎无法处理请求或响应极慢，它实际上对用户是不可用的（effective availability）。

软件恢复领域的现有方法存在根本性矛盾：**保留全部状态 vs 丢弃全部状态**。Process restart 丢弃所有内存状态，保证正确性（避免 buggy state）但遭受长时间停机——进程必须从磁盘读取大文件、重放日志、从网络拉取更新等，重建缓存在此期间系统完全无法服务请求，且恢复后还有很长的 warm-up 时间。Checkpoint（如 CRIU）通过定期保存完整内存快照改善了停机时间，但以 preserve-all 为代价——如果 checkpoint 发生在 bug 之后，buggy state 也被持久化了，导致不正确的恢复。持久化内存（persistent memory）和 whole-system persistence 技术将内存设为非易失的，实现即时恢复，但仍会保存 buggy state。

这种两难困境的深层原因在于：**现代服务器应用程序中，bug 和字节的分布极不均衡**。大多数 bug 集中在少数复杂的控制逻辑代码中（虽然内存占比较小），而大多数程序状态被大量由简单、经过充分测试的逻辑管理的数据结构占据（如 Web cache server 的大部分内存用于缓存页面，仅用少量数据类型）。例如，Redis 将大部分内存用于 key-value hashtable，而请求处理和调度代码虽然更复杂但内存占用小得多。

## 要解决的问题

如何在软件故障后同时实现快速恢复、恢复后接近正常的性能，同时保证正确性？

具体来说：现有方法无法同时兼顾以下三个目标：
1. **停机时间短**：不花费大量时间重建状态
2. **恢复后性能好**：保留有价值的 in-memory 状态（缓存、连接池等），避免冷启动
3. **正确性**：不保留 buggy 或 inconsistent 状态

## 核心贡献

- 提出一种新的设计点：**Optimistic Custom Recovery through Partial Process State Preservation**。在 common case 中，PHOENIX 模式恢复保留有价值的长期状态（long-lived state），丢弃瞬态状态（temporary state），重置执行——结合了 full restart 的有效性和 state reuse 的速度。
- 设计并实现 PHOENIX，一个跨越 OS kernel、runtime、libc 和 compiler 的完整解决方案，提供简单 API 用于选择性状态标注、支持 unsafe region 检测的一致性验证、以及 cross-check validation 提供强正确性保障。
- 在六种大型服务器应用（Redis、LevelDB、Varnish、Squid、XGBoost、VPIC）上应用 PHOENIX，并在 17 个真实 bug 上评估，证明 PHOENIX 恢复显著改善可用性而不牺牲正确性：将长达半小时的恢复和 warm-up 降至亚秒级，在所有案例中成功恢复，恢复后性能接近 100% 基准。
- 大规模随机故障注入测试（8,400 次注入）：PHOENIX 在 85.6% 的案例中成功恢复，对于禁用 unsafe region 的案例，仍不引入额外数据损坏。

## 主要研究方法

**核心观察 1：Custom Recovery 对通用恢复不可或缺**
Lowell et al. 的研究已证明，没有应用程序的协助，通用恢复（generic recovery）无法同时保证 failure transparency（恢复到与先前输出一致的状态）和 bug avoidance。要实现 optimistic recovery，必须依赖开发者利用其对应用程序逻辑的理解。

**核心观察 2：大多数故障只影响瞬态状态**
论文对 64 个真实世界故障（来自 Redis、Hadoop、MongoDB、Ceph、Elasticsearch 六种应用）的研究显示：
- **87.5% 的故障只 corrupt 临时状态或不 corrupt 任何状态**：35 个故障源于读写局部变量或短期堆对象（如 client/request 结构）；21 个源于逻辑错误/错误假设但不影响全局状态。
- **可恢复性与是否在修改操作期间失败高度相关**：21 个故障发生在写相关函数中；43 个发生在只读事务或修改操作前后。9 个 partial-update 案例全部涵盖在这 21 个中。
- 仅 8 个故障（12.5%）实际 corrupt 了全局状态，对这些案例 PHOENIX 不尝试恢复而回退到默认恢复。

**核心观察 3：大多数状态可安全保留**
在研究的 64 个案例中，87.5% 的故障不影响长期状态或最多 corrupt 少量临时状态，这表明 selective preservation 具有很高的实用价值。

**Optimistic Recovery 的正确性边界**
论文明确定义了 PHOENIX 恢复的正确性标准：**如果应用恢复到与默认恢复等效的状态，则认为 PHOENIX 恢复是正确的**。这意味着 PHOENIX 不尝试修复默认恢复无法修复的 corruption（如已持久化到磁盘的错误状态）。这是一个务实的定义，避免了过度承诺。

## 设计与实现

**PHOENIX API**（表 2）：
- `phx_init()`: 初始化 PHOENIX context，注册 restart handler
- `phx_restart()`: 触发 PHOENIX 模式恢复，支持配置 preservation targets（heap、ELF sections、custom ranges）
- `phx_is_recovery_mode()`: 检查是否处于 PHOENIX 恢复模式
- `phx_mark_preserve()`: 标记 malloc 变量避免被 GC 回收
- `phx_unsafe_begin/end()`: 标注 unsafe region 边界
- `phx_stage()`: 支持基于 stage 的进度恢复（用于长计算任务）

**Zero-Copy Transfer**
PHOENIX kernel 在 `preserve_exec` 系统调用中直接在内存中转移状态：通过操作页表，将保留范围的 PTE 从旧页表移动到新页表，避免跨地址空间边界的昂贵数据复制。新进程在其原始虚拟地址安装保留页，确保指针有效性（无需 address swizzling）。

**Section-Based Preservation**
静态变量通常位于 `.data` 或 `.bss` 段。PHOENIX 引入 `.phx.data` 和 `.phx.bss` 段，其内容在重启后自动保留。开发者只需用 `phxsec` 宏标注变量即可。

**Over-Approximate Allocation Tracking**
PHOENIX 与 glibc malloc 集成，跟踪 arena（小额对象）、mmap 直接映射（大额对象）和 brk 段（sbrk）的分配。在 `preserve_exec` 时，kernel 在加载可执行文件前安装保留的 heap 页、section 页和用户自定义范围。

**Cleanup (Mark-and-Sweep GC)**
Over-approximate preservation 会保留整个 heap，可能包含 unreferenced data。开发者提供遍历函数，`phx_finish_recovery` 执行 mark-and-sweep 垃圾回收，释放未标记的对象。

**Unsafe Region 检测一致性**
Unsafe region 定义为修改 preservable state 的最小代码段。如果 crash 发生在 unsafe region 内部，说明存在状态不一致的风险，PHOENIX 回退到默认恢复路径。PHOENIX 提供 LLVM 静态分析工具自动识别 unsafe region：分析函数修改操作符的 taint 集，计算 first/last modification 作为边界。

**Cross-Check Validation（可选）**
启用后，主进程以 speculative 模式快速恢复并开始服务新请求，同时后台进程运行默认恢复并比较两种状态的初始快照（`S_i` vs `S_r`）。匹配则继续 PHOENIX 恢复；分歧则 hot-switch 到验证后的恢复进程。

**Progress Recovery（用于计算任务）**
`phx_stage` API 支持基于 stage 的进度恢复。开发者定义 stage 的 PRESERVE_HOOK 和 RESTORE_HOOK，运行时将 hook 记录在链表中。恢复时 PHOENIX 遍历 restore hook 链重建栈并从最近的 consistent stage 恢复。

## 主要实验结果

**Redis 真实 bug 案例（#12290：无限循环导致 hang）**：
- Vanilla: 1 秒内重启，但需要 25 分钟达到 90% 吞吐量
- Builtin (RDB): 53.5 秒停机（加载 6GB RDB），6 分钟达到 90% 吞吐量
- CRIU: 19 秒停机（无需 unmarshalling），但与 PHOENIX 相比仍较慢
- **PHOENIX: 仅 0.8 秒停机，2 秒内达到 90% 吞吐量**，无需从磁盘加载 RDB

**LevelDB（log replay 瓶颈）**：
- Builtin (log replay): ~4 秒停机 + log replay
- CRIU: ~14× 停机改善但仍从旧 checkpoint 恢复
- **PHOENIX: 恢复 skiplist 避免 replay，130× 停机改善快于 Builtin**

**Varnish 和 Squid（内存缓存）**：
- PHOENIX 保留 in-memory cache，5 秒后有效可用性提升 4.7-7.1×

**XGBoost 和 VPIC（计算任务）**：
- Builtin 和 CRIU 都需要重新计算，PHOENIX 从最后一个 preserved stage 恢复，有效不可用时间减少 19.8×（XGBoost）和 76.4×（VPIC）

**大规模故障注入（8,400 次注入）**：
- PHOENIX 在 85.6% 的案例中成功恢复
- 732 次回退由 unsafe region 检测触发（防止不一致状态）
- 478 次崩溃发生在恢复后立即回退（避免 buggy state 传播）
- 禁用 unsafe region 时，Redis 的恢复成功率提升（更激进），但允许 incorrect state 持久化

**Runtime Overhead**：
- 平均仅 2.7% 开销（与 Builtin 3.1% 相当），远低于 CRIU 的 22.5%
- 内存保留率：平均 88.4% 的应用程序内存被安全重用

## 潜在问题 / 局限性

**1. 需要应用程序配合**
PHOENIX 依赖开发者理解应用逻辑并选择性标注状态。这与论文声称的"simple APIs"存在张力——实践中 Redis 的集成需要约 140 行代码修改，识别所有 application resources 需要约 7 天工作量。论文承认这是"最耗时的部分"。

**2. 静态分析的精度局限**
LLVM 静态分析工具在以下场景存在挑战：(a) 间接函数调用保守合并所有可能 callee 的效果；(b) C++ 依赖 heavy STL 内联和 opaque 内部函数使用，论文明确承认"precise C++ analysis is difficult"；(c) 仅考虑内存效果，不考虑外部效应（如文件写入与内存状态更新的隐含关联）。Redis 的 unsafe region 被保守地过度插桩，导致假阳性。

**3. Cross-check validation 的假设**
Cross-check validation 假设背景进程的恢复状态 `S_r` 是正确的——如果默认恢复本身就是 buggy 的，cross-check 会通过但 `S_i` 仍不正确。论文坦然承认"PHOENIX cannot be more correct than the default recovery"，这是设计上的限制。

**4. 指针有效性的隐含假设**
Zero-copy transfer 通过在原始虚拟地址安装保留页来避免 address swizzling，但这要求 preserved state 是"self-contained"的——不引用被丢弃的内存。论文承认这取决于开发者确保这一不变量，对于包含复杂指针图的应用（如包含循环引用的数据结构）可能难以保证。

**5. 故障注入评估的局限性**
8,400 次注入实验是在确定性工作负载下进行的，可能无法反映生产环境中复杂、非确定性的工作负载。此外，注入的故障类型（如 comparison inversion、missing assignment）是典型的 software fault 模型，但可能无法代表所有真实故障类型（如 race conditions、memory corruption due to heap layout）。

**6. "87.5% 故障不影响全局状态"的泛化性**
这一发现来自六种特定类型的应用（数据库、缓存、计算）。对于其他类型的应用（如包含复杂事务逻辑的分布式系统），这一比例可能显著不同。

## 未来工作

- 探索自动推断 preservable state 的方法，降低开发者标注负担。
- 将 PHOENIX 扩展到分布式系统（需要处理跨节点状态协调）。
- 研究基于机器学习的 unsafe region 预测，提高检测精度。
- 探索 PHOENIX 与其他恢复技术的组合（如与 replication 结合）。

## 个人评注

PHOENIX 的核心洞察——现代应用程序中 bug 和 bytes 的分布极不均衡——是一个深刻且实用的观察。87.5% 的故障只影响瞬态状态这一数据为 selective preservation 提供了坚实的实证基础。这种"大多数状态可保留、少数问题状态需丢弃"的不对称性，是 PHOENIX 设计得以 work 的根本原因。

论文的工程实现非常全面：从 kernel-level `preserve_exec` 系统调用到 user-level malloc 集成，再到 LLVM 静态分析工具，构建了一个跨越多个层次的完整系统。这种 holistic approach 虽然增加了复杂度，但也是实现实用性的必要代价。

然而，PHOENIX 的成功高度依赖应用程序的配合。识别哪些状态可安全保留需要深入的应用理解，这可能限制了该技术在大规模生产环境中的自动应用。论文中提到识别 MySQL 的所有 application resources 需要约 7 天，这在一个有经验的 PhD 研究生的情况下完成的——对于普通开发团队来说可能更耗时。

最令人印象深刻的是 fault injection 实验的结果：在 8,400 次随机注入中，85.6% 成功 PHOENIX 恢复，且禁用 unsafe region 时"does not introduce additional corruption"——这证明了即使在激进模式下，PHOENIX 也不会比 Vanilla 更差。但需要注意的是，Vanilla 本身的 corruption 率（如 CRIU 引入额外 corrupted state 的案例）是否真的为零，论文没有明确比较。

总体而言，PHOENIX 代表了软件恢复领域的一个重要进步，提供了介于"preserve all"和"discard all"之间的实用中间路线。其设计哲学——optimistic——既务实又深刻：不追求完美的正确性保证（那将需要不可接受的开销），而是接受可能的回退，同时最大化 common case 的收益。
