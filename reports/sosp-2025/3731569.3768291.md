## 研究背景

非易失性内存（NVM）技术（如 Intel Optane persistent memory、Samsung CMM-H）兼具高吞吐、低延迟、字节寻址和持久性特性，催生了大量用户态 NVM 文件系统研究。此前的内核态 NVM 文件系统（BPFS、PMFS、NOVA）虽然利用了 NVM 的性能，但仍受制于系统调用和 VFS 层开销。

为追求更高性能，近年的工作将文件系统逻辑从内核移到用户态，实现直接 NVM 访问（如 SplitFS、Strata、KucoFS、ctFS）。然而，用户态文件系统面临安全挑战：恶意应用可能篡改元数据。已有方案要么在每次元数据操作时进行完整性验证（高安全但性能损失大），要么完全不做检查（高性能但安全漏洞大）。

Trio 架构和 ArckFS 文件系统（SOSP 2023）尝试在性能和安全之间取得平衡：通过将文件系统状态分解为核心态（Core state，存储在 NVM 中用于完整性验证）和辅助态（Auxiliary state，在 DRAM 中用于高性能索引），在 inode 所有权转移时才做完整性验证，从而摊薄验证成本。ArckFS 在此基础上针对多核可扩展性做了优化。

## 要解决的问题

KAIST 团队通过仔细审阅 Trio/ArckFS 论文和发布的 artifact，识别出两类问题：

1. **表述不清**：原论文对 multi-inode 操作（如跨目录重命名）的处理规则描述不够充分
2. **实现 bug**：ArckFS artifact 中存在 6 个实现缺陷，可能导致操作失败或崩溃不一致

## 核心贡献

1. **补充了 Trio 的 multi-inode 操作规则**：明确了 LibFS 在目录重命名等操作中必须遵守的 3 条规则（Rule 1/2/3），使 Trio 的完整性验证逻辑更加严谨
2. **识别并修复了 ArckFS 的 6 个 bug**：涵盖完整性违规、崩溃不一致和并发 bug，创建了增强版 ArckFS+
3. **展示了 Artifact Evaluation 的价值**：以 Trio/ArckFS 为案例，论证了 artifact 评审对系统研究的重要意义

## 主要研究方法

### 静态代码分析与协作式增强

KAIST 团队在发现 bug 后联系了 Trio 原作者，双方协作完成 ArckFS+ 的开发。

### Bug 分类

| 类别 | Bug 描述 | ArckFS+ 补丁 | 性能影响 |
|------|---------|------------|---------|
| 完整性违规 | 跨目录重命名失败（无法区分删除 vs 重命名） | 补丁 verifier + LibFS 遵循 Rule (2)/(3) | 目录重命名开销增加 |
| 崩溃不一致 | inode 创建时缺少内存 fence，导致部分持久化 | 添加 memory fence | 文件创建开销略增 |
| 并发 Bug | inode 释放时缺少同步，解引用已释放内存 | 释放时获取相关所有锁 | inode 释放开销增加 |
| 并发 Bug | 辅助态不一致（桶锁未覆盖 PM 操作） | 扩展桶锁临界区 | 目录写入竞争增加 |
| 并发 Bug | 目录桶读端未加锁导致 use-after-free | 引入 RCU 保护哈希桶 | 目录读取开销略增 |
| 并发 Bug | 未禁止目录循环（rename into descendant） | 全局 rename 锁 +  descendant 检查 | 目录重命名开销增加 |

## 设计与实现

### LibFS Multi-inode 操作规则

Rule (1): LibFS 只能在父目录已被释放后才能 commit 或 release 新创建的 inode（否则 I3 不变量被破坏）

Rule (2): 目录重命名操作中，当目标目录在父目录获取前非空时，LibFS 必须在 commit/release 旧父目录之前先 commit/release 新父目录

Rule (3): 防止 Rule (1) 和 Rule (2) 之间的循环依赖——在执行 rename 时，LibFS 应先 commit 新父目录

### ArckFS+ 关键补丁

- **跨目录重命名**：为 verifier 添加 parent pointer 以区分 rename 和 delete；在 LibFS 中添加 global rename lock
- **崩溃一致性**：在 commit marker flush 前添加 memory fence
- **inode 释放同步**：在释放 inode 时获取所有相关锁（文件用 writer lock，目录用所有桶锁）
- **目录桶 RCU**：用 RCU 替代原来不加锁的读端，消除 use-after-free
- **目录循环检测**：case (1) 加全局锁；case (2) 在 rename 前检查是否为后代目录

## 主要实验结果

### 单线程性能

元数据操作（open/create/delete）：ArckFS+ 分别达到 ArckFS 的 83.3% / 92.8% / 92.2%。open 和 delete 的下降源于 RCU 读端临界区的引入，create 的下降源于额外的 memory fence。

### 多线程可扩展性（FxMark，48 线程）

ArckFS+ 在元数据工作负载中达到 ArckFS 性能的 **97.23%**（几何平均），保持了原有的可扩展性优势。其中 MWUM 反而更快（cacheline 对齐变化），MRDL 最慢（RCU 读端临界区）。

### 宏基准测试

- **Filebench Webproxy/Varmail**（1 线程）：ArckFS+ 达到 ArckFS 的 **101.1% / 102.1%**
- **Filebench**（16 线程）：达到 **97.1% / 98.8%**
- **LevelDB**：与 ArckFS 性能相当（因为 benchmark 以数据操作为主）

## 潜在问题 / 局限性

1. **Short Paper 的局限性**：这是一篇 10 页的短论文，很多技术细节（如完整规则证明、每个 bug 的完整修复代码）只能点到为止，缺乏深度分析

2. **性能退化不可忽视**：虽然总体性能维持在 97%，但 open 操作单线程性能下降了 17%，在以 open 为主的工作负载下影响显著

3. **Global rename lock 的可扩展性问题**：全局锁在高并发 rename 场景下可能成为瓶颈，论文未评估此场景

4. **RCU 内存开销**：RCU 延迟释放机制会积累内存开销，高频删除场景下可能造成内存压力

5. **验证工作仅针对单一 artifact**：本文的 bug 发现能力高度依赖研究者的代码审查质量，其他 artifact 是否存在类似问题无法推断

6. **目录循环检测的完整性**：descendant check 的正确性本身也值得形式化验证

## 个人评注

本文是 SOSP 2025 Session 13 中较为特殊的一篇——它是唯一的 Short Paper，且其研究方法本身就是"元研究"：通过审查一个已有的 SOSP 2023 artifact 来发现 bug。这使得本文的主题具有双重价值：（1）实际改进了 ArckFS 系统的正确性；（2）示范了 Artifact Evaluation 机制对系统研究的重要性。

从技术内容看，本文识别的 bug 质量较高——尤其是部分持久化（missing memory fence）和 use-after-free（桶读端无锁）都是典型的真实并发 bug，而非吹毛求疵。ArckFS+ 在修复后仍能维持 97% 的性能，说明正确性和性能并不必然冲突。

然而，本文的核心价值不在技术突破，而在于它对系统研究社区的示范意义：鼓励研究者认真对待 artifact评审，透过协作而非竞争的方式共同提升系统质量。Trio 作者愿意与 KAIST 团队合作发布 ArckFS+，这种学术诚信值得肯定。

对IntervalVM（SOSP 2025 同 Session）而言，ArckFS 的 bug 类型分析也有参考价值——两者都涉及复杂的并发数据结构，IntervalVM 的 skiplist 实现是否可能存在类似问题，值得后续关注。
