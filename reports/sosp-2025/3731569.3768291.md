# Analyzing and Enhancing ArckFS: An Anecdotal Example of Benefits of Artifact Evaluation

**作者**：Jonguk Jeon, Subeen Park（KAIST）；Sanidhya Kashyap（EPFL）；Sudarsun Kannan（Rutgers University）；Diyu Zhou（Peking University）；Jeehoon Kang（KAIST/FuriosaAI）

## 一、背景

Non-volatile memory（NVM）技术（如 Intel Optane Persistent Memory、Samsung CMM-H）兼具高吞吐、低延迟、字节可寻址和持久化特性，催生了一批绕过内核 VFS 层、在用户态直接访问 NVM 的高性能文件系统（KucoFS、SplitFS、ctFS 等）。

Zhou et al. 在 SOSP 2023 提出了 Trio 架构及其原型实现 ArckFS，试图在高性能与元数据完整性之间取得平衡：将文件系统状态分为"核心状态"（core state，用于完整性验证）和"辅助状态"（auxiliary state，用于高性能访问），仅在 inode 所有权转移时延迟批量验证，从而摊薄验证开销。

本文由 KAIST 的一组研究者通过仔细审阅 SOSP 2023 论文及其公开 Artifact 发起，随后与原 Trio 作者展开协作，共同分析、修复 ArckFS 中的问题，并发布了增强版本 ArckFS+。

---

## 二、要解决的问题

KAIST 团队在审阅 ArckFS artifact 时发现了以下三类问题：

1. **论文描述不清**：原论文对涉及多 inode 操作（如跨目录 rename）的处理规则描述不足，导致读者无法从论文中还原出正确实现。

2. **崩溃一致性漏洞**：ArckFS 在文件创建过程中使用了一种基于 commit marker 的原子提交机制，但 artifact 引入的优化遗漏了关键 memory fence，在系统崩溃时可能留下部分持久化的目录项和 inode。

3. **并发 Bug（多处）**：
   - inode 主动释放与另一线程并发写之间缺乏同步，导致访问已 unmap 内存；
   - 目录核心状态（NVM）与辅助状态（DRAM 哈希表）之间的更新未加锁同步，可能造成访问不存在的核心数据；
   - 目录哈希桶的读端未持锁，写端可能 free 掉读端正在遍历的条目，引发 use-after-free；
   - 缺乏目录环检测，并发 rename 或将目录 rename 进自身子树时可产生环形结构。

## 三、核心设计

### Trio 架构回顾

Trio 将文件系统状态分为两部分：

- **Core state**（NVM）：超级块、shadow inode 表、文件页，作为完整性验证的基准；
- **Auxiliary state**（DRAM）：每个 LibFS 私有的哈希表等索引结构，用于高性能访问。

Inode 在应用间共享时才触发完整性验证，通过 in-kernel Controller + trusted userspace Verifier 协作完成；ArckFS 基于 Trio 实现了支持多核扩展的用户态 NVM 文件系统。

### ArckFS+ 的修复策略

ArckFS+ 对六个 Bug 逐一开发补丁（见论文 Table 1）：

| Bug 类型 | 具体问题 | 修复方案 |
|---------|---------|---------|
| 完整性违反 | 跨目录 rename 导致 Verifier 误判，验证失败 | 引入 parent pointer 于 shadow inode；明确 LibFS 须在 rename 前后 commit 新旧父目录 |
| 崩溃一致性 | 省略 memory fence 导致 commit marker 所在 cache line 的 flush 可能乱序 | 在 flush commit marker 前加一条 memory fence |
| 并发：inode 释放 | 主动释放 inode 时未加锁，与其他线程并发访问冲突 | 释放前获取该 inode 全部相关锁（文件的 RW 锁，目录的所有 bucket 锁） |
| 并发：core/aux 不一致 | 哈希表更新未延伸至 NVM core state | 将 bucket lock 的临界区扩展以覆盖对应 NVM 更新 |
| 并发：读端无锁 | 哈希桶读端不持锁，写端 free 导致 dangling pointer | 引入 RCU 保护哈希桶，延迟释放直到读端退出 |
| 目录环 | 并发 rename 或 rename 进子孙目录产生环 | 引入全局 rename lock（防并发环）+ LibFS 侧目录祖先检查（防 rename 进子树） |

## 四、实现细节

- **ArckFS+ 源码**：与 ArckFS 在同一仓库 `https://github.com/vmexit/trio-sosp23-ae`。
- **Memory fence 修复**：在 `creat()` 路径中 flush commit marker cache line 之前插入 `sfence`，开销极小。
- **RCU 引入**：保护目录哈希桶的读端，写端删除条目后延迟 free，消除 use-after-free。
- **全局 rename lock**：实现为带超时的 lease（防止恶意应用永久持锁），与 Linux VFS 的 `s_vfs_rename_mutex` 语义类似。
- **Parent pointer**：在 kernel shadow inode 中新增字段，记录每个 inode 当前父目录，辅助 Verifier 区分 rename 与 delete。
- **Filebench 修改**：原 Trio artifact 已将 Filebench 的共享目录改为私有目录（偏离原始语义），ArckFS+ 重新实现了基于细粒度文件名锁的共享目录框架，兼顾原语义与可扩展性。

## 五、实验结果

**实验平台**：2× 24-core Intel Xeon Gold 6248R（共 48 核），384 GB DDR4，6× Intel Optane PM 256 GB（1,536 GB），Ubuntu 20.04，Linux 5.13.13。

### 单线程性能（vs. ArckFS）

| 操作 | ArckFS+ / ArckFS |
|-----|--------------|
| open | 83.3% |
| create | 92.8% |
| delete | 92.2% |
| Filebench Webproxy | 101.1% |
| Filebench Varmail | 102.1% |

open/delete 下降主因：引入 RCU 读端进入临界区的开销；create 下降主因：额外 memory fence。

### 多线程扩展性（FxMark，48 线程，geomean）

ArckFS+ 达到 ArckFS 的 **97.23%**，最大下降在 MRDL（目录枚举，-24.55%），最大提升在 MWUM（+54.70%，因 shadow inode 字段改变 cache line 对齐）。

### 宏观基准

| 场景 | ArckFS+ / ArckFS |
|-----|---------|
| Filebench Webproxy（1 线程） | 101.1% |
| Filebench Varmail（1 线程） | 102.1% |
| Filebench Webproxy（16 线程） | 97.1% |
| Filebench Varmail（16 线程） | 98.8% |

LevelDB（数据操作为主）：ArckFS+ 与 ArckFS 表现相近，均优于其他文件系统。

### Sharing Cost

使用 trust group 机制（组内应用共享 inode 不经验证），ArckFS+ 基本维持原始 Trio 论文的性能声明。

## 六、批判性分析

### 1. "Short Paper"定位掩盖了工作的边界

本文以 short paper 形式发表，声称目的是展示 artifact evaluation 的价值，而非提出新的技术贡献。但实际上发现了 6 个 bug（含崩溃一致性和并发 bug），并重新实现了 Filebench 评测框架——这远超一般的 artifact 复现研究。将工作定性为"anecdotal example"在某种程度上低估了系统级 bug 修复的严肃性。

### 2. 性能下降未被充分对待

ArckFS+ 在 open 和某些多线程场景中的性能下降（最高达 -24.55%，MRDL@48 线程）并非微不足道，但作者以"geomean 97.23%"一句话带过，未对 MRDL 这类极端情况给出合理的工程权衡分析。对于目录读密集型工作负载，RCU 引入的额外开销是否可被接受，文章没有给出充分论证。

### 3. "性能声明基本维持"论断存在循环论证风险

作者声称 ArckFS+ 维持了原始 Trio 论文的性能声明，但 Filebench 评测已在 ArckFS+ 中被重新实现（从私有目录改为共享目录框架）。在修改了评测框架的前提下，直接拿 ArckFS+ 的结果与原始 Trio 论文对比，等于换了尺子量同一把物品并声称长度不变。

### 4. Bug 的严重性评估过于保守

论文对 Bug 的描述刻意温和（如"可能导致 segfault"、"偶发操作失败"），但这些都是生产文件系统中的 safety-critical 问题：
- 崩溃一致性 bug 在真实掉电场景下可能导致数据丢失；
- 并发 use-after-free 在实际负载下是可以稳定触发的（论文自己也插入 sleep 来复现）。
将这些 bug 归类为"anecdotal"显然对安全性影响有所淡化。

### 5. 实验不具代表性

所有 bug 触发均依赖手工插入 sleep/flush 以提高复现概率，作者并未展示这些 bug 在真实工作负载（FxMark/Filebench/LevelDB）中的实际触发率。若触发率极低，则修复的实用价值需重新评估。

### 6. 论文本身存在文档错误

作者指出 Trio 论文中 §4.2 将哈希桶的锁类型误记为 readers-writer lock（实际是 spinlock），这说明原论文评审过程也未能发现此类不一致。本文对这一发现一笔带过，未深入探讨论文评审与 artifact 评审的互补关系。

---

## 七、总结

本文通过分析 SOSP 2023 ArckFS 的公开 artifact，识别并修复了 6 个涉及完整性、崩溃一致性和并发的 Bug，产出了增强版 ArckFS+，并在与原作者协作下验证 ArckFS+ 以极小性能代价（geomean -2.77%@48线程）维持了原始性能声明。其核心价值在于倡导将 artifact evaluation 作为推进系统研究严谨性的重要机制——公开 artifact 不仅提升可重现性，更为社区提供了发现并改进已发表系统的基础。主要局限在于：工作量被"short paper + anecdotal"框架低估，部分性能回归缺乏深入分析，且 bug 触发率在真实负载下未被量化验证。
