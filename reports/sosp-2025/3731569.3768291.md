## 一、背景

非易失性内存（NVM）技术（如 Intel Optane、Samsung CMM-H）提供了高吞吐、低延迟、字节寻址和持久化特性，推动了高性能文件系统的发展。传统内核态 NVM 文件系统（BPFS、PMFS、NOVA）受限于系统调用和 VFS 层开销，因此近年研究将文件系统逻辑迁移至用户态，以实现对 NVM 的直接访问和应用定制化。

用户态文件系统面临的核心挑战是安全性，特别是元数据完整性保护。现有方案在性能和安全性之间存在权衡：KucoFS、SplitFS、Strata 在每次元数据操作时验证完整性（安全但开销大），ctFS 则完全跳过完整性检查（快但不安全）。

Trio 架构及其实现 ArckFS（SOSP 2023）试图打破这一权衡：通过将文件系统状态分为 core state（用于共享和完整性验证）和 auxiliary state（用于高性能访问），并将完整性验证延迟到 inode 所有权在应用间转移时才执行，从而摊销验证开销。

---

## 二、要解决的问题

本文是一篇 short paper，由 KAIST 团队发起，通过仔细审查 Trio 论文和公开的 artifact，发现了以下问题：

1. **论文描述不充分**：Trio 论文对多 inode 操作（如跨目录 rename）的处理规则描述不够清晰，导致读者无法完全理解系统行为。
2. **跨目录 rename 失败**：ArckFS 的 verifier 无法区分子目录被删除还是被 rename 移走，导致合法操作的验证失败。
3. **崩溃一致性 bug**：inode 创建过程中缺少 memory fence，可能导致目录项和 inode 仅部分持久化。
4. **并发 bug（4 个）**：
   - inode release 过程中缺少同步，导致 use-after-unmap 崩溃
   - core state 和 auxiliary state 之间缺少同步，导致段错误
   - 目录 hash bucket 的读端缺少保护，导致 use-after-free
   - 缺少目录环路检测，可能产生目录循环

## 三、洞察与设计

**关键洞察**：Trio 的 inode 粒度共享和延迟验证设计在单 inode 操作上是正确且高效的，但在涉及多 inode 的操作（如目录重定位）时，需要额外的规则来确保验证的正确性；这些规则在原论文中未被明确阐述，且原始实现存在多个并发和一致性 bug，但这些都是可以修复的实现问题，而非架构层面的固有缺陷。

基于这一观察，作者团队与 Trio 原作者合作开发了 ArckFS+，核心设计包括：

1. **多 inode 操作规则**：明确了三条 LibFS 规则——(1) 新建 inode 必须在父目录 release 后才能 commit/release；(2) 目录重定位后，需先 commit 新父目录再处理旧父目录；(3) 在新建兄弟目录下 rename 时，需先 commit 新父目录以打破循环依赖。
2. **Verifier 增强**：引入 shadow inode 中的 parent pointer，使 verifier 能区分子目录的删除和 rename。
3. **崩溃一致性修复**：在 commit marker flush 前添加 memory fence。
4. **并发控制修复**：
   - inode release 时获取所有相关锁
   - 扩展 hash bucket 锁的临界区覆盖 core state 更新
   - 引入 RCU 保护 hash bucket 读端
   - 添加全局 rename 锁和后代检查防止目录环路

## 四、实现细节

ArckFS+ 基于 ArckFS 的原始代码仓库（https://github.com/vmexit/trio-sosp23-ae）进行修改，6 个 patch 对应 6 个 bug：

| Bug | 修复方案 | 关键实现 |
|-----|---------|---------|
| 跨目录 rename 失败 | Verifier + LibFS 修改 | shadow inode 增加 parent pointer，LibFS 按 Rule (2)(3) 顺序 commit |
| 部分持久化 | 添加 memory fence | 在 commit marker cache line flush 前插入单条 fence 指令 |
| inode release 竞态 | 加锁同步 | 文件获取写锁，目录获取所有 hash bucket 锁；读操作缓存 inode 状态 |
| core/auxiliary 不一致 | 扩展锁范围 | hash bucket 锁的临界区扩展到覆盖 core state 更新 |
| hash bucket 读端竞态 | 引入 RCU | 删除的 hash table 项延迟释放，读端进入 RCU 临界区 |
| 目录环路 | 全局锁 + 后代检查 | 跨目录 rename 使用全局锁（带 lease 超时），LibFS 检查是否 rename 到自身后代 |

实验平台：双路 Intel Xeon Gold 6248R（48 核），384 GB DDR4 DRAM，1536 GB Intel Optane PMem 100，Ubuntu 20.04，Linux 5.13.13。

## 五、实验结果

ArckFS+ 在修复所有 bug 后，性能与原始 ArckFS 基本持平：

**单线程性能**：

| 操作 | ArckFS+ 相对 ArckFS |
|------|---------------------|
| open | 83.3% |
| create | 92.8% |
| delete | 92.2% |
| read/write | ~100% |

**FxMark 48 线程可扩展性**：

| 指标 | 结果 |
|------|------|
| 几何平均 | 97.23% |
| 最大下降 (MRDL) | 75.45%（RCU 读端开销） |
| 最大提升 (MWUM) | 154.70%（cache line 对齐变化） |

**Filebench 宏基准测试**：

| 工作负载 | 单线程 | 16 线程 |
|----------|--------|---------|
| Webproxy | 101.1% | 97.1% |
| Varmail | 102.1% | 98.8% |

**LevelDB**：数据操作主导，ArckFS+ 与 ArckFS 性能相当。

## 六、批判性分析

1. **Bug 影响范围被低估**：论文展示的 6 个 bug 中有 4 个是并发 bug，在实际多线程工作负载下可能导致崩溃或数据损坏，但作者对这些 bug 在生产环境中的严重性缺乏量化讨论。仅通过人工注入 `sleep()` 来复现 bug 并不能说明这些 bug 在真实工作负载下的触发频率。

2. **性能评估的选择性**：论文指出目录重定位（跨目录 rename）和全局 rename 锁"不影响性能评估，因为评估工作负载中不包含这些操作"。这恰恰暴露了原始评估的局限性——如果评估工作负载覆盖了这些路径，bug 可能早就暴露了。ArckFS+ 也同样没有评估这些修复对 rename-heavy 工作负载的性能影响。

3. **MRDL 25% 的性能下降值得关注**：虽然论文以几何平均 97.23% 来总结性能，但 MRDL（枚举私有目录文件）在 48 线程下下降了约 25%，对于读密集的目录操作场景这是显著的退化。

4. **单线程 open 17% 下降**：单线程 open 操作下降到 83.3%，考虑到 open 是最基础和频繁的文件系统操作之一，这一退化不容忽视。

5. **实验平台不同**：作者在不同于原论文的服务器上进行评估，虽然这有助于验证可重现性，但也意味着无法直接归因性能差异——是 bug 修复带来的还是硬件差异造成的？论文缺少在相同硬件上的对比。

6. **形式化验证的缺失**：论文在结论中提到了 formal verification 的重要性，但 ArckFS+ 本身并未进行形式化验证。考虑到原始系统存在如此多的并发 bug，新增的修复是否引入了新 bug 同样值得怀疑。

---

## 七、总结

本文是一篇典型的 artifact evaluation 驱动的后续研究，通过仔细审查 Trio/ArckFS（SOSP 2023）的论文和代码，发现了 1 个描述不清的设计规则和 6 个实现 bug（涵盖完整性、崩溃一致性和并发三类），并通过 ArckFS+ 修复了所有问题，性能损失控制在几何平均 ~3% 以内。论文的核心贡献不在于技术创新，而在于展示了 artifact evaluation 对系统研究的实际价值：公开的 artifact 使外部团队能够发现并修复原始工作中的问题，促进了跨团队的学术合作。但其评估存在选择性盲区（未覆盖 rename-heavy 场景），且部分修复带来的单线程性能退化值得在实际部署中关注。
