## 一、背景

随着 ChatGPT、AI Agent、视频生成等大模型技术的快速普及，隐私保护的需求推动了端侧推理的兴起——越来越多的用户希望将 LLM 运行在本地手机上，而非将数据上传至云端。为满足端侧 AI 的算力需求，主流手机 SoC 厂商（Qualcomm、Apple、MediaTek、华为）均已集成异构 AI 加速器，最典型的组合是 GPU + NPU（神经网络处理单元）。以 Snapdragon 8 Gen 3 为例：Adreno 750 GPU 峰值约 2.8 TFLOPS（实测约 1 TFLOPS），Hexagon NPU 峰值 34 TOPS（FP16 约 17 TFLOPS）。然而，当时已有的手机端推理引擎（llama.cpp、MLC、MNN-LLM、llm.npu、PowerInfer-2 等）均只利用了 GPU 或 NPU 中的一种，未能充分发挥异构 SoC 的整体算力和带宽。

---

## 二、要解决的问题

论文识别出三个核心痛点，阻碍了现有方案实现高效 GPU+NPU 协同推理：

1. **NPU 性能高度依赖张量特征**：NPU 的实际算力取决于张量的形状（shape）、顺序（order）、尺寸（size），对不合适的张量形状性能可能急剧下降，甚至不如 GPU。现有工作对此缺乏系统认识。

2. **GPU-NPU 同步开销过大**：手机端 GPU-NPU 之间的同步（如 `clFinish`）延迟约 400 微秒，与单个 decode kernel 的执行时间相当，直接抵消并行收益。

3. **NPU 静态计算图限制**：移动端 NPU 依赖离线编译的静态 dataflow graph，无法原生支持动态序列长度。现有方案要么在线即时生成图（开销大），要么对输入做 padding（浪费计算）。

---

## 三、核心设计

论文提出 **HeteroInfer**，一个面向异构移动 SoC 的 LLM 推理引擎，核心思想是：**综合利用 GPU 提升 NPU 性能下界，以 NPU 为主计算单元，通过 GPU-NPU 并行最大化算力和内存带宽利用率**。

### 3.1 性能特征归纳

基于 Snapdragon 8 Gen 3 的深度测量，论文总结了 6 个关键特征：

| 特征 | 描述 |
|------|------|
| GPU-1：线性性能 | 小张量时内存受限，大张量时趋于计算饱和，性能随尺寸线性增长 |
| GPU-2：高同步代价 | `clFinish` 引入约 400μs 固定延迟，还需显式拷贝数据（OpenCL 不默认共享地址空间） |
| NPU-1：阶梯性能 | 受系统阵列硬件尺寸（32×32）限制，张量未对齐时产生阶梯状性能跳变 |
| NPU-2：顺序敏感性能 | `[K,N]×[N,M]` 与 `[M,N]×[N,K]` 计算量相同，但性能差异可达 6×，源于 weight-stall 范式下权重张量越大内存开销越高 |
| NPU-3：形状敏感性能 | 输入张量的行列比影响性能，row size > col size 时效率更高 |
| Memory-1：单处理器带宽不足 | 单个 GPU/NPU/CPU 仅能利用约 40-45 GB/s，低于峰值 68 GB/s；GPU+NPU 并行可达 60 GB/s |

### 3.2 三级优化策略

**层级 GPU-NPU 分配（Layer-level）**

- Prefill 阶段：Matmul 分配给 NPU（算力强），RMSNorm / SwiGLU 等算子给 GPU
- Decode 阶段：因 NPU-1（阶梯性能），矩阵向量乘退化，主计算改由 GPU 承担
- 利用 NPU-2：对 Matmul 做张量顺序交换，`[M,N]×[N,K]` → `[[K,N]×[N,M]]^T`

**张量级并行（Tensor-level）——三种分区策略**

| 策略 | 场景 | 做法 |
|------|------|------|
| Weight-centric（权重中心）| 静态序列长度，NPU 性能不稳定 | 按行切分权重张量，GPU+NPU 并行计算，结果 merge |
| Activation-centric（激活中心）| 动态序列长度 | 动态部分（余量 chunk）给 GPU，标准大小 chunk 给 NPU，避免在线生成 NPU 图 |
| Hybrid（混合）| 动态输入 + NPU-3 形状敏感 | activation-centric + padding + weight-centric 组合，提高 NPU 利用率 |

**快速同步（Fast Synchronization）**

- 利用 UMA：GPU/NPU 通过内存池直接共享张量缓冲区，消除数据拷贝
- 利用内核执行时间的可预测性：同步线程先 `usleep` 预估等待时间，醒来后用小核轮询 flag bit，实现微秒级精确同步，替代 `clFinish` 的 400μs 固定延迟

### 3.3 Profiler-Solver 框架

离线阶段：
- **Profiler** 对目标 SoC 执行各种张量形状的基准测试（< 20 分钟）
- **Solver** 根据 profiling 数据枚举最优分区策略，目标函数：
  `T_total = min(max(T_GPU, T_NPU) + T_sync + T_copy, T_GPU_only, T_NPU_only)`

在线阶段：推理引擎根据当前序列长度动态选择执行路径（NPU-only / GPU-only / 并行）。

## 四、实现细节

- **平台**：Snapdragon 8 Gen 3（主要）+ Snapdragon 8 Elite（部分测试）
- **GPU 算子**：OpenCL 自定义优化 kernel
- **NPU 算子**：集成 Qualcomm QNN 提供的算子库
- **量化方案**：W4A16（权重 INT4 存储，FP16 计算），避免激活量化带来的精度损失
- **内存管理**：维护小型内存池（仅几个 slot，层间复用），host/device 地址映射固定保留，绕过驱动分配开销
- **CPU 角色**：仅作控制面，负责调度和同步，不参与计算（能效比低）
- **NPU 并行同步细节**：
  - Prefill（NPU-dominant）：GPU 执行隐藏在 NPU 执行中，NPU 完成后再提交下一个 GPU kernel
  - Decode（GPU-dominant）：NPU 执行与 GPU 执行重叠，NPU 完成时直接入队下一 GPU kernel，利用 GPU 队列顺序保证正确性

## 五、实验结果

### 端到端性能（Snapdragon 8 Gen 3，真实数据集）

| 工作负载类型 | 数据集 | HeteroInfer vs. 最佳基线 |
|------------|--------|------------------------|
| 解码主导（多轮对话） | BELLE | vs. MNN 2.06×，vs. llm.npu 3.40× |
| 均衡（简单 QA） | GSM8K | 平均 2.62× 提升 |
| 预填充主导（长文） | LongBench | vs. MNN 最高 6.02× |

**端到端加速范围：1.34× ~ 6.02×**

### Prefill 性能（固定序列长度）

- Llama-8B, seq=256：vs. MNN 5.85×，vs. MLC 5.64×，vs. llama.cpp 24.9×，vs. PowerInfer-2 3.29×
- 首个在移动设备上突破 **1000 tokens/s（prefill）** 的推理引擎（InternLM-1.8B 达 1092 tokens/s）

### Prefill 性能（动态序列长度）

- 在 seq=525 时，vs. Online-prepare 2.24×，vs. Padding 2.21×，vs. NPU-pipe 1.35×

### Decode 性能

- 达到 14.01 tokens/s（Llama-8B），29.9 tokens/s（Llama-3B），51.12 tokens/s（InternLM-1.8B）
- 首个突破 **50 tokens/s（decode）** 的移动端引擎
- GPU+NPU 并行带宽利用：43.3 GB/s（GPU-only）→ 59.5 GB/s（GPU+NPU），达理论峰值 96%

### 快速同步效果

| 阶段 | 提升 |
|------|------|
| Prefill（Llama-8B）| Hetero-tensor 平均 24.3% |
| Decode（Llama-8B）| 4.01× 加速（decode kernel 短，同步开销占比高） |

### 干扰与能耗

- 与游戏（League of Legends: Wild Rift）并发：FPS 无下降，prefill 仅下降 2.2%（GPU-only 基线导致 FPS 降至 0）
- 能耗：比 GPU-only 节省 **55%**，比 Hetero-layer 节省 **12.8%**

## 六、批判性分析

**1. 实验规模局限性**
所有核心实验仅在 Snapdragon 8 Gen 3 一款 SoC 上进行，Snapdragon 8 Elite 只做了局部测试。论文声称设计可泛化到其他 SoC（Kirin、Dimensity、Apple），但无数据支撑。移动端 SoC 的 NPU 架构差异显著，Apple Neural Engine 和华为 NPU 的编程模型与 Qualcomm QNN 完全不同，泛化主张存疑。

**2. 基线不完整**
Decode 阶段未与 llm.npu 对比（表格缺失），而 llm.npu 在 prefill 阶段是较强的基线。论文对此未作解释。此外，能耗对比仅对比了 GPU-only 和 Hetero-layer，未与其他 SOTA 基线（如 PowerInfer-2、llm.npu）对比能耗。

**3. Profiling 开销轻描淡写**
论文提到 offline profiling 需要不到 20 分钟，但对于每款新设备都需重新执行、profiling 结果如何跨版本复用等问题未作讨论。对于消费级手机 OTA 更新场景，profiling 的维护成本是个实际问题。

**4. 动态负载与 batch size 假设过于乐观**
所有实验均以 batch size = 1 进行，理由是"并发请求在移动端不常见"。但随着 AI Agent 和多模态应用兴起，同一设备多 app 并发调用 LLM 的场景不可忽视，HeteroInfer 在多任务争用 NPU 时的表现完全未被评估。

**5. 精度声明的完整性**
论文强调维持 W4A16 精度而不使用 INT4 激活量化，这是相对 llm.npu / Qualcomm-AI 的优势。但 W4A16 本身的精度损失和模型特定性（某些模型对 weight-only 量化更敏感）未做详细分析，相关基准测试（MMLU、HellaSwag 等）缺失。

**6. 同步机制的鲁棒性**
Fast synchronization 基于"NPU kernel 执行时间可预测"的假设，采用 sleep + polling 实现。作者未充分讨论手机温控（thermal throttling）、后台任务抢占等导致执行时间波动时，同步机制的退化行为和容错策略。

## 七、AI Infra / MLSys 视角

### 对 AI Infra 的启发

**1. 异构硬件特征驱动的 operator scheduling**
论文对 NPU 的三类性能特征（Stage / Order-sensitive / Shape-sensitive）的系统化测量和建模，提供了一个可借鉴的 profiler-driven scheduling 框架。类似方法可用于云端混合硬件（CPU+GPU+专用加速器）的算子调度。

**2. 统一内存架构下的 zero-copy 同步**
利用 UMA 实现 GPU-NPU 间 zero-copy 的 tensor 共享，再配合 predictable-wait + polling 的微秒级同步，这一思路对 NVLink / CXL 等高带宽互联场景的同步原语设计有直接参考价值。

**3. 面向内存带宽的 decode 加速**
论文清晰地将 decode 阶段定性为"内存带宽受限"，并通过多处理器并行来饱和 SoC 内存总线。这与 GQA、Speculative Decoding 等针对 decode 的优化逻辑一脉相承，区别在于从硬件并行而非算法角度突破带宽瓶颈。

**4. 静态图 + 动态输入的适配**
Activation-centric partition（将动态 chunk 卸载到 GPU）是一种巧妙的"避开静态图限制"策略，在 Cloud 端面对 compilation-heavy 硬件（如某些 ASIC）时，类似的动态余量分流思路同样适用。

### 值得跟进的 Future Work

- **跨 SoC 自动迁移**：设计一个通用 profiler，自动检测 NPU 硬件特征并生成最优调度策略，降低移植到 Kirin / MediaTek Dimensity 等平台的工程成本
- **多应用 NPU 共享**：移动端同时运行多个 AI 应用时，HeteroInfer 的 NPU-GPU 资源该如何与操作系统协同进行细粒度分时/空间复用（参考同期 OSDI 25 的 XSched 工作）
- **Speculative Decoding + Hetero 并行**：在 GPU 负责 draft model、NPU 负责 target model 的分工模式下，GPU-NPU 并行与推测解码的结合是否有额外增益
- **MoE 模型的专家路由**：MoE 架构中不同 expert 的激活频率差异，可能天然适合 GPU-NPU 异构负载分配，值得系统研究

---

## 八、总结

HeteroInfer 是首个系统化利用手机 SoC 中 GPU+NPU 协同执行 LLM 推理的工业级引擎。论文的核心贡献在于：（1）对移动端 NPU 的三类性能特征（阶梯/顺序/形状敏感）进行了深度实测和量化分析；（2）设计了三种互补的张量分区策略和微秒级快速同步机制；（3）在真实手机 SoC 上实现了 1.34× ~ 6.02× 的端到端加速，同时在移动端首次突破 1000 tokens/s（prefill）和 50 tokens/s（decode）门槛，且能耗降低 55%。主要局限在于目前仅验证于 Qualcomm 平台，batch size = 1 的单用户假设，以及 profiling 开销在消费级设备上的实际可行性。
