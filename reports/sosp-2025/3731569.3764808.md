# Characterizing Mobile SoC for Accelerating Heterogeneous LLM Inference

---

## 一、背景

随着 ChatGPT、AI Agent、视频生成等 AI 技术的快速发展，越来越多的用户出于隐私和延迟考虑，倾向于在移动端本地运行 LLM 推理。为满足这一需求，现代移动 SoC（如高通骁龙 8 Gen 3、Apple A18、联发科天玑 9300 等）集成了多种 AI 加速器，包括 GPU 和 NPU。例如骁龙 8 Gen 3 的 GPU 实际算力约 1 TFLOPS（FP16），而 NPU 可达 10 TFLOPS 以上。然而，现有移动端推理引擎大多只利用单一加速器（GPU-only 或 NPU-only），未能充分发挥 SoC 的异构计算潜力。

---

## 二、要解决的问题

1. **GPU 与 NPU 的性能差异巨大**：NPU 理论算力远高于 GPU，但受 tensor 形状、顺序等因素影响，实际性能波动很大。简单地按算力比划分任务并不能保证端到端提升。

2. **异构处理器间同步开销大**：移动端 GPU-NPU 同步一次约需 400 微秒，这与单个 GPU/NPU kernel 的执行时间相当甚至更长，严重制约并行效率。

3. **单处理器无法饱和内存带宽**：解码阶段是 memory-bound 的，单个处理器（GPU 或 NPU）仅能利用约 40-45 GB/s 的带宽，远低于 SoC 理论峰值 68 GB/s。

4. **NPU 浮点能力未被充分利用**：现有 NPU-only 方案（如 llm.npu、Qualcomm-AI）主要依赖 INT 量化计算，导致模型精度下降（Qualcomm-AI 报告 20% 以上的精度退化），或需要对输入数据集做特定量化，影响通用性。

---

## 三、洞察与设计

**关键洞察**：移动 SoC 中的 NPU 性能对 tensor 的阶段（stage）、顺序（order）和形状（shape）极度敏感——当 tensor 特征与 NPU 硬件的 systolic array 对齐时性能优异，不对齐时可能退化到比 GPU 更差。同时，SoC 的统一内存架构（UMA）使得 GPU 和 NPU 可以共享地址空间，而双处理器并行可将内存带宽利用率从 ~43 GB/s 提升至 ~60 GB/s（接近理论峰值）。

基于此洞察，HeteroInfer 采用分阶段优化策略：

- **Prefill 阶段**（compute-bound）：最大化 SoC 计算吞吐
  - **Layer-level 异构执行**：根据算子亲和性，将 Matmul 分配给 NPU，非 Matmul 算子（如 RMSNorm、SiLU、Softmax）分配给 GPU
  - **Tensor-level 异构执行**：将 FFN 层的权重和激活 tensor 按 NPU 友好的形状切分，一部分在 NPU 上计算，剩余部分卸载到 GPU 并行执行
  - **Activation-centric partitioning**：针对动态序列长度，将激活 tensor 按 NPU graph 标准尺寸切分，避免在线生成计算图的开销
  - **Weight-centric partitioning**：在解码阶段，按权重维度切分以最大化内存带宽利用

- **Decoding 阶段**（memory-bound）：最大化内存带宽利用
  - GPU 和 NPU 并行访问内存，以 75/25 的比例分担工作负载，聚合带宽可达 ~60 GB/s

- **快速同步机制**：利用 NPU kernel 执行时间的可预测性，CPU 在 NPU 预计完成前提前提交 GPU kernel，实现微秒级同步（相比默认 clFinish 的 ~400μs 开销）

- **Profiler-Solver 协作**：硬件 profiler 采集 GPU/NPU 性能数据，solver 搜索最优 tensor 划分方案

## 四、实现细节

- **硬件平台**：骁龙 8 Gen 3 SoC（Adreno 750 GPU + Hexagon NPU），同时在骁龙 8 Elite 上验证
- **GPU 后端**：基于 OpenCL 开发优化的 GPU kernel
- **NPU 后端**：集成高通 QNN SDK 提供的 NPU 算子
- **量化方式**：W4A16（权重 INT4 存储，FP16 计算），不使用激活量化和稀疏化技术，保持模型精度
- **共享内存**：通过 OpenCL API 建立 CPU-GPU 共享内存，通过 QNN API 建立 CPU-NPU 共享内存，进而实现 GPU-NPU 间的数据共享
- **NPU 静态图处理**：由于移动 NPU 只支持静态计算图，预先编译标准尺寸的 graph，运行时通过 activation-centric partition 将动态序列长度映射到标准 graph 的组合
- **快速同步实现**：记录 NPU kernel 的历史执行时间用于预测，CPU 端提前启动 GPU kernel 提交流程，消除 clFinish 的阻塞等待
- **Tensor 划分 Solver**：基于 profiler 数据，对每个算子搜索最优的 GPU/NPU 工作划分比例

## 五、实验结果

**实验平台**：骁龙 8 Gen 3（OnePlus 12），骁龙 8 Elite；模型：InternLM-1.8B、Llama-3B、Llama-7B、Llama-8B

**基线**：llama.cpp (CPU)、MNN-OpenCL (GPU)、MLC (GPU)、llm.npu (NPU)、PowerInfer-2 (NPU)

| 指标 | 结果 |
|------|------|
| 端到端加速比 | 1.34× – 6.02×（vs SOTA GPU-only 和 NPU-only 方案） |
| Prefill 阶段加速 | 3.29× – 24.9×（vs 各基线） |
| Decoding 阶段加速 | 1.50× – 2.53×（vs 各基线） |
| Prefill 吞吐（InternLM-1.8B, seq=256） | 1092 tokens/s |
| Prefill 吞吐（Llama-8B, seq=256） | 247.9 tokens/s |
| Decoding 速率（Llama-8B） | 14.01 tokens/s |
| Decoding 速率（InternLM-1.8B） | 51.12 tokens/s |
| 内存带宽利用率（GPU+NPU 并行） | 59.5 GB/s（96% of max available 61.9 GB/s） |
| 动态序列长度加速（vs Padding） | 平均 2.21× |
| 动态序列长度加速（vs Online-prepare） | 平均 2.24× |

**与游戏并行运行**：Prefill 阶段仅降低 2.2%，游戏 FPS 不受影响；Decoding 阶段降低 17.7%，FPS 不受影响。GPU-only 方案则会导致游戏 FPS 降为 0。

**能耗**：Hetero-tensor 端到端能耗比 GPU-only 低 55%，比 Hetero-layer 低 12.8%。

**快速同步效果**：Prefill 阶段提升 15.8%–24.3%；Decoding 阶段提升高达 4.01×（Llama-8B）。

## 六、批判性分析

1. **硬件平台覆盖有限**：实验仅在高通骁龙 8 Gen 3 和 8 Elite 两款 SoC 上进行。论文声称设计可迁移到其他 SoC（Apple、联发科、华为），但未提供任何跨平台实验。不同厂商的 NPU 架构差异很大（Apple Neural Engine、华为 Da Vinci），systolic array 的尺寸、weight stall 特性、编译器行为都可能不同，可迁移性存疑。

2. **加速比跨度大但未充分解释**：1.34× – 6.02× 的端到端加速比跨度极大。最低 1.34× 的提升出现在 decoding-heavy 的多轮对话场景（vs PowerInfer-2 的稀疏模型），而最高 6.02× 出现在 prefill-dominant 的长文本场景。论文倾向于突出最优结果，但在最常见的对话场景中（prefill 和 decoding 均衡），加速比约为 2.62×，远低于标题暗示的水平。

3. **基线公平性问题**：PowerInfer-2 使用稀疏模型（改变了模型结构），而 HeteroInfer 使用完整模型。虽然论文在公平性上有意识地做了区分，但在对比加速比时仍然将 PowerInfer-2 作为基线之一，可能给读者造成误导。llm.npu 使用 INT 量化导致精度损失，这使得与它的性能对比意义有限——二者不在同一精度水平上。

4. **Decoding 阶段改进有限**：尽管论文将 decoding 阶段的内存带宽优化作为核心贡献之一，但实际提升（1.50×–2.53×）相对于 prefill 阶段（3.29×–24.9×）显著较小。考虑到大多数交互场景中 decoding 占据主要时间，这一局限值得关注。

5. **快速同步的鲁棒性未充分论证**：快速同步机制依赖于 NPU kernel 执行时间的可预测性。论文未讨论在多任务场景下（如后台有其他 NPU 任务时），kernel 执行时间的方差是否会增大、预测精度是否会下降。

6. **Batch size 固定为 1**：所有实验都使用 batch size = 1，论文以"移动端尚不存在并发请求场景"为由。但随着端侧 Agent 和多模态应用的发展，多请求并发的场景正在出现，系统在 batch > 1 时的表现完全未知。

## 七、AI Infra / MLSys 视角

1. **异构调度思路的启发**：论文对 NPU 的 stage、order-sensitive、shape-sensitive 特性的详细刻画，对 AI Infra 领域设计面向异构硬件的 workload 调度器有重要参考价值。在数据中心场景中，不同代 GPU（如 A100 vs H100）、GPU vs TPU 之间也存在类似的 operator-level 性能差异，tensor-level 的精细划分策略可以迁移。

2. **Profiler-Solver 协作模式**：通过硬件 profiler 采集实际性能数据驱动 partition solver 的方法，与 ML 编译器（TVM、XLA）中的 auto-tuning 思路一脉相承，但粒度更细（到 tensor partition 级别）。可以考虑将此方法集成到通用 ML 编译器中，为异构集群的 operator placement 提供更精细的决策。

3. **内存带宽共享的洞察**：单处理器无法饱和内存带宽、多处理器并行可聚合带宽的发现，在多 GPU 系统（如 NVLink 互连的多卡系统）中也有类似现象。这一观察对设计 KV cache 管理（跨设备分散存储以聚合带宽）有启发意义。

4. **值得跟进的方向**：
   - 将 tensor-level 异构执行扩展到 MoE 模型：不同 expert 可以按 NPU/GPU 亲和性动态分配
   - 探索 GPU-NPU 协同在 speculative decoding 中的应用：NPU 执行 draft model，GPU 执行 verification
   - 研究端云协同推理中，端侧 HeteroInfer 与云端 prefill 的 pipeline 衔接

---

## 八、总结

HeteroInfer 是首个充分利用移动 SoC 中 GPU 和 NPU 异构算力的 LLM 推理引擎。其核心贡献在于：(1) 系统刻画了移动 NPU 的 stage/order/shape-sensitive 性能特性；(2) 提出了 layer-level 和 tensor-level 两种粒度的 GPU-NPU 并行策略；(3) 设计了基于 kernel 执行时间预测的微秒级快速同步机制。在骁龙 8 Gen 3 平台上实现了 1.34×–6.02× 的端到端加速，同时保持模型精度不受损、与其他应用的干扰可忽略。主要局限在于仅在高通平台验证、decoding 阶段提升相对有限、以及在多任务/多请求场景下的鲁棒性尚未充分论证。
