---

## 一、背景

形式化验证长期以来被视为提升操作系统内核可靠性和安全性的终极手段，但其高昂的开发成本一直阻碍实际应用。seL4 的验证花费了 20 person-years（其中 11 年用于证明，9 年用于形式化框架和工具），proof-to-code ratio 高达 20:1。CertiKOS 使用 Coq 也需要 14.9:1 的比例。近年来，线性类型系统、permission-based separation logic 和 SMT 自动化求解的结合为降低验证复杂度提供了新的可能性。Verus 作为 Rust 的新型验证框架，利用 Rust 的线性类型系统简化 SMT 编码，将别名分析和堆推理交由类型系统处理，大幅降低了 SMT 查询复杂度。

然而，即使有了 Verus 这样的工具，验证功能丰富的、充满指针操作的低级系统代码是否真正可行，仍然是一个开放问题。现代内核广泛使用递归数据结构（链表、树等）和非线性指针引用，而 SMT 求解器对归纳证明的支持天生有限——只能有限次展开递归，无法处理无界数据结构。

---

## 二、要解决的问题

1. **递归数据结构的验证可扩展性**：内核中的容器树、进程树、链表等无界递归数据结构需要归纳证明，但 SMT 求解器只能有限次展开递归定义，导致验证复杂度爆炸或证明不完备。
2. **指针密集代码的正确性保证**：现代内核大量使用反向指针、内部存储（internal storage）、环形引用等非线性指针模式以优化性能，这与 Rust 的线性所有权模型直接冲突。现有做法要么回避非线性结构（牺牲性能），要么信任 unsafe 代码（牺牲安全性）。
3. **内存安全与泄漏自由的全局推理**：Rust 的 borrow checker 不保护内存泄漏，且自动内存管理在规约层面引入不确定性（无法精确描述系统中所有内存的状态），使非干扰（non-interference）等全局性质的证明变得困难。
4. **验证速度与开发体验**：先前系统的验证时间从数十分钟到数小时不等，无法支持交互式开发。

---

## 三、洞察与设计

**关键洞察**：将递归数据结构的所有权（tracked permissions）从层次化的父子嵌套组织扁平化为全局 flat map 存储，可以将原本需要归纳证明的递归规约转化为非递归的全称量化，从而根本性地降低 SMT 求解难度，同时保留指针密集设计的性能优势。

基于这一洞察，Atmosphere 做出了三个关键设计决策：

### 1. Pointer-Centric Design（拥抱原始指针）
不回避非线性指针，而是像写 unsafe C 一样自由使用 raw pointer，但通过 Verus 的 tracked permission（PointsTo<T>）证明所有指针操作的正确性。这保留了反向指针、内部链表存储等性能优化手段。

### 2. Flat Permission Storage（扁平权限存储）
所有子系统的 tracked permissions 统一存储在该子系统的最顶层，作为一个 flat map（如 `thrd_perms: Map<ThrdPtr, PointsTo<Thread>>`）。这提供了全局视角，带来三个好处：
- **非递归规约**：容器树的 path 不变量无需递归定义父子关系，而是直接对任意节点的路径进行全称量化
- **结构与非结构证明分离**：用 closed spec function 封装结构不变量，用 open spec function 描述状态变化，两者独立验证，大幅减小 SMT 搜索空间
- **灵活遍历**：双向遍历（既可访问父节点也可访问所有子节点）不需要复杂的所有权转移

### 3. Manual Memory Management（手动内存管理）
放弃 Rust 的自动内存管理，显式分配/回收所有内核对象。通过 `page_closure()` 函数层次化地追踪每个数据结构占用的物理页面集合，自底向上合并并证明两两不相交，从而建立内存安全和泄漏自由。这使得精确描述系统中所有内存的状态成为可能，是 non-interference 证明的前提。

### 系统架构
Atmosphere 是一个完整的 microkernel，支持进程/线程、地址空间、IPC（endpoint-based）、IOMMU、容器（container，用于混合关键性系统的隔离），运行在多核硬件上（big lock 同步）。设备驱动、文件系统等运行在用户态。

## 四、实现细节

- **语言与工具链**：全部代码用 Rust 编写，使用 Verus 进行验证。Ghost code 在编译时由 Verus 擦除，无运行时开销。
- **代码规模**：6K 行可执行代码 + 20.1K 行证明代码（14.3K 行规约 + 5.8K 行验证提示/证明），其中 2.9K 行为顶层系统调用抽象规约。
- **Proof-to-code ratio**：3.32:1，显著低于 seL4 (20:1) 和 CertiKOS (14.9:1)。
- **页表**：4 级页表，支持 4KiB、2MiB、1GiB 页。所有 PML 级别的 tracked permissions 存储在页表顶层。refinement 证明通过 4 级 spec function 模拟 MMU 地址解析。
- **内存分配器**：基于 page array（类似 Linux），物理页三种状态（free/mapped/merged/allocated），三个双向链表管理不同大小的空闲页。
- **页表更新一致性**：每次页表写操作（包括中间级别）建模为独立步骤，分别证明地址空间映射不变或仅变化一个条目。
- **Non-interference 证明**：基于 unwinding theorem，证明 Output Consistency、Step Consistency、Local Respect 三个条件。针对三容器场景（A、B 互不信任 + V 经验证的共享服务），证明任意系统调用保持内存隔离和 endpoint 隔离。
- **TCB**：包括 Verus 前端、Z3 求解器、Rust 编译器、core 库子集、约 3000 行 trusted Rust 代码（硬件接口）、172 行汇编（trampoline）、boot loader、约 700 行缺失的 Verus 公理。
- **开发历程**：三个版本迭代（v1: 2 月 1 人熟悉 Verus，v2: 8 月 2 人 clean-slate 重写，v3: 4 月 1 人 50% 代码复用），总计约 2.5 person-years。

## 五、实验结果

**平台**：CloudLab c220g5（2x Intel Xeon Silver 4114, 192GB RAM）、c220g2（Intel X520 10Gb NIC）、d430（Intel P3700 NVMe SSD）。

### 验证性能

| 系统 | 1 线程 | 8 线程 | 证明行 | 代码行 | P/C Ratio |
|------|--------|--------|--------|--------|-----------|
| NrOS 页表 | 1m52s | 51s | 5329 | 400 | 13.3:1 |
| Atmosphere 页表 | 33s | – | 2168 | 496 | 4.3:1 |
| VeriSMo | 61m24s | 12m11s | 16101 | 7915 | 2.0:1 |
| Atmosphere | 3m29s | 1m7s | 20098 | 6048 | 3.3:1 |

- 在 i9-13900hx 笔记本上 32 线程验证 < 20 秒，比编译内核还快。
- 与 NrOS 页表对比（同用 Verus），flat 设计带来 3x 更低的 proof-to-code ratio 和 3x 更快的验证速度。

## 六、批判性分析

1. **Big lock 的实际影响被淡化**：论文承认使用全局大锁且中断禁用，但对其实际影响的讨论不够充分。在多核场景下，所有系统调用和中断串行化会严重限制可扩展性。论文中所有性能评估都是单核或少量核心场景，回避了这个根本限制。对于声称"支持多处理器机器"的系统，这是一个重要的缺失。

2. **Non-interference 证明的通用性存疑**：论文仅针对一个特定的三容器配置（A、B + V）完成了 non-interference 证明，然后声称"such proofs will be similar"。但不同的系统配置可能引入完全不同的信息流路径和资源共享模式。论文没有提供从特定证明到通用框架的路径，每种新配置都需要重新构造证明。

3. **与 seL4 的微基准比较不严谨**：论文自己也承认 mmap 系统调用"not strictly equivalent"，但仍然放在同一表格比较。IPC 比较中 Atmosphere 略慢（1058 vs 1026 cycles），而 Atmosphere 运行在 KVM 虚拟化环境下，这个开销未被讨论。

4. **TCB 规模被低估**：约 3000 行 trusted Rust 代码 + 172 行汇编 + boot loader + 700 行未验证公理 + Verus/Z3/Rust 编译器，实际 TCB 相当大。特别是 700 行"axioms missing in Verus"本质上是未经证明的假设，其正确性只能靠人工审查。

5. **容器资源回收模型过于简化**：禁止细粒度资源回收（只能终止整个容器才能回收资源），虽然简化了验证，但在实际 mixed-criticality 系统中可能不可接受。论文将这个限制包装为"设计选择"，但实际上是验证能力的妥协。

6. **开发成本的呈现方式**：2.5 person-years 包含了 1 person-year 的非验证工作（boot、驱动、benchmarks），且经历了两次 clean-slate 重写。如果计入学习曲线和废弃的代码，实际成本远高于呈现的数字。

---

## 七、总结

Atmosphere 展示了利用 Verus（Rust 的 SMT-based 验证框架）开发形式化验证 microkernel 的可行性。其核心贡献在于 flat permission storage 设计——将递归数据结构的所有权扁平化为全局 map，从而将递归规约转化为非递归全称量化，根本性地降低了 SMT 验证复杂度。结合 pointer-centric 设计和手动内存管理，Atmosphere 以 3.32:1 的 proof-to-code ratio 和 < 20 秒的全量验证时间，实现了接近 seL4 的性能和功能。主要局限在于 big lock 限制了多核可扩展性、non-interference 证明仅覆盖特定配置、以及较大的 TCB。该工作主要面向高可靠性要求的 mixed-criticality 系统场景。
