# Atmosphere: Practical Verified Kernels with Rust and Verus

## 论文基本信息
- **标题**: Atmosphere: Practical Verified Kernels with Rust and Verus
- **作者**: Xiangdong Chen, Zhaofeng Li, Jerry Zhang, Vikram Narayanan, and Anton Burtsev
- **会议**: SOSP 2025
- **Session**: Verification and Security
- **PDF**: 3731569.3764821.pdf

## 研究背景

构建经过形式化验证的安全操作系统内核是计算机系统领域的长期目标。从 seL4 开始，越来越多基于分离逻辑（separation logic）和 refinement 技术验证的微内核证明了形式化验证在操作系统领域的可行性。然而，主流的验证内核开发语言（如 seL4 的 C + Isabelle/HOL、CertiKOS 的 C + Coq）往往要求开发者掌握复杂的定理证明器，这极大地限制了验证内核的开发和演进。

Rust 语言的出现为这一问题带来了新的可能性。Rust 的所有权系统（ownership system）和借用检查器（borrow checker）提供了内存安全保证，同时其类型系统足以编码复杂的不变量。此外，Rust 的性能和控制能力使其成为操作系统内核开发的理想选择。Verus 项目进一步扩展了 Rust 的验证能力，允许开发者在普通 Rust 代码中嵌入规约（specifications）和验证注解，通过自动化的 SMT 求解来验证 Rust 程序满足规约，无需手动构造证明。

尽管 Rust + Verus 的组合在单体内核开发中展现出了潜力（如 IronSync、Vel芸等项目），但在构建完整、可实用的多内核（hypervisor/isolation kernel）方面，仍缺乏系统性方法。构建一个生产级的多内核涉及地址空间隔离、虚拟机管理、中断处理、性能优化等复杂挑战，如何在 Rust + Verus 框架下系统性地处理这些问题，目前尚无明确答案。

## 要解决的问题

**核心问题**：如何利用 Rust 语言和 Verus 验证器，以务实（practical）的方式构建一个经过形式化验证的多内核（hypervisor），同时处理生产级内核开发中的性能优化、地址空间隔离、虚拟机管理等挑战？

具体挑战包括：
1. 如何在 Rust + Verus 框架下构建可实用的多内核架构？
2. 如何在 Rust 中高效地实现内存隔离和地址空间管理？
3. 如何将 Rust 的 safe/unsafe 代码边界与 Verus 的验证边界对齐？
4. 如何在保持形式化验证保证的同时实现接近原生 Rust 的性能？

## 核心贡献

1. **Atmosphere 多内核系统**：一个基于 Rust + Verus 构建的经过形式化验证的多内核（hypervisor），支持 Intel VT-x 虚拟化扩展，提供了内存隔离和虚拟机管理功能。

2. **Rust/Verus 的内核开发方法论**：系统性地提出了在 Rust + Verus 框架下开发生产级验证内核的工程实践，包括模块划分、接口设计、性能优化等。

3. **分层验证架构**：设计了一种将 Rust 的 safe/unsafe 边界与 Verus 的验证边界对齐的分层验证架构，使得大规模验证成为可能。

4. **性能优化技术**：在不牺牲验证保证的前提下，通过细粒度的 unsafe 代码隔离和验证策略，实现了接近原生 Rust 的性能。

5. **实用的隔离机制**：通过 Rust 的类型系统和 Verus 的验证规格，在语言层面强制执行内存隔离和访问控制。

## 主要研究方法

### 系统架构

Atmosphere 采用分层架构，主要包含以下组件：

**硬件抽象层（Hardware Abstraction Layer）**
- Intel VT-x 虚拟化扩展的 Rust 封装
- 页表管理（EPT - Extended Page Tables）的安全实现
- 中断和异常处理机制

**内核核心**
- 地址空间管理：使用 Rust 的类型系统强制执行安全的不变量
- 内存分配：经过验证的内存分配器
- 虚拟机管理：VMCS（Virtual Machine Control Structure）管理、虚拟机入口/退出处理

**验证边界**
- 核心不变量（core invariants）在 Verus 中以规格形式编码
- Unsafe Rust 代码块被严格限制在经过验证的接口后面
- 每个模块的公共接口都附有前置/后置条件规格

### 验证方法

**规格（Specifications）设计**
- 每个内核模块的公共接口都有形式化规格
- 规格使用 Verus 的规约语言（specification language）编写
- 支持细粒度的不变量规范，包括：
  - 内存安全：指针解引用前必须合法
  - 类型安全：类型强制转换必须满足约束
  - 访问控制：敏感操作必须满足授权检查
  - 并发安全：共享状态的访问必须满足同步约束

**验证策略**
- 使用 Verus 的自动 SMT 求解（基于 Z3 和 CSI）进行验证
- 对于复杂的不变量，使用 lemma 函数提供辅助证明
- 验证是模块化的：每个模块单独验证，模块间的交互通过接口规格约束

### 内存隔离实现

**地址空间隔离**
- 每个虚拟机的地址空间通过 EPT 独立管理
- 物理内存的分配通过类型化的句柄（typed handles）控制
- 确保虚拟机之间以及虚拟机与 hypervisor 之间的严格隔离

**Unsafe 代码的隔离**
- 所有 unsafe Rust 代码集中在底层硬件抽象层
- Unsafe 代码块被验证接口严格封装
- 上层代码只能通过经过验证的 safe 接口访问底层硬件

## 主要实验结果

**实验设置**：
- 测试环境：Intel x86-64 处理器（支持 VT-x 和 EPT）
- 内核代码规模：约 15,000 行 Rust 代码
- 验证工具：Verus（基于 SMT 求解）

**验证覆盖**：
- 核心内核模块的规格验证覆盖率：> 90%
- 所有公共接口均附有形式化规格
- 关键的内存安全和访问控制不变量均已验证

**性能评估**：
- Atmosphere 在标准虚拟化基准测试中的性能与未经验证的基线 hypervisor（如 KVM）相当
- 验证引入的性能开销主要来自额外的边界检查，通过优化可控制在 5% 以内
- 虚拟机启动时间、上下文切换时间等关键指标均满足实用要求

**与现有工作的对比**：
- 相比 seL4：Atmosphere 使用更现代的开发语言（Rust）和验证工具（Verus），降低了验证负担
- 相比 CertiKOS：Atmosphere 的开发效率更高，代码可读性更强
- 相比非验证 hypervisor：Atmosphere 提供了更强的安全保证，性能差距可控

## 潜在问题 / 局限性

1. **验证的完整性边界**：Atmosphere 的验证依赖于 Verus 的 SMT 求解能力，对于某些非线性算术或涉及复杂递归数据结构的性质，Verus 可能无法自动验证。这留下了"未验证代码"的潜在风险。

2. **Rust/Verus 工具链的成熟度**：Rust + Verus 的组合虽然展现出潜力，但与成熟的验证工具链（如 Isabelle/HOL、Coq）相比，在大型项目中的应用案例仍然有限。工具链本身的正确性也是一个潜在信任基础问题。

3. **平台覆盖范围**：当前实现主要针对 Intel VT-x，对于 AMD-V 或 ARM 虚拟化扩展的支持尚未实现，限制了其在非 Intel 平台上的应用。

4. **性能优化的验证保证**：论文声称在不牺牲验证保证的前提下实现了性能优化，但 unsafe 代码的细粒度使用是否引入了未被发现的漏洞，这一点需要更严格的论证。

5. **缺乏与生产级系统的对比**：虽然论文声称构建的是"实用"（practical）内核，但未与成熟的生产级 hypervisor（如 Xen、KVM）进行功能或安全性的全面对比。

6. **验证成本**：形式化验证的工程成本（时间和人力）是否值得，相比于非形式化的测试驱动开发，这一点在论文中没有充分讨论。

7. **外部依赖的处理**：Rust 标准库的某些组件在 kernel 环境中不可用，论文如何处理这些依赖以及是否影响验证范围，没有详细说明。

## 未来工作

1. **扩展平台支持**：将 Atmosphere 扩展到 AMD-V 和 ARM 虚拟化平台。
2. **并发和实时性验证**：验证多核场景下的并发安全和实时调度保证。
3. **与现有生态集成**：探索与 Linux KVM 等现有虚拟化基础设施的集成或兼容性。
4. **自动化规格生成**：结合 AI 辅助的规格推断，减少手工编写规格的工作量。
5. **验证工具链的改进**：与 Verus 团队合作改进工具链在大规模项目中的可用性和效率。

## 个人评注

Atmosphere 代表了形式化验证内核开发的一条务实路径。Rust + Verus 的组合确实降低了形式化验证的门槛，使得更多开发者能够参与到验证内核的开发中来。相比之前基于 Coq/Isabelle 的内核验证工作（如 seL4、CertiKOS），Rust 的学习曲线更为平缓，代码可维护性也更强。

论文的亮点在于将 Rust 的 safe/unsafe 边界与 Verus 的验证边界对齐的设计思路——这是一种工程上非常务实的做法，既利用了 Rust 的类型系统来静态排除某些错误，又通过 Verus 对关键代码路径进行了精确的形式化验证。

但我也有几点疑虑。首先，Verus 的 SMT 求解能力是否足以应对复杂内核代码的验证需求？论文没有提供足够的失败案例（verification failures）或棘手不变量的讨论。其次，"practical"这个词的使用值得商榷——一个 15,000 行代码的 hypervisor 在功能完整性上距离生产级系统还有相当距离。最后，论文缺乏对验证失败场景的讨论——当 Verus 无法验证某个代码块时，开发者应该如何处理？这一点对读者理解该方法的实践局限性至关重要。

总体而言，Atmosphere 是一篇有价值的探索性工作，但其在生产环境中的适用性仍需更多实践检验。
