## 一、背景

形式验证（formal verification）长期被视为系统软件领域"可望而不可即"的目标：代码越复杂、越底层，完成验证所需的人力和专业知识就越庞大。seL4 的验证耗费了 20 person-years，CertiKOS 也需要 14.9:1 的 proof-to-code ratio。即便近年来出现了 Dafny、Verus 等基于 SMT 的自动化验证器，如何将其应用于指针密集、含复杂递归数据结构的内核代码，仍是一个开放问题。

与此同时，混合关键性系统（mixed-criticality systems）的兴起对操作系统提出了更严格的隔离要求。传统微内核（seL4、NOVA 等）提供了运行时隔离机制，但缺乏机器可检查的功能正确性证明。如何以可接受的工程代价，开发出既有形式化功能正确性证明、又具备实用性能的微内核，是本文的核心动机。

---

## 二、要解决的问题

**问题 1：SMT 求解器对递归数据结构的验证能力有限**

内核大量使用链表、树、页表等递归数据结构。SMT 求解器不原生支持归纳证明（inductive proofs），通常需要手动展开（unrolling），导致 SMT 搜索空间指数级增长，验证时间和复杂度难以控制。

**问题 2：Rust 的所有权模型与内核设计存在语义鸿沟**

Rust 的 borrow checker 和智能指针不支持内核常见的非线性指针结构（循环引用、反向指针等），迫使开发者要么引入 `unsafe` 的智能指针类型（留下未验证的信任基础），要么放弃性能优化。

**问题 3：自动内存管理与全局内核证明不兼容**

Rust 的自动内存管理隐藏了系统的全局内存状态，使得内存安全性和 leak freedom 的规范变成非确定性的，无法支撑跨子系统的全局证明（如非干涉定理要求一个域不能耗尽另一个域的内存）。

**问题 4：开发效率与验证速度的矛盾**

现有验证内核的主要瓶颈之一是验证速度过慢（seL4 的验证工具链需要数小时），阻碍了交互式开发体验。

## 三、核心设计

Atmosphere 是一个全功能微内核，支持多 CPU（大锁下运行）、进程/线程、动态内存管理、IPC、虚拟地址空间、IOMMU 和容器组（container groups，用于隔离的混合关键性域）。开发语言为 Rust，用 Verus 进行功能正确性的形式验证（精化高层抽象规范）。

三个关键设计选择使得验证保持实用：

### 1. 指针中心设计（Pointer-centric design）

放弃 Rust 的规范惯用法，直接使用 raw 非线性指针，类似 unsafe C。内核数据结构使用内部存储表示树节点指针（类似 Linux），使用反向指针支持 O(1) 链表删除。指针操作的正确性完全由 Verus 的 permission pointer 机制（线性权限指针，ghost state）来证明，而非依赖 Rust 类型系统。

这避免了"要么不使用非线性结构，要么信任未验证的 `unsafe` 智能指针"的两难困境，同时保留了性能优化的空间。

### 2. 扁平权限存储（Flat permission storage）

将层次化数据结构（页表各级节点、进程树中的所有线程等）的 tracked permission 统一存放在最顶层子系统的 flat map 中，而不是随数据结构递归分布。

这带来了关键收益：
- 用非递归的方式编码无界递归数据结构的属性，直接消除了 SMT 的递归展开需求。
- 允许将结构性不变量（树无环、反向指针正确）与非结构性不变量（新线程加入某进程）的证明解耦。
- 使非干涉证明能以非递归方式访问全局内核状态，大幅降低证明复杂度。

### 3. 手动内存管理（Manual memory management）

放弃 Rust borrow checker 对内核对象生命周期的管理，改为显式分配/释放（类似 C），但通过 Verus 证明所有内存操作的安全性和 leak freedom。

通过 `page_closure()` 规范函数（返回某数据结构及其所有子对象占用的物理页集合），以自底向上的层次方式维护内存证明：局部证明两两不相交，然后合并各子系统的 page_closure，避免将所有对象的全局不变量作为 SMT 约束（指数级搜索空间）。

## 四、实现细节

- **代码规模**：6K 行可执行代码，20,098 行规范/证明代码，proof-to-code ratio 3.32:1
- **Verus 版本**：基于 Verus 的 linear permission pointer 抽象，不依赖 Rust 标准库的向量、智能指针、hashmap、mutex 等；只使用 Rust `core` 的最小子集
- **不可验证的部分（TCB）**：约 3,000 行 trusted Rust 代码（IOMMU 配置 465 行、执行环境初始化 321 行、中断处理 293 行等）+ 172 行汇编（系统调用/中断 trampoline）+ Verus 前端 + Z3 + Rust 编译器 + Rust core + 约 700 行用于弥补 Verus 缺失公理的 axiom 代码
- **非干涉证明**：基于 Luke 等人的 unwinding theorem，证明 Output Consistency（OC）、Step Consistency（SC）和 Local Respect（LR）三个 unwinding 条件，覆盖三容器场景（两个不可信隔离容器 A/B + 一个已验证共享容器 V）
- **并发限制**：当前在大锁下运行；多核页表一致性通过对每个页表更新步骤建模、分别证明中间状态的一致性来处理
- **开发历程**：三个版本的 clean-slate 重写，总历时约 1.5 个物理年，2 person-years（其中约 14 个月在验证代码上）

## 五、实验结果

**实验环境**：CloudLab c220g5（2× Intel Xeon Silver 4114 10-core @ 2.20GHz，192GB RAM）；笔记本 Intel i9-13900hx；禁用超线程、turbo boost、CPU idle 和频率缩放。

### 验证复杂度对比

| 系统 | 语言 | 规范语言 | Proof-to-Code Ratio |
|------|------|---------|---------------------|
| seL4 | C+Asm | Isabelle/HOL | 20:1 |
| CertiKOS | C+Asm | Coq | 14.9:1 |
| SeKVM | C+Asm | Coq | 6.9:1 |
| Ironclad | Dafny | Dafny | 4.8:1 |
| NrOS | Rust | Verus | 10:1 |
| VeriSMo | Rust | Verus | 2:1 |
| **Atmosphere** | **Rust** | **Verus** | **3.32:1** |

### 验证速度

| 系统 | 单线程 | 8线程 | Proof LOC | Code LOC | P/C Ratio |
|------|--------|-------|-----------|----------|-----------|
| NrOS page table | 1m52s | 51s | 5329 | 400 | 13.3:1 |
| Atmo. page table | 33s | — | 2168 | 496 | 4.3:1 |
| Mimalloc | 8m12s | 1m40s | 13703 | 3178 | 4.3:1 |
| VeriSMo | 61m24s | 12m11s | 16101 | 7915 | 2.0:1 |
| **Atmosphere** | **3m29s** | **1m7s** | **20098** | **6048** | **3.32:1** |

Atmosphere 在现代笔记本（32 线程）上完成全量验证仅需 **20 秒以内**。

### 系统调用延迟（cycles，在 CloudLab c220g5，KVM 下）

| 系统调用 | Atmosphere | seL4 |
|----------|-----------|------|
| Call/reply (IPC) | 1,058 | 1,026 |
| Map a page | 1,984 | 2,650 |

### 设备驱动与应用性能

- **Ixgbe 网络驱动（64B UDP）**：批次 32 时达到 10GbE 线速（14.2 Mpps）；独立进程+单次上下文切换时 2.3 Mpps/core
- **NVMe 驱动（4K 顺序读写）**：读性能与 SPDK 持平；写有约 10% 额外开销（232K IOPS vs 256K IOPS）
- **Maglev 负载均衡器**：驱动独立核时 13.3 Mpps/core（DPDK：9.72 Mpps）
- **httpd web 服务器**：99.4K req/s（vs Nginx on Linux：70.9K req/s）

## 六、批判性分析

**1. 大锁是主要的实用性限制，但被轻描淡写**

Atmosphere 当前在大锁下运行，作者将并发支持推到"future work"。对于混合关键性系统，这意味着实时性保证（时间可预测性）存疑——长时间持有大锁（如终止容器、发送大内存区域）会导致其他进程被阻塞，形成隐性时序信道。论文承认了这一点，但并未评估实际影响的量级，对"可实用"的定性结论有一定的夸大成分。

**2. 设备驱动性能对比存在设置偏差**

Maglev 实验中，Atmosphere 的 atmo-c2 配置（驱动独立核）实测 13.3 Mpps，超越了 DPDK 的 9.72 Mpps。然而论文未明确说明 CPU 亲和性配置、中断路由、NUMA 拓扑是否对齐；DPDK 和 Atmosphere 的驱动使用方式本质上不同（前者用户态轮询，后者微内核用户进程），"比 DPDK 快"的结论需要更仔细的分析，而非直接引用数字。httpd 超越 Nginx 的结果（99.4K vs 70.9K req/s）同样缺乏对 Nginx 调优程度的说明。

**3. VeriSMo 的 2:1 ratio 比较不够公平**

作者将 Atmosphere 的 3.32:1 与 VeriSMo 的 2:1 对比，并归因于 VeriSMo"语义更简单"和"放宽了验证超时限制"。但 VeriSMo 验证的是 AMD SEV-SNP 上的安全模块，与全功能微内核相比语义差异悬殊，这一比较的参考价值有限。

**4. TCB 未经验证的 trusted Rust 代码规模不小**

约 3,000 行 trusted Rust 代码（IOMMU、中断初始化等）+ 172 行汇编 + 700 行 axiom 代码共约 3,872 行游离于形式证明之外。对于安全关键系统，这部分的漏洞依然是实际威胁，论文在这一点上的讨论较为简略。

**5. 非干涉证明的通用性存疑**

当前的非干涉证明仅覆盖固定的三容器配置（A、B、V）。作者声称对不同配置的证明"类似"，但并未提供自动化或参数化机制，每换一种系统配置都需要重写证明，限制了实际部署的灵活性。

---

## 七、总结

Atmosphere 通过三项核心设计选择——指针中心设计、扁平权限存储、手动内存管理——在 Rust + Verus 上实现了一个全功能形式验证微内核，将 proof-to-code ratio 降低至 3.32:1，全量验证在现代笔记本上仅需 20 秒，综合性能与 seL4 相当甚至更优。这是自动化 SMT 验证器首次被证明足以应对复杂、指针密集的微内核代码，为系统软件形式验证的工程可行性树立了重要里程碑。主要局限在于：大锁限制并发支持、TCB 中仍存在约 3,000 行未验证代码、非干涉证明仅覆盖固定系统配置，以及部分性能对比的实验设计存在局限性。
