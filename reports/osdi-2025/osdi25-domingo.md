# Kamino: Efficient VM Allocation at Scale with Latency-Driven Cache-Aware Scheduling

## 研究背景与动机

### VM 分配系统的重要性

大型云服务商（Azure、AWS、GCP）投入数十亿美元建设基础设施来满足不同 VM 类型的需求。VM 分配系统负责将 VM 请求映射到物理硬件，是云栈中的关键系统。设计目标：
1. 在严格延迟上限（毫秒级）内完成 VM 分配
2. 实现"高质量"分配（考虑提供商和客户偏好，高服务器利用率）

这两个目标天然矛盾——高质量分配需要评估大量约束和库存（数十万台服务器），这通常计算密集，在高负载下成为瓶颈。

### 现有 VM 分配系统

Azure 的 Protean 等现代 VM 分配器采用：
- **多分配代理（AA，Allocation Agent）**：多 AA 协同处理同一硬件库存的请求，充分利用多核并行性，减少跨节点通信和一致性开销
- **分层缓存**：Top-level cache（快速路径）处理完全相同的请求；Lower-level cache（慢速路径）处理有部分相同约束的请求

### 核心问题：请求调度与缓存的割裂

现有 VM 分配器的关键局限：**调度请求到 AA 的策略与底层缓存机制缺乏协同**。

现有调度策略（round-robin、work-stealing、uniform random、hash-based）不考虑请求类型是否在 AA 缓存中存在：
- 调度到缓存中无请求类型的 AA → 缓存未命中，增加数百毫秒延迟
- 调度到缓存中已有请求类型的 AA → 缓存命中，延迟低
- 缓存分层结构（top-level + lower-level）的复杂交互使得难以预估调度结果

### 另一个问题：AA 可扩展性

每个 AA 需要维护私有缓存（避免锁竞争和同步开销），但这导致内存消耗巨大。每个 cache slot 10-100MB，限制了每台机器可运行的 AA 数量（Azure 机器每台约 4 个 AA，远低于 CPU 核心数）。

---

## 要解决的核心问题

如何设计一种延迟驱动的缓存感知请求调度算法和系统，在考虑 AA 缓存状态的情况下将 VM 请求分配给最合适的 AA，从而同时优化端到端延迟、吞吐量和内存效率？

---

## 主要贡献

1. **LatCache 算法**：首个延迟驱动的缓存感知在线请求调度算法，基于理论（最优在线作业调度）但针对 VM 分配场景扩展
2. **Kamino 框架**：生产级 VM 分配请求调度框架，实现 LatCache，支持请求分类、队列分配、层级缓存感知
3. **部分指标推理**：通过 AA 队列中请求类型和缓存命中预测来估计延迟，无需完整缓存状态
4. **大规模生产评估**：基于 Azure 真实控制平面的仿真 + 生产部署，验证了 42% 延迟降低、33% 缓存未命中率降低、17% 内存占用减少

## 研究方法与设计

### 问题建模

VM 分配请求调度可建模为在线作业调度问题：
- 每个请求有已知的请求类型
- 每个 AA 有请求队列和私有缓存
- 缓存命中/未命中决定处理时间（未命中可达数百毫秒）
- 目标：最小化平均和尾延迟（排队时间 + 处理时间）

这一问题的理论复杂度极高（已知难解），且实际情况更复杂：请求处理时间不固定，取决于缓存状态，而缓存状态又取决于调度器的历史决策。

### LatCache 算法

**核心洞察**：无需知道完整缓存状态，仅需部分指标即可估计 AA 的预期延迟。

**LatCache 使用的部分指标**：
1. AA 队列中每种请求类型的数量
2. 每种请求类型的缓存命中预测（基于历史数据）
3. AA 当前的处理时间估计

**延迟估计公式**（核心思想）：
```
estimated_latency(AA) = queue_wait_time(AA)
                        + estimated_processing_time(AA, request_type)
```

其中：
- `queue_wait_time`：基于 AA 队列长度和历史处理时间
- `estimated_processing_time`：根据请求类型是否在缓存中以及部分命中情况估算

**关键创新**：
- 缓存感知而非缓存固定：考虑不同请求类型的缓存命中率差异
- 层级缓存感知：top-level 和 lower-level cache 的命中率差异都纳入估计
- 延迟驱动而非请求类型驱动：避免简单地将某类型固定到某 AA（会导致热点）

### Kamino 架构

**系统架构**：
1. **Gateway/Load-balancer**：接收请求并路由到 allocator node
2. **LatCache Agent Assigner**：Kamino 的核心组件，对每个到达的请求：
   - 查询所有 AA 的当前队列状态和缓存预测
   - 计算每 AA 的预期延迟
   - 将请求分配给延迟最低的 AA
3. **Allocation Agents (AAs)**：运行规则评估，执行实际的 VM 分配
4. **层级缓存**：top-level（快速路径）和 lower-level（慢速路径），各有不同延迟特性

**LatCache 与 AA 缓存的协同**：
- LatCache 估计的 processing time 考虑了缓存命中情况
- AA 的缓存策略决定哪些数据被逐出
- 两者共同决定了端到端延迟

### 层级缓存详细设计

- **Top-level cache**：存储完全相同的请求结果
- **Lower-level cache**：存储部分相同约束（如相同 VM 大小但不同优先级）的结果
- 不同 AA 的缓存槽位大小可变（10-100MB）
- 缓存命中/未命中的 processing time 差异巨大（最高达 5 倍）

---

## 关键实现细节

- **仿真器**：高精度请求调度仿真器，支持真实生产 traces
- **生产部署**：Azure 控制平面真实生产 zone（每个 zone 数万台机器）
- **与其他系统集成**：与 Protean（Azure VM 分配系统）集成，无需修改 AA 内部逻辑
- **分阶段流水线**：请求分类和队列分配流水线执行，保持高吞吐量

---

## 实验结果与分析

### 仿真评估

**实验配置**：
- Azure 真实多区域分配 traces（超过 50 个 allocator 节点）
- 对比基线：Protean（Azure 现有 VM 分配器）、Round-Robin、Consistent Hashing

**延迟结果**：
- **平均延迟降低 42%**（相比延迟无关的调度器）
- **尾部延迟（P90）改善显著**：Round-Robin 和 Consistent Hashing 分别比 Protean 高 30% 和 60% 的尾延迟

**缓存效果**：
- **缓存命中率提升**：LatCache 智能地将请求分配到缓存友好的 AA
- **吞吐量提升**：队列等待时间减少，AA 吞吐量提升达 2 倍（在突发负载期间尤其显著）

### 生产部署结果

**Azure 生产 zone 验证**（18 个月以上）：
- **P90 延迟降低 11.9%**
- **缓存未命中率降低 33%**
- **每 AA 内存占用减少 17%**

**实际意义**：
- 尾部延迟降低确保了延迟敏感工作负载（数据分析平台、在线游戏、虚拟桌面）的资源调配可靠性
- 缓存未命中率降低减少了对机器的需求，降低了争夺和重试
- 内存效率提升使每台控制平面机器可运行更多 AA，降低了资源争夺和通信开销

### 可扩展性

- LatCache 在数十万台机器规模下仍保持稳定效果
- 算法复杂度为 O(AA_count × request_type_count)，对 AA 数量和请求类型数量均线性

---

## 潜在问题与局限性

1. **与通用调度理论的差距**：论文将 VM 分配建模为在线作业调度问题，但实际系统中的层级缓存和非固定处理时间使得理论边界与实际性能之间的联系不紧密
2. **延迟估计的准确性**：LatCache 的核心依赖历史数据和缓存命中率预测，在新请求类型或负载模式突变时可能失效
3. **生产部署规模**：虽然声称在 Azure 生产 zone 验证，但具体规模（AA 数量、zone 规模）未量化
4. **与其他云厂商的对比**：缺乏与 AWS、GCP 等其他云厂商 VM 分配系统的对比
5. **与 Kubernetes 调度器的对比缺失**：Kubernetes 的 POD 调度器也面临类似问题，但论文未涉及

## 未来工作方向

- 将延迟驱动的缓存感知调度扩展到其他系统（LSM-tree 数据库、CDN、微服务架构）
- 更精细的缓存命中率预测模型（考虑时间因素、负载波动）
- 多区域协同调度
- 与弹性伸缩系统的深度集成

## 个人评注

### 优势

1. **理论与工程的精准结合**：将 VM 分配请求调度建模为在线作业调度问题，为工程方案提供了理论依据；同时针对 VM 分配的独特特性（层级缓存、处理时间依赖缓存状态）进行了实用扩展
2. **部分指标推理的洞察**：不追求完美的全局状态感知，而是利用"部分指标足够好"的原则，大幅简化了调度决策的计算复杂度
3. **生产验证的价值**：不仅有仿真，还有 Azure 生产 zone 的实际部署数据（P90 降低 11.9%、缓存未命中降低 33%、内存减少 17%），这在学术论文中极为罕见
4. **LSM 扩展的暗示**：论文提到在 LSM-tree key-value store 上的初步实验，暗示了方案的广泛适用性

### 潜在问题

1. **"42% 延迟降低"的适用范围**：这一数字来自仿真环境（vs. 延迟无关调度器），而实际生产部署改善为 11.9%（P90）。读者应注意区分仿真结果和生产结果的差距
2. **延迟估计模型的敏感性**：LatCache 的效果高度依赖命中率预测的准确性。预测模型在新工作负载下可能不准确，实际部署需要持续校准
3. **Azure 特定的工程细节未披露**：作为微软内部系统，Kamino 的许多工程细节（如具体使用哪些特征进行预测、缓存替换策略等）未公开，限制了复现和迁移到其他系统
4. **AA 数量与内存效率的取舍**：论文强调内存效率（减少 17%），但未讨论这是否以牺牲 AA 数量为代价，以及这个权衡在什么负载条件下是合理的
