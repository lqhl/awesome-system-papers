# Spars: OS Rendering Service Made Parallel with Out-of-Order Execution and In-Order Commit

## 论文基本信息

- **标题**: OS Rendering Service Made Parallel with Out-of-Order Execution and In-Order Commit
- **作者**: Yuanpei Wu, Dong Du (Shanghai Jiao Tong University); Chao Xu (Huawei Fields Lab); Yubin Xia, Yang Yu (Shanghai Jiao Tong University); Ming Fu (Huawei Fields Lab); Binyu Zang, Haibo Chen (Shanghai Jiao Tong University)
- **会议**: OSDI 2025
- **链接**: https://www.usenix.org/conference/osdi25/presentation/wu-yuanpei

## 研究背景与动机

渲染服务是智能设备操作系统（Android、iOS、OpenHarmony）中不可或缺的系统服务，使 GUI 元素能够在帧缓冲区中正确显示。现代用户平均每天花费 6 小时 40 分钟在屏幕上，渲染相关任务在商用智能手机上消耗了 65%-95% 的总 CPU 和 GPU 运行时间。

然而，随着折叠屏手机（三折叠设备需要渲染 117% 更多像素）和一芯多屏（智能座舱）等高扩展性显示场景的出现，传统顺序渲染模型面临严峻挑战：
1. **工作负载大幅增加**: 三折叠手机每帧需渲染 117% 更多像素，但华为 Mate70（单屏）和 MateXT（三折）使用相同 SoC
2. **现有并行化方案不足**: 帧间并行（inter-frame）和多窗口并行（multi-window）均无法有效应对持续重负载
3. **核心瓶颈：单核垄断**: 渲染线程独占单核 80% 利用率，12 核中 9 个处于空闲

**关键观察**: 在商用智能手机上，终端到终端渲染过程中 CPU 占 82% 时间，GPU 只负责将数学表达的 2D 基元三角化后进行光栅化。渲染程序中的大量依赖（状态依赖、绘图顺序依赖、接口依赖）阻碍了细粒度并行化。

## 要解决的核心问题

1. **状态依赖**: 渲染树中每个节点只包含相对于父节点的相对信息（如相对变换矩阵），修改一个节点需要更新整个子树，阻碍任务封装
2. **绘图顺序依赖**: 图形基元（graphics primitives）之间的重叠关系必须被严格执行（背景必须在前景之前绘制），传统深度优先遍历隐式保证这一顺序
3. **接口依赖（兼容性）**: 为并行化而重构渲染服务不能影响现有的状态式渲染接口（Skia Canvas、Drawing API）和依赖于此的命令批处理优化

## 主要贡献

1. **Spars: 首个利用乱序执行/有序提交架构的并行 OS 渲染服务**: 将经典计算机体系结构中的乱序执行/有序提交思想首次系统性地引入 OS 渲染服务
2. **三阶段渲染管线**: In-order preparation（自包含任务构造）→ Out-of-order execution（乱序并行执行）→ In-order commit（有序提交），在保证绘图正确性的同时最大化并行性
3. **Spade2D: 新型 2D 绘图引擎**: 提供无状态接口以支持细粒度并行化，同时保持与现有状态式渲染接口的兼容性
4. **显著性能提升**: 在单屏、双折、三折手机和一芯多屏配置下，平均帧率提升 1.76×-1.91×，功耗降低 3.0%，图形基元预算增加 2.31×

## 研究方法与设计

### 乱序执行/有序提交的核心类比

**经典处理器中的乱序执行**:
- 处理器以与原程序顺序不同的顺序执行指令（当依赖满足时）
- 执行单元空闲时，分派器调度就绪指令，充分利用执行单元
- 最终按原始顺序提交结果到寄存器/内存，保证程序正确性

**Spars 中的渲染并行化**:
- **In-order preparation**: 按深度优先遍历构造自包含渲染任务和重叠关系
- **Out-of-order execution**: 工作线程以任意顺序执行自包含任务，最大化多核利用率
- **In-order commit**: 提交线程按绘图顺序提交执行结果到 GPU 命令缓冲区

### 三阶段详细设计

#### Stage 1: In-order Preparation（主线程）

**自包含任务构造**:
- 任务封装完整绘图状态：变换矩阵 + 裁剪区域 + 基元参数 + 颜色样式
- 深度优先遍历变体：快速 dry run，不执行任何核心渲染逻辑（不调用 2D 引擎生成任何 GPU 对象）
- 在 preparation 阶段计算每个渲染任务之间的重叠关系

**重叠关系管理**:
- 追踪每个任务的"前驱依赖"——必须在当前任务提交前完成的任务
- 使用位图或链表高效存储重叠关系

**命令批处理优化**:
- 在 preparation 阶段执行状态式命令批处理优化（兼容现有优化）

#### Stage 2: Out-of-order Execution（Worker 线程）

**无状态执行**:
- 每个 worker 线程调用 Spade2D 引擎将 2D 图形基元翻译为 GPU 对象（mesh、texture、pipeline 等）
- Spade2D 提供无状态接口：每个任务携带完整上下文，无需维护历史状态

**可配置线程数**:
- 典型配置 3-5 个 worker 线程
- 保留部分核心给提交线程、应用线程和其他系统线程

**GPU 对象收集**:
- 生成的 GPU 对象放入多生产者单消费者（MPSC）资源池

#### Stage 3: In-order Commit（提交线程）

**重叠感知的顺序提交**:
- 提交线程从 MPSC 池收集 GPU 对象
- 根据 preparation 阶段记录的重叠关系，保证按正确绘图顺序提交
- GPU 对象通过句柄引用绑定到 GPU 命令缓冲区，无需等待所有 worker 完成

**关键设计**: 提交线程不必等待所有 worker 完成，只需按重叠关系顺序提交。等待仅在绘图依赖不满足时发生，且大多被 worker 执行时间覆盖。

### Spade2D 绘图引擎

**无状态接口设计**:
- 与传统 Skia Canvas 等有状态接口不同，Spade2D 每个 API 调用携带完整绘图上下文
- 兼容 stateful 接口的自定义渲染应用（API 兼容层）

**多核并行化基础**:
- 无状态设计确保每个任务可在任意 worker 线程上执行而无需同步

## 关键实现细节

### 自包含任务的具体结构
- **Transform Matrix** (12 floats): 绝对变换矩阵（由父节点累乘到当前节点）
- **Clipping Region** (4 floats): 绝对裁剪矩形
- **Primitive Parameters** (variable): 具体图形参数
- **Color/Style** (variable): 颜色和样式信息

### 与 OpenHarmony 的集成
- 基于 OpenHarmony 5.0 渲染管线修改
- 实现了 VMM 实时升级（通过 Orthus），无需重启 VM 即可部署 Spars
- Iperf 测试显示 VMM 升级期间约 200ms 轻微性能波动

### 与 D-VSync 的协同
- D-VSync 利用单核 CPU 能力处理帧率波动
- Spars 与 D-VSync 协同：VIO 利用多核处理持续重负载，D-VSync 保持帧间同步

## 实验结果与分析

### 测试平台
- 华为 Mate70（单屏）、MateX5（双折）、MateXT（三折）
- 12 种一芯多屏配置（智能座舱场景）
- OpenHarmony 5.0 渲染管线

### 关键结果
- **帧率提升**: 平均 1.76×-1.91×（涵盖所有测试配置）
- **功耗降低**: 整体设备功耗降低 3.0%（通过更好地利用多核）
- **图形基元预算增加**: 在相同稳定帧率下，图形基元总数预算增加 2.31×
- **折叠屏场景**: MateX5 和 MateXT 在更大屏幕面积下帧率改善尤为显著

### CPU 利用率改善
- 传统方案：渲染线程独占单核 80% 利用率，9 核空闲
- Spars：CPU 核心利用率显著改善，多核并行有效分担负载

## 潜在问题与局限性

1. **Spade2D 的 API 兼容层开销**: 为兼容现有有状态渲染 API 而设计的兼容层可能引入额外开销
2. **Worker 线程数配置敏感性**: 论文建议 3-5 个 worker，但不同设备（不同 SoC、不同核心数）可能需要不同的配置，缺乏自适应机制
3. **提交线程的负载**: 提交线程负责收集 GPU 对象和顺序提交，在极高帧率或极多图形基元场景下可能成为瓶颈
4. **与 GPU 命令缓冲区的交互**: Vulkan/Metal 等现代 GPU API 对命令缓冲区的提交有特定约束（commandbuffer 大小限制、secondary command buffer 限制），这些约束在论文中未被充分讨论
5. **现有渲染优化（如 Skia 的命令批处理）的保持**: 命令批处理等状态式优化是否在 Spade2D 中得到同等保持？

## 未来工作方向

1. 自适应 worker 线程数配置
2. 与 GPU API 的更紧密协同
3. 扩展到 3D 渲染场景

## 个人评注

### 优点
1. **跨领域思想迁移的典范**: 将计算机体系结构中经典的乱序执行/有序提交思想迁移到 OS 渲染服务，是一个优雅且具有广泛启发价值的设计选择
2. **自包含任务的构造**: 在"快速 dry run"中计算完整绘图状态和重叠关系，避免了核心渲染逻辑重复执行，是一个精妙的实现技巧
3. **与现有生态的兼容性设计**: Spade2D 同时提供无状态接口（供 Spars 并行化使用）和有状态 API 兼容层（供现有应用使用），很好地解决了接口依赖挑战
4. **工业级验证**: 在华为多款旗舰手机（Mate70、MateX5、MateXT）和智能座舱配置上的验证，具有高度的生产可信度

### 潜在问题
1. **"82% CPU 时间"的分解**: 82% 是 CPU 渲染时间占端到端帧渲染时间的比例，但未说明 CPU 时间中 preparation、execution、commit 三个阶段各自的占比。如果 preparation 阶段（dry run）本身耗时较长，可能会抵消并行化的收益
2. **帧率改善倍数与设备配置的关系**: 论文报告了 1.76×-1.91× 的平均帧率改善，但未清晰说明三折手机（MateXT）是否比单折（MateX5）改善更多或更少——从理论上，三折需要渲染更多像素，应该更能从并行化中受益
3. **提交线程的瓶颈风险**: 虽然论文声称"除最后几个渲染任务外，提交线程的执行时间被 worker 线程完全覆盖"，但未提供量化数据证明这一断言。GPU 命令提交本身（特别是 Vulkan 的 pipeline binding）可能引入显著延迟
4. **与帧率同步（VSync）的交互**: Android/iOS/OpenHarmony 均依赖 VSync 来协调帧渲染节奏。Spars 的乱序执行/有序提交是否与 VSync 机制完全兼容？如果提交线程在 VSync 边界附近延迟提交，可能影响帧率稳定性
5. **图形基元预算增加 2.31× 的条件**: 这个 2.31× 是在"相同稳定帧率"条件下测量的，但"稳定帧率"的具体定义（允许的帧率波动范围？）未说明。此外，这一改善是否在不同场景（桌面、应用页面、游戏等）下均匀分布？
