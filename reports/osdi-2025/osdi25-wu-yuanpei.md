# OS Rendering Service Made Parallel with Out-of-Order Execution and In-Order Commit

**作者**：Yuanpei Wu, Dong Du, Chao Xu, Yubin Xia, Yang Yu, Ming Fu, Binyu Zang, Haibo Chen（上海交通大学 IPADS 实验室 / 华为中央软件院 Fields Lab）
**会议**：OSDI 2025
**链接**：https://www.usenix.org/conference/osdi25/presentation/wu-yuanpei
**源文件**：[osdi25-wu-yuanpei.pdf](../../papers/osdi-2025/osdi25-wu-yuanpei.pdf)

## 一、背景

智能设备操作系统（Android、iOS、OpenHarmony）的渲染服务（Rendering Service）是最核心的系统服务之一，负责将所有 GUI 元素转换为屏幕上的每一个像素。全球人均每天屏幕使用时间达 6 小时 40 分钟，渲染相关任务在商用智能手机中通常占据 65%–95% 的 CPU 和 GPU 总运行时间。

近年来，折叠屏手机（双折、三折）和一芯多屏（智能座舱）的兴起，使得屏幕面积大幅增加。例如华为 Mate X5（双折）和 Mate XT（三折）相比单屏 Mate 70 需要多渲染 70% 和 117% 的像素。然而，当前主流渲染服务仍采用顺序执行模型，无法充分利用现代 SoC 的多核能力。

---

## 二、要解决的问题

1. **多核利用率低**：当前渲染服务的渲染线程垄断单个 CPU 核心达 80% 利用率，而 12 核 SoC 中有 9 个核心处于空闲/低利用状态。CPU 时间占端到端帧渲染时间的 82%，是性能瓶颈。

2. **折叠屏/多屏场景帧率不足**：由于渲染服务无法并行化，厂商被迫在像素密度（Samsung 降低 PPI）或帧率（华为折叠屏降至 90Hz）上做出妥协。智能座舱多屏环境只能运行在 45–60Hz。

3. **现有并行化方案粒度过粗**：
   - **帧间并行**（Inter-frame parallelism）：线程数与流水线阶段耦合，不可扩展，且存在阶段负载不均衡问题。
   - **多窗口并行**（Multi-window parallelism）：依赖窗口抽象，负载高度不均（焦点窗口占大部分工作量），且额外消耗内存。

4. **三重依赖阻碍并行化**：
   - **状态依赖**：渲染树中每个节点只存储相对父节点的信息，需要顺序深度优先遍历。
   - **绘制顺序依赖**：重叠的图形原语必须从后到前渲染。
   - **接口依赖**：现有 2D 引擎（Skia 等）采用有状态接口，新命令依赖历史状态。

---

## 三、洞察与设计

**关键洞察**：渲染过程中的大部分工作（76%）本质上是可并行化的——渲染任务的实际执行不影响所需绘制状态的构建。只要在执行前通过一次快速的有序"干跑"（dry run）预先解开状态依赖，并在执行后通过有序提交维护绘制顺序，就可以实现乱序并行执行。这与计算机体系结构中的乱序执行 + 顺序提交（Out-of-Order Execution with In-Order Commit）高度类似。

基于这一洞察，论文提出 **Spars**——一个可扩展的并行 OS 渲染服务，配合底层无状态 2D 绘制引擎 **Spade2D**，采用三阶段渲染流程：

### 阶段 1：顺序准备（In-Order Preparation，主线程）

主线程对渲染树进行一次深度优先遍历，但不执行任何实际渲染逻辑（不调用 2D 引擎生成 GPU 对象）。这次 dry run 完成：
- 将每个节点的相对信息转换为绝对信息（绝对变换矩阵、裁剪区域等），构造**自包含渲染任务**（Self-Contained Tasks）。
- 记录任务之间的**重叠关系**（Overlapping Relations），使用 AABB（轴对齐包围盒）高效判断图形原语是否重叠。
- 执行传统的**命令批处理**优化（Command Batching），将共享同一 GPU Pipeline 的绘制命令合并。

### 阶段 2：乱序执行（Out-of-Order Execution，Worker 线程）

自包含任务通过 SPMC 任务池分发到可配置数量的 Worker 线程。每个任务封装了完整的绝对绘制状态，无需依赖其他任务，可在任意核心上以任意顺序并行执行。Worker 线程调用 Spade2D 将 2D 图形原语转换为 GPU 对象（mesh、纹理、pipeline 等），结果放入 MPSC 资源池。

### 阶段 3：顺序提交（In-Order Commit，Commit 线程）

Commit 线程从 MPSC 池中获取已完成的任务，根据主线程准备的重叠关系检查是否可以安全提交到 GPU 命令缓冲区。如果当前任务是链表头部（所有前序任务已提交），直接提交；如果不是头部，则检查 AABB——若与未完成的前序任务无重叠，也可安全提交。AABB 检查有预设最大次数（3–5 次），避免重型任务阻塞后续提交。

### 有状态/无状态接口解耦

Spars 将接口分为两层：上层提供与传统 2D 引擎兼容的**有状态 API**（Canvas::translate、Canvas::drawRect 等），保持对第三方应用（Flutter、游戏、Web 应用）的兼容性；下层 Spade2D 采用**无状态 API**，每个任务以自包含结构体形式传入，输出 GPU 对象。

## 四、实现细节

- **语言与 GPU 后端**：C++ 实现，使用 Vulkan GPU API。
- **部署方式**：作为自定义渲染服务直接使用 GPU 资源，绕过 Android/OpenHarmony 原生渲染服务进行性能评估。
- **GPU 资源管理**：Spade2D 使用线程安全的资源管理器，采用 size-class 池、哈希表、与帧缓冲轮转绑定的循环队列。耗时操作（顶点/索引缓冲区填充、图像解码、Pipeline 创建）可无锁并行执行；资源读取使用 `std::shared_mutex`。
- **防止资源重复创建**：当两个并行任务同时引用同一未准备好的 GPU 资源时，第一个任务原子标记为 "preparing"，第二个任务阻塞等待，避免不必要的重复创建。
- **绝对信息存储开销**：渲染树中约 25% 的节点含绘制命令（如 Mate XT Desktop 场景中 800 个节点中约 200 个），每个绝对信息最多 10KB，额外内存 < 2MB。
- **Worker 线程数**：标准配置为 5 个 Worker 线程（6 个中等核心的 SoC 上预留 1 个给 Commit 线程），运行时可动态调整。
- **Spade2D 渲染算法**：使用 CPU 曲面细分（tessellation）将 2D 原语三角化为 mesh，结合 SDF（Signed Distance Field）和 StC（Stencil then Cover）算法进行抗锯齿。文字（glyph）仍由 CPU 通过 FreeType 栅格化到 atlas，再由 GPU 映射到指定位置。

## 五、实验结果

**测试平台**：华为 Mate 70（单屏）、Mate X5（双折）、Mate XT（三折），以及基于麒麟 9010 芯片的多屏配置。CPU 架构：4 小核 + 6 中核 + 2 大核。

**测试场景**：42 个代表性智能手机使用场景（桌面、聊天、购物、视频、生活服务等）。

**基线**：Commercial（OpenHarmony 5.0 商用渲染服务）、Sequential（Spars 的顺序版本，公平对照）。

| 指标 | 结果 |
|------|------|
| 可并行化比例 | 76%（乱序执行 + 顺序提交合计） |
| Amdahl 理论上限 | 3 Worker: 2.14×，5 Worker: 2.65× |
| 实际帧率提升（vs Sequential） | Spars-3: 1.38×，Spars-5: 1.76×（单屏/双折/三折平均） |
| 多屏帧率提升 | Spars-5 平均 1.91×，6 屏桌面最高 2.16× |
| 120Hz 达标率 | Spars-5: 42/42 场景全部达标；Sequential: 仅 15/42 |
| 最高帧率提升 | 多窗口/画中画场景最高 2.07× |
| 小核 + 低频配置 | Spars-3 帧率提升 1.65× |
| 功耗降低 | Mate XT 整机功耗降低 3.0%（相同帧率下） |
| 图形原语预算提升 | 相同时间预算下可渲染 2.31× 图形原语（Spars-5） |
| 最重负载核心利用率 | Sequential: 80% → Spars-5: 45% |
| 额外内存开销 | < 50MB（5 Worker 线程） |
| 任务封装/调度额外 CPU 开销 | < 2% |

## 六、批判性分析

1. **评估方法的局限性**：Spars 并非集成到 OpenHarmony 渲染服务中的增量修改，而是从 OpenHarmony 导出渲染树后在独立环境中重建渲染。这意味着实验绕过了真实系统中的进程间通信、内存压力、调度竞争等因素，实际部署效果可能不如实验数据。

2. **功能完备性存疑**：论文承认 "Spars still lacks some features compared with vanilla rendering services"，但未详细说明缺失了哪些功能。如果缺失的功能恰好是性能敏感的（如复杂动画、阴影、模糊等视觉效果），那么补全后的性能可能显著下降。

3. **部署代价被轻描淡写**：论文估计需要修改渲染服务（~200K LoC）和 2D 引擎（~400K LoC）超过三分之一的代码，这是一个巨大的工程量，但论文仅在 §6.7 末尾一句话带过，未讨论渐进式迁移策略。

4. **Sequential 基线的公平性**：Sequential 是 Spars 的顺序版本，而非 OpenHarmony 原生渲染服务。虽然论文也报告了 Commercial 数据，但 Mate XT 的 Commercial 数据缺失。两个基线的差异未被充分讨论。

5. **多屏实验使用虚拟屏幕**：一芯多屏实验使用 2K 分辨率虚拟屏幕而非真实物理屏幕，可能忽略了真实多屏场景中的显示同步、帧缓冲管理等额外开销。

6. **动态场景覆盖不足**：测试场景是从真实应用导出的静态渲染树填充 dummy 数据，未涉及频繁的渲染树更新（如滚动、动画）带来的 dry run 重计算开销。论文声称 dry run 很快，但未量化频繁更新场景下的影响。

7. **Commit 线程瓶颈风险**：论文声称 Commit 线程的等待时间大部分被 Worker 执行时间覆盖，但在任务粒度极小或重叠关系复杂的场景中，Commit 线程可能成为新的瓶颈。论文未提供此类极端场景的分析。

---

## 七、总结

Spars 借鉴计算机体系结构中乱序执行与顺序提交的思想，将 OS 渲染服务解耦为顺序准备、乱序执行、顺序提交三个阶段，通过自包含任务构造和 AABB 重叠关系管理，在不违反状态依赖和绘制顺序的前提下实现了细粒度的多核并行渲染。在华为折叠屏和多屏配置上实现了 1.76×–1.91× 的帧率提升，同时降低 3.0% 功耗或允许 2.31× 的图形原语预算。其核心贡献在于证明了 OS 2D 渲染的大部分工作（76%）可以通过恰当的状态解耦实现并行化，但从实验原型到商用部署仍面临巨大的工程挑战和功能补全工作。
