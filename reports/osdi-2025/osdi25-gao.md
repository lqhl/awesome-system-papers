## 研究背景与动机

容错是分布式内存存储系统的关键需求。这些系统基于 RDMA 网络提供比磁盘快数个数量级的数据访问，但仍需在故障恢复期间重新加载底层存储，此时系统可能遭受严重的性能下降或数据不可用。

复制（Replication）简单但存储开销高；纠删码（Erasure Coding）以较低存储开销提供容错能力，是内存存储的理想选择。

**传统纠删码的核心问题**：Stripe 概念

Stripe 是几乎所有现有纠删码方案的基本组成部分，要求：
- 每个数据块恰好属于一个 stripe
- 每个校验块仅由同一 stripe 内的数据块生成

但当数据存储在快速主内存时，Stripe 概念带来严重问题：

**Intra-object（块内）方法**：
- 必须将对象拆分到 k 个节点，导致高 I/O fanout
- 读取/写入一个对象需要访问 k 或 (k+p) 个节点
- 小对象（实际工作负载中普遍存在）访问多个节点开销极大

**Inter-object（块间）方法**：
- 静态分配：基于 key hash 的策略不考虑实时系统状态，导致存储空间浪费
- 动态分配：需要 MDS（元数据服务），引入额外网络往返和单点故障

## 核心问题

如何设计一个**无 stripe 概念**的纠删码数据放置方案，同时保证：
1. 支持多节点故障恢复
2. 无需 MDS 协调
3. 最小化 I/O fanout
4. 高效的节点修复性能

## 主要贡献

1. **Nos：无 stripe 的数据放置方案**：基于对称平衡不完全区组设计（SBIBD）决定主节点到备份节点的亲和关系
2. **Nostor：基于 Nos 构建的分布式内存键值存储**：使用 Rust 实现，代码开源
3. **理论保证**：证明 SBIBD 模型可保证任意 p 个节点故障时的成功恢复
4. **恢复开销分析**：恢复丢失块的均摊成本不超过读取 k 个块

## 研究方法与设计

### 核心思想

放弃 stripe 概念：
- **可用性**：每个对象存储在一个主节点，复制到多个备份节点；主节点独立动态决定备份节点，无需 MDS
- **低内存开销**：每个节点将接收到的对象副本编码为 XOR 和（校验块）

### SBIBD（对称平衡不完全区组设计）

**定义**：一个 (v, k, 1)-SBIBD 是一个 v×v 的 0/1 矩阵 A，每行每列恰好有 k 个 1；对于任意两行 r1, r2，恰有 λ=1 列使得 A[r1,c] = A[r2,c] = 1

**关键性质**：v = k² - k + 1

**与 Nos 的对应关系**：
- v：集群节点数
- k：一次编码 k 个对象
- SBIBD 的 Affinity Matrix A：A[i,j]=1 当且仅当节点 i 可以将主对象复制到节点 j

**性质**：如果两个对象的主节点不同，则它们**不会**被复制到相同的两个备份节点 → 这正是多节点故障可恢复的数学保证

### Nos 编码设计

两个参数 (k, p)：
- **k**：一次编码进一个校验块的对象数（k > p）
- **p**：容错阈值，容忍 p 个节点故障

**两步擦除编码策略**：
1. 主节点将对象复制到其 replication target set 中的 k 个节点（选择 p+1 个中的 k 个）
2. 当每个节点收到来自 k 个其他节点的副本后，计算 XOR 和作为校验块

**恢复机制**：
- 正常情况下直接恢复：读取 k-1 个对象 + 1 个校验块 → XOR 得到目标对象
- 多节点故障时需要递归恢复（当失败节点数 ≥ (p+3)/2 时触发）
- SBIBD 保证任何失败对象都存在直接可恢复的校验块

### Nostor 系统设计

基于 Pasha 架构：
- 数据初始分区到各主机 DRAM
- 使用 CXL 内存或 RDMA RPC 通信
- **Cross-host Active Tuples（CAT）**：跨主机并发访问的元组集合，维护在共享 CXL 内存中
- 版本化方法确保普通 I/O、降级 I/O 和节点修复的数据一致性

## 关键实现细节

- Nostor 使用 Rust 实现
- 数据放置支持灵活的运行时约束适应
- 对 RDMA 网络（ConnectX-5）进行优化
- 开源代码：https://github.com/IcicleF/Nos（master 分支）

## 实验结果与分析

### Twitter Twemcache 真实轨迹

在 (k,p) = (4,2) 配置下：
- **吞吐量**：Nostor 比 Cocytus/PQ 高 **1.61×-2.60×**
- **中等延迟**：Nostor 与 Cocytus/PQ 相近
- **P99 延迟**：大多数场景优于 Split（除 Repl 外）

### 运行时数据放置约束

模拟两个节点临时慢速场景（1ms 额外延迟）：
- Nostor 可以避免向慢节点复制，P99 延迟仅轻微上升
- Cocytus 慢节点 P99 延迟上升 48.2×
- Repl 吞吐量下降 25.0%，P99 延迟上升 47.7×

### 节点修复时间

- Nostor 和 Repl 修复速度最快
- Split 比 Nostor 慢 16.4%
- Cocytus/PQ 比 Nostor 慢 88.2%

### 降级读取延迟

- Nostor 的 (k,p)=(4,2) 配置：比 Split 高 16.5%，比 Cocytus 快 11.0%
- (k,p)=(6,3) 最坏情况：比 Cocytus 高 35.0%，比 Split 高 62.4%

### 内存消耗

- 比 Repl 低 18.7%-57.4%
- 比 Cocytus 在小对象时高，大对象时相近

## 潜在问题与局限性

1. **降级读取性能**：最坏情况下（p=3）降级读取延迟比传统纠删码高 35%-62.4%，但论文认为"罕见情况下可接受"
2. **仅支持 XOR 编码**：不能利用更复杂的编码（如 Reed-Solomon 矩阵乘法），限制了对部分磁盘故障的恢复能力
3. **SBIBD 参数约束**：v = k² - k + 1 意味着节点数必须符合特定形式（虽然论文指出对大多数常用 k 值都存在有效构造）
4. **长尾延迟**：Nostor 不专门优化尾延迟，部分场景 P99 比 Repl 高 27%-40%
5. **对慢存储无效**：Nos 主要针对快速主内存设计，在慢速存储上效果有限

## 未来工作方向

1. 支持更复杂的编码方法
2. 进一步优化降级读取性能
3. 自适应参数选择算法

## 个人评注

**优点**：
- 从根本上挑战了"stripe 是纠删码的必要组成部分"这一传统假设，非常有洞察力
- SBIBD 的数学保证严格且优雅，理论和实践紧密结合
- Nostor 相比现有系统展现出显著的性能提升，特别是吞吐量和写入延迟
- Rust 实现 + 开源，有助于社区复现和扩展

**潜在争议**：
- "无 stripe"方案中降级读取性能的最坏情况分析值得进一步关注。论文认为递归降级读取"罕见"，但在高故障率场景下可能成为瓶颈
- 实验中与 Cocytus+、Repl+ 的比较表明：现有系统经过适当优化后也能获得不错的性能，Nostor 的优势可能部分来自 baseline 实现未充分优化
- 对"SBIBD 不需要 MDS"的声称值得注意：虽然数据放置无需 MDS，但系统仍需知道 SBIBD 矩阵配置，这在实践中如何分发和管理？
- 与 Repl 的对比显示，Nostor 在某些场景（如 Cluster-31 的 GET 性能）仅"略优于"复制方案，考虑到纠删码的复杂性，需要权衡是否值得

总体而言，Nos/Nostor 是一项极具创新性的工作，将组合数学理论应用于存储系统设计，思路清晰、实现扎实。
