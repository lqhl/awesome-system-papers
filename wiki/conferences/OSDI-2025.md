# OSDI 2025

> 53 篇论文覆盖 LLM 推理/训练、GPU kernel 与 profiling、存储/文件系统、分布式系统与数据库、网络、内存/虚拟化、安全沙箱、形式验证与 silent-failure 可靠性八条主线，验证与可靠性占比最高（15+ 篇），LLM 系统明显向「推理极值 + 训练可靠性」两端分化，形式化方法、CXL 新硬件、量子系统与 XPU 抽象形成新增长点。

## 概览

**形式验证与 silent-failure 可靠性构成本届最密集的议题**。从 [[Paralegal-OSDI25|Paralegal]]（静态隐私分析）到 [[Basilisk-OSDI25|Basilisk]]（自动推导 Multi-Paxos invariant），再到 [[PoWER-OSDI25|PoWER]]（crash consistency 工具无关验证）、[[DeCl-OSDI25|DeCl]]（确定性机器码）、[[KRR-OSDI25|KRR]]（kernel record-replay），形式方法正从「专家工具」向「生产线标配」迁移。另一条平行线是运行时 silent failure 检测：[[TrainCheck-OSDI25|TrainCheck]] 给 DL 训练做不变量检查、[[T2C-OSDI25|T2C]] 把单测泛化为生产 checker、[[SMon-OSDI25|SMon]] 用 what-if 分析大模型训练 straggler——共同信号是「跑通 ≠ 跑对」已成为系统研究的一等问题。

**LLM 系统从「吞吐与延迟优化」扩展到「极值硬件 + 生产可靠性」**。推理端 [[WaferLLM-OSDI25|WaferLLM]] 首次把 LLM 推到 wafer-scale，[[NanoFlow-OSDI25|NanoFlow]] 把 LLaMA-2-70B 吞吐推到 TensorRT-LLM 的 1.91×、理论上限 68.5%，[[BlitzScale-OSDI25|BlitzScale]] 用 O(1) host caching 做 live autoscaling。训练端出现 [[SMon-OSDI25|SMon]]（3079 个生产 job 的 straggler 诊断）、[[WLB-LLM-OSDI25|WLB-LLM]]（4D 并行负载均衡）、[[ZEN-OSDI25|ZEN]]（稀疏 AllReduce）。量化侧 [[DecDEC-OSDI25|DecDEC]] 用 CPU 残差补偿让 3-bit Llama-3 perplexity 降 1 分。LLM 工作整体结构更「成熟」：不再堆单点加速，而是面对极值硬件（wafer）、生产规模故障（straggler）、底层数值（量化残差）。

**CXL / 异构内存 / XPU 抽象开始改写 OS 与数据库层**。[[Tigon-OSDI25|Tigon]] 首个利用 CXL 原子操作消灭 2PC 的内存 DB，比 RDMA 方案快 18.5×；[[SoarAlto-OSDI25|SoarAlto]] 用 AOL = Latency/MLP 代替 hotness 做 tiered memory；[[FineMem-OSDI25|FineMem]] 用 RDMA MW + bitmap tree 把 disaggregated memory 分配粒度降到 4KB；[[EMT-OSDI25|EMT]] 给 Linux 加架构中立 MMU 框架支持 ECPT/FPT；[[XSched-OSDI25|XSched]] 定义跨 10 种 XPU 的抢占式调度抽象。硬件多样性（CXL 池、RDMA、DPU、加速器）倒逼 OS/DB 重新设计抽象层。

**GPU kernel 工具链进入「compiler-centric + 可编程 probe」新阶段**。[[KPerfIR-OSDI25|KPerfIR]] 把 profiling 改造成 MLIR/Triton compiler pass，[[Neutrino-OSDI25|Neutrino]] 给 GPU 带来 eBPF 级的 PTX/GCNAsm 可编程探针，[[PipeThreader-OSDI25|PipeThreader]] 软件定义 GPU 异构单元流水，[[Mirage-OSDI25|Mirage]] 用 µGraph 统一 kernel/block/thread 三层 superoptimize。和 MLSys 2026 的 [[AccelOpt]]/[[PIKE]] 式 LLM-agent 生成 kernel 形成互补：OSDI 侧更重「compiler 基础设施」，MLSys 侧更重「agent 生成体验」。

**与往届对比**：相比 OSDI 2024，本届 [[PagedAttention]] 或 vLLM 内部优化类论文几乎消失，取而代之的是面向新硬件（wafer / CXL / XPU / DPU）的极值工作和面向生产可靠性的 silent-failure 检测。LLM 与验证占半壁江山、存储/网络保留 10 篇左右的稳健阵地、量子系统（[[QOS-OSDI25|QOS]]/[[HyperQ-OSDI25|HyperQ]]）首次进入主会两篇、AI 编译器与 GPU 工具链呈集群化——这届 OSDI 的气质是「研究对象更硬核，研究方法更严肃」。

## 研究趋势

**1. 形式验证从「专家工具」转为「研究者默认选项」**。[[Basilisk-OSDI25|Basilisk]] 把 Multi-Paxos / PCC 16 个分布式协议的 inductive invariant 完全自动化（用户手写 0 条）；[[PoWER-OSDI25|PoWER]] 用标准 Hoare logic 给 PM KV 存储做 crash consistency 验证；[[DeCl-OSDI25|DeCl]] 把 SFI 扩到确定性机器码执行；[[Paralegal-OSDI25|Paralegal]] 对 Rust 实际应用做静态隐私审查。共同信号是「verification 的入门门槛在下降」——可以在研究项目里把验证当作工具链的一部分而非独立研究方向。

**2. Silent failure 成为与 performance 并列的 first-class 问题**。[[TrainCheck-OSDI25|TrainCheck]] 在 18 个真实 DL silent error 上验证了自动不变量推断的可行性；[[T2C-OSDI25|T2C]] 把单元测试泛化为生产 checker；[[SMon-OSDI25|SMon]] 证明 42.5% LLM 训练 job 被 stragglers 拖慢 ≥10%——三篇都说明「跑完没崩」不够了，系统社区开始系统化处理「看似成功其实错了」。这类工作对研究生态的改造比 perf 工作更深：意味着实验 baseline 的「成功」本身需要被重新审视。

**3. LLM 系统研究的极化：要么极值、要么生产**。极值端有 [[WaferLLM-OSDI25|WaferLLM]]（wafer-scale）、[[NanoFlow-OSDI25|NanoFlow]]（吞吐逼近理论上限）、[[DecDEC-OSDI25|DecDEC]]（3-bit 量化）；生产端有 [[SMon-OSDI25|SMon]]（straggler 诊断）、[[BlitzScale-OSDI25|BlitzScale]]（live autoscaling）、[[WLB-LLM-OSDI25|WLB-LLM]]（4D 并行负载均衡）、[[ZEN-OSDI25|ZEN]]（稀疏同步）。中间地带的「serving 单点加速」（vLLM/SGLang 内部改法）在 OSDI 本届几乎消失——与 MLSys 2026 仍有大量此类论文形成鲜明对比。推测原因：OSDI 审稿口味更重「系统贡献的不可替代性」，而 serving 单点优化经过 2023-2024 的密集产出后已经饱和。

**4. CXL / RDMA / DPU 等异构硬件开始重写抽象层**。[[Tigon-OSDI25|Tigon]] 利用 CXL 原子操作消灭分布式事务的 2PC（比 RDMA 方案快 18.5×）；[[SoarAlto-OSDI25|SoarAlto]] 引入 AOL = Latency/MLP 指标取代 hotness 做 CXL tiering；[[FineMem-OSDI25|FineMem]] 把 RDMA disaggregated memory 分配粒度降到 4KB；[[Scalio-OSDI25|Scalio]] 用 DPU NVMe-oF offload 重写 JBOF 架构；[[EMT-OSDI25|EMT]] 给 Linux 做架构中立 MMU 框架。这批工作共同信号：当数据中心硬件从「CPU + 本地内存 + TCP」的 20 年范式迁移到「池化内存 + 智能网卡 + 加速器」时，OS/DB 的抽象层第一次大范围重写，而不是打补丁。

**5. GPU Kernel 工具链进入 compiler-centric 时代**。[[KPerfIR-OSDI25|KPerfIR]] 把 profiling 做成 MLIR/Triton 编译 pass，[[Neutrino-OSDI25|Neutrino]] 提供 PTX/GCNAsm 级可编程 probe，[[PipeThreader-OSDI25|PipeThreader]] 把 GPU 流水抽象成软件调度，[[Mirage-OSDI25|Mirage]] 用 µGraph 三层统一 superoptimize，[[QiMeng-Xpiler-OSDI25|QiMeng-Xpiler]] 跨 ISA 翻译张量程序。和 MLSys 2026 上的 LLM-agent 式 kernel 生成（[[AccelOpt]]/[[PIKE]]）互补——OSDI 聚焦「可编程的 kernel 基础设施」，给下游 agent 和自动调优提供了工具链底座。

**6. 量子系统 / XPU 首次进入主会建制**。[[QOS-OSDI25|QOS]]、[[HyperQ-OSDI25|HyperQ]] 两篇量子系统论文（分别做量子 OS 抽象与量子云 VM）在 OSDI 史上相当罕见；[[XSched-OSDI25|XSched]] 把抢占式调度从 GPU 推广到 10 种 XPU；[[bpftime-OSDI25|bpftime]] 则给用户态扩展提供了新 sandbox 框架。这些「新硬件抽象」型工作的集中出现，意味着 OSDI 社区开始系统性接收 CPU 之外的计算设备。

## 共同观察

**1. 「跑通 ≠ 跑对」与 performance 并列为一等问题，且检测手段从高层 metric 下沉到不变量 / checker / replay**。15+ 篇验证与可靠性论文共享观察：silent failure 在生产中普遍且昂贵。[[TrainCheck-OSDI25|TrainCheck]] 在 20 个真实 DL silent error 中 18 个单 iteration 检出；[[T2C-OSDI25|T2C]] 把单测泛化为带 precondition 的 runtime checker；[[SMon-OSDI25|SMon]] 在 3079 个生产 job 上量化 straggler 浪费 10.4% GPU-hour；[[Basilisk-OSDI25|Basilisk]] / [[PoWER-OSDI25|PoWER]] / [[DeCl-OSDI25|DeCl]] 把形式验证门槛降到「研究项目默认工具链」。适用边界：[[TrainCheck-OSDI25|TrainCheck]] 不覆盖 torch.compile 路径、纯数值 hyperparameter 错误、C++/CUDA 算子内部缺陷；[[T2C-OSDI25|T2C]] 依赖已有单测 oracle。

**2. 数据中心硬件范式从「CPU + 本地 DRAM + TCP」迁向「池化内存 + 智能网卡 + 加速器」，OS/DB 抽象层在大范围重写而非打补丁**。[[Tigon-OSDI25|Tigon]] 用 CXL 原子操作消灭跨主机 2PC；[[SoarAlto-OSDI25|SoarAlto]] / [[FineMem-OSDI25|FineMem]] 分别用 AOL 指标与 4KB 粒度 RDMA 分配改写 tiering / disaggregated memory；[[Scalio-OSDI25|Scalio]] 用 DPU NVMe-oF offload 重写 JBOF；[[EMT-OSDI25|EMT]] 给 Linux 加架构中立 MMU 框架；[[XSched-OSDI25|XSched]] 统一 10 种 XPU 抢占抽象。观察在 CXL pod（~8–16 机）、RDMA/JBOF、DPU 可编程数据面已部署的环境最稳；纯 TCP + 本地盘云 VM 传统栈上收益需重测。

**3. LLM 系统研究极化：一端追求硬件/算法极值，一端用生产 trace 诊断可靠性，中间「引擎内部单点加速」几乎消失**。极值端 [[WaferLLM-OSDI25|WaferLLM]]（wafer-scale）、[[NanoFlow-OSDI25|NanoFlow]]（吞吐达理论上限 68.5%）、[[DecDEC-OSDI25|DecDEC]]（3-bit + CPU 残差）；生产端 [[SMon-OSDI25|SMon]]、[[BlitzScale-OSDI25|BlitzScale]]、[[WLB-LLM-OSDI25|WLB-LLM]]、[[ZEN-OSDI25|ZEN]] 分别处理 straggler、live autoscaling、4D 并行不平衡、稀疏 AllReduce。与 MLSys 2026 大量 vLLM/SGLang 改动形成对比——OSDI 更青睐「不可替代系统贡献」或「万卡 / wafer / 生产 trace 级证据」。

**4. GPU kernel 工具链进入 compiler-centric + 可编程 probe 阶段，与下游 LLM-agent 自动优化形成上下游分工**。[[KPerfIR-OSDI25|KPerfIR]] 把 profiling 做成 MLIR/Triton pass；[[Neutrino-OSDI25|Neutrino]] 提供 PTX/GCNAsm 级 probe；[[PipeThreader-OSDI25|PipeThreader]] 软件定义异构单元流水；[[Mirage-OSDI25|Mirage]] µGraph 三层 superoptimize；[[QiMeng-Xpiler-OSDI25|QiMeng-Xpiler]] 跨 ISA 翻译；[[SysGPT-OSDI25|SysGPT]] 用 477 篇论文验证优化方法论覆盖性。共识是「可编程 IR + 测量闭环」比单次手写 kernel 更可扩展；但 [[Tintin-OSDI25|Tintin]] 提醒 perf counter 多路复用本身有 uncertainty，probe 结果需反馈校正。

**5. 存储与网络论文继续坚守「把瓶颈钉死在可测量物理约束上」传统，且与 AI workload 交叉加深**。[[Okapi-OSDI25|Okapi]] / [[Nostor-OSDI25|Nostor]] 解耦 EC stripe 语义；[[PipeANN-OSDI25|PipeANN]] 打破 ANN best-first 顺序做 compute-I/O 重叠；[[FuseLink-OSDI25|FuseLink]] 用 NVLink relay 聚合 NIC 带宽加速 LLM TTFT；[[rxBisect-OSDI25|rxBisect]] 拆 NIC Rx ring 解耦分配与接收。观察在 RDMA/NVMe-oF 已部署、且 workload 可明确区分 compute-bound vs I/O-bound 时最稳；通用云硬盘 + 共享 TCP 场景下倍数需打折。

## 互相冲突的假设

**1. LLM 训练 straggler 主因是 compute 还是 network？** [[SMon-OSDI25|SMon]] 在 ByteDance 专用训练集群（带宽充裕、job 独占 GPU）结论：42.5% job slowdown ≥10% 主要来自 **compute** straggling（PP 尾段、sequence imbalance、GC），与 FALCON 等「网络主导」观察相反。相对地 [[ZEN-OSDI25|ZEN]] / [[WLB-LLM-OSDI25|WLB-LLM]] 仍围绕通信与并行不平衡优化。**仲裁测量**：在同一集群同时采集 per-collective 时间与 per-GPU compute idle，按 job 分类 communication-bound vs compute-bound；多租户拥塞集群上重复 [[SMon-OSDI25|SMon]] trace 实验。

**2. CXL 共享内存能否普遍替代 2PC / RDMA 消息路径？** [[Tigon-OSDI25|Tigon]] 假设 CAT（跨主机活跃 tuple 集）很小（TPC-C ~7MB），可用 CXL HWcc 原子同步消灭 2PC，比 RDMA DB 快 18.5×。相对地 [[Mako-OSDI25|Mako]] 在 geo-replication 场景仍用 vector clock + epoch 限制级联回滚，解耦 2PC 与复制；[[FineMem-OSDI25|FineMem]] 的 RDMA 细粒度分配假设延迟仍高于本地 DRAM 1–2 数量级。**仲裁测量**：扫描事务 touched tuple 数 / CAT 大小与 TPS 的关系曲线，在 CAT 膨胀（大范围扫描、热点跨分区）时对比 Tigon vs [[Mako-OSDI25|Mako]] / 传统 2PC 交叉点。

**3. LLM 推理应押注极值单机还是弹性多卡池？** [[WaferLLM-OSDI25|WaferLLM]] 假设 mesh 远程访问延迟可达本地 1000×，必须把通信约束在 PLMR 合规模式，单 wafer 比多卡 A100 快 10–20×。相对地 [[BlitzScale-OSDI25|BlitzScale]] 假设 MAAS 场景可用 O(1) host 缓存 + RDMA 多播做层粒度 live 扩容，尾延迟降 94%、节省 49% GPU。**仲裁测量**：在相同模型与 SLA 下比较 wafer 固定容量 vs 弹性 GPU 池的总成本与 p99 TTFT，并计入 [[BlitzScale-OSDI25|BlitzScale]] 冷启动 / 权重加载是否与 [[AFaaS-OSDI25|AFaaS]] 的 ms 级冷启动可协同。

**4. 内存 tiering 应追 hotness 还是 AOL = Latency/MLP？** [[SoarAlto-OSDI25|SoarAlto]] 在 56 workload 上证明 LLC-miss 计数与 hotness 策略常伤害性能，AOL 预测 Pearson 0.951，Soar 静态分配 + Alto 抑制无效迁移最高 12.4×。传统 TPP/Nomad/NBT/Colloid 假设访问频率即可指导 promotion。**仲裁测量**：在 CXL tiering 真机（非仅 NUMA 代理）上对比同一 LLM inference KV working set 的 tier 决策，报告 tail latency 而非仅平均 throughput；带宽争用时应观测 AOL 膨胀（[[SoarAlto-OSDI25|SoarAlto]] 自述失效场景）。

**5. 吞吐接近理论上限时，生产集群仍有多少「隐形浪费」？** [[NanoFlow-OSDI25|NanoFlow]] 报告 LLaMA-2-70B 吞吐达 TensorRT-LLM 1.91×、理论上限 68.5%，假设 intra-device pipeline 挖尽算子重叠。相对地 [[SMon-OSDI25|SMon]] 显示即使无网络拥塞，10.4% GPU-hour 因 straggler 浪费，且修复最慢 3% worker 对 98.3% job 几乎无效。**仲裁测量**：把 [[NanoFlow-OSDI25|NanoFlow]] 级单卡效率与 [[SMon-OSDI25|SMon]] 级 job 级 waste 放在同一 roofline 框架——区分「kernel 效率」与「调度 / 并行 / 数据 skew 效率」。

**6. 形式验证 / runtime checker 开销是否可忽略？** [[TrainCheck-OSDI25|TrainCheck]] / [[T2C-OSDI25|T2C]] 报告开销通常 <2%、中位检测 0.188s；[[PoWER-OSDI25|PoWER]] crash consistency 验证 <1min。相对地 [[TrainCheck-OSDI25|TrainCheck]] 离线推断最坏 ~38h，且与 torch.compile 不兼容；[[Paralegal-OSDI25|Paralegal]] 静态分析仍限特定 Rust 应用形态。**仲裁测量**：在目标系统（是否 JIT/compile）上测 p99 latency 与 CPU 占用；对 LLM serving 需定义「per-token correctness check」是否可行（[[TrainCheck-OSDI25|TrainCheck]] future work 方向）。

**7. GPU 优化应靠 LLM 方法论（SysGPT）还是 compiler 搜索（Mirage / BayesianCodeDiffusion）？** [[SysGPT-OSDI25|SysGPT]] 用 477 篇论文验证 3 原则 + 8 方法论对系统优化的覆盖性，并 fine-tune 建议模型；[[Mirage-OSDI25|Mirage]] / [[BayesianCodeDiffusion-OSDI25|BayesianCodeDiffusion]] 假设 subgraph 结构重复、schedule 参数邻近，适合搜索 + 等价验证。二者假设「人类可读启发式」与「自动 superoptimize」可分工而非替代。**仲裁测量**：同一 kernel suite 上比较 SysGPT 建议 → 人工实现 vs Mirage 自动搜索的 hit rate、验证时间、跨 GPU 迁移成功率。

## 值得关注的方向

### 1. Silent failure 检测的通用化与跨层移植

**为什么小团队能做**：[[TrainCheck-OSDI25|TrainCheck]] 全部用开源框架（PyTorch + 公开 bug repo）和单机实验，核心工作是「不变量推断算法 + bug repro」；[[T2C-OSDI25|T2C]] 只需已有单测和目标系统源码；[[SMon-OSDI25|SMon]] 用生产 trace 离线分析，不需要现场运行训练。

**指向空白的论文**：[[TrainCheck-OSDI25|TrainCheck]] 只覆盖训练框架内部；[[T2C-OSDI25|T2C]] 只用现成单测而非派生新 oracle；[[SMon-OSDI25|SMon]] 仅做 what-if diagnosis 而未闭环修复。

**Open problems**：能否把 TrainCheck 的不变量推断扩到 inference（检测 serving 的 numerical silent corruption）？能否把 T2C 与 property-based testing 结合，自动生成 precondition？能否在 LLM 推理链路里做 per-token silent error 检测（如 KV cache corruption、attention NaN）而不是只在训练 loss 级别？

### 2. Provenance-style invariant 推断扩展到新协议

**为什么小团队能做**：[[Basilisk-OSDI25|Basilisk]] 把 16 个协议的 invariant 完全自动推导，说明工具本身已经足够成熟，1-2 人应用到新协议上主要是建模工作。作者开源了工具。

**指向空白的论文**：[[Basilisk-OSDI25|Basilisk]] 的 atom sharding 局限于「单机可枚举的小节点数」；部分 liveness invariant 不在 provenance 模型内；复杂协议（CRDT、distributed SQL 事务）未验证。

**Open problems**：能否把 Basilisk 扩到 2PC / 3PC + geo-replication 混合（如 [[Mako-OSDI25|Mako]] 的 vector clock 组合）？能否给 [[Tigon-OSDI25|Tigon]] 的 CXL 原子操作序列做 invariant 验证？Provenance invariant 能否用于 LLM serving 的 request-level 正确性（如 [[Skybridge-OSDI25|Skybridge]] 的 bounded staleness 保证）？

### 3. CXL tiering / disaggregated memory 的新成本模型

**为什么小团队能做**：[[SoarAlto-OSDI25|SoarAlto]] 的 AOL 指标只需 perf counter 和 Linux 改动；AMD EPYC + 商用 CXL PCIe 卡在云平台可租；实验基线（TPP/Nomad）都开源。

**指向空白的论文**：[[SoarAlto-OSDI25|SoarAlto]] 只覆盖 on-demand page promotion；[[FineMem-OSDI25|FineMem]] 只解决分配粒度不触及调度；[[Tigon-OSDI25|Tigon]] 只用 CXL 做跨主机事务同步。

**Open problems**：能否用 AOL 指标指导 LLM serving 的 KV cache 分层（local HBM / CXL DRAM / host DRAM / SSD）？CXL 原子操作能否替代 RDMA atomics 做分布式锁、优化序列化 LLM training 的梯度同步？CXL pod 内的 fault domain（一个 CXL switch 宕了就地炸整张池）能否用 [[Basilisk-OSDI25|Basilisk]] 风格自动验证？

### 4. GPU kernel profiling 工具链的「MLIR 化」

**为什么小团队能做**：[[KPerfIR-OSDI25|KPerfIR]]、[[Neutrino-OSDI25|Neutrino]]、[[Tintin-OSDI25|Tintin]] 都基于开源 MLIR/Triton/eBPF 生态，单机 GPU 足够，重点在工具设计而非大规模 workload。

**指向空白的论文**：[[KPerfIR-OSDI25|KPerfIR]] 聚焦单 kernel 区域；[[Neutrino-OSDI25|Neutrino]] 聚焦指令级 probe；[[Tintin-OSDI25|Tintin]] 聚焦多路复用误差；三者没有统一 IR。

**Open problems**：MLIR 里能否定义一个「profile-annotated tensor IR」让 Mirage/TVM 生成的 kernel 在编译期就自带 probe？Neutrino 的 probe 能否做 GPU/CPU 跨设备一致抽象以支持 RDMA 通信 profile？KPerfIR + LLM agent 能否把 profile 结果闭环反馈给 [[AccelOpt]] 式自动优化？

### 5. 形式化 + serverless / container 冷启动

**为什么小团队能做**：[[MettEagle-OSDI25|MettEagle]] 证明微内核上的容器 TCB 能小 31×；[[AFaaS-OSDI25|AFaaS]] 的树状 seed 完全软件侧改造；二者都不需要大规模集群。

**指向空白的论文**：[[MettEagle-OSDI25|MettEagle]] 只覆盖容器引擎；[[AFaaS-OSDI25|AFaaS]] 只优化冷启动延迟不做安全；[[bpftime-OSDI25|bpftime]] 的 sandbox 没有用于 serverless 场景。

**Open problems**：能否在微内核 serverless 上用 [[bpftime-OSDI25|bpftime]] 式 eBPF sandbox 替代完整容器？能否对 AFaaS 的冷启动路径做形式验证（seed tree 的 isolation 正确性）？WASM / Rust + [[Omniglot-OSDI25|Omniglot]] 式安全 FFI 能否成为比容器更轻的 serverless runtime？

### 6. XPU 抽象 / 量子系统的接口层扩展

**为什么小团队能做**：[[XSched-OSDI25|XSched]] 的 XQueue 抽象建立在现有硬件抢占能力之上，适合 1-2 人做特定 XPU 的 port；[[QOS-OSDI25|QOS]] 的 Qernel 抽象开源在 IBM Eagle 上可验证。

**指向空白的论文**：[[XSched-OSDI25|XSched]] 只处理 preemption，未处理 DMA/memory；[[QOS-OSDI25|QOS]] 只到 scheduler 层未到应用层抽象；[[HyperQ-OSDI25|HyperQ]] 只覆盖 IBM 架构。

**Open problems**：能否把 XSched 扩到 TPU / MTIA / Trainium 这些无 preempt 原生支持的 XPU？Qernel 能否跨多厂商 QPU（Google Willow / Quantinuum / Rigetti）提供统一抽象？能否把 [[Basilisk-OSDI25|Basilisk]] 式 invariant 推断用于量子纠错码的 fault-tolerance 验证？
