# ATC 2025

> 100 篇论文横跨 LLM 推理/训练、GPU 调度与 Kernel、网络（数据中心 + 流媒体 + 卫星）、OS 虚拟化、存储、安全可靠性、编译器与工具八条主线；网络相关共 21 篇占比最高，LLM 系统紧随其后 22 篇，国内云厂商生产系统论文密度爆发（阿里 / 腾讯 / 字节 / 华为云 / TikTok / 淘宝多家），异构硬件（CXL / SmartNIC-DPU / 可编程交换机 / PIM / NPU / Intel DSA）横贯各条主线。

## 概览

**LLM 系统占 22 篇，「从单 GPU benchmark 转向多租户生产托管」是本届最强信号**。推理侧 [[KVCacheInTheWild-ATC25|KVCacheInTheWild]]（阿里首份 to-C/to-B 生产 KVCache trace 刻画，QTTFT 降 28-41%）、[[DeepServe-ATC25|DeepServe]]（华为 Ascend NPU serverless 平台，秒级扩 64 实例）、[[Torpor-ATC25|Torpor]]（阿里 GPU pool late binding，4-GPU 节点服务 480 函数）、[[Toppings-ATC25|Toppings]]（CPU+LoRA prefill 掩盖 adapter 冷启动 1.7×）、[[Katz-ATC25|Katz]]（T2I diffusion + ControlNet 服务 7.8×）共同显示业内一线已经把推理框架从「vLLM/SGLang 单 GPU 调优」推向「多模型多租户多硬件托管」。训练侧 [[Optimus-ATC25|Optimus]]（3072 GPU MLLM bubble exploitation）、[[Greyhound-ATC25|Greyhound]]（10K GPU fail-slow 检测）、[[CrossPipe-ATC25|CrossPipe]]（跨 DC PP+DP overlap）、[[UCP-ATC25|UCP]]（Universal Checkpointing 让 1T 模型重配 < 3min）、[[Hermes-ATC25|Hermes]]（Ascend 训练 profiling 落地）、[[Primus-ATC25|Primus]]（字节跳动 DLRM 三层统一训练系统）一齐把「大集群 + 大模型 + 工业落地」做到了主轴位置。

**国内 hyperscaler production paper 密度爆发**。除前述外，[[TGW-ATC25|TGW]]（腾讯云软件网关，单节点 2.9× 吞吐 + 多 Tbps 流量）、[[AnchorNet-ATC25|AnchorNet]]（TikTok 直播架构，rebuffer -60%、参与度 +3.83%）、[[SolFS-ATC25|SolFS]]（移动云备份 sync 时间 -88.8%）、[[MARC-ATC25|MARC]]（淘宝云渲染 freeze rate -71%）、[[FastACS-ATC25|FastACS]]（消息分发 1.8 Tbps p99 亚秒）、[[FlexPipe-ATC25|FlexPipe]]（变长 PP 训练）等多个论文都是带真实 A/B 测和大规模生产部署数字的工作。这种密度在前几届 ATC 罕见，反映出国内 hyperscaler 工程经验首次大规模进入顶会主流叙事。

**异构硬件横贯多条主线，「软件可编程硬件」从 GPU 扩散到 SmartNIC/DPU/PIM/DSA/可编程交换机**。CXL：[[DRack-ATC25|DRack]] 用 CXL 3.0 把 NIC 与内存做 rack-level 解聚共享、[[DSA-2LM-ATC25|DSA-2LM]] 用 Intel DSA bypass DMA 做 tiered memory；SmartNIC/DPU：[[Snary-ATC25|Snary]]（FPGA 检索）、[[Poby-ATC25|Poby]]（BlueField-2 镜像 provisioning）、[[DShuffle-ATC25|DShuffle]]（DPU Spark Shuffle）、[[SwCC-ATC25|SwCC]]（BlueField + RISC-V 软件 CC，3.1µs RTT）、[[Barre-ATC25|Barre]]（BlueField-3 PCC 上 AI 集群 CC，10K GPU 训练吞吐 +9.6%）；可编程交换机：[[Trochilus-ATC25|Trochilus]]（Tofino BRNN 蒸馏部署）、[[Minos-ATC25|Minos]]（流量分析防御）、[[SwitchGNN-ATC25|SwitchGNN]]（P4 在网 GNN 聚合，Reddit epoch -74%）、[[Pallas-ATC25|Pallas]]（ToR µs 调度）；PIM：[[PIMANN-ATC25|PIMANN]] 在 UPMEM 上做 ANNS；NPU：[[DeepServe-ATC25|DeepServe]]、[[Hermes-ATC25|Hermes]]、[[CLONE-ATC25|CLONE]]（28nm 边缘 LLM 加速器）；Intel DSA：[[Para-ksm-ATC25|Para-ksm]]（DSA 加速 ksm 内存去重）、[[DSA-2LM-ATC25|DSA-2LM]]。

**Rust 在 OS 与 kernel-extension 阵营继续工程化**。[[Asterinas-ATC25|Asterinas]] 推出 Rust framekernel OS（driver 全 safe Rust，TCB 仅 14% 代码、性能与 Linux 持平）、[[Rex-ATC25|Rex]] 用 safe Rust 替代 eBPF verifier、[[Converos-ATC25|Converos]] 用 PlusCal 多层规约对 Asterinas 做 model checking 找出 20 个真实 bug（4 人月）。这条线延续了 [[OSDI-2025]] 的「verification 工具化」与 SOSP 2025 的 Rust + 形式方法基调，且 Asterinas/Converos 是同一作者群体的配套交付。

**网络工作显著倒向 AI workload，传统 CC/LB 大幅 AI 化**。[[Barre-ATC25|Barre]]（AI 集群 RoCEv2 PCC）、[[SwCC-ATC25|SwCC]]（软件可编程 RDMA CC）、[[FLB-ATC25|FLB]]（无损 DC LB，PFC PAUSE -96%）、[[Pallas-ATC25|Pallas]]（µs rack 调度）、[[SwitchGNN-ATC25|SwitchGNN]]（在网 GNN）、[[Snary-ATC25|Snary]]（SmartNIC ANN）几乎都打着 AI 标签；与此同时 [[KernelBypassTCP-ATC25|KernelBypassTCP]]（6-stack 横评，Linux 在 bulk 上 1.7× IX，IX 在 small msg 上 5.2× Linux）和 [[SplitConn-ATC25|SplitConn]]（重审 PEP 与 BBR 相关性）给社区拉了一次基础认知 reset。

**与 ATC 2024 对比**：LLM 论文占比从 ~10% 升到 ~22%；网络从纯 RDMA 优化扩展到「AI 集群 CC + DPU CC offload」；OS/虚拟化议题增多（13 篇，含 Rust framekernel、microkernel UEFI、eBPF 用户态 paging、嵌套虚拟化 hyperupcall）；卫星网络与空间计算自成一支（3 篇：[[LEOCraft-ATC25|LEOCraft]]、[[Rhone-ATC25|Rhone]]、[[SpaceExit-ATC25|SpaceExit]]）；可编程交换机从「玩具 demo」变成产线工具（多个 Tofino Tbps line-rate 论文）。整体气质：**工业落地浓度 + LLM 渗透深度**是 ATC 2025 的两条明线。

- [[MemoryTrap-ATC25|MemoryTrap]] — 编译期插不可读 NOP 陷阱 + Intel MPK 防 JIT-ROP，最多泄 657B 即触发，开销 0.74-1.85%
- [[Bin2Wrong-ATC25|Bin2Wrong]] — source/compiler/opt/format 四维统一反编译器 fuzz，binary diversity 提升 10-17×、确认 30 个 bug
- [[CountingAtomicity-ATC25|CountingAtomicity]] — symbolic range analysis + SMT 自动推断 PM 数组与 size 的 counting 原子性，4 系统找 14 bug
- [[FiDe-ATC25|FiDe]] — OS 隔离 + XDP + SDN 双冗余 multicast tree，crash 检测 < 30µs（uKharon-FD 7.2×），Zookeeper 吞吐 2.23×

### 编译器、Shell、其他工具（8 篇）

- [[IRHash-ATC25|IRHash]] — 在 LLVM IR 后做 hash 的编译缓存，比 Ccache/cHash 准 1-2 数量级，C 项目 build -19%
- [[HEC-ATC25|HEC]] — 静态 datapath + 动态 control-flow 重写规则混合的 e-graph MLIR 等价性验证，40 分钟跑 100k+ 行
- [[Koala-ATC25|Koala]] — 126 个真实 shell 程序 + 3 档输入（最大 146GB）+ 自动化基础设施，统一评估 PASH/Shark
- [[FPRev-ATC25|FPRev]] — masked all-one array 黑盒重建 summation tree（O(n²) vs O(4ⁿ) brute），首支持 Tensor Core fused
- [[HypeReca-ATC25|HypeReca]] — 异构 embedding DB 去中心索引 pipeline + 2-fold parallel 复制，DLRM 32 GPU 上 2.16-16.8×
- [[Cosmic-ATC25|Cosmic]] — cell-grouping + speculation 让 SmartScan 在 Lambda 上满足 50ms 时序，3D 打印控制省 2.8-3.5×
- [[Chitu-ATC25|Chitu]] — Fair-Fallback 框架的异步 DAG-BFT，最佳 4 message delays，相比 Tusk 端到端延迟 -82.5%

## 研究趋势

**1. LLM 系统从「单 GPU benchmark」全面进入「多模型多租户多硬件托管」**。同一时段 ATC 出现 [[Weaver-ATC25|Weaver]]（多 LLM 共 GPU attention 卸载）、[[LLMStation-ATC25|LLMStation]]（fine-tuning + inference 共享）、[[Toppings-ATC25|Toppings]]（CPU/GPU 共担 LoRA）、[[Torpor-ATC25|Torpor]]（GPU pool late binding 服务 480 函数）、[[Katz-ATC25|Katz]]（diffusion + multi-adapter）—共同信号是「serving 系统已经是异构资源 + 异构模型 + 异构 adapter 三重多路复用」，单 GPU 单模型论文几乎不再出现。这与 [[OSDI-2025]] LLM 服务议题向「极值/生产」分化、MLSys 2026 仍有大量「单 GPU 单模型」工作形成清晰互补。

**2. 国内云厂商生产系统首次集中进入主流叙事**。[[KVCacheInTheWild-ATC25|阿里 KVCache trace]]、[[Torpor-ATC25|阿里 Torpor]]、[[Primus-ATC25|字节 Primus]]、[[DeepServe-ATC25|华为 DeepServe]]、[[Hermes-ATC25|华为 Hermes]]、[[TGW-ATC25|腾讯 TGW]]、[[AnchorNet-ATC25|TikTok AnchorNet]]、[[SolFS-ATC25|移动云 SolFS]]、[[MARC-ATC25|淘宝 MARC]] 几乎覆盖国内 hyperscaler 主流玩家。这些工作普遍带 A/B 测和大规模生产数字（10K-1M+ 用户级），而不是 lab 级 benchmark。这种密度在前几届 ATC 罕见，反映出系统社区在 2025 年开始把「中国生产规模」当作一等公民。

**3. 异构硬件「软件可编程性」从 GPU 扩散到 SmartNIC/DPU/PIM/DSA/Tofino**。[[SwCC-ATC25|SwCC]] 把 RDMA CC 从 ASIC 搬到 RISC-V 软件、[[Barre-ATC25|Barre]] 在 BlueField-3 上跑 AI CC、[[Snary-ATC25|Snary]]/[[Poby-ATC25|Poby]]/[[DShuffle-ATC25|DShuffle]] 一系列把不同 workload 卸载到 SmartNIC、[[Trochilus-ATC25|Trochilus]]/[[Minos-ATC25|Minos]]/[[SwitchGNN-ATC25|SwitchGNN]]/[[Pallas-ATC25|Pallas]] 把 P4/Tofino 当成可编程加速器、[[PIMANN-ATC25|PIMANN]] 在 UPMEM 上做 ANN、[[Para-ksm-ATC25|Para-ksm]]/[[DSA-2LM-ATC25|DSA-2LM]] 利用 Intel DSA、[[DRack-ATC25|DRack]] 用 CXL 3.0 解聚 NIC+内存。共同信号是：硬件加速器的「可被研究者编程」拐点已过，论文不再争论「能不能做」，而是争论「做哪些 workload 性价比最高」。

**4. CC、CXL 与生产网关把网络主线倒向 AI**。[[Barre-ATC25|Barre]] 与 [[SwCC-ATC25|SwCC]] 共同把 RDMA CC 重新当成研究问题（前者 AI 集群专用，后者通用软件可编程）；[[FLB-ATC25|FLB]] 把无损 LB 做到 PFC PAUSE -96%；[[Pallas-ATC25|Pallas]] 把 ToR 调度做到 µs；[[DRack-ATC25|DRack]] 用 CXL 把 NIC 解聚。同时 [[KernelBypassTCP-ATC25|KernelBypassTCP]] 与 [[SplitConn-ATC25|SplitConn]] 给社区拉了基础认知 reset：经过十年的 CC 演进，许多 received wisdom 需要重新评估（IX 不再永远赢、PEP 不再过时、BBRv2/v3 行为反转）。这两条路线（前沿 AI 网络 + 基础 CC 重审）在同届 ATC 共存，反映出社区对「网络是否已经过度复杂」的内部反思。

**5. Rust + 形式方法在 OS 阵营产线化交付**。[[Asterinas-ATC25|Asterinas]] 的 Rust framekernel + [[Converos-ATC25|Converos]] 的 PlusCal model checking 是同一作者群体的配套交付：先建立一个完整 OS（Asterinas，driver 全 safe Rust），再用 model checking 工具（Converos）验证它（4 人月找出 20 bug）。[[Rex-ATC25|Rex]] 提出用 safe Rust 替代 eBPF verifier。延续 [[OSDI-2025]] 的 [[Basilisk-OSDI25|Basilisk]]/[[PoWER-OSDI25|PoWER]]/[[Paralegal-OSDI25|Paralegal]] 路线，这条「Rust + verification」的 OS 工程交付路线已经成型，不再是单点研究。

**6. 编译器/工具基础设施的工业化重做**。[[IRHash-ATC25|IRHash]] 在 LLVM IR 后做 hash 比 Ccache 准 1-2 个数量级；[[HEC-ATC25|HEC]] 用 e-graph 验证 100k+ 行 MLIR 重写在 40 分钟内完成；[[ATLAS-ATC25|ATLAS]] 通过 attribute fuzzing 在 GCC/LLVM 找 73 个新 bug；[[Bin2Wrong-ATC25|Bin2Wrong]] 统一反编译器 fuzz 在 4 个开源反编译器找 30 个 bug；[[Koala-ATC25|Koala]] 给 shell 加速器一个完整 benchmark suite。这些工作不是新算法，而是把「工具链工程」当作一等论文产出对待，反映出 ATC 社区对「基础工程严肃化」的接纳度提升。

## 共同观察

- **生产 trace 先于系统优化，且 workload 与合成 benchmark 显著偏离。** [[KVCacheInTheWild-ATC25|KVCacheInTheWild]] 的阿里 trace 显示 ideal hit 仅 54%–62%、P99 lifespan 97s、to-B single-turn 贡献 97% hit；[[Torpor-ATC25|Torpor]] 生产 trace 中 85% 函数 ≤1 次/分钟；[[Katz-ATC25|Katz]] 与 [[DeepServe-ATC25|DeepServe]] 同样以生产形态（adapter 偏斜、PD 分离边界）驱动调度。适用边界：各 trace 仅一周/单厂商；reasoning/agent 新 workload 未覆盖；匿名 token replay 保 pattern 不保 compute 特征。

- **GPU/NPU 从「独占加速器」变成可切片、可晚绑定、可跨模型复用的资源池。** [[Torpor-ATC25|Torpor]] late binding + host memory swap、[[Weaver-ATC25|Weaver]] 跨模型 attention 卸载、[[Toppings-ATC25|Toppings]] CPU/GPU 共担 LoRA、[[GMI-DRL-ATC25|GMI-DRL]] 子 GPU 切分、[[Sirius-ATC25|Sirius]] 推理-训练毫秒级显存交接、[[GPreempt-ATC25|GPreempt]] 通用抢占，共同假设是「多租户/多 workload 混部」已是常态。适用边界：多数实验为 1–4 GPU 或小集群；跨地域 PD disaggregation、百万 QPS 全局调度未系统验证。

- **异构硬件「软件可编程」拐点已过，论文争论点转为 workload 选型与 offload 边界。** [[SwCC-ATC25|SwCC]]/[[Barre-ATC25|Barre]] 把 CC 搬到 NIC 软件、[[Poby-ATC25|Poby]]/[[DShuffle-ATC25|DShuffle]]/[[Snary-ATC25|Snary]] 把容器/Shuffle/检索卸到 DPU/SmartNIC、[[Trochilus-ATC25|Trochilus]]/[[SwitchGNN-ATC25|SwitchGNN]]/[[Pallas-ATC25|Pallas]] 把 Tofino 当通用加速器、[[DRack-ATC25|DRack]]/[[DSA-2LM-ATC25|DSA-2LM]] 用 CXL/DSA 解聚。适用边界：单 NIC 或小 rack 实验为主；PCIe 往返、功耗与运维成本 rarely 量化。

- **fail-slow / silent failure 从「任意 I/O 变慢」收敛到可定位的 fault point。** [[Sieve-ATC25|Sieve]] 锁定 sync/timeout I/O；[[Greyhound-ATC25|Greyhound]] 在 NCCL 路径 hook；[[Hermes-ATC25|Hermes]] 用粗粒度 step time 触发细粒度 profiling；[[CAFault-ATC25|CAFault]] 学 fault-config 依赖。适用边界：[[Sieve-ATC25|Sieve]] 不覆盖 async I/O；[[Greyhound-ATC25|Greyhound]] 需 LD_PRELOAD 侵入；生产 straggler 根因仍高度依赖人工 case study。

- **解聚与 tiering 从存储/DB 扩散到 rack 网络与内存。** [[RCuckoo-ATC25|RCuckoo]]/[[HDTX-ATC25|HDTX]] 假设 100Gbps RDMA 下 RTT/锁竞争成主瓶颈；[[DRack-ATC25|DRack]] 用 CXL 池化 NIC+内存；[[DSA-2LM-ATC25|DSA-2LM]] 用 DSA 卸载页迁移。适用边界：[[RCuckoo-ATC25|RCuckoo]] 强依赖小 value + ConnectX-5 device memory；CXL 3.0 真机平台仍少。

## 互相冲突的假设

- **[[KV-Cache]] 容量：GPU HBM「可能够用」vs 多层/跨设备 offload 必要。** [[KVCacheInTheWild-ATC25|KVCacheInTheWild]] 在 GQA + to-B trace 上认为 2× HBM + LRU 已接近 ideal，ephemeral lifespan 使 LFU 失效；[[Weaver-ATC25|Weaver]] 则假设多 LLM 混部必须 attention 跨 GPU offload 才能提吞吐 +77%。仲裁需要：按模型族（GQA/MHA）、tenant 类型（API/chat）、混部度分别测 ideal hit 与 offload 开销曲线。

- **GPU 绑定时机：late binding 省资源 vs prewarm/fork 省冷启动 vs 毫秒级复用。** [[Torpor-ATC25|Torpor]] 假设 85% 低频函数应 host memory 驻留、按需 swap；[[DeepServe-ATC25|DeepServe]] 假设冷启动瓶颈在 TE 加载，DRAM-hit + NPU-fork 是关键；[[Sirius-ATC25|Sirius]] 假设推理-训练可在 5ms 内交接显存。仲裁需要：同一 serverless trace 上对比 swap/fork/prewarm 的 P99 冷启动、GPU 利用率与内存 footprint 三维权衡。

- **训练通信 overlap：盲目 overlap 有益 vs HBM 带宽争抢反噬。** [[CrossPipe-ATC25|CrossPipe]]/[[Optimus-ATC25|Optimus]]/[[PopFetcher-ATC25|PopFetcher]] 假设跨 DC PP、bubble filling、专家预取应最大化 overlap；[[Hermes-ATC25|Hermes]] 在 Ascend 上观察到 MatMul 与 HCCS DMA 并发可掉 20%–40%。仲裁需要：按算子 memory-bound 程度与互连类型（NVLink/HCCS/RoCE）分档 profiling，而非统一「overlap good」。

- **网络栈选型：kernel TCP 在 bulk 上仍强 vs kernel bypass 在小消息上强 vs 软件 NIC CC 面向 AI。** [[KernelBypassTCP-ATC25|KernelBypassTCP]] 显示 Linux bulk 1.7× IX、IX small msg 5.2× Linux；[[SwCC-ATC25|SwCC]]/[[Barre-ATC25|Barre]] 假设 RoCE AI 集群需要可编程 PCC。仲裁需要：按消息大小分布、CC 算法、是否 lossless DC 联合 benchmark；micro-benchmark 结论不能直接外推到 10K GPU 训练 job。

- **Serverless 隔离粒度：function 级 vs job 级 vs 事务级。** [[BurstComputing-ATC25|BurstComputing]] 假设 burst-parallel analytics 需要 job-level simultaneity；[[Torpor-ATC25|Torpor]]/[[RTSFaaS-ATC25|RTSFaaS]] 在 function/事务粒度做 late binding 与 lease；[[DeepServe-ATC25|DeepServe]] 再抬高到 request-job-task 三层。仲裁需要：按 workload（analytics vs LLM vs 事务）测量 locality、冷启动频率与故障隔离需求，无单一粒度普适。

## 值得关注的方向

### 1. 多模型多租户 LLM serving 的资源调度

**为什么小团队能做**：[[Toppings-ATC25|Toppings]]、[[Weaver-ATC25|Weaver]]、[[Torpor-ATC25|Torpor]]、[[Katz-ATC25|Katz]] 都是单机或小集群（1-4 GPU）实验；workload 用公开数据集（ShareGPT、MS-MARCO 等）即可；核心创新是 scheduler / runtime 而非新模型。

**指向空白的论文**：[[Toppings-ATC25|Toppings]] 只解决 LoRA 冷启动；[[Torpor-ATC25|Torpor]] 只做 model-switching；[[Weaver-ATC25|Weaver]] 仅在 attention 算子层 offload；[[LLMStation-ATC25|LLMStation]] 把 fine-tuning 和 inference 复用但限于 PEFT。三者各自只覆盖一段。

**Open problems**：能否把 Toppings/Torpor/Weaver 三种异构资源复用统一在一个调度器里？跨模型的 [[KV-Cache]] 复用（同 prompt 跨不同 LLM 重用前缀）？Multi-adapter serving 与 multi-model serving 在 SLO 模型上有何不同——能否用统一 priority 模型？

### 2. 生产 KVCache trace 驱动的 cache policy 研究

**为什么小团队能做**：[[KVCacheInTheWild-ATC25|KVCacheInTheWild]] 公开了阿里生产 trace 特征统计；trace replay 实验只需开源 LLM 推理框架（vLLM/SGLang）；不需要拥有大集群，只需读懂 trace。

**指向空白的论文**：[[KVCacheInTheWild-ATC25|KVCacheInTheWild]] 只提了 workload-aware eviction，未触及 prefix tree 共享、RAG 场景、多模型共缓存；现有 prefix-cache 工作（vLLM/SGLang）的 eviction policy 在 to-B 长上下文下基本失效。

**Open problems**：to-B（API 调用）vs to-C（聊天）的 KVCache 复用模式有何根本差异？能否针对 RAG（长 document prefix）专门设计 cache layout？多模型共享同一段前缀缓存的语义正确性如何保证？

### 3. SmartNIC/DPU 上的 CC 与卸载 workload 选型

**为什么小团队能做**：BlueField-2/3 在云上可租；P4 Tofino dev kit 普及；[[SwCC-ATC25|SwCC]]、[[Barre-ATC25|Barre]]、[[Snary-ATC25|Snary]]、[[Poby-ATC25|Poby]]、[[DShuffle-ATC25|DShuffle]] 都是单 NIC 或小集群实验，重点在 workload 拆分而非新硬件。

**指向空白的论文**：[[SwCC-ATC25|SwCC]] 给出了软件 CC 的可行性但未对比与 ASIC 的 power/cost；[[Barre-ATC25|Barre]] 只优化 AI 集群一类 workload；[[Snary-ATC25|Snary]]/[[DShuffle-ATC25|DShuffle]] 只各自做一类应用 offload。

**Open problems**：哪些 workload 卸载到 SmartNIC 是「净收益」、哪些是「PCIe 来回反而更慢」——能否给出量化决策模型？SmartNIC + CXL（[[DRack-ATC25|DRack]]）共同存在时如何分工？SmartNIC 上软件 CC 的可调试性（区别于 ASIC 黑盒）能否用于科研。

### 4. Rust framekernel + model checking 的可移植性

**为什么小团队能做**：[[Asterinas-ATC25|Asterinas]]、[[Converos-ATC25|Converos]]、[[Rex-ATC25|Rex]] 全部开源；4 人月即可在 [[Asterinas-ATC25|Asterinas]] 上找 20 个 bug，单人在小模块上的可重复实验门槛很低。

**指向空白的论文**：[[Converos-ATC25|Converos]] 只验证 Asterinas 的 12 模块；[[Rex-ATC25|Rex]] 只做 eBPF verifier 替代；[[Asterinas-ATC25|Asterinas]] 只展示 driver 的 safe Rust 化但 IO 路径未深入。

**Open problems**：能否把 Converos 工具链应用到 Linux kernel 的 Rust 子系统（rust-for-linux）？Rex 风格的「safe Rust 取代 verifier」能否扩到 BPF 之外的 sandbox（WASM、 [[bpftime-OSDI25|bpftime]]）？framekernel 对 driver-内核交互延迟的影响是否需要 [[KPerfIR-OSDI25|KPerfIR]] 风格 profiling？

### 5. 卫星/空间计算的开源仿真栈

**为什么小团队能做**：[[Rhone-ATC25|Rhone]] 提出单节点 700 卫星仿真器、[[LEOCraft-ATC25|LEOCraft]] 提出星座设计框架——都是工具型工作；[[SpaceExit-ATC25|SpaceExit]] 用 multi-exit DNN 做卫星推理，硬件需求低（嵌入式开发板足够）。

**指向空白的论文**：[[Rhone-ATC25|Rhone]] 只 covers 单节点 emulation；[[LEOCraft-ATC25|LEOCraft]] 只优化拓扑设计；[[SpaceExit-ATC25|SpaceExit]] 只做单星推理调度。

**Open problems**：卫星端 LLM 推理（单 token 数百毫秒功耗预算）的可行边界？跨卫星协同推理（partial offload，类似边缘云分卸载）？卫星 fail-slow 检测（[[Greyhound-ATC25|Greyhound]] 风格）下的 ground-station 协调？

### 6. 编译器 / 工具链 fuzz 与等价性验证的工程化

**为什么小团队能做**：[[ATLAS-ATC25|ATLAS]] 用 GCC/LLVM 公开 attribute spec 即可；[[Bin2Wrong-ATC25|Bin2Wrong]] 在 4 个开源反编译器（Ghidra/IDA/RetDec 等）上做差分；[[HEC-ATC25|HEC]] 基于 e-graph + MLIR 现有生态；[[FPRev-ATC25|FPRev]] 黑盒探测，硬件只需单 GPU。

**指向空白的论文**：[[ATLAS-ATC25|ATLAS]] 只 fuzz 编译器；[[Bin2Wrong-ATC25|Bin2Wrong]] 只 fuzz 反编译器；[[HEC-ATC25|HEC]] 只验证 MLIR；[[IRHash-ATC25|IRHash]] 只优化构建缓存；五者无共享中间层。

**Open problems**：能否用 e-graph 验证 LLVM IR 优化 pass 的等价性（HEC 思路下沉到 IR 层）？把 ATLAS attribute fuzzing 与 [[Bin2Wrong-ATC25|Bin2Wrong]] 差分反编译结合做端到端编译器/反编译器一致性检测？面向 LLM agent 自动生成 kernel（[[AccelOpt]]/[[PIKE]]）的 IR 层正确性验证框架？
