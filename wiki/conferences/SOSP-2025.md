# SOSP 2025

> 66 篇论文把 LLM 系统(推理/训练/编译)、形式化验证、eBPF 可靠性、CXL/SmartNIC 硬件抽象、GPU OS、分布式事务、存储/文件系统并列推向前沿;LLM 相关占约 1/3,形式方法与 eBPF 各出 7 篇形成新主线,硬件异构(CXL/FPGA/SmartNIC/移动 SoC/CHERI)首次在 OS 抽象层集中重写。

## 概览

**LLM 系统研究的重心从 OSDI 的「单点推理加速」扩散到 SOSP 的「全栈生产化」**。推理侧仍有 [[Aegaeon-SOSP25|Aegaeon]]（阿里多模型 GPU 池化省 82% 卡）、[[KTransformers-SOSP25|KTransformers]]（单 A100 跑 DeepSeek-V3 671B）、[[Jenga-SOSP25|Jenga]]（异构 attention 的 KV 管理跑通 Llama 4 10M context）、[[HeteroInfer-SOSP25|HeteroInfer]]（手机 GPU+NPU 并行）,但应用层系统涌现成独立主题:[[Pie-SOSP25|Pie]] 把 serving 拆成 42 个 WebAssembly handler 支持 agent workflow,[[HedraRAG-SOSP25|HedraRAG]]/[[METIS-SOSP25|METIS]] 给 RAG 做 workflow 图级协同优化,[[PrefillOnly-SOSP25|PrefillOnly]]/[[IC-Cache-SOSP25|IC-Cache]] 瞄准推荐和 P/D 分离等新负载。训练侧 [[ByteRobust-SOSP25|ByteRobust]]（字节 9600 GPU 三月 97% ETTR）、[[Sailor-SOSP25|Sailor]]（异构/跨 zone 自动规划）、[[Mycroft-SOSP25|Mycroft]]（NCCL 依赖追踪）、[[TrainVerify-SOSP25|TrainVerify]]（Llama3 405B 并行计划等价性验证）共同构成「LLM 训练可靠性」栈。

**形式化验证走出「专家玩具」成为 OS 研究通用工具**。[[Atmosphere-SOSP25|Atmosphere]] 用 Rust + Verus 在 **1.5 人年**内验证完整 mixed-criticality 微内核、验证 <20 秒,[[TickTock-SOSP25|TickTock]] 用 refinement-type verifier Flux 给生产嵌入式 OS Tock 验证进程隔离(30 秒验证),[[AutoMan-SOSP25|AutoMan]] 用 Dafny refinement-based 工作流把 Multi-Paxos/PBFT 手写工作量降 70-97%,[[KNighter-SOSP25|KNighter]] 反而让 LLM 去合成 Clang 静态分析器从 Linux 挖 92 个 4.3 年潜伏漏洞,[[Miralis-SOSP25|Miralis]] 用 Kani 符号执行验证 RISC-V 虚拟固件监控器。趋势是「verifier 成熟到能写产品代码」,与 [[OSDI-2025]] 的 [[Basilisk-OSDI25|Basilisk]]/[[PoWER-OSDI25|PoWER]] 路线并行。

**eBPF 扩展从「加速打补丁」变成「可靠性一等公民」**。[[BCF-SOSP25|BCF]] 用 proof-guided abstraction refinement 让 verifier 接受 78.7% 过去被误拒的真实程序,[[Veritas-SOSP25|Veritas]] 用 specification-based oracle 做差分 fuzzing 挖 verifier 15 个 bug(含提权),[[cache_ext-SOSP25|cache_ext]] 让 eBPF 改写 Linux page cache 淘汰策略,[[FlexGuard-SOSP25|FlexGuard]] 用 sched_switch hook 做精确 lock preemption 检测,[[Loom-SOSP25|Loom]]/[[NEX-DSim-SOSP25|NEX-DSim]] 用 eBPF 做高频遥测和加速器模拟时钟同步。共出 6-7 篇直接使用或针对 [[eBPF]] 的论文,和 OSDI 2024 的 [[bpftime-OSDI25|bpftime]] 一起,标志 eBPF 成为继 KVM 之后最密集的内核扩展研究阵地。

**硬件异构性首次在 OS 抽象层集中重写**。[[CXL]] 侧有 [[Oasis-SOSP25|Oasis]]（CXL 内存池做 PCIe 设备池化）、[[Demeter-SOSP25|Demeter]]（CXL tiered memory guest 代理）;SmartNIC 有 [[TaiChi-SOSP25|TaiChi]]（阿里 DP/CP 资源融合、生产 3 年）;RDMA 有 [[RDMA-LiveMigration-SOSP25|RDMA-LiveMigration]]（NVIDIA CX-7 首个亚秒级 live migration）、[[Mage-SOSP25|Mage]]（解决 far memory 多核扩展性崩塌）、[[Spirit-SOSP25|Spirit]]（拍卖机制做 remote memory 公平分配）;FPGA 有 [[Coyote-v2-SOSP25|Coyote-v2]]（三层 shell、10 行 Python 部署 NN）;移动 SoC 有 [[HeteroInfer-SOSP25|HeteroInfer]];CHERI/capability 硬件有 [[CHERIoT-RTOS-SOSP25|CHERIoT-RTOS]]/[[uFork-SOSP25|μFork]]。硬件多样性倒逼「一级 OS 服务」重构——而不是在老 OS 上加补丁。

**与往届对比**:SOSP 2025 LLM 篇数显著超 [[OSDI-2025]]（~25 vs ~15）,且向「生产可靠性(ByteRobust、Mycroft、TrainVerify)+ 应用层抽象(Pie、HedraRAG、METIS)」倾斜;形式化论文体量相当,但「研究型 verifier」转向「工程化 verifier」;eBPF 密度继续上升;不再有专门的 serverless 大类(仅 [[Dandelion-SOSP25|Dandelion]]/[[Quilt-SOSP25|Quilt]] 两篇),取而代之的是 edge([[Radical-SOSP25|Radical]])、恢复([[PHOENIX-SOSP25|PHOENIX]])、overload control([[Atropos-SOSP25|Atropos]])等「弹性系统」细分方向。这届 SOSP 的气质:LLM 支撑骨架、形式方法当钢筋、eBPF 做内饰、异构硬件拉起新楼。

## 研究趋势

**1. LLM 系统的「应用层抽象」开始浮出水面**。SOSP 2025 LLM 论文不再只盯着 serving 吞吐,而是针对新 workload 重新定义接口和抽象层:[[Pie-SOSP25|Pie]] 用 WebAssembly inferlet 让用户程序编排 42 个 handler,天然支持 agentic workflow 吞吐 1.3-3.4×;[[HedraRAG-SOSP25|HedraRAG]] 用 RAGraph 统一刻画多样 RAG 流程并做子图级调度;[[METIS-SOSP25|METIS]] 按 query 自适应调 RAG 配置;[[PrefillOnly-SOSP25|PrefillOnly]] 针对推荐/P-D 分离 prefill 节点这一新负载设计专门引擎。和 OSDI 2025 NanoFlow/BlitzScale 那种「把 vLLM 再压一截」的路数对照——SOSP 这届的气味更像「LLM 开始长出生态」,推理 runtime 的上一层(编排、RAG、agent)成为研究对象。

**2. 生产化 LLM 训练可靠性形成完整栈**。[[ByteRobust-SOSP25|ByteRobust]] 在字节 9600 GPU 三月训练上把 ETTR 做到 97%;[[Mycroft-SOSP25|Mycroft]] 用 NCCL 侧追踪在 20 秒内定位 root cause GPU;[[TrainVerify-SOSP25|TrainVerify]] 把 Llama3 405B、DeepSeek-V3 671B 的并行化计划在训练前形式化验证,消灭「跑几周才发现 loss scale 错」这类 silent bug;[[Sailor-SOSP25|Sailor]] 把异构+跨 zone 自动规划做到 <1 秒;[[DCP-SOSP25|DCP]] 在长上下文训练里按 hypergraph partitioning 动态分配 attention block。四篇合起来正好组成「规划 → 运行 → 故障定位 → 等价验证」的训练可靠性闭环——这是上届 OSDI 只零散出现([[SMon-OSDI25|SMon]] 等)、此届 SOSP 第一次集中成型的工作流。

**3. 形式化验证从「研究项目」变成「工程交付」**。三年前 IronFleet 需要数人年才能验证 Multi-Paxos;今年 [[Atmosphere-SOSP25|Atmosphere]] 1.5 人年验证完整微内核、证明 <20 秒,[[TickTock-SOSP25|TickTock]] 30 秒内验证生产嵌入式 OS Tock 的进程隔离,[[AutoMan-SOSP25|AutoMan]] 让 Multi-Paxos/PBFT 手写量降 70-97%,[[TrainVerify-SOSP25|TrainVerify]] 把分布式训练的并行等价性验证做成「训练前跑一下」的 CI 步骤。关键变化是 SMT-based verifier(Verus/Kani/Flux/Dafny)对「真实低层代码 + 并发」具备实用性,配合 LLM 合成(如 [[KNighter-SOSP25|KNighter]] 让 LLM 写 Clang Checker、从 Linux 挖 92 个漏洞),形式方法开始进入工程团队的工具箱,而不只是定理证明实验室。

**4. eBPF 成为「最密集的内核扩展研究阵地」**。一届 SOSP 里 7 篇直接用或针对 [[eBPF]] 的论文:[[BCF-SOSP25|BCF]] 把 verifier 证明 offload 到用户态 SMT,[[Veritas-SOSP25|Veritas]] 用 specification-based oracle fuzzing 挖 verifier 漏洞,[[cache_ext-SOSP25|cache_ext]] 让应用用 eBPF 定义 page cache 淘汰策略(类 sched_ext),[[FlexGuard-SOSP25|FlexGuard]] 用 sched_switch hook 做 lock preemption 检测,[[Loom-SOSP25|Loom]]/[[NEX-DSim-SOSP25|NEX-DSim]] 分别在遥测和加速器模拟时钟同步里用到 eBPF。和 [[OSDI-2025]] 的 [[bpftime-OSDI25|bpftime]] 一起,eBPF 研究已经从「加速路径」扩展到「Verifier 理论→安全 fuzzing→资源策略→调度→遥测」的多条主线——接过了十年前 KVM 在 OS 社区的位置。

**5. 硬件异构性正在「OS 抽象层」集中重写**。[[CXL]] 侧 [[Oasis-SOSP25|Oasis]] 用内存池做跨主机 PCIe 设备共享、[[Demeter-SOSP25|Demeter]] 做 guest-delegated tiered memory;[[RDMA]] 侧 [[RDMA-LiveMigration-SOSP25|RDMA-LiveMigration]] 首个亚秒级 device live migration、[[Mage-SOSP25|Mage]] 解决多核下 far memory 扩展性崩塌、[[Spirit-SOSP25|Spirit]] 用拍卖做公平分配;SmartNIC 侧 [[TaiChi-SOSP25|TaiChi]] 让 CP/DP 共享 CPU 且生产 3 年;FPGA 侧 [[Coyote-v2-SOSP25|Coyote-v2]] 三层 shell 做到 10 行 Python 部署 NN;CHERI 侧 [[CHERIoT-RTOS-SOSP25|CHERIoT-RTOS]] 和 [[uFork-SOSP25|μFork]] 开始在低端 MCU 和单地址空间 OS 上落地硬件能力。和 OSDI 2025 的 [[Tigon-OSDI25|Tigon]]、[[SoarAlto-OSDI25|SoarAlto]]、[[EMT-OSDI25|EMT]] 平行——两届共同信号:数据中心硬件范式已经从「CPU+DRAM+TCP」20 年惯性迁到「池化内存 + SmartNIC + capability 硬件 + CXL switch」,OS 首次大范围重写抽象层。

**6. 「弹性 / 恢复 / overload」取代「serverless」成为新显学**。过去几届 SOSP 都有 5-8 篇 serverless,这届仅 [[Dandelion-SOSP25|Dandelion]]/[[Quilt-SOSP25|Quilt]] 两篇,但出现了 [[PHOENIX-SOSP25|PHOENIX]]（optimistic recovery,85.6% 故障走亚秒 fast path）、[[Atropos-SOSP25|Atropos]]（选择性 cancel 元凶请求而非受害者）、[[Orthrus-SOSP25|Orthrus]]（data path 异步跨核重执行检测 silent data corruption 2-6% 开销）、[[Radical-SOSP25|Radical]]（强一致应用跑 edge 仍 Linearizable）、[[Sandman-SOSP25|Sandman]]（SPDK 能耗降 33% 性能差 ≤5%）这批「运行时弹性」工作。共同信号是:研究重心从「冷启动快」迁到「生产级 SLO + 故障时的优雅降级」,和前面讲的「LLM 训练可靠性栈」一起,都在说 silent failure 和部分故障已经是系统研究的一等问题。

## 共同观察

**1. 生产 trace 已成为系统论文的默认动机来源,而非合成 benchmark。** [[ByteRobust-SOSP25|ByteRobust]]（字节 9600 GPU 三月 ETTR）、[[Mycroft-SOSP25|Mycroft]]（NCCL 生产 6 月 trace）、[[LithOS-SOSP25|LithOS]]（Meta inference GPU 利用率 <30%）、[[Aegaeon-SOSP25|Aegaeon]]（阿里模型市场 94.1% 模型仅 1.35% 请求）、[[TaiChi-SOSP25|TaiChi]]（阿里 SmartNIC 3 年生产）、[[Mantle-SOSP25|Mantle]]（百度 COSS 100 亿对象）都把「fleet 实测分布」写进隐含假设。**适用边界**:公开 trace 稀缺时第三方只能验证机制,不能复现绝对数字;trace 窗口(3 月/6 月)对长尾故障和 regime shift 的覆盖有限。

**2. LLM 系统的瓶颈从「算力」系统性迁移到「KV / 内存 / 调度形态」。** 推理侧 [[Jenga-SOSP25|Jenga]]/[[DiffKV-SOSP25|DiffKV]]/[[KTransformers-SOSP25|KTransformers]] 假设 KV 形态与压缩策略决定能否跑 10M context 或 671B 单卡;服务侧 [[Aegaeon-SOSP25|Aegaeon]]/[[PrefillOnly-SOSP25|PrefillOnly]]/[[IC-Cache-SOSP25|IC-Cache]] 分别针对多模型池化、prefill-only、历史示例路由做专门引擎;训练侧 [[DCP-SOSP25|DCP]]/[[TrainVerify-SOSP25|TrainVerify]] 把 context parallelism 与并行计划正确性当一等公民。**适用边界**:短序列、KV 充裕、compute-bound 的 workload(如 [[PrefillOnly-SOSP25|PrefillOnly]] 自己承认的 general path)上,这些优化的边际收益会急剧缩小。

**3. 形式化与 fuzzing 正在形成「证明 + 差分 oracle」双轨,把 silent bug 从事后审计变成设计期约束。** [[Atmosphere-SOSP25|Atmosphere]]/[[TickTock-SOSP25|TickTock]]/[[AutoMan-SOSP25|AutoMan]] 用 Verus/Flux/Dafny 把验证压到秒级;[[BCF-SOSP25|BCF]]/[[Veritas-SOSP25|Veritas]] 针对 [[eBPF]] verifier 本身做证明与 fuzzing;[[TrainVerify-SOSP25|TrainVerify]]/[[KNighter-SOSP25|KNighter]] 分别验证训练计划等价性与用 LLM 合成静态分析器挖 Linux 漏洞;[[Fawkes-SOSP25|Fawkes]]/[[Orthrus-SOSP25|Orthrus]] 把 silent corruption 检测推进到 DBMS 与 data path。**适用边界**:需要人类主观判断、wet-lab 或 simulator 与生产严重失真的领域,形式化收益仍有限;LLM 合成 checker([[KNighter-SOSP25|KNighter]]) 的 false positive 率与维护成本未充分量化。

**4. 硬件异构倒逼 OS 在「设备池化 / 远程内存 / capability」层重写抽象,而不是继续给 Linux 打补丁。** [[Oasis-SOSP25|Oasis]]/[[Demeter-SOSP25|Demeter]] 处理 CXL 设备与 tiered memory;[[RDMA-LiveMigration-SOSP25|RDMA-LiveMigration]]/[[Mage-SOSP25|Mage]]/[[Spirit-SOSP25|Spirit]] 处理 far memory 的迁移、扩展性与公平性;[[TaiChi-SOSP25|TaiChi]]/[[Coyote-v2-SOSP25|Coyote-v2]] 处理 SmartNIC/FPGA 动态服务;[[CHERIoT-RTOS-SOSP25|CHERIoT-RTOS]]/[[uFork-SOSP25|μFork]] 把 capability 硬件落到嵌入式与单地址空间 OS。**适用边界**:单租户、HBM 充裕、无跨主机共享需求的部署,这些抽象的复杂度和运维成本可能超过收益。

**5. 「弹性」研究从冷启动优化转向 partial failure、overload 与 optimistic recovery 的 SLO 保持。** [[PHOENIX-SOSP25|PHOENIX]] 选择性保留长期状态做亚秒恢复;[[Atropos-SOSP25|Atropos]] 在 overload 时 cancel 元凶而非受害者;[[Orthrus-SOSP25|Orthrus]] 用 2-6% 开销检测 silent data corruption;[[Radical-SOSP25|Radical]] 在 edge 仍保持 linearizability;[[Sandman-SOSP25|Sandman]] 在 SPDK 上平衡能耗与性能。**适用边界**:需要强 crash-stop 语义或严格 exactly-once 的应用,optimistic recovery 的 fast path 与 slow path 切换边界需额外验证。

## 互相冲突的假设

**1. 多模型 GPU 池化 vs 单模型极限 offload:共享 GPU 还是掏空单卡?** [[Aegaeon-SOSP25|Aegaeon]] 假设长尾模型市场下 token-level 抢占可把 7 模型/GPU 做到生产可行,且 HOL blocking 是主要敌人;[[KTransformers-SOSP25|KTransformers]] 则假设单请求跑 671B 时 CPU/AMX offload + Expert Deferral 比多模型 multiplexing 更关键,且 GPU 应尽可能留给热 expert。**仲裁测量**:同一硬件预算下,marketplace skew(模型数 × 请求稀疏度) vs 单模型超大推理的 TTFT/TBT/P99 曲线;以及 KV swap 带宽是否成为两者共同瓶颈。

**2. Prefill 专门化 vs 通用 serving:KV 能否只保留一层?** [[PrefillOnly-SOSP25|PrefillOnly]] 假设 prefill-only 负载(推荐、P/D 分离 prefill 节点)只需一层 KV + shortest-prefill-first 即可 4× QPS;[[Jenga-SOSP25|Jenga]]/[[DiffKV-SOSP25|DiffKV]] 假设异构 attention 与多维 KV 压缩是 10M context 的必要条件;[[Pie-SOSP25|Pie]] 又把 serving 拆成 42 个 handler 需要跨调用状态。**仲裁测量**:在真实 trace 上统计 prefill-only 占比、单 token 输出比例、以及 hybrid workload 下专用引擎相对 general path 的 P99 回退幅度。

**3. eBPF verifier 应该更宽松还是更严格?** [[BCF-SOSP25|BCF]] 用 proof-guided abstraction refinement 让 78.7% 过去被误拒的真实程序通过,隐含假设是「当前 verifier 过保守」;[[Veritas-SOSP25|Veritas]] 用 specification-based oracle fuzzing 在 verifier 里挖出 15 个 bug(含提权),隐含假设是「现有 verifier 仍有过宽/错误路径」。**仲裁测量**:对同一 eBPF 程序集合,统计 BCF 接受而 Veritas 报漏洞的比例;以及 sched_ext/cache_ext 类生产策略在更宽松 verifier 下的 privilege escalation 回归测试。

**4. Far memory 应该 always-async 还是 auction-fair?** [[Mage-SOSP25|Mage]] 假设 always-async decoupling + cross-batch pipelining 是多核 far memory 扩展性的关键,愿意牺牲部分同步语义换吞吐;[[Spirit-SOSP25|Spirit]] 假设 remote memory 的 cache 与带宽是 interdependent 资源,需要 140ms 收敛的拍卖机制才能保证公平,否则多核扩展性崩塌。**仲裁测量**:memcached/Redis batch workload 上 P99 vs 平均吞吐 vs 跨核公平性(每核带宽方差)三维权衡曲线。

**5. GPU OS 细粒度调度 vs 框架侧 right-sizing:谁该拥有 TPC?** [[LithOS-SOSP25|LithOS]] 假设 TPC 粒度 kernel atomization + stealing 是 inference stacking 尾延迟 13× 改善的根因,且需 OS 级透明拦截;[[Aegaeon-SOSP25|Aegaeon]]/[[ByteRobust-SOSP25|ByteRobust]] 则在框架/引擎层做 token-level scaling 与容错,假设不改 driver 也能获得生产收益。**仲裁测量**:同一 LLM trace 上 LithOS vs engine-only scheduling 的 tail latency 分解(SM occupancy vs queueing vs KV swap);以及 exotic CUDA kernel 在 LibLithOS 下的覆盖率与 fallback 率。

**6. 形式化验证的 ROI:手写证明 vs LLM 合成 checker?** [[Atmosphere-SOSP25|Atmosphere]]/[[TickTock-SOSP25|TickTock]] 假设 Verus/Flux 已成熟到 1.5 人年可验证完整微内核/生产嵌入式 OS;[[KNighter-SOSP25|KNighter]] 假设从 Linux patch 历史合成 Clang checker 更划算,且能挖 4.3 年平均潜伏漏洞。**仲裁测量**:同一子系统(如 Linux MM 或驱动)上,证明行数/人月/检出 CVE 数/误报率四象限对比;以及 verifier CI 集成后的 merge latency。

## 值得关注的方向

### 1. LLM 应用层抽象的标准化

**为什么小团队能做**:[[Pie-SOSP25|Pie]] 的 inferlet(WebAssembly)、[[HedraRAG-SOSP25|HedraRAG]] 的 RAGraph、[[METIS-SOSP25|METIS]] 的 config adaptation 都是软件层工作,单机或小规模集群即可跑通;开源 vLLM/SGLang 够做 baseline。

**指向空白的论文**:[[Pie-SOSP25|Pie]] 只支持单主机 handler 编排未做跨主机;[[HedraRAG-SOSP25|HedraRAG]] 专注 RAG 未覆盖 agent workflow;[[METIS-SOSP25|METIS]] 只做 RAG 配置未扩展到 agent/prompt chaining;agentic workflow 仍缺统一 IR。

**Open problems**:能否把 Pie 的 inferlet 模型与 HedraRAG 的 RAGraph 统一为跨主机 LLM workflow IR?能否给 agent 的 tool-call/planning/memory 三段式流水建立类似 [[Mercury-SOSP25|Mercury]] 那样的「通信 first-class」IR?如果 LLM 服务逻辑可编程,能否给这些 user handler 做形式化验证(类 [[TrainVerify-SOSP25|TrainVerify]])?

### 2. 生产级 LLM 训练故障诊断扩展到新硬件

**为什么小团队能做**:[[Mycroft-SOSP25|Mycroft]] 只用 NCCL 侧的轻量 instrumentation,核心工作是 trace 分析与 heuristic 设计;[[TrainVerify-SOSP25|TrainVerify]] 只需训练计划 DFG 的 symbolic 版本;二者都不需要真开大规模训练。

**指向空白的论文**:[[Mycroft-SOSP25|Mycroft]] 专注 NCCL 未覆盖 RCCL/HCCL/oneCCL;[[TrainVerify-SOSP25|TrainVerify]] 只做 dense transformer 未覆盖 MoE 路由正确性;[[ByteRobust-SOSP25|ByteRobust]] 的 ETTR 指标未区分不同硬件故障模式。

**Open problems**:能否把 Mycroft 的 CCL 追踪移植到 AMD MI300/Huawei Ascend 集群?[[MoE]] 模型的 expert routing 正确性能否用 TrainVerify 风格等价性验证?能否把 [[SMon-OSDI25|SMon]] 的 what-if straggler 分析与 Mycroft 的 chunk-level 依赖结合做端到端根因定位?

### 3. eBPF-style「可编程策略」扩展到 OS 其它子系统

**为什么小团队能做**:[[cache_ext-SOSP25|cache_ext]] 和 [[FlexGuard-SOSP25|FlexGuard]] 都是单机 Linux 内核工作,参考 sched_ext 模板;不需要新硬件;用户态 SMT/fuzzer 开源(Z3、libfuzzer)。

**指向空白的论文**:[[cache_ext-SOSP25|cache_ext]] 只覆盖 page cache;[[FlexGuard-SOSP25|FlexGuard]] 只用 sched_switch 未扩展到其它 hook;[[BCF-SOSP25|BCF]]/[[Veritas-SOSP25|Veritas]] 都只针对 verifier 自身。

**Open problems**:能否把「ext」模式做到 block layer IO scheduler、TCP congestion control、swap policy?能否给 CXL tiered memory(结合 [[Demeter-SOSP25|Demeter]])做 mem_ext——让 guest VM 用 eBPF 定义 promotion 策略?能否用 Veritas 的 spec-based oracle 给应用自定义 eBPF 程序做差分验证?

### 4. 形式化验证的「CI 化」路径

**为什么小团队能做**:[[Atmosphere-SOSP25|Atmosphere]]/[[TickTock-SOSP25|TickTock]] 开源,Verus/Flux/Kani 工具链可用;[[KNighter-SOSP25|KNighter]] 用 GPT-4 + 历史 patch 合成 checker,无需自建模型;单个研究者 1-2 月能复现小规模案例。

**指向空白的论文**:[[Atmosphere-SOSP25|Atmosphere]] 只验证微内核 core 未做驱动;[[TickTock-SOSP25|TickTock]] 仅针对 MPU 隔离;[[KNighter-SOSP25|KNighter]] 从 patch 学习但未做增量(每次新 patch 就重训);形式化工具之间缺少统一 CI 接口。

**Open problems**:能否把 Atmosphere 的验证模式扩到 Rust-for-Linux(Android Binder?);能否把 KNighter 的 patch→checker 合成工具化成 GitHub Action,每次 merge 就自动生成新规则?能否用 [[pKVM-GhostShell-SOSP25|pKVM-GhostShell]] 的可执行 spec 模式写「runtime check」替代部分 unit test,在生产长期对照?

### 5. CXL / 远程内存「工作负载特定的公平与调度」

**为什么小团队能做**:[[Spirit-SOSP25|Spirit]] 的拍卖算法只需 perf 和 swap trace,AMD EPYC + 商用 CXL 卡云上可租;[[Demeter-SOSP25|Demeter]] 的 guest 代理完全软件;[[Mage-SOSP25|Mage]]/[[Oasis-SOSP25|Oasis]] 开源工具基础上扩新 workload 即可。

**指向空白的论文**:[[Spirit-SOSP25|Spirit]] 只做 cache+bandwidth,未纳入 TLB shootdown;[[Demeter-SOSP25|Demeter]] 只解决 guest 代理未做跨租户 QoS;[[Mage-SOSP25|Mage]] 的三原则未形式化、扩到其它 LibOS 未验证。

**Open problems**:能否给 LLM serving 专门做 CXL tiering——按 [[KV-Cache]] attention head 的 reuse 频率分配到 HBM/CXL/DRAM?能否把 Spirit 拍卖扩展到多 tenant KV cache 分配(如 [[Aegaeon-SOSP25|Aegaeon]] 的多模型)?CXL pod 内 fault domain 能否用 [[AutoMan-SOSP25|AutoMan]]/[[Basilisk-OSDI25|Basilisk]] 风格自动验证?

### 6. SmartNIC / FPGA / RDMA「服务抽象」的开源普及

**为什么小团队能做**:[[Coyote-v2-SOSP25|Coyote-v2]] 是开源 shell,10 行 Python 即能跑 NN 推理;[[RDMA-LiveMigration-SOSP25|RDMA-LiveMigration]] 虽是 NVIDIA 硬件但基础模式(device-assisted + guest-transparent)可软件模拟;[[TaiChi-SOSP25|TaiChi]] 的 hybrid 虚拟化可在 DPU 模拟器上复现。

**指向空白的论文**:[[Coyote-v2-SOSP25|Coyote-v2]] 只覆盖 FPGA + AFU 模式未做 ASIC/ACAP;[[RDMA-LiveMigration-SOSP25|RDMA-LiveMigration]] 只针对 ConnectX-7 未跨厂商;[[TaiChi-SOSP25|TaiChi]] 只做调度未做安全隔离。

**Open problems**:能否把 Coyote 三层 shell 思路搬到 DPU(BlueField/Pensando)做统一 service 抽象?能否让 FPGA / SmartNIC 的动态 service 加载过程做 `[[PhoenixOS-SOSP25|PhoenixOS]]` 风格 C/R?SmartNIC 上的 hybrid virtualization 能否用 [[Miralis-SOSP25|Miralis]] 式 VFM 做形式化 firmware 管理?

### 7. Silent failure 与运行时正确性检测跨场景复用

**为什么小团队能做**:[[Orthrus-SOSP25|Orthrus]] 只需 LLVM pass + 多核重执行;[[PHOENIX-SOSP25|PHOENIX]] 只改运行时 state 划分;[[Atropos-SOSP25|Atropos]] 只需改 76% 应用已有的 cancel 路径——三者单机即可实验。

**指向空白的论文**:[[Orthrus-SOSP25|Orthrus]] 只覆盖 data path(未覆盖 control path);[[PHOENIX-SOSP25|PHOENIX]] 针对 crash 恢复未做 silent 故障;[[Atropos-SOSP25|Atropos]] 需手动识别 cancel initiator,尚无自动化工具;[[Fawkes-SOSP25|Fawkes]] 只针对 DBMS 持久化未扩展到 KV。

**Open problems**:能否把 Orthrus 的 versioned-memory 思路用到 LLM 推理的 KV cache 上做 per-token silent corruption 检测(连接 [[TrainCheck-OSDI25|TrainCheck]] 训练端与 Orthrus 推理端)?能否把 [[PHOENIX-SOSP25|PHOENIX]] 的「state 可恢复分类」自动化——用 LLM 或静态分析区分 long-lived vs transient?能否把 Atropos 的 cancel initiator 自动发现器做成通用工具应用到数据库/分布式 KV?
